The browser hits `GET /file/users/:identifier/avatar`, which is routed to the file server. Here is each hop from HTTP handler to stored data:

1. `serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (HTTP handler registered at line 124)
2. `getUserByUsername` — `server/router/fileserver/fileserver.go:715` (resolves the `:identifier` param to a user; called at line 185)
3. `Store.GetUser` — `store/user.go:148` (store-layer lookup; called by `getUserByUsername`)
4. `Store.ListUsers` — `store/user.go:136` (called by `GetUser` at line 158)
5. `Driver.ListUsers` — `store/driver.go:47` (driver interface; `ListUsers` delegates to the concrete driver at line 137, e.g. `store/db/sqlite/user.go:88`)

The avatar data itself is stored as a base64 data URI in the user's `AvatarURL` field, so no further storage hop is needed — `serveUserAvatar` calls `parseDataURI` (`server/router/fileserver/fileserver.go:737`, at line 196) to decode the inline data and serves it directly via `c.Blob`.
