The browser hits `GET /file/users/:identifier/avatar`. Here is each hop from HTTP handler to data layer:

1. `serveUserAvatar` — `server/router/fileserver/fileserver.go:167` (HTTP handler, registered at line 124)
2. `getUserByUsername` — `server/router/fileserver/fileserver.go:715` (resolves the `:identifier` param to a `store.User`)
3. `Store.GetUser` — `store/user.go:148` (store-layer lookup; checks user cache, then delegates to `ListUsers`)
4. `Store.ListUsers` — `store/user.go:136` (calls through to the driver interface)
5. `Driver.ListUsers` (interface) — `store/driver.go:47` (the `Driver` interface method)
6. `DB.ListUsers` (SQLite impl) — `store/db/sqlite/user.go:88` (executes the SQL query against the `user` table, which holds `avatar_url`)

The avatar data itself is stored inline as a data URI in the user's `avatar_url` column. Back in `serveUserAvatar`, the handler calls `parseDataURI` (`server/router/fileserver/fileserver.go:737`) to decode the base64-encoded image from `user.AvatarURL` and serves the bytes directly — no additional storage hop is needed.
