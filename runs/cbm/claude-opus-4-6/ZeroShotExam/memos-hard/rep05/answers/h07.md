The browser hits `GET /file/users/:identifier/avatar`. Here is each hop from handler to stored data:

1. `serveUserAvatar` — `server/router/fileserver/fileserver.go:168`
2. `getUserByUsername` — `server/router/fileserver/fileserver.go:715` (calls `s.Store.GetUser` with a `FindUser{Username: &identifier}`)
3. `(*Store).GetUser` — `store/user.go:148` (checks user cache, then delegates to `ListUsers`)
4. `(*Store).ListUsers` — `store/user.go:136` (calls `s.driver.ListUsers`)
5. `Driver.ListUsers` (interface) — `store/driver.go:47` (dispatches to the concrete DB driver)
6. `(*DB).ListUsers` — `store/db/sqlite/user.go:88` (builds a `SELECT … FROM user WHERE username = ?` query, scans `avatar_url` column into `User.AvatarURL`)
7. `parseDataURI` — `server/router/fileserver/fileserver.go:737` (back in the handler: decodes the `data:image/…;base64,…` string from `User.AvatarURL` into raw bytes, which are returned via `c.Blob`)

The avatar is stored inline in the `user` table's `avatar_url` column as a base64 data URI. There is no separate file/blob storage hop — `serveUserAvatar` reads it from the user row and decodes it in-process.
