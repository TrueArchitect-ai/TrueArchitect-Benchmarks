The premise is incorrect: there is no Redis connection in this repository. The cache layer is a **pure in-memory Go cache**, not backed by Redis or any external store.

The cache implementation lives in `store/cache/cache.go`, which defines a `Cache` struct built on Go's `sync.Map` with TTL-based expiration and a background cleanup goroutine. It has no Redis dependency — `grep` for "redis" across the entire repo returns zero results, and `go.mod` contains no Redis client library.

The user cache is configured in `store/store.go:38-45`, where `New()` constructs a `cache.Config` with:

- **`DefaultTTL`: 10 minutes** (`10 * time.Minute`)
- `CleanupInterval`: 5 minutes
- `MaxItems`: 1000

This same config is applied uniformly to all three caches (`instanceSettingCache`, `userCache`, `userSettingCache`) at `store/store.go:51-53`. User entries are cached on every create, update, list, and get operation (`store/user.go:98`, `:122`, `:143-144`, `:167`) using `s.userCache.Set(ctx, userCacheKey(user.ID), user)`, which delegates to the default 10-minute TTL (`store/cache/cache.go:93-95`). Entries expire either when the TTL elapses (checked lazily on read at `cache.go:135` and proactively by the cleanup goroutine at `cache.go:227`) or when the item count exceeds 1000, triggering eviction of the oldest 20% (`cache.go:253-313`).
