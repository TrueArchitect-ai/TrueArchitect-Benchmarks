The premise is incorrect — webhook delivery workers consume from **neither NATS nor RabbitMQ**. There is no external message broker involved at all.

The actual mechanism is a **plain Go buffered channel** used as an in-process async queue. It is declared in `internal/webhook/webhook.go:39`:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

Four goroutine workers are spawned in the `init()` function of the same file (`internal/webhook/webhook.go:42–55`) to drain this channel. Each worker loops over `range asyncPostQueue`, calling `Post()` to make a synchronous HTTP request for each payload it receives.

Webhook payloads are enqueued via `PostAsync()` (`internal/webhook/webhook.go:184–196`), which does a non-blocking send into the channel (dropping the payload with a warning log if the 128-slot buffer is full). The callers — such as `DispatchMemoCreatedWebhook` and related methods in `server/router/api/v1/memo_service_webhooks.go` — invoke `webhook.PostAsync(payload)` directly in the request path.

In short: this is a simple in-memory fan-out with no external broker, no durable queue, and no retry mechanism beyond the initial HTTP call.
