By explicit Go code; reactions are removed in two ways within the same transaction.

**Mechanism:** Explicit Go code deletes reactions in `deleteUserTargetsTx()` via two separate SQL DELETE statements inside the user-deletion transaction — there are no database-level CASCADE rules involved.

**Evidence locations:**

1. **`store/db/sqlite/user_delete.go:92-103`** — `deleteUserTargetsTx` calls both:
   - `deleteReactionsByContentIDsTx` (line 96) — deletes reactions on the user's memos (by `content_id`)
   - `deleteReactionsByCreatorTx` (line 102) — deletes reactions the user themselves created (by `creator_id`)

2. **`store/db/sqlite/user_delete.go:380-388`** — `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` in batches, removing all reactions left on the deleted user's memos.

3. **`store/db/sqlite/user_delete.go:400-403`** — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`, removing all reactions the deleted user placed on any memo.

4. **`store/migration/sqlite/LATEST.sql:92-98`**, **`store/migration/postgres/LATEST.sql:91-97`**, **`store/migration/mysql/LATEST.sql:91-97`** — The `reaction` table schema has no `FOREIGN KEY` or `ON DELETE CASCADE` constraints on `creator_id` or `content_id` in any of the three database backends, confirming there is no database-level rule.

The same pattern exists in the Postgres (`store/db/postgres/user_delete.go`) and MySQL (`store/db/mysql/user_delete.go`) drivers.
