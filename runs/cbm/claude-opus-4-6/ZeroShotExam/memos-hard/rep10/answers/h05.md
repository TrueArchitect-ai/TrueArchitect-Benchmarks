**By explicit Go code**; reactions are removed via two dedicated functions in the user-deletion transaction — there are no database-level foreign keys or CASCADE rules on the `reaction` table.

**Evidence:**

1. **`store/db/sqlite/user_delete.go:92-104`** — `deleteUserTargetsTx` explicitly calls two reaction-deletion functions:
   - Line 96: `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — deletes all reactions on the user's memos (by content ID)
   - Line 102: `deleteReactionsByCreatorTx(ctx, tx, userID)` — deletes all reactions the user themselves created on any memo

2. **`store/db/sqlite/user_delete.go:380-388`** — `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` in batches.

3. **`store/db/sqlite/user_delete.go:400-403`** — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`.

4. **No database CASCADE** — The `reaction` table schema (e.g. `store/migration/sqlite/LATEST.sql:92-98`, same for postgres at lines 91-97, mysql at lines 91-97) has no `FOREIGN KEY` or `ON DELETE CASCADE` constraint. The `creator_id` column is a plain `INTEGER NOT NULL` with no referential integrity rule.

So both categories of a deleted user's reactions — reactions *on* their memos and reactions *by* them on other memos — are cleaned up by explicit Go `DELETE` statements within the same transaction that removes the user.
