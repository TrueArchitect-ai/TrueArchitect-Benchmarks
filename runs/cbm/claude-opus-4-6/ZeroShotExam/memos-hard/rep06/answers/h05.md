By explicit Go code; reactions are removed in two ways within the same transaction:

1. **Reactions on the deleted user's memos** are removed by `deleteReactionsByContentIDsTx` — it deletes all rows from `reaction` where `content_id` matches the content IDs of the user's memos (`store/db/sqlite/user_delete.go:96, 380-388`).

2. **Reactions created by the deleted user** (on anyone's memos) are removed by `deleteReactionsByCreatorTx` — it deletes all rows from `reaction` where `creator_id` matches the user ID (`store/db/sqlite/user_delete.go:102, 400-403`).

Both are called from `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`), which runs inside a transaction in `DeleteUser`. The same pattern exists in all three database drivers (sqlite, postgres, mysql — e.g., `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`).

There is **no database-level CASCADE** for reactions — the `reaction` table has no foreign key constraints at all (`store/migration/sqlite/LATEST.sql:92-98`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-97`). The only `ON DELETE CASCADE` in the schema is on `memo_share.memo_id`.
