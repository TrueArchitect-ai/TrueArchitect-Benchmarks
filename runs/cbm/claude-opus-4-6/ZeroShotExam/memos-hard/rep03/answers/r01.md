The premise is incorrect — there is no Redis connection in this project. The cache layer is an **in-process, in-memory cache**, not Redis-backed.

The cache is implemented in `store/cache/cache.go` as a Go struct (`cache.Cache`) built on `sync.Map` with TTL-based expiration. It is configured and instantiated in `store/store.go:38-45`, where the `Store` constructor creates a `userCache` (line 52) using a `cache.Config` with:

- **DefaultTTL: 10 minutes** (`10 * time.Minute`, line 41)
- CleanupInterval: 5 minutes (line 42)
- MaxItems: 1000 (line 43)

User entries are cached under a key derived from their numeric ID (`store/user.go:88-90`, `strconv.Itoa(int(userID))`), and all `Set` calls on `userCache` use the default TTL (e.g., `store/user.go:98`, `132`, `167`), so user entries have a **10-minute TTL**.

The only other "cache" in the project is the frontend's `cacheService` (`web/src/components/MemoEditor/services/cacheService.ts`), which uses browser `localStorage` for editor draft persistence — also not Redis, and unrelated to user entries.
