**Concrete method:** `(*sqlite.DB).CreateMemo` — `store/db/sqlite/memo.go:16` — this is what runs `INSERT INTO memo (...) VALUES (...) RETURNING ...` via `d.db.QueryRowContext(ctx, stmt, args...)` (`store/db/sqlite/memo.go:41-42`).

**Determination method:**
1. `store.Store.CreateMemo` (`store/memo.go:109`) is a thin façade that just validates the UID and delegates to `s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`), where `driver` is the `store.Driver` interface (`store/driver.go`) — so the concrete implementation depends on which driver was constructed at startup.
2. That construction happens in `db.NewDBDriver` (`store/db/db.go:14-32`), a `switch profile.Driver { case "sqlite": ... case "mysql": ... case "postgres": ... }`.
3. `profile.Driver` is populated from the CLI/env config in `cmd/memos/main.go`: `viper.SetDefault("driver", "sqlite")` (`cmd/memos/main.go:122`) and the `--driver` flag itself defaults to `"sqlite"` (`cmd/memos/main.go:130`). With no database flags supplied, `profile.Driver == "sqlite"`.
4. Therefore `NewDBDriver` takes the `case "sqlite": driver, err = sqlite.NewDB(profile)` branch (`store/db/db.go:19-20`), making the runtime `store.Driver` a `*sqlite.DB`, whose `CreateMemo` method (`store/db/sqlite/memo.go:16`) is the one that actually executes the SQL `INSERT`.
