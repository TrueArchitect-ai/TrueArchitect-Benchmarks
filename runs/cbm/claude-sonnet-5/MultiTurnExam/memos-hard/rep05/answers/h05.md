h05.

**Mechanism: explicit Go code** (not a database-level cascade/rule).

**Evidence:**
- Schema check: `store/migration/postgres/0.20/00__reaction.sql:2-9` (and the equivalent sqlite/mysql `0.20` migrations) define `reaction` with a plain `creator_id INTEGER NOT NULL` column and no `FOREIGN KEY … REFERENCES user … ON DELETE CASCADE` clause — so there's no DB-level rule that would auto-remove reactions when a user row is deleted. The later `0.23__reactions.sql` migrations only rewrite `reaction_type` values, not constraints.
- Deletion code: each driver's `user_delete.go` explicitly deletes reactions as part of the `DeleteUser` transaction:
  - `store/db/sqlite/user_delete.go:96` and `:102` — calls `deleteReactionsByContentIDsTx` (removes reactions on the deleted user's memos, `DELETE FROM reaction WHERE content_id IN (...)`, defined at `store/db/sqlite/user_delete.go:380-388`) and `deleteReactionsByCreatorTx` (removes reactions the user made on others' content, `DELETE FROM reaction WHERE creator_id = ?`, defined at `store/db/sqlite/user_delete.go:400-403`).
  - Same two calls/queries exist in `store/db/postgres/user_delete.go:383` and `:401`, and `store/db/mysql/user_delete.go:420` and `:438`.
- These deletes run inside the same transaction as the rest of the user-deletion cleanup (`deleteUserTargetsTx`, `store/db/sqlite/user_delete.go:92-127`), before the `user` row itself is deleted (`deleteUserRowTx`, `store/db/sqlite/user_delete.go:461-464`), i.e. it's ordinary application-level cleanup, not something the database enforces on its own.
