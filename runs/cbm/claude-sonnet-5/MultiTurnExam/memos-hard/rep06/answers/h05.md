**Mechanism: Explicit Go code** (no database-level cascade rule exists).

**Evidence locations:**
- **Schema check — no DB-level rule:** `store/migration/postgres/LATEST.sql:90-97` (and equivalently `store/migration/mysql/0.20/00__reaction.sql`, `store/migration/sqlite/0.20/00__reaction.sql`) define `reaction.creator_id` as a plain `INTEGER NOT NULL` with no `FOREIGN KEY` / `ON DELETE CASCADE` constraint to `user.id` at all — so the database itself would never remove reaction rows when a user is deleted.
- **Explicit application code:** Each driver's `DeleteUser` transaction explicitly deletes reactions:
  - `store/db/postgres/user_delete.go:29` (`DeleteUser`) calls `deleteReactionsByContentIDsTx` at line 96 (removes reactions left on the deleted user's memos, via `DELETE FROM reaction WHERE content_id IN (...)` at line 383) and `deleteReactionsByCreatorTx` at line 102 (removes reactions the deleted user made, via `DELETE FROM reaction WHERE creator_id = ...` at line 401).
  - Identical logic in `store/db/mysql/user_delete.go` (lines 420, 438) and `store/db/sqlite/user_delete.go` (lines 383, 401).

So reactions are cleaned up in both directions — as the reaction's creator, and as reactions attached to content the deleted user owned — purely through explicit `DELETE` statements issued by Go code inside the user-deletion transaction, not via any FK cascade.
