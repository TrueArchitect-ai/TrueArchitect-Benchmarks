**Mechanism: explicit Go code** (not a database-level `ON DELETE CASCADE` rule).

**Evidence locations:**
- Each DB backend's `DeleteUser` transaction explicitly deletes reactions in two ways, in `deleteUserTargetsTx`:
  - `deleteReactionsByContentIDsTx` — removes reactions on all memos owned by the deleted user (by `content_id`), e.g. `store/db/postgres/user_delete.go:96,380-398`, `store/db/sqlite/user_delete.go:96,380-398`, `store/db/mysql/user_delete.go:96,417-435`.
  - `deleteReactionsByCreatorTx` — removes reactions the deleted user themself made on any content, e.g. `store/db/postgres/user_delete.go:102,400-403`, `store/db/sqlite/user_delete.go:102,400-403`, `store/db/mysql/user_delete.go:102,437-440`. This runs a plain `DELETE FROM reaction WHERE creator_id = ?`.
- All three backends (`postgres`, `sqlite`, `mysql`) implement the identical pattern inside their `DeleteUser`/`deleteUserTargetsTx` transaction (`store/db/{postgres,sqlite,mysql}/user_delete.go`), so this is consistent app-level cleanup rather than something the schema does for free.
- I also checked the reaction table's schema/migrations (`store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql`, `.../0.23/00__reactions.sql`, and `LATEST.sql`) — the reaction table's `creator_id` column carries no `ON DELETE CASCADE` foreign-key clause referencing `user`; deletion is driven entirely by the explicit `DELETE FROM reaction ...` statements in Go, not by the DB.
