**Mechanism:** Explicit Go code, run inside the transactional `DeleteUser` flow in each database backend — not a database-level cascade rule.

**Evidence locations:**
- Reaction removal is done via two explicit `DELETE FROM reaction` statements issued inside `deleteUserTargetsTx`, one per backend:
  - `store/db/postgres/user_delete.go:96` (`deleteReactionsByContentIDsTx`, removes reactions on the deleted user's memos) and `store/db/postgres/user_delete.go:102` (`deleteReactionsByCreatorTx`, removes reactions the user itself made), implemented at `store/db/postgres/user_delete.go:380-402`.
  - Identical pattern in `store/db/sqlite/user_delete.go:96,102` (impl. at `store/db/sqlite/user_delete.go:380-402`) and `store/db/mysql/user_delete.go:96,102` (impl. at `store/db/mysql/user_delete.go:417-439`).
- I checked the `reaction` table schema to rule out a DB-level rule: `store/migration/postgres/0.20/00__reaction.sql:2-9` creates `reaction` with `creator_id INTEGER NOT NULL` and only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — **no foreign key** to the `user` table at all, so no `ON DELETE CASCADE` (or any other DB-level rule) exists or could exist for this column. The later migration `store/migration/postgres/0.23/00__reactions.sql` only remaps emoji values and adds no constraints.
- `store/test/user_delete_test.go:13` (`TestDeleteUserCleansRelatedData`) exercises this behavior, confirming reactions are asserted to be cleaned up as part of user deletion.

So without this explicit cleanup code, orphaned reaction rows (with a dangling `creator_id` or `content_id`) would remain — the database schema provides no automatic protection.
