**Premise correction:** Neither. There's no NATS, RabbitMQ, or any external message broker in this codebase — no such dependency appears in `go.mod`, and no queue-declaration or broker-connection code exists.

**Actual mechanism:** Webhook "delivery workers" are just 4 in-process goroutines draining an in-memory buffered Go channel, `asyncPostQueue` (`internal/webhook/webhook.go:39`, `chan *WebhookRequestPayload` with capacity 128), spun up in the package's `init()` function (`internal/webhook/webhook.go:42-55`). `PostAsync` (`internal/webhook/webhook.go:184`) enqueues onto this channel with a non-blocking `select`/`default` (dropping and logging a warning if the queue is full, `internal/webhook/webhook.go:189-195`), and each worker goroutine calls `Post` (`internal/webhook/webhook.go:120`) to perform the actual HTTP delivery. There's no persistence, no cross-process queue, and no restart durability — it's purely an in-memory worker pool within the single `memos` server process.
