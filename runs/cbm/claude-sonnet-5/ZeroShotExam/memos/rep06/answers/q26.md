q26. When `DeleteMemo` (RPC handler `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go:518-591`) runs, it directly touches and cascades into the following tables:

- **`memo`** — the target memo row is deleted (and, for each linked comment memo found via `memo_relation` with type `COMMENT`, those comment memo rows are recursively deleted too), via `store.DeleteMemo` (`store/memo.go:140`) → driver `DeleteMemo` (e.g. `store/db/sqlite/memo.go:237`, `DELETE FROM memo WHERE id = ?`).
- **`memo_relation`** — cleaned up explicitly for the memo both as source and as target, via `driver.DeleteMemoRelation` calls in `store.DeleteMemo` (`store/memo.go:142-147`).
- **`attachment`** — all attachments belonging to the memo are looked up and deleted one-by-one via `s.DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`).
- **`memo_share`** — declared with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in postgres/mysql/sqlite schemas (`store/migration/{sqlite,postgres,mysql}/LATEST.sql`), so rows cascade-delete when the memo row is deleted (note: sqlite opens its connection with `_pragma=foreign_keys(0)` in `store/db/sqlite/sqlite.go:53`, so this cascade is not actually enforced on sqlite backends — only postgres/mysql enforce it at the DB level).

Not affected: `reaction` rows are only *listed* (for the deletion webhook payload) in `server/router/api/v1/memo_service.go:545-550`, but no delete call is issued against them — they are left orphaned by `content_id` string reference (no FK exists for this table).
