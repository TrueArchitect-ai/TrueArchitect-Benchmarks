**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the row itself is deleted (`store/db/sqlite/memo.go:237-248`, and equivalents in `store/db/postgres/memo.go`, `store/db/mysql/memo.go`), and recursively for each child comment memo (`server/router/api/v1/memo_service.go:567-577`, which loops comment relations and calls `s.Store.DeleteMemo` again).
- **`memo_relation`** — explicitly cleared for the memo as both source and target (`store/memo.go:142-147`, via `driver.DeleteMemoRelation`).
- **`attachment`** — each attachment linked to the memo is explicitly deleted one-by-one (`store/memo.go:148-157`, via `s.DeleteAttachment`).
- **`memo_share`** — not touched by application code, but cascades at the DB schema level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (present identically in `store/migration/sqlite/LATEST.sql:102-109`, `store/migration/postgres/LATEST.sql`, and `store/migration/mysql/LATEST.sql:108`), so its rows are removed automatically when the `memo` row is deleted.

Note: `reaction` is **not** cascaded — `DeleteMemo` (`server/router/api/v1/memo_service.go:518-591`) only calls `ListReactions` (for the deleted-webhook payload) and never calls `DeleteReaction`, and there's no DB-level FK from `reaction` to `memo` (`reaction.content_id` is a plain text column, not a FK) — so reaction rows for a deleted memo become orphaned rather than "affected."
