q26. Database tables affected when `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518` → `store.Store.DeleteMemo`, `store/memo.go:140`):

- **`memo`** — the target memo row itself is deleted, plus any comment memos (rows in `memo_relation` of type `COMMENT` pointing at this memo) are recursively deleted the same way (`memo_service.go:567-577` loops `s.Store.DeleteMemo` for each comment relation).
- **`memo_relation`** — explicitly cleared for the memo both as source and as target (`store/memo.go:142-147`, `DeleteMemoRelation`).
- **`attachment`** — attachments linked to the memo (`memo_id`) are looked up and deleted one-by-one via `DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`); this also triggers non-DB blob/file storage cleanup.
- **`memo_share`** — not deleted by application code, but the schema defines `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:104-111`, same in sqlite/mysql `LATEST.sql`), so rows cascade-delete at the DB level when the `memo` row is removed.

Note: `reaction` rows (queried via `ListReactions` at `memo_service.go:545-550`, keyed by `content_id`, not a real FK) are read only for the webhook payload and are **not** deleted — they are not affected by this operation, and there's no DB-level FK/cascade on `reaction` to `memo`.
