- **Auth interceptor:** `web/src/connect.ts` (the `authInterceptor`, a Connect-RPC `Interceptor`) attaches `Authorization: Bearer <token>` to every request, transparently refreshes on expiry/401, and redirects on refresh failure. It reads/writes tokens via `web/src/auth-state.ts` (in-memory + `localStorage`, synced across tabs via `BroadcastChannel`) and calls `refreshToken()` through a separate no-interceptor transport to avoid recursion.

- **Token kinds managed:**
  - Short-lived **JWT access token** ("Access Token V2", ~15 min) — kept client-side in memory/localStorage and sent as `Authorization: Bearer`.
  - Long-lived **refresh token** — stored as an httpOnly cookie (never touched by JS; sent via `credentials: "include"`), used only to mint new access tokens.
  - (Backend also supports a third kind, **Personal Access Tokens (PAT)**, for programmatic API access, though the web frontend doesn't manage these — they're issued/used separately.)

- **Backend validation package:** `server/auth` (see `server/auth/authenticator.go`, plus `token.go`, `extract.go`, `context.go`). The `Authenticator` there validates JWT access tokens (`AuthenticateByAccessTokenV2`), refresh tokens (`AuthenticateByRefreshToken`), and PATs (`AuthenticateByPAT`), and is shared across the gRPC/Connect interceptors and file server (`server/router/api/v1/connect_services.go`, `server/router/fileserver/fileserver.go`).
