**Tables directly/cascade-affected when `DeleteMemo` runs** (`server/router/api/v1/memo_service.go:518` → `store.Store.DeleteMemo` at `store/memo.go:140` → per-DB driver `DeleteMemo` in `store/db/{sqlite,postgres,mysql}/memo.go`):

- **`memo`** — the target memo row is deleted directly (`DELETE FROM memo WHERE id = ?`); additionally, before deleting the target memo, the handler in `memo_service.go:567-577` finds all `COMMENT`-type relations pointing at it and calls `Store.DeleteMemo` recursively on each comment memo, deleting those `memo` rows too.
- **`memo_relation`** — explicitly cleaned up inside `Store.DeleteMemo` (`store/memo.go:142-147`) via two calls to `driver.DeleteMemoRelation`, removing rows where the deleted memo is either `memo_id` or `related_memo_id` (done for the target memo and for each deleted comment memo).
- **`attachment`** — explicitly cleaned up inside `Store.DeleteMemo` (`store/memo.go:148-157`): lists attachments by `memo_id` and calls `Store.DeleteAttachment` for each, which also removes the attachment's blob/file from storage (`store/attachment.go:132-149`).
- **`memo_share`** — not deleted in application code, but cascades automatically at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, defined identically in all three schemas: `store/migration/postgres/LATEST.sql:101-109`, `store/migration/sqlite/LATEST.sql:102-110`, `store/migration/mysql/LATEST.sql:101-109`.

**Notably NOT deleted/cascaded:** the `reaction` table — `DeleteMemo` in `memo_service.go:545-550` only *lists* reactions (for the webhook payload before deletion) but never deletes them, and there's no DB-level FK from `reaction.content_id` (a free-text field) to `memo`, so reaction rows are orphaned after a memo delete.
