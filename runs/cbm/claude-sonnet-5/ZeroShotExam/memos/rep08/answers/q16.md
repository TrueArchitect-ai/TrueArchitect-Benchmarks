When `store.Store.DeleteMemo` (`/bench/repo/store/memo.go:140-158`) is called, before deleting the memo row itself (via `driver.DeleteMemo`), it deletes:

1. **Memo relations where the memo is the source** — `driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` (`/bench/repo/store/memo.go:142`)
2. **Memo relations where the memo is the target/related memo** — `driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`/bench/repo/store/memo.go:145`) — this covers things like comment links, references, etc.
3. **Attachments linked to the memo** — it lists all attachments via `ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})` and calls `s.DeleteAttachment(...)` for each one (`/bench/repo/store/memo.go:149-157`), which in turn also removes the attachment's underlying storage (local file or S3 object) via `DeleteAttachmentStorage` (`/bench/repo/store/attachment.go:132-149`).

Note: at the API layer (`/bench/repo/server/router/api/v1/memo_service.go:518-593`), reactions are listed (`ListReactions`) and memo comments are recursively deleted (each comment is itself a memo, deleted via a separate `store.DeleteMemo` call, lines 567-577) before the parent memo's `store.DeleteMemo` is invoked — but reaction rows themselves are not explicitly deleted by `store.DeleteMemo`; they are only fetched for the webhook payload/message construction (lines 545-550), not deleted there. I did not find explicit reaction-row deletion tied to memo deletion in the store layer — if that matters, it may rely on a DB-level cascade rather than application code, which I could not confirm from the store package alone.
