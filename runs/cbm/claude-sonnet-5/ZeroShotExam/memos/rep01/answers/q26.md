**Tables affected when `DeleteMemo` runs** (server/router/api/v1/memo_service.go:518 → store/memo.go:140 `Store.DeleteMemo`):

- **`memo`** — the target memo row is deleted directly (`store/db/sqlite/memo.go:237`, and the postgres/mysql equivalents). Also, before deleting the target memo, `DeleteMemo` in `memo_service.go:567-577` finds all `MemoRelationComment` relations pointing at it and recursively calls `s.Store.DeleteMemo` for each comment memo, deleting those `memo` rows too (and cascading the same cleanup for each).
- **`memo_relation`** — explicit cascade in `store/memo.go:142-147`: deletes rows where the memo is either `memo_id` or `related_memo_id`.
- **`attachment`** — explicit cascade in `store/memo.go:148-157`: lists attachments by `memo_id` and deletes each via `DeleteAttachment` (this also triggers non-DB storage cleanup of the underlying file/blob).
- **`memo_share`** — cascades via a DB-level foreign key, not application code: `memo_share.memo_id REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, same in postgres/mysql `LATEST.sql`), so rows are removed automatically when the `memo` row is deleted.

Note: `reaction` is **read** in `DeleteMemo` (`ListReactions` by `ContentID`, memo_service.go:545-550) only to build the webhook payload — there is no delete/cascade against the `reaction` table, and no FK ties it to `memo`, so reaction rows are left orphaned after a memo delete.
