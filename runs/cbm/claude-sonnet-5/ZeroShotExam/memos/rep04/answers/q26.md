**Directly/explicitly cascaded tables:**

- **`memo`** — the target memo row is deleted (`store/memo.go:158` → `DB.DeleteMemo`, e.g. `store/db/sqlite/memo.go:237`). Additionally, the API layer (`server/router/api/v1/memo_service.go:567-577`) first finds all comment memos via `memo_relation` (type `COMMENT`) and recursively calls `store.DeleteMemo` on each, deleting those `memo` rows too.
- **`memo_relation`** — explicitly cleared for the memo in both directions before the memo row is deleted (`store/memo.go:142-147`: `DeleteMemoRelation` where `memo_id = id` and where `related_memo_id = id`). This runs once for the parent memo and once per deleted comment memo.
- **`attachment`** — all attachments tied to the memo are looked up and explicitly deleted via `s.DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`), which also removes the underlying blob/file storage. Runs for the parent memo and each deleted comment.
- **`memo_share`** — not deleted in Go code, but cascades automatically at the DB level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, same in postgres/mysql `LATEST.sql`).

**Notably NOT cascaded:** `reaction` rows referencing the memo (`content_id`) are only read (`ListReactions` in `memo_service.go:545`, for the deletion webhook payload) but never deleted — `reaction.content_id` is a string reference, not an FK, so reactions on a deleted memo are left orphaned.
