Before deleting the memo row itself, `Store.DeleteMemo` (store/memo.go:140-159) deletes:

1. **`memo_relation` records** — deleted twice, once where the memo is the source (`MemoID`) and once where it is the target (`RelatedMemoID`), via `s.driver.DeleteMemoRelation` (store/memo.go:142-147).
2. **`attachment` records** — all attachments linked to the memo are listed (`s.ListAttachments`) and deleted one by one via `s.DeleteAttachment` (store/memo.go:149-157).

Only after these are removed does it call `s.driver.DeleteMemo(ctx, delete)` (store/memo.go:158) to delete the memo row.

Note: at the API layer, `APIV1Service.DeleteMemo` (server/router/api/v1/memo_service.go:518-582) additionally deletes child "comment" memos (via recursive calls to `s.Store.DeleteMemo`) before deleting the target memo, but that cascading is orchestrated in the router layer, not inside the store's `DeleteMemo` itself. Also, `memo_share` rows are cleaned up via a DB-level `ON DELETE CASCADE` foreign key (store/migration/sqlite/LATEST.sql:109), not by explicit store-layer code.
