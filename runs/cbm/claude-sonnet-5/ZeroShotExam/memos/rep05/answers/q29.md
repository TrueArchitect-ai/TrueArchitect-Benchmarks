q29. Frontend requests are authenticated via a Connect-RPC interceptor (`authInterceptor`) defined in `web/src/connect.ts:156`, attached to the shared transport at `web/src/connect.ts:184`. It reads the token from `web/src/auth-state.ts`, injects it as an `Authorization: Bearer <token>` header, and on a `Code.Unauthenticated` response transparently refreshes and retries once (via `refreshToken` on `AuthService`) before redirecting to login on repeated failure.

Token kinds managed:
- **JWT access token** — short-lived (15 min), kept in memory + `localStorage` (`memos_access_token`/`memos_token_expires_at`), sent as the `Authorization: Bearer` header.
- **Refresh token** — longer-lived, stored as an HTTP-only cookie (not touched directly by JS; sent automatically via `credentials: "include"` in `fetchWithCredentials`), used only by the dedicated `refreshTransport`/`AuthService.refreshToken` call to mint a new access token.
- (Backend also supports a third kind, **Personal Access Tokens (PAT)**, for programmatic/API clients, though the web frontend itself only uses access + refresh tokens.)

Backend validation package: `server/auth` (see `server/auth/authenticator.go`), specifically the `Authenticator` type's `AuthenticateByAccessTokenV2` (JWT access token), `AuthenticateByRefreshToken` (refresh token, checked against the DB for revocation), and `AuthenticateByPAT` (personal access tokens), unified through `AuthenticateToUser`/`Authenticate`. This is invoked by the Connect interceptor at `server/router/api/v1/connect_interceptors.go` and other transport entry points (gRPC, file server) per the doc comment in `authenticator.go:17-25`.
