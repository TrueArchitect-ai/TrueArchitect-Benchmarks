**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted directly (`store/db/{sqlite,postgres,mysql}/memo.go: DeleteMemo`, called from `store/memo.go:158`). Additionally, before deleting the target memo, the handler recursively deletes any child "comment" memos (`server/router/api/v1/memo_service.go:567-577`), so multiple `memo` rows can be removed.
- **`memo_relation`** — explicitly cleaned up for both directions (`memo_id` and `related_memo_id`) via `s.driver.DeleteMemoRelation` in `store/memo.go:142-147`, for every memo deleted (including comment memos, since each comment delete also goes through `store.DeleteMemo`).
- **`attachment`** — attachments belonging to the memo are looked up and explicitly deleted one-by-one via `s.DeleteAttachment` in `store/memo.go:149-157`.
- **`memo_share`** — declared with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the schema (`store/migration/{sqlite,postgres,mysql}/LATEST.sql`), so deleting the `memo` row cascades to `memo_share` at the database level in Postgres/MySQL. Note: in SQLite this constraint is effectively inert because the driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite `memo_share` rows are **not** actually cascade-deleted.

Not affected despite being read: `reaction` rows are fetched (`ListReactions`, `memo_service.go:545-550`) only to build the webhook payload — they are never deleted, so deleted memos can leave orphaned `reaction` rows (matched by `content_id`, which isn't an enforced FK anywhere).
