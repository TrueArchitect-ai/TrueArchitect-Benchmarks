Frontend requests are authenticated by a Connect-RPC `Interceptor` in `web/src/connect.ts` (the `authInterceptor`, lines 156–178), which reads the access token via `getAccessToken()`/`getRequestToken()` from `web/src/auth-state.ts` and attaches it as `Authorization: Bearer <token>`; on a `Code.Unauthenticated` response it triggers `refreshAccessToken()` and retries once (falling back to `redirectOnAuthFailure()` in `web/src/utils/auth-redirect.ts` on failure). It manages two token kinds: a short-lived JWT **access token** (stored in-memory + `localStorage`, synced across tabs via a `BroadcastChannel`, sent as the `Authorization` bearer header) and a **refresh token** (an HttpOnly cookie sent automatically via `credentials: "include"`, used only against the dedicated `refreshTransport`/`AuthService.refreshToken` call to mint a new access token). On the backend, these are validated by the `server/auth` package (`server/auth/authenticator.go`, `token.go`, `extract.go`, `context.go`), specifically `Authenticator.AuthenticateByAccessTokenV2` (stateless JWT check), `Authenticator.AuthenticateByRefreshToken` (DB-backed refresh-token/revocation check), and `Authenticator.AuthenticateByPAT` for personal access tokens — all wired into the Connect/gRPC interceptor chain in `server/router/api/v1/connect_interceptors.go`.
