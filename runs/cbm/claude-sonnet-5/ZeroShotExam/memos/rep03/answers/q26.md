**Directly/explicitly affected tables:**
- **`memo`** — the target memo row is deleted, and (via the same `DeleteMemo` code path called recursively) any child *comment* memos related to it are deleted too (`server/router/api/v1/memo_service.go:567-582`, `store/memo.go:140-159`).
- **`memo_relation`** — `store.DeleteMemo` explicitly deletes rows where the memo is either `memo_id` or `related_memo_id` (`store/memo.go:142-147`, e.g. `store/db/sqlite/memo_relation.go:137-159`).
- **`attachment`** — `store.DeleteMemo` lists and explicitly deletes all attachments tied to the memo via `DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`), which also removes the underlying file/blob storage (not a DB table).

**Cascaded at the DB-constraint level (Postgres/MySQL only):**
- **`memo_share`** — has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). Note: for SQLite this cascade is effectively inert because the driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), disabling FK enforcement — so on SQLite, `memo_share` rows are **not** actually cleaned up when a memo is deleted (likely a latent bug/orphan-row risk).

**Not affected (checked, no FK/explicit cleanup):** `reaction` (keyed by a string `content_id`, no FK, and never explicitly deleted in `DeleteMemo`) — reaction rows for a deleted memo appear to become orphaned.
