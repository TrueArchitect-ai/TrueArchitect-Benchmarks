This confirms the `reaction` table has no foreign key constraints at all (no `creator_id` FK to `user`, no `content_id` FK, no `ON DELETE CASCADE`) — unlike `memo_share`, which does declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`. h05.

**Mechanism: explicit Go application code (in an explicit transaction), not a database-level rule.**

The `reaction` table has no foreign keys at all — confirmed in the schema (`store/migration/{sqlite,postgres,mysql}/LATEST.sql`, `CREATE TABLE reaction (...)`, lines ~91-99 in each), so there is no `ON DELETE CASCADE` and no DB trigger that could remove reactions automatically (contrast with `memo_share`, which *does* declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` right below it).

Instead, `DeleteUser` in each of the three store drivers runs inside a transaction and explicitly deletes matching rows from `reaction` before deleting the `user` row:

- `store/db/sqlite/user_delete.go:96-104`, `store/db/postgres/user_delete.go:96-104`, `store/db/mysql/user_delete.go:96-104` — inside `deleteUserTargetsTx`, it calls:
  - `deleteReactionsByContentIDsTx` (removes reactions **on** all memos/comments owned by the deleted user, via `DELETE FROM reaction WHERE content_id IN (...)`, matched against `"memos/"+uid` content IDs collected from the user's memo tree)
  - `deleteReactionsByCreatorTx` (removes reactions **made by** the deleted user, via `DELETE FROM reaction WHERE creator_id = ?`)

Both helper functions (`deleteReactionsByContentIDsTx`, `deleteReactionsByCreatorTx`) are duplicated identically across `store/db/sqlite/user_delete.go`, `store/db/postgres/user_delete.go`, and `store/db/mysql/user_delete.go` (lines 380-403 / 417-440 respectively), so every backend performs the same explicit cleanup as part of the delete-user transaction, ordered before the memo rows and the user row itself are deleted.
