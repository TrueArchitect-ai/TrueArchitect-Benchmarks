Enforcement site — path, one per line

1. Core API read-access check (`checkMemoReadAccess`, gates GetMemo/GetMemoComment single-object reads by visibility + row status) — `server/router/api/v1/memo_service.go` (also invoked from `server/router/api/v1/memo_service_comments.go`)
2. ListMemos query-level visibility filter (separate inline logic building `VisibilityList`/CEL filter rather than calling `checkMemoReadAccess`) — `server/router/api/v1/memo_service.go` (~lines 218-227)
3. File/attachment server permission check (`checkAttachmentPermission`, re-derives visibility rules independently for raw file downloads) — `server/router/fileserver/fileserver.go`
4. SSE real-time delivery filter (`SSEClient.canReceive`, decides which connected clients get pushed a memo event based on its visibility) — `server/router/api/v1/sse_hub.go`
5. RSS feed generation (hardcodes `VisibilityList: []store.Visibility{store.Public}` when querying memos for the feed) — `server/router/rss/rss.go`
6. Sitemap generation (hardcodes `VisibilityList: []store.Visibility{store.Public}`) — `server/router/frontend/frontend.go`

Note: several other files (`reaction_service.go`, `attachment_service.go`, `memo_attachment_service.go`, `memo_mention_helpers.go`) also contain inline `memo.Visibility` comparisons, but these gate *derived* actions (reactions, attachments-via-API, mentions) rather than being independent "can this user view the memo" surfaces — I did not count them separately.
