**Mechanism: explicit Go code (application-level transaction), not a database-level cascade rule.**

When `Store.DeleteUser` runs (`/bench/repo/store/user_delete.go:1`, dispatched to the per-backend implementations), each backend's `DeleteUser` opens a transaction and explicitly deletes reactions before deleting the user row:

- `/bench/repo/store/db/postgres/user_delete.go:96-104` and `:380-403` — `deleteUserTargetsTx` calls `deleteReactionsByContentIDsTx` (deletes reactions on all memos owned by the user, matched via `content_id IN (...)`, batched at 500) and `deleteReactionsByCreatorTx` (`DELETE FROM reaction WHERE creator_id = $1`, removing reactions the deleted user themselves placed on others' memos).
- Identical logic in `/bench/repo/store/db/sqlite/user_delete.go:96-104,380-403` and `/bench/repo/store/db/mysql/user_delete.go:96-104,417-440`.

This happens before `deleteMemosTx`/`deleteUserRowTx` in the same transaction, and before the failpoint check at `/bench/repo/store/user_delete.go:47` used in tests.
