**Premise correction:** There is no Redis connection anywhere in this repository — a full-repo search (`grep -ril "redis"`) returns zero matches. The "cache layer" is not backed by an external Redis instance at all.

**Actual mechanism:** The cache layer is a custom in-process, in-memory cache implemented in `store/cache/cache.go` (a `sync.Map`-backed store with TTL expiration, periodic cleanup, and size-based eviction — see `Cache.cleanupLoop`/`cleanup`/`cleanupOldest`, lines 199–313).

It's wired up in `store/store.go:38-61` (`store.New`), where the `Store` struct holds three separate instances of this in-memory cache — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`) — all built from one shared `cache.Config`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

So **user entries (`userCache`) get a 10-minute TTL** (`store/store.go:41`), the same default applied to instance settings and user settings caches. User records are read/written through this cache in `store/user.go:150-151` (`s.userCache.Get(ctx, userCacheKey(*find.ID))`), with cache keys built via helpers like `getUserSettingCacheKey` in `store/cache.go:7-9`.

There's also an unrelated `cacheService.ts` under `web/src/components/MemoEditor/services/cacheService.ts`, but that's a frontend browser-side draft cache for the memo editor, not part of the backend cache layer.
