Confirmed: no `FOREIGN KEY ... ON DELETE CASCADE` clause on the `reaction` table (`creator_id`/`content_id` are plain columns, no FK constraint at all) in any of the three DB schemas.

h05.

**Mechanism:** Explicit Go application code, not a database-level rule (no FK/cascade exists on the `reaction` table).

**Evidence:**
- `reaction` table schema has no foreign key/cascade constraints — just a `UNIQUE(creator_id, content_id, reaction_type)` — confirmed in `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`.
- Each driver's `DeleteUser` runs the deletion inside an explicit transaction (`store/db/postgres/user_delete.go:29-59`, `store/db/sqlite/user_delete.go:29-59`, `store/db/mysql/user_delete.go:29-59`) and calls `deleteUserTargetsTx`, which explicitly issues two `DELETE FROM reaction` statements:
  - `deleteReactionsByContentIDsTx` — removes reactions left *on* memos owned by the deleted user, matched via `content_id IN (...)` built from that user's memo UIDs (e.g. `store/db/postgres/user_delete.go:380-388`).
  - `deleteReactionsByCreatorTx` — removes reactions the deleted user *made* on any content, via `DELETE FROM reaction WHERE creator_id = ?` (e.g. `store/db/postgres/user_delete.go:400-403`).
- Both calls appear as the first two steps of `deleteUserTargetsTx` (`store/db/postgres/user_delete.go:92-127`, mirrored identically in the sqlite and mysql versions), i.e. reactions are cleaned up before memos/settings/identities are removed, all within the same transaction as the user row deletion.
- Test coverage exists at `store/test/reaction_test.go` and `store/test/user_delete_test.go`, plus API-level test `server/router/api/v1/test/user_service_delete_test.go`, reinforcing that reaction cleanup on user deletion is intentional, tested behavior.
