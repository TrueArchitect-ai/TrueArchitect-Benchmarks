h05.
**Mechanism: explicit Go application code, not a database-level cascade rule.**

Evidence:
- Schema check: `reaction` table (`store/migration/{sqlite,postgres,mysql}/LATEST.sql`) has `creator_id`/`content_id` as plain columns with no `FOREIGN KEY ... ON DELETE CASCADE` and no triggers — so the database itself does nothing when a user row is deleted.
- Application code: each driver's `store/db/{postgres,sqlite,mysql}/user_delete.go` implements `DB.DeleteUser` as a single transaction that explicitly issues two reaction deletes before removing the user row:
  - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` for every memo/comment the user authored (removes reactions *left on* the user's deleted content), lines ~380-388 (postgres/sqlite), ~417-425 (mysql).
  - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (removes reactions the user themself *made*), lines ~400-403 (postgres/sqlite), ~437-440 (mysql).
  - Both are called from `deleteUserTargetsTx` (lines ~92-127 in each file) before `deleteMemosTx` and `deleteUserRowTx`, all inside one transaction (`d.db.BeginTx` / `tx.Commit` in `DeleteUser`, lines ~29-59).
- This is verified by `store/test/user_delete_test.go` and `server/router/api/v1/test/user_service_delete_test.go`, which exercise the delete-user flow (both files listed under the earlier `grep -ril "reaction"` scan).

So reaction cleanup on user deletion is handled entirely by explicit, duplicated-per-driver Go code (`store/db/postgres/user_delete.go`, `store/db/sqlite/user_delete.go`, `store/db/mysql/user_delete.go`), not by a `FOREIGN KEY ... ON DELETE CASCADE` or DB trigger.
