**Premise correction:** There is no Redis anywhere in this codebase (it's the [usememos/memos](https://github.com/usememos/memos) repo) — a repo-wide search for "redis" turns up zero matches. The cache layer is a self-contained, thread-safe **in-memory** cache, not a Redis-backed one.

**Actual mechanism:**
- The cache implementation lives in `/bench/repo/store/cache/cache.go` — a `sync.Map`-based store with per-item expiration timestamps, a background `cleanupLoop` goroutine, and LRU-ish eviction when `MaxItems` is exceeded.
- It's instantiated in `/bench/repo/store/store.go:38-58`, where `Store.New()` creates three separate cache instances (`instanceSettingCache`, `userCache`, `userSettingCache`) all sharing the same `cacheConfig`.
- That config sets `DefaultTTL: 10 * time.Minute` (`store/store.go:41`, matching the package default in `store/cache/cache.go:59`), `CleanupInterval: 5 * time.Minute`, and `MaxItems: 1000`.
- User entries are cached via `userCacheKey(userID)` in `/bench/repo/store/user.go` (e.g. lines 88, 98, 122, 132, 143, 150, 167), and these calls use the plain `Set()` method rather than `SetWithTTL()`, so they inherit the store-wide default **10-minute TTL**. Deletion is explicit via `s.userCache.Delete(...)` in `store/user_delete.go:40` on user deletion.
