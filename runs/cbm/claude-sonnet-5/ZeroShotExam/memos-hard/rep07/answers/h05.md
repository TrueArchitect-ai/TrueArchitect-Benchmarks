**Mechanism: explicit Go code (application-level), not a database-level cascade/trigger.**

Evidence:

1. **Reaction table has no foreign key to `user`**, in any of the three supported drivers — deletion cannot be a DB cascade:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`
   
   Each `reaction` table only has `creator_id`/`content_id` columns with a `UNIQUE` constraint — no `REFERENCES user(id)` / `ON DELETE CASCADE` clause.

2. **`DeleteUser` explicitly deletes reactions in Go**, inside a manual transaction, for each driver (identical logic in all three):
   - `store/db/sqlite/user_delete.go:96-104`
   - `store/db/postgres/user_delete.go:96-104`
   - `store/db/mysql/user_delete.go:96-104`

   Specifically, `deleteUserTargetsTx` calls two explicit raw-SQL deletes before removing the user row:
   - `deleteReactionsByContentIDsTx` (line 380/417 depending on driver): `DELETE FROM reaction WHERE content_id IN (...)` for every memo (and comment) owned by the deleted user — removes reactions *other people* left on that user's content.
   - `deleteReactionsByCreatorTx` (line 400/437): `DELETE FROM reaction WHERE creator_id = ?` — removes reactions *the deleted user* left on other people's content.

   Both run before `deleteUserRowTx` (`DELETE FROM user WHERE id = ?`), all inside the same `sql.Tx`, so the cleanup is atomic with the user deletion but is driven entirely by hand-written Go/SQL, not a database rule.

So: reactions tied to the user (as creator) and reactions on the user's own memos/comments are both removed, but via explicit application code (`deleteReactionsByCreatorTx` / `deleteReactionsByContentIDsTx`) rather than a DB foreign-key cascade or trigger.
