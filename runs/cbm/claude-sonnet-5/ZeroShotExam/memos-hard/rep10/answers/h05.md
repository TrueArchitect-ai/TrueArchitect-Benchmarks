Confirmed: the `reaction` table schema has no foreign key or `ON DELETE CASCADE` clause at all — `creator_id` and `content_id` are plain columns with just a `UNIQUE` constraint. This holds identically across sqlite, postgres, and mysql migrations.

h05. Mechanism: removed by explicit Go application code, not by a database-level cascade rule (the `reaction` table has no foreign keys at all, just a `UNIQUE(creator_id, content_id, reaction_type)` constraint).

Evidence:
- Schema has no FK/cascade on `reaction`: `store/migration/postgres/LATEST.sql:91-98` (and equivalently `store/migration/sqlite/LATEST.sql:~98`, `store/migration/mysql/LATEST.sql:~97`) — table only declares `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type`, and a `UNIQUE` constraint; no `REFERENCES user` / `ON DELETE CASCADE`.
- Explicit deletion in the `DeleteUser` transaction, identical logic in all three DB drivers:
  - `store/db/postgres/user_delete.go:96,102,380-388,400-403` — `deleteReactionsByContentIDsTx` (deletes reactions on the user's own memos/comments, batched by `content_id`) and `deleteReactionsByCreatorTx` (`DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user made on others' memos).
  - Same two functions at `store/db/sqlite/user_delete.go:96,102,380-403` and `store/db/mysql/user_delete.go:96,102,417-440`.
  - Both calls happen inside `deleteUserTargetsTx` (e.g. `store/db/postgres/user_delete.go:92-127`), which runs before the user row itself is deleted (`deleteUserRowTx`, line ~461-464 in each file), all inside one transaction (`DeleteUser`, lines 29-59).

So a deleted user's reactions are cleaned up two ways in code: reactions they *authored* (`creator_id`) are deleted directly, and reactions *on* their memos/comments (matched via `content_id`, including the recursively-collected comment tree) are deleted before the memos themselves are removed. There is no DB trigger or FK cascade involved — it's all orchestrated in Go.
