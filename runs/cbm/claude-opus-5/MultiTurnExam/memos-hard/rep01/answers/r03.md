**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never used by the server — so there is no scheduled time to report.**

Two separate corrections:

**1. The cron scheduler is dead code.** `internal/scheduler` is a complete, self-contained cron implementation (`scheduler.go`, `parser.go`, `job.go`, `middleware.go`, plus a README and doc.go), supporting 5- and 6-field expressions, timezones, and middleware. But nothing outside the package imports it: `grep -rn "internal/scheduler" --include=*.go` over the repo returns no non-test hits, and there are no calls to `scheduler.New` or `Register(&scheduler.Job{...})` anywhere in `server/`, `cmd/`, or `store/`. The only cron expressions in the tree are in the package's own tests and in illustrative doc comments — including `internal/scheduler/doc.go:14-21`, which shows an example job literally named `"daily-cleanup"` with `Schedule: "0 2 * * *" // 2 AM daily`. That is documentation for how to use the library, not a registered job; if that's the "2 AM nightly cleanup" the question has in mind, it never runs.

**2. There is no database-cleanup job at all,** scheduled or otherwise. Grepping for cleanup/vacuum/purge/nightly across `server/`, `store/`, and `cmd/` turns up only inline, request-scoped cleanup — e.g. attachment storage cleanup during user deletion (`server/router/api/v1/user_service.go:421-450`), and cascade deletes inside `DeleteUser`/`DeleteMemo` in the drivers (`store/db/*/user_delete.go`).

**What actually runs on a timer:** exactly two background loops, neither cron-driven and neither doing DB cleanup:

- `s3presign.Runner` — a `time.Ticker` at a hardcoded 12-hour interval (`server/runner/s3presign/runner.go:27-41`), started from `Server.startBackgroundRunners` (`server/server.go:162-171`), which refreshes S3 presigned attachment URLs.
- The in-memory cache sweeper — `cleanupLoop` running every 5 minutes per cache instance (`store/cache/cache.go:199`, configured at `store/store.go:42`). This evicts expired cache entries in process memory; it never touches the database.
