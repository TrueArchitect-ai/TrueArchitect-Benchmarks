Notes on the shape of this path:

- **The image is not a file or an attachment row.** `serveUserAvatar` reads `user.AvatarURL` and calls `s.parseDataURI` (`fileserver.go:196`) — the avatar is stored inline as a base64 data URI in the `user.avatar_url` column, decoded per request and written with `c.Blob` (`fileserver.go:207`). So "the data layer" is the `user` table, not blob/S3 storage.
- **Lookup is by username, not ID**: `getUserByUsername` passes `&store.FindUser{Username: &identifier}` (`fileserver.go:716`).
- **Cache is bypassed on this path.** `Store.GetUser` only consults `userCache` when `find.ID != nil` (`store/user.go:149-156`); a username lookup always falls through to `ListUsers` → driver → SQL. The result is written back into the cache keyed by ID (`store/user.go:167`).
- **Access control**: on a private instance (`!s.Profile.AllowAnonymous()`), an unauthenticated request is rejected 401 before any store call (`fileserver.go:171-179`); on an open instance any browser can fetch any user's avatar. Output is further gated by a MIME allowlist, `avatarAllowedTypes` (`fileserver.go:75`, checked at `:201`), plus `setSecurityHeaders` and a cache-control header (`:205-206`).
