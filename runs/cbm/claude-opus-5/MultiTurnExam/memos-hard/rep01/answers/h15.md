Observations worth flagging:

- **The rules aren't centralized.** `checkMemoReadAccess` (`memo_service.go:39`) is the closest thing to a canonical predicate — anonymous is denied anything non-`Public`, `Private` requires creator, and archived memos are creator-only — but the reaction, attachment, RSS, SSE, and fileserver paths each reimplement the comparison inline rather than calling it. Notably several of them (`reaction_service.go:38`, `attachment_service.go:451`, `memo_attachment_service.go:222`, `fileserver.go:699`) additionally admit admins via `isSuperUser(user)` / `store.RoleAdmin`, while `checkMemoReadAccess` does **not** — an admin cannot read another user's private memo through `GetMemo`, but can list its attachments and reactions.
- **List enforcement is different in kind**: `ListMemos` never inspects a loaded memo; it constrains the SQL/CEL query up front (`VisibilityList = {Public}` for anonymous, or `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` for a logged-in user), so enforcement happens in the data layer.
- **Share tokens are a deliberate bypass**, honored in two places: the API (`GetMemoByShare`, no auth required) and the file server's `share_token` query param (`fileserver.go:685-690`), both gated on non-expiry and matching memo ID.
- The fileserver adds an orthogonal instance-level gate: `Public` attachments are served anonymously only when `s.Profile.AllowAnonymous()` (`fileserver.go:677`).
