**Premise correction: there is no nightly database-cleanup job, and nothing is scheduled in the cron scheduler at all — so there is no run time to report.**

Two separate corrections are folded into that:

**1. The cron scheduler exists but has zero registered jobs in production code.** `internal/scheduler` is a complete, self-contained cron package — `scheduler.New`, `Register`, cron-expression parsing in `internal/scheduler/parser.go`, and middleware (`Recovery`, `Logging`, `Timeout`) in `internal/scheduler/middleware.go`. But every reference to it from outside the package is in its own tests and docs: `internal/scheduler/example_test.go` and `internal/scheduler/doc.go`. No file under `server/`, `store/`, or `cmd/` imports it, so `Register` is never called with a real job and the scheduler is never started. It's an unused library sitting in the tree.

**2. Background work that does run doesn't use cron, and isn't a cleanup job.** The only background runner wired into startup is the S3 presign refresher — constructed at `server/server.go:162` and driven by a plain `time.Ticker` on a 12-hour interval (`server/runner/s3presign/runner.go:27-41`), not a cron expression, so it has no wall-clock time of day. It re-signs S3 attachment URLs; it deletes nothing.

For completeness, the things that use the word "cleanup" in this codebase are all either request-scoped or unrelated to a schedule:

- **Cache eviction** — a goroutine sweeping expired in-memory entries every 5 minutes (`store/store.go:41`, loop at `store/cache/cache.go:200-215`). In-memory only, never touches the database.
- **Attachment/storage cleanup on delete** — runs inline as part of user or memo deletion (`server/router/api/v1/user_service.go:421-450`, `store/attachment.go:171`), triggered by the request, not by a timer.

So database row cleanup here is entirely event-driven — it happens within the delete transaction (see the user-deletion path in `store/db/*/user_delete.go`) rather than in a periodic sweep.
