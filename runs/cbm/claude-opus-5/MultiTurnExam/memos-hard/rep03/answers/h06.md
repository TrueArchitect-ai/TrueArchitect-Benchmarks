The three `Set*`/`Update*` entry points share a hop: `dispatchMemoUpdatedSideEffects` (`server/router/api/v1/memo_update_helpers.go:66`) calls `DispatchMemoUpdatedWebhook` at `memo_update_helpers.go:67`.

All four `Dispatch*Webhook` methods (`server/router/api/v1/memo_service_webhooks.go:15`, `:20`, `:25`, `:30`) load the creator's configured hooks via `s.Store.GetUserWebhooks` and call `webhook.PostAsync` (`memo_service_webhooks.go:43`, `:71`). `PostAsync` (`internal/webhook/webhook.go:184`) only enqueues onto a bounded channel; the four worker goroutines started in `init()` (`webhook.go:42-55`) are what invoke **`webhook.Post`**, where the request is built, optionally HMAC-signed, and sent via `safeClient.Do` (`webhook.go:152`). Every path above passes through that one function.

The URL is user-configured — a per-user webhook managed through `server/router/api/v1/user_service_webhooks.go` (validated on save by `webhook.ValidateURL`).

One adjacent path worth distinguishing: `GetLinkMetadata` reaches out over HTTP too, via `fetchHTMLMeta` / `httpgetter.GetHTMLMeta` (`server/router/api/v1/memo_service.go:28`). That's a URL supplied in the request rather than a stored configuration, and it does **not** route through `webhook.Post` — so it's outside the convergence point above.
