Notes on the path:

**Where the URL comes from.** The browser doesn't get raw image bytes in the API response — `convertUserToProto` rewrites a base64 avatar into a URL of the form `/file/{users/username}/avatar` (`server/router/api/v1/user_service_converters.go:31-36`) specifically to keep responses small. That is the URL the `<img>` tag then requests.

**Handler.** `serveUserAvatar` (`fileserver.go:168`) first gates anonymous access: if `s.Profile.AllowAnonymous()` is false, it resolves the caller via `getCurrentUser` and 401s when there's no valid session/access token/PAT (`fileserver.go:173-181`). Note the lookup is by **username**, not ID — `:identifier` is passed straight through as `FindUser{Username: &identifier}`.

**Storage shape.** The avatar isn't a file on disk or in S3; it's stored inline on the user row as a data URI in `avatar_url`. The handler decodes it with `parseDataURI` (`fileserver.go:736`), rejects anything outside `avatarAllowedTypes` (`fileserver.go:75`, `:201`) as an XSS guard, sets security headers plus `Cache-Control`, and writes the bytes with `c.Blob` (`fileserver.go:205-209`).

**Cache hop.** `Store.GetUser` consults `userCache` only when looking up by ID (`store/user.go:149-156`). Since this path searches by username, it always falls through to `ListUsers` → driver → SQL, then populates the cache on the way back (`store/user.go:166-167`).
