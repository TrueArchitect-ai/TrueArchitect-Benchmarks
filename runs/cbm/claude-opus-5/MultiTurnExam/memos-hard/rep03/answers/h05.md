**Explicit Go code — two targeted `DELETE FROM reaction` statements inside the delete-user transaction, implemented separately in all three drivers. There is no database-level rule that would do it.**

What I checked:

**1. The delete path.** `store.DeleteUser` (`store/user.go:171`) dispatches to the driver. Each driver's `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which removes reactions first, before the memos and the user row:

- `store/db/sqlite/user_delete.go:96` and `:102` — the two calls in `deleteUserTargetsTx` (`user_delete.go:92`)
- `deleteReactionsByContentIDsTx` — `store/db/sqlite/user_delete.go:380-388`, batched at 500 (`deleteUserBatchSize`, `user_delete.go:14`)
- `deleteReactionsByCreatorTx` — `store/db/sqlite/user_delete.go:400-403`

**2. Both directions are covered.** The `reaction` table has no `memo_id`; it points at content by string (`content_id`). So the code deletes on two axes:
- `WHERE creator_id = ?` — reactions *the deleted user made* on anyone's memos.
- `WHERE content_id IN (...)` — reactions *others made* on the deleted user's memos. The content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + memo.UID` (`store/db/sqlite/user_delete.go:512-518`), over the recursive memo tree that also pulls in comment descendants (`listDeleteUserMemoTreeRecursive`, `user_delete.go:133-147`).

**3. All three drivers, independently.** The same pair exists in `store/db/postgres/user_delete.go:383` and `:401`, and `store/db/mysql/user_delete.go:420` and `:438`.

**4. Why it can't be database-level.** The `reaction` table in every schema — `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98` — declares only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint. No `FOREIGN KEY`, no `ON DELETE CASCADE`. Grepping for FK clauses across the migrations shows they exist elsewhere (e.g. `memo_share.memo_id → memo(id) ON DELETE CASCADE` at `store/migration/sqlite/LATEST.sql:109`), which confirms the schema does use cascades where intended — reaction simply isn't one of them. `content_id` being a `"memos/<uid>"` string rather than an integer FK makes a cascade impossible there anyway.
