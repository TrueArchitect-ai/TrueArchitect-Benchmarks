**Explicit Go code — no database-level rule exists for `reaction`; each driver's `DeleteUser` transaction deletes reactions with two explicit statements.**

What I checked, and what it shows:

**1. The delete path in Go.** `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which runs the deletions in order. Two of those steps target reactions:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions *others left on the deleted user's memos*. Content IDs are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs`, over the full memo tree (roots plus `COMMENT`-related descendants gathered by `listDeleteUserMemoTreeIterative`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions *the user left on anyone's content*.

Both run before the memos and the user row are deleted, in batches of 500 (`deleteUserBatchSize`).

All three drivers implement this identically:
- `store/db/sqlite/user_delete.go` — calls at `:96` and `:102`, definitions at `:380` and `:400`
- `store/db/postgres/user_delete.go` — calls at `:96` and `:102`, definitions at `:380` and `:400`
- `store/db/mysql/user_delete.go` — same call sites in `deleteUserTargetsTx`, definitions `deleteReactionsByContentIDsTx` / `deleteReactionsByCreatorTx`

**2. The schema — no cascade to fall back on.** The `reaction` table declares `creator_id` and `content_id` as plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and *no* `FOREIGN KEY` at all: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. A repo-wide grep for `FOREIGN KEY` / `ON DELETE` across `store/migration/` returns hits only for `memo_share` → `memo` in the current schema (e.g. `store/migration/sqlite/LATEST.sql:109`) and for historical tables in old migrations (`store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql`) — never for `reaction`.

Note also that `content_id` is a string key (`"memos/<uid>"`), not an integer FK to `memo.id`, so a database-level cascade from memo deletion isn't even expressible here. The Go code is the only mechanism.
