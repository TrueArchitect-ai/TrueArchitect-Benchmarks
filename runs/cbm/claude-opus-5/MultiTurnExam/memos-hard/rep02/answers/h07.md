Notes on the hops:

- **Where the URL comes from.** The browser gets this path from the API rather than guessing it: `convertUserFromStore` rewrites a base64 avatar into `/file/{user.Name}/avatar` to keep responses small — `server/router/api/v1/user_service_converters.go:31-36`.
- **Service wiring.** `FileServerService` is constructed with the `*store.Store` and registered on the Echo server at `server/server.go:81-82`; `RegisterRoutes` creates the `/file` group at `server/router/fileserver/fileserver.go:121-125`.
- **Access control before the data hop.** On a private instance (`!s.Profile.AllowAnonymous()`), `serveUserAvatar` requires a session/access token/PAT via `s.getCurrentUser` and 401s otherwise — `fileserver.go:170-179`. On a public instance any visitor may fetch another user's avatar.
- **The lookup key is the username**, not an ID: `getUserByUsername` builds `store.FindUser{Username: &identifier}` (`fileserver.go:716`).
- **Cache behavior.** `Store.GetUser` consults `userCache` only when `find.ID` is set (`store/user.go:149-156`), so a username lookup always falls through to `ListUsers` → the driver → SQL; the result is then written back into the cache (`store/user.go:167`).
- **Storage form.** There is no blob table involved — the avatar lives in the `user.avatar_url` column as a data URI, decoded by `parseDataURI` (`fileserver.go:737`), MIME-checked against `avatarAllowedTypes` (`fileserver.go:75`, checked at `:201`), and written with `c.Blob` (`fileserver.go:207`).
