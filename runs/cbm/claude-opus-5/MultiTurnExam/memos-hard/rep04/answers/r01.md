**Premise correction: there is no Redis anywhere in this repository — no client library, no connection config, no code path.** A case-insensitive search for `redis` across all Go sources, `go.mod`, `go.sum`, and docs returns zero hits. The cache layer is process-local and in-memory only.

**Actual mechanism.**

The cache is a hand-rolled in-memory store in `store/cache/cache.go`: a `Cache` struct backed by a `sync.Map` with an atomic item counter (`store/cache/cache.go:66-73`), created by `cache.New(config)` (`:76`), which spawns a background `cleanupLoop` goroutine. Entries are `item` values carrying the value, an absolute `expiration` timestamp, and an approximate size (`:34-39`). It satisfies the `cache.Interface` declared at `store/cache/cache.go:11-32`.

**Configuration site.** Not connection settings but a config struct, built inline in `store.New` at `store/store.go:40-45`:

- `DefaultTTL: 10 * time.Minute`
- `CleanupInterval: 5 * time.Minute`
- `MaxItems: 1000`
- `OnEviction: nil`

That one config is shared by all three caches constructed at `store/store.go:51-53`: `instanceSettingCache`, `userCache`, and `userSettingCache`. The same values are duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), though the store doesn't call that helper — it builds its own copy. Nothing reads these from flags, env, or a config file; there's no way to tune them without editing the source.

**TTL for user entries: 10 minutes**, inherited from `DefaultTTL` because every user write path calls the plain `Set` (which applies `c.config.DefaultTTL` at `store/cache/cache.go:94`) rather than `SetWithTTL` — see `store/user.go:98`, `:122`, `:132`, `:143`, `:167`. Reads consult it in `Store.GetUser`, and only when looking up by ID (`store/user.go:150`); a lookup by username bypasses the cache entirely.

Two practical caveats on that 10 minutes: it's an upper bound, not a guarantee. The 1000-item cap is shared per cache, and exceeding it triggers `cleanupOldest` (`store/cache/cache.go:117-119`), so entries can be evicted early on a busy instance. And user deletion explicitly invalidates the entry via `s.userCache.Delete` (`store/user_delete.go:40`). Since the cache lives in the process heap, it is not shared across replicas — multiple memos instances behind a load balancer each keep their own copy, with up to 10 minutes of staleness relative to the database.
