**No — `mysql.NewDB` is called from exactly one place, the factory in `store/db/db.go:22`, and `store/db/db.go:8` is the only import of the `store/db/mysql` package anywhere in the tree.**

Evidence:

1. **Single constructor.** The MySQL package exports one constructor: `func NewDB(profile *profile.Profile) (store.Driver, error)` at `store/db/mysql/mysql.go:20`. Every other exported symbol in the package is a method on `*DB` (e.g. `store/db/mysql/attachment.go:17`, `store/db/mysql/instance_setting.go:10`, `store/db/mysql/auth_config.go:23`), so a caller cannot get a driver without going through `NewDB`.

2. **Single call site.** `grep -rn "mysql\.NewDB\|store/db/mysql" --include=*.go` across the repo, excluding the package's own directory, returns only two lines — both in the factory: the import at `store/db/db.go:8` and the call at `store/db/db.go:22`, inside `NewDBDriver`'s `case "mysql":` switch arm. No test file, cmd, or server package imports it. Widening the search beyond `.go` files turns up matches only in `docs/plans/**`, which are prose references to driver file paths, not code.

3. **Consumers go through the factory.** The three callers of `db.NewDBDriver` — `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70` — all select the driver by `profile.Driver` string rather than constructing a concrete driver. Notably the test harness does this too, so even MySQL integration tests obtain their driver via the factory.

One nearby thing that is *not* a counterexample: `store/test/containers.go` imports `github.com/go-sql-driver/mysql` (line 16) and calls `sql.Open("mysql", dsn)` (line 145). That is the upstream SQL driver registration plus testcontainers setup for provisioning a MySQL container — it never constructs the repo's `store/db/mysql.DB`.
