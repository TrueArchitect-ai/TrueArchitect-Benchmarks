`dispatchMemoUpdatedSideEffects` (`server/router/api/v1/memo_update_helpers.go:66`) calls `DispatchMemoUpdatedWebhook`, so the two `Set*` handlers reach the webhook layer even though they aren't memo mutations in the obvious sense.

**Convergence.** The four `Dispatch*Webhook` entry points live in `server/router/api/v1/memo_service_webhooks.go`; created/updated/deleted funnel through the shared `dispatchMemoRelatedWebhook` (`memo_service_webhooks.go:48`), while the comment variant has its own loop (`:30`). Both loops end at the same call — `webhook.PostAsync(payload)` at `memo_service_webhooks.go:71` and `:43` — which is the single function every path passes through. It only enqueues onto a bounded 128-slot channel; four worker goroutines started in `init()` (`internal/webhook/webhook.go:42-55`) drain it and call `webhook.Post`, where the outbound request to the user-configured `hook.Url` actually executes via `safeClient.Do` (`internal/webhook/webhook.go:152`).

If you want the convergence point at the moment of delivery rather than hand-off, that's `webhook.Post`; `PostAsync` is where the handler-side call graph collapses to one function.

Two related handlers worth distinguishing: `CreateUserWebhook`/`UpdateUserWebhook` (`server/router/api/v1/user_service_webhooks.go:74`, `:161`, `:182`) touch user-configured URLs but only run `webhook.ValidateURL`, which does a DNS resolution — not an HTTP request.
