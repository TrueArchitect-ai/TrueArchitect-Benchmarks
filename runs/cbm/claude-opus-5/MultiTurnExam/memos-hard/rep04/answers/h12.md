The chain and how each link was pinned down:

1. **Default driver value.** `cmd/memos/main.go:122` sets `viper.SetDefault("driver", "sqlite")` and `cmd/memos/main.go:130` declares the flag with the same default. With no flags, `viper.GetString("driver")` yields `"sqlite"`, which is stored on the profile at `cmd/memos/main.go:43`. (Env override is possible via viper, so this holds for "no database flags / no env override".) `internal/profile/profile.go:110` corroborates it by treating `sqlite` + empty DSN as the default deployment, deriving `memos_prod.db`.

2. **Factory resolution.** `db.NewDBDriver(instanceProfile)` is called once at `cmd/memos/main.go:60`; its body switches on `profile.Driver` at `store/db/db.go:18-27`, so `"sqlite"` selects `sqlite.NewDB(profile)` (`store/db/db.go:20`). The returned `store.Driver` is handed to `store.New` at `cmd/memos/main.go:65` and never re-selected, so the concrete type is fixed for the process lifetime.

3. **Call path to the insert.** The API handler `CreateMemo` (`server/router/api/v1/memo_service.go:70`) calls `s.Store.CreateMemo`; the store method validates the UID then delegates through the interface at `store/memo.go:113` (`s.driver.CreateMemo`). `CreateMemo` is declared on the `store.Driver` interface in `store/driver.go`, and there are exactly three implementations — `store/db/sqlite/memo.go:16`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go`. Step 2 is what disambiguates them; the interface call site alone cannot.

The Postgres and MySQL `CreateMemo` implementations are compiled in but unreachable on a default install.

One implementation detail worth noting: the SQLite path builds the column list dynamically — `created_ts`/`updated_ts` are appended only when non-zero (`store/db/sqlite/memo.go:30-39`) — and uses SQLite's `RETURNING` clause to populate `ID`, timestamps, and `RowStatus` on the passed-in `*store.Memo` in one round trip rather than a follow-up `SELECT`.
