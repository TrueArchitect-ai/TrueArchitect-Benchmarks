**Premise correction: there is no per-user API rate-limiting middleware in this repository — no request-per-interval limiter exists at any layer, so there is no registration site and no request limits to report.**

Evidence: a case-insensitive search for `ratelimit`, `rate_limit`, `rate limit`, `limiter`, and `throttl` across all Go sources returns exactly one hit, and it's a doc comment describing something *not* implemented — "Rate limit email sending to prevent abuse" in a future-work list at `internal/email/doc.go:86`. `go.mod` pulls in no limiter dependency (no `golang.org/x/time/rate`, no `ulule/limiter`, no echo rate-limit middleware).

The complete set of registered middleware/interceptors, none of which counts requests:

- Echo level (`server/server.go:51-52`): `middleware.Recover()` and `newCORSMiddleware(profile)`.
- Static/SPA serving (`server/router/frontend/frontend.go:54,59`).
- Connect interceptor chain (`server/router/api/v1/v1.go:133-138`): `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` — header conversion, logging, panic recovery, and authn/authz respectively (`server/router/api/v1/connect_interceptors.go`).

What does exist are limits of other kinds, which may be what the question is reaching for:

| Mechanism | Limit | Path |
|---|---|---|
| Request body size (gRPC-Gateway, Connect read, Connect handler) | 256 MiB (`maxAPIRequestBytes = 256 << 20`) | `server/router/api/v1/v1.go:20`, applied at `:126`, `:141`, `:144` |
| Concurrent thumbnail generation (file server) | 3 (`maxConcurrentThumbnails`) | `server/router/fileserver/fileserver.go:46,116`, acquired at `:448` |
| Concurrent thumbnail / image processing (API service) | 3 and 2 | `server/router/api/v1/v1.go:59-60`, acquired at `server/router/api/v1/attachment_service_image.go:71` |
| Upload buffer size | 32 MiB (`MaxUploadBufferSizeBytes`) | `server/router/api/v1/attachment_service.go:27,122` |
| Memo content length | instance setting `ContentLengthLimit` | `server/router/api/v1/memo_service.go:595-601`, enforced at `:105` and `:443` |
| Webhook async queue depth | 128, oldest-drop | `internal/webhook/webhook.go:39,189-195` |

These are concurrency and size caps applied globally or per-request — none is keyed by user identity, and none rejects a caller for issuing too many requests over time. Deploying this behind a reverse proxy would be the only way to get per-user rate limiting today.
