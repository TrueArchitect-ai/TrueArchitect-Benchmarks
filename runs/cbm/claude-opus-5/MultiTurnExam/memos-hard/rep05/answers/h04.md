**No — in production code the MySQL driver is constructed only inside the factory.**

Evidence:

1. **Single importer.** Grepping for the package path across all `.go` files returns exactly one hit: `store/db/db.go:8`. No other file in the repo — server, store, cmd, or tests — imports `github.com/usememos/memos/store/db/mysql`. Since Go requires an import to reference an exported identifier, that alone bounds external construction to this one file.

2. **Single call site.** `mysql.NewDB` is referenced exactly once, at `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver` (`store/db/db.go:14-32`). The sibling drivers are called from the same switch (`sqlite.NewDB` at `:20`, `postgres.NewDB` at `:24`), and an unrecognized value returns `errors.New("unknown db driver")` at `:26`. The constructor itself is defined at `store/db/mysql/mysql.go:20` and returns the `store.Driver` interface, so callers get the abstraction rather than the concrete `*DB`.

3. **Two caveats, both benign and both in-package:**
   - `store/db/mysql/mysql.go:29` — `driver := DB{profile: profile}` is `NewDB`'s own struct literal, i.e. the factory-called constructor building its receiver.
   - `store/db/mysql/auth_config_test.go:12` — `db := &DB{}` constructs a zero-value struct in a same-package test. It never opens a connection; it exists only to get a method receiver for `IsRetryableAuthenticationMutationError`, which is a pure error-classification function tested against MySQL error codes 1213/1205/1062 (`:13-15`). This bypasses `NewDB` but is not a driver instantiation in any meaningful sense.

For contrast, SQLite *is* constructed directly outside the factory in tests — `sqlite.NewDB(p)` at `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416` — which is what a genuine out-of-factory construction looks like. MySQL has no equivalent.
