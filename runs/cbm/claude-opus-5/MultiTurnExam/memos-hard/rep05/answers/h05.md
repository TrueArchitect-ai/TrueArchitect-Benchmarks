**Explicit Go code — an in-transaction `DELETE FROM reaction WHERE creator_id = ?` issued by each of the three DB drivers. There is no database-level cascade for reactions.**

What I checked:

**1. The delete path.** `DB.DeleteUser` opens a transaction, collects targets, then calls `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:29-58`). That function runs an ordered sequence of deletes at `store/db/mysql/user_delete.go:88-122`, two of which cover reactions:
- `deleteReactionsByContentIDsTx` (`:95`) — removes reactions *on* the user's memos, including comment descendants. Implemented at `:415-424`, batched 500 at a time (`deleteUserBatchSize`, `:14`), keyed by `content_id`. The content IDs are the string form `"memos/" + memo.UID`, built by `memoContentIDsFromRefs` (`:552-558`), and the memo set comes from the iterative comment-tree walk in `listDeleteUserMemoTreeIterative` (`:126-175`).
- `deleteReactionsByCreatorTx` (`:102`) — removes reactions the user *left elsewhere*, defined at `:437-440`: `DELETE FROM reaction WHERE creator_id = ?`.

Both run before `deleteMemosTx` (`:116`) and `deleteUserRowTx` (`:119`), and the whole set commits atomically at `:52`.

**2. All three drivers, identically.** The same two functions exist per-driver at the same line offsets: `store/db/mysql/user_delete.go:400/437`-equivalents in `store/db/postgres/user_delete.go:383` and `:400-402`, and `store/db/sqlite/user_delete.go:383` and `:400-402`. So the behavior does not depend on which backend is configured.

**3. Ruled out a DB-level rule.** The `reaction` table has no foreign key at all — `creator_id` is a plain `INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint, in all three schemas: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. The original creating migrations match (`store/migration/sqlite/0.20/00__reaction.sql:2-8`, `store/migration/postgres/0.20/00__reaction.sql:2-8`). Grepping `REFERENCES|CASCADE` across `store/migration/` shows cascades on other tables (e.g. `memo_share.memo_id` at `store/migration/sqlite/LATEST.sql:109`, and older user-scoped cascades in `0.5/00__regenerate_foreign_keys.sql`) but none on `reaction` — which is consistent with `content_id` being a string resource name rather than a real FK column, so a cascade wouldn't be expressible for the memo side anyway.

Note the two deletes are complementary and both necessary: the content-ID pass removes *other people's* reactions to the deleted user's memos, while the creator pass removes the deleted user's reactions to memos that survive.
