**Convergence chain.** The four `Dispatch*Webhook` entry points are thin wrappers in `server/router/api/v1/memo_service_webhooks.go`: created/updated/deleted all delegate to `dispatchMemoRelatedWebhook` (`:48`) with a different activity type (`:16`, `:21`, `:26`), while the comment variant (`:30`) is separate because it targets the *related memo owner's* hooks rather than the actor's. Both resolve the owner's configured hooks via `s.Store.GetUserWebhooks` (`:31`, `:57`), then per hook set `payload.URL = hook.Url` and `payload.SigningSecret = hook.SigningSecret` (`:41-42`, `:67-68`) — this is where the user-configured URL enters — and call `webhook.PostAsync` (`:43`, `:71`).

`PostAsync` (`internal/webhook/webhook.go:184`) does not itself perform I/O; it enqueues onto a bounded 128-slot channel (`:39`), dropping with a log warning if full. Four worker goroutines started in `init()` (`:42-55`) drain that queue, and every one of them calls **`webhook.Post`** — so all six handler paths converge on that single function, which builds the request, optionally signs it, and issues `safeClient.Do(req)` at `internal/webhook/webhook.go:152`.

One consequence of the async hop worth noting: because delivery happens on the worker goroutines rather than the request goroutine, webhook failures never surface to the RPC caller — the handlers only log them (e.g. `memo_service.go:157-159`).
