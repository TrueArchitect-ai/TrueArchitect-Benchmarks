**Premise correction: neither. There is no message broker in this repository at all.** Grepping for `nats|rabbitmq|amqp|kafka|nsq|asynq|redis` across all Go sources returns nothing, and `go.mod` declares no broker client dependency (the single `go.sum` hit is a coincidental base64 substring in a hash line, not a package). There is no queue declaration, no exchange/subject binding, and no broker connection string anywhere. The webhook "workers" are goroutines in the same process as the API server, not consumers of an external broker.

**Actual mechanism — an in-process buffered Go channel**

Everything lives in `internal/webhook/webhook.go`:

- **The queue** is a package-level buffered channel with capacity 128, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- **The workers** are 4 goroutines started in the package `init()` (`:42-55`). Each ranges over the channel and calls `Post(payload)` for every item, logging a warning on failure (`:45-51`). Because they're launched from `init()`, they start when the package is first loaded, not from any explicit server-startup wiring — and there is no shutdown path that drains or stops them.
- **The producer** is `PostAsync` (`:184-196`), which does a non-blocking send: `select { case asyncPostQueue <- requestPayload: default: ... }` (`:189-195`). When the buffer is full the payload is **dropped** with a `slog.Warn`, not retried or persisted. It also drops a nil payload with a warning at `:185-187`.
- **Delivery** happens in `Post` (`:120`), which marshals the JSON body, optionally signs it with Standard-Webhooks HMAC headers (`:133-150`), and issues `safeClient.Do(req)` at `:152` through the SSRF-guarded transport.

Practical consequences of it being a channel rather than a broker: delivery is at-most-once with no persistence, no retry, and no dead-letter — anything in the buffer is lost on restart, and overflow is silently dropped past the log line. Concurrency is fixed at 4 in-flight deliveries, each with a 30-second timeout (`:26-27`), and the queue is per-process, so it does not coordinate across multiple server instances.
