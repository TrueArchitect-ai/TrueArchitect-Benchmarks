**Premise correction: there is no Redis in this repository, and no external cache of any kind. A case-insensitive search for "redis" across all Go sources, `go.mod`/`go.sum`, and YAML/JSON config returns zero hits — there is no client dependency, no connection string, and no configuration surface to point at a Redis server.**

The actual mechanism:

- **In-process memory cache.** `store/cache/cache.go` implements a self-contained, thread-safe TTL cache: a `sync.Map` for entries, an atomic item counter, and a background cleanup goroutine (`Cache`, `store/cache/cache.go:66-72`). Entries are `item{value, expiration, size}` (`:34-38`). This is per-process state, so it does not survive a restart and is not shared between instances — relevant if you were considering a multi-replica deployment.

- **Configuration site.** Not a connection — a struct literal in `store.New` (`store/store.go:40-45`): `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil`. The same `cacheConfig` value is handed to all three caches created there — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). `cache.DefaultConfig()` (`store/cache/cache.go:56-63`) declares identical values but is not what the store uses; the store inlines its own copy.

- **TTL for user entries: 10 minutes**, inherited from that `DefaultTTL`. Every user cache write goes through `Set` — `store/user.go:98`, `:122`, `:132`, `:143`, `:167` — and `Set` forwards to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:94`). Nothing in the store calls `SetWithTTL` directly, so no user entry ever gets a custom TTL. Entries are also evicted early on explicit `Delete` (e.g. `deleteUserCache`, `store/user_delete.go:39`) and when the 1000-item cap is hit.

- **No environment or flag override.** The cache values are hardcoded at `store/store.go:40`; `internal/profile/profile.go` carries no cache settings, so there's nothing to tune without a code change.

One nuance if you're reasoning about cache hit rates: `Store.GetUser` only consults `userCache` when the lookup is by ID (`store/user.go:149-156`). Lookups by username or email always hit the database and then populate the cache keyed by ID.
