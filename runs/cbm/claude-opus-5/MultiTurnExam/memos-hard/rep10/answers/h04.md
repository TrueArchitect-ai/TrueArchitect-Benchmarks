**No — in production code the MySQL driver is constructed only by the factory. The single exception is one in-package unit test that builds a zero-value struct, not a real driver.**

Evidence:

1. **Only one call to `mysql.NewDB` exists in the entire repo**, and it's inside the factory: `store/db/db.go:22`, in the `case "mysql"` branch of `NewDBDriver`. A repo-wide grep for `mysql.NewDB` / `mysql.New` returns exactly that line.

2. **Only one file imports the package at all.** Grepping the full import path `github.com/usememos/memos/store/db/mysql` across all Go files yields a single hit — `store/db/db.go:8`. (The other textual matches are `docs/plans/*.md`, which merely list filenames in planning docs, not code.) Since Go requires an import to reference `mysql.NewDB` or the exported `mysql.DB` type from outside the package, this import graph alone rules out external direct construction.

3. **All driver acquisition funnels through the factory.** Every `NewDBDriver` caller — `store/test/store.go:28`, `store/test/store.go:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70` — selects by `profile.Driver` string rather than naming a concrete driver, so even the MySQL integration tests reach the driver via the factory.

The one caveat, stated precisely: `store/db/mysql/auth_config_test.go:12` does `db := &DB{}` — a direct composite-literal construction. But it is *inside* package `mysql` (so it needs no import and is invisible to external callers), and it deliberately creates an empty struct with nil `db`/`profile`/`config` fields purely to invoke the pure-logic method `IsRetryableAuthenticationMutationError` on MySQL error codes 1213/1205/1062. It never opens a connection — `NewDB` (`store/db/mysql/mysql.go:20`) is what parses the DSN and calls `sql.Open`. So it is not a functioning driver instance and does not constitute an alternate construction path.
