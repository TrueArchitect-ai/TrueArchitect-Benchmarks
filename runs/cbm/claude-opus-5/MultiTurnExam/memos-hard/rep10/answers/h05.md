**Explicit Go code — two hand-written `DELETE FROM reaction` statements per driver, inside the delete-user transaction. There is no database-level cascade for reactions.**

What I checked:

**1. The Go delete path.** Each driver's `DeleteUser` opens a transaction, collects targets, then runs `deleteUserTargetsTx`, which issues the reaction deletes explicitly (`store/db/sqlite/user_delete.go:96` and `:102`; identical structure at `store/db/mysql/user_delete.go:96`/`:102` and `store/db/postgres/user_delete.go:96`/`:102`). Two distinct passes are needed:

- `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380`) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`deleteUserBatchSize`, `:14`). This removes reactions *other people* left on the deleted user's memos.
- `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400`) — `DELETE FROM reaction WHERE creator_id = ?`. This removes the reactions *the deleted user* left on anyone's memos, which is what the question asks about.

The whole set runs before `tx.Commit()` (`store/db/sqlite/user_delete.go:50`), so reaction cleanup is atomic with the user row deletion; a test-only failpoint (`store/user_delete.go:14`, checked at `store/db/sqlite/user_delete.go:46`) exists to force a rollback and verify that.

**2. The schema — ruling out a DB-level rule.** The `reaction` table is declared with no foreign key at all in any of the three dialects: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`. Each has just `creator_id`, `content_id`, `reaction_type` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `REFERENCES user(id)`, so no `ON DELETE CASCADE` is possible.

To be sure this wasn't a schema-wide omission, I listed every `REFERENCES` in the SQLite schema: the only one in the current schema is `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`). So cascades do exist in this codebase — reactions simply aren't covered by one, which is exactly why the explicit Go deletes are required.

Note also `content_id` is a `VARCHAR`/`TEXT` holding a memo UID rather than an integer memo id, which forecloses an FK on that column too — reinforcing that application code is the only cleanup mechanism.
