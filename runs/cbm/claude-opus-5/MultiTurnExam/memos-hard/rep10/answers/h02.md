**`webhook.Post` — `internal/webhook/webhook.go:120` (the actual `safeClient.Do(req)` call is at `internal/webhook/webhook.go:152`); protection is the SSRF-guarding dialer `safeDialContext` + `isReservedIP` — `internal/webhook/webhook.go:59` and `internal/webhook/validate.go:44`**

How it fits together:

- **Delivery path.** Memo create/update/delete/comment events call `webhook.PostAsync` (`server/router/api/v1/memo_service_webhooks.go:43`, `:71`), which just enqueues onto a bounded 128-slot channel (`internal/webhook/webhook.go:184-196`, dropping with a warning when full). Four worker goroutines started in `init()` (`internal/webhook/webhook.go:42-55`) drain that queue and call `Post`, so `Post` is where the outbound HTTP request actually executes.

- **Primary protection (dial-time).** All dispatches share `safeClient` (`internal/webhook/webhook.go:32-37`), whose `Transport.DialContext` is `safeDialContext`. That function resolves the hostname itself and refuses to dial if *any* resolved address falls in a reserved range (`internal/webhook/webhook.go:59-77`). Because the check happens at dial time on the addresses actually being connected to, it also defeats DNS rebinding — a TOCTOU attack that a validate-only check would miss.

- **The blocklist.** `isReservedIP` (`internal/webhook/validate.go:44`) tests against `reservedNetworks`, parsed once at init from `reservedCIDRs` (`internal/webhook/validate.go:14-23`): IPv4 loopback, all three RFC-1918 ranges, link-local `169.254.0.0/16` (which covers the cloud IMDS endpoint `169.254.169.254`), plus the IPv6 equivalents `::1/128`, `fc00::/7`, `fe80::/10`.

- **Secondary, up-front check.** `webhook.ValidateURL` (`internal/webhook/validate.go:62`) runs when a user registers or updates a webhook URL (`server/router/api/v1/user_service_webhooks.go:74`, `:161`, `:182`). It enforces http/https scheme and rejects hostnames resolving to reserved IPs, returning a gRPC `InvalidArgument` for a clean error at configuration time.

- **Escape hatch.** The package-level `AllowPrivateIPs` flag (`internal/webhook/validate.go:41`) short-circuits `isReservedIP`, disabling both layers for self-hosted setups targeting LAN services. Note that within this repo's Go source, nothing assigns it outside of tests — the `--allow-private-webhooks` flag referenced in `CHANGELOG.md:121` has no corresponding wiring I could find in the current tree, so as it stands the protection is always on in production.

Two things worth flagging as caveats rather than protections: the response body is capped at 1 MiB via `io.LimitReader` (`internal/webhook/webhook.go:158`) and there's a 30s client timeout (`:27`), but redirects are handled by the default `http.Client` policy — a redirect to an internal address is still caught, since every hop goes through `safeDialContext`.
