Notes on the hops:

- **Where the URL comes from.** The browser only requests this path because the API rewrote it: `convertUserFromStore` replaces a base64 `AvatarURL` with `/file/{user}/avatar` (`server/router/api/v1/user_service_converters.go:36`) to keep raw image data out of JSON responses. If the stored avatar is a plain URL rather than a data URI, it's passed through as-is (`:38`) and no server hop happens at all.

- **Access control.** `serveUserAvatar` gates on `s.Profile.AllowAnonymous()` (`fileserver.go:173`): on a private instance an unauthenticated viewer gets 401; on a public instance any browser can fetch any user's avatar by username.

- **The data is in the user row, not the attachment table.** `user.AvatarURL` holds a `data:` URI; `parseDataURI` (`fileserver.go:737`) regex-matches and base64-decodes it, the MIME type is checked against `avatarAllowedTypes` (`fileserver.go:75`, `:201`), then it's written with `c.Blob` (`fileserver.go:209`). So the "stored data" endpoint is the `avatar_url` column of the `user` table — no filesystem or S3 hop, unlike `serveAttachmentFile`.

- **Cache short-circuit.** `Store.GetUser` consults `userCache` only when `find.ID` is set (`store/user.go:149-156`). This lookup goes by `Username`, so it always falls through to `ListUsers` → driver → SQL; the result is then written into the cache keyed by ID (`store/user.go:167`).

- **Driver dispatch** is via the `store.Driver` interface held in `Store.driver`, selected at startup by `NewDBDriver` (`store/db/db.go:14`); the SQLite implementation is cited above, with identical `ListUsers` implementations in `store/db/mysql/user.go` and `store/db/postgres/user.go`.
