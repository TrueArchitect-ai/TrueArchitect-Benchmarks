**Premise correction: neither. There is no message broker in this codebase — a search across all Go sources, `go.mod`, and `go.sum` for `nats`, `rabbitmq`, `amqp`, `kafka`, and `streadway` returns zero hits. There is no external queue, and therefore no queue declaration.**

The actual mechanism — an in-process buffered Go channel:

- **The "queue" is a package-level channel**: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` at `internal/webhook/webhook.go:39`. Capacity 128, in-memory, per-process.

- **The "workers" are four goroutines started in `init()`** (`internal/webhook/webhook.go:42-55`). Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. They start on package import, not via any explicit server wiring, and there is no graceful drain on shutdown.

- **Producers enqueue via `PostAsync`** (`internal/webhook/webhook.go:184-196`). Note the delivery semantics this implies: the send is a non-blocking `select` with a `default` branch, so **when the buffer is full the event is dropped**, with a warning naming the URL and activity type (`:192-194`). That's at-most-once delivery with no retry, no persistence, and no dead-letter — events are lost on queue saturation or process restart, which is the main practical difference from a real broker.

- **Delivery itself happens in `Post`** (`internal/webhook/webhook.go:120`), which marshals the payload, optionally adds Standard Webhooks HMAC headers (`:133-150`), and issues the request through the SSRF-guarded `safeClient` at `:152`.

Producers are the memo lifecycle handlers, which call `webhook.PostAsync` from `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.
