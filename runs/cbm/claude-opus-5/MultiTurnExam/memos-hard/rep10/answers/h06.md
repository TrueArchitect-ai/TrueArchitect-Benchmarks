**Handlers: `CreateMemo`, `UpdateMemo`, `DeleteMemo`, `CreateMemoComment`, `SetMemoRelations`, `SetMemoAttachments`; convergence function — `webhook.Post` — `internal/webhook/webhook.go:120` (all six paths funnel into it via the single enqueue point `webhook.PostAsync`, `internal/webhook/webhook.go:184`)**

The last three of these are the non-obvious ones: `SetMemoRelations` and `SetMemoAttachments` don't look like content-change RPCs, but both touch the memo timestamp and then call the shared `dispatchMemoUpdatedSideEffects` (`server/router/api/v1/memo_update_helpers.go:66`), which fires the `memos.memo.updated` webhook exactly as `UpdateMemo` does.

**Convergence.** All `Dispatch*Webhook` methods live in `server/router/api/v1/memo_service_webhooks.go`; each loads the target user's webhooks via `s.Store.GetUserWebhooks` and calls `webhook.PostAsync` (`memo_service_webhooks.go:43` and `:71`). `PostAsync` only enqueues onto a bounded 128-slot channel; four worker goroutines started in `init()` (`internal/webhook/webhook.go:42-55`) drain it and call `webhook.Post`, where the actual `safeClient.Do(req)` executes (`internal/webhook/webhook.go:152`). So `Post` is the single chokepoint for outbound delivery — which is why the SSRF guard only needs to live there (`safeDialContext`, `internal/webhook/webhook.go:59`).

The URL is user-configured in the strict sense: it comes from the webhook record the user registered through `user_service_webhooks.go` (validated at `:74`, `:161`, `:182`).

One adjacent case worth distinguishing: `GetLinkMetadata` / `BatchGetLinkMetadata` (`server/router/api/v1/memo_service_link_metadata.go:14`, via `httpgetter.GetHTMLMeta` bound at `memo_service.go:28`) also makes outbound HTTP to a URL the caller supplies. I've excluded it because that URL is a per-request argument rather than stored user configuration, and it does not pass through `webhook.Post`.
