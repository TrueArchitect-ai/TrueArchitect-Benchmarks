**Premise correction: there is no nightly database-cleanup job, and the cron scheduler that exists is never used by the server — so there is no schedule to report.**

Two separate corrections:

**1. No database-cleanup job exists at all.** Searching the server, cmd, and store trees for `cleanup`/`purge`/`prune`/`nightly`/`cron` turns up no scheduled data-maintenance work. The only "cleanup" hits are unrelated: the in-memory cache's expiry goroutine on a 5-minute interval (`store/cache/cache.go:47`, `:199`; configured at `store/store.go:42`), best-effort deletion of a provisional SSO user row (`server/router/api/v1/auth_service_sso.go:76`), and attachment-blob removal during user deletion (`server/router/api/v1/user_service.go:421-450`). All of these are event-driven or in-process — none touches the database on a clock.

**2. The cron scheduler is dead code.** `internal/scheduler/` is a complete cron implementation — cron-expression parser (`internal/scheduler/parser.go`), job type (`job.go`), middleware for recovery/logging/timezone (`middleware.go`), plus a README and doc.go. But grepping the whole repo for `scheduler.` outside the package itself returns nothing in non-test code: `scheduler.New` is called only from `internal/scheduler`'s own tests and examples. It is not imported by `server/`, `cmd/`, or `store/`, so no job of any kind is registered with it.

**What actually runs on a schedule.** Exactly one background runner: `s3presign.Runner` (`server/runner/s3presign/runner.go`), which refreshes expiring S3 presigned URLs. It is driven by a plain `time.Ticker` at `runnerInterval = 12 hours` (`server/runner/s3presign/runner.go:27`, ticker at `:30`) — an interval, not a wall-clock time, so it fires 12h after process start and every 12h thereafter, plus one immediate `RunOnce` at boot. It's wired in `Server.startBackgroundRunners` (`server/server.go:162-171`). Since it's interval-based off startup time, there is no fixed hour it runs at.

If you want a nightly database-cleanup job, `internal/scheduler` is already built and tested for it; the wiring point would be `startBackgroundRunners` at `server/server.go:153`, alongside the existing runner.
