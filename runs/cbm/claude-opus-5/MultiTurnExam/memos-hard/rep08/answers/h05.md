**Explicit Go code** — two hand-written `DELETE FROM reaction` statements inside each driver's `DeleteUser` transaction. There is no database-level cascade for reactions.

What I checked:

**1. The delete path.** `store.Store.DeleteUser` (`store/user.go:171-181`) just delegates to `s.driver.DeleteUser`. Each driver implements it in its own `user_delete.go`, all with the same structure: begin a transaction, collect targets, then run `deleteUserTargetsTx`.

**2. The explicit reaction deletes.** `deleteUserTargetsTx` calls two separate reaction cleanups — and they cover two distinct cases:

| | sqlite | mysql | postgres |
|---|---|---|---|
| by `content_id` (reactions *others* left on this user's memos) | `store/db/sqlite/user_delete.go:381` | `store/db/mysql/user_delete.go:420` | `store/db/postgres/user_delete.go:383` |
| by `creator_id` (reactions *this user* left elsewhere) | `store/db/sqlite/user_delete.go:399` | `store/db/mysql/user_delete.go:438` | `store/db/postgres/user_delete.go:401` |

The `content_id` variant is driven by `memoContentIDsFromRefs`, which builds `"memos/" + memo.UID` strings from the recursive memo tree (`store/db/sqlite/user_delete.go` — `memoContentIDsFromRefs`, and the `WITH RECURSIVE memo_tree` query in `listDeleteUserMemoTreeRecursive`). Both run in batches of 500 (`deleteUserBatchSize`) and execute before the memo and user rows are deleted, inside the same transaction (`deleteUserTargetsTx`).

**3. Ruling out a database-level rule.** The `reaction` table carries no foreign keys in any dialect — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`
- original creation: `store/migration/sqlite/0.20/00__reaction.sql:2-8` (and the postgres/mysql equivalents)

A grep for `FOREIGN KEY` / `ON DELETE` across `store/migration` shows the only cascade in the current schema is `memo_share.memo_id → memo(id) ON DELETE CASCADE` (e.g. `store/migration/sqlite/LATEST.sql:109`). The older per-table `ON DELETE CASCADE` constraints on `creator_id → user(id)` exist only in legacy migrations like `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql`, and never applied to `reaction`, which was introduced later in 0.20. Note also that `content_id` is a text string (`"memos/{uid}"`), not an integer memo id, so it could not be a foreign key even in principle.
