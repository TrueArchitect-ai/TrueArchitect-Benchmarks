**Premise correction: neither. There is no message broker in this project — no NATS, no RabbitMQ, no Kafka, AMQP, or SQS — and therefore no queue declaration.** A case-insensitive grep across all `.go` files for `nats|rabbitmq|amqp|kafka|pubsub|sqs` returns zero hits, and `go.mod` declares no broker client dependency. There is no connection URL, exchange, or topic configuration anywhere; `cmd/memos/main.go` exposes no broker flags.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool**, entirely inside `internal/webhook/webhook.go`.

- **The "queue"** is a package-level buffered channel of 128 slots, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- **The workers** are four goroutines started in that package's `init()` (`webhook.go:42-55`). Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. They start when the package is first imported and live for the process lifetime — there is no shutdown path that drains or stops them.
- **The producer** is `PostAsync` (`webhook.go:184-196`), called from the memo webhook dispatchers at `server/router/api/v1/memo_service_webhooks.go:43,71`. It does a non-blocking `select` send: if the buffer is full, the event is **dropped** with a warning rather than blocking the RPC (`webhook.go:189-195`). It also drops nil payloads (`:185-188`).
- **Delivery** happens in `Post` (`webhook.go:120-180`) — JSON-marshals the payload, optionally adds Standard-Webhooks HMAC headers, and POSTs via `safeClient` (`webhook.go:152`).

The practical consequences of it being a channel rather than a broker: the queue is per-process and in-memory, so pending deliveries are lost on restart; there is no persistence, no acknowledgement, no retry (a failed `Post` is logged and discarded), no dead-letter handling, and no cross-instance sharing if you run multiple servers. Concurrency is capped at 4 in-flight deliveries.
