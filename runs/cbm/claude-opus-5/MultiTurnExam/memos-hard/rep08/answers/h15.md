Two structural notes. The enforcement splits into two idioms: *gates* that reject a request after loading a memo (`checkMemoReadAccess`, `checkAttachmentPermission`, `checkAttachmentAccess`, `canReceive`) and *filters* that constrain the query up front via `FindMemo.VisibilityList` (`ListMemos`, the two stats handlers, both RSS handlers, the sitemap) — the latter never load non-visible rows at all. Note the three `canViewerAccessMemo`-style helpers are near-duplicate logic in three files, differing only in the admin check (`viewer.Role == store.RoleAdmin` vs `isSuperUser(viewer)`).

The MCP surface (`server/router/mcp`) is **not** a separate site: `catalog.go:12,14` whitelists `MemoService_ListMemos`/`MemoService_GetMemo` and proxies to the same API handlers, inheriting their checks. The share-token path is the one deliberate bypass — a valid, unexpired `memo_share` grants attachment access regardless of visibility (`server/router/fileserver/fileserver.go:683-689`, using `isMemoShareExpired` from `server/router/api/v1/memo_share_service.go:195`).
