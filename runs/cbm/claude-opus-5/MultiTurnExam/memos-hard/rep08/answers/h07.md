Details per hop:

- **Route registration**: `FileServerService.RegisterRoutes` binds `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` at `server/router/fileserver/fileserver.go:120`, wired into startup at `server/server.go:81-82`.
- **`serveUserAvatar`** (`fileserver.go:161`): if the instance isn't public (`!s.Profile.AllowAnonymous()`) it first requires a viewer via `s.getCurrentUser`, returning 401 otherwise (`:165-173`). It then reads the `:identifier` path param and looks the user up.
- **`getUserByUsername`** (`fileserver.go:715`): a one-line pass-through — `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`. Note the identifier is always treated as a username, never an ID.
- **`Store.GetUser`** (`store/user.go:148`): consults `userCache` only when `find.ID` is set — since this path filters by username, the cache is always missed and it falls through to `ListUsers`, taking `list[0]` and populating the cache on the way back (`:158-168`).
- **`Store.ListUsers`** (`store/user.go:136`): delegates to `s.driver.ListUsers` and warms `userCache` for each row.
- **Driver `ListUsers`** (`store/db/sqlite/user.go:88`): builds `WHERE username = ?` (`:127-129`) and issues the `SELECT id, username, role, email, nickname, password_hash, avatar_url, … FROM user` query (`:150-165`) — `avatar_url` is the column carrying the image.

Back in the handler, the stored `user.AvatarURL` is not a file reference: it's a base64 data URI, decoded in-process by `parseDataURI` (`fileserver.go:737`, using `dataURIRegex` at `:94`), MIME-checked against `avatarAllowedTypes` (`:74-82`, enforced at `:200`), and written out with `c.Blob` plus security and `Cache-Control: public, max-age=3600` headers (`:204-208`). So the avatar bytes live in the `user.avatar_url` column itself — no filesystem or S3 hop.
