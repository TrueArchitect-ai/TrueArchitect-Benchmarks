**Premise correction: neither. There is no message broker in this repository — no NATS, no RabbitMQ, no queue declaration anywhere. Webhook delivery uses an in-process Go channel.**

Evidence for the correction: searching all Go sources and `go.mod` for `nats`, `rabbitmq`, `amqp`, `kafka`, `sqs`, `nsq`, `pubsub`, and Go job-queue libraries (`asynq`, `machinery`) returns zero real matches — the handful of apparent hits are substring artifacts (`migrationSQL`/`driver` matching `nsq`/`river`). `go.mod` (lines 6-43) lists no broker client; the only network-service dependencies are AWS S3, OpenAI/genai, and the SQL drivers.

**Actual mechanism** — a bounded buffered channel with a fixed worker pool, all inside one process:

- **The "queue":** `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a package-level Go channel declared at `internal/webhook/webhook.go:39`. That single line is the closest thing to a "queue declaration"; it is not durable and not shared across instances.
- **The workers:** four goroutines started in the package `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post` for every payload, logging a warning on failure.
- **The producer:** `PostAsync` (`internal/webhook/webhook.go:184`) does a non-blocking `select` send (`:189-195`). When the buffer is full it takes the `default` branch and **drops** the payload with a `"Dropped webhook dispatch because the async queue is full"` warning — there is no retry, no dead-letter, and no persistence, so events are lost on overflow or process exit.
- **Delivery:** `webhook.Post` (`internal/webhook/webhook.go:120`) builds the JSON body, optionally signs it (HMAC-SHA256 Standard Webhooks headers, `:133-150`), and sends via `safeClient.Do` at `:152`.

Producers are the memo RPC handlers, which reach `PostAsync` through `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.
