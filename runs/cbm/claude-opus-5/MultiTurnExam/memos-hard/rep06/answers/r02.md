**Premise correction: there is no per-user API rate-limiting middleware in this repository — none is registered anywhere, and there are no request limits to report.**

What I checked:

- A repo-wide grep across Go sources and `go.mod` for `rate limit`, `ratelimit`, `throttle`, `golang.org/x/time/rate`, `leaky`, and `token bucket` returns exactly one hit, and it is not an implementation: a "could add rate limiting" suggestion in a doc comment at `internal/email/doc.go:86`. The only other mentions in the tree are aspirational docs — `internal/email/README.md:286-295` sketches rate limiting as a future enhancement for email sending. No `golang.org/x/time/rate` or equivalent limiter package appears in `go.mod`.

- The actual middleware stack is short and contains no limiter. Echo-level: `middleware.Recover()` and the CORS middleware, both at `server/server.go:51-52` (CORS config in `server/cors.go:14`). Connect/RPC-level: exactly three interceptors registered at `server/router/api/v1/v1.go:133-136` — `MetadataInterceptor`, `LoggingInterceptor`, and `RecoveryInterceptor`, all defined in `server/router/api/v1/connect_interceptors.go`. Authentication/authorization is separate (the shared authorizer at `server/router/api/v1/v1.go:65-` and the ACL config in `server/router/api/v1/acl_config.go`), and it gates *who* may call an endpoint, not *how often*.

The nearest thing that exists is server-wide concurrency capping, which is not per-user and does not reject requests — callers block rather than receive a 429:

- `thumbnailSemaphore: semaphore.NewWeighted(3)` and `imageProcessingSemaphore: semaphore.NewWeighted(2)` — `server/router/api/v1/v1.go:59-60`
- `thumbnailSemaphore: semaphore.NewWeighted(maxConcurrentThumbnails)` — `server/router/fileserver/fileserver.go:116`

There are also fixed-size work queues that shed load rather than throttle it — e.g. the 128-slot webhook dispatch channel that drops payloads when full (`internal/webhook/webhook.go:39`, `:189-195`) — but again, that's outbound and not a per-user API limit.
