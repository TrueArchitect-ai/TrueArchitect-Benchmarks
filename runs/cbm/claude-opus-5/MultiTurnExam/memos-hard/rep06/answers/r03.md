**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never used by the running server — so there is no schedule to report.**

Two separate parts of the premise fail:

**1. The cron scheduler isn't wired into the application.** `internal/scheduler` is a complete, self-contained cron package (`internal/scheduler/scheduler.go`, `parser.go`, `job.go`, `middleware.go`, plus a README and `doc.go`), but grepping for its import path across the repo returns only its own test files — `internal/scheduler/example_test.go:10` and `internal/scheduler/integration_test.go:13`. No production package imports it; `scheduler.New`, `Register`, and `ParseCronExpression` have no non-test callers. The `scheduler.New(...)` and `WithTimezone("America/New_York")` snippets that turn up in a grep are illustrative comments in `internal/scheduler/doc.go:12-32`, not registrations.

**2. No database-cleanup job exists, cron-scheduled or otherwise.** There is no vacuum, purge, prune, or retention task anywhere in `server/`, `store/`, or `cmd/`. The only background work registered at startup is the S3 presign refresher — `s3presignRunner` in `Server.startBackgroundRunners` (`server/server.go:162-171`), which runs on a 12-hour `time.Ticker` (`server/runner/s3presign/runner.go:27`), not a cron expression and not at a fixed wall-clock time.

The grep hits that sound like cleanup are all something else: `store/cache/cache.go:83` / `store/store.go:42` are the in-memory cache's 5-minute expiry sweep (per-process, not the database); `store/attachment.go:171` and `server/router/api/v1/user_service.go:421-450` are synchronous, request-triggered deletion of blob storage during memo/user deletion, not scheduled maintenance.
