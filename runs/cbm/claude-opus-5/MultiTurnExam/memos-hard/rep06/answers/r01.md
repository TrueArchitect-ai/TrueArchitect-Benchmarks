**Premise correction: there is no Redis (or any external cache server) in this repository. The cache layer is a process-local, in-memory map — so there is no connection to configure. User entries get a 10-minute TTL from the shared default cache config.**

Evidence for the correction: grepping the whole repo — Go sources, `go.mod`, `go.sum`, YAML, and docs — for `redis`, `memcach`, or `valkey` returns zero hits. There is no client dependency and no connection string, host, port, or DSN for a cache server anywhere.

**Actual mechanism.** `store/cache/cache.go` implements a thread-safe in-memory cache: a `sync.Map` of `item{value, expiration, size}` (`store/cache/cache.go:35-39`, `:67-73`) guarded by an atomic item counter, with a background `cleanupLoop` goroutine (`:200`) sweeping expired entries and `cleanupOldest` (`:253`) shedding ~20% when `MaxItems` is exceeded. It's constructed with `cache.New(config)` (`:76`) — a plain struct, no dialing, no I/O.

**Where it's configured.** `store.New` builds one `cache.Config` and shares it across three caches (`store/store.go:39-53`):

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

instantiating `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`, `:50-52`). An identical set of values is also in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), though `store.New` declares its own copy rather than calling it.

**TTL for user entries: 10 minutes.** `userCache` is populated only via `Set` — `store/user.go:143` (in `ListUsers`) and `store/user.go:167` (in `GetUser`) — and `Cache.Set` forwards to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`), i.e. the 10 minutes above. No user code path calls `SetWithTTL` with a custom duration, so all three caches share that TTL. Expiry is enforced both lazily on read (`store/cache/cache.go:135-144`) and by the 5-minute sweep.

Two consequences worth noting, since they're what a Redis setup would change: the cache is per-process, so a multi-instance deployment would not share or invalidate entries across instances; and it's lost on restart. Explicit invalidation on writes is handled in-process — e.g. `Store.DeleteUser` calls `deleteUserCache` (`store/user.go:171-180`), and `Store.Close` shuts down all three cleanup goroutines (`store/store.go:74-76`).
