**Explicit Go code — deleted by hand-written SQL inside the `DeleteUser` transaction in all three store drivers. There is no DB-level cascade for reactions.**

What I checked:

**1. The Go delete path.** Each driver's `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which runs two separate reaction deletes:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions *by anyone* on the deleted user's memos. Content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + memo.UID` strings (`store/db/mysql/user_delete.go:~440`), matching the `content_id` column format.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing the deleted user's own reactions on *other people's* memos.

Both are invoked from `deleteUserTargetsTx`, ordered before the memo and user row deletes:
- MySQL: `store/db/mysql/user_delete.go:96` and `:102`; definitions at `:380` and `:400`
- Postgres: `store/db/postgres/user_delete.go:96` and `:102`; definitions at `:380` and `:400`
- SQLite: `store/db/sqlite/user_delete.go:96` and `:102`; definitions at `:380` and `:400`

The memo set is gathered transitively first — `listDeleteUserMemoTreeIterative` walks `memo_relation` `COMMENT` edges to pull in descendant comment threads — so reactions on comments under the user's memos are covered too. Deletes are batched at 500 IDs (`deleteUserBatchSize`).

**2. The schema — no cascade exists.** The `reaction` table declares no foreign keys in any dialect: `store/migration/mysql/LATEST.sql`, `store/migration/postgres/LATEST.sql`, `store/migration/sqlite/LATEST.sql` each define it with only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Same in the original `store/migration/*/0.20/00__reaction.sql`; the `0.23/00__reactions.sql` migration only rewrites `reaction_type` values to emoji.

Grepping `FOREIGN KEY|REFERENCES|ON DELETE` across all three `LATEST.sql` files returns exactly one hit each — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (mysql:108, postgres:108, sqlite:109). Nothing references `user(id)`, and nothing touches `reaction`. (Historical SQLite migrations such as `sqlite/0.5/00__regenerate_foreign_keys.sql` did define user cascades, but those predate the `reaction` table and are not in the current schema.) `CREATE TRIGGER` occurrences are all `updated_ts` bookkeeping, not deletion logic.

A cascade also couldn't work for the content side regardless: `content_id` stores a `memos/{uid}` string rather than a memo FK, so that half is only expressible in application code.
