**Premise correction: neither. There is no message broker in this repository** — no NATS, no RabbitMQ, no AMQP, Kafka, or NSQ client in `go.mod`/`go.sum` or any Go source. The 11 apparent matches from a broker-name search are all false positives: substring hits on `openMigrationSQLDB` / `execMigrationSQL` in `store/test/migrator_upgrade_test.go`. There is no queue declaration to point to, and nothing consumes from an external system.

**Actual mechanism — an in-process buffered Go channel with a fixed worker pool**, entirely inside `internal/webhook/webhook.go`:

- **The "queue"** is a package-level channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`). Capacity 128, declared as a package var — no broker connection, no topic/exchange, no durability.

- **The "workers"** are 4 goroutines started in `init()` (`webhook.go:42-55`). Each ranges over the channel and calls `Post(payload)` (`:46`), logging a warning on failure (`:47-51`). The pool size is a hardcoded `for range 4`.

- **Producers** call `PostAsync` (`webhook.go:184`), which does a non-blocking send via `select` with a `default` branch (`:189-195`). When the buffer is full the payload is **dropped** with a warning — no retry, no dead-letter, no persistence. Producers are the memo lifecycle dispatchers in `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

- **Delivery** happens in `Post` (`webhook.go:120`), which marshals the payload, optionally signs it with HMAC-SHA256 Standard Webhooks headers (`:133-150`), and sends via the SSRF-guarded `safeClient` (`:152`).

Practical implications of this being a channel rather than a broker: the queue is per-process (not shared across replicas), non-durable (anything buffered is lost on restart or shutdown — the workers aren't drained by `Server.Shutdown`), and delivery is at-most-once with no backoff or redelivery.
