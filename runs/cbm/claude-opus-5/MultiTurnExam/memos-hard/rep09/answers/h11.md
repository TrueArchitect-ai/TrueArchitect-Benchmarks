**1st: `store.User` — ~6 packages outside the data layer; 2nd: `store.Memo` — ~4 packages.**

Method: the data layer is the `store/` tree (entity structs declared in `store/*.go`, drivers in `store/db/*`). For each persistent entity type I counted the distinct packages *outside* `store/` that reference `store.<Type>`, using a trailing non-identifier guard so `store.User` doesn't absorb `store.UserSetting` / `store.UserIdentity`.

Ranking (non-test files, packages outside `store/`):

| Type | Packages | File refs |
|---|---|---|
| **`store.User`** | **6** | 21 |
| **`store.Memo`** | **4** | 14 |
| `store.Attachment` | 3 | — |
| `store.Inbox`, `store.MemoShare` | 2 | — |
| `store.Reaction`, `store.MemoRelation`, `store.UserIdentity`, `store.IdentityProvider`, `store.UserSetting`, `store.InstanceSetting` | 1 | — |

**`store.User`** — `server/auth`, `server/notification`, `server/router/api/v1`, `server/router/api/v1/test`, `server/router/fileserver`, `server/router/rss`. Its breadth follows from being the identity carried through authentication (`server/auth`) and the permission checks in every serving path, including the non-gRPC file server (`server/router/fileserver/fileserver.go`, e.g. `getUserByUsername` at `:715`).

**`store.Memo`** — `server/notification`, `server/router/api/v1`, `server/router/rss`, `server/runner/memopayload` (`server/runner/memopayload/runner.go`, `RebuildMemoPayload`).

Two caveats on the counts:
- `server/router/api/v1/test` is a test-support package; its files aren't named `*_test.go`, so they survive a `--exclude=*_test.go` filter. Excluding it by intent, `store.User` sits at **5** packages and still leads.
- Including `_test.go` files raises the totals to 7 (`User`) and 6 (`Memo`), preserving the same ordering.

Either way `store.User` is first and `store.Memo` second. Note the gap is in *package* spread, not raw usage — within `server/router/api/v1` alone, `User` appears in 15 files and `Memo` in 11, so both are heavily concentrated in that one API package.
