**No — in production code the MySQL driver is constructed only inside the factory. The one exception is a zero-value struct literal in an in-package unit test.**

Evidence:

1. **Sole import of the package.** `grep -rn 'db/mysql"' --include=*.go .` across the whole repo returns exactly one hit: `store/db/db.go:8`. No other file — not `cmd/`, `server/`, `store/test/`, nor any test — imports `github.com/usememos/memos/store/db/mysql`. Since `NewDB` is the only exported constructor (`store/db/mysql/mysql.go:20`), and it's unreachable without importing the package, no external caller can construct the driver.

2. **Sole call site.** `mysql.NewDB(profile)` appears once, at `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver` — the driver-selection factory.

3. **Every consumer goes through the factory.** All driver acquisition routes through `db.NewDBDriver`: `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70`. `store/test/store.go:88`'s `case "mysql"` selects a DSN/profile string, not a driver object; `store/test/containers.go` deals with the testcontainer and the raw `database/sql` registration `sql.Open("mysql", dsn)` (`containers.go:145`) — that's the `go-sql-driver/mysql` SQL driver, a different thing from this repo's `store.Driver` implementation.

4. **The one direct construction.** `store/db/mysql/auth_config_test.go:12` does `db := &DB{}` — an in-package test building a zero-value `DB` (no profile, no connection) purely to exercise the pure-logic method `IsRetryableAuthenticationMutationError`. Being in `package mysql` it bypasses `NewDB` entirely. Within `mysql.go` itself, `NewDB` builds the value at `store/db/mysql/mysql.go:29` (`driver := DB{profile: profile}`).

So: outside the factory, the only direct construction is that test's zero-value literal; there is no direct construction in any non-test code.
