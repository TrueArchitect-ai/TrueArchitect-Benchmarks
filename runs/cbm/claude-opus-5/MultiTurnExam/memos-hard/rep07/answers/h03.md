**`internal/idp` (abstraction); `internal/idp/oauth2` (implementation — OAuth2 is the only concrete protocol that ships)**

Supporting detail:

- **Abstraction**: `internal/idp/idp.go:1-8` — the package is deliberately thin: it defines only the shared `IdentityProviderUserInfo` struct (`Identifier`, `DisplayName`, `Email`, `AvatarURL`) that every provider normalizes to. There is no Go `interface` here; the abstraction is the common user-info shape plus the discriminated config in the store schema.

- **Implementation**: `internal/idp/oauth2/oauth2.go` — `IdentityProvider` wrapping `storepb.OAuth2Config` (`oauth2.go:20`), constructed by `NewIdentityProvider` with required-field validation (`oauth2.go:27`), and providing `ExchangeToken` with PKCE `code_verifier` support (`oauth2.go:47`) and `UserInfo`, which fetches the userinfo endpoint and maps claims through the configurable `FieldMapping` into `idp.IdentityProviderUserInfo` (`oauth2.go:83`).

- **Only one protocol ships**: the store enum `IdentityProvider.Type` has just `TYPE_UNSPECIFIED` and `OAUTH2` (`proto/store/idp.proto:11-14`), and `IdentityProviderConfig` is a `oneof` with a single `oauth2_config` member (`proto/store/idp.proto:21-25`). No SAML/LDAP/OIDC-specific package exists — OIDC providers are used via the generic OAuth2 config.

- **Dispatch point**: `resolveSSOIdentity` branches on `identityProvider.Type == storepb.IdentityProvider_OAUTH2` and calls into the oauth2 package — `server/router/api/v1/auth_service_sso.go:120-133`. (Note that if the type were ever anything else, `userInfo` stays nil and the identifier-filter check at `auth_service_sso.go:142` would dereference nil — harmless today since OAUTH2 is the only valid value.)
