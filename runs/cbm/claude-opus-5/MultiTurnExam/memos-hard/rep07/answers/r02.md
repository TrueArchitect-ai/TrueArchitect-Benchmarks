**Premise correction: there is no per-user API rate-limiting middleware in this repository, so there is nothing to register and no request limits to report.**

Evidence:

- A case-insensitive grep for `ratelimit`, `rate_limit`, `rate limit`, `throttl`, `golang.org/x/time/rate`, and `middleware.RateLimiter` across all Go sources and `go.mod` produces exactly one hit, and it is a comment describing future work, not code: `internal/email/doc.go:86` — `//   - Rate limit email sending to prevent abuse`.
- `golang.org/x/time/rate` is not a dependency in `go.mod`, and Echo's `middleware.RateLimiter` is never used.

What actually is registered on the HTTP server (`server/server.go:51-52`): `middleware.Recover()` and `newCORSMiddleware(profile)` — that's the whole Echo middleware chain.

On the RPC side, the Connect interceptors in `server/router/api/v1/connect_interceptors.go` are `MetadataInterceptor` (`:22`), `LoggingInterceptor` (`:98`), `RecoveryInterceptor` (`:165`), and `AuthInterceptor` (`:205`) — authentication and observability, no quota or throttling logic.

The closest things to per-request limiting in the codebase are resource concurrency guards and size caps, which are not rate limits:

- `thumbnailSemaphore` (3 concurrent) and `imageProcessingSemaphore` (2 concurrent) on `APIV1Service` — `server/router/api/v1/v1.go:56-62`; and a separate 3-slot thumbnail semaphore in the file server — `server/router/fileserver/fileserver.go:116`.
- A bounded 128-entry webhook dispatch queue with 4 workers — `internal/webhook/webhook.go:39,42-55`.
- Per-memo content length limits enforced in `CreateMemo`/`UpdateMemo` — `server/router/api/v1/memo_service.go:100-106`, `:440-445`.

If you need per-user rate limiting, it would have to be added — the natural insertion points are a new Connect interceptor alongside `AuthInterceptor` (which already resolves the calling user) or Echo middleware next to the CORS registration at `server/server.go:52`.
