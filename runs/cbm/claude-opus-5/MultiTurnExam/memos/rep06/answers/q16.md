Inside `Store.DeleteMemo` (`store/memo.go:140-159`), before the memo row is deleted:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one (`store/memo.go:149-157`)

Only then does it call `driver.DeleteMemo`, which is a plain `DELETE FROM memo WHERE id = ?` with no DB-level cascade (`store/db/sqlite/memo.go:237-248`, and the postgres/mysql equivalents).

Additionally, at the API layer in `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`), **child comment memos** are deleted first — it lists `memo_relation` rows of type `comment` pointing at this memo and calls `Store.DeleteMemo` on each (`:567-577`), which recursively applies the cleanup above to every comment.

Note: reactions and attachments are only *listed* at `:545-557` for the webhook payload, not deleted there — reaction rows are not removed by this path.
