Inside `Store.DeleteMemo` (`store/memo.go:140-159`), in order, before `driver.DeleteMemo` runs:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID:...}` and deleted one by one (`store/memo.go:149-157`). Each goes through `Store.DeleteAttachment` (`store/attachment.go:132`), which also removes the **backing stored file/blob** first via `DeleteAttachmentStorage` — for `LOCAL` storage a failed file removal aborts the delete.

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`).

One level up, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first deletes **child comment memos** — it lists `memo_relation` rows of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each (so each comment's own relations and attachments get cleaned up too) — before deleting the target memo.

Note: **reactions are not deleted** by either layer. The handler only *reads* reactions (`memo_service.go:545`) to populate the memo-deleted webhook payload; rows in `reaction` keyed by the memo's resource name are left behind.
