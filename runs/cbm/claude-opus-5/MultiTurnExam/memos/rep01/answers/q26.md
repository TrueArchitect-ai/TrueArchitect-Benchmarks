**memo, memo_relation, attachment** (plus **memo_share** by DB-level FK cascade on Postgres/MySQL only)

Breakdown of `Store.DeleteMemo` (`store/memo.go:140-159`):

| Table | How |
|---|---|
| `memo_relation` | Explicit cascade code — deleted twice, once by `MemoID` and once by `RelatedMemoID` (`store/memo.go:142,145`) |
| `attachment` | Explicit cascade code — listed by `MemoID`, then each deleted via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying stored file (`store/attachment.go:141`) |
| `memo` | The row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`) |
| `memo` (again) | Via the API handler: child comment memos are deleted first, each through the same `Store.DeleteMemo` path (`server/router/api/v1/memo_service.go:568-573`) — so their relations and attachments go too |

Two caveats worth flagging:

- **`memo_share`** has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`), but the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite those rows are **not** cascaded and are left orphaned. No Go code deletes them as part of memo deletion.
- **`reaction`** is not touched at all — the handler only reads reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545`), and reactions key off the memo's resource name with no FK, so those rows survive.
