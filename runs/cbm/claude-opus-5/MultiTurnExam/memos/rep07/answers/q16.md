`Store.DeleteMemo` (`store/memo.go:140-159`) deletes, in order, before issuing the `DELETE FROM memo`:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachment rows linked to the memo** — listed via `FindAttachment{MemoID}` then deleted one by one (`store/memo.go:149-157`). Each goes through `Store.DeleteAttachment` (`store/attachment.go`), which also removes the **underlying stored blob/file** (local or external storage) before deleting the DB row.

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`); the driver method is a plain single-table delete, e.g. `store/db/sqlite/memo.go`.

One level up, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-582`) first deletes **child comment memos** — every memo related to this one with type `MemoRelationComment` — by recursively calling `Store.DeleteMemo` on each (`:567-577`), so each comment's own relations and attachments are cleaned up too. It also dispatches the memo-deleted webhook beforehand; the reactions it loads at `:545` are only used to build that webhook payload, not deleted there.
