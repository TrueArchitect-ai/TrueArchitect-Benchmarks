**memo, memo_relation, attachment** (plus **memo_share** by DB-level FK cascade on Postgres/MySQL only)

Breakdown:

- **memo_relation** — explicitly deleted twice in `Store.DeleteMemo`, once for rows where the memo is the source and once where it's the target (`store/memo.go:142`, `:145`).
- **attachment** — rows linked via `MemoID` are listed and deleted individually (`store/memo.go:149-157`); each goes through `Store.DeleteAttachment` (`store/attachment.go`), which also removes the underlying blob from local/external storage.
- **memo** — the row itself, via `s.driver.DeleteMemo` (`store/memo.go:158`), a plain `DELETE FROM memo` (e.g. `store/db/sqlite/memo.go`). The API handler `APIV1Service.DeleteMemo` additionally deletes every child comment memo first by recursing into `Store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`), so more `memo` rows and their own relations/attachments go too.
- **memo_share** — no explicit cleanup code; it relies on `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Worth flagging: the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and share rows are left orphaned.

Not touched: **reaction**. `APIV1Service.DeleteMemo` loads reactions at `server/router/api/v1/memo_service.go:545`, but only to build the webhook payload — reactions key off a `ContentID` string with no FK, so those rows survive the delete.
