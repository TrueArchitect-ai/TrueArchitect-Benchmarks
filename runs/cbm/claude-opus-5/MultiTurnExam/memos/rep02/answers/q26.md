**memo_relation, attachment, memo** — plus **memo_share** on MySQL/Postgres only (DB-level cascade), and the same set again for each comment memo.

Breakdown:

| Table | How | Where |
|---|---|---|
| `memo_relation` | explicit delete, both directions (`MemoID`, then `RelatedMemoID`) | `store/memo.go:142`, `:145` |
| `attachment` | explicit — listed by `MemoID`, deleted one by one (also removes the stored file/S3 object) | `store/memo.go:149-157`, `store/attachment.go:132-148` |
| `memo` | the row itself, last | `store/memo.go:158` → `store/db/sqlite/memo.go:237` |
| `memo` / `memo_relation` / `attachment` for **comment memos** | API layer recursively calls `Store.DeleteMemo` for each child comment | `server/router/api/v1/memo_service.go:566-577` |
| `memo_share` | **DB-level `ON DELETE CASCADE`**, not application code | `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109` |

Two caveats worth flagging:

- **`memo_share` does not cascade on SQLite.** The SQLite connection is opened with foreign keys explicitly disabled — `_pragma=foreign_keys(0)` in the DSN at `store/db/sqlite/sqlite.go:53` — so the FK declared at `store/migration/sqlite/LATEST.sql:109` is inert and share rows are orphaned. On Postgres/MySQL the cascade does fire. That's a behavioral difference between dialects, not a designed one.
- **`reaction` rows are never deleted.** They're only read to build the webhook payload (`server/router/api/v1/memo_service.go:545`), and the `reaction` table has no FK to `memo` (it keys on a `content_id` string, `store/migration/sqlite/LATEST.sql:92-99`), so reactions for a deleted memo persist on all three dialects.
