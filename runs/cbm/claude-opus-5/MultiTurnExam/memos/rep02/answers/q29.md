**web/src/connect.ts (with token state in web/src/auth-state.ts); access token (JWT, `Bearer`) + refresh token (HttpOnly cookie `memos_refresh`) — and PATs for programmatic clients; server/auth**

**Frontend interceptor.** `authInterceptor` at `web/src/connect.ts:156-178` is attached to the shared Connect transport (`:188`). Per request it calls `getRequestToken()` (`:124`), sets `Authorization: Bearer <token>`, and on a `Code.Unauthenticated` response refreshes once, retries with an `X-Retry` marker, and on failure calls `redirectOnAuthFailure()`. Refresh itself goes through a *second*, interceptor-free transport and `refreshAuthClient` (`:65-72`) to avoid recursion, and `refreshAccessToken` (`:89`) dedupes concurrent refreshes via `tokenRefreshManager` (`:30-51`).

**Tokens it manages** (`web/src/auth-state.ts`):
- **Access token** — short-lived JWT held in memory and mirrored to `localStorage` (`memos_access_token` / `memos_token_expires_at`), sent as the bearer header. Refreshed preemptively when within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30 s), or 2 min on tab focus. Fresh tokens are shared across tabs over a `BroadcastChannel` (`memos_token_sync`) so only one tab refreshes.
- **Refresh token** — never touched by JS; it's an HttpOnly cookie (`RefreshTokenCookieName = "memos_refresh"`, `server/auth/token.go:49`), which is why every transport uses `fetchWithCredentials` with `credentials: "include"` (`web/src/connect.ts:57-62`).

**Backend validation: `server/auth`** (`server/auth/authenticator.go`, `token.go`, `extract.go`, `context.go`). `Authenticator` handles three credential kinds:
- `AuthenticateByAccessTokenV2` → `ParseAccessTokenV2` (JWT/HMAC against the instance secret) — `authenticator.go:41`, `token.go:220`
- `AuthenticateByRefreshToken` → `ParseRefreshToken` plus a DB lookup of the stored token ID — `authenticator.go:61-73`
- `AuthenticateByPAT` → prefix check, SHA-hash lookup via `GetUserByPATHash`, expiry check, last-used recording — `authenticator.go:102-123`

`resolveBearer` (`:149`) decides JWT-vs-PAT by prefix, and `Authenticate` (`:213`) returns the `AuthResult` applied to the request context.

Both serving paths funnel into it: the Connect `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:213-228`) and the gRPC-gateway middleware in `server/router/api/v1/v1.go:85-92`, with per-RPC access rules in `server/router/api/v1/authz.go` / `acl_config.go`.
