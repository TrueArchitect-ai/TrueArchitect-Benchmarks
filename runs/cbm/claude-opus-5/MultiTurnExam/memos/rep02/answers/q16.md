`Store.DeleteMemo` (`store/memo.go:140-159`) deletes, in order, before the `memo` row:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one (`store/memo.go:149-157`); each `Store.DeleteAttachment` (`store/attachment.go:132-148`) also removes the **underlying stored blob** (local file via `os.Remove`, or the S3/external object) before the DB row.

Only then does it call `s.driver.DeleteMemo` (`store/memo.go:158`), whose dialect implementations are a plain `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237-248`).

Two things the API layer adds on top, outside `Store.DeleteMemo`:

- **Comment memos** are deleted first — `APIV1Service.DeleteMemo` lists `memo_relation` rows of type `comment` pointing at this memo and calls `Store.DeleteMemo` on each child (`server/router/api/v1/memo_service.go:566-577`), so each comment goes through the same relation/attachment cleanup.
- **Reactions are not deleted.** They're only read to build the webhook payload (`server/router/api/v1/memo_service.go:545`); no `reaction` rows are removed in either layer, and the `reaction` table has no FK cascade (`store/migration/sqlite/LATEST.sql:92`) — so reaction rows for a deleted memo are left behind.
