**memo_relation, attachment, memo** (plus **memo_share** via the schema's FK cascade, where foreign keys are enforced)

Breakdown of `Store.DeleteMemo` (`store/memo.go:140-158`):

| Table | How |
|---|---|
| `memo_relation` | two explicit deletes — rows where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`), `store/memo.go:142,145` |
| `attachment` | explicit: listed by `MemoID` and deleted one at a time via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying local/object storage file (`store/attachment.go:132-148`) |
| `memo` | the row itself, last, via `s.driver.DeleteMemo` (`store/memo.go:158`; e.g. `store/db/sqlite/memo.go:237`) |
| `memo_share` | no explicit code — only the `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` declared at `store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108` |

Two caveats worth flagging. First, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first deletes every **comment memo** related to this one, each recursing through `Store.DeleteMemo` — so the same three tables are hit again for each comment. Second, the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), meaning the `memo_share` cascade does **not** fire on SQLite; those rows are left behind there. The `reaction` table is untouched on this path — reactions are read only to build the webhook payload.
