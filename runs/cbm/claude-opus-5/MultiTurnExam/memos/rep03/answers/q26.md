**memo, memo_relation, attachment, memo_share (via DB-level FK cascade on Postgres/MySQL only)**

Breakdown of what touches each:

| Table | How | Where |
|---|---|---|
| `memo_relation` | Explicit deletes in both directions — `MemoID` and `RelatedMemoID` | `store/memo.go:142`, `:145` |
| `attachment` | Explicit — attachments with `memo_id` are listed and deleted one by one (each also removes the backing file/object from storage) | `store/memo.go:149-157`, `store/attachment.go:132-149` |
| `memo` | The row itself, plus **each comment memo**, which the API layer deletes first via `Store.DeleteMemo` (so comments recursively hit the same tables) | `store/db/sqlite/memo.go:237-248`; comments at `server/router/api/v1/memo_service.go:567-577` |
| `memo_share` | **Not** deleted by any Go code — relies on `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` | `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:102-110` |

Two caveats worth flagging:

- On **SQLite**, the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the `memo_share` cascade does **not** fire — those rows are left orphaned. The cascade only takes effect on Postgres and MySQL.
- `reaction` rows are **not** deleted. `DeleteMemo` reads them only to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); the `reaction` table has no FK to `memo` (it keys off a string `content_id`), so reactions for a deleted memo persist.
