`Store.DeleteMemo` (`/bench/repo/store/memo.go:140-158`) deletes, in order, before issuing the `DELETE FROM memo`:

1. **memo_relation rows where this memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where this memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachment rows linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one (`store/memo.go:149-157`); each `Store.DeleteAttachment` (`store/attachment.go:132-149`) also removes the **backing file/object in storage** (local file or external storage) before the DB row.

Then `s.driver.DeleteMemo` runs the plain `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237-248`).

Additionally, at the API layer above this, `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`) first finds all **comment memos** (memo_relations of type `COMMENT` pointing at this memo) and calls `Store.DeleteMemo` on each — so each comment goes through the same relation/attachment cleanup — before deleting the parent memo.

Note: reactions are read for the webhook payload (`memo_service.go:545-550`) but are **not** deleted by this path.
