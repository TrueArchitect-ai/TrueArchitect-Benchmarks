**Interceptor: `web/src/connect.ts` (`authInterceptor`, lines 156-178); tokens: short-lived JWT access token + HTTP-only refresh-token cookie (and Personal Access Tokens on the API surface); backend package: `server/auth/`**

How it works:
- The interceptor attaches `Authorization: Bearer <access token>` on every Connect call (`web/src/connect.ts:158-159`). On a `Code.Unauthenticated` response it refreshes once, sets an `X-Retry` header, and replays the request; if the refresh fails it calls `redirectOnAuthFailure` (lines 161-177).
- Token state lives in `web/src/auth-state.ts` — the access token and its expiry are kept in `localStorage` with cross-tab sync via `BroadcastChannel`, plus a preflight refresh when the token is within 30 s of expiry (`getRequestToken`, `web/src/connect.ts:124-150`).
- The refresh token is never touched by JS: the transport uses `credentials: "include"` (`web/src/connect.ts:57-62`) so the HTTP-only cookie rides along, and refresh goes through a separate interceptor-free transport/client to avoid recursion (lines 65-91, calling `AuthService.RefreshToken`).
- Server side, `server/auth/authenticator.go` validates all three kinds: `AuthenticateByAccessTokenV2` (JWT, line 41), `AuthenticateByRefreshToken` (JWT + DB lookup of the stored refresh token, line 61), and `AuthenticateByPAT` (hashed lookup for `PersonalAccessTokenPrefix` tokens, line 102), dispatched by `resolveBearer`/`Authenticate` (lines 149, 213). Token minting/parsing is in `server/auth/token.go`, header/cookie extraction in `server/auth/extract.go`. The API-side session endpoints that issue and rotate these tokens are `server/router/api/v1/auth_service_session.go`.
