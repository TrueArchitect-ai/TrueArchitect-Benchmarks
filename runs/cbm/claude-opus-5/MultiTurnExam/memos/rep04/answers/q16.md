Inside `Store.DeleteMemo` (`store/memo.go:140-159`), before the memo row is deleted (line 158):

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID}` (`store/memo.go:145`)
3. **attachments linked to the memo** — listed then deleted one by one (`store/memo.go:149-157`); each `Store.DeleteAttachment` (`store/attachment.go:132-149`) also removes the underlying blob from local disk or S3 via `DeleteAttachmentStorage` before deleting the `attachment` row

The API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally deletes **comment memos** first — it lists `memo_relation` rows of type `comment` pointing at this memo and calls `Store.DeleteMemo` on each (which recursively cleans up their own relations and attachments) — before deleting the parent memo.

Two things that are *not* explicit store-layer deletes: `memo_share` rows go away via `ON DELETE CASCADE` on the FK (`store/migration/sqlite/LATEST.sql:102-110`), and reactions are only *read* in the handler (to build the webhook payload, `server/router/api/v1/memo_service.go:545`) — they are not deleted there.
