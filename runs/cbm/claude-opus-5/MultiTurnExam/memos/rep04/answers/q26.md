**memo, memo_relation, attachment, memo_share**

- **memo_relation** — deleted twice, once as source (`MemoID`) and once as target (`RelatedMemoID`), in `Store.DeleteMemo` (`store/memo.go:142,145`)
- **attachment** — rows linked to the memo are listed and deleted individually (`store/memo.go:149-157`), each also removing the underlying blob from local disk/S3 (`store/attachment.go:132-149`)
- **memo** — the row itself (`store/memo.go:158` → e.g. `DELETE FROM memo WHERE id = ?` in `store/db/sqlite/memo.go:237`), plus any **comment memos**, which the API handler deletes first by walking `comment`-type relations (`server/router/api/v1/memo_service.go:568-576`)
- **memo_share** — removed by the DB via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`), not by explicit Go code

Note on **reaction**: rows are *read* in the delete handler to build the webhook payload (`server/router/api/v1/memo_service.go:545`) but are not deleted, and the `reaction` table has no FK to `memo` — so reactions for a deleted memo are left behind.
