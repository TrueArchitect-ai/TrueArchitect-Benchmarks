**memo, memo_relation, attachment, memo_share**

Breakdown by mechanism:

| Table | How | Where |
|---|---|---|
| `memo_relation` | explicit cascade code — deleted twice, once as `memo_id` and once as `related_memo_id` | `/bench/repo/store/memo.go:142,145` |
| `attachment` | explicit cascade code — listed by `MemoID`, deleted one at a time (each also removes the stored file/blob) | `/bench/repo/store/memo.go:149-157`, `/bench/repo/store/attachment.go:132` |
| `memo` | the target row itself, plus one row per comment memo | `/bench/repo/store/db/sqlite/memo.go:237`; comments looped in `/bench/repo/server/router/api/v1/memo_service.go:567-577` |
| `memo_share` | DB-level `ON DELETE CASCADE` foreign key, not Go code | `/bench/repo/store/migration/sqlite/LATEST.sql:107`, `/bench/repo/store/migration/postgres/LATEST.sql:108` |

Because comment memos are themselves deleted through `Store.DeleteMemo`, the same four tables are hit again for each comment.

Two caveats worth flagging: `reaction` rows are **not** removed — `APIV1Service.DeleteMemo` only *reads* reactions to build the webhook payload (`memo_service.go:545`), leaving orphaned rows keyed by the memo's resource name. And the `memo_share` cascade relies on the foreign key being enforced, which for SQLite requires `PRAGMA foreign_keys=ON` on the connection rather than any Go-side deletion.
