**memo, memo_relation, attachment** — plus **memo_share** via a DB-level `ON DELETE CASCADE` (not on SQLite; see below).

Breakdown, following `Store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) and `APIV1Service.DeleteMemo` (`/bench/repo/server/router/api/v1/memo_service.go:518-593`):

| Table | How |
|---|---|
| `memo_relation` | Explicit: deleted twice — where the memo is `memo_id` and where it is `related_memo_id` (`store/memo.go:142`, `:145`) |
| `attachment` | Explicit: listed by `MemoID` and deleted row-by-row (`store/memo.go:149-157`); `Store.DeleteAttachment` also removes the backing file/blob from local or external storage (`/bench/repo/store/attachment.go`) |
| `memo` | The memo row itself (`store/memo.go:158` → e.g. `DELETE FROM memo WHERE id = ?` in `/bench/repo/store/db/sqlite/memo.go`), **plus** every comment memo — the API handler deletes each `MemoRelationComment` child through the same `Store.DeleteMemo` path first (`memo_service.go:567-577`), so their relations and attachments are cleaned up too |
| `memo_share` | DB cascade only: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` at `/bench/repo/store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`. There is no Go code deleting shares on memo delete |

Two caveats worth flagging:

- **On SQLite the `memo_share` cascade does not fire.** The connection is opened with `_pragma=foreign_keys(0)` (`/bench/repo/store/db/sqlite/sqlite.go:53`), so foreign keys are disabled and `memo_share` rows are orphaned there; the cascade is effective only on MySQL and Postgres.
- **`reaction` rows are not deleted.** `DeleteMemo` lists reactions only to build the webhook payload (`memo_service.go:545-550`); nothing removes them, and the table has no FK to `memo` (it keys off the resource-name string `content_id`).
