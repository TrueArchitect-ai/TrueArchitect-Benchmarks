Before the `memo` row is deleted, `Store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) removes, in order:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (line 142).
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (line 145).
3. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one (lines 149-157). Each `Store.DeleteAttachment` (`/bench/repo/store/attachment.go`) also deletes the **backing stored file/blob** (local disk or external storage) before removing the DB row.

Only then does it call `s.driver.DeleteMemo` for the memo row itself (line 158) — the dialect implementation is a plain `DELETE FROM memo WHERE id = ?` (e.g. `/bench/repo/store/db/sqlite/memo.go`).

At the API layer, `APIV1Service.DeleteMemo` (`/bench/repo/server/router/api/v1/memo_service.go:518-593`) does one more step ahead of all this: it finds all **comment memos** (memo relations of type `MemoRelationComment` pointing at this memo) and deletes each of them via `Store.DeleteMemo` first (lines 567-577), so each comment gets the same relation/attachment cleanup.

Note that **reactions are not deleted** — `DeleteMemo` lists them only to build the webhook payload (lines 545-550); no reaction cleanup happens in either the API handler or the store, so `reaction` rows keyed by the memo's resource name are left behind.
