Inside `Store.DeleteMemo` (`store/memo.go:140-159`), in order, before `driver.DeleteMemo` runs:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachment rows linked to the memo** — listed by `MemoID`, then deleted one by one via `Store.DeleteAttachment` (`store/memo.go:148-157`), which also **deletes the underlying stored file/blob** (`Store.DeleteAttachmentStorage`, `store/attachment.go:141` — local file removal or external storage object)
4. **the memo row itself** — `driver.DeleteMemo` (`store/memo.go:158`)

Two things the API handler does first, before calling into the store (`server/router/api/v1/memo_service.go:518-591`):

- **Comment memos are deleted recursively** — it lists `MemoRelationComment` relations pointing at this memo and calls `Store.DeleteMemo` on each child (lines 567-577), so each comment goes through the same relation/attachment cascade.
- A memo-deleted webhook is dispatched and an SSE `MemoDeleted` event broadcast (lines 559-565, 583-589).

Worth flagging: **reactions are not deleted.** The handler reads them at line 545 only to build the webhook payload, and nothing in `Store.DeleteMemo` touches the `reaction` table — reaction rows key off `ContentID` (the memo's resource name) and are left orphaned.
