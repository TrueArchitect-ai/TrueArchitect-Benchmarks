`Store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) — called by the API handler at `/bench/repo/server/router/api/v1/memo_service.go:580` — deletes, in order, before issuing the `DELETE FROM memo` row delete:

1. **`memo_relation` rows where the memo is the source** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target/related memo** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments(FindAttachment{MemoID})` and deleted one by one with `s.DeleteAttachment` (`store/memo.go:148-157`). Each of those also removes the **underlying stored file/blob** (local file or external storage object) via `DeleteAttachmentStorage` before the attachment row (`store/attachment.go:132-149`, `202-223`).

Only then does it call `s.driver.DeleteMemo` to remove the memo row itself (`store/memo.go:158`; drivers at `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259` do a plain single-row delete).

Note the scope boundary: comment memos and reactions are *not* handled by the store layer. The API handler deletes child comment memos itself first (each via another `Store.DeleteMemo` call, `memo_service.go:567-577`), and reactions are only listed for the webhook payload — the store's memo deletion path never deletes reaction rows.
