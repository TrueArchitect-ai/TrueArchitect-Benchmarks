**Tables: `memo`, `memo_relation`, `attachment`** (plus **`memo_share`** via a schema-level `ON DELETE CASCADE`, which is inert on SQLite).

**Call chain**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) resolves the memo, then:
1. Lists child comment relations and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`).
2. Calls `Store.DeleteMemo` for the memo itself (`memo_service.go:580`).

`Store.DeleteMemo` (`store/memo.go:140-159`) is the explicit cascade:
- `s.driver.DeleteMemoRelation` twice — by `memo_id` and by `related_memo_id` → **`memo_relation`** (`store/db/sqlite/memo_relation.go:148-150`).
- Lists attachments with `MemoID` and calls `DeleteAttachment` for each → **`attachment`** (`store/attachment.go:132-149`, SQL at `store/db/sqlite/attachment.go:212`); this also removes the underlying blob/local file.
- `s.driver.DeleteMemo` → **`memo`** (`store/db/sqlite/memo.go:237-239`, `store/db/postgres/memo.go:246`, `store/db/mysql/memo.go:261`).

**`memo_share`** is deleted only by database FK cascade: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). There is no Go code for it in the delete path. Note the SQLite driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does **not** fire and `memo_share` rows are left orphaned.

**Not touched: `reaction`.** `DeleteMemo` lists reactions only to build the webhook payload (`memo_service.go:545-550`); nothing deletes them, and `reaction` has no FK to `memo` (it keys off `content_id` as a text name — `store/migration/sqlite/LATEST.sql:92-100`). Reactions are only cleaned up in the user-deletion path (`store/db/sqlite/user_delete.go:383`).
