**`web/src/connect.ts`; JWT access token (in-memory + localStorage, `Authorization: Bearer`) and JWT refresh token (HttpOnly `memos_refresh` cookie) — plus PATs (`memos_pat_`) supported on the same header for programmatic clients; `server/auth`**

**Frontend interceptor — `web/src/connect.ts:156`**
- `authInterceptor` is attached to the single Connect-Web transport (`web/src/connect.ts:184-189`) that backs every service client (`memoServiceClient`, `userServiceClient`, etc.), so all API calls flow through it. Transport uses `credentials: "include"` (`web/src/connect.ts:57`) so the refresh cookie rides along.
- On each request it calls `getRequestToken()` (`web/src/connect.ts:124`) and sets `Authorization: Bearer <token>` (`web/src/connect.ts:97`). It preemptively refreshes when the token is within 30s of expiry, and reactively retries once on `Code.Unauthenticated`, marking the retry with an `X-Retry` header to prevent loops; on failure it calls `redirectOnAuthFailure()` (`web/src/utils/auth-redirect.ts`).
- Refresh goes through a *separate* transport with no interceptors to avoid recursion (`web/src/connect.ts:65-72`), calling `AuthService.RefreshToken`; concurrent refreshes are deduped by `tokenRefreshManager` (`web/src/connect.ts:30`).

**Token storage — `web/src/auth-state.ts`**
- Access token + expiry cached in module state and `localStorage` under `memos_access_token` / `memos_token_expires_at`; a `BroadcastChannel` (`memos_token_sync`) shares freshly refreshed tokens across tabs. `web/src/hooks/useTokenRefreshOnFocus.ts` refreshes proactively on tab focus using a larger 2-minute buffer.
- The refresh token itself is never in JS — it's the server-set cookie.

**Backend validation — `server/auth/`**
- `server/auth/token.go` defines the scheme: JWT issuer `memos`, access-token audience `user.access-token` (15 min), refresh-token audience `user.refresh-token` (30 days) in cookie `memos_refresh`, and PAT prefix `memos_pat_`.
- `server/auth/authenticator.go` does the validating: `AuthenticateByAccessTokenV2` (stateless signature check), `AuthenticateByRefreshToken` (DB-backed revocation/expiry check via `store.GetUserRefreshTokenByID`), and `AuthenticateByPAT` (SHA-256 hash lookup). `resolveBearer` picks access-token vs. PAT by prefix.
- `server/auth/extract.go` pulls the bearer token from the header and the refresh token from the cookie.
- The wiring point for Connect RPCs is `server/router/api/v1/connect_interceptors.go:220-227`, which reads the `Authorization` header, calls `Authenticate`, and stashes the result in the context via `auth.ApplyToContext`. The same package is reused by the file server (per the package doc at `server/auth/token.go:1-10`).
