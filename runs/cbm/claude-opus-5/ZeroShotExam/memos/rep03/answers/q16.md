`store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`), which the API's `DeleteMemo` handler calls (`/bench/repo/server/router/api/v1/memo_service.go:579-581`), deletes these before issuing the memo-row delete (`s.driver.DeleteMemo`):

1. **Memo relations where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **Memo relations where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — each row found by `ListAttachments{MemoID: ...}` is removed via `s.DeleteAttachment` (`store/memo.go:149-157`), which also deletes the underlying stored file/blob (local or external storage) before the attachment row (`store/attachment.go:132-148`).

Two related points on the boundary of the question:
- Child **comment memos** are deleted by the API layer, not the store: it lists comment relations and calls `store.DeleteMemo` on each comment first (`server/router/api/v1/memo_service.go:567-577`) — each of those recursively goes through the same relation/attachment cleanup.
- Reactions are only *read* for the webhook payload in the API handler (`memo_service.go:544`); the store's `DeleteMemo` does not delete reaction rows.
