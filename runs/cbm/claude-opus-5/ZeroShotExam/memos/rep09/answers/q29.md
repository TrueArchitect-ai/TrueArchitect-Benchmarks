**`web/src/connect.ts`; JWT access token (localStorage, `Bearer`) + refresh token (`memos_refresh` HttpOnly cookie), with Personal Access Tokens also accepted; `server/auth`**

**Frontend interceptor — `web/src/connect.ts:156` (`authInterceptor`)**
- It's registered on the single Connect-RPC transport (`web/src/connect.ts:184-189`) that all service clients (`memoServiceClient`, `userServiceClient`, etc.) are built from, so every API call passes through it.
- Per request it calls `getRequestToken()` (`connect.ts:124`) and sets `Authorization: Bearer <token>` (`connect.ts:97`).
- Two refresh paths: a **preflight** refresh when the token is within 30s of expiry (`connect.ts:140`), and a **reactive** retry on `Code.Unauthenticated` — refresh, re-set the header, mark `X-Retry: true`, replay once; on failure it calls `redirectOnAuthFailure()` (`connect.ts:163-177`). A separate `refreshTransport` with no interceptors (`connect.ts:65`) avoids recursion, and `tokenRefreshManager` (`connect.ts:30`) dedupes concurrent refreshes.

**Tokens it manages — `web/src/auth-state.ts`**
- **Access token**: short-lived JWT held in memory + `localStorage` under `memos_access_token` / `memos_token_expires_at`, synced across tabs via a `memos_token_sync` BroadcastChannel (`auth-state.ts:6-50`).
- **Refresh token**: never touched by JS — it rides as an HttpOnly cookie, which is why both transports use `credentials: "include"` (`connect.ts:57`). The frontend only calls `AuthService.refreshToken` (`connect.ts:75`). A proactive refresh on tab focus lives in `web/src/hooks/useTokenRefreshOnFocus.ts`.

**Backend validating package — `server/auth`**
- `server/auth/token.go` defines the scheme: access tokens 15 min (`user.access-token`), refresh tokens 30 days (`user.refresh-token`), cookie name `memos_refresh`, PAT prefix `memos_pat_`.
- `server/auth/authenticator.go` does the validation: `AuthenticateByAccessTokenV2` (stateless JWT signature check), `AuthenticateByRefreshToken` (JWT parse **plus** a DB lookup for revocation/expiry), and `AuthenticateByPAT` (SHA-256 hash lookup). `resolveBearer` routes a bearer token to the JWT or PAT path by prefix.
- `server/auth/extract.go` pulls the token out of the `Authorization` header and the refresh token out of the cookie.
- Consumed by the Connect/gRPC interceptor via `Authorizer` in `server/router/api/v1/authz.go:36`, and also by `server/router/fileserver/fileserver.go`. `MetadataInterceptor` forwards the `Cookie` header so `RefreshToken` can read it (`server/router/api/v1/connect_interceptors.go:54`); that method is exempt from auth in `server/router/api/v1/acl_config.go:14`.
