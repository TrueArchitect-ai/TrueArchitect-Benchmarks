`store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) performs these deletions before issuing the `DELETE FROM memo` row delete:

1. **Memo relation records where the memo is the source** — `driver.DeleteMemoRelation(&DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`).
2. **Memo relation records where the memo is the target/related memo** — `driver.DeleteMemoRelation(&DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`).
3. **Attachments linked to the memo** — it lists them via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and calls `DeleteAttachment` on each (`store/memo.go:149-157`). Each `DeleteAttachment` (`store/attachment.go:132-149`) also removes the attachment's backing storage (local file / S3 object) via `DeleteAttachmentStorage` before deleting the attachment row.

Only then does it call `driver.DeleteMemo` to remove the memo row itself (`store/memo.go:158`; e.g. the SQLite implementation at `store/db/sqlite/memo.go:237` is a plain `DELETE FROM memo WHERE id = ?`).

Note on scope: comment memos are *not* handled by the store layer — the API service deletes them first by looking up `MemoRelationComment` relations and calling `store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:572-578`). Reactions are only listed (for the webhook payload), not deleted, in this path.
