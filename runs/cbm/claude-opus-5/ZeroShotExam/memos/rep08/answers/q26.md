**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`** (the last via DB-level `ON DELETE CASCADE`).

**Call path**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) resolves the memo, checks permissions, dispatches the webhook, then:
- lists direct comment relations and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`)
- calls `Store.DeleteMemo` for the memo itself (`memo_service.go:580`)

`Store.DeleteMemo` (`store/memo.go:140-159`) is where the explicit cascade lives:
- `memo_relation` — two `DeleteMemoRelation` calls, one by `MemoID`, one by `RelatedMemoID` (`store/memo.go:142-147`)
- `attachment` — lists attachments with `MemoID` and calls `DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the underlying file/object storage (`store/attachment.go:132-148`)
- `memo` — `driver.DeleteMemo` issues the plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`)

**`memo_share` caveat:** it is not touched by any Go code — it relies on `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:100-110`, `store/migration/postgres/LATEST.sql:101-109`, `store/migration/mysql/LATEST.sql:101-109`). That cascade fires on Postgres and MySQL, but **not on SQLite**, which opens the connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`) — so on SQLite `memo_share` rows are orphaned.

**Not affected:** `reaction`. Reactions are only *listed* (by `content_id`) to populate the webhook payload (`memo_service.go:545-550`); no delete is issued, and `reaction.content_id` has no FK to `memo`, so those rows survive the deletion.
