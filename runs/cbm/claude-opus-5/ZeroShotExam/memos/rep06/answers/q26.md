**Tables affected: `memo`, `memo_relation`, `attachment` — plus `memo_share` only via DB-level FK cascade (Postgres/MySQL; not SQLite). `reaction` is NOT touched.**

**Call chain**

1. `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) — reads memo/reactions/attachments/relations for the webhook payload, then finds comment relations (`ListMemoRelations` with `MemoRelationComment`) and calls `Store.DeleteMemo` for each comment memo, then for the memo itself (`memo_service.go:568-583`).
2. `Store.DeleteMemo` (`store/memo.go:140-159`) does the explicit cascade:
   - `DeleteMemoRelation{MemoID}` and `DeleteMemoRelation{RelatedMemoID}` → **`memo_relation`**
   - `ListAttachments{MemoID}` → `DeleteAttachment` per row (`store/attachment.go:132-149`, which also removes the file/blob from storage) → **`attachment`**
   - `driver.DeleteMemo` → `DELETE FROM memo` → **`memo`** (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`)

**Caveats**

- **`memo_share`**: `memo_share.memo_id` has `FOREIGN KEY ... REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:101-109`, `postgres/LATEST.sql:101-109`, `mysql/LATEST.sql:101-109`). There is no explicit Go cleanup, so rows go away only where the engine enforces FKs. SQLite opens the connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite `memo_share` rows are left orphaned.
- **`reaction`**: reactions are listed for the webhook payload but never deleted. `Store.DeleteReaction` is only called from `server/router/api/v1/reaction_service.go:141` (`DeleteMemoReaction`), and `reaction.content_id` is a plain text name with no FK (`sqlite/LATEST.sql:92-100`), so reaction rows for a deleted memo are orphaned.
- Comment memos are deleted recursively through the same path, so they hit the same three tables.
