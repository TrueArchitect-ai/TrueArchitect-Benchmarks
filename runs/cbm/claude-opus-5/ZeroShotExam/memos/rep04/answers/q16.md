`store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) removes these before issuing the `DELETE FROM memo` statement:

1. **Memo relations where the memo is the source** — `driver.DeleteMemoRelation(&DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **Memo relations where the memo is the target/related memo** — `driver.DeleteMemoRelation(&DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and deleted one by one with `DeleteAttachment` (`store/memo.go:148-157`), which also removes the underlying stored file/blob via `DeleteAttachmentStorage` before deleting the attachment row (`store/attachment.go:132-148`).

Only after those does it call `s.driver.DeleteMemo` (`store/memo.go:158`), which is a plain `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237`).

Two notes on the surrounding API path (`server/router/api/v1/memo_service.go:518-582`): comment memos are deleted first by the service layer, each recursing through `store.DeleteMemo`, and reactions are only *listed* (for the webhook payload) — they are not deleted by this path.
