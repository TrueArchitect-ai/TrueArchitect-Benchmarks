**Tables affected: `memo`, `memo_relation`, `attachment`, `memo_share`** (plus repeats of all four for each comment memo). Notably **not** `reaction`.

**How each is touched**

| Table | Where | Mechanism |
|---|---|---|
| `memo_relation` | `store/memo.go:142-147` → `store/db/sqlite/memo_relation.go:137` (and postgres/mysql equivalents) | Explicit cascade code in `Store.DeleteMemo`: two deletes, one by `memo_id`, one by `related_memo_id` |
| `attachment` | `store/memo.go:149-157` → `Store.DeleteAttachment` (`store/attachment.go:132`) → `store/db/sqlite/attachment.go:211` | Explicit cascade: lists attachments with `MemoID`, deletes each row (also removes the backing local/S3 blob, not a table) |
| `memo` | `store/memo.go:158` → `store/db/sqlite/memo.go:237` | The direct `DELETE FROM memo WHERE id = ?` |
| `memo_share` | `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109` | DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` — no Go code deletes shares |

**Comments are deleted too:** `server/router/api/v1/memo_service.go:568-577` finds child memos via `memo_relation` of type `COMMENT` and calls `Store.DeleteMemo` on each, so every comment repeats the same four-table cleanup. (Only one level — a comment's own comments aren't walked.)

**Two caveats worth flagging:**

- `reaction` rows are **not** deleted. `memo_service.go:545-550` lists reactions only to build the webhook payload, and nothing in the delete path calls `Store.DeleteReaction`. Reactions key off `content_id` (the memo resource name, `store/migration/sqlite/LATEST.sql:96`) with no FK, so they are orphaned.
- The `memo_share` cascade is **Postgres/MySQL only**. The SQLite driver opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so FK enforcement is off and share rows are orphaned on SQLite deployments.
