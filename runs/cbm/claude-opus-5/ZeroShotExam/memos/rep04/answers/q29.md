**`web/src/connect.ts`; JWT access token (in-memory + localStorage) + refresh token (HttpOnly `memos_refresh` cookie) — plus Personal Access Tokens server-side; `server/auth`**

**Frontend interceptor — `web/src/connect.ts:156` (`authInterceptor`)**
- Registered on the single Connect-Web transport (`web/src/connect.ts:184-189`) that backs every service client (memo, user, attachment, AI, shortcut, IdP, instance, auth). Transport uses `fetch` with `credentials: "include"` (`connect.ts:57-62`) so the refresh cookie rides along.
- Per request it calls `getRequestToken()` (`connect.ts:124`) and sets `Authorization: Bearer <token>` (`connect.ts:97-100`).
- Proactive path: if the access token is within the 30s expiry buffer, it refreshes *before* sending (`connect.ts:140`) — the comment notes this matters for public endpoints like ListMemos that would otherwise silently return guest-scoped data.
- Reactive path: on `Code.Unauthenticated`, it refreshes once, retries with an `X-Retry: true` header guard, and on failure calls `redirectOnAuthFailure()` (`connect.ts:163-177`).
- Refresh goes through a *separate* transport with no interceptors to avoid recursion (`connect.ts:65-72`), and through a dedup manager so concurrent refreshes collapse into one (`connect.ts:30-51`, `89-91`).

**Token storage — `web/src/auth-state.ts`**
- Access token + expiry cached in module memory and mirrored to `localStorage` keys `memos_access_token` / `memos_token_expires_at`.
- Cross-tab sync via a `BroadcastChannel` named `memos_token_sync`, so one tab's refresh is adopted by the others instead of racing (`auth-state.ts:26-50`).
- Refresh token is never touched by JS — it's the server-set cookie.

**Backend validation — `server/auth/`**
- `server/auth/token.go` defines the scheme: JWT issuer `memos`, key id `v1`, access-token audience `user.access-token` with a 15-minute lifetime, refresh-token audience `user.refresh-token` with a 30-day lifetime, cookie name `memos_refresh`, and PAT prefix `memos_pat_`.
- `server/auth/authenticator.go` validates: `AuthenticateByAccessTokenV2` (stateless HMAC parse, no DB hit), `AuthenticateByRefreshToken` (parses, then checks the store for revocation/expiry and that the user isn't archived), and `AuthenticateByPAT` (hash lookup via `GetUserByPATHash`, async last-used update).
- `server/auth/extract.go` pulls the bearer token out of the header and the refresh token out of the cookie.
- Wired into the API at `server/router/api/v1/authz.go:36` (`Authorizer`) and `server/router/api/v1/connect_interceptors.go:227`, plus `sse_handler.go:26` and the file server.

One asymmetry worth knowing: `Authenticate` (used by the Connect interceptor) accepts only the Bearer header, while `AuthenticateToUser` also falls back to the refresh cookie — so normal API calls authenticate purely by access token/PAT, and the cookie is only exercised on the refresh and file-server paths.
