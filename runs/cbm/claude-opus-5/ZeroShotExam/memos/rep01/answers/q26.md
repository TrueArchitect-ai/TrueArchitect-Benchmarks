**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share` (DB-level FK cascade, Postgres/MySQL only).**

**Trace**

1. **API handler** — `server/router/api/v1/memo_service.go:518` `APIV1Service.DeleteMemo`:
   - Lists comment relations and calls `Store.DeleteMemo` on each comment memo (`memo_service.go:567-577`) — so `memo` rows for comments are deleted too.
   - Then deletes the memo itself (`memo_service.go:580`).

2. **Store layer** — `store/memo.go:140` `Store.DeleteMemo`:
   - `memo_relation`: two explicit deletes, one by `MemoID`, one by `RelatedMemoID` (`store/memo.go:142-147`).
   - `attachment`: lists attachments with `MemoID` and calls `Store.DeleteAttachment` for each (`store/memo.go:149-157`), which issues `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go:211`; same in postgres/mysql) and also removes the backing local/S3 blob (`store/attachment.go:132-148`).
   - `memo`: driver delete, a plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

3. **`memo_share`** — no Go code deletes it; it relies on the schema FK `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:105`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Caveat: on SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the cascade does **not** fire there — `memo_share` rows are left orphaned on SQLite.

**Not affected:** `reaction`. The handler reads reactions only to build the webhook payload (`memo_service.go:545-550`); nothing deletes them, and `reaction.content_id` is a plain TEXT column with no FK (`store/migration/sqlite/LATEST.sql`), so reaction rows are orphaned on all three drivers. There is no `memo_organizer` table in the current schema (pinning is the `memo.pinned` column).
