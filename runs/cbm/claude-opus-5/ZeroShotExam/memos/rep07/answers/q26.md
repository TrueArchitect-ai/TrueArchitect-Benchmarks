**Tables affected by `DeleteMemo`: `memo`, `memo_relation`, `attachment` (plus `memo_share` only via the DB-level FK cascade on Postgres/MySQL).**

### The delete path

**API layer** — `server/router/api/v1/memo_service.go:518` (`APIV1Service.DeleteMemo`):
- Lists comment relations and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`) — so every child comment goes through the same cascade.
- Then deletes the memo itself (`memo_service.go:580`).
- Reactions and attachments are only *read* here (`:545`, `:552`) to build the webhook payload — no deletes.

**Store layer** — `store/memo.go:140` (`Store.DeleteMemo`) is where the explicit cascade code lives:
1. `memo_relation` — deleted twice, once by `MemoID` and once by `RelatedMemoID` (`store/memo.go:142-147`), via the driver's `DELETE FROM memo_relation`.
2. `attachment` — lists attachments with `MemoID` and calls `Store.DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the blob from local/S3 storage before the row delete (`store/attachment.go:132-149`).
3. `memo` — final `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

### Two caveats worth flagging

- **`memo_share`** is *not* deleted by any code in this path. It has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:101-109`, `postgres/LATEST.sql:101-109`, `mysql/LATEST.sql:101-109`), so rows disappear on Postgres/MySQL. On SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the cascade does not fire and share rows are left orphaned. Explicit `memo_share` cleanup exists only in the user-deletion path (`store/db/*/user_delete.go:406-411`).
- **`reaction`** is never cleaned up on memo delete. Its `content_id` is a resource-name string with no FK (`LATEST.sql` reaction table), so reactions on a deleted memo are orphaned on all three drivers.
