**How I determined it over the other candidates**

There are three implementations of `Driver.CreateMemo`, each with its own `INSERT INTO memo`:
- `store/db/sqlite/memo.go:41` — backticked identifiers, `RETURNING`
- `store/db/postgres/memo.go:38` — `$n` placeholders, `RETURNING`
- `store/db/mysql/memo.go:41` — no `RETURNING` (uses `LastInsertId` instead)

Selection is runtime dispatch through an interface, not static, so I traced the wiring rather than the call graph:

1. **Call path is driver-agnostic.** `APIV1Service.CreateMemo` calls `s.Store.CreateMemo` (`server/router/api/v1/memo_service.go:115`), which validates the UID and delegates straight to the interface: `return s.driver.CreateMemo(ctx, create)` (`store/memo.go:109-114`, interface declared at `store/driver.go:29`). No caching or wrapper layer intercepts memos — `store.New` (`store/store.go:37`) stores the driver as-is and its caches cover only instance settings, users, and user settings.

2. **The concrete driver is chosen once at startup** by `db.NewDBDriver`, which switches on `profile.Driver` (`store/db/db.go:18-27`) — `"sqlite"`/`"mysql"`/`"postgres"`, error otherwise. `main.go:57` calls it and passes the result to `store.New` (`cmd/memos/main.go:64`), so the value bound to `s.driver` for the process lifetime is whatever that switch returned.

3. **`profile.Driver` defaults to `sqlite`** with no flags: `viper.SetDefault("driver", "sqlite")` (`cmd/memos/main.go:122`) and the flag's own default is also `"sqlite"` (`cmd/memos/main.go:130`); the profile field is populated from `viper.GetString("driver")` (`cmd/memos/main.go:43`).

So the switch takes the `case "sqlite"` branch, `s.driver` is `*sqlite.DB`, and the SQLite implementation is the one that runs. The MySQL and Postgres versions are only reachable by explicitly passing `--driver mysql`/`--driver postgres` (or the equivalent env/config value).
