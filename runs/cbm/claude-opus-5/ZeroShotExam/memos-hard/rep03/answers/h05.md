**Mechanism: explicit Go code** — the reaction rows are deleted by hand-written `DELETE FROM reaction` statements inside the delete-user transaction, in all three DB drivers. There is no database-level cascade for reactions.

## What I checked

**1. The delete path** — `store/db/{sqlite,postgres,mysql}/user_delete.go` all implement `DB.DeleteUser` identically. `deleteUserTargetsTx` (line 92 in each) runs two reaction deletes as the *first* and *third* steps, before the memos themselves are dropped:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (sqlite/postgres line 380–383, mysql line 417–420). The content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + memo.UID` over the recursive memo tree (the user's memos plus their `COMMENT` descendants). This clears *everyone's* reactions on the departing user's memos.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (sqlite/postgres line 400–401, mysql line 437–438). This clears the user's own reactions left on other people's memos.

Both run inside the same `tx` that ends with `deleteUserRowTx`, so they commit or roll back atomically with the user row.

**2. The schema** — `store/migration/{sqlite,postgres,mysql}/LATEST.sql` (reaction table at lines 92 / 91 / 91). The `reaction` table has only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY` and no `ON DELETE CASCADE`. `creator_id` is a bare `INTEGER`/`INT`, and `content_id` is a text name (`memos/<uid>`), not an FK-able column. The only `ON DELETE CASCADE` in those files is `memo_share.memo_id → memo(id)` (lines 108/108/109), unrelated to reactions. Separately, SQLite opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so FK actions wouldn't fire there anyway.

**3. Tests confirming the behavior** — `store/test/user_delete_test.go:97-112,217-220` and `server/router/api/v1/test/user_service_delete_test.go:188-209,287-298` seed reactions on the user's own memo, on their comment under a foreign memo, and a peer's reaction on a foreign memo; after deletion the first two sets are asserted empty while the unrelated peer reaction survives. `user_service_delete_test.go:366-431` uses the `DeleteUserFailpointBeforeCommit` hook (`store/user_delete.go:16`) to assert the reaction is still present after a rollback — i.e. the deletion is transactional Go code, not an independent DB rule.
