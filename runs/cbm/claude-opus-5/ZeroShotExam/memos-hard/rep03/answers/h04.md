**No** — outside the factory, the MySQL driver is never constructed in production code. The only in-package direct struct literal is a zero-value one in a unit test.

Evidence:

- **The factory is the sole production construction site.** `store/db/db.go:14-32` — `NewDBDriver(profile)` switches on `profile.Driver` and calls `mysql.NewDB(profile)` at `store/db/db.go:22`. That file is also the *only* file in the repo that imports `github.com/usememos/memos/store/db/mysql` (`store/db/db.go:8`); a repo-wide grep for `db/mysql` imports returns exactly that one line, so no other package can even reference `mysql.NewDB` or `mysql.DB`.
- **`mysql.NewDB` has exactly one caller**, `store/db/db.go:22`. Its own internal `driver := DB{profile: profile}` at `store/db/mysql/mysql.go:29` is the constructor's own body, not an outside construction.
- **Test/setup paths also go through the factory**, not around it: `store/test/store.go:28` and `store/test/store.go:50` both call `db.NewDBDriver(profile)`. `store/test/containers.go` only spins up a MySQL testcontainer and builds a DSN (`github.com/testcontainers/testcontainers-go/modules/mysql`, plus `mysqldriver.ParseDSN` at `store/test/containers.go:363`); it never constructs the memos MySQL driver.
- **One direct struct literal exists, but it is inside the `mysql` package itself and in a test:** `store/db/mysql/auth_config_test.go:12` — `db := &DB{}`, used only to invoke the pure method `IsRetryableAuthenticationMutationError` on a zero value with no DB connection. Since it lives in `package mysql`, it isn't "outside the factory" in the import-boundary sense, and it isn't a functioning driver instance.

For contrast, the Postgres driver does have an extra construction pattern — `store/db/postgres/postgres.go:33` (`var driver store.Driver = &DB{...}`) and test literals at `store/db/postgres/user_setting_test.go:36,194,257` — but those are within the postgres package too.
