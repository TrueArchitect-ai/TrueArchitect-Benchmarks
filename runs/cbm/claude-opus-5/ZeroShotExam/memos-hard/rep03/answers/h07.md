Then back in the handler, the bytes come out of the row itself, not a blob store: `user.AvatarURL` holds a `data:<mime>;base64,...` URI, which `parseDataURI` (server/router/fileserver/fileserver.go:735) splits with `dataURIRegex` (line 93) and base64-decodes. The MIME type is checked against `avatarAllowedTypes` (line 72), then served via `c.Blob` with `Cache-Control: public, max-age=3600` and the `setSecurityHeaders` CSP.

Two things worth noting for the "another user's" part of the question:

- There is no per-user authorization check on this route — any avatar is readable by any caller once the instance gate passes. The only gate is at fileserver.go:172: if `!s.Profile.AllowAnonymous()` (a private instance with no InstanceURL), the request must authenticate via `getCurrentUser` → `authenticator.AuthenticateToUser` (server/auth) using a Bearer token/PAT or refresh-token cookie. On a public instance, avatars are anonymous-readable.
- The `:identifier` param is matched against username only, not user ID (fileserver.go:711).
