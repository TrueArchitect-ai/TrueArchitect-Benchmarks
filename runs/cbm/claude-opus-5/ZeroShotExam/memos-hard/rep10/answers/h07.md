Notes that matter for the trace:

- **The avatar bytes live in the `user` table, not in file/object storage.** They're stored as a `data:<mime>;base64,...` URI in `user.avatar_url` and decoded per-request by `parseDataURI` (`fileserver.go:737`). None of the attachment paths (local FS / S3 / blob column) are involved — those are only reached by `serveAttachmentFile`.
- **Cache hop is bypassed here.** `Store.GetUser` (`store/user.go:148`) only consults `s.userCache` when `find.ID` is set; this lookup is by `Username`, so it always falls through to `ListUsers` → driver → SQL. The result is written back into `userCache` (`store/user.go:143,167`).
- **Auth side-branch before the read:** on a private instance (`!s.Profile.AllowAnonymous()`), `serveUserAvatar` calls `getCurrentUser` (`fileserver.go:708`) → `auth.Authenticator.AuthenticateToUser` (`server/auth/authenticator.go:190`), which does its own store reads. Otherwise the avatar is served anonymously — there is no per-user authorization check, so any user's avatar is readable by any viewer that clears the instance-level gate.
- Route wiring is registered in `server/server.go:81-82`.
