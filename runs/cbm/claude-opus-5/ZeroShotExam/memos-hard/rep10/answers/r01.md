**Premise correction:** There is no Redis in this repository. The cache layer is a hand-rolled, in-process, in-memory cache — no external cache server, no connection string, no `redis` dependency anywhere (`go.mod`/`go.sum` contain zero Redis references, and there is no Redis client, host/port, or URL setting in any config path). Nothing about the cache is externally configurable; there are no env vars for it.

**Actual mechanism**

The cache is `store/cache/cache.go` — a `sync.Map`-backed `Cache` struct with per-item expiration timestamps, an atomic item counter, and a background cleanup goroutine (`cleanupLoop`, `store/cache/cache.go:200`). Its `Config` (`store/cache/cache.go:42`) has `DefaultTTL`, `CleanupInterval`, `MaxItems`, and an `OnEviction` callback.

Where it's "configured": `store.New()` in `store/store.go:38-61` builds the config literal inline and constructs three separate cache instances that share it:

- `instanceSettingCache` — instance settings
- `userCache` — users
- `userSettingCache` — user settings

The config values, hardcoded at `store/store.go:40-45`:

- `DefaultTTL: 10 * time.Minute`
- `CleanupInterval: 5 * time.Minute`
- `MaxItems: 1000`
- `OnEviction: nil`

(`cache.DefaultConfig()` at `store/cache/cache.go:57` declares the same three values, but the store doesn't call it — it duplicates them.)

**TTL for user entries: 10 minutes.** User entries go through `s.userCache.Set(...)`, which is `Cache.Set` (`store/cache/cache.go:93`) — it delegates to `SetWithTTL` with `c.config.DefaultTTL`, i.e. the 10 minutes from `store/store.go:41`. There is no user-specific TTL override; nothing in the store calls `SetWithTTL` directly, so users, user settings, and instance settings all get the same 10 minutes.

Write sites for user entries, all using the default TTL: `CreateUser` (`store/user.go:98`), `UpdateUser` (`store/user.go:122`), `store/user.go:132`, `ListUsers` (`store/user.go:143`, caches every listed user), and `GetUser` (`store/user.go:167`). Read path is `GetUser` (`store/user.go:148-156`) — cache is only consulted when `find.ID` is set; lookups by username or other fields always hit the DB. Keys are just the decimal user ID (`userCacheKey`, `store/user.go:88`); user-setting keys are `"<userID>-<key>"` (`getUserSettingCacheKey`, `store/cache.go:7`).

Eviction beyond TTL: expired entries are dropped lazily on `Get` (`store/cache/cache.go:135`) and swept every 5 minutes by `cleanup()`; exceeding `MaxItems: 1000` triggers `cleanupOldest()` (`store/cache/cache.go:253`), which drops roughly 20% of capacity. `DeleteUser` explicitly invalidates via `deleteUserCache` (`store/user.go:179`). Since the cache is per-process with no shared backend, a multi-instance deployment would have independent caches with no cross-instance invalidation.
