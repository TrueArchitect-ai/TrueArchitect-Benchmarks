**No** — outside `NewDBDriver`, the MySQL driver is never constructed in production code.

Evidence:

1. **The factory is the sole call site.** `store/db/db.go:22` is the only place `mysql.NewDB(profile)` is invoked, inside `NewDBDriver` (`store/db/db.go:14-31`), selected by `profile.Driver == "mysql"`.

2. **Only one import of the package repo-wide.** `grep -rn "usememos/memos/store/db/mysql" --include=*.go .` returns exactly one hit: `store/db/db.go:8`. No other Go file — including `cmd/`, `server/`, `store/`, or the test harness — imports the internal MySQL driver package at all, so it cannot be constructed elsewhere.

3. **Everything else goes through the factory.** `store/test/store.go:28` and `:50` and `server/router/api/v1/test/memo_service_benchmark_test.go:70` all call `db.NewDBDriver(profile)` rather than a concrete driver. (By contrast, sqlite *is* constructed directly in two tests — `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416` call `sqlite.NewDB(p)` — so the pattern is not universal, but MySQL has no such bypass.)

Two things that look like counterexamples but aren't:

- `store/test/containers.go:20,101` imports and calls `mysql.Run(...)` — that's `testcontainers-go/modules/mysql` (a Docker container helper), not the repo's driver. That file gets its DSN into a driver via `NewDBDriver`, and its raw `sql.Open("mysql", dsn)` at line 145 is a readiness probe using the `go-sql-driver/mysql` stdlib registration.
- `store/db/mysql/auth_config_test.go:12` does `db := &DB{}` — a zero-value struct in an in-package unit test for the pure method `IsRetryableAuthenticationMutationError`. It never calls `NewDB` and holds no connection; if you count any literal construction of the `DB` type, this is the one instance, and it's test-only and inside the package itself.
