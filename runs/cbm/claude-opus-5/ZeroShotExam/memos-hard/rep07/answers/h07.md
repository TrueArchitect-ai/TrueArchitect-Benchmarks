The avatar is not a file on disk or in S3 — it's a base64 data URI stored in the `user.avatar_url` column, decoded at serve time.

**Notes on the trace:**

- **URL origin.** The browser never sees the raw base64. `convertUserFromStore` swaps `user.AvatarURL` for the `/file/...` path when the stored value parses as a data URI, otherwise it passes the stored value through as an external URL (`user_service_converters.go:32-39`). The name segment is `users/{username}` via `BuildUserName` (`server/router/api/v1/user_resource_name.go:13`).
- **Auth side-hop.** For "another user's" avatar there's no per-user permission check — only an instance-level gate. If `s.Profile.AllowAnonymous()` is false, `serveUserAvatar` calls `getCurrentUser` (`fileserver.go:708`) → `Authenticator.AuthenticateToUser` (`server/auth/authenticator.go:190`) and 401s on nil; any authenticated viewer may then fetch any user's avatar.
- **Lookup key.** `getUserByUsername` sets only `FindUser.Username`, so the `Store.GetUser` cache fast path (keyed on `find.ID`, `store/user.go:149-156`) is skipped and every request reaches the driver. The result is then written into `userCache`.
- **Driver fan-out.** The `Driver.ListUsers` interface has three implementations with equivalent SQL: `store/db/sqlite/user.go:88`, `store/db/postgres/user.go`, `store/db/mysql/user.go`.
- **Response.** Back in the handler, the decoded MIME type is checked against `avatarAllowedTypes` (`fileserver.go:71`), security headers plus `Cache-Control: public, max-age=3600` are set, and the bytes go out via `c.Blob`.

Route wiring is at `server/server.go:81-82`.
