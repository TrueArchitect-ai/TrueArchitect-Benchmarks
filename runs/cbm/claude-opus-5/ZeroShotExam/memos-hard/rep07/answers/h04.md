**No** — outside `NewDBDriver`, the MySQL store driver is never constructed in production code. The single exception is a zero-value literal in the mysql package's own unit test.

**Evidence:**

1. **The `store/db/mysql` package has exactly one importer in the entire repo** — the factory:
   - `store/db/db.go:8` — `"github.com/usememos/memos/store/db/mysql"` is the only line matching `store/db/mysql` across all `.go` files.
   - Since the type is `mysql.DB` with all-unexported fields (`db`, `profile`, `config` — `store/db/mysql/mysql.go:14-18`), no external package could construct a usable instance even if it imported the package.

2. **`mysql.NewDB` has exactly one call site** — `store/db/db.go:22`, inside `NewDBDriver`'s `case "mysql":` branch.

3. **The only `&DB{}` literal in the mysql package is in-package test code** — `store/db/mysql/auth_config_test.go:12`:
   ```go
   db := &DB{}
   require.True(t, db.IsRetryableAuthenticationMutationError(...))
   ```
   This is a zero-value receiver used only to call the pure error-classification method `IsRetryableAuthenticationMutationError`; it opens no connection. (The parallel Postgres package does the same at `store/db/postgres/auth_config_test.go:12`, plus real `&DB{db: db}` literals in `store/db/postgres/user_setting_test.go:36,194,257` — MySQL has no such equivalent.)

4. **Test helpers also route through the factory** — `store/test/store.go:28` and `store/test/store.go:50` both call `db.NewDBDriver(profile)` rather than constructing a driver directly. The `mysql.*` references in `store/test/containers.go:101-105` are the *testcontainers* MySQL module (`testcontainers-go/modules/mysql`), and `mysqldriver` there is `go-sql-driver/mysql` — neither is the memos store driver.

One nuance on wording: within `NewDB` itself the struct is built as a value literal, `driver := DB{profile: profile}` (`store/db/mysql/mysql.go:29`), and returned as `&driver` — but that is inside the factory path, not outside it.
