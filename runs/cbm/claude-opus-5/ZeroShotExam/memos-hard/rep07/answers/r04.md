**Premise correction:** Neither. This repository (memos, a Go monolith) has no external message broker at all — there is no NATS, RabbitMQ, AMQP, or Kafka client anywhere. `go.mod` contains no such dependency, and a repo-wide search for `nats`/`rabbitmq`/`amqp` across `.go`, `.yaml`, `.ts`, and `.md` files returns zero hits. There is also no broker service in any deployment/compose config, and no "queue declaration" in the AMQP/JetStream sense exists to point at.

**Actual mechanism — an in-process buffered Go channel with a fixed goroutine pool:**

The whole thing lives in `internal/webhook/webhook.go`:

- **The "queue"** is a package-level buffered channel of capacity 128, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- **The "workers"** are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over the channel and calls `Post(payload)`, logging a warning on failure. There is no retry, no dead-letter, and no persistence — a failed delivery is logged and dropped.
- **Enqueue** happens in `PostAsync` at `internal/webhook/webhook.go:184-196`. It uses a non-blocking `select` with a `default` branch, so when the 128-slot buffer is full the payload is **silently dropped** (with a warning log), rather than blocking the caller.
- **Delivery itself** is a plain `net/http` POST in `Post` (`internal/webhook/webhook.go:120-180`), using a shared `safeClient` with a 30s timeout and an SSRF-guarding `DialContext` (`internal/webhook/webhook.go:32-37`, `59-77`). Optional HMAC-SHA256 signing follows the Standard Webhooks spec (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers).

**Producers** are the API service methods in `server/router/api/v1/memo_service_webhooks.go` — `DispatchMemoCreatedWebhook`, `...Updated`, `...Deleted`, and `DispatchMemoCommentCreatedWebhook`. They read the user's registered webhooks from the store (`s.Store.GetUserWebhooks`) and call `webhook.PostAsync(payload)` for each (lines 43 and 71).

Practical consequence: since the queue is in-memory and process-local, pending webhooks are lost on restart, and this design does not fan out across multiple server replicas — each process has its own independent 128-slot buffer and 4 workers.
