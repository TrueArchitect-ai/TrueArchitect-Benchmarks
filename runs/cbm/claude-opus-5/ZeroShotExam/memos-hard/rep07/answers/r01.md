**Premise correction:** There is no Redis in this repository — and no external cache server of any kind. A case-insensitive search for `redis`, `memcached`, and `valkey` across the whole repo (code, configs, docs, `go.mod`) returns zero matches. There is no connection string, host/port setting, or client dependency to configure. The only pluggable backend Memos has is the *database* driver (sqlite/mysql/postgres, `internal/profile/profile.go:30`).

**Actual mechanism:** The cache layer is a hand-rolled, in-process, in-memory cache — a `sync.Map` with per-entry expiry timestamps, defined in `store/cache/cache.go`. It lives inside the single Go server process, so nothing is shared across instances and everything is lost on restart.

Where it's configured — `store/store.go:38-61`, in `store.New()`. The config is a hardcoded literal, not read from env or a config file:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

Three separate cache instances are built from that same struct (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. An identical set of defaults is also declared in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), but `store.New` doesn't call it — it duplicates the values inline.

**TTL for user entries — 10 minutes.** Every write to `userCache` uses the plain `Set` method (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). `SetWithTTL` is never called with a custom duration anywhere outside the cache package, so users get no special TTL — they expire on the same 10-minute clock as instance settings and user settings.

Two details worth knowing about that 10 minutes:

- **It's a fixed TTL from the last write, not a sliding one.** `expiration` is stamped once at `Set` time (`store/cache/cache.go:112`); a cache hit in `Get` does not extend it. Any read/write of a user resets it only because `GetUser` re-`Set`s on a miss and `UpdateUser`/`ListUsers` re-`Set` on every call.
- **The TTL is an upper bound, not a guarantee.** With `MaxItems: 1000`, exceeding the cap triggers `cleanupOldest` (`store/cache/cache.go:253`), which evicts ~20% of entries by soonest expiration — so on an instance with heavy churn a user entry can be dropped well before 10 minutes. Expired entries are also swept lazily on `Get` and by the background `cleanupLoop` every 5 minutes.

Invalidation is explicit on delete: `store/user_delete.go:40` calls `s.userCache.Delete(...)`. All three caches' cleanup goroutines are stopped in `Store.Close()` (`store/store.go:72-79`).
