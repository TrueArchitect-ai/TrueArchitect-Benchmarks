**Premise correction:** Neither. This repository (memos) uses no external message broker at all — there is no NATS, RabbitMQ/AMQP, Kafka, or Redis dependency anywhere in `go.mod`, and no broker config in the repo. The only repo-wide grep hits for "rabbit" are the "CodeRabbit" sponsor links in `README.md` and the seed data. There is also no separate "worker" process — webhook delivery happens in-process inside the single memos server binary.

**Actual mechanism:** the "queue" is a buffered Go channel, and the "workers" are four goroutines started in a package `init()`.

- **Queue declaration** — `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A package-level buffered channel with capacity 128, declared in the same `var` block as the SSRF-guarded shared HTTP client (`internal/webhook/webhook.go:32-37`).

- **Consumers** — `internal/webhook/webhook.go:42-55`: an `init()` spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`; failures are only logged via `slog.Warn`, not retried or dead-lettered.

- **Producer** — `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning ("Dropped webhook dispatch because the async queue is full"). So there is no durability, no persistence, and no redelivery: anything in flight is lost on process restart.

- **Callers** — `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, which fan out per user webhook (`s.Store.GetUserWebhooks`) for activity types `memos.memo.created`/`updated`/`deleted`/`comment.created`.

Actual delivery is a plain `net/http` POST in `Post` (`internal/webhook/webhook.go:120-180`), with a 30s timeout, optional Standard Webhooks HMAC-SHA256 signing (`webhook-id`/`webhook-timestamp`/`webhook-signature` headers), and a dial-time guard rejecting reserved/private IPs (`safeDialContext`, `internal/webhook/webhook.go:59-77`).
