Notes on the hops that matter:

- **The image bytes live in the `user.avatar_url` column**, not on disk or S3 — they're stored as a `data:<mime>;base64,...` URI (`dataURIRegex`, fileserver.go:98). The API deliberately does *not* ship that base64 blob in the user proto; it swaps in the `/file/...` URL (user_service_converters.go:31-38), which is why the browser makes a second request at all.
- **The path segment is the username**, not the user ID: `BuildUserName(user.Username)` produces `users/{username}`, so `/file/%s/avatar` yields `/file/users/{username}/avatar`, and the handler resolves it via `FindUser{Username: &identifier}` (fileserver.go:716).
- **The user cache is bypassed on this path.** `Store.GetUser` only consults `s.userCache` when `find.ID != nil` (store/user.go:149-156); a username lookup always falls through to `ListUsers` → driver → SQL, then populates the cache keyed by ID.
- **Authorization**: for *another user's* avatar there is no per-user permission check. Access is gated only by `s.Profile.AllowAnonymous()` (fileserver.go:173) — on a public instance anyone may fetch any user's avatar; on a private instance any authenticated session/PAT suffices. MIME type is then restricted to `avatarAllowedTypes` (fileserver.go:75-83, 201) before `c.Blob`.
- Routes are registered before the gRPC-gateway in `server/server.go:81-82`, so `/file/*` never reaches the API v1 gateway.
