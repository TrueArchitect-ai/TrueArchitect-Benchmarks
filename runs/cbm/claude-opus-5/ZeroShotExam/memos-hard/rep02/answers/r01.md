**Premise correction:** There is no Redis in this repository. `grep -ri redis` across the entire tree (Go source, `go.mod`, docs, scripts, web) returns zero hits. Memos ships with no external cache server and no Redis connection string, host/port setting, or client dependency to configure. The cache layer is a hand-rolled, in-process, in-memory cache.

**Actual mechanism**

*The cache implementation* — `store/cache/cache.go` defines a `Cache` backed by a `sync.Map` plus an `atomic.Int64` item counter. Each entry (`item`, line ~35) stores the value, an absolute `expiration` time, and a rough size estimate. There is no network connection of any kind; `Close()` just stops the background cleanup goroutine.

*Where it's "configured"* — `store/store.go:38-61`, in `store.New()`. The config is hardcoded in Go, not read from env or a config file:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

Three separate `*cache.Cache` instances are created from that same config (`store/store.go:27-29, 51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. `store/cache/cache.go` also has an identical `DefaultConfig()` (10m / 5m / 1000), used by `NewDefault()`.

*TTL for user entries* — **10 minutes**, inherited from `DefaultTTL`. `store/user.go` only ever calls `s.userCache.Set(...)` (lines 98, 122, 132, 143, 167), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). No caller anywhere in the codebase invokes `SetWithTTL` with a custom duration outside the cache package's own tests, so users get the plain 10-minute default. Keys are the stringified user ID (`userCacheKey`, `store/user.go:88-90`).

*Expiry enforcement* — two paths:
- Lazily on read: `Get` (`store/cache/cache.go:123`) checks `time.Now().After(itm.expiration)` and deletes + reports a miss.
- Proactively: a `cleanupLoop` goroutine (line 200) sweeps expired entries every `CleanupInterval` (5 min).

Additionally, exceeding `MaxItems` (1000) triggers `cleanupOldest` (line 253), which evicts roughly 20% of max items chosen by earliest expiration — so a user entry can be dropped before its 10 minutes elapse under cache pressure. Writes and deletes also refresh/invalidate the entry directly (`store/user.go:167`, and `deleteUserCache` at line 179), so the TTL is a staleness ceiling rather than the primary invalidation mechanism.
