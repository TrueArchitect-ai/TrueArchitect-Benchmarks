**Premise correction: this repository has no per-user API rate-limiting middleware.** There is nothing to register and no request limits to report. The premise assumes a component that does not exist in the codebase.

## What the middleware/interceptor chain actually contains

The Connect RPC interceptor chain is registered in `server/router/api/v1/v1.go:133-138`, and it has exactly four entries, none of them a rate limiter:

```go
connectInterceptors := connect.WithInterceptors(
    NewMetadataInterceptor(), // Convert HTTP headers to gRPC metadata first
    NewLoggingInterceptor(logStacktraces),
    NewRecoveryInterceptor(logStacktraces),
    NewAuthInterceptor(authorizer),
)
```

All four are defined in `server/router/api/v1/connect_interceptors.go`. The HTTP-level middleware is likewise limited to two entries — `middleware.Recover()` and CORS — at `server/server.go:51-52` (CORS itself in `server/cors.go:13`). The gRPC-Gateway path adds only an auth middleware (`server/router/api/v1/v1.go:69,97`).

Supporting evidence that this is absence rather than my failing to find it:

- No rate-limiting dependency is present in `go.mod` — no `golang.org/x/time/rate`, `tollbooth`, `ulule/limiter`, or throttling package of any kind.
- A repo-wide search for `rate.limit` / `ratelimit` / `rate_limit` returns only two hits, both prose: `internal/email/README.md:286` and `internal/email/doc.go:86`. Those are *recommendations to the reader* ("### 5. Implement Rate Limiting", "Rate limit email sending to prevent abuse"), including a `rate.NewLimiter(rate.Every(time.Second), 10)` snippet that is a documentation example, not compiled code. If the "10 per second" figure is what prompted the question, that is its source — it limits nothing at runtime.
- There is no login-attempt throttling or account lockout either (`server/auth/authenticator.go`, `server/router/api/v1/auth_service_session.go`).

## The real limits that do exist

These are the closest actual protections, and they are worth distinguishing because none of them is per-user:

| Limit | Value | Location |
|---|---|---|
| Max API request body size | 256 MiB (`256 << 20`) | `server/router/api/v1/v1.go:20`, applied at lines 126, 141, 144 |
| Concurrent image (EXIF) processing | 2 | `server/router/api/v1/v1.go:60` |
| Concurrent thumbnail generation (API) | 3 | `server/router/api/v1/v1.go:59` |
| Concurrent thumbnail generation (fileserver) | 3 | `server/router/fileserver/fileserver.go:46,116` |

The two concurrency semaphores are the only things that can reject a request for exceeding a threshold — `acquireImageProcessingSlot` in `server/router/api/v1/attachment_service_image.go:67-77` returns `ResourceExhausted` / "too many image processing requests" (`server/router/api/v1/attachment_service.go:158-160`). Note the mechanics differ from rate limiting in a way that matters: these are global, instance-wide semaphores with no per-user accounting and no time window. They bound *simultaneous* in-flight work to protect memory, and callers block waiting for a slot rather than being rejected on a per-user quota. A single user can issue unlimited sequential requests without ever tripping them.
