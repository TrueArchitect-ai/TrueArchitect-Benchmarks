The URL the browser requests is `/file/users/{username}/avatar` — the API rewrites a user's base64 `avatar_url` into that path so responses stay small, and the `<img>` then fetches it.

**Main path (serving the image):**

- `UserAvatar` (`<img src={avatarUrl}>`) — web/src/components/UserAvatar.tsx:12
- `convertUserFromStore` (rewrites base64 avatar to `/file/users/{username}/avatar` via `BuildUserName`) — server/router/api/v1/user_service_converters.go:36 (name built at server/router/api/v1/user_resource_name.go:13)
- `FileServerService.RegisterRoutes` (`GET /file/users/:identifier/avatar`) — server/router/fileserver/fileserver.go:124 (wired at server/server.go:81-82)
- `FileServerService.serveUserAvatar` — server/router/fileserver/fileserver.go:168
- `FileServerService.getUserByUsername` — server/router/fileserver/fileserver.go:715
- `Store.GetUser` (cache checked only when finding by ID; a username lookup always falls through) — store/user.go:148
- `Store.ListUsers` (populates `userCache`) — store/user.go:136
- `Driver.ListUsers` (interface) — store/driver.go:47
- `DB.ListUsers` (`SELECT ... avatar_url ... FROM user WHERE username = ?`) — store/db/sqlite/user.go:88; same for store/db/postgres/user.go:87 and store/db/mysql/user.go:84

Back out: `parseDataURI` decodes the stored `data:image/...;base64,...` value (server/router/fileserver/fileserver.go:737), the MIME type is checked against `avatarAllowedTypes` (fileserver.go:75), and the bytes go out via `c.Blob` (fileserver.go:209). The avatar data itself lives in the `user.avatar_url` column — it is never on disk or S3, unlike attachments.

**Auth branch (only on a private instance, i.e. no `InstanceURL`):**

- `FileServerService.getCurrentUser` — server/router/fileserver/fileserver.go:708
- `Authenticator.AuthenticateToUser` — server/auth/authenticator.go:190

If `Profile.AllowAnonymous()` is true, this branch is skipped and any visitor can fetch any user's avatar; there is no per-viewer authorization check beyond that gate.
