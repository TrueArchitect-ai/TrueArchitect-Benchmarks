**Premise correction:** There is no Redis in this repository. A case-insensitive search across all Go, Markdown, YAML, JSON, TS/TSX and Dockerfile sources found zero references to `redis` (or `memcached`/`valkey`), and `go.mod` (`/bench/repo/go.mod`) contains no Redis client dependency. There is no Redis connection to configure — no host/port/DSN, no env var, no config struct field. Memos (`github.com/usememos/memos`) is a self-contained single-binary app whose only external datastore is its SQL database (SQLite/MySQL/Postgres, see `/bench/repo/store/db/`).

**Actual mechanism — in-process in-memory cache:**

The cache layer is a hand-rolled, thread-safe in-memory cache in `/bench/repo/store/cache/cache.go`. It's backed by a `sync.Map` plus an `atomic.Int64` item counter (`Cache` struct, cache.go:66-73), with a background goroutine (`cleanupLoop`, cache.go:200-215) evicting expired entries on a ticker. Each entry (`item`, cache.go:35-39) stores the value, an absolute `expiration` time, and a rough size estimate. Because it lives in process memory, it is per-instance and not shared across replicas.

**Configuration** happens in Go code, not in a connection string — `store.New()` at `/bench/repo/store/store.go:38-61` builds a `cache.Config` literal and hands the *same* config to three separate cache instances:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

- `instanceSettingCache`, `userCache`, `userSettingCache` (`/bench/repo/store/store.go:27-29`, constructed at lines 51-53)
- An identical default set exists in `cache.DefaultConfig()` at `/bench/repo/store/cache/cache.go:57-64`, though `store.New` builds its own literal rather than calling it.
- These values are hardcoded — there is no env var or settings hook to override them.

**TTL for user entries: 10 minutes.** All user writes go through `s.userCache.Set(...)` (`/bench/repo/store/user.go:98, 122, 132, 143, 167`), and `Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (`/bench/repo/store/cache/cache.go:93-95`). `SetWithTTL` is never called directly anywhere in non-test code, so users get the default 10-minute TTL, same as instance settings and user settings. The cache key is just the decimal user ID (`userCacheKey`, `/bench/repo/store/user.go:88-90`).

Two caveats on the eviction behavior:
- Expiry is lazy plus periodic: `Get` checks `time.Now().After(itm.expiration)` and deletes on read (cache.go:135-144), while `cleanup` sweeps every 5 minutes (cache.go:218-250). So an entry can outlive its TTL in memory by up to the cleanup interval, but will never be *served* stale.
- Entries can also be dropped early, before their 10 minutes are up: exceeding `MaxItems: 1000` triggers `cleanupOldest` (cache.go:117-119, 253-313), which drops ~20% of capacity.

Invalidation is explicit on user deletion — `s.userCache.Delete(ctx, userCacheKey(userID))` at `/bench/repo/store/user_delete.go:40`. Reads consult the cache only when looking up by ID (`/bench/repo/store/user.go:150`); lookups by username or other fields always hit the database.
