**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the driver-level `DeleteUser` transaction. There is no FK/cascade on the `reaction` table.

**What I checked**

1. **The delete-user driver code** (all three backends, identical structure):
   - `store/db/sqlite/user_delete.go:96,102` — `deleteUserTargetsTx` calls `deleteReactionsByContentIDsTx` then `deleteReactionsByCreatorTx`, implemented at `:380-388` (`DELETE FROM reaction WHERE content_id IN (...)`, batched at 500) and `:400-403` (`DELETE FROM reaction WHERE creator_id = ?`).
   - `store/db/postgres/user_delete.go:96,102,380,400` — same two calls/implementations.
   - `store/db/mysql/user_delete.go:96,102,417,437` — same.

   Two passes, because two things must go: reactions the deleted user *made* anywhere (`creator_id`), and reactions *others* made on the deleted user's content (`content_id IN` the memo tree, built as `"memos/"+uid` in `memoContentIDsFromRefs`, `store/db/sqlite/user_delete.go:512-518`). The content-ID pass runs on a recursive memo tree that includes comment descendants (`listDeleteUserMemoTreeRecursive`, `:133-166`), so reactions on comments under the user's memos go too. All of this runs in one transaction (`:29-59`), committed before the cache is invalidated in `store/user.go:171-181`.

2. **The schema — no database-level rule.** `store/migration/{sqlite,postgres,mysql}/LATEST.sql:91-99` define `reaction` with `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` as plain columns — no `FOREIGN KEY`, no `ON DELETE CASCADE`, no trigger. A grep for `FOREIGN KEY|REFERENCES` across all three `LATEST.sql` files returns exactly one hit each: `memo_share.memo_id → memo(id) ON DELETE CASCADE` (line ~108). `content_id` is a text name (`memos/<uid>`), not a numeric FK, so a cascade isn't even expressible there. The `0.23/00__reactions.sql` migration only rewrites `reaction_type` values.

3. **Tests confirming the behavior**: `server/router/api/v1/test/user_service_delete_test.go:287-298` asserts reactions on the deleted user's own memo and on their comment are empty afterward, while a peer's reaction on a foreign memo survives; `store/test/user_delete_test.go:217-220` asserts the same at the store layer. `user_service_delete_test.go:429-431` checks the reaction is still present after a failpoint-induced rollback, confirming the deletes are transactional.

**Answer:** explicit Go code (two `DELETE FROM reaction` statements per driver, by `creator_id` and by `content_id`); `store/db/sqlite/user_delete.go:96-102,380-403`, `store/db/postgres/user_delete.go:96-102,380-403`, `store/db/mysql/user_delete.go:96-102,417-440`; schema evidence of no cascade at `store/migration/{sqlite,postgres,mysql}/LATEST.sql:91-99`.
