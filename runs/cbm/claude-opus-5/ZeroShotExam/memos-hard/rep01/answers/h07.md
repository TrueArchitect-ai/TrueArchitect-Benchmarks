The browser gets `avatarUrl = "/file/users/{username}/avatar"` from the User API (the server rewrites base64 avatars into that path), then the `<img>` tag issues a plain GET that the Echo file server handles. Avatar bytes live in the `user.avatar_url` column as a data URI — not in attachment/S3/local-file storage.

**Frontend origin of the URL**
- `UserAvatar` (`<img src={avatarUrl}>`) — web/src/components/UserAvatar.tsx:14 (callers pass `user.avatarUrl`, e.g. web/src/components/MemoView/components/MemoHeader.tsx:122, web/src/pages/UserProfile.tsx:32)
- `convertUserFromStore` — server/router/api/v1/user_service_converters.go:32-40 (replaces the base64 data URI with `/file/{users/username}/avatar`; `BuildUserName` — server/router/api/v1/user_resource_name.go:13)

**Serving hops for `GET /file/users/:identifier/avatar`**
- `FileServerService.RegisterRoutes` — server/router/fileserver/fileserver.go:124 (route registered on the Echo server; wired in server/server.go:81-82, before the gRPC gateway)
- `FileServerService.serveUserAvatar` — server/router/fileserver/fileserver.go:168 (the serving handler)
- `FileServerService.getCurrentUser` → `auth.Authenticator.AuthenticateToUser` — server/router/fileserver/fileserver.go:708-712 (only on private instances, i.e. `Profile.AllowAnonymous()` false)
- `FileServerService.getUserByUsername` — server/router/fileserver/fileserver.go:715-717 (builds `store.FindUser{Username: &identifier}`)
- `Store.GetUser` — store/user.go:148 (ID-keyed cache is skipped here since the lookup is by username)
- `Store.ListUsers` — store/user.go:127
- `driver.ListUsers` (interface) — store/driver.go:47
- `DB.ListUsers` — store/db/sqlite/user.go:88 (also store/db/postgres/user.go:87, store/db/mysql/user.go:84) — `SELECT ... avatar_url ... FROM user WHERE username = ?`, scanned into `store.User.AvatarURL` (store/user.go:41)

**Back out to the response**

- `setSecurityHeaders` + `c.Blob` — server/router/fileserver/fileserver.go:205-209
