## Method

The data layer is the `store/` package (`store/store.go`), which defines the persistent entity structs: `User`, `Memo`, `Attachment`, `Reaction`, `Inbox`, `MemoRelation`, `MemoShare`, `UserSetting`, `UserIdentity`, `IdentityProvider`, `InstanceSetting`. I counted distinct Go packages outside the `store/` tree (and outside generated `proto/gen/store`) that reference each type via `store.<Type>`.

## Ranking

|---|---|---|
| **User** | **7** | `server/auth`, `server/notification`, `server/router/api/v1`, `server/router/api/v1/test`, `server/router/fileserver`, `server/router/frontend`, `server/router/rss` |
| **Memo** | **6** | `server/notification`, `server/router/api/v1`, `server/router/api/v1/test`, `server/router/frontend`, `server/router/rss`, `server/runner/memopayload` |

| IdentityProvider / UserSetting / InstanceSetting | 0 | only reached through proto types at the API edge |

Definitions: `store/user.go:29` (`User`), `store/memo.go:35` (`Memo`).

Notes on robustness of the ranking:

- Excluding the `_test` packages doesn't change the order (User 6, Memo 5).
- Including the store-internal subpackages (`store/db/sqlite|mysql|postgres`, `store/test`) also doesn't change it (User 11, Memo 10) — those are part of the data layer itself.
- By raw reference count rather than package count, Memo edges ahead (64 vs 93 — actually User leads there too: 93 `store.User` refs vs 64 `store.Memo` refs outside `store/`), so both metrics agree.

`User` spreads wider because it is the authentication/authorization subject: `server/auth` carries it through session validation, `server/router/fileserver` uses it for attachment access checks, and `server/notification` and `server/router/rss` need the owner. `Memo` is denser inside `server/router/api/v1` (48 refs) but touches fewer packages.
