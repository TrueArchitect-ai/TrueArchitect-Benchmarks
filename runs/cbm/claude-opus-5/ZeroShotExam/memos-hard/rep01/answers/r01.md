**Premise correction:** There is no Redis in this repository. A case-insensitive search across the entire tree (Go source, `go.mod`/`go.sum`, docs, configs, web) returns zero matches for "redis" — no client dependency, no connection string, no config option. The cache layer is a hand-rolled, in-process, in-memory cache with no external server and no network configuration to point anywhere.

**Actual mechanism**

*The cache implementation* — `store/cache/cache.go`:
- `cache.Interface` (lines 10–32) defines `Set`/`SetWithTTL`/`Get`/`Delete`/`Clear`/`Size`/`Close`.
- `Cache` (line 66) is backed by a `sync.Map` plus an `atomic.Int64` item counter. Each `item` (line 35) stores the value, an absolute `expiration time.Time`, and a rough `size` estimate.
- Expiry is lazy plus swept: `Get` (line 118) deletes and reports a miss for any entry past `expiration`, and a background `cleanupLoop` goroutine (line 187) ticks on `CleanupInterval` to evict expired entries. `cleanupOldest` (line 244) trims ~20% when `MaxItems` is exceeded.

*Where it's "configured"* — `store/store.go:38–58`, in `store.New()`. The config is a hardcoded Go struct literal, not env vars or a config file:
```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
The same `cacheConfig` value is handed to three separate cache instances (`store/store.go:27–29`, `51–53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. All three goroutines are stopped in `Store.Close()` (`store/store.go:73–76`).

*TTL for user entries:* **10 minutes**, inherited from `DefaultTTL`. There is no user-specific TTL. Every write path calls plain `Set`, which forwards the default (`store/cache/cache.go:93–95`): `CreateUser` (`store/user.go:98`), `CreateUserIfNoUsers` (:122), `UpdateUser` (:132), `ListUsers` (:143, caching each listed user), and `GetUser` (:167). `SetWithTTL` is never called anywhere in the codebase outside of tests, so the 10-minute default is the only TTL in effect for user entries. Keys are the plain user ID (`userCacheKey`, `store/user.go:88`); `GetUser` only consults the cache when looking up by ID (`store/user.go:150`). Invalidation on delete is explicit: `store/user_delete.go:40`.

Note this is per-process memory, so in a multi-replica deployment each replica keeps its own copy — a stale user can persist on other replicas for up to 10 minutes after an update. That's the tradeoff Redis would normally remove, but it isn't wired up here.

Other, unrelated caches exist with their own TTLs — e.g. `instanceStatsCacheTTL = 60 * time.Second` (`server/router/api/v1/instance_stats.go:21`) and an RSS feed cache (`server/router/rss/rss.go:34`) — but neither touches user entries.
