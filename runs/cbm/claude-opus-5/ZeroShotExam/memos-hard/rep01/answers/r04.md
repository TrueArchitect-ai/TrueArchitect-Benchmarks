**Premise correction:** Neither. There is no external message broker in this repository — no NATS, RabbitMQ, Kafka, or Redis. `go.mod` contains no broker client dependency, and the only textual hit for "nats" anywhere in the tree is an unrelated Catalan word in `web/src/locales/ca.json`. Memos is a single Go binary, so webhook delivery never leaves the process.

**Actual mechanism:** an in-process buffered Go channel with a fixed pool of goroutine workers, all in `internal/webhook/webhook.go`:

- **"Queue" declaration** — `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel with capacity 128.
- **Workers** — `internal/webhook/webhook.go:42-55`: an `init()` function spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are only logged via `slog.Warn` — there is no retry, no dead-letter, and no persistence.
- **Producer** — `PostAsync` at `internal/webhook/webhook.go:184-196` does a non-blocking `select` send. If the buffer is full, the payload is **dropped** (logged as "Dropped webhook dispatch because the async queue is full"), rather than blocking or persisting.
- **Delivery** — `Post` at `internal/webhook/webhook.go:120` does the actual HTTP POST through `safeClient` (30s timeout, SSRF-guarded dialer at line 59), signing with HMAC-SHA256 per the Standard Webhooks spec when a signing secret is set.

Callers enqueue from the API layer: `server/router/api/v1/memo_service_webhooks.go:43` and `:71` (`webhook.PostAsync(payload)`) for memo created/updated/deleted and comment-created events.

Two consequences of this design worth noting: the queue is in-memory only, so anything pending is lost on restart, and dispatch is best-effort — a burst beyond 128 queued payloads silently drops webhooks.
