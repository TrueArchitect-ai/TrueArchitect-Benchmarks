**Premise correction:** Neither. This repository (memos) has no message broker at all — no NATS, no RabbitMQ, no Kafka or Redis. `grep` over `go.mod`/`go.sum` and the whole tree returns zero hits for `nats`, `amqp`, `rabbit`, or `kafka`, and there are no "webhook delivery workers" as separate processes.

**Actual mechanism:** webhook delivery is in-process, using a buffered Go channel and a fixed pool of goroutines, all inside `internal/webhook/webhook.go`:

- **The "queue"** is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:
  `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — capacity 128, in memory, per-process.
- **The "workers"** are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. There is no retry and no persistence — a payload lost to a restart is gone.
- **Enqueue** happens in `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send; if the buffer is full the payload is **dropped** with a warning rather than blocking the caller.
- **Delivery** itself is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120-180`), through a shared `http.Client` with a 30s timeout and an SSRF-guarding `DialContext` (`internal/webhook/webhook.go:32-37`, `59-77`), optionally signed per the Standard Webhooks scheme (`webhook-id` / `webhook-timestamp` / `webhook-signature` HMAC-SHA256).

Producers are the API layer: `server/router/api/v1/memo_service_webhooks.go:43` and `:71` call `webhook.PostAsync(payload)` after looking up the user's registered webhooks via `s.Store.GetUserWebhooks`. Webhook registrations themselves live in user settings (`server/router/api/v1/user_service_webhooks.go`, `store/user_setting.go`), not in any broker.
