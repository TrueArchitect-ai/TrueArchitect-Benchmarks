**Premise correction:** There is no Redis anywhere in this repository. `grep -ri redis` over the whole tree (including `go.mod`/`go.sum`) returns zero hits — there is no Redis client dependency, no connection string, no cache-related env var or config flag. The premise that a Redis connection is configured for the cache layer is false.

**Actual mechanism — an in-process, in-memory cache:**

- **Implementation:** `store/cache/cache.go` — a thread-safe in-memory `Cache` built on `sync.Map` plus an `atomic.Int64` item counter. Each entry (`item`, `store/cache/cache.go:35`) stores the value, an absolute `expiration` time, and a rough size estimate. A background goroutine (`cleanupLoop`, `store/cache/cache.go:200`) sweeps expired entries on a ticker, and `cleanupOldest` (`store/cache/cache.go:253`) evicts when the item cap is exceeded. Expired entries are also evicted lazily on `Get` (`store/cache/cache.go:135`).

- **Where it's "configured":** `store/store.go:38-61`. `store.New` builds a single `cache.Config` literal and hands the same config to three separate cache instances:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  used for `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). The same values are duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), though `store.New` doesn't call it. All three are shut down in `Store.Close` (`store/store.go:72-79`).

- **TTL for user entries:** **10 minutes**, inherited from `DefaultTTL`. `store/user.go` only ever calls `s.userCache.Set(...)` (lines 98, 122, 132, 143, 167), never `SetWithTTL`, and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). Keys are just the stringified user ID (`userCacheKey`, `store/user.go:88`). User settings use the same 10-minute TTL under the key `"<userID>-<settingKey>"` (`store/cache.go:7`).

  Two things can end a user entry earlier than 10 minutes: explicit invalidation on delete (`deleteUserCache`, `store/user_delete.go:39-47`), and the 1000-item cap triggering `cleanupOldest` — that cap is shared per-cache, so a busy instance can evict users before expiry.

Note also that the user cache is only consulted on lookup by ID (`store/user.go:150`); other find paths go straight to the driver.

Since this is a single-process in-memory cache, it is per-instance and not shared across replicas — there is no distributed cache tier to point a Redis connection at.
