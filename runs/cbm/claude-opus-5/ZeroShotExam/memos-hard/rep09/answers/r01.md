**Premise correction:** There is no Redis in this repository. `redis` appears nowhere in the Go source, config files, docs, or `go.mod` — there's no Redis client dependency at all. The cache layer is a hand-rolled, in-process, in-memory cache, so there is no connection to configure.

**Actual mechanism**

*The cache implementation* — `store/cache/cache.go` defines a thread-safe in-memory `Cache` backed by a `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). It's configured by a plain struct, not a connection string (`store/cache/cache.go:41-54`):

- `DefaultTTL` — per-entry time-to-live
- `CleanupInterval` — background sweep period
- `MaxItems` — capacity cap, triggering `cleanupOldest()` eviction of ~20% (`store/cache/cache.go:253-255`)
- `OnEviction` — optional eviction callback

A goroutine started in `cache.New` (`store/cache/cache.go:83`) ticks on `CleanupInterval` and drops expired entries; `Get` also lazily evicts on read when `time.Now().After(itm.expiration)` (`store/cache/cache.go:135-144`).

*Where it's "configured"* — `store.New` in `store/store.go:38-61`. One `cache.Config` literal is built inline and shared across all three caches: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). The values are hardcoded — no env var, flag, or profile setting feeds them, and `cacheConfig` is never overridden anywhere else in the codebase.

*TTL for user entries* — **10 minutes**, from `DefaultTTL: 10 * time.Minute` at `store/store.go:41`. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98, 122, 132, 143, 167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — nothing in the user path calls `SetWithTTL` with a custom duration, so users get the plain default. Cache keys are just the stringified user ID (`store/user.go:88-90`). Expired entries are swept every 5 minutes (`CleanupInterval`, `store/store.go:42`), capped at 1000 items.

`cache.DefaultConfig()` (`store/cache/cache.go:57-64`) happens to carry identical values, but `store.New` doesn't call it — it duplicates the literal.

One consequence worth noting: because this is in-process memory, each Memos instance has its own independent cache. In a multi-replica deployment, a user update on one replica leaves the other replicas serving stale user data for up to 10 minutes — there's no cross-instance invalidation, which is exactly the gap a shared Redis would close.
