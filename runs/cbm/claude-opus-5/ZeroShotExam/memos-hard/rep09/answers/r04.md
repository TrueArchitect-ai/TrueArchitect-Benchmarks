**Premise correction:** Neither. This repository (memos) has no external message broker at all — no NATS, no RabbitMQ, and no AMQP/Kafka/Redis/asynq client anywhere. `go.mod`/`go.sum` contain zero broker dependencies, and a grep for `nats|rabbitmq|amqp|kafka|redis` across all `.go` files returns nothing. There is also no separate "worker" process or deployment; webhook dispatch runs in-process inside the single memos server binary.

**Actual mechanism — an in-process buffered Go channel:**

The "queue" is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

The "workers" are four goroutines started from `func init()` in the same file (`internal/webhook/webhook.go:42-55`), each ranging over that channel and calling `Post` for every payload, logging a warning on failure.

Producers call `webhook.PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send: if the 128-slot buffer is full, the payload is **dropped** with a `"Dropped webhook dispatch because the async queue is full"` warning rather than blocking or retrying. A nil payload is likewise dropped with a warning.

Call sites that enqueue are in `server/router/api/v1/memo_service_webhooks.go:43` (comment-created) and `:71` (memo created/updated/deleted), each iterating the creator's registered webhooks from `s.Store.GetUserWebhooks`.

**Implications of it being a channel rather than a broker:** no durability (pending webhooks are lost on restart), no retries or dead-lettering, no cross-instance distribution, and at-most-once delivery with silent drops under backpressure. Actual HTTP delivery is done by `Post` (`internal/webhook/webhook.go:120`) using a shared 30-second-timeout client whose transport blocks reserved/private IPs at dial time to prevent SSRF, and it optionally signs requests with Standard Webhooks HMAC-SHA256 headers.
