Back up the stack, `serveUserAvatar` decodes `user.AvatarURL` — the avatar is stored as a base64 data URI in the `user.avatar_url` column, not as a file or attachment — via `FileServerService.parseDataURI` (`server/router/fileserver/fileserver.go:737`), rejects any MIME type outside `avatarAllowedTypes` (`:75-83`), sets nosniff/DENY/CSP headers plus `Cache-Control: public, max-age=3600`, and writes the bytes with `c.Blob` (`:196-209`).

Two things worth noting:
- The data layer is the `user` table itself — there is no filesystem or S3 hop for avatars, unlike attachments (`serveAttachmentFile`, same file:132).
- `/memos.api.v1.UserService/GetUserAvatar` appears in the ACL allowlist (`server/router/api/v1/acl_config.go:25`) but has no implementation anywhere in `server/` or the web client; the fileserver route above is the only live path.
