**No** — outside `NewDBDriver`, the MySQL driver is never constructed via its constructor. The one exception is a zero-value struct literal inside the package's own unit test, which is not a real driver instance.

Evidence:

1. **Single construction site.** `mysql.NewDB(profile)` is called exactly once in the whole repo: `store/db/db.go:22`, inside the `NewDBDriver` factory's `switch profile.Driver` (alongside `sqlite.NewDB` at :20 and `postgres.NewDB` at :24). A repo-wide `grep -rn "NewDB\b" --include="*.go"` returns only that call plus the three definitions and two `sqlite.NewDB` calls in tests (`store/demo_seed_test.go:24`, `store/deployment_config_test.go:416`).

2. **Single importer.** `grep -rn "store/db/mysql" --include="*.go" .` matches one line: `store/db/db.go:8`. No other package imports `store/db/mysql`, so no other package *can* construct it.

3. **No struct-literal bypass outside the package.** Searching `&DB{` / `new(DB)` across `store/` finds only in-package hits: `store/db/postgres/*` (including `postgres.go:33`, that package's own `NewDB`) and `store/db/mysql/auth_config_test.go:12`, which is `db := &DB{}` — an empty struct (nil `db`, `profile`, `config`) used solely to call the pure method `IsRetryableAuthenticationMutationError`. It never opens a connection.

4. **Tests go through the factory too.** The test harness constructs drivers via `db.NewDBDriver(profile)` (`store/test/store.go:28` and :50), selecting `"mysql"` by env (`getDriverFromEnv`, `getTestingProfileForDriver` at :75–:100) rather than calling `mysql.NewDB` directly.

One near-miss worth noting so it isn't mistaken for a counterexample: `store/test/containers.go:101–105` calls `mysql.Run(...)`, `mysql.WithDatabase(...)`, etc. — that's the *testcontainers* MySQL module spinning up a server container, not `store/db/mysql`. Likewise `store/db/mysql/mysql.go:17,30,73` reference `mysql.Config`/`mysql.ParseDSN` from `github.com/go-sql-driver/mysql`, the SQL driver library, not the repo's driver type.
