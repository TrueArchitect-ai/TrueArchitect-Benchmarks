h15.

Memo visibility (PUBLIC / PROTECTED / PRIVATE) is not centralized in one guard — it is re-implemented at each surface that can surface memo content. Distinct enforcement sites:

**Core API v1 (Connect/gRPC)**

- Single-memo read gate `checkMemoReadAccess` (PUBLIC → open; PROTECTED → any authenticated user; PRIVATE → creator only) — `server/router/api/v1/memo_service.go:39-68`; callers: `GetMemo` at `:356` and its parent-memo re-check at `:367`, and `ListMemoComments` at `server/router/api/v1/memo_service_comments.go:148`
- List-query scoping — `ListMemos` builds `VisibilityList`/CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` — `server/router/api/v1/memo_service.go:218-227`
- User-stats list scoping (same filter shape, separate copy) — `server/router/api/v1/user_service_stats.go:84-92` (ListAllUserStats) and `:216-221` (GetUserStats)
- Comment creation gate on the parent memo — `server/router/api/v1/memo_service_comments.go:41`; comment listing relation filter at `:156-162`
- Memo-relation expansion filters (so a relation can't leak a hidden memo's snippet) — `server/router/api/v1/memo_relation_service.go:107-112` and `server/router/api/v1/memo_service_converter.go:181-187` (`batchConvertMemoRelations`)
- Reactions — `server/router/api/v1/reaction_service.go:29-42` (ListMemoReactions) and `:83` (UpsertMemoReaction)
- Attachments over the API — `server/router/api/v1/attachment_service.go:437-454` (linked-attachment check) and `server/router/api/v1/memo_attachment_service.go:213-225` (ListMemoAttachments)

**Other server surfaces**

- HTTP file server (raw attachment/blob bytes) — `server/router/fileserver/fileserver.go:650-703` (`checkAttachmentPermission`; PUBLIC + AllowAnonymous, share-token fallback, then PRIVATE → creator or admin)
- SSE broadcast delivery filter — `server/router/api/v1/sse_hub.go:134-143` (`canReceive`), with event visibility/creator stamped in `server/router/api/v1/sse_event_helpers.go:24-39`
- Share links (deliberate visibility bypass, gated on a valid non-expired token) — `server/router/api/v1/memo_share_service.go:153-197` (`GetMemoByShare` + `getActiveMemoShare`); share management is creator/admin-only at `:43`, `:92`, `:133`
- RSS feeds — public-only `VisibilityList` — `server/router/rss/rss.go:90` (explore) and `:141` (per-user)
- Sitemap — public-only `VisibilityList` — `server/router/frontend/frontend.go:148-152`
- Notifications/inbox — `canViewerAccessMemo` in `server/router/api/v1/user_service_notifications.go:302-316`
- Notification emails — a second, independent `canViewerAccessMemo` — `server/notification/email.go:306-320`
- Mention notifications — `canUserAccessMentionContext` / `shouldSkipMentionInbox` — `server/router/api/v1/memo_mention_helpers.go:56-89`

**Store layer (mechanism the filters above rely on)** — `VisibilityList` → SQL `visibility IN (...)`, and the relation `MemoFilter` CEL clause: `store/db/sqlite/memo.go:96`, `store/db/postgres/memo.go:89`, `store/db/mysql/memo.go:104` (plus the `memo_relation.go` counterparts).

Note: the MCP surface is not a separate enforcement site — `server/router/mcp/adapter.go:33-89` replays tool calls as in-process HTTP requests against the same API handlers with the caller's `Authorization` header, so it inherits the API v1 checks.
