**Premise correction:** There is no Redis (or any external cache server) in this repository. `go.mod` (`/bench/repo/go.mod`) has no Redis client dependency, and a grep for `redis`/`memcache` across the Go sources, configs, and docs returns nothing. So there is no Redis connection to configure — no host/port, URL, pool, or auth settings exist.

**Actual mechanism:** The cache layer is a hand-rolled, in-process, in-memory cache living entirely inside the Go binary.

- Implementation: `/bench/repo/store/cache/cache.go` — a `Cache` backed by a `sync.Map` plus an `atomic.Int64` item counter, with per-entry `expiration` timestamps, a background `cleanupLoop()` goroutine, and size-based eviction (`cleanupOldest()`, which drops ~20% of `MaxItems` when the cap is exceeded). It exposes `Set`/`SetWithTTL`/`Get`/`Delete`/`Clear`/`Size`/`Close` via the `Interface` type.
- Configuration: `/bench/repo/store/store.go:38-61`. `store.New()` builds one `cache.Config` literal — `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil` — and hands the same config to three separate cache instances: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store.go:27-29`, `51-53`). These values are hardcoded; they are not read from env vars or a config file. `cache.DefaultConfig()` in `cache.go` defines an identical default.
- Lifecycle: `Store.Close()` (`/bench/repo/store/store.go:72-79`) closes all three caches, stopping their cleanup goroutines, before closing the DB driver.

**TTL for user entries:** 10 minutes. `userCache` is populated only through `Set` (`/bench/repo/store/user.go:98`, `122`, `132`, `143`, `167`), which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`cache.go`, `Set`). No call site anywhere in the repo uses `SetWithTTL` directly (grep outside `store/cache/` returns nothing), so users get the default 10-minute TTL with no override. Keys are the stringified user ID (`userCacheKey`, `/bench/repo/store/user.go:88-90`).

Expiry is lazy plus periodic: `Get` checks `time.Now().After(itm.expiration)` and evicts on read, while the 5-minute cleanup tick sweeps expired entries in the background. Entries can also disappear before the 10 minutes elapse — either via explicit invalidation (`s.userCache.Delete` in `/bench/repo/store/user_delete.go:40`) or via `MaxItems` eviction once the 1000-item cap is hit. Related but separate: user *settings* live in `userSettingCache` under a `"<userID>-<key>"` key (`getUserSettingCacheKey`, `/bench/repo/store/cache.go:7-9`) with the same 10-minute TTL.
