**Premise correction:** Neither. This repo (Memos) has no message broker at all — no NATS, no RabbitMQ, no AMQP client, no queue declaration anywhere. `go.mod`/`go.sum` contain no broker dependency, and the only textual "nats"/"amqp" hits in the tree are false positives inside Catalan words in `web/src/locales/ca.json` (e.g. "seleccio**nats**", "elimi**nats**"). Memos ships as a single self-contained Go binary, so there is no external broker to consume from.

**Actual mechanism — an in-process buffered Go channel with a fixed worker pool:**

- **The "queue"** is a plain buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, in package-level `var` block — process memory only, nothing durable.

- **The "workers"** are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`; failures are logged via `slog.Warn` and dropped — no retry, no dead-letter, no ack.

- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184-196`). It's a non-blocking `select` with a `default` branch: if the buffer is full the payload is **discarded** with a "Dropped webhook dispatch because the async queue is full" warning. A broker-backed design would block or persist here.

- **Enqueue call sites** are in `server/router/api/v1/memo_service_webhooks.go` — `dispatchMemoRelatedWebhook` (line 71) for `memos.memo.created/updated/deleted`, and `DispatchMemoCommentCreatedWebhook` (line 43) for `memos.memo.comment.created`. Each looks up subscriber URLs via `s.Store.GetUserWebhooks(ctx, creatorID)`.

- **Delivery itself** is a direct HTTP POST in `Post` (`internal/webhook/webhook.go:120-180`) using a shared `safeClient` with a 30s timeout and an SSRF-guarding `DialContext` (`webhook.go:32-37`, `safeDialContext` at line 59), plus optional Standard Webhooks HMAC-SHA256 signing (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers).

Practical consequence: webhook delivery is best-effort and non-durable — a process restart loses everything buffered, and burst traffic beyond 128 queued items is silently dropped rather than backpressured.
