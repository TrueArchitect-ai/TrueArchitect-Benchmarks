**Premise correction: there is no per-user API rate-limiting middleware in this repository.** Nothing registers a request-rate limiter, so there are no per-user request limits to report.

What's actually registered:

**HTTP middleware** — `server/server.go:51-52` is the complete Echo middleware stack:
```go
echoServer.Use(middleware.Recover())
echoServer.Use(newCORSMiddleware(profile))
```
Panic recovery and CORS (`server/cors.go`). No limiter.

**Connect RPC interceptors** — `server/router/api/v1/v1.go:133-137` is the complete chain:
- `NewMetadataInterceptor()` — HTTP headers → gRPC metadata
- `NewLoggingInterceptor(logStacktraces)`
- `NewRecoveryInterceptor(logStacktraces)`
- `NewAuthInterceptor(authorizer)` — authentication/anonymous-access policy only

All four are defined in `server/router/api/v1/connect_interceptors.go`. None counts requests per user or per IP.

### The closest thing that exists — and why it isn't what you're describing

Two **global concurrency semaphores**, initialized in `server/router/api/v1/v1.go:59-60`:

```go
thumbnailSemaphore:       semaphore.NewWeighted(3), // Limit to 3 concurrent thumbnail generations
imageProcessingSemaphore: semaphore.NewWeighted(2),
```

The image one is acquired in `acquireImageProcessingSlot` (`server/router/api/v1/attachment_service_image.go:67-77`) around EXIF stripping during attachment upload, returning `ResourceExhausted` / "too many image processing requests" at `server/router/api/v1/attachment_service.go:158-161`.

These differ from per-user rate limiting in three ways: they're **process-global**, not keyed by user or IP; they cap **simultaneous in-flight work**, not requests per time window; and they're **middleware-adjacent handler code** on two specific image paths, not registered middleware covering the API.

### Supporting evidence

- `golang.org/x/time` is marked `// indirect` in `go.mod:151` and is not imported by any file in the repo — the `rate.Limiter` package is pulled in transitively and unused.
- No rate-limiting dependency (tollbooth, ulule/limiter, didip, etc.) appears in `go.mod`.
- Repo-wide grep for `rate.limit` / `ratelimit` / `throttl` matches only `internal/email/README.md:286-297` and `internal/email/doc.go:86` — both are *recommendations* to future implementers of SMTP sending ("Example using golang.org/x/time/rate"), not shipped code.
- The one HTTP-level middleware file, `internal/scheduler/middleware.go`, is background-job middleware (`Chain`, `Recovery`, timeout) for the scheduler, unrelated to HTTP requests.

If you want per-user API rate limiting, the natural insertion point is a new interceptor in the `connect.WithInterceptors(...)` chain at `server/router/api/v1/v1.go:133`, placed after `NewAuthInterceptor` so the authenticated user is available for keying.
