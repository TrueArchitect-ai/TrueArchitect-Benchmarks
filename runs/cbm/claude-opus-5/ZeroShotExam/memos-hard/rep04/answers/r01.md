**Premise correction:** There is no Redis connection to configure. This repository (`github.com/usememos/memos`, a Go application) has zero Redis references — no `redis` dependency in `go.mod`, no client code, no connection string, no env var, no Docker/compose service. The same is true for Memcached or any other external cache server. The cache layer is entirely **in-process, in-memory**, so there is no connection to configure at all.

**Actual mechanism**

The cache is a hand-rolled implementation in `store/cache/cache.go` — a thread-safe `sync.Map` wrapper with per-item expiration timestamps, an item-count cap, and a background cleanup goroutine (`Cache.cleanupLoop`, `store/cache/cache.go:200`). Because it lives in the server process's memory, it is not shared across replicas and is lost on restart.

**Where it's "configured"** — in Go code, not in config files or env vars: `store.New()` builds a `cache.Config` literal at `store/store.go:40-45`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That one config is passed to three independent cache instances (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. `cache.DefaultConfig()` at `store/cache/cache.go:57-64` holds an identical set of values, but the store doesn't call it — it duplicates the literal inline. Nothing reads an environment variable or config file to override these; the values are compile-time constants.

**TTL on user entries: 10 minutes.** Every write to `userCache` goes through `Cache.Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). No user code path passes a custom TTL — `SetWithTTL` is never called directly outside the cache package and its tests. So user entries inherit the 10-minute default, with expiration stamped at write time (`time.Now().Add(ttl)`, `store/cache/cache.go:112`).

Two caveats on that 10 minutes being the effective lifetime:

- **Eviction can be earlier.** With `MaxItems: 1000`, exceeding the cap triggers `cleanupOldest` (`store/cache/cache.go:253`), which drops roughly 20% of entries. On an instance with more than 1000 users, `ListUsers` caches every returned user (`store/user.go:142-144`), so entries can be evicted well before their TTL.
- **Expiry is lazy plus periodic.** `Get` checks expiration on read and evicts on the spot (`store/cache/cache.go:135-144`); the sweeper otherwise runs every 5 minutes, so an expired entry may physically linger up to ~5 minutes past its TTL — but it is never *served*, since the read path rejects it.

Invalidation is explicit rather than TTL-driven for the paths that matter: updates re-`Set` the entry (`store/user.go:132`) and deletes purge it along with the user's settings (`store/user_delete.go:40-45`).
