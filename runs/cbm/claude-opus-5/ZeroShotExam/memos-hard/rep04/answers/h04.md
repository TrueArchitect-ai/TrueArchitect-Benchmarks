**No** — the MySQL driver is never constructed outside the factory in production code. The only exception is one in-package unit test that builds a zero-value struct.

Evidence:

1. **Single production construction site** — `store/db/db.go:22`, inside the factory `NewDBDriver`:
   ```go
   case "mysql":
       driver, err = mysql.NewDB(profile)
   ```

2. **Only one importer of the package** — `grep -rn "store/db/mysql" --include=*.go .` returns exactly one hit: `store/db/db.go:8`. No other Go file in the repo imports `github.com/usememos/memos/store/db/mysql`, so `mysql.NewDB` cannot be called from anywhere else. (Other files matching "mysql" reference the unrelated `github.com/go-sql-driver/mysql` package or the testcontainers `mysql` module in `store/test/containers.go:101`.)

3. **Constructor definition** — `store/db/mysql/mysql.go:20` `func NewDB(profile *profile.Profile) (store.Driver, error)`; internally it builds `driver := DB{profile: profile}` (line 29) and returns `&driver`. That is the factory's own path, not an external construction.

4. **Struct-literal search** — grepping `DB{` across `store/db/mysql/` yields only two hits: the constructor at `mysql.go:29`, and `store/db/mysql/auth_config_test.go:12` (`db := &DB{}`), an in-package test constructing an empty driver with no `*sql.DB` connection (it exercises pure logic, not database access). That's a same-package test, not a caller bypassing the factory.

For comparison, `sqlite.NewDB` *is* called directly outside the factory in two tests (`store/demo_seed_test.go:24`, `store/deployment_config_test.go:416`) — MySQL has no such direct callers.
