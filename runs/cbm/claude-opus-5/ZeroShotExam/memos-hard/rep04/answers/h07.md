`GET /file/users/{username}/avatar` — the browser reaches this because the API rewrites a base64 avatar into that path; the image bytes live in the `user.avatar_url` column as a data URI, not on disk or S3.

**Hops:**

- `convertUserFromStore` (rewrites base64 `AvatarURL` → `/file/users/{username}/avatar`) — server/router/api/v1/user_service_converters.go:36
- `FileServerService.RegisterRoutes` (`fileGroup.GET("/users/:identifier/avatar", …)`) — server/router/fileserver/fileserver.go:124 (wired at server/router/server.go → server/server.go:81)
- `FileServerService.serveUserAvatar` — server/router/fileserver/fileserver.go:168

- `Store.ListUsers` — store/user.go:136

**Return path:** `serveUserAvatar` then calls `FileServerService.parseDataURI` (server/router/fileserver/fileserver.go:737) to split the stored `data:image/png;base64,…` string into MIME type + bytes, rejects anything outside `avatarAllowedTypes` (fileserver.go:75), sets `X-Content-Type-Options`/`X-Frame-Options`/CSP via `setSecurityHeaders` plus `Cache-Control: public, max-age=3600`, and writes the decoded bytes with `c.Blob`.

Note the terminal hop is the `user` table itself — unlike attachments, avatars never touch `getAttachmentBlob`, local disk, or S3.
