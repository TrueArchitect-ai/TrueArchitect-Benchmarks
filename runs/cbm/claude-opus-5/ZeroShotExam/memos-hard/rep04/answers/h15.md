Memo visibility (PUBLIC / PROTECTED / PRIVATE) is enforced independently in several places — there is no single chokepoint. Grouped by surface:

**Core Connect/gRPC memo API**
- Single-memo read gate (`checkMemoReadAccess`, also applied to the parent of a comment) — `server/router/api/v1/memo_service.go:39` (callers at `:356`, `:367`)
- List-path query scoping in `ListMemos` (`VisibilityList` + `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` CEL filter) — `server/router/api/v1/memo_service.go:217-226`
- Comment listing: read gate plus its own visibility filter on the relation query — `server/router/api/v1/memo_service_comments.go:148`, `server/router/api/v1/memo_service_comments.go:156-162`
- Comment creation gate on the parent memo — `server/router/api/v1/memo_service_comments.go:41`
- User stats list-path scoping (both `ListAllUserStats` and per-user stats) — `server/router/api/v1/user_service_stats.go:84-92`, `server/router/api/v1/user_service_stats.go:217-221`
- Share-token read path (deliberate bypass of visibility; gated instead on token validity/expiry + non-archived) — `server/router/api/v1/memo_share_service.go:152` (`GetMemoByShare`, with `getActiveMemoShare`/`isMemoShareExpired`)

**Memo-adjacent API resources (re-check the owning memo's visibility)**
- Attachment access check — `server/router/api/v1/attachment_service.go:422` (`checkAttachmentAccess`, visibility branch at `:445-453`)
- `ListMemoAttachments` — `server/router/api/v1/memo_attachment_service.go:213-225`
- Reactions: `ListMemoReactions` and `UpsertMemoReaction` — `server/router/api/v1/reaction_service.go:29-41`, `server/router/api/v1/reaction_service.go:82-85`

**Non-gRPC HTTP surfaces**
- Raw attachment/file serving (own auth path, incl. anonymous-instance rule and `share_token` fallback) — `server/router/fileserver/fileserver.go:650` (`checkAttachmentPermission`, visibility logic at `:676-701`)
- RSS feeds — public-only query — `server/router/rss/rss.go:90` (explore), `server/router/rss/rss.go:141` (per-user)
- Sitemap — public-only query — `server/router/frontend/frontend.go:150`

**Push / notification fan-out**
- SSE broadcast filtering per connected client — `server/router/api/v1/sse_hub.go:135` (`SSEClient.canReceive`; event visibility populated in `server/router/api/v1/sse_event_helpers.go:29-37`)
- In-app notification visibility (`canViewerAccessMemo`) — `server/router/api/v1/user_service_notifications.go:302` (used at `:337`, `:342`, `:370`, `:385`)
- Email notification visibility (a second, separate `canViewerAccessMemo`) — `server/notification/email.go:306` (used at `:155`, `:187`)
- Mention notification/inbox eligibility — `server/router/api/v1/memo_mention_helpers.go:56` (`canUserAccessMentionContext`), `server/router/api/v1/memo_mention_helpers.go:74` (`shouldSkipMentionInbox`)

Shared mechanism (not an independent policy): `FindMemo.VisibilityList` is translated to SQL per driver in `store/db/sqlite/memo.go:96`, `store/db/postgres/memo.go:89`, `store/db/mysql/memo.go:104` — the list-path sites above rely on it.

Note the MCP surface (`server/router/mcp/`) is not a separate site: `server/router/mcp/adapter.go:27` proxies tool calls back through the HTTP API, so it inherits the `ListMemos`/`GetMemo` checks.
