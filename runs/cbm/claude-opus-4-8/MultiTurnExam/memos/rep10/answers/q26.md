`Store.DeleteMemo` (`store/memo.go:140-158`) explicitly cascades: it deletes `memo_relation` rows (both source and target directions), deletes linked `attachment` rows (via `DeleteAttachment` → `driver.DeleteAttachment`, plus storage cleanup), then deletes the `memo` row itself. The API handler additionally recurses into comment memos (`server/router/api/v1/memo_service.go:567-577`), but those hit the same three tables.

Note: `reaction` rows are **not** removed by this code path — the API `DeleteMemo` lists reactions only to build the webhook payload, and no explicit reaction deletion occurs (so orphan cleanup would rely on DB-level constraints, not cascade code here).
