**Mechanism: explicit Go code** (in the `DeleteUser` transaction for all three DB backends). There is no database-level cascade — the `reaction` table has no foreign key on `creator_id`/`content_id`, so nothing would clean them up automatically.

### What I checked

**1. The delete path — explicit SQL in Go.** `DeleteUser` runs a transaction that explicitly removes reactions two ways:
- `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on the deleted user's memos* (any user's reactions).
- `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` — removes reactions *the deleted user made* on anyone's content.

Both are invoked from `deleteUserTargetsTx` (calls at `store/db/sqlite/user_delete.go:96` and `:102`; definitions at `:380` and `:400`). The same code exists per backend:
- SQLite: `store/db/sqlite/user_delete.go:380`, `:400`
- Postgres: `store/db/postgres/user_delete.go` (same structure)
- MySQL: `store/db/mysql/user_delete.go` (same structure)

**2. The schema — no DB-level rule.** The `reaction` table definition in every backend's `LATEST.sql` has only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type`, and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — **no `FOREIGN KEY ... REFERENCES user ... ON DELETE CASCADE`**:
- `store/migration/sqlite/LATEST.sql:92`
- `store/migration/postgres/LATEST.sql:91`
- `store/migration/mysql/LATEST.sql:91`

So the removal depends entirely on the explicit Go code; the database would not do it on its own.
