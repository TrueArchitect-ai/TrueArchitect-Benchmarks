**Premise correction:** There is no Redis anywhere in this codebase. A search for `redis` across all Go files and `go.mod` returns nothing — the cache layer is not backed by Redis and there is no Redis connection to configure. The cache is a purely **in-process, in-memory** implementation.

**Actual mechanism:**
- The cache is defined in `store/cache/cache.go` — an in-memory store guarded by `sync`/`sync/atomic` primitives (`store/cache/cache.go:1`–`8`), implementing the `cache.Interface` (`store/cache/cache.go:10`). Entries carry an `expiration time.Time` and are reaped by a background cleanup goroutine on a `CleanupInterval`; `Close()` stops that goroutine (there is no external connection to close).
- Configuration happens in `store.New`, not via any connection string. The `cache.Config` there sets `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store/store.go:40`–`45`), and this one config is used to construct all three caches, including the user cache: `userCache: cache.New(cacheConfig)` (`store/store.go:52`).

**TTL for user entries: 10 minutes.** User rows are written with `s.userCache.Set(...)` (e.g. `store/user.go:98`, `:122`, `:143`, `:167`), and `Set` applies the cache's `DefaultTTL` (`store/cache/cache.go:12`–`13`), which is the 10-minute value configured in `store/store.go:41`. There is no user-specific TTL override — it inherits the default.
