**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the delete-user transaction — in two ways: reactions the user *created* (by `creator_id`) and reactions on the *user's memos* (by `content_id`). This is done identically in all three DB drivers; there is no reliance on a database-level cascade rule.

Evidence locations (per driver, all invoked from `deleteUserTargetsTx`):

- MySQL — `store/db/mysql/user_delete.go`:
  - `deleteReactionsByContentIDsTx` (line 380) → `DELETE FROM reaction WHERE content_id IN (...)` — reactions on the deleted user's memos.
  - `deleteReactionsByCreatorTx` (line 401) → `DELETE FROM reaction WHERE creator_id = ?` — reactions the user themselves made.
  - Both wired in `deleteUserTargetsTx` at lines 96 and 102.
- Postgres — `store/db/postgres/user_delete.go`: same two functions (lines 380, 400), called at lines 96, 102.
- SQLite — `store/db/sqlite/user_delete.go`: same two functions (lines 380, 400), called at lines 96, 102.

What I checked and did not find: I looked for a database-level rule instead — the reaction table schema/migrations define no `ON DELETE CASCADE` foreign key that would auto-remove reactions; removal is driven entirely by the explicit Go statements above. (The reaction's `content_id` links to a memo by resource name `memos/{uid}`, not a FK, so a cascade isn't even available for that path — it must be, and is, done in code.)
