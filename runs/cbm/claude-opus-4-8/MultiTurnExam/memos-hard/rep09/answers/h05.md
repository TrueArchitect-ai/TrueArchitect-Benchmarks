**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the per-driver `DeleteUser` transaction — there is no database-level cascade rule. Reactions are cleaned up in two directions:
1. Reactions the user *authored* — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`.
2. Reactions *on the user's memos* (deleted along with those memos) — `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` in batches.

What I checked:
- **Explicit code (all three drivers):** `store/db/sqlite/user_delete.go:380` (`deleteReactionsByContentIDsTx`) and `:400` (`deleteReactionsByCreatorTx`); the same functions in `store/db/postgres/user_delete.go:383,401` and `store/db/mysql/user_delete.go:420,438`. These are invoked from each driver's `DeleteUser` (e.g. `store/db/sqlite/user_delete.go:29`), reached via the store method `Store.DeleteUser` (`store/user.go:171`).
- **Schema — no DB rule:** the `reaction` table definition (`store/migration/sqlite/LATEST.sql:92-99`, and the `0.20`/`0.23` reaction migrations) declares only a `UNIQUE` constraint on `(creator_id, content_id, reaction_type)` and has **no** `FOREIGN KEY` / `ON DELETE CASCADE` / `REFERENCES`. A grep for `foreign key|cascade|references` across all reaction migrations and the `LATEST.sql` files returned nothing.
- **Test corroboration:** `store/test/user_delete_test.go:13` (`TestDeleteUserCleansRelatedData`).

Answer: **explicit Go code (no DB cascade); evidence — `store/db/sqlite/user_delete.go:380,400`, `store/db/postgres/user_delete.go:383,401`, `store/db/mysql/user_delete.go:420,438` (called from each `DeleteUser` / `store/user.go:171`), while the `reaction` schema in `store/migration/*/LATEST.sql` (sqlite lines 92–99) defines no foreign key or cascade.**
