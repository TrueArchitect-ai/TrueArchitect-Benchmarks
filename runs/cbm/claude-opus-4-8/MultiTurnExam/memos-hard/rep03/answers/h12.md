**Concrete method: `(*DB).CreateMemo` in the SQLite driver — `store/db/sqlite/memo.go:16`**, which builds and executes `INSERT INTO \`memo\` (...) VALUES (...) RETURNING ...` (`store/db/sqlite/memo.go:41-42`).

**How I determined which of the three candidates runs** (there are parallel `CreateMemo` methods in `store/db/sqlite/memo.go`, `store/db/postgres/memo.go`, and `store/db/mysql/memo.go`, all satisfying the `store.Driver` interface):

1. The store calls the memo INSERT polymorphically through the interface: `Store.CreateMemo` → `s.driver.CreateMemo(ctx, create)` (`store/memo.go:109,113`). So the concrete method is whichever `store.Driver` was constructed.
2. The driver is chosen by the factory `NewDBDriver`, which switches on `profile.Driver` and has no fallthrough default that picks a driver — an unknown value errors (`store/db/db.go:18-27`). So the result depends entirely on the configured driver string.
3. With a **default installation (no flags)**, that string is `"sqlite"`: the CLI sets `viper.SetDefault("driver", "sqlite")` and the flag default is `"sqlite"` (`cmd/memos/main.go:122` and `:130`), which populates `Profile.Driver` (`cmd/memos/main.go:43`; field at `internal/profile/profile.go:30`).
4. Therefore the factory takes the `case "sqlite": sqlite.NewDB(profile)` branch (`store/db/db.go:20`), and `s.driver` is the SQLite `*DB` — so the INSERT is executed by `store/db/sqlite/memo.go:16`, not the postgres/mysql variants.
