**Premise correction:** The webhook delivery workers consume from **neither NATS nor RabbitMQ** — this codebase uses no external message broker at all. There are zero references to `nats`, `rabbitmq`/`amqp`, or `kafka` in the Go code, and no such dependency in `go.mod`. There is no broker queue "declared" anywhere.

**Actual mechanism:** Webhook delivery is handled entirely in-process using a buffered Go channel as the queue:
- The queue is a package-level buffered channel with capacity 128: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`.
- The workers are 4 goroutines started in `init()` that range over that channel and call `Post` for each payload — `internal/webhook/webhook.go:42-55`.
- Producers enqueue via `PostAsync`, which does a non-blocking send onto the channel and drops the event (with a warning log) if the buffer is full — `internal/webhook/webhook.go:184-196`.
- Actual HTTP delivery converges in `Post` (`internal/webhook/webhook.go:120`), sending via the SSRF-guarded `safeClient`.

So it is a single-process, in-memory channel-and-goroutine-pool design — no broker, no durable queue, and dropped-on-overflow semantics rather than broker-backed persistence.
