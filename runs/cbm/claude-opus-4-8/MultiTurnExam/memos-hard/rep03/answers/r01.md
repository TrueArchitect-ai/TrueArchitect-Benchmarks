**Premise correction:** There is no Redis anywhere in this codebase. A repo-wide search finds zero `redis` references in Go code and no Redis dependency in `go.mod`. The cache layer is **not** backed by Redis — it is a process-local, in-memory TTL cache.

**Actual mechanism:**
- The cache implementation is `store/cache/cache.go` — a thread-safe in-memory cache (`sync.Map` + atomic counters + a background cleanup goroutine), defined by the `Interface` (`store/cache/cache.go:10`) and `Cache` type. There is no connection to configure — nothing is opened, dialed, or authenticated.
- The user cache is one of three such in-memory caches constructed in `store.New` — `userCache: cache.New(cacheConfig)` at `store/store.go:52`, using the config built at `store/store.go:40-45`.
- **TTL for user entries: 10 minutes.** User rows are cached via `s.userCache.Set(...)` in `Store.GetUser` (`store/user.go:167`), and `Set` applies the cache's `DefaultTTL`, which is `10 * time.Minute` (`store/store.go:41`; same value in `cache.DefaultConfig`, `store/cache/cache.go:60`). The cache also runs cleanup every 5 minutes and caps at 1000 items (`store/store.go:42-43`). Cache entries are additionally invalidated on user create/update/delete via `deleteUserCache` (`store/user.go`), independent of the TTL.
