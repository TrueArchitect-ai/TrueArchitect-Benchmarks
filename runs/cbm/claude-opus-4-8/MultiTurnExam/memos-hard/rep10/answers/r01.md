**Premise correction: there is no Redis in this project.** A repo-wide search for `redis` across all Go files returns zero matches. The cache layer is not backed by Redis (or any external cache server) — it's a custom **in-process, in-memory** cache.

**Actual mechanism:**
- The cache implementation is `store/cache/cache.go` — a mutex/`sync`-based in-memory store of `item{value, expiration, size}` with a background cleanup goroutine (`cache.Interface` at `store/cache/cache.go:11`, config at `:40`). There is no connection to configure; it lives entirely in the process.
- It's instantiated in `store.New` (`store/store.go:38`), which builds one `cacheConfig` and creates three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`).
- **Config / TTL:** `cacheConfig` sets `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store/store.go:40-45`). The same 10-minute default is also the library default (`store/cache/cache.go:57`, `DefaultConfig`).
- **User entries specifically:** user records are written with the plain `Set` (not `SetWithTTL`) — e.g. `store/user.go:98,122,132,143,167` — so they use the cache's `DefaultTTL`, i.e. **10 minutes** (with cleanup sweeps every 5 minutes and a 1000-item cap). `GetUser`/`ListUsers` populate this cache (`store/user.go`, `store/store.go:143`).

So: no Redis connection exists; user cache entries expire after a 10-minute in-memory TTL.
