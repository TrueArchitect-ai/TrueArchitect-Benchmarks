**Mechanism: explicit Go code.** The user's emoji reactions are removed by hand-written `DELETE FROM reaction ...` statements inside the `DeleteUser` transaction — not by an ON DELETE CASCADE / database rule, and not "not at all."

Evidence locations (I checked the store layer and all three driver implementations):

- **Orchestration:** `store/db/sqlite/user_delete.go:92-127` (`deleteUserTargetsTx`) runs the deletes in one transaction. Two explicit reaction deletions fire:
  - `deleteReactionsByContentIDsTx` (line 96) — reactions attached to the deleted user's content.
  - `deleteReactionsByCreatorTx` (line 102) — reactions the user themselves authored.
- **The actual SQL for the user's own reactions:** `store/db/sqlite/user_delete.go:400-403` — `DELETE FROM reaction WHERE creator_id = ?`. Content-scoped deletion is at `store/db/sqlite/user_delete.go:380`.
- **Same explicit code in the other two drivers** (so it's not driver-specific cascade behavior): `store/db/mysql/user_delete.go:417` and `:437`, and `store/db/postgres/user_delete.go:380` and `:400`.
- **Driver contract:** the store exposes reaction operations as ordinary Go methods (`store/driver.go:70-74`), consistent with deletion being application-level rather than DB-rule-level.

So both categories of a user's emoji reactions — those they created and those on their content — are deleted by explicit Go code within the transactional `DeleteUser` flow.
