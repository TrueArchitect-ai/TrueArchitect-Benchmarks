**Mechanism: explicit Go code** (executed inside the user-deletion transaction). There is no database-level cascade rule — the `reaction` table has no foreign key / `ON DELETE CASCADE`.

Evidence locations:
- **Explicit deletion code** — in the per-driver `DeleteUser` transaction, `deleteUserTargetsTx` calls two reaction cleanups:
  - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` for the deleted user's memos (`store/db/sqlite/user_delete.go:96`, `:380-388`). This removes reactions *on* the user's content (regardless of who reacted).
  - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:102`, `:400-403`). This removes the reactions the user *made*.
  - The same code exists for the other drivers: `store/db/postgres/user_delete.go:96,102` and `store/db/mysql/user_delete.go` (which has the matching `deleteReactionsBy...Tx` helpers).
- **No DB-level rule** — the `reaction` table definition has no foreign key or cascade on `creator_id`/`content_id`; it only declares columns and a `UNIQUE(creator_id, content_id, reaction_type)` constraint (`store/migration/sqlite/LATEST.sql:92-99`). So the removal depends entirely on the explicit Go code above.

Answering directly: the emoji reactions a deleted user made (and those on their content) **are removed, by explicit Go code**, not by a database cascade.
