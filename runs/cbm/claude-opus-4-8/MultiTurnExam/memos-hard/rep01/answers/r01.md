**Premise correction:** There is no Redis anywhere in this codebase. A repo-wide search for `redis` in Go sources returns nothing, and there is no Redis client dependency. The cache layer is an **in-process, in-memory cache** — a custom implementation in `store/cache/cache.go` (backed by a Go map with a background cleanup goroutine), not an external/networked cache. So there is no "Redis connection to configure."

**Actual mechanism:**
- The cache type is `cache.Cache` implementing `cache.Interface` — `store/cache/cache.go:11-32`. Entries are plain in-memory `item` structs with an `expiration` timestamp (`store/cache/cache.go:34-39`).
- It is instantiated (not connected — just allocated in-process) in the `Store` constructor `store.New`, which builds one shared `cache.Config` and creates three caches: `instanceSettingCache`, `userCache`, and `userSettingCache` via `cache.New(cacheConfig)` — `store/store.go:40-53`.
- The **TTL for user entries** comes from that config's `DefaultTTL`: **10 minutes** (`store/store.go:41`; the package default is likewise 10 minutes in `cache.DefaultConfig`, `store/cache/cache.go:59`). User entries are written with the default-TTL `Set` (e.g. `s.userCache.Set(...)` in `(*Store).GetUser`, `store/user.go:167`), so no custom TTL is applied — they expire 10 minutes after being cached, with a cleanup sweep every 5 minutes (`store/store.go:42`) and a 1000-item cap (`store/store.go:43`).
