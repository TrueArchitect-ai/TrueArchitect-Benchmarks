**Premise correction: neither. The webhook delivery workers do not consume from any external message broker — there is no NATS and no RabbitMQ in this codebase.** A repo-wide search finds no NATS (`nats.go`) or RabbitMQ/AMQP client dependency or import anywhere in the Go sources.

**Actual mechanism:** The "queue" is a plain **in-process, buffered Go channel** held in package state:
- Declared as `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39` (a bounded buffer of 128 payloads).
- The delivery workers are 4 goroutines started in the package `init()` that range over that channel and call `Post` for each payload — `internal/webhook/webhook.go:42-55`.
- Producers enqueue via `PostAsync`, which does a non-blocking send onto the channel and drops the payload (with a warning log) if the buffer is full — `internal/webhook/webhook.go:184-196`.

So webhook delivery is an entirely in-memory producer/consumer setup within a single process (channel + goroutine pool), not a broker-backed queue. Because the queue is in-memory and non-durable, enqueued webhooks are lost on process restart or when the 128-slot buffer overflows.
