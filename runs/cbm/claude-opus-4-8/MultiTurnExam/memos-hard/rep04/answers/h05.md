**mechanism: explicit Go code** (inside the `DeleteUser` transaction) — there is no database-level cascade rule.

**Evidence locations:**

1. **Explicit deletion in Go.** `DeleteUser` (`store/db/sqlite/user_delete.go:29`) runs `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92`), which explicitly deletes reactions in two ways:
   - `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400`) → `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the deleted user authored.
   - `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380`) → `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions attached to the user's (also-deleted) memos.
   The same logic exists in the postgres and mysql drivers (`store/db/postgres/user_delete.go`, `store/db/mysql/user_delete.go` — both define `deleteUserTargetsTx` and the matching reaction-delete helpers).

2. **No DB-level rule.** The `reaction` table schema (`store/migration/sqlite/LATEST.sql:92`) declares `creator_id` and `content_id` as plain columns with no `FOREIGN KEY … ON DELETE CASCADE`. I checked the LATEST schema; there is no FK constraint tying reactions to users, so the database would not remove them on its own — the Go code is what does it.
