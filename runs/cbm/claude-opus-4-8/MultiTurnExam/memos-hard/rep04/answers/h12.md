**concrete method — path:** `(*DB).CreateMemo` in the SQLite driver — `store/db/sqlite/memo.go:16`, which builds and executes the statement `INSERT INTO \`memo\` (...) VALUES (...) RETURNING ...` via `d.db.QueryRowContext` at `store/db/sqlite/memo.go:40–41`.

**determination method:** I followed the driver-selection chain from the default configuration to the concrete implementation:

1. **Default driver value.** With no flags, the `driver` setting defaults to `"sqlite"` — set two ways in `cmd/memos/main.go`: `viper.SetDefault("driver", "sqlite")` (`cmd/memos/main.go:122`) and the flag default in `rootCmd.PersistentFlags().String("driver", "sqlite", ...)` (`cmd/memos/main.go:130`). The value is read into the profile at `cmd/memos/main.go:43` (`Driver: viper.GetString("driver")`). (`internal/profile/profile.go:110` further confirms sqlite is the assumed default by auto-filling its DSN when empty.)

2. **Factory dispatch.** `NewDBDriver` (`store/db/db.go:14`) switches on `profile.Driver`; the `case "sqlite":` branch constructs `sqlite.NewDB(profile)` (`store/db/db.go:20`). So the polymorphic `store.Driver` interface is backed by the SQLite `*DB` — not the postgres or mysql candidates.

3. **Save path resolves to that driver.** `Store.CreateMemo` (`store/memo.go:109`) delegates to `s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`). Since `s.driver` is the SQLite `*DB`, that interface call binds to `store/db/sqlite/memo.go:16`, which issues the `INSERT`.

That's how I ruled out the postgres (`store/db/postgres/memo.go`) and mysql (`store/db/mysql/memo.go`) `CreateMemo` implementations: they satisfy the same interface but are only constructed when `driver` is set to `postgres`/`mysql`, which a default install does not do.
