**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the delete-user transaction — in two ways: reactions *created by* the user (`creator_id`), and reactions *on the user's memos* (by `content_id`). This is done in every DB driver, not via a database-level cascade.

Evidence locations:

- **MySQL** (`store/db/mysql/user_delete.go`): the transaction orchestrator `deleteUserTargetsTx` calls `deleteReactionsByContentIDsTx` (line 95) and `deleteReactionsByCreatorTx` (line 102). Their implementations run `DELETE FROM reaction WHERE content_id IN (...)` (`deleteReactionsByContentIDsTx`, ~line 380-384) and `DELETE FROM reaction WHERE creator_id = ?` (`deleteReactionsByCreatorTx`, ~line 400-402). The content IDs come from the user's memos, built as `"memos/"+memo.UID` in `memoContentIDsFromRefs`.
- **Postgres** (`store/db/postgres/user_delete.go`): same two calls at lines 96 and 102, with the `DELETE FROM reaction ...` statements at lines 380-384 and 400-401.
- **SQLite** (`store/db/sqlite/user_delete.go`): same two calls at lines 96 and 102, with the `DELETE FROM reaction ...` statements at lines 380-384 and 400-401.

I checked the per-driver `user_delete.go` files (the only place `DeleteUser` is implemented); deletion is driven by explicit SQL in Go rather than an `ON DELETE CASCADE` foreign-key rule.
