**Premise correction:** Neither. The webhook delivery workers don't consume from a message broker at all — there is no NATS or RabbitMQ anywhere in this repository (nothing in `go.mod`, and no `nats`/`amqp`/`rabbitmq` imports in any Go file).

**Actual mechanism:** Webhook delivery is handled entirely in-process using a buffered Go channel and a fixed pool of goroutine workers, all in `internal/webhook/webhook.go`:

- The "queue" is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  It's an in-memory Go channel with capacity 128, not a broker-declared queue.

- The workers are 4 goroutines spun up in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` (a direct HTTP POST via a shared, SSRF-guarded `http.Client`) for each payload.

- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto `asyncPostQueue` and drops the payload (logging a warning) if the buffer is full.

So the delivery model is: buffered in-process channel (`asyncPostQueue`) → 4 goroutine workers → synchronous HTTP POST. There is no external message broker involved, and consequently no broker-side queue declaration.
