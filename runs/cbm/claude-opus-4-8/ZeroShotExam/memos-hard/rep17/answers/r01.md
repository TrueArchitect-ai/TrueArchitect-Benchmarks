**Premise correction:** There is no Redis anywhere in this repository — a case-insensitive search for `redis` across the whole codebase returns zero matches. The cache layer is **not** backed by Redis; it is a custom, thread-safe **in-process in-memory cache** built on `sync.Map`, defined in `store/cache/cache.go`.

**Actual mechanism:**

- **Where it's configured:** The cache is instantiated in the store constructor `New(...)` in `store/store.go:38-53`. A single `cache.Config` literal (lines 40-45) is shared to create three separate in-memory cache instances — `instanceSettingCache`, `userCache`, and `userSettingCache` (each a `*cache.Cache` from `cache.New(cacheConfig)`). There is no connection string, host, port, or external store involved; it lives inside the Go process and is torn down via `Close()` (`store/store.go:74-76`).

- **The cache implementation** (`store/cache/cache.go`) is a TTL map with a background cleanup goroutine (`cleanupLoop`/`cleanup`), size-based eviction (`cleanupOldest`), and atomic item counting.

- **TTL for user entries:** User entries are stored in `userCache`, which uses the shared config's `DefaultTTL` of **10 minutes** (`store/store.go:41`; the package default in `store/cache/cache.go:59` is also `10 * time.Minute`). User records are written via `s.userCache.Set(...)` in `store/user.go` (e.g. lines 98, 122, 132, 143, 167), and `Set` applies the default TTL (`cache.go:93-95`). There is no user-specific `SetWithTTL` override, so users expire 10 minutes after write, with expired entries reaped either lazily on `Get` or by the cleanup loop every 5 minutes (`CleanupInterval`, `store/store.go:42`).

Related keys: user cache key is `userCacheKey(userID)` (`store/user.go:88`); user-setting cache key is `getUserSettingCacheKey` (`store/cache.go:7`).
