## h05.

**Mechanism: removed by explicit Go code** (two `DELETE FROM reaction` statements in the user-deletion transaction), **not** by a database-level rule — the `reaction` table has no foreign key on `creator_id`, so there is no cascade.

### Evidence

**Explicit Go deletions** — `store/db/sqlite/user_delete.go`, inside `deleteUserTargetsTx` (the transactional worker for `DeleteUser`):

- Line 96 → `deleteReactionsByContentIDsTx(...)`, defined at lines 380–388: `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on* the deleted user's memos (content IDs built as `memos/<uid>` at line 512–518).
- Line 102 → `deleteReactionsByCreatorTx(...)`, defined at lines 400–403: `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the user *made*.

Both run inside the single transaction opened in `DeleteUser` (`store/db/sqlite/user_delete.go:29-59`), which is what the store facade `store/user.go:171` calls via `s.driver.DeleteUser`, itself invoked from the API handler `server/router/api/v1/user_service.go:414`.

The same driver method exists for the other backends (`store/db/postgres/user_delete.go:29`, `store/db/mysql/user_delete.go:29`), confirming this is engine-independent Go logic rather than a per-DB rule.

**No database-level rule** — the `reaction` table schema declares `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and no `FOREIGN KEY`/`ON DELETE CASCADE`:
- `store/migration/sqlite/0.20/00__reaction.sql:1-9`
- `store/migration/sqlite/LATEST.sql:91-98` (and the postgres/mysql `LATEST.sql` equivalents). In `LATEST.sql`, the only `FOREIGN KEY … ON DELETE CASCADE` present is on `memo_organizer` (line 109), not on `reaction`.

### What I checked
- Located the deletion path: `user_service.go` → `store/user.go` → driver `user_delete.go`.
- Read the full `store/db/sqlite/user_delete.go` (the two reaction deletes above).
- Grepped the reaction migration/schema files for `FOREIGN KEY`/`CASCADE`/`creator_id` and found none on the `reaction` table.

I did not exhaustively diff the postgres/mysql `user_delete.go` bodies line-by-line, but they expose the identical `DeleteUser` driver entry point, and their reaction schemas likewise lack a foreign key.
