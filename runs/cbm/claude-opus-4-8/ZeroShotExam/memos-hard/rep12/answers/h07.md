The browser hits `GET /file/users/:identifier/avatar`. The avatar image is not a separate file/attachment — it's stored inline as a base64 data URI in the `avatar_url` column of the `user` table, fetched via the normal user-lookup path and decoded at serve time.

Hops (browser → data layer):

route `GET /file/users/:identifier/avatar` → RegisterRoutes — server/router/fileserver/fileserver.go:124
serveUserAvatar (handler; on private instances first authenticates the viewer, then looks up the *target* user by the `:identifier` param) — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
store.(*Store).GetUser — store/user.go:148
store.(*Store).ListUsers — store/user.go:136
store.Driver.ListUsers (interface hop) — store/driver.go:47
db.(*DB).ListUsers (concrete driver; SELECTs `avatar_url` FROM `user`) — store/db/sqlite/user.go:88 (mirrored in store/db/postgres/user.go and store/db/mysql/user.go)

Then back in the handler, the stored data is decoded and written to the response:
parseDataURI (decodes `user.AvatarURL` data URI → mime type + bytes) — server/router/fileserver/fileserver.go:737
`c.Blob(...)` writes the image bytes — server/router/fileserver/fileserver.go:209

Stored data: the image lives entirely in `user.avatar_url` (a `data:<mime>;base64,...` URI), so the DB row *is* the backing store — there is no filesystem/S3 hop for avatars, unlike attachments.
