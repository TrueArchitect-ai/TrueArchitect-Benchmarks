**Mechanism: Explicit Go code.** A user's emoji reactions are removed by hand-written `DELETE FROM reaction ...` statements inside the delete-user transaction — there is no database-level cascade for the `reaction` table.

**Evidence:**

- **The `reaction` table has no foreign key / no `ON DELETE CASCADE`.** In all three dialects the table is a bare table keyed only by `creator_id`/`content_id` columns with no FK constraint:
  - `store/migration/sqlite/LATEST.sql:92-99`
  - `store/migration/postgres/LATEST.sql:91-98`
  - `store/migration/mysql/LATEST.sql:91-98`
  
  (Contrast with the adjacent `memo_share` table at lines 102–110, which *does* declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` — showing cascade is used deliberately elsewhere but not for reactions.)

- **Explicit Go deletes.** `store/db/sqlite/user_delete.go` runs two reaction-deleting statements as steps in `deleteUserTargetsTx` (lines 96 and 102):
  - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions on the deleted user's memos (`store/db/sqlite/user_delete.go:380-388`).
  - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user themselves made on any content (`store/db/sqlite/user_delete.go:400-403`).

- **Same in the other dialects:** `store/db/postgres/user_delete.go:383,401` and `store/db/mysql/user_delete.go:420,438`.

So both directions are covered — reactions *by* the user and reactions *on* the user's memos — and it is done entirely by explicit application code within the transaction, not by a DB-level rule.
