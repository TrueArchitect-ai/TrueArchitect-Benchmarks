**Premise correction:** Neither. The webhook delivery workers do not consume from NATS *or* RabbitMQ — this repository (Memos) uses no external message broker for webhooks at all.

**Actual mechanism:** Webhook delivery is handled entirely in-process using a buffered Go channel and a pool of goroutine workers.

- The "queue" is a buffered channel declared in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  It holds up to 128 pending payloads in memory.

- The workers are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` to make the outbound HTTP request.

- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto the channel and drops the payload (with a warning log) if the buffer is full.

So the "queue" is an in-memory Go channel local to the process — there is no NATS, RabbitMQ, AMQP, or JetStream anywhere in the delivery path (confirmed by the absence of any such dependency in the webhook code and repo-wide search).
