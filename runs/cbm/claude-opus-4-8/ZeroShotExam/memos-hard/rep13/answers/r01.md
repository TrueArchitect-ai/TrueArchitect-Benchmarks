**Premise correction:** There is no Redis anywhere in this repository. The cache layer is not backed by Redis (or any external cache server) — there is no `redis` dependency in `go.mod`, and no Redis client, connection string, or config exists. The grep hits for "redis" in `proto/gen/**.pb.go` are false substring matches, not real usage. So the question's premise ("Redis connection for the cache layer") is mistaken.

**Actual mechanism:** The cache is a **thread-safe in-memory Go cache** (no network connection to configure), implemented in `store/cache/cache.go` (package `store/cache`). It uses a `sync.Map` with per-item TTL, a background cleanup goroutine, and a `MaxItems` eviction cap — entirely in-process.

- **Where it's "configured":** In `store/store.go:38-61`, `New()` builds a `cache.Config` and instantiates three separate in-memory caches, including `userCache` (`store/store.go:28`, `:52`). The config values are:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  (`store/store.go:40-45`). The same defaults are also defined in `cache.DefaultConfig()` at `store/cache/cache.go`.

- **TTL for user entries:** User records are stored via `s.userCache.Set(...)` in `store/user.go` (e.g. lines 98, 122, 132, 143, 167). `Set` uses the cache's default TTL (`store/cache/cache.go`, `Set` → `SetWithTTL(..., c.config.DefaultTTL)`), and no per-user `SetWithTTL` override is used. Therefore **user entries expire after 10 minutes** (the `DefaultTTL`), subject also to eviction if the 1000-item cap is exceeded.
