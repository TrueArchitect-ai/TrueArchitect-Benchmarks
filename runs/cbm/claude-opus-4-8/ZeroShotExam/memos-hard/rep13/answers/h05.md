**Mechanism: by explicit Go code** (two `DELETE FROM reaction` statements run inside the user-deletion transaction). There is no database-level foreign-key/cascade rule doing it.

**Evidence:**

- The delete driver `deleteUserTargetsTx` explicitly calls both reaction-cleanup functions during user deletion:
  - `store/db/sqlite/user_delete.go:96` (`deleteReactionsByContentIDsTx`) and `:102` (`deleteReactionsByCreatorTx`)
  - Identical logic in `store/db/postgres/user_delete.go:96,102` and `store/db/mysql/user_delete.go:96,102`

- The two functions issue raw SQL deletes:
  - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions *on* the deleted user's memos, batched (`store/db/sqlite/user_delete.go:380-388`, likewise pg/mysql).
  - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions *made by* the deleted user (`store/db/sqlite/user_delete.go:400-403`, likewise pg/mysql at :400 / :437).
  - All run within the transaction opened in `DeleteUser` (e.g. `store/db/sqlite/user_delete.go:29-56`).

- The `reaction` table schema has **no foreign keys and no `ON DELETE CASCADE`** — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint, so the DB does not remove reactions on its own:
  - `store/migration/sqlite/LATEST.sql:92-99`
  - `store/migration/postgres/LATEST.sql:91-98`
  - `store/migration/mysql/LATEST.sql:91-98`

So emoji reactions are removed, but only because the Go deletion path explicitly deletes them (both the user's own reactions and reactions on the user's memos); nothing at the database level would clean them up automatically.
