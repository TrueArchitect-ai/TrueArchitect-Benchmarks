Memo-visibility ("who may view a memo") is enforced across several distinct server surfaces:

Single-memo read gate (GetMemo, parent/related memo, comment thread) — `checkMemoReadAccess` — server/router/api/v1/memo_service.go:39 (called from `GetMemo` at :356/:367 and from `ListMemoComments` at server/router/api/v1/memo_service_comments.go:148)
List-query visibility filter (ListMemos) — server/router/api/v1/memo_service.go:217-227 (injects `VisibilityList`/`creator_id == … || visibility in ["PUBLIC","PROTECTED"]`)
Attachment/blob file server — `checkAttachmentPermission` — server/router/fileserver/fileserver.go:677 & :699
RSS feeds (explore & per-user) — server/router/rss/rss.go:90 & :141 (restricts to `store.Public`)
Frontend SSR sitemap/metadata — server/router/frontend/frontend.go:150 (restricts to `store.Public`)

Related, more specific object endpoints reuse the same rule (memo attachments list: server/router/api/v1/memo_attachment_service.go:214-222; reactions: server/router/api/v1/reaction_service.go:30-38,83; attachment service: server/router/api/v1/attachment_service.go:445-451), and `GetMemoByShare` (server/router/api/v1/memo_share_service.go:153) is a deliberate share-token bypass of these checks.

The three primary independent enforcement sites are the single-memo read gate (memo_service.go), the ListMemos query filter (memo_service.go), and the file server's attachment permission check (fileserver.go), with RSS and frontend as additional read-only surfaces.
