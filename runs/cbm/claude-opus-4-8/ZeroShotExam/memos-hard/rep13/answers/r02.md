**Premise correction: this repository (Memos) has no per-user API rate-limiting middleware — it does not exist, so there is nothing registered and there are no request limits to report.**

I verified this by looking at every middleware/interceptor actually wired into the API server:

- The Connect RPC interceptor chain is registered in `server/router/api/v1/v1.go:133-137` as exactly four interceptors — `NewMetadataInterceptor()`, `NewLoggingInterceptor(...)`, `NewRecoveryInterceptor(...)`, and `NewAuthInterceptor(...)`. None of these is a rate limiter (see their definitions in `server/router/api/v1/connect_interceptors.go`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor`).
- The gRPC-Gateway side registers only `gatewayAuthMiddleware` (`server/router/api/v1/v1.go:69` and `:95-97`) — again authentication, not rate limiting.
- A grep across all Go source for `rate limit / ratelimit / throttle / limiter` and for common rate-limiting libraries (`golang.org/x/time/rate`, `tollbooth`, `ulule/limiter`) in `go.mod`/`go.sum` returns **no** implementation. The single hit is a documentation comment in `internal/email/doc.go:86` (`// - Rate limit email sending to prevent abuse`), which merely lists a best-practice consideration for email delivery — it is not code and is unrelated to per-user API request limiting.

The closest thing to a request-level control that *does* exist is a request-body **size** cap, not a request-rate cap: `connect.WithReadMaxBytes(maxAPIRequestBytes)` in `server/router/api/v1/v1.go:141`. That limits how large a single request payload may be, not how many requests a user may make.

So: there is no per-user API rate-limiting middleware, no registration point for one, and no configured request limits.
