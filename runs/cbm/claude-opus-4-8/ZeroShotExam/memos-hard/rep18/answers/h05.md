**Mechanism: explicit Go code** (inside the DeleteUser transaction), not a database cascade.

When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements — there is **no** foreign-key/`ON DELETE CASCADE` doing it.

## What I checked

**1. The delete-user transaction orchestration** — `store/db/sqlite/user_delete.go`, `deleteUserTargetsTx` runs a fixed sequence of deletes inside a single `tx`. It removes reactions in two distinct ways:
- `deleteReactionsByContentIDsTx` — reactions *on* the deleted user's memos (`DELETE FROM reaction WHERE content_id IN (...)`, content IDs = `memos/<uid>`), `store/db/sqlite/user_delete.go:277-285`.
- `deleteReactionsByCreatorTx` — reactions the user *authored* (`DELETE FROM reaction WHERE creator_id = ?`), `store/db/sqlite/user_delete.go:296-299`.

The same two explicit deletes exist in the other two drivers:
- Postgres: `store/db/postgres/user_delete.go:102` and `:400-402`
- MySQL: `store/db/mysql/user_delete.go:102` and `:437-439`

**2. Whether the schema does it instead** — the `reaction` table definitions in `store/migration/{sqlite,postgres,mysql}/LATEST.sql` show `creator_id` and `content_id` as plain `INTEGER`/`TEXT` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — **no foreign key and no `ON DELETE CASCADE`**. So the database itself does nothing on user deletion; the cleanup depends entirely on the Go code above.

Both reaction deletes run before `deleteUserRowTx` (the `DELETE FROM user`) and are committed atomically, so a user's own reactions (by `creator_id`) and reactions others left on the user's memos (by `content_id`) are both removed explicitly.
