**Concrete method that runs the INSERT:** `(*DB).CreateMemo` in the SQLite driver — `store/db/sqlite/memo.go:16`. It builds and executes `INSERT INTO \`memo\` (...) VALUES (...) RETURNING ...` via `d.db.QueryRowContext` (the statement is assembled at store/db/sqlite/memo.go:40‑41).

**Determination method (why this one, not the MySQL/Postgres candidates):**

The store layer doesn't run SQL directly. `store.Store.CreateMemo` (store/memo.go:109‑113) delegates through an interface: `return s.driver.CreateMemo(ctx, create)`, where `s.driver` is the `store.Driver` interface (store/driver.go:29). That interface has three concrete implementations — `store/db/sqlite/memo.go`, `store/db/mysql/memo.go`, `store/db/postgres/memo.go` — the "multiple candidates."

Which concrete type is bound is decided at startup by `db.NewDBDriver` (store/db/db.go), a `switch profile.Driver` that returns `sqlite.NewDB`, `mysql.NewDB`, or `postgres.NewDB`. So the running implementation is fixed by `profile.Driver`.

I then traced how `profile.Driver` gets its value: `cmd/memos/main.go:43` sets it from `viper.GetString("driver")`, and the default is `"sqlite"` — set both via `viper.SetDefault("driver", "sqlite")` (main.go:122) and the flag default at main.go:130 (`--driver`, default `"sqlite"`). With no database flags/env overrides, `profile.Driver == "sqlite"`, so `NewDBDriver` returns the SQLite driver and the SQLite `CreateMemo` is the code that executes the INSERT.
