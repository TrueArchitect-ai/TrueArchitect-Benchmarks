**Premise correction:** The webhook delivery workers consume from **neither NATS nor RabbitMQ**. This repository (memos) has no external message broker at all — a search of `go.mod`/`go.sum` and all Go sources for `nats`, `rabbitmq`, `amqp`, `streadway`, etc. returns nothing.

**Actual mechanism:** Webhook delivery is entirely in-process, backed by a buffered Go channel — not a broker, and nothing is "declared" as a broker queue.

- The "queue" is a package-level buffered channel with capacity 128, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The delivery workers are 4 goroutines spawned in `init()` that range over that channel and call `Post()` for each payload — `internal/webhook/webhook.go:42-55`.
- Producers enqueue via `PostAsync()` using a non-blocking `select`; if the channel is full, the dispatch is dropped with a warning rather than blocked — `internal/webhook/webhook.go:184-196`.
- The enqueue path is driven from the API layer, e.g. `server/router/api/v1/memo_service_webhooks.go:43` and `:71` calling `webhook.PostAsync(payload)`.

So the correct answer is: it's a single-process, ephemeral in-memory channel (`asyncPostQueue`) with 4 consumer goroutines, declared in `internal/webhook/webhook.go` — no broker, no persistence, and drops on overflow.
