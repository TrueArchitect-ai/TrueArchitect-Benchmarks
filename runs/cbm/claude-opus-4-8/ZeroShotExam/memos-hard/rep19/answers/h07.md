A browser requesting another user's avatar (`GET /file/users/:identifier/avatar`) reaches the stored `avatar_url` (a base64 data URI on the `user` table) through this chain:

- `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` — server/router/fileserver/fileserver.go:124 (route registration)
- `(*FileServerService).serveUserAvatar` — server/router/fileserver/fileserver.go:168 (serving handler: auth-gates on private instances, reads `:identifier`, decodes `user.AvatarURL` data URI, writes image bytes)
- `(*FileServerService).getUserByUsername` — server/router/fileserver/fileserver.go:715 (builds `store.FindUser{Username: &identifier}`)
- `(*Store).GetUser` — store/user.go:148 (cache check, then delegates)
- `(*Store).ListUsers` — store/user.go:136 (calls the DB driver)
- `(*DB).ListUsers` — store/db/sqlite/user.go:88 (SQL `SELECT ... avatar_url ... FROM user WHERE username = ?`, scans into `user.AvatarURL`)

The stored data lives in the `user` table's `avatar_url` column (the image is held inline as a base64-encoded `data:` URI, not a file on disk). The sqlite driver is shown; equivalent implementations exist at store/db/postgres/user.go:87 and store/db/mysql/user.go:84.
