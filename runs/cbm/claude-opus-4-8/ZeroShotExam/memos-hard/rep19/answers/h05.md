**Mechanism: explicit Go code.** A user's emoji reactions are deleted by hand-written `DELETE FROM reaction …` statements inside the `DeleteUser` transaction — there is no database-level cascade.

## Evidence

**The reaction deletions are explicit Go**, run as steps in the delete-user transaction (`deleteUserTargetsTx`, `store/db/sqlite/user_delete.go:92-127`):

- `store/db/sqlite/user_delete.go:400-403` — `deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = ?` — removes the reactions the deleted user *made*.
- `store/db/sqlite/user_delete.go:380-388` — `deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on* the deleted user's memos (batched by the memo tree collected at line 96).

These two calls are wired in at `store/db/sqlite/user_delete.go:96` and `:102`.

**Same in the other two drivers** (verified identical statements):
- `store/db/postgres/user_delete.go:383` (by content_id) and `:401` (by creator_id).
- `store/db/mysql/user_delete.go:420` (by content_id) and `:438` (by creator_id).

**No DB-level rule exists.** The `reaction` table DDL has no foreign key and no `ON DELETE CASCADE` — `creator_id` is a plain `INTEGER`/`SERIAL` column:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`

(also confirmed the store wrappers only expose `DeleteReaction` by ID with no cascade logic — `store/reaction.go:39-41`, `store/user_delete.go` holds only the shared types/cache helpers, not the SQL.)

So: both the reactions a deleted user authored and the reactions others left on that user's content are removed, and it's done entirely by explicit Go DELETE statements in the transaction, not by a cascade.
