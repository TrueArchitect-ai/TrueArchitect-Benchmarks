**Premise correction:** This repository (the *memos* project) has **no Redis** anywhere — there is no Redis client, connection string, or Redis-backed cache layer in the codebase (a full search for `redis` across Go/TS/JS/config files returns zero hits). There is also **no cache of "user entries"** — no user-level cache with a configurable TTL exists on the server. So the question's premise (a Redis cache layer with a user-entry TTL) doesn't match how this system actually works.

**Actual mechanism:** All caching here is small, in-process/in-browser memoization — never Redis, and never keyed on users:

- **RSS feed cache** — `server/router/rss/rss.go`. An in-memory `map[string]*cacheEntry` guarded by a `sync.RWMutex` (rss.go:47-48), with TTL `defaultCacheDuration = 1 * time.Hour` (rss.go:25); entries are evicted when `time.Since(entry.createdAt) > defaultCacheDuration` (rss.go:357).
- **Instance stats cache** — `server/router/api/v1/instance_stats.go`. A single in-memory struct holding a value + expiry time, with `instanceStatsCacheTTL = 60 * time.Second` (instance_stats.go:21), set via `set(...)` (instance_stats.go:39-43). Held on the API service struct in `server/router/api/v1/v1.go:43-44`.
- **Client-side memo editor cache** — `web/src/components/MemoEditor/services/cacheService.ts` (browser storage), plus TanStack Query client caching in `web/src/lib/query-client.ts`. These are frontend only, not a server cache layer.

User data itself is read directly from the SQL store (`server/store/user.go`, backed by SQLite/MySQL/Postgres drivers) with no caching layer in front of it, so there is no user-entry TTL to report.
