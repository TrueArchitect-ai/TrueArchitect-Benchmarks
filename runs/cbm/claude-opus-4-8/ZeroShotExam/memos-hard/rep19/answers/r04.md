**Premise correction:** Neither. The webhook delivery workers do not consume from NATS or RabbitMQ — there is no external message broker in this codebase at all. A repo-wide search for `nats`, `rabbitmq`, and `amqp` returns zero matches.

**Actual mechanism:** Webhook delivery is handled entirely in-process using a bounded Go channel as the queue. In `internal/webhook/webhook.go:39`, the "queue" is declared as a package-level buffered channel:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

The `init()` function (`internal/webhook/webhook.go:42-55`) spawns **4 goroutine workers**, each ranging over that channel and calling `Post()` to dispatch the webhook over HTTP via the shared `safeClient` (an `http.Client` with SSRF-guarding dial logic).

Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto `asyncPostQueue` and drops the payload (with a warning log) if the buffer of 128 is full. Callers such as `server/router/api/v1/memo_service_webhooks.go:43,71` invoke `webhook.PostAsync(payload)` when memos are created/updated/deleted or comments are created.

So the "queue" is an in-memory `chan *WebhookRequestPayload` declared in `internal/webhook/webhook.go`, drained by 4 local goroutines that POST directly to each webhook URL — not any broker.
