**Premise correction:** There is no Redis anywhere in this repository (`usememos/memos`). The cache layer is **not** backed by Redis — there is no Redis client, connection string, or config. The caching is a self-contained, in-process, in-memory implementation. So there is no "Redis connection to configure."

**Actual mechanism:**

- **Cache implementation:** A thread-safe in-memory cache lives in `store/cache/cache.go` — a `Cache` struct built on `sync.Map` with per-item `expiration` timestamps and a background cleanup goroutine (`store/cache/cache.go:66`, item struct at `store/cache/cache.go:34-39`). No external store.

- **Where it's "configured":** In `store/store.go:40-53`, the `Store` constructor builds one `cache.Config` literal and passes it to three separate in-memory caches via `cache.New(...)`: `instanceSettingCache`, `userCache`, and `userSettingCache`. The config is:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  
  (The same defaults are also defined in `cache.DefaultConfig()` at `store/cache/cache.go:57-64`, but `store.New` uses its own inline copy.)

- **TTL for user entries:** User records are written to `userCache` using the plain `Set` method (e.g. `store/user.go:98,122,132,143,167`), which applies the **default TTL of 10 minutes**. The cache key is `userCacheKey(userID)` → `"user:<id>"` (`store/user.go:88`). There is no per-user custom TTL (`SetWithTTL` is not used for users), so user entries expire 10 minutes after they're cached, with a cleanup sweep every 5 minutes. Deletes/updates proactively refresh or evict the entry (`store/user.go:132`, `store/user_delete.go:39-40`).

So: no Redis; user cache entries live for **10 minutes** via the shared in-memory `cacheConfig` defined in `store/store.go:40`.
