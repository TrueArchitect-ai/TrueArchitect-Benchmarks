**Premise correction:** There is no Redis anywhere in this repository, and no external cache server of any kind. I grepped the entire tree (`grep -rEil "redis"`) and found zero matches. The cache layer is a **thread-safe, in-process in-memory cache** written in Go, backed by a `sync.Map` — not Redis. So there is no "Redis connection" to configure.

**Actual mechanism:**

- The cache implementation lives at `store/cache/cache.go`. It's a custom `Cache` struct (`store/cache/cache.go:66-73`) holding entries in a `sync.Map`, with per-item expiration timestamps and a background `cleanupLoop` goroutine that evicts expired items on a ticker (`store/cache/cache.go:199-215`).

- It is "configured" not via a connection string but via a `cache.Config` struct constructed in `store/store.go:40-45` inside `store.New(...)`. The store creates three separate in-memory cache instances there — `instanceSettingCache`, `userCache`, and `userSettingCache` — each passed the same `cacheConfig` (`store/store.go:51-53`).

- **TTL for user entries:** User records are stored in `userCache` via plain `Set` calls (e.g. `store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` uses the cache's `DefaultTTL` (`store/cache/cache.go:93-95`). That default is **10 minutes**, set at `store/store.go:41` (`DefaultTTL: 10 * time.Minute`). The package-level default in `store/cache/cache.go:57-64` is also 10 minutes, but the store passes its own explicit config, which is what actually applies. Alongside the TTL, cleanup runs every 5 minutes and the cache is capped at 1000 items with oldest-item eviction.

There is no user-specific override — user entries use the same 10-minute default TTL as the other two caches. Cache keys for users are `userCacheKey(userID)` (`store/user.go:88`), and entries are invalidated explicitly on delete via `store/user_delete.go:40`.
