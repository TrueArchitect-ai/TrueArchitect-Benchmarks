**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the delete-user transaction — there is no database-level cascade (the `reaction` table has no foreign keys).

Two explicit paths run, covering both senses of "their" reactions:
1. **Reactions *on* the user's memos** — `deleteReactionsByContentIDsTx` issues `DELETE FROM reaction WHERE content_id IN (...)`, where the content IDs are `"memos/<uid>"` built from the user's (recursively collected) memo tree.
2. **Reactions *authored by* the user** — `deleteReactionsByCreatorTx` issues `DELETE FROM reaction WHERE creator_id = ?`.

Both are called from `deleteUserTargetsTx`, before the memo rows and the user row are deleted, all within one transaction (`BeginTx`/`Commit`, rollback on failure).

**Evidence locations:**
- `store/db/sqlite/user_delete.go` — orchestration in `deleteUserTargetsTx` (calls `deleteReactionsByContentIDsTx` then `deleteReactionsByCreatorTx`); the two `DELETE FROM reaction ...` implementations; `DeleteUser` transaction wrapper; content-ID construction in `memoContentIDsFromRefs` (`"memos/"+memo.UID`).
- `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437` — same two deletions mirrored in the Postgres and MySQL drivers.
- `store/migration/sqlite/LATEST.sql:92` (and `store/migration/sqlite/0.20/00__reaction.sql`) — the `reaction` table defines only columns `creator_id INTEGER` and `content_id TEXT` with a `UNIQUE(creator_id, content_id, reaction_type)` constraint and **no** `FOREIGN KEY`/`REFERENCES`/`ON DELETE CASCADE`, confirming no DB-level rule does this. (Same for the Postgres/MySQL reaction migrations.)

So: removal happens, and it is done entirely by explicit application code, not a database cascade.
