**Concrete method that runs the INSERT:** `(*sqlite.DB).CreateMemo` — `store/db/sqlite/memo.go:16`. It builds `INSERT INTO `memo` (...) VALUES (...) RETURNING ...` (line 41) and executes it via `d.db.QueryRowContext` (line 42).

**How I determined it's the one that actually runs (out of the sqlite/mysql/postgres candidates):**

1. **The store layer is driver-agnostic.** `Store.CreateMemo` (`store/memo.go:109`) simply delegates: `return s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`). `driver` is the `store.Driver` interface (`store/driver.go`), which each of the three backends implements — so the concrete implementation is chosen by which driver was constructed.

2. **Driver construction is a switch on `profile.Driver`.** `NewDBDriver` (`store/db/db.go:14`) picks `sqlite.NewDB` / `mysql.NewDB` / `postgres.NewDB` based on `profile.Driver`. So the deciding factor is the value of that profile field.

3. **With no database flags, `profile.Driver` defaults to `"sqlite"`.** In `cmd/memos/main.go`, both the viper default (`main.go:122`, `viper.SetDefault("driver", "sqlite")`) and the persistent flag default (`main.go:130`, `String("driver", "sqlite", ...)`) are `"sqlite"`. So the `case "sqlite"` branch runs, giving the sqlite driver.

Therefore, for a default install, `sqlite.NewDB` produces the `*sqlite.DB`, and the interface call resolves to `(*sqlite.DB).CreateMemo` in `store/db/sqlite/memo.go`, which executes the SQL INSERT. The mysql/postgres `CreateMemo` methods exist but are unreachable unless `--driver` is set otherwise.
