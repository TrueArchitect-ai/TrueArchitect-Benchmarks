**Premise correction:** Neither. The webhook delivery workers don't consume from NATS or RabbitMQ — this repo (`usememos/memos`) has no external message broker at all. There's no NATS, RabbitMQ, or AMQP dependency in `go.mod`, and no broker client anywhere in the Go source.

**Actual mechanism:** Webhook delivery uses an in-process Go **buffered channel** as the queue, drained by a fixed pool of goroutine workers — all within a single process.

- The "queue" is declared in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  a plain in-memory channel with a capacity of 128.

- The workers are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` to make the outbound HTTP request.

- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto the channel and drops the payload (logging a warning) if the buffer is full.

So delivery is entirely a local channel-plus-goroutine-pool design — no message broker, no durable queue, and enqueued work is lost on process restart or when the 128-slot buffer overflows.
