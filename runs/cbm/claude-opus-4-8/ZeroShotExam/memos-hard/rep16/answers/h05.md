**Mechanism: explicit Go code** (raw `DELETE` statements inside the user-deletion transaction) — not a database cascade, and not "left in place." A deleted user's emoji reactions are removed in two distinct ways:

1. **Reactions the user *authored*** (on anyone's content) — deleted by `creator_id`.
2. **Reactions *on the user's own memos*** (including comment-tree descendants), regardless of who made them — deleted by `content_id`.

Both run explicitly in Go, batched, within the single `DeleteUser` transaction, before the user row itself is removed.

**Evidence locations** (implemented identically per dialect):

- `store/db/postgres/user_delete.go`
  - Orchestration in `deleteUserTargetsTx` (lines 92–127): calls `deleteReactionsByContentIDsTx` (line 96) then `deleteReactionsByCreatorTx` (line 102).
  - `deleteReactionsByContentIDsTx` (lines 380–388): `DELETE FROM reaction WHERE content_id IN (...)`.
  - `deleteReactionsByCreatorTx` (lines 400–403): `DELETE FROM reaction WHERE creator_id = ...`.
  - Content IDs come from the recursive memo/comment tree via `memoContentIDsFromRefs` (lines 512–518), formatted as `memos/<uid>`.
- `store/db/sqlite/user_delete.go` — same structure: `deleteReactionsByContentIDsTx` (lines 380–388) and `deleteReactionsByCreatorTx` (lines 400–403).
- `store/db/mysql/user_delete.go` — same: `deleteReactionsByContentIDsTx` (lines 417–425) and `deleteReactionsByCreatorTx` (lines 437–440).

**What I checked and ruled out:** The `reaction` table lives in `store/db/{postgres,sqlite,mysql}/reaction.go` with its own store logic; deletion here is driven by these explicit Go statements rather than an `ON DELETE CASCADE` foreign key. There is a dedicated `store/db/*/user_delete.go` per dialect plus a shared `store/user_delete.go` and tests (`store/test/user_delete_test.go`), confirming user deletion is handled by application code, not DB-level cascade rules.
