**Premise correction:** The webhook delivery workers consume from *neither* NATS nor RabbitMQ. The memos codebase does not use any external message broker for webhooks at all.

**Actual mechanism:** Delivery is handled entirely in-process by a buffered Go channel drained by a fixed pool of goroutines.

- The "queue" is a package-level buffered channel declared in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  It holds up to 128 pending `*WebhookRequestPayload` values.

- The "workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)` to perform the actual HTTP POST.

- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto the channel and **drops** the payload (logging a warning) if the buffer is full — there is no broker-backed durability or retry.

- Callers that enqueue are in `server/router/api/v1/memo_service_webhooks.go` (e.g. `dispatchMemoRelatedWebhook` at line 48 and `DispatchMemoCommentCreatedWebhook` at line 30), which invoke `webhook.PostAsync(payload)`.

So the whole pipeline is internal to a single Go process — a `chan *WebhookRequestPayload` plus goroutines — with no NATS, RabbitMQ, or any other message broker involved.
