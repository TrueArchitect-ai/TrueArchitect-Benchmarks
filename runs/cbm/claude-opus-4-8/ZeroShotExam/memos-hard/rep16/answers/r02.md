**Premise correction: there is no per-user API rate-limiting middleware in this repository, so there is no registration site or per-user request limit to report.**

I traced the full server request-handling chain and found no rate limiter of any kind — per-user or global:

- The only interceptor/middleware chain for the API is registered in `server/router/api/v1/v1.go:133-138`, and it consists of exactly four Connect interceptors: `NewMetadataInterceptor()`, `NewLoggingInterceptor(...)`, `NewRecoveryInterceptor(...)`, and `NewAuthInterceptor(...)`. None does rate limiting. The interceptor implementations live in `server/router/api/v1/connect_interceptors.go` and confirm this (metadata conversion, logging, panic recovery, auth/anonymous-access policy).
- No rate-limiting library is used. `golang.org/x/time` appears in `go.mod:151` but is marked `// indirect` (transitive), and `grep` for `golang.org/x/time` across the Go source (`server`, `internal`, `store`, `cmd`) returns nothing — it's never imported by application code. No `tollbooth`/`ulule/limiter`/`go-limiter` either.
- The only request "limits" that exist are **size** limits, not **rate** limits:
  - `maxAPIRequestBytes = 256 << 20` (256 MiB) applied via `http.MaxBytesHandler` and `connect.WithReadMaxBytes` at `server/router/api/v1/v1.go:126,141,144`.
  - A per-memo content-length limit enforced in `server/router/api/v1/memo_service.go:103-106`.
  - An upload file-size limit (`UploadSizeLimitMb`) surfaced in `server/router/api/v1/instance_service_converters.go:138,161`.

If what you're after is throttling abusive clients, note that none of these caps requests-per-user-per-time; the codebase currently has no such control. (`internal/scheduler/middleware.go` is middleware for the internal background-job scheduler, unrelated to the HTTP/gRPC API.)
