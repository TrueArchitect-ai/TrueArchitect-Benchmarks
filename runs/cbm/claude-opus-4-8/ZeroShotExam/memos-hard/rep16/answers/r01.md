**Premise correction:** There is no Redis anywhere in this repository (a codebase-wide search for "redis" returns zero matches). The premise that a Redis connection backs the cache layer is incorrect. This project (memos) uses a **thread-safe, in-process in-memory cache** — there is no external cache server to connect to, so there is nothing to "configure a connection" for.

**Actual mechanism:**

- The cache is implemented as a Go in-memory cache in `store/cache/cache.go` — a `sync.Map`-backed store with per-item TTL expiration and a background cleanup goroutine (`cleanupLoop`). No network/connection setup exists.
- It is instantiated (not "connected") in `store/store.go:38-61`. The `Store` holds three separate cache instances (`store/store.go:27-29`): `instanceSettingCache`, `userCache`, and `userSettingCache`, each created via `cache.New(cacheConfig)`.
- The single `cacheConfig` shared by all three is defined inline at `store/store.go:40-45`:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  
  (This matches `cache.DefaultConfig()` at `store/cache/cache.go:57-64`.)

**TTL for user entries:** User records are written to `userCache` via `s.userCache.Set(...)` at `store/user.go:98, 122, 132, 143, 167`. `Set` (`store/cache/cache.go:93-95`) always applies the cache's `DefaultTTL` — no call site uses `SetWithTTL` to override it for users. Therefore **user entries expire after the default 10-minute TTL**, and are also invalidated explicitly on delete (`store/user_delete.go:40`) and re-cached on read/update.
