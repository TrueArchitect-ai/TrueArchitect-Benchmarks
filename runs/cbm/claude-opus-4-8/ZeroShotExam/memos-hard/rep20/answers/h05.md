**Mechanism: explicit Go code** (two separate `DELETE FROM reaction` statements). There is no database-level cascade rule — the `reaction` table has no foreign key on `creator_id` at all.

**Evidence:**

- `store/db/sqlite/user_delete.go:92-127` — `deleteUserTargetsTx` orchestrates deletion within a transaction and explicitly calls two reaction-deleting helpers:
  - `deleteReactionsByContentIDsTx` (line 96) — removes reactions **on** the deleted user's memos (matched by `content_id` = `memos/<uid>`).
  - `deleteReactionsByCreatorTx` (line 102) — removes reactions **made by** the deleted user (matched by `creator_id`).
- The helpers themselves: `store/db/sqlite/user_delete.go:380-388` (`DELETE FROM reaction WHERE content_id IN (...)`) and `store/db/sqlite/user_delete.go:400-403` (`DELETE FROM reaction WHERE creator_id = ?`).
- Entry point: `store/user.go:171` `DeleteUser` → dispatches to the driver's `DeleteUser` (`store/db/sqlite/user_delete.go:29`). Postgres and MySQL have parallel implementations (`store/db/postgres/user_delete.go`, `store/db/mysql/user_delete.go`).
- Schema confirms no DB-level rule: `store/migration/sqlite/0.20/00__reaction.sql` defines `reaction` with `creator_id INTEGER NOT NULL` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — **no foreign key, no `ON DELETE CASCADE`**. So the database would not remove reactions on its own; the Go code is what does it.
