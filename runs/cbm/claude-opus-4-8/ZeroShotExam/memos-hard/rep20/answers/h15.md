Memo visibility (who may *view* a memo) is not centralized in one guard — it is re-enforced independently on each server surface that can expose memo content. The distinct enforcement sites:

**Core "view a memo" surfaces**

Single-memo read guard (`checkMemoReadAccess`) — `server/router/api/v1/memo_service.go:39` (lines 55–66; public passes, non-public requires auth, private requires `CreatorID == user.ID`). Called from `GetMemo`/parent-memo reads at `memo_service.go:356,367`.

List-memos visibility filter injection (`ListMemos`) — `server/router/api/v1/memo_service.go:218-227` (anonymous → `PUBLIC` only; authenticated → `creator_id == me || visibility in ["PUBLIC","PROTECTED"]`).

File server raw attachment/blob serving (`checkAttachmentPermission`) — `server/router/fileserver/fileserver.go:650` (visibility logic at lines 677–701; private blocked unless creator or admin, with a share-token fallback).

RSS feed — `server/router/rss/rss.go:90` and `:141` (feed queries force `VisibilityList: [store.Public]`).

Frontend sitemap — `server/router/frontend/frontend.go:150` (sitemap lists `store.Public` memos only).

**Related-content surfaces that re-check memo visibility before exposing a memo's associated data**

Memo comments (create + list) — `server/router/api/v1/memo_service_comments.go:41,148,158-160`.

API attachment access — `server/router/api/v1/attachment_service.go:445-451`.

Reactions (list/upsert) — `server/router/api/v1/reaction_service.go:30-38,83`.

Memo relations — `server/router/api/v1/memo_relation_service.go:109-111`.

The first five are the surfaces that directly gate viewing a memo (well over the "at least three"); the last four re-apply the same private/protected/public rules when serving a memo's related content.
