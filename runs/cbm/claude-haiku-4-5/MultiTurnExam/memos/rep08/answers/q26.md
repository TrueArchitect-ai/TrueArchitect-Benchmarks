When DeleteMemo runs, the following tables are affected:
1. **memo** — the target memo row is deleted (direct deletion)
2. **memo_share** — automatically deleted via CASCADE foreign key constraint on `memo_id`
3. **attachment** — attachments with `memo_id` referencing the deleted memo remain in the table (no cascade; orphaned records)
4. **reaction** — reactions referencing the memo via `content_id` remain in the table (no cascade; orphaned records)
5. **memo_relation** — memo relations (both as `memo_id` and `related_memo_id`) remain in the table (no cascade; orphaned records)

Additionally, when the memo being deleted has child comments (memos with `MemoRelationComment` relation), those comment memos are deleted recursively via `Store.DeleteMemo` calls in the API layer (lines 573-577 of memo_service.go), which then trigger the same cascade effects for those child memos.
