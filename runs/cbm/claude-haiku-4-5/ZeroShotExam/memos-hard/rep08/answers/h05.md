**Mechanism: Explicit Go code**

When a user is deleted, emoji reactions created by that user are removed by explicit Go code, not by database-level foreign key constraints.

**Evidence locations:**

1. **Line 102 in `/bench/repo/store/db/mysql/user_delete.go`**: The function `deleteUserTargetsTx()` explicitly calls `deleteReactionsByCreatorTx(ctx, tx, userID)` to delete all reactions created by the user being deleted.

2. **Lines 437-440 in `/bench/repo/store/db/mysql/user_delete.go`**: The `deleteReactionsByCreatorTx()` function executes a SQL DELETE statement: `DELETE FROM reaction WHERE creator_id = ?` - this deletes reactions where the user is the creator.

3. **Lines 96-98 in `/bench/repo/store/db/mysql/user_delete.go`**: Additionally, reactions on the user's own memos are deleted by calling `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` for each memo's content ID (lines 417-425 show this deletes reactions based on content IDs matching `memos/<memo_uid>`).

4. **Database schema in `/bench/repo/store/migration/mysql/0.20/00__reaction.sql` and postgres equivalent**: The reaction table has no foreign key constraints on `creator_id` to the user table - there's only a UNIQUE constraint on (creator_id, content_id, reaction_type). This confirms the deletion is NOT handled at the database level.
