The filter expression is parsed by **CEL (Common Expression Language)** engine, located at `internal/filter/engine.go`. The CEL filter string is compiled into a dialect-agnostic intermediate representation (condition tree), which is then rendered into dialect-specific SQL by the `renderer` in `internal/filter/render.go` — each dialect uses distinct SQL syntax handled via switch statements on `DialectName` (sqlite, mysql, postgres).

The mechanism: `Engine.Compile()` parses CEL expressions via `cel.NewEnv().Compile()` into an AST, then `buildCondition()` converts it to a condition tree; `Program.Render()` walks the tree calling `renderer.renderCondition()` and related methods, which switch on `r.dialect` to emit syntax like PostgreSQL's `$1` placeholders vs MySQL's `?`, SQLite's `strftime()` vs PostgreSQL's `EXTRACT()` for timestamps, and backticks vs unquoted column names per dialect.

- `internal/filter/engine.go:24-34` — Engine initialization with CEL environment
- `internal/filter/helpers.go:9-25` — AppendConditions() applies dialect-specific rendering
- `internal/filter/render.go:24-30, 919-926, 932-942` — Dialect-aware SQL generation with switch cases for each DialectName
