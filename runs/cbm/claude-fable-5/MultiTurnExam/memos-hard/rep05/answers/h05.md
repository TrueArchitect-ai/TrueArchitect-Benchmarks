**Mechanism: explicit Go code** — each database driver's `DeleteUser` implementation deletes the user's reactions inside the same transaction, in two passes: reactions the user authored (`DELETE FROM reaction WHERE creator_id = ?`) and reactions attached to the user's own content (`DELETE FROM reaction WHERE content_id IN (...)`). There is no database-level rule doing this.

Evidence locations:

- **SQLite driver:** `store/db/sqlite/user_delete.go` — `DeleteUser` (line 29) calls `deleteReactionsByContentIDsTx` at line 96 and `deleteReactionsByCreatorTx` at line 102; the helpers issue the batched `DELETE FROM reaction WHERE content_id IN ...` (line 383) and `DELETE FROM reaction WHERE creator_id = ?` (line 401) statements.
- **MySQL driver:** same pattern in `store/db/mysql/user_delete.go` (lines 420 and 438).
- **PostgreSQL driver:** same pattern in `store/db/postgres/user_delete.go` (lines 383 and 401).
- **No database-level rule:** the `reaction` table schema in `store/migration/sqlite/LATEST.sql` has plain `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` columns with no `FOREIGN KEY ... ON DELETE CASCADE`, and a grep across all of `store/migration/` (sqlite, mysql, postgres) for `FOREIGN`/`CASCADE`/`REFERENCES` involving `reaction` returns nothing — so cleanup cannot happen via cascading deletes.
