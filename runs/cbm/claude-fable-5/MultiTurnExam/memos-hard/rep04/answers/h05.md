**Mechanism: explicit Go code — each database driver's `DeleteUser` transaction deletes the user's reactions with direct `DELETE FROM reaction` statements; there is no database-level cascade on the reaction table.**

Evidence:

- **Explicit Go deletion:** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver. In the SQLite driver, `DeleteUser` runs a transaction whose `deleteUserTargetsTx` step explicitly removes reactions two ways: `deleteReactionsByCreatorTx` executes `DELETE FROM reaction WHERE creator_id = ?` for reactions the user made (`store/db/sqlite/user_delete.go:400-403`, invoked at line 102), and `deleteReactionsByContentIDsTx` executes `DELETE FROM reaction WHERE content_id IN (...)` for reactions others left on the user's memos (`store/db/sqlite/user_delete.go:380-388`, invoked at line 96, with content IDs built as `memos/<uid>` at lines 512-518). The same functions exist in the MySQL and Postgres drivers (`store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`).
- **No database-level rule:** the current reaction table schema has no foreign keys at all — just columns and a UNIQUE constraint — in all three dialects (`store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-97`, and the original `0.20/00__reaction.sql` migrations). The `ON DELETE CASCADE` rules that do exist in migrations apply to other tables (e.g. memo, user_setting, resource), not reaction, so nothing at the database level would remove reactions on user deletion.
