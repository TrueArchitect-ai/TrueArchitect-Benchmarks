A profile image (avatar) request hits the file server route `GET /file/users/:identifier/avatar` and descends through the store to the database driver, where the avatar is read from the `user` table's `avatar_url` column (stored as a data URI that the handler decodes and serves as an image blob). The hops:

- `FileServerService.RegisterRoutes` (route `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (handler: optional auth check on private instances, then decodes `user.AvatarURL` via `parseDataURI`, validates MIME type, writes blob) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` (wraps the lookup by the `:identifier` path param) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (cache check, then delegates) — `store/user.go:148`
- `Store.ListUsers` (delegates to the DB driver, populates cache) — `store/user.go:136`
- `DB.ListUsers` (driver SQL `SELECT ... avatar_url ... FROM user`) — `store/db/sqlite/user.go:88` (equivalently `store/db/mysql/user.go:84` / `store/db/postgres/user.go:87` depending on configured driver)

Note the data-layer endpoint: the avatar bytes are not a separate file — they live inline in the `avatar_url` column of the `user` table as a `data:` URI, which `serveUserAvatar` decodes with `parseDataURI` (`server/router/fileserver/fileserver.go:737`) before responding.
