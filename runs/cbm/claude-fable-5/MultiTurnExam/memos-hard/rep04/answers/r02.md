**Premise correction: there is no per-user API rate-limiting middleware in this codebase — none is registered anywhere, and no request limits exist.**

What I checked:

- The Echo server registers only `middleware.Recover()` and a CORS middleware (`server/server.go:51-52`); Echo's built-in `middleware.RateLimiter` is never used (no references anywhere).
- The Connect/gRPC API stack's full interceptor chain is metadata, logging, recovery, and auth — no throttling interceptor (`server/router/api/v1/v1.go:133-138`).
- No rate-limiting library is imported: `golang.org/x/time/rate` and similar packages are absent from `go.mod`, and repo-wide searches for "rate limit"/"throttle"/"limiter" find no Go implementation. The only mention is a documentation comment suggesting email sending "should" be rate limited as a best practice (`internal/email/doc.go:86`) — advisory text, not code.

The closest things to request limiting that do exist are of a different nature: a request body size cap on the API (`connect.WithReadMaxBytes(maxAPIRequestBytes)` at `server/router/api/v1/v1.go:141`), concurrency semaphores for thumbnail/image processing (`server/router/api/v1/v1.go` and `server/router/fileserver/fileserver.go:107`), and a bounded webhook dispatch queue (`internal/webhook/webhook.go:39`). None of these are per-user request rate limits.
