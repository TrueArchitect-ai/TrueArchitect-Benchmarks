h05.

**Mechanism: explicit Go code — reactions are deleted by hand-written SQL inside each database driver's user-deletion transaction, not by any database-level rule.**

Evidence locations:

1. **Explicit Go deletion (all three drivers).** Each driver's `DeleteUser` runs a transaction that deletes reactions two ways: by creator (`DELETE FROM reaction WHERE creator_id = ?` in `deleteReactionsByCreatorTx`) and by content (`DELETE FROM reaction WHERE content_id IN (...)` in `deleteReactionsByContentIDsTx`, covering reactions left by *other* users on the deleted user's memos):
   - `store/db/sqlite/user_delete.go:383` and `:401`
   - `store/db/mysql/user_delete.go:420` and `:438`
   - `store/db/postgres/user_delete.go:383` and `:401`

2. **No database-level rule.** The `reaction` table DDL has no foreign keys at all — `creator_id` and `content_id` are plain columns with no `REFERENCES ... ON DELETE CASCADE` (unlike, say, `memo_share`, which does cascade from `memo`):
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/mysql/LATEST.sql:91-98`
   - `store/migration/postgres/LATEST.sql:91-97`

So a database cascade couldn't do this cleanup even in principle; the explicit statements in the drivers' `DeleteUser` transactions are what remove the reactions.
