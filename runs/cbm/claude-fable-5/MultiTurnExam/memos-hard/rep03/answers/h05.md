h05.

**Mechanism: explicit Go code — reactions are deleted by hand-written SQL inside each database driver's user-deletion transaction, not by any database-level rule.**

Evidence:

1. **Explicit Go deletion.** Each driver's `DeleteUser` runs a transaction that calls `deleteReactionsByCreatorTx`, executing `DELETE FROM reaction WHERE creator_id = ?`:
   - SQLite: `store/db/sqlite/user_delete.go:400-403`, invoked from the ordered deletion sequence at `store/db/sqlite/user_delete.go:102`.
   - MySQL: `store/db/mysql/user_delete.go:437-438` (invoked at line 102).
   - Postgres: `store/db/postgres/user_delete.go:400-401` (invoked at line 102).
   
   The same transaction also removes reactions left *on* the deleted user's memos via `deleteReactionsByContentIDsTx` (`DELETE FROM reaction WHERE content_id IN (...)`) — `store/db/sqlite/user_delete.go:380-388`, and the mysql/postgres equivalents at `user_delete.go:420` and `user_delete.go:383` respectively.

2. **No database-level rule.** The `reaction` table schema has no foreign keys at all — no `FOREIGN KEY ... ON DELETE CASCADE` referencing `user`. See `store/migration/sqlite/LATEST.sql:92-99` (the table has only a primary key and a UNIQUE constraint). By contrast, other tables in the same schema do use cascades where intended — e.g. `memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` at `store/migration/sqlite/LATEST.sql:109` — confirming the absence on `reaction` is deliberate and that reaction cleanup relies on the Go code.
