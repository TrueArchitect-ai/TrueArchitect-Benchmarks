The avatar is stored as a data URI in the user row's `avatar_url` column, so "stored data" is reached through the user store. The chain:

- `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` (route registration) — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (serving handler; anonymous-access check, then user lookup) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (cache check, then delegates) — `store/user.go:148`
- `Store.ListUsers` (delegates to the DB driver) — `store/user.go:136`
- `DB.ListUsers` (driver SQL that reads the user row, including `avatar_url`) — `store/db/sqlite/user.go:88` (equivalents in `store/db/mysql/user.go` / `store/db/postgres/user.go` depending on the configured database)

Back in the handler, the fetched `user.AvatarURL` data URI is decoded by `FileServerService.parseDataURI` (`server/router/fileserver/fileserver.go:196`), validated against `avatarAllowedTypes` (`fileserver.go:75`, checked at `fileserver.go:201`), and written to the response as an image blob (`fileserver.go:209`).
