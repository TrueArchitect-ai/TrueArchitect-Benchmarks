**Mechanism: explicit Go code** — reactions are deleted inside the user-deletion transaction in each database driver, not by any database-level rule.

What I checked:

1. **The user-deletion path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver. Each driver's `DeleteUser` runs a transaction that calls `deleteUserTargetsTx`, which explicitly issues two reaction deletes:
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (removes reactions the user made): `store/db/sqlite/user_delete.go:401`, `store/db/postgres/user_delete.go:400-401`, `store/db/mysql/user_delete.go:437-438`.
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (removes reactions on the user's memos): `store/db/sqlite/user_delete.go:383`, `store/db/postgres/user_delete.go:383`, `store/db/mysql/user_delete.go:420`. Both are wired into the transaction at `user_delete.go:96` and `:102` in each driver.

2. **The schema, to rule out a database-level rule.** The `reaction` table definition has no `FOREIGN KEY ... ON DELETE CASCADE` (or any FK at all) — just columns and a UNIQUE constraint: `store/migration/sqlite/LATEST.sql:91-99`, and the same shape in `store/migration/postgres/LATEST.sql:90-97` and `store/migration/mysql/LATEST.sql`. So no cascade could do this work.

**Answer:** explicit Go code; `deleteReactionsByCreatorTx` / `deleteReactionsByContentIDsTx` within each driver's `DeleteUser` transaction (`store/db/{sqlite,postgres,mysql}/user_delete.go`, e.g. sqlite lines 96, 102, 383, 401), with no FK/cascade in the `reaction` schema (`store/migration/*/LATEST.sql`).
