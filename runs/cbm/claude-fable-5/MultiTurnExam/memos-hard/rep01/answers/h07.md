A browser requests `GET /file/users/{username}/avatar`; the avatar itself is stored as a data URI in the user row's `avatar_url` column, so the "stored data" is reached through the user store. The hops:

- `FileServerService.RegisterRoutes` (binds `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:121-124`
- `FileServerService.serveUserAvatar` (handler: optional auth check on private instances, then looks up the user, parses `user.AvatarURL` via `parseDataURI`, validates MIME type, writes the blob) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks the user cache, else falls through to a list query) — `store/user.go:148`
- `Store.ListUsers` (delegates to the DB driver) — `store/user.go:136`
- driver `(*DB).ListUsers` (SQL `SELECT` on the `user` table including `avatar_url`) — `store/db/sqlite/user.go:88` (equivalents in `store/db/mysql/user.go` and `store/db/postgres/user.go`)

After the data returns, `serveUserAvatar` decodes the stored data URI (`parseDataURI` in `server/router/fileserver/fileserver.go`) and responds with the image bytes — no separate blob storage is involved for avatars, unlike attachments.
