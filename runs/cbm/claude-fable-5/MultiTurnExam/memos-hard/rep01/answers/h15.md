Memo visibility is enforced independently at these server surfaces/sites:

- **gRPC/Connect API — single-memo read gate:** `checkMemoReadAccess` (public → anyone; non-public requires auth; private → creator only; archived → creator only) — `server/router/api/v1/memo_service.go:39`, applied in `GetMemo` (`memo_service.go:356,367`) and `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`)
- **gRPC/Connect API — list-query narrowing:** `ListMemos` constrains `VisibilityList` to `Public` for anonymous viewers and `Public+Protected` when browsing other users — `server/router/api/v1/memo_service.go:219-225` (same pattern for user stats at `server/router/api/v1/user_service_stats.go:84-90,218-220`)
- **gRPC/Connect API — reaction listing:** inline visibility check before returning a memo's reactions — `server/router/api/v1/reaction_service.go:30`
- **gRPC/Connect API — attachment listing for a memo:** inline visibility check — `server/router/api/v1/memo_attachment_service.go:214`
- **File server (raw attachment bytes over HTTP):** `checkAttachmentPermission` re-derives access from the owning memo's visibility, with share-token fallback and admin override — `server/router/fileserver/fileserver.go:650-700` (invoked from `serveAttachmentFile` at `fileserver.go:149`)
- **RSS feeds:** instance and per-user feeds query only `store.Public` memos — `server/router/rss/rss.go:90` and `rss.go:141`
- **Frontend sitemap/SEO surface:** `getSitemapXML` lists only public memos — `server/router/frontend/frontend.go:150`

So the enforcement is replicated across four distinct surfaces (API v1, fileserver, RSS, frontend), with the API surface itself containing several distinct check sites.
