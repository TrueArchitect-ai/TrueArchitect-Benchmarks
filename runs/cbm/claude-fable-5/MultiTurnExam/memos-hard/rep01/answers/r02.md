**Premise correction: there is no per-user API rate-limiting middleware in this codebase.** A repo-wide search for rate-limit/throttle/limiter code returns only a documentation comment suggesting email sending "should" be rate-limited (`internal/email/doc.go:86`) — no implementation. The Echo server registers only `middleware.Recover()` and a CORS middleware (`server/server.go:51-52`), and the API layer's middleware stack is authentication/authorization only (gateway auth middleware and Connect interceptor in `server/router/api/v1/v1.go:64-` onward). Echo's built-in `middleware.RateLimiter` is never used.

What the server does have are unrelated, non-per-user throttles that shouldn't be confused with rate limiting:

- Concurrency semaphores for expensive image work: 3 concurrent thumbnail generations and 2 concurrent image-processing jobs (`server/router/api/v1/v1.go:59-60`), and a thumbnail semaphore in the file server (`server/router/fileserver/fileserver.go:106-117`).
- A bounded webhook dispatch queue (128 entries, drops when full) — `internal/webhook/webhook.go:39,184-196`.
- A per-memo content length limit enforced per request (`server/router/api/v1/memo_service.go:100-106`).

So: no registration site and no request limits exist; any rate limiting would have to be provided outside the application (e.g., a reverse proxy).
