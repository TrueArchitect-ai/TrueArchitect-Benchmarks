Tables affected when DeleteMemo runs:

1. **memo_relation** — `Store.DeleteMemo` (`store/memo.go:142-147`) explicitly deletes relation rows where the memo is either the source (`MemoID`) or target (`RelatedMemoID`). Additionally, the API handler (`server/router/api/v1/memo_service.go:568-578`) first deletes all comment memos (relations of type `COMMENT`) by recursively calling `Store.DeleteMemo` for each.
2. **attachment** — `Store.DeleteMemo` (`store/memo.go:149-157`) lists attachments linked to the memo and deletes each via `Store.DeleteAttachment` (`store/attachment.go:132`), which also removes the underlying file from local/S3 storage (not a table, but part of the cascade).
3. **memo** — the memo row itself is deleted last via the driver (`store/db/sqlite/memo.go:237-248`, `DELETE FROM memo WHERE id = ?`), and comment memos' rows are also deleted from this table by the recursive comment cleanup.

Notably, `reaction` and `memo_share` rows are **not** deleted by this path — the handler lists reactions only to build the deletion webhook payload, and no cleanup code for those tables exists in the DeleteMemo chain.
