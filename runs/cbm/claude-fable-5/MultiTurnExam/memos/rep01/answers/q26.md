Tables affected: **memo_relation, attachment, memo**

`Store.DeleteMemo` (`store/memo.go:140-159`) explicitly cascades:

1. `memo_relation` — two `DeleteMemoRelation` calls remove rows where the memo is the source (`memo_id`) or the target (`related_memo_id`).
2. `attachment` — attachments linked to the memo are listed and deleted via `Store.DeleteAttachment` (`store/attachment.go:132`), which also removes the underlying file from local/S3 storage.
3. `memo` — finally the memo row itself is deleted by the driver (e.g. `store/db/sqlite/memo.go:237`, a plain `DELETE FROM memo WHERE id = ?` with no SQL-level cascade).

Note the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:568-577`) additionally deletes comment memos first by calling `Store.DeleteMemo` for each comment relation — hitting the same three tables for each comment. No other tables (e.g. `reaction`) are deleted in this path.
