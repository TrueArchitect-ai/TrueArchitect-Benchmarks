I have the full chain confirmed. The avatar image data lives in the `user.avatar_url` column (a data URI) read via `QueryContext`.

h07.
A browser requests `GET /file/users/:identifier/avatar`. The route is registered in `RegisterRoutes` and dispatched to the serving handler, which loads the target user (including the base64 avatar data URI stored in the `avatar_url` column) through the store and DB driver, then decodes it and writes the image bytes.

serveUserAvatar — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
DB.ListUsers (driver, SQLite) — store/db/sqlite/user.go:88
db.QueryContext(SELECT ... avatar_url FROM user) — store/db/sqlite/user.go:173

Notes: The route registration lives at `server/router/fileserver/fileserver.go:124` (`fileGroup.GET("/file/users/:identifier/avatar", s.serveUserAvatar)`). `Store.GetUser` may short-circuit on `userCache` only when looking up by ID; the avatar path looks up by username, so it always falls through to `ListUsers` → the driver. The MySQL/Postgres drivers have equivalent `ListUsers` implementations (`store/db/mysql/user.go`, `store/db/postgres/user.go`) selected by configuration. The image itself is not a separate file/blob — it is stored inline in the `user.avatar_url` column as a data URI and decoded by `parseDataURI` (`fileserver.go:737`).
