**Concrete method:** `(*DB).CreateMemo` in the SQLite driver — `store/db/sqlite/memo.go:16`. It builds and runs the ``INSERT INTO `memo` (...) VALUES (...) RETURNING ...`` statement via `d.db.QueryRowContext` (`store/db/sqlite/memo.go:41-42`).

**Determination method:** static resolution of the interface dispatch through the driver-selection code path, rather than assuming from the multiple `CreateMemo` implementations:

1. There are three candidate implementations of the `store.Driver` interface's `CreateMemo` (declared in `store/driver.go`): `store/db/sqlite/memo.go`, `store/db/mysql/memo.go`, and `store/db/postgres/memo.go`. The store layer just delegates: `Store.CreateMemo` calls `s.driver.CreateMemo(ctx, create)` at `store/memo.go:113`, so which one runs depends entirely on which driver was instantiated.
2. The driver is chosen in `NewDBDriver` (`store/db/db.go`), which switches on `profile.Driver`: `"sqlite"` → `sqlite.NewDB`, `"mysql"` → `mysql.NewDB`, `"postgres"` → `postgres.NewDB`.
3. With no flags, the default is SQLite: `cmd/memos/main.go:122` sets `viper.SetDefault("driver", "sqlite")` and line 130 registers the `--driver` flag with default value `"sqlite"` (additionally, `internal/profile/profile.go:110` fills in a default DSN when the driver is sqlite and no DSN is given).

So in a default installation the dynamic type behind the `store.Driver` interface is `*sqlite.DB`, and the INSERT executes in `store/db/sqlite/memo.go`'s `CreateMemo`. Note it uses `QueryRowContext` (not `ExecContext`) because the SQLite statement uses `RETURNING` to read back the generated id and timestamps — unlike the MySQL variant, which uses `ExecContext` + `LastInsertId`.
