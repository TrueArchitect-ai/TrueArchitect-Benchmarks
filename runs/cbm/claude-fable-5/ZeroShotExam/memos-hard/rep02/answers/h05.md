**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction ...` statements inside each database driver's `DeleteUser` transaction — not by any database-level rule.

What I checked:

1. **The user-deletion code path.** `store.Store.DeleteUser` (`store/user_delete.go`) delegates to a per-driver `DeleteUser`, and all three drivers run the same transactional cleanup in `deleteUserTargetsTx`, which deletes reactions in two ways before deleting the user row:
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (reactions the user made): `store/db/sqlite/user_delete.go:400-403`, `store/db/mysql/user_delete.go:438`, `store/db/postgres/user_delete.go:401`.
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (reactions left by anyone on the user's memos and their comment tree, keyed by `"memos/"+uid`): `store/db/sqlite/user_delete.go:380-388` and `:512-518`, `store/db/mysql/user_delete.go:420`, `store/db/postgres/user_delete.go:383`.
   
   Both are called from `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127` and the mysql/postgres equivalents) inside the same transaction that deletes the `user` row.

2. **The schema, to rule out a database-level rule.** The `reaction` table definitions in `store/migration/sqlite/LATEST.sql:92-98`, `store/migration/mysql/LATEST.sql:91-97`, and `store/migration/postgres/LATEST.sql:91-97` have no foreign key at all — just a `UNIQUE(creator_id, content_id, reaction_type)` constraint. A grep for `FOREIGN KEY`/`CASCADE` across all three `LATEST.sql` files finds only one FK in each schema (`memo_id REFERENCES memo(id) ON DELETE CASCADE`, around line 108), which belongs to a different table, not `reaction`. So no cascade could remove reactions; the explicit Go code is what does it.
