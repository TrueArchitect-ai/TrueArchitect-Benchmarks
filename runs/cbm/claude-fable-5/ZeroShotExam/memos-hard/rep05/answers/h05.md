**Mechanism: explicit Go code.** When a user is deleted, the store-layer `DeleteUser` runs a transaction that explicitly issues `DELETE FROM reaction ...` statements — there is no database-level cascade on the `reaction` table.

What I checked:

1. **Explicit Go deletion** — each database driver's `DeleteUser` transaction deletes reactions two ways: reactions the user *created* and reactions *on the user's memos* (by content ID):
   - SQLite: `store/db/sqlite/user_delete.go` — `deleteUserTargetsTx` calls `deleteReactionsByContentIDsTx` (line 96) and `deleteReactionsByCreatorTx` (line 102); the actual SQL is `DELETE FROM reaction WHERE content_id IN (...)` (line 383) and `DELETE FROM reaction WHERE creator_id = ?` (line 401).
   - Postgres: `store/db/postgres/user_delete.go:96,102,383,401` — same pair of functions.
   - MySQL: `store/db/mysql/user_delete.go:96,102,420,438` — same pair of functions.

2. **No database-level rule for reactions** — the `reaction` table schema has no foreign keys at all, only a `UNIQUE(creator_id, content_id, reaction_type)` constraint:
   - `store/migration/sqlite/LATEST.sql:92-98`, `store/migration/postgres/LATEST.sql:91-97`, `store/migration/mysql/LATEST.sql:91-97`, and the original `store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql`. `ON DELETE CASCADE` clauses exist in old migrations for other tables (e.g. `memo`, `user_setting` in `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql`), but none reference `reaction`, so a cascade could not remove reactions.

So reactions are removed, and it happens purely in application (Go) code, not via the database.
