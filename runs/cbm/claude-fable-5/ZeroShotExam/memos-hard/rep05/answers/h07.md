I have the complete chain. The avatar image is stored inline as a base64 data URI in the `user.avatar_url` column, and the handler decodes it on the fly.

h07.

A browser requesting another user's profile image (`GET /file/users/:identifier/avatar`) reaches stored data through these hops:

`serveUserAvatar` — server/router/fileserver/fileserver.go:168
`getUserByUsername` — server/router/fileserver/fileserver.go:715
`(*Store).GetUser` — store/user.go:148
`(*Store).ListUsers` — store/user.go:136
`(*DB).ListUsers` — store/db/sqlite/user.go:88
`(*FileServerService).parseDataURI` — server/router/fileserver/fileserver.go:737

Notes:
- The route is registered in `RegisterRoutes` (server/router/fileserver/fileserver.go:124) as `/file/users/:identifier/avatar`.
- `getUserByUsername` calls `s.Store.GetUser(&store.FindUser{Username: &identifier})`; `GetUser` delegates to `ListUsers`, which calls `s.driver.ListUsers`, dispatching to the DB-specific driver (sqlite shown; postgres/mysql have parallel implementations).
- The driver's `SELECT` includes the `avatar_url` column (store/db/sqlite/user.go:159) — the profile image is **not** a file on disk or in object storage. It is stored as a base64 data URI directly in the `user` table's `avatar_url` field.
- Back in the handler, `parseDataURI` decodes that stored `user.AvatarURL` string into MIME type + bytes, which are written to the response via `c.Blob` (fileserver.go:209). So the "data layer" endpoint is the `user.avatar_url` column.
