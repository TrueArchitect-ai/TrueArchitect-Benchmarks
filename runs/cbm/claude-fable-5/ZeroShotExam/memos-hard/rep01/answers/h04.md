**Yes — but only in one in-package unit test; all production code goes through the factory.**

The driver-selection factory is `NewDBDriver` in `store/db/db.go:14-32`, which calls `mysql.NewDB(profile)` for the `"mysql"` case (`store/db/db.go:22`).

Evidence from searching the whole repo:

1. **`mysql.NewDB` is called exactly once** — at `store/db/db.go:22`. A grep for `NewDB(` call sites finds no other invocation of the MySQL constructor (the other hits are the sqlite/postgres cases in the factory and two sqlite-only tests, `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416`).

2. **The mysql package is imported by only one file** — a grep for the import path `github.com/usememos/memos/store/db/mysql` matches only `store/db/db.go:8`, so no external package can even reference the `mysql.DB` type.

3. **The one direct construction:** `store/db/mysql/auth_config_test.go:12` builds the driver struct literally as `db := &DB{}` to unit-test `IsRetryableAuthenticationMutationError`. This is inside the `mysql` package itself (bypassing `NewDB`, which lives at `store/db/mysql/mysql.go:20` and internally builds `DB{profile: profile}` at line 29).

4. **Integration tests don't bypass the factory** — `store/test/store.go:28` and `store/test/store.go:50` obtain drivers via `db.NewDBDriver(profile)`; `store/test/containers.go` only spins up a MySQL testcontainer and uses the raw `go-sql-driver/mysql` / `database/sql` packages for readiness checks, never the repo's driver type.

So: outside the factory, the MySQL driver is never constructed in production code; the sole direct construction is the zero-value `&DB{}` in the package's own unit test at `store/db/mysql/auth_config_test.go:12`.
