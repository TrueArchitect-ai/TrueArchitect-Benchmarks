**Mechanism: explicit Go code.** When a user is deleted, the store's `DeleteUser` transaction explicitly runs `DELETE FROM reaction ...` statements — both for reactions the user authored and for reactions on the user's memos. There is no database-level cascade for the `reaction` table; its schema has no foreign keys at all.

What I checked:

1. **Go deletion path** — `store/user.go:171` (`Store.DeleteUser`) dispatches to per-driver implementations. In each driver's `DeleteUser` transaction:
   - `store/db/sqlite/user_delete.go:96,102` calls `deleteReactionsByContentIDsTx` and `deleteReactionsByCreatorTx`, defined at lines 380–401, which execute `DELETE FROM reaction WHERE content_id IN (...)` (reactions on the deleted user's memos) and `DELETE FROM reaction WHERE creator_id = ?` (reactions the user made).
   - Identical code exists for Postgres (`store/db/postgres/user_delete.go:96,102,380,400`) and MySQL (`store/db/mysql/user_delete.go:96,102,417,437`).

2. **Database schema** — the `reaction` table has no foreign key or `ON DELETE CASCADE` in any dialect: `store/migration/sqlite/LATEST.sql:92-98`, `store/migration/postgres/LATEST.sql:91-97`, `store/migration/mysql/LATEST.sql:91-98`, and the original creation migrations (`store/migration/{sqlite,postgres}/0.20/00__reaction.sql`) — just columns and a UNIQUE constraint. A repo-wide grep for `FOREIGN KEY`/`REFERENCES` in `store/migration/` shows cascades on other tables (e.g. `user_setting`, `memo_organizer`) but none touching `reaction`, so a DB rule cannot be what cleans reactions up.

There's also a test asserting this cleanup happens: `store/test/user_delete_test.go:13` (`TestDeleteUserCleansRelatedData`).

**Answer:** explicit Go code (per-driver `DELETE FROM reaction` in the `DeleteUser` transaction); evidence: `store/db/{sqlite,postgres,mysql}/user_delete.go` (deleteReactionsByCreatorTx / deleteReactionsByContentIDsTx) plus FK-free schema in `store/migration/*/LATEST.sql`.
