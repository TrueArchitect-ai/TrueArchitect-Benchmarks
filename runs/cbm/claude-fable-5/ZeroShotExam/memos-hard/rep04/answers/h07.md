A browser GETs `/file/users/:identifier/avatar`, and the request reaches the stored avatar (a base64 data-URI held in the `user.avatar_url` column) through these hops:

```
serveUserAvatar — server/router/fileserver/fileserver.go:168   (route registered at fileserver.go:124)
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
(*DB).ListUsers — store/db/sqlite/user.go:88
```

The last hop is the DB driver: `ListUsers` builds a `SELECT … avatar_url … FROM user WHERE username = ?` (store/db/sqlite/user.go:152–173) and executes it via `QueryContext`, returning the row whose `avatar_url` data URI the handler then decodes (`parseDataURI`, fileserver.go:737) and serves as an image blob.

Notes:
- The `identifier` from the URL is looked up by username, so this serves *any* user's profile image (with an anonymous-access gate at fileserver.go:173 on private instances).
- The Postgres and MySQL drivers have equivalent `ListUsers` implementations (`store/db/postgres/user.go`, `store/db/mysql/user.go`); SQLite is shown as the representative data-layer driver. `Store.GetUser`/`ListUsers` also populate `s.userCache`, so a warm cache can short-circuit the driver hop.
