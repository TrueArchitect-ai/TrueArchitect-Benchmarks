Memo visibility is enforced independently at each of these server surfaces (all paths relative to repo root):

1. gRPC/Connect API (memo reads) — `server/router/api/v1/memo_service.go` — `checkMemoReadAccess` (line 39) gates single-memo access (public → anyone, protected → any authenticated user, private → creator only), and `ListMemos` scopes queries with a `VisibilityList`/creator filter (lines ~218–227).
2. File server (attachment bytes) — `server/router/fileserver/fileserver.go` — `checkAttachmentPermission` (line 650) re-checks the owning memo's visibility before serving attachment/thumbnail bytes (public + anonymous allowed at line 677, private restricted to creator/admin at line 699, with a share-token fallback).
3. SSE real-time events — `server/router/api/v1/sse_hub.go` — `SSEClient.canReceive` (line 134) filters broadcast memo events per connected client: private events are delivered only to the creator or an admin.
4. RSS feeds — `server/router/rss/rss.go` — both feed handlers query with `VisibilityList: []store.Visibility{store.Public}` (lines 90 and 141), so only public memos are ever exposed.
5. Frontend router (sitemap/rendered pages) — `server/router/frontend/frontend.go` — sitemap generation lists only `store.Public` memos (line 150).
6. Email notifications — `server/notification/email.go` — `canViewerAccessMemo` (line ~306) applies the same visibility rules before memo content is included in a notification email.

Additionally, several API-v1 sub-services re-enforce the parent memo's visibility for their own resources (same rule, separate code sites): reactions (`server/router/api/v1/reaction_service.go:30–38,83`), attachment metadata (`server/router/api/v1/attachment_service.go:445–451`), memo-attachment listing (`server/router/api/v1/memo_attachment_service.go:214–222`), comments (`server/router/api/v1/memo_service_comments.go:41`), and mention notifications (`server/router/api/v1/memo_mention_helpers.go:62–67`).
