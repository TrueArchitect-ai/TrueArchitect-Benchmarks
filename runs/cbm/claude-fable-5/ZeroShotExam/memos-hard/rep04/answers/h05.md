**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the user-deletion transaction, not by any database rule.

What I checked:

1. **The user-deletion code path.** Each database driver's `DeleteUser` runs a transaction that calls `deleteUserTargetsTx`, which explicitly removes reactions in two ways:
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (reactions the deleted user made): `store/db/sqlite/user_delete.go:400-403`, `store/db/mysql/user_delete.go:438`, `store/db/postgres/user_delete.go:401`.
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (reactions *on* the user's memos and their comment tree, since `content_id` is the string `"memos/<uid>"` rather than a real foreign key): `store/db/sqlite/user_delete.go:380-388` (called from `deleteUserTargetsTx` at `store/db/sqlite/user_delete.go:96,102`), with matching statements at `store/db/mysql/user_delete.go:420` and `store/db/postgres/user_delete.go:383`.

2. **The schema, to rule out a database-level rule.** The `reaction` table has no foreign keys at all — just columns and a UNIQUE constraint (`store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, and the same in `store/migration/postgres/LATEST.sql`). The only `ON DELETE CASCADE` in any of the three schemas is on `memo_share.memo_id → memo(id)` (e.g. `store/migration/sqlite/LATEST.sql:109`), which doesn't touch reactions. So no cascade or trigger could remove them; the explicit Go code is the only mechanism.
