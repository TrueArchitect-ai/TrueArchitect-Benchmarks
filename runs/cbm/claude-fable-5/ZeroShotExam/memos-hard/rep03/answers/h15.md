Memo visibility is checked independently on several server surfaces, not just in the memo API. The distinct enforcement sites are:

- gRPC/REST API v1 memo reads — `checkMemoReadAccess` at `server/router/api/v1/memo_service.go:39` (public/protected/private + archived-only-to-creator rules); the same surface also enforces it inline for list queries (`memo_service.go:219-225` restricts `VisibilityList` per viewer), comments (`server/router/api/v1/memo_service_comments.go:41`), reactions (`server/router/api/v1/reaction_service.go:30-38,83`), memo attachments (`server/router/api/v1/memo_attachment_service.go:214-222`), and attachment metadata (`checkAttachmentAccess`, `server/router/api/v1/attachment_service.go:422`)
- File server serving attachment blobs over HTTP — `checkAttachmentPermission` at `server/router/fileserver/fileserver.go:650` (re-loads the memo, checks Public + anonymous access, share-token fallback, and Private = creator/admin only)
- SSE realtime event stream — `SSEClient.canReceive` at `server/router/api/v1/sse_hub.go:134` (private-memo events delivered only to the creator or an admin)
- Notification emails — `canViewerAccessMemo` at `server/notification/email.go:306` (mention emails only sent if the recipient may view the memo)
- In-app notifications/inbox — a second `canViewerAccessMemo` at `server/router/api/v1/user_service_notifications.go:302` (with `canUserAccessMentionContext` in `server/router/api/v1/memo_mention_helpers.go:56` gating mention inbox entries)
- Public-only feeds — RSS at `server/router/rss/rss.go:90,141` and the sitemap at `server/router/frontend/frontend.go:150`, both hard-filter queries to `store.Public`

So the three headline surfaces are the v1 API (`checkMemoReadAccess`), the attachment file server (`checkAttachmentPermission`), and the SSE hub (`canReceive`), with notifications (email + in-app) and the RSS/sitemap public-only filters as additional independent enforcement points.
