**Mechanism: explicit Go code.** When a user is deleted, their reactions are removed by hand-written `DELETE FROM reaction ...` statements inside the user-deletion transaction — not by any database-level rule (the `reaction` table has no foreign key or `ON DELETE CASCADE`).

What I checked:

**Explicit Go deletion.** The API handler `DeleteUser` (`server/router/api/v1/user_service.go:393`) calls `Store.DeleteUser`, which each driver implements as a single transaction. In `deleteUserTargetsTx` the transaction runs two reaction cleanups:
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (the user's own reactions): `store/db/sqlite/user_delete.go:400-403`, called at line 102.
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (reactions left by others on the user's memos and comments): `store/db/sqlite/user_delete.go:380-388`, called at line 96.

The same pair exists in the other drivers: `store/db/mysql/user_delete.go:96,102,417,437` and `store/db/postgres/user_delete.go:96,102,380,400`.

**No database-level rule.** The `reaction` table definition has no foreign key at all — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/sqlite/LATEST.sql:92-99`, and likewise `store/migration/postgres/LATEST.sql:91-97` and `store/migration/mysql/LATEST.sql`. I grepped all migrations for `FOREIGN KEY`/`CASCADE`; cascades exist for other tables (e.g. `memo_share` → `memo` in `store/migration/sqlite/0.27/04__memo_share.sql:11`), but none reference `reaction`, so nothing would clean reactions up automatically.
