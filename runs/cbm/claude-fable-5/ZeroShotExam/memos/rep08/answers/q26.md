**Tables affected: `memo`, `memo_relation`, `attachment`**

Tracing the call chain:

- `Store.DeleteMemo` (`store/memo.go:140`) contains the explicit cascade code. Before deleting the memo row itself, it:
  - deletes `memo_relation` rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`) via two `driver.DeleteMemoRelation` calls;
  - lists all attachments linked to the memo and deletes each via `Store.DeleteAttachment` (`store/attachment.go:132`), which removes the storage object and then the `attachment` row (`store/db/sqlite/attachment.go:211`);
  - finally deletes the row from `memo` via `driver.DeleteMemo` (`store/db/sqlite/memo.go:237`, with equivalent code in the postgres and mysql drivers).
- The API-level handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally finds all comment memos (memo relations of type `COMMENT` pointing at this memo) and calls `Store.DeleteMemo` on each — which touches the same three tables for every comment.

Notably *not* deleted by code: `reaction` rows are only listed (to build the webhook payload) and are left in place, and `memo_share` rows are cleaned up only by a schema-level `ON DELETE CASCADE` foreign key (`store/migration/sqlite/LATEST.sql:109`), not by explicit code — so if you count DB-schema cascades, `memo_share` is also affected, but there is no cascade code for it.
