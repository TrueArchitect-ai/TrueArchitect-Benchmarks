**Engine:** Google's CEL (Common Expression Language) via `github.com/google/cel-go`, wrapped in the repo's own filter-to-SQL engine at `internal/filter/` (`engine.go`, `parser.go`, `ir.go`, `render.go`, `schema.go`, `helpers.go`).

**Mechanism:** `ListMemos` (`server/router/api/v1/memo_service.go:211-223`) validates the `filter` string and passes it through `MemoFind.Filters` to the store layer; each dialect driver (`store/db/sqlite/memo.go:57-61`, and the equivalents in `store/db/mysql/memo.go` and `store/db/postgres/memo.go`) calls `filter.AppendConditions` with its `DialectName`. The engine compiles the string with a schema-constrained `cel.Env` (`internal/filter/engine.go`), walks the resulting CEL AST in `internal/filter/parser.go` to build a dialect-agnostic `Condition` IR tree (`internal/filter/ir.go` — logical, comparison, IN, contains, etc.), and then a per-dialect renderer (`internal/filter/render.go`) turns that tree into a parameterized SQL WHERE fragment plus args, using per-dialect column expression templates defined in the schema (`internal/filter/schema.go`, e.g. `DialectSQLite`/`DialectMySQL`/`DialectPostgres` variants like `('users/' || %s)` vs `CONCAT('users/', %s)`).

In one sentence: the filter is a CEL expression compiled by cel-go into an AST, lowered by `internal/filter` into an intermediate condition tree, and rendered per dialect (SQLite/MySQL/Postgres) into a parameterized SQL fragment appended to the memo query's WHERE clause.
