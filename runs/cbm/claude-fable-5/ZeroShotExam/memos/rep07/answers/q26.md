**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`.**

How each is touched when `DeleteMemo` runs (API handler `server/router/api/v1/memo_service.go:518`, store layer `store/memo.go:140`):

- **`memo`** — the memo row itself is deleted via `DELETE FROM memo` in the driver (`store/db/sqlite/memo.go:237`, with mysql/postgres equivalents). The API handler also recursively calls `store.DeleteMemo` for each comment memo first (`memo_service.go:567-577`), so comment rows in `memo` are deleted too.
- **`memo_relation`** — explicit cascade code in `store/memo.go:142-147` deletes relations where the memo is either the source (`memo_id`) or target (`related_memo_id`), via `DeleteMemoRelation` (`store/db/sqlite/memo_relation.go:137`).
- **`attachment`** — explicit cascade code in `store/memo.go:148-157` lists the memo's attachments and deletes each via `DeleteAttachment`, which removes the row (`store/db/sqlite/attachment.go:211-212`) as well as the backing local/S3 file (`store/attachment.go:132-148` — the file itself isn't a table, but the `attachment` rows are).
- **`memo_share`** — not touched by Go code, but affected directly by the schema-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`), so share grants are cascade-deleted when the `memo` row goes.

Notably **not** affected: the `reaction` table — the handler only *lists* reactions to build the webhook payload (`memo_service.go:545-550`); nothing deletes them, and there's no FK cascade on `reaction`.
