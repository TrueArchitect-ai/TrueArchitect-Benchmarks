`web/src/connect.ts`; short-lived JWT access tokens (sent as `Authorization: Bearer`, refreshed via refresh tokens held in the `memos_refresh` cookie); `server/auth`

Frontend API requests go through the Connect RPC `authInterceptor` defined in `web/src/connect.ts` (attached to the transport at `web/src/connect.ts:184-189`). Before each request it fetches an access token via `getRequestToken()` — proactively refreshing it if expired or missing (token state lives in `web/src/auth-state.ts`) — and sets it as an `Authorization: Bearer` header. On a 401 (`Code.Unauthenticated`) it calls `refreshAccessToken()`, which uses a separate no-interceptor transport with `credentials: "include"` so the refresh-token cookie is sent to `AuthService.RefreshToken`, then retries the request once (marked with an `X-Retry` header) before redirecting to login on failure.

On the backend, validation lives in the `server/auth` package (`github.com/usememos/memos/server/auth`): `server/auth/authenticator.go` provides the shared `Authenticator` used by the gRPC/Connect interceptors and the file server, and `server/auth/token.go` defines the JWT parsing/signing — access tokens are 15-minute stateless JWTs (audience `user.access-token`), refresh tokens are 30-day JWTs stored in the `memos_refresh` cookie and checked against the database, and the package also validates long-lived Personal Access Tokens (`memos_pat_` prefix) for programmatic access.
