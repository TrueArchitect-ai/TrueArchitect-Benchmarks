**Tables affected by explicit code: `memo`, `memo_relation`, `attachment`.**

The delete path is:

1. **API layer** — `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) first deletes any comment memos (each via `store.DeleteMemo`), then the memo itself. It *lists* reactions and attachments, but only to build the webhook payload — it never deletes reaction rows.
2. **Store layer** — `Store.DeleteMemo` (`store/memo.go:140-159`) does the explicit cascade:
   - `DeleteMemoRelation` twice (as `MemoID` and as `RelatedMemoID`) → `memo_relation` table (`store/db/sqlite/memo_relation.go:149`, same for mysql/postgres)
   - lists attachments and calls `Store.DeleteAttachment` for each (`store/attachment.go:132-149`) → `attachment` table (`DELETE FROM attachment` at `store/db/sqlite/attachment.go:212`), plus the file blob in local/S3 storage (not a table)
   - finally `driver.DeleteMemo` → `memo` table (`DELETE FROM memo` at `store/db/sqlite/memo.go:239`)

One caveat worth noting: the `memo_share` table is also emptied when a memo is deleted, but only via a schema-level foreign key `ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`), not by any code. `reaction` rows are not cleaned up at all in this path.

So, strictly per the question's "directly or by explicit cascade code": **memo, memo_relation, attachment** (with memo_share affected only by the database FK cascade).
