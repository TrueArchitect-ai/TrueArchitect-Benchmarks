Frontend requests are authenticated via a Connect RPC client-side interceptor that attaches a JWT and transparently refreshes it, with a Go `auth` package validating tokens on the server.

- **Interceptor path:** `web/src/connect.ts` — the `authInterceptor` (line 156) is installed on the Connect transport used by all service clients. It sets the `Authorization: Bearer <token>` header on every request, does a preflight refresh if the token is expired (via `getRequestToken`), and on a 401 (`Code.Unauthenticated`) retries once after refreshing (guarded by an `X-Retry` header to prevent loops). Token state itself lives in `web/src/auth-state.ts`.

- **Token kinds:** two tokens — a short-lived **JWT access token** (kept in memory by the frontend, sent as a Bearer header) and a **refresh token** stored in an HTTP-only cookie (sent automatically via `credentials: "include"`, used by `refreshAccessToken()` calling `AuthService.RefreshToken` on a separate interceptor-free transport to avoid recursion). The backend additionally accepts **Personal Access Tokens** (PATs) on the same Bearer header for programmatic access, though the web interceptor itself only manages access/refresh tokens.

- **Backend package:** `server/auth` — `server/auth/authenticator.go` defines `Authenticator`, which statelessly validates access tokens (`AuthenticateByAccessTokenV2`), validates refresh tokens against the database with a revocation check (`AuthenticateByRefreshToken`), and validates PATs by hash lookup (`AuthenticateByPAT`). Bearer/cookie extraction helpers live in `server/auth/extract.go`.

**Answer format:** `web/src/connect.ts`; JWT access token (Bearer header) + refresh token (HTTP-only cookie), with PATs also accepted server-side; `server/auth` (`server/auth/authenticator.go`).
