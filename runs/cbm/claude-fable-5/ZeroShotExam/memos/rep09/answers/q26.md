**Tables affected: `memo`, `memo_relation`, `attachment`** (plus `memo_share` via a schema-level foreign-key cascade rather than code).

Details of the delete path:

- The API handler `DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first deletes all comment memos (memos related via a `COMMENT` relation) by calling `store.DeleteMemo` for each, then calls `store.DeleteMemo` for the memo itself. It lists reactions and attachments, but only to build the webhook payload — reactions are never deleted here.
- The store-level `DeleteMemo` (`store/memo.go:140`) performs the explicit cascade code:
  - `memo_relation` — deleted twice, once with the memo as source (`MemoID`) and once as target (`RelatedMemoID`).
  - `attachment` — each attachment linked to the memo is deleted via `store.DeleteAttachment` (`store/attachment.go:132`), which also removes the underlying storage blob (local file/S3, not a table).
  - `memo` — the memo row itself, via the driver (`store/db/sqlite/memo.go:237`, with equivalents in `store/db/postgres/memo.go` and `store/db/mysql/memo.go`).
- `memo_share` rows are removed too, but by the database itself: the schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, same in the postgres schema) — there is no cascade code for it.
- Notably, `reaction` rows for the memo are **not** cleaned up anywhere in this path, and there is no FK cascade on that table.
