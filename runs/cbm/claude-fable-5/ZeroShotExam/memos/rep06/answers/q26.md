**Tables affected: `memo`, `memo_relation`, `attachment`**

When the API handler `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518`), it calls `store.DeleteMemo` — once per comment memo and once for the memo itself (`memo_service.go:574,580`). The store-level cascade in `store/memo.go:140-159` explicitly:

1. Deletes `memo_relation` rows where the memo is source or target (`s.driver.DeleteMemoRelation`, e.g. `store/db/sqlite/memo_relation.go`)
2. Deletes each linked `attachment` row via `s.DeleteAttachment` (`store/attachment.go:132` → `DELETE FROM attachment` in `store/db/sqlite/attachment.go:211`; this also removes the file from storage, which isn't a table)
3. Deletes the `memo` row itself (`DELETE FROM memo`, `store/db/sqlite/memo.go:237`)

Since comment memos go through the same `store.DeleteMemo`, their rows in the same three tables are cleaned up too.

Two clarifying notes:
- `memo_share` rows are also removed, but only via the database-level `ON DELETE CASCADE` foreign key in the schema (`store/migration/sqlite/LATEST.sql:109`), not by any explicit Go cascade code — so it falls outside "explicit cascade code" strictly read, but is worth knowing.
- `reaction` rows are **not** deleted: the handler lists reactions only to build the webhook payload (`memo_service.go:545`), and no deletion of them occurs in this path.
