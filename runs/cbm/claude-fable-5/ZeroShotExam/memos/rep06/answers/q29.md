`web/src/connect.ts`; JWT access tokens (short-lived, sent as `Authorization: Bearer …`) and refresh tokens (long-lived, held in the `memos_refresh` cookie and exchanged via `refreshToken` for new access tokens); `server/auth`.

Details:

- **Interceptor**: `authInterceptor` in `web/src/connect.ts:156` is a Connect RPC `Interceptor` attached to the transport (`web/src/connect.ts:184-189`) used by all service clients. On each request it obtains an access token via `getRequestToken()` (with a preflight refresh if the token is near expiry) and sets the `Authorization: Bearer <token>` header. On a `Code.Unauthenticated` error it refreshes once and retries (marked with an `X-Retry` header), redirecting to login if the refresh fails.
- **Tokens managed**: a short-lived JWT **access token** kept in memory/shared across tabs via `web/src/auth-state.ts`, and a long-lived **refresh token** carried in a cookie (`credentials: "include"`; cookie name `memos_refresh`) used by a separate no-interceptor transport to call `AuthService.refreshToken`. Concurrent refreshes are deduplicated by `tokenRefreshManager`.
- **Backend validation**: the `server/auth` package (`server/auth/token.go`, `server/auth/authenticator.go`) — its `Authenticator` validates JWT access tokens statelessly (`AuthenticateByAccessTokenV2`, 15-minute lifetime, audience `user.access-token`), validates refresh tokens against the database (30-day lifetime, audience `user.refresh-token`), and also supports `memos_pat_`-prefixed Personal Access Tokens. It's consumed by the gRPC/Connect interceptors in `server/router/api/v1` and the file server, per the package doc comment.
