**Token kinds it manages:**
- **Access token (JWT, "Access Token V2")** — short-lived bearer token sent as `Authorization: Bearer <token>` (`setAuthorizationHeader`, connect.ts:97–100). Held in `auth-state.ts` via `getAccessToken`/`setAccessToken`.
- **Refresh token** — used to mint new access tokens. The interceptor doesn't send it directly in the header; it calls `refreshAccessToken()` → `doRefreshAccessToken()` which hits `refreshAuthClient.refreshToken({})` (connect.ts:74–90), and the refresh token itself rides as an HTTP-only cookie (`fetchWithCredentials`). The interceptor does a preflight refresh on near-expiry and a reactive refresh on a `Code.Unauthenticated` 401, then retries once (connect.ts:161–177).

The backend additionally validates **Personal Access Tokens (PATs)** on the same `Authorization` header, though the frontend interceptor only manages access/refresh tokens.

**Backend package that validates them:** `server/auth/` (package `auth`, `server/auth/authenticator.go`). The Connect-side `AuthInterceptor.WrapUnary` (`server/router/api/v1/connect_interceptors.go:217`) reads the `Authorization` header and delegates to `Authorizer` → `auth.Authenticate` (authenticator.go:213), which resolves an access token via `AuthenticateByAccessTokenV2` (stateless JWT check, line 41) or falls back to `AuthenticateByPAT` (line 102); `AuthenticateByRefreshToken` (line 61) validates the refresh token against the store.
