**Interceptor path:** `web/src/connect.ts` — `authInterceptor` (defined at line 156), registered on the main Connect transport (`interceptors: [authInterceptor]`, line 188). It sets `Authorization: Bearer <token>` on every request (`setAuthorizationHeader`, lines 97–100), and on a 401 it transparently refreshes and retries once. Token state (get/set/expiry/broadcast across tabs) lives in `web/src/auth-state.ts`.

**Token kinds** the flow manages:
- **Short-lived JWT access token** — held in memory + `localStorage` (`memos_access_token`), attached as the `Bearer` header; 15-minute lifetime, audience `user.access-token` (`server/auth/token.go:37,40`).
- **Refresh token** — a JWT delivered as a `SameSite=Lax` HttpOnly cookie (`memos_refresh`), audience `user.refresh-token`, 30-day lifetime (`server/auth/token.go:46,49,43`). The frontend never reads it directly; it calls `RefreshToken` (via `refreshTransport`, a separate transport with no auth interceptor to avoid recursion — `web/src/connect.ts:64–72`) to mint a new access token.
- **Personal Access Tokens (PATs)** — long-lived `memos_pat_`-prefixed tokens for API/script access, also carried in the `Authorization` header (`server/auth/token.go:52`).

**Backend package that validates them:** `server/auth` — `token.go` verifies the JWTs via `jwt.ParseWithClaims` (lines 222, 238) against the configured secret and audience, and `authenticator.go`'s `AuthenticateToUser` (line 190) resolves a request to a `*store.User` by checking the Authorization header (access token or PAT) first, then falling back to the refresh-token cookie. This `Authenticator` is driven by the `Authorizer` in `server/router/api/v1/authz.go`, which is invoked from the server-side `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:217–222`) and the gRPC-Gateway middleware (`server/router/api/v1/v1.go:76–78`).
