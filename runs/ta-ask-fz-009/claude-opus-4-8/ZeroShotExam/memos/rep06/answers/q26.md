**Tables written to (DELETE) by DeleteMemo:**

- **`memo_relation`**
- **`attachment`**
- **`memo`**

**How it gets there:**

1. `v1.APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first finds comment child-memos via `ListMemoRelations` and deletes each one, then deletes the target memo — both through `store.Store.DeleteMemo` (`memo_service.go:574` and `:580`).
2. `store.Store.DeleteMemo` (`store/memo.go:140`) performs the explicit cascade, in order:
   - Two `DeleteMemoRelation` calls (source and target) → `DELETE FROM memo_relation` (`store/db/sqlite/memo_relation.go:149`)
   - Lists and deletes each linked attachment → `DELETE FROM attachment` (`store/db/sqlite/attachment.go:212`)
   - Finally deletes the memo itself → `DELETE FROM memo` (`store/db/sqlite/memo.go:239`)

**Not affected:** The `reaction` table. The handler calls `ListReactions` at `memo_service.go:545`, but that's only to build the webhook payload — neither the handler nor `store.Store.DeleteMemo` deletes reaction rows. (Reaction deletion on memo removal only happens in the separate user-delete path, `store/db/sqlite/user_delete.go`, which is not reached by `DeleteMemo`.)

(SQL anchors cited are the SQLite driver; the same DELETEs exist in the mysql/postgres drivers under `store/db/`.)
