**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the user-deletion transaction — not by any database-level cascade rule.

**What I checked and evidence locations:**

1. **The `reaction` table schema — no FK / cascade.** In all three dialects the table has only a `creator_id INTEGER NOT NULL` column with a `UNIQUE(creator_id, content_id, reaction_type)` constraint, and **no `FOREIGN KEY ... ON DELETE CASCADE`**:

   So the database will not clean up reactions on its own.

2. **The explicit deletion path.** `DeleteUser` runs a transaction whose target set is deleted by `deleteUserTargetsTx`, which calls two reaction-deleting helpers before removing the user row:
   - `store/db/sqlite/user_delete.go:96` → `deleteReactionsByContentIDsTx` (reactions *on* the deleted user's memos, matched by `content_id`)
   - `store/db/sqlite/user_delete.go:102` → `deleteReactionsByCreatorTx` (reactions *made by* the user, matched by `creator_id`)

   The SQL itself:

Both facets are covered: reactions the user *authored* (`creator_id`) and reactions others left on the user's *memos* (`content_id`) are deleted, all within the same transaction as the user removal.
