**Premise correction:** Neither. The question presupposes an external message broker, but the webhook delivery workers consume from *neither NATS nor RabbitMQ*. A search across all Go files for `nats|rabbitmq|amqp|broker` turns up no message-broker usage anywhere in the repo — the only "queue" hits are in-process Go channels. (The map also returns a certified miss for the concept "worker" — there is no dedicated worker type.)

**Actual mechanism:** Webhook dispatch is an in-memory Go channel with a fixed pool of goroutines, all inside the process — no broker, no network queue, no persistence.

Declared in `internal/webhook/webhook.go`:

- **The "queue"** is a buffered channel, `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`) — capacity 128.
- **The "workers"** are 4 goroutines spawned in `init()` (`internal/webhook/webhook.go:42-55`), each ranging over `asyncPostQueue` and calling `Post(payload)` for every payload.
- **Producers** enqueue via `PostAsync`, which does a non-blocking send: `case asyncPostQueue <- requestPayload` (`internal/webhook/webhook.go:190`), and on a full buffer *drops* the webhook with a warning (`internal/webhook/webhook.go:192`) rather than blocking or persisting.

So delivery is bounded, best-effort, and entirely in-process. Anything that overflows the 128-slot channel is silently discarded — there is no broker-backed durability. (The same pattern is mirrored for email in `internal/email/email.go:14`.)
