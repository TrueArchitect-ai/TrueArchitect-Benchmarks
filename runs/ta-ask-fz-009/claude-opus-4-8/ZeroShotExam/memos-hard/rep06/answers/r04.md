**Premise correction:** Neither. There is no message broker in this webhook path — no NATS, no RabbitMQ. The question presupposes an external broker and delivery workers consuming from a declared queue; that architecture does not exist here.

**Actual mechanism:** Webhook delivery is an *in-process* async dispatch built on a Go buffered channel and a fixed goroutine worker pool, all inside `internal/webhook/webhook.go`:

- The "queue" is a package-level buffered channel of capacity 128, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The "workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over that channel and calling `Post` per payload.
- Producers enqueue via `PostAsync` (`webhook.go:184-196`), which does a non-blocking `select` send — if the channel is full, the dispatch is *dropped* with a warning (`webhook.go:191-194`), not persisted or retried.
- `Post` (`webhook.go:120-180`) is the actual delivery: it marshals the payload to JSON and does a plain HTTP `POST` to the target URL via a shared `safeClient` with SSRF-guarded dialing (`webhook.go:32-37`, `safeDialContext` at `webhook.go:59-77`).

So the transport to the webhook consumer is HTTP; the internal hand-off between the API layer and the delivery goroutines is a bounded in-memory channel. No broker sits in between, which also means delivery is best-effort and lost on process restart or queue overflow.
