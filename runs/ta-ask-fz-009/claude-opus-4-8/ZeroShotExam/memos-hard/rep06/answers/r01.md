**Premise correction:** There is no Redis in this cache layer. The question presupposes an external Redis connection, but the cache is a thread-safe **in-memory** cache built entirely in-process — a `sync.Map` with a background cleanup goroutine. It's defined in `store/cache/cache.go:66-73` (`Cache` struct) and explicitly documented as "a thread-safe in-memory cache with TTL and memory management." A codebase search for "redis" surfaced no connection code, config, or client anywhere. There is no Redis endpoint, DSN, or connection to configure.

**Actual mechanism:**

- **Where it's configured:** The store wires up three separate in-memory caches in `store/store.go:40-53`. The `cacheConfig` is constructed inline in `store.New(...)` (`store/store.go:40-45`), then handed to `cache.New(cacheConfig)` for each of `instanceSettingCache`, `userCache`, and `userSettingCache`. There's no connection string — the "configuration" is just this in-process `cache.Config` struct (TTL, cleanup interval, max items, eviction hook).

- **TTL for user entries:** The user cache (`userCache`, `store/store.go:52`) uses the shared `cacheConfig`, whose `DefaultTTL` is **10 minutes** (`store/store.go:41`; identical default in `cache.DefaultConfig()` at `store/cache/cache.go:59`). User records are written via `s.userCache.Set(...)` (e.g. `store/user.go:98, 122, 132, 143, 167`), and `Set` applies the default TTL — `Set` delegates to `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:93-95`). No user write path passes a custom TTL, so every user entry expires **10 minutes** after it's stored. A cleanup loop sweeps expired entries every 5 minutes (`CleanupInterval`, `store/store.go:42`), and entries are also evicted early if the cache exceeds `MaxItems: 1000` (`store/store.go:43`, enforced at `store/cache/cache.go:117-119`).

The user cache key is just the stringified user ID (`userCacheKey`, `store/user.go:88-90`), and entries are invalidated on delete via `deleteUserCache` (`store/user_delete.go:39-40`).
