**Premise correction:** There is no Redis in this cache layer. The question presupposes a Redis-backed cache with a configurable connection — that mechanism does not exist in this repository. A search for `redis` across the code graph returned zero cache-related symbols (only unrelated filter/proto matches). The cache is a **thread-safe in-memory cache**, not an external store, so there is no connection to configure — nothing to point at a host, port, or DSN.

**Actual mechanism:**

- **Implementation:** `store/cache/cache.go` — `cache.Cache` (`store/cache/cache.go:67`) is an in-process cache built on `sync.Map` plus an `atomic.Int64` item counter and a background `cleanupLoop` goroutine (`cache.go:200`). No network client, no serialization, no Redis driver.

- **Where "configuration" actually lives:** `store/store.go:40–45`, in `store.New(...)`. The store builds a single `cache.Config` literal and hands the *same* config to three separate in-memory caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51–53`). This is the closest thing to what you called "the Redis connection for the cache layer."

- **TTL for user entries:** User records are stored via `s.userCache.Set(...)` (e.g. `store/user.go:98`, keyed by `userCacheKey`, which is just the stringified user ID — `store/user.go:88`). `Set` uses the cache's `DefaultTTL` (`store/cache/cache.go:93–94`). Since `userCache` is constructed from `cacheConfig`, the applicable TTL is **`DefaultTTL = 10 * time.Minute`** (`store/store.go:41`). There is no user-specific TTL override — no call path uses `SetWithTTL` for users, so all user entries expire 10 minutes after write.

Two related details worth noting: the config also sets `CleanupInterval: 5 * time.Minute` (background sweep of expired items) and `MaxItems: 1000` (LRU-ish eviction of oldest entries once exceeded). Note the identical hardcoded config also appears as `cache.DefaultConfig()` at `store/cache/cache.go:57`, though `store.New` inlines its own copy rather than calling it.
