**Mechanism: by explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the delete-user transaction — not by any database-level `ON DELETE CASCADE` (the `reaction` table has no foreign keys at all).

The deletion is two-pronged, both executed explicitly:
- **Reactions the deleted user authored** — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`.
- **Reactions others left on the deleted user's memos** — `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)`, where the content IDs are built (`"memos/" + uid`) from the recursively-collected tree of the user's memos and their comment children.

Both are invoked from `deleteUserTargetsTx`, inside the transaction opened in `DeleteUser`, and are identical across all three drivers.

**Why not database-level:** the `reaction` table definition lists only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE` constraint — no `FOREIGN KEY`, so `creator_id` is a plain integer with no referential action. Nothing cascades from the `user` row.
