**Premise correction:** The webhook delivery workers consume from *neither* NATS nor RabbitMQ. This repository (the memos server) has no message broker in the webhook path — a `go.mod` search for `nats`, `rabbitmq`, `amqp`, and related driver names returns no matches, and there is no external queue declaration anywhere.

**Actual mechanism:** Webhook delivery is an in-process, in-memory design in `internal/webhook/webhook.go`:

- The "queue" is a buffered Go channel, not a broker queue: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — declared at `internal/webhook/webhook.go:39`, capacity 128.
- The "workers" are four goroutines started in `init()` (`for range 4 { go func() { ... } }`), each ranging over that channel and calling `Post` for every payload — `internal/webhook/webhook.go:42-55`.
- Producers enqueue via `PostAsync` (`webhook.go:184-196`), a non-blocking send: if the channel buffer is full, the `default` branch drops the webhook and logs a warning rather than blocking or persisting it.
- Each worker's `Post` (`webhook.go:120-180`) just does an HTTP `POST` to the target URL using a shared SSRF-guarded `http.Client`.

So the "broker" is a bounded, non-durable in-memory channel local to the process — nothing is consumed from NATS or RabbitMQ, and no external queue is declared. A consequence worth noting: because the buffer is in-memory and lossy on overflow (and on process restart), there's no delivery durability guarantee.
