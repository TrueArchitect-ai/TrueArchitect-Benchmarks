**Premise correction:** Neither. The webhook delivery workers do not consume from NATS or RabbitMQ — there is no external message broker in this repository at all. The grep for `nats|rabbitmq|amqp|broker` across all Go files turned up nothing; the only "queue" is an in-process Go channel.

**Actual mechanism:** Webhook delivery is an in-memory bounded channel with a fixed pool of goroutine workers, all inside `internal/webhook/webhook.go` (package `webhook`):

- **The queue** is a buffered Go channel of capacity 128, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- **The "workers"** are 4 goroutines spun up in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` for every payload.
- **Producers** enqueue via `PostAsync()` (`webhook.go:184-196`), which does a non-blocking `select` send: if the buffer is full, the dispatch is **dropped** (logged as a warning), not persisted or retried — there is no durable broker semantics.
- Each `Post()` (`webhook.go:120`) just does an HTTP POST to the webhook target URL via a shared, SSRF-guarded `http.Client`.

So the "message broker" framing doesn't apply: delivery is fire-and-forget over an internal channel that lives and dies with the process. The identical pattern is used for email (`internal/email/email.go:14`, `asyncEmailQueue`), confirming this is the codebase's house style rather than any external queue.
