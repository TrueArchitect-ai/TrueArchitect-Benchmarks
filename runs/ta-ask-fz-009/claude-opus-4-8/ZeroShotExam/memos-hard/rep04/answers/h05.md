**Mechanism: removed by explicit Go code** (an application-level `DELETE` inside the user-deletion transaction), *not* by a database-level rule.

When a user is deleted, their emoji reactions are removed twice over by explicit SQL that the Go code issues — once by creator, once by content:

- `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` for the deleted user's ID — this is the direct removal of reactions the user authored.
- `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` for the deleted user's memos — this removes reactions *others* placed on the deleted user's content.

Both are called from `deleteUserTargetsTx`, all inside the single delete-user transaction. This is implemented identically across all three DB drivers.

There is **no database-level rule** doing this: the `reaction` table declares `creator_id INT NOT NULL` with no `REFERENCES`/foreign key and no `ON DELETE CASCADE` in any dialect's schema, so the cleanup depends entirely on the Go code running.

One caveat worth noting: because removal is code-driven rather than enforced by a constraint, a reaction is only cleaned up when it is authored by the deleted user or attached to that user's memos. A reaction the deleted user placed on *another* user's memo is caught by the `creator_id` delete; it is not left dangling.
