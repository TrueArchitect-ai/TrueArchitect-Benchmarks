**Premise correction:** There is no Redis in this cache layer. The premise assumes an external Redis connection, but the cache is a thread-safe **in-memory** cache — a `sync.Map` with per-item expiration and a background cleanup goroutine. There is no Redis client, connection string, or network dependency anywhere in it (`store/cache/cache.go`; the `Cache` struct is backed by `sync.Map` at `store/cache/cache.go:67-73`).

**Actual mechanism:**

- **Where it's "configured":** Not via a connection — via a `cache.Config` struct constructed in code at `store/store.go:40-45` (inside `store.New`). The `Store` holds three separate in-memory caches — `instanceSettingCache`, `userCache`, and `userSettingCache` — each created with `cache.New(cacheConfig)` (`store/store.go:51-53`). There's also a `DefaultConfig()` with identical values at `store/cache/cache.go:57-64`.

- **TTL for user entries:** **10 minutes.** User entries are written with `s.userCache.Set(...)` (e.g. `store/user.go:98`, `:122`, `:132`, `:143`, `:167`). `Set` applies the cache's `DefaultTTL` (`store/cache/cache.go:93-94`) — there's no `SetWithTTL` override anywhere for the user cache — and that `DefaultTTL` is the 10 minutes wired in at `store/store.go:41`. Expiry is enforced lazily on `Get` (`store/cache/cache.go:135-144`) and swept every 5 minutes by the cleanup loop (`store/cache/cache.go:200-215`). Cache keys are just the stringified user ID (`userCacheKey`, `store/user.go:88-90`).
