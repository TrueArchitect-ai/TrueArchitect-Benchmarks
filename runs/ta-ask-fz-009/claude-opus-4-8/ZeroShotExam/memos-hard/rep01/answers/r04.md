**Premise correction:** Neither. The webhook delivery workers do not consume from NATS or RabbitMQ — there is no external message broker in this repository at all. A search for `nats`, `rabbitmq`, `amqp`, and `streadway` across all 343 Go files returned zero matches, and the event topology shows only browser DOM events, no broker topics.

**Actual mechanism:** Webhook delivery is an in-process, in-memory pipeline built on a buffered Go channel, all in `internal/webhook/webhook.go`:

- **The "queue"** is a package-level buffered channel, not a broker queue:
  `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — declared at `internal/webhook/webhook.go:39`.
- **The workers** are 4 goroutines spawned in `init()` (`internal/webhook/webhook.go:42–55`), each ranging over `asyncPostQueue` and calling `Post` to fire the HTTP request.
- **Producers** enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking `select` send onto the channel and drops the payload with a warning if the buffer (128) is full.
- **Delivery itself** is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120`), using a shared SSRF-guarded `http.Client`, optionally HMAC-SHA256 signed per the Standard Webhooks spec.

So the "message broker" and "consume from a queue" framing doesn't apply — it's a bounded fan-out worker pool over an in-memory channel that lives and dies with the server process. If the process restarts, anything still buffered in `asyncPostQueue` is lost; there is no durable broker backing it.
