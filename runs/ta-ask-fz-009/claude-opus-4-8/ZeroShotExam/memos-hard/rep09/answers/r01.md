**Premise correction:** There is no Redis in this repository. A whole-tree search for `[Rr]edis` matched **0 of 1042 files** — no Redis client, no connection config, nothing. The cache layer is a **thread-safe in-memory cache** (Go `sync.Map`), not a Redis-backed one. `store/cache/cache.go:66` describes `Cache` verbatim as "a thread-safe in-memory cache with TTL and memory management."

**Actual mechanism:**

- **Where it's configured:** `store/store.go:38-58`, in `store.New`. A single `cache.Config` literal (`cacheConfig`) is built there and passed to `cache.New(...)` for three caches: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). The cache type and its config struct live in `store/cache/cache.go` (`Config` at line 42, `New` at line 76).

- **TTL for user entries:** **10 minutes.** User records are written via `s.userCache.Set(...)` (e.g. `store/user.go:98, 122, 132, 143, 167`). `Cache.Set` uses the configured `DefaultTTL` (`store/cache/cache.go:93-95`), and that value is `10 * time.Minute` as set in `store/store.go:41`. There is no per-user `SetWithTTL` override anywhere in the user store, so the default applies to every user entry.

- **Related settings on the same config:** `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store/store.go:42-43`). Expiry is enforced by a background `cleanupLoop` goroutine (`store/cache/cache.go:83, 200`), and entries are also lazily treated as expired on `Get`. Note that user settings (`userSettingCache`, keyed via `getUserSettingCacheKey` in `store/cache.go:7`) share the identical 10-minute TTL — same config struct.
