**Premise correction:** The premise is false on both counts — the webhook delivery workers consume from *neither* NATS nor RabbitMQ. There is no external message broker anywhere in the webhook path (nor in the repository — no NATS, AMQP, or RabbitMQ dependency or client appears in the webhook code). "Queue" here is not a broker queue and there is no queue "declaration" in the AMQP/JetStream sense.

**Actual mechanism:** Webhook delivery uses an in-process, in-memory Go buffered channel with a fixed pool of goroutine workers — all inside `internal/webhook/webhook.go`:

- The "queue" is a package-level buffered channel of capacity 128, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The workers are 4 goroutines spawned in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` to make the outbound HTTP POST.
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto the channel and **drops** the payload with a warning if the buffer is full (`internal/webhook/webhook.go:189-195`).

So the design is a bounded in-memory fan-out (channel + goroutine pool), not a durable broker. A notable consequence: because the queue lives only in process memory, pending webhooks are lost on restart, and overflow is silently dropped rather than backpressured or persisted. The same pattern is used for email at `internal/email/email.go:14-19`.
