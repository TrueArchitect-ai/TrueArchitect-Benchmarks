The serving handler is `serveUserAvatar` for `GET /users/:identifier/avatar`. It authorizes the viewer (only on private instances), then looks up the *target* user by username and returns the avatar, which is stored inline as a data URI in the user record's `AvatarURL` column and decoded on the way out. The chain from handler to stored data:

serveUserAvatar — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
store.Store.GetUser — store/user.go:148
store.Store.ListUsers — store/user.go:136
store.Driver.ListUsers — store/driver.go:47 (interface)
DB.ListUsers — store/db/sqlite/user.go:88 (and store/db/postgres/user.go:87, store/db/mysql/user.go:84) — the concrete driver that issues the SQL

Notes:
- The bytes themselves are not a separate blob table: back in the handler at fileserver.go:192–199, `user.AvatarURL` is decoded by `parseDataURI` (fileserver.go:737) and written with `c.Blob`. So "stored data" here is the `AvatarURL` field on the user row fetched above, not a file or attachment store.
- `store.Store.GetUser` (store/user.go:148) checks `userCache` only when the lookup is by ID; this request looks up by `Username`, so it always falls through to `ListUsers` → driver → DB.
- On a private instance, there's an additional auth branch (`getCurrentUser` → `auth.Authenticator.AuthenticateToUser` → store/driver) that resolves the *viewer*, but the profile-image data path is the `getUserByUsername` branch above.
