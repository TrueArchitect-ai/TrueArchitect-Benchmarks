**Premise correction:** Neither. The webhook delivery workers don't consume from NATS *or* RabbitMQ — there is no external message broker in this system. The premise assumes a broker-backed queue that doesn't exist.

**Actual mechanism:** Webhook delivery is handled entirely in-process by a Go buffered channel with a worker pool. It's all in `internal/webhook/webhook.go`:

- The "queue" is a package-level Go channel, not a broker-declared queue: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a bounded in-memory channel with capacity 128 (`internal/webhook/webhook.go:39`).
- The workers are 4 goroutines started in `init()`, each ranging over that channel and calling `Post(payload)` to fire the HTTP request (`internal/webhook/webhook.go:42-55`).
- Producers enqueue via `PostAsync`, a non-blocking `select` send that drops the payload (with a warning log) if the channel is full, rather than blocking (`internal/webhook/webhook.go:184-196`).

Delivery itself is a plain HTTP POST over a shared `http.Client` with SSRF protection, optionally HMAC-SHA256 signed per the Standard Webhooks spec (`Post`, `internal/webhook/webhook.go:120-180`).

The only imports in that file are stdlib plus `google/uuid`, `pkg/errors`, and the generated proto package — no NATS, AMQP, or RabbitMQ client anywhere (`internal/webhook/webhook.go:3-23`). The broker-keyword search across the Go tree turned up only SSE hub pub/sub and unrelated locale strings, confirming there's no broker dependency backing webhook delivery.

One consequence worth flagging: because the queue lives in process memory, enqueued-but-undelivered webhooks are lost on restart, and there's no cross-instance distribution or persistence — which a NATS/RabbitMQ design would have provided.
