From q16, `Store.DeleteMemo` explicitly deletes memo_relation and attachment records, then the memo row. Let me verify the attachment delete doesn't cascade further, and check whether reactions get touched anywhere in the delete path.

`DeleteAttachment` deletes the attachment row (plus underlying blob storage, not a DB table). So the store-layer `DeleteMemo` path touches three tables.

q26.
- **memo_relation** — deleted directly in `Store.DeleteMemo` (both `MemoID` and `RelatedMemoID` directions), `store/memo.go:142,145`
- **attachment** — each linked attachment deleted via `DeleteAttachment` → `driver.DeleteAttachment`, `store/memo.go:153-157` and `store/attachment.go:148`
- **memo** — the memo row itself, `store/memo.go:158`

Notes: `DeleteAttachment` also removes the underlying blob storage (`DeleteAttachmentStorage`, `store/attachment.go:141`), but that's filesystem/object storage, not a DB table. The `reaction` table is **not** touched by the store's `DeleteMemo` (no explicit cascade in code). If the DB schema declares foreign-key cascades, additional rows could be removed at the engine level, but that's not explicit cascade code in the Go layer.
