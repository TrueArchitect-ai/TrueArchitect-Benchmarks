**Premise correction:** There is no Redis in this codebase. A full-text search for "redis" across all 343 Go files returns zero matches, and the cache layer imports only the standard library (`context`, `sync`, `sync/atomic`, `time`) — no Redis client. So "the Redis connection for the cache layer" does not exist; there's nothing to configure.

**Actual mechanism:** The cache is an **in-process, in-memory** implementation — `cache.Cache`, defined in `store/cache/cache.go`. It stores entries in a Go map guarded by a mutex, with per-item expiration timestamps and a background cleanup goroutine (`item` struct at `store/cache/cache.go:35`, `Config` at `:42`). It is *not* a shared/external cache, so state is per-server-instance and not persisted.

**Configuration site:** The caches are constructed in `store.New` at `store/store.go:40–53`, where a single `cache.Config` is built and passed to three `cache.New(cacheConfig)` calls — one of which is `userCache` (`store/store.go:52`). User entries are keyed by user ID via `userCacheKey` (`store/user.go:88`) and populated on reads (`store/user.go:98,122,132,143,167`).

**TTL applied to user entries:** **10 minutes.** The `userCache` uses the store's shared `cacheConfig` with `DefaultTTL: 10 * time.Minute` (`store/store.go:41`), and all user entries are written via `userCache.Set(...)`, which applies the default TTL (`cache.Interface.Set` uses the default TTL per `store/cache/cache.go:12–13`). No user write uses `SetWithTTL`, so nothing overrides the 10-minute default. (Cleanup of expired entries runs every 5 minutes — `store/store.go:42`.) This is the same default configured by `cache.DefaultConfig()` (`store/cache/cache.go:57–59`).
