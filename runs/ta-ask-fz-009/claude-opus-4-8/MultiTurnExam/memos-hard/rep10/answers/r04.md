**Premise correction: The webhook delivery workers do not consume from any message broker — neither NATS nor RabbitMQ. Neither exists in the codebase.** A search for `nats`, `rabbitmq`, `amqp`, `streadway`, and `nats-io` across all 343 Go files returns zero matches; no such dependency is imported.

**Actual mechanism: an in-process buffered Go channel with a fixed pool of worker goroutines** — all inside `internal/webhook/webhook.go`, no external broker and no separately "declared queue":

- The "queue" is a package-level buffered channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`) — capacity 128, in-memory, local to the process.
- The "workers" are 4 goroutines started in `init()` that range over that channel and call `Post` for each payload (`internal/webhook/webhook.go:42-55`).
- Producers enqueue via `PostAsync`, which does a non-blocking send onto the channel and drops the delivery (with a warning log) if the buffer is full (`internal/webhook/webhook.go:184-196`).
- Each worker's `Post` performs the actual outbound HTTP POST via the SSRF-guarded `safeClient.Do` (`internal/webhook/webhook.go:152`).

So there is no broker to consume from and no queue declaration in the broker sense — the entire delivery pipeline is a bounded in-memory channel (`asyncPostQueue`) drained by four in-process goroutines, initialized in the `webhook` package's `init()` function. If durable, cross-process queuing were required, it would have to be introduced; today webhook delivery is best-effort and non-persistent (undelivered items are dropped on full buffer or lost on restart).
