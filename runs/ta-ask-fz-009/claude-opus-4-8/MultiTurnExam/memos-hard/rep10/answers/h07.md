The profile image is stored as a data-URI in the target user's row (`User.AvatarURL`), so serving it is fundamentally a user-record read. The hops, from the browser's `GET /users/:identifier/avatar` down to the driver:

`serveUserAvatar — server/router/fileserver/fileserver.go:168`
`FileServerService.getUserByUsername — server/router/fileserver/fileserver.go:715`

Notes on the trace:
- The handler resolves the URL `:identifier` param and calls `getUserByUsername` (`fileserver.go:185`), which builds a `store.FindUser{Username: ...}` and calls `Store.GetUser` (`fileserver.go:716`).
- `Store.GetUser` (`store/user.go:148`) — for a username lookup there's no ID cache hit, so it delegates to `Store.ListUsers`.
- `Store.ListUsers` (`store/user.go:136`) calls `s.driver.ListUsers(ctx, find)` (`store/user.go:137`) — the interface hop into the concrete SQL driver (`store/db/{sqlite,mysql,postgres}`) that reads the `user` table.
- Back in the handler, the retrieved `user.AvatarURL` (the stored data URI) is decoded by `parseDataURI` (`fileserver.go:737`), MIME-type-checked against `avatarAllowedTypes`, and written to the response via `c.Blob` (`fileserver.go:209`).

So the "stored data" is the user row itself — no separate blob/attachment store is involved for avatars.
