**Premise correction:** There is no Redis in this cache layer — no Redis connection is configured anywhere. A search for "redis" across all 343 Go files returns zero matches. The cache layer is a **process-local, in-memory cache**, not a networked/Redis one.

**Actual mechanism:** The cache is `cache.Cache` (`store/cache/cache.go:67`) — "a thread-safe in-memory cache with TTL and memory management," backed by a `sync.Map` (`cache.go:69`) with a background `cleanupLoop` goroutine (`cache.go:200`). There is no connection to configure; it's created with `cache.New(config)` in-process.

- **Where it's "configured":** in the store constructor, `store.New`, at `store/store.go:40-45`. That builds a single `cache.Config{DefaultTTL: 10*time.Minute, CleanupInterval: 5*time.Minute, MaxItems: 1000}` and instantiates three separate in-memory caches with it — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). The user cache is the `userCache *cache.Cache` field (`store/store.go:28`), keyed by user ID via `userCacheKey` (`store/user.go:88`).

- **TTL for user entries:** **10 minutes.** User entries are written via `s.userCache.Set(...)` (e.g. `store/user.go:98,122,132,143,167`), and `Set` applies the config's `DefaultTTL` (`cache.go:93-94`), which is `10 * time.Minute` (`store/store.go:41`). Expired entries are lazily dropped on `Get` (`cache.go:135`) and swept by the cleanup loop every 5 minutes (`cache.go:218`); entries are also invalidated explicitly on user delete via `userCache.Delete` (`store/user_delete.go:40`). There is no per-entry custom TTL for users, so the 10-minute default is the effective user-entry TTL.
