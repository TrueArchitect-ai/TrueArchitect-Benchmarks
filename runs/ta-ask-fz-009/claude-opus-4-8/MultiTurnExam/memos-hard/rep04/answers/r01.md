**Premise correction: there is no Redis. The cache layer is a purpose-built, in-process in-memory cache — no Redis (or any external cache server) connection exists to configure.**

Actual mechanism:

- The cache is `store/cache/cache.go` — a thread-safe in-memory `Cache` backed by a `sync.Map` (`Cache` struct, store/cache/cache.go:66–73), with TTL expiry and a background cleanup goroutine (`cleanupLoop`, line 200). There is no network client, no connection string, no Redis import anywhere in the package — entries live in the process's heap. So the "Redis connection … is configured" premise does not hold; nothing connects to Redis.

- **Where the cache is "configured":** in `Store.New`, store/store.go:38–53. The config is hardcoded (not env/DSN-driven): `cache.Config{DefaultTTL: 10*time.Minute, CleanupInterval: 5*time.Minute, MaxItems: 1000}` (store/store.go:40–45). Three separate in-memory caches are constructed from it — `instanceSettingCache`, `userCache`, `userSettingCache` (store/store.go:51–53). This is the closest analogue to what the question calls "connection configuration," but it's just struct initialization for an embedded map, not a network endpoint.

- **TTL for user entries:** the user cache (`store/store.go:28`, `userCache`) is written exclusively via the default-TTL `Set(...)` call — never `SetWithTTL` — at store/user.go:98, :122, :132, :143, and :167. `Cache.Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (store/cache/cache.go:93–95). Since that `DefaultTTL` is `10 * time.Minute` (store/store.go:41), **user entries expire 10 minutes after they are written.** Expiry is enforced lazily on `Get` (store/cache/cache.go:135) and swept every 5 minutes by the cleanup loop (`CleanupInterval`). Entries are also proactively removed on user deletion (`deleteUserCache`, store/user_delete.go:40).

So: no Redis to point at; the user-entry TTL is 10 minutes, set as the hardcoded `DefaultTTL` in `store/store.go:41` and applied through the in-memory cache in `store/cache/cache.go`.
