**Premise correction: neither. The webhook delivery workers do not consume from any external message broker — there is no NATS, no RabbitMQ, no AMQP/Kafka/pub-sub anywhere in this codebase, and therefore no broker-declared queue.**

Evidence for the negative: a case-insensitive search across all 343 Go files for `nats|rabbitmq|amqp|streadway|message broker` returned no matches, and `go.mod` contains no broker client dependency (`nats|rabbit|amqp|kafka|pubsub` → no matches). So there is no external queue to declare and nowhere it could be declared.

**Actual mechanism** (all in `internal/webhook/webhook.go`):

The "queue" is an **in-process, in-memory Go channel** — a bounded buffered channel of webhook payloads:
- Declared as `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — internal/webhook/webhook.go:39. That's the entire "queue": a 128-slot channel living in the server process's memory, not a broker topic/exchange.
- **Workers**: a package `init()` spawns a fixed pool of 4 goroutines, each ranging over that channel and delivering via `Post` — internal/webhook/webhook.go:42–54. These are the "delivery workers"; they consume from the local channel, not from a broker.
- **Producer**: `PostAsync` enqueues onto the channel with a non-blocking `select`, dropping (with a warning log) if the buffer is full rather than blocking — internal/webhook/webhook.go:184–196. Callers are the memo lifecycle handlers (create/update/delete/comment) traced earlier.
- **Delivery**: each worker calls `Post` (internal/webhook/webhook.go:120), which issues the outbound HTTP POST via the SSRF-guarded `safeClient` (line 152).

So the design is entirely intra-process: producers push webhook payloads onto a buffered channel, and four worker goroutines drain it and make the HTTP calls. There is no message-broker layer, no durable queue, and no cross-process delivery guarantee — if the process restarts, anything still buffered in `asyncPostQueue` is lost.
