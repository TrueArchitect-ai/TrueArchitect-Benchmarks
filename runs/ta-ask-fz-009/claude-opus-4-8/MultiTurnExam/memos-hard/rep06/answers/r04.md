**Premise correction:** Neither. The webhook delivery workers do not consume from any external message broker — there is no NATS, no RabbitMQ, and no queue *declared* in a broker at all. A full-tree search for `nats`, `rabbitmq`, `amqp`, `kafka`, and `broker` across all 343 Go files returns zero matches. No broker client is imported or configured anywhere.

**Actual mechanism:** Webhook delivery uses an **in-process buffered Go channel** as its queue, entirely inside the server process:

- **The queue** is a package-level buffered channel with capacity 128, declared at `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`. That's the only "queue declaration" — an in-memory channel, not a broker-side queue.
- **The workers** are 4 goroutines started in the package's `init()` (`internal/webhook/webhook.go:42-54`), each ranging over `asyncPostQueue` and calling `webhook.Post` to perform the actual outbound HTTP request (the SSRF-guarded delivery from h02, `webhook.go:120`).
- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184`), which non-blockingly enqueues onto the channel with a `select`/`default`; if the buffer is full it **drops** the delivery and logs a warning (`webhook.go:189-195`). This is the `PostAsync` invoked by the memo-service dispatch helpers (from h06).

So the design is a bounded in-memory producer/consumer within one process — messages are lost on drop or restart, with no durable broker, no persistence, and no cross-process queue. The choice "NATS or RabbitMQ" is a false premise; the answer is an internal channel declared at `internal/webhook/webhook.go:39`.
