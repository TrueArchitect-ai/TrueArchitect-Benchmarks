**Premise correction:** There is no Redis anywhere in this codebase — a search for `redis` across all 1042 files returns zero matches. The cache layer is not backed by Redis (or any external cache server); it is an **in-process, in-memory cache** living in the Go process itself.

**Actual mechanism:**

- The cache implementation is `store/cache/cache.go` — a plain in-memory map (`cache.Cache`, satisfying `cache.Interface`) with a background cleanup goroutine, not a network client. There's no connection string, host, or port to configure; nothing "connects" anywhere.

- The store holds three of these caches as struct fields, including the user cache: `userCache *cache.Cache` at `store/store.go:28`. They're constructed in `store.New` with a single shared config (`store/store.go:40-53`):
  ```
  DefaultTTL:      10 * time.Minute
  CleanupInterval: 5 * time.Minute
  MaxItems:        1000
  ```

- **TTL for user entries:** user records are written via `s.userCache.Set(...)` (e.g. `store/user.go:98, 122, 132, 143, 167`). `Set` uses the cache's default TTL (see `cache.Interface.Set`, `store/cache/cache.go:12-13`), and no `SetWithTTL` override is used for users — so user entries expire after the **default 10 minutes** (`store/store.go:41`), with expired items swept every 5 minutes by the cleanup goroutine. Entries are also proactively invalidated on user deletion via `deleteUserCache` → `userCache.Delete` (`store/user_delete.go:39-40`).

So: no Redis and no external configuration point; user entries are held in an in-memory cache with a 10-minute default TTL configured in `store/store.go`.
