**Premise correction:** There is no Redis. The cache layer is an in-process, in-memory cache — a Go struct (`cache.Cache`) backed by a `sync.Map` with per-item expiration, defined entirely in `store/cache/cache.go` (`store/cache/cache.go:66`). There is no Redis client, connection string, or config anywhere in it (the package imports only `context`, `sync`, `sync/atomic`, `time` — `store/cache/cache.go:3-8`), so there is nothing to "connect" to and no external server. It is purely local to the running process, which is why `Store.Close` just stops the cleanup goroutines rather than closing a network connection (store/store.go:74-76).

**Actual mechanism:**

- **Where it's "configured":** In `store.New`, which builds a `cache.Config` and constructs three sibling caches — including the user cache — with that config (store/store.go:40-52): `userCache: cache.New(cacheConfig)`. The config values are `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (store/store.go:41-43). These match the package defaults in `cache.DefaultConfig` (store/cache/cache.go:57-64).

- **TTL for user entries:** User entries get the **default TTL of 10 minutes.** Every user cache write goes through `s.userCache.Set(...)` (e.g. store/user.go:98, :122, :132, :143, :167), and `Cache.Set` applies `c.config.DefaultTTL` (store/cache/cache.go:93-94) — which for this cache is the 10-minute value from store.go:41. Nothing in the user paths calls `SetWithTTL`, so no custom TTL overrides it. Expiration is enforced on read (store/cache/cache.go:135) and swept every 5 minutes by the cleanup loop (store/cache/cache.go:200-215); entries are also explicitly invalidated on user deletion via `userCache.Delete` (store/user_delete.go:40).

So: the "Redis connection" doesn't exist — it's a local TTL map configured in `store/store.go:40`, and user entries live for 10 minutes.
