**Premise correction:** Neither. The webhook delivery workers do not consume from any external message broker — there is no NATS, no RabbitMQ, and no message-broker infrastructure in this codebase at all. A case-insensitive search for `nats`, `rabbitmq`, `amqp`, `streadway`, `kafka`, `broker` across all 343 Go files returns zero matches, and `go.mod` has no such dependency. So there is no external queue to "declare."

**Actual mechanism:** The webhook "queue" is an in-process, bounded Go channel, entirely local to the running server:

- **Declaration:** `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`. It's a buffered channel with capacity 128, a package-level variable, not a broker topic/exchange.
- **Workers:** In `init()` the package spawns 4 goroutines that range over that channel and call `Post` for each payload — `internal/webhook/webhook.go:42-55` (`for range 4 { go func() { for payload := range asyncPostQueue { … Post(payload) … } }() }`).
- **Producer:** `PostAsync` (`internal/webhook/webhook.go:184`) does a non-blocking send onto the channel; if the buffer is full it drops the dispatch and logs a warning (`internal/webhook/webhook.go:189-195`) rather than blocking or persisting.

Consequences worth noting: because the queue is just an in-memory channel, it is per-process and non-durable — pending webhooks are lost on restart, there's no cross-instance fan-out, and the 128-slot buffer plus drop-on-full behavior is the only backpressure. If you were expecting broker-backed delivery (durability, retries, multiple consumers), that does not exist here.
