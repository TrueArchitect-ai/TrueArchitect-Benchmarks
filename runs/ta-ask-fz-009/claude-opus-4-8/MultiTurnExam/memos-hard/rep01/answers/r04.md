**Premise correction: neither — there is no external message broker (NATS, RabbitMQ, or otherwise) in this codebase.** A case-insensitive search across all 343 Go files for `nats`, `rabbitmq`, `amqp`, `kafka`, `broker`, and `streadway` (the classic Go AMQP client) returns zero matches. There is no broker dependency, no connection, and no queue *declared* anywhere, because none is used.

**Actual mechanism:** Webhook delivery is done with an **in-process buffered Go channel and a fixed pool of goroutine workers**, all inside `internal/webhook/webhook.go`:

- The "queue" is a plain buffered channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39` (capacity 128, in-memory only).
- The "workers" are 4 goroutines started in the package `init()`, each ranging over that channel and calling `Post` for every payload: `internal/webhook/webhook.go:42–55` (`for range 4 { go func() { for payload := range asyncPostQueue { ... Post(payload) } }() }`).
- Producers enqueue via `PostAsync`, a non-blocking send with a `default` drop path when the buffer is full: `internal/webhook/webhook.go:184–196`. This is how the RPC handlers (traced in h06 via `dispatchMemoRelatedWebhook`) hand work to the workers.
- Each worker's actual delivery is the synchronous `Post` (`internal/webhook/webhook.go:120`), which issues the outbound HTTP POST via `safeClient.Do` (`internal/webhook/webhook.go:152`).

So the delivery pipeline is entirely process-local — a bounded channel (`asyncPostQueue`, `webhook.go:39`) drained by 4 goroutines (`webhook.go:42`). Because it lives in memory, it has the usual trade-offs: queued webhooks are lost on process restart, and overflow is silently dropped with a warning rather than back-pressured (`webhook.go:191–194`). There is no broker to point at and no queue declaration to cite beyond that channel.
