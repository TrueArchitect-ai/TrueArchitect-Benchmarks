**Premise correction:** There is no Redis anywhere in this codebase. A repository-wide search for `redis`/`Redis`/`go-redis` across all 343 Go files returns zero matches — the cache layer is **not** backed by Redis and there is no Redis connection to configure.

**Actual mechanism:** The cache is a self-contained, **in-process in-memory** cache implemented in pure Go at `store/cache/cache.go`. `Cache` (store/cache/cache.go:66) stores items in a `sync.Map` with per-item expiration timestamps, and a background `cleanupLoop` goroutine (store/cache/cache.go:200) evicts expired entries on a ticker. There's no external connection, host/port, or client — nothing to "configure" beyond the in-Go `cache.Config`.

**Where it's "configured":** the store constructs three of these caches — including the user cache — in `store.New` (store/store.go:38), all sharing one hard-coded `cache.Config` literal at **store/store.go:40-45**: `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`. (This matches the package-level `DefaultConfig`, store/cache/cache.go:57.)

**TTL for user entries:** **10 minutes.** The user cache (`userCache`, store/store.go:52) is populated via the plain `Set` method (e.g. in `Store.ListUsers`/`GetUser`, store/user.go:143,167), and `Set` applies the cache's `DefaultTTL` (store/cache/cache.go:94) — i.e. the 10-minute value from the config above. No user-specific `SetWithTTL` override is used, so user entries expire 10 minutes after they're written.
