**Premise correction: neither. The webhook delivery workers do not consume from any external message broker — there is no NATS, no RabbitMQ (nor AMQP, Kafka, or any broker) in this codebase.** A repository-wide search for `nats`, `rabbitmq`, `amqp`, `kafka`, `broker` across all 343 Go files returns zero matches, and there's no such queue declaration to point to.

**Actual mechanism:** webhook delivery is dispatched through an **in-process Go channel with a fixed goroutine worker pool**, all inside `internal/webhook/webhook.go`:

- The "queue" is a buffered in-memory channel declared at `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — capacity 128, process-local, lost on restart.
- The "workers" are 4 goroutines started in the package `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post` for every payload.
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), a non-blocking `select` send: if the channel is full it drops the dispatch and logs a warning (webhook.go:191-195) rather than blocking or persisting.
- `Post` (`internal/webhook/webhook.go:120`) is where each worker performs the actual outbound HTTP `POST` (`safeClient.Do`, webhook.go:152).

So the design is a single-process fan-out (channel → 4 workers), not a broker-backed queue. There is no durable queue, no cross-process consumption, and nothing to declare in a broker.
