**Actual mechanism:** Webhook delivery is fully in-process, backed by a buffered Go channel and a fixed pool of goroutine workers — all inside `internal/webhook/webhook.go`:

- **The "queue"** is a package-level buffered channel, `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`. That's the entire queue "declaration": an in-memory channel with capacity 128, not a broker topic/exchange.
- **The workers** are 4 goroutines started in the package `init()` (`internal/webhook/webhook.go:42‑54`), each ranging over `asyncPostQueue` and calling `Post` (the actual HTTP delivery, `internal/webhook/webhook.go:120`).
- **Producers** enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking send onto the channel and drops the payload with a warning if the buffer is full (`internal/webhook/webhook.go:189‑195`) — there is no durable broker, no persistence, and no external consumer.

So the dispatch is a same-process channel-plus-worker-pool pattern; delivery does not survive a restart and involves no message broker. If broker-backed durability were wanted, it would have to be added — today it is `chan *WebhookRequestPayload` in `internal/webhook/webhook.go`.
