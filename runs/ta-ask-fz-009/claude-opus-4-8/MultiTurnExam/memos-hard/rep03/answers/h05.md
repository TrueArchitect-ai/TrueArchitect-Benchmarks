**Mechanism: explicit Go code.** User deletion removes reactions in the application's `DeleteUser` transaction; there is no database-level cascade to fall back on.

Evidence I checked:

- **Go deletion path** — `store/db/mysql/user_delete.go`. `DeleteUser` (line 29) opens a transaction and calls `deleteUserTargetsTx` (line 92), which explicitly deletes reactions in two ways:
  - `deleteReactionsByContentIDsTx` (line 96, defined line 417) — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions attached to the deleted user's memos.
  - `deleteReactionsByCreatorTx` (line 102, defined line 437) — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user authored on anyone's content.
  - The same file layout exists per-driver: `store/db/postgres/user_delete.go` and `store/db/sqlite/user_delete.go` (confirmed earlier by the directory listing and the driver-parallel `attachmentIDsFromList` helpers).

- **Database schema** — the `reaction` table definitions carry no foreign key and no `ON DELETE CASCADE` on `creator_id` or `content_id`, so the DB does not remove them on its own:
  - `store/migration/mysql/LATEST.sql:91‑98` (and `store/migration/mysql/0.20/00__reaction.sql`)
  - `store/migration/postgres/LATEST.sql:91‑98` (and `store/migration/postgres/0.20/00__reaction.sql`)
  - `store/migration/sqlite/0.20/00__reaction.sql:2‑9`
  
  Each declares `creator_id`/`content_id` as plain `NOT NULL` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no referential action.

So removal is done entirely by explicit Go statements in the per-driver `user_delete.go` files; the schema provides no cascade rule that would do it otherwise.
