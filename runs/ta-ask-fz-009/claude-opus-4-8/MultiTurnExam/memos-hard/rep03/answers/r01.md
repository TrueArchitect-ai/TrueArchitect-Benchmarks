**Premise correction:** There is no Redis in this codebase. A case-insensitive search for `redis` across all 343 Go files returns zero matches — the cache layer is **not** backed by Redis and there is no external cache connection to configure. So "where is the Redis connection configured" has no answer because that mechanism doesn't exist.

**Actual mechanism:** The cache is an in-process, in-memory implementation, `cache.Cache` in `store/cache/cache.go` — a `map`-backed store guarded by a mutex, with a background cleanup goroutine that evicts expired entries (`store/cache/cache.go`, interface at lines 10‑32, `Config` at 41‑54). It's constructed per-`Store`, not connected to any server:

- **Where it's "configured":** in `Store.New` at `store/store.go:38‑58`. It builds one `cache.Config` (`DefaultTTL: 10m`, `CleanupInterval: 5m`, `MaxItems: 1000`) and instantiates three in-memory caches with it — `instanceSettingCache`, **`userCache`**, and `userSettingCache` (`store/store.go:51‑53`). There is no host/port/DSN because it's local memory. (The same defaults are echoed in `cache.DefaultConfig`, `store/cache/cache.go:57‑60`.)

- **TTL for user entries:** **10 minutes.** User rows are cached via `s.userCache.Set(...)` (e.g. `store/user.go:98,122,132,167`), and `Set` applies the cache's `DefaultTTL` (`cache.Interface.Set`, `store/cache/cache.go:12‑13`) — which for `userCache` is the `10 * time.Minute` configured in `store/store.go:41`. No user write path uses `SetWithTTL`, so there is no per-user override; expired entries are reclaimed by the cleanup goroutine every 5 minutes, and entries are also invalidated explicitly on user delete (`s.userCache.Delete`, `store/user_delete.go:40`).
