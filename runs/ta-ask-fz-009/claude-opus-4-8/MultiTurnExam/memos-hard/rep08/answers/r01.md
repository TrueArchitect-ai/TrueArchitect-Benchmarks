**Premise correction:** There is no Redis. The cache layer is not backed by Redis (or any external cache server) — a search across all 343 Go files finds zero occurrences of "redis." So there is no "Redis connection" to configure, and the TTL is not a Redis expiry.

**Actual mechanism:** The cache is a purely **in-process, in-memory** store implemented in `store/cache/cache.go` — a `map`-backed `Cache` type guarded by a mutex, with per-item `expiration time.Time` and a background cleanup goroutine (there's an `Interface` at `store/cache/cache.go:11` and the concrete `Cache` with `Set`/`SetWithTTL`/`Get`). No network client, no connection setup.

- **Where it's "configured":** in `store.New`, which builds a `cache.Config` and instantiates three separate in-memory caches — including the user cache — via `cache.New(cacheConfig)`:
  - config: `store/store.go:40–44`
  - `userCache: cache.New(cacheConfig)`: `store/store.go:52`
  (There is also a `cache.DefaultConfig()` with identical values at `store/cache/cache.go:57`.)

- **TTL for user entries:** User rows are cached via `s.userCache.Set(...)` (e.g. `store/user.go:98, 122, 132, 143, 167`). `Set` uses the cache's **default TTL** (`Set` → `SetWithTTL(..., c.config.DefaultTTL)`, `store/cache/cache.go:93–94`), and none of the user call sites use a custom TTL. That default is **10 minutes** (`DefaultTTL: 10 * time.Minute`, `store/store.go:41`), with a **5-minute** cleanup sweep (`CleanupInterval: 5 * time.Minute`) and a 1000-item cap. Entries are also invalidated explicitly on user deletion (`userCache.Delete`, `store/user_delete.go:40`).

So: **user cache entries live ~10 minutes in an in-memory cache**, evicted lazily on read past expiry and swept every 5 minutes — there is no Redis involved.
