**Premise correction: neither.** There is no message broker involved in webhook delivery — no NATS, no RabbitMQ (and no AMQP/Kafka either). A search across all 343 Go files finds zero occurrences of `nats`/`rabbitmq`/`amqp`/`kafka`, and `go.mod` declares no such dependency. So there is no externally-declared queue to point to.

**Actual mechanism:** The webhook workers consume from an **in-process, buffered Go channel** — not a broker. In `internal/webhook/webhook.go`:

- The "queue" is a bounded in-memory channel declared at package scope: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39` (buffer capacity 128).
- The "workers" are **4 goroutines** spawned in the package `init()` (`internal/webhook/webhook.go:42–43`), each ranging over that channel (`for payload := range asyncPostQueue`, `:45`) and calling `Post` to perform the actual outbound HTTP delivery (`:46`).
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking send onto `asyncPostQueue` and **drops** the payload with a warning if the buffer is full (the `select { case asyncPostQueue <- ...: default: ... }` pattern) — there's no durability or redelivery, which is exactly what you'd expect from an in-memory channel rather than a broker-backed queue.

So the whole fan-out is a single-process channel + goroutine pool living entirely inside the `webhook` package; nothing crosses a network to a broker, and there is no queue declaration outside this file.
