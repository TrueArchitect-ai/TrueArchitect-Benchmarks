q29.

**Answer:** `web/src/connect.ts`; short-lived access tokens (Bearer JWT) + refresh tokens (HTTP-only cookie); `server/auth`

**How it works:**

- **Interceptor location:** The Connect RPC `authInterceptor` lives in `web/src/connect.ts` (defined at line 156, wired into the transport at line 188). All frontend service clients (memo, user, auth, attachment, etc.) share this transport.

- **Tokens it manages — two kinds:**
  1. **Access token** — kept in memory via `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`), attached to every request as an `Authorization: Bearer <token>` header (`setAuthorizationHeader`, connect.ts:97–100). The interceptor does a preflight refresh if the token is expired or near expiry (`isTokenExpired` with `REQUEST_TOKEN_EXPIRY_BUFFER_MS`, connect.ts:140), and a reactive refresh-and-retry (once, guarded by an `X-Retry` header) on `Unauthenticated` errors (connect.ts:161–177).
  2. **Refresh token** — an HTTP-only cookie sent automatically because the transport uses `fetch` with `credentials: "include"` (connect.ts:57–62). Refreshes go through a dedicated `refreshTransport` with **no** auth interceptor to avoid recursion (connect.ts:64–72), deduplicated by `tokenRefreshManager` (connect.ts:30–51). If refresh fails, the user is redirected via `redirectOnAuthFailure()`.

- **Backend validation:** the `server/auth` package. Its `Authenticator` validates the credentials: `AuthenticateByAccessTokenV2` (server/auth/authenticator.go:41), `AuthenticateByRefreshToken` (:61), and `AuthenticateByPAT` (:102), with bearer-token parsing in `server/auth/extract.go` and JWT generation/verification in `server/auth/token.go`. The server-side entry point is the Go `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208–231`, which reads the `Authorization` header and delegates to the shared `Authorizer` → `auth.Authenticate` (server/auth/authenticator.go:213), then places the result into the request context via `auth.ApplyToContext`.
