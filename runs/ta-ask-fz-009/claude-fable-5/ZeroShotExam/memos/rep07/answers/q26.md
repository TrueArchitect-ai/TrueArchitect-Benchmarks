**Tables affected: `memo`, `memo_relation`, `attachment`**

The write path when `DeleteMemo` runs:

1. **API layer** — `APIV1Service.DeleteMemo` (server/router/api/v1/memo_service.go:518) first deletes all comment memos of the target (loops calling `store.DeleteMemo` per comment relation, lines 567–577), then deletes the memo itself (line 580). All actual writes go through the store layer.

2. **Store layer cascade** — `Store.DeleteMemo` (store/memo.go:140–159) explicitly:
   - Deletes rows from **`memo_relation`** where the memo is source *or* target (`driver.DeleteMemoRelation`, lines 142–147)
   - Lists and deletes linked rows in **`attachment`** (`Store.DeleteAttachment` per attachment, lines 148–157) — the SQL is `DELETE FROM attachment WHERE id = ?` (store/db/sqlite/attachment.go:212)
   - Finally deletes the row from **`memo`** — `DELETE FROM memo WHERE id = ?` (store/db/sqlite/memo.go:237–239)

Note: the API handler *reads* the `reaction` table (`ListReactions`, memo_service.go:545) but only to build the webhook payload — there is no explicit reaction deletion in this path, so `reaction` is not written. Same for `webhook`/SSE, which are read/notify only.
