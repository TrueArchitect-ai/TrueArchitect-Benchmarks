**Interceptor path:** `web/src/connect.ts` — `authInterceptor` (line 156), attached to the Connect transport for all service clients (line 188).

**How it works:** For every RPC, the interceptor obtains an access token via `getRequestToken()` (web/src/connect.ts:124) and sets the `Authorization: Bearer <token>` header (line 97–100). It manages two token kinds:

- **Short-lived JWT access token** — held in memory + localStorage (`memos_access_token`, `web/src/auth-state.ts:3–6`), attached as the Bearer header.
- **Refresh token** — an HTTP-only cookie, sent automatically via `credentials: "include"` (`fetchWithCredentials`, connect.ts:57) to `AuthService.refreshToken` on a dedicated interceptor-free transport (connect.ts:65–83) to avoid recursion. Refresh happens proactively when the access token is near expiry, and reactively on a `Code.Unauthenticated` error with one retry (marked via the `X-Retry` header); a failed refresh redirects to login (connect.ts:161–177). A `tokenRefreshManager` deduplicates concurrent refreshes (connect.ts:30–51).

**Backend validation:** `server/auth` — the `Authenticator` (server/auth/authenticator.go) parses/validates JWT access tokens (`AuthenticateByAccessTokenV2`, line 41), refresh tokens against the DB (`AuthenticateByRefreshToken`, line 61), and personal access tokens (`resolveBearer`, line 141), with JWT logic in `server/auth/token.go`. It's wired into the request path via the Connect `AuthInterceptor` → `Authorizer` in `server/router/api/v1/connect_interceptors.go:217–230` and `server/router/api/v1/authz.go:26`.

**Answer format:** `web/src/connect.ts`; short-lived JWT access token (Bearer header) + refresh token (HTTP-only cookie); `server/auth` (validated behind `server/router/api/v1`'s AuthInterceptor/Authorizer).
