**Tables: `memo`, `memo_relation`, `attachment`** (plus `memo_share` via schema-level `ON DELETE CASCADE`, not Go code).

Breakdown:

- **`memo`** — directly. The driver's `DeleteMemo` runs `DELETE FROM memo WHERE id = ?` (store/db/sqlite/memo.go:237–239, with mysql/postgres equivalents). Note that the API-layer `DeleteMemo` (server/router/api/v1/memo_service.go:518) first deletes all comment memos of the memo (memo_service.go:567–577), so multiple `memo` rows can go.
- **`memo_relation`** — explicit cascade code in `store.Store.DeleteMemo` (store/memo.go:140–147): it calls `DeleteMemoRelation` twice, cleaning rows where the memo is either `memo_id` or `related_memo_id` (`DELETE FROM memo_relation ...`, store/db/sqlite/memo_relation.go:149).
- **`attachment`** — explicit cascade code in the same function (store/memo.go:148–157): it lists attachments by `MemoID` and calls `DeleteAttachment` for each, which executes `DELETE FROM attachment WHERE id = ?` (store/db/sqlite/attachment.go:212) and also removes the underlying storage object (store/attachment.go:141).
- **`memo_share`** — affected, but by a **database-level** foreign-key cascade, not Go code: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/sqlite/LATEST.sql:109, introduced in store/migration/sqlite/0.27/04__memo_share.sql). Include it if "explicit cascade" covers schema declarations.

Not affected: `reaction` — the API handler lists reactions (memo_service.go:545–550) only to build the deleted-webhook payload; no delete against the `reaction` table occurs in this path.
