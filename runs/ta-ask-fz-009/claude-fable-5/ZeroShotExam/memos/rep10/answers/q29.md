**Interceptor path:** `web/src/connect.ts` — the `authInterceptor` (line 156) is a Connect RPC `Interceptor` wired into the shared transport (line 188) used by all service clients.

**Token kinds it manages:**
- **Access token** — a short-lived JWT attached as `Authorization: Bearer <token>` on every request (`setAuthorizationHeader`, web/src/connect.ts:97-99), read/written via `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`). The interceptor does preflight refresh when the token is near expiry (`getRequestToken`, connect.ts:124-150).
- **Refresh token** — held in an HTTP cookie sent via `credentials: "include"` (connect.ts:57-62). On a missing/expired token or an `Unauthenticated` (401) response, the interceptor calls `AuthService.refreshToken` over a separate no-interceptor transport (`refreshTransport`, connect.ts:65-72) to mint a new access token, deduplicated through `tokenRefreshManager` (connect.ts:30-51), then retries once with an `X-Retry` header before redirecting to login.

**Backend validation:** the `server/auth` package. The server-side Connect `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208-231`) pulls the `Authorization` header and delegates to the shared `Authorizer` (`server/router/api/v1/authz.go:26-46`), which wraps `auth.NewAuthenticator` from `server/auth/authenticator.go`. That authenticator validates short-lived JWT access tokens (`AuthenticateByAccessTokenV2` → `ParseAccessTokenV2` in `server/auth/token.go`), refresh tokens (with a database revocation check), and long-lived Personal Access Tokens (PATs).
