**Engine:** CEL (Common Expression Language, via `github.com/google/cel-go` — `go.mod:13`), wrapped in the project's own filter engine at **`internal/filter/`** (`engine.go`, `parser.go`, `ir.go`, `render.go`, `schema.go`).

**Mechanism:** `ListMemos` (`server/router/api/v1/memo_service.go:178`) passes the filter string through to the store; the engine compiles it with a CEL environment (`Engine.Compile`, `internal/filter/engine.go:48-71`), lowers the CEL AST into a dialect-agnostic condition tree (`buildCondition` in `parser.go` / `ir.go`), and each store driver renders that tree into a dialect-specific SQL fragment plus args by calling `filter.AppendConditions(..., filter.DialectSQLite/MySQL/Postgres, ...)` → `Program.Render` → `newRenderer` in `render.go` — see `store/db/sqlite/memo.go:57-61`, `store/db/mysql/memo.go:65-69`, `store/db/postgres/memo.go:54-58`.

So: one CEL parse into an internal IR, three dialect renderers (SQLite/MySQL/Postgres) that turn the same condition tree into WHERE-clause SQL for each backend.
