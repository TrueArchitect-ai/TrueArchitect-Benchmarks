**Tables affected: `memo`, `memo_relation`, `attachment`**

Cascade path when `DeleteMemo` runs:

1. **`memo_relation`** — `store.Store.DeleteMemo` (store/memo.go:140–147) explicitly calls `driver.DeleteMemoRelation` twice, deleting rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`).
2. **`attachment`** — store/memo.go:149–157 lists attachments linked to the memo and deletes each via `Store.DeleteAttachment` (store/attachment.go:132–149), which removes the row via `driver.DeleteAttachment` (and also deletes the backing storage object, which isn't a table).
3. **`memo`** — the final `driver.DeleteMemo` call (store/memo.go:158) issues `DELETE FROM memo WHERE id = ?` (e.g. store/db/sqlite/memo.go:237–248; same pattern in the mysql/postgres drivers).

Additionally, the API layer (`APIV1Service.DeleteMemo`, server/router/api/v1/memo_service.go:567–577) first finds comment memos (`memo_relation` type COMMENT) and recursively calls `Store.DeleteMemo` on each — so comment rows in the same three tables are cascaded too.

Note: the API handler **lists** reactions (memo_service.go:545–550), but only to build the webhook payload — there is no explicit delete of the `reaction` table in this path, so it is not affected by cascade code.
