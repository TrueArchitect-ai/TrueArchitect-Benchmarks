**Interceptor path; token kinds; backend package path:** `web/src/connect.ts` (the `authInterceptor`, line 156); short-lived **access tokens** (sent as `Authorization: Bearer …`) refreshed via a **refresh token** held in an HTTP-only cookie; validated by **`server/auth`** (`github.com/usememos/memos/server/auth`).

How it fits together:

1. **Frontend interceptor** — `authInterceptor` in `web/src/connect.ts:156` is installed on the Connect transport shared by all service clients (`web/src/connect.ts:184-189`). Per request it:
   - Fetches the current access token via `getRequestToken()` (line 124), which does a **preflight refresh** if the token is expired or near expiry (using `isTokenExpired`/`REQUEST_TOKEN_EXPIRY_BUFFER_MS` from `web/src/auth-state.ts`), then sets `Authorization: Bearer <token>`.
   - On a `Code.Unauthenticated` response, it does a **reactive refresh + one retry** (marked with an `X-Retry` header), and redirects to login if the refresh fails.
   - Refresh calls `AuthService.refreshToken` over a **separate transport with no interceptors** (`refreshTransport`, line 65) to prevent recursion; the refresh token itself travels as a cookie because all fetches use `credentials: "include"` (`fetchWithCredentials`, line 57). Concurrent refreshes are deduplicated by `tokenRefreshManager` (line 30).

2. **Token kinds managed:** the access token (received from `refreshToken`, stored via `setAccessToken` with its expiry) and, indirectly, the refresh-token cookie the browser sends on refresh calls. Server-side, credentials can also be personal access tokens (PATs) — noted in the `CheckAccess` policy comment (`server/router/api/v1/authz.go:53`).

3. **Backend validation** — the Connect `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208-231`) reads the `Authorization` header and delegates to the shared `Authorizer` (`server/router/api/v1/authz.go:26`), whose `Authenticate` wraps `auth.NewAuthenticator(store, secret)` from the **`server/auth`** package (`authenticator.go`, `token.go` do the actual token validation). The same `Authorizer` is shared with the gRPC-Gateway path so both transports enforce identical rules (`authz.go:20-22`).
