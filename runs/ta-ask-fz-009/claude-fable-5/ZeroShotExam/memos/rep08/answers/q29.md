**Interceptor:** `authInterceptor` in `web/src/connect.ts` (defined at line 156, attached to the Connect transport at line 188). On each RPC it obtains an access token via `getRequestToken()` and sets the `Authorization: Bearer <token>` header (`setAuthorizationHeader`, connect.ts:97-99). On a 401 (`Code.Unauthenticated`) it refreshes once and retries (marking the retry with the `X-Retry` header), redirecting to login if refresh fails.

**Tokens it manages:**
- **Access token** — short-lived bearer token held in memory (`web/src/auth-state.ts`: `getAccessToken`/`setAccessToken`/`isTokenExpired`), sent as `Authorization: Bearer …`; the interceptor does a preflight refresh when it's near expiry (connect.ts:140).
- **Refresh token** — an HTTP-only cookie sent implicitly via `credentials: "include"` (`fetchWithCredentials`, connect.ts:57-62); a separate interceptor-free `refreshTransport` calls `AuthService.refreshToken` to mint a new access token (connect.ts:65-83), with concurrent refreshes deduplicated by `tokenRefreshManager`.

**Backend validation:** the server-side `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208`) reads the `Authorization` header and delegates to the `Authorizer` (`server/router/api/v1/authz.go:44`), which in turn delegates to the shared auth package — **`server/auth`** (`authenticator.go`, `token.go`) — the package that actually validates the tokens and produces the `auth.AuthResult` applied to the request context.

**Answer:** `web/src/connect.ts` (authInterceptor); access token (in-memory bearer) + refresh token (HTTP-only cookie); `server/auth`.
