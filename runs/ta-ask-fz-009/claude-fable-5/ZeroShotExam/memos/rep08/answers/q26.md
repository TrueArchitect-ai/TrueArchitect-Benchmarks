**Tables affected by `DeleteMemo`: `memo`, `memo_relation`, `attachment`, and `memo_share`.**

The delete flow spans two layers:

**API layer** — `APIV1Service.DeleteMemo` (server/router/api/v1/memo_service.go:518):
- Deletes comment memos first: lists `MemoRelationComment` relations and calls `store.DeleteMemo` for each comment (memo_service.go:567–577), then deletes the memo itself (memo_service.go:580) → **`memo`** table (parent row + comment rows).

**Store layer** — `Store.DeleteMemo` (store/memo.go:140) runs explicit cascade code before the memo row delete:
- **`memo_relation`** — `driver.DeleteMemoRelation` twice, for rows where the memo is source (`memo_id`) or target (`related_memo_id`) (store/memo.go:142–147; SQL: `DELETE FROM memo_relation ...` in store/db/sqlite/memo_relation.go:137).
- **`attachment`** — lists attachments by `MemoID` and calls `Store.DeleteAttachment` for each (store/memo.go:149–157; SQL: `DELETE FROM attachment WHERE id = ?` in store/db/sqlite/attachment.go:211–212). This also deletes attachment blob storage (store/attachment.go:141), but that's filesystem/S3, not a table.
- **`memo`** — finally `driver.DeleteMemo` (`DELETE FROM memo WHERE id = ?`, store/db/sqlite/memo.go:237–239, same in postgres/mysql).

**Database-level cascade** — **`memo_share`** is the only table in the current schema with an FK cascade on memo: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/sqlite/LATEST.sql:109; introduced in store/migration/sqlite/0.27/04__memo_share.sql, whose comment says exactly that share grants are cleaned up when the parent memo is deleted).

Note: `reaction` is **not** deleted — the API layer lists reactions (memo_service.go:545) only to build the webhook payload; no delete is issued, and the `reaction` table has no FK cascade in the latest schema.
