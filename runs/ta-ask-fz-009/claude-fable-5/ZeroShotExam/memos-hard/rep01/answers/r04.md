**Premise correction:** Neither. This codebase (Memos) has no message broker at all — the grep for `nats|rabbit|amqp` across the whole repository turned up nothing but README/locale noise, and there is no broker client in the dependency graph. The "webhook delivery workers" are not broker consumers.

**Actual mechanism:** Webhook delivery is entirely in-process, built on a plain buffered Go channel:

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a bounded in-memory channel of capacity 128.
- **Workers:** the package `init()` at `internal/webhook/webhook.go:42-55` spawns **4 goroutines** that `range` over `asyncPostQueue` and call `Post()` (the HTTP dispatch with HMAC signing and an SSRF-safe transport).
- **Producer side:** `PostAsync()` at `internal/webhook/webhook.go:184-196` enqueues non-blockingly — if the channel is full, the payload is **dropped** with a `slog.Warn`, so there's no durability or retry semantics a broker would provide.
- **Callers:** the API layer dispatches via `server/router/api/v1/memo_service_webhooks.go` (e.g., `DispatchMemoCreatedWebhook`), invoked from `memo_service.go` on create/update/delete events.

So the honest architectural characterization is: fire-and-forget, best-effort, in-memory fan-out with bounded backpressure (drop-on-full) — not durable queue consumption from NATS or RabbitMQ.
