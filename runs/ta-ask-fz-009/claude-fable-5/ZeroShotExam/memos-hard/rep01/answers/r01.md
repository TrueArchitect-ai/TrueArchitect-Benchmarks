**Premise correction:** There is no Redis in this codebase. The cache layer is not backed by Redis at all — no Redis client appears in `go.mod` (0 matches), and the cache package is a pure in-process implementation.

**Actual mechanism:**

- The cache layer is an **in-memory, thread-safe cache** built on `sync.Map`, defined in `store/cache/cache.go`. The `Cache` struct (`store/cache/cache.go:67`) implements the `Interface` contract (`store/cache/cache.go:11`) with TTL support, a background cleanup loop, and item-count/size limits — all inside the server process, no external cache service.

- **User entries get the default TTL of 10 minutes.** The user cache is constructed in `store.New` (`store/store.go:38-53`), where `userCache` is created via `cache.New(cacheConfig)` with:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000` (`store/store.go:40-45`)

- User entries are written with `s.userCache.Set(ctx, userCacheKey(user.ID), user)` (e.g., `store/user.go:98`, `:122`, `:167`), and `Set` delegates to `SetWithTTL` using `config.DefaultTTL` (`store/cache/cache.go:93-95`) — so users always get the 10-minute default; no per-entry TTL override is used for them.

Same config also backs the `instanceSettingCache` and `userSettingCache` (`store/store.go:51-53`). If you were expecting Redis (perhaps from another deployment's architecture), this project deliberately keeps caching in-process with bounded size and periodic expiry cleanup instead.
