**Mechanism: explicit Go code** — user deletion runs a single transaction per DB driver that issues `DELETE FROM reaction WHERE creator_id = ?` (plus a second pass removing reactions on the user's own memos by `content_id`). There is no database-level rule; the schema defines no foreign keys or `ON DELETE CASCADE` on the `reaction` table.

**What I checked:**

1. **Delete path (Go):** `Store.DeleteUser` in `store/user.go:171` delegates to the driver. Each driver's `DeleteUser` (`store/db/sqlite/user_delete.go:29`, `store/db/postgres/user_delete.go:29`, `store/db/mysql/user_delete.go:29`) opens a transaction and calls `deleteUserTargetsTx`.

2. **Explicit reaction deletes:** `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92–104`) calls:
   - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — line 96, removes reactions attached to the deleted user's memo tree;
   - `deleteReactionsByCreatorTx(ctx, tx, userID)` — line 102, defined at `store/db/sqlite/user_delete.go:400`: `DELETE FROM reaction WHERE creator_id = ?`. Identical implementations exist for Postgres (`store/db/postgres/user_delete.go:400`) and MySQL (`store/db/mysql/user_delete.go:437`).

3. **Schema (ruling out DB-level cascade):** the `reaction` table definitions in `store/migration/sqlite/LATEST.sql:92`, `store/migration/postgres/LATEST.sql:91`, and `store/migration/mysql/LATEST.sql:91` have only `creator_id INTEGER NOT NULL` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY ... REFERENCES user ... ON DELETE CASCADE`, so nothing at the database level would clean these rows.

4. **Test corroboration:** `store/test/user_delete_test.go:13` (`TestDeleteUserCleansRelatedData`) exercises this cleanup behavior.
