**memo, memo_relation, attachment**

The cascade is explicit in code, not FK constraints:

- **memo_relation** — `Store.DeleteMemo` first deletes relations where the memo is source or target (`store/memo.go:142-147`)
- **attachment** — it then deletes each attachment linked to the memo (`store/memo.go:149-157`, via `Store.DeleteAttachment`, `store/attachment.go:132`, which also removes blob storage)
- **memo** — finally the memo row itself (`store/memo.go:158`, e.g. `store/db/sqlite/memo.go:237-239`); additionally, the API handler deletes all comment memos first — each comment is itself a `memo` row deleted through the same `Store.DeleteMemo` cascade (`server/router/api/v1/memo_service.go:567-577`)

Note: `reaction` and `memo_share` rows are *not* explicitly deleted in this path — the handler only lists reactions for the webhook payload (`memo_service.go:545-550`); I found no reaction/share cleanup in the DeleteMemo flow.
