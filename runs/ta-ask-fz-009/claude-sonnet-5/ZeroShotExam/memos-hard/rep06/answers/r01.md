r01. Premise correction: there is no Redis in this codebase — the cache layer is an in-process, in-memory Go cache, not a Redis-backed one. A repo-wide search for "redis" returned zero matches across 1042 files.

Actual mechanism:
- The cache implementation lives in `store/cache/cache.go` — a thread-safe in-memory map with TTL and max-item eviction (`type Cache struct`, `func New(config Config)`), configured via a `cache.Config{DefaultTTL, CleanupInterval, MaxItems, OnEviction}` struct.
- It's wired up in `store/store.go:38-61` (`func New(driver Driver, profile *profile.Profile) *Store`): the `Store` constructs one `cacheConfig` and instantiates three separate `*cache.Cache` instances from it — `instanceSettingCache`, `userCache`, and `userSettingCache` (declared at `store/store.go:27-29`).
- The default TTL is set at `store/store.go:41`: `DefaultTTL: 10 * time.Minute`, with `CleanupInterval: 5 * time.Minute` and `MaxItems: 1000`. Since `userCache` is built from this same `cacheConfig`, **user entries get a 10-minute TTL** unless a call site overrides it via `SetWithTTL` (the interface exposes both `Set`, which uses `DefaultTTL`, and `SetWithTTL` for a custom duration — `store/cache/cache.go:12-16`).
- User cache entries are populated/invalidated in `store/user.go` (e.g. `s.userCache.Set(ctx, userCacheKey(user.ID), user)` at lines 98, 122, 132, 143, 167) and evicted on delete in `store/user_delete.go:39-40`. All of these use the plain `Set`, so they inherit the 10-minute default TTL — none override it with `SetWithTTL`.
