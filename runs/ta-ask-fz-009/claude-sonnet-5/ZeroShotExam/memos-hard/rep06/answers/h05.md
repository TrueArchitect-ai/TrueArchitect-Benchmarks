**Mechanism: explicit Go code (application-level transaction), not a database-level cascade/trigger.**

When `DeleteUser` runs, the store layer executes an explicit multi-step deletion inside a single DB transaction, and reaction rows are deleted by hand in two passes before the user row itself is removed:

- `store/db/mysql/user_delete.go:92` — `deleteUserTargetsTx` orchestrates the whole delete-user transaction and calls, in order:
  - `deleteReactionsByContentIDsTx` (`store/db/mysql/user_delete.go:417-425`): `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions attached to memos owned by the deleted user (memo content IDs collected earlier via `collectDeleteUserTargets`, `store/db/mysql/user_delete.go:61`).
  - `deleteReactionsByCreatorTx` (`store/db/mysql/user_delete.go:437-440`): `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the deleted user made on other people's content.
  - Only after these (and other cleanup: attachments, memo shares, inbox rows, identities, settings, memo relations, memos) does it call `deleteUserRowTx` to delete the `user` row itself (`store/db/mysql/user_delete.go:123`).

- The identical two-step pattern (content-id based + creator-id based reaction deletes, both run before the user row delete) is duplicated per backend:
  - Postgres: `store/db/postgres/user_delete.go:380` (`deleteReactionsByContentIDsTx`) and `:400` (`deleteReactionsByCreatorTx`), called from `deleteUserTargetsTx` at `store/db/postgres/user_delete.go:92`.
  - SQLite: `store/db/sqlite/user_delete.go:380` and `:400`, called from `deleteUserTargetsTx` at `store/db/sqlite/user_delete.go:92`.

- Entry point: `store.Store.DeleteUser` (`store/user.go:171`) dispatches to the backend-specific `DB.DeleteUser` (`store/db/{mysql,postgres,sqlite}/user_delete.go:29`), which wraps the whole sequence in one `BeginTx`/`Commit` transaction.

I checked the actual `DELETE FROM reaction ...` statements in source (not just the call graph) to confirm they're plain application-issued SQL, and there's no `ON DELETE CASCADE` involved here — the cascade is simulated manually in Go by deleting dependent rows in dependency order (reactions → attachments → memo shares → inbox → identities → settings → memo relations → memos → user), which is why each backend needs its own hand-written `user_delete.go`.
