Trace: browser GET request for another user's avatar image → stored user record.

- `GET /users/:identifier/avatar` route → `FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (registered endpoint per code graph; handles auth check via `Profile.AllowAnonymous`/`getCurrentUser`, then looks up the target user)
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715` (builds `store.FindUser{Username: &identifier}` and calls the store)
- `Store.GetUser` — `store/user.go:148` (checks in-memory `userCache`, falls back to `ListUsers` on miss)
- `Store.ListUsers` — `store/user.go:136` (delegates to the DB driver, populates cache with results)
- `DB.ListUsers` (driver implementation, e.g. SQLite) — `store/db/sqlite/user.go:88` (equivalent implementations also in `store/db/mysql/user.go:84` and `store/db/postgres/user.go:87`) — builds and runs the SQL query against the `user` table, the actual stored data (including `avatar_url`/`AvatarURL` column read back at fileserver.go:192,196 via `parseDataURI`).

So the chain is: `serveUserAvatar` → `getUserByUsername` → `Store.GetUser` → `Store.ListUsers` → driver `ListUsers` (SQL) → users table row, whose `AvatarURL` is decoded as a data URI and streamed back as the image blob (`fileserver.go:196-209`).
