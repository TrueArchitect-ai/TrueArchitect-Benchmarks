Memo-visibility enforcement is duplicated (not centralized) across at least these server surfaces, each with its own visibility check:

enforcement site — server/router/api/v1/memo_service.go:39 (`checkMemoReadAccess`, used by `GetMemo` and for parent-memo checks — gRPC/API memo read path)
enforcement site — server/router/api/v1/memo_service_comments.go:41 (inline visibility check gating `CreateMemoComment`)
enforcement site — server/router/api/v1/reaction_service.go:30-40,83 (inline checks in `ListMemoReactions` / reaction creation)
enforcement site — server/router/api/v1/attachment_service.go:422-454 (`checkAttachmentAccess`, used by `GetAttachment`/attachment blob serving)
enforcement site — server/router/api/v1/memo_attachment_service.go:213-225 (inline visibility check in `ListMemoAttachments`)
enforcement site — server/router/fileserver/fileserver.go:650-704 (`checkAttachmentPermission`, the raw HTTP file-serving surface — separate from the gRPC attachment API, adds share-token fallback)
enforcement site — server/router/rss/rss.go:90,141 (RSS feed query-time filter, restricts to `store.Public` only)
enforcement site — server/router/frontend/frontend.go:150 (sitemap.xml generator, restricts to `store.Public` only)
enforcement site — server/router/api/v1/user_service_notifications.go:302-316 (`canViewerAccessMemo`, gates in-app notification content)
enforcement site — server/notification/email.go:306-320 (`canViewerAccessMemo`, a separately-defined duplicate gating email notification content)
enforcement site — server/router/api/v1/memo_mention_helpers.go:56-89 (`canUserAccessMentionContext`, gates whether an @mention generates a notification)

Note: `user_service_notifications.go` and `email.go` each define their own `canViewerAccessMemo` function with the same PRIVATE/PROTECTED/PUBLIC logic — they are duplicated implementations, not a shared helper, which is itself evidence of the enforcement being scattered rather than centralized.
