Memo-visibility enforcement is re-implemented independently in several places rather than going through one shared gate. Distinct sites:

1. Core Memo API read-access check (`checkMemoReadAccess`) — server/router/api/v1/memo_service.go:39-68
2. Memo comment creation check — server/router/api/v1/memo_service_comments.go:33-43
3. Memo reaction API (list/upsert reaction) — server/router/api/v1/reaction_service.go:29-41
4. Memo attachment listing API — server/router/api/v1/memo_attachment_service.go:213-225
5. Linked-attachment access check (`checkAttachmentAccess`-style) — server/router/api/v1/attachment_service.go:436-455
6. Static file/attachment server (raw byte serving over HTTP) — server/router/fileserver/fileserver.go:674-703
7. RSS feed generation (filters memo list to Public only) — server/router/rss/rss.go:90,141
8. Frontend SSR/meta route (filters memo list to Public only) — server/router/frontend/frontend.go:150
9. Email notification dispatch gate (`canViewerAccessMemo`) — server/notification/email.go:306-320
10. In-app/webhook notification dispatch gate (`canViewerAccessMemo`, separately defined) — server/router/api/v1/user_service_notifications.go:302-315
11. Mention-notification access checks — server/router/api/v1/memo_mention_helpers.go:62-84

Each of these independently branches on `store.Public` / `store.Protected` / `store.Private` and (where relevant) `CreatorID`/`isSuperUser`/`RoleAdmin`, rather than delegating to a single shared visibility-check function — note items 9 and 10 even duplicate the same function name `canViewerAccessMemo` in two different files with separate definitions.
