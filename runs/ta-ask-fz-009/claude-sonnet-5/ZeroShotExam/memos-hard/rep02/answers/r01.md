**Premise correction:** There is no Redis connection anywhere in this codebase — a repo-wide search for "redis" returns zero matches across all 1042 searched files. The cache layer is not backed by Redis at all.

**Actual mechanism:** The cache is an in-process, thread-safe in-memory cache implemented in `store/cache/cache.go` (a `sync.Map`-based struct with TTL expiration, size tracking, and periodic cleanup — see the `Cache` type and `Config` struct at `store/cache/cache.go:42-70`). It's instantiated and wired up in `store/store.go`, where the `Store` struct holds three separate cache instances — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`) — all constructed with the same `cache.Config` in `New()` (`store/store.go:38-58`).

The TTL for user entries comes from that shared default config:
```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
(`store/store.go:40-45`), and `userCache` is created with this same config (`store/store.go:52`). User records are set into it via `s.userCache.Set(...)` in `store/user.go` (e.g. lines 98, 122, 132, 143, 167), which calls the cache's `Set` method — and `Set` always applies the `DefaultTTL` (`store/cache/cache.go:92-95`, via `SetWithTTL`). So **user entries live in the in-memory cache for 10 minutes** before expiring, unless explicitly deleted first (e.g. `deleteUserCache` in `store/user_delete.go:39-41`, invoked on user deletion at `store/user.go:179`).
