**Premise correction:** There is no Redis connection anywhere in this codebase — a repo-wide search for "redis" returns zero matches across 1042 files, and the map's `[ArchMap query]` results show no Redis client, connection pool, or config for one. The cache layer is not backed by Redis at all.

**Actual mechanism:** The cache is a thread-safe **in-process memory cache** (`sync.Map`-backed), implemented in `store/cache/cache.go:67` (`cache.Cache`, implementing `cache.Interface` at `store/cache/cache.go:11`). It's constructed and wired into the `Store` in `store/store.go`:

- `store/store.go:40-45` — `New()` builds a `cache.Config{DefaultTTL: 10*time.Minute, CleanupInterval: 5*time.Minute, MaxItems: 1000, OnEviction: nil}`.
- `store/store.go:47-58` — this single config is reused to build three separate in-memory caches: `instanceSettingCache`, `userCache`, and `userSettingCache` (all `*cache.Cache`), each closed in `Store.Close()` at `store/store.go:74-76`.

**TTL for user entries:** User records are stored via `s.userCache.Set(ctx, userCacheKey(user.ID), user)` (e.g. `store/user.go:98, 122, 132, 143, 167`). `Set` (`store/cache/cache.go:93`) delegates to `SetWithTTL` using `c.config.DefaultTTL` — i.e. the same **10-minute TTL** set in `store/store.go:41` (`cache.DefaultConfig()` in `store/cache/cache.go:57-64` also defines this same 10-minute default, though `store.go` builds its own literal config rather than calling that helper). No per-entry custom TTL is used for users — entries expire lazily on `Get` (`store/cache/cache.go:135-144`) or via the periodic `cleanupLoop` running every 5 minutes (`store/cache/cache.go:200-215`), and are also explicitly evicted on user deletion (`store/user_delete.go:40`).
