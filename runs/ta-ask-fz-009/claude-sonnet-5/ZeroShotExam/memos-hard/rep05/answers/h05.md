**Mechanism: explicit Go application code (not a database-level cascade rule).**

Evidence:
- `store/db/sqlite/user_delete.go:96,102,380-403` — inside `DeleteUser`'s transaction, `deleteUserTargetsTx` explicitly calls `deleteReactionsByContentIDsTx` (deletes reactions on all memos owned by the user, `DELETE FROM reaction WHERE content_id IN (...)`, line 383) and `deleteReactionsByCreatorTx` (deletes the user's own reactions on any content, `DELETE FROM reaction WHERE creator_id = ?`, line 401).
- The same two functions exist verbatim in the other drivers: `store/db/mysql/user_delete.go:417-439` and `store/db/postgres/user_delete.go:380-402`, each wired into their respective `DeleteUser` implementations (mysql `user_delete.go:29`, postgres `user_delete.go:29`).
- Call chain: `store/user.go:171` `Store.DeleteUser` → driver's `DeleteUser` (`store/db/{sqlite,mysql,postgres}/user_delete.go:29`) → `deleteUserTargetsTx` → the two reaction-delete helpers, all inside one transaction before the memo rows and user row are deleted (`deleteMemosTx`, `deleteUserRowTx`).
- Schema check: the `reaction` table (`store/migration/{sqlite,mysql,postgres}/LATEST.sql:90-98`, e.g. sqlite `LATEST.sql:91-99`) has no `FOREIGN KEY` clause referencing `user` and no `ON DELETE CASCADE` at all — the only `ON DELETE CASCADE` FKs in the whole migration tree are on `memo_share.memo_id → memo(id)` and legacy 0.3–0.5 tables (`creator_id/user_id → user(id)`), none of which touch `reaction`. So there is no DB-level rule that would clean up reactions on user deletion — it has to be (and is) done explicitly in the Go delete-user routine for every backend.
