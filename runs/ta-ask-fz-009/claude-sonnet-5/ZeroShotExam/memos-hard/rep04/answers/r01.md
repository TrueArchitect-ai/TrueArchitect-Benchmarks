r01. **Premise correction:** There is no Redis connection in this codebase — this is the [usememos/memos](https://github.com/usememos/memos) repo, and the cache layer is a pure in-process/in-memory cache, not a Redis-backed one. A repo-wide search for "redis" returns zero matches across all 1042 files, and the map's `[ArchMap query]` call also surfaced no cache-related hits — only unrelated symbols like `renderer`, `reservedCIDRs`, etc. (i.e., substring noise, not a Redis client/config).

**Actual mechanism:** The cache layer is implemented as a thread-safe in-memory store, `cache.Cache`, defined in `store/cache/cache.go:67`, backed by a `sync.Map` with atomic item counting, background TTL cleanup (`cleanupLoop`/`cleanup`, `store/cache/cache.go:200-250`), and an LRU-ish eviction (`cleanupOldest`, `store/cache/cache.go:253`) when `MaxItems` is exceeded.

It's wired up in `store/store.go`: the `Store` struct holds three separate `*cache.Cache` instances — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`) — each constructed with the same `cache.Config` in `store.New` (`store/store.go:38-58`).

**TTL for user entries:** User cache entries use the store-wide default TTL of **10 minutes**, set via `cacheConfig.DefaultTTL = 10 * time.Minute` in `store/store.go:41`, and applied through `cache.Cache.Set` (`store/cache/cache.go:93-95`), which calls `SetWithTTL` with `c.config.DefaultTTL`. User records are cached/evicted via `userCacheKey(userID int32)` (`store/user.go:88`), used throughout `store/user.go` (lines 98, 122, 132, 143, 150, 167) and cleared explicitly on deletion in `store/user_delete.go:40`. There is no per-user override — `userCache.Set` is always called without a custom TTL, so all user entries inherit the same 10-minute default (matching `cache.DefaultConfig()` at `store/cache/cache.go:57-64`, which is otherwise unused in favor of the store's own inline config).
