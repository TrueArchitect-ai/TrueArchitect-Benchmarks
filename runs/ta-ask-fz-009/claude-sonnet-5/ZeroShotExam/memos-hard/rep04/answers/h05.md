**Mechanism: explicit Go code (application-level), not a database cascade rule.**

The `reaction` table schema has no foreign key / `ON DELETE CASCADE` clause at all — it's just a plain table with `creator_id` and `content_id` columns (e.g. `store/migration/mysql/LATEST.sql:91-98`, mirrored in the postgres and sqlite LATEST.sql files). So the database itself enforces nothing on user deletion.

Instead, `DeleteUser` explicitly issues `DELETE FROM reaction` statements inside the deletion transaction:

- `store/db/mysql/user_delete.go:29` `DB.DeleteUser` → `deleteUserTargetsTx` (line 92) → 
  - `deleteReactionsByContentIDsTx` (`store/db/mysql/user_delete.go:417-425`): `DELETE FROM reaction WHERE content_id IN (...)` for content the user's memos/comments own
  - `deleteReactionsByCreatorTx` (`store/db/mysql/user_delete.go:437-440`): `DELETE FROM reaction WHERE creator_id = ?` for reactions the user itself created
- Same pattern duplicated per-backend: `store/db/postgres/user_delete.go:380` / `:400`, and `store/db/sqlite/user_delete.go:380` / `:400`, all called from their respective `DeleteUser` (line 29) → `deleteUserTargetsTx` (line 92).
- `store.Store.DeleteUser` (`store/user.go:171`) is the entry point that dispatches to whichever backend driver is active, so all three paths are exercised depending on the configured DB.

So reactions are cleaned up both when the user is the reaction's creator and when the user owned the reacted-to content — but purely via explicit `DELETE` calls inside the same transaction as the user delete, not via any DB-level cascade constraint.
