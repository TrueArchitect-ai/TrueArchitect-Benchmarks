**Premise correction:** There is no Redis in this codebase — `grep_content` for "redis" across the whole repo (1042 files) returned zero matches, and the cache layer is a self-contained, thread-safe **in-memory** cache implemented in Go (`sync.Map` + TTL bookkeeping), not a Redis client. Nothing in this repository configures a Redis connection.

**Actual mechanism:**
- The cache interface and implementation live in `store/cache/cache.go`. It's an in-process `Cache` struct backed by `sync.Map`, with a background `cleanupLoop`/`cleanup` goroutine for expiry and eviction (`store/cache/cache.go:66-218`).
- The cache is wired up in `store/store.go:23-58`. `Store` holds three separate cache instances — `instanceSettingCache`, `userCache`, and `userSettingCache` — each constructed via `cache.New(cacheConfig)` (`store/store.go:27-29, 51-53`).
- The shared `cacheConfig` used for all three (including `userCache`) is set explicitly in `store.New`:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  (`store/store.go:40-45`, matching `cache.DefaultConfig()` at `store/cache/cache.go:56-64`).
- User entries are written via `s.userCache.Set(ctx, userCacheKey(user.ID), user)` in `store/user.go:98, 122, 132, 143, 167`, which calls the plain `Set` method — not `SetWithTTL` — so they get the cache's `DefaultTTL`.

**TTL for user entries: 10 minutes**, with a 5-minute cleanup sweep interval and a 1000-item cap, per `store/store.go:41-43`. User cache entries are also explicitly invalidated on delete via `s.userCache.Delete(ctx, userCacheKey(userID))` in `store/user_delete.go:40`, so the TTL is a backstop rather than the primary invalidation path.
