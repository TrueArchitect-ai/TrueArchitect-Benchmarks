h05. Mechanism: **explicit Go application code**, not a database-level cascade rule (no FK/`ON DELETE CASCADE` exists on the `reaction` table in any dialect).

Evidence:

- `store/migration/{mysql,postgres,sqlite}/LATEST.sql` — the `reaction` table (e.g. `store/migration/postgres/LATEST.sql:90-98`) has no `FOREIGN KEY ... ON DELETE CASCADE` clause referencing `user`; it stores `creator_id`/`content_id` as plain columns. A repo-wide grep for `ON DELETE CASCADE` (across all migrations) shows cascade rules exist for `memo_share`, `user_setting`, `memo_resource`, etc., but none target `reaction`. So there is no DB-level rule cleaning up reactions.
- The deletion is instead driven explicitly from Go inside the `DeleteUser` transaction:
  - `server/router/api/v1/user_service.go:414-419` — API handler calls `s.Store.DeleteUser(ctx, &store.DeleteUser{ID: user.ID})`.
  - `store/user.go:171-179` — `Store.DeleteUser` delegates to the driver's `DeleteUser`.
  - Driver implementations run the whole cleanup inside one SQL transaction, each with the identical sequence, and explicitly delete reactions in two passes before deleting the memo/user rows:
    - `store/db/postgres/user_delete.go:96,102,380-403` (`deleteReactionsByContentIDsTx` — deletes `DELETE FROM reaction WHERE content_id IN (...)` for all memos owned by the user; `deleteReactionsByCreatorTx` — deletes `DELETE FROM reaction WHERE creator_id = ?` for reactions the user itself made on others' content).
    - Same two functions exist identically in `store/db/mysql/user_delete.go:96,102,417,437` and `store/db/sqlite/user_delete.go:96,102,380,400`.
  - Order in `deleteUserTargetsTx` (`store/db/postgres/user_delete.go:92-126`) is: delete reactions by content_id → delete attachments → delete reactions by creator_id → delete memo_shares → inboxes → user_identities → user_settings → memo_relations → memos → the user row — all before commit.

So: emoji reactions tied to a deleted user's memos (`content_id`) and reactions the user itself authored (`creator_id`) are both removed by explicit Go-orchestrated `DELETE FROM reaction ...` statements run inside the same transaction as the rest of the user-deletion cleanup — not by a database foreign-key cascade.
