Actual mechanism: it's an in-process, TTL-based memory cache implemented from scratch in `store/cache/cache.go` (`cache.Cache`, backed by a `sync.Map`), not a network-attached cache. It's wired up in `store/store.go`:

- `Store.userCache` is created at `store/store.go:52` via `cache.New(cacheConfig)`, using the config defined at `store/store.go:40-45`.
- That config sets `DefaultTTL: 10 * time.Minute` (`store/store.go:41`), which matches the package's own `cache.DefaultConfig()` (`store/cache/cache.go:57-64`).
- User entries are written with `s.userCache.Set(ctx, userCacheKey(user.ID), user)` (e.g. `store/user.go:98, 122, 132, 143, 167`), and `Set` (`store/cache/cache.go:93-95`) delegates to `SetWithTTL` using `c.config.DefaultTTL` — i.e. the same 10-minute TTL, since no call site overrides it with `SetWithTTL`.
- Expiration is enforced lazily on `Get` (`store/cache/cache.go:135-144`) and actively by a background `cleanupLoop` running every `CleanupInterval` (5 minutes, `store/store.go:42`), per `store/cache/cache.go:200-215`.

So: user cache entries live for 10 minutes in an in-memory `sync.Map`-based cache local to the process (also used for `instanceSettingCache` and `userSettingCache` with the same config) — there is no Redis connection to configure because Redis isn't part of this stack.
