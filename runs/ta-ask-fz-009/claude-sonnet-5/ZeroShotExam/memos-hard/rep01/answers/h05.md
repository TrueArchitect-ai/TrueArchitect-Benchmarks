This confirms explicit Go code in the sqlite driver deletes reactions both by content (memos deleted) and by creator. Let me confirm the same pattern in mysql/postgres drivers, and check the schema for any FK constraint/cascade (to rule out DB-level rule).

h05.

**Mechanism: explicit Go application code, run inside a transaction — not a database-level rule.**

The `reaction` table has no foreign key at all (it can't even reference `user` by FK, since `creator_id` is an integer but `content_id` is a string like `memos/{uid}`, not a real FK column). Confirmed by the schema:

- `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:90-97`, `store/migration/sqlite` equivalents — `CREATE TABLE reaction (...)` has no `FOREIGN KEY`/`REFERENCES`/`ON DELETE` clause anywhere in the definition. (Contrast with `memo_share`, which explicitly documents `ON DELETE CASCADE` on `memo_id` — `store/migration/*/0.27/04__memo_share.sql:3,11` — showing the schema *does* use DB cascades elsewhere when intended, but not for `reaction`.)

So cleanup has to be done in application code, and it is. The RPC path is:

- `server/router/api/v1/user_service.go:393` `APIV1Service.DeleteUser` calls `s.Store.DeleteUser(ctx, &store.DeleteUser{ID: user.ID})`.
- `store/user.go:171` `Store.DeleteUser` delegates to the driver's `DeleteUser`.
- Each driver (`store/db/sqlite/user_delete.go`, `store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`) implements `DeleteUser` as a single transaction that explicitly issues `DELETE FROM reaction ...` twice:
  - `deleteReactionsByContentIDsTx` — deletes reactions on every memo/comment the user owns (`DELETE FROM reaction WHERE content_id IN (...)`), e.g. `store/db/sqlite/user_delete.go:380-388`.
  - `deleteReactionsByCreatorTx` — deletes reactions the user themself placed on any content (`DELETE FROM reaction WHERE creator_id = ?`), e.g. `store/db/sqlite/user_delete.go:400-403`.
- These two calls happen early in `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`, lines 96 and 102), before attachments, memo shares, inbox rows, identities, settings, memo relations, memos, and finally the `user` row itself are deleted, all inside the same transaction (`tx.Commit()` at the end, `user_delete.go:51`).

The mysql and postgres drivers mirror this exactly (`store/db/mysql/user_delete.go:96,102,417-438`; `store/db/postgres/user_delete.go:96,102,380-401`), each with its own `deleteReactionsByContentIDsTx`/`deleteReactionsByCreatorTx` pair.

**Conclusion:** reactions are removed by explicit, transactional Go code in the store layer (both reactions the deleted user made on others' content, and reactions others left on the deleted user's content), not by a `FOREIGN KEY ... ON DELETE CASCADE` rule — the `reaction` table has no such constraint in any dialect's schema.
