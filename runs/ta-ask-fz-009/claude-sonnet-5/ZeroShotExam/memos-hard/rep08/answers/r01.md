r01. Premise correction: there is no Redis connection in this codebase — the cache layer is not backed by Redis at all. `store/cache/cache.go` implements a self-contained, thread-safe **in-memory** cache (`sync.Map` + TTL bookkeeping, no external dependency, no network client).

Actual mechanism:
- The cache is defined in `store/cache/cache.go`, with a `Config{DefaultTTL, CleanupInterval, MaxItems, OnEviction}` struct and a `Cache` type built on `sync.Map` (store/cache/cache.go:41-70).
- It's wired up in `store/store.go:38-61` (`New`), where `Store` constructs three independent in-memory cache instances — `instanceSettingCache`, `userCache`, and `userSettingCache` — all sharing one `cacheConfig`.
- That shared config sets `DefaultTTL: 10 * time.Minute` (store/store.go:41), `CleanupInterval: 5 * time.Minute`, and `MaxItems: 1000`.
- `userCache` (store/store.go:28, 52) is the entry used for user records, keyed via `userCacheKey(userID)` in `store/user.go:88`, and populated/read via `s.userCache.Set(...)` / `s.userCache.Get(...)` in `store/user.go:98,122,132,143,150,167`, with invalidation on delete in `store/user_delete.go:39-40`.

So: user entries get the cache's **default 10-minute TTL** (no per-entry override is used for users — no call to `SetWithTTL` appears in `store/user.go`), applied by an in-process map, not by any Redis instance.
