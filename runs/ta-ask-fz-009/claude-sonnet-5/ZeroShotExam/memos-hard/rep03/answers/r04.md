Actual mechanism: webhook delivery is not queue-based at all. It's an in-process Go channel worker pool defined in `internal/webhook/webhook.go`:

- `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`) — a buffered Go channel acts as the "queue," capacity 128.
- `init()` (`internal/webhook/webhook.go:42-55`) spawns 4 goroutines that range over `asyncPostQueue` and call `Post(payload)` for each item, logging a warning on failure.
- Producers push work by sending `*WebhookRequestPayload` values into that channel (dispatched from memo/comment update paths, per `server/router/api/v1/memo_service.go` per the design docs referencing webhook dispatch).

So there's no external broker, no AMQP/NATS client dependency, and no queue "declared" in infra config — the "queue" is purely the in-memory buffered channel `asyncPostQueue` in `internal/webhook/webhook.go:39`, consumed by a fixed pool of 4 goroutines started in that file's `init()`.
