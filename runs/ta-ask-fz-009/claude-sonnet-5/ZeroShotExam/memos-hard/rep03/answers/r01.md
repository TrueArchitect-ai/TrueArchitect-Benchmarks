**Premise correction:** There is no Redis connection anywhere in this codebase — I searched for `redis`/`Redis` across all 1042 files and found zero matches. The cache layer is not backed by Redis at all; it's a plain in-process, in-memory cache.

**Actual mechanism:** The cache is implemented in `store/cache/cache.go` as `cache.Cache`, a thread-safe in-memory store built on `sync.Map` with TTL expiration and a background cleanup goroutine (`cleanupLoop`, `store/cache/cache.go:200`). It's configured via a `cache.Config` struct (`store/cache/cache.go:42`) with `DefaultTTL`, `CleanupInterval`, `MaxItems`, and an eviction callback.

The user-entry cache specifically is wired up in `store/store.go`:
- `store/store.go:40-45` — a `cacheConfig` is constructed with `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`.
- `store/store.go:52` — `userCache: cache.New(cacheConfig)` creates the actual user cache instance using that config, held on the `Store` struct (`store/store.go:28`).

So the TTL applied to user entries is **10 minutes**, set/read via `userCache.Set(...)` in `store/user.go:98,122,132,143,167` using keys from `userCacheKey(userID)` (`store/user.go:88`), and invalidated on delete via `store/user_delete.go:40`. There's a similarly-configured `instanceSettingCache` and `userSettingCache` (same 10-minute default), but no Redis client, connection string, or network cache backend exists in this project — the "connection" question doesn't apply.
