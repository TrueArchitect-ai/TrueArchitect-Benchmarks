**Interceptor:** `web/src/connect.ts:156` (`authInterceptor`, a Connect-RPC `Interceptor`) — attached to the shared `transport` at `web/src/connect.ts:184-189` and used by every generated service client (`instanceServiceClient`, `authServiceClient`, `memoServiceClient`, etc.) in that file.

**Tokens it manages:**
- **Access token** — short-lived JWT, kept in memory/localStorage and injected as the `Authorization` header on every request (`getRequestToken()`/`setAuthorizationHeader`, `web/src/connect.ts:124-159`, backed by `web/src/auth-state.ts` which stores/broadcasts it via `BroadcastChannel` and `localStorage` under `TOKEN_KEY`).
- **Refresh token** — held server-side as an httpOnly cookie (requests use `credentials: "include"`, `fetchWithCredentials` at `web/src/connect.ts:57-61`); the interceptor calls `refreshAndGetAccessToken()` on 401s to mint a new access token, retrying once via the `X-Retry` header (`web/src/connect.ts:161-177`).

The backend (`server/auth/authenticator.go:22-23,39-70`) additionally recognizes a third kind, **Personal Access Tokens (PAT)**, for programmatic (non-browser) API access — validated via `Authenticator.AuthenticateByPAT` (`server/auth/authenticator.go:102`), though this isn't issued/managed by the frontend interceptor itself.

**Backend package that validates them:** `server/auth` (package `auth`), specifically `auth.Authenticator` in `server/auth/authenticator.go` — `AuthenticateByAccessTokenV2` (line 41), `AuthenticateByRefreshToken` (line 61), `AuthenticateByPAT` (line 102), and the dispatching `Authenticate` (line 213). This is wired into the Connect-RPC layer via `v1.AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208-237`.
