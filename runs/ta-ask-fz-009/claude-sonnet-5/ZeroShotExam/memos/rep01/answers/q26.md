q26. **Tables affected when DeleteMemo runs: `memo`, `memo_relation`, `attachment`**

Tracing the call chain:

1. **Handler** `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`)
   - First deletes any comment-memos (memos whose relation type is `COMMENT` and are related to the target memo) by calling `s.Store.DeleteMemo` on each — line 574.
   - Then calls `s.Store.DeleteMemo` on the target memo itself — line 580.
   - Reactions and attachments are only *listed* here (`ListReactions`, `ListAttachments`) to build the webhook payload — no deletion happens at this layer for reactions.

2. **Store layer** `store.Store.DeleteMemo` (`store/memo.go:140-159`) does the explicit cascade for every memo it's called on (including the comment-memos looped above):
   - Deletes rows from **`memo_relation`** where the memo is the source (`s.driver.DeleteMemoRelation(... MemoID: &delete.ID)`) — line 142.
   - Deletes rows from **`memo_relation`** where the memo is the target (`s.driver.DeleteMemoRelation(... RelatedMemoID: &delete.ID)`) — line 145.
   - Lists and deletes all **`attachment`** rows linked to the memo via `s.DeleteAttachment` (which itself removes the underlying storage blob then the DB row) — lines 148-157, with the actual delete SQL in `store/db/mysql/attachment.go:230-241` (`DELETE FROM attachment WHERE id = ?`).
   - Finally deletes the **`memo`** row itself via `s.driver.DeleteMemo`, e.g. `store/db/mysql/memo.go:259-270` (`DELETE FROM memo WHERE id = ?`).
   - Equivalent driver SQL exists for `memo_relation` in `store/db/mysql/memo_relation.go:137`.

Note: `reaction` rows tied to the memo are **read** (`ListReactions`) but not deleted by this code path — the reactions table is not part of the explicit cascade, so it's not included in the affected-table list.
