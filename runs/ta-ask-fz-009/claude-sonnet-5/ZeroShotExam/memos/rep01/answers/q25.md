**Engine:** Google's CEL (`google/cel-go`), wrapped by a custom package at **`internal/filter/`**. The proto request field `ListMemosRequest.filter` (see `proto/gen/api/v1/memo_service.pb.go:524`) carries a CEL-syntax filter expression — the same filter language used elsewhere (see the comment in `proto/gen/api/v1/apiv1connect/shortcut_service.connect.go:58`).

**Where it lives:**
- `internal/filter/schema.go` — declares the CEL variable schema (`content`, `creator`, `tag`, `tags`, `visibility`, `pinned`, `has_task_list`, etc. at schema.go:232-248) as `cel.EnvOption`s, used to build the `cel.Env`.
- `internal/filter/engine.go` — `Engine.Compile` calls `cel.NewEnv(...)`, then `env.Compile(filter)` to get a CEL AST, converts it to a parsed expr (`cel.AstToParsedExpr`), and walks it via `buildCondition` into a dialect-agnostic `Condition` tree (a custom IR, `internal/filter/ir.go`). A process-wide singleton is exposed via `filter.DefaultEngine()`.
- `internal/filter/render.go` — a `renderer` (`newRenderer(schema, opts)`) walks that `Condition` tree and emits SQL text + args per node type (comparisons, `IN`, tag/list comprehensions, regex/text match, JSON array access, timestamp casts, etc.), branching on `RenderOptions.Dialect`.

**Mechanism → SQL per dialect:** each store backend (`store/db/mysql/memo.go:65-69`, `store/db/postgres/memo.go:54-58`, `store/db/sqlite/memo.go:57-61`) calls `filter.AppendConditions(ctx, engine, find.Filters, filter.DialectMySQL|DialectPostgres|DialectSQLite, &where, &args)`, which invokes `engine.CompileToStatement` — CEL-compile the string → build the neutral `Condition` IR → `Render` it with the given `DialectName`, so the *same* parsed condition tree is rendered into MySQL/Postgres/SQLite-specific SQL fragments (dialect-specific JSON functions, timestamp casts, placeholder styles) in `render.go`, appended as a `WHERE` clause fragment plus its bound args.
