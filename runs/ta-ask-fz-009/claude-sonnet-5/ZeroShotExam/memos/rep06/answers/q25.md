**Engine + path**: A CEL (Common Expression Language) based filter engine at `internal/filter/` (Go package `filter`, built on `github.com/google/cel-go/cel`). Key files: `internal/filter/engine.go` (`Engine.Compile` compiles the filter string via `cel.NewEnv`/`env.Compile`), `internal/filter/schema.go` (defines the CEL variable schema for memos — `content`, `creator`, `tag`, `tags`, `visibility`, `pinned`, `has_task_list`, etc., in `NewSchema()` at schema.go:232+), `internal/filter/ir.go` (the dialect-agnostic condition-tree types the CEL AST is lowered into via `buildCondition`), and `internal/filter/render.go` (the per-dialect SQL renderer).

**Wiring for ListMemos**: `server/router/api/v1/memo_service.go:211-215` takes `request.Filter`, validates it (`s.validateFilter`), and appends it to `store.FindMemo.Filters` (`store/memo.go:72`), which is a `[]string` of raw CEL filter expressions.

**Mechanism (how it becomes SQL per dialect)**: The CEL string is compiled to a CEL AST (`e.env.Compile` → `cel.AstToParsedExpr`), then walked once into a dialect-agnostic `Condition` tree (`buildCondition` in `internal/filter/parser.go`); that same tree is rendered into dialect-specific SQL and args by `internal/filter/render.go`'s `renderer` (selected via `RenderOptions{Dialect: ...}` with `DialectMySQL`/`DialectPostgres`/`DialectSQLite`), invoked from each store backend's `ListMemos` through `filter.AppendConditions` in `internal/filter/helpers.go:9` — called from `store/db/mysql/memo.go:69`, `store/db/postgres/memo.go:58`, and `store/db/sqlite/memo.go:61` — so the same CEL filter compiles once into one AST/condition tree but is rendered three separate ways (e.g. backtick-quoted columns + `?` placeholders + `JSON_TABLE`/`CHAR_LENGTH` for MySQL, `$N` placeholders + `ILIKE`/`jsonb_array_elements_text` for Postgres, and `?` placeholders + `json_each`/`strftime` for SQLite).
