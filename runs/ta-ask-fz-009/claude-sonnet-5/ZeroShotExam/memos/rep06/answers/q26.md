q26. Deleting a memo cascades across three tables (mirrored per SQL dialect: MySQL/Postgres/SQLite):

- **`memo`** — the target row itself is deleted (`store.DeleteMemo` → driver `DeleteMemo`, e.g. `store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`). Note that `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) also recursively deletes any **comment memos** first (`memo_service.go:567-577`), each of those going through the same `memo`/`memo_relation`/`attachment` cascade — so multiple `memo` rows can be removed in one call.
- **`memo_relation`** — explicitly cleaned up before the memo row is dropped, once for rows where the memo is the source and once where it's the target (`store/memo.go:142-147`, driver impl `store/db/sqlite/memo_relation.go:137`).
- **`attachment`** — all attachments linked to the memo are listed and deleted individually via `Store.DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`, driver impl `store/db/sqlite/attachment.go:211`). This also triggers non-DB storage cleanup (`DeleteAttachmentStorage`, `store/attachment.go:193`), but that's file-system, not a table.

Not touched by `DeleteMemo` itself: `reaction` rows are only *listed* (`ListReactions`, `memo_service.go:545`) for the webhook payload before deletion — no reaction delete call appears in this path, so `reaction` is not part of the cascade (verify if you expected otherwise, since the code lists but never deletes them here).

**Tables affected: `memo`, `memo_relation`, `attachment`**
