**Tables affected when `DeleteMemo` runs:**

1. **`memo`** — the target row itself is deleted (`store/db/{mysql,postgres,sqlite}/memo.go: DeleteMemo`, invoked from `store/memo.go:158`). Additionally, the API handler first deletes any *comment* memos related to it (`server/router/api/v1/memo_service.go:567-577`), which recursively re-enters `store.DeleteMemo` for those child memo rows too.

2. **`memo_relation`** — explicitly cleaned up inside `store.Store.DeleteMemo` (`store/memo.go:142-147`), deleting rows where the memo is either `memo_id` or `related_memo_id`, via `driver.DeleteMemoRelation`.

3. **`attachment`** — explicitly cleaned up inside `store.Store.DeleteMemo` (`store/memo.go:148-157`): it lists attachments by `MemoID` and calls `s.DeleteAttachment` for each, which deletes the row via `driver.DeleteAttachment` (also attempts to delete the underlying blob/storage, not a DB table).

4. **`memo_share`** — not deleted by any Go code path in `DeleteMemo`; it is cleaned up only via a database-level `ON DELETE CASCADE` foreign key on `memo_share.memo_id → memo.id`, defined in the schema (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`). Note: for SQLite this cascade is only effective if foreign-key enforcement is on, but the driver opens SQLite with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite this cascade would **not** actually fire — it's a comment/DDL intent, not a runtime guarantee, on that dialect.

**Not affected:** `reaction` — `DeleteMemo` only *reads* reactions (`ListReactions`, `server/router/api/v1/memo_service.go:545`) for the webhook payload; no code in `store.DeleteMemo` or the handler deletes rows from `reaction`, and there is no DB-level FK/cascade on `reaction.content_id`, so reaction rows referencing a deleted memo are left orphaned.
