**Interceptor path:** `web/src/connect.ts:156` — the `authInterceptor` Connect-RPC `Interceptor`, which reads the access token via `getRequestToken()` (backed by `web/src/auth-state.ts`), attaches it as the `Authorization` header, and on a `401`/unauthenticated response triggers a refresh-and-retry flow (`refreshAndGetAccessToken`) before redirecting via `web/src/utils/auth-redirect.ts`.

**Token kinds it manages:**
- **Access token** — short-lived JWT, kept in memory + `localStorage` (`memos_access_token`) and synced across tabs via a `BroadcastChannel` (`web/src/auth-state.ts:1-80`), sent as the `Authorization: Bearer` header.
- **Refresh token** — longer-lived, stored server-side as an httpOnly cookie (not touched directly by JS); the frontend calls a refresh endpoint with `credentials: "include"` (`fetchWithCredentials`, `web/src/connect.ts:57`) to mint a new access token when the current one is expired or a request comes back unauthenticated.

**Backend validation package:** `server/auth` (specifically `server/auth/authenticator.go`, `server/auth/token.go`, `server/auth/context.go`). The `Authenticator` there validates:
- access tokens via `AuthenticateByAccessTokenV2` (`server/auth/authenticator.go:41`),
- refresh tokens via `AuthenticateByRefreshToken` (`server/auth/authenticator.go:61`, pulling the refresh token out of the cookie header with `ExtractRefreshTokenFromCookie`, `server/auth/extract.go:23`),
- and Personal Access Tokens via `AuthenticateByPAT` (`server/auth/authenticator.go:102`).

This `Authenticator` is wired into the Connect-RPC layer through `Authorizer` (`server/router/api/v1/authz.go:26`), which the Go-side `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208`, `WrapUnary` at line 217) calls on every unary request — reading the `Authorization` header and invoking `authorizer.Authenticate` / `CheckAccess` before passing the request through.
