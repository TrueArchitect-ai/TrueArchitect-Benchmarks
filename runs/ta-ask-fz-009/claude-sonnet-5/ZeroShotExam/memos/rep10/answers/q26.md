**Tables affected when `DeleteMemo` runs: `memo`, `memo_relation`, `attachment`, `memo_share`.** (`reaction` is read but not deleted.)

Trace:

1. **`server/router/api/v1/memo_service.go:518-593`** (`APIV1Service.DeleteMemo`) — reads the memo, reactions (`ListReactions`) and attachments (`ListAttachments`) just to build the webhook payload; it does **not** delete reactions. It then, for each memo-comment relation (`ListMemoRelations` with `MemoRelationComment`), calls `s.Store.DeleteMemo` on each comment memo, and finally calls `s.Store.DeleteMemo` on the target memo itself (line 574, 580).

2. **`store/memo.go:140-159`** (`Store.DeleteMemo`) — the real cascade logic:
   - Deletes rows from **`memo_relation`** where the memo is the source (`driver.DeleteMemoRelation(MemoID: …)`) and where it is the target (`driver.DeleteMemoRelation(RelatedMemoID: …)`) — lines 142-147.
   - Lists and deletes every **`attachment`** row linked to the memo via `s.ListAttachments` / `s.DeleteAttachment` (lines 149-157), which in turn issues `DELETE FROM attachment …` (e.g. `store/db/mysql/attachment.go:230-231`).
   - Finally calls `driver.DeleteMemo` (line 158), which issues `DELETE FROM memo WHERE id = ?` (`store/db/mysql/memo.go:259-270`).

3. **`memo_share`** is not touched by app code, but the schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/mysql/LATEST.sql:108`, same in `postgres/LATEST.sql:108` and `sqlite/LATEST.sql:109`), so deleting the `memo` row triggers a DB-level cascade delete of its `memo_share` rows.

Not affected: `reaction` — `DeleteMemo` only calls `ListReactions` (read-only, for the webhook payload); actual reaction deletion happens only via the separate `DeleteMemoReaction` RPC (`server/router/api/v1/reaction_service.go:111`), which is not invoked from this path.
