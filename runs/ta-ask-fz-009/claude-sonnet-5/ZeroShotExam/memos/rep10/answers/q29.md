q29. The frontend uses a Connect-RPC interceptor called `authInterceptor` defined in **`web/src/connect.ts:156`**. It runs on every outbound request: it fetches the current access token (`getRequestToken`), sets it as `Authorization: Bearer <token>` (`setAuthorizationHeader`, line 97), and if a request comes back unauthenticated it triggers a token refresh (`refreshAndGetAccessToken`/`refreshAccessToken`, lines 74–91) and retries once (tagged via the `X-Retry` header) before falling back to `redirectOnAuthFailure()`. The refresh call itself goes over a separate transport with no interceptor (to avoid recursion) and relies on an HTTP-only cookie (`credentials: "include"` in `fetchWithCredentials`, line 57-62) carrying the refresh token.

So the frontend manages two token kinds:
- **Short-lived JWT access token** — held in memory/local state (`web/src/auth-state.ts`, via `getAccessToken`/`setAccessToken`), sent as a Bearer header on every request.
- **Refresh token** — carried via cookie, exchanged through `AuthService.refreshToken` to mint a new access token.

On the backend, both of these (plus a third kind, Personal Access Tokens/PATs) are validated by the **`server/auth`** package — specifically `auth.Authenticator` in `server/auth/authenticator.go`, which exposes `AuthenticateByAccessTokenV2` (line 41, stateless JWT validation), `AuthenticateByRefreshToken` (line 61, DB-backed revocation/expiry check), and `AuthenticateByPAT` (line 102, for programmatic/API-key access). This `Authenticator` is invoked from the Connect-level `v1.AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208`), which is what actually enforces auth on incoming gRPC/Connect calls server-side.
