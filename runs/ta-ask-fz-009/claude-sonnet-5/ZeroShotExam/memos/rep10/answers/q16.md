Before deleting the memo row itself, `store.Store.DeleteMemo` (store/memo.go:140-159) deletes:

1. **Memo relations** — all `memo_relation` rows where the memo is the source (`MemoID`) or the target (`RelatedMemoID`), via two calls to `driver.DeleteMemoRelation` (store/memo.go:142-147).
2. **Attachments** — every attachment linked to the memo (fetched via `ListAttachments` with `MemoID`), each removed individually via `s.DeleteAttachment` (store/memo.go:148-157).

Only after both of these cleanups does it call `s.driver.DeleteMemo(ctx, delete)` to remove the memo row itself (store/memo.go:158).

Note: at the API layer (`server/router/api/v1/memo_service.go:566-577`), the handler also deletes any child "comment" memos (memos related via `MemoRelationComment`) by calling `store.DeleteMemo` recursively for each before deleting the target memo — but that's a service-layer orchestration step, not something the store's `DeleteMemo` itself performs. Reactions and webhook dispatch are read/handled at the API layer too, but reactions are not deleted by the store's `DeleteMemo` (no `DeleteReaction` call appears in store/memo.go).
