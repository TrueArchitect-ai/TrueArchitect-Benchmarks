**Tables affected by `DeleteMemo`:** `memo`, `memo_relation`, `attachment`, `memo_share`

Trace:
- `v1.APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) first deletes any child "comment" memos (memos linked via a `memo_relation` of type Comment) by recursively calling `store.DeleteMemo` for each (`memo_service.go:567-577`), then calls `store.DeleteMemo` on the target memo itself (`memo_service.go:580`).
- `store.Store.DeleteMemo` (`store/memo.go:140-159`) does the explicit cascade work in app code:
  - deletes rows from **`memo_relation`** where the memo is the source (`memo_id`) or the target (`related_memo_id`) — `store/memo.go:142-147`
  - lists and deletes all rows in **`attachment`** for the memo via `s.DeleteAttachment` — `store/memo.go:148-157` (each `DeleteAttachment` call also removes the backing blob storage, but only the `attachment` table row is a DB effect — `store/attachment.go:132-149`)
  - finally deletes the row from **`memo`** itself via the driver (`store/db/sqlite/memo.go:237-248`, and equivalents in `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`)
- **`memo_share`** rows are removed by a database-level `ON DELETE CASCADE` foreign key on `memo_share.memo_id → memo.id`, defined in the schema (e.g. `store/migration/sqlite/LATEST.sql:102-110`, `store/migration/mysql/LATEST.sql:101-108`), so deleting the `memo` row cascades there automatically even though no store code explicitly calls a memo_share delete for this path.

Note: `reaction` rows tied to the memo (`ListReactions` at `memo_service.go:545`) are only *read* (for the deletion webhook payload) — there is no explicit delete call against the `reaction` table in this flow, and the schema has no FK/cascade from `reaction.content_id` to `memo.id` (`store/migration/sqlite/LATEST.sql:92-99`), so `reaction` is not affected by `DeleteMemo`.
