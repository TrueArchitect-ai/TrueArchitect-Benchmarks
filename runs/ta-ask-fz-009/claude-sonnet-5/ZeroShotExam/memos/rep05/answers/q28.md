**Background workers actually started by the server**

- **s3presign.Runner — ticker-driven, every 12 hours** (`server/runner/s3presign/runner.go:27,29-41`, `runnerInterval = time.Hour * 12`). It's instantiated and launched from `Server.startBackgroundRunners` in `server/server.go:153-174`: an immediate `RunOnce(ctx)` call at startup (`server/server.go:163`) followed by a goroutine running `s3presignRunner.Run(s3Context)` (`server/server.go:167-171`), which loops on `time.NewTicker(runnerInterval)` until its per-runner cancel context is done. This is the only entry in `startBackgroundRunners`, and `Server.Start` calls it once, right after the HTTP listener goroutine is spun up (`server/server.go:129`).

**Not actually started as a background runner (present but unused for scheduling)**

- **memopayload.Runner** (`server/runner/memopayload/runner.go:14-24`) has its own `NewRunner`/`RunOnce` (lines 19, 27), structurally identical in shape to the s3presign runner, but `memopayload.NewRunner` is never called anywhere in `server/server.go` or `cmd/` (confirmed via reference search — 343 files scanned, zero hits). Only the free function `RebuildMemoPayload` from that package is used, and it's invoked synchronously inside request handling in `server/router/api/v1/memo_service.go:108,447` (on memo create/update), not via any scheduled loop. So the `Runner` type in this package is dead code with respect to scheduling — it's built but never started.
- **`internal/scheduler`** is a complete, general-purpose cron scheduler (`Scheduler`, `Job`, cron-expression parser — `internal/scheduler/scheduler.go`, `job.go`, `parser.go`) with its own README and tests. A repo-wide reference search shows it is imported only by its own package's test files (`example_test.go`, `integration_test.go`) — never by `server/` or `cmd/`. This is scheduling infrastructure that exists in the codebase but is **not wired into anything the server starts**.
