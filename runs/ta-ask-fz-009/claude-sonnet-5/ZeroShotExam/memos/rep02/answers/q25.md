**Engine:** Google's `cel-go` (Common Expression Language), driving a purpose-built compiler at `internal/filter` (`engine.go`, `parser.go`, `ir.go`, `render.go`, `schema.go` — see `internal/filter/README.md`).

**Mechanism:** The `ListMemos` filter string flows from `store.Store.ListMemos` into each dialect's memo query (`store/db/mysql/memo.go:69`, `store/db/postgres/memo.go:58`, `store/db/sqlite/memo.go:61`), where `filter.AppendConditions` uses the `internal/filter` `Engine` to (1) parse the CEL expression and type-check it against a fixed variable schema (`internal/filter/schema.go`, e.g. `content`, `tag`, `visibility`, `created_ts`) via `cel.NewEnv`/`cel.AstToParsedExpr` in `internal/filter/engine.go:25,57`; (2) walk the resulting CEL AST into a dialect-agnostic intermediate representation (`internal/filter/ir.go`); and (3) render that IR into a dialect-specific `WHERE` fragment plus bound args (`internal/filter/render.go`), branching per `DialectSQLite`/`DialectMySQL`/`DialectPostgres` (e.g. producing `REGEXP`/`json_each` for SQLite, `~`/`jsonb_array_elements_text` for Postgres, `REGEXP`/`JSON_TABLE` for MySQL — confirmed in `internal/filter/engine_test.go:100-167`). cel-go itself never evaluates the expression — it's used purely as parser/type-checker, and `internal/filter` owns the SQL-generation logic (per `internal/filter/README.md:8` and `docs/superpowers/specs/2026-06-15-cel-filter-surface-expansion-design.md:11-13`).
