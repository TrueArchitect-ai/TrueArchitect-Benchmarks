q26. **Tables affected when `DeleteMemo` runs:**

1. **`memo`** — the target row is deleted directly (`store/db/sqlite/memo.go:237`, mirrored in mysql/postgres drivers), and the handler also recurses into `store.DeleteMemo` for each child "comment" memo found via `memo_relation` before deleting the parent (`server/router/api/v1/memo_service.go:567-582`).

2. **`memo_relation`** — explicitly cleaned up in `store.DeleteMemo` (`store/memo.go:140-147`), which calls `driver.DeleteMemoRelation` twice: once for rows where the memo is the source (`MemoID`) and once where it's the target (`RelatedMemoID`).

3. **`attachment`** — explicitly cleaned up in `store.DeleteMemo` (`store/memo.go:148-157`): it lists attachments via `FindAttachment{MemoID: &delete.ID}` and deletes each one through `s.DeleteAttachment`, which also removes the underlying blob/file storage (`store/attachment.go:132-149`).

4. **`memo_share`** — not touched by Go code, but the schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` for this table (`store/migration/sqlite/LATEST.sql:102-110`, same in mysql/postgres `LATEST.sql`), so any share rows for the memo are removed automatically at the database level when the `memo` row is deleted. The migration comment even states this intent: "ON DELETE CASCADE ensures grants are cleaned up when the parent memo is deleted" (`store/migration/sqlite/0.27/04__memo_share.sql:3`).

Note: `reaction` rows tied to the memo (looked up via `ListReactions` for the webhook payload, `server/router/api/v1/memo_service.go:545-550`) are **not** deleted — there's no FK/cascade on `reaction.content_id` and no explicit delete call in this path, so they are read but not affected.
