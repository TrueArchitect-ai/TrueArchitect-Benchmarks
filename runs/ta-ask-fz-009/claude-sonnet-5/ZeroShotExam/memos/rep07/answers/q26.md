q26. **Tables affected when `DeleteMemo` runs: `memo`, `memo_relation`, `attachment`, and `memo_share`.**

- **`memo`** — direct delete. `store.Store.DeleteMemo` (store/memo.go:140-159) ultimately calls the driver's `DeleteMemo`, e.g. `DELETE FROM memo WHERE id = ?` (store/db/sqlite/memo.go:237-248, same pattern in mysql/postgres). The API handler `APIV1Service.DeleteMemo` (server/router/api/v1/memo_service.go:518-593) also loops over comment memos and calls `store.DeleteMemo` again for each (memo_service.go:567-577), so multiple `memo` rows can be removed.

- **`memo_relation`** — explicit cascade code. `store.Store.DeleteMemo` explicitly cleans up relation rows where the memo is either the source or the target before deleting the memo itself: `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` and `...{RelatedMemoID: &delete.ID}` (store/memo.go:141-147), executed as `DELETE FROM memo_relation WHERE memo_id = ? / related_memo_id = ?` (store/db/sqlite/memo_relation.go:137-159).

- **`attachment`** — explicit cascade code. `store.Store.DeleteMemo` lists attachments tied to the memo and deletes each one via `s.DeleteAttachment` (store/memo.go:148-157), which removes storage and then issues `DELETE FROM attachment WHERE id = ?` (store/attachment.go:132-149, store/db/sqlite/attachment.go:212-238-style statements).

- **`memo_share`** — cascades at the schema level, not in Go code. `memo_share.memo_id` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three dialects (store/migration/sqlite/LATEST.sql:109, store/migration/mysql/LATEST.sql:108, store/migration/postgres/LATEST.sql:108), so deleting the `memo` row cascades to `memo_share` rows automatically when the DB enforces the constraint. Note: the sqlite driver opens its connection with `_pragma=foreign_keys(0)` (store/db/sqlite/sqlite.go:53), so on sqlite this cascade is declared but not actually enforced at the DB layer unless that pragma changes — worth flagging as a discrepancy between schema intent and runtime behavior.

**Not affected:** `reaction` — `DeleteMemo` only calls `s.Store.ListReactions` to build the webhook payload (memo_service.go:545-550); it never calls `store.DeleteReaction`, so reaction rows tied to the deleted memo are left behind (no FK exists from `reaction.content_id` to `memo`, since `content_id` is just a string reference).
