**Evidence:**
- Each backend's user-deletion path runs explicit, hand-written `DELETE FROM reaction` statements inside the deletion transaction — identical logic replicated per driver:
  - `store/db/mysql/user_delete.go:417-440` — `deleteReactionsByContentIDsTx` (deletes reactions on the user's content, e.g. memos/comments) and `deleteReactionsByCreatorTx` (deletes reactions the user itself created), both called from the main delete flow at `store/db/mysql/user_delete.go:96` and `:102`.
  - `store/db/postgres/user_delete.go:380-402`, called at `store/db/postgres/user_delete.go:96` and `:102` — same two functions, same SQL (`DELETE FROM reaction WHERE content_id IN ...` / `WHERE creator_id = ...`).
  - `store/db/sqlite/user_delete.go:380-402`, called at `store/db/sqlite/user_delete.go:96` and `:102` — same pattern again.
- These are plain `tx.ExecContext` calls issuing manual `DELETE` statements against the `reaction` table, not something triggered automatically by the schema (I did not find `ON DELETE CASCADE` on the reaction table's FK, and no DB trigger was found for this table in the migration files I checked (`store/migration/{mysql,postgres,sqlite}/LATEST.sql`) — the deletion is driven entirely from Go before/alongside the user row's removal, so if this code weren't invoked the rows would remain).

So: reactions are removed by explicit Go-level DELETE statements executed as part of the user-deletion transaction in each of the three driver-specific `user_delete.go` files, not by an automatic database rule.
