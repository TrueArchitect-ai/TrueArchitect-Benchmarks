**Mechanism: explicit Go code** (not a database-level rule such as `ON DELETE CASCADE`).

**Evidence:**
- The `reaction` table schema, e.g. `store/migration/postgres/LATEST.sql:90-98` (and the equivalent MySQL/SQLite `LATEST.sql`), has no foreign-key constraint on `creator_id`/`content_id` and no `ON DELETE CASCADE` clause — so the database itself would not remove reaction rows when a user (or their memos) are deleted.
- Instead, each driver's user-deletion transaction explicitly deletes reactions in Go: `deleteUserTargetsTx` calls `deleteReactionsByContentIDsTx` (removing reactions attached to the deleted user's memo content) and `deleteReactionsByCreatorTx` (removing reactions the deleted user itself created), at `store/db/postgres/user_delete.go:96,102`, `store/db/mysql/user_delete.go:96,102`, and `store/db/sqlite/user_delete.go:96,102`.
- Those helper functions issue literal `DELETE FROM reaction WHERE content_id IN (...)` and `DELETE FROM reaction WHERE creator_id = ?` statements — see `store/db/postgres/user_delete.go:380-403`, `store/db/mysql/user_delete.go:417-440`, and `store/db/sqlite/user_delete.go:380-403`.

So reaction cleanup on user deletion is handled entirely by explicit application-level SQL executed inside the delete-user transaction, identical across all three supported drivers.
