**No** (with one narrow caveat for test code) — the store's MySQL driver constructor `mysql.NewDB` (`store/db/mysql/mysql.go:20`) is called from exactly one place in the whole codebase: the driver-selection factory `NewDBDriver` in `store/db/db.go:22`. `find_references` for `NewDB` across `*.go` turns up only the three factory call sites (`store/db/db.go:20,22,24` for sqlite/mysql/postgres) plus test helpers calling `sqlite.NewDB` — never `mysql.NewDB` — directly (`store/demo_seed_test.go:24`, `store/deployment_config_test.go:416`).

Caveats found, neither of which is "the MySQL driver" via the factory's abstraction:
- `store/db/mysql/auth_config_test.go:12` constructs a bare `&DB{}` struct literal to unit-test `IsRetryableAuthenticationMutationError`, which needs no live connection — it bypasses `NewDB` but isn't opening a real MySQL driver.
- `store/test/containers.go:145` (test container helper) calls `sql.Open("mysql", dsn)` directly via `database/sql`, but this is throwaway test infrastructure for creating a fresh test database, not a construction of the application's `store.Driver`/`mysql.DB` abstraction.

So within the actual application code path, the MySQL driver is only ever built through `db.NewDBDriver`'s factory switch.
