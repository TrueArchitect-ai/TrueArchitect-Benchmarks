**Mechanism: explicit Go code**, not a database-level rule (no `ON DELETE CASCADE`/foreign key/trigger exists on the `reaction` table — its schema is a plain table with no FK constraints, e.g. `store/migration/postgres/LATEST.sql:91-98`, and identically in `store/migration/mysql/LATEST.sql:90-97` and `store/migration/sqlite` — just columns and a unique constraint, no `REFERENCES`/`CASCADE`).

Instead, each of the three DB backends implements `DeleteUser` as an explicit transactional Go routine that deletes reactions in two passes:
- `deleteReactionsByContentIDsTx` — deletes reactions attached to the deleted user's own memos (matched by `content_id`), e.g. `store/db/postgres/user_delete.go:380-396`, `store/db/mysql/user_delete.go:417-`, `store/db/sqlite/user_delete.go:380-`.
- `deleteReactionsByCreatorTx` — deletes reactions the deleted user placed on *other* users' content (`DELETE FROM reaction WHERE creator_id = ?`), e.g. `store/db/postgres/user_delete.go:400-403`, and the mysql/sqlite equivalents at `store/db/mysql/user_delete.go:437-440` / `store/db/sqlite/user_delete.go:400-403`.

Both calls are invoked from the shared `DeleteUser` transaction flow (`store/db/postgres/user_delete.go:96,102`, mirrored in mysql/sqlite at the same line numbers), so reactions are removed both as content owned by the deleted user and as actions taken by them, while reactions other users placed on content that isn't being deleted (peer content) are preserved. This is explicitly verified in `store/test/user_delete_test.go:97-220`, which confirms one user's own/placed reactions are gone after deletion while a peer's unrelated reaction (`peerReactionToKeep`) survives.
