**Premise correction:** there is no Redis anywhere in this codebase — a repo-wide search for "redis" (case-insensitive, across all 1042 tracked files) returns zero matches. The cache layer is not backed by an external service at all; it's a pure in-process, in-memory cache.

**Actual mechanism:** the cache is `store/cache.Cache`, a self-contained in-memory implementation (`store/cache/cache.go`) with its own background cleanup goroutine, no network client, and no connection config of any kind. It's constructed and wired up entirely in-process by `store.New` — `store/store.go:38-53` — which builds three separate `cache.Cache` instances (`instanceSettingCache`, `userCache`, `userSettingCache`, fields at `store/store.go:27-29`) from a single `cache.Config` literal defined inline at `store/store.go:40-45`.

**TTL for user entries:** the `userCache` is created with `DefaultTTL: 10 * time.Minute` (`store/store.go:41`, matching the package's own `cache.DefaultConfig()` default at `store/cache/cache.go:59`), with a `CleanupInterval` of 5 minutes and a cap of `MaxItems: 1000`. Entries are read/written through `store.Store.GetUser`/`ListUsers` (`store/user.go:148-171`), which populate `userCache` via `userCacheKey(user.ID)` on lookup.
