**Mechanism: explicit Go code (application-level cascade), not a database-level rule.**

**Evidence checked:**

1. **No DB-level cascade exists.** The `reaction` table schema has no foreign key with `ON DELETE CASCADE` (or any FK at all) referencing the user — confirmed in `store/migration/mysql/LATEST.sql:90-98`, and the same simple-column definition (no FK constraint) is mirrored in `store/migration/postgres/LATEST.sql:90-97` and `store/migration/sqlite/*` (grep of all three migration schemas above shows plain `CREATE TABLE reaction (... creator_id ...)` with no `REFERENCES`/`CASCADE` clause).

2. **Explicit Go deletion exists in each driver's `DeleteUser` path.** All three drivers (`store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`, `store/db/sqlite/user_delete.go`) implement identical logic:
   - `DeleteUser` (line 29 in each file) → `deleteUserTargetsTx` (line 92) calls `deleteReactionsByContentIDsTx` (line ~96, deletes reactions on memos the user owned) and `deleteReactionsByCreatorTx` (line ~102, deletes reactions the user personally made).
   - `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ...` (mysql `user_delete.go:437-439`, postgres `user_delete.go:400-402`, sqlite `user_delete.go:400-402`) — this is the direct removal of the deleted user's own emoji reactions.
   - `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` (mysql `:417-422`, postgres `:380-385`, sqlite `:380-385`) — removes reactions (by anyone) attached to memos that are being deleted along with the user.

All of this happens inside the same SQL transaction as the rest of the user-delete cascade (settings, identities, memos, attachments, inboxes, shares), so it's a coordinated application-level deletion, not something the database enforces on its own via constraints.
