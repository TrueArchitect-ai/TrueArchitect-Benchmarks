**Mechanism: explicit Go code** — not a database-level rule (no `ON DELETE CASCADE`/foreign key or trigger governs the `reaction` table).

**Evidence:**
- Schema: `reaction` table definitions in `store/migration/{mysql,postgres,sqlite}/LATEST.sql` (e.g. `store/migration/mysql/LATEST.sql:91-98`) declare only columns and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no foreign key to `user`, no `ON DELETE CASCADE`, no trigger.
- Deletion logic: each driver's `DeleteUser` transaction explicitly issues two reaction deletes as part of `deleteUserTargetsTx`:
  - `deleteReactionsByContentIDsTx` — deletes reactions on all memos owned by the user (by `content_id`, i.e. `memos/{uid}`), e.g. `store/db/mysql/user_delete.go:417-425`, `store/db/postgres/user_delete.go:380-388`, `store/db/sqlite/user_delete.go:380-388`.
  - `deleteReactionsByCreatorTx` — deletes reactions the user themselves created (by `creator_id`), e.g. `store/db/mysql/user_delete.go:437-440`, `store/db/postgres/user_delete.go:400-403`, `store/db/sqlite/user_delete.go:400-403`.
  - Both are invoked in sequence from `deleteUserTargetsTx` (e.g. `store/db/mysql/user_delete.go:96-104`) before the memo, memo_relation, and user rows are removed, all within the same DB transaction.

This confirms the mechanism is application-level (Go) code executing explicit `DELETE FROM reaction ...` statements in the delete-user transaction, identical across all three supported drivers.
