h05. By explicit Go code, not a database-level rule.

Evidence checked:
- `store/migration/mysql/LATEST.sql:90-98` — the `reaction` table schema has no `FOREIGN KEY`/`ON DELETE CASCADE` clause referencing `user`; `creator_id` is just a plain `INT NOT NULL` column. Same pattern holds in postgres/sqlite equivalents (`store/migration/postgres/LATEST.sql:90-97`, `store/migration/sqlite/LATEST.sql` region for `reaction`). So there is no DB-level cascade rule.
- `store/db/mysql/user_delete.go:437-440` — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` for the deleted user's own reactions.
- `store/db/mysql/user_delete.go:417-425` — `deleteReactionsByContentIDsTx` also deletes reactions on memos the user authored, matched via `content_id IN (...)` (the memo's own content IDs), keyed off `memoContentIDsFromRefs` (`user_delete.go:549-555`).
- Both are invoked explicitly inside the transactional deletion pipeline `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:92-127`, calls at lines 96 and 102), which runs before the memo rows and user row themselves are deleted.

This confirms the removal is done by explicit application-level Go code issuing `DELETE FROM reaction ...` statements inside the user-deletion transaction, not by a foreign-key cascade at the schema level (the postgres/sqlite drivers under `store/db/postgres` and `store/db/sqlite` mirror this same pattern per the earlier reference scan of `attachmentIDsFromList`/similar helpers across all three drivers).
