**Mechanism: explicit Go code** (not a database-level `ON DELETE CASCADE` rule).

**Evidence:**

1. **Schema check** — the `reaction` table definition has no foreign key or cascade rule at all, in any dialect. E.g. `store/migration/mysql/LATEST.sql:91-98` (and equivalently `store/migration/postgres/LATEST.sql:91-97`, `store/migration/sqlite/LATEST.sql`) declares `reaction` with just `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type`, and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `REFERENCES ... ON DELETE CASCADE` on `creator_id` or `content_id`. So there is no DB-level rule that would auto-remove reactions when a user (or memo) is deleted.

2. **Go code check** — each driver's `DeleteUser` explicitly deletes reactions as part of the user-deletion transaction:
   - `store/db/mysql/user_delete.go:92-104` (`DeleteUser` → `deleteUserTargetsTx`): calls `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` (line 96, removing reactions on the user's own memos) and `deleteReactionsByCreatorTx(ctx, tx, userID)` (line 102, removing reactions the user made on others' content). Implementations at `store/db/mysql/user_delete.go:417-439` (`deleteReactionsByContentIDsTx`, `deleteReactionsByCreatorTx`) issue literal `DELETE FROM reaction WHERE content_id IN (...)` / `WHERE creator_id = ?` statements.
   - Same pattern mirrored identically in `store/db/postgres/user_delete.go:96,102` (functions at lines 380, 400) and `store/db/sqlite/user_delete.go:96,102` (functions at lines 380, 400).

All three SQL-dialect drivers implement the same explicit two-step deletion (by content owned by the deleted user's memos, and by the deleted user as reaction creator) inside the `DeleteUser` transaction — confirming this is handled entirely by explicit Go/SQL logic in the store layer, not by a schema-level cascade.
