h05. **Explicit Go code** (not a database-level rule).

**Evidence locations:**
- The `reaction` table schema has no `FOREIGN KEY ... ON DELETE CASCADE` referencing `user`/`creator_id` — the only cascade rule in the schema is on `memo_share.memo_id → memo.id` (`store/migration/mysql/LATEST.sql:108`). The `reaction` table (`store/migration/mysql/LATEST.sql:91`) has no such constraint, so the DB itself performs no automatic cleanup on user deletion.
- Instead, deletion is handled explicitly in the `DeleteUser` transaction in each driver package's `user_delete.go`. For MySQL: `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:92-127`) calls `deleteReactionsByContentIDsTx` (line 96, defined at line 417) — deletes reactions attached to memos owned by the deleted user (and their comment tree) via `DELETE FROM reaction WHERE content_id IN (...)` — and `deleteReactionsByCreatorTx` (line 102, defined at line 437) — deletes reactions the user themselves created via `DELETE FROM reaction WHERE creator_id = ?`.
- The identical pattern (`deleteReactionsByContentIDsTx` / `deleteReactionsByCreatorTx`) is duplicated in `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/sqlite/user_delete.go:96,102,380,400`, confirming all three supported drivers implement the same explicit Go-level cleanup rather than relying on any DB constraint.
