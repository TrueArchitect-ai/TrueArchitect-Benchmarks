**Concrete method:** `(*sqlite.DB).CreateMemo` — `store/db/sqlite/memo.go:16-41`, which builds and executes `INSERT INTO \`memo\` (...) VALUES (...) RETURNING \`id\`, \`created_ts\`, \`updated_ts\`, \`row_status\``.

**Determination method:** Traced the default driver-selection chain rather than assuming it:

1. `cmd/memos/main.go:122` — `viper.SetDefault("driver", "sqlite")`: with no flags/env overriding it, Viper resolves `driver` to `"sqlite"` by default.
2. `cmd/memos/main.go:43` — `Driver: viper.GetString("driver")` populates `profile.Profile.Driver` with that resolved value, so a default install gets `Profile.Driver == "sqlite"`.
3. `internal/profile/profile.go:110` (`Validate`) confirms sqlite is the driver path that also derives a default DSN file (`memos_prod.db`) when none is given — consistent with "default install, no DB flags."
4. `store/db/db.go:14-32` (`NewDBDriver`) switches on `profile.Driver`; the `"sqlite"` case (store/db/db.go:20) calls `sqlite.NewDB(profile)`, so the `store.Driver` backing every subsequent `Store` call is the sqlite implementation.
5. `store.Store.CreateMemo` (in `store/memo.go`) delegates to `s.driver.CreateMemo`, which at runtime is the sqlite one selected in step 4 — landing on `store/db/sqlite/memo.go:16`, the function that actually issues the `INSERT INTO memo` statement.

I ruled out the mysql/postgres candidates (`store/db/mysql/memo.go`, `store/db/postgres/memo.go`) because they're reached only when `profile.Driver` is `"mysql"`/`"postgres"` in the same switch — not the default value baked into `main.go`.
