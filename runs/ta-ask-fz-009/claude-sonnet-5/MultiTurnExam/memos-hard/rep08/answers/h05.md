h05. Explicit Go code; evidence:

- The `reaction` table schema (e.g. `store/migration/sqlite/LATEST.sql:91-99`, and equivalent mysql/postgres LATEST.sql) has no foreign key or `ON DELETE CASCADE` clause on `creator_id` — so there is no database-level rule doing the cleanup.
- Instead, each driver's user-deletion transaction explicitly deletes reactions in Go. In `store/db/sqlite/user_delete.go:96-102` (and identically in `store/db/mysql/user_delete.go:96-102` and `store/db/postgres/user_delete.go:96-102`), the delete-user flow calls `deleteReactionsByContentIDsTx` (removes reactions on content the deleted user owned, e.g. `store/db/sqlite/user_delete.go:380-397`, executing `DELETE FROM reaction WHERE content_id IN ...`) and `deleteReactionsByCreatorTx` (removes reactions the deleted user made on others' content, `store/db/sqlite/user_delete.go:400-403`, executing `DELETE FROM reaction WHERE creator_id = ...`), each mirrored in the mysql and postgres packages.
- `store/test/user_delete_test.go:97-220` confirms the intended behavior: it upserts reactions from the deleted user and a peer, then asserts after deletion that only the peer's reaction on unrelated content survives — matching explicit-code cleanup rather than a blanket cascade.

So reactions are removed by explicit application-level SQL executed inside the user-deletion transaction in each of the three DB driver packages, not by a DB-level cascade constraint, and not left orphaned.
