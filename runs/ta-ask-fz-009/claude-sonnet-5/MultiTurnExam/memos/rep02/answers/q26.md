q26. Tables affected when `DeleteMemo` runs:

- **memo** — the target row itself, deleted last via `driver.DeleteMemo` (store/memo.go:158; SQL executed in store/db/sqlite/memo.go:239, `DELETE FROM memo WHERE id = ?`)
- **memo_relation** — explicitly cleaned up in code before the memo delete, both where the memo is the source (`MemoID`) and the target (`RelatedMemoID`) (store/memo.go:142-147)
- **attachment** — explicitly cleaned up in code: attachments linked to the memo are listed then deleted one-by-one (store/memo.go:149-157)
- **memo_share** — not touched by explicit Go code, but cascades automatically at the DB level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/sqlite/LATEST.sql:109)

Note: `attachment.memo_id` (store/migration/sqlite/LATEST.sql:65) has no `ON DELETE CASCADE` FK constraint, which is exactly why the store layer must delete attachments explicitly in code rather than relying on the DB. `reaction` rows reference memo content by a string `content_id` (store/migration/sqlite/LATEST.sql:92-98), not a memo FK, so they are not cascaded or explicitly cleaned by `DeleteMemo`.
