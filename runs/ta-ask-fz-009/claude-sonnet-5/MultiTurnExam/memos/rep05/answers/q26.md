q26. **memo, memo_relation, attachment, memo_share**

- `memo` — the row itself is deleted (store/db/sqlite/memo.go:237, and mysql/postgres equivalents)
- `memo_relation` — explicitly deleted in `store.Store.DeleteMemo` for both directions (memo as source `MemoID` and as target `RelatedMemoID`), store/memo.go:142-147
- `attachment` — explicitly deleted per-attachment via `s.DeleteAttachment` after listing attachments for the memo, store/memo.go:148-157
- `memo_share` — not touched by explicit Go code, but the schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/sqlite/LATEST.sql:109, and equivalently mysql/LATEST.sql:108, postgres/LATEST.sql:108), so the DB engine cascades the delete to `memo_share` rows automatically.

Note: `reaction` rows referencing the memo via `content_id` are read (`ListReactions`) during the delete handler for webhook payload construction (server/router/api/v1/memo_service.go:545-550) but are not deleted as part of this flow — no FK/cascade or explicit delete call was found for `reaction` in `store.Store.DeleteMemo` or its schema.
