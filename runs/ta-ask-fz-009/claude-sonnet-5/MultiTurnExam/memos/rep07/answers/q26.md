Based on the code path in `store.Store.DeleteMemo` (store/memo.go:140) plus the API handler's explicit cascade code, the affected tables are:

q26. **memo** (the row itself, deleted last), **memo_relation** (rows where the memo is source or target — explicit `DeleteMemoRelation` calls, store/memo.go:142,145), **attachment** (rows linked via `memo_id`, deleted per-attachment via `DeleteAttachment`, store/memo.go:149-157).

Additionally, at the API handler layer (`APIV1Service.DeleteMemo`, server/router/api/v1/memo_service.go:518+), any child **memo** rows that are comments (found via `memo_relation` of type comment) are recursively deleted first — server/router/api/v1/memo_service.go:567-577 — which in turn triggers the same cascade (their own `memo_relation` and `attachment` cleanup) for each comment memo.

Note: `memo_share` has a SQL-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/sqlite/LATEST.sql:109), so it is also affected — but implicitly via the database's cascade constraint rather than explicit Go code. I did not find explicit application-level cleanup of `reaction` rows tied to a deleted memo's `content_id` in `DeleteMemo` itself (reaction deletion by content ID appears only in the user-deletion path, e.g. `store/db/sqlite/user_delete.go:96`), so `reaction` rows referencing a deleted memo are not confirmed to be cleaned up by `DeleteMemo`.
