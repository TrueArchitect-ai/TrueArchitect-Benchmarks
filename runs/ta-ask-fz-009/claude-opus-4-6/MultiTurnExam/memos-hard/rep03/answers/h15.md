Memo visibility is enforced at these distinct sites:

1. **`APIV1Service.checkMemoReadAccess`** — `server/router/api/v1/memo_service.go:39`
   The central per-memo guard for the gRPC/Connect API. Checks `memo.Visibility` against the current user: PUBLIC is open, PROTECTED requires authentication, PRIVATE requires creator-only. Called by `GetMemo` (line 356), parent memo checks (line 367), and `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`).

2. **`APIV1Service.ListMemos` query-level filtering** — `server/router/api/v1/memo_service.go:218–226`
   Before any memos are fetched, the query is scoped: anonymous users get only `Public` (line 219); authenticated users viewing others' memos get `Public + Protected` (line 225); when viewing all users' memos, a CEL filter restricts to `creator_id == self OR visibility in ["PUBLIC", "PROTECTED"]` (line 222). This is a data-layer enforcement that prevents private memos from even being returned.

3. **`FileServerService.checkAttachmentPermission`** — `server/router/fileserver/fileserver.go:650`
   The HTTP file-serving surface. When serving attachment files (`/file/attachments/:uid/:filename`), it looks up the linked memo and enforces its visibility: PUBLIC memos are served to anonymous visitors (if the instance allows it), PRIVATE requires the creator or admin (line 699), and share tokens provide a fallback path (line 684).

4. **`APIV1Service.checkAttachmentAccess`** — `server/router/api/v1/attachment_service.go:422`
   The gRPC attachment service's own visibility check, separate from the file server. For memo-linked attachments, it checks `memo.Visibility`: PUBLIC is open (line 445), PRIVATE requires creator or super-user (line 451).

5. **RSS feed generation** — `server/router/rss/rss.go:90` and `server/router/rss/rss.go:141`
   Both the global RSS feed and per-user RSS feed hard-code `VisibilityList: []store.Visibility{store.Public}`, ensuring only PUBLIC memos ever appear in RSS output.
