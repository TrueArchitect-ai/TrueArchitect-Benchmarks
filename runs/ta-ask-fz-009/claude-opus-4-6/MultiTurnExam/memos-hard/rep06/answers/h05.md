**Mechanism: explicit Go code**, executed within the same database transaction that deletes the user.

**Evidence:** In every DB driver's `deleteUserTargetsTx` function, reactions are removed in two passes before the user row itself is deleted:

1. **Reactions on the user's memos** (by content ID) — `deleteReactionsByContentIDsTx` issues `DELETE FROM reaction WHERE content_id IN (…)`:
   - `store/db/mysql/user_delete.go:96` (call) → `:417–423` (implementation)
   - `store/db/postgres/user_delete.go:96` → `:380–386`
   - `store/db/sqlite/user_delete.go:96` → `:380–386`

2. **Reactions the user created on anyone's content** (by creator ID) — `deleteReactionsByCreatorTx` issues `DELETE FROM reaction WHERE creator_id = ?`:
   - `store/db/mysql/user_delete.go:102` (call) → `:437–440` (implementation)
   - `store/db/postgres/user_delete.go:102` → `:400–403`
   - `store/db/sqlite/user_delete.go:102` → `:400–403`

Both calls happen inside the transaction orchestrated by `deleteUserTargetsTx`, which is called from `DeleteUser`. There are no database-level `ON DELETE CASCADE` rules doing this work — it is all explicit application-layer SQL in Go.
