**Mechanism: explicit Go code** — reactions are removed by two explicit SQL `DELETE` statements executed within the user-deletion transaction, not by database-level foreign key cascades.

**Evidence locations:**

1. **`deleteReactionsByContentIDsTx`** (`store/db/sqlite/user_delete.go:380–388`) — deletes reactions whose `content_id` matches any of the user's memo content IDs (i.e., reactions *on* the user's memos, regardless of who created them): `DELETE FROM reaction WHERE content_id IN (…)`.

2. **`deleteReactionsByCreatorTx`** (`store/db/sqlite/user_delete.go:400–402`) — deletes reactions the user themselves created on *any* content: `DELETE FROM reaction WHERE creator_id = ?`.

3. Both are called from **`deleteUserTargetsTx`** (`store/db/sqlite/user_delete.go:96` and `:102`), which orchestrates all dependent deletions inside a single transaction before removing the user row itself.

The same pattern is present in the MySQL and PostgreSQL drivers (`store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`). I also checked the schema files (`store/migration/sqlite/LATEST.sql`, etc.) — the `reaction` table has no `ON DELETE CASCADE` foreign key that would handle this at the database level; it relies entirely on this Go-level cleanup.
