

Let me trace the webhook/notification delivery mechanism and its SSRF protection.

h02.

**Delivery function — `webhook.Post`** (`internal/webhook/webhook.go:120`). It marshals the payload to JSON, optionally signs it with HMAC-SHA256 (Standard Webhooks headers), and sends a POST via `safeClient` (line 152). Async dispatch uses `webhook.PostAsync` (line 184), which enqueues onto a buffered channel consumed by 4 goroutines spawned in `init()` (line 42).

**Protection mechanism — `safeDialContext` + `isReservedIP`** (`internal/webhook/webhook.go:59`, `internal/webhook/validate.go:44`). Two layers of SSRF defense:

1. **At connection time (dial-time guard):** The `safeClient` HTTP client uses a custom `Transport` whose `DialContext` is `safeDialContext` (`internal/webhook/webhook.go:34–36`). This function resolves the target hostname via DNS and checks every returned IP against a list of reserved/private CIDR ranges (loopback, RFC-1918, link-local/cloud IMDS, IPv6 equivalents) parsed at startup in `internal/webhook/validate.go:14–36`. If any IP matches, the connection is refused — this also defeats DNS rebinding attacks because the check happens at dial time, not just at registration time.

2. **At registration time (input validation):** `webhook.ValidateURL` (`internal/webhook/validate.go:62`) performs the same DNS-resolve-and-check when a webhook URL is first configured, rejecting it with a gRPC `InvalidArgument` error before it is ever stored.

Both checks are gated by `webhook.AllowPrivateIPs` (`internal/webhook/validate.go:41`), an opt-in flag wired from the `--allow-private-webhooks` CLI flag at `cmd/memos/main.go:49,133` for self-hosted deployments that intentionally target internal services.
