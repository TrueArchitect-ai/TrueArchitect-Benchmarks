**Engine:** [CEL (Common Expression Language)](https://github.com/google/cel-go) via `github.com/google/cel-go/cel`, wrapped in a custom `filter.Engine` at `internal/filter/engine.go`.

**Path:** `internal/filter/` — the key files are:
- `engine.go` — `Engine` struct, `Compile()` parses the CEL string into an AST then `buildCondition()` lowers it to a dialect-agnostic `Condition` IR (`internal/filter/ir.go`)
- `parser.go` — `buildCondition()` implementation that walks the CEL parsed expression
- `render.go` — `renderer` emits dialect-specific SQL from the `Condition` tree
- `schema.go` — declares `DialectName` (`sqlite`, `mysql`, `postgres`) and field metadata
- `helpers.go` — `AppendConditions()` convenience used by each DB driver

**Mechanism:** Each DB driver (e.g. `store/db/sqlite/memo.go:57–62`, and the analogous `postgres/memo.go`, `mysql/memo.go`) calls `filter.DefaultEngine()` to get the singleton CEL engine, then calls `filter.AppendConditions(…, filter.DialectSQLite/DialectPostgres/DialectMySQL, …)` which compiles the CEL filter string into a dialect-agnostic condition IR via `Engine.Compile()` (CEL parse → AST → `Condition` tree), and then `Program.Render(RenderOptions{Dialect: …})` walks that IR to emit dialect-specific SQL `WHERE` fragments and parameterized args, which are appended directly to the query's `where` clauses and bind-arg slices.

**One-sentence summary:** The `google/cel-go` CEL engine (`internal/filter/engine.go`) parses the filter expression into a CEL AST, lowers it to an intermediate `Condition` tree (`internal/filter/parser.go` → `internal/filter/ir.go`), and a dialect-aware renderer (`internal/filter/render.go`) emits SQL fragments tailored to SQLite, MySQL, or Postgres based on the `DialectName` passed by each store driver.
