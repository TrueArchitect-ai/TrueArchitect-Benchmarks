The following database tables are affected when `DeleteMemo` runs:

1. **`memo`** — the memo row itself is deleted (`store/db/mysql/memo.go:261`, `store/db/postgres/memo.go:246`, `store/db/sqlite/memo.go:239`).

2. **`memo_relation`** — explicitly deleted in `store.Store.DeleteMemo` (`store/memo.go:142–146`), which calls `DeleteMemoRelation` twice: once for `MemoID` and once for `RelatedMemoID`, cleaning up both sides of any relation. The SQL hits `memo_relation` (`store/db/mysql/memo_relation.go:137`).

3. **`attachment`** — explicitly deleted in `store.Store.DeleteMemo` (`store/memo.go:149–157`), which lists all attachments for the memo and calls `DeleteAttachment` for each, hitting the `attachment` table (`store/attachment.go:148`).

4. **`memo_share`** — deleted via **database-level `ON DELETE CASCADE`** on the `memo_id` foreign key (`store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). When the `memo` row is deleted, the DB engine cascades the delete to `memo_share`.

Additionally, the API-level handler (`server/router/api/v1/memo_service.go:567–577`) **recursively deletes comment memos**: it finds `memo_relation` rows of type `Comment` pointing at the memo, then calls `store.Store.DeleteMemo` for each comment — so the same four tables are affected again for each comment memo.

**Table list:** `memo`, `memo_relation`, `attachment`, `memo_share`
