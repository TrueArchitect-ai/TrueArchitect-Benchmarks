**Interceptor path:** `web/src/connect.ts` (the `authInterceptor` function, line 156)

**Token kinds:** Three token types are managed across the auth flow:
1. **Access tokens (JWT)** — short-lived (15 min), sent as `Bearer` in the `Authorization` header. Stored in-memory and localStorage (`web/src/auth-state.ts`). The interceptor attaches them to every request and proactively refreshes them before expiry.
2. **Refresh tokens** — sent as an HTTP-only cookie (with `credentials: "include"`). Used by `refreshToken()` RPC (line 75) to obtain new access tokens when the current one expires or a 401 is received. Validated server-side against the database for revocation.
3. **Personal Access Tokens (PAT)** — long-lived tokens for programmatic access, prefixed with a distinguishing string. Also sent as `Bearer` tokens but resolved through a different server-side path (hash-based DB lookup).

**Backend validation package:** `server/auth` (`server/auth/authenticator.go`). The `Authenticator` struct provides `AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, and `AuthenticateByPAT`. The Connect-layer `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go` delegates to an `Authorizer` (`server/router/api/v1/authz.go`), which in turn calls through to `server/auth.Authenticator.Authenticate()`.

**Compact format:**  
`web/src/connect.ts`; access token (JWT), refresh token (cookie), personal access token (PAT); `server/auth`
