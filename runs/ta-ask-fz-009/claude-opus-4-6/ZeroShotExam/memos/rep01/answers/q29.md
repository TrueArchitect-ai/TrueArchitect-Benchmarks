**Interceptor path:** `web/src/connect.ts` — the `authInterceptor` function (line 156) is a Connect `Interceptor` that attaches a `Bearer` token to every outgoing request's `Authorization` header, handles 401 retry with token refresh, and redirects on permanent auth failure.

**Token kinds managed (3):**
1. **Access Token (JWT, short-lived, ~15 min)** — stored in-memory and `localStorage` (`web/src/auth-state.ts`); set on the `Authorization: Bearer <token>` header by the interceptor.
2. **Refresh Token** — an HTTP-only cookie (not managed in JS); used by `refreshToken()` RPC (via a separate interceptor-free transport at line 65) to obtain new access tokens. Validated server-side via `AuthenticateByRefreshToken` (`server/auth/authenticator.go:61`).
3. **Personal Access Token (PAT)** — long-lived tokens for programmatic access, also sent as `Bearer` tokens; validated server-side via `AuthenticateByPAT` (`server/auth/authenticator.go:102`).

**Backend validation package:** `server/auth` — specifically the `Authenticator` struct in `server/auth/authenticator.go`. The Connect-layer wiring is in `server/router/api/v1/authz.go` (the `Authorizer` struct, line 26), whose `Authenticate` method (line 44) delegates to `auth.Authenticator`, and whose `CheckAccess` method (line 58) enforces per-procedure authorization. The `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208` calls `Authorizer.Authenticate` + `Authorizer.CheckAccess` on every unary request.
