When `DeleteMemo` runs, the following database tables are affected:

1. **`memo_relation`** — Explicitly deleted via `store.Store.DeleteMemo` (`store/memo.go:142-147`), which calls `driver.DeleteMemoRelation` twice (once for `memo_id` match, once for `related_memo_id` match), issuing `DELETE FROM memo_relation` (`store/db/sqlite/memo_relation.go:148-150`).

2. **`attachment`** — Explicitly deleted via `store.Store.DeleteMemo` (`store/memo.go:149-157`), which lists attachments for the memo and deletes each one with `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go:212`).

3. **`memo`** — The memo row itself is deleted via `driver.DeleteMemo` at the end: `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:239`, `store/memo.go:158`).

4. **`memo_share`** — Cascade-deleted by the database engine via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, and equivalently in MySQL/Postgres schemas).

Additionally, the service layer (`server/router/api/v1/memo_service.go:567-577`) recursively deletes **comment memos** by listing `memo_relation` rows of type `Comment` where the memo is the `related_memo_id`, and calling `store.Store.DeleteMemo` for each comment — so the same four tables are affected again for each comment.
