**Interceptor path:** `web/src/connect.ts` (lines 156–178) — the `authInterceptor` function, a Connect `Interceptor` that attaches a `Bearer` token to every outgoing request's `Authorization` header and reactively retries on `Unauthenticated` (code 16) after refreshing.

**Token kinds managed:**

1. **Access token (JWT)** — short-lived (15 min), stored in-memory and persisted to `localStorage` (`memos_access_token` key, managed in `web/src/auth-state.ts`). Sent as `Authorization: Bearer <token>` on every request.
2. **Refresh token** — used via `AuthService.RefreshToken` RPC (called through a separate interceptor-free transport at `web/src/connect.ts:65–72`) to obtain a new access token when the current one expires or a 401 is received. The refresh token itself travels as an HTTP cookie (`credentials: "include"`, line 60).
3. **Personal Access Token (PAT)** — the backend `Authenticator` also accepts PATs as Bearer tokens (see `AuthenticateByPAT` method at `server/auth/authenticator.go:26`), so the same `Authorization` header path carries both JWTs and PATs.

**Backend validation package:** `server/auth` — specifically the `auth.Authenticator` struct defined at `server/auth/authenticator.go:26`. It is wrapped by `v1.Authorizer` (`server/router/api/v1/authz.go:26`) which the server-side `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208`) delegates to. `Authenticator.Authenticate()` dispatches to `AuthenticateByAccessTokenV2` (JWT) or `AuthenticateByPAT` (personal access token) depending on the bearer token format.
