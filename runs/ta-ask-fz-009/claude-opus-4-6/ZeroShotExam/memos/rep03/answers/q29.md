**Interceptor path:** `web/src/connect.ts` — the `authInterceptor` function (line 156) is a Connect `Interceptor` wired into the shared transport at line 188. It attaches a `Bearer` token to every outgoing request via the `Authorization` header, handles reactive 401 retry with token refresh, and proactively refreshes near-expiry tokens before sending.

**Token kinds managed (three):**

1. **JWT access tokens** — short-lived (15 min), sent as `Bearer <token>` in the `Authorization` header. Stored in-memory and `localStorage` (`memos_access_token`). Managed in `web/src/auth-state.ts`.
2. **JWT refresh tokens** — long-lived (30 days), carried as an HTTP-only cookie (`memos_refresh`, see `server/auth/token.go:49`). The frontend calls `AuthService.refreshToken` (via a separate interceptor-less transport, `web/src/connect.ts:65-72`) to obtain a fresh access token using the cookie.
3. **Personal Access Tokens (PATs)** — long-lived opaque strings prefixed `memos_pat_`, SHA-256-hashed for DB lookup (`server/auth/token.go:189-203`). Also sent as `Bearer` tokens.

**Backend validation package:** `server/auth` (files `server/auth/authenticator.go`, `server/auth/token.go`, `server/auth/extract.go`, `server/auth/context.go`). The `Authenticator` struct in `server/auth/authenticator.go` is the central validator: its `Authenticate` method (line 213) is called by the server-side `AuthInterceptor.WrapUnary` in `server/router/api/v1/connect_interceptors.go:222`. It dispatches to `ParseAccessTokenV2` for JWT access tokens and `AuthenticateByPAT` / `AuthenticateByRefreshToken` for the other two token types.
