The following database tables are affected when `DeleteMemo` runs:

1. **`memo`** — the memo row itself is deleted (`DELETE FROM memo WHERE id = ?`) via `store.Driver.DeleteMemo` (`store/db/sqlite/memo.go:239`, `store/db/mysql/memo.go:261`, `store/db/postgres/memo.go:246`).

2. **`memo_relation`** — explicitly deleted in `store.Store.DeleteMemo` (`store/memo.go:142–146`) via two `DeleteMemoRelation` calls (once for `memo_id`, once for `related_memo_id`), issuing `DELETE FROM memo_relation` (`store/db/mysql/memo_relation.go:137`).

3. **`attachment`** — explicitly deleted in `store.Store.DeleteMemo` (`store/memo.go:149–157`) via `DeleteAttachment` for each attachment linked to the memo, issuing `DELETE FROM attachment WHERE id = ?` (`store/db/mysql/attachment.go:231`).

4. **`memo_share`** — deleted by **ON DELETE CASCADE** from the `memo_id` foreign key referencing `memo(id)` (`store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`).

Additionally, at the API layer (`server/router/api/v1/memo_service.go:567–577`), comment memos (child memos linked via `MemoRelationComment`) are **recursively deleted** by calling `store.Store.DeleteMemo` for each comment, which cascades the same set of tables for every comment memo.
