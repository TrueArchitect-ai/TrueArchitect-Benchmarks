When `DeleteMemo` runs, the following database tables are affected:

1. **`memo`** — the memo row itself is deleted (`DELETE FROM memo WHERE id = ?`) via `store.driver.DeleteMemo` (`store/db/sqlite/memo.go:239`, `store/db/mysql/memo.go:261`, `store/db/postgres/memo.go:246`)

2. **`memo_relation`** — all relation rows where the memo is either `memo_id` or `related_memo_id` are deleted via `store.driver.DeleteMemoRelation` (`store/memo.go:142–146`, SQL at `store/db/sqlite/memo_relation.go:148–150`)

3. **`attachment`** — all attachments linked to the memo are deleted via `store.driver.DeleteAttachment` (`store/memo.go:149–157`, SQL at `store/db/sqlite/attachment.go:212`)

4. **`memo` (comment memos)** — at the service layer (`server/router/api/v1/memo_service.go:567–577`), comment memos (found via `memo_relation` with type `Comment`) are recursively deleted by calling `store.Store.DeleteMemo` for each, which in turn cascades through `memo_relation` and `attachment` cleanup for those comments as well.

**Not deleted:** The `reaction` table is queried (`ListReactions`) for webhook dispatch purposes but reactions are **not** explicitly deleted in the `DeleteMemo` flow, and there are no foreign key `ON DELETE CASCADE` constraints in the schema.
