**Explicit Go code**; no database-level cascade is involved.

When a user is deleted, their emoji reactions are removed by two explicit `DELETE` SQL statements executed within the same transaction, across all three database drivers (MySQL, PostgreSQL, SQLite):

1. **`deleteReactionsByContentIDsTx`** — deletes all reactions *on* the user's memos (by `content_id`), i.e., reactions from any user on content the deleted user owned.
   - SQL: `DELETE FROM reaction WHERE content_id IN (...)` 
   - `store/db/mysql/user_delete.go:417–425`, `store/db/sqlite/user_delete.go:380`, `store/db/postgres/user_delete.go:380`

2. **`deleteReactionsByCreatorTx`** — deletes all reactions *created by* the deleted user (on anyone's content).
   - SQL: `DELETE FROM reaction WHERE creator_id = ?`
   - `store/db/mysql/user_delete.go:437–439`, `store/db/sqlite/user_delete.go:400`, `store/db/postgres/user_delete.go:400`

Both are called from `deleteUserTargetsTx` (e.g., `store/db/mysql/user_delete.go:96–103`) inside the delete-user transaction.

**No database-level cascade exists**: the `reaction` table schema has no `FOREIGN KEY ... ON DELETE CASCADE` in any dialect — confirmed in `store/migration/sqlite/LATEST.sql:92–99`, `store/migration/mysql/LATEST.sql:91–98`, `store/migration/postgres/LATEST.sql:91–98`. The `creator_id` and `content_id` columns are plain columns with no FK constraints at all.
