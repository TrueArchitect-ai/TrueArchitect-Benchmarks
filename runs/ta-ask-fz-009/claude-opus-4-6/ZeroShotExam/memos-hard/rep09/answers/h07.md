After the user row is returned (which carries the `AvatarURL` field — a base64 data URI stored in the database), control returns to `serveUserAvatar` which calls:

7. `FileServerService.parseDataURI` — `server/router/fileserver/fileserver.go:737`

This decodes the base64 data URI from the `user.AvatarURL` column into raw image bytes, then the handler writes them directly to the response via `c.Blob()`.

**Summary:** the avatar image is not a file on disk or in object storage — it is a base64-encoded data URI stored inline in the `user` table's `avatar_url` column. There is no attachment/blob-storage hop. An intermediate cache layer (`store/cache/cache.go:123`) sits in `Store.GetUser` and can short-circuit the DB call if the user was previously fetched by ID (though username-based lookups always go to the DB driver).
