**The premise is incorrect — there is no Redis connection.** The cache layer is purely **in-memory**, not backed by Redis.

The cache is implemented as a generic in-process Go cache using `sync.Map` at `store/cache/cache.go`. It defines a `Cache` struct (line 67) and a `cache.Interface` (line 11) with `Set`, `Get`, `Delete`, `Clear`, etc. There is zero mention of Redis anywhere in the codebase (confirmed: grep for `redis` across 1,042 files returned no matches).

**How user entries are cached:**

- The `Store` struct (`store/store.go:28`) holds a `userCache *cache.Cache` field.
- It is initialized at `store/store.go:52` with `cache.New(cacheConfig)`, where `cacheConfig` is defined inline at `store/store.go:40–45`:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
  }
  ```
- User entries are cached via `s.userCache.Set(ctx, userCacheKey(user.ID), user)` (e.g., `store/user.go:98`), which delegates to `Cache.Set` (`store/cache/cache.go:93`), which calls `SetWithTTL` with the default TTL.

**TTL for user entries: 10 minutes** (`store/store.go:41`), applied uniformly — the same `DefaultTTL` governs instance-setting and user-setting caches as well. A background cleanup goroutine (`store/cache/cache.go:200`) sweeps expired items every 5 minutes.
