**Premise correction**: There is no Redis connection for the cache layer. The project implements an in-memory cache instead.

**Actual mechanism**: 

The cache layer is configured in **`store/store.go`** (lines 38–60), where the `Store` struct is initialized with three in-memory cache instances:
- `userCache` (for users)
- `userSettingCache` (for user settings)  
- `instanceSettingCache` (for instance settings)

The cache implementation itself lives in **`store/cache/cache.go`** (a thread-safe, in-memory cache with TTL and memory management).

**TTL for user entries**: All three cache instances—including `userCache` for user entries—use the same default configuration defined in `store/store.go` lines 40–45:
- **DefaultTTL: 10 minutes** (10 * time.Minute)
- CleanupInterval: 5 minutes
- MaxItems: 1000

User entries are stored in `userCache` with the default 10-minute TTL via `Set()` calls (e.g., `store/user.go` line 98: `s.userCache.Set(ctx, userCacheKey(user.ID), user)`). The cache does not use `SetWithTTL()` with a custom duration—only the standard `Set()` method, which applies the default TTL from the config.
