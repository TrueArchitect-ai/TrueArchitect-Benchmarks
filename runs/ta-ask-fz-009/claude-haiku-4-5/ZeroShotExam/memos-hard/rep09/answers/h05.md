**Mechanism: Explicit Go code; no database-level foreign key constraint.**

When a user is deleted, emoji reactions are removed by **explicit Go code via two separate DELETE operations**:

1. **Reactions on the user's own memos** — deleted by `deleteReactionsByContentIDsTx()` (line 96 of `store/db/mysql/user_delete.go`), which deletes all reactions where `content_id` matches the deleted user's memos (memos/{uid}).

2. **Reactions created by the user** — deleted by `deleteReactionsByCreatorTx()` (line 102 of `store/db/mysql/user_delete.go`), which deletes all reactions where `creator_id` equals the deleted user's ID.

Both operations execute as explicit SQL `DELETE` statements within a transaction during the `DeleteUser()` function.

**Why no database-level constraint:** The `reaction` table schema (MySQL, PostgreSQL, SQLite versions all identical across `store/migration/{mysql,postgres,sqlite}/0.20/00__reaction.sql`) has no foreign key constraint on `creator_id` pointing to the `user` table. The table only defines a composite UNIQUE constraint on `(creator_id, content_id, reaction_type)`.
