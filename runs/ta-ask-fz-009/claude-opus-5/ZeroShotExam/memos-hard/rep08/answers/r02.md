**Premise correction: there is no per-user API rate-limiting middleware in this repository.** Nothing registers a rate limiter, so there are no per-user request limits to report.

Evidence:

- The code graph returns a **certified miss** for `rate limit` / `ratelimit` across all 7,293 indexed symbols. Text search for `rate.?limit|throttl|limiter|golang.org/x/time/rate` finds only aspirational prose — `internal/email/README.md:286` ("### 5. Implement Rate Limiting", a suggested-extension section) and `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"). No implementation.
- The full server middleware stack is two entries: `server/server.go:51` `middleware.Recover()` and `server/server.go:52` `newCORSMiddleware(profile)`.
- The Connect interceptor chain is registered at `server/router/api/v1/v1.go:133-138` and contains exactly four interceptors — `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor` — all defined in `server/router/api/v1/connect_interceptors.go`. None does rate limiting; the file's only `CodeResourceExhausted` reference (line 153) is error *classification* for logging, not enforcement.

What does exist, and is probably what the question is reaching for — these are **global concurrency caps and payload caps, not per-user rate limits**:

| Guard | Location | Limit |
|---|---|---|
| Request body size (gateway + Connect) | `server/router/api/v1/v1.go:20`, applied at lines 126, 141, 144 | `maxAPIRequestBytes = 256 << 20` (256 MiB) |
| Concurrent thumbnail generation | `server/router/api/v1/v1.go:59` | semaphore weight 3 |
| Concurrent image/EXIF processing | `server/router/api/v1/v1.go:60`, acquired at `attachment_service_image.go:67` | semaphore weight 2 |

The image semaphore is the only guard that rejects rather than queues-with-context: on acquire failure `server/router/api/v1/attachment_service.go:158-161` returns `codes.ResourceExhausted, "too many image processing requests"`. That message reads like rate limiting but it is a process-wide concurrency slot shared by all callers — one user's uploads can exhaust it for everyone, and no user identity is consulted anywhere in the path.
