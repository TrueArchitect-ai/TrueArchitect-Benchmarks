**Key architectural point:** avatars are *not* files. `user.avatar_url` is stored as a base64 **data URI in the `user` row** (`store/db/sqlite/user.go:76` selects `avatar_url` into `store.User.AvatarURL`), and the handler decodes it in-process (`parseDataURI`, fileserver.go:737-750) before writing the blob. No filesystem or S3 hop is involved, unlike `serveAttachmentFile` (fileserver.go:132) which branches on `AttachmentStorageType` LOCAL/S3/database.

Other details worth noting:
- **Cross-user access is by design, gated only at instance level:** the viewer check (fileserver.go:173-181) runs only when `Profile.AllowAnonymous()` is false; it verifies *a* session exists, not that the viewer may see *that* user. Lookup is by username (`store.FindUser{Username: &identifier}`), so any authenticated viewer can fetch any user's avatar.
- **Cache hop:** `Store.GetUser` only consults `userCache` when looking up by ID (store/user.go:149-156); a username lookup always falls through to `ListUsers` → driver → DB, then populates the cache (store/user.go:143).
- **Response hardening:** MIME allow-list `avatarAllowedTypes` (fileserver.go:75), `setSecurityHeaders` with `nosniff`/`X-Frame-Options: DENY`/restrictive CSP (fileserver.go:758), and `Cache-Control: public, max-age=3600` (fileserver.go:49).
- **Browser side:** `web/src/components/UserAvatar.tsx:12-18` renders whatever `avatarUrl` the API returned in the `User` message — if that value is itself a data URI, the browser never hits this endpoint at all; it only does so when the URL points at `/file/users/:identifier/avatar`.
