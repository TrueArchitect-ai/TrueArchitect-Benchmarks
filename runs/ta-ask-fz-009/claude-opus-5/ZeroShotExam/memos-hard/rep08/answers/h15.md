h15.

Memo visibility is enforced at many independent surfaces — the rule is *not* centralized in one guard. Distinct enforcement sites:

**Connect/gRPC API v1**
- `checkMemoReadAccess` — canonical single-memo read gate (public → open, protected → any authed user, private → creator only; archived → creator only) — `server/router/api/v1/memo_service.go:39-68`, called from GetMemo/parent-memo at `:356`, `:367` and from ListMemoComments at `server/router/api/v1/memo_service_comments.go:148`
- ListMemos query-level filter (`VisibilityList` / `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`) — `server/router/api/v1/memo_service.go:218-227`
- Comment listing filter for the comment memos themselves — `server/router/api/v1/memo_service_comments.go:156-161`
- Comment creation gate on the parent memo — `server/router/api/v1/memo_service_comments.go:41`
- Memo relation listing filter (`MemoFilter`) — `server/router/api/v1/memo_relation_service.go:107-131`
- Attachment access via memo visibility (`checkAttachmentAccess`) — `server/router/api/v1/attachment_service.go:419-455`
- ListMemoAttachments inline visibility check (duplicate of the above rule) — `server/router/api/v1/memo_attachment_service.go:213-225`
- Reaction list/upsert visibility checks — `server/router/api/v1/reaction_service.go:38`, `:83`
- User stats / activity filters (`VisibilityList` + CEL filter) — `server/router/api/v1/user_service_stats.go:81-92`, `:217-221`
- Notification read model gate (`canViewerAccessMemo`) — `server/router/api/v1/user_service_notifications.go:302-316`, applied at `:337`, `:342`, `:370`, `:385`
- Mention-notification eligibility (private memos don't notify non-creators) — `server/router/api/v1/memo_mention_helpers.go:62-84`
- SSE fan-out filter (`SSEClient.canReceive`) — `server/router/api/v1/sse_hub.go:134-144`

**Non-gRPC HTTP surfaces**
- File server attachment permission (`checkAttachmentPermission`, includes anonymous-instance rule and share-token fallback) — `server/router/fileserver/fileserver.go:650-703`
- RSS feeds — public-only `VisibilityList` — `server/router/rss/rss.go:90`, `:141`
- Sitemap — public-only `VisibilityList` — `server/router/frontend/frontend.go:149-151`

**Outbound notification**
- Email dispatcher's own copy of `canViewerAccessMemo` — `server/notification/email.go:306-320`

**Deliberate bypass worth noting:** `GetMemoByShare` returns the memo on a valid, unexpired share token with **no** visibility check (only archived/missing are hidden) — `server/router/api/v1/memo_share_service.go:153-192`; the matching bypass exists in the file server at `server/router/fileserver/fileserver.go:684-688`.

The duplication is the architectural risk here: the same predicate (`private → creator or admin`, `protected → authenticated`) is re-implemented in at least six places (`memo_service.go:63`, `attachment_service.go:451`, `memo_attachment_service.go:222`, `reaction_service.go:38/83`, `fileserver.go:699`, and twice as `canViewerAccessMemo` in `user_service_notifications.go` / `notification/email.go`), and the variants differ — e.g. `checkMemoReadAccess` has **no** admin override, while the attachment, reaction, notification and fileserver paths do.
