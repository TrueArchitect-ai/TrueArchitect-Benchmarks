I'll identify the identity provider abstraction and its concrete implementation.

h03.

**`internal/idp`; `internal/idp/oauth2`**

- **Abstraction:** `internal/idp/idp.go` — package `idp` defines the shared, protocol-neutral contract for third-party identity: `IdentityProviderUserInfo` with `Identifier`, `DisplayName`, `Email`, `AvatarURL` (`internal/idp/idp.go:3-8`). That struct is the boundary type every provider must produce, so callers upstream never touch protocol specifics.
- **Implementation:** `internal/idp/oauth2` — "Package oauth2 implements the OAuth2 identity provider integration" (`internal/idp/oauth2/oauth2.go:1-2`). It exposes `IdentityProvider` wrapping a `*storepb.OAuth2Config` (`oauth2.go:20-21`), the constructor `NewIdentityProvider` (`oauth2.go:27`), and the two protocol operations `ExchangeToken` (`oauth2.go:47`) and `UserInfo` (`oauth2.go:83`), the latter returning `*idp.IdentityProviderUserInfo` — the point where the concrete protocol collapses back into the abstraction. Backed by `golang.org/x/oauth2` (`go.mod:37`).

OAuth2 is the **only** concrete provider that ships: `internal/idp` contains exactly one implementation subpackage (`internal/idp/oauth2`), and the design docs confirm the scope boundary — "Supporting IdP types other than `OAUTH2` in this issue" and "Non-OAUTH2 IdP types" are listed as explicit non-goals (`docs/plans/2026-04-21-sso-user-identity-linkage/definition.md:47`, `plan.md:325`), with SAML named as out of scope in `design.md:71`. Note the abstraction here is a shared *data* contract rather than a Go interface — there is no `Provider` interface for multiple protocols to satisfy, so adding a second protocol would likely mean introducing one.
