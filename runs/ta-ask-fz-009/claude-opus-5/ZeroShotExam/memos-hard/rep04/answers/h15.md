h15.

Memo visibility is not funnelled through one guard — it is enforced at **twelve distinct sites** across four transport surfaces (Connect/gRPC API, the file server, SSE broadcast, and the public HTML/feed routes). Two enforcement *styles* coexist: per-object checks after a fetch, and query-level predicate injection into `store.FindMemo`.

**Per-object checks (post-fetch, deny with PermissionDenied/NotFound)**
`checkMemoReadAccess` — the canonical memo read guard (public / protected-needs-auth / private-needs-owner) — server/router/api/v1/memo_service.go:39-68 (callers: GetMemo :356, parent memo :367, ListMemoComments server/router/api/v1/memo_service_comments.go:148)
CreateMemoComment parent-memo guard — server/router/api/v1/memo_service_comments.go:41-42, plus comment-visibility coercion at :100
ListMemoAttachments inline re-implementation of the same rules — server/router/api/v1/memo_attachment_service.go:214-225
`checkAttachmentAccess` — attachment access derived from its memo's visibility — server/router/api/v1/attachment_service.go:422-455 (used by GetAttachment path :256)
Reaction read/write guards — server/router/api/v1/reaction_service.go:30-39 and :83-84
File-server attachment streaming (Echo, HTTP 403/401, with `share_token` bypass) — server/router/fileserver/fileserver.go:677-701

**Query-level filtering (rows never leave the store)**
ListMemos visibility predicate — server/router/api/v1/memo_service.go:218-227
User stats visibility predicate, both list and single-user paths — server/router/api/v1/user_service_stats.go:83-91 and :218-220
Sitemap: public-only memo listing — server/router/frontend/frontend.go:149-151
RSS feeds: public-only, instance and per-user — server/router/rss/rss.go:90 and :141

**Fan-out / push surfaces**
SSE per-client event filter (`canReceive`: private events only to creator or admin) — server/router/api/v1/sse_hub.go:134-144
Mention/notification eligibility gating on the mentioned target — server/router/api/v1/memo_mention_helpers.go:62-84, with content redaction by visibility in server/router/api/v1/user_service_notifications.go:309-312 and server/notification/email.go:313-316

**Two architectural notes worth flagging:**
1. The rules are *duplicated*, not shared. `memo_service.go:39`, `memo_attachment_service.go:214`, `attachment_service.go:445`, and `fileserver.go:677` each re-express "public → allow; private → owner only" independently, and they disagree in detail: `checkMemoReadAccess` has no admin override, whereas the attachment paths grant one via `isSuperUser(user)` (attachment_service.go:451, memo_attachment_service.go:222) and the file server via `user.Role != store.RoleAdmin` (fileserver.go:699). An admin can read a private memo's attachment but not the memo itself. That is an invariant drift, not an intentional asymmetry as far as the code shows.
2. `GetMemoByShare` (server/router/api/v1/memo_share_service.go:153) deliberately performs **no** visibility check — the share token is the authorization, so it returns private memos by design; only archived/expired are rejected (:164, :204). The file server mirrors that bypass at fileserver.go:684-689.
