**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside the store-level `DeleteUser` transaction, in all three dialect drivers. There is no database-level cascade, because the `reaction` table carries no foreign key at all.

**Two deletes, not one.** Both fire per user deletion (`deleteUserTargetsTx`, `store/db/sqlite/user_delete.go:92-127`):

1. `deleteReactionsByContentIDsTx` — removes *everyone's* reactions on the deleted user's memo subtree (`DELETE FROM reaction WHERE content_id IN (...)`), batched: `store/db/sqlite/user_delete.go:380-386`, `store/db/postgres/user_delete.go:380-386`, `store/db/mysql/user_delete.go:417-423`.
2. `deleteReactionsByCreatorTx` — removes the user's own reactions wherever they were left, including on other people's memos (`DELETE FROM reaction WHERE creator_id = ?`): `store/db/sqlite/user_delete.go:400-403`, `store/db/postgres/user_delete.go:400-403`, `store/db/mysql/user_delete.go:437-440`.

Both run before `deleteMemosTx` / `deleteUserRowTx` in the same transaction opened at `store/db/sqlite/user_delete.go:29-59`, so the cleanup is atomic — a failpoint before commit rolls the whole set back.

**Why it can't be a DB rule.** The `reaction` schema declares only a PK and a uniqueness constraint on `(creator_id, content_id, reaction_type)` — no `FOREIGN KEY`, no `ON DELETE CASCADE`, and `content_id` is a *text* resource name (`memos/{uid}`), not a memo FK: `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:90-98`, `store/migration/mysql/LATEST.sql:90-98` (contrast `memo_share`, which does declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, e.g. `store/migration/postgres/LATEST.sql:108`). The text `content_id` is exactly why the app layer has to collect memo resource names first and delete by name list.

**Call path.** `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:393-455`) does authz, then delegates the whole cascade to `s.Store.DeleteUser`; it does no reaction work itself — attachment blob cleanup is the only post-transaction step.

**Behavior is pinned by tests.** `server/router/api/v1/test/user_service_delete_test.go:186-211` seeds a peer's reaction on the deleted user's memo, a peer reaction on the user's comment, the user's reaction on a foreign memo, and a peer reaction on a foreign memo; lines 287-298 assert the first three are gone and the unrelated peer reaction survives. Rollback coverage at lines 366-371 and 429-431 asserts the reaction is still present when the transaction aborts.
