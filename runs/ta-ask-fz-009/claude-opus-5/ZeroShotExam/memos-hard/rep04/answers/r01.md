**Premise correction:** there is no Redis anywhere in this repository — no client dependency, no connection config, no `redis` identifier of any kind. A case-insensitive text search for `redis` across all 1042 files returns zero matches, and the code graph surfaces no Redis symbol. The cache layer is a purely **in-process, in-memory** cache, so there is no connection to configure at all (no host, port, DSN, or pool).

**Actual mechanism**

- **Implementation:** `store/cache/cache.go` — a hand-rolled thread-safe cache built on `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:67`), behind the `cache.Interface` contract (`store/cache/cache.go:11`). Expiry is per-entry (`item.expiration`, `store/cache/cache.go:35`), swept by a background `cleanupLoop` goroutine (`store/cache/cache.go:200`) and lazily on read (`Get` deletes expired keys, `store/cache/cache.go:135`).
- **Where it's "configured":** hardcoded in `store.New`, not in any config file or env var — `store/store.go:40-45` builds a `cache.Config` with `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`. The same config instance is used for all three caches: `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). `cache.DefaultConfig()` (`store/cache/cache.go:57`) carries identical values but isn't what the store calls.
- **TTL applying to user entries: 10 minutes.** Every user write path calls `s.userCache.Set(...)` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:93-94`). No user code path calls `SetWithTTL` with a custom duration, so users inherit the 10-minute default. Keys are just the stringified user ID (`userCacheKey`, `store/user.go:88`); reads hit the cache only when looking up by ID (`store/user.go:150`).
- **Invalidation beyond TTL:** user deletion explicitly evicts the user key and its settings keys (`deleteUserCache`, `store/user_delete.go:39-46`); cache goroutines are stopped in `Store.Close` (`store/store.go:74-76`).

Two consequences worth noting, since they're the practical difference a Redis premise would hide: the cache is **per-process**, so a multi-instance deployment gets no shared invalidation — a stale user can persist up to 10 minutes on other instances after an update; and eviction under pressure is a rough "drop ~20% of oldest" pass (`cleanupOldest`, `store/cache/cache.go:253`) capped at 1000 items, not an LRU.

Unrelated caches exist but don't touch user entries: `server/router/api/v1/instance_stats.go:21` (`instanceStatsCacheTTL`), the RSS cache (`server/router/rss/rss.go:23`), and thumbnail/motion file caches (`server/router/fileserver/fileserver.go:31`).
