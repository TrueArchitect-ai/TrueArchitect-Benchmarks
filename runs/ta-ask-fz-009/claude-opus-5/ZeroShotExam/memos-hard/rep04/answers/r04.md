**Premise correction: neither.** There is no message broker in this repository — no NATS, no RabbitMQ, no AMQP client, no Kafka or task-queue library. `go.mod` contains no such dependency (searched, zero matches), and a repo-wide search for `nats`/`rabbitmq`/`amqp` turns up only incidental substring hits in locale JSON files (e.g. `web/src/locales/ca.json`). So there is no external queue to declare, and no broker connection/config to point at.

**Actual mechanism: an in-process buffered Go channel with a fixed goroutine pool.**

All of it lives in `internal/webhook/webhook.go`:

- **The "queue"** is a package-level buffered channel, capacity 128: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`. That line is the closest thing to a "queue declaration."
- **The "workers"** are 4 goroutines started in `func init()` — `internal/webhook/webhook.go:42-55`. Each ranges over the channel and calls `Post(payload)`, logging a warning on failure. No retry, no backoff, no dead-letter — a failed delivery is logged and dropped (`webhook.go:46-51`).
- **The producer** is `PostAsync` — `internal/webhook/webhook.go:184-196`. It uses a `select` with a `default` branch, so enqueue is non-blocking: when the buffer is full the payload is **dropped** with a `"Dropped webhook dispatch because the async queue is full"` warning (`webhook.go:191-195`).
- **Callers** are the memo webhook dispatch paths: `APIV1Service.DispatchMemoCommentCreatedWebhook` and `APIV1Service.dispatchMemoRelatedWebhook`, both in `server/router/api/v1/memo_service_webhooks.go:30` and `:48`.
- **Actual delivery** is a plain HTTP POST in `Post` — `internal/webhook/webhook.go:120-180` — via a shared `safeClient` (30s timeout) whose transport blocks reserved/private IPs at dial time as SSRF/DNS-rebinding defense (`webhook.go:32-37`, `safeDialContext` at `webhook.go:59-77`). Optional Standard Webhooks HMAC-SHA256 signing adds `webhook-id`/`webhook-timestamp`/`webhook-signature` headers (`webhook.go:133-150`).

Architectural consequence worth naming: because the queue is in-process and unbounded-drop rather than durable, webhook delivery is best-effort and does not survive process restart — anything sitting in the 128-slot buffer is lost on shutdown, and there is no at-least-once guarantee. That's the invariant to be aware of if you were expecting broker-backed semantics.
