**Premise correction:** there is no Redis anywhere in this repository. The cache layer is a process-local, in-memory cache — no external cache server, no Redis client dependency (grep for `redis` across `go.mod`/`go.sum` returns zero matches). So there is no Redis connection string, pool, or config to point you at.

**Actual mechanism**

1. **Implementation** — `store/cache/cache.go`: a `Cache` struct backed by `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:67-73`), fronted by an `Interface` with `Set`/`SetWithTTL`/`Get`/`Delete`/`Clear`/`Size`/`Close` (`store/cache/cache.go:11-32`). Each entry stores value + absolute `expiration` + an estimated size (`store/cache/cache.go:35-39`). Expiry is lazy on read (`Get` deletes and reports a miss past expiration, `store/cache/cache.go:135-144`) plus a background `cleanupLoop` ticker (`store/cache/cache.go:200-250`), with count-based eviction of oldest entries when over `MaxItems` (`cleanupOldest`, `store/cache/cache.go:253-313`).

2. **Where it's "configured"** — in Go code, not in a config file or env var: `store.New` builds one `cache.Config` literal and hands it to three separate cache instances (`store/store.go:40-53`):
   - `DefaultTTL: 10 * time.Minute`
   - `CleanupInterval: 5 * time.Minute`
   - `MaxItems: 1000`
   - `OnEviction: nil`

   The three caches are `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:26-29`), all closed in `Store.Close` (`store/store.go:72-79`). `store/cache/cache.go:57-64` defines an identical `DefaultConfig()` used by tests/`NewDefault()`.

3. **TTL for user entries — 10 minutes.** `userCache` is populated only via the default-TTL `Set` (never `SetWithTTL`): on create/update/upsert and on read-through in `store/user.go:98,122,132,143,167`, keyed by `userCacheKey(userID)` (`store/user.go:88`). `Set` delegates to `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:93-95`), i.e. the 10 minutes from `store/store.go:41`. Same 10 minutes applies to user *settings* entries, keyed by `getUserSettingCacheKey(userID, key)` (`store/cache.go:7-9`, used in `store/user_setting.go:59,78,86,106`).

4. **Invalidation, not just expiry** — user deletion explicitly evicts the user entry and its settings entries rather than waiting out the TTL: `deleteUserCache` in `store/user_delete.go:39-45`, called from `store/user.go:179`.

Note also that the cache is per-process only, so in a multi-replica deployment each replica has its own copy with independent 10-minute windows — `docs/configuration-provisioning.md:423-426` calls out exactly this (no cross-process invalidation for process-local configuration).
