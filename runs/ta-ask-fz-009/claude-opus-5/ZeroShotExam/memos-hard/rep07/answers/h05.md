**Mechanism: explicit Go code, inside the DeleteUser transaction — not a DB cascade.** The `reaction` table has no foreign key at all, so nothing at the database level would clean it up.

**Explicit deletion (two separate statements, per driver)**

Each driver's `deleteUserTargetsTx` runs reaction deletes first in the transaction:

- `store/db/sqlite/user_delete.go:96` → `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-388`): `DELETE FROM reaction WHERE content_id IN (...)` — removes *other* users' reactions on the deleted user's memos (and comment descendants), keyed by `"memos/"+uid` content IDs built at `store/db/sqlite/user_delete.go:512-518`.
- `store/db/sqlite/user_delete.go:102` → `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`): `DELETE FROM reaction WHERE creator_id = ?` — removes the deleted user's own reactions, including ones on memos they don't own.

Mirrored identically in the other two drivers: `store/db/mysql/user_delete.go:96,102,417-441` and `store/db/postgres/user_delete.go:96,102,380-402`.

The whole thing is one transaction — `BeginTx` at `store/db/sqlite/user_delete.go:30`, `Commit` at line 51 — so reaction removal is atomic with the user row delete (`deleteUserRowTx`, line 461).

**Why the DB can't be doing it**

`reaction` is declared with no `FOREIGN KEY` and no `ON DELETE CASCADE` in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-97`, `store/migration/postgres/LATEST.sql:91-97`, and the original `store/migration/*/0.20/00__reaction.sql`. `creator_id` and `content_id` are plain columns under a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Grepping FK/cascade/trigger declarations across `store/migration/**/*.sql` turned up cascades only on `memo_share`, `memo`, `user_setting`, `memo_resource` etc. — never on `reaction`.
