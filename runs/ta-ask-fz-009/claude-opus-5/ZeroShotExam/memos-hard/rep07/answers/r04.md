**Premise correction:** neither. There is no message broker in this repository — no NATS, no RabbitMQ, no Kafka/Redis/AMQP client of any kind. A search for `nats|rabbit|amqp|streadway|kafka|redis|asynq` across the Go manifests (`go.mod`, `go.sum`) returns zero matches, so there is no broker dependency to consume from and no queue declaration (no exchange, no binding, no subject/stream) to point at. The "workers consume from a broker" framing doesn't apply.

**Actual mechanism — an in-process buffered Go channel with a fixed goroutine pool:**

1. **The "queue" is a channel**, declared in the package-level `var` block of `internal/webhook/webhook.go:39`:
   ```go
   asyncPostQueue = make(chan *WebhookRequestPayload, 128)
   ```
   That's the whole declaration — capacity 128, in memory, process-local.

2. **The "workers" are 4 goroutines** started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`; failures are logged at warn level (`internal/webhook/webhook.go:47`) and dropped — there is no retry, no redelivery, no dead-letter path.

3. **Enqueue is non-blocking and lossy by design.** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a `select` with a `default:` branch, so when the buffer is full the payload is discarded with a "Dropped webhook dispatch because the async queue is full" warning (`:192`). Nil payloads are likewise dropped at `:186`.

4. **Producers** are the memo webhook dispatchers: `APIV1Service.DispatchMemoCommentCreatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:30`) and `APIV1Service.dispatchMemoRelatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:48`) — the only two callers of `PostAsync`.

5. **Delivery itself** is a plain HTTP POST via a shared client (`internal/webhook/webhook.go:120-180`), with Standard Webhooks HMAC-SHA256 signing headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) and an SSRF-guarding dialer that rejects reserved/private IPs at dial time (`safeDialContext`, `:59-77`).

**Architectural consequence worth naming:** because the queue is a bounded in-memory channel, webhook delivery has no durability boundary — a process restart or a burst past 128 queued payloads loses deliveries silently apart from a log line. The same pattern appears for email (`email.asyncEmailQueue`, `internal/email/email.go:14`), so this is a deliberate house style for fire-and-forget side effects in this single-binary deployment, not an oversight in the webhook package alone.
