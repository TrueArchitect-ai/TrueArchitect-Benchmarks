**Mechanism: explicit Go code.** Reactions are deleted by hand-written `DELETE FROM reaction` statements inside the user-deletion transaction, in every SQL driver. There is no database-level rule doing it — the `reaction` table declares no foreign key to `user` at all, so no `ON DELETE CASCADE` could fire.

## The explicit code

Each driver's `DeleteUser` opens one transaction and calls `deleteUserTargetsTx`, which removes reactions in **two passes** before deleting the memos and the user row:

| Pass | Function | SQL |
|---|---|---|
| Reactions *by* the user, anywhere | `deleteReactionsByCreatorTx` | `DELETE FROM reaction WHERE creator_id = ?` |
| Reactions by *anyone* on the user's memo tree | `deleteReactionsByContentIDsTx` | `DELETE FROM reaction WHERE content_id IN (…)` |

Anchors, all three dialects:
- `store/db/sqlite/user_delete.go:400` (by creator), `:380` (by content_id); orchestrated at `:96` and `:102` inside `deleteUserTargetsTx`
- `store/db/postgres/user_delete.go:400`, `:380`; calls at `:96`, `:102`
- `store/db/mysql/user_delete.go:437`, `:420`; calls at `:96`, `:102`

The `content_id` values are derived from the user's recursive memo tree (own memos plus `COMMENT`-related descendants) at `store/db/sqlite/user_delete.go:133-147`, converted to `memos/<uid>` strings by `memoContentIDsFromRefs` (`:512-518`) — which matches how reactions key to content rather than to a memo id.

## Why it is not a DB rule

The `reaction` table has no FK constraint in any dialect — only a uniqueness constraint:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

Contrast the adjacent `memo_share` table, which *does* rely on the database: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`) — yet `deleteMemoSharesTx` still deletes those rows explicitly too (`store/db/sqlite/user_delete.go:405-416`). So reaction cleanup is entirely the application's responsibility, and the transaction boundary (`:29-53`, with a `tx.Rollback` defer and a pre-commit failpoint hook at `:47`) is what makes it atomic with the user row removal.
