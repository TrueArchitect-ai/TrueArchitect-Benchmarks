**Premise correction: neither.** There is no message broker in this repository at all. `go.mod`/`go.sum` contain no NATS, RabbitMQ/AMQP, Kafka, or task-queue client (verified: search over both manifest files returned zero matches), and no broker connection code exists in the tree. There are also no separate "webhook delivery worker" processes — delivery happens inside the single Memos server process.

**Actual mechanism: an in-process buffered Go channel with a fixed goroutine pool**, all in `internal/webhook/webhook.go`:

- **Queue declaration** — `internal/webhook/webhook.go:39`:
  `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a package-level buffered channel, capacity 128. That is the entire "queue": in-memory, per-process, not durable.
- **Workers** — `internal/webhook/webhook.go:42-55`: a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`, logging a warning on failure.
- **Producer** — `PostAsync` at `internal/webhook/webhook.go:184`: non-blocking `select` send with a `default` branch that **drops the webhook and logs** "Dropped webhook dispatch because the async queue is full" (line 192). Backpressure is shed, not buffered.
- **Delivery** — `Post` at `internal/webhook/webhook.go:120` does a plain `http.Client` POST via `safeClient` (30s timeout, SSRF-guarded dialer at line 59), signs with HMAC-SHA256 Standard Webhooks headers when a signing secret is present (lines 133-150).
- **Callers** — `v1.APIV1Service.DispatchMemoCommentCreatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:30`) and `dispatchMemoRelatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:48`).

Architectural consequences worth naming: because the queue is a channel rather than a broker, delivery is **at-most-once** — pending payloads are lost on process restart, there is no retry or dead-letter path (a failed `Post` is only logged, line 47), and concurrency is hard-coded at 4 with no horizontal scaling across instances.
