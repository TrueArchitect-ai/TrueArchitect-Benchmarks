I'll start by locating the identity-provider abstraction in the code graph.

h03. `internal/idp` (abstraction); `internal/idp/oauth2` (implementation)

**The abstraction** — `internal/idp/idp.go:3-8` defines the provider-neutral contract: a single `IdentityProviderUserInfo` struct carrying `Identifier`, `DisplayName`, `Email`, `AvatarURL`. That is the whole boundary — the shared shape every provider must normalize its claims into. Note the abstraction is a *data* contract, not a Go interface; there's no `IdentityProvider` interface type declared in the parent package.

**The implementation** — `internal/idp/oauth2/oauth2.go`, documented at line 1 as "Package oauth2 implements the OAuth2 identity provider integration." It ships:
- `IdentityProvider` struct wrapping `*storepb.OAuth2Config` (line 20-22)
- `NewIdentityProvider` with required-field validation on `clientId`, `clientSecret`, `tokenUrl`, `userInfoUrl`, `fieldMapping.identifier` (line 27-43)
- `ExchangeToken` — authorization-code exchange over `golang.org/x/oauth2`, with optional PKCE `code_verifier` and `AuthStyleAutoDetect` (line 47-80)
- `UserInfo` — fetches the UserInfo endpoint with a bearer token and maps claims into `idp.IdentityProviderUserInfo` via the configured `FieldMapping` (line 83-142)

**OAuth2 is the only concrete protocol.** `internal/idp/` contains exactly `idp.go`, `oauth2/oauth2.go`, and `oauth2/oauth2_test.go` — no SAML, LDAP, or separate OIDC package. This is corroborated in the design docs: `docs/plans/2026-04-21-sso-user-identity-linkage/definition.md:47` lists "Supporting IdP types other than `OAUTH2`" as an explicit non-goal, and `docs/configuration-provisioning.md:152` states provisioning validation "supports only OAuth2 providers." OIDC providers are handled *as* OAuth2 — `docs/configuration-provisioning.md:495` references GitLab's OpenID Connect docs as a configuration target, meaning OIDC IdPs are wired through the generic OAuth2 authorization-code + UserInfo flow rather than a dedicated discovery-based implementation.
