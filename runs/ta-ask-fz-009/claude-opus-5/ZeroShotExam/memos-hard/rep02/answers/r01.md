**Actual mechanism**

*The cache implementation* — `store/cache/cache.go`:
- `Cache` (line 67) is a thread-safe in-memory store built on `sync.Map` plus an `atomic.Int64` item counter. No network, no serialization.
- Each entry is an `item` (line 35) carrying `value`, an absolute `expiration time.Time`, and a rough `size` estimate.
- Expiry is enforced two ways: lazily on read (`Get`, line 135 — expired key is deleted and reported as a miss) and eagerly by a background `cleanupLoop` goroutine on a ticker (line 200 → `cleanup`, line 218).
- Capacity pressure is handled separately from TTL: when `MaxItems` is exceeded, `cleanupOldest` (line 253) drops roughly 20% of `MaxItems` by nearest-expiration.

*Where it's "configured"* — `store/store.go:38-58`. `store.New` builds one `cache.Config` literal inline and hands the same config to three separate cache instances:
```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
- `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:27-29`, wired at :51-53).
- These values are hardcoded — not read from env vars, flags, or the profile. `cache.DefaultConfig()` (`store/cache/cache.go:57`) declares the identical 10min/5min/1000 triple, so the literal in `store.New` is a duplicate of the package default.
- All three caches are shut down in `Store.Close` (`store/store.go:74-76`), which stops the cleanup goroutines.

*TTL for user entries:* **10 minutes**, inherited from `DefaultTTL`. User writes go through `s.userCache.Set(...)` — `store/user.go:98, 122, 132, 143, 167` — and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). No user-specific TTL and no call to `SetWithTTL` with a custom duration anywhere in `store/`; user entries are keyed by `userCacheKey(userID)` = the plain user ID as a string (`store/user.go:88`).

Correctness against staleness relies on explicit invalidation rather than short TTLs: `deleteUserCache` (`store/user_delete.go:39-47`) evicts the user key and every associated `userSettingCache` key on delete. Note the consequence of the in-process design — with multiple server replicas, each has its own copy and one replica's invalidation does not reach the others; a user update can stay stale elsewhere for up to 10 minutes.
