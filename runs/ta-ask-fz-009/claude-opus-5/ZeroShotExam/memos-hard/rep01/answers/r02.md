**Premise correction: there is no per-user API rate-limiting middleware in this repository.** No middleware, interceptor, or handler enforces per-user (or per-IP) request limits, so there are no request limits to report.

What I verified:

- **The interceptor chain has no rate limiter.** All server-side Connect interceptors are registered in one place — `server/router/api/v1/v1.go:133-138` — and the chain is exactly `NewMetadataInterceptor()`, `NewLoggingInterceptor()`, `NewRecoveryInterceptor()`, `NewAuthInterceptor(authorizer)`. Those four are also the complete set of interceptor types defined in `server/router/api/v1/connect_interceptors.go`.
- **The Echo middleware stack has no rate limiter.** `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware(profile)`.
- **The grpc-gateway mux has no rate limiter.** `server/router/api/v1/v1.go:96-98` installs only `gatewayAuthMiddleware` (authentication/anonymous-access policy).
- **No rate-limiting library is present.** `go.mod` pulls in no limiter package; `golang.org/x/time` is present only as an indirect dependency and `golang.org/x/time/rate` is never imported anywhere in the Go tree.
- The code graph returns a **certified miss** for "ratelimit" across all 7,293 indexed symbols, and text search for `rate limit|throttl|quota` finds only documentation prose in `internal/email/README.md:286` and `internal/email/doc.go:86`, which *recommend* rate-limiting email sends as future work.

**What likely prompted the question** — there are concurrency limits, which are a different invariant (bounded in-flight work, not per-user request budgets):

| Guard | Limit | Location |
|---|---|---|
| `imageProcessingSemaphore` (EXIF stripping on upload) | 2 concurrent | `server/router/api/v1/v1.go:60`, acquired at `attachment_service_image.go:67-77` |
| `thumbnailSemaphore` (API service) | 3 concurrent | `server/router/api/v1/v1.go:59` |
| `thumbnailSemaphore` (file server) | 3 concurrent (`maxConcurrentThumbnails`) | `server/router/fileserver/fileserver.go:46,116` |

These are process-wide, identity-agnostic, and fail with `codes.ResourceExhausted` ("too many image processing requests", `server/router/api/v1/attachment_service.go:160`) only when the caller's context expires while waiting — they do not count requests per user and never return HTTP 429.
