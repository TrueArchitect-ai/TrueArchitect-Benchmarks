**Premise correction:** there is no Redis in this repository. `go.mod` contains no Redis client dependency (searched — zero matches for `redis`), and the ArchMap symbol search for `redis` returned only unrelated fuzzy hits (`renderList*`, `IdentityProvider*`, etc.), no cache-transport symbols. There is no Redis connection string, pool, or client to configure — nothing external to point at.

**Actual mechanism: a process-local in-memory cache in the store layer.**

- Implementation: `store/cache/cache.go` — a `Cache` struct backed by `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`), with a background `cleanupLoop` goroutine ticking on `CleanupInterval` to evict expired entries (`store/cache/cache.go:200-250`). Expiry is also checked lazily on read (`store/cache/cache.go:135`).
- Configuration point: `store.New` in `store/store.go:38-61`. The config is a hard-coded literal — `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil` (`store/store.go:40-45`). It is not env-driven or file-driven. The same `cacheConfig` value instantiates all three caches: `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`).
- Duplicate default: `cache.DefaultConfig()` declares the same 10min/5min/1000 values (`store/cache/cache.go:57-64`), but the store does not call it — it builds its own identical literal.

**TTL for user entries: 10 minutes.** User entries are written via `s.userCache.Set(...)` (`store/user.go:98, 122, 132, 143, 167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — no user-specific TTL override exists anywhere in the store. Two secondary details worth knowing:

- Keying is by user ID only (`userCacheKey`, `store/user.go:88`), and the cache is consulted only when the lookup carries an ID (`store/user.go:150`) — lookups by username fall through to the driver.
- Entries can also disappear before TTL: explicit invalidation on delete (`store/user_delete.go:40`), and capacity eviction once `MaxItems` is exceeded via `cleanupOldest` (`store/cache/cache.go:117-119`).

Architectural consequence: because this cache is per-process memory, cache state is not shared across replicas and there is no cross-instance invalidation — the same constraint `docs/configuration-provisioning.md:423` calls out for process-local configuration. A stale user record can live up to 10 minutes in one replica after another replica writes.
