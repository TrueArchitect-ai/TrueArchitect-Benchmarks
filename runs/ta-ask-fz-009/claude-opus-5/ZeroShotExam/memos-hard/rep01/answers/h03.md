h03. `internal/idp`; `internal/idp/oauth2`

- **Abstraction package — `internal/idp`** (`internal/idp/idp.go:1`). It is deliberately thin: it defines only the provider-neutral result contract `IdentityProviderUserInfo` (`Identifier`, `DisplayName`, `Email`, `AvatarURL`) at `internal/idp/idp.go:3`. There is no Go interface here — the shared vocabulary is the user-info struct that every provider must produce, so the boundary is data-shaped rather than method-shaped.

- **Implementation package — `internal/idp/oauth2`** (`internal/idp/oauth2/oauth2.go:1-2`, "Package oauth2 implements the OAuth2 identity provider integration"). `oauth2.IdentityProvider` wraps a `storepb.OAuth2Config` (`oauth2.go:20-22`), is constructed with required-field validation in `NewIdentityProvider` (`oauth2.go:27`), and exposes the two-step flow: `ExchangeToken` — authorization-code exchange with optional PKCE `code_verifier` (`oauth2.go:47`) — and `UserInfo`, which calls the configured userinfo endpoint and maps raw claims into `idp.IdentityProviderUserInfo` via the config's `FieldMapping` (`oauth2.go:83-141`).

OAuth2 is the only concrete protocol that ships: `internal/idp` contains just `idp.go` plus the `oauth2/` subdirectory (no OIDC, SAML, or LDAP package), and the enum on the wire has a single provider type, `IdentityProvider_OAUTH2` (`proto/gen/store/idp.pb.go:26`, `proto/gen/api/v1/idp_service.pb.go:29`) — so the config union `IdentityProviderConfig` currently has exactly one variant, `Oauth2Config` (`proto/gen/store/idp.pb.go:214`). Adding a second protocol would mean a new enum value, a new config variant, and a new sibling package under `internal/idp/`.
