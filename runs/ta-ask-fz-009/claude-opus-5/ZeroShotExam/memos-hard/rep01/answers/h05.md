h05.

**Mechanism: explicit Go code** — reaction rows are deleted by hand-written SQL inside the user-deletion transaction, once per SQL dialect. There is **no** database-level cascade for reactions.

## Why it can't be the database

The `reaction` table has **no foreign key at all** — `creator_id` is a bare `INTEGER NOT NULL`, and the only table-level constraint is a uniqueness triple:

- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`
- original creation: `store/migration/sqlite/0.20/00__reaction.sql:2-9` (same in the postgres/mysql `0.20` variants)

For contrast, tables that *do* rely on the DB rule declare it explicitly — `FOREIGN KEY(creator_id) REFERENCES user(id) ON DELETE CASCADE` on `memo` (`store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql:59`), on `user_setting` (`:204`), and `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` on `memo_share` (`store/migration/sqlite/0.27/04__memo_share.sql:11`). Reactions are absent from that list. Also note `content_id` is a free-form `TEXT`/`VARCHAR(256)` resource name (`memos/{uid}`), not an integer FK to `memo.id`, so it is structurally incapable of cascading.

## The explicit code path

`Store.DeleteUser` → driver `DeleteUser` → `deleteUserTargetsTx`, which runs **two** reaction deletes as the first steps of the transaction (`store/db/sqlite/user_delete.go:92-104`):

1. `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched over the content IDs of the user's whole memo tree, i.e. *other people's* reactions on the departing user's memos.
   - `store/db/sqlite/user_delete.go:380-388`, `store/db/postgres/user_delete.go:380`, `store/db/mysql/user_delete.go:417`
2. `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, i.e. the user's own reactions anywhere, including on memos that survive.
   - `store/db/sqlite/user_delete.go:400-403`, `store/db/postgres/user_delete.go:400`, `store/db/mysql/user_delete.go:437`

Both run before `deleteMemosTx` and `deleteUserRowTx` (`store/db/sqlite/user_delete.go:120-123`) — ordering matters because the content IDs are read from the memo rows during `collectDeleteUserTargets` (`store/db/sqlite/user_delete.go:61-90`) before those rows go away.

## The architectural consequence

Reaction cleanup is an **application-layer invariant, not a schema invariant**, and it is duplicated three times — sqlite, postgres, mysql each carry their own copy of both deletes. Any future write path that removes a user or a memo *without* going through `deleteUserTargetsTx` will silently orphan `reaction` rows; the database will not stop it. That's the maintenance cost to be aware of: the guarantee lives in `store/db/*/user_delete.go` and holds only for callers of that function.
