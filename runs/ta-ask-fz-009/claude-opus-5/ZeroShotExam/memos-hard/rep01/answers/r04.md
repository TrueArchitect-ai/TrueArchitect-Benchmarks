**The actual mechanism: an in-process buffered Go channel with four goroutines.**

Declared at `internal/webhook/webhook.go:39`:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

- **The "queue"** is a package-level `chan *WebhookRequestPayload` with a fixed capacity of 128, living in the server process's memory.
- **The "workers"** are spun up in `init()` at `internal/webhook/webhook.go:42-55` — a fixed pool of 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`, logging a warning on failure.
- **Enqueue** happens in `PostAsync` (`internal/webhook/webhook.go:184`), via a `select` with a `default:` branch — so when the buffer is full the payload is **dropped** with a warning log (`webhook.go:191-195`), not blocked or retried.
- **Delivery** is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120`) using a shared `safeClient` with a 30s timeout and an SSRF-guarding dialer (`webhook.go:32-37`, `safeDialContext` at `webhook.go:59`), optionally HMAC-SHA256 signed per Standard Webhooks (`webhook.go:133-150`).

Producers are the API layer, not a broker publisher: `DispatchMemoCommentCreatedWebhook` and `dispatchMemoRelatedWebhook` in `server/router/api/v1/memo_service_webhooks.go:30` and `:48` call `webhook.PostAsync` directly in the request path.

Two architectural consequences worth naming, since a broker question is usually really a durability question: this queue is **not durable** (process restart loses in-flight payloads) and has **no retry or dead-letter path** (a failed `Post` is logged and discarded). Backpressure is shed by dropping, not by slowing the producer.
