h15.

Memo visibility is enforced at **twelve** distinct sites across five server surfaces (gRPC API, SSE hub, raw file server, public/SEO routes, notification fan-out). Each is its own copy of the rule — there is no single chokepoint.

**gRPC API (`server/router/api/v1/`)**

Single-memo read gate `checkMemoReadAccess` (archived→creator, non-public→auth, private→creator) — `server/router/api/v1/memo_service.go:39-68` (callers at `:356`, `:367`, and `memo_service_comments.go:148`)
List-query visibility predicate on `ListMemos` (anon→`[Public]`; authed→`creator_id == N || visibility in ["PUBLIC","PROTECTED"]`) — `server/router/api/v1/memo_service.go:218-227`
User-stats list filters (same predicate, duplicated twice) — `server/router/api/v1/user_service_stats.go:78-92` and `:216-221`
Attachment access by owning memo's visibility — `server/router/api/v1/attachment_service.go:422-455`
Memo attachment listing gate — `server/router/api/v1/memo_attachment_service.go:213-225`
Reaction read + create gates — `server/router/api/v1/reaction_service.go:29-41` and `:83`
Comment creation gate on parent memo — `server/router/api/v1/memo_service_comments.go:41-43`
Share-token read path that intentionally bypasses visibility (`GetMemoByShare`, no auth) — `server/router/api/v1/memo_share_service.go:153-192`, expiry via `isMemoShareExpired:195`

**SSE fan-out**

Per-client delivery filter `SSEClient.canReceive` (private→creator or admin) — `server/router/api/v1/sse_hub.go:134-144`, applied in `Broadcast:115-131`

**Raw file server (HTTP, non-gRPC)**

Attachment file serving: public+anonymous-allowed short-circuit, then share-token fallback, then auth/creator/admin check — `server/router/fileserver/fileserver.go:666-703`

**Notification / mention fan-out**

`canViewerAccessMemo` — two independent copies: `server/router/api/v1/user_service_notifications.go:302-316` and `server/notification/email.go:306-320`
`canUserAccessMentionContext` / `shouldSkipMentionInbox` (private memo or private parent suppresses the mention) — `server/router/api/v1/memo_mention_helpers.go:56-89`

**Public/unauthenticated surfaces (hardcoded `VisibilityList: [Public]`)**

RSS feeds — `server/router/rss/rss.go:90` and `:141`
Sitemap — `server/router/frontend/frontend.go:149-151`

**Where it actually lands:** all of these funnel into the store-level SQL predicate for `FindMemo.VisibilityList` — `store/db/sqlite/memo.go:96`, `store/db/postgres/memo.go:89`, `store/db/mysql/memo.go:104` — but the store enforces nothing on its own; it applies whatever list the caller supplies. Any new read path that forgets to set it returns private memos.

Two consistency notes worth flagging: the API-layer checks use `isSuperUser(user)`, while `sse_hub.go:137`, `fileserver.go:699` and `notification/email.go:310` compare `role == store.RoleAdmin` directly — divergent superuser semantics across surfaces. Also, `checkMemoReadAccess` is the only site that gates on `RowStatus == store.Archived`; the reaction, attachment, and SSE paths do not.
