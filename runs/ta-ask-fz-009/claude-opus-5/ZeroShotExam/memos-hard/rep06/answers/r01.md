**Premise correction:** there is no Redis connection to configure. Redis appears nowhere in this repository — no client dependency in `go.mod` (the only external datastores are `go-sql-driver/mysql`, `lib/pq`, and `modernc.org/sqlite`), and a case-insensitive content search for "redis" across 1042 files returned zero matches. The cache layer is a hand-rolled, **in-process, in-memory** cache, so there is no connection string, host/port, or auth to configure at all.

**Actual mechanism**

1. **Implementation** — `store/cache/cache.go`. A `sync.Map`-backed struct with per-entry expiration (`item.expiration`, line 37), an atomic item counter, and a background `cleanupLoop` goroutine (line 200) driven by a ticker. Eviction has two paths: lazy expiry on `Get` (line 135) and size-pressure eviction via `cleanupOldest` (line 253), which drops ~20% of `MaxItems` when the count exceeds the cap.

2. **Where it's "configured"** — `store.New` in `store/store.go:40-45` constructs the one `cache.Config` used for every cache instance:
   - `DefaultTTL: 10 * time.Minute`
   - `CleanupInterval: 5 * time.Minute`
   - `MaxItems: 1000`
   - `OnEviction: nil`

   These are hardcoded literals — not env vars, not viper settings. `store/cache/cache.go:57` (`DefaultConfig()`) holds an identical duplicate set of defaults, but the store does not call it; it builds its own copy.

3. **TTL applying to user entries** — **10 minutes**, and it is not user-specific. Three caches are created from that same shared config at `store/store.go:51-53`: `instanceSettingCache`, `userCache`, and `userSettingCache`. All user writes go through `Set` (`store/user.go:98, 122, 132, 143, 167`), which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:94`). No call site anywhere in the repo invokes `SetWithTTL` with a custom duration outside of tests — so the custom-TTL branch of the interface is effectively unused in production code.

4. **Correctness boundary worth knowing** — because the cache is per-process and keyed locally (`userCacheKey` at `store/user.go:88`, `getUserSettingCacheKey` at `store/cache.go:7`), invalidation is explicit and local: deletes happen in `store/user_delete.go:40,45` and `store/user_setting.go:122`. This design assumes a single server process; running multiple replicas against one database would give each replica an independent view with up to 10 minutes of staleness, since nothing propagates invalidation between them. That is the gap a Redis layer would normally close — it just isn't present here.
