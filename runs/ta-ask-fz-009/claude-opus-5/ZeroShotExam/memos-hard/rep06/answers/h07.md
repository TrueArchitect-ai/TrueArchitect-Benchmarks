**Request path:** the browser loads `<img src="/file/users/{username}/avatar">` — that URL is minted server-side at `server/router/api/v1/user_service_converters.go:36` (`/file/%s/avatar` from the canonical user name), so viewing another user's profile hits a plain HTTP GET on the fileserver router, not the gRPC/Connect API.

**Then back out:** `FileServerService.parseDataURI` decodes the stored value — the avatar is *not* a blob in a separate table, it's a base64 `data:` URI held in the `user.avatar_url` column (server/router/fileserver/fileserver.go:737-745) — the MIME type is checked against `avatarAllowedTypes`, security headers plus `Cache-Control` are set, and the bytes go out via `c.Blob` (fileserver.go:196-209).

Two access-control notes worth flagging: authentication is required only on private instances (no `InstanceURL` ⇒ `AllowAnonymous()` false, internal/profile/profile.go:46) and there is no per-user authorization check — any authenticated viewer, or anyone at all on a public instance, can fetch any username's avatar. The route also resolves usernames only, not numeric IDs (comment at fileserver.go:714).
