**Mechanism: explicit Go code** — a per-dialect `DeleteUser` transaction issues raw `DELETE FROM reaction` statements. There is no FK/cascade on the `reaction` table to do it for you.

## The explicit deletions

`DeleteUser` runs one transaction that collects targets, then deletes dependents in order (`store/db/sqlite/user_delete.go:29-59`, `:92-123`). Two separate reaction deletes happen inside it:

- `deleteReactionsByContentIDsTx` — reactions *on* the deleted user's memos (batched `DELETE FROM reaction WHERE content_id IN (...)`), called at `store/db/sqlite/user_delete.go:96`, defined `:380-388`
- `deleteReactionsByCreatorTx` — the user's *own* reactions, `DELETE FROM reaction WHERE creator_id = ?`, called `:102`, defined `:400-403`

Same structure is duplicated in all three dialect packages:
- `store/db/sqlite/user_delete.go:96, 102, 380, 400`
- `store/db/postgres/user_delete.go:96, 102, 380, 400`
- `store/db/mysql/user_delete.go:96, 102, 417, 437`

## Why the DB can't do it

The `reaction` table is declared with no foreign key at all — `creator_id` is a bare `INTEGER/INT NOT NULL`, and the only constraint is the uniqueness triple:
- `store/migration/sqlite/LATEST.sql:91-99`
- `store/migration/postgres/LATEST.sql:90-98`
- `store/migration/mysql/LATEST.sql:90-98`
- original creation: `store/migration/sqlite|postgres|mysql/0.20/00__reaction.sql`

I grepped every migration file for `FOREIGN KEY|REFERENCES|ON DELETE`: the only cascade in the current schema is `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, and the `0.27/04__memo_share.sql` files). Older SQLite migrations did carry `creator_id → user(id) ON DELETE CASCADE` on other tables (`store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql:59,97,125,167,204`), but those were stripped by `store/migration/sqlite/0.7/00__remove_fk.sql` — and reaction never had one, since it was introduced in 0.20, after the FK removal.

## Consequence

Reaction cleanup is an application-layer invariant, not a database-enforced one, and it's implemented three times. If a code path deletes a user row without going through `DeleteUser` (or a new dialect is added), reactions orphan silently — nothing in the schema catches it. The whole sequence is transactional, so a failure mid-way rolls back (`store/db/sqlite/user_delete.go:34-36, 51-53`), which is what keeps it consistent in practice.
