**Premise correction: there is no nightly database-cleanup job, and the cron scheduler isn't wired into the running server at all — so there is no scheduled time to report.**

What actually exists:

1. **`internal/scheduler` is a standalone, unwired library.** It provides cron parsing and job registration (`internal/scheduler/parser.go:30` `ParseCronExpression`, `internal/scheduler/scheduler.go:70` `Scheduler.Register`), but nothing in the application calls it. A repo-wide search for the import path `github.com/usememos/memos/internal/scheduler` returns only its own two test files (`internal/scheduler/example_test.go:10`, `internal/scheduler/integration_test.go:13`), and the code graph reports a certified zero callers for both `scheduler.New` and `Scheduler.Register`.

2. **The `"0 2 * * *"` daily-cleanup you may be thinking of is documentation prose, not a registered job.** It appears as an illustrative snippet named `"daily-cleanup"` in `internal/scheduler/README.md:34-37` and again in the package doc comment `internal/scheduler/doc.go:14-16`. Those are examples of the API, not wiring.

3. **Real background work uses plain tickers, not cron.** `Server.startBackgroundRunners` (`server/server.go:153-174`) starts exactly one runner: the S3 presign refresher, which runs once at boot and then on a **12-hour interval** (`server/runner/s3presign/runner.go:27` `runnerInterval = time.Hour * 12`, loop at `:29-41`). The only other runner, `server/runner/memopayload/runner.go:27`, exposes `RunOnce` and is not on any schedule. Neither touches database cleanup.

If you're after cleanup-shaped behavior, the closest thing in the repo is user-deletion cascade logic (referenced in `CHANGELOG.md:69`, "delete user cleanup"), which is request-driven, not scheduled.
