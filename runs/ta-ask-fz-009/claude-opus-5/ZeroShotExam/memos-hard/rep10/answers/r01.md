**Premise correction:** there is no Redis anywhere in this repository. `redis` does not appear in `go.mod`/`go.sum` (searched both, zero matches), and the cache layer is a hand-rolled in-process implementation. There is no external cache server to configure, hence no connection string, host, port, or pool settings to point you at.

**Actual mechanism**

The cache is an in-memory, per-process store in `store/cache/cache.go`:
- `cache.Cache` (`store/cache/cache.go:67`) wraps a `sync.Map` plus an `atomic.Int64` item counter — purely local to the running server, lost on restart, not shared across replicas.
- Each entry is an `item{value, expiration, size}` (`store/cache/cache.go:35`); expiry is enforced lazily on read (`Get`, `store/cache/cache.go:135`) and proactively by a background `cleanupLoop` ticker (`store/cache/cache.go:200`).
- Capacity is bounded by `MaxItems`, with `cleanupOldest` shedding ~20% when exceeded (`store/cache/cache.go:253`).

**Where it's "configured":** in code, at store construction — `store.New` builds a `cache.Config` literal (`store/store.go:40-45`) and hands it to three separate cache instances: `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). All three share the same config values. There is no env var or config file wiring for this; `cache.DefaultConfig()` (`store/cache/cache.go:57`) carries identical values as the package-level default.

**TTL for user entries:** 10 minutes, with a 5-minute cleanup sweep and a 1000-item cap (`store/store.go:41-43`). User entries go in via plain `Set`, which applies `config.DefaultTTL` (`store/cache/cache.go:93-94`) — no user-specific `SetWithTTL` call exists. Writes happen on create/update/list/get (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), keyed by user ID (`userCacheKey`, `store/user.go:88`), and reads short-circuit only when looked up by ID (`store/user.go:149-155`). Correctness doesn't rely on the TTL: mutations write through immediately and deletes invalidate explicitly (`store/user.go:179`), so the 10 minutes is a bound on staleness from out-of-band DB changes, not the normal invalidation path.
