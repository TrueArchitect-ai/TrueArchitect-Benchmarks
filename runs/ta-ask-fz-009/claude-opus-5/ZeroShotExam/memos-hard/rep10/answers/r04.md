**Premise correction: neither.** There is no message broker in this repository at all. No NATS, no RabbitMQ, no AMQP client, no Kafka — `go.mod`/`go.sum` contain no such dependency (grep for `nats|rabbit|amqp|streadway|kafka` across both manifest files: zero matches). So there is no queue *declaration* in the broker sense — no exchange, no subject, no durable consumer group, nothing to point at.

**Actual mechanism: an in-process buffered Go channel with a fixed goroutine pool**, all in `internal/webhook/webhook.go`.

- **The "queue"** is a package-level channel declared at `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — capacity 128, in memory, process-local.
- **The "workers"** are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)` (`webhook.go:120`), logging a warning on failure. That's the whole consumer side.
- **The producer** is `PostAsync` (`webhook.go:184-196`). It does a non-blocking `select` send: if the buffer is full, the payload is **dropped** with a `slog.Warn` (`webhook.go:191-195`).
- **Callers** are the memo webhook dispatch paths: `APIV1Service.DispatchMemoCommentCreatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:30`) and `APIV1Service.dispatchMemoRelatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:48`).

Delivery semantics worth being explicit about, since a broker premise implies guarantees this design doesn't offer:

- **At-most-once, and lossy by design.** Overflow drops the event (`webhook.go:191`); process restart loses everything still buffered. Nothing is persisted, so there is no redelivery.
- **No retry.** A failed `Post` is logged and discarded — there's no backoff or dead-letter path.
- **No cross-process fan-out.** Because the channel lives in the server process, webhook dispatch does not survive or coordinate across replicas.

Note the same pattern exists for email — `email.asyncEmailQueue` at `internal/email/email.go:14` — so this channel-plus-pool idiom is the codebase's general approach to background work, not a webhook-specific choice.

The actual HTTP delivery is where the engineering effort went: HMAC-SHA256 signing in the Standard Webhooks format (`webhook-id`/`webhook-timestamp`/`webhook-signature` headers, `webhook.go:133-150`) and an SSRF guard that rejects reserved/private IPs at dial time via `safeDialContext` (`webhook.go:59-77`).
