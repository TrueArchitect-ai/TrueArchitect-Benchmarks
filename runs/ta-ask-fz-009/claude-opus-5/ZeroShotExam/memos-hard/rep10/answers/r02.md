**What actually is registered on the request path.** The middleware chain has four interceptors, wired at `server/router/api/v1/v1.go:133-138`:

| Interceptor | Definition | Purpose |
|---|---|---|
| `MetadataInterceptor` | `connect_interceptors.go:22` | HTTP headers → gRPC metadata (runs first) |

At the Echo layer, `server/server.go:51-52` adds only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:13`).

**The one limit that does exist is a size cap, not a rate cap.** `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied three ways: `http.MaxBytesHandler` on the gRPC-Gateway routes (`v1.go:126`), `connect.WithReadMaxBytes` on the Connect handlers (`v1.go:141`), and `MaxBytesHandler` on the Connect mux (`v1.go:144`). This bounds *per-request body size* — it does nothing to limit request *frequency*, and it is per-request rather than per-user.

**Practical implication.** The API has no request-frequency defense at the application layer, and no per-identity accounting to build one on. If you need rate limiting, `AuthInterceptor` is the natural anchor point: it is the only interceptor that resolves caller identity (`Authorizer`, `v1.go:137`), so a limiter placed immediately after it in the `connect.WithInterceptors` chain would have a user ID to key buckets on. Note that any such interceptor covers only the Connect and gateway paths through `v1.go`; the SSE routes registered at `v1.go:125` take a different path and would need separate treatment.
