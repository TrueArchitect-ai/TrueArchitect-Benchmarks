**What each hop does**

- **Route registration** — `RegisterRoutes` mounts the file group and both file routes; it is wired from `server.NewServer` (`server/server.go`), so avatars are served by the Echo file server, *not* the gRPC-gateway `/api/v1` surface.
- **`serveUserAvatar`** (fileserver.go:168) — the serving handler. Gates anonymous access when `s.Profile.AllowAnonymous()` is false (falls through to `getCurrentUser` → `authenticator.AuthenticateToUser`, `server/auth/authenticator.go:190`), reads the `:identifier` path param, then looks the user up by **username**.
- **`getUserByUsername`** (fileserver.go:715) — thin adapter: builds `store.FindUser{Username: &identifier}` and calls the store. This is the only data call on the happy path.
- **`Store.GetUser`** (store/user.go:148) — cache layer. The `userCache` shortcut only fires when `find.ID != nil`; a username lookup **always misses cache** and delegates to `ListUsers`, which then populates the cache by user ID.
- **`Store.ListUsers`** (store/user.go:136) → `s.driver.ListUsers` — the driver interface (`store/driver.go`) fans out to the dialect implementation.
- **Driver SQL** — the `SELECT` includes `avatar_url` and filters `WHERE username = ?` (sqlite/user.go:128-129, :151-165).

**Where the bytes actually live:** there is no blob/file storage hop for avatars. The image is stored inline in the `user.avatar_url` column as a base64 `data:` URI (`store/migration/sqlite/LATEST.sql:20`, added in `store/migration/sqlite/0.11/00__user_avatar.sql`). `parseDataURI` (fileserver.go:737) splits the MIME type and base64-decodes it; the type is checked against `avatarAllowedTypes` (fileserver.go:75) before `c.Blob` writes it out with security and cache headers.

One caveat on the browser side: I could not find any frontend code that constructs the `/file/users/.../avatar` URL — `grep` over 433 files in `web/src` found no `/file/users` or `/avatar` string. `UserAvatar` (`web/src/components/UserAvatar.tsx:14`) renders whatever `avatarUrl` it is given, and the API returns `AvatarUrl: user.AvatarURL` (`server/router/api/v1/user_service_converters.go:25`) — i.e. the raw data URI. So in the current frontend the avatar typically arrives inline via the user API; the `/file/users/:identifier/avatar` endpoint is a real, exercised route (`server/router/fileserver/fileserver_test.go:527`) but I found no frontend caller for it.
