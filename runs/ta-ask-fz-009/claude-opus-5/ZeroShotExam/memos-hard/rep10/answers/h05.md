**Mechanism: explicit Go code** — the per-driver `DeleteUser` transaction issues `DELETE FROM reaction` statements itself. There is no FK/cascade or trigger on the `reaction` table.

**Evidence — the Go path**

- API entry: `server/router/api/v1/user_service.go:393` (`APIV1Service.DeleteUser`) → `store.DeleteUser` at line 414.
- Store facade: `store/user.go:171` — pure delegation to `s.driver.DeleteUser`, no reaction logic here.

  - `store/db/postgres/user_delete.go:96, 102` (helpers at 380, 400).
  - `store/db/mysql/user_delete.go:96, 102` (helpers at 417, 437).

So two distinct sweeps run inside the same transaction as the user row delete (`deleteUserRowTx`, sqlite line 461):
1. reactions **authored by** the deleted user (`creator_id`);
2. reactions **on** the deleted user's memos, authored by anyone else — keyed by `content_id` built as `"memos/" + memo.UID` (`memoContentIDsFromRefs`, `store/db/sqlite/user_delete.go:512`), over the recursive memo tree including comment descendants (`listDeleteUserMemoTreeRecursive`, line 133).

**Evidence — no database-level rule**

- Schema: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-97` — `reaction` has `creator_id INTEGER NOT NULL` and `content_id`, a `UNIQUE(creator_id, content_id, reaction_type)` constraint, and **no `FOREIGN KEY` / `ON DELETE CASCADE`**. Same in the original migration `store/migration/*/0.20/00__reaction.sql`.
- A repo-wide grep for `FOREIGN KEY|REFERENCES|ON DELETE|TRIGGER` across `store/migration/**/*.sql` returns cascades for `memo_share`, `memo_organizer`, `resource`, `user_setting`, etc. — but zero hits touching `reaction`.

Note on coupling: because `content_id` is a *string* (`"memos/<uid>"`) rather than an FK to `memo.id`, a DB-level cascade isn't available for the memo-side sweep even in principle — that correctness burden lives entirely in `memoContentIDsFromRefs` and must be kept in sync with the resource-name format.
