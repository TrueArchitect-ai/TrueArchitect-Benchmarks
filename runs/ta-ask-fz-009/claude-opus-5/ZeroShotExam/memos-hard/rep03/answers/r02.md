**Premise correction: there is no per-user API rate-limiting middleware in this repository.** Nothing is registered, so there are no request limits to report.

What I verified:

- The code graph reports a **certified miss** for both `rate_limit` and `RateLimit` across all 7,293 indexed symbols (all tiers probed, including doc text) — no limiter type, constructor, or interceptor exists.
- A text search for `Limiter|limiter|TooManyRequests|429` across 343 Go files returns **no matches** — no `golang.org/x/time/rate` bucket, no 429 response path.
- The actual server-side interceptor chain is registered in one place, `server/router/api/v1/v1.go:133-138`, and consists of exactly four interceptors: `NewMetadataInterceptor()`, `NewLoggingInterceptor(logStacktraces)`, `NewRecoveryInterceptor(logStacktraces)`, `NewAuthInterceptor(authorizer)` — all defined in `server/router/api/v1/connect_interceptors.go` (lines 22, 98, 165, 208). None throttles.
- Echo-level middleware is likewise limiter-free: only `middleware.Recover()` and `newCORSMiddleware(profile)` at `server/server.go:51-52`, plus static file serving at `server/router/frontend/frontend.go:54`.

The closest thing to a request limit is a **size** limit, not a rate limit: `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` to the gateway routes and Connect mux (`v1.go:126, 141, 144`) and as `connect.WithReadMaxBytes`. That caps payload size per request and is global, not per-user.

Rate limiting appears only as an aspirational note in docs — `internal/email/README.md:286-295` ("Implement Rate Limiting", with an example sketch using `golang.org/x/time/rate`) and `internal/email/doc.go:86` — and that concerns outbound email sending, not the API surface. Neither is implemented.
