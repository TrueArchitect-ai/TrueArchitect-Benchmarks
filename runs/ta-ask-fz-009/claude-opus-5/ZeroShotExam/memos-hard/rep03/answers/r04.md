**Premise correction:** Neither. There is no message broker in this repository at all — no NATS, no RabbitMQ, no Kafka or Redis. A case-insensitive search of the Go manifests (`go.mod`, `go.sum`) for `nats|amqp|rabbit|streadway|kafka|redis` returns zero matches, so no broker client is even a dependency. There is also no separate "worker" process; webhook delivery happens inside the Memos server process.

**Actual mechanism — an in-process buffered Go channel with a fixed goroutine pool**, all in `internal/webhook/webhook.go`:

1. **The "queue" is a channel**, declared as a package-level variable at `internal/webhook/webhook.go:39`:
   ```go
   asyncPostQueue = make(chan *WebhookRequestPayload, 128)
   ```
   Capacity 128, buffering `*WebhookRequestPayload` values (`internal/webhook/webhook.go:79`).

2. **The "workers" are four goroutines** started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`; failures are logged with `slog.Warn` and dropped — there is no retry, no dead-letter path, no persistence.

3. **Producers enqueue via `PostAsync`** (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send: if the buffer is full, the payload is **discarded** with a "Dropped webhook dispatch because the async queue is full" warning. Overflow is lossy by design.

4. **Callers** are the memo webhook dispatchers: `APIV1Service.DispatchMemoCommentCreatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:30`) and `APIV1Service.dispatchMemoRelatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:48`).

5. **Actual delivery** is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120`), using a shared `safeClient` with a 30s timeout and an SSRF-guarding dialer that rejects reserved/private IPs (`internal/webhook/webhook.go:32-37`, `59-77`), plus optional Standard Webhooks HMAC-SHA256 signing headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) at lines 133-150.

The architectural consequence: webhook delivery state lives entirely in process memory. A restart or crash loses whatever is buffered, and there is no at-least-once guarantee — the same shape as `internal/email/email.go:14`'s `asyncEmailQueue`, which uses the identical channel pattern.
