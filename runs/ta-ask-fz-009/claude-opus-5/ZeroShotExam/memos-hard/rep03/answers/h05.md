## The explicit deletion

`DeleteUser` opens a transaction, collects targets, then runs an ordered sequence of deletes. Reactions are handled by **two** distinct passes:

1. **Reactions *on* the user's memos** (any author) — `deleteReactionsByContentIDsTx`, matching on `content_id` in batches of 500:
   - `store/db/mysql/user_delete.go:417-425`
   - `store/db/postgres/user_delete.go:380-388`
   - `store/db/sqlite/user_delete.go:380-388`
2. **Reactions *authored by* the user** (on anyone's content) — `deleteReactionsByCreatorTx`, matching `creator_id`:
   - `store/db/mysql/user_delete.go:437-440`
   - `store/db/postgres/user_delete.go:400-403`
   - `store/db/sqlite/user_delete.go:400-403`

Both are invoked from `deleteUserTargetsTx` — reaction cleanup runs *first*, before memos are removed (`store/db/mysql/user_delete.go:96` and `:102`), which matters because the content-ID pass reads memo UIDs collected earlier at `store/db/mysql/user_delete.go:93-94`. The whole sequence is one transaction with rollback on failure (`store/db/mysql/user_delete.go:29-59`).

Entry path: `server/router/api/v1/user_service.go:393` → `store/user.go:171` → the per-driver `DeleteUser` (`store/db/{mysql,postgres,sqlite}/user_delete.go:29`).

## Why the DB can't do it

The `reaction` schema declares only a uniqueness constraint on `(creator_id, content_id, reaction_type)` — no FK to `user`, and `content_id` is a free-form `TEXT`/`VARCHAR(256)` resource-name string, not a memo FK:
- `store/migration/sqlite/LATEST.sql:91-99`
- `store/migration/postgres/LATEST.sql:90-98`
- `store/migration/mysql/LATEST.sql:90-98`
- Original creation: `store/migration/{mysql,postgres,sqlite}/0.20/00__reaction.sql`

The only `FOREIGN KEY ... ON DELETE CASCADE` in the latest schema is `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). So reaction cleanup is entirely an application-layer invariant.

**Architectural consequence:** because `content_id` is a string with no referential integrity, orphaned reactions are only prevented by that explicit Go sequence. Any future path that deletes memos or users without going through `deleteUserTargetsTx` will silently leave reaction rows behind.
