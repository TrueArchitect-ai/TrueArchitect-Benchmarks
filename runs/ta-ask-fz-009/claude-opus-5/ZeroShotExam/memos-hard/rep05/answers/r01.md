**Premise correction:** there is no Redis in this repository. A case-insensitive search for `redis` across 1042 files returns zero matches, and there is no Redis client in the dependency graph. The cache layer is entirely **in-process, in-memory** — no external cache server, no connection string, no network hop to configure.

**Actual mechanism**

The cache is a hand-rolled TTL map in `store/cache/cache.go`:

- `cache.Cache` (`store/cache/cache.go:67`) wraps a `sync.Map` plus an atomic item counter, behind the `cache.Interface` contract (`store/cache/cache.go:11`).
- Entries are `item{value, expiration, size}` (`store/cache/cache.go:35`). `Set` stamps `expiration = time.Now().Add(ttl)` (`store/cache/cache.go:112`); `Get` treats a passed expiration as a miss (`store/cache/cache.go:135`).
- Eviction is two-pronged: a background `cleanupLoop` ticker sweeps expired items (`store/cache/cache.go:200`, `:218`), and `cleanupOldest` drops ~20% of `MaxItems` when the count exceeds the cap (`store/cache/cache.go:253`).

**Where it's "configured"** — `store.New` in `store/store.go:38-58`, inline in Go code, not in any config file or env var:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

Three separate cache instances are constructed from that one config: `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`), each with its own cleanup goroutine, all shut down in `Store.Close()` (`store/store.go:74-76`). `store/cache/cache.go:57` has an identical `DefaultConfig()`, but the store does not call it — it duplicates the values.

**TTL for user entries: 10 minutes**, inherited from `DefaultTTL` — there is no user-specific TTL. Writes in `store/user.go` all use plain `Set` (`store/user.go:98, 122, 132, 143, 167`), which routes through `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:94`). Keys are just the stringified user ID (`userCacheKey`, `store/user.go:88`).

Two consequences worth noting, since a Redis assumption usually hides them:
- **Not shared across processes.** Each server instance holds its own copy, so multi-replica deployments can serve up to 10 minutes of divergent user state — the cache is only correct for single-process deployment.
- **Invalidation is explicit and narrow.** Only delete paths purge: `deleteUserCache` (`store/user_delete.go:39-46`) removes the user key plus that user's setting keys. Reads are cache-first on lookup by ID only (`store/user.go:150`); lookups by other fields bypass the cache and refresh it on the way out.
