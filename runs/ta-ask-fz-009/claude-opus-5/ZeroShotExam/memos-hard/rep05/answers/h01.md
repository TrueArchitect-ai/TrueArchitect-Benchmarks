h01.

**`s3presign.Runner` (`server/runner/s3presign/runner.go:16`) — once at startup, then every 12 hours (`runnerInterval = time.Hour * 12`, `runner.go:27`) — wired at `server/server.go:162-171`, reached from `Server.Start` via `s.startBackgroundRunners(ctx)` at `server/server.go:129`.**

How it holds the invariant:

- **What goes stale:** S3 presigned GET URLs are minted with a 5-day expiry (`internal/storage/s3/s3.go:77-79`), and the URL is persisted as the attachment's `Reference`. Without refresh, stored links break after 5 days.
- **The work:** `CheckAndPresign` (`server/runner/s3presign/runner.go:47`) pages `ListAttachments` filtered to `AttachmentStorageType_S3` in batches of 100, and for each attachment whose payload carries an `S3Object`, re-presigns via `s3Client.PresignGetObject` and writes back both the new `Reference` and `LastPresignedTime` (`runner.go:108-123`).
- **The safety margin:** attachments presigned within the last 4 days are skipped (`runner.go:85-91`) — a 1-day buffer against the 5-day expiry, which is why a 12-hour tick is enough to never let a link lapse.
- **Config resolution:** per-attachment `s3ObjectPayload.S3Config` wins over the instance-level `GetInstanceStorageSetting` config (`runner.go:93-96`), so attachments uploaded under an older bucket config still refresh correctly.
- **Lifecycle:** it runs on its own cancellable context stored in `s.backgroundRunnerCancels` (`server/server.go:156-159`) and is tracked by `backgroundRunnerWG`, so shutdown is graceful via `stopBackgroundRunners` (`server/server.go:176`). Note `RunOnce(ctx)` at `server/server.go:163` runs **synchronously** on the startup path — a large S3 attachment table will delay server startup.

One documentation cross-check: `AGENTS.md:64` describes `server/runner/` as "Background memo processing and S3 presign refresh", matching the two runners present (`memopayload`, `s3presign`).
