**How the candidate was resolved**

Three concrete types implement `store.Driver.CreateMemo`, and each writes its own dialect-specific INSERT:
- `store/db/sqlite/memo.go:16`
- `store/db/mysql/memo.go:16`
- `store/db/postgres/memo.go:16`

Interface dispatch alone can't pick between them, so I followed the wiring to the single construction site instead of the call site:

- `cmd/memos/main.go:57` builds the driver exactly once — `db.NewDBDriver(instanceProfile)` — and hands the result to `store.New(dbDriver, instanceProfile)` (`cmd/memos/main.go:64`). That is the only value ever assigned to `Store.driver` in the server process.
- `NewDBDriver` switches on `profile.Driver` (`store/db/db.go:18-27`): `"sqlite"` → `sqlite.NewDB`, `"mysql"` → `mysql.NewDB`, `"postgres"` → `postgres.NewDB`, otherwise error.
- `profile.Driver` comes from `viper.GetString("driver")` (`cmd/memos/main.go:43`), whose default is `"sqlite"` — set both as the viper default (`cmd/memos/main.go:122`) and as the flag default (`cmd/memos/main.go:130`).

So with no `--driver`/`MEMOS_DRIVER` set, the switch takes the `"sqlite"` arm, `Store.driver` holds a `*sqlite.DB`, and the sqlite implementation is the one that runs. Corroborating detail: `internal/profile/profile.go:110` only synthesizes a default DSN when `p.Driver == "sqlite" && p.DSN == ""`, which is the default-install path — a file-backed sqlite database under the data directory.

The other two implementations are live code, just unreachable in a default install; they only execute when the driver flag/env selects them (the test harness does exactly this via `MEMOS_DRIVER` in `store/test/store.go:26-28`).
