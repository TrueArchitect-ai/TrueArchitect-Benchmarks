## What the Go code does

`deleteUserTargetsTx` runs two separate reaction deletes as the *first* and *third* steps of the transaction (identical in all three dialects):

## Why it is *not* a database rule

The `reaction` table declares no foreign keys at all — only a uniqueness constraint:

- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

Columns are `creator_id`, `content_id`, `reaction_type` with `UNIQUE(creator_id, content_id, reaction_type)` — no `FOREIGN KEY ... ON DELETE CASCADE`. For contrast, the adjacent `memo_share` table *does* carry one (`FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, sqlite `:109`, postgres `:108`, mysql `:108`), so the absence on `reaction` is a real design difference, not a dialect quirk.

Note also that `content_id` is a text column, not an integer FK to `memo.id` — a DB-level cascade from memo→reaction isn't even expressible here, which is precisely why the by-content_id sweep exists in Go.
