**Premise correction:** There is no Redis in this repository — no Redis client dependency, no connection string, no external cache service to configure. The cache layer is a hand-rolled, in-process, in-memory cache. My search across the whole tree for `redis`/`memcach` returned nothing but unrelated hits (e.g. `sizeCache` protobuf fields, `STARTTLS` in `internal/email/`), and the graph's symbol search for "redis" produced only fuzzy name matches like `filter.renderer.*`. **Actual mechanism:**

1. **Implementation** — `store/cache/cache.go`. A `Cache` struct backed by `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:67-73`), with a per-entry `expiration time.Time` (`store/cache/cache.go:35-39`). Eviction is a background goroutine started in `New` (`store/cache/cache.go:83`) that ticks on `CleanupInterval` and sweeps expired keys (`cleanupLoop` at :200, `cleanup` at :218); over-capacity entries are shed by `cleanupOldest` (:253). Expired entries are also evicted lazily on read (`Get`, :135-144). Nothing crosses a network boundary and nothing survives process restart.

2. **Where it's "configured"** — `store/store.go:38-58`. `store.New` builds one `cache.Config` literal and shares it across three caches: `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`, fields declared at `store/store.go:27-29`). The values are hardcoded in the constructor — `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil` (`store/store.go:40-45`). There is no env var, config file, or profile flag feeding these; `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) carries identical defaults but the store doesn't call it.

3. **TTL for user entries** — **10 minutes**, with a 1000-item cap shared per cache. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98, 122, 132, 143, 167`), and `Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — no user-specific TTL override exists. Reads hit the cache only when looked up by ID (`store/user.go:150`). Staleness is bounded further by explicit invalidation on delete: `deleteUserCache` drops the user key and its settings keys (`store/user_delete.go:39-46`).

One nuance worth knowing: because `MaxItems` is 1000 per cache and `cleanupOldest` sheds ~20% at a time (`store/cache/cache.go:255`), a user entry can disappear well before its 10-minute TTL on a busy instance. And since the cache is per-process, a multi-replica deployment would have independent, potentially divergent user caches — there's no shared invalidation channel, which is the gap Redis would normally fill.
