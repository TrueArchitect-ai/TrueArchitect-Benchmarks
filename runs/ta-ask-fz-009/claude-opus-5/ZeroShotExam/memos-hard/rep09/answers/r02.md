**The absence is verified, not just unfound:**
- The code graph returns a *certified miss* for both `rate limit` and `ratelimit` across all 7,293 indexed symbols (exact, prefix, substring, qname, abbreviation, and doc-text tiers).

Implement Rate Limiting") and `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse").

**The actual middleware/interceptor chain — no throttling in it:**
- Echo-level middleware, registered in `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:14`). That's the whole global chain.
- Connect RPC interceptors, registered in `server/router/api/v1/v1.go:133-138`: `NewMetadataInterceptor()`, `NewLoggingInterceptor()`, `NewRecoveryInterceptor()`, `NewAuthInterceptor()` — all four defined in `server/router/api/v1/connect_interceptors.go` (lines 22, 98, 165, 208). Metadata translation, logging, panic recovery, authorization. No rate or quota logic in any of them.

**The one limit that does exist is a size limit, not a rate limit** — possibly the source of the premise:
- `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, enforced via `http.MaxBytesHandler` on the gateway routes (`server/router/api/v1/v1.go:126`), on the Connect mux (`:144`), and as `connect.WithReadMaxBytes` (`:141`).

So the API is protected per-request by a body-size cap and per-caller by authentication, but there is no per-user request-rate ceiling anywhere in the server. If you need one, the natural insertion points are `server/server.go:51` for a global Echo-level limiter, or a new interceptor in the chain at `server/router/api/v1/v1.go:133` if you want it keyed off the authenticated user the `AuthInterceptor` resolves.
