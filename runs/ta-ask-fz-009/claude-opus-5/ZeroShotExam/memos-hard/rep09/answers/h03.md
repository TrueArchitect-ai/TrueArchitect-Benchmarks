**`internal/idp`; `internal/idp/oauth2`**

- **Abstraction package — `internal/idp`** (`internal/idp/idp.go:1`). It is a deliberately thin seam: the only thing it defines is the provider-neutral result contract `IdentityProviderUserInfo` (`Identifier`, `DisplayName`, `Email`, `AvatarURL` — `internal/idp/idp.go:3-8`). No Go interface is declared; the abstraction is the shared user-info type that any provider implementation must produce.

- **Implementation package — `internal/idp/oauth2`** (`internal/idp/oauth2/oauth2.go:1-2`, "Package oauth2 implements the OAuth2 identity provider integration"). It is the only concrete provider in the tree — `internal/idp` contains exactly `idp.go` plus the `oauth2/` subdirectory. It defines `IdentityProvider` over `storepb.OAuth2Config` (`oauth2.go:20-22`), constructed by `NewIdentityProvider` with required-field validation (`oauth2.go:27-43`), and exposes two operations:
  - `ExchangeToken` — authorization-code exchange via `golang.org/x/oauth2`, with optional PKCE `code_verifier` (`oauth2.go:47-80`)
  - `UserInfo` — bearer-token call to the configured `UserInfoUrl`, then maps raw claims into `idp.IdentityProviderUserInfo` through the configured field mapping (`oauth2.go:83-142`)

The boundary crossing is visible at `oauth2.go:15` and `oauth2.go:83`: the implementation imports the abstraction package and returns its type, so callers depend on `idp`, not on OAuth2 specifics. At the API layer the protocol choice is also modeled as a one-of variant, `IdentityProviderConfig_Oauth2Config` (`proto/gen/api/v1/idp_service.pb.go:216`) — the extension point for future protocols exists in the contract, but only the OAuth2 arm ships.
