**How the funnel narrows** (all in `server/router/api/v1/memo_service_webhooks.go`):

- The three plain memo events are thin wrappers that pass only an activity-type string into the shared helper `dispatchMemoRelatedWebhook` (`:48`) — created `:15-17`, updated `:20-22`, deleted `:25-27`. That helper resolves the memo's creator (`ResolveUserByName`, `:49`), loads their hooks via `s.Store.GetUserWebhooks` (`:57`), and fires one payload per hook.
- The comment event is deliberately *not* routed through that helper (`:30-46`): its recipient is the **related memo's owner**, not the comment author, so it takes `relatedMemoCreatorID` directly and looks hooks up against that ID (`:31`). Same payload shape, different subscriber resolution.
- Both paths build the payload with `convertMemoToWebhookPayload` (`:76`), stamp `ActivityType`, `URL`, `SigningSecret`, and call `webhook.PostAsync(payload)` (`:43` and `:71`).

`PostAsync` is only an enqueue onto a buffered channel (`asyncPostQueue`, cap 128, `internal/webhook/webhook.go:39`); four worker goroutines started in `init()` (`:42-55`) drain it and call `Post`, which is the single place the HTTP request is built, signed with the Standard Webhooks `webhook-id`/`-timestamp`/`-signature` headers (`:147-149`), and sent through the SSRF-guarded `safeClient` (`:32`, dialer at `:59`).

Two boundary notes worth knowing: the queue is lossy under pressure — a full channel drops the dispatch with a warning rather than blocking (`:192`), so webhook delivery is best-effort by design; and the private-IP guard is enforced at dial time, overridable via the `--allow-private-webhooks` flag (`cmd/memos/main.go:49`, `internal/webhook/validate.go:38`).
