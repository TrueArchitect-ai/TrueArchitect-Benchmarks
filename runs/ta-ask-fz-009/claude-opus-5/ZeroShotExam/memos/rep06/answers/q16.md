The store-layer `Store.DeleteMemo` (`store/memo.go:140-159`) deletes, in order, before removing the memo row:

1. **`memo_relation` rows where the memo is the source** — `driver.DeleteMemoRelation(&DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target/related memo** — `driver.DeleteMemoRelation(&DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **Attachment records linked to the memo** — listed via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and removed one by one with `DeleteAttachment` (`store/memo.go:149-157`), which also deletes the backing blob/file in storage before the row (`store/attachment.go:132-148`)

Only then does it call `driver.DeleteMemo` to remove the `memo` row itself (`store/memo.go:158`; e.g. `DELETE FROM memo WHERE id = ?` in `store/db/sqlite/memo.go:237-248`).

Note on scope: comment memos and reactions are *not* handled inside the store method — the API handler `APIV1Service.DeleteMemo` deletes child comment memos beforehand by looking up `MemoRelationComment` relations and recursively calling `Store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`).
