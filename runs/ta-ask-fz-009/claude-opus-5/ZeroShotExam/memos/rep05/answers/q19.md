**MemoService is exposed twice from the same `APIV1Service` implementation — once as REST/JSON through the gRPC-Gateway, once over the Connect protocol (Connect/gRPC/gRPC-Web wire formats).**

1. **REST/JSON via gRPC-Gateway** — `server/router/api/v1/v1.go:108` (`v1pb.RegisterMemoServiceHandlerServer(ctx, gwMux, s)`), registered on the gateway mux built at `v1.go:96` with the shared auth middleware, then mounted on Echo at `/api/v1/*` and `/file/*` (`v1.go:126-129`). Generated glue: `proto/gen/api/v1/memo_service.pb.gw.go:961`.

2. **Connect protocol** — `server/router/api/v1/connect_handler.go:40` (`wrap(apiv1connect.NewMemoServiceHandler(s, opts...))`) inside `RegisterConnectHandlers` (`connect_handler.go:31`). It's wired in `server/router/api/v1/v1.go:139-144`: a plain `http.ServeMux`, the Connect interceptor chain (metadata → logging → recovery → auth, `v1.go:133-138`), and mounting on Echo at `/memos.api.v1.*`. Generated glue: `proto/gen/api/v1/apiv1connect/memo_service.connect.go:461`.

Two notes worth having:
- Both paths share one authorizer instance (`v1.go:68`) — the gateway consumes it through `gatewayAuthMiddleware`, Connect through `NewAuthInterceptor(authorizer)`, so the auth policy is a single source of truth across protocols.
- `RegisterMemoServiceServer` exists only in the generated file `proto/gen/api/v1/memo_service_grpc.pb.go:439`; I found no call site in the server, so there is no standalone gRPC listener — gRPC/gRPC-Web reach the service only through the Connect handler, which speaks those wire formats.
