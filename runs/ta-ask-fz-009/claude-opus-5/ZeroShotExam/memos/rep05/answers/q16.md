`(*Store).DeleteMemo` in `store/memo.go:140-159` performs cascade cleanup before delegating the row delete to the driver (`s.driver.DeleteMemo`, `store/memo.go:158` → e.g. `store/db/mysql/memo.go:259` which is a bare `DELETE FROM memo WHERE id = ?`):

1. **Memo relations where this memo is the source** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **Memo relations where this memo is the target** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and deleted one by one with `DeleteAttachment` (`store/memo.go:149-157`); `Store.DeleteAttachment` (`store/attachment.go:132`) additionally removes the backing blob through `DeleteAttachmentStorage` (`store/attachment.go:193`).
4. **Then** the memo row itself.

Note: reactions are *not* deleted here — the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) only reads reactions/relations for the webhook and SSE payloads; no reaction cleanup happens in the store's memo-delete path.
