**Two things worth flagging:**

1. **`reaction` is *not* cleaned up.** `DeleteMemo` lists reactions (`memo_service.go:545-550`) but only to build the webhook/SSE payload — no delete call. Reaction rows key off `content_id` (a resource name string, `reaction` table has no FK to `memo`), so they are orphaned after deletion. Contrast with the user-deletion path, which does purge reactions explicitly (`store/db/*/reaction.go` `DeleteReaction`).

2. **The `memo_share` cascade does not fire on SQLite.** The SQLite connection is opened with foreign keys disabled: `_pragma=foreign_keys(0)` at `store/db/sqlite/sqlite.go:53`. So on SQLite deployments `memo_share` rows survive the memo, while on Postgres/MySQL they are cascaded away. That's a real cross-dialect behavioral divergence in the delete invariant, not just a schema detail.
