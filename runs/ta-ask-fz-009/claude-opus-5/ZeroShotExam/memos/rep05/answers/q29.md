## How it works

**Frontend — one interceptor on one transport.** `authInterceptor` (`web/src/connect.ts:156`) is the only interceptor on the shared Connect transport (`web/src/connect.ts:184-189`), so every service client exported from that file (memo, user, attachment, AI, shortcut, instance, IdP, auth — lines 192-203) is authenticated by it. Its contract:

- Pre-flight: `getRequestToken()` (`connect.ts:124`) fetches the access token, and if it is within 30s of expiry (`REQUEST_TOKEN_EXPIRY_BUFFER_MS`, `auth-state.ts:18`) refreshes *before* sending — deliberately, because an expired token on a public endpoint would silently return guest-scoped data (`connect.ts:136-147`).
- Sets `Authorization: Bearer <token>` (`connect.ts:97-100`).
- Reactive: on `Code.Unauthenticated`, refresh once, stamp `X-Retry: true`, replay; on second failure call `redirectOnAuthFailure()` (`connect.ts:163-177`). The `X-Retry` guard is what bounds the retry to one attempt.

**Token kinds the frontend manages:**
1. **Access token** — JWT, 15 min (`server/auth/token.go:40`), held in-memory + `localStorage` under `memos_access_token` / `memos_token_expires_at` (`web/src/auth-state.ts:6-7`), and broadcast across tabs over a `BroadcastChannel` so only one tab refreshes (`auth-state.ts:26-50`).
2. **Refresh token** — JWT, 30 days (`server/auth/token.go:43`), never touched by JS: it rides an HTTP cookie, which is why the transport uses `credentials: "include"` (`connect.ts:57-62`) and why the refresh call goes through a *separate* transport with `interceptors: []` to avoid recursion (`connect.ts:65-72`).

Concurrent refreshes are deduplicated by `createTokenRefreshManager` (`connect.ts:30-51`) — the interceptor's reactive 401 path and the focus-based proactive refresh share one in-flight promise, since server-side refresh-token rotation makes duplicate calls conflict.

**Backend — validation lives in `server/auth/`.** The Connect-side enforcement point is `AuthInterceptor.WrapUnary` (`server/router/api/v1/connect_interceptors.go:217`), which reads the `Authorization` header and delegates to `Authorizer.Authenticate` + `CheckAccess`, then puts the result on the context via `auth.ApplyToContext`. The actual credential validation is `auth.Authenticator` (`server/auth/authenticator.go:26`):

- `AuthenticateByAccessTokenV2` — stateless JWT parse, no DB hit (`authenticator.go:41`)
- `AuthenticateByPAT` — hash lookup, prefix-discriminated (`authenticator.go:102`)
- `AuthenticateByRefreshToken` — parses, then checks the DB for revocation and expiry (`authenticator.go:61`)

`resolveBearer` (`authenticator.go:149`) is the dispatch: a `PersonalAccessTokenPrefix` prefix routes to PAT, otherwise access-token V2. Note the invariant — invalid bearer tokens return `(nil, nil)`, not an error, so callers can fall back; that fallback to the refresh cookie exists only in `AuthenticateToUser` (`authenticator.go:190`), used by the file server, **not** in the interceptor path, which ignores the cookie (`authenticator.go:210-224`). Per the package doc, `server/auth` is shared by both `server/router/api/v1` and `server/router/fileserver` (`server/auth/token.go:1-11`), which is what keeps auth behavior consistent across API and file downloads.
