Two-stage convergence worth noting:

- The three plain memo events funnel through one private helper, `dispatchMemoRelatedWebhook` (`memo_service_webhooks.go:48`), which differs only in the `activityType` string it stamps on the payload. The comment event does **not** use that helper — it resolves webhooks from `relatedMemoCreatorID` (the parent memo's owner) rather than the comment author's creator (`memo_service_webhooks.go:31`), so it duplicates the loop body.
- All four then call `webhook.PostAsync(payload)` (`:43` and `:71`), which enqueues onto a buffered channel `asyncPostQueue` (cap 128, `internal/webhook/webhook.go:39`) drained by 4 worker goroutines started in `init()` (`internal/webhook/webhook.go:42-55`). Each worker calls `Post`, the single function that performs the actual signed HTTP request through `safeClient`, whose transport blocks reserved/private IPs at dial time as an SSRF guard (`internal/webhook/webhook.go:32-37`, `safeDialContext` at `:59`).

Failure semantics at the boundary: dispatch errors are logged only (`slog.Warn`, `internal/webhook/webhook.go:47`), never returned to the caller — the queue is fire-and-forget, and a full queue or nil payload is dropped with a warning (`:185`).
