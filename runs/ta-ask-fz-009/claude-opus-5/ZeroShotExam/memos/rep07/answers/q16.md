`store.Store.DeleteMemo` (`store/memo.go:140`) performs two cleanup steps before delegating the actual row delete to the driver at `store/memo.go:158`:

1. **`memo_relation` rows where the memo is the source** — `driver.DeleteMemoRelation(&DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `driver.DeleteMemoRelation(&DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and removed one by one with `s.DeleteAttachment(...)` (`store/memo.go:149-157`). Each of those also deletes the underlying stored file/blob first (`store/attachment.go:141` → `DeleteAttachmentStorage`) before the `attachment` row (`store/attachment.go:148`).
4. Then the memo row itself: `driver.DeleteMemo` — e.g. `DELETE FROM memo WHERE id = ?` in `store/db/sqlite/memo.go:237-248` (same in `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).

Two adjacent facts worth noting, since they're outside the store layer:
- **Reactions are not deleted by the store layer** in this path. `DeleteMemo` in `store/memo.go` only reads reactions... actually it doesn't touch them at all; the API handler merely *lists* them for the webhook payload (`server/router/api/v1/memo_service.go:545`).
- **Comment memos** are deleted by the API handler before it calls the store, not by the store itself: it lists `MemoRelationComment` relations pointing at the memo and calls `Store.DeleteMemo` recursively on each (`server/router/api/v1/memo_service.go:568-577`), so each comment gets the same relation + attachment cleanup.
