### Frontend: `web/src/connect.ts`
- `authInterceptor` (`web/src/connect.ts:156`) is registered on the single Connect-RPC transport (`web/src/connect.ts:184-189`), so every generated service client (memo, user, attachment, AI, shortcut, IdP, instance, auth) goes through it.
- Per request it calls `getRequestToken()` (`connect.ts:124`) and sets `Authorization: Bearer <token>` (`connect.ts:97-100`).
- Two refresh paths:
  - **Preflight** — if `isTokenExpired(REQUEST_TOKEN_EXPIRY_BUFFER_MS)` it refreshes *before* sending, specifically so an expired token isn't silently downgraded to anonymous on public endpoints (`connect.ts:136-147`).
  - **Reactive** — on `Code.Unauthenticated` it refreshes once, retries with an `X-Retry: true` header guard against loops, and on failure calls `redirectOnAuthFailure()` (`connect.ts:161-177`).
- Refresh uses a **separate transport with no interceptors** to avoid recursion (`connect.ts:65-72`), calling `AuthService.refreshToken` with `credentials: "include"` so the refresh cookie rides along. Concurrent refreshes are deduplicated by `tokenRefreshManager` (`connect.ts:30-51, 89-91`).

### Tokens managed
- **Access token (JWT, 15 min)** — held in memory + `localStorage` under `memos_access_token` / `memos_token_expires_at` (`web/src/auth-state.ts:1-7`), synced across tabs via a `BroadcastChannel` named `memos_token_sync` (`auth-state.ts:13, 28-50`) so only one tab hits the refresh endpoint.
- **Refresh token (JWT, 30 days)** — never touched by JS; it's an HttpOnly cookie `memos_refresh` (`server/auth/token.go:49`), sent because the transport's fetch forces `credentials: "include"` (`connect.ts:57-62`). Rotated server-side by `APIV1Service.RefreshToken` (`server/router/api/v1/auth_service_session.go:113`, cookie built at `:224`), exposed as `POST /api/v1/auth/refresh`.
- **Personal Access Tokens** — backend-only path for programmatic clients, prefix `memos_pat_` (`server/auth/token.go:52`); the web interceptor never issues these.

### Backend validation: `server/auth`
- Server-side gate is `AuthInterceptor.WrapUnary` (`server/router/api/v1/connect_interceptors.go:217`): reads the `Authorization` header, calls `authorizer.Authenticate` then `CheckAccess` on the procedure, maps failure to `CodeUnauthenticated`, and stamps identity into context via `auth.ApplyToContext`.
- Actual token verification lives in the **`server/auth`** package (`server/auth/authenticator.go`):
  - `resolveBearer` (`:149`) branches on the `memos_pat_` prefix — non-PAT goes to `AuthenticateByAccessTokenV2` (`:41`), stateless JWT parse via `ParseAccessTokenV2`; PAT goes to `AuthenticateByPAT` (`:102`) using a SHA-256 hash lookup.
  - `AuthenticateByRefreshToken` (`:61`) parses the refresh JWT *and* checks it against the DB (`GetUserRefreshTokenByID`) so revocation works — the one stateful check.
- Per that package's own doc header, it's shared by both `server/router/api/v1` interceptors and `server/router/fileserver` (`server/auth/token.go:1-11`), which is what keeps auth behavior consistent across the RPC and file-serving boundaries.
