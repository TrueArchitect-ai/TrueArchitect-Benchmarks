**q20.**

**Mechanism:** Server-Sent Events (SSE) over HTTP — a long-lived `GET /api/v1/sse` stream with `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `X-Accel-Buffering: no`, plus a 30s heartbeat (`sseHeartbeatInterval`) to keep the connection open. Not WebSockets (`gorilla/websocket` is only an indirect dependency in `go.mod:79`). Route registration and the per-connection handler live in `server/router/api/v1/sse_handler.go:25` (`RegisterSSERoutes`) and `:34` (`handleSSE`), which authenticates via Bearer token before subscribing.

**Hub path:** `server/router/api/v1/sse_hub.go` — `SSEHub` struct at `sse_hub.go:56` (mutex + `map[*SSEClient]struct{}`, safe for concurrent use), with `SSEHub.Broadcast` at `sse_hub.go:115`. Event payload type `SSEEvent` (`sse_hub.go:24`) carries `Visibility`/`CreatorID` as JSON-excluded fields used purely for server-side delivery filtering, so the hub fans out per-client rather than blindly. Event-type vocabulary is the const block at `sse_hub.go:15-21`: `memo.created`, `memo.updated`, `memo.deleted`, `memo.comment.created`, `reaction.upserted`, `reaction.deleted`.

Two design details worth noting. The update event is broadcast through the shared side-effect helper `dispatchMemoUpdatedSideEffects`, not inline — so `UpdateMemo` (`memo_service.go:401`), `SetMemoAttachments` (`memo_attachment_service.go:16`), and `SetMemoRelations` (`memo_relation_service.go:16`) all emit `memo.updated` transitively via that one funnel. And comment creation deliberately avoids a double broadcast: `CreateMemoComment` calls `CreateMemo` wrapped in `withSuppressSSE(ctx)` (`memo_service_comments.go:56`), suppressing the generic `memo.created` event so only the more specific `memo.comment.created` reaches clients — the context-key suppression mechanism is `suppressSSEKey`/`withSuppressSSE`/`isSSESuppressed` at `memo_service.go:22-37`.
