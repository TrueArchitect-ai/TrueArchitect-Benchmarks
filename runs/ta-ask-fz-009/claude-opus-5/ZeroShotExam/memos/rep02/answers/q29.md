**Frontend interceptor**
- `authInterceptor` (`web/src/connect.ts:156`) is the only interceptor on the transport used by every service client (`web/src/connect.ts:184-203`), so all Connect RPCs pass through it.
- Per request: `getRequestToken()` (`web/src/connect.ts:124`) returns the access token, refreshing preemptively when within a 30s expiry buffer; `setAuthorizationHeader` (:97) sets `Authorization: Bearer <token>`.
- On a `Code.Unauthenticated` response it refreshes once and replays the request with an `X-Retry: true` marker to prevent loops (:164-176); if the refresh fails it calls `redirectOnAuthFailure()` (`web/src/utils/auth-redirect.ts`).

**Tokens it manages**
- **Access token** — short-lived JWT held in memory + `localStorage` under `memos_access_token` / `memos_token_expires_at` (`web/src/auth-state.ts:6-7`), shared across tabs over a `BroadcastChannel` (`web/src/auth-state.ts:13,31-46`).
- **Refresh token** — never touched by JS; it's an HttpOnly cookie, which is why the transport uses `credentials: "include"` (`web/src/connect.ts:57-62`). Refresh goes through a separate interceptor-free transport to avoid recursion (:65-72) calling `AuthService.RefreshToken`, deduplicated by `tokenRefreshManager` (:30-51).
- **PAT** is a backend-supported third kind for programmatic clients, not something the web interceptor issues.

**Backend validation**
- `server/router/api/v1/connect_interceptors.go:217-230` reads the `Authorization` header, calls `Authorizer.Authenticate` / `CheckAccess`, and returns `CodeUnauthenticated` on failure.
- Actual token verification lives in **`server/auth`**: `Authenticator.Authenticate` (`server/auth/authenticator.go:213`) → `resolveBearer` (:149), which routes to `AuthenticateByAccessTokenV2` (:41, stateless JWT parse) or `AuthenticateByPAT` (:102, hash lookup). Refresh tokens are validated statefully with a DB revocation check in `AuthenticateByRefreshToken` (:61); cookie extraction is `server/auth/extract.go:23`, token constants/parsing in `server/auth/token.go`.
