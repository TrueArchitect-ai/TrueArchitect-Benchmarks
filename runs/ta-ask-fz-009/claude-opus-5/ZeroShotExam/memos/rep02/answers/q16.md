I'll trace the memo deletion path through the store layer.

q16.

`store.Store.DeleteMemo` (`store/memo.go:140`–`159`) performs exactly two kinds of dependent cleanup before delegating the row delete to the driver:

1. **`memo_relation` rows where the memo is the source** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and deleted one at a time with `s.DeleteAttachment` (`store/memo.go:149`–`157`). That path also removes the backing blob/local file, since `Store.DeleteAttachment` calls `DeleteAttachmentStorage` before the row delete (`store/attachment.go:132`–`148`).

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`), which is a plain single-row `DELETE FROM memo WHERE id = ?` in each driver (e.g. `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

Two boundary notes:

- **Comment memos are cascaded one layer up, not in the store.** `APIV1Service.DeleteMemo` first lists `memo_relation` rows of type `MemoRelationComment` targeting the memo and recursively calls `Store.DeleteMemo` on each child memo (`server/router/api/v1/memo_service.go:567`–`577`), then deletes the parent (`:580`).
- **Reactions and memo shares are not deleted on this path.** The API handler only *reads* reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545`); neither `Store.DeleteMemo` nor the handler issues a reaction or `memo_share` delete, so those rows are left to DB-level constraints if any exist.
