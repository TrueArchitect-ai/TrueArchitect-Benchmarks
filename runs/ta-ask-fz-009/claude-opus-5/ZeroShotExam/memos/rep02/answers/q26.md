Two things worth flagging about the boundary:

- **Comments recurse.** The API layer (`server/router/api/v1/memo_service.go:567-582`) first lists `memo_relation` rows of type `comment` pointing at the target and calls `store.DeleteMemo` on each child memo, so the same four tables are touched once per comment plus once for the parent.
- **`reaction` is *not* cleaned up.** `DeleteMemo` reads reactions only to build the webhook payload (`memo_service.go:545-565`); nothing deletes them. The `reaction` table has no FK to `memo` either — it keys off a text `content_id` (`store/migration/sqlite/LATEST.sql:92-99`), so no DB cascade can fire. Reaction rows for a deleted memo are orphaned. Same for `memo_organizer`-style pinning data, which in this schema lives as a column on `memo` rather than a separate table.

There is no transaction wrapping the sequence — `store.DeleteMemo` issues each statement on `d.db` directly, so a mid-sequence failure leaves relations or attachments deleted with the memo row still present.
