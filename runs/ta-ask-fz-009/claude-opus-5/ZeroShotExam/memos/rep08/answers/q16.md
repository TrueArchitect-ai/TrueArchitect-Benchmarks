I'll trace the memo deletion path through the store layer.

q16.

`Store.DeleteMemo` (`store/memo.go:140`–`159`) performs exactly two kinds of cleanup before delegating the memo row deletion to the driver (`s.driver.DeleteMemo` at `store/memo.go:158`):

1. **Memo relation records where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **Memo relation records where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments(FindAttachment{MemoID:...})` then deleted one by one with `DeleteAttachment` (`store/memo.go:149`–`157`). Each `Store.DeleteAttachment` also removes the underlying stored file/blob before the attachment row (`store/attachment.go:132`–`148`).

Two adjacent facts worth knowing, since they're often assumed to live in the store:

- **Comment memos are deleted by the API layer, not the store.** `APIV1Service.DeleteMemo` lists `MemoRelationComment` relations pointing at the memo and calls `Store.DeleteMemo` for each comment first (`server/router/api/v1/memo_service.go:567`–`577`), which recursively triggers the relation/attachment cleanup above.
- **Reactions are not deleted by `Store.DeleteMemo`.** The service reads reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545`–`560`); there is no reaction delete on this path in the store layer. The driver-level `DeleteMemo` is a plain `DELETE FROM memo WHERE id = ?` with no extra statements (e.g. `store/db/sqlite/memo.go:237`–`248`), so any reaction removal would have to come from DB-level cascade, not from this code path.
