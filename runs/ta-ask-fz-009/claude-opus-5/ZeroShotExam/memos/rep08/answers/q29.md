## Frontend side

`authInterceptor` (`web/src/connect.ts:156-178`) is installed on the single Connect-Web transport (`web/src/connect.ts:184-189`) that backs every service client (`memoServiceClient`, `userServiceClient`, etc., lines 192-203). Its contract per request:

1. `getRequestToken()` (`connect.ts:124`) returns the in-memory/localStorage access token, doing a **preflight refresh** if `isTokenExpired(REQUEST_TOKEN_EXPIRY_BUFFER_MS)` — 30s buffer — so public endpoints like ListMemos don't silently degrade to guest scope (`connect.ts:136-147`).
2. Sets `Authorization: Bearer <token>` (`connect.ts:97-100`).
3. On a `Code.Unauthenticated` response it refreshes reactively, retries once marked with the `X-Retry` header (`connect.ts:23-24`, `164-172`), and on failure calls `redirectOnAuthFailure()`.

Refresh itself goes through a **separate transport with no interceptors** to prevent recursion (`connect.ts:64-72`), and all refreshes are funneled through `tokenRefreshManager` to deduplicate concurrent refreshes (`connect.ts:30-51, 89-91`).

## Tokens managed

| Token | Storage | Managed where |
|---|---|---|
| Access token (JWT, 15 min) | `localStorage["memos_access_token"]` + `memos_token_expires_at`, mirrored in memory, cross-tab synced via `BroadcastChannel("memos_token_sync")` | `web/src/auth-state.ts:1-128` |
| Refresh token (JWT, 30 days) | HttpOnly cookie `memos_refresh` — never touched by JS; sent because the transport uses `credentials: "include"` (`connect.ts:57-62`) | `server/auth/token.go:49` |
| Personal Access Token | not frontend-managed; same `Authorization` header path, prefix `memos_pat_` | `server/auth/token.go:52` |

## Backend validation

`server/auth` is the single validation package (its doc comment at `server/auth/token.go:1-11` states exactly this contract):

- `auth.Authenticator.Authenticate` dispatches on prefix — no `memos_pat_` prefix ⇒ stateless `AuthenticateByAccessTokenV2` (`authenticator.go:41`, JWT parse only, no DB hit); otherwise `AuthenticateByPAT` (`authenticator.go:102`, SHA-256 hash lookup).
- `AuthenticateByRefreshToken` (`authenticator.go:61`) parses *and* checks the DB for revocation via `store.GetUserRefreshTokenByID`.

It's reached from three edges: the Connect `AuthInterceptor.WrapUnary` (`server/router/api/v1/connect_interceptors.go:217-231`) via the `Authorizer` shim (`server/router/api/v1/authz.go:44`); the SSE handler (`server/router/api/v1/sse_handler.go:37`); and the file server (`server/router/fileserver/fileserver.go:711`). Refresh/rotation is handled by `APIV1Service.RefreshToken` (`server/router/api/v1/auth_service_session.go:113-131`, endpoint `POST /api/v1/auth/refresh`), which reads the cookie and rotates the token — the reason the frontend deduplicates refreshes.
