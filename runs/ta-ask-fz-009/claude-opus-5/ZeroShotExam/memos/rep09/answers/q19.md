q19.

MemoService is exposed twice over HTTP from the same `APIV1Service` implementation — the wrapper comment at `server/router/api/v1/connect_handler.go:13-20` states this explicitly ("Support both native gRPC and Connect protocols… single source of truth for business logic").

**Connect (connect-go / connectrpc) — `server/router/api/v1/connect_handler.go:40**
`wrap(apiv1connect.NewMemoServiceHandler(s, opts...))` inside `RegisterConnectHandlers`, mounted on the `http.ServeMux` at line 48. The generated constructor it calls lives at `proto/gen/api/v1/apiv1connect/memo_service.connect.go:461`.

**gRPC-Gateway (REST/JSON transcoding) — `server/router/api/v1/v1.go:108**
`v1pb.RegisterMemoServiceHandlerServer(ctx, gwMux, s)` inside `RegisterGateway`; the mux is wrapped with a size limit and mounted on Echo at `/api/v1/*` and `/file/*` (lines 126–129). The generated transcoding layer is `proto/gen/api/v1/memo_service.pb.gw.go`.

Note the `...HandlerServer` (in-process) form is used, not `RegisterMemoServiceServer` from `proto/gen/api/v1/memo_service_grpc.pb.go:439` — so the gateway calls the service directly rather than dialing a gRPC socket. Auth differs per path: the gateway uses `gatewayAuthMiddleware` (`v1.go:69-93`), Connect uses an interceptor, both backed by the shared `NewAuthorizer` at `v1.go:68`.
