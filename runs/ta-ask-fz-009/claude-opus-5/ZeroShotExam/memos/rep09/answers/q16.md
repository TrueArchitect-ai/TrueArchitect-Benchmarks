`Store.DeleteMemo` (`store/memo.go:140-159`) performs this cleanup before delegating the memo row delete to the driver (`store/memo.go:158`):

1. **`memo_relation` records where the memo is the source** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **`memo_relation` records where the memo is the target** — same call with `RelatedMemoID: &delete.ID` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments(FindAttachment{MemoID: ...})` and removed one by one with `s.DeleteAttachment` (`store/memo.go:149-157`). That path also removes the underlying blob: `Store.DeleteAttachment` calls `DeleteAttachmentStorage` before deleting the attachment row (`store/attachment.go:132-146`).

Note on scope: reactions are *not* deleted here. The API handler only reads reactions to build the webhook/SSE payload (`server/router/api/v1/memo_service.go:545-560`), so at the store layer the ordered cleanup is memo relations (both directions), then attachments + their storage, then the memo row.
