### Frontend side

The interceptor is registered on a single Connect transport that backs every service client (`web/src/connect.ts:184-203`), so all RPC traffic goes through it:

- **Attach**: `getRequestToken()` (`connect.ts:124`) reads the in-memory/localStorage access token and sets `Authorization: Bearer <token>` (`connect.ts:97-100`).
- **Preflight refresh**: if the token is within 30s of expiry (`REQUEST_TOKEN_EXPIRY_BUFFER_MS`, `auth-state.ts:18`) it refreshes *before* sending — explicitly so public endpoints like `ListMemos` don't silently return guest-scoped data (`connect.ts:136-147`).
- **Reactive retry**: on `Code.Unauthenticated`, it refreshes once, re-sends with an `X-Retry: true` marker to prevent loops, and on failure calls `redirectOnAuthFailure()` (`connect.ts:163-177`).
- **Refresh isolation**: refresh goes through a *separate* transport with `interceptors: []` to avoid recursion (`connect.ts:65-72`), and all callers funnel through `tokenRefreshManager` (`connect.ts:30-51`) to deduplicate concurrent refreshes racing the on-focus refresher.

### Token kinds

| Token | Lifetime | Storage | Validation |
|---|---|---|---|
| Access token (JWT v2) | 15 min (`server/auth/token.go:40`) | localStorage `memos_access_token` (`auth-state.ts:6`) | Stateless — `AuthenticateByAccessTokenV2` (`authenticator.go:41`) |
| Refresh token (JWT) | 30 days (`token.go:43`) | HttpOnly cookie `memos_refresh` (`token.go:49`); sent via `credentials: "include"` | Stateful — DB revocation + expiry check (`authenticator.go:61-99`) |
| Personal Access Token | long-lived | client-supplied | Hash lookup `AuthenticateByPAT` (`authenticator.go:102`) |

Cross-tab coordination is handled by a `BroadcastChannel` (`memos_token_sync`, `auth-state.ts:13-50`) so one tab's refresh is adopted by the others rather than each firing its own.

### Backend validation

`AuthInterceptor.WrapUnary` pulls the `Authorization` header, delegates to `Authorizer.Authenticate`, then gates the procedure via `CheckAccess`, returning `CodeUnauthenticated` on failure and stamping identity into the context with `auth.ApplyToContext` (`connect_interceptors.go:217-231`). The `server/auth` package is the shared authority — its own doc comment names its consumers as `server/router/api/v1` and `server/router/fileserver` (`server/auth/token.go:1-11`), which is what keeps API and file-serving auth behavior consistent.

One asymmetry worth noting: the interceptor path (`Authenticate`, `authenticator.go:213`) **ignores the refresh cookie** and accepts only Bearer credentials; `AuthenticateToUser` (`authenticator.go:190`) is the variant that falls back to the cookie. So the refresh cookie authenticates only the refresh/file-server flows, not ordinary RPCs.
