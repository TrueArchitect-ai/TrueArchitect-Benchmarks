**How the funnel is shaped**

- The three plain lifecycle events are thin wrappers over one shared helper, `dispatchMemoRelatedWebhook(ctx, memo, activityType)` (`server/router/api/v1/memo_service_webhooks.go:48`) — it resolves the memo creator, loads that user's hooks via `s.Store.GetUserWebhooks`, stamps `ActivityType`/`URL`/`SigningSecret` on the payload, and calls `webhook.PostAsync` (line 71).
- `DispatchMemoCommentCreatedWebhook` bypasses that helper because it targets the *related* memo's owner rather than the comment author (`GetUserWebhooks(ctx, relatedMemoCreatorID)`, line 31), but it lands on the same `webhook.PostAsync` (line 43).
- `PostAsync` enqueues onto a bounded 128-slot channel `asyncPostQueue` drained by 4 goroutines started in `init()` (`internal/webhook/webhook.go:39–55`); each worker calls `Post`, which does the HMAC-SHA256 Standard-Webhooks signing and the actual HTTP POST through `safeClient` (SSRF-guarded dialer, `:59`). Overflow is dropped with a warning — delivery is best-effort, not durable.
