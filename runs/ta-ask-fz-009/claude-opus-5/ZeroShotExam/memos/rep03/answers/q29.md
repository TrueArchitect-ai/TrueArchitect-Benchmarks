## Frontend: `web/src/connect.ts`

`authInterceptor` (`web/src/connect.ts:156`) is installed on the single Connect transport (`connect.ts:184-189`), so every generated service client (memo, user, attachment, AI, shortcut, IdP, instance, auth) gets it for free.

Flow per request:
1. `getRequestToken()` (`connect.ts:124`) returns the access token, doing a **preflight refresh** if it's within 30s of expiry (`connect.ts:140`) — needed so public endpoints like `ListMemos` don't silently return guest-scoped data.
2. Token is attached as `Authorization: Bearer <token>` (`connect.ts:97-100`).
3. On a `Code.Unauthenticated` response, it does a **reactive refresh**, sets an `X-Retry: true` header, and replays the request once (`connect.ts:164-172`). Second failure → `redirectOnAuthFailure()`.

Two details worth knowing:
- Refresh goes through a **separate transport with no interceptors** (`connect.ts:65-72`) to prevent recursion, and through `tokenRefreshManager` (`connect.ts:30-51`) which dedupes concurrent refreshes racing between the 401 path and the tab-focus proactive refresh.
- `fetch` is wrapped with `credentials: "include"` (`connect.ts:57`) — that's how the refresh-token cookie reaches the server.

## Token kinds

| Token | Storage | Lifetime | Managed in |
|---|---|---|---|
| Access token (JWT) | `localStorage` key `memos_access_token` + `memos_token_expires_at` | 15 min (`server/auth/token.go:40`) | `web/src/auth-state.ts` |
| Refresh token (JWT) | HttpOnly cookie, never touched by JS | 30 days (`server/auth/token.go:9`) | server-set; sent via `credentials: "include"` |
| Personal Access Token | — | long-lived | backend only, same `Authorization` header |

`web/src/auth-state.ts` also syncs freshly-refreshed tokens across tabs over a `BroadcastChannel` (`memos_token_sync`, lines 28-50) so only one tab hits the refresh endpoint.

## Backend: `server/auth/`

The Connect-side `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208`) reads the `Authorization` header and delegates to `Authorizer.Authenticate` / `CheckAccess`, then puts the result on the context via `auth.ApplyToContext` (lines 219-227). Role/admin checks stay in the service layer.

Actual validation lives in `server/auth/authenticator.go`:
- `resolveBearer` (line 149) branches on the PAT prefix: no prefix → stateless JWT validation via `AuthenticateByAccessTokenV2` → `ParseAccessTokenV2` (line 42, no DB hit); prefix → `AuthenticateByPAT` (line 102, hash lookup + expiry).
- `AuthenticateByRefreshToken` (line 61) parses the refresh JWT *and* checks the store for revocation and expiry — refresh tokens are stateful, access tokens are not.
- Note the asymmetry: `Authenticate` (line 213) ignores the refresh cookie entirely; only `AuthenticateToUser` (line 190) falls back to it. So the cookie is effectively only useful for the `RefreshToken` RPC and the file server.

Per `server/auth/token.go:1-10`, this package is shared by the gRPC interceptor, the Connect interceptor, and `server/router/fileserver` — one validation path for all three.
