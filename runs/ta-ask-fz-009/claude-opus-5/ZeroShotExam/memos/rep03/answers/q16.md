I'll trace the memo deletion path through the store layer.

q16.

`store.DeleteMemo` (`store/memo.go:140`–`159`) performs this cleanup before handing the row to the driver:

1. **`memo_relation` rows where this memo is the source** — `driver.DeleteMemoRelation(&DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **`memo_relation` rows where this memo is the target** — `driver.DeleteMemoRelation(&DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **Attachment records linked to the memo** — listed via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and removed one by one with `s.DeleteAttachment` (`store/memo.go:149`–`157`). Note that `Store.DeleteAttachment` also deletes the *backing blob* (local file / S3 object) via `DeleteAttachmentStorage` before deleting the attachment row (`store/attachment.go:132`–`149`).

Only then does it call `s.driver.DeleteMemo(ctx, delete)` (`store/memo.go:158`), which is the plain `DELETE FROM memo WHERE id = ?` in each driver (e.g. `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

Two adjacent facts, since they shape what actually disappears on an API delete:

- **Comment memos** are deleted *before* this, but at the API layer, not the store layer: `APIV1Service.DeleteMemo` lists `memo_relation` rows of type `comment` pointing at the memo and calls `Store.DeleteMemo` on each child memo (`server/router/api/v1/memo_service.go:567`–`577`), so each child runs the same three-step cleanup.
- **Reactions** are *not* deleted by the store path — the handler only *lists* them to build the webhook payload (`server/router/api/v1/memo_service.go:545`). Nothing in `store.DeleteMemo` touches the reaction table, so reaction rows depend on DB-level cascade or are left behind.
