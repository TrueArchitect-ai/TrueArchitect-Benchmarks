### Frontend: the interceptor
`authInterceptor` in `web/src/connect.ts:156` is registered on the single Connect-Web transport (`web/src/connect.ts:184-189`), so every generated service client (`memoServiceClient`, `userServiceClient`, …, lines 192-203) is authenticated by it. Its contract:

1. Pre-flight — `getRequestToken()` (`connect.ts:124`) fetches the access token, and if it's absent or within 30 s of expiry (`REQUEST_TOKEN_EXPIRY_BUFFER_MS`, `web/src/auth-state.ts:18`) refreshes *before* sending. The comment at `connect.ts:136-139` explains why: an expired token on a public endpoint would silently return guest-scoped data instead of 401.
2. Attach — `Authorization: Bearer <token>` (`connect.ts:97-100`).
3. Reactive retry — on `Code.Unauthenticated` and only when the `X-Retry` header isn't already set (`connect.ts:102-113`), it refreshes, re-attaches, marks `X-Retry: true`, retries once; on failure `redirectOnAuthFailure()`.

Refresh itself goes through a **separate transport with no interceptors** (`connect.ts:65-70`) to break recursion, and through `tokenRefreshManager` (`connect.ts:30-51`) which de-duplicates concurrent refreshes so the tab-focus refresh and the 401 path can't race server-side token rotation.

### Tokens it manages
- **Access token** — short-lived JWT held in memory + `localStorage` under `memos_access_token` / `memos_token_expires_at` (`web/src/auth-state.ts:6-7`), 15 min server-side (`server/auth/token.go:40`). Cross-tab sync via a `BroadcastChannel` named `memos_token_sync` so only one tab hits the refresh endpoint (`auth-state.ts:13, 28-46`).
- **Refresh token** — never touched by JS: it's the `memos_refresh` cookie (`server/auth/token.go:49`), 30-day lifetime (`token.go:43`), carried because both transports use `fetch` with `credentials: "include"` (`connect.ts:57-62`). Exchanged at `POST /api/v1/auth/refresh` (`proto/gen/api/v1/auth_service.pb.gw.go:331`).
- **PAT** (`memos_pat_` prefix, `server/auth/token.go:52`) is a third credential the backend accepts on the same `Authorization` header, but it's for programmatic clients — the web interceptor doesn't manage it.

### Backend: validation
`server/auth` is the authority. `AuthInterceptor.WrapUnary` (`server/router/api/v1/connect_interceptors.go:217-230`) reads the `Authorization` header, calls `Authorizer.Authenticate` (`server/router/api/v1/authz.go:44`) which delegates to `auth.Authenticator.Authenticate`, then `CheckAccess` on the procedure name and `auth.ApplyToContext`. Inside `server/auth/authenticator.go` the credential is dispatched by prefix (`:154`): non-`memos_pat_` → stateless JWT verify via `AuthenticateByAccessTokenV2` (`:41`, no DB hit); PAT → `AuthenticateByPAT` (`:102`, hashed lookup); refresh tokens → `AuthenticateByRefreshToken` (`:61`), which is DB-backed so it can honor revocation, and is called only from the refresh RPC (`server/router/api/v1/auth_service_session.go:127-131`).

The same `auth.Authenticator` is reused by the SSE handler (`server/router/api/v1/sse_handler.go:37`) and the file server (`server/router/fileserver/fileserver.go:711`), which is what keeps authentication behavior identical across Connect, gRPC, and plain-HTTP surfaces.
