q16.

`store.Store.DeleteMemo` (`store/memo.go:140-159`) performs two classes of cleanup before handing off to `s.driver.DeleteMemo` (the actual `memo` row delete at `store/memo.go:158`):

1. **Memo relation records — both directions.**
   - `DeleteMemoRelation{MemoID: &delete.ID}` — relations where this memo is the source (`store/memo.go:142`)
   - `DeleteMemoRelation{RelatedMemoID: &delete.ID}` — relations where this memo is the target (`store/memo.go:145`)

2. **Attachments linked to the memo.** It lists them via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and deletes each with `DeleteAttachment` (`store/memo.go:149-157`). Note `Store.DeleteAttachment` (`store/attachment.go:132`) also removes the backing blob via `DeleteAttachmentStorage` (`store/attachment.go:193`), so the physical file goes too, not just the DB row.

One layer up, the API handler adds a third step *before* calling the store for the target memo: it deletes **child comment memos**, by listing `memo_relation` rows of type `MemoRelationComment` pointing at this memo and calling `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:567-577`) — each of those recursions then does its own relation + attachment cleanup. Reactions are read for the webhook payload (`server/router/api/v1/memo_service.go:545`) but are **not** deleted on either path.
