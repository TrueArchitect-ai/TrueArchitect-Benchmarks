### Frontend side

`authInterceptor` is installed on the single Connect transport that every service client is built from (`web/src/connect.ts:184-203`), so all RPC traffic passes through it. Per request it:

1. Calls `getRequestToken()` (`connect.ts:124`) — reads the access token, and **preflight-refreshes** if it's within 30s of expiry (`REQUEST_TOKEN_EXPIRY_BUFFER_MS`, `web/src/auth-state.ts:18`). The comment at `connect.ts:136-139` gives the invariant: an expired token on a public endpoint would silently return guest-scoped data, so expiry must be handled *before* the send, not only on 401.
2. Sets `Authorization: Bearer <token>` (`connect.ts:97`).
3. On a `Code.Unauthenticated` response, refreshes once and replays the request with an `X-Retry: true` marker to prevent infinite recursion (`connect.ts:164-176`); if the refresh fails, `redirectOnAuthFailure()`.

Two tokens are managed, with different storage boundaries:

- **Access token** — JWT in `localStorage` under `memos_access_token` plus `memos_token_expires_at` (`auth-state.ts:6-7`), mirrored in-memory. Cross-tab coordination goes over a `BroadcastChannel` (`memos_token_sync`, `auth-state.ts:13`) so only one tab hits the refresh endpoint.
- **Refresh token** — never touched by JS; it rides as an HttpOnly cookie, which is why the transport's fetch wrapper forces `credentials: "include"` (`connect.ts:57-62`). The refresh call uses a *separate* transport with `interceptors: []` (`connect.ts:65-70`) specifically to avoid interceptor recursion.

Refresh requests are deduplicated through `tokenRefreshManager` (`connect.ts:30-51`) — the comment at `connect.ts:85-88` states why: proactive focus-refresh and reactive 401-refresh could otherwise race against server-side token rotation.

### Backend side

`AuthInterceptor.WrapUnary` (`server/router/api/v1/connect_interceptors.go:217`) reads the `Authorization` header, delegates to `Authorizer.Authenticate` / `CheckAccess`, and on failure returns `CodeUnauthenticated` — the exact code the frontend retry path keys on. The real validation lives in the **`server/auth`** package:

- `Authenticator.AuthenticateByAccessTokenV2` (`server/auth/authenticator.go:41`) — stateless JWT parse via `ParseAccessTokenV2`, **no DB hit**.
- `Authenticator.AuthenticateByPAT` (`authenticator.go:102`) — hash lookup for long-lived programmatic tokens, distinguished by `PersonalAccessTokenPrefix` (`authenticator.go:154`).
- `Authenticator.AuthenticateByRefreshToken` (`authenticator.go:61`) — parse, then a DB revocation check plus expiry and archived-user checks. This is the stateful one.
- Token constants/generation in `server/auth/token.go` (`RefreshTokenCookieName`, `RefreshTokenDuration` at line 25); cookie extraction in `server/auth/extract.go:23`.

The refresh endpoint itself is `POST /api/v1/auth/refresh`, handled by `APIV1Service.RefreshToken` (`server/router/api/v1/auth_service_session.go:113`), which reissues the cookie via `buildRefreshTokenCookie` (line 224).

One boundary worth noting: `server/auth` is deliberately shared — its doc comment (`authenticator.go:17-19`) says it backs the gRPC interceptor, the Connect interceptor, and the file server, so auth semantics stay identical across all three entry paths. `AuthenticateToUser` (`authenticator.go:190`) falls back from Bearer to the refresh cookie, while `Authenticate` (line 213) ignores the cookie entirely — the Connect interceptor uses the latter, so ordinary RPCs authenticate on the header alone.
