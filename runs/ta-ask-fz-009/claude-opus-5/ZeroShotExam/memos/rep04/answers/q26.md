### The delete chain

**1. API layer — `APIV1Service.DeleteMemo`** (`server/router/api/v1/memo_service.go:518`)
- Lists comment relations and recursively calls `Store.DeleteMemo` for each child comment memo (lines 568–577) — so the same table set is hit again per comment.
- Then deletes the memo itself (line 580).
- Reactions and attachments are only *read* here (lines 545–557) to build the webhook payload — no delete.

**2. Store layer — `Store.DeleteMemo`** (`store/memo.go:140-159`) is where the explicit cascade lives:
- `memo_relation` — two deletes, once as `memo_id` and once as `related_memo_id` (lines 142–147); SQL at `store/db/sqlite/memo_relation.go:149`.
- `attachment` — lists attachments by `memo_id` and calls `DeleteAttachment` per row (lines 149–157); `Store.DeleteAttachment` (`store/attachment.go:132`) also removes blob/local-file storage, then `store/db/sqlite/attachment.go:212` deletes the row.
- `memo` — the driver delete, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

**3. Database-level cascade — `memo_share`**
`memo_share.memo_id` has `FOREIGN KEY … REFERENCES memo(id) ON DELETE CASCADE` in all three dialects (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). It's the only FK cascade reaching memo rows.

### Two things worth flagging

- **`memo_share` cascade does not fire on SQLite.** The connection is opened with `?_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), which disables FK enforcement entirely. On SQLite deployments, share grants for a deleted memo are orphaned; on Postgres/MySQL they are removed.
- **`reaction` rows are never deleted.** Reactions key off a string `content_id` (`store/migration/sqlite/LATEST.sql:92-99`) with no FK, and nothing in the `DeleteMemo` callee set deletes them — so reactions on a deleted memo are left behind in all dialects.
