**memo, memo_relation, attachment**

Rows deleted, by layer:

- **`memo_relation`** — `Store.DeleteMemo` deletes in both directions: `MemoID = id` and `RelatedMemoID = id` (`store/memo.go:142,145`)
- **`attachment`** — listed by `MemoID` then deleted one-by-one via `Store.DeleteAttachment` (`store/memo.go:149-157`), which resolves the row first (`store/attachment.go:133`) before the driver's `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go:212`)
- **`memo`** — the row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:239`), and additionally **one row per comment memo**: the API handler first lists `MemoRelationComment` relations pointing at this memo and recursively calls `Store.DeleteMemo` for each child (`server/router/api/v1/memo_service.go:568-577`), so each comment repeats the whole three-table cascade

Three qualifications that matter:

- **`reaction` is *not* deleted.** The handler reads reactions to build the webhook payload (`memo_service.go:545-550`, used at :560) but no delete is issued against that table — reaction rows for a deleted memo are left behind. If you're auditing orphan data, that's the gap.
- **The cascade is application code, not FK constraints.** The schema declares no foreign keys on `memo_relation` (`store/migration/sqlite/LATEST.sql:47-52`); earlier migrations explicitly removed them (`store/migration/sqlite/0.7/00__remove_fk.sql`). The invariant lives entirely in `Store.DeleteMemo` — bypassing it via the driver leaves orphans.
- **Non-table side effects.** `Store.DeleteAttachment` also disposes of the underlying blob/file, and the handler fires a webhook (`:562`) and an SSE `memo.deleted` broadcast (`:585`). None of that is transactional — deletes are sequential, so a mid-way failure can leave partial state.
