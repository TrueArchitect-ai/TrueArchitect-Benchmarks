**s3presign — a 12-hour `time.Ticker`, plus one eager pass at startup**
**webhook delivery workers (4 goroutines) — channel-driven, woken by enqueued payloads (not time-based)**

Details:

- **s3presign.** `startBackgroundRunners` (`server/server.go:153`) constructs the runner (`:162`), calls `RunOnce(ctx)` synchronously so presigned URLs refresh immediately at boot (`:163`), then launches `Run(s3Context)` in a tracked goroutine (`:166-171`). `Run` is a `time.NewTicker(runnerInterval)` loop with `runnerInterval = 12 * time.Hour` (`server/runner/s3presign/runner.go:27-41`), re-presigning S3 attachments whose URL is within 4 days of its 5-day expiry (`:85-91`), in batches of 100. It's the only entry in `backgroundRunnerCancels`/`backgroundRunnerWG`, so it's the only runner with managed shutdown (`server.go:176-201`).
- **Webhook workers.** `internal/webhook/webhook.go:42-55` spawns 4 goroutines in `package init()` draining `asyncPostQueue` (a 128-slot buffered channel, `:39`). Triggered by `PostAsync` enqueues from the API layer, not by a clock. Note these are started by package initialization rather than by `Server.Start`, and they are **not** registered with the WaitGroup — they aren't drained on shutdown, so queued webhooks can be dropped.

**Unused scheduling infrastructure: `server/runner/memopayload` is never started as a runner.** It has the full runner shape — `Runner` struct, `NewRunner(store, markdownService)`, and a batching `RunOnce` that rebuilds every memo's payload (`server/runner/memopayload/runner.go:14-72`) — but a reference search shows `NewRunner`/`RunOnce` have no call sites; the only external uses are the *stateless helper* `memopayload.RebuildMemoPayload`, called inline on the write path at `server/router/api/v1/memo_service.go:108` (create) and `:447` (update). So payload rebuilding happens synchronously per-memo, and the bulk backfill runner is dormant code — presumably retained for a one-off migration path.

Two smaller things that are *not* runners but often get counted as such: the SSE hub (`server/router/api/v1/sse_hub.go`) holds a goroutine per connected client, driven by HTTP requests; and `s.closeLongLivedConnections()` (`server.go:203`) exists precisely because those SSE streams don't terminate on their own during `http.Server.Shutdown`.
