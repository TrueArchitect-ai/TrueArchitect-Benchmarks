Inside `Store.DeleteMemo` (`store/memo.go:140-159`), in order, before `s.driver.DeleteMemo` at line 158:

3. **Attachments linked to the memo** — listed via `ListAttachments(FindAttachment{MemoID:...})` then deleted one at a time through `s.DeleteAttachment` (`store/memo.go:149-157`)

Note the deliberate asymmetry in how those two are deleted: relations go straight to `s.driver`, while attachments go through the **store-level** `s.DeleteAttachment` — that wrapper is what also disposes of the blob/file behind the attachment, so bypassing it would orphan storage.

**Reactions are not deleted here.** The API handler separately lists reactions for the memo (`server/router/api/v1/memo_service.go:545-550`) before calling delete, so that cleanup is driven from the API layer, not from `Store.DeleteMemo`. If you're reasoning about invariants, the memo-deletion contract is split across those two files rather than being fully owned by the store.
