**Interceptor: `web/src/connect.ts` (`authInterceptor` at :156, installed on the shared transport at :188); tokens: short-lived JWT access token (in-memory, `Authorization: Bearer`) + long-lived refresh token (HttpOnly `memos_refresh` cookie) — with Personal Access Tokens as a third kind the backend accepts but the browser doesn't use; backend validator: `server/auth`**

**Frontend flow** (`web/src/connect.ts`):
- Every request runs `getRequestToken()` (:124) → sets `Authorization: Bearer <token>` (:97-100).
- **Proactive refresh:** if the token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry, it refreshes *before* sending (:140-147). The comment at :137-139 gives the reason — on public endpoints like `ListMemos` an expired token would silently be treated as anonymous and return guest-scoped data instead of 401ing.
- **Reactive refresh:** on `Code.Unauthenticated`, it refreshes once, replays the request with an `X-Retry: true` marker to prevent loops (:164-172), and on second failure calls `redirectOnAuthFailure()` (:174).
- **Refresh is deduplicated and recursion-free:** `tokenRefreshManager` collapses concurrent refreshes into one promise (:30-51, rationale at :85-88), and `refreshAuthClient` runs on a separate `refreshTransport` with `interceptors: []` (:65-72) so the refresh call can't re-enter the auth interceptor.
- The cookie rides along because both transports use `fetchWithCredentials` (`credentials: "include"`, :57-62) — the refresh token is never touched by JS.

**Backend validation** (`server/auth/`):
- `Authenticator.Authenticate(ctx, authHeader)` (`authenticator.go:213`) is the request path; `resolveBearer` (:149) discriminates by prefix — `memos_pat_` → `AuthenticateByPAT` (:102), otherwise stateless `AuthenticateByAccessTokenV2` (:41).
- `AuthenticateToUser` (:190) additionally falls back to the cookie via `ExtractRefreshTokenFromCookie` (`extract.go:23`) → `AuthenticateByRefreshToken` (:61).
- Token constants in `token.go`: access = 15 min, stateless (`:40`); refresh = 30 days, cookie `memos_refresh` (`:43,49`), and **validated against the DB for revocation** — `GetUserRefreshTokenByID` (`authenticator.go:73`); PAT prefix `memos_pat_` (`token.go:52`).

The asymmetry worth remembering: access tokens are verified by signature alone (no DB hit), while refresh tokens and PATs require a store lookup — so revocation only takes effect at the next refresh, bounded by the 15-minute access-token lifetime.
