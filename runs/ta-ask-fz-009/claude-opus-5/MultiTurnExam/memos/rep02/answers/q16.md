q16. Inside `Store.DeleteMemo` (`store/memo.go:140-159`), two kinds of records are removed before the memo row:

1. **`memo_relation` rows — both directions.** Two calls: one matching `MemoID` (this memo as source, `store/memo.go:142`) and one matching `RelatedMemoID` (this memo as target, `store/memo.go:145`).
2. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID}` then deleted one by one (`store/memo.go:149-157`). Each `Store.DeleteAttachment` also deletes the **underlying stored file/blob** first (`store/attachment.go:141`, local-file failures are fatal, remote failures are logged) before removing the DB row (`store/attachment.go:148`).

Only then does it call the dialect driver's `DeleteMemo`, which is a bare single-row `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237-247`).

Two things the API handler adds on top, above the store layer:

- **Comment memos** are deleted first — the handler finds child memos via comment-type relations and calls `Store.DeleteMemo` on each, recursing through the same relation/attachment cleanup (`server/router/api/v1/memo_service.go:567-577`).
- **Reactions are not deleted here.** The handler only *reads* them to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); nothing in `Store.DeleteMemo` touches the `reaction` table, so reaction rows keyed by the memo's resource name are left behind.
