Breakdown by mechanism:

**Explicit cascade code in `Store.DeleteMemo` (`store/memo.go:140-159`):**
- `memo_relation` — deleted in both directions, `MemoID` then `RelatedMemoID` (lines 142, 145)
- `attachment` — rows found by `FindAttachment{MemoID}` and deleted individually (lines 149-157), each also removing the underlying stored file/blob first (`store/attachment.go:141`)

**The direct DELETE:**
- `memo` — a single-row `DELETE FROM memo WHERE id = ?` in each driver (`store/db/sqlite/memo.go:237-248`, `store/db/postgres/memo.go:244-255`, `store/db/mysql/memo.go:259-270`)

**By declared FK cascade, not application code:**
- `memo_share` — `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`; same table at `store/migration/postgres/LATEST.sql:101`). Nothing in `Store.DeleteMemo` touches it, so removal depends entirely on the engine enforcing the constraint — worth confirming SQLite's `foreign_keys` pragma is on in `store/db/sqlite/sqlite.go`, since SQLite defaults it off per-connection.

**Also affected transitively:** the API handler deletes comment memos first (`server/router/api/v1/memo_service.go:567-577`), so each child memo runs the whole list above again.

**Explicitly not touched: `reaction`.** Reactions are keyed by `content_id` (a resource-name string, `store/migration/sqlite/LATEST.sql:96`) with no FK to `memo`, and the delete handler only *reads* them for the webhook payload (`server/router/api/v1/memo_service.go:545-550`). Those rows are orphaned.
