```
s3presign.Runner — 12-hour time.Ticker loop, plus one eager RunOnce at startup
```

That is the **only** background runner the server starts. `startBackgroundRunners` (`server/server.go:153-174`) constructs exactly one: `s3presign.NewRunner(s.Store)`, calls `RunOnce(ctx)` synchronously so S3 URLs are refreshed immediately on boot (`:163`), then launches `Run(s3Context)` in a goroutine (`:166-171`). Inside `Run`, the trigger is a `time.NewTicker(runnerInterval)` with `runnerInterval = time.Hour * 12` (`server/runner/s3presign/runner.go:27-41`); each pass re-presigns S3 attachment URLs in batches of 100, skipping any whose presigned URL is still valid for 4+ days (`:85-91`). It gets its own cancellable context registered in `backgroundRunnerCancels` and a WaitGroup slot so `Shutdown` can stop and drain it (`server/server.go:140-143`, `:176-201`).

**Unused-infra note:** `server/runner/memopayload` is present but **never started by the server**. `memopayload.Runner.RunOnce` (`server/runner/memopayload/runner.go:27`) has a certified zero callers in the graph — nothing invokes it, and `server/server.go` doesn't import the package (imports at `:18-26` include only `s3presign`). It's a full-table backfill that rebuilds every memo's payload (tags/properties) from Markdown, so it reads as a migration/maintenance utility rather than a scheduled job. Its sibling `memopayload.RebuildMemoPayload` (`:74`) *is* used — the API layer calls it per-memo on write.

Two other things that look like background work but aren't runners: the SSE hub (`server/router/api/v1/sse_hub.go`) holds long-lived connections closed explicitly on shutdown (`server/server.go:203-208`), and webhook delivery is fired best-effort inline from the request handler, not queued.
