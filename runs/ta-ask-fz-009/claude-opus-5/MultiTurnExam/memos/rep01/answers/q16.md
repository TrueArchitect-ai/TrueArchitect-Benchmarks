q16. `Store.DeleteMemo` (`store/memo.go:140-159`) performs three cleanup steps before the memo row:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachments linked to the memo** — listed via `ListAttachments{MemoID: ...}` then deleted one by one through `Store.DeleteAttachment` (`store/memo.go:149-157`)

Only then does it call `s.driver.DeleteMemo(ctx, delete)` (`store/memo.go:158`), which is the bare `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237-248`).

Two things happen at the API layer, not the store layer, and are worth separating out:

- **Comment memos** are deleted first by the handler: `APIV1Service.DeleteMemo` lists comment-type relations pointing at the memo and calls `Store.DeleteMemo` for each child memo, so each comment gets the same three-step cleanup (`server/router/api/v1/memo_service.go:567-577`).
- **Reactions are not deleted.** The handler only *reads* reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545-565`), and `Store.DeleteMemo` never touches the `reaction` table — reaction rows key off a string `ContentID` rather than a foreign key, so they are left orphaned.
