q29. **web/src/connect.ts (`authInterceptor`, :156); short-lived access token in memory as `Authorization: Bearer` + refresh token as an HTTP-only cookie (plus personal access tokens accepted server-side); server/auth**

The frontend side:

- **Interceptor**: `authInterceptor` (`web/src/connect.ts:156-178`) is installed on the single shared Connect transport (`:188`), so every service client gets it. Token state lives in `web/src/auth-state.ts` (`getAccessToken`, `isTokenExpired`, `setAccessToken`).
- **Two tokens, two carriers.** The **access token** is attached per request as `Authorization: Bearer <token>` (`:97-100`). The **refresh token** is never read by JS — it rides as a cookie, which is why both transports use `fetch` with `credentials: "include"` (`:57-62`).
- **Refresh has two paths.** *Preflight*: if the access token is expired or within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry, refresh before sending (`:140-147`) — the comment notes this matters for public endpoints like `ListMemos`, where an expired token would silently degrade to guest-scoped data instead of 401-ing. *Reactive*: on a `Code.Unauthenticated` response, refresh once, set an `X-Retry` header, and replay; a second failure triggers `redirectOnAuthFailure()` (`:163-177`). The `X-Retry` guard prevents infinite retry loops.
- **Recursion break**: `refreshToken` itself goes through a separate transport with `interceptors: []` (`:65-72`), so a failing refresh can't re-enter the interceptor.
- **Concurrency**: `tokenRefreshManager` deduplicates in-flight refreshes so the focus-triggered proactive refresh and the 401-triggered reactive one can't both fire and collide with server-side token rotation (`:30-51`, `:85-91`).

The backend side: **`server/auth`** — `Authenticator.resolveBearer` (`server/auth/authenticator.go:149`) validates the `Authorization: Bearer` credential and `Authenticator.AuthenticateByRefreshToken` (`:61`) handles the cookie-borne refresh; both resolve to a user via `Store.GetUser`. Token minting/parsing lives in `server/auth/token.go`, header/cookie extraction in `server/auth/extract.go`, and request-scoped identity in `server/auth/context.go`. Note the bearer path also accepts **personal access tokens** — `Store.GetUserByPATHash` (`store/user_setting.go:128`) is the lookup for API clients that don't use the browser refresh flow.
