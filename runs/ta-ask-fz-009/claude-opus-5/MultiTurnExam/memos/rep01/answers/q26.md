q26. **memo, memo_relation, attachment, memo_share**

Breakdown by mechanism:

- **`memo`** — the target row itself, plus any child comment memos. The API handler deletes comment memos first by walking comment-type relations (`server/router/api/v1/memo_service.go:567-577`), then the row is removed by `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`).
- **`memo_relation`** — explicit cascade in the store layer, deleted twice: once where the memo is the source (`MemoID`) and once where it's the target (`RelatedMemoID`) (`store/memo.go:142-146`).
- **`attachment`** — explicit cascade: attachments are listed by `MemoID` and deleted one at a time via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying file/object from storage before the row (`store/attachment.go:132-148`). So this hop has a side effect outside the database.
- **`memo_share`** — DB-level cascade, not application code: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`).

Notably **not** affected: **`reaction`**. `Store.DeleteMemo` never touches it, and the handler only reads reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545-565`). Reaction rows key off a string `ContentID` rather than a memo FK, so they survive as orphans.
