All four are `*APIV1Service` methods in `server/router/api/v1/memo_service_webhooks.go` (:15, :20, :25, :30), invoked from:

- create → `server/router/api/v1/memo_service.go:157`
- update → `server/router/api/v1/memo_update_helpers.go:67` (inside `dispatchMemoUpdatedSideEffects`)
- delete → `server/router/api/v1/memo_service.go:562` (before the cascade, so the payload still reflects live state)
- comment → `server/router/api/v1/memo_service_comments.go:119`

**Convergence — `webhook.PostAsync` → `webhook.Post` in `internal/webhook/webhook.go` (`PostAsync` :184, `Post` :120).**

The first three funnel through a shared private helper `dispatchMemoRelatedWebhook(ctx, memo, activityType)` (`memo_service_webhooks.go:48`), which resolves the memo creator, loads that user's hooks via `Store.GetUserWebhooks` (:57), and calls `webhook.PostAsync(payload)` (:71). `DispatchMemoCommentCreatedWebhook` deliberately bypasses that helper (:30-46) because it targets a *different* recipient — the parent memo's owner (`relatedMemoCreatorID`) rather than the comment author — but it too ends at `webhook.PostAsync` (:43).

From there delivery is uniform: `PostAsync` enqueues onto a 128-slot channel drained by 4 workers (`internal/webhook/webhook.go:39-55`), and `Post` signs the body HMAC-SHA256 (`webhook-id` / `webhook-timestamp` / `webhook-signature`, :139-149) before POSTing through the SSRF-guarded `safeClient` (:32).

Every call site treats failure as best-effort — logged via `slog.Warn`, never propagated to the API response.
