Cascade performed in application code, in this order:

1. **Child comment memos** — deleted at the API layer first (`server/router/api/v1/memo_service.go:567-577`): every `memo_relation` row of type `MemoRelationComment` pointing at this memo is resolved and each comment memo is recursively passed through `Store.DeleteMemo`, so each comment's own relations and attachments are cleaned up too.
2. **`memo_relation` rows where the memo is the source** (`memo_id = X`) — `store/memo.go:142`.
3. **`memo_relation` rows where the memo is the target** (`related_memo_id = X`) — `store/memo.go:145`, so no dangling links point back at the deleted memo.
4. **Attachments linked to the memo** — listed then deleted one by one (`store/memo.go:149-157`), which routes through `Store.DeleteAttachment` so blob/file cleanup runs, not just the row.
5. **The memo row itself** — `s.driver.DeleteMemo(ctx, delete)` at `store/memo.go:158`.

Two architectural notes:

- **Reactions are not deleted.** `DeleteMemo` loads reactions at `server/router/api/v1/memo_service.go:545` only to build the webhook payload (:560-565); no reaction delete occurs in either layer. Reactions key off a content name string (`FindReaction.ContentID`), not a memo FK, so they outlive the memo as orphans — the test `TestMemo...orphan reaction` in `server/router/api/v1/test/memo_service_test.go:388` exercises exactly that state.
- **No transaction wraps the cascade.** Steps 1-5 are sequential calls that each return early on error (`store/memo.go:140-158`), so a mid-cascade failure leaves partially-deleted state.
