q26. **memo, memo_relation, attachment**

Verified writes, all issued by explicit application code — the schema has no FK cascades (`store/migration/sqlite/LATEST.sql`), so nothing happens that isn't coded:

| Table | Where | What |
|---|---|---|
| `memo_relation` | `store/memo.go:142` and `:145` | two deletes — rows where the memo is the source (`memo_id`) and where it's the target (`related_memo_id`) |
| `attachment` | `store/memo.go:149-157` → `Store.DeleteAttachment` (`store/attachment.go:132`) → `s.driver.DeleteAttachment` (:148) | per-attachment row delete, preceded by blob/file removal |
| `memo` | `store/memo.go:158` → `sqlite.DB.DeleteMemo` (`store/db/sqlite/memo.go:237`) | `DELETE FROM memo WHERE id = ?` (:239) |

The same three tables are hit **recursively** for each child comment memo: `DeleteMemo` at the API layer first enumerates comment relations and calls `Store.DeleteMemo` per comment (`server/router/api/v1/memo_service.go:567-577`), so each comment's own `memo_relation`, `attachment`, and `memo` rows go too.

Two boundaries worth naming:

- **`reaction` is NOT affected.** Reactions are read at `server/router/api/v1/memo_service.go:545` purely to build the webhook payload; no delete is issued in either layer. Because `reaction` keys off a content-name string rather than a memo FK, its rows survive as orphans — pinned by the orphan-reaction test at `server/router/api/v1/test/memo_service_test.go:388`.
- **Side effects reach beyond the database.** `Store.DeleteAttachment` calls `DeleteAttachmentStorage` (`store/attachment.go:141`), which removes local files or S3 objects (`deleteAttachmentStorageImpl`, `store/attachment.go:202-218`). Local-file failures abort the delete; remote failures only log. And since none of this runs in a transaction (`store/memo.go:140-158` returns early on each error), a mid-cascade failure can leave rows deleted in some of the three tables but not others.
