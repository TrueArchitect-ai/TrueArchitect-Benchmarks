**Runners the server actually starts** — all wiring is in `Server.startBackgroundRunners` (`server/server.go:153-174`), called from `Start` after the HTTP listener goes up (`server/server.go:129`):

```
s3presign.Runner — one eager RunOnce at startup (server/server.go:163), then a 12-hour time.Ticker loop (server/runner/s3presign/runner.go:27-41)
```

That is the only one. `startBackgroundRunners` creates a single cancellable child context (`s3Context`, `:156`), registers its cancel in `backgroundRunnerCancels` (`:159`), and launches exactly one goroutine tracked by `backgroundRunnerWG` (`:166-171`). Shutdown is orderly: `stopBackgroundRunners` cancels (`:176-182`) and `waitBackgroundRunners` joins with a deadline (`:184-201`).

What that runner does: batches of 100 S3-backed attachments, re-presigning any whose URL is within 1 day of its 5-day expiry (`server/runner/s3presign/runner.go:85-91`), writing the fresh URL back via `UpdateAttachment` (`:116`). The eager `RunOnce` exists because presigned URLs may already be stale after downtime.

**Unused scheduling infrastructure — `server/runner/memopayload`.** The package defines `Runner`, `NewRunner`, and a batched `RunOnce` that rebuilds every memo's payload (`server/runner/memopayload/runner.go:14-72`), but nothing constructs it: `[ArchMap query]` returns a **certified zero**, and the only references to the package anywhere in the tree are two direct calls to the standalone helper `RebuildMemoPayload` from the API layer — on create (`server/router/api/v1/memo_service.go:108`) and on content update (`:447`). So payload rebuilding happens inline, per-memo, on the request path; the bulk backfill runner is dormant code with no trigger. It has no `Run`/ticker at all, so even if constructed it would need an explicit caller.

Two related mechanisms that are *not* runners, to avoid conflating them: the webhook delivery pool (4 goroutines draining a 128-slot queue, started by `init()` in `internal/webhook/webhook.go:42-55`) and the SSE hub (`server/router/api/v1/sse_hub.go`, closed on shutdown via `closeLongLivedConnections`, `server/server.go:203-208`). Both are event-driven, not scheduled.
