Inside `Store.DeleteMemo` (`store/memo.go:140-158`), before the memo row:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`) — both directions, so no dangling edges either way
3. **attachments linked to the memo** — listed via `FindAttachment{MemoID:…}` then deleted one by one (`store/memo.go:149-157`)

Then `s.driver.DeleteMemo(ctx, delete)` removes the memo row itself (`store/memo.go:158`).

Two things the API layer adds on top, in `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`):

- **Comment memos** are deleted first, before the parent: it lists `memo_relation` rows of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each child (`server/router/api/v1/memo_service.go:567-577`), so each child's own relations and attachments get cleaned up by the same store logic.
- **Reactions are not deleted.** They're only *read* beforehand to build the payload for the memo-deleted webhook (`server/router/api/v1/memo_service.go:545-565`). No reaction-delete call appears in either path — reactions key off the memo's resource name (`ContentID`), so they are left orphaned in the `reaction` table.

There's also no transaction wrapping these steps — a failure partway through leaves relations or attachments already deleted.
