q29. **web/src/connect.ts (`authInterceptor`, `:156`); short-lived JWT access token (in-memory, `Authorization: Bearer`) + HTTP-only refresh-token cookie, plus personal access tokens (PATs) as an alternative bearer; server/auth**

**Interceptor.** `authInterceptor` (`web/src/connect.ts:156-178`) is installed on the single shared Connect transport (`:188`), so every generated client (`memoServiceClient` etc., `:192-203`) inherits it. Per request it:
1. resolves a token via `getRequestToken()` (`:124`) and sets `Authorization: Bearer <token>` (`:97-99`);
2. **preflight-refreshes** if the token is within an expiry buffer (`:140`) — the comment at `:136-139` names the reason: on public endpoints like `ListMemos` an expired token would silently return guest-scoped data instead of 401;
3. on a `Code.Unauthenticated` reply, refreshes once, marks the request with an `X-Retry` header to prevent loops (`:157`, `:171`), and retries; if refresh fails it calls `redirectOnAuthFailure()` (`:174`).

**Tokens.**
- *Access token* — held in memory by `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`/`isTokenExpired`, imported at `:4`), sent as a bearer header.
- *Refresh token* — never touched by JS; it rides as an HTTP-only cookie, which is why both transports use `credentials: "include"` (`fetchWithCredentials`, `:57-62`). Refresh goes through `AuthService.RefreshToken` on a **separate interceptor-free transport** (`:65-72`) specifically to avoid recursion, and concurrent refreshes are deduplicated by `tokenRefreshManager` (`:30-51`, `:89-91`) so proactive tab-focus refresh and reactive 401 refresh can't both race server-side token rotation.
- *PATs* — validated server-side via `Store.GetUserByPATHash` (`store/user_setting.go:128`), reachable through the same `Authorization` header.

**Backend validation — `server/auth`.** `Authenticator` in `server/auth/authenticator.go` is the single policy source: `resolveBearer` (`:149`) and `AuthenticateByRefreshToken` (`:61`) look users up through `Store.GetUser`; JWT signing/parsing lives in `server/auth/token.go`, identity-to-context plumbing in `server/auth/context.go` (`auth.ApplyToContext`), and header extraction in `server/auth/extract.go`. It's constructed once as `NewAuthorizer(s.Store, s.Secret, s.Profile)` (`server/router/api/v1/v1.go:68`) and applied on both protocol paths — as grpc-gateway middleware calling `Authenticate` + `CheckAccess` (`server/router/api/v1/v1.go:69-93`) and as the Connect interceptor — so REST and Connect share one anonymous-access policy.
