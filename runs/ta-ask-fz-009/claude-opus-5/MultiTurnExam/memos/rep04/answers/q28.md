**Started by the server:**

```
s3presign.Runner — startup RunOnce, then a 12-hour time.Ticker in its own goroutine
webhook async dispatch pool (internal/webhook) — 4 goroutines started by package init(), driven by a 128-slot queue (event-driven, not timed)
```

- **s3presign** — `startBackgroundRunners` (`server/server.go:153`) constructs the runner (`:162`), fires `RunOnce(ctx)` immediately at startup (`:163`), then runs `Run` in a tracked goroutine (`:166-171`). `Run` loops on `time.NewTicker(runnerInterval)` with `runnerInterval = 12 * time.Hour` (`server/runner/s3presign/runner.go:27, 29-41`), exiting on `ctx.Done()`. It's the only entry in `startBackgroundRunners` — lifecycle is managed via a dedicated cancel func plus a WaitGroup (`server/server.go:156-159`, `stopBackgroundRunners` `:176`, `waitBackgroundRunners` `:184`).
- **webhook pool** — 4 worker goroutines spawned in `internal/webhook`'s `init()` (`internal/webhook/webhook.go:42-54`), draining `asyncPostQueue` (`:39`). Triggered per enqueue from `webhook.PostAsync` (`:184`), called by the memo webhook dispatchers (`server/router/api/v1/memo_service_webhooks.go:43, 71`). Not scheduled and not wired into the server's shutdown WaitGroup — it starts on package import regardless of server config.

**Unused-infra note:** `server/runner/memopayload` is a runner package in name and shape — it exposes `NewRunner` (`server/runner/memopayload/runner.go:19`) and a batched `RunOnce` that rebuilds the payload of **all** memos in pages of 100 (`:26-35`) — but **the server never starts it.** `startBackgroundRunners` doesn't reference it, and the only production callers of the package use the standalone helper `memopayload.RebuildMemoPayload` synchronously inside the request path, for one memo at a time: `server/router/api/v1/memo_service.go:108` (create) and `:447` (update). So the batch/backfill runner is dormant infrastructure — presumably a migration-era backfill retained but not scheduled.
