**`memo_relation`, `attachment`, `memo`**

Established from `Store.DeleteMemo` (`store/memo.go:140-159`), which is the only cascade logic — the driver-level delete touches exactly one table (`DELETE FROM memo WHERE id = ?`, `store/db/sqlite/memo.go:239`).

| Table | Written by | Anchor |
|---|---|---|
| `memo_relation` | two deletes — memo as source, then as target | `store/memo.go:142`, `:145` |
| `attachment` | listed by `MemoID`, deleted per row via `Store.DeleteAttachment` → `driver.DeleteAttachment` | `store/memo.go:149-157`; `store/attachment.go:132`, delete at `:148` |
| `memo` | the row itself, last | `store/memo.go:158` → `store/db/sqlite/memo.go:237` |

Because the API handler recursively calls `Store.DeleteMemo` for each comment memo (`server/router/api/v1/memo_service.go:568-577`), the same three tables are hit again per child comment — no additional tables enter the set.

Two boundaries worth flagging:

- **Not a table, but a real side effect:** attachment deletion also removes the backing blob from local disk or S3 via `DeleteAttachmentStorage` (`store/attachment.go:141`, impl at `:202-212`). For `LOCAL` storage a failure aborts the delete; for remote storage it only logs a warning (`:142-145`).
- **Tables *not* cleaned up:** `reaction` and `memo_share` both reference memos but are untouched by this path — reactions are only read to build the webhook payload (`server/router/api/v1/memo_service.go:545`). Since foreign keys were dropped from the schema (`store/migration/sqlite/0.7/00__remove_fk.sql`) and `memo_relation` carries no `ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:47`), the database will not clean these up either — they become orphaned rows.
