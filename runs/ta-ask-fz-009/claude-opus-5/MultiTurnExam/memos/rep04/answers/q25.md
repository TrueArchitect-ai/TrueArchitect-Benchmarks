**Engine.** `filter.Engine` (`internal/filter/engine.go:14`) wraps a `cel.Env` built from a `Schema` (`:25`). `Compile` runs `env.Compile(filter)` and converts the AST to a parsed expression (`internal/filter/engine.go:48-60`), producing a `Program` that exposes a `Condition` tree (`:37-45`) — explicitly "a dialect-agnostic condition tree" per the type comment at `:13`. Supporting pieces: `internal/filter/parser.go` (AST → condition), `internal/filter/ir.go` (the condition IR), `internal/filter/schema.go` (allowed fields/functions), `internal/filter/helpers.go`.

**Dialect rendering.** `internal/filter/render.go` holds the renderer, parameterized by `DialectName` and a `placeholderOffset` (`:10-30`) — the offset is what lets Postgres's `$N` numbering continue from conditions already in the query while SQLite/MySQL use `?`. `Render` returns a `Statement{SQL, args}`, with constant-folding shortcuts: an unsatisfiable condition collapses to `1 = 0` (`:43-45`), and trivial ones are elided.

**Driver integration.** Each dialect calls the same entry point with its own dialect constant. In SQLite: `filter.DefaultEngine()` then `filter.AppendConditions(ctx, engine, find.Filters, filter.DialectSQLite, &where, &args)` (`store/db/sqlite/memo.go:57-61`), appending into the `where`/`args` slices seeded at `:55`. The mysql and postgres drivers (`store/db/mysql/memo.go:62`, `store/db/postgres/memo.go:51`) do the same with `DialectMySQL` / `DialectPostgres` — the three constants also appear in the API-layer validation path (`server/router/api/v1/shortcut_service.go:349-353`), which pre-compiles a shortcut's filter against the active dialect so bad expressions fail at write time rather than query time.
