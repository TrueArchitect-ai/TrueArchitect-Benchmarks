Inside `Store.DeleteMemo` (`store/memo.go:140-159`), before the memo row is deleted:

1. **`memo_relation` records where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` records where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` records linked to the memo** — listed via `ListAttachments(FindAttachment{MemoID})` then deleted one by one (`store/memo.go:149-157`)

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`).

The API handler adds one layer above this: `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first finds all comment relations pointing at the memo and recursively calls `Store.DeleteMemo` for each comment memo (`server/router/api/v1/memo_service.go:568-577`), so **child comment memos** — with their own relations and attachments — are removed before the parent.

Note what is *not* cleaned up in this path: reactions are read for the webhook payload (`server/router/api/v1/memo_service.go:545`) but never deleted, and neither layer touches `memo_share`. The relevant tables have no `FOREIGN KEY ... ON DELETE CASCADE` — `memo_relation` (`store/migration/sqlite/LATEST.sql:47`) is a bare table, and foreign keys were deliberately removed in `store/migration/sqlite/0.7/00__remove_fk.sql` — so this ordering is enforced entirely in Go, not by the database.
