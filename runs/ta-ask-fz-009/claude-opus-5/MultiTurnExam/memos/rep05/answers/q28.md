s3presign.Runner — 12-hour time.Ticker, plus one immediate RunOnce at startup

That is the **only** background runner the server starts. `startBackgroundRunners` (`server/server.go:153`) does exactly two things with it: a synchronous `s3presignRunner.RunOnce(ctx)` at line 163 (so stale presigned URLs are refreshed immediately on boot, not 12 hours later), then `go s3presignRunner.Run(s3Context)` in a `WaitGroup`-tracked goroutine (lines 166-171). The loop itself is a `time.NewTicker(runnerInterval)` select against `ctx.Done()` (`server/runner/s3presign/runner.go:29-41`), with `runnerInterval = 12 * time.Hour` (line 27). Work per tick: batch through S3-backed attachments 100 at a time and re-presign any whose `LastPresignedTime` is within 1 day of the 5-day expiry (`s3presign/runner.go:85-91`).

Lifecycle is clean: its own cancelable context registered in `backgroundRunnerCancels` (`server/server.go:156-159`), cancelled by `stopBackgroundRunners` and awaited by `waitBackgroundRunners` on shutdown (`server/server.go:140,143`).

**Unused scheduling infrastructure:**

- **`memopayload.Runner` (`server/runner/memopayload/runner.go:14`) is never instantiated by the server.** `memopayload.NewRunner` has a certified-zero caller set in the graph, and the only references to the package anywhere are two calls to the *free function* `RebuildMemoPayload` from the request path — `server/router/api/v1/memo_service.go:108` (create) and `:447` (update). So payload rebuilding happens synchronously per-memo on write; the batch `Runner.RunOnce` that walks every memo (`memopayload/runner.go:27`) is dead as far as the server is concerned. Note it also has *no* scheduling of its own — no ticker, only `RunOnce` — so it was designed as a one-shot backfill, not a periodic job.

One nuance on "workers" more broadly: the SSE hub (`server/server.go:38,77`) holds long-lived goroutines per connected client and is explicitly closed during shutdown (`closeLongLivedConnections`, `server/server.go:203-208`), but it's request-driven, not scheduled. Webhook delivery is likewise fire-and-forget goroutines via `webhook.PostAsync`, not a runner.
