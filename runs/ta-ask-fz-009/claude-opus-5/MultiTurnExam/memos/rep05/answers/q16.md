q16. Inside `Store.DeleteMemo` (`store/memo.go:140-159`), in order:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments{MemoID: ...}` then deleted one by one through `DeleteAttachment` (`store/memo.go:149-157`)

Only then does it call `s.driver.DeleteMemo(ctx, delete)` for the memo row itself (`store/memo.go:158`).

Two things worth flagging about this boundary:

- **Relations are cleaned in both directions** — a single `MemoID` sweep would leave dangling rows where the deleted memo was the `related_memo_id`. That matches the join-table shape in `store/migration/sqlite/LATEST.sql:47-52`, which has no FK/cascade, so the invariant is enforced in Go rather than by the database.
- **Reactions are *not* deleted here.** The API handler separately lists reactions before deleting (`server/router/api/v1/memo_service.go:545-550`) and lists attachments too (`:552-557`) — that pre-fetch is for side-effect/event payloads, and the reaction cleanup path lives in the handler rather than in `Store.DeleteMemo`. So if you're reasoning about the store layer alone, reactions fall outside its cascade.
