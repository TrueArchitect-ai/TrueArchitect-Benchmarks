q29. **`web/src/connect.ts` (authInterceptor, line 156); short-lived in-memory access token + HTTP-only refresh cookie, plus PATs server-side; `server/auth`**

**Interceptor.** `authInterceptor` (`web/src/connect.ts:156-178`) is installed on the shared Connect transport (line 188), so it covers every generated client. Per request it resolves a token via `getRequestToken()` and sets `Authorization: Bearer <token>` (lines 97-100, 158-159). On a `Code.Unauthenticated` response it refreshes once, retries with an `X-Retry: true` marker to prevent loops (lines 164-172), and on refresh failure calls `redirectOnAuthFailure()` (line 174).

**Tokens.**
- **Access token** — held in memory via `./auth-state` (`getAccessToken`/`setAccessToken`, line 4), sent as a bearer header. Refreshed *proactively* when within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry (line 140) — the comment at lines 136-139 explains why: on public endpoints like `ListMemos` an expired token would otherwise silently degrade to guest-scoped data rather than 401.
- **Refresh token** — a credential the browser never reads. All fetches use `credentials: "include"` (`fetchWithCredentials`, lines 57-62), and refresh is `authServiceClient.refreshToken({})` returning a new access token + `expiresAt` (lines 74-83) — i.e. the refresh token rides as an HTTP-only cookie, which is why `ConnectServiceHandler` wraps calls in `connectWithHeaderCarrier` to set response headers (`server/router/api/v1/connect_services.go:79`).
- **Personal access tokens** — a third kind the interceptor doesn't manage but the backend accepts; see `Store.GetUserByPATHash` (`store/user_setting.go:128`).

Two deliberate structural choices worth noting: refresh goes through a **separate transport with `interceptors: []`** (`web/src/connect.ts:65-72`) so a 401 on the refresh call can't recurse into the interceptor that triggered it; and `tokenRefreshManager` (lines 30-51) deduplicates concurrent refreshes, since server-side token rotation would make parallel refreshes conflict (comment at lines 85-88).

**Backend validation.** `server/auth` — `auth.Authenticator` with `resolveBearer` (`server/auth/authenticator.go:149`) and `AuthenticateByRefreshToken` (`server/auth/authenticator.go:61`), both resolving the claim to a user through `Store.GetUser`; JWT minting/parsing in `server/auth/token.go`, context plumbing in `server/auth/context.go`, header extraction in `server/auth/extract.go`. It's applied to REST traffic via `gatewayAuthMiddleware` (`server/router/api/v1/v1.go:69`, wired at line 97).
