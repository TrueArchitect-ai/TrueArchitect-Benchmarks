q25. **CEL (Common Expression Language, `github.com/google/cel-go`) — `internal/filter/` (engine at `internal/filter/engine.go:25`); mechanism: the CEL expression is parsed into a dialect-neutral condition IR, then a per-dialect renderer emits a parameterized SQL `WHERE` fragment plus args, which each driver's `ListMemos` appends to its query.**

**Engine.** `internal/filter/` is a self-contained filter compiler: `engine.go` builds the CEL environment via `cel.NewEnv(schema.EnvOptions...)` (line 25), `schema.go` declares the allowed fields/aliases and CEL extensions, `parser.go` lowers the CEL AST, `ir.go` holds the neutral condition types (`LogicalCondition`, `ComparisonCondition`, `InCondition`, `TextMatchCondition`, `RegexCondition`, …), and `render.go` does the SQL emission. (A second, separate CEL env exists for user filtering at `server/router/api/v1/user_service_filter.go:29`.)

**Where dialects diverge.** Each driver calls the same two entry points with its own dialect token — `filter.DefaultEngine()` + `filter.AppendConditions(ctx, engine, find.Filters, filter.Dialect…, &where, &args)`:

- `store/db/sqlite/memo.go:57,61` → `DialectSQLite`
- `store/db/postgres/memo.go:54,58` → `DialectPostgres`
- `store/db/mysql/memo.go:65,69` → `DialectMySQL`

The `renderer` carries `dialect` (`internal/filter/render.go:12`) and switches on it wherever SQL differs. Concrete examples:

- **Timestamp accessors** — `accessorSpecs` maps each CEL accessor to three tokens (`internal/filter/render.go:181-198`), rendered as `strftime(..., 'unixepoch')` on SQLite, `EXTRACT(... FROM to_timestamp(...) AT TIME ZONE 'UTC')` on Postgres, and a bare function call on MySQL (lines 231-239), with an offset to reconcile CEL's 0-based months against SQL's 1-based (lines 177-180).
- **`size()` semantics** — `CHAR_LENGTH` on MySQL vs `LENGTH` elsewhere, because MySQL's `LENGTH` counts bytes and CEL counts code points (`internal/filter/render.go:293-301`).
- **JSON tag membership** — `LIKE` on SQLite, `JSON_CONTAINS` on MySQL, `@> jsonb_build_array(...)` on Postgres, each paired with a prefix match to support hierarchical tags like `book/something` (`internal/filter/render.go:451-468`, `501-510`).

**Safety property.** Literals never enter the SQL text — the renderer routes them through `r.addArg(...)`, which allocates a placeholder (with `placeholderOffset`/`placeholderCounter` handling `?` vs `$N` numbering, `internal/filter/render.go:13-14`), so user-supplied filter values arrive as bound parameters. `Render` also reports `trivial` and `unsatisfiable` outcomes (`internal/filter/render.go:19-21`) so a filter that can't match can short-circuit rather than emit dead SQL.
