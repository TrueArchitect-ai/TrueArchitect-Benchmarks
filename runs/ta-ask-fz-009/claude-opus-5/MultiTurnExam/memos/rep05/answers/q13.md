Where the risk concentrates:

- **`store/driver.go`** is the load-bearing one — `store.Memo` appears in the `Driver` interface signatures, so any field or shape change propagates to all three dialect implementations simultaneously. Change it there first, then the three `store/db/*/memo.go` files.
- **`server/notification/email.go`** has the highest raw count (7) despite being outside the memo API package — an easy file to miss.
- **`memo_service_converter.go`** is the proto boundary: it maps `store.Memo` → `apiv1.Memo`, so a field change here decides whether the wire contract also shifts.

Two caveats. Test files are excluded from that list but do construct the struct literally — at least `server/router/api/v1/sse_hub_test.go`, `server/router/api/v1/test/memo_service_test.go`, `server/router/api/v1/test/memo_service_benchmark_test.go`, `server/router/api/v1/test/user_service_stats_test.go`, `server/router/frontend/frontend_test.go`.
