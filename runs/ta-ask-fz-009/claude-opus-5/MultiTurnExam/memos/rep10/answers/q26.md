**Three tables:**

```
memo_relation   — deleted first, both directions (store/memo.go:142, :145 → store/db/sqlite/memo_relation.go:149)
attachment      — rows linked to the memo (store/memo.go:149-157 → store/db/sqlite/attachment.go:212)
memo            — the row itself, last (store/memo.go:158 → store/db/sqlite/memo.go:239)
```

The cascade is explicit application code, not FK `ON DELETE` — the schema declares no foreign keys on `memo_relation` (`store/migration/sqlite/LATEST.sql:47-52`), so ordering is enforced by `Store.DeleteMemo` (`store/memo.go:140-158`).

Two scope notes:

- Via the API handler, the same three tables are hit repeatedly: comment memos are deleted first by recursing into `Store.DeleteMemo` per comment relation (`server/router/api/v1/memo_service.go:567-577`), so a parent delete cascades N+1 times over the same table set.
- Deleting an attachment also removes the underlying blob from local/S3 storage (`store/attachment.go:141`, `deleteAttachmentStorageImpl` :202) — a side effect outside the database.

Tables that are **not** touched, worth flagging as gaps: `reaction` rows keyed on the memo's resource name are only *read* for the webhook payload (`server/router/api/v1/memo_service.go:545`), never deleted; and `memo_share` grants for the memo are left in place. Both *are* cleaned up on the user-deletion path (`store/db/sqlite/user_delete.go:383`, `:406-411`), which shows the cleanup exists but isn't wired into memo deletion.
