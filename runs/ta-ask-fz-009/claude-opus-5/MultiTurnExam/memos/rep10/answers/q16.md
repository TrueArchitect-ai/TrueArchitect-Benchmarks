Inside `Store.DeleteMemo` (`store/memo.go:140-158`), in order, before `driver.DeleteMemo`:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments{MemoID: ...}` then deleted one by one (`store/memo.go:149-157`)

Only then does it hit the memo row itself: `s.driver.DeleteMemo(ctx, delete)` at `store/memo.go:158`.

One level up, the API handler adds a step the store doesn't do: **child comment memos** are deleted first, by listing `memo_relation` rows of type `MemoRelationComment` pointing at this memo and recursing through `Store.DeleteMemo` for each (`server/router/api/v1/memo_service.go:567-577`) — which is what cascades their own relations and attachments.

Worth flagging as an asymmetry: **reactions are not deleted.** The handler *reads* them (`server/router/api/v1/memo_service.go:545`) purely to build the webhook payload, and neither the handler nor `Store.DeleteMemo` removes `reaction` rows — so reactions keyed by the memo's resource name are left orphaned.
