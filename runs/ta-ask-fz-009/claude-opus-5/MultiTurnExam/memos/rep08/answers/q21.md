Where the risk sits:

- **The auth path is the blast center.** Four of the twelve are authentication resolution (`server/auth/authenticator.go` ×2, `auth_service_session.go`, plus the two SSO resolvers). A subtle change — e.g. nil-vs-error semantics on "user not found" — silently alters authentication behavior rather than failing to compile.
- **Two callers are amplifiers, not leaves.** `APIV1Service.fetchCurrentUser` and `ResolveUserByName` are used throughout the API layer, so the *effective* reach is much wider than 12 even though the compile-time edit set is 12. This list is depth 1 only.
- **`Store.GetUserByPATHash` is an intra-store caller** (`store/user_setting.go:128`) — same package, easy to overlook when scanning `server/` for breakage.
- **Two non-API transports depend on it directly**: the file server (`fileserver.go:715`) and the RSS endpoint `GET /u/:username/rss.xml` (`rss.go:111`). Neither goes through the gRPC/Connect layer, so API-level tests won't catch a regression there.

Note `GetMemo`-style convenience wrappers apply here too: `Store.GetUser` itself is the thin single-result wrapper over `ListUsers`, so if the change is additive to `FindUser` rather than to the signature, most of these sites compile unchanged.
