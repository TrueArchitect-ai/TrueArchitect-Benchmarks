**Runners the server actually starts** — all wiring in `Server.startBackgroundRunners` (`server/server.go:153-174`):

s3presign — startup one-shot `RunOnce(ctx)` (`server/server.go:163`), then a `time.Ticker` loop every 12 hours (`server/runner/s3presign/runner.go:27`, `Run` at :29-41)
webhook async dispatch workers — 4 goroutines started in `init()`, driven by a bounded 128-slot channel, not a clock (`internal/webhook/webhook.go:39-55`)
SSE hub — event-driven; fans out per `Broadcast` call, no schedule (`server/router/api/v1/sse_hub.go`)

Only the s3presign runner is a true scheduled background worker. It's given its own cancellable context and tracked in `backgroundRunnerCancels` + `backgroundRunnerWG` so `Shutdown` can stop and await it (`server/server.go:156-171`, `:176-201`). Its job: re-presign S3 attachment URLs whose 5-day expiry is within 4 days, in batches of 100 (`s3presign/runner.go:47-131`).

**Unused scheduling infrastructure:** `server/runner/memopayload` has a full `Runner` type with `NewRunner` and a batching `RunOnce` that rebuilds every memo's payload (`server/runner/memopayload/runner.go:14-72`) — **but nothing starts it.** `server/server.go` doesn't import the package (only `s3presign` is imported, `:25`), and the only references anywhere are to the standalone helper `memopayload.RebuildMemoPayload`, called synchronously on the write path from `APIV1Service.CreateMemo` (`server/router/api/v1/memo_service.go:108`) and `UpdateMemo` (`:447`). So `Runner.RunOnce` and `NewRunner` in that package are effectively dead code — a backfill/migration tool with no invocation site. Payload rebuilding happens inline per request instead.

Also worth noting: the runner harness has no retry/backoff and no jitter — a 12-hour tick that fails simply logs and waits for the next tick.
