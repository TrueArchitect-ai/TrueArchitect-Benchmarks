**Engine: CEL (Google Common Expression Language) via `github.com/google/cel-go` — `internal/filter/` (engine at `internal/filter/engine.go`, memo variable schema at `internal/filter/schema.go:232-248`)**

**Mechanism:** each dialect driver calls `filter.DefaultEngine()` then `filter.AppendConditions(ctx, engine, find.Filters, filter.Dialect<X>, &where, &args)`, which parses the CEL expression to an AST and walks it into dialect-specific `WHERE` fragments plus bound parameters that are appended to the query the driver is already assembling — e.g. `store/db/sqlite/memo.go:57-63` passing `filter.DialectSQLite`, with `store/db/mysql/memo.go` and `store/db/postgres/memo.go` passing their own dialect constants.

Supporting detail:

- The engine compiles against a fixed variable set declared in `internal/filter/schema.go:233-246` — `content`, `creator`, `creator_id`, `created_ts`, `updated_ts`, `pinned`, `tag`, `tags`, `visibility`, `has_task_list`, `has_link`, `has_code`, `has_incomplete_tasks`, `now`. Anything outside that vocabulary fails at compile time rather than reaching SQL.
- `cel.ASTValidators(cel.ValidateRegexLiterals())` (`schema.go:248`) rejects malformed regex literals up front — a ReDoS/injection guard at the parse boundary.
- Parameters are bound (`args`), never interpolated, so the CEL→SQL translation is injection-safe by construction.
- There's a second schema in the same file for attachment filters (`schema.go:303-309`: `filename`, `mime_type`, `create_time`, `memo_id`), and a separate ad-hoc CEL env for user filters at `server/router/api/v1/user_service_filter.go:29`.
- The same syntax is what `ShortcutService` persists: a shortcut is a named, reusable CEL filter passed straight to `ListMemos` (`proto/api/v1/shortcut_service.proto:15-17`).
