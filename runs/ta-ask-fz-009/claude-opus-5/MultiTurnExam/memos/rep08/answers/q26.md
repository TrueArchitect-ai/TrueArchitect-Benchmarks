**memo_relation, attachment, memo**

Order and provenance, from `Store.DeleteMemo` (`store/memo.go:140-159`):

| Table | Operation | Site |
|---|---|---|
| `memo_relation` | deleted twice — once as source (`MemoID`), once as target (`RelatedMemoID`) | `store/memo.go:142`, `:145` |
| `attachment` | listed by `MemoID`, then deleted row-by-row via `s.DeleteAttachment` | `store/memo.go:149-157` → `store/attachment.go:132-148` |
| `memo` | the row itself, last | `store/memo.go:158` |

Two amplifications, both still confined to those three tables:

- **Comments are memos.** The API handler `APIV1Service.DeleteMemo` first lists relations of type `store.MemoRelationComment` and calls `Store.DeleteMemo` once per comment (`server/router/api/v1/memo_service.go:567-577`) before deleting the parent (`:580`). So `memo` is hit N+1 times, with each pass repeating the relation/attachment cleanup.
- **Attachment deletion has a non-table side effect**: `DeleteAttachment` calls `DeleteAttachmentStorage` first (`store/attachment.go:141`), removing the local file or object-storage blob — hard-failing for `LOCAL` storage, warn-only otherwise (`:142-146`).

**`reaction` is notably *not* touched.** The handler reads reactions at `server/router/api/v1/memo_service.go:545` purely to build the webhook payload; no delete follows. Reactions key on `ContentID` (the `memos/{uid}` resource-name string) rather than a memo FK, so they are left orphaned. Also relevant: none of this runs in a transaction, so a partial failure leaves the memo row present with its relations, attachments, and blobs already gone.
