**Interceptor: `web/src/connect.ts` (`authInterceptor`, line 156) with token state in `web/src/auth-state.ts`; token kinds: short-lived access token (Bearer header, in-memory) + refresh token (HTTP-only cookie) + Personal Access Tokens; backend validation: `server/auth/`**

How it works:

**Interceptor.** `authInterceptor` (`web/src/connect.ts:156-178`) is registered on the single shared transport (`:188`). Per request it resolves a token via `getRequestToken()` and sets `Authorization: Bearer <token>` (`:97-100`). Two refresh paths:
- *Preflight* — if `isTokenExpired(REQUEST_TOKEN_EXPIRY_BUFFER_MS)` it refreshes before sending (`:140-147`). The comment at :136-139 names the invariant: without this, an expired token on a public endpoint like `ListMemos` would be treated as anonymous and silently return guest-scoped data.
- *Reactive* — on `Code.Unauthenticated` it refreshes, retries once, and marks the retry with an `X-Retry` header to prevent loops (`:164-172`); if refresh fails, `redirectOnAuthFailure()` (`:174`).

**Token kinds.**
1. **Access token** — held in memory/`auth-state` (`getAccessToken`/`setAccessToken`), sent as `Bearer`, with an expiry timestamp.
2. **Refresh token** — never read by JS; carried as a cookie, which is why both transports use `fetchWithCredentials` with `credentials: "include"` (`:57-62`). Redeemed via `AuthService.RefreshToken` (`:75`), which returns a new access token + `expiresAt`.
3. **Personal Access Tokens** — server-side, validated by hash lookup (`Store.GetUserByPATHash`, `store/user_setting.go:128`).

A detail worth noting: refresh runs on a **separate transport with no interceptors** (`refreshTransport`, `:65-70`) specifically to avoid recursion, and concurrent refreshes are deduplicated by `tokenRefreshManager` (`:30-51`) — the comment at :86-88 explains this guards against tab-focus refresh racing the 401 refresh under server-side token rotation.

**Backend validation.** Package `server/auth`: `Authenticator.resolveBearer` (`server/auth/authenticator.go:149`) and `AuthenticateByRefreshToken` (`:61`) resolve credentials to a user via `Store.GetUser`; JWT minting/parsing lives in `server/auth/token.go`, request-header extraction in `extract.go`, and context propagation in `context.go`. Session-side handling on the API layer is `server/router/api/v1/auth_service_session.go` (`fetchCurrentUser`, :246), with the sign-in entry point at `server/router/api/v1/auth_service.go:51`.
