`Store.DeleteMemo` (`store/memo.go:140-159`) performs manual cascade cleanup in this order before the memo row:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (line 142)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (line 145) — both directions, since the table has no FK cascade (`store/migration/sqlite/LATEST.sql:47-52`)
3. **Attachments linked to the memo** — listed via `FindAttachment{MemoID: &delete.ID}` then deleted one at a time in a loop (lines 149-157); going through `s.DeleteAttachment` rather than the driver directly means blob/file cleanup logic in the store layer still runs

Only then: `s.driver.DeleteMemo(ctx, delete)` at line 158.

Two things worth flagging:

- **Reactions are *not* deleted here.** The API handler `APIV1Service.DeleteMemo` reads them (`ListReactions` at `server/router/api/v1/memo_service.go:545`) but only to build the webhook payload — no reaction delete appears in the store cascade. Reactions key off `ContentID` (the resource name string), not a memo FK, so they are orphaned by design or by omission.
- **No transaction wraps the sequence** — relations and attachments are deleted before the memo, so a mid-sequence failure leaves the memo present with its relations/attachments already gone.
