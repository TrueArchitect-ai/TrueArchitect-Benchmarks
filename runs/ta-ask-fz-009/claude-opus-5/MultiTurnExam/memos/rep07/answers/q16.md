Cleanup happens at two levels. Ordered as they execute:

**In the API handler (`server/router/api/v1/memo_service.go`, `DeleteMemo` at :518)**
1. **Comment memos** — child memos linked by a `MemoRelationComment` relation are deleted first, each via a recursive `Store.DeleteMemo` (`:567–577`), which cascades their own relations and attachments.

**In the store layer (`store/memo.go`, `Store.DeleteMemo` at :140)**
2. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID}` (`:142`)
3. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID}` (`:145`) — both directions, since the table has no FKs
4. **attachments linked to the memo** — listed by `FindAttachment{MemoID}` and deleted one by one (`:148–157`)
5. **the memo row itself** — `s.driver.DeleteMemo` (`:158`)

Two things this path does *not* delete, which is easy to misread:

- **Reactions** are only *read* (`:545`, for the webhook payload) — no reaction delete is issued here. `Store.DeleteMemo` doesn't touch the `reaction` table either.
- **memo_share** rows aren't cleaned up in either function.

Since the schemas declare no foreign keys on these tables (`store/migration/sqlite/LATEST.sql:47–52` for `memo_relation`), that cleanup is entirely application-enforced — and it's not wrapped in a transaction, so a mid-sequence failure leaves partial deletion.
