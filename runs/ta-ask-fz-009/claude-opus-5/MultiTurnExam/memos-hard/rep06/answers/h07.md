**Notes on the hops that matter:**

**Entry.** The route is registered on `fileGroup` as `GET /users/:identifier/avatar` (`fileserver.go:124`); the group prefix makes the browser-visible path `/file/users/{name}/avatar`. That's exactly what the API hands clients — `user_service_converters.go:36` rewrites `AvatarUrl` to `fmt.Sprintf("/file/%s/avatar", userpb.Name)` instead of inlining base64, so profile-image bytes are fetched over this dedicated file route rather than through the user RPC.

**Auth gate before any lookup.** `serveUserAvatar` first checks `s.Profile.AllowAnonymous()` (`fileserver.go:173`, defined `internal/profile/profile.go:46`). On a private instance it calls `getCurrentUser` (`fileserver.go:708`) → `auth.Authenticator.AuthenticateToUser` (`server/auth/authenticator.go:190`) and 401s when there's no viewer (`fileserver.go:178-180`). On a public instance this branch is skipped entirely — another user's avatar is anonymously readable by design.

**Data hop.** `getUserByUsername` is a one-line adapter — `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})` (`fileserver.go:716`). Note the lookup is by **username**, not ID.

**Cache asymmetry, worth knowing.** `Store.GetUser` (`store/user.go:148`) consults `userCache` **only when `find.ID != nil`** (lines 149–156). Since this path queries by `Username`, every avatar request misses the cache and falls through to `ListUsers` (line 158), which delegates to the dialect driver via `s.driver`. The result is then cached by ID (line 167), but that entry can never serve a subsequent avatar request.

**Where the bytes actually live.** There is no blob table or filesystem read here: the image is stored **inline on the user row** as a data URI in `user.AvatarURL`. `serveUserAvatar` decodes it with `parseDataURI` (`fileserver.go:737`, base64 under the hood), validates the MIME against the `avatarAllowedTypes` allowlist (`fileserver.go:75`, checked at `:201`), sets security + cache headers (`:205-207`), and writes `c.Blob` (`:209`). So avatars bypass the attachment/S3 machinery completely — which is why the presign runner and `checkAttachmentPermission` play no part in this trace.
