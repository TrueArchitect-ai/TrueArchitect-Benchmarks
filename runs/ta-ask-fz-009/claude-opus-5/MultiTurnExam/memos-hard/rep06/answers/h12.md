**The concrete code.** `store/db/sqlite/memo.go:41` assembles the statement — `INSERT INTO \`memo\` (...) VALUES (...) RETURNING \`id\`, \`created_ts\`, \`updated_ts\`, \`row_status\`` — with `?` placeholders and a parallel `args` slice (lines 17–39), then executes it via `d.db.QueryRowContext(ctx, stmt, args...).Scan(...)` at line 42, reading the generated columns straight back into the passed-in `*store.Memo`. That `QueryRowContext` call is the actual write.

**How I established that this candidate, not the other two, runs.** Three linked facts, none of them guesswork:

1. **The default is `sqlite`.** `cmd/memos/main.go:122` sets `viper.SetDefault("driver", "sqlite")`, and the flag itself defaults the same way (`cmd/memos/main.go:130`). With no database flags supplied, `profile.Driver == "sqlite"`. `internal/profile/profile.go:110` corroborates by synthesizing a DSN — `memos_prod.db` under the data dir — precisely when the driver is sqlite and no DSN was given, so a flagless install is a self-configuring SQLite file.

2. **One factory seam converts that string into a concrete type.** `db.NewDBDriver` switches on `profile.Driver` and returns `sqlite.NewDB(profile)` for `case "sqlite":` (`store/db/db.go:19-20`). This is the same sealed boundary established in h04: only `store/db/db.go` imports the dialect packages, so no other path can produce a `mysql` or `postgres` driver.

3. **The store layer dispatches through the interface, never a concrete type.** `Store.CreateMemo` validates the UID and then calls `s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`) — `s.driver` is a `store.Driver`. That's why grep alone can't answer this question: three methods named `CreateMemo` satisfy the contract (`store/db/sqlite/memo.go:16`, plus the mysql and postgres equivalents), and the call site names none of them. The binding is decided once at startup by step 2 and is fixed for the process lifetime.

**The one dialect-specific detail worth noting:** SQLite here uses `RETURNING` to recover the auto-assigned `id` and timestamps in a single round trip (line 41). The MySQL implementation cannot do that and must use a different retrieval strategy — which is exactly the sort of divergence that makes it wrong to answer this question from `store/memo.go` alone.
