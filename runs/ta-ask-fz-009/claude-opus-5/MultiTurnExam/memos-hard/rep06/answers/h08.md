**`s3presign.Runner.RunOnce` — invoked from production, two ways.** Both are in the startup path established earlier: the synchronous catch-up call at `server/server.go:163` inside `Server.startBackgroundRunners`, and the ticker loop at `server/runner/s3presign/runner.go:36`, where `Run` re-invokes it every 12 hours. **`memopayload.Runner.RunOnce` — not invoked at all.** `[ArchMap query]` returns a **certified zero** — no direct or indirect callers, and the widening probes found nothing either. Text search agrees and sharpens the picture: the `memopayload` package *is* used in production, but only via a different symbol. `server/router/api/v1/memo_service.go:108` and `:447` call the package-level function `memopayload.RebuildMemoPayload` directly during memo create and update. Nothing constructs a `memopayload.Runner` or calls its `RunOnce`.

**What that means architecturally.** Payload rebuilding migrated from a background-runner model to inline, request-time invocation. The per-memo work function survived that move and is load-bearing; the `Runner` wrapper around it is vestigial — dead code in the exec sense, and notably it is *not* wired into `startBackgroundRunners` alongside the s3presign runner (`server/server.go:153-173`), which is the only place a runner would be started. Worth flagging: the `RunOnce` name collision across the two types is coincidental convention, not an interface — there is no shared runner interface either type satisfies, so nothing dispatches to `memopayload.Runner.RunOnce` indirectly.
