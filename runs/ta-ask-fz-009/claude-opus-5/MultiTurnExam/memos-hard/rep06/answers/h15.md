**Two distinct enforcement strategies, worth separating:**

**1. Post-fetch predicate checks** — load the memo, then decide. The canonical one is `checkMemoReadAccess` (`memo_service.go:39`), used by `GetMemo` (`:356`), parent-memo checks (`:367`), and comment listing (`memo_service_comments.go:148`). Its logic: archived memos are creator-only (`:45-53`); non-public memos require an authenticated viewer (`:55-60`); private memos require `memo.CreatorID == user.ID` (`:63`). Note it does *not* grant admin override, unlike most other sites.

**2. Query-level narrowing** — never fetch what the viewer can't see. `ListMemos` sets `memoFind.VisibilityList = []store.Visibility{store.Public}` for anonymous viewers and `{Public, Protected}` for authenticated non-owners (`memo_service.go:219,225`). RSS does the same unconditionally — public only, on both the instance feed (`rss.go:90`) and per-user feed (`rss.go:141`). Related-memo and comment sub-lists use a filter expression string instead: `visibility == "PUBLIC"` (`memo_relation_service.go:109`, `memo_service_converter.go:184`, `memo_service_comments.go:158`).

**The non-obvious surfaces.** Three enforce visibility outside the memo RPCs entirely:

- **SSE** (`sse_hub.go:134`) filters *outbound realtime events* per subscriber: private events reach only the creator or an admin (`:137`), and unknown visibility values **deny by default** with a warning (`:140-142`) — fail-closed. Visibility rides on the event purely for this purpose and is excluded from JSON (`sse_hub.go:32`, `json:"-"`).
- **File serving** (`fileserver.go:650`) inherits memo visibility for attachments: unlinked attachments are creator-or-admin only (`:652-663`), and linked ones fall through to the parent memo's visibility. This is the gate called at `fileserver.go:149` in the attachment path.
- **Email notifications** (`email.go:306`) re-checks before sending, so a comment digest can't leak a private memo's content to a mentioned user (`:155`, `:187`).

**Architectural read:** there is no single authorization service — the rule "private ⇒ creator (usually + admin)" is re-implemented at ~11 sites in 4 packages. The predicates are near-identical (`memo.Visibility == store.Private && memo.CreatorID != user.ID && !isSuperUser(user)` recurs verbatim at `reaction_service.go:38,83`, `attachment_service.go:451`, `memo_attachment_service.go:222`, `memo_service_comments.go:41`), which makes the invariant correct today but fragile: adding a visibility level would require touching every one of these, and the `checkMemoReadAccess`/`isSuperUser` divergence on admin override is already an inconsistency between surfaces.
