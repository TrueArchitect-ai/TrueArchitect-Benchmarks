**`internal/idp` — `internal/idp/idp.go`; `internal/idp/oauth2` — `internal/idp/oauth2/oauth2.go`**

**Abstraction.** `internal/idp` is a deliberately thin package — the whole of `internal/idp/idp.go` is one struct, `IdentityProviderUserInfo` (line 3), carrying the four normalized fields every provider must produce: `Identifier`, `DisplayName`, `Email`, `AvatarURL`. Worth being precise here: there is **no Go interface** defining the provider contract. The abstraction is the shared *return type*, not a polymorphic port. Any future provider conforms by producing an `*idp.IdentityProviderUserInfo`, and callers would still have to switch on provider type explicitly rather than dispatch through an interface.

**Implementation.** `internal/idp/oauth2` is the only concrete protocol that ships. Its package doc says so directly (`internal/idp/oauth2/oauth2.go:1`). The type is `IdentityProvider` (line 20), wrapping a `*storepb.OAuth2Config`, built by `NewIdentityProvider` (line 27) which fail-fasts on the five required config fields — `clientId`, `clientSecret`, `tokenUrl`, `userInfoUrl`, `fieldMapping.identifier` (lines 28–38). Two behaviors make up the login flow:

- `ExchangeToken` (line 47) — trades the authorization code for an access token via `golang.org/x/oauth2`, with optional PKCE `code_verifier` support (per the doc comment at line 46).
- `UserInfo` (line 83) — calls the userinfo endpoint under a 10s timeout (`userInfoRequestTimeout`, line 24) and maps the raw claims into `idp.IdentityProviderUserInfo` (line 114) using the configured field mapping.

The field-mapping indirection is what lets one OAuth2 implementation cover OIDC-ish providers generically — GitHub, Google, Keycloak and friends differ in claim names, not in protocol, so they're configuration rather than new packages. Storage of provider config lives in the protobuf-backed `storepb.OAuth2Config`, and the admin-facing CRUD surface is the `IdentityProviderService` RPC (`proto/gen/api/v1/apiv1connect/idp_service.connect.go:26`).
