**What the middleware/interceptor stack actually contains.** The registered chain has four Connect interceptors, none of which limits request volume:

| Component | Path | Purpose |
|---|---|---|
| `MetadataInterceptor` | `server/router/api/v1/connect_interceptors.go:22` | HTTP headers → gRPC metadata |
| `LoggingInterceptor` | `:98` | per-RPC logging with error classification |

Plus CORS at the HTTP layer (`newCORSMiddleware`, `server/cors.go:13`).

**The nearest thing that exists, and why it isn't rate limiting.** Two weighted semaphores cap *concurrency* for expensive image work — `thumbnailSemaphore` at 3 and `imageProcessingSemaphore` at 2 (`server/router/api/v1/v1.go:59-60`), with a third in the file server (`server/router/fileserver/fileserver.go:116`, acquired at `:448`). These bound how many operations run *simultaneously* to prevent memory exhaustion; they don't count requests per user per unit time, don't reject with 429, and apply only to thumbnail/image paths. A client can issue unlimited sequential requests through them.

So if you need per-user throttling, it would be new work — the natural insertion point being a fifth Connect interceptor alongside `AuthInterceptor`, since that's where the caller identity is already resolved.
