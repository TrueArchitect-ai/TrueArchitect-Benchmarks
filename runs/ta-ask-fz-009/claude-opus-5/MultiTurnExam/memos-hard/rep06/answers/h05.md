**Explicit Go code — two deliberate `DELETE FROM reaction` statements per dialect inside the user-deletion transaction. There is no database-level rule to fall back on.**

**What I checked, and what each check established:**

**1. The Go deletion path.** `deleteUserTargetsTx` runs both reaction cleanups back to back, ahead of the memo/user rows:
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched (`store/db/sqlite/user_delete.go:380-388`, mysql `:417-424`, postgres `:380-388`)
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`, mysql `:437-440`, postgres `:400-403`)

Both are invoked from the orchestrator at `store/db/sqlite/user_delete.go:96` and `:102` (identically at mysql `:96,102` and postgres `:96,102`).

The **two** statements are the substantive point — they cover the two distinct ways a deleted user touches the reaction table:
- *by creator* — reactions **the deleted user left** on anyone's memos;
- *by content_id* — reactions **other users left on the deleted user's memos**, keyed off `memoContentIDsFromRefs(targets.memos)` (`store/db/sqlite/user_delete.go:94`), where the memo set comes from `listDeleteUserMemoTree` during target collection (`:64`).

Dropping either one would orphan rows, so this is intentional, not redundant.

**2. The schema, to rule out a DB-level rule.** The `reaction` table has **no foreign keys and no `ON DELETE CASCADE`** in any of the three dialects — `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`. `creator_id` and `content_id` are plain `INTEGER`/`TEXT` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. The contrast is right next door: `memo_share` *does* declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (sqlite `:109`, mysql `:108`, postgres `:108`), which confirms the codebase uses cascades where it wants them — and pointedly does not here.

**Consequence for the invariant:** reaction cleanup is application-enforced only. It's transactional (all statements share the `*sql.Tx`), so it's atomic on the supported delete path, but any deletion of a user row that bypasses `deleteUserTargetsTx` — direct SQL, an out-of-band admin script — will leave orphaned reactions behind. The database will not catch it.
