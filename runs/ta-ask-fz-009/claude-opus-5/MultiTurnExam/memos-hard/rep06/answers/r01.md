**Premise correction: there is no Redis. The cache layer is a hand-rolled in-process, in-memory cache — no external store, no connection to configure. User entries get a 10-minute TTL from the shared default config.**

**Why the premise doesn't hold.** A case-insensitive search for `redis` across the repo returns **no matches in 1042 files**, and `go.mod` contains no Redis client — no `go-redis`, no `redigo`, nothing in either the direct or indirect require blocks. There is no Redis dependency, config key, or connection string anywhere in this codebase.

**The actual mechanism.** `store/cache/cache.go` implements the cache from scratch:

- `Cache` (`store/cache/cache.go:67`) holds entries in a `sync.Map` with an atomic item counter — pure process memory, so nothing is shared between instances and everything is lost on restart.
- `Interface` (`:11`) is the contract: `Set`, `SetWithTTL`, `Get`, `Delete`, `Clear`, `Size`, `Close`.
- Expiry is per-entry — `SetWithTTL` stamps `expiration: time.Now().Add(ttl)` (`:112`) — and enforced two ways: lazily on read, where `Get` deletes and misses if `time.Now().After(itm.expiration)` (`:135-144`), and actively by a `cleanupLoop` goroutine started in `New` (`:83`, loop at `:200`).

**The TTL on user entries: 10 minutes.** There is no user-specific TTL. `NewStore` builds all three caches from one shared `cacheConfig`:

```go
instanceSettingCache: cache.New(cacheConfig),
userCache:            cache.New(cacheConfig),   // store/store.go:52
userSettingCache:     cache.New(cacheConfig),
```

and `DefaultConfig()` (`store/cache/cache.go:57-64`) sets `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`. Since `Store.GetUser` caches via `s.userCache.Set(...)` (`store/user.go:167`) — the plain `Set`, which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`cache.go:94`) — user entries expire 10 minutes after write, with a sweep every 5 minutes and eviction of the oldest ~20% once 1000 items are exceeded (`cleanupOldest`, `:253-255`).

**Two consequences worth flagging.** First, because it's in-process, a multi-replica deployment has no cache coherence — each process holds its own copy, and a user updated on replica A can be served stale by replica B for up to 10 minutes. Second, as established in h07, the user cache is only consulted when looking up by ID (`store/user.go:149`), so username-keyed lookups write to it but never read from it.
