### Triggers

Recomputation happens on exactly two production paths, both in the memo write flow:

| Trigger | Site | Condition |
|---|---|---|
| `CreateMemo` | `server/router/api/v1/memo_service.go:108` | always, before `Store.CreateMemo` (line 115) |
| `UpdateMemo` | `server/router/api/v1/memo_service.go:447` | **only** when the `content` field is in the update mask |

The `UpdateMemo` gating matters architecturally: the rebuild sits inside the `path == "content"` branch, and the sibling branch `path == "visibility"` (line 452) does not recompute. So metadata is refreshed precisely when the input it derives from changes — content is assigned at line 446, rebuilt at 447, and both `update.Content` and `update.Payload` are written together (lines 450–451), keeping row and derived data consistent in one write.

A third path exists but is **dead**: `memopayload.Runner.RunOnce` (`server/runner/memopayload/runner.go:27`) batch-rebuilds all memos 100 at a time, but as established, nothing constructs that runner in production. It's a leftover backfill.

Note also that `SetMemoAttachments` and `SetMemoRelations` fire `memo.updated` webhooks without touching content — so they don't recompute, correctly.

### What gets extracted

`RebuildMemoPayload` (lines 74–88) initializes `memo.Payload` if nil, calls `ExtractAll` once, then assigns just two fields (lines 85–86):

- **`Payload.Tags`** — `#tag` nodes, deduplicated with original case preserved via `uniquePreserveCase` (`internal/markdown/markdown.go:418`). `asMemoTagNode` (:376, helper at :134) filters out tags nested inside links/images.
- **`Payload.Property`** — a `MemoPayload_Property` with five derived flags/values:
  - `Title` — text of the first block-level child *only if* it's an H1 (:384-388)
  - `HasLink` — any `KindLink` node (:393)
  - `HasCode` — code block, fenced code block, or code span (:396)
  - `HasTaskList` — any task checkbox (:399)
  - `HasIncompleteTasks` — an unchecked checkbox (:402-404)

`ExtractAll` also collects `Mentions` (:379-381, lowercased), but `RebuildMemoPayload` deliberately **discards** them — mentions are consumed separately at `server/router/api/v1/memo_mention_helpers.go:32` to drive notifications rather than being persisted in the payload.

The whole extraction is a **single AST walk** (`gast.Walk` at :371, comment at :79 notes this is for efficiency) over one parse, rather than one traversal per property.

### Why these properties exist

They're precomputed at write time so list and preview rendering never has to parse markdown. That's what makes filter expressions over `has_link`/`has_code`/`has_task_list` cheap at query time — the flags live in the stored payload, which is why `internal/filter` has the JSON-column machinery (`jsonArrayExpr`, `qualifyColumn`) seen elsewhere in this codebase.

One consequence of the inline-only design: since the batch runner is dead, any change to `ExtractAll`'s logic applies **only to memos written afterward**. Existing rows keep their old payloads until their content is next edited — there's no live backfill path.
