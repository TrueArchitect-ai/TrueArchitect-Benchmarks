### The adjacent controls that do exist

If the underlying concern is abuse protection, the codebase defends resources by other means — bounded concurrency and size caps rather than request-rate quotas:

- **Concurrency semaphores** — `thumbnailSemaphore` limited to 3, plus `imageProcessingSemaphore` (`server/router/api/v1/v1.go:39-41,59`); a separate `maxConcurrentThumbnails` semaphore in the file server (`server/router/fileserver/fileserver.go:107,116`).
- **Content length limit** — enforced per memo on create and update (`server/router/api/v1/memo_service.go:105,443`).
- **Bounded webhook queue** — 128 slots with drop-on-full (`internal/webhook/webhook.go:39,191`).
- **Response body cap** — webhook replies read through `io.LimitReader(resp.Body, 1<<20)` (`internal/webhook/webhook.go:158`).
- **Authorization gating** — the `AuthInterceptor` + `Authorizer` (`server/router/api/v1/authz.go`) with a public-method allowlist in `server/router/api/v1/acl_config.go`.

So per-user request throttling is a genuine gap, not something I failed to locate: unauthenticated endpoints like the RSS feeds (`server/router/rss/rss.go`) and login RPCs have no per-caller quota. Any rate limiting in a deployment would have to come from a reverse proxy in front of the server.
