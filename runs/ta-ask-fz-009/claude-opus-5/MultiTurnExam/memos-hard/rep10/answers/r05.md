These are the **single source of truth**. Generated Go lands in `proto/gen/api/v1/` (message/service stubs, `apiv1connect/` for Connect, `.pb.gw.go` for the gateway); generated TypeScript for the web client lands in `web/src/types/proto/api/v1/`.

One protobuf definition therefore yields three transports:

1. **gRPC** — `*_grpc.pb.go` service descriptors
2. **Connect RPC** — `proto/gen/api/v1/apiv1connect/*.connect.go`, procedures like `/memos.api.v1.UserService/GetUser`
3. **REST/JSON via grpc-gateway** — `*.pb.gw.go`, giving the `/api/v1/...` HTTP surface

### Why the confusion is understandable

Custom-method syntax like `users:batchGet` and `:getStats` collapses multiple reads into one call, which resembles GraphQL's batching intent. But it's Google AIP-136 custom methods over REST — the field selection is driven by protobuf `FieldMask` (visible in the `PATCH` patterns' update masks), not by a client-specified query language. To change the API contract you edit a `.proto` file and regenerate; there is no schema to introspect at runtime.
