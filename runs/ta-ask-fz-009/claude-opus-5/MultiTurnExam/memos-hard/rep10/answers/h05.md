**Explicit Go code — not a database-level rule.** Reactions are removed by two hand-written `DELETE` statements inside the user-deletion transaction, in each of the three driver packages.

### Evidence

**1. The explicit Go deletions.** `deleteUserTargetsTx` calls two separate reaction cleanups (shown at `store/db/sqlite/user_delete.go:96` and `:102`, identical at `store/db/mysql/user_delete.go:96,102` and `store/db/postgres/user_delete.go:96,102`):

| Function | SQL | sqlite | mysql | postgres |
|---|---|---|---|---|
| `deleteReactionsByContentIDsTx` | `DELETE FROM reaction WHERE content_id IN (…)` | `:380,383` | `:417,420` | `:380,383` |
| `deleteReactionsByCreatorTx` | `DELETE FROM reaction WHERE creator_id = ?` | `:400,401` | `:437,438` | `:400,401` |

Two passes because there are two ways a reaction relates to a departing user, and both must go:

- **`creator_id`** — reactions the deleted user placed on *anyone's* content.
- **`content_id`** — reactions *other users* placed on the deleted user's memos. The content IDs come from `memoContentIDsFromRefs(targets.memos)` (`store/db/sqlite/user_delete.go:94`), derived from the memo tree gathered by `listDeleteUserMemoTree` during `collectDeleteUserTargets` (line 64).

Deleting only by `creator_id` would orphan the second set. All of this runs on a single `*sql.Tx`, so cleanup is atomic with the user removal.

**2. Why no DB rule could do it.** The schema confirms the cascade option isn't available. In all three dialects the `reaction` table declares **no foreign keys at all**:

- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/mysql/LATEST.sql:91-98`
- `store/migration/postgres/LATEST.sql:91-98`

Columns are `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type`, plus a `UNIQUE(creator_id, content_id, reaction_type)` constraint. `creator_id` is a bare `INTEGER NOT NULL` with no `REFERENCES user(id)`.

The contrast is instructive: my search *did* find `ON DELETE CASCADE` in the same files — `memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, mysql `:108`, postgres `:108`). So the codebase uses DB-level cascades where it wants them; reaction cleanup is deliberately application-level.

`content_id` also explains part of this — it's a `TEXT`/`VARCHAR(256)` UID rather than an integer memo FK, so a cascade on that side would need a schema change first.

### Architectural note

The consequence is that this invariant is enforced in **three parallel implementations** with no database backstop. Any new driver, or any deletion path that bypasses `deleteUserTargetsTx`, silently leaves orphaned reaction rows — and since `creator_id` has no FK, the database will happily accept them.
