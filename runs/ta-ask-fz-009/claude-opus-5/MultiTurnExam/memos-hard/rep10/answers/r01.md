**Premise correction: there is no Redis.** A case-insensitive search for `redis` across **1,042 files** returns zero matches — no client library, no config key, no connection string, no docker-compose service. The cache layer is entirely **in-process and in-memory**, so there is no connection to configure.

### The actual mechanism

`store/cache/cache.go` implements a hand-rolled TTL cache:

- `Cache` struct (`store/cache/cache.go:67`) — a `sync.Map` for data plus an `atomic.Int64` item counter. No network dependency; the only imports are `context`, `sync`, `sync/atomic`, and `time` (lines 3–8).
- `cache.Interface` (line 11) defines `Set`/`SetWithTTL`/`Get`/`Delete`/`Clear`/`Size`/`Close`.

### The user-entry TTL: 10 minutes

Configured where the caches are constructed, not in any external config file. `store.New` (`store/store.go:38`) builds one `cache.Config` literal (lines 40–45):

```go
DefaultTTL:      10 * time.Minute
CleanupInterval: 5 * time.Minute
MaxItems:        1000
OnEviction:      nil
```

and passes that **same config** to all three caches (`store/store.go:51-53`):

- `instanceSettingCache`
- `userCache` ← user entries
- `userSettingCache`

So user entries expire **10 minutes** after write. `Set` applies `c.config.DefaultTTL` (`cache/cache.go:94`), and `SetWithTTL` stamps an absolute `expiration: time.Now().Add(ttl)` (line 112) — note this is write-time expiry, **not** sliding: `Get` (line 123) reads the timestamp but never extends it, so a hot user entry still gets evicted every 10 minutes.

These values are duplicated in `cache.DefaultConfig()` (`cache/cache.go:57-64`) with identical numbers, but `store.New` doesn't call it — it inlines its own literal. Either way, **10 minutes is not configurable at runtime**; there are no flags or env vars for it (contrast `--driver`, `--dsn` in `cmd/memos/main.go`).

### Two eviction paths

1. **Lazy** — `Get` deletes and reports a miss if `time.Now().After(itm.expiration)` (lines 135–144).
2. **Background** — `cleanupLoop` (line 200) ticks every `CleanupInterval` (5 min) and sweeps expired entries via `cleanup()` (line 218). These are the goroutines `Store.Close` shuts down at `store/store.go:74-76`.

Plus a size guard: exceeding `MaxItems: 1000` triggers `cleanupOldest` (line 253), which drops ~20% of capacity.

### Architectural consequence

Because the cache is per-process with no shared backing store, **multi-instance deployments do not share cache state and cannot invalidate each other's entries**. A user record updated on node A can be served stale from node B's `userCache` for up to 10 minutes. That's the practical reason the Redis premise matters — adopting it would be a real architectural change, not a config swap. The `cache.Interface` abstraction (line 11) is the seam where such an implementation would attach, though as noted nothing currently dispatches through it — `Store` holds concrete `*cache.Cache` fields (`store/store.go:27-29`).
