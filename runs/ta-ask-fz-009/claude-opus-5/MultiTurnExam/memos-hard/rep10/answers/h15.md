### The two enforcement idioms

**Guard idiom** — the recurring predicate is `memo.Visibility == store.Private && memo.CreatorID != user.ID && !isSuperUser(user)`. Note the inconsistency: `memo_service.go:63` omits the super-user escape (`memo.Visibility == store.Private && memo.CreatorID != user.ID` only), and `fileserver.go:699` spells the admin check inline as `user.Role != store.RoleAdmin` rather than calling `isSuperUser`. Same intent, three spellings.

**Narrowing idiom** — two variants. Authenticated requests build a CEL-style filter string `creator_id == %d || visibility in ["PUBLIC", "PROTECTED"]` (five sites, identically formatted via `fmt.Sprintf`); anonymous requests set the structured `memoFind.VisibilityList = []store.Visibility{store.Public, store.Protected}` (`memo_service.go:225`, `user_service_stats.go:90,220`).

The unauthenticated surfaces are stricter still — RSS (`rss.go:90,141`) and the sitemap (`frontend.go:150`) restrict to `store.Public` **only**, excluding Protected, which is correct since those outputs are anonymous by nature.

### Worth flagging

`SSEClient.canReceive` (`sse_hub.go:134`) is the one enforcement point on a *push* path rather than a pull, and it's the only one with a **default-deny** branch (`:140-143`) that logs and rejects unknown visibility values. The other sites are default-allow: they test specifically for `Private` and let anything else through, so a hypothetical new visibility tier would leak everywhere except SSE.

The broader observation: this invariant is replicated across ~15 call sites in 6 packages with no shared helper — there's no single `canView(user, memo)` chokepoint. `isSuperUser` is the only shared fragment. Any new memo-reading surface must re-derive the rule, and the variations already visible at `memo_service.go:63` suggest that drift has begun.
