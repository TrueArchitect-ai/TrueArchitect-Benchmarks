How they converge:

1. The three `Dispatch*Webhook` methods all funnel into `dispatchMemoRelatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:48`), except the comment case which has its own loop (`:30`). Both loops load the target user's webhooks via `s.Store.GetUserWebhooks` and call `webhook.PostAsync` (`:71`, `:43`) — the URL comes from `hook.Url`, i.e. user-configured.
2. `PostAsync` (`internal/webhook/webhook.go:184`) only enqueues onto a 128-slot channel; it never dials. The four worker goroutines started in `init()` (`webhook.go:42-55`) are what call `Post`, which is why the graph reports `webhook.init.webhook.go.42` as `Post`'s sole caller — the async queue is the seam that decouples handlers from delivery.
3. `Post` is therefore the single choke point: every one of the six handlers, both transports, and all four activity types (`memos.memo.created/updated/deleted/comment.created`) pass through it before any packet leaves the process.

Worth noting for the threat model: because the queue-and-worker hop erases the caller's identity and context, `Post` cannot enforce per-handler policy — the SSRF guard has to live below it, in the shared `safeClient` transport (`webhook.go:32-37`).
