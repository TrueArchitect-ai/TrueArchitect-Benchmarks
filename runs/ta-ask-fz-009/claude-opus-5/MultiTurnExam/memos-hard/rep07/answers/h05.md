**Explicit Go code — two deliberate SQL deletes inside the user-deletion transaction, replicated per driver. There is no database-level cascade to fall back on.**

What I checked, and what it showed:

**1. The Go deletion path.** `deleteUserTargetsTx` issues two separate reaction deletes before the user row goes away:
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched (`store/db/sqlite/user_delete.go:380-388`), called at `:96`. This removes reactions *others* left on the departing user's memos, keyed by the `memos/{uid}` content IDs built in `memoContentIDsFromRefs` (`:512-517`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`:400-403`), called at `:102`. This removes reactions the user left on *anyone's* content.

Both run inside the single transaction opened by `DeleteUser` (`store/db/sqlite/user_delete.go:29`), so reaction cleanup is atomic with the user row delete at `:123`.

**2. Both directions are needed because the schema is unusual.** `reaction.content_id` is a *text* column holding a resource name (`content_id TEXT NOT NULL`, `store/migration/sqlite/LATEST.sql:96`), not an integer FK to `memo.id`. A polymorphic string reference cannot carry a foreign key, which is exactly why the memo-side cleanup has to be hand-written.

**3. No DB-level rule exists for this table.** In all three dialects the `reaction` table declares only a PK, columns, and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`, no `ON DELETE CASCADE`:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/mysql/LATEST.sql:91-98`
- `store/migration/postgres/LATEST.sql:91-97`

For contrast, the same Postgres file *does* use a cascade where an integer FK is available — `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` on `memo_share` (`store/migration/postgres/LATEST.sql:108`). So the absence on `reaction` is a schema property, not an oversight in my search.

**4. All three drivers implement it.** The same two functions and the same two call sites exist in `store/db/mysql/user_delete.go:96,102,417,437` and `store/db/postgres/user_delete.go:96,102,380,400` — the invariant is upheld per-dialect by duplicated code rather than by a shared layer, which is the maintenance risk here: a fourth driver, or a new reaction-bearing content type, would have to remember both deletes.
