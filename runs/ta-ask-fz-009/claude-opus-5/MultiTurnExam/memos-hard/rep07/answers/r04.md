**Premise correction: neither. There is no message broker in this system at all — no NATS, no RabbitMQ, no Kafka, no AMQP client. The "workers" are goroutines in the same process, and the "queue" is a Go channel, not a declared broker queue.**

Evidence for the absence: a case-insensitive scan for `nats|rabbitmq|amqp|kafka|streadway|nats-io` across the repo matches only four Catalan translation strings in `web/src/locales/ca.json` (words like "predeterminats" containing the substring "nats") — zero Go hits, and `go.mod` carries no broker client.

**Actual mechanism** — an in-process bounded worker pool, all inside `internal/webhook/webhook.go`:

- **The "queue"**: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`. A buffered channel with capacity 128, declared as a package-level var. That is the only queue declaration; the graph confirms `webhook.asyncPostQueue` is a single package-scope variable anchored at `internal/webhook/webhook.go:25` (the `var` block).
- **The "workers"**: four goroutines started in `init()` — `internal/webhook/webhook.go:42-55` — each looping `for payload := range asyncPostQueue` and calling `Post(payload)`, logging failures with `slog.Warn`.
- **The producer**: `PostAsync` — `internal/webhook/webhook.go:184` — does a non-blocking `select` send (`:189-195`). When the buffer is full it takes the `default` branch and **drops the event** with a warning. Producers are the memo RPC handlers via `dispatchMemoRelatedWebhook` / `DispatchMemoCommentCreatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:71`, `:43`).
- **Delivery**: `Post` — `internal/webhook/webhook.go:120` — HMAC-signs the body if a secret is configured (`:139-149`) and sends via the SSRF-guarded `safeClient` (`:152`).

The architectural consequences of using a channel rather than a broker are worth stating plainly, since they're the properties people usually assume a broker provides:

- **No durability** — the buffer lives in process memory; a restart or crash loses every queued webhook.
- **No retry** — `Post` failures are logged once and discarded (`:46-51`); there is no redelivery, backoff, or dead-letter path.
- **At-most-once, lossy under load** — overflow past 128 silently drops (`:191-195`).
- **No cross-replica coordination** — each server process has its own independent queue and its own four workers.

So the async seam here is a deliberate "fire and forget, don't block the request" decoupling, not a guaranteed-delivery pipeline.
