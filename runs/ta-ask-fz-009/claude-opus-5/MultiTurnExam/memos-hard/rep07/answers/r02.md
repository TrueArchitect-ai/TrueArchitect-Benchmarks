**Premise correction: there is no per-user API rate-limiting middleware in this codebase. It does not exist, so there is no registration site and no request limits to report.**

Evidence:

- **Certified miss from the code graph**: `[ArchMap query]` probed all 7,293 indexed symbols across exact, prefix, substring, qualified-name, abbreviation, and doc-text tiers and found nothing.
- **Text search agrees**: a case-insensitive scan for `rate.?limit|ratelimit|throttl|golang.org/x/time/rate` across the repo returns only documentation prose — `internal/email/README.md:286,291,295` and `internal/email/doc.go:86` — both of which *suggest* rate limiting as a future hardening idea for email sending, with `golang.org/x/time/rate` shown as example code in a comment. Neither is implemented.
- **The dependency is not directly used**: `golang.org/x/time v0.15.0` appears in `go.mod` marked `// indirect`, i.e. pulled in transitively, not imported by this project.
- **The full middleware stack is short and contains no limiter.** Everything registered on the Echo server:
  - `middleware.Recover()` — `server/server.go:51`
  - `newCORSMiddleware(profile)` — `server/server.go:52` (defined at `server/cors.go:14`)
  - static file serving + SPA fallback — `server/router/frontend/frontend.go:54`, `:59`

What *does* exist in adjacent territory, so the gap is clear rather than implied:

- **Authentication/authorization** interception, not throttling — the ACL config at `server/router/api/v1/acl_config.go` plus the gateway auth middleware referenced at `server/router/api/v1/v1.go:95`.
- **Concurrency limiters**, which are sometimes mistaken for rate limits: `semaphore.NewWeighted(3)` for thumbnail generation and `NewWeighted(2)` for image processing (`server/router/api/v1/v1.go:59-60`, and `maxConcurrentThumbnails = 3` at `server/router/fileserver/fileserver.go:46`). These cap *simultaneous in-flight work* to protect memory; they impose no per-user request quota and no time window.
- **Per-request size/content bounds**: content-length limits on memo writes (`server/router/api/v1/memo_service.go:105`, `:443`) and a 1 MiB response cap on webhook delivery (`internal/webhook/webhook.go:158`).

So abuse protection here is authentication plus resource-bounding, not request-rate accounting. If you need per-user limits, there is no existing seam to configure — it would be new middleware registered alongside `server/server.go:51-52`.
