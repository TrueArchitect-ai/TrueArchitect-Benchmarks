**Premise correction: there is no Redis anywhere in this codebase.** A case-insensitive search for "redis" across 1,042 files returns zero matches — no client library, no connection config, no flag. The cache layer is a hand-rolled, process-local in-memory cache with no external dependency and no cross-process coherence.

**Actual mechanism:**

- **Implementation**: `cache.Cache` — `store/cache/cache.go:67` — a `sync.Map` plus an atomic item counter, behind the `cache.Interface` contract (`store/cache/cache.go:11`). Entries are `item{value, expiration, size}` (`:35-39`).
- **Configuration site**: `store/store.go:51-53`, where three separate cache instances are built with one shared `cacheConfig` — `instanceSettingCache`, `userCache`, `userSettingCache` (fields declared at `store/store.go:27-29`). This is the closest thing to "connection configuration" that exists: no address, no credentials, just tuning knobs.
- **TTL on user entries**: **10 minutes**, from `cache.DefaultConfig()` at `store/cache/cache.go:57-64` (`DefaultTTL: 10 * time.Minute`). Every user write goes through `userCache.Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` applies `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). No caller uses `SetWithTTL` for users, so there is no per-user override.

The rest of the eviction policy, since it shapes the same invariant:

- **`CleanupInterval: 5 * time.Minute`** — a background `cleanupLoop` goroutine sweeps expired entries (`store/cache/cache.go:200-215`); it's stopped by `Cache.Close`, called from `Store.Close` (`store/store.go:74-76`).
- **`MaxItems: 1000` per cache instance** — exceeding it triggers `cleanupOldest`, which drops ~20% of capacity (`store/cache/cache.go:117-119`, `:253-255`). Worth knowing: on an instance with more than 1,000 active users, user entries can be evicted well before their 10-minute TTL.
- **Lazy expiry on read** — `Get` checks `time.Now().After(itm.expiration)` and deletes on the spot (`store/cache/cache.go:135-144`), so a stale entry is never served even between sweeps.
- **Explicit invalidation** exists for deletes: `userCache.Delete` in `store/user_delete.go:40`.

One consequence of there being no Redis: the cache is per-process, so a multi-replica deployment would have independent caches and up to 10 minutes of divergence on user data. And note the read path only consults the cache when looking up by ID (`store/user.go:149-156`) — username lookups always hit SQL.
