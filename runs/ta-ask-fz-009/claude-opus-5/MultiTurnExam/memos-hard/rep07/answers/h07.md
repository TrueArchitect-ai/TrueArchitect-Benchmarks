Notes on the boundary behavior, since a few things are not obvious from the hop list:

- **No blob storage is involved.** The avatar is not an attachment — it lives inline on the user row as a base64 data URI in `user.AvatarURL`, decoded at request time by `parseDataURI` (`fileserver.go:737`, regex at `:98`) and written straight out with `c.Blob` (`:209`). The data layer returns the image bytes as part of the user record.
- **Why this endpoint exists at all:** `convertUserToProto` rewrites the user's `avatar_url` field to `/file/{name}/avatar` when it detects base64 content (`server/router/api/v1/user_service_converters.go:32-36`), specifically to keep raw base64 out of API responses. So the browser is following a URL the API minted for it.
- **The lookup is by username, not ID** (`FindUser{Username: &identifier}`, `fileserver.go:716`), which means it misses the `userCache` fast path in `GetUser` — that cache is only consulted when `find.ID` is set (`store/user.go:149-156`). Every avatar request goes to `ListUsers` and thus to SQL; results are cached on the way back (`store/user.go:142-144`).
- **Access control:** anonymous fetches are allowed only if `s.Profile.AllowAnonymous()`; otherwise `getCurrentUser` → `authenticator.AuthenticateToUser` must resolve a viewer (`fileserver.go:173-181`, `:708-712`). There is no per-target authorization beyond that — any authenticated viewer may fetch any user's avatar. Output is constrained by `avatarAllowedTypes` (`:75-83`, `:201`) plus `setSecurityHeaders` (`:758`), which is the XSS guard on this path.
- **Service wiring:** the handler is constructed and mounted at `server/server.go:81`.
