**Premise correction: there is no per-user API rate-limiting middleware in this codebase. No registration site and no request limits exist to report.**

**Evidence for the absence, not just grep silence:**
- The code graph returns a **certified miss** for `ratelimit` — fuzzy matching probed exact, prefix, substring, qname, abbreviation, and doc-text tiers across all 7,293 symbols and found nothing.
- A repo-wide regex for `rate.?limit|ratelimit|throttl|too.?many.?requests|StatusTooManyRequests` matches only two *aspirational doc comments* (`internal/email/README.md:286`, `internal/email/doc.go:86` — "Rate limit email sending to prevent abuse", a suggestion, not an implementation) and two unrelated `ResourceExhausted` uses.
- The complete middleware registration surface is small enough to enumerate: `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware`. The frontend adds static-file and SPA-fallback middleware (`server/router/frontend/frontend.go:54,59`). Nothing else is `Use`'d at the server level.

**What exists instead — and why it is not rate limiting.** Two *concurrency semaphores*, both process-global:

| Mechanism | Limit | Site |
|---|---|---|
| `thumbnailSemaphore` | 3 concurrent | `server/router/api/v1/v1.go:59` |
| `imageProcessingSemaphore` | 2 concurrent | `server/router/api/v1/v1.go:60` |
| `thumbnailSemaphore` (fileserver) | 3 concurrent (`maxConcurrentThumbnails`) | `server/router/fileserver/fileserver.go:46,116` |

The EXIF-stripping path returns `codes.ResourceExhausted, "too many image processing requests"` when a slot can't be acquired (`server/router/api/v1/attachment_service.go:158-161`) — which *reads* like rate limiting but isn't. The distinction matters architecturally:

- These cap **simultaneous in-flight work**, not requests per unit time. A single client can issue unlimited sequential requests forever.
- They are **instance-wide, not per-user**. There is no identity in the accounting — one user saturating the 2 image-processing slots degrades everyone. That's the inverse of per-user fairness.
- They protect **memory**, not availability — the comments say so explicitly ("prevent memory exhaustion", `fileserver.go:45`).

**Practical implication:** authentication-endpoint brute-forcing, memo-creation floods, and webhook-registration abuse are all currently unthrottled at the application layer. If rate limiting is expected in this deployment, it must be supplied upstream (reverse proxy, CDN, or ingress) — nothing in the Go server provides it. The natural insertion point, if you wanted it in-process, is `server/server.go:51-52` for HTTP-wide coverage, or the Connect interceptor chain (`server/router/api/v1/connect_interceptors.go`) for per-RPC, per-identity limits since that layer already has the authenticated user.
