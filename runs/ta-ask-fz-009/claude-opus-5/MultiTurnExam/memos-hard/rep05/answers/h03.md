**`internal/idp` (`internal/idp/idp.go`) — the abstraction; `internal/idp/oauth2` (`internal/idp/oauth2/oauth2.go`) — the only concrete implementation (OAuth 2.0, with PKCE support).**

**A caveat on the word "abstraction."** `internal/idp` is deliberately thin — it defines exactly one type, the shared result shape `IdentityProviderUserInfo` (identifier, display name, email, avatar URL) at `internal/idp/idp.go:3-8`. There is **no Go interface** declaring an IdP contract. The abstraction is structural, not nominal: any provider is expected to offer `ExchangeToken` + `UserInfo` returning `*idp.IdentityProviderUserInfo`, but nothing in the type system enforces that, and callers reference the concrete `*oauth2.IdentityProvider` directly.

**What ships.** `internal/idp/oauth2` is the sole implementation — the directory holds only `oauth2.go` and its test (`internal/idp/oauth2/oauth2_test.go`). It implements:
- `NewIdentityProvider` with required-field validation on clientId/clientSecret/tokenUrl/userInfoUrl/fieldMapping.identifier (`oauth2.go:27-43`);
- `ExchangeToken`, the authorization-code exchange via `golang.org/x/oauth2`, passing `code_verifier` when present so PKCE flows work (`oauth2.go:47-80`);
- `UserInfo`, a bearer-token GET against the userinfo endpoint that maps raw JSON claims through the configured `FieldMapping` (`oauth2.go:83-142`).

**The type system agrees this is single-protocol.** The enum for provider type has exactly one real member — `IdentityProvider_OAUTH2` alongside `TYPE_UNSPECIFIED` (`proto/gen/store/idp.pb.go:26`, `proto/gen/api/v1/idp_service.pb.go:29`), and the config wrapper carries a single `Oauth2Config` variant (`proto/gen/store/idp.pb.go:214`). So no SAML/LDAP/OIDC-specific provider exists; OIDC providers are used by pointing the generic OAuth2 config at their endpoints.

Adding a second protocol would mean introducing a real interface plus a new enum variant and config oneof arm in `proto/store/idp.proto` — the current shape has no dispatch seam to plug into.
