**Extracted properties.** `RebuildMemoPayload` assigns exactly two fields — `memo.Payload.Tags` and `memo.Payload.Property` (`server/runner/memopayload/runner.go:85-86`) — from `ExtractAll`. The contract is in `proto/store/memo.proto:7-29`:

- **`tags`** — `#tag` occurrences, deduplicated case-preserving, and *excluding* tags nested inside links/images (`asMemoTagNode`, `internal/markdown/markdown.go:134-140`)
- **`property.title`** — text of the first H1, only if it's the document's first block-level child (`internal/markdown/markdown.go:384-389`)
- **`property.has_link`**, **`has_code`** (fenced/indented blocks *and* inline spans), **`has_task_list`**, **`has_incomplete_tasks`** (any unchecked box) — `internal/markdown/markdown.go:392-405`

**Two boundaries worth being precise about.** First, `ExtractAll` also returns `Mentions` (`internal/markdown/markdown.go:379-381`), but `RebuildMemoPayload` **does not persist them** — mentions are consumed elsewhere for notifications, not stored in the payload. Second, `Payload.Location` is *not* derived: it's user-supplied and written separately right after the rebuild (`memo_service.go:112`). Since `RebuildMemoPayload` mutates only `Tags` and `Property` on the existing payload rather than replacing it (`runner.go:75-77`), location survives recomputation — that ordering is load-bearing.

**The staleness risk is the `UpdateMemo` guard.** Recomputation is gated on `path == "content"` (`memo_service.go:446-451`). Any write path that changes content without that mask entry — or any change to the extraction rules themselves — leaves existing rows with stale tags and properties, and the one component built to repair that (`memopayload.Runner`) is no longer wired into startup. Backfilling today would require re-invoking it manually.
