**The key architectural point: there is no attachment/blob lookup on this path.** The avatar is not stored as a file — it lives in the `user.avatar_url` column as a base64 **data URI**, and `parseDataURI` (`fileserver.go:737-749`) decodes it in-process via `dataURIRegex` (`fileserver.go:98`) before `c.Blob` writes the bytes. So "stored data" here means a user row, not the `attachment` table. The `/file/...avatar` URL is a presentation convenience minted by the converter at `server/router/api/v1/user_service_converters.go:36` (`fmt.Sprintf("/file/%s/avatar", userpb.Name)`) precisely so API responses don't carry inline base64.

**Two details worth calling out:**

1. **This is an Echo route, not an RPC.** It's registered in `RegisterRoutes` (`fileserver.go:121-125`) on the `/file` group, so it bypasses the Connect/gRPC handler stack entirely. There *is* a separate `UserService/GetUserAvatar` RPC listed in the ACL allowlist (`server/router/api/v1/acl_config.go:25`), but the browser's `<img src>` hits the fileserver route.

2. **Authorization is instance-wide, not per-user.** `serveUserAvatar` only authenticates when `!s.Profile.AllowAnonymous()` (`fileserver.go:173-181`), calling `getCurrentUser` → `auth.Authenticator.AuthenticateToUser` (`server/auth/authenticator.go:190`). On a public instance any avatar is served to anonymous callers; on a private one *any* authenticated viewer may fetch *any* user's avatar. Unlike `serveAttachmentFile`, which calls `checkAttachmentPermission` (`fileserver.go:149`), there is no ownership check — deliberate for a profile image, but worth knowing it's the design.

The cache layer sits at `Store.GetUser`: the `userCache` short-circuit only fires when lookup is by `ID` (`store/user.go:149-156`). This request looks up by `Username`, so it always falls through to `ListUsers` → driver → SQL, then populates the cache on the way back (`store/user.go:142-144`, `:167`).
