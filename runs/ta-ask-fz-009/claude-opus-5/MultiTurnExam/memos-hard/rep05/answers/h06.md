**Two things worth noting about the shape of this graph.** First, `SetMemoAttachments` and `SetMemoRelations` are the non-obvious entries — they're not "memo edit" endpoints by name, but both route through the shared `dispatchMemoUpdatedSideEffects` helper (`server/router/api/v1/memo_update_helpers.go:66`), so attaching a file or linking two memos fires a `memos.memo.updated` webhook. Any new handler that calls that helper inherits outbound HTTP for free — that's the seam to watch.

Second, the funnel narrows in two stages. All six handlers converge first on `webhook.PostAsync` (`internal/webhook/webhook.go:184`) via one of the four `Dispatch*` methods in `server/router/api/v1/memo_service_webhooks.go:15-46`, which resolve the memo owner's registered webhooks through `Store.GetUserWebhooks` and stamp `payload.URL` / `SigningSecret` per hook (`:41-43`, `:67-68`). But `PostAsync` **only enqueues** onto a 128-slot channel and drops on overflow (`:189-195`) — it never touches the network. The single function where every path actually performs the outbound request is **`webhook.Post`**, run by one of four worker goroutines draining that queue (`internal/webhook/webhook.go:42-55`).

That distinction matters for your original question's phrasing: the user-configured URL is *selected* in `memo_service_webhooks.go`, but it is *dialed* only in `Post` — which is also why the SSRF guard lives on that one shared client's transport (`safeDialContext`, `internal/webhook/webhook.go:59`). One chokepoint, one place to enforce policy.
