**The actual mechanism: an in-process buffered Go channel**

Webhook delivery is asynchronous, but entirely inside the server process. Three pieces, all in `internal/webhook/webhook.go`:

1. **The "queue"** — a package-level buffered channel with a fixed capacity of 128:
   ```go
   asyncPostQueue = make(chan *WebhookRequestPayload, 128)   // internal/webhook/webhook.go:39
   ```
   Confirmed by the map as the sole symbol of that name (`internal/webhook/webhook.go:25`, the `var` block).

2. **The consumers** — four goroutines started in `init()`, each ranging over the channel and calling `Post`, logging failures rather than retrying:
   ```go
   for range 4 {
       go func() {
           for payload := range asyncPostQueue {
               if err := Post(payload); err != nil { slog.Warn(...) }
           }
       }()
   }   // internal/webhook/webhook.go:42-55
   ```

3. **The producer** — `PostAsync` (`:184`) does a non-blocking send with a `default` branch that **drops the payload** and logs a warning when the buffer is full (`:189-195`).

**Operational consequences worth being explicit about**

Because this is a channel and not a broker, the delivery pipeline has none of the durability properties a broker would give you:

- **No persistence** — a restart loses every queued webhook; nothing is written to disk or an external service.
- **Silent loss under load** — overflow past 128 is dropped, not backpressured (`:191-195`).
- **No retries or dead-letter path** — `Post` failures are logged at `Warn` and discarded (`:47-51`).
- **No cross-instance coordination** — each replica has its own channel and its own four workers.
- **Fixed concurrency** — worker count (4) and buffer (128) are hardcoded constants, not configuration.

The `init()`-based startup also means the workers exist for the lifetime of the process with no shutdown hook — the channel is never closed, so in-flight webhooks aren't drained on `Server.Shutdown` (`server/server.go:134`).
