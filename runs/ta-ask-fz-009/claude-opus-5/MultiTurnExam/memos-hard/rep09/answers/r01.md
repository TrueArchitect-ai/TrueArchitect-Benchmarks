**Premise correction: there is no Redis anywhere in this repository.** A case-insensitive search for `redis|go-redis|rueidis|memcach` across 1,042 files returns zero matches — no client library, no config key, no connection string, no dependency. There is nothing to point at.

**The actual mechanism: a hand-rolled in-process memory cache**

`store/cache/cache.go` implements the whole cache layer as a `sync.Map` behind a `Cache` struct (`:67-73`), with an atomic item counter and a background cleanup goroutine started in `New` (`:83`). No network, no serialization, no external process. Consequences worth noting: the cache is per-process, so a multi-replica deployment has N independent caches with no invalidation between them, and everything is lost on restart.

**The TTL for user entries: 10 minutes**

There is no user-specific TTL. The user cache is constructed with the same generic config as the other two, in `store.New` (`store/store.go:40-53`):

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
}
...
userCache: cache.New(cacheConfig),   // :52
```

The same `cacheConfig` value is shared by `instanceSettingCache`, `userCache`, and `userSettingCache` (`:51-53`). Note this literal duplicates `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) rather than calling it — same values, two places.

Every user write goes through `userCache.Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` applies `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). `SetWithTTL` exists (`:98`) but is never called for users — its only non-interface caller is a test (`store/cache/cache_test.go:26`). So **10 minutes** applies uniformly.

**Two eviction details beyond TTL**

Expiry is lazy plus swept: `Get` deletes on read if expired (`:135-144`), and `cleanupLoop` sweeps every 5 minutes (`:200-215`). Independently, exceeding `MaxItems: 1000` triggers `cleanupOldest`, which drops ~20% of capacity (`:253-255`) — so a user entry can be evicted well before 10 minutes under cache pressure.

Cache keys are just the stringified user ID (`store/user.go:88-90`), which is why `GetUser` only consults the cache when looking up by ID and always misses on username lookups (`store/user.go:149-156`). Invalidation on delete happens via `deleteUserCache` (`store/user_delete.go:40`), and all three caches are closed during shutdown (`store/store.go:74-76`).
