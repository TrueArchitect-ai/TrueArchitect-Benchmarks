### What actually guards the request path
Per-request enforcement is authentication and authorization only, not volume:
- The shared `authorizer` used by both the gRPC-Gateway middleware and the Connect interceptor (`server/router/api/v1/v1.go:68`), with an anonymous-access allowlist at `server/router/api/v1/acl_config.go`.
- Visibility checks per surface, as covered earlier (`checkMemoReadAccess`, `checkAttachmentPermission`, etc.).

The closest things to throttling are **concurrency** limits, not rate limits — semaphores bounding simultaneous work rather than requests over time:
- `thumbnailSemaphore: semaphore.NewWeighted(3)` and `imageProcessingSemaphore: semaphore.NewWeighted(2)` (`server/router/api/v1/v1.go:59-60`)
- the 128-slot webhook dispatch queue with 4 workers (`internal/webhook/webhook.go:39`, `42-55`)

These cap resource contention; a single user can still issue unlimited API calls.

### Practical implication
If you need per-user rate limiting, it doesn't exist to be tuned — it has to be built. The natural insertion points are the Echo chain at `server/server.go:51` (for all HTTP surfaces including `/file` and RSS) or the Connect interceptor / gateway middleware at `server/router/api/v1/v1.go:68` (for the API only, where the authenticated user identity is already resolved).
