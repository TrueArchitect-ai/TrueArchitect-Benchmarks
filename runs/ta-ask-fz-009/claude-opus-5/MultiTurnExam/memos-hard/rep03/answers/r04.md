### The actual mechanism
The "queue" is one line — `internal/webhook/webhook.go:39`:
```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```
A package-level Go channel with a 128-item buffer, holding in-memory pointers. Around it:

- **Workers:** four goroutines started in `init()` (`internal/webhook/webhook.go:42-55`), each ranging over the channel (line 45) and calling `Post` (line 46). Fixed at four, spun up on package load — not configurable, not supervised.
- **Producer:** `PostAsync` (line 184) does a **non-blocking** send via `select` with a `default` branch (lines 189-195). When the buffer is full the payload is **dropped** with a `slog.Warn`, never retried.
- **Delivery:** `Post` (line 120) issues the HTTP request through `safeClient.Do` (line 152).

### Why the distinction matters architecturally
Calling this a broker would imply guarantees it does not provide:
- **No durability.** The buffer is process memory. A restart or crash silently loses up to 128 pending webhooks — no persistence, no replay.
- **No retries or DLQ.** A failed delivery is logged (lines 47-51) and discarded. Consumers get at-most-once delivery, not at-least-once.
- **No backpressure.** Producers never block; overflow is data loss by design (line 191).
- **No cross-instance coordination.** Each server process owns its own channel and workers, so nothing is shared or load-balanced across replicas.

If you need durable, retryable webhook delivery, the insertion point is `PostAsync` (`internal/webhook/webhook.go:184`) — it's the single producer, and all six triggering RPC handlers funnel through it.
