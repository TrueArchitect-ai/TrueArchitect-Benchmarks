**Premise correction: there is no Redis. The cache layer is a hand-rolled in-process, in-memory cache — nothing to connect to. User entries get a 10-minute TTL.**

### There is no Redis anywhere in this repository
Grepping `(?i)redis` across **1042 files** returns zero matches — no client library, no config key, no DSN, no Docker service. `list_dependencies` isn't needed to confirm it; the pattern would have hit `go.mod`/`go.sum` if a Redis driver were vendored. So the question's premise — a Redis connection to locate — has no referent. There's no host, port, pool, or auth config to point you at.

### The actual mechanism
`store/cache/cache.go` implements a self-contained cache: `Cache` (line 67) holds a `sync.Map` plus an atomic item counter (lines 68-73). `New` (line 76) spawns a `cleanupLoop` goroutine (line 83) — that goroutine is the only "background infrastructure," and it's the reason `Close` exists (line 187) to stop it.

It's **per-process and non-shared**, which is the architecturally significant difference from Redis: run two Memos instances and each keeps its own copy, with no cross-instance invalidation. Eviction is TTL-based sweeping (`cleanup`, line 218) plus a rough size cap (`cleanupOldest`, line 253, dropping ~20% when over `MaxItems`).

### The TTL on user entries
**10 minutes.** The config is built inline in the store constructor at `store/store.go:40-45`:
```go
DefaultTTL:      10 * time.Minute
CleanupInterval: 5 * time.Minute
MaxItems:        1000
```
That single `cacheConfig` value is handed to all three caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`) — so users have no distinct TTL from the others.

The 10 minutes applies because writes go through `Set`, which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). `Store.ListUsers` caches users via plain `Set` (`store/user.go:143`), never `SetWithTTL` — grep confirms `SetWithTTL` has no production caller outside the cache package and its own test. The same default is duplicated in `DefaultConfig()` (`store/cache/cache.go:57-64`), but that constructor isn't what the store uses.

### One practical caveat
Expiry is lazily enforced on read too: `Get` checks `time.Now().After(itm.expiration)` and deletes on the spot (`store/cache/cache.go:135-144`), so a stale user entry is never returned even if the 5-minute sweep hasn't run yet. And as noted earlier, `Store.GetUser` only consults `userCache` when looking up by ID (`store/user.go:149-156`) — username lookups bypass the cache entirely, so the TTL never comes into play for those.
