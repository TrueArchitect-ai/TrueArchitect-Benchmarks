It's `internal/idp/` (not `plugin/idp/`). Reading the abstraction and checking what else ships alongside oauth2.

h03.

**`internal/idp` — `internal/idp/idp.go`; `internal/idp/oauth2` — `internal/idp/oauth2/oauth2.go`**

### The abstraction is a shared data type, not an interface
Worth being precise here, because the word "abstraction" suggests a Go `interface` and there isn't one. `internal/idp/idp.go` is 9 lines and defines exactly one thing: `IdentityProviderUserInfo` (line 3) with `Identifier`, `DisplayName`, `Email`, `AvatarURL`. That struct is the entire contract — the normalized shape every provider must produce. There is no `Provider` interface declaring `ExchangeToken`/`UserInfo`, so callers depend on the concrete `*oauth2.IdentityProvider` type directly.

### OAuth2 is the only implementation
`internal/idp/oauth2/oauth2.go` — package doc at line 1, `IdentityProvider` struct at line 20 wrapping a `*storepb.OAuth2Config`. The directory holds only `idp.go` and `oauth2/`, so no SAML, LDAP, or OIDC-specific package ships. The proto enums agree: `store.IdentityProvider_Type` has just `TYPE_UNSPECIFIED` and `OAUTH2` (`proto/gen/store/idp.pb.go:26`), mirrored on the API side at `proto/gen/api/v1/idp_service.pb.go:29`, and `IdentityProviderConfig` carries a single `Oauth2Config` variant (`proto/gen/store/idp.pb.go:214`).

Note that OIDC providers are still usable — they're configured *as* OAuth2 entries, since the implementation reads claims generically from the userinfo endpoint rather than doing OIDC discovery or ID-token validation.

### What the implementation does
- `NewIdentityProvider` (line 27) validates five required config fields up front — `clientId`, `clientSecret`, `tokenUrl`, `userInfoUrl`, `fieldMapping.identifier`.
- `ExchangeToken` (line 47) uses `golang.org/x/oauth2` with `AuthStyleAutoDetect`, and supports **PKCE** by passing `code_verifier` when supplied (lines 64-66).
- `UserInfo` (line 83) does a bearer-token GET, then maps arbitrary JSON claims onto the shared struct via the configured `FieldMapping` (lines 115-140). `Identifier` is mandatory and errors if absent (line 118); `DisplayName` falls back to the identifier (line 128); email and avatar are best-effort. Error bodies are read through `io.LimitReader(..., 4096)` (line 98) and the client carries a 10-second timeout (lines 24, 84).

One asymmetry: unlike the webhook path, this outbound userinfo call has no SSRF guard on `UserInfoUrl` — it uses a plain `http.Client`.
