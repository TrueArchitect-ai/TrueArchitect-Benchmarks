**Explicit Go code — two DELETE statements per driver inside the `DeleteUser` transaction; there is no FK/cascade on `reaction`.**

What I checked:

**1. The explicit deletes.** All three drivers run the same orchestration in `deleteUserTargetsTx`, which fires two distinct reaction deletes:
- `deleteReactionsByContentIDsTx` — removes reactions *on* the user's memos (and their comment subtree), keyed by `content_id IN (...)`: `store/db/sqlite/user_delete.go:380`, `store/db/mysql/user_delete.go:417`, `store/db/postgres/user_delete.go:380`.
- `deleteReactionsByCreatorTx` — removes reactions the user *left on other people's* memos, keyed by `creator_id`: `store/db/sqlite/user_delete.go:400`, `store/db/mysql/user_delete.go:437`, `store/db/postgres/user_delete.go:400`.

Both are invoked from `deleteUserTargetsTx` at lines 96 and 102 in each of the three files, inside the single transaction opened by `DeleteUser` (`store/db/sqlite/user_delete.go:29-59` and the mysql/postgres equivalents). The `content_id` values are synthesized as `"memos/"+uid` by `memoContentIDsFromRefs` (e.g. `store/db/sqlite/user_delete.go:512`) — reactions are joined to memos by that string key, not by an integer FK.

**2. Why the DB can't do it.** The `reaction` table carries no foreign key at all — only a uniqueness constraint:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/mysql/LATEST.sql:91-98`
- `store/migration/postgres/LATEST.sql:91-97`
- original DDL: `store/migration/{mysql,postgres}/0.20/00__reaction.sql`

A repo-wide scan for `FOREIGN KEY|REFERENCES|ON DELETE` across all `.sql` files returns cascades only for `memo_share → memo` (`store/migration/*/0.27/04__memo_share.sql:11`, `*/LATEST.sql:108`) and legacy SQLite-only tables in `0.3`–`0.5` migrations — never `reaction`.

**Consequence:** because `reaction.content_id` is a string reference with no FK, this cleanup is an application-level invariant. Ordering matters and the code respects it — reactions are deleted *before* `deleteMemosTx` (line 120 in each file) — but the guarantee lives in Go, not in the schema, so any other path that removes memos or users without going through `DeleteUser` would orphan reaction rows.
