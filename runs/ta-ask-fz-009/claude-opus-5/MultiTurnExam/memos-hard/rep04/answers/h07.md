The avatar is **not** served by an RPC — it's a dedicated Echo file route. Hops from browser to stored data:

```
FileServerService.RegisterRoutes (GET /file/users/:identifier/avatar) — server/router/fileserver/fileserver.go:124
FileServerService.serveUserAvatar — server/router/fileserver/fileserver.go:168
FileServerService.getCurrentUser → authenticator.AuthenticateToUser — server/router/fileserver/fileserver.go:708-711  (gate only)
FileServerService.getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
driver.ListUsers (store.Driver) — store/user.go:137
DB.ListUsers (per-dialect SQL) — store/db/sqlite/user.go:88 (also store/db/mysql/user.go, store/db/postgres/user.go)
```

Then back out: `parseDataURI(user.AvatarURL)` decodes the base64 payload (`fileserver.go:196`), the MIME type is checked against `avatarAllowedTypes` (`fileserver.go:201`, allowlist at `:75-83`), and bytes go out via `c.Blob` (`fileserver.go:209`).

Notes that matter for the trace:

- **How the browser learns the URL**: the avatar is stored inline as a base64 data URI in `user.avatar_url`. `convertUserFromStore` detects that and rewrites the API-visible field to `/file/{user.name}/avatar` so responses don't carry the image bytes (`server/router/api/v1/user_service_converters.go:32-39`). Non-data-URI values pass through unchanged, in which case the browser never hits this route.
- **There is no blob storage hop** — the image lives in the `user` row itself, which is why the path ends at `ListUsers` rather than in the attachment/S3 machinery used by `serveAttachmentFile` (`fileserver.go:132`).
- **Access control on "another user's" avatar**: the only check is instance-level. If `Profile.AllowAnonymous()` is false, a valid session/access token/PAT is required; otherwise the route is open (`fileserver.go:173-181`). There is no per-user authorization comparing viewer to target — any authenticated viewer (or anyone, on a public instance) can fetch any username's avatar.
- **Caching layer**: `Store.GetUser` only consults `userCache` when the lookup is by ID (`store/user.go:149-156`); this path looks up by username, so it always falls through to `ListUsers` and the SQL driver, then populates the cache (`store/user.go:167`).
- **Wiring**: the service is constructed and its routes registered at `server/server.go:81-82`.
