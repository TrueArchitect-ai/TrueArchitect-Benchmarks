**Premise correction: there is no per-user API rate-limiting middleware in this codebase — nothing to register, and no limits to report.**

Evidence:

- **Certified miss from the code graph**: `[ArchMap query]` probed all 7,293 symbols across exact, prefix, substring, qualified-name, abbreviation, and doc-text tiers and found nothing.
- **Text search agrees**: a case-insensitive scan for `rate.?limit|ratelimit|throttl|golang.org/x/time/rate|limiter` across the repo returns no production code. The only hits are documentation *suggesting* rate limiting as future work — `internal/email/README.md:286-295` sketches a `rate.NewLimiter(rate.Every(time.Second), 10)` example for email sending, and `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a recommendation. Neither is implemented. The remaining matches are frontend markdown-editor `delimiter` variables, unrelated.
- **The middleware/interceptor chain contains no such stage.** What actually wraps requests:
  - Echo HTTP middleware: CORS only — `newCORSMiddleware`, `server/cors.go:13`.
  - Connect RPC interceptors: `MetadataInterceptor` (header→gRPC metadata, `server/router/api/v1/connect_interceptors.go:22`), `LoggingInterceptor` (`:98`), `RecoveryInterceptor` (panic recovery, `:165`). That's the full set.

What does exist, and may be what you're thinking of, are non-rate-based resource guards:

- **Concurrency semaphores**, not request-rate limits: `thumbnailSemaphore`/`imageProcessingSemaphore` on `APIV1Service` (`server/router/api/v1/v1.go:40-41`, constructed with weight 3 at `:59`) and the file server's `thumbnailSemaphore` (`server/router/fileserver/fileserver.go:107`, `maxConcurrentThumbnails = 3` at `:46`). These cap simultaneous in-flight work globally, not requests per user per interval.
- **A bounded webhook dispatch queue** — 128 slots, 4 workers, overflow dropped (`internal/webhook/webhook.go:39-55`).
- **Per-request content size limits** — e.g. memo content length checked against an instance setting (`server/router/api/v1/memo_service.go:105`).

If you want per-user rate limiting, it would be a new Connect interceptor alongside those in `server/router/api/v1/connect_interceptors.go`, registered where the existing three are wired — that's the natural seam, since the interceptor already has authenticated context available.
