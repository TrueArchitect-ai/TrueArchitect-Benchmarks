**Premise correction: there is no Redis anywhere in this repository.** A case-insensitive search for `redis` across 1,042 files returns zero matches — no client dependency, no config key, no connection code. The cache layer is a hand-rolled, in-process, in-memory cache with no external store and therefore nothing to configure a connection to.

**Actual mechanism:**

- **Implementation** — `store/cache/cache.go`: a `Cache` struct backed by `sync.Map` plus an atomic item counter (`store/cache/cache.go:67-73`), satisfying the `cache.Interface` contract at `:11-32`. Purely process-local; it dies with the process and is not shared across instances.
- **"Configuration"** is a Go struct literal, not connection settings — `cache.Config{DefaultTTL, CleanupInterval, MaxItems, OnEviction}` (`store/cache/cache.go:42-54`), with `DefaultConfig()` returning **TTL 10 minutes, cleanup every 5 minutes, max 1000 items** (`store/cache/cache.go:57-64`).
- **Wiring** — `store/store.go:51-53` constructs three independent caches (`instanceSettingCache`, `userCache`, `userSettingCache`) from one shared `cacheConfig`; they're torn down in `Store.Close` (`store/store.go:74-76`).

**TTL for user entries specifically:** whatever `cacheConfig` carries at `store/store.go:51-53` — every `userCache.Set` call goes through `Cache.Set`, which applies `c.config.DefaultTTL` unconditionally (`store/cache/cache.go:93-95`). No user-entry call site uses `SetWithTTL`: the writes at `store/user.go:98,122,132,143,167` are all plain `Set`. If `cacheConfig` is `DefaultConfig()`, that's **10 minutes**, with expiry enforced lazily on read (`cache.go:135-144`) and by a 5-minute sweeper goroutine (`cache.go:200-215`). I'd confirm the exact `cacheConfig` value at `store/store.go` around line 45-51 if the precise number matters — I read lines 51-53 via search context but not the literal's definition.

Two behavioral notes that a Redis mental model would get wrong:
- **Invalidation is explicit, not TTL-driven** — user deletion purges entries directly (`store/user_delete.go:40,45`), because a 10-minute stale window on a deleted user would be a correctness problem.
- **Cache reads are keyed by ID only** — `Store.GetUser` consults `userCache` solely when `find.ID != nil` (`store/user.go:149-156`); username lookups always hit the database.
