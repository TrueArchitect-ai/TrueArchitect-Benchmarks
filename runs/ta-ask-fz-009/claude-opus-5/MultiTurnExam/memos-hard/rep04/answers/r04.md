**Premise correction: neither. There is no message broker in this system — no NATS, no RabbitMQ, no Kafka, no AMQP client of any kind, and therefore no queue declaration.** A case-insensitive search for `nats|rabbitmq|amqp|kafka|streadway|pubsub` across the repo returns zero Go matches (only unrelated Google API doc comments in generated frontend types and a Catalan locale string), and `go.mod` contains no broker dependency.

**Actual mechanism — an in-process Go channel:**

- **The "queue"** is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  128 slots, holding pointers to payload structs — not serialized messages.
- **The "workers"** are 4 goroutines spawned in the package `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `webhook.Post` (`:46`), logging a warning on failure (`:47-50`).
- **The "producer"** is `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking send: on a full queue it takes the `default` branch and **drops the event** with a warning (`:191-195`). Callers are the memo-lifecycle and comment dispatchers in `server/router/api/v1/memo_service_webhooks.go:43,71`.

Consequences worth being explicit about, since broker semantics don't apply:

- **No durability** — the queue lives in process memory. A restart or crash loses everything in flight; there's no persistence, no redelivery.
- **No retries and no dead-letter path** — `Post` failures are logged and discarded (`webhook.go:46-51`). Delivery is at-most-once.
- **No backpressure** — overflow is silent loss rather than blocking or spooling.
- **No cross-instance fan-out** — workers are per-process, so a multi-replica deployment has independent 128-slot queues with no coordination.
- **Concurrency is fixed at 4**, hardcoded by `for range 4` (`webhook.go:43`), not configurable.

If you're looking for the delivery path itself, that's `webhook.Post` at `internal/webhook/webhook.go:120`, executing through the SSRF-guarded `safeClient` (`:152`).
