### Actual mechanism: an in-process buffered Go channel

The "queue" is a package-level variable, declared at **`internal/webhook/webhook.go:39`**:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

A buffered channel with capacity 128, holding `*WebhookRequestPayload` values directly — no serialization, no wire protocol, no network.

**The workers** are 4 goroutines started in `init()` (`internal/webhook/webhook.go:42–55`), each ranging over the channel and calling `Post` (line 46), logging failures with `slog.Warn` (lines 47–50). They begin at package initialization, not from server startup wiring.

**Producers** call `PostAsync` (`internal/webhook/webhook.go:184`), which is a non-blocking `select` with a `default` arm (lines 189–195): if the buffer is full, the event is **dropped** with a warning rather than queued or retried.

### Consequences of channel-not-broker

This distinction matters operationally, and the differences are all visible in the code:

- **No durability.** The queue lives in process memory. A crash or restart loses every buffered payload — there is no persistence and no redelivery.
- **No retries or DLQ.** A failed `Post` is logged once (line 47) and discarded. Delivery is at-most-once, not at-least-once.
- **Lossy under pressure.** The `default` branch at line 191 sheds load silently past 128 queued items.
- **No cross-instance fan-out.** Each server process has its own channel and its own 4 workers; nothing is shared between replicas.
- **Failures are invisible to callers.** Because the channel severs the static call chain, `webhook.Post` has no caller reachable from any RPC handler — `[ArchMap query]` returns a certified zero (established in h06). The RPC returns success regardless of delivery outcome.

So the design is a lightweight in-process work queue chosen to keep the deployment single-binary — consistent with the rest of the architecture (the in-memory cache in place of Redis per r01, interval runners in place of cron per r03).
