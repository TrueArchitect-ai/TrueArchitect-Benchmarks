### The distinct enforcement patterns

These 11 sites fall into three architecturally different kinds of enforcement:

**Post-fetch gate on a single memo** — fetch, then authorize. `checkMemoReadAccess` (`memo_service.go:39–67`) is the canonical one: archived memos are creator-only (lines 45–52), non-public requires authentication (lines 55–62), private requires ownership (line 63). Note the deliberate error asymmetry — archived leaks `NotFound`, private leaks `PermissionDenied`.

**Query-level scoping** — visibility never leaves the database. `ListMemos` sets `VisibilityList = [PUBLIC]` for anonymous callers (`memo_service.go:219`), and for authenticated callers either injects the CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` (line 222) or restricts to `[PUBLIC, PROTECTED]` when browsing another user (line 225). RSS does the same, hard-pinning `[PUBLIC]` on both the instance feed (`rss.go:90`) and per-user feed (`rss.go:141`).

**Fan-out filtering** — `SSEClient.canReceive` (`sse_hub.go:134–144`) decides per subscriber whether a broadcast event is deliverable: private events reach only the creator or an admin (line 137), public/protected reach everyone (line 138). Its `default` branch denies unknown visibility values with a warning (lines 140–142) — fail-closed, unlike the read gate.

### Duplicated predicate — worth flagging

`canViewerAccessMemo` is **declared twice with the same name and semantics** in different packages: `server/notification/email.go:306` and `server/router/api/v1/user_service_notifications.go:302`. Both implement admin-bypass → private-requires-owner → protected-requires-any-user → else allow. That's a copy of the same invariant in two packages, so a policy change must be applied twice.

### Divergence between surfaces

The rules are not uniform, and the differences matter:
- `checkMemoReadAccess` (`memo_service.go:63`) does **not** grant admins access to private memos; `canViewerAccessMemo` (`email.go:310`) and `canReceive` (`sse_hub.go:137`) both do.
- `PROTECTED` means "any authenticated user" in the notification and SSE paths, but the read gate reaches the same outcome only implicitly, by falling through the private check.

So visibility is enforced consistently enough to be safe, but it is an invariant replicated across surfaces rather than centralized in one policy object.
