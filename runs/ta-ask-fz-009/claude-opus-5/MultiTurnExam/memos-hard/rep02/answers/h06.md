### The URL is genuinely user-configured

In both dispatchers the target comes straight off the stored per-user webhook row: `payload.URL = hook.Url` from `s.Store.GetUserWebhooks(...)` — `server/router/api/v1/memo_service_webhooks.go:57,67` for the memo path and `:31,41` for the comment path. Each dispatcher loops over *all* of the owner's registered hooks, so one RPC can fan out to N outbound requests.

Ownership differs subtly between the two: `dispatchMemoRelatedWebhook` resolves the memo's own creator (`:49–57`), while `DispatchMemoCommentCreatedWebhook` takes `relatedMemoCreatorID` — the *parent* memo's owner (`:31`). So commenting triggers delivery to someone else's configured endpoint.

### Convergence, and why the graph stops there

All six handler paths funnel into a single call: `webhook.PostAsync(payload)` — `server/router/api/v1/memo_service_webhooks.go:71` (memo events) and `:43` (comments).

`PostAsync` (`internal/webhook/webhook.go:184`) does not perform the request. It enqueues onto `asyncPostQueue`, a 128-slot buffered channel (`internal/webhook/webhook.go:39`), drained by four goroutines started in `init()` (`internal/webhook/webhook.go:42–55`) which call `Post`. `Post` (`:120`) is where the HTTP request is issued, at `safeClient.Do(req)` (`:152`).

This queue is worth flagging as a real architectural boundary, not a detail: `[ArchMap query]` returned a **certified zero** — no call path exists within depth 6. That is correct, not a gap. The channel handoff severs the static call chain, so `Post` has no caller reachable from any handler. Two consequences: delivery failures never surface to the RPC caller (workers only log, `:47–51`), and a full queue silently drops the event (`:191–195`).
