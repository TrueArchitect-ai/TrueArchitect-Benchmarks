### What does exist (adjacent, but not rate limiting)

Several **concurrency and size** bounds guard resource exhaustion, which is a different control than request-rate limiting:
- `thumbnailSemaphore: semaphore.NewWeighted(3)` and `imageProcessingSemaphore: semaphore.NewWeighted(2)` (`server/router/api/v1/v1.go:59–60`) — cap simultaneous work, not requests per user.
- Webhook dispatch uses a 128-slot queue with 4 workers (`internal/webhook/webhook.go:39–55`), dropping on overflow — outbound, and per-process rather than per-user.
- A content-length limit on memos (`server/router/api/v1/memo_service.go:443`).

If you need per-user rate limiting, it would be a new component. The natural insertion points given the existing architecture are a Connect interceptor alongside `NewMetadataInterceptor` (`server/router/api/v1/v1.go:133`) — that interceptor already resolves auth metadata, so user identity is available there — or an Echo middleware at `server/server.go:52` for the file-serving and RSS surfaces, which bypass the Connect chain entirely.
