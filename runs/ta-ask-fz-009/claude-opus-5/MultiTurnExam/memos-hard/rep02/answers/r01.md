**Premise correction: there is no Redis in this codebase.** A case-insensitive search for `redis` across 1042 files returns zero matches — no client library, no connection config, no dependency. The cache layer is a hand-rolled, in-process, in-memory cache. There is no external cache server to configure, and consequently no network connection, no serialization, and no cross-instance sharing.

### Actual mechanism

`store/cache/cache.go` implements `Cache` (line 67) over a `sync.Map` (line 69) plus an `atomic.Int64` item counter (line 68). It's process-local: restart the server and the cache is empty; run two instances and they hold independent caches with no invalidation between them.

**Configuration** is a plain struct, not connection settings — `cache.Config` (`store/cache/cache.go:42–54`) carries `DefaultTTL`, `CleanupInterval`, `MaxItems`, and an optional `OnEviction` callback.

`DefaultConfig()` (`store/cache/cache.go:57–64`):
- `DefaultTTL: 10 * time.Minute`
- `CleanupInterval: 5 * time.Minute`
- `MaxItems: 1000`

### TTL on user entries

**10 minutes.** The store creates three caches from one shared `cacheConfig` (`store/store.go:51–53`) — `instanceSettingCache`, `userCache`, `userSettingCache` — so the user cache has no distinct TTL of its own; it inherits the same `DefaultTTL`.

Every write to the user cache goes through `Set`, never `SetWithTTL`: `store/user.go:98`, `:122`, `:132`, `:143`, `:167`. `Set` forwards `c.config.DefaultTTL` (`store/cache/cache.go:94`), so user entries expire 10 minutes after write (`expiration: time.Now().Add(ttl)`, line 112). `SetWithTTL` exists on the interface (`cache.go:16`) but is only exercised in tests (`store/cache/cache_test.go:26`) — nothing in the store overrides the default.

### Two eviction paths beyond TTL

- **Lazy + periodic expiry**: `Get` deletes on read if expired (`cache.go:135–144`); a `cleanupLoop` goroutine sweeps every 5 minutes (`cache.go:200–215`, sweep at `:218`).
- **Capacity pressure**: exceeding `MaxItems` triggers `cleanupOldest` (`cache.go:117–119`), which drops ~20% of capacity (`threshold := max(c.config.MaxItems/5, 1)`, line 255). With `MaxItems: 1000` shared per-cache, a busy instance can evict users well before 10 minutes.

Explicit invalidation exists on delete: `s.userCache.Delete(...)` in `store/user_delete.go:40`.

### One caveat worth noting

User entries are keyed by ID via `userCacheKey` (`store/user.go:88`), and `Store.GetUser` consults the cache **only when `find.ID != nil`** (`store/user.go:149–150`). Lookups by username fall through to the database every time — the same behavior that makes the avatar path (h07) uncached.
