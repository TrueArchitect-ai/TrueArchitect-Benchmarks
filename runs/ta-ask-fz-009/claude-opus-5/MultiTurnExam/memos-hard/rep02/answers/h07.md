### How the browser gets that URL

The client never sees the stored avatar bytes in the user JSON. `convertUserToProto` rewrites the field: when `user.AvatarURL` holds base64 data, it substitutes the path `/file/%s/avatar` (`server/router/api/v1/user_service_converters.go:32–36`), explicitly "to reduce the response size." So the browser receives a URL and issues a second GET.

### Hop detail

**Route** — registered on the `/file` group as `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` (`fileserver.go:122–124`). Note the real path segment is `/users/`, while the converter emits `/file/{userpb.Name}/avatar` where `Name` is already the `users/{id}` resource name — the two compose to the same shape.

**Handler** (`fileserver.go:168–210`) does four things in order:
- Anonymous gate: if `!s.Profile.AllowAnonymous()`, requires a viewer via `getCurrentUser` (`:173–181`), which delegates to `s.authenticator.AuthenticateToUser` with the Authorization and Cookie headers (`:708–711`). On a public instance this check is skipped entirely.
- Lookup by the `identifier` path param (`:183–191`).
- Decodes the stored value with `parseDataURI` (`:196`, defined `:737`) — confirming the avatar is stored **as a data URI in the user row**, not as a file on disk or in S3.
- Re-validates the decoded MIME against `avatarAllowedTypes` (`:75–79`, checked `:201`) before `c.Blob` (`:209`), with `setSecurityHeaders` and a 1-hour `cacheMaxAge` (`:205–207`).

**Data layer** — `getUserByUsername` builds `&store.FindUser{Username: &identifier}` (`:716`). Inside `Store.GetUser` (`store/user.go:148`) the cache is consulted **only when `find.ID != nil`** (`:149–150`); a username-keyed find always falls through to `ListUsers` (`:136`), which calls `s.driver.ListUsers` (`:137`) and populates the cache by ID on the way back (`:143`).

That is the notable property of this path: avatar requests are keyed by username, so they miss the user cache by construction and hit the database on every request. The 1-hour `Cache-Control` on the response is what actually absorbs the load, at the HTTP layer rather than the store layer.

**Driver boundary** — `store.Driver.ListUsers` (`store/driver.go:47`) is an interface; the concrete implementation is selected once by `db.NewDBDriver` (`store/db/db.go:14`), so the final SQL hop lands in `store/db/mysql/user.go`, `store/db/postgres/user.go`, or `store/db/sqlite/user.go` depending on configuration.
