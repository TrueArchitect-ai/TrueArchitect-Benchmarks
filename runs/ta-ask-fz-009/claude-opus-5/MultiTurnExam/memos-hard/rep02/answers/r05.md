### Actual API surface: Protobuf/gRPC with three transports

The contract is defined in **`.proto` files under `proto/api/v1/`** — e.g. `proto/api/v1/memo_service.proto`, `user_service.proto`, `auth_service.proto`, `idp_service.proto`, `attachment_service.proto`, `instance_service.proto`, `shortcut_service.proto`, `ai_service.proto`. Generated Go lands in `proto/gen/api/v1/`, generated TypeScript in `web/src/types/proto/`.

**81 HTTP doors** total, in four groups:

**1. gRPC-Gateway REST — 76 endpoints under `/api/v1`**, AIP-style resource paths. Route tables live in the generated `*.pb.gw.go` files:

Examples: `GET /api/v1/memos`, `POST /api/v1/memos`, `PATCH /api/v1/{memo.name=memos/*}`, `GET /api/v1/auth/me`.

**2. Connect-RPC** for browser clients — registered with interceptors at `server/router/api/v1/v1.go:133–136`, handlers in `server/router/api/v1/connect_services.go`. This is the transport the web frontend actually uses (replacing grpc-web), speaking the same proto services.

**3. Server-Sent Events** — `GET /api/v1/sse` (`server/router/api/v1/sse_handler.go:25`) for live updates. GraphQL subscriptions' rough equivalent here.

**4. Plain HTTP surfaces** outside the proto contract, registered on Echo:

- `GET /explore/rss.xml`, `GET /u/:username/rss.xml` (`server/router/rss/rss.go:72`, `:111`)
- `GET /robots.txt`, `GET /sitemap.xml` (`server/router/frontend/frontend.go:128`, `:143`)
- `GET /healthz` (`server/server.go:44`)

### The architectural difference worth noting

Where GraphQL centralizes a schema and lets clients shape queries, this API is resource-oriented and server-shaped: field selection happens via protobuf field masks (visible in the `UpdateMemo` mask loop at `server/router/api/v1/memo_service.go:446–472`), and filtering via CEL expressions passed as a `filter` string (`server/router/api/v1/memo_service.go:211–215`). That CEL filter, compiled by `internal/filter`, is the closest analogue to a GraphQL query language in this system.
