**The Go path (all three dialects, identical structure).** User deletion runs inside one transaction, and `deleteUserTargetsTx` issues *two distinct* reaction deletes:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *others* left on the deleted user's memos (`store/db/sqlite/user_delete.go:96`, impl at `:380-383`).

Both passes are needed because the two directions aren't reachable from each other. Mirrored at `store/db/mysql/user_delete.go:96,102` (impls `:417`, `:437`) and `store/db/postgres/user_delete.go:96,102` (impls `:380`, `:400`).

**Why the DB can't do it — the schema evidence.** The `reaction` table declares only `UNIQUE(creator_id, content_id, reaction_type)`; `creator_id INTEGER NOT NULL` and `content_id` carry **no foreign key and no `ON DELETE` clause** in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`. A repo-wide search for `FOREIGN KEY|ON DELETE|REFERENCES|CREATE TRIGGER` across all migration SQL returns cascades for other tables — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:108`), plus legacy 0.3–0.5 user cascades — but **never for `reaction`**. Note also that `content_id` is a text handle, not an integer memo FK, so it couldn't cascade even in principle.

**Ordering matters and is correct.** Reactions are deleted *before* the memos (`:120`) and the user row (`:123`). Since nothing enforces referential integrity here, wrong ordering wouldn't error — it would silently orphan rows. The explicit code is load-bearing, not belt-and-braces.
