**Premise correction: neither. There is no message broker in this codebase, and no queue is declared anywhere.**

**Evidence.** A case-insensitive search for `nats|rabbitmq|amqp|kafka|streadway|nats-io|pubsub|sqs` across the repo returns **zero substantive hits** — the only matches are coincidental: a Catalan locale string containing "correctament" (`web/src/locales/ca.json:326`), a `xxhash` line in `go.sum:63`, and Google API proto comments mentioning Cloud Pub/Sub in generated frontend types (`web/src/types/proto/google/api/client_pb.ts:246`). Corroborating from the manifest: all 142 `go.mod` dependencies are accounted for and **none** is a broker client — no `nats-io/nats.go`, no `rabbitmq/amqp091-go`, no `segmentio/kafka-go`, no `aws-sdk-go-v2/service/sqs` (the AWS deps present are S3, STS, SSO, and IMDS only).

**Actual mechanism: an in-process buffered Go channel.** The "workers" are real, but they consume from memory, not a broker:

- **The queue** is declared as a package-level buffered channel with **128 slots** — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` at `internal/webhook/webhook.go:39`. That line is the closest thing to a "queue declaration."
- **The workers** are **4 goroutines** started in `init()` (`internal/webhook/webhook.go:42-55`), each ranging over the channel and calling `Post` for every payload, logging failures with `slog.Warn` (`:47-51`).
- **The producer** is `PostAsync` (`:184`), which does a non-blocking `select` send and, on a full queue, **drops the event** with a warning rather than blocking the RPC handler (`:189-195`).
- **Delivery** happens in `Post` (`:120`), which signs the payload and executes `safeClient.Do` (`:152`).

**Consequences of this design that a broker would change.** Because the queue is in-process memory:
- events are **lost on restart or crash** — nothing is persisted;
- there are **no retries and no dead-letter path** — a failed `Post` is logged once and discarded;
- overflow is **silently lossy** at 128 in-flight payloads;
- delivery is **not shared across instances** — each server process has its own channel and its own 4 workers, so a horizontally scaled deployment has no coordinated delivery or de-duplication.

The at-most-once semantics here are a deliberate trade for handler latency (dispatch never blocks the RPC), not an accident — but it's worth knowing if you were assuming broker-backed durability.
