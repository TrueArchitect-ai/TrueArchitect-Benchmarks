**Two enforcement styles.** Sites 1, 3–7 are *post-fetch gates*: load the memo, then reject. Sites 2, 8 are *pre-fetch query constraints* — they push `VisibilityList` into `store.FindMemo` so non-public rows never leave the database. The query-level style is the stronger pattern; the RSS and sitemap surfaces hard-code `[]store.Visibility{store.Public}` unconditionally, which is why they're safe for anonymous access.

**The canonical rule** lives at `server/router/api/v1/memo_service.go:55-66`: non-public requires an authenticated user (`Unauthenticated` if absent), and `Private` additionally requires creator ownership (`PermissionDenied`). Note it does **not** grant admin override — unlike sites 3–6, which all add `!isSuperUser(user)` (e.g. `memo_service_comments.go:41`, `reaction_service.go:38`) or `user.Role != store.RoleAdmin` (`fileserver.go:699`). That's a real inconsistency: an admin can reach a private memo's attachments and reactions but not the memo itself through `GetMemo`.

**`ListMemos` is graduated** rather than binary — anonymous callers get `{Public}` (`memo_service.go:219`), authenticated callers get `{Public, Protected}` (`:225`). The same two-tier logic is duplicated in stats at `server/router/api/v1/user_service_stats.go:84-90` and `:218-220`.

**The SSE filter is the one push-based site** (`sse_hub.go:134-143`): it evaluates per subscriber at fan-out time, treats empty visibility as broadcastable, and fails *closed* on an unrecognized value with a warning — the only site with an explicit default-deny.

**Notification filtering** (site 9) is about who gets *told*, not who may read, but it keys off the same field and suppresses `Private`/`Protected` mentions — worth counting since leaking content via email would bypass every other gate.
