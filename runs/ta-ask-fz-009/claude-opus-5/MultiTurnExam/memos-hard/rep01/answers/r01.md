**Premise correction: there is no Redis.** A case-insensitive search for `redis` across the repository returns **no matches (searched 1042 files)** — no client dependency, no connection string, no config key. The cache layer is entirely in-process.

**Actual mechanism: a hand-rolled in-memory TTL cache.** `store/cache/cache.go` implements `Cache` as a `sync.Map` plus an atomic item counter (`cache.go:67-73`), behind the `cache.Interface` contract (`cache.go:11-32`). Nothing crosses a network boundary — `Get`/`Set` ignore the `context.Context` they accept (note the `_ context.Context` parameters at `cache.go:98` and `:123`), which is the tell that this was shaped to *allow* a remote backend later without being one today.

**TTL for user entries: 10 minutes.** The store constructs three separate cache instances — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:27-29`) — from one shared `cache.Config` built in `store.New`: `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store/store.go:40-45`, applied at `:51-53`). So users get the default 10 minutes; there's no user-specific override, and no call site uses `SetWithTTL` to vary it — `Store.GetUser`/`ListUsers` call plain `Set` (`store/user.go:122`, `:143`). The same values are duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), though the store doesn't use that helper.

**Eviction has three paths**, worth knowing since they affect staleness:
- lazy — `Get` deletes and reports a miss when past `expiration` (`cache.go:135-144`);
- periodic — a `cleanupLoop` goroutine per cache instance ticks every 5 minutes (`cache.go:200-215`);
- capacity — exceeding `MaxItems` triggers `cleanupOldest`, which drops ~20% (`cache.go:117-119`, `:253-255`).

**Two operational consequences of it being in-process rather than Redis:** the cache does not survive a restart, and it is **not shared across instances** — so a horizontally scaled deployment can serve up to 10 minutes of divergent user data per node. Invalidation is local only; `Store.UpdateUser` refreshes just its own process's entry (`store/user.go:132`). Each cache's goroutine is shut down explicitly via `Store.Close` (`store/store.go:74-76`).
