**Two intermediate layers, then one funnel.** The four `Dispatch*Webhook` methods are thin activity-type labels — `memos.memo.created` / `.updated` / `.deleted` (`server/router/api/v1/memo_service_webhooks.go:15-27`) — all delegating to `dispatchMemoRelatedWebhook` (`memo_service_webhooks.go:48`). Comment creation is the one path that bypasses that helper, calling `PostAsync` directly from `DispatchMemoCommentCreatedWebhook` (`memo_service_webhooks.go:43`), because it targets the *parent* memo's owner rather than the actor.

So there are exactly two `PostAsync` call sites in the server — `memo_service_webhooks.go:43` and `:71` — and both loop over the resolved user's stored webhooks, taking the target from `hook.Url` and the HMAC key from `hook.SigningSecret` (lines 41-42, 68). That `hook.Url` is the user-configured URL the question asks about.

**Convergence and delivery are deliberately split.** `PostAsync` (`webhook.go:184`) only enqueues onto a 128-slot channel; four worker goroutines started in `init` drain it into `Post` (`webhook.go:42-55`), which performs the real `safeClient.Do` (`webhook.go:152`). Consequence worth knowing: handler latency is decoupled from receiver latency, and on a full queue the event is **dropped with a warning**, not retried (`webhook.go:191-195`). Failures are logged, never surfaced to the RPC caller — note `dispatchMemoUpdatedSideEffects` swallows the error (`memo_update_helpers.go:67-69`).

**Adjacent but out of scope:** `dispatchMemoMentionNotifications` (`memo_mention_helpers.go:91`) fires on the same handlers but writes in-app inbox records, not outbound HTTP.
