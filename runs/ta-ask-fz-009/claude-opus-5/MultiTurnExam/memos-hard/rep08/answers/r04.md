**Neither. There is no message broker in this codebase** — no NATS, no RabbitMQ, no Kafka, no AMQP client. A case-insensitive search for `nats|rabbitmq|amqp|kafka|streadway|message broker|pubsub` across the repo returns only irrelevant hits: Catalan locale strings that coincidentally contain the letters "nats" (`web/src/locales/ca.json`) and Google API doc comments mentioning Cloud Pub/Sub in generated protobuf files (`web/src/types/proto/google/api/client_pb.ts`, `resource_pb.ts`). No Go dependency, no connection URL, no queue declaration.

**Actual mechanism: an in-process Go channel with a fixed worker pool.** Everything lives in `internal/webhook/webhook.go`:

- **The "queue"** is a buffered channel declared as a package-level variable: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` at `internal/webhook/webhook.go:39`. Confirmed as the only such symbol by the graph (`webhook.asyncPostQueue`, anchored to that file). Capacity is a hard-coded 128 — no configuration knob.
- **The "consumers"** are four goroutines started in `init()` (`internal/webhook/webhook.go:42-55`), each ranging over the channel and calling `Post` for every payload, logging a warning on failure (`:46-51`). The pool size is the literal `for range 4`.
- **The "producer"** is `PostAsync` (`:184-196`), which does a non-blocking `select` send.

Three consequences of this being a channel rather than a broker, worth being explicit about:

1. **Overflow drops silently-ish.** The `select` has a `default` branch: when the buffer is full, the payload is discarded with a warning — "Dropped webhook dispatch because the async queue is full" (`:191-195`). A broker would persist or block; here the delivery is simply lost.
2. **No durability.** Queue state is process memory. A restart loses every pending dispatch — there is nothing to replay and no acknowledgement protocol.
3. **No retry and no cross-replica coordination.** `Post` returns an error that the worker only logs (`:46-51`); there is no redelivery, dead-letter path, or backoff. Each server replica has its own independent 128-slot channel and its own four workers.

The delivery itself still executes in `Post` (`internal/webhook/webhook.go:120`, HTTP call at `:152`) via the SSRF-guarded `safeClient` — that part is unchanged by the queueing model.
