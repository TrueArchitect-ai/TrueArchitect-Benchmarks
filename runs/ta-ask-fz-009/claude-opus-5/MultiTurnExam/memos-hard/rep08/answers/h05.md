**h05.**

**Explicit Go code — two deliberate `DELETE FROM reaction` statements per driver, inside the delete-user transaction. There is no database-level cascade for reactions, and there could not be: `reaction` has no foreign key to `user`.**

What I checked, in order:

**1. The Go delete path.** Each driver implements `DeleteUser` as one transaction (`store/db/mysql/user_delete.go:29-59`) whose orchestrator `deleteUserTargetsTx` removes reactions *twice*, for two distinct ownership relations:

- `deleteReactionsByContentIDsTx` (`store/db/mysql/user_delete.go:96`, defined at `:417-425`) — `DELETE FROM reaction WHERE content_id IN (...)`, i.e. *other people's* reactions on the departing user's content. The content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + memo.UID` (`:549-555`), matching how reactions key their target.
- `deleteReactionsByCreatorTx` (`store/db/mysql/user_delete.go:102`, defined at `:437-440`) — `DELETE FROM reaction WHERE creator_id = ?`, i.e. the user's own reactions anywhere.

Ordering matters and is correct: both reaction deletes run *before* `deleteMemosTx` (`:120`) and `deleteUserRowTx` (`:123`), so the content IDs are still resolvable. The memo set is itself the full comment tree, gathered iteratively via `memo_relation ... type = 'COMMENT'` (`:133-181`), so reactions on descendant comments are included. Both statements are batched at 500 (`deleteUserBatchSize`, `:14`).

**2. All three drivers, not just one.** The identical pair exists in each dialect at the same call sites and function names: `store/db/mysql/user_delete.go:96,102,417,437`, `store/db/postgres/user_delete.go:96,102,380,400`, `store/db/sqlite/user_delete.go:96,102,380,400`.

**3. The schema, to rule out a cascade.** The `reaction` table declares only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`, in any dialect: `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/sqlite/LATEST.sql:92-99` (originals at `store/migration/{mysql,postgres}/0.20/00__reaction.sql`). A repo-wide scan of `store/migration/**/*.sql` for `FOREIGN KEY|REFERENCES|ON DELETE` returns cascades for `memo_share`, `user_setting`, `memo`, `memo_resource` — but no row referencing `reaction`.

Structurally this is why the Go code must do the work: `content_id` is a *string* reference (`memos/{uid}`), not an integer FK to `memo(id)`, so the database has no declared relationship to cascade along. The cleanup invariant lives entirely in `deleteUserTargetsTx` and is only as complete as that function's memo-tree traversal.
