**h03.**

**`internal/idp` (`internal/idp/idp.go`); `internal/idp/oauth2` (`internal/idp/oauth2/oauth2.go`) — OAuth2 is the only concrete protocol that ships**

Details worth flagging, because the "abstraction" here is thinner than the phrasing suggests:

- **`internal/idp`** is the shared contract package, but it contains no Go `interface` — the whole file is a single struct, `IdentityProviderUserInfo` with `Identifier`, `DisplayName`, `Email`, `AvatarURL` (`internal/idp/idp.go:3-8`). So the boundary is a **normalized user-info DTO**, not a polymorphic provider interface. Concrete providers depend on `internal/idp` for the return type and are selected by concrete type, not dispatched through an interface.
- **`internal/idp/oauth2`** is the sole implementation — the package doc says so directly: "Package oauth2 implements the OAuth2 identity provider integration" (`internal/idp/oauth2/oauth2.go:1`). It defines `IdentityProvider` wrapping a `*storepb.OAuth2Config` (line 20), constructed by `NewIdentityProvider` which enforces required fields `clientId`, `clientSecret`, `tokenUrl`, `userInfoUrl`, `fieldMapping.identifier` (lines 27-43).
- The two operations forming the effective provider contract are `ExchangeToken` (line 47, with optional PKCE `code_verifier`, lines 63-66) and `UserInfo` (line 83), which maps arbitrary provider claims onto the `idp.IdentityProviderUserInfo` struct via the configured `FieldMapping` (lines 114-140). Identifier is mandatory (lines 118-120); display name falls back to identifier (lines 128-130); email and avatar are best-effort.

`internal/idp/` contains only `idp.go` and the `oauth2/` subdirectory — no SAML, LDAP, or OIDC-specific package exists alongside it. Note that OIDC providers are still usable, since OIDC is OAuth2-shaped and the `userInfoUrl` + field-mapping configuration accommodates its claims.
