Two structural notes:

- **Two enforcement *styles*, not one.** Single-object paths check `memo.Visibility` after loading (`memo_service.go:55`); list paths never load private rows at all, instead injecting either `FindMemo.VisibilityList` or a CEL filter string like `creator_id == %d || visibility in ["PUBLIC", "PROTECTED"]`. The ACL config makes this explicit: `GetMemo`/`ListMemos` are unauthenticated-allowed because "visibility filtering done in service layer" (`server/router/api/v1/acl_config.go:32-35`).
- **The rules are not uniform.** `checkMemoReadAccess` omits the admin escape hatch that its siblings include — compare `memo_service.go:63` (no `isSuperUser`) with `reaction_service.go:38` and `attachment_service.go:451` (both `&& !isSuperUser(user)`), and `fileserver.go:699` which uses `user.Role != store.RoleAdmin` directly. The fileserver also adds a share-token fallback and an anonymous-instance condition (`fileserver.go:677`) that the gRPC path has no equivalent for. Each surface re-derives the invariant, so a change to visibility semantics requires touching all of them.
