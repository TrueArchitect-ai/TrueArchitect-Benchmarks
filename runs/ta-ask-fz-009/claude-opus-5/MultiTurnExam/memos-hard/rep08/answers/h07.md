The avatar is **not** served through the gRPC/Connect API — it's an Echo route on the file server. Main path:

```
route registration: GET /file/users/:identifier/avatar — server/router/fileserver/fileserver.go:124
FileServerService.serveUserAvatar — server/router/fileserver/fileserver.go:168
FileServerService.getUserByUsername — server/router/fileserver/fileserver.go:715

store.Store.ListUsers — store/user.go:158 (cache miss path)
Store.driver.ListUsers (dialect impl) — store/db/{sqlite,mysql,postgres}/user.go
FileServerService.parseDataURI — server/router/fileserver/fileserver.go:196 (decode, in-handler)
c.Blob — server/router/fileserver/fileserver.go:209
```

Two things shape this trace:

**The bytes come from the `user` row, not from attachment storage.** `serveUserAvatar` reads `user.AvatarURL` (`fileserver.go:192`) and hands it to `parseDataURI` (`:196`) — the image is a base64 data URI stored inline in the user record. There is no attachment table or S3 hop. The reason this endpoint exists at all is size: `convertUserToProto` rewrites the field to `/file/{user}/avatar` when the stored value parses as a data URI, precisely to keep raw base64 out of API responses (`server/router/api/v1/user_service_converters.go:31-38`).

**The auth pre-hop is conditional and adds a second store path.** On a private instance (`!s.Profile.AllowAnonymous()`, `fileserver.go:173`) the handler first resolves the *viewer*:

```
FileServerService.getCurrentUser — server/router/fileserver/fileserver.go:708
auth.Authenticator.AuthenticateToUser — server/auth/authenticator.go:190
  ├─ resolveBearer — server/auth/authenticator.go:149  (→ AuthenticateByPAT :102 → Store.GetUserByPATHash, store/user_setting.go:128)
  └─ AuthenticateByRefreshToken — server/auth/authenticator.go:61
store.Store.GetUser — store/user.go:148
```

On an open instance that branch is skipped entirely, so the request reaches `GetUser` in one hop.

Caching detail worth noting: `Store.GetUser` only consults `userCache` when the lookup is by **ID** (`store/user.go:149-156`). This path queries by `Username` (`fileserver.go:716`), so every avatar request falls through to `ListUsers` and hits the database; the result is then cached by ID (`:167`) for other callers, not for this one.

Response hardening before the blob: `setSecurityHeaders`, MIME allow-list check against `avatarAllowedTypes` (PNG/JPEG/JPG/GIF/WebP, `fileserver.go:75-80`, enforced at `:201`), and `Cache-Control: cacheMaxAge` (`:207`).
