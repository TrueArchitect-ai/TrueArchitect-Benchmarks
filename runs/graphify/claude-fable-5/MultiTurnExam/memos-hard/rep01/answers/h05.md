**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside the user-deletion transaction, not by any database-level rule.

Evidence checked:

1. **Explicit deletion code.** Each database driver's `DeleteUser` runs a single transaction that explicitly deletes reactions twice — once for reactions *on* the user's memos and once for reactions *made by* the user:
   - SQLite: `deleteUserTargetsTx` calls `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:96`, defined at line 380, executing `DELETE FROM reaction WHERE content_id IN ...`) and `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:102`, defined at line 400, executing `DELETE FROM reaction WHERE creator_id = ?`).
   - MySQL: same pair at `store/db/mysql/user_delete.go:96,102` (implementations at lines 417 and 437).
   - Postgres: same pair at `store/db/postgres/user_delete.go:96,102` (implementations at lines 380 and 400).
   The entry point is `Store.DeleteUser` at `store/user.go:171` delegating to these drivers.

2. **No database-level rule.** The `reaction` table DDL has no foreign keys at all — hence no `ON DELETE CASCADE`. In all three schemas the table is just id/created_ts/creator_id/content_id/reaction_type with a UNIQUE constraint: `store/migration/sqlite/prod/LATEST.sql` (reaction table around line 92), `store/migration/postgres/prod/LATEST.sql:91`, and the MySQL equivalents (`store/migration/mysql/prod/LATEST.sql`, original DDL in `store/migration/mysql/prod/0.20/00__reaction.sql`). With no FK referencing `user`, cascade deletion is impossible; the explicit Go code is the only removal mechanism.
