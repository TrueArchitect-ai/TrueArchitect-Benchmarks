A request for `GET /file/users/:identifier/avatar` flows through these hops:

- `RegisterRoutes` (route registration: `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)`) — `server/router/fileserver/fileserver.go:124` (service wired up at `server/server.go:81-82`)
- `(*FileServerService).serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (handler: enforces auth on private instances, looks up the target user by the `:identifier` path param, parses `user.AvatarURL`)
- `(*FileServerService).getUserByUsername` — `server/router/fileserver/fileserver.go:715` (thin wrapper: `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`)
- `(*Store).GetUser` — `store/user.go:148` (checks the in-memory user cache, otherwise delegates to `ListUsers` and caches the result)
- `(*Store).ListUsers` — `store/user.go:136` (delegates to the database driver interface `s.driver.ListUsers`)
- `(*DB).ListUsers` (driver implementation, e.g. SQLite) — `store/db/sqlite/user.go:88` (equivalent implementations exist for MySQL/Postgres under `store/db/mysql/` and `store/db/postgres/`; which one runs is chosen by the factory in `store/db/db.go:14`)

The stored data itself is the `avatar_url` column on the `user` row — the avatar is a base64 `data:` URI kept in the user record, which `serveUserAvatar` decodes via `parseDataURI` (`server/router/fileserver/fileserver.go:196`), validates against `avatarAllowedTypes` (`fileserver.go:75`), and returns as an image blob. There is no separate attachment/object-storage hop for avatars.
