The avatar is not a separate blob — it's stored inline as a `data:` URI in the user row's `avatar_url` column, so the request resolves to a user-table read. The route registration is `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` at `server/router/fileserver/fileserver.go:124`.

Hops from handler to data layer:

- `serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (serving handler; then parses the stored data URI via `parseDataURI` and writes the bytes with `c.Blob`)
- `getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` — `store/user.go:148`
- `Store.ListUsers` — `store/user.go` (calls `s.driver.ListUsers`)
- `(*DB).ListUsers` (SQLite driver; Postgres/MySQL analogues exist) — `store/db/sqlite/user.go:88` — runs the SQL `SELECT` that returns the `avatar_url` field

The stored data itself is the `avatar_url` column of the `user` table; `serveUserAvatar` reads `user.AvatarURL` (`fileserver.go:196`) and decodes it, so no attachment/S3/local-file path is involved for avatars.
