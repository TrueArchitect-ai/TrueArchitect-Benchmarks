**Explicit Go code** (SQL `DELETE` statements issued inside each driver's user-deletion transaction), not a database-level rule.

What I checked:

1. **Go deletion code — reactions are removed explicitly, in two ways, in every driver:**
   - By creator: `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` — `store/db/sqlite/user_delete.go:400-403`, `store/db/postgres/user_delete.go:401`, `store/db/mysql/user_delete.go:438`.
   - By content: `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` to clean up reactions attached to the deleted user's memos — `store/db/sqlite/user_delete.go:380-388`, `store/db/postgres/user_delete.go:383`, `store/db/mysql/user_delete.go:420`.
   - These run inside the transactional `DeleteUser` flow (e.g. `store/db/mysql/user_delete.go:29`), entered via `Store.DeleteUser` at `store/user.go:171`.

2. **Schema — no database-level rule exists for reactions:** the `reaction` table has no foreign key at all (only a UNIQUE constraint) in all three dialects: `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. The only `ON DELETE CASCADE` in the schemas belongs to `memo_share.memo_id → memo(id)` (e.g. `store/migration/sqlite/LATEST.sql:109`), so cascades could not remove reactions.
