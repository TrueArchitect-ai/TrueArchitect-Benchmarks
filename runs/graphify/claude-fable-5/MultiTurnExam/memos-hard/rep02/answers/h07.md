The browser hits `GET /file/users/{username}/avatar`; the avatar bytes live as a data-URI in the user's row (`avatar_url` column), so the "stored data" is reached through the user store. Hops:

- `FileServerService.RegisterRoutes` (binds `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:121-124`
- `FileServerService.serveUserAvatar` (serving handler; optional auth check via `getCurrentUser`, then user lookup) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:714-717`
- `Store.GetUser` (checks `userCache`, else falls through) — `store/user.go:148`
- `Store.ListUsers` — `store/user.go:136`
- `Driver.ListUsers` (driver interface dispatch, e.g. `(*DB).ListUsers` SQL query against the `user` table) — `store/db/sqlite/user.go:88` (equivalents in `store/db/mysql/user.go`, `store/db/postgres/user.go`)
- back in the handler: `FileServerService.parseDataURI` decodes `user.AvatarURL` (the stored base64 data-URI) and `c.Blob(...)` writes the image with a validated MIME type — `server/router/fileserver/fileserver.go:196-209`

Note the profile image is not in the attachment/blob storage path — it's stored inline on the user record, so the data layer terminates at the users table read.
