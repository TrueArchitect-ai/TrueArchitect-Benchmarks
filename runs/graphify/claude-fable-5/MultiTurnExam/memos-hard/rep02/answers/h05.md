**Mechanism: explicit Go code** — reactions are deleted by SQL `DELETE` statements executed inside each driver's `DeleteUser` transaction, not by any database-level rule.

Evidence checked:

1. **Explicit deletion code**: All three driver implementations of user deletion delete reactions in two passes — by the deleted user's memos' content IDs and by the user as reaction creator:
   - `store/db/sqlite/user_delete.go:96,102` call `deleteReactionsByContentIDsTx` / `deleteReactionsByCreatorTx`, which run `DELETE FROM reaction WHERE content_id IN ...` (line 383) and `DELETE FROM reaction WHERE creator_id = ?` (line 401).
   - Same pattern in `store/db/postgres/user_delete.go:96,102,383,401` and `store/db/mysql/user_delete.go:96,102,420,438`.
   - This runs inside the transaction driven by `(*DB).DeleteUser` (e.g. `store/db/sqlite/user_delete.go:29`), invoked via `store/user.go:171-172`.

2. **No database-level rule**: The `reaction` table schema has no foreign key or cascade at all — `store/migration/sqlite/LATEST.sql:92-99` (mirrored in the mysql/postgres `LATEST.sql`) defines only columns and a UNIQUE constraint. The only `ON DELETE CASCADE` in the schemas is on `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`), which doesn't touch reactions.
