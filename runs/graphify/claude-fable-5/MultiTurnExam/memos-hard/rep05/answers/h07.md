A profile-image request hits `GET /file/users/:identifier/avatar` and resolves to the avatar bytes stored inline (as a data URI) in the user's database row. Hops:

- `FileServerService.RegisterRoutes` (route `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (serving handler; anonymous-access check, then decodes and returns the image) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks the user cache, else delegates) — `store/user.go:148`
- `Store.ListUsers` (calls the selected driver) — `store/user.go:136`
- `DB.ListUsers` (driver SQL that reads the `user` row, including `avatar_url`) — `store/db/sqlite/user.go:88` (equivalently `store/db/postgres/user.go:87` / `store/db/mysql/user.go:84`)

Back in the handler, the stored `user.AvatarURL` data URI is decoded by `FileServerService.parseDataURI` and type-checked against `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:196-203`) before the bytes are written to the response — the image is not a separate file/blob; it lives in the user record itself.
