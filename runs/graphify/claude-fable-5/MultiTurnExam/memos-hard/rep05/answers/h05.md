**Mechanism: explicit Go code — `DELETE FROM reaction ...` statements run inside each driver's user-deletion transaction. There is no database-level rule for reactions.**

What I checked:

1. **Explicit Go deletion (the mechanism):** Each database driver's `DeleteUser` implementation issues two explicit deletes for reactions within the delete-user transaction:
   - Reactions *on* the user's memos: `DELETE FROM reaction WHERE content_id IN ...` — `store/db/sqlite/user_delete.go:383`, `store/db/postgres/user_delete.go:383`, `store/db/mysql/user_delete.go:420`
   - Reactions *made by* the user: `DELETE FROM reaction WHERE creator_id = ?` — `store/db/sqlite/user_delete.go:401`, `store/db/postgres/user_delete.go:401`, `store/db/mysql/user_delete.go:438`
   
   These run from `DeleteUser` (e.g. `store/db/sqlite/user_delete.go:29`), which the store layer invokes via `store/user_delete.go`.

2. **No database-level rule:** The current schema for the `reaction` table has no foreign keys at all — `store/migration/sqlite/LATEST.sql:92-99` defines only columns and a UNIQUE constraint (same in the postgres and mysql `LATEST.sql`). The only `ON DELETE CASCADE` clauses in the current schemas are on other tables (e.g. `memo_id REFERENCES memo(id)` at `store/migration/sqlite/LATEST.sql:109`). Historical migrations like `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql` had user-cascade FKs on other tables, but the reaction table (added later, `store/migration/postgres/0.20/00__reaction.sql`) never got one.
