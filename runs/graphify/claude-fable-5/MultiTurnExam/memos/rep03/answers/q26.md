**memo_relation, attachment, memo**

`Store.DeleteMemo` (`store/memo.go:140-158`) explicitly cascades in this order:

1. `memo_relation` — deleted twice, covering rows where the memo is the source (`MemoID`) and the target (`RelatedMemoID`)
2. `attachment` — each attachment linked to the memo is deleted via `Store.DeleteAttachment` (`store/attachment.go:132`, which also removes the stored file/blob from local or S3 storage — a filesystem/object-store side effect, not a table)
3. `memo` — the row itself, via the driver's plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-247`)

Additionally, the API-layer handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:568-582`) first deletes all comment memos (rows in `memo` related by `memo_relation` type COMMENT) by calling `Store.DeleteMemo` on each — so the same three tables are hit recursively per comment. No explicit cascade deletes `reaction` or `memo_share` rows in this path.
