**Tables affected: `memo_relation`, `attachment`, `memo`**

`Store.DeleteMemo` (`store/memo.go:140-159`) explicitly cascades:

1. `memo_relation` — deleted for both directions (memo as source and as target), lines 142–147.
2. `attachment` — each attachment linked to the memo is deleted via `Store.DeleteAttachment` (`store/attachment.go:132`), whose driver SQL is `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go:211-221`); this also removes the stored file, which is blob storage rather than a table.
3. `memo` — the row itself, via the dialect driver (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

Additionally, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go`) deletes comment memos first by calling `Store.DeleteMemo` for each comment relation — those hit the same three tables. (Reactions are listed there only to build the webhook payload; there is no explicit `reaction` cleanup in this path.)
