**Tables affected: `memo`, `memo_relation`, `attachment`**

When `Store.DeleteMemo` runs (`store/memo.go:140`), the explicit cascade code does the following, in order:

1. **`memo_relation`** — two `DeleteMemoRelation` calls remove rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`) of a relation (`store/memo.go:142-147`; SQL `DELETE FROM memo_relation` in e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists attachments linked to the memo and deletes each one via `Store.DeleteAttachment` (`store/memo.go:149-157`), which executes `DELETE FROM attachment` in the driver (`store/db/sqlite/attachment.go:211-212`). This also removes the attachment's backing storage (local file or S3 object), but that's filesystem/object storage, not a database table.
3. **`memo`** — finally the driver deletes the memo row itself with `DELETE FROM memo` (`store/db/sqlite/memo.go:237-239`, `store/db/mysql/memo.go:259-261`, `store/db/postgres/memo.go:244-246`).

All three database drivers (SQLite, MySQL, Postgres) implement `DeleteMemo` as a plain single-table `DELETE FROM memo` with no additional SQL-level cascades, so the full set of tables touched is exactly: `memo`, `memo_relation`, `attachment`.
