**Interceptor path:** `web/src/connect.ts`. The Connect-RPC auth interceptor there attaches `Authorization: Bearer <token>` to every request via `setAuthorizationHeader()`/`getRequestToken()` (web/src/connect.ts:97, web/src/connect.ts:124), and on a `Code.Unauthenticated` response it refreshes and retries once (`shouldHandleUnauthenticatedRetry()`, web/src/connect.ts:102), guarded by an `X-Retry` header. Token storage helpers live in `web/src/auth-state.ts`.

**Token kinds:** two — a short-lived **JWT access token** kept in memory/frontend state and sent as a Bearer header, and an HTTP-only **refresh token cookie** used by `refreshAccessToken()` (web/src/connect.ts:89), which calls `AuthService.refreshToken` over a separate interceptor-free transport with `credentials: "include"`. Refreshes are deduplicated by a token-refresh manager and run both proactively (preflight expiry check) and reactively (on 401).

**Backend validation:** the server-side `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208`) reads the `Authorization` header and delegates to the `Authorizer` (`server/router/api/v1/authz.go`), which uses the **`server/auth`** package — `Authenticator.Authenticate` / `AuthenticateByAccessTokenV2` / `ParseAccessTokenV2` in `server/auth/authenticator.go` and `server/auth/token.go` validate the JWTs (refresh tokens via `AuthenticateByRefreshToken`/`ParseRefreshToken`; the package also supports personal access tokens via `AuthenticateByPAT`).

**Answer format:** `web/src/connect.ts`; JWT access token (Bearer header) + refresh token (HTTP-only cookie); `server/auth` (wired via `server/router/api/v1/connect_interceptors.go`).
