Frontend requests are authenticated by a Connect RPC client interceptor. The `authInterceptor` lives in `web/src/connect.ts` (defined at `web/src/connect.ts:156` and installed on the transport at line 188). On every request it calls `getRequestToken()` to attach an in-memory JWT access token as an `Authorization: Bearer <token>` header, proactively refreshing it if expired; on a 401 (`Code.Unauthenticated`) it reactively refreshes once (marking the retry with an `X-Retry` header) and redirects to login if the refresh fails.

The tokens it manages:
- **Short-lived JWT access token** (~15 minutes) — held in memory via `web/src/auth-state.ts`, sent as the Bearer header.
- **Refresh token** (~30 days) — stored in an HTTP-only cookie (`memos_refresh`), sent automatically because the transport uses `credentials: "include"`; the interceptor uses it via `refreshAccessToken()` → `AuthService.refreshToken` on a dedicated interceptor-free transport to avoid recursion.

On the backend, the server-side `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208` reads the `Authorization` header and delegates to the `Authorizer` (`server/router/api/v1/authz.go`), which wraps the **`server/auth`** package — that package's `Authenticator` and `token.go` (`ParseAccessTokenV2`, `ParseRefreshToken`) validate the JWTs (HS256, typed access/refresh claims) and also handle long-lived personal access tokens.

**Answer format:** `web/src/connect.ts` (authInterceptor); JWT access tokens (in-memory, Bearer header) + refresh tokens (`memos_refresh` HTTP-only cookie) — plus PATs also accepted server-side; `server/auth`.
