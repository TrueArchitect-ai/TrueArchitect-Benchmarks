`web/src/connect.ts`; short-lived JWT access tokens plus refresh tokens (and the backend also accepts personal access tokens); `server/auth`

How it works:

- **Interceptor:** The `authInterceptor` (a Connect RPC `Interceptor`) is defined in `web/src/connect.ts:156` and installed on the shared transport at `web/src/connect.ts:188`, which all frontend service clients (memo, user, auth, etc.) are built on. It attaches `Authorization: Bearer <token>` to every request (`web/src/connect.ts:97-99`).
- **Tokens it manages:** A short-lived **access token**, persisted in localStorage by `web/src/auth-state.ts` and refreshed proactively when near expiry (`getRequestToken`, `web/src/connect.ts:124`) or reactively after a 401 with a single `X-Retry` retry (`web/src/connect.ts:161-177`). Refreshing calls `AuthService.RefreshToken` over a separate interceptor-free transport using a **refresh token** carried in an HTTP cookie (`credentials: "include"`, `web/src/connect.ts:57-83`), deduplicated through `tokenRefreshManager` to avoid conflicting with server-side token rotation.
- **Backend validation:** The server-side `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208` reads the `Authorization` header and delegates to the `Authorizer` (`server/router/api/v1/authz.go`), which wraps the **`server/auth`** package — `server/auth/authenticator.go` validates JWT access tokens (`AuthenticateByAccessTokenV2`), refresh tokens (`AuthenticateByRefreshToken`), and personal access tokens (`AuthenticateByPAT`).
