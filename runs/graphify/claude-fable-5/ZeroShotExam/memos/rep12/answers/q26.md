**Tables affected: `memo`, `memo_relation`, `attachment`**

When `Store.DeleteMemo` runs (`store/memo.go:140`), the explicit cascade code does the following:

1. **`memo_relation`** — it calls `driver.DeleteMemoRelation` twice, once with the memo as `MemoID` and once as `RelatedMemoID`, removing relation rows in both directions (`store/memo.go:141-147`; the driver executes `DELETE FROM memo_relation`, e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists attachments linked to the memo and calls `Store.DeleteAttachment` for each (`store/memo.go:149-157`), which deletes the file from local/S3 storage and then deletes the row via `DELETE FROM attachment` (`store/attachment.go:132-149`, `store/db/sqlite/attachment.go:212`).
3. **`memo`** — finally it calls `driver.DeleteMemo`, which executes `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-249`; equivalents in `store/db/mysql/memo.go:259` and `store/db/postgres/memo.go:244`).

The API-level handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) adds no additional tables: it recursively calls `Store.DeleteMemo` on comment memos first (same three tables), and while it lists reactions, that is only to build the webhook payload — no explicit delete of `reaction` (or `memo_share`, `inbox`) rows occurs in the DeleteMemo path.
