**Tables affected: `memo`, `memo_relation`, `attachment`**

When `Store.DeleteMemo` runs (`store/memo.go:140`), the explicit cascade code does the following, in order:

1. **`memo_relation`** — two `driver.DeleteMemoRelation` calls remove rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL `DELETE FROM memo_relation` at `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists attachments linked to the memo and calls `Store.DeleteAttachment` for each (`store/memo.go:149-158`), which deletes the row (`DELETE FROM attachment` at `store/db/sqlite/attachment.go:212`) after removing the backing local/S3 file (`store/attachment.go:132-148` — filesystem/object storage, not a DB table).
3. **`memo`** — finally `driver.DeleteMemo` deletes the memo row itself (`DELETE FROM memo` in `store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).

The API-level handler (`server/router/api/v1/memo_service.go:518`) adds one more explicit cascade: it deletes each comment memo (memos related via `MemoRelationComment`) by calling `Store.DeleteMemo` recursively — which touches the same three tables, no additional ones. It lists reactions only to build the deleted-webhook payload; no reaction rows are deleted in this path.
