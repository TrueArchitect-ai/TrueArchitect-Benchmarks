**Tables affected: `memo`, `memo_relation`, `attachment`**

`Store.DeleteMemo` (`store/memo.go:140`) contains explicit cascade code that runs before deleting the memo row itself:

1. **`memo_relation`** — two `driver.DeleteMemoRelation` calls remove rows where the memo is the source (`MemoID`) or the target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL in e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists attachments linked to the memo and calls `Store.DeleteAttachment` for each (`store/memo.go:149-158`), which deletes the `attachment` row (`store/db/sqlite/attachment.go:212`). This step also removes the attachment's backing blob (local file or external storage via `DeleteAttachmentStorage`, `store/attachment.go:141`), but that is filesystem/object storage, not a database table.
3. **`memo`** — finally `driver.DeleteMemo` issues `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-239`, with equivalent implementations in `store/db/mysql/memo.go:259` and `store/db/postgres/memo.go:244`).

No other tables are touched by the store-level cascade — there is no cleanup of `reaction`, `inbox`, or similar tables inside `Store.DeleteMemo`. (For context: the API handler `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go:518` additionally deletes comment memos by recursively calling `Store.DeleteMemo` on each comment, which hits the same three tables again per comment, but the per-run table set is still `memo`, `memo_relation`, `attachment`.)
