Three tables: **`memo_relation`**, **`attachment`**, and **`memo`**.

`Store.DeleteMemo` in `store/memo.go:140` performs an explicit cascade before the final delete:

1. **`memo_relation`** — two `DeleteMemoRelation` calls remove rows where the memo is the source (`MemoID`) or the target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL in e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists attachments linked to the memo and deletes each one via `Store.DeleteAttachment` (`store/memo.go:149-157`), which removes the stored file (local disk or S3 — not a table) and then deletes the `attachment` row (`store/attachment.go:132-149`, SQL at `store/db/sqlite/attachment.go:212`).
3. **`memo`** — finally the driver-level `DeleteMemo` runs `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).

For completeness: the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally deletes comment memos by calling `Store.DeleteMemo` recursively for each comment relation, but that touches the same three tables. It lists `reaction` rows only to build the webhook payload — it does not delete them — so `reaction` is not affected.
