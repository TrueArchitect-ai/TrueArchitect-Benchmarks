**Tables: `memo`, `memo_relation`, `attachment`**

When `Store.DeleteMemo` runs (`store/memo.go:140`), the explicit cascade code does the following:

1. **`memo_relation`** — deleted twice via `driver.DeleteMemoRelation`, once matching the memo as source (`MemoID`) and once as target (`RelatedMemoID`) (`store/memo.go:141-147`; e.g. `DELETE FROM memo_relation` in `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — the store lists attachments linked to the memo and calls `DeleteAttachment` for each (`store/memo.go:149-157`), which deletes the row via the driver (`DELETE FROM attachment` in `store/db/sqlite/attachment.go:212`). This also removes the underlying blob from local disk or S3 (`store/attachment.go:132-148`), but that's file/object storage, not a table.
3. **`memo`** — the driver's `DeleteMemo` runs `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

Note that the API-layer handler (`server/router/api/v1/memo_service.go:518`) additionally deletes comment memos by calling `Store.DeleteMemo` for each comment relation, but that recursion still only touches the same three tables. Reactions (`reaction`) and shares (`memo_share`) are *not* cleaned up by this path — the reaction listing there is only used to build the webhook payload (those tables are only cascaded in the separate user-deletion path, `store/db/sqlite/user_delete.go`).
