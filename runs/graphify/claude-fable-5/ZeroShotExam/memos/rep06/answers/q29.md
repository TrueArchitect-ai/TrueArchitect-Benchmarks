**Answer:** `web/src/connect.ts`; short-lived JWT access tokens + long-lived refresh tokens (plus support for personal access tokens); `server/auth`

Details, verified via the graphify knowledge graph and confirmed in source:

- **Interceptor location:** The frontend authentication interceptor lives in `web/src/connect.ts` (the "Authentication Interceptor" section around line 153, with helpers `getRequestToken()` at `web/src/connect.ts:124`, `refreshAccessToken()` at `web/src/connect.ts:89`, and `shouldHandleUnauthenticatedRetry()` at `web/src/connect.ts:102`). It attaches an `Authorization: Bearer <token>` header to every Connect RPC, with token state kept in `web/src/auth-state.ts`.

- **Tokens it manages:** Two kinds. A short-lived **JWT access token** (15-minute lifetime, audience `user.access-token`) that it stores in memory and sends as the Bearer header, and a long-lived **refresh token** (30-day, audience `user.refresh-token`, carried in the `memos_refresh` cookie) that it uses — via a dedicated interceptor-free transport calling `refreshToken({})` — to preflight-refresh expired access tokens and to retry after 401s, with a refresh-manager deduplicating concurrent refreshes. (The backend additionally accepts `memos_pat_`-prefixed personal access tokens, managed in Settings rather than by the interceptor.)

- **Backend validation:** Token generation and validation live in the `server/auth` package (`server/auth/token.go`, with an `Authenticator`). It's wired into request handling through the `Authorizer` in `server/router/api/v1/authz.go:26` and the Connect `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208`, which resolves the caller from the Authorization header and enforces the anonymous-access policy.
