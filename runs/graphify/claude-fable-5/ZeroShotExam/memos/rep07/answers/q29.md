**Answer:** `web/src/connect.ts`; short-lived JWT access tokens (Bearer, localStorage) plus a refresh token sent as an HTTP-only cookie; validated by `server/auth`.

How it works:

- **Interceptor:** The Connect RPC `authInterceptor` lives in `web/src/connect.ts` (defined at `web/src/connect.ts:156`, wired into the transport at line 188 so all service clients — memo, user, auth, etc. — pass through it).
- **Tokens it manages:** A short-lived **access token** attached as `Authorization: Bearer <token>` (stored in memory/localStorage and synced across tabs via BroadcastChannel — see `web/src/auth-state.ts`), and a **refresh token** held in an HTTP-only cookie that rides along via `credentials: "include"`. The interceptor does a preflight refresh when the access token is near expiry (`getRequestToken`, `connect.ts:124`), and on an `Unauthenticated` error it calls `AuthService.RefreshToken` through a separate interceptor-free transport (`refreshAccessToken`, `connect.ts:74–91`), retries the request once with an `X-Retry` header, and redirects to login if the refresh fails.
- **Backend validation:** The server-side `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208` reads the `Authorization` header and delegates to the `Authorizer` (`server/router/api/v1/authz.go`), which is backed by the **`server/auth` package** (`auth.NewAuthenticator` in `server/auth/authenticator.go`, with JWT parsing/generation in `server/auth/token.go` — e.g. `ParseAccessTokenV2`, `GenerateRefreshToken`). That package validates both access tokens and personal access tokens; the same `Authorizer` is shared by the Connect interceptor and the gRPC-Gateway middleware.
