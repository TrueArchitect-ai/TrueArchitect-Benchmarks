**Tables affected: `memo_relation`, `attachment`, `memo`**

`Store.DeleteMemo` (`store/memo.go:140`) performs explicit cascade cleanup before deleting the memo row itself:

1. **`memo_relation`** — two `driver.DeleteMemoRelation` calls remove relation rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`). The driver executes `DELETE FROM memo_relation` (e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists attachments linked to the memo and calls `Store.DeleteAttachment` for each (`store/attachment.go:132`), which deletes the storage blob (local file / S3 object — filesystem/object storage, not a table) and then executes `DELETE FROM attachment` (e.g. `store/db/sqlite/attachment.go:212`).
3. **`memo`** — finally `driver.DeleteMemo` runs `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).

For completeness: the API-layer `DeleteMemo` (`server/router/api/v1/memo_service.go:518`) also recursively deletes comment memos via the same `Store.DeleteMemo`, which touches the same three tables — it lists reactions but only for the webhook payload, it does not delete them. So no additional tables beyond `memo_relation`, `attachment`, and `memo`.
