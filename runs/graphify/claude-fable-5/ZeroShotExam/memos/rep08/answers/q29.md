Frontend requests are authenticated by a Connect RPC interceptor: `authInterceptor` in `web/src/connect.ts` (defined around line 156). It attaches `Authorization: Bearer <token>` to every request, and it manages a short-lived **JWT access token** held in memory (via `web/src/auth-state.ts`, shared across tabs with a BroadcastChannel). When the access token is missing, near expiry, or a request comes back `Unauthenticated`, the interceptor calls `refreshAccessToken()`, which hits the `refreshToken` RPC over a separate interceptor-free transport; that refresh is authenticated by a **refresh token** carried in an HTTP-only cookie (see `ExtractRefreshTokenFromCookie` in `server/auth/extract.go`). The same Bearer scheme also accepts long-lived **Personal Access Tokens (PATs)** for programmatic clients.

On the backend, the `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go` (line 208) reads the `Authorization` header and delegates to the shared `Authorizer` (`server/router/api/v1/authz.go`), which wraps the validating package: **`server/auth`** (`github.com/usememos/memos/server/auth`). Its `Authenticator` (`server/auth/authenticator.go`) validates JWT access tokens (~15 min lifetime), refresh tokens (checked against the database for revocation/expiry), and PATs (looked up by hash).

Answer in the requested format: `web/src/connect.ts` (authInterceptor); JWT access tokens + cookie-based refresh tokens + personal access tokens (PATs); `server/auth` (validated via the AuthInterceptor/Authorizer in `server/router/api/v1/`).
