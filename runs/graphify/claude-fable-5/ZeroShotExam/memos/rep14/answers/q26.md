**Tables: `memo_relation`, `attachment`, `memo`** (plus `memo_share` via a database-level foreign-key cascade, not code).

`Store.DeleteMemo` in `store/memo.go:140` performs explicit cascade cleanup before deleting the memo row:

1. **`memo_relation`** — `driver.DeleteMemoRelation` is called twice, once with the memo as source (`MemoID`) and once as target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL in e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists the memo's attachments and calls `Store.DeleteAttachment` for each, which removes the stored file (filesystem/S3 — not a table) and then runs `DELETE FROM attachment` (`store/memo.go:149-157`, `store/attachment.go:132-149`, `store/db/sqlite/attachment.go:212`).
3. **`memo`** — finally the driver's `DeleteMemo` executes `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).

Additionally, **`memo_share`** rows are removed when the `memo` row is deleted, but by a schema-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, same in the postgres/mysql schemas), not by explicit Go code.

Notably, `reaction` is **not** touched by `Store.DeleteMemo` itself — the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) reads reactions only for the webhook payload, and it also recursively deletes comment memos (each recursion hitting the same three tables above).
