**Engine: CEL (Common Expression Language, via `github.com/google/cel-go`) — living in `internal/filter/`.**

Mechanism: `ListMemos` (`server/router/api/v1/memo_service.go:211-215`) validates the filter string and passes it through `FindMemo.Filters` to the store layer; each dialect driver (`store/db/sqlite/memo.go:57-61`, `store/db/mysql/memo.go:65-69`, `store/db/postgres/memo.go:54-58`) calls `filter.DefaultEngine()` and `filter.AppendConditions(...)` with its own `DialectName`. Inside the package, `Engine.Compile` (`internal/filter/engine.go`) compiles the string in a CEL environment built from a `Schema` (`internal/filter/schema.go`), then `buildCondition` in `internal/filter/parser.go` walks the CEL AST into a dialect-agnostic condition tree (`internal/filter/ir.go`); `Program.Render` (`internal/filter/render.go`) then turns that tree into a dialect-specific SQL fragment plus args, using per-dialect expression templates in the schema (e.g. `CONCAT(...)`/`UNIX_TIMESTAMP(...)` for MySQL vs `||` for SQLite/Postgres) and dialect-appropriate placeholders.

So: one CEL parse produces one intermediate condition tree, and SQL divergence is confined to the render step's per-dialect templates — the same compiled program renders for SQLite, MySQL, or Postgres depending on the `RenderOptions.Dialect` the driver passes.
