Frontend API requests go through a ConnectRPC client interceptor that attaches a bearer token and transparently refreshes it, and the Go backend validates those tokens in a shared auth package.

- **Interceptor path:** `web/src/connect.ts` — the `authInterceptor` (line 156) is installed on the shared Connect transport used by all service clients. It calls `getRequestToken()` to fetch/refresh the token, sets `Authorization: Bearer <token>`, and on a `Code.Unauthenticated` error does a one-shot refresh-and-retry (marked via the `X-Retry` header) before redirecting to login.
- **Token kinds:** two — a short-lived **access token** (JWT kept in memory via `web/src/auth-state.ts`, sent as the `Authorization` bearer header, refreshed proactively when near expiry and reactively on 401) and a **refresh token** (HttpOnly cookie sent automatically via `credentials: "include"`, used by the `AuthService.RefreshToken` RPC over a separate interceptor-free transport to mint new access tokens). The backend additionally accepts personal access tokens as bearers, but the interceptor itself manages the access/refresh pair.
- **Backend validation package:** `server/auth` — `authenticator.go` (`AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, `AuthenticateByPAT`), `token.go` (`ParseAccessTokenV2`, `ParseRefreshToken`), and `extract.go` (`ExtractBearerToken`). It's invoked server-side by the `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208`, which delegates to the `Authorizer` in `server/router/api/v1/authz.go`.

Answer format: `web/src/connect.ts`; access token (JWT bearer) + refresh token (cookie), with PATs also accepted server-side; `server/auth`.
