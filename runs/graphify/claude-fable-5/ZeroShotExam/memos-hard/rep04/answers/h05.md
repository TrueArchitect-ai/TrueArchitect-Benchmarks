**Mechanism: explicit Go code** — each database driver's `DeleteUser` transaction issues direct `DELETE FROM reaction ...` statements. There is no database-level rule for reactions: the `reaction` table has no foreign key at all (the only `ON DELETE CASCADE` in the schema is on `memo_share.memo_id`, not reactions).

Evidence locations:

- `store/db/sqlite/user_delete.go:92-127` — `deleteUserTargetsTx` runs inside the `DeleteUser` transaction and calls both `deleteReactionsByContentIDsTx` (line 96, removes reactions *on* the user's memos: `DELETE FROM reaction WHERE content_id IN (...)`, line 383) and `deleteReactionsByCreatorTx` (line 102, removes reactions the user *made*: `DELETE FROM reaction WHERE creator_id = ?`, line 401).
- `store/db/mysql/user_delete.go:96,102,417,437` and `store/db/postgres/user_delete.go:96,102,380,400` — the MySQL and Postgres drivers have the same two explicit reaction-delete helpers.
- `store/user.go:171-172` — `Store.DeleteUser` dispatches to the driver implementation above.
- Schema: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98` — the `reaction` table definition has `creator_id INTEGER NOT NULL` with no `FOREIGN KEY`/`REFERENCES` clause, so no cascade could apply. A grep for `FOREIGN KEY|REFERENCES` across all three `LATEST.sql` files hits only `memo_share`.
