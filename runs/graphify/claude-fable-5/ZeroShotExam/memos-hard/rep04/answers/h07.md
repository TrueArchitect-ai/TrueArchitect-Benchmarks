The route `GET /file/users/:identifier/avatar` serves another user's profile image. The image bytes are not a separate file — they're stored inline as a base64 data URI in the `user.avatar_url` column, which the handler decodes and streams. Each hop from serving handler down to that column:

`serveUserAvatar()` — server/router/fileserver/fileserver.go:168
`getUserByUsername()` — server/router/fileserver/fileserver.go:715
`Store.GetUser()` — store/user.go:148
`Store.ListUsers()` — store/user.go (calls `s.driver.ListUsers`)
`DB.ListUsers()` — store/db/sqlite/user.go:88 (SQL `SELECT ... avatar_url ... FROM user`; MySQL/Postgres equivalents at store/db/mysql/user.go:84, store/db/postgres/user.go:87)
`user.avatar_url` column — the stored data (base64 data URI), scanned into `User.AvatarURL`

Back in the handler, `serveUserAvatar` then calls `parseDataURI()` (fileserver.go:~770) to decode `user.AvatarURL` into `imageType`/`imageData` and returns it via `c.Blob(...)`.

Notes on the path:
- The route is registered in `RegisterRoutes` at server/router/fileserver/fileserver.go:124.
- Access control for cross-user reads is in `serveUserAvatar` itself: if the instance disallows anonymous access (`s.Profile.AllowAnonymous()` is false), it requires an authenticated viewer via `getCurrentUser` → `authenticator.AuthenticateToUser`; otherwise any user's avatar is public.
- `Store.GetUser`/`ListUsers` also populate `s.userCache`, so a repeat request can be served from that in-memory cache rather than re-hitting the driver.
