**Mechanism: explicit Go code** — reactions are deleted by explicit `DELETE` statements inside the user-deletion transaction in each database driver. There is no database-level rule: the `reaction` table has no foreign key or `ON DELETE CASCADE` at all.

What I checked:

1. **Go deletion code** — each driver's `DeleteUser` implementation runs a multi-step transaction (`deleteUserTargetsTx`) that removes reactions in two ways:
   - `deleteReactionsByCreatorTx` executes `DELETE FROM reaction WHERE creator_id = ?` — removes the reactions the deleted user authored (`store/db/sqlite/user_delete.go:400-401`, `store/db/postgres/user_delete.go:400-401`, `store/db/mysql/user_delete.go:437-438`).
   - `deleteReactionsByContentIDsTx` executes `DELETE FROM reaction WHERE content_id IN (...)` — also removes anyone's reactions on the deleted user's memos (`store/db/sqlite/user_delete.go:380-383`, and the parallel postgres/mysql files).
   - Both are invoked from `deleteUserTargetsTx` (e.g. `store/db/sqlite/user_delete.go:96` and `:102`), reached via each driver's `DeleteUser` (`store/db/postgres/user_delete.go:29`), which is called from the store layer's `Store.DeleteUser` (`store/user.go`).

2. **Database schema** — the `reaction` DDL contains only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint, with no `REFERENCES`, foreign key, cascade, or trigger, in all three backends: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-97`, `store/migration/mysql/LATEST.sql:91-97` (and the original `0.20/00__reaction.sql` migrations). A grep for `REFERENCES`/`FOREIGN` around the reaction table confirmed nothing database-level exists, so cleanup depends entirely on the application code above.
