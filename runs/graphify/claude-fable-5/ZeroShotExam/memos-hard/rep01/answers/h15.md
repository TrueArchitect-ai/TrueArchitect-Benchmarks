Memo visibility (Private / Protected / Public) is enforced independently at several server surfaces, not just one central place:

- gRPC/REST API memo read path — `server/router/api/v1/memo_service.go` (the visibility check in the memo-access helper at ~lines 55–66 rejects anonymous access to non-public memos and non-creator access to private ones; `ListMemos` restricts `VisibilityList` at ~lines 219–225)
- API sub-services that re-check visibility before related operations — `server/router/api/v1/memo_service_comments.go` (comment creation, ~lines 33–43), `server/router/api/v1/reaction_service.go` (~lines 16–30, 69–82), `server/router/api/v1/memo_relation_service.go` (~lines 36, 109–111), and `server/router/api/v1/memo_attachment_service.go` (~line 213)
- Attachment API access control — `server/router/api/v1/attachment_service.go` (`checkAttachmentAccess`, ~lines 421–455: linked attachments inherit the memo's visibility rules)
- Attachment/file HTTP server — `server/router/fileserver/fileserver.go` (~lines 660–705: public memos served anonymously only if the instance allows it, share-token fallback, private memos restricted to creator or admin)
- SSE real-time event delivery — `server/router/api/v1/sse_hub.go` (`canReceive`, ~lines 134–144: private-memo events delivered only to the creator or an admin)
- RSS feeds — `server/router/rss/rss.go` (lines 90 and 141: queries hard-code `VisibilityList: []store.Visibility{store.Public}`, so only public memos appear)
- Notification/email delivery — `server/notification/email.go` (`canViewerAccessMemo`, line 306) and `server/router/api/v1/user_service_notifications.go` (`canViewerAccessMemo`, line 302), which suppress memo content the receiver isn't allowed to view

That's at least five clearly distinct surfaces (API service layer, attachment API, fileserver, SSE, RSS) plus the notification path, each enforcing the same visibility rules in its own code.
