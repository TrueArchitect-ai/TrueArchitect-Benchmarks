**Mechanism: explicit Go code.** When a user is deleted, the store-layer `DeleteUser` implementation for each database driver runs explicit `DELETE FROM reaction ...` SQL statements inside the delete-user transaction — there is no database-level cascade, because the `reaction` table has no foreign keys at all.

What I checked:

1. **The delete path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver's `DeleteUser`. In the SQLite driver (`store/db/sqlite/user_delete.go`), `deleteUserTargetsTx` explicitly removes reactions in two ways within the transaction:
   - `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`) — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user made anywhere.
   - `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-388`) — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions (by anyone) on the user's memos and their comment tree.

2. **The other drivers do the same.** The MySQL driver has identical statements at `store/db/mysql/user_delete.go:420` and `:438`, and Postgres at `store/db/postgres/user_delete.go:383` and `:401`.

3. **No database-level rule.** The `reaction` table definitions in `store/migration/sqlite/LATEST.sql:92-99` and `store/migration/postgres/LATEST.sql:91-98` (MySQL is equivalent) declare only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY` and no `ON DELETE CASCADE`, so the database itself would not remove anything.
