I have the complete trace. The avatar image itself is stored inline as a base64 data URI in the `user.avatar_url` column (not on disk/S3 like attachments), so the data layer is the `user` table row read.

h07.
The browser hits `GET /file/users/:identifier/avatar`, which the fileserver resolves the requested user's `avatar_url` (a base64 data URI stored in the `user` table), decodes it, and writes the bytes to the response. Each hop:

`FileServerService.RegisterRoutes` (route `GET /file/users/:identifier/avatar`) — server/router/fileserver/fileserver.go:124
`FileServerService.serveUserAvatar` (serving handler) — server/router/fileserver/fileserver.go:168
`FileServerService.getUserByUsername` — server/router/fileserver/fileserver.go:715
`Store.GetUser` — store/user.go:148
`Store.ListUsers` — store/user.go:136
`(*DB).ListUsers` (SQL driver; sqlite shown, also postgres/mysql) — store/db/sqlite/user.go:88
`d.db.QueryContext` — SELECT `avatar_url` … FROM `user`, scanned into `User.AvatarURL` — store/db/sqlite/user.go:173

Back in the handler, `FileServerService.parseDataURI` (server/router/fileserver/fileserver.go:737) decodes the `avatar_url` data URI and `c.Blob` returns the image bytes. Postgres/MySQL equivalents of the last two hops: store/db/postgres/user.go:87 and store/db/mysql/user.go:84.

Note the stored data for a profile image is the `avatar_url` column in the `user` table itself (a `data:<type>;base64,...` string) — unlike memo attachments, which route through `GetAttachment` to local disk / S3 / DB blob.
