**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction ...` statements inside the per-database `DeleteUser` transaction — not by any database-level rule. In fact, the `reaction` table has no foreign key at all, so a DB cascade would be impossible.

What I checked:

**1. The explicit Go deletes.** `Store.DeleteUser` (`store/user.go:171`) dispatches to a driver-specific `DeleteUser` that runs a single transaction deleting all user-owned data. In each of the three drivers, that transaction deletes reactions in two ways — reactions the user made (`deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = ?`) and reactions anyone made on the user's memos (`deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)`, using content IDs built from the user's memo tree):

- SQLite: `store/db/sqlite/user_delete.go:96,102` (call sites) and `store/db/sqlite/user_delete.go:380-403` (the SQL)
- MySQL: `store/db/mysql/user_delete.go:96,102,417-438`
- Postgres: `store/db/postgres/user_delete.go:96,102,380-401`

**2. The schema, to rule out a database-level rule.** The `reaction` table definition in `store/migration/postgres/LATEST.sql:91-97`, `store/migration/sqlite/LATEST.sql:92-98`, and `store/migration/mysql/LATEST.sql:91-95` (and the original `0.20/00__reaction.sql` migrations) contains only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY` and no `ON DELETE CASCADE`. A cascade grep across `store/migration/` shows `ON DELETE CASCADE` clauses exist for other tables (e.g., `memo_share` → `memo`), but none reference `reaction`.

So: reactions survive only until the explicit Go transaction removes them; nothing at the database layer would clean them up on its own.
