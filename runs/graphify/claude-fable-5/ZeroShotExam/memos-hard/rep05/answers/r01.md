**Premise correction:** There is no Redis in this repository. A search across the codebase (Go sources, configs, `go.mod`) finds no Redis client, connection string, or dependency anywhere. The cache layer is a homegrown, thread-safe **in-memory** cache built on `sync.Map`, defined in `store/cache/cache.go` — so there is no Redis connection to configure.

**Actual mechanism and TTL for user entries:**

- The cache implementation lives in `store/cache/cache.go`. It stores items with an expiration timestamp (`item.expiration`), lazily evicts expired entries on `Get` (`store/cache/cache.go:135-144`), and runs a background `cleanupLoop` goroutine on a ticker (`store/cache/cache.go:200-215`).
- The caches are instantiated in `store/store.go:38-56` (`Store.New`), which creates three separate caches — `instanceSettingCache`, `userCache`, and `userSettingCache` — all sharing one hardcoded config: **`DefaultTTL: 10 * time.Minute`**, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store/store.go:39-44`). The same defaults also appear in `cache.DefaultConfig()` at `store/cache/cache.go:57-64`.
- User entries are written to `userCache` via plain `Set` (e.g. `store/user.go:98`, with the key built by `userCacheKey()` at `store/user.go:88`), and `Set` delegates to `SetWithTTL` using the config's default (`store/cache/cache.go:93-95`).

**So the TTL that applies to user entries is 10 minutes**, enforced in-process — not by Redis. The config is compiled in; there's no external configuration file or environment variable controlling it. Additionally, if the cache exceeds 1000 items, the oldest ~20% are evicted early regardless of TTL (`cleanupOldest`, `store/cache/cache.go:253`).
