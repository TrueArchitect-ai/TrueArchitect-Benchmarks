A browser request for another user's profile image (`GET /file/users/:identifier/avatar`) is served entirely from the `user.avatar_url` column, which holds the image as a base64 `data:` URI — there is no separate blob/attachment store for avatars. Each hop from handler to data layer:

`fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` — server/router/fileserver/fileserver.go:124
`serveUserAvatar` — server/router/fileserver/fileserver.go:168
`getUserByUsername` — server/router/fileserver/fileserver.go:715
`Store.GetUser` — store/user.go:148
`Store.ListUsers` — store/user.go:136
`DB.ListUsers` (SQL `SELECT ... avatar_url ... FROM user WHERE username = ?`) — store/db/sqlite/user.go:88

The handler then decodes the stored value in place: `parseDataURI(user.AvatarURL)` (server/router/fileserver/fileserver.go:196, defined at :737) base64-decodes the data URI and `c.Blob(...)` (fileserver.go:209) writes the bytes to the response. So the "stored data" reached is the `avatar_url` field of the `user` row itself — the profile image is inlined there, not fetched from a filesystem or attachments table.
