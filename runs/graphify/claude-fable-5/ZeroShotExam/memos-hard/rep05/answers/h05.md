h05.

**Explicit Go code** — when a user is deleted, their emoji reactions are removed by hand-written `DELETE` statements inside the user-deletion transaction, not by any database rule.

**Evidence checked:**

1. **The Go deletion path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver interface (`store/driver.go:48`). Each of the three database drivers implements a transactional `DeleteUser` that explicitly deletes reactions in two ways:
   - `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` — this is the user's own reactions. Found identically in `store/db/mysql/user_delete.go:437-440`, `store/db/postgres/user_delete.go:400-401`, and `store/db/sqlite/user_delete.go:400-401`.
   - `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` (`store/db/mysql/user_delete.go:417-425` and line 383 in the postgres/sqlite counterparts) — this removes *other users'* reactions on the deleted user's memos.
   
   Both are called from `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:96` and `:102`, mirrored at line 102 in the other drivers) inside the same transaction that deletes the user row.

2. **No database-level rule.** The `reaction` table schema has no foreign key at all — just a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. The only `ON DELETE CASCADE` in the schemas belongs to `memo_share.memo_id → memo(id)` (e.g. `store/migration/mysql/LATEST.sql:108`), which is unrelated to reactions. So a raw `DELETE FROM user` would leave reactions orphaned; cleanup happens only because the Go code does it explicitly.
