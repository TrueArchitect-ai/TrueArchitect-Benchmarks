**Mechanism: explicit Go code** (inside the `DeleteUser` transaction). There is no database-level cascade — the `reaction` table declares no foreign key / `ON DELETE` rule on `creator_id`, so removal is done entirely by hand-written `DELETE` statements.

Evidence locations:

- **Explicit Go deletion, called from the delete-user flow (sqlite):** `store/db/sqlite/user_delete.go:96` and `:102` invoke `deleteReactionsByContentIDsTx` and `deleteReactionsByCreatorTx`. Those helpers run raw `DELETE FROM reaction WHERE content_id IN (...)` (`store/db/sqlite/user_delete.go:380-388`) and `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`). So the user's own reactions (by `creator_id`) *and* reactions on the user's deleted content (by `content_id`) are removed. The same helpers exist in the MySQL and Postgres implementations (`store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`, both flagged by grep for "reaction").

- **No DB-level rule:** the `reaction` table schema defines only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE` constraint — no `FOREIGN KEY` and no `ON DELETE CASCADE` — across all three engines: `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-97`.

Conclusion: a deleted user's emoji reactions are removed by explicit Go code within the delete-user transaction, not by any database cascade.
