**Premise correction:** Neither. The webhook delivery workers do not consume from an external message broker at all — there is no NATS and no RabbitMQ in this codebase (a repo-wide search finds no such dependency in `go.mod` and no client code). So there is no broker "queue" declaration to point to.

**Actual mechanism:** Delivery is handled entirely in-process using a bounded Go channel plus a fixed pool of goroutine workers, all in `internal/webhook/webhook.go`:
- The "queue" is a buffered channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`.
- The workers are 4 goroutines started in `init()`, each ranging over that channel and calling `Post` to perform the HTTP delivery — `internal/webhook/webhook.go:42-55`.
- Producers enqueue via `PostAsync`, which does a non-blocking send onto the channel and drops the event (with a warning) if the buffer is full — `internal/webhook/webhook.go:184-196`.

So the flow is: RPC handler → `webhook.PostAsync` → in-memory channel `asyncPostQueue` (capacity 128) → one of 4 in-process worker goroutines → `webhook.Post` (`internal/webhook/webhook.go:120`). This is process-local and not durable — nothing survives a restart, and no broker is involved.
