**Premise correction: neither. There is no external message broker involved in webhook delivery — no NATS, no RabbitMQ (and no AMQP/Kafka anywhere in the codebase; a repo-wide search for `nats`, `rabbitmq`, `amqp`, `kafka` in non-test Go files returns nothing). So there is no broker-declared queue to point to.**

**Actual mechanism:** Webhook delivery is fully in-process. The "queue" is a **buffered Go channel** declared at `internal/webhook/webhook.go:39`:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

A package `init()` at `internal/webhook/webhook.go:42-55` spawns **4 goroutine workers**, each ranging over that channel and calling `Post` (`internal/webhook/webhook.go:120`) to perform the actual outbound HTTP POST. Producers enqueue onto the channel via `PostAsync` (`internal/webhook/webhook.go:184`), which is what the memo RPC dispatchers call (e.g. `server/router/api/v1/memo_service_webhooks.go:43,71`). The buffer holds up to 128 pending payloads; there is no persistence, no network broker, and no externally-declared queue — everything lives in the server process's memory.
