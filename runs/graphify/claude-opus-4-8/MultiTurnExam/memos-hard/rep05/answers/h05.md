**Mechanism — explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements issued inside the `DeleteUser` transaction, not by any database-level cascade rule.

Evidence locations:

- **Postgres** — `store/db/postgres/user_delete.go`. The transaction orchestrator `deleteUserTargetsTx` explicitly calls two reaction deletions (lines 96 and 102):
  - `deleteReactionsByContentIDsTx` (defined `store/db/postgres/user_delete.go:380`) → `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions *on* the deleted user's memos (content IDs built as `"memos/"+uid` at line 512-518).
  - `deleteReactionsByCreatorTx` (defined `store/db/postgres/user_delete.go:400`) → `DELETE FROM reaction WHERE creator_id = $1`, removing reactions the user *made*.
- **SQLite** — same pattern, `store/db/sqlite/user_delete.go:96,102` (helpers at lines 380 and 400).
- **MySQL** — same pattern, `store/db/mysql/user_delete.go:96,102` (helpers at lines 417 and 437).

What I checked to rule out a DB-level rule: I grepped `store/migration` for foreign-key / `ON DELETE CASCADE` clauses referencing the `reaction` table and found none, so removal is not enforced by the schema. It is handled uniformly in application code across all three storage drivers.
