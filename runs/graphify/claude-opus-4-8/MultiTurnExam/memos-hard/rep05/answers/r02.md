**Premise correction: there is no per-user API rate-limiting middleware in this codebase — it does not exist, so there is nothing to register and no request limits to report.**

Evidence:
- A repo-wide search for rate-limiting (`rate.?limit`, `ratelimit`, `throttle`, `tollbooth`, `golang.org/x/time/rate`, `limiter`) in non-test Go code returns exactly one hit, and it is only a doc-comment aspiration — "Rate limit email sending to prevent abuse" at `internal/email/doc.go:86` — not an implemented HTTP/gRPC middleware.
- The middleware/interceptor stack that *is* registered contains no rate limiter. The Echo server registers only `middleware.Recover()` and the CORS middleware (`server/server.go:51-52`, with CORS defined in `server/cors.go`). The API layer uses auth interceptors (`server/router/api/v1/authz.go`, `connect_interceptors.go`) and an `Authorizer`, but none impose request-count limits.

The only per-request throttling that exists is **concurrency limiting via weighted semaphores**, which is a different mechanism (bounding simultaneous work, not requests-per-user-per-time): thumbnail generation is capped in the fileserver (`server/router/fileserver/fileserver.go:107,448`) and image processing is capped in the attachment service (`server/router/api/v1/attachment_service_image.go:71`, semaphore set to weight 2 in `server/router/api/v1/v1.go:60`). These are not user-scoped rate limits.
