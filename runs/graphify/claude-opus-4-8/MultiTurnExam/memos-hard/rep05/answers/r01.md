**Premise correction:** There is no Redis anywhere in the cache layer — in fact, no Redis in the codebase at all (a repo-wide search for `redis` in non-test Go files returns nothing). The premise that a "Redis connection for the cache layer" exists and needs configuring is false. The caches are process-local, in-memory only.

**Actual mechanism:** The cache is an in-memory implementation in `store/cache/cache.go` — a `*cache.Cache` backed by a map with per-item `expiration` timestamps (`item` struct at `store/cache/cache.go:34`) and a background cleanup goroutine, exposed via the `cache.Interface` (`store/cache/cache.go:10`). There is no network connection, host, or DSN to configure; the only "configuration" is the in-process `cache.Config` (DefaultTTL, CleanupInterval, MaxItems).

The user cache (`Store.userCache`) is constructed in `store.New` at `store/store.go:52` using the shared `cacheConfig` defined at `store/store.go:40-45`. That config sets **`DefaultTTL: 10 * time.Minute`** (store/store.go:41), with a 5-minute cleanup interval and a 1000-item cap. User entries are written via `Store.GetUser`/`ListUsers` using `Set` (the default-TTL path, `store/user.go:143` and `:167`), so **user cache entries live for 10 minutes** (they can also be evicted earlier if the 1000-item `MaxItems` limit is hit). The same 10-minute default applies equally to the instance-setting and user-setting caches, since all three share `cacheConfig`.
