**Premise correction:** There is no Redis in this codebase. A repo-wide search for `redis` finds nothing in the Go source and nothing in `go.mod` — the cache layer is not backed by Redis (or any external cache server). It is an in-process, in-memory cache.

**Actual mechanism:**
- The cache is implemented in `store/cache/cache.go` — a `*cache.Cache` type (a `sync.Map`/map-based store with per-item expiration and a background cleanup goroutine), created via `cache.New(...)`. There is no connection to configure; it lives inside the server process.
- The `Store` constructs three such caches (users, user settings, instance settings) in `store.New` at `store/store.go:39-52`, all using the same `cacheConfig`: `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store/store.go:40-45`). This matches the package default in `cache.DefaultConfig` (`store/cache/cache.go:57-60`).
- User entries are written with `s.userCache.Set(...)` (e.g. `store/user.go:98,122,132,143,167`). `Cache.Set` applies the default TTL (`store/cache/cache.go:93-94` → `SetWithTTL(..., c.config.DefaultTTL)`).

**TTL for user entries: 10 minutes** (the `DefaultTTL` configured for `userCache` in `store/store.go:41`), with expired entries reaped every 5 minutes by the cleanup interval. No per-user custom TTL is used.
