**Mechanism: explicit Go code** — reactions are removed by hand-written `DELETE FROM reaction` statements inside each driver's `DeleteUser` transaction. There is no database-level cascade, because the `reaction` table has no foreign key on `creator_id`.

Evidence locations (what I checked):

1. **Schema — no DB-level rule.** The `reaction` table in all three dialects declares `creator_id` and `content_id` as plain columns with no `FOREIGN KEY`/`ON DELETE`:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`
   
   So a database cascade is not possible.

2. **Explicit Go deletion.** Each driver's user-deletion routine deletes reactions in two ways within the delete transaction — by the deleted user's own reactions (`creator_id`) and by reactions on the deleted user's content (`content_id`, i.e. their memos):
   - sqlite: `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380`, `DELETE FROM reaction WHERE content_id IN ...` at :383) and `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400`, `DELETE FROM reaction WHERE creator_id = ...` at :401); both invoked at `store/db/sqlite/user_delete.go:96` and `:102`.
   - postgres: `store/db/postgres/user_delete.go:380-401`, invoked at `:96`/`:102`.
   - mysql: `store/db/mysql/user_delete.go:417-438`, invoked at `:96`/`:102`.

3. **Entry point.** `Store.DeleteUser` (`store/user.go:171-172`) simply delegates to `s.driver.DeleteUser`, which runs the transaction above.
