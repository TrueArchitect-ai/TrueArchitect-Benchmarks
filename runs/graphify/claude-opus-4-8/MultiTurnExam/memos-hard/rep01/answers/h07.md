A browser GET to `/file/users/:identifier/avatar` reaches stored data through these hops:

- Route registration `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (handler; reads `user.AvatarURL`, decodes it via `parseDataURI`, writes the image bytes with `c.Blob`) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` (builds `store.FindUser{Username: &identifier}`) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (cache check, then delegates to ListUsers) — `store/user.go:148`
- `Store.ListUsers` (delegates to driver, populates user cache) — `store/user.go:136`
- `(*DB).ListUsers` (driver: builds `WHERE username = ?` and queries the `user` table, selecting `avatar_url` among columns) — `store/db/sqlite/user.go:88` (and the matching `store/db/postgres/user.go`, `store/db/mysql/user.go` per the driver selected in `store/db/db.go`)

The stored data itself: the image is not a separate blob/file — it lives inline in the `user` table's `avatar_url` column as a data URI, which `serveUserAvatar` decodes with `parseDataURI` (`server/router/fileserver/fileserver.go:196`) before returning the raw bytes.
