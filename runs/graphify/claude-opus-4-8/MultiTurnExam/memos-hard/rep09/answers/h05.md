**Mechanism: explicit Go code** (not a DB-level cascade). When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the `DeleteUser` transaction — covering both reactions the user *made* (by `creator_id`) and reactions *on the user's deleted content* (by `content_id`). The `reaction` table has no foreign key on `creator_id`, so nothing removes them automatically.

Evidence locations:
- **No DB rule**: `store/migration/sqlite/LATEST.sql:92-98` — the `reaction` table declares only `UNIQUE(creator_id, content_id, reaction_type)`, with no `FOREIGN KEY`/`ON DELETE` on `creator_id` (the only `ON DELETE CASCADE` in that schema is `memo.memo_id`, line 109). Same in `store/migration/postgres/LATEST.sql` and `store/migration/mysql/LATEST.sql`.
- **Explicit Go deletion** (all three drivers): the delete-targets transaction calls `deleteReactionsByContentIDsTx` and `deleteReactionsByCreatorTx` — `store/db/sqlite/user_delete.go:96,102` (defined at `:380`,`:400`, running `DELETE FROM reaction WHERE content_id IN …` / `WHERE creator_id = …`); identical in `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`.
- **Test confirming behavior**: `store/test/user_delete_test.go:97-112,217-220` (`TestDeleteUserCleansRelatedData`) asserts the deleted user's reactions are gone while a peer's reaction is kept.

Answer: **explicit Go code; `store/db/{sqlite,postgres,mysql}/user_delete.go` (`deleteReactionsByCreatorTx` and `deleteReactionsByContentIDsTx`, called at lines 96/102), and the schema `store/migration/*/LATEST.sql` reaction table has no `creator_id` FK/cascade**
