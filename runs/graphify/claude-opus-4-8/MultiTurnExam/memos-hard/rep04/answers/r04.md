**Premise correction:** Neither. The webhook delivery workers do not consume from any external message broker — there is no NATS and no RabbitMQ in this codebase. A repo-wide search for either turns up nothing; the "queue" is an in-process Go channel, not a broker-declared queue.

**Actual mechanism:** Webhook delivery uses an in-memory buffered channel with a fixed pool of goroutine workers, all inside `internal/webhook/webhook.go`:

- The "queue" is a package-level buffered channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`). This is the only queue — capacity 128, in-process, not durable, and not backed by any broker.
- The workers are 4 goroutines started in `init()` that range over that channel and deliver each payload via `Post` (`internal/webhook/webhook.go:42-55`).
- Producers enqueue with `PostAsync`, a non-blocking send that drops the payload (with a warning log) if the channel is full (`internal/webhook/webhook.go:184-196`).
- Actual delivery is a plain outbound HTTP POST via the shared `safeClient` in `Post` (`internal/webhook/webhook.go:120`, send at `webhook.go:152`) — SSRF-guarded by `safeDialContext` (`internal/webhook/webhook.go:59`).

So there is no broker to name and no queue "declaration" in a NATS/RabbitMQ sense; the queue is declared as a Go channel at `internal/webhook/webhook.go:39`, and it lives entirely within the server process.
