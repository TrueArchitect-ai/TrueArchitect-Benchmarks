**Mechanism: explicit Go code** (there is no database-level rule — the `reaction` table has no foreign key or `ON DELETE CASCADE`; deletion is done by hand-written SQL inside the delete-user transaction).

Evidence locations:

- **Entry point:** `Store.DeleteUser` delegates to the driver's `DeleteUser` (`store/user.go:171-181`). The per-driver implementation is `store/db/sqlite/user_delete.go` (mirrored by `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`).
- **Orchestration:** `deleteUserTargetsTx` runs the deletions in one transaction and explicitly calls the reaction cleanup twice (`store/db/sqlite/user_delete.go:92-127`):
  - line 96 → `deleteReactionsByContentIDsTx` — removes reactions **on the deleted user's memos**, matched by `content_id` (`store/db/sqlite/user_delete.go:380-388`, issuing `DELETE FROM reaction WHERE content_id IN (...)`).
  - line 102 → `deleteReactionsByCreatorTx` — removes reactions **made by the deleted user**, matched by `creator_id` (`store/db/sqlite/user_delete.go:400-403`, issuing `DELETE FROM reaction WHERE creator_id = ?`).
- **No DB-level rule:** the `reaction` table definitions in `store/migration/sqlite/LATEST.sql`, `store/migration/mysql/LATEST.sql`, and `store/migration/postgres/LATEST.sql` declare `creator_id`/`content_id` as plain columns with only a `UNIQUE` constraint — no `FOREIGN KEY`/`REFERENCES` and no `ON DELETE CASCADE` — so nothing at the database layer removes reactions automatically. The removal depends entirely on the explicit Go code above.
