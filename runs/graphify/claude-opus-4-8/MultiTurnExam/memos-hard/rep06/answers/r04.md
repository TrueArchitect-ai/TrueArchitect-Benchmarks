**Premise correction:** Neither. The webhook delivery workers do not consume from NATS or RabbitMQ (or any external message broker) — a repo-wide search for `nats`, `rabbitmq`, `amqp`, etc. in the Go source and `go.mod` returns zero hits. There is no broker and no externally-declared queue.

**Actual mechanism:** The "queue" is an in-process, buffered Go channel local to the webhook package. In `internal/webhook/webhook.go`:

- The queue is declared as a buffered channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39` (capacity 128, in memory).
- Four worker goroutines are started in `init()` and range over that channel, calling `Post` for each payload — `internal/webhook/webhook.go:42-54` (loop at `:44-45`).
- Producers enqueue via `PostAsync`, a non-blocking `select` send into the channel that drops the payload (with a warning) if the buffer is full — `internal/webhook/webhook.go:184-196` (send at `:190`).

So webhook delivery is handled entirely by in-process goroutines draining an in-memory channel; it is not backed by any message broker, and the state does not survive a process restart.
