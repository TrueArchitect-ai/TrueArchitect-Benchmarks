**concrete method — path:** `(*DB).CreateMemo` in the **sqlite** driver — `store/db/sqlite/memo.go:16`. It builds and executes the actual `INSERT INTO \`memo\` ... RETURNING ...` via `d.db.QueryRowContext(ctx, stmt, args...)` at `store/db/sqlite/memo.go:26-27`.

**determination method (how I ruled out the postgres/mysql candidates):**

1. There are three candidate `(*DB).CreateMemo` implementations — `store/db/sqlite/memo.go:16`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go` — all satisfying the `store.Driver` interface. The application never calls them by name; `Store.CreateMemo` delegates through the interface: `return s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`).

2. Which concrete `s.driver` is bound is decided at startup by the driver-selection factory `NewDBDriver`, a `switch profile.Driver` — `case "sqlite": sqlite.NewDB(profile)` at `store/db/db.go:19-20` (also confirmed in h04 as the only construction site of each driver).

3. So the deciding input is `profile.Driver`. In a default installation with no database flags, the default is `sqlite`: set in `cmd/memos/main.go:122` (`viper.SetDefault("driver", "sqlite")`) and the flag default at `cmd/memos/main.go:130`. With `Driver == "sqlite"` and empty DSN, the profile even defaults the SQLite DSN (`internal/profile/profile.go:110`).

Therefore the factory binds `s.driver` to the sqlite `*DB`, and `s.driver.CreateMemo` dispatches to `store/db/sqlite/memo.go:16`, which runs the SQL INSERT. The postgres/mysql `CreateMemo` methods exist but are unreachable unless `--driver` is changed.
