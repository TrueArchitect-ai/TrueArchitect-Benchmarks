**mechanism: explicit Go code** (application-level `DELETE FROM reaction` statements inside the delete-user transaction), not a database cascade.

Evidence locations:

1. **Schema has no FK/cascade.** The `reaction` table declares `creator_id`/`content_id` as plain columns with only a `UNIQUE(...)` constraint and no `FOREIGN KEY ... ON DELETE CASCADE` — `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-97`, `store/migration/mysql/LATEST.sql:91-98`. So the database itself will not remove reactions when a user row is deleted.

2. **Explicit Go deletes.** In the delete-user transaction, `deleteUserTargetsTx` explicitly removes reactions two ways — `store/db/sqlite/user_delete.go:96` (`deleteReactionsByContentIDsTx`) and `store/db/sqlite/user_delete.go:102` (`deleteReactionsByCreatorTx`):
   - `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` — removes the reactions the deleted user made (`store/db/sqlite/user_delete.go:400-403`).
   - `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` for the user's memos — removes others' reactions on the deleted user's content (`store/db/sqlite/user_delete.go:380-388`).
   These run before the final `DELETE FROM user` at `store/db/sqlite/user_delete.go:461-464`.

3. **Entry point.** `Store.DeleteUser` (`store/user.go:171`) dispatches to the driver implementation `(*DB).DeleteUser` (`store/db/sqlite/user_delete.go:29`), which calls `deleteUserTargetsTx`.

So a deleted user's emoji reactions (and reactions on their content) are removed by explicit Go code, since the reaction table carries no cascading foreign key.
