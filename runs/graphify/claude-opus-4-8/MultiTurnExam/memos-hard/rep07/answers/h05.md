**Mechanism: explicit Go code.** A deleted user's emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the `DeleteUser` transaction — not by any database-level cascade.

Evidence locations:
- `store/db/sqlite/user_delete.go:400` — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user authored.
- `store/db/sqlite/user_delete.go:380` — `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions on the user's deleted memos.
- Both are invoked in the delete orchestration `deleteUserTargetsTx` at `store/db/sqlite/user_delete.go:96` and `:102`, all within the single transaction opened in `DeleteUser` (`store/db/sqlite/user_delete.go:29`). The mysql and postgres drivers have the same structure (`store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`).

What rules out a database-level rule:
- The `reaction` table schema in all three dialects (`store/migration/sqlite/LATEST.sql:92`, `store/migration/postgres/LATEST.sql:91`, `store/migration/mysql/LATEST.sql:91`) defines `creator_id` and `content_id` as plain `NOT NULL` columns with **no `FOREIGN KEY` / `ON DELETE CASCADE`** constraint. So nothing at the DB layer would remove reactions automatically; the explicit Go code is what does it.
