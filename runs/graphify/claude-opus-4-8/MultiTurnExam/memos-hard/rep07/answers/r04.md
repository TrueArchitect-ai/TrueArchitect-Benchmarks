**Premise correction:** The webhook delivery workers do not consume from a message broker at all — neither NATS nor RabbitMQ. There is no NATS, RabbitMQ/AMQP, or Kafka dependency anywhere: `go.mod` declares none, and no `.go` file references any of them. So there is no externally-declared queue.

**Actual mechanism:** Webhook delivery uses a **bounded in-process Go channel** as its queue, entirely within the `internal/webhook` package (`internal/webhook/webhook.go`):
- The "queue" is declared as `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a buffered channel of capacity 128 (`internal/webhook/webhook.go:39`).
- The "workers" are 4 goroutines started in `init()` that range over that channel and call `Post` for each payload (`internal/webhook/webhook.go:42-55`).
- Producers enqueue via `PostAsync`, which does a non-blocking send onto the channel and drops the event (with a warning log) if the buffer is full (`internal/webhook/webhook.go:184-196`).
- Actual delivery happens in `Post` via the SSRF-guarded `safeClient.Do(req)` (`internal/webhook/webhook.go:120`, `:152`).

So it's an in-memory channel + goroutine-pool design, not a broker-backed queue — meaning queued webhooks are not durable and are lost on process restart.
