**Mechanism: explicit Go code (in each DB driver's `DeleteUser` transaction), not a database cascade rule.**

Evidence locations:

- **The schema has no cascade.** The `reaction` table stores `creator_id` and `content_id` as plain `INTEGER/TEXT NOT NULL` columns with only a `UNIQUE(...)` constraint — no foreign key, no `ON DELETE CASCADE`. See `store/migration/sqlite/LATEST.sql:92-99` (identical in `store/migration/postgres/LATEST.sql:91` and `store/migration/mysql/LATEST.sql:91`). So the database will not remove reactions on its own.

- **Explicit Go code does it.** Each driver's user-delete path removes reactions in two ways inside the delete transaction:
  - reactions *on the deleted user's content*: `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)`
  - reactions *made by the user*: `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?`
  
  Both are invoked from the driver's `DeleteUser` flow and defined in all three drivers:
  - SQLite: called at `store/db/sqlite/user_delete.go:96,102`; defined at `store/db/sqlite/user_delete.go:380,400`
  - Postgres: called at `store/db/postgres/user_delete.go:96,102`; defined at `store/db/postgres/user_delete.go:380,400`
  - MySQL: called at `store/db/mysql/user_delete.go:96,102`; defined at `store/db/mysql/user_delete.go:417,437`

- The store-level entry point is `Store.DeleteUser` at `store/user.go:171`, which dispatches to the driver implementations above.

So a deleted user's emoji reactions are removed by explicit `DELETE FROM reaction` statements in Go, covering both reactions they authored and reactions left on their content.
