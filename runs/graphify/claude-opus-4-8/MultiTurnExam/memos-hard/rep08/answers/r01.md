**Premise correction:** There is no Redis anywhere in this codebase. A repository-wide search for `redis` returns zero hits (no import in `go.mod`, no code references). The cache layer is **not** backed by Redis — it's a self-contained, thread-safe **in-memory** cache built on `sync.Map`, defined in `store/cache/cache.go` (`type Cache` at `store/cache/cache.go:66`, backed by `data sync.Map`). So "where the Redis connection is configured" has no answer because no such connection exists.

**Actual mechanism:** The caches are constructed in `Store.New` — `store/store.go:38-54`. Three in-process caches (`instanceSettingCache`, `userCache`, `userSettingCache`) are each created with `cache.New(cacheConfig)` using a single shared `cache.Config`:
- `DefaultTTL: 10 * time.Minute`
- `CleanupInterval: 5 * time.Minute`
- `MaxItems: 1000`
(`store/store.go:40-45`; this matches `cache.DefaultConfig()` at `store/cache/cache.go:55`.)

**TTL for user entries:** User entries live in `userCache`, and every write goes through `s.userCache.Set(...)` (e.g. `store/user.go:98,122,132,143,167`). `Set` applies the cache's default TTL (`Interface.Set` "adds a value with the default TTL", `store/cache/cache.go:12`). Since `userCache` was created with the config above, **user cache entries have a 10-minute TTL**, with a background cleanup sweep every 5 minutes and a 1000-item cap. There is no per-user custom TTL (`SetWithTTL` is not used for user entries).
