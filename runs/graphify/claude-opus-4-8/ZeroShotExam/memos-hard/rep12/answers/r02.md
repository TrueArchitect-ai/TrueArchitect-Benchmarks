**Premise correction:** This repository (the Memos server, a Go/Echo application) has **no per-user API rate-limiting middleware**. The premise of the question does not hold — there is nothing to register, and there are no per-user request limits configured anywhere.

What actually exists:

**HTTP middleware chain** (`server/server.go:51-52`) — the only middleware registered on the Echo server is:
- `middleware.Recover()` (panic recovery)
- `newCORSMiddleware(profile)` (CORS)

Plus an **authentication/authorization** middleware layer, not a rate limiter: the gRPC-Gateway middleware `gatewayAuthMiddleware` and a Connect interceptor, both wired through `NewAuthorizer(...)` in `server/router/api/v1/v1.go:64-100`.

Things that *sound* related but are not per-user API rate limiting:

- **Global concurrency semaphores**, not per-user request-rate limits: `thumbnailSemaphore` (3 concurrent) and `imageProcessingSemaphore` (2 concurrent) in `server/router/api/v1/v1.go:56-57`. These cap simultaneous work process-wide to prevent memory exhaustion — they are not keyed by user and impose no requests-per-interval limit. There's also a `maxAPIRequestBytes = 256 << 20` payload-size constant (`v1.go:18`), which is a body-size cap, not a rate limit.
- **Scheduler middleware** in `internal/scheduler/middleware.go` — this is a cron-job handler middleware pattern (`Recovery`, `Logging`, `Timeout`), for background jobs, unrelated to HTTP APIs or users.
- A lone documentation comment "Rate limit email sending to prevent abuse" in `internal/email/doc.go:86` — advisory text only, with no implementation.

No rate-limiting library (e.g. `golang.org/x/time/rate`, `tollbooth`, etc.) appears in `go.mod`/`go.sum`, and no rate-limiter exists in the `web/` frontend either.

So: **there is no such middleware and no request limits to report.**
