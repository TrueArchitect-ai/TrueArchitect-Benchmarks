The avatar is not a file blob — it's stored inline as a base64 data URI in the `avatar_url` column of the `user` table. A browser request for `GET /file/users/:identifier/avatar` reaches that column through these hops:

`RegisterRoutes()` (route `GET /file/users/:identifier/avatar` → handler) — server/router/fileserver/fileserver.go:124
`serveUserAvatar()` (serving handler; auth-gates, then fetches user, decodes data URI, `c.Blob`) — server/router/fileserver/fileserver.go:168
`getUserByUsername()` (resolves `:identifier` to a user via the store) — server/router/fileserver/fileserver.go:715
`(*Store).GetUser()` (store facade; user cache then list) — store/user.go:148
`(*Store).ListUsers()` → `s.driver.ListUsers()` (delegates to DB driver) — store/user.go:136
`(*DB).ListUsers()` (SQLite driver: `SELECT ... avatar_url ... FROM user`, scans into `user.AvatarURL`) — store/db/sqlite/user.go:88 (SELECT at :159, scan at :189)

Back in the handler, the returned `user.AvatarURL` (a `data:<type>;base64,...` string) is split by `parseDataURI()` (server/router/fileserver/fileserver.go:737) and the decoded bytes are written with `c.Blob(...)` (fileserver.go:209).

Notes:
- The Postgres and MySQL drivers are the equivalent data-layer leaf for those backends (`store/db/postgres/user.go`, `store/db/mysql/user.go`); SQLite is shown above.
- This path differs from attachment serving (`serveAttachmentFile`, fileserver.go:132), which reads real blob storage (local disk / S3 / DB `blob` column) via `store.GetAttachment`. Avatars never hit that; they live entirely in the `user` row.
