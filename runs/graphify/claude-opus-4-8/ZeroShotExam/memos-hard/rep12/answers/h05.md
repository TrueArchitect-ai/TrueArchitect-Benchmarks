**Mechanism: removed by explicit Go code** (this codebase is `memos`, which uses raw per-dialect SQL, not an ORM with cascade rules). When a user is deleted, their emoji reactions are removed by two explicit `DELETE FROM reaction` statements inside the delete-user transaction — covering both reactions the user *authored* and reactions *on the user's memos*.

**Evidence locations** (identical logic in all three DB drivers):

- `store/db/sqlite/user_delete.go:102` — `deleteReactionsByCreatorTx` is called from `deleteUserTargetsTx`; defined at lines `400-403`: `DELETE FROM reaction WHERE creator_id = ?`. This removes reactions the deleted user made.
- `store/db/sqlite/user_delete.go:96` — `deleteReactionsByContentIDsTx` is also called; defined at lines `380-388`: `DELETE FROM reaction WHERE content_id IN (...)`, where the content IDs come from the deleted user's memo tree (`memoContentIDsFromRefs`, line `512`). This removes other people's reactions on the deleted user's memos.
- `store/db/postgres/user_delete.go:96,102` (defs at `380-388` and `400-403`) — same two deletes.
- `store/db/mysql/user_delete.go:96,102` (defs at `417-425` and `437-440`) — same two deletes.

All of this runs inside the single `DeleteUser` transaction (`DeleteUser` → `deleteUserTargetsTx`), so reaction cleanup is committed atomically with the user-row deletion.

What I checked and ruled out:
- **Not a DB-level cascade rule.** The `reaction` table stores its author as `creator_id` and its target as a string `content_id` (e.g. `"memos/<uid>"`), not a foreign key to `user.id`. Because reactions are deleted by explicit code rather than an `ON DELETE CASCADE`, there is no schema-level rule doing this — it's the Go code above. (The presence of a dedicated `deleteReactionsByCreatorTx`/`deleteReactionsByContentIDsTx` for each dialect is itself the evidence that no cascade exists; a cascade would make this code redundant.)
- I confirmed the reaction model/store exists at `store/reaction.go` and dialect files `store/db/{sqlite,postgres,mysql}/reaction.go`, and that the delete path is `DeleteUser` in each `*/user_delete.go`.

One caveat worth noting: the `content_id`-based delete only targets memos owned by the deleted user (and their comment subtree). Reactions the deleted user placed on *other* users' memos are handled separately by the `creator_id` delete — so both directions are covered.
