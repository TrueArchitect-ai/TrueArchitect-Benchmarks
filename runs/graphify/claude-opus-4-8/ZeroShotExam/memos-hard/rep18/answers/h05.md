**Mechanism: explicit Go code.** Emoji reactions are removed by hand-written `DELETE` statements executed inside the user-deletion transaction — there is no database-level cascade backing them up.

**What I checked:**

1. **The delete logic** — each DB backend has a `user_delete.go` that removes reactions two ways, both inside the delete-user transaction:
   - `store/db/sqlite/user_delete.go:96,102` calls `deleteReactionsByContentIDsTx` (line 380 → `DELETE FROM reaction WHERE content_id IN (...)`, i.e. reactions *on* the user's memos) and `deleteReactionsByCreatorTx` (line 400 → `DELETE FROM reaction WHERE creator_id = ?`, i.e. reactions *made by* the user).
   - Identical pair in `store/db/postgres/user_delete.go:96,102` (defs at 380/400) and `store/db/mysql/user_delete.go:96,102` (defs at 417/437).
   - Call site: `deleteUserTargetsTx` in `store/db/sqlite/user_delete.go:92-105`.

2. **The schema** — the `reaction` table has no foreign key or `ON DELETE CASCADE`; `creator_id` and `content_id` are plain `NOT NULL` columns:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`
   
   So the DB does nothing on its own — the cleanup depends entirely on the Go code above. (Original table defs in `store/migration/*/0.20/00__reaction.sql` are likewise FK-free.)

Note this covers both reactions the deleted user authored (`creator_id`) and reactions others left on the deleted user's memos (`content_id`).
