**Premise correction:** There is no Redis anywhere in this codebase. A repo-wide search for `redis` (`grep -rni "redis" --include=*.go`) returns zero matches. The cache layer is **not** backed by Redis — so there is no "Redis connection" to configure.

**Actual mechanism:**

- **The cache is a thread-safe, in-process, in-memory cache.** It's implemented in `store/cache/cache.go` — a `Cache` struct backed by a `sync.Map` with `atomic.Int64` item counting, per-item expiration timestamps, a background cleanup goroutine (`cleanupLoop`/`cleanup`), and a `MaxItems` eviction bound (`cleanupOldest`). No network client, no external store.

- **"Connection"/instantiation is configured in `store/store.go:38-53`.** `Store.New()` builds one `cache.Config` and constructs three separate caches via `cache.New(cacheConfig)`, including `userCache` (`store/store.go:52`). The config it passes (`store/store.go:40-45`) is:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  - `OnEviction: nil`

  (The package also ships a `DefaultConfig()` at `store/cache/cache.go:57-64` with the same values, but `store.New` supplies its own literal config rather than calling it.)

- **TTL for user entries = 10 minutes.** User entries are written through `s.userCache.Set(...)` in `store/user.go` (lines 98, 122, 132, 143, 167). `Set` uses the cache's `DefaultTTL` (`cache.go:93-95`) — none of the user-cache writes call `SetWithTTL`, so every user entry gets the configured default of **10 minutes**. Expiry is enforced lazily on `Get` (`cache.go:135-144`) and proactively by the cleanup goroutine every 5 minutes. Entries are also explicitly invalidated on delete via `s.userCache.Delete(...)` (`store/user_delete.go:40`).

Cache keys are just the stringified user ID (`userCacheKey()` at `store/user.go:88-90`).
