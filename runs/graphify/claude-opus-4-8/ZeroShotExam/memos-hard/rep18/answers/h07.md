The browser hits `GET /file/users/:identifier/avatar` (registered in `RegisterRoutes`, `server/router/fileserver/fileserver.go:124`). Each hop from serving handler down to stored data:

1. `serveUserAvatar` — server/router/fileserver/fileserver.go:168
2. `getUserByUsername` — server/router/fileserver/fileserver.go:715
3. `Store.GetUser` — store/user.go:148
4. `Store.ListUsers` — store/user.go:136
5. `(*DB).ListUsers` — store/db/sqlite/user.go:88

The stored data is the `avatar_url` column of the `user` table: the SQL `SELECT ... avatar_url ... FROM user` at store/db/sqlite/user.go:151-165 is scanned into `user.AvatarURL` (store/db/sqlite/user.go:189). Back in the handler, that value (a `data:` URI) is decoded by `parseDataURI` (fileserver.go:196 → fileserver.go:737) and written to the response with `c.Blob` (fileserver.go:209).

Notes:
- The identifier is looked up by username only (`store.FindUser{Username: &identifier}`, fileserver.go:716), so any user's avatar is reachable; access control is only the anonymous-instance gate at fileserver.go:173-181.
- `store.GetUser`/`ListUsers` are driver-dispatched (`s.driver.ListUsers`, store/user.go:137). I traced the SQLite driver; the Postgres and MySQL equivalents are `store/db/postgres/user.go` and `store/db/mysql/user.go`, which read the same `avatar_url` column.
