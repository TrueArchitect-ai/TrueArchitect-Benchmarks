**Mechanism: by explicit Go code** (inside the user-delete transaction), not by any database-level rule.

When a user is deleted, `DeleteUser` runs a transaction that explicitly issues `DELETE FROM reaction` statements. Two functions handle reactions:

- `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the deleted user *made*.
- `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on* the deleted user's memos.

Both are called from the driver's `DeleteUser` transaction body. This is duplicated identically across all three DB backends.

**Evidence locations:**

- SQLite: `store/db/sqlite/user_delete.go:102` (calls `deleteReactionsByCreatorTx`) and `:96` (calls `deleteReactionsByContentIDsTx`); implementations at `:400-402` and `:380-388`.
- Postgres: `store/db/postgres/user_delete.go:96`, `:102`, `:380`, `:400`.
- MySQL: `store/db/mysql/user_delete.go:96`, `:102`, `:417`, `:437`.
- Entry point: `store/user.go:171` `DeleteUser` → delegates to `s.driver.DeleteUser`.

**Why it is not a database rule** — the `reaction` table declares `creator_id INTEGER NOT NULL` with no foreign key and no `ON DELETE CASCADE`; in fact there is no `REFERENCES user` foreign key anywhere in the schema:
- `store/migration/sqlite/LATEST.sql:92-100` (reaction table definition — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint, no FK).
- A grep for `REFERENCES user(...)` across `store/migration/{sqlite,postgres,mysql}/LATEST.sql` returns nothing, so no cascade exists at the DB level for reactions (or for user references generally).

So removal happens purely through the explicit Go `DELETE` statements in the transaction; if that code were absent, the reactions would remain (no DB cascade would clean them up).
