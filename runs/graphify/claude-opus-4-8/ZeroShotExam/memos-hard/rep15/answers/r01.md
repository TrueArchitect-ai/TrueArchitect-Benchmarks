**Premise correction:** There is no Redis anywhere in the cache layer. The cache is a **thread-safe in-memory cache** built on Go's `sync.Map` — no external cache server, no Redis client, no connection string. The premise that a "Redis connection" is configured somewhere is false.

**Actual mechanism:**

- The cache implementation lives in `store/cache/cache.go`. `Cache` is defined at `store/cache/cache.go:66-73` as an in-process struct holding a `sync.Map` for data plus an atomic item counter and a background cleanup goroutine (`cleanupLoop`, started in `New()` at `store/cache/cache.go:83`). Expiry is enforced two ways: lazily on `Get()` (`store/cache/cache.go:135`) and by a periodic sweep in `cleanup()` (`store/cache/cache.go:218`). There is no network I/O — the "connection" doesn't exist.

- The user cache is wired up in `store/store.go`. The `Store.New` constructor builds a `cache.Config` inline (`store/store.go:40-45`) and instantiates `userCache: cache.New(cacheConfig)` at `store/store.go:52` (three caches share the same config: instance-setting, user, and user-setting). It's closed in `Store.Close` at `store/store.go:75`.

**TTL for user entries: 10 minutes.** All user writes go through the store methods in `store/user.go` — `CreateUser`, `UpdateUser`, `ListUsers`, `GetUser`, etc. — which all call `s.userCache.Set(...)` (e.g. `store/user.go:98`, `:132`, `:143`, `:167`). `Set` uses the cache's **default** TTL (`SetWithTTL` with `c.config.DefaultTTL`, `store/cache/cache.go:93-95`), and `DefaultTTL` is configured as `10 * time.Minute` in `store/store.go:41`. No user entry uses a custom TTL. (Cleanup runs every 5 minutes; max 1000 items with oldest-eviction.) Cache keys are just the stringified user ID via `userCacheKey()` at `store/user.go:88`.
