The request `GET /file/users/:identifier/avatar` is served natively (not through the gRPC/API layer). The avatar is stored inline in the `user` table's `avatar_url` column as a base64 `data:` URI — there is no separate blob/file store for it. Each hop from handler to stored data:

- `FileServerService.RegisterRoutes` — server/router/fileserver/fileserver.go:124 (registers `GET /file/users/:identifier/avatar` → `serveUserAvatar`)
- `FileServerService.serveUserAvatar` — server/router/fileserver/fileserver.go:168 (serving handler; reads `user.AvatarURL`, then `parseDataURI` + `c.Blob`)
- `FileServerService.getUserByUsername` — server/router/fileserver/fileserver.go:715 (calls `s.Store.GetUser` with `FindUser{Username: &identifier}`)
- `Store.GetUser` — store/user.go:148 (delegates to `ListUsers`)
- `Store.ListUsers` — store/user.go:136 (calls `s.driver.ListUsers`)
- `DB.ListUsers` — store/db/sqlite/user.go:88 (runs `SELECT ... avatar_url ... FROM user WHERE username = ?`)
- `avatar_url` column of the `user` table — store/db/sqlite/user.go:159 (the stored data: the avatar as a base64 `data:` URI)

Notes on the trace:
- The store layer has a `userCache`; on a cache miss the driver query above is what fetches the row. `GetUser` caches by ID only, so a lookup by username still hits the driver (store/user.go:148–168).
- The driver shown is the SQLite implementation; the equivalent lives in `store/db/postgres/user.go` and `store/db/mysql/user.go` for those backends (selected via `s.driver`).
- Access control before the data hop: `serveUserAvatar` requires an authenticated viewer only when `s.Profile.AllowAnonymous()` is false (server/router/fileserver/fileserver.go:173–181) — otherwise any user's avatar is public.
