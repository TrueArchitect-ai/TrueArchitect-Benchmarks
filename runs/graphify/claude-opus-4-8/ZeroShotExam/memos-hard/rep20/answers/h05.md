**Mechanism: by explicit Go code** (not a database-level rule). When a user is deleted, their emoji reactions are removed in two distinct ways inside the `DeleteUser` transaction — both reactions *on* the deleted user's memos and reactions *authored by* the deleted user (on anyone's memos).

**Evidence:**

- `store/db/sqlite/user_delete.go:92-127` — `deleteUserTargetsTx` orchestrates the deletion and explicitly calls two reaction-deleting helpers:
  - Line 96: `deleteReactionsByContentIDsTx(...)` — removes reactions on the user's memos and their comment subtree.
  - Line 102: `deleteReactionsByCreatorTx(...)` — removes reactions the user made anywhere.
- The two helpers, both raw `DELETE` statements:
  - `store/db/sqlite/user_delete.go:380-388` — `DELETE FROM reaction WHERE content_id IN (...)` (content IDs built as `"memos/"+uid` at line 512-518).
  - `store/db/sqlite/user_delete.go:400-403` — `DELETE FROM reaction WHERE creator_id = ?`.
- The MySQL and Postgres drivers mirror this exactly: `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go` contain the same `deleteReactionsByContentIDsTx` / `deleteReactionsByCreatorTx` calls.
- Store entry point: `store/user.go:171` (`Store.DeleteUser`) delegates to the driver; `store/user_delete.go` holds the `DeleteUserResult` types.

**Why it's not a DB-level rule:** the `reaction` table has *no* foreign keys or `ON DELETE CASCADE` in any driver — see `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, and `store/migration/mysql/LATEST.sql:91-98`. (By contrast, `memo_share` in the same files *does* declare `FOREIGN KEY ... ON DELETE CASCADE`, confirming reactions deliberately do not — so the cleanup must be, and is, done in Go.)
