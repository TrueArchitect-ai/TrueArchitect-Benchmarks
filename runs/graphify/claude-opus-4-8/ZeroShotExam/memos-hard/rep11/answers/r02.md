**Premise correction: there is no per-user API rate-limiting middleware in this repository.** The question assumes one exists and is registered somewhere with configurable request limits — it does not.

What actually exists:

- **The registered API middleware/interceptor chain** is in `server/router/api/v1/v1.go:133-137`, applied via `connect.WithInterceptors(...)`. It consists of exactly four interceptors, none of which rate-limit:
  - `NewMetadataInterceptor()` — HTTP-header→gRPC-metadata conversion (`server/router/api/v1/connect_interceptors.go:22`)
  - `NewLoggingInterceptor(...)` — request logging (`connect_interceptors.go:98`)
  - `NewRecoveryInterceptor(...)` — panic recovery (`connect_interceptors.go:165`)
  - `NewAuthInterceptor(...)` — authentication/authorization (`connect_interceptors.go:208`)
- The gRPC-Gateway side (`v1.go:69-97`) adds only an auth middleware (`gatewayAuthMiddleware`), again no rate limiter.
- There is a separate `internal/scheduler/middleware.go` (`Logging()`, `Recovery()` at L27/L51), but that is background-job middleware, not API request middleware, and also has no rate limiting.

The only request-count/size limits present are **not per-user rate limits**:

- `connect.WithReadMaxBytes(maxAPIRequestBytes)` — a per-request body-size cap, not a request-frequency limit (`server/router/api/v1/v1.go:141`).
- `thumbnailSemaphore: semaphore.NewWeighted(3)` — a global concurrency cap of 3 simultaneous thumbnail generations, not per-user and not rate-based (`server/router/api/v1/v1.go:39`, `:59`).

The only literal occurrence of "rate limit" anywhere in the Go/TS code is an aspirational doc comment listing a *future* consideration, not an implementation: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse").

So: no such middleware is registered, and consequently there are no per-user request limits to report.
