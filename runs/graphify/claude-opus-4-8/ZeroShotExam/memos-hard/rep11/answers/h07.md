The route `GET /file/users/:identifier/avatar` serves another user's avatar. The image bytes are not a file on disk or S3 — they are stored inline as a base64 data-URI in the target user's `avatar_url` column, fetched by username and decoded at serve time.

Serving handler and hops to the data layer:

- `serveUserAvatar` — server/router/fileserver/fileserver.go:168 (registered as `/file/users/:identifier/avatar` at server/router/fileserver/fileserver.go:124)
- `getUserByUsername` — server/router/fileserver/fileserver.go:715
- `(*Store).GetUser` — store/user.go:148
- `(*Store).ListUsers` — store/user.go:136 (delegates to `s.driver.ListUsers`)
- `(*DB).ListUsers` — store/db/sqlite/user.go:88 (`SELECT ... avatar_url ... FROM user WHERE username = ?` — the stored data)

Back in the handler, the returned `user.AvatarURL` data-URI is decoded by `parseDataURI` (server/router/fileserver/fileserver.go:737) and written to the response via `c.Blob` (server/router/fileserver/fileserver.go:209).

Note: the SQLite driver is shown; MySQL/Postgres have equivalent `ListUsers` implementations in store/db/mysql/user.go and store/db/postgres/user.go selecting the same `avatar_url` column.
