**Premise correction:** There is no Redis connection anywhere in this codebase. The cache layer is **not** backed by Redis (nor any external cache server) — a repo-wide search for `redis` in the Go sources returns nothing. The premise that a "Redis connection for the cache layer" exists is incorrect.

**Actual mechanism:**

The cache is a **thread-safe in-process, in-memory cache** implemented in pure Go, defined in `store/cache/cache.go`. It stores entries in a `sync.Map` (`Cache` struct, `store/cache/cache.go:66-73`), tracks per-item `expiration` timestamps (`store/cache/cache.go:35-39`), and runs a background goroutine (`cleanupLoop`, `store/cache/cache.go:200-215`) that evicts expired items on a ticker. There is no network connection, DSN, or client to configure.

**Where it's "configured":** The cache is instantiated in `store/store.go:40-53`, inside `store.New()`. A single `cache.Config` literal is built there and reused for three separate in-memory caches — `instanceSettingCache`, `userCache`, and `userSettingCache`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
...
userCache: cache.New(cacheConfig),
```

(The same defaults are also defined in `cache.DefaultConfig()` at `store/cache/cache.go:57-64`.)

**TTL for user entries:** User entries live in `s.userCache`. They are written via `s.userCache.Set(...)` (e.g. `store/user.go:98, 122, 132, 143, 167`), and `Set` applies the cache's `DefaultTTL` (`store/cache/cache.go:93-95`). Since `userCache` is created with the config above, the TTL for user entries is **10 minutes**. Entries are also swept every 5 minutes by the cleanup loop, capped at 1000 items, and explicitly invalidated on user deletion (`store/user_delete.go:39-40`).
