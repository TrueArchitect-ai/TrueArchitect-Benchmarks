**Premise correction:** This repository (a Memos-style Go note-taking server) has **no per-user API rate-limiting middleware**. There is no request-rate or request-count limiter registered anywhere in the API stack, so there are no "request limits" of that kind to report. A thorough search for rate-limiting concepts (`ratelimit`, `limiter`, `throttle`, `golang.org/x/time/rate`, `429`, `too many requests`, etc.) across `server/`, `internal/`, and `web/` turns up only a single doc-comment suggestion about throttling *email* sending (`internal/email/doc.go:86`) — not an HTTP/API middleware.

What the API request middleware chain actually consists of:

- **Echo-level middleware** — registered in `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)` (recovery + CORS only).
- **API interceptor/middleware stack** — registered in `server/router/api/v1/v1.go`:
  - gRPC-Gateway auth middleware (`v1.go:69`, wired at `v1.go:97`)
  - Connect interceptors (`v1.go:133-137`): `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor` — i.e. metadata, logging, panic recovery, and authentication. **None of these is a rate limiter.**

The only per-request "limit" that exists is a **payload size cap, not a rate cap**: `maxAPIRequestBytes = 256 << 20` (256 MiB), defined at `server/router/api/v1/v1.go:20` and enforced via `http.MaxBytesHandler(...)` and `connect.WithReadMaxBytes(...)` at `v1.go:126`, `v1.go:141`, and `v1.go:144`. This limits the size of each request body but does not limit how many requests a user may make.

So if the goal is per-user request-rate limiting, it is not present and would need to be added.
