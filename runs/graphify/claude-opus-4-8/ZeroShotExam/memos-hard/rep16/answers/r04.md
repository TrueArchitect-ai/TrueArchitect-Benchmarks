**Premise correction:** The webhook delivery workers don't consume from NATS *or* RabbitMQ — this repository (the `usememos/memos` Go server) uses **no external message broker at all**. There is no NATS/RabbitMQ/AMQP dependency anywhere in the Go code (`grep -riE "nats|rabbitmq|amqp"` over `*.go` returns nothing).

**Actual mechanism:** Delivery runs entirely in-process on a **buffered Go channel** with a fixed pool of goroutine workers.

- The "queue" is declared as a package-level buffered channel in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The workers are 4 goroutines started in `init()` (`internal/webhook/webhook.go:42-55`), each ranging over `asyncPostQueue` and calling `Post()` to make the outbound HTTP request.
- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send and drops the payload (logging a warning) if the 128-slot buffer is full.

So the mechanism is a bounded in-memory channel + goroutine worker pool inside the single server process — not a broker-backed queue. State is not durable: a restart or a full buffer silently loses pending deliveries.
