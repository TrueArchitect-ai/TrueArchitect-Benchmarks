**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the delete-user transaction — there is no database-level cascade. Reactions are cleaned up in two ways: reactions *on the deleted user's content* (by `content_id`) and reactions *authored by the deleted user* (by `creator_id`).

What I checked:

**1. The delete orchestration calls two explicit reaction-delete steps** — `store/db/postgres/user_delete.go:96-104` (`deleteUserTargetsTx`):
```go
if err := deleteReactionsByContentIDsTx(ctx, tx, contentIDs); err != nil { ... }
...
if err := deleteReactionsByCreatorTx(ctx, tx, userID); err != nil { ... }
```

**2. The two functions run raw SQL** — `store/db/postgres/user_delete.go:395-440`:
- `deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)` (content IDs are `"memos/"+uid` of the user's memo tree, incl. comment descendants).
- `deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = $1`.

**3. Same logic exists for the other two drivers** (so it's not DB-specific):
- SQLite: `store/db/sqlite/user_delete.go:96,102` and funcs at `:380`, `:400`.
- MySQL: `store/db/mysql/user_delete.go:96,102` and funcs at `:417`, `:437`.

**4. No DB-level rule backs this up.** The `reaction` table DDL in all three `LATEST.sql` files (`store/migration/sqlite/LATEST.sql`, `store/migration/postgres/LATEST.sql`, `store/migration/mysql/LATEST.sql`) declares `creator_id`/`content_id` as plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`, no `REFERENCES`, no `ON DELETE CASCADE`. A grep for `FOREIGN KEY|REFERENCES|ON DELETE` in the store code/schema returned nothing for reactions.

All deletes happen within a single transaction (`DeleteUser` in each driver, e.g. `store/db/postgres/user_delete.go:29`), so reaction removal is atomic with the user row deletion.
