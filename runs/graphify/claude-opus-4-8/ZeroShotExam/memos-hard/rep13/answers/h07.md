The image bytes for another user's avatar are stored as a base64 data-URI in the `avatar_url` column of the `user` table, and reach the browser through this chain (the request is `GET /file/users/:identifier/avatar`):

`RegisterRoutes` (route `/file/users/:identifier/avatar` → handler) — server/router/fileserver/fileserver.go:124
`(*FileServerService).serveUserAvatar` (serving handler; looks up user by URL identifier, decodes AvatarURL, returns `c.Blob`) — server/router/fileserver/fileserver.go:168
`(*FileServerService).getUserByUsername` — server/router/fileserver/fileserver.go:715
`(*Store).GetUser` — store/user.go:148
`(*Store).ListUsers` (delegates to `s.driver.ListUsers`) — store/user.go:136
`(*DB).ListUsers` (SQLite driver; builds `SELECT ... avatar_url ... FROM user`) — store/db/sqlite/user.go:88
`d.db.QueryContext` (executes SQL against the DB, scans `avatar_url` into `user.AvatarURL`) — store/db/sqlite/user.go:173

The handler then decodes the stored data URI via `(*FileServerService).parseDataURI` (server/router/fileserver/fileserver.go:737) and writes the raw image bytes back with `c.Blob` (server/router/fileserver/fileserver.go:209).

Notes:
- The data layer is pluggable — equivalent driver implementations exist at store/db/postgres/user.go:87 and store/db/mysql/user.go:84; SQLite is shown as the representative hop.
- `Store.GetUser`/`ListUsers` also populate/read an in-memory `userCache` (store/user.go:143,167), but a lookup by username (as here) still falls through to the driver/DB.
