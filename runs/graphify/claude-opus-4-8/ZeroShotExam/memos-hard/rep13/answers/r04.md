**Premise correction:** Neither. The webhook delivery workers consume from **neither NATS nor RabbitMQ** — this repository (Memos) has no external message broker at all. `go.mod` contains no NATS, RabbitMQ, or AMQP dependency (the grep for `nats|rabbitmq|amqp|streadway` returns nothing).

**Actual mechanism:** Webhook delivery uses an **in-process buffered Go channel** with a fixed pool of goroutine workers, all inside `internal/webhook/webhook.go`:

- The "queue" is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  (buffer capacity 128).

- The consuming workers are started in `init()` at `internal/webhook/webhook.go:42-55` — a loop of **4 goroutines**, each ranging over `asyncPostQueue` and calling `Post()` to make the HTTP delivery.

- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), a non-blocking `select` that drops the payload (with a warning log) if the channel buffer is full.

So the whole thing is a single-process fan-out: an in-memory channel plus goroutine workers, not a broker-backed queue. There is no queue "declaration" in any broker sense — the closest equivalent is the channel allocation at `internal/webhook/webhook.go:39`.
