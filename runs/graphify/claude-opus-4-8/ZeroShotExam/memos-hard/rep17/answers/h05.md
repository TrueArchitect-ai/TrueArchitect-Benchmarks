**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements executed inside the delete-user transaction — not by any database-level rule. The `reaction` table has no foreign key or `ON DELETE CASCADE`, so nothing is automatic.

What I checked:

1. **The delete-user transaction (Go).** `deleteUserTargetsTx` explicitly calls two reaction-cleanup helpers, per database dialect:
   - `deleteReactionsByContentIDsTx` — removes reactions *on* the deleted user's memos
   - `deleteReactionsByCreatorTx` — removes reactions the user *authored*

   Evidence (identical across all three dialects):
   - `store/db/sqlite/user_delete.go:96,102` (helpers at `:380` `DELETE FROM reaction WHERE content_id IN ...` and `:400` `DELETE FROM reaction WHERE creator_id = ...`)
   - `store/db/postgres/user_delete.go:96,102,380,400`
   - `store/db/mysql/user_delete.go:96,102,417,437`

2. **The schema — confirming no DB-level rule.** The `reaction` table defines `creator_id` and `content_id` as plain columns with only a `UNIQUE` constraint; there is no `FOREIGN KEY`/`REFERENCES`/`ON DELETE CASCADE`:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/0.20/00__reaction.sql` (and `store/migration/mysql/LATEST.sql`)

So the deletion is guaranteed by the application code, and it covers both the reactions the user made and the reactions others left on the user's content.
