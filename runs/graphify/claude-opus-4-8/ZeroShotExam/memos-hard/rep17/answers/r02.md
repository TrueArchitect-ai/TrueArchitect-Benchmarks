**Premise correction:** This repository (the Memos server, a Go/Connect-RPC + gRPC-Gateway application) has **no per-user API rate-limiting middleware**. There is no rate limiter registered anywhere in the request path, so there are no per-user request limits to report. The question's premise is mistaken.

I verified this by inspecting the complete middleware/interceptor chain:

- **Echo-level middleware** — `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware(profile)`. No limiter.
- **gRPC-Gateway middleware** — `server/router/api/v1/v1.go:69-98` registers a single `gatewayAuthMiddleware` (authentication/authorization only) via `runtime.WithMiddlewares(...)`.
- **Connect interceptors** — `server/router/api/v1/v1.go:133-138` chains `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor` (defined in `server/router/api/v1/connect_interceptors.go`). None throttle by user or IP.

A repo-wide grep for `rate`/`ratelimit`/`throttle`/`limiter`/`golang.org/x/time/rate` across `.go` files returns no rate-limiting implementation (only pagination `limit`, upload-size settings, and JWT/token code).

What does exist — and may be what the premise conflates with rate limiting — are unrelated, *not* per-user request-rate controls:

- **Global request body-size cap:** `maxAPIRequestBytes = 256 << 20` (256 MiB), applied via `http.MaxBytesHandler` to `/api/v1/*`, `/file/*`, and the Connect handler — `server/router/api/v1/v1.go:20, 126-144`. This is a byte-size limit per request, not a rate.
- **Global concurrency semaphores:** `thumbnailSemaphore` (3 concurrent) and `imageProcessingSemaphore` (2 concurrent) — `server/router/api/v1/v1.go:59-60`. These bound concurrent image work process-wide, not per user.
- **`internal/scheduler/middleware.go`** is middleware for background *job* handlers (Recovery/etc.), not HTTP/API request handling.

So: no such middleware, no request limits.
