I have the full trace. This is the memos project; profile images are user avatars stored inline as a data URI in the `user.avatar_url` column.

A browser GET to `/file/users/:identifier/avatar` reaches stored avatar data through this chain:

`serveUserAvatar()` — server/router/fileserver/fileserver.go:168 (route registered at fileserver.go:124)
`(*FileServerService).getUserByUsername()` — server/router/fileserver/fileserver.go:715
`(*Store).GetUser()` — store/user.go:148
`(*Store).ListUsers()` — store/user.go (calls `s.driver.ListUsers`)
`(*DB).ListUsers()` — store/db/sqlite/user.go:88 (also store/db/postgres/user.go:87, store/db/mysql/user.go:84)
`SELECT ... avatar_url ... FROM user` — store/db/sqlite/user.go:151-165 (data layer / `user` table)

Notes:
- The avatar bytes are not a separate blob store — they live inline in the `user.avatar_url` column as a `data:` URI. After the store returns the `*store.User`, `serveUserAvatar` reads `user.AvatarURL`, decodes it via `parseDataURI()` (fileserver.go:737), validates the MIME type against `avatarAllowedTypes`, and writes it with `c.Blob(...)` (fileserver.go:196-209).
- `Store.GetUser` first checks `s.userCache` (only on ID lookups; here the lookup is by username, so it falls through to `ListUsers`), and populates the cache on the way back.
