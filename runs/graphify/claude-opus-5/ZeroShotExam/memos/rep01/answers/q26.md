**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`** (the last only on Postgres/MySQL — see caveat).

**Path:** `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) → for each comment child memo and then the memo itself calls `Store.DeleteMemo` (`store/memo.go:140`).

What each layer touches:

| Table | How | Where |
|---|---|---|
| `memo` | `DELETE FROM memo WHERE id = ?` — once per comment memo (`memo_service.go:573-577`) and once for the target memo (`memo_service.go:580`) | `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259` |
| `memo_relation` | explicit cascade code: two deletes, one where the memo is `memo_id`, one where it is `related_memo_id` | `store/memo.go:142-147` → `store/db/*/memo_relation.go` |
| `attachment` | explicit cascade code: lists attachments by `MemoID` and deletes each (also removes the backing blob/local file) | `store/memo.go:149-157` → `store/attachment.go:132` → `store/db/*/attachment.go` |
| `memo_share` | DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` — no Go code | `store/migration/{sqlite,postgres,mysql}/LATEST.sql:108-109` |

Two caveats worth flagging:

- **`memo_share` cascade does not fire on SQLite.** The SQLite driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the declared cascade is inert and share rows are orphaned there. It does fire on Postgres/MySQL.
- **`reaction` is *not* touched.** `DeleteMemo` reads reactions only to build the webhook payload (`memo_service.go:545-550`). `reaction.content_id` is a text name (`memos/<uid>`) with no FK (`LATEST.sql:92-99`), and the only bulk reaction cleanup lives in the user-deletion path (`store/db/*/user_delete.go:383`). So reaction rows for a deleted memo remain.

Also note none of this runs in a transaction — the relation/attachment/memo deletes are separate statements, so a mid-way failure leaves partial state.
