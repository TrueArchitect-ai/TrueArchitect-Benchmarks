**`APIV1Service.SignIn` — `server/router/api/v1/auth_service.go`** (line 51)

This is the real business-logic implementation of the `SignIn` RPC declared at `proto/api/v1/auth_service.proto:24`. It handles both authentication paths:

- **Password credentials** — looks up the user by username, `bcrypt.CompareHashAndPassword` against the stored hash, and rejects if `DisallowPasswordAuth` is set for a `RoleUser` account.
- **SSO credentials** — `resolveSSOIdentity` then `resolveSSOUser` (same file, below line 110).

It rejects archived users, then calls `s.doSignIn` (`server/router/api/v1/auth_service_session.go:24`) to mint the access token and set the refresh-token cookie, returning user info + token + expiry.

Two related pieces of plumbing, in case they're what you're after:

- `ConnectServiceHandler.SignIn` — `server/router/api/v1/connect_services.go:78` — the Connect-RPC transport wrapper. It only wraps the call in `connectWithHeaderCarrier` (so cookies can be set protocol-agnostically) and delegates to `APIV1Service.SignIn`.
- `proto/gen/api/v1/auth_service_grpc.pb.go` and `proto/gen/api/v1/apiv1connect/auth_service.connect.go` are generated stubs/clients, not handlers.
