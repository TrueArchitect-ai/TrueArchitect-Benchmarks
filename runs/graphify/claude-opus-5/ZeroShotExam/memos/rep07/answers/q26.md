Trace, starting at `server/router/api/v1/memo_service.go:518` (`APIV1Service.DeleteMemo`):

1. **Comment memos** — lists `memo_relation` rows of type `comment` pointing at the memo and calls `Store.DeleteMemo` for each child memo (`memo_service.go:567-577`), so everything below applies recursively to comments too.
2. **`Store.DeleteMemo`** (`store/memo.go:140-159`) does the explicit cascade:
   - **`memo_relation`** — deleted twice, once by `MemoID` and once by `RelatedMemoID` (`store/memo.go:142-147`; SQL in `store/db/sqlite/memo_relation.go`, plus the mysql/postgres equivalents).
   - **`attachment`** — lists attachments with `MemoID` and calls `Store.DeleteAttachment` per row (`store/memo.go:148-157`), which also removes the underlying file/blob before `DELETE FROM attachment` (`store/attachment.go:132-149`, `store/db/sqlite/attachment.go:211`).
   - **`memo`** — final `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`).

Two notable non-effects:

- **`memo_share`** is *not* touched by Go code; it relies on the schema FK `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/{sqlite,postgres,mysql}/LATEST.sql:108-109`). That cascade fires on Postgres/MySQL, but SQLite opens its connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite these rows are left orphaned.
- **`reaction`** rows are only *read* (to build the webhook payload, `memo_service.go:545-550`); nothing deletes them, and the `reaction` table has no FK to `memo` in any of the three schemas.
