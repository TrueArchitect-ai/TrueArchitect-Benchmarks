Inside `Store.DeleteMemo` (`store/memo.go:140-159`), before the memo row is removed via `s.driver.DeleteMemo`, these records are deleted:

1. **Memo relations where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **Memo relations where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — each one listed via `ListAttachments{MemoID}` then deleted with `Store.DeleteAttachment` (`store/memo.go:148-157`), which also removes the attachment's backing storage/blob (local file or external object) before deleting the attachment row (`store/attachment.go:132-149`)

Two related notes on scope:

- The driver-level `DeleteMemo` is a plain `DELETE FROM memo WHERE id = ?` with no extra cleanup (e.g. `store/db/sqlite/memo.go:237`), so all cascading lives in the store wrapper.
- Comment memos and reactions are *not* handled by the store layer. The API handler deletes child comment memos first by recursively calling `Store.DeleteMemo` for each `MemoRelationComment` relation (`server/router/api/v1/memo_service.go:567-577`); reactions are only read for the webhook payload, not deleted there.
