**Tables affected: `memo`, `memo_relation`, `attachment` — plus `memo_share` via DB-level `ON DELETE CASCADE` (Postgres/MySQL only).**

**Call chain**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):
1. Reads the memo, reactions, attachments, relations only to build the webhook payload (`memo_service.go:523-565`) — reads, no writes.
2. Lists child comments via `ListMemoRelations` and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`), then for the memo itself (`memo_service.go:580`).

`Store.DeleteMemo` (`store/memo.go:140-159`) is where the explicit cascade code lives:
- `memo_relation` — two deletes, one on `memo_id`, one on `related_memo_id` (`store/memo.go:142-147`; SQL at `store/db/sqlite/memo_relation.go:149`, `store/db/postgres/memo_relation.go:164`).
- `attachment` — lists attachments for the memo and calls `Store.DeleteAttachment` per row (`store/memo.go:148-157`). That also deletes the underlying blob/local/S3 file (`store/attachment.go:132-148`), which is filesystem/object storage, not a table.
- `memo` — the row itself (`store/memo.go:158`; e.g. `store/db/sqlite/memo.go:237-248`).

**`memo_share`** is *not* touched by code; it relies on `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). Note this cascade does **not** fire on SQLite — the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so share rows are orphaned there.

**Not affected:** `reaction`. Reactions are read for the webhook payload but never deleted — `reaction.content_id` is a plain TEXT column with no FK (`store/migration/sqlite/LATEST.sql:92-99`), and the only `DeleteReaction` call site is the explicit `DeleteMemoReaction` API (`server/router/api/v1/reaction_service.go:141`). Deleting a memo leaves its reaction rows behind.
