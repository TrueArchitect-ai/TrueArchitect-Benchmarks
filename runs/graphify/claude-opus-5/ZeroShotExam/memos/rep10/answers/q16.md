`Store.DeleteMemo` (`store/memo.go:140-159`) performs this cleanup before calling `s.driver.DeleteMemo`:

1. **Memo relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **Memo relation rows where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments(FindAttachment{MemoID: &delete.ID})` and removed one by one with `DeleteAttachment` (`store/memo.go:149-157`). Each of those also deletes the attachment's backing storage (local file / S3 object) before the attachment row (`store/attachment.go:132-149`).

Only then does it delete the memo row itself (`store/memo.go:158`).

Note on scope: reactions are *not* deleted by the store layer here, and the API handler (`server/router/api/v1/memo_service.go:518-593`) only lists reactions for the webhook payload. The handler does, however, first delete comment memos (relations of type `MemoRelationComment`) by recursively calling `Store.DeleteMemo` on each (`memo_service.go:567-577`), which triggers the same relation/attachment cleanup for those comments.
