**Call chain**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):
1. Lists comment relations (`store.MemoRelationComment`) and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`), then for the memo itself (`memo_service.go:580`).

`Store.DeleteMemo` (`store/memo.go:140-159`) — explicit cascade code:
- **`memo_relation`** — two deletes, one matching `memo_id`, one matching `related_memo_id` (`store/memo.go:142-147`; SQL in `store/db/sqlite/memo_relation.go`, and the postgres/mysql equivalents).
- **`attachment`** — lists attachments with `MemoID` and calls `Store.DeleteAttachment` per row (`store/memo.go:149-157`), which deletes the row via the driver plus the underlying local/S3 file (`store/attachment.go:132-149`).
- **`memo`** — final `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

**Cascade at the schema level**
- **`memo_share`** has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). Caveat: SQLite opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so FK enforcement is off there and `memo_share` rows are **not** cascaded on SQLite — they're orphaned.

**Not affected**
- **`reaction`** — reactions are only *read* for the webhook payload (`memo_service.go:545-550`); nothing deletes them, and the table has no FK to `memo` (it keys on a text `content_id`, `store/migration/sqlite/LATEST.sql:92-99`). Reaction rows are left orphaned.
- `inbox`, `user`, etc. are untouched.
