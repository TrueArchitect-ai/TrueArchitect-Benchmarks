**Engine:** Google CEL (`github.com/google/cel-go`), wrapped by the in-repo memo filter engine at **`internal/filter/`** — `engine.go` (entry point `filter.DefaultEngine()`), `schema.go`, `parser.go`, `ir.go`, `render.go`, `helpers.go`.

**Mechanism (one sentence):** `Engine.Compile` type-checks the CEL string against the memo-specific `cel.Env` declared in `internal/filter/schema.go`, `internal/filter/parser.go` lowers the CEL AST into a dialect-agnostic IR condition tree (`internal/filter/ir.go`), and `internal/filter/render.go` walks that IR to emit a dialect-specific SQL fragment plus bound args (`Statement{SQL, Args}`) that `filter.AppendConditions` (`internal/filter/helpers.go:9`) appends to the `WHERE` clause.

**Path through the RPC:**
- `ListMemos` validates the filter up-front via `s.validateFilter` (`server/router/api/v1/memo_service.go:211-215`; implementation at `server/router/api/v1/shortcut_service.go:336`, which compiles it against the driver's dialect), then stashes the raw string in `memoFind.Filters`. Note it also *synthesizes* filter strings itself, e.g. the visibility clause `creator_id == %d || visibility in ["PUBLIC", "PROTECTED"]` at `server/router/api/v1/memo_service.go:224`.
- Each store driver calls the engine with its own dialect: `store/db/sqlite/memo.go:57-62` (`DialectSQLite`), `store/db/mysql/memo.go:65-70` (`DialectMySQL`), `store/db/postgres/memo.go:54-59` (`DialectPostgres`).

**Dialect differences** are confined to the renderer: placeholders are `?` for SQLite/MySQL vs `$n` for Postgres with an offset so fragments compose with pre-existing args (`internal/filter/render.go:842-849`, `RenderOptions.PlaceholderOffset` in `engine.go`); JSON access (`json_extract` vs `JSON_EXTRACT` vs `->`/`->>`), boolean coercion, string-length, and `LIKE` vs `ILIKE` are switched on `DialectName` throughout `render.go`. Trivially-true filters render to empty SQL (skipped) and unsatisfiable ones to `1 = 0` (`internal/filter/render.go:31-57`). Background is documented in `internal/filter/README.md`.
