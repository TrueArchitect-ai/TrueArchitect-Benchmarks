**`web/src/connect.ts`; JWT access token (in-memory + localStorage, sent as `Authorization: Bearer`) + HTTP-only refresh-token cookie, plus Personal Access Tokens (PAT) accepted on the same header; `server/auth/`**

**Frontend interceptor — `web/src/connect.ts`**
- `authInterceptor` (`web/src/connect.ts:145`) is a Connect-RPC `Interceptor` registered on the shared `createConnectTransport` (`web/src/connect.ts:170`), which every generated service client (`memoServiceClient`, `userServiceClient`, `authServiceClient`, …) is built from. So all API calls go through it.
- Per request it calls `getRequestToken()` (`web/src/connect.ts:124`) and sets `Authorization: Bearer <token>` via `setAuthorizationHeader()`.
- On a `Code.Unauthenticated` error it refreshes once and replays the request, marking the retry with an `X-Retry: true` header to prevent loops; if the refresh fails it calls `redirectOnAuthFailure()` (`web/src/utils/auth-redirect.ts`).

**Tokens it manages**
- **Access token** — short-lived JWT held in module state and mirrored to `localStorage` under `memos_access_token` / `memos_token_expires_at` (`web/src/auth-state.ts`). It's proactively refreshed when within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30s) of expiry, and on tab focus with a 2-minute buffer (`web/src/hooks/useTokenRefreshOnFocus.ts`).
- **Refresh token** — never touched by JS; it's an HTTP-only cookie (`memos_refresh`), which is why the transport uses `fetchWithCredentials` (`credentials: "include"`). Refresh goes through a *separate* transport with no interceptors (`refreshTransport`, `web/src/connect.ts:66`) to avoid recursion, and concurrent refreshes are deduped by `tokenRefreshManager`; results are broadcast to other tabs over a `BroadcastChannel` (`memos_token_sync`).

**Backend validation — `server/auth/`**
- `server/auth/token.go` defines the token model: `AccessTokenDuration` 15 min, `RefreshTokenDuration` 30 days, audiences `user.access-token` / `user.refresh-token`, cookie `memos_refresh`, and the PAT prefix `memos_pat_`. Signing/parsing uses `github.com/golang-jwt/jwt/v5`.
- `server/auth/authenticator.go` — `Authenticator.AuthenticateByAccessTokenV2()` validates access tokens statelessly (signature only, no DB hit); `AuthenticateByRefreshToken()` additionally checks the token against the store for revocation; PATs are looked up in the DB.
- `server/auth/extract.go` pulls the bearer token off the `Authorization` header and the refresh token out of the cookie.
- It's wired into the API by `Authorizer` in `server/router/api/v1/authz.go:26`, which wraps `auth.NewAuthenticator(store, secret)` and is shared by both the Connect interceptor and the gRPC-Gateway middleware (`server/router/api/v1/v1.go:88`) so both transports enforce identical rules. `server/router/fileserver` uses the same package.
