**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`.**

Trace of the delete path:

**1. `server/router/api/v1/memo_service.go:518` — `APIV1Service.DeleteMemo`**
- Lists comment memos via `ListMemoRelations` (type `MemoRelationComment`) and calls `Store.DeleteMemo` on each (`memo_service.go:567-577`), then deletes the memo itself (`memo_service.go:580`). So `memo` rows are deleted for both the target memo and its comment memos.

**2. `store/memo.go:140` — `Store.DeleteMemo`** (explicit cascade code)
- `memo_relation`: two `DeleteMemoRelation` calls, one by `MemoID` and one by `RelatedMemoID`, clearing rows in both directions (`store/memo.go:142-147`).
- `attachment`: `ListAttachments{MemoID}` then `DeleteAttachment` per row (`store/memo.go:149-157`), which deletes the DB row via the driver plus the backing local/S3 object (`store/attachment.go:132-148`) — storage, not a table.
- `memo`: `driver.DeleteMemo` issues `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

**3. `memo_share` — by DB-level FK cascade**
- `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in `store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`.
- Caveat: the SQLite driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite this cascade does **not** fire and there is no compensating Go code — `memo_share` rows for the deleted memo are left orphaned there. It does fire on Postgres/MySQL.

**Not affected:** `reaction`. `DeleteMemo` reads reactions only to build the webhook payload (`memo_service.go:545-550`); nothing deletes them, and `reaction.content_id` is a plain `TEXT` column with no FK (`store/migration/sqlite/LATEST.sql:92-100`), so reaction rows survive the memo.
