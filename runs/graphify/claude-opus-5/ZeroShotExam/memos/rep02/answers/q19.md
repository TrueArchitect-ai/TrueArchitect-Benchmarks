**Connect RPC (connectrpc, over HTTP)** — `server/router/api/v1/connect_handler.go:40` registers it: `wrap(apiv1connect.NewMemoServiceHandler(s, opts...))` inside `RegisterConnectHandlers`. The per-method wrapping that adapts the gRPC implementations to Connect request/response envelopes lives in `server/router/api/v1/connect_services.go:304` onward (the `// MemoService` block: `CreateMemo`, `ListMemos`, `GetMemo`, …), backed by the generated handler in `proto/gen/api/v1/apiv1connect/memo_service.connect.go`.

**REST/HTTP+JSON via grpc-gateway** — `server/router/api/v1/v1.go:108`: `v1pb.RegisterMemoServiceHandlerServer(ctx, gwMux, s)`, where `gwMux` is the `runtime.NewServeMux` mounted on `/api/v1/*` and `/file/*`. The generated in-process gateway bindings are in `proto/gen/api/v1/memo_service.pb.gw.go`.

Both protocols share one implementation: `APIV1Service` (`server/router/api/v1/v1.go:26`, embedding `v1pb.UnimplementedMemoServiceServer`), which `ConnectServiceHandler` embeds.

Note: there is no native gRPC listener in this repo — no `grpc.NewServer` or `RegisterMemoServiceServer` call exists, so the generated `memo_service_grpc.pb.go` server is only used indirectly through the gateway. MCP (`server/router/mcp/catalog.go:12-25`) exposes the same methods as tools, but it's a tool catalog over the existing handlers rather than a third transport registration.
