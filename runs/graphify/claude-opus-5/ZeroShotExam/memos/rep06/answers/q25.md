**Engine:** Google CEL (`github.com/google/cel-go`), wrapped by the in-repo filter engine at `internal/filter/` — `engine.go` (`NewEngine`/`Compile`/`CompileToStatement`/`DefaultEngine`), `schema.go` (field + CEL env declarations), `parser.go` (CEL AST → IR), `ir.go` (dialect-agnostic condition tree), `render.go` (IR → SQL), `helpers.go` (`AppendConditions`).

**Mechanism (one sentence):** `ListMemos` validates `request.Filter` via `APIV1Service.validateFilter` (`server/router/api/v1/shortcut_service.go:336`, called from `server/router/api/v1/memo_service.go:212`) and passes it into `store.FindMemo.Filters`, where each dialect driver calls `filter.DefaultEngine()` + `filter.AppendConditions(ctx, engine, find.Filters, filter.Dialect{SQLite,Postgres,MySQL}, &where, &args)` (`store/db/sqlite/memo.go:57-61`, `store/db/postgres/memo.go:54-58`, `store/db/mysql/memo.go:65-69`), which compiles the CEL string against the memo schema into an IR tree and then renders it per-dialect into a parameterized `WHERE` fragment plus args.

Dialect specifics live in the renderer: `qualifyColumn`/`Field.columnExpr` apply per-dialect column expressions (`internal/filter/schema.go:321-327`), `addArg` emits `$n` for Postgres and `?` for SQLite/MySQL with a `PlaceholderOffset` so fragments compose with pre-existing args (`internal/filter/render.go:842-849`), and JSON/tag/time handling branches per dialect (e.g. `strftime` vs `EXTRACT … to_timestamp` vs MySQL date functions at `internal/filter/render.go:227-239`; `LIKE` vs `JSON_CONTAINS` vs `@>` for tags). `internal/filter/README.md` documents the three-phase parse → normalize → render pipeline.
