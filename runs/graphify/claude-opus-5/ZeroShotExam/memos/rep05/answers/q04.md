**`APIV1Service.SignIn` — `server/router/api/v1/auth_service.go:51`**

This is where the actual RPC logic lives. It handles both authentication methods declared in the proto (`proto/api/v1/auth_service.proto:24`):

- **Password credentials** — looks up the user by username, compares the bcrypt hash, and rejects if `DisallowPasswordAuth` is set for a non-admin role
- **SSO credentials** — delegates to `s.resolveSSOIdentity` / `s.resolveSSOUser` for the OAuth2 authorization-code exchange

It then rejects archived users and calls `s.doSignIn` to mint the access token returned in `SignInResponse`.

One wrinkle worth noting: there is a second `SignIn` at `server/router/api/v1/connect_services.go:78`, `ConnectServiceHandler.SignIn`. That's the Connect protocol entry point registered with the server, but it's a thin wrapper — it unwraps `req.Msg`, calls `s.APIV1Service.SignIn`, and re-wraps the result via `connectWithHeaderCarrier` so the service can set response headers protocol-agnostically. If you're after the transport binding, that's the one; for the handler that implements the RPC's behavior, it's `APIV1Service.SignIn`.
