**Premise correction:** Neither. This repository (memos) has no message broker at all — no NATS, RabbitMQ, Kafka, or Redis. `go.mod` contains no broker client dependency, and the only repo-wide match for those terms is an unrelated word in a translation file (`web/src/locales/ca.json`). There is also no "queue declaration" in the broker sense (no `QueueDeclare`, no subject/stream subscription).

**Actual mechanism — an in-process Go channel with a fixed goroutine pool:**

- **Queue:** a buffered Go channel declared as a package-level var in `internal/webhook/webhook.go:39`:
  `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — capacity 128, in-memory, per-process.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are logged with `slog.Warn` only; there is no retry, no ack, and no persistence.
- **Producer:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning — there's no backpressure or dead-letter path.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, dispatching memo created/updated/deleted and comment-created events fetched via `s.Store.GetUserWebhooks`.
- **Delivery itself:** `Post` (`internal/webhook/webhook.go:120`) does a plain HTTP POST through a shared `safeClient` with a 30s timeout and an SSRF-guarding dialer (`safeDialContext`, `internal/webhook/webhook.go:59`), optionally adding Standard Webhooks HMAC-SHA256 headers.

Practical consequence: because the queue lives in process memory, anything still buffered is lost on restart or crash, and a burst beyond 128 pending payloads is silently discarded.
