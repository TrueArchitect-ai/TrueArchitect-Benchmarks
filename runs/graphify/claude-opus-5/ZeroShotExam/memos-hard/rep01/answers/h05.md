**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the delete-user transaction, in all three DB drivers. There is no database-level cascade, FK, or trigger that would do it.

## What the Go code does

`DeleteUser` runs everything in one transaction and issues **two** separate reaction deletes (`store/db/sqlite/user_delete.go:92-127`):

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`store/db/sqlite/user_delete.go:380-388`). The content IDs are `"memos/" + uid` for every memo in the user's memo tree (`memoContentIDsFromRefs`, line 512), which is collected recursively so comment descendants are included (`listDeleteUserMemoTreeRecursive`, line 133). This removes *other people's* reactions on the deleted user's memos.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`). This removes the deleted user's *own* reactions on anyone's memos.

Note the ordering: both run before `deleteMemosTx` / `deleteUserRowTx` (lines 120-125), so the reaction rows are found while the memo tree still exists.

Same structure in the other drivers: `store/db/mysql/user_delete.go:96,102,417,437` and `store/db/postgres/user_delete.go:96,102,380,400`.

Entry points: `store/user.go:170` → `store/driver.go:48` → per-driver impl; called from `server/router/api/v1/user_service.go:414` and `server/router/api/v1/auth_service_sso.go:77`.

## What I checked to rule out a DB-level rule

- `grep REFERENCES store/migration/*/LATEST.sql` returns exactly one FK across all three schemas — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`).
- The `reaction` table itself declares **no** foreign key on `creator_id` or `content_id` — just columns plus a `UNIQUE(creator_id, content_id, reaction_type)` (`store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`). `content_id` is a text `memos/<uid>` string, so it couldn't be an FK anyway.
- No triggers touch `reaction`; the historical triggers were dropped in `store/migration/sqlite/0.7/01__remove_triggers.sql`.
- Even if an FK existed, SQLite has enforcement off: the DSN sets `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`).
