**Premise correction:** There is no Redis connection anywhere in this repository. A case-insensitive search for `redis` across every tracked file returns zero matches, and `go.mod` declares no Redis (or memcached/ristretto/bigcache) client dependency. This is the Go-based memos server, and its cache layer is entirely **in-process and in-memory** — there is nothing to configure a connection string, host, port, or auth for.

**Actual mechanism**

The cache is a hand-rolled implementation in `store/cache/cache.go`. It is a `sync.Map` guarded by an `atomic.Int64` item counter, with per-item expiration timestamps (`store/cache/cache.go:35-39`) and a background cleanup goroutine started in `New()` (`store/cache/cache.go:83`) that sweeps expired entries on a ticker (`store/cache/cache.go:200-250`).

Configuration happens at store construction, not via any config file or environment variable. `store.New()` builds a `cache.Config` literal inline (`store/store.go:40-45`) and hands the *same* config to three separate cache instances (`store/store.go:51-53`):

- `instanceSettingCache`
- `userCache`
- `userSettingCache`

**TTL for user entries: 10 minutes** — `DefaultTTL: 10 * time.Minute` at `store/store.go:41`. Alongside it: `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil`.

Two details worth noting:

1. **The TTL is not user-specific.** All three caches share one identical config, so user entries, user settings, and instance settings all expire at 10 minutes. The same 10-minute value is also duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:59`), but `store.New()` does not call that helper — it re-declares the values, so the two would have to be edited in tandem.

2. **The TTL is a compile-time constant.** Nothing reads it from the environment or profile. `SetWithTTL` exists on the interface (`store/cache/cache.go:16`) for per-entry overrides, but every user write path uses plain `Set`, which falls through to `DefaultTTL` (`store/cache/cache.go:94`). See the user write sites at `store/user.go:98`, `:122`, `:132`, `:143`, `:167`, keyed by `userCacheKey` (stringified user ID, `store/user.go:88-90`).

Staleness is bounded more tightly than 10 minutes in practice, because writes refresh the entry and deletes evict explicitly (`store/user_delete.go:39-45`). Cache reads are also only consulted on lookup by ID — `GetUser` skips the cache entirely when finding by username or any other field (`store/user.go:148-156`).

One caveat on scope, since it likely motivates the question: because this cache is per-process memory, it is **not shared across replicas**. Running multiple memos instances against one database gives each its own independent copy with independent expiry, and a user update on one replica does not invalidate the others — they can serve stale user data for up to 10 minutes. That is the practical gap a Redis layer would close, but it does not exist here today.
