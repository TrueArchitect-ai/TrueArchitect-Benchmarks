**Premise correction: there is no per-user API rate-limiting middleware in this repository.** The question presupposes one exists; it doesn't, so there are no request limits to report.

**What I checked**

- Repo-wide grep for `ratelimit` / `rate_limit` / "rate limit" / `throttle` across Go, TS/TSX, and YAML: the only hits are aspirational docs in `internal/email/README.md:286-295` and `internal/email/doc.go:86`, which suggest implementing `golang.org/x/time/rate` for outbound email sending — future guidance, not shipped code, and not per-user API limiting.
- `golang.org/x/time` appears in `go.mod:151` only as an **indirect** dependency; no package imports it.
- No `429` / `http.StatusTooManyRequests` responses anywhere in the codebase.

**What is actually registered (the full middleware/interceptor set)**

- Echo HTTP middleware, `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`). That's it.
- Connect RPC interceptors, `server/router/api/v1/v1.go:132-141`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (all in `server/router/api/v1/connect_interceptors.go`). None does rate limiting.
- Frontend SPA fallback, `server/router/frontend/frontend.go:59`.

**The nearest thing to a limit** — worth knowing, but global, not per-user:

- **Request body size**: `maxAPIRequestBytes` enforced via `http.MaxBytesHandler` on `/api/v1/*`, `/file/*`, and the Connect routes, plus `connect.WithReadMaxBytes` (`server/router/api/v1/v1.go:126-144`).
- **Concurrency semaphores** (server-wide, shared across all users), `server/router/api/v1/v1.go:59-60`:
  - `thumbnailSemaphore` — 3 concurrent thumbnail generations
  - `imageProcessingSemaphore` — 2 concurrent EXIF-strip operations; exceeding it returns `codes.ResourceExhausted` "too many image processing requests" (`server/router/api/v1/attachment_service.go:158-160`, `attachment_service_image.go:68-75`)

These cap in-flight concurrent work to protect memory, not request rate, and they are not scoped to a user identity — one user saturating the two image slots blocks everyone.
