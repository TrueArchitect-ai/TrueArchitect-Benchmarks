The premise is incorrect: **there is no per-user API rate-limiting middleware in this repository.** No rate limiter is registered anywhere, and consequently there are no request limits to report.

What I checked:

- **Echo-level middleware** — `server/server.go:51-52` registers exactly two: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`). No `middleware.RateLimiter`, no throttling.
- **Connect RPC interceptor chain** — `server/router/api/v1/v1.go:133-137` registers four interceptors, all defined in `server/router/api/v1/connect_interceptors.go`: `MetadataInterceptor` (header→gRPC metadata), `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor` (auth/anonymous-access policy). None does rate limiting.
- **gRPC-gateway middleware** — `server/router/api/v1/v1.go:69,97` registers a single `gatewayAuthMiddleware`, which is auth-only.
- **Dependencies** — `go.mod`/`go.sum` contain no rate-limiting library (no `golang.org/x/time/rate`, `tollbooth`, `ulule/limiter`, etc.).
- **Repo-wide grep** for `rate limit|ratelimit|throttl` matches only two non-code spots: `internal/email/doc.go:86` and `internal/email/README.md:286-295`, both of which list rate limiting as a *suggested future enhancement* for email sending, not an implementation.

The only per-request limit that does exist is a **size** limit, not a rate limit: `maxAPIRequestBytes = 256 << 20` (256 MiB) in `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` to the gateway (`v1.go:126`) and Connect mux (`v1.go:144`), and via `connect.WithReadMaxBytes` on the Connect handlers (`v1.go:141`). It is global and per-request, with no per-user dimension.

There is also a `Middleware` concept in `internal/scheduler/middleware.go`, but it wraps background *jobs* (Recovery, Logging, Timeout) — not HTTP requests — and includes no limiter either.
