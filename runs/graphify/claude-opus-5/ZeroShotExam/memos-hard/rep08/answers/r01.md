**Premise correction:** There is no Redis in this repository. A case-insensitive search for `redis` across all source, config, `go.mod`/`go.sum`, CI, and docs returns zero hits — there is no Redis client dependency, no connection string, no host/port setting, and no environment variable for one. The cache layer is entirely in-process and in-memory.

**Actual mechanism**

The cache is a hand-rolled, thread-safe in-memory cache in `store/cache/cache.go`:

- `Cache` (`store/cache/cache.go:67`) is backed by a `sync.Map` plus an `atomic.Int64` item counter — process-local state, so it is not shared between server instances.
- `Config` (`store/cache/cache.go:42`) holds `DefaultTTL`, `CleanupInterval`, `MaxItems`, and an `OnEviction` hook. `DefaultConfig()` (`store/cache/cache.go:57`) sets 10 min / 5 min / 1000 items.
- Expiry is lazy on read plus a background sweep: `New()` launches `cleanupLoop()` (`store/cache/cache.go:200`), and `cleanupOldest()` (`store/cache/cache.go:253`) trims when `MaxItems` is exceeded.

**Where it's "configured"** — `store.New()` in `store/store.go:38-58`. This is the closest thing to the connection setup you asked about: instead of dialing a server, it constructs a literal `cache.Config` inline (`store/store.go:40-45`) and instantiates three independent caches with it (`store/store.go:51-53`):

- `instanceSettingCache`
- `userCache`
- `userSettingCache`

Note this literal duplicates `cache.DefaultConfig()` rather than calling it. Shutdown closes all three cleanup goroutines in `Store.Close()` (`store/store.go:72-78`).

**TTL for user entries — 10 minutes**, inherited from the default; there is no user-specific override. Every user write goes through `s.userCache.Set(...)`, which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). `SetWithTTL` is exported and available, but no user code path calls it — user entries are cached at:

- `CreateUser` — `store/user.go:98`
- `CreateUserIfNoUsers` — `store/user.go:122`
- `UpdateUser` — `store/user.go:132`
- `ListUsers` (caches each row) — `store/user.go:143`
- `GetUser` — `store/user.go:167`

Reads hit the cache only on lookup by ID (`store/user.go:148-156`); any other `FindUser` predicate falls through to the driver. Keys are the plain decimal user ID via `userCacheKey()` (`store/user.go:88`), and deletion invalidates explicitly at `store/user_delete.go:40`.

So the effective staleness bound for a user entry is 10 minutes, but in practice writes and deletes refresh or evict the entry eagerly, and the 1000-item cap is shared per-cache — a busy instance can evict user entries well before their TTL expires.
