**Premise correction:** There is no Redis in this repository. Nothing in `go.mod`/`go.sum` pulls in a Redis (or Memcached/Valkey) client, and a case-insensitive grep for `redis` across all Go, config, TS, and docs files returns zero hits. There is no external cache server, no connection string, no cache host/port/password config anywhere. So there is no "Redis connection for the cache layer" to configure.

**Actual mechanism:** The cache is a hand-rolled, in-process, in-memory cache backed by `sync.Map`.

- Implementation: `store/cache/cache.go` — `Cache` struct (`store/cache/cache.go:67`) holding a `sync.Map` plus an atomic item counter, with per-entry `expiration time.Time` (`store/cache/cache.go:35-39`). Background goroutine `cleanupLoop` (`store/cache/cache.go:200`) sweeps expired entries; `cleanupOldest` (`store/cache/cache.go:253`) evicts when over `MaxItems`.
- Where it's "configured": `store.New()` in `store/store.go:38-61` builds a single `cache.Config` literal — `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil` — and uses it for all three caches: `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). These values are hardcoded in Go; there is no env var, flag, or config-file override. `store/cache/cache.go:57-64` defines an identical `DefaultConfig()`, but the store doesn't call it — it duplicates the values inline.
- Lifecycle: caches are per-`Store` instance and die with the process; `Store.Close()` stops the three cleanup goroutines (`store/store.go:72-79`).

**TTL for user entries:** 10 minutes. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — which is the 10 minutes from `store/store.go:41`. No user code path calls `SetWithTTL` with a custom duration, so users get the same TTL as instance settings and user settings.

Two caveats worth noting since they affect real behavior more than the TTL does:
- Cache keys are the bare user ID (`userCacheKey` → `strconv.Itoa`, `store/user.go:88-90`), and all three caches are separate `Cache` instances, so there's no key-namespace collision between them.
- Entries are also invalidated explicitly on delete (`store/user_delete.go:39-45`), and evicted early under pressure — the shared 1000-item `MaxItems` cap means a busy instance can drop user entries well before 10 minutes.
