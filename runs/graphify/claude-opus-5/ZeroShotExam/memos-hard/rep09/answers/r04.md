**Premise correction:** Neither. Memos has no external message broker — there's no NATS, RabbitMQ, AMQP, or Kafka dependency anywhere in the project (`grep -niE "nats|rabbit|amqp|kafka"` over `go.mod`/`go.sum` returns nothing). Webhook delivery is entirely in-process.

**Actual mechanism — an in-memory buffered Go channel with a fixed worker pool:**

- **Queue declaration:** `internal/webhook/webhook.go:39` — a package-level buffered channel:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, declared in the same `var` block as the shared `safeClient`.

- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` starts **4** goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are only logged (`slog.Warn`) — there is no retry, no ack, and no dead-letter path.

- **Producer:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning — delivery is best-effort, not durable.

- **Call sites:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` (memo created/updated/deleted and comment-created events), which fetch subscribers via `s.Store.GetUserWebhooks(...)` and enqueue one payload per hook.

- **Actual HTTP send:** `Post` at `internal/webhook/webhook.go:120-180` — POSTs JSON over `safeClient`, which uses an SSRF-guarding `safeDialContext` (`internal/webhook/webhook.go:59-77`) and adds Standard Webhooks HMAC headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) when a signing secret is configured.

Practical consequence: because the queue lives in process memory, queued webhooks are lost on server restart, and there's no cross-instance distribution — each Memos instance dispatches only what it enqueued.
