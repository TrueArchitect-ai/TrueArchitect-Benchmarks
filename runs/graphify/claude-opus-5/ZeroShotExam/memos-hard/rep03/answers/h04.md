**No** — in production code, `mysql.NewDB` is called from exactly one place: the driver-selection factory.

Evidence:

- **The factory:** `store/db/db.go:14-30` — `NewDBDriver(profile)` switches on `profile.Driver` and calls `mysql.NewDB(profile)` at `store/db/db.go:22` (alongside `sqlite.NewDB` / `postgres.NewDB`).
- **Only external reference:** grepping every `.go` file for `mysql.` outside `store/db/mysql/` yields exactly one hit for the constructor — `store/db/db.go:22`. The other matches are unrelated packages that happen to be named `mysql`: `github.com/go-sql-driver/mysql` (`store/db/mysql/mysql.go:17,30,73` — `mysql.Config`, `mysql.ParseDSN`) and the testcontainers MySQL module (`store/test/containers.go:42,101-105` — `mysql.MySQLContainer`, `mysql.Run`), neither of which constructs the store driver.
- **All driver consumers go through the factory:** `cmd/memos/main.go:57`, `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70` all call `db.NewDBDriver(...)`, never a concrete driver constructor.
- **One caveat (test-only, in-package):** `store/db/mysql/auth_config_test.go:12` builds the struct literal directly — `db := &DB{}` — but that's a zero-value struct inside the `mysql` package used solely to invoke the pure method `IsRetryableAuthenticationMutationError`; it opens no connection and doesn't use `NewDB`. Note also that `NewDB` itself returns `&driver` from a local `DB{profile: profile}` literal (`store/db/mysql/mysql.go:29`), which is the constructor's own internals rather than an external construction site.
