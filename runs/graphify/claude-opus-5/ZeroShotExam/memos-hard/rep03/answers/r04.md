**Premise correction:** Neither. This repo (Memos) has no external message broker at all — no NATS, RabbitMQ, AMQP, Kafka, or Redis appears anywhere in `go.mod`/`go.sum` or the Go sources. There is no separate "worker" process either; the webhook workers are goroutines inside the single Memos binary.

**Actual mechanism — an in-process buffered Go channel:**

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel with capacity 128.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` starts exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`, logging a warning on failure. The workers live for the process lifetime; nothing closes the channel.
- **Producer:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a `slog.Warn` ("Dropped webhook dispatch because the async queue is full") — there is no persistence, no retry, and no redelivery, so webhooks are lost on overflow or on process restart.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` enqueue payloads for memo created/updated/deleted and comment-created events, after loading endpoints via `s.Store.GetUserWebhooks`.
- **Delivery itself:** `Post` (`internal/webhook/webhook.go:120-180`) does a plain `POST` over a shared `http.Client` with a 30s timeout and an SSRF-guarding dialer (`safeDialContext`, `:59`), optionally signing with Standard Webhooks HMAC-SHA256 headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`).

This matches the project's stated design of a single self-contained Go binary (`README.md`, "Single Go binary" under Features) with no broker infrastructure to deploy.
