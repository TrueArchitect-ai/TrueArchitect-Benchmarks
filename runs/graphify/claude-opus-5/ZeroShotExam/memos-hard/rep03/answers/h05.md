**Mechanism: explicit Go code** — inside the `DeleteUser` transaction in each DB driver. There is no database-level cascade for reactions.

## The explicit deletion (two passes)

`store/db/sqlite/user_delete.go:92-104` (`deleteUserTargetsTx`) calls, in order:

1. `deleteReactionsByContentIDsTx` — `store/db/sqlite/user_delete.go:380-389`: `DELETE FROM reaction WHERE content_id IN (...)` — removes *everyone's* reactions on the deleted user's memos. The content IDs come from `memoContentIDsFromRefs` (`:512-518`), which builds `"memos/" + memo.UID` from the collected memo tree.
2. `deleteReactionsByCreatorTx` — `store/db/sqlite/user_delete.go:400-403`: `DELETE FROM reaction WHERE creator_id = ?` — removes the deleted user's own reactions on other people's memos.

Both run inside the transaction opened at `store/db/sqlite/user_delete.go:29-58`, which commits only after all deletes succeed (with a test failpoint to force rollback). The same code exists per-dialect at `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`.

Entry points: `store/user.go:171` (`Store.DeleteUser` → driver, then cache invalidation via `store/user_delete.go:39`), called from `server/router/api/v1/user_service.go:414`.

## What I checked to rule out a DB-level rule

- Schema: `reaction` table in `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:90-97` — columns `creator_id`, `content_id`, no `FOREIGN KEY` / `ON DELETE CASCADE`. A grep for `FOREIGN KEY|REFERENCES` across all three `LATEST.sql` files returns exactly one hit each — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (line ~108) — and nothing on `reaction`.
- Original reaction migrations (`store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql`, `.../0.23/00__reactions.sql`) — no FK constraints either.
- Triggers: the only triggers in the migration tree are legacy modification-time triggers, dropped in `store/migration/sqlite/0.7/01__remove_triggers.sql`. None touch reactions.

Note the `content_id` side *couldn't* use an FK anyway — it's a TEXT resource name (`memos/<uid>`), not a numeric memo FK, which is why the Go code resolves memo UIDs first.
