**Premise correction:** There is no Redis anywhere in this repository. A repo-wide search (excluding `.git/` and `graphify-out/`) for `redis`/`ioredis` returns zero hits, and `go.mod` pulls in no cache client library. The cache layer is a hand-rolled, in-process, in-memory cache — nothing external, nothing network-backed, and nothing shared between server instances.

**Actual mechanism**

*The implementation* — `store/cache/cache.go`: a `Cache` struct backed by a `sync.Map` plus an `atomic.Int64` item counter. Each entry is an `item{value, expiration, size}`. Expiry is lazy on read (`Get` at `store/cache/cache.go:135` deletes and reports a miss when `time.Now().After(itm.expiration)`) plus a background `cleanupLoop` goroutine (`store/cache/cache.go:200`) that sweeps expired entries on a ticker. There's also a `MaxItems` cap that triggers `cleanupOldest` to drop ~20% of capacity when exceeded.

*Where it's "configured"* — `store/store.go:40-54`, inside `store.New()`. The config is hardcoded in Go, not read from env vars or a config file:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That single config value is used to construct three separate cache instances: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). All three are closed in `Store.Close()` (`store/store.go:73-76`) to stop their cleanup goroutines.

*TTL for user entries* — **10 minutes**, from `DefaultTTL`. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). Nothing in the user path calls `SetWithTTL` directly, so there is no user-specific TTL override — users, user settings, and instance settings all share the same 10-minute expiry and 5-minute cleanup cadence.

*Cache key and invalidation* — user entries are keyed by the bare user ID as a string (`userCacheKey`, `store/user.go:88`). Reads only hit the cache when the lookup is by ID (`store/user.go:149-156`); a `FindUser` by username or email always falls through to the driver. Deletion explicitly evicts via `s.userCache.Delete(ctx, userCacheKey(userID))` at `store/user_delete.go:40`. User *settings* use a separate composite key `"<userID>-<key>"` built by `getUserSettingCacheKey` in `store/cache.go:7`.
