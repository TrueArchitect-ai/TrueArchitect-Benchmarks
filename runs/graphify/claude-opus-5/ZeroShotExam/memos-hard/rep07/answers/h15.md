h15.

Memo visibility is enforced independently in a number of places — there is no single chokepoint. The distinct sites:

**Core API read gate (shared helper)**
- `checkMemoReadAccess` — anonymous blocked on non-public, PRIVATE restricted to creator; called by `GetMemo` (and its parent-memo check) and `ListMemoComments` — `server/router/api/v1/memo_service.go:39` (callers at `:356`, `:367`, `server/router/api/v1/memo_service_comments.go:148`)

**Query-scoping (list/stat surfaces build a visibility-restricted store query instead of checking per memo)**
- `ListMemos` visibility scoping — `server/router/api/v1/memo_service.go:218-227`
- `ListAllUserStats` visibility scoping — `server/router/api/v1/user_service_stats.go:77-92`
- `GetUserStats` visibility scoping — `server/router/api/v1/user_service_stats.go:216-221`
- RSS feeds (public-only) — `server/router/rss/rss.go:90`, `server/router/rss/rss.go:141`
- Sitemap XML (public-only) — `server/router/frontend/frontend.go:150`

**Per-memo checks re-implemented inline (not using the helper)**
- `ListMemoReactions` — `server/router/api/v1/reaction_service.go:29-41`; reaction upsert/delete — `server/router/api/v1/reaction_service.go:83`
- `CreateMemoComment` — `server/router/api/v1/memo_service_comments.go:41` (and comment-visibility rule at `:100`)
- `ListMemoAttachments` — `server/router/api/v1/memo_attachment_service.go:213-225`
- Attachment access check (linked attachments inherit memo visibility) — `server/router/api/v1/attachment_service.go:444-453`

**Non-gRPC HTTP surface**
- Raw file/attachment server, incl. anonymous-instance rule and `share_token` fallback — `server/router/fileserver/fileserver.go:665-701`

**Realtime**
- SSE broadcast filter `SSEClient.canReceive` — `server/router/api/v1/sse_hub.go:134-143` (event visibility stamped in `server/router/api/v1/sse_event_helpers.go:29-37`)

**Share-link bypass path (visibility deliberately not enforced; token validity/expiry + archived check substitute for it)**
- `GetMemoByShare` — `server/router/api/v1/memo_share_service.go:153-192`

**Notification/mention fan-out (gates whether memo content reaches a recipient)**
- Inbox notifications `canViewerAccessMemo` — `server/router/api/v1/user_service_notifications.go:302-315`
- Email notifications, a second independent copy of `canViewerAccessMemo` — `server/notification/email.go:306-320`
- Mention targets `canUserAccessMentionContext` — `server/router/api/v1/memo_mention_helpers.go:56-72`

Note: the MCP surface is not a separate enforcement site — `server/router/mcp/adapter.go:33-84` replays tool calls as in-process HTTP requests against the v1 API, so it inherits the checks above.

Two things worth flagging: `canViewerAccessMemo` exists twice with a subtle divergence (`isSuperUser(user)` in `user_service_notifications.go:306` vs. `viewer.Role == store.RoleAdmin` in `email.go:310`), and the inline per-memo checks in reactions/attachments/comments duplicate `checkMemoReadAccess` but add `isSuperUser` — which `checkMemoReadAccess` itself does *not* honor.
