**Premise correction:** There is no Redis in this repository. A case-insensitive grep across the whole tree (excluding `.git`) returns zero hits for "redis", and `go.mod` contains no Redis client (no `go-redis`, `redigo`, etc.). Memos is a single-binary app whose only external datastore is SQL (SQLite / MySQL / PostgreSQL). So there is no Redis connection to configure, and no Redis-side TTL/expiry on user entries.

**Actual mechanism — an in-process in-memory cache:**

- **Implementation:** `store/cache/cache.go` — a thread-safe cache built on `sync.Map` plus an `atomic.Int64` item counter, with per-item `expiration time.Time` (`cache.go:35-39`) and a background `cleanupLoop` goroutine (`cache.go:200-215`). Interface: `Set`, `SetWithTTL`, `Get`, `Delete`, `Clear`, `Size`, `Close` (`cache.go:11-32`).
- **Where it's "configured":** `store/store.go:38-61`. `store.New` builds one `cache.Config` literal and uses it for three separate cache instances:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  - `OnEviction: nil`
  
  That config is shared by `instanceSettingCache`, `userCache`, and `userSettingCache` (`store.go:51-53`). An equivalent `DefaultConfig()` with the same three values also lives at `store/cache/cache.go:57-64`, but `store.New` supplies its own literal rather than calling it. Caches are torn down in `Store.Close` (`store.go:72-79`).

- **TTL that applies to user entries: 10 minutes**, inherited from `DefaultTTL`. Every write to `userCache` goes through `Set`, never `SetWithTTL` — see `store/user.go:98` (CreateUser), `:122` (CreateUserIfNoUsers), `:132` (UpdateUser), `:143` and `:167` (list/get paths). `Set` forwards to `SetWithTTL(..., c.config.DefaultTTL)` (`cache.go:93-95`). Grepping for `SetWithTTL` callers outside the cache package returns nothing, so no user entry ever gets a custom TTL.

Two caveats worth noting beyond the raw TTL:

1. **Eviction can happen before 10 minutes.** With `MaxItems: 1000`, exceeding the cap triggers `cleanupOldest` (`cache.go:117-119`, `253-313`), which drops ~20% (200) of entries by soonest expiration regardless of remaining TTL.
2. **Expiry is lazy plus swept.** `Get` checks expiration on read and deletes on the spot (`cache.go:135-144`); the 5-minute `cleanupInterval` sweep (`cache.go:218-250`) reclaims the rest. So a stale user entry can linger in the map past 10 minutes but is never served.
3. **Explicit invalidation on delete:** `store/user_delete.go:39-47` removes the user key and its associated user-setting keys. Cache keys are just the stringified user ID (`store/user.go:88-90`); user settings use `"<userID>-<key>"` (`store/cache.go:7-9`).

Because the cache is per-process, running multiple Memos instances against one database gives each its own independent 10-minute user cache — there is no shared invalidation, which is exactly the gap a Redis layer would fill if one existed.
