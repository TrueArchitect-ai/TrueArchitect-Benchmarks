**Mechanism: explicit Go code** — the delete-user transaction issues two `DELETE FROM reaction` statements per driver. There is **no** database-level cascade for reactions (the `reaction` table has no foreign keys at all).

## Evidence

**Explicit deletes (all three drivers, identical structure):**

Inside the single delete transaction, `deleteUserTargetsTx` runs both reaction deletes before deleting memos (`store/db/sqlite/user_delete.go:96,102`, `store/db/postgres/user_delete.go:96,102`, `store/db/mysql/user_delete.go:96,102`):

1. `deleteReactionsByContentIDsTx` — deletes reactions *on the deleted user's memos/comments*, regardless of who reacted. Batched at 500 IDs (`store/db/sqlite/user_delete.go:380-388`, postgres `:380`, mysql `:417`). Content IDs are the memo resource names, built as `"memos/"+memo.UID` (`store/db/sqlite/user_delete.go:512-518`).
2. `deleteReactionsByCreatorTx` — deletes reactions the user left *on anyone's* content: `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`, postgres `:400`, mysql `:437`).

Entry point: `DeleteUser` opens the tx, collects targets, calls `deleteUserTargetsTx`, then commits (`store/db/sqlite/user_delete.go:29-59`); reached from the API at `server/router/api/v1/user_service.go:393-414`.

**No DB-level rule:** the `reaction` table definition has only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`/`ON DELETE CASCADE` on `creator_id` or `content_id`, in any dialect:
- `store/migration/sqlite/LATEST.sql:92-99` and `store/migration/sqlite/0.20/00__reaction.sql`
- `store/migration/postgres/LATEST.sql:91-98` and `store/migration/postgres/0.20/00__reaction.sql`
- `store/migration/mysql/LATEST.sql:91-98` and `store/migration/mysql/0.20/00__reaction.sql`

A repo-wide grep for `FOREIGN KEY|REFERENCES` across `store/migration/` returns hits only for `memo_share`, `user_setting`, `memo`, `memo_resource`, etc. — none for `reaction`.

**Test confirmation** (`server/router/api/v1/test/user_service_delete_test.go`): after deletion, reactions on the user's own memo and on their comment are empty (`:287-293`), while another user's reaction on a *foreign* memo survives (`:295-298`) — and the rollback test verifies the reaction is still present when the pre-commit failpoint fires (`:429-431`), confirming the deletes are inside the same transaction.

One consequence of there being no FK: since these deletes are hand-written, any reaction row whose `content_id` points at content not covered by the two queries would be orphaned rather than cleaned up by the database.
