**How I determined which of the three implementations runs**

There are exactly three implementations of `Driver.CreateMemo`: `store/db/sqlite/memo.go:16`, `store/db/mysql/memo.go:16`, `store/db/postgres/memo.go:16`. Selection is a plain runtime `switch profile.Driver` in `store/db/db.go` (`NewDBDriver`) — no build tags, no plugin registry, so the answer is fixed entirely by the `driver` config value:

- `cmd/memos/main.go:130` — `rootCmd.PersistentFlags().String("driver", "sqlite", "database driver")`
- `cmd/memos/main.go:122` — `viper.SetDefault("driver", "sqlite")` (covers the env-var/config-file path when no flag is passed)
- `cmd/memos/main.go:43` — `Driver: viper.GetString("driver")` feeds that into the profile, which is passed to `db.NewDBDriver` at `main.go:57`.

With no flags, both the viper default and the flag default are `"sqlite"`, so `db.go` takes the `case "sqlite"` branch → `sqlite.NewDB(profile)` (`store/db/sqlite/sqlite.go:24`), whose returned `*sqlite.DB` is stored in `store.New(dbDriver, ...)` at `main.go:64`. `internal/profile/profile.go` confirms this is a complete default: when `Driver == "sqlite"` and `DSN` is empty, it synthesizes `<data>/memos_prod.db`, so no database flag is required at all.

Two supporting details worth noting: the SQLite implementation is distinguishable from the others by its backtick-quoted identifiers and `?` placeholders (Postgres uses `$n`), and it relies on SQLite's `RETURNING` clause to populate `ID`/`CreatedTs`/`UpdatedTs`/`RowStatus` on the passed-in struct — the MySQL version at `store/db/mysql/memo.go` cannot do this and uses `LastInsertId` instead. The underlying SQL driver is `modernc.org/sqlite` (pure Go, registered in `store/db/sqlite/functions.go` per the comment at `sqlite.go:9-10`).
