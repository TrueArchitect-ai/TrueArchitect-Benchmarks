**Premise correction:** Neither. This repository (memos, a Go monolith) has no message broker at all — there is no NATS, RabbitMQ, Kafka, or Redis dependency anywhere in `go.mod`/`go.sum`, and no external "delivery workers" process. Grepping the tree for `nats`, `amqp`, `rabbit` returns nothing outside of unrelated text.

**Actual mechanism:** webhook delivery is an in-process fan-out over a buffered Go channel, entirely inside the server binary.

- **The "queue"** is declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A package-level `chan *WebhookRequestPayload` with a fixed capacity of 128.

- **The "workers"** are 4 goroutines started in the package `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. There is no retry, no ack, and no persistence — a failed delivery is dropped after one attempt.

- **Enqueue** happens in `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send. If the buffer is full, the payload is **discarded** with a "Dropped webhook dispatch because the async queue is full" warning — so backpressure is handled by dropping, not by blocking or spilling to a broker.

- **Producers** are the API service methods in `server/router/api/v1/memo_service_webhooks.go` (`DispatchMemoCreatedWebhook`, `...Updated`, `...Deleted`, `DispatchMemoCommentCreatedWebhook` — see lines 43 and 71), which look up the user's webhooks via `s.Store.GetUserWebhooks` and call `webhook.PostAsync` per hook.

- **Actual sending** is `Post` (`internal/webhook/webhook.go:120`): a plain HTTP POST over a shared `safeClient` (30s timeout, SSRF-guarded dialer at `webhook.go:59`), optionally HMAC-SHA256 signed per the Standard Webhooks spec (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers).

Because the queue lives in process memory, it is also not shared across replicas and does not survive a restart.
