**Premise correction:** There is no Redis in this repository. This is Memos (`github.com/usememos/memos`), and a case-insensitive search for `redis`/`memcach` across the whole tree returns nothing — no client dependency in `go.mod`, no connection string, no config key, no env var. The cache layer is **in-process, in-memory**, consistent with the project's "single Go binary" design (`README.md`). So there is no Redis connection to configure.

**Actual mechanism:**

The cache is a hand-rolled in-memory cache in `store/cache/cache.go` — a `sync.Map` of `item{value, expiration, size}` guarded by an `atomic.Int64` item count, with a background `cleanupLoop` goroutine (`store/cache/cache.go:200`) evicting expired entries on a ticker.

**Where it's "configured"** — `store/store.go:38-61`, in `store.New()`. The config is a hardcoded literal, not read from any env var or config file:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That single config value is used to construct three separate cache instances (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. The same defaults are also duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), but that constructor isn't used by the store.

**TTL on user entries:** **10 minutes.** User objects are written via `s.userCache.Set(...)` (`store/user.go:98`, `:122`, `:132`, `:143`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). Nothing in the user path calls `SetWithTTL` with a custom duration, so users get the shared 10-minute default — as do user settings (`store/user_setting.go:59`, keyed `<userID>-<key>` by `getUserSettingCacheKey` in `store/cache.go:7`) and instance settings.

Two details worth noting:

- **Expiry is lazy, plus a sweep.** `Get` checks `time.Now().After(itm.expiration)` and deletes on read (`store/cache/cache.go:135-144`); the 5-minute `cleanupLoop` sweep catches entries never read again. So a user entry can linger in the map past 10 minutes but will never be *served* past it.
- **TTL isn't the only invalidation.** Writes refresh the entry (`CreateUser`/`UpdateUser`/`ListUsers` all re-`Set`), and `deleteUserCache` (`store/user_delete.go:39-45`) explicitly evicts both the user and its settings. There's also capacity-based eviction at `MaxItems: 1000` via `cleanupOldest` (`store/cache/cache.go:253`), which drops ~20% when the cap is exceeded.

Because the cache lives inside the process, it is not shared across replicas — each Memos instance holds its own copy, and there is no cross-process invalidation.
