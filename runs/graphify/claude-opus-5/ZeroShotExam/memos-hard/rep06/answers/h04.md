**No** — outside the factory, no other package constructs the MySQL driver. (One in-package unit test builds a zero-value `DB{}`, but that's inside `store/db/mysql` itself, not an external construction site.)

Evidence:

1. **The factory is the sole external caller.** `store/db/db.go:22` — `driver, err = mysql.NewDB(profile)` inside `NewDBDriver`. A repo-wide grep for `mysql.NewDB` across all `.go` files returns exactly this one hit.

2. **Only one file in the whole repo imports the driver package.** `grep -rn "store/db/mysql" --include=*.go .` returns a single result: `store/db/db.go:8`. Since `NewDB` and the `DB` struct are only reachable via that import path, no other package *can* construct it — the encapsulation is enforced by the import graph, not just by convention. (Note `NewDB` returns the `store.Driver` interface, not `*mysql.DB`, so callers get an abstract handle anyway — `store/db/mysql/mysql.go:19`.)

3. **All consumers go through the factory.** `NewDBDriver` call sites are `store/test/store.go:28`, `store/test/store.go:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70`. Test helpers select the driver by populating `profile.Driver`/`profile.DSN` (`store/test/store.go:88` sets the MySQL DSN) and then let the factory dispatch — they never reach into the mysql package.

4. **The one direct struct literal outside `NewDB` is intra-package test code.** `store/db/mysql/auth_config_test.go:12` — `db := &DB{}` — a zero-value struct used to call the pure helper `IsRetryableAuthenticationMutationError`; no connection is opened. It compiles only because it lives in `package mysql`. The genuine construction path stays `store/db/mysql/mysql.go:29` (`driver := DB{profile: profile}`) inside `NewDB`.

Other `mysql` matches in the tree are unrelated: the upstream `github.com/go-sql-driver/mysql` package (DSN parsing, error types) and the testcontainers MySQL module in `store/test/containers.go:16,20`, which stands up a MySQL *container*, not the app's driver type.
