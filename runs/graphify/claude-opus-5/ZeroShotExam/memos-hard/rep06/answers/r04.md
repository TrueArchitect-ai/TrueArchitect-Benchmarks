**Premise correction:** Neither. There is no external message broker anywhere in this repo — `go.mod`/`go.sum` contain no NATS, AMQP/RabbitMQ, Kafka, or Redis dependency, and there is no broker service in any deployment config. There are also no separate "webhook delivery workers" as a deployable unit; delivery happens inside the single Memos server process.

**Actual mechanism — an in-process buffered Go channel:**

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel with capacity 128.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` starts 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`; failures are only logged (`slog.Warn`), so there is no retry or dead-letter handling.
- **Producer:** `PostAsync` at `internal/webhook/webhook.go:184-196` does a non-blocking `select` send; if the buffer is full the payload is **dropped** with a "Dropped webhook dispatch because the async queue is full" warning. Nil payloads are dropped too.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go` (`dispatchMemoRelatedWebhook` at line ~48 and `DispatchMemoCommentCreatedWebhook`) look up the user's webhooks via `s.Store.GetUserWebhooks` and call `webhook.PostAsync` per hook.
- **Delivery itself:** `Post` (`internal/webhook/webhook.go:120`) does a plain HTTP POST through `safeClient`, a 30s-timeout `http.Client` whose dialer (`safeDialContext`, line 59) rejects reserved/private IPs for SSRF protection, and optionally signs with Standard Webhooks HMAC-SHA256 headers (`webhook-id`/`webhook-timestamp`/`webhook-signature`).

Practical consequence: the queue is memory-only and per-process — pending webhooks are lost on restart, and bursts beyond 128 queued items are silently discarded rather than backpressured.
