**Where the URL comes from (why the browser requests it):** the API never returns raw avatar bytes — `convertUserFromStore` rewrites a base64 avatar into the path `/file/users/{username}/avatar`, and `<UserAvatar>` puts that in an `<img src>`.

- `convertUserFromStore` — `server/router/api/v1/user_service_converters.go:16` (URL built at :36)
- `UserAvatar` — `web/src/components/UserAvatar.tsx:9` (`<img src={avatarUrl}>`)

**Back out:** `FileServerService.parseDataURI` (`fileserver.go:737`) splits the stored `data:<mime>;base64,...` string, the MIME type is checked against `avatarAllowedTypes` (`fileserver.go:74`), security + cache headers are set (`setSecurityHeaders`, `fileserver.go:764`), and the decoded bytes go out via `c.Blob` (`fileserver.go:206`).

The key fact about the data layer: avatars are **not** attachments/blob storage. They live inline in the `user.avatar_url` column as a base64 data URI, so the terminal hop is the user-row query, not `store.GetAttachment` or S3/local-file access.
