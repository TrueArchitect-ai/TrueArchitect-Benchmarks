**Premise correction:** There is no Redis in this repository. The cache layer is a hand-rolled, in-process, in-memory cache — no external cache server, no client library. `grep -ri redis` across the Go sources, `go.mod`, `go.sum`, `docs/`, and the web frontend returns zero hits. So there is no "Redis connection" to configure anywhere.

**Actual mechanism:**

**Implementation** — `store/cache/cache.go` defines `cache.Cache`, a thread-safe in-memory cache backed by a `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). Entries carry an absolute `expiration time.Time` (`store/cache/cache.go:34-39`), and a background goroutine (`cleanupLoop`, `store/cache/cache.go:200-215`) sweeps expired items on a ticker. Expired entries are also evicted lazily on read (`store/cache/cache.go:135-144`). There is a `MaxItems` bound enforced by `cleanupOldest` (`store/cache/cache.go:253`).

**Where it's "configured"** — in Go code, not in any config file or env var. `store.New` builds a single `cache.Config` literal and hands the same config to all three caches (`store/store.go:38-58`):

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

The three instances are `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`, `store/store.go:51-53`), all closed on shutdown (`store/store.go:72-79`). An identical set of defaults is duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), though `store.New` doesn't call it — it inlines its own copy.

**TTL for user entries — 10 minutes.** Users are cached in `userCache` keyed by the stringified user ID (`userCacheKey`, `store/user.go:88-90`). Every write goes through `Set`, not `SetWithTTL` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` applies `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — so the 10-minute `DefaultTTL` from `store/store.go:41`. There is no user-specific TTL override; `SetWithTTL` is only ever called from the test file (`store/cache/cache_test.go:26`). User settings (`userSettingCache`, keyed `userID-key` via `store/cache.go:7-9`) get the same 10 minutes.

Note the TTL is not the only lifetime control: entries are invalidated explicitly on user deletion (`store/user_delete.go:40`, `:45`), and can be dropped early by the `MaxItems: 1000` eviction path regardless of remaining TTL.
