**No** — outside the factory, the MySQL driver is never constructed as a real, usable driver anywhere in the codebase. The one exception is a zero-value struct literal in a unit test, which is not a constructed driver.

Evidence:

- **The only production construction site is the factory.** `store/db/db.go:22` calls `mysql.NewDB(profile)` inside `NewDBDriver`, the single dispatch point over `profile.Driver` (`sqlite` / `mysql` / `postgres`).
- **Nothing else imports the package.** `grep -rn "db/mysql" --include="*.go"` returns exactly one hit: the import in `store/db/db.go:8`. Since `mysql.NewDB` and the `mysql.DB` type are only reachable through that import path, no code outside `store/db/mysql/` and `store/db/db.go` can construct it.
- **`mysql.NewDB` has exactly one caller**, `store/db/db.go:22` (grep for `mysql.NewDB`).
- **All factory consumers go through `NewDBDriver`**: `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70`. The test harness in `store/test/containers.go` mentions MySQL only for container/DSN setup, not driver construction.
- **In-package literals**: `store/db/mysql/mysql.go:29` (`driver := DB{profile: profile}`) is inside `NewDB` itself. The only other literal is `store/db/mysql/auth_config_test.go:12` (`db := &DB{}`) — a zero-value struct with a nil `*sql.DB`, used solely to invoke the pure method `IsRetryableAuthenticationMutationError`, so it never acts as a database driver.

For contrast, the Postgres driver *is* constructed directly outside its own constructor path in tests: `store/db/postgres/user_setting_test.go:36`, `:194`, `:257` build `&DB{db: db}` with a live/mock handle. MySQL has no equivalent.
