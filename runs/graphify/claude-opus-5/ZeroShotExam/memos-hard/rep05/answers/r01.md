**Premise correction:** There is no Redis in this repository — nothing to configure. A case-insensitive search for `redis` (also `memcached`/`valkey`) across the entire tree, including `go.mod`/`go.sum`, `docs/`, `scripts/`, and `AGENTS.md`, returns zero hits. The cache layer is **purely in-process, in-memory Go**, which fits the project's stated design ("Single Go binary, ~20MB Docker image", `README.md`) — there is no external cache server, no connection string, no client, and no network hop at all.

**The actual mechanism**

*Implementation* — `store/cache/cache.go` defines the whole cache layer: a `Cache` struct backed by a `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). Each entry is an `item{value, expiration, size}` (`store/cache/cache.go:35-39`). Configuration is a plain `Config` struct — `DefaultTTL`, `CleanupInterval`, `MaxItems`, `OnEviction` (`store/cache/cache.go:41-54`) — not a DSN or connection object.

*Where it's "configured"* — in `store.New()` at `store/store.go:40-45`, constructed inline:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

The same `cacheConfig` value is passed to three separate caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`, declared at `store/store.go:27-29`). These values are hardcoded; there is no env var or config-file override. `cache.DefaultConfig()` at `store/cache/cache.go:57-64` duplicates the identical numbers but isn't what the store uses.

**TTL for user entries: 10 minutes**, inherited from `DefaultTTL`. Every user write path calls `Set` (not `SetWithTTL`) — `CreateUser` (`store/user.go:98`), `CreateUserIfNoUsers` (`:122`), `UpdateUser` (`:132`), `ListUsers` per-user (`:143`), and `GetUser` (`:167`) — and `Set` delegates to `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:92-95`). No user-specific TTL is defined anywhere. Keys are just the stringified user ID (`userCacheKey`, `store/user.go:88-90`).

Two caveats worth noting: expiry is lazy-plus-sweep — `Get` checks `time.Now().After(itm.expiration)` and evicts on read (`store/cache/cache.go:135-144`), while a background `cleanupLoop` sweeps every 5 minutes (`store/cache/cache.go:200-215`). And entries can be dropped *before* 10 minutes: exceeding `MaxItems: 1000` triggers `cleanupOldest`, which evicts ~20% (`store/cache/cache.go:117-119`, `:253-255`). Explicit invalidation happens on delete (`store/user_delete.go:40`).

Because the cache lives in the process, it is not shared across replicas — each instance holds its own copy, so a user updated on one node can be served stale by another for up to 10 minutes. That's the tradeoff Redis would normally address, and it's simply not taken here.

*Unrelated but nearby:* a second, independent cache exists for instance stats with a 60-second TTL (`instanceStatsCacheTTL`, `server/router/api/v1/instance_stats.go:21`) — also in-memory, not part of the store cache layer.
