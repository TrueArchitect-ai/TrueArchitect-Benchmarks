**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the driver's user-deletion transaction. There is **no** database-level rule (no foreign key, no `ON DELETE CASCADE`) on the `reaction` table.

## What I checked

**1. Schema — is there a DB-level cascade?** No.

`reaction` is declared with a bare `creator_id` column and no FK in any dialect:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/mysql/LATEST.sql:91-98`
- `store/migration/postgres/LATEST.sql:91-98`
- original creation migrations: `store/migration/{sqlite,mysql,postgres}/0.20/00__reaction.sql`

A repo-wide grep for `REFERENCES|FOREIGN KEY` across `store/migration/` returns hits only for `memo_share`, `user_setting`, `memo_resource`, and the old `memo.creator_id` — never `reaction`. So nothing cascades from `user` to `reaction`.

**2. Delete path — where the Go code does it.** Two separate deletes, both in the same transaction:

`store/db/sqlite/user_delete.go:92-127` (`deleteUserTargetsTx`) calls:
- `deleteReactionsByContentIDsTx` (line 96) → `DELETE FROM reaction WHERE content_id IN (...)` at `store/db/sqlite/user_delete.go:380-388`. Removes reactions *other people* left on the deleted user's memos. The content IDs are `"memos/"+uid` (`store/db/sqlite/user_delete.go:512-518`), gathered from the recursive memo subtree in `listDeleteUserMemoTree` (line 129).
- `deleteReactionsByCreatorTx` (line 102) → `DELETE FROM reaction WHERE creator_id = ?` at `store/db/sqlite/user_delete.go:400-403`. Removes reactions the deleted user left *on anyone's* memos.

Identical logic in the other two drivers:
- `store/db/mysql/user_delete.go:420` and `:438`
- `store/db/postgres/user_delete.go:383` and `:401`

**3. Call chain.** `server/router/api/v1/user_service.go:414` → `store/user.go:171` (`Store.DeleteUser`, which just delegates to the driver and invalidates cache) → the driver `DeleteUser` at `store/db/sqlite/user_delete.go:29`, which wraps everything in one `BeginTx`/`Commit`.

**4. Tests confirming the behavior.**
- `server/router/api/v1/test/reaction_service_test.go:229-233` — after `Store.DeleteUser(reactor)`, `ListMemoReactions` on another user's memo returns empty.
- `server/router/api/v1/test/memo_service_test.go:405`, `:445` — same pattern.
- `server/router/api/v1/test/user_service_delete_test.go:366`, `:429-431` — with a before-commit failpoint, the reaction is still present after rollback, which is the tell that removal is transactional application code rather than a DB rule.

**Answer:** explicit Go code, in a single transaction, covering both directions (reactions authored by the user and reactions on the user's memos); evidence in `store/db/{sqlite,mysql,postgres}/user_delete.go` and the absence of any FK in `store/migration/*/LATEST.sql`.
