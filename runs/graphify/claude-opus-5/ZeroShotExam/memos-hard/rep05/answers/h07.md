**Where the URL comes from:** the browser never gets raw avatar bytes in the user JSON — `convertUserFromStore` rewrites a base64 data-URI avatar into the path `/file/users/{username}/avatar` (`server/router/api/v1/user_service_converters.go:31-39`, name built by `BuildUserName` at `server/router/api/v1/user_resource_name.go:13`). `<UserAvatar>` puts that into an `<img src>` (`web/src/components/UserAvatar.tsx:14`), so the browser issues a plain GET.

Two notes worth flagging:

- The avatar bytes live **in the `user.avatar_url` column as a base64 data URI**, not in object/file storage. So the "data layer" hop terminates at the SQL row — there is no local-disk or S3 branch here, unlike `serveAttachmentFile`, which fans out to `resolveLocalPath`/`getAttachmentReader`/S3 (`server/router/fileserver/fileserver.go:126-190`).
- The handler resolves the target user by **username only** (`store.FindUser{Username: &identifier}`), and authorization is coarse: on a public instance (`Profile.AllowAnonymous()`) any visitor gets any user's avatar; on a private instance any authenticated viewer does. There's no per-user check tying the viewer to the requested profile.
