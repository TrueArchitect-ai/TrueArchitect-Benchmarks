**Premise correction: this repository has no per-user API rate-limiting middleware.** Memos does not register any rate limiter — there is no request-per-user/per-IP throttle, no 429/`Too Many Requests` path, and no rate-limiting dependency in use (`golang.org/x/time` appears in `go.mod:151` only as an *indirect* dependency, not imported by any code). The only occurrence of the phrase "rate limit" in the codebase is aspirational documentation for a future email feature (`internal/email/README.md:286-295`, `internal/email/doc.go:86`), not implemented behavior.

What actually exists at the middleware/interceptor layer:

**Echo middleware** — `server/server.go:51-52`: only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:13`). Plus static-file and SPA-fallback middleware in `server/router/frontend/frontend.go:54,59`.

**Connect RPC interceptor chain** — `server/router/api/v1/v1.go:133-138`, defined in `server/router/api/v1/connect_interceptors.go`:
- `MetadataInterceptor` (line 22) — HTTP headers → gRPC metadata
- `LoggingInterceptor` (line 98)
- `RecoveryInterceptor` (line 165)
- `AuthInterceptor` (line 208) — authn/anonymous-access policy only

No rate-limiting interceptor is in that chain.

The closest things to "limits", none of which are per-user:

| Limit | Value | Location |
|---|---|---|
| Max API request body size | 256 MiB (`256 << 20`) | `server/router/api/v1/v1.go:20`, applied at lines 126, 141, 144 |
| Concurrent image EXIF-strip ops | 2 (process-wide semaphore) | `server/router/api/v1/v1.go:60`, acquired in `attachment_service_image.go:68-75` |
| Concurrent thumbnail generation (API) | 3 | `server/router/api/v1/v1.go:59` |
| Concurrent thumbnail generation (file server) | 3 (`maxConcurrentThumbnails`) | `server/router/fileserver/fileserver.go:45-46,116` |

These are global concurrency semaphores guarding memory exhaustion, not per-user request budgets — they are shared across all users and enforce no requests-per-time-window. When the image semaphore is exhausted the server returns `codes.ResourceExhausted` "too many image processing requests" (`server/router/api/v1/attachment_service.go:160`), which is the only rate-limit-*looking* error in the codebase.

There is also no login-attempt throttling or account lockout on the auth path (`server/auth/authenticator.go`, `server/router/api/v1/auth_service_session.go`).
