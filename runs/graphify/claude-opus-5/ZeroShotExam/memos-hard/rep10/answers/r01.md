**Premise correction:** There is no Redis (or any external cache server) in this repository. `grep -ri redis` across the whole tree — including `go.mod`/`go.sum` — returns nothing. Memos' cache layer is a hand-rolled, in-process, in-memory cache, so there's no connection string, host/port, or auth to configure at all.

**Actual mechanism**

- **Implementation:** `store/cache/cache.go` — a `Cache` struct backed by `sync.Map` plus an `atomic.Int64` item counter, with per-item `expiration time.Time`, a background `cleanupLoop` goroutine, and size-based eviction (`cleanupOldest`). The `Interface` at `store/cache/cache.go:11` defines `Set`/`SetWithTTL`/`Get`/`Delete`/`Clear`/`Size`/`Close`.

- **Where it's "configured":** `store/store.go:40-45`, inside `store.New()`. The config is a Go literal, not an env var or config file:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  Three separate cache instances share that same config (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, `userSettingCache`. `store/cache/cache.go:57-64` defines an identical `DefaultConfig()`, but `store.New()` doesn't call it — it duplicates the values inline. They're closed in `Store.Close()` (`store/store.go:74-76`).

- **TTL for user entries: 10 minutes**, inherited from `DefaultTTL`. Nothing sets a user-specific TTL — every user write path calls plain `Set`, which forwards to `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:93-95`). The only `SetWithTTL` calls outside the cache package's own code are in `store/cache/cache_test.go:26`.

- **User cache call sites** (`store/user.go`): keyed by user ID as a string (`userCacheKey`, line 88). Populated on `CreateUser` (:98), `CreateUserIfNoUsers` (:122), `UpdateUser` (:132), and every `ListUsers` result (:143); read only in `GetUser` when `find.ID` is set (:150) — lookups by username/email always hit the DB. Invalidated on delete (:179).

- **Caveat worth noting:** because this is per-process memory, the cache is not shared across replicas — running multiple Memos instances against one database means each has its own independently-expiring copy of user rows. Also note `MaxItems: 1000` triggers eviction of ~20% of entries, so user entries can disappear well before the 10-minute TTS under load.

Related: `store/user_setting.go` and `store/instance_setting.go` use the same 10-minute default; the frontend has an unrelated, separate `web/src/components/MemoEditor/services/cacheService.ts` for draft persistence.
