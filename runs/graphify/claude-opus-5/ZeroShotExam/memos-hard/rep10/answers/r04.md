**Premise correction:** Neither. This repo (memos) has no external message broker at all — there is no NATS, RabbitMQ, Kafka, or Redis dependency anywhere in `go.mod`, and no broker client code in the tree. There is also no "queue declaration" in the AMQP/JetStream sense.

**Actual mechanism — an in-process buffered Go channel:**

- **The "queue"** is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, holding `*WebhookRequestPayload` values (defined at `internal/webhook/webhook.go:79-90`).

- **The "workers"** are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`; failures are logged via `slog.Warn` and dropped — there is no retry, no ack/nack, and no dead-letter path.

- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send. If the buffer is full the payload is **dropped** with a warning, not backpressured. Callers are `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

- **Delivery itself** is a plain HTTP POST via the shared `safeClient` (`internal/webhook/webhook.go:32-37`), with SSRF protection at dial time (`safeDialContext`, `internal/webhook/webhook.go:59-77`) and optional Standard Webhooks HMAC-SHA256 signing (`internal/webhook/webhook.go:133-150`).

Consequence worth noting: because the queue lives in process memory, queued webhooks are lost on restart and are not shared across replicas. The same pattern is used for email at `internal/email/email.go` (`asyncEmailQueue`, also cap 128).
