**Premise correction: this repository (Memos) has no per-user API rate-limiting middleware.** There is nothing registered anywhere in the request path, so there are no request limits to report.

**What I checked**

- Every Echo middleware registration in the codebase — `server/server.go:51-52` registers exactly two: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:13`). The frontend service adds only static-file serving and an SPA fallback (`server/router/frontend/frontend.go:54,59`).
- The full Connect RPC interceptor chain, `server/router/api/v1/v1.go:133-137`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` — all defined in `server/router/api/v1/connect_interceptors.go`. No limiter.
- The gRPC-Gateway middleware chain, `server/router/api/v1/v1.go:69-97` — a single `gatewayAuthMiddleware` doing authentication and access-policy checks only.
- A repo-wide grep for `ratelimit`, `throttl`, `golang.org/x/time/rate`, `tollbooth`, `leaky/token bucket`, `429`, and `TooManyRequests` across Go, TS, and config files. The only two hits are aspirational documentation, not implementation.

**The only matches, both non-code:**

- `internal/email/README.md:286-297` — a "Best Practices" section titled *"5. Implement Rate Limiting"* with an illustrative snippet (`rate.NewLimiter(rate.Every(time.Second), 10)` — 10 emails/second). This is a suggestion to consumers of the package; no such limiter is constructed in `internal/email`.
- `internal/email/doc.go:86` — a bullet reading "Rate limit email sending to prevent abuse," also a recommendation.

Note that `golang.org/x/time` appears in `go.mod:151` marked `// indirect` — a transitive dependency, not used by this project's own code.

**Adjacent limits that exist but are not per-user rate limits** (in case one of these is what you were after):

- **Request body size**: `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` to the gateway and Connect handlers (lines 126, 141, 144). This caps bytes per request, not requests per user.
- **Concurrency semaphores**: `thumbnailSemaphore` (3 concurrent) and `imageProcessingSemaphore` (2 concurrent) in `NewAPIV1Service` (`server/router/api/v1/v1.go`, ~line 280). These are global server-wide concurrency caps on image work, not per-user and not time-windowed.

If you want per-user API rate limiting, it would need to be built — the natural insertion points are a new interceptor in the chain at `server/router/api/v1/v1.go:133` (which has authenticated identity available via the `AuthInterceptor`) plus the parallel gateway middleware at line 69, since the two paths are separate.
