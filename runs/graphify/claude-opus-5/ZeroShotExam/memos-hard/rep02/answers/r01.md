**Premise correction:** There is no Redis in this repository. Grepping the entire tree (Go sources, `go.mod`/`go.sum`, YAML, TS/TSX, JSON, Markdown) for `redis` — and for `memcached`/`valkey`/`dragonfly` — returns zero hits. There is no connection string, no client dependency, no env var, and no external cache service of any kind. So there is nothing to "configure" in the sense the question implies.

**Actual mechanism:** the cache layer is a hand-rolled, in-process, in-memory cache.

**Implementation** — `store/cache/cache.go`
- `Cache` (`store/cache/cache.go:67`) is a thread-safe struct backed by a `sync.Map` plus an `atomic.Int64` item counter. No network, no serialization.
- Config knobs are `DefaultTTL`, `CleanupInterval`, `MaxItems`, `OnEviction` (`store/cache/cache.go:41-54`).
- `New` (`store/cache/cache.go:76`) starts a background `cleanupLoop` goroutine that ticks on `CleanupInterval` and sweeps expired entries (`store/cache/cache.go:200-250`). Expiry is also checked lazily on read in `Get` (`store/cache/cache.go:135`).
- When `MaxItems` is exceeded, `cleanupOldest` (`store/cache/cache.go:253`) evicts roughly 20% of `MaxItems` by earliest expiration.

**Where it's "configured"** — `store/store.go:40-45`, hardcoded at `store.New`, not from env or a config file:
```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
The same struct is passed to all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). (`cache.DefaultConfig()` at `store/cache/cache.go:57` has identical values but is not what the store uses.)

**TTL for user entries:** **10 minutes**, with no user-specific override. All writes to `userCache` go through `Set` (`store/user.go:98, 122, 132, 143, 167`), and `Set` applies `c.config.DefaultTTL` (`store/cache/cache.go:94`). `SetWithTTL` exists (`store/cache/cache.go:98`) but is never called for users. Freshness in practice comes from write-through and explicit invalidation rather than the TTL: create/update/list re-`Set` the entry, and `deleteUserCache` (`store/user_delete.go:39-45`) removes the user plus its per-key user settings. Cache-hit reads only happen in `GetUser` when looked up by ID (`store/user.go:148-156`).

Two related caches, for contrast:
- `userSettingCache`, keyed `"<userID>-<settingKey>"` (`store/cache.go:7`), same 10-minute default TTL.
- A separate, unrelated cache at `server/router/api/v1/instance_stats.go:21` uses an explicit `instanceStatsCacheTTL = 60 * time.Second`.

One consequence worth flagging: because this is per-process memory, a multi-replica deployment gives each replica its own independent cache — invalidation on one replica does not propagate to the others, so a stale user can persist elsewhere for up to 10 minutes.
