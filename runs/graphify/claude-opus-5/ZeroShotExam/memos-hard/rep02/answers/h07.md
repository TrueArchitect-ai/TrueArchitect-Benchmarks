The `<img src>` the browser hits is `/file/users/{username}/avatar`, produced by the API when the stored avatar is a base64 data URI. The avatar bytes are **not** in blob/file/S3 storage — they live inline in the `user.avatar_url` column as a data URI, so the "data layer" hop is the user table, not the attachment storage path.

Details worth noting:

- **Auth gate** (fileserver.go:173-181): on a private instance (`!s.Profile.AllowAnonymous()`), `getCurrentUser` → `auth.Authenticator.AuthenticateToUser` (fileserver.go:708) must resolve a session/PAT first. If the instance allows anonymous access, any user's avatar is served unauthenticated — there's no per-viewer check on *which* user's avatar is requested.
- **Cache short-circuit**: `Store.GetUser` only hits the `userCache` when looked up by ID (store/user.go:149). The avatar path looks up by username, so it always falls through to `ListUsers` → SQL, then populates the cache (store/user.go:143).
- **Response** (fileserver.go:196-209): MIME type is taken from the data URI, validated against `avatarAllowedTypes` (fileserver.go:75), then written with `nosniff`/`DENY`/CSP headers and `max-age=3600` via `c.Blob`.
