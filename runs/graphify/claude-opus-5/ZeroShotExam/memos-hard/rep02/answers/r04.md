**Premise correction:** Neither. This repository (memos) has no external message broker at all — there is no NATS, RabbitMQ/AMQP, Kafka, or Redis dependency anywhere in `go.mod`/`go.sum` or the Go sources. Webhook delivery is entirely in-process.

**Actual mechanism:**

- **The "queue" is a buffered Go channel**, declared in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  It's a package-level var holding at most 128 pending payloads, living in the memos server process itself.

- **The "workers" are 4 goroutines** started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. There is no retry, no ack, and no persistence — a dropped or failed delivery is gone.

- **Producers** enqueue via `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send: if the channel is full, the payload is **dropped** with a `slog.Warn`, not backpressured. Callers are in `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

- **Delivery itself** is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120-180`) using a shared `http.Client` with a 30s timeout and an SSRF-guarding `DialContext` that rejects reserved/private IPs (`internal/webhook/webhook.go:32-37`, `:59-77`). Optional Standard Webhooks HMAC-SHA256 signing adds `webhook-id` / `webhook-timestamp` / `webhook-signature` headers.

Practical consequence: because the queue is an in-memory channel, pending webhooks are lost on process restart, and delivery does not survive or coordinate across multiple server replicas.
