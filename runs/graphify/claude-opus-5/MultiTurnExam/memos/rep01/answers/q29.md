**`web/src/connect.ts` (the `authInterceptor`, line 156, installed on the transport at line 188); short-lived JWT access tokens + an HttpOnly refresh-token cookie (`memos_refresh`), with Personal Access Tokens supported on the same header for programmatic clients; validated by `server/auth`.**

How it works:

- **Interceptor** — `authInterceptor` (`web/src/connect.ts:156-178`) calls `getRequestToken()` to obtain a token, sets `Authorization: Bearer <token>`, and on a `Code.Unauthenticated` response refreshes once and retries with an `X-Retry` marker; a second failure triggers `redirectOnAuthFailure()`.
- **Tokens it manages** — the access token is held in memory/`auth-state` (`web/src/auth-state.ts`: `getAccessToken`, `setAccessToken`, `isTokenExpired`), and is proactively refreshed when within 30 s of expiry (`REQUEST_TOKEN_EXPIRY_BUFFER_MS`, line 18) or on tab focus (2 min buffer). The **refresh token** is never touched by JS — it rides as an HttpOnly cookie, which is why every request uses `credentials: "include"` (`connect.ts:57-62`). Refresh goes through a separate interceptor-free transport (`refreshTransport`/`refreshAuthClient`, lines 65-72) calling `AuthService.RefreshToken`, deduplicated by `tokenRefreshManager` (line 30) so concurrent 401s and focus refreshes don't race token rotation.
- **Backend validation** — `server/auth` (`server/auth/authenticator.go`): `AuthenticateByAccessTokenV2` (line 41) parses the JWT with the instance secret; `AuthenticateByRefreshToken` (line 61) parses and then checks the token ID against the DB; `AuthenticateByPAT` (line 102) hashes a `PersonalAccessTokenPrefix` token and looks it up via `Store.GetUserByPATHash`. `resolveBearer` (line 149) picks between JWT and PAT by prefix; cookie extraction lives in `server/auth/extract.go:23` with the cookie name `memos_refresh` defined at `server/auth/token.go:49`. This authenticator is invoked from the gateway middleware in `server/router/api/v1/v1.go` and the Connect handler options.
