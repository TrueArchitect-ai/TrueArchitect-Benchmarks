Tables touched by a `DeleteMemo`:

| Table | How |
|---|---|
| `memo_relation` | explicitly deleted twice — as source (`MemoID`) and as target (`RelatedMemoID`) — `store/memo.go:142,145` |
| `attachment` | listed by `MemoID` and deleted row-by-row — `store/memo.go:149-157` → `store/attachment.go:132-149` |
| `memo` | the row itself, plus one row per **comment memo**, which the API handler deletes recursively — `store/memo.go:158` (`store/db/sqlite/memo.go:237`) and `server/router/api/v1/memo_service.go:568-577` |
| `memo_share` | deleted by DB-level `ON DELETE CASCADE` on `memo_share.memo_id` — `store/migration/sqlite/LATEST.sql:102-110` |

Two caveats worth flagging:

- **`reaction` rows are not deleted.** `APIV1Service.DeleteMemo` reads them (`memo_service.go:545`) only to build the webhook payload, and `reaction.content_id` is a text memo *name*, so no FK cascade applies — reaction rows for a deleted memo are left orphaned.
- The attachment path also deletes the underlying **blob/file in storage** (local file or S3 object) via `DeleteAttachmentStorage` (`store/attachment.go:141`), which is outside the database.
