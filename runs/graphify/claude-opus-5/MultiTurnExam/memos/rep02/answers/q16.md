`Store.DeleteMemo` (`store/memo.go:140-159`) removes, in this order, before deleting the memo row via `s.driver.DeleteMemo`:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID:...}` and deleted one by one (`store/memo.go:148-157`). Each goes through `Store.DeleteAttachment` (`store/attachment.go:132-149`), which also deletes the **underlying stored blob/file** (local disk or external storage) via `DeleteAttachmentStorage` before removing the DB row.

Above that, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-592`) first deletes **child comment memos** — it lists `memo_relation` rows of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each (`:567-577`), so every comment's own relations and attachments are cleaned up too. It then dispatches the memo-deleted webhook and, after deletion, broadcasts an SSE event.

Not deleted at this layer: **reactions** — the handler only *lists* them to build the webhook payload (`:545-550`); no reaction cleanup happens in `Store.DeleteMemo`. Memo shares aren't touched here either.
