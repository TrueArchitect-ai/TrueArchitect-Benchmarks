**Engine: CEL (Common Expression Language, `github.com/google/cel-go`) — `internal/filter/`** (`engine.go`, `schema.go`, `parser.go`, `ir.go`, `render.go`, `helpers.go`)

**Mechanism:** `filter.Engine.Compile` compiles the CEL string against a typed schema into a dialect-agnostic condition tree (IR), and each driver then renders that tree into a parameterized SQL `WHERE` fragment by passing its own dialect constant — `filter.AppendConditions(ctx, engine, find.Filters, filter.DialectSQLite|DialectPostgres|DialectMySQL, &where, &args)` — so one filter expression yields per-dialect SQL with bound arguments rather than interpolated strings.

Key files:
- `internal/filter/engine.go:13-33` — `Engine` wraps a `cel.Env` built from a `Schema`; `Compile` (`:47`) rejects empty filters, compiles the AST, and converts it to the condition tree (`Program.ConditionTree`, `:42`). `nowFunc` is frozen per-compile so a filter sees one instant.
- `internal/filter/schema.go` — the CEL environment/variable declarations available to filter expressions.
- `internal/filter/render.go` — the dialect switchboard; `DialectSQLite` / `DialectPostgres` / `DialectMySQL` branches handle the divergences (JSON extraction, string length, boolean/timestamp handling — e.g. `:231-237`, `:297-298`, `:565-568`).
- Call sites: `store/db/sqlite/memo.go:57-61`, `store/db/postgres/memo.go:58`, `store/db/mysql/memo.go:69`. The same machinery is reused for attachments (`.../attachment.go`) and memo relations (`.../memo_relation.go`, which uses `engine.CompileToStatement` with explicit `RenderOptions`).

The API layer validates/normalizes the incoming filter before it reaches the store in `server/router/api/v1/memo_service_filter.go` (with the user-facing equivalent in `user_service_filter.go`). Saved shortcuts are simply stored CEL filter strings intended to be passed straight to `ListMemos`' `filter` argument (`proto/api/v1/shortcut_service.proto:16-18`).
