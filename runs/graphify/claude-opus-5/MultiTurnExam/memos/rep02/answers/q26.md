Two things worth flagging:

- **`memo_share` is not cleaned up on SQLite.** The SQLite connection is opened with foreign keys explicitly disabled — `_pragma=foreign_keys(0)` in `store/db/sqlite/sqlite.go:53` — so the declared `ON DELETE CASCADE` never fires there, and no application code deletes shares on memo deletion (the only explicit `memo_share` cleanup by `memo_id` is in the user-deletion path, e.g. `store/db/mysql/user_delete.go:448`). That leaves orphaned `memo_share` rows on the default SQLite backend.
- **`reaction` rows are not deleted.** `APIV1Service.DeleteMemo` only *reads* reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); there's no delete, and reactions key off a string `content_id` with no FK.
