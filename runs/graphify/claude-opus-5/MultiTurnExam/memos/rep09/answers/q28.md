s3presign runner — started at boot: one immediate RunOnce, then a 12h time.Ticker loop
SSE heartbeat ticker — per-connection, started when a browser opens the SSE stream

**s3presign** — `server/server.go:162-171` constructs `s3presign.NewRunner(s.Store)`, calls `RunOnce(ctx)` synchronously, then runs `Run(s3Context)` in a goroutine under its own cancelable context tracked in `backgroundRunnerCancels`/`backgroundRunnerWG` for clean shutdown. The loop is `time.NewTicker(runnerInterval)` with `runnerInterval = time.Hour * 12` (`server/runner/s3presign/runner.go:27,30`); each pass re-signs S3 object URLs, skipping any presigned within the last 4 days (`runner.go:88`).

**SSE heartbeat** — `time.NewTicker(sseHeartbeatInterval)` at `server/router/api/v1/sse_handler.go:64`. Not a background worker in the runner sense; it's request-scoped, living as long as the client's event stream, to keep the connection from idling out.

**Unused scheduling infrastructure:** `server/runner/memopayload` defines `NewRunner(store, markdownService)` and `RunOnce` (`server/runner/memopayload/runner.go:19,27`), but **nothing ever calls them** — `server.go` constructs only the s3presign runner. The package's other export, the plain function `RebuildMemoPayload` (`runner.go:74`), *is* used, called inline from the API handlers at `server/router/api/v1/memo_service.go:108` (create) and `:447` (update). So payload rebuilding happens synchronously on write, and the batch runner is dead code retained for what would be a one-shot backfill.
