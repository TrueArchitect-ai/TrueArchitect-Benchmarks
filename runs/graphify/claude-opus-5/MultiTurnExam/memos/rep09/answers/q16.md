`Store.DeleteMemo` (`store/memo.go:140-158`) deletes, in order, before the memo row:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachment rows linked to the memo** — listed by `FindAttachment{MemoID}` and deleted one at a time (`store/memo.go:149-157`); each `Store.DeleteAttachment` also removes the backing blob/local file via `DeleteAttachmentStorage` before the row (`store/attachment.go:132-148`)

Then `s.driver.DeleteMemo` removes the memo row itself (`store/memo.go:158`).

Two things worth noting about the API path in `server/router/api/v1/memo_service.go:518-582`:

- **Comment memos are deleted first, at the handler level, not the store level.** The handler lists relations of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each comment memo (lines 567-577), so each comment gets the same relation + attachment cleanup recursively.
- **Reactions are not deleted.** The handler reads them (line 545) only to build the webhook payload. Since `reaction.content_id` stores the memo's resource name rather than a foreign key, reaction rows for a deleted memo are left orphaned by this path.
