**memo, memo_relation, attachment** (+ **memo_share** on MySQL/Postgres only, via DB-level FK cascade)

Breakdown of the delete path:

| Table | How | Where |
|---|---|---|
| `memo_relation` | explicit cascade code, both directions (`MemoID` and `RelatedMemoID`) | `store/memo.go:142,145` |
| `attachment` | explicit cascade code — listed by `MemoID`, deleted one by one | `store/memo.go:149-157` |
| `memo` | the row itself, plus any comment memos deleted first by the handler | `store/db/sqlite/memo.go:237`; handler loop at `server/router/api/v1/memo_service.go:573-577` |
| `memo_share` | **DB-level** `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` — no Go code | `store/migration/{sqlite,mysql,postgres}/LATEST.sql:109/108/108` |

Comment memos are removed recursively: the handler deletes each comment via `Store.DeleteMemo`, so their own `memo_relation` and `attachment` rows go too.

Two caveats worth flagging:

- **`memo_share` cascade does not fire on SQLite.** The connection is opened with `?_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the FK is declared but unenforced, and no Go code deletes those rows. On MySQL/Postgres the same constraint is enforced. That's a real dialect divergence, not just a formality.
- **`reaction` rows are never deleted.** `DeleteMemo` reads them only to build the webhook payload (`memo_service.go:545`); since `reaction.content_id` holds the memo's resource name rather than a foreign key, those rows are orphaned.

Beyond tables, `Store.DeleteAttachment` also removes each attachment's backing blob or local file before deleting its row (`store/attachment.go:141`).
