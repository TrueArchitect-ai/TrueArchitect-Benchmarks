**memo, memo_relation, attachment, memo_share**

- **memo_relation** — deleted explicitly in both directions (`MemoID` and `RelatedMemoID`) at `store/memo.go:142-147`.
- **attachment** — rows linked to the memo are listed and deleted one by one at `store/memo.go:148-157`; `Store.DeleteAttachment` (`store/attachment.go:132`) also removes the underlying file/object from local or S3 storage first (not a table).
- **memo** — the row itself, plus every comment memo: the API handler `APIV1Service.DeleteMemo` deletes each comment-type child through `Store.DeleteMemo` before the parent (`server/router/api/v1/memo_service.go:567-580`), so each child repeats the same relation/attachment cleanup. The final `DELETE FROM memo` is in the drivers, e.g. `store/db/sqlite/memo.go:237`.
- **memo_share** — via a database-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`), not explicit Go code. Worth flagging: the SQLite connection opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade is not enforced and share rows can be orphaned.

**reaction is not touched** — reactions are only read to build the webhook payload (`server/router/api/v1/memo_service.go:545`), and the `reaction` table has no FK to `memo` (it keys on a string `content_id`).
