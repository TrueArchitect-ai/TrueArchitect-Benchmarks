**Engine: Google CEL (Common Expression Language), via `github.com/google/cel-go` — wrapped in `internal/filter/` (`internal/filter/engine.go`)**

Mechanism: each driver's `ListMemos` compiles the filter strings with the shared CEL engine into a dialect-agnostic condition tree (`internal/filter/engine.go:47` `Compile`, IR in `internal/filter/ir.go`), then renders that tree to a parameterized SQL fragment for its own dialect and appends it to the query's `WHERE` clause and arg list.

Supporting detail:

- The CEL environment and the allowed variables/functions come from the schema in `internal/filter/schema.go`; `Engine` is built by `NewEngine` (`internal/filter/engine.go:24`), with `filter.DefaultEngine()` used by the drivers.
- Rendering is dialect-switched in `internal/filter/render.go` — `DialectSQLite`, `DialectPostgres`, `DialectMySQL` each get their own SQL for date extraction (`strftime` vs `EXTRACT` vs MySQL functions, :231-238), string length (:297), JSON access, and placeholder style.
- The bridge is `filter.AppendConditions` (`internal/filter/helpers.go:9`), which calls `CompileToStatement` with a `PlaceholderOffset` and pushes `(stmt.SQL)` + `stmt.Args` onto the caller's slices. Call sites: `store/db/sqlite/memo.go:57-61`, `store/db/postgres/memo.go:58`, `store/db/mysql/memo.go:69`.
- On the API side the filter arrives via `ListMemosRequest.filter` (`proto/api/v1/memo_service.proto`) and is handled in `server/router/api/v1/memo_service_filter.go`; users get the same treatment in `server/router/api/v1/user_service_filter.go`. Notes on maintaining the grammar live in `internal/filter/README.md` and `internal/filter/MAINTENANCE.md`.
