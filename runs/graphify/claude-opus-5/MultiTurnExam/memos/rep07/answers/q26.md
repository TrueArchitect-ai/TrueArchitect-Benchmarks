```
memo            — the memo row itself, plus any comment memos deleted recursively
memo_relation   — rows where the memo is the source, and rows where it is the target
attachment      — rows linked to the memo (each also removes its stored blob/file)
memo_share      — via ON DELETE CASCADE foreign key, not explicit code
```

Where each comes from:

- `memo` — `driver.DeleteMemo` issues `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`). Comment memos are deleted first by the API handler, which recurses through `Store.DeleteMemo` for every `MemoRelationComment` child (`server/router/api/v1/memo_service.go:567-577`).
- `memo_relation` — two explicit deletes in `Store.DeleteMemo`, one for `MemoID` and one for `RelatedMemoID` (`store/memo.go:142-147`).
- `attachment` — listed by `FindAttachment{MemoID}` and deleted individually (`store/memo.go:149-157`); `Store.DeleteAttachment` also removes the underlying local/S3 object before the row (`store/attachment.go:132-149`).
- `memo_share` — no cascade code in Go; the table declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`), so the database removes those rows.

One caveat worth flagging: `reaction` rows are *not* deleted. `server/router/api/v1/memo_service.go:545` reads them only to build the webhook payload, and reactions are keyed by `content_id` (a resource name string) rather than a memo foreign key, so no cascade applies either — they are left behind.
