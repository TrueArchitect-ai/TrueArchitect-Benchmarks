**memo_relation, attachment, memo** (+ **memo_share** via DB-level FK cascade on postgres/mysql only)

- **memo_relation** — two deletes, once as `memo_id` and once as `related_memo_id` (`store/memo.go:142,145`).
- **attachment** — every row with `MemoID` = this memo, deleted one at a time (`store/memo.go:148-157` → `store/attachment.go:132`); each also removes the underlying blob from local/S3 storage, which is filesystem/object state rather than a table.
- **memo** — the row itself (`store/db/sqlite/memo.go:237`), plus additional `memo` rows for each comment child, since `APIV1Service.DeleteMemo` first deletes every memo linked by a `MemoRelationComment` relation, recursing through the same cleanup (`server/router/api/v1/memo_service.go:567-577`).
- **memo_share** — not touched by any Go code; it has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). Note the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and share rows are left orphaned.

Not affected: **reaction** — rows are read to build the webhook payload (`server/router/api/v1/memo_service.go:545`) but never deleted, and the table has no FK to `memo` (it keys on a string `content_id`).
