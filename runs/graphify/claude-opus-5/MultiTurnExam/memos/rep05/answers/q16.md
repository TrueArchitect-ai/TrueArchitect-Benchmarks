Deleting a memo via `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) cascades in this order:

1. **Comment memos** — every memo linked to it by a `MemoRelationComment` relation is deleted first, each recursing through the same store cleanup (`server/router/api/v1/memo_service.go:567-577`).

Then, inside `Store.DeleteMemo` (`store/memo.go:140-158`), before the `memo` row:

2. **`memo_relation` rows where the memo is the source** (`MemoID`) — `store/memo.go:142`
3. **`memo_relation` rows where the memo is the target** (`RelatedMemoID`) — `store/memo.go:145`
4. **`attachment` rows linked to the memo** — listed by `MemoID` and deleted one by one (`store/memo.go:148-157`); each `Store.DeleteAttachment` also removes the backing blob/file from storage before the row (`store/attachment.go:132-149`).

Only then does the driver run `DELETE FROM memo` (`store/memo.go:158` → e.g. `store/db/sqlite/memo.go:237`).

Not deleted by this path: `reaction` rows are only *read* (to build the webhook payload, `server/router/api/v1/memo_service.go:545`), and memo shares aren't touched here either — neither is removed as part of memo deletion.
