**Engine: Google CEL (`cel-go`), wrapped by the memo filter engine at `/bench/home/work/internal/filter/` — entry point `filter.DefaultEngine()` in `/bench/home/work/internal/filter/engine.go` (CEL env constructed at line 25 from `schema.go`).**

**Mechanism:** A three-phase pipeline — `parser.go` parses the CEL expression and validates it against the memo-specific schema (`schema.go`), normalizing it into a dialect-agnostic IR (`ir.go`), and then `render.go` walks that IR to emit a SQL fragment plus placeholder args tailored to the target dialect, so `RenderOptions.Dialect` (`sqlite` / `mysql` / `postgres`) is what selects JSON-access syntax, boolean semantics, placeholder style (`?` vs `$N`), and `LIKE` vs `ILIKE`.

Supporting detail: the pipeline and dialect handling are documented in `/bench/home/work/internal/filter/README.md`; `Engine.CompileToStatement` returns a `Statement{SQL, Args}` that callers splice into the memo query. The renderer special-cases whole-expression outcomes — unsatisfiable filters become `1 = 0` and trivially-true ones render an empty fragment (`/bench/home/work/internal/filter/render.go:41-57`). Call-site wiring for `ListMemos` lives in `/bench/home/work/server/router/api/v1/memo_service_filter.go` and `memo_service_query.go`. Note that user listing uses a separate, smaller CEL filter implemented inline at `/bench/home/work/server/router/api/v1/user_service_filter.go:29` — the `internal/filter` engine is memo-only by design.
