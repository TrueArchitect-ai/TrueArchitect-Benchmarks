**Memo relations, then attachments** — in that order, before the memo row.

`Store.DeleteMemo` at `/bench/home/work/store/memo.go:140-158` does exactly three things:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (line 142).
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (line 145), so inbound references from other memos are cleared too.
3. **Attachments linked to the memo** — listed via `ListAttachments{MemoID:...}` and deleted one by one (lines 149-157). `Store.DeleteAttachment` also removes the backing blob/file, not just the row.

Only then does it call `s.driver.DeleteMemo(ctx, delete)` (line 158) to remove the memo row itself.

One layer up, the API handler `APIV1Service.DeleteMemo` (`/bench/home/work/server/router/api/v1/memo_service.go:518`) first deletes the memo's **comments** — it lists `memo_relation` rows of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each comment memo (lines 567-578), which recursively runs the same relation/attachment cleanup for each. That comment cascade lives in the API layer, not the store.

Note that reactions are *not* deleted: the handler lists them only to build the webhook payload (lines 545-550), and no reaction deletion happens on either path.
