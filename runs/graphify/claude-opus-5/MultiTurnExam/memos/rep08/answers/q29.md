How it fits together:

**Frontend** — `authInterceptor` at `/bench/home/work/web/src/connect.ts:156-178` is installed on the shared Connect transport (line 188). On each request it resolves a token via `getRequestToken()` (line 124) and sets the `Authorization: Bearer` header. `getRequestToken` proactively refreshes when the access token is missing or within an expiry buffer (`isTokenExpired(REQUEST_TOKEN_EXPIRY_BUFFER_MS)`, line 140) — the comment at lines 136-139 explains this matters for public endpoints like `ListMemos`, where an expired token would silently degrade to guest-scoped data. Reactively, on an `Unauthenticated` error it refreshes once, marks the retry with an `X-Retry` header, and replays; a second failure calls `redirectOnAuthFailure()` (lines 163-177). Refreshes go through `refreshAccessToken` → a deduplicating `tokenRefreshManager` (lines 30-91) so concurrent callers can't race server-side token rotation, and they use a *separate* interceptor-free transport (`refreshTransport`, line 65) to avoid recursion. Token storage lives in `/bench/home/work/web/src/auth-state.ts`; the cookie rides along because the transport sets `credentials: "include"` (line 60).

**Backend** — package `auth` at `/bench/home/work/server/auth`:
- `ExtractBearerToken` / `ExtractRefreshTokenFromCookie` (`extract.go:11,23`) pull credentials off the headers.
- `Authenticator.AuthenticateByAccessTokenV2` (`authenticator.go:41`) verifies the JWT via `ParseAccessTokenV2` against the server secret (`token.go`).
- `AuthenticateByRefreshToken` (`authenticator.go:61`) parses the refresh JWT *and* checks it against the DB with `GetUserRefreshTokenByID` (line 73), so refresh tokens are revocable.
- `AuthenticateByPAT` (`authenticator.go:102`) handles `pat_`-prefixed tokens by hash lookup; `resolveBearer` (line 149) dispatches between PAT and JWT.
- `context.go` stashes the resolved user/claims into the request context for handlers.
