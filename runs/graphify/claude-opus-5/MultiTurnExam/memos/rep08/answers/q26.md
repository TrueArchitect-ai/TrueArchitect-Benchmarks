**memo, memo_relation, attachment, memo_share**

Breakdown by how each is hit:

- **`memo_relation`** — deleted explicitly, twice, in `Store.DeleteMemo`: rows where the memo is the source (`MemoID`) and where it's the target (`RelatedMemoID`) — `/bench/home/work/store/memo.go:142,145`.
- **`attachment`** — explicitly listed by `MemoID` and deleted one by one (`/bench/home/work/store/memo.go:149-157`); `Store.DeleteAttachment` also removes the backing file/object before deleting the row (`/bench/home/work/store/attachment.go:132-148`).
- **`memo`** — the row itself, via `driver.DeleteMemo` (`/bench/home/work/store/memo.go:158`; the SQL is a plain `DELETE FROM memo WHERE id = ?`, e.g. `/bench/home/work/store/db/sqlite/memo.go:237-248`). Additional `memo` rows go too when the API handler cascades to comments: `APIV1Service.DeleteMemo` lists comment-type relations and calls `Store.DeleteMemo` on each comment memo (`/bench/home/work/server/router/api/v1/memo_service.go:567-578`), which recursively repeats all of the above.
- **`memo_share`** — not touched by Go code, but removed by a database-level `ON DELETE CASCADE` foreign key on `memo_share.memo_id`, present in all three dialects: `store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`.

Not affected: `reaction` rows survive — the handler reads them only to build the webhook payload (`/bench/home/work/server/router/api/v1/memo_service.go:545-550`), and there's no reaction delete or FK cascade on memo deletion. `inbox` is likewise untouched.
