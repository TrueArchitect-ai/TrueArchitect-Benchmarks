Inside `Store.DeleteMemo` (`store/memo.go:140-158`), before the `memo` row is deleted:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachment rows linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one (`store/memo.go:149-157`); each `Store.DeleteAttachment` also removes the backing stored file/object before deleting the DB row (`store/attachment.go:132-148`)

Only then does it call `s.driver.DeleteMemo`, which issues the plain `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237-248`).

Additionally, at the API layer above this, `APIV1Service.DeleteMemo` first deletes **comment memos** — it lists `memo_relation` rows of type `comment` pointing at the memo and calls `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:566-577`), so each comment goes through the same relation/attachment cleanup. Reactions are read at `server/router/api/v1/memo_service.go:545` only to build the webhook payload — the code path shown does not delete `reaction` rows.
