**memo, memo_relation, attachment** (plus **memo_share** by DB-level FK cascade on MySQL/Postgres)

Breakdown from `Store.DeleteMemo` (`store/memo.go:140-158`) and the API handler above it:

| Table | How |
|---|---|
| `memo_relation` | Explicit cascade code — deleted twice, once as source (`MemoID`) and once as target (`RelatedMemoID`): `store/memo.go:142`, `:145` |
| `attachment` | Explicit cascade code — listed by `MemoID` then deleted individually (`store/memo.go:149-157`); `Store.DeleteAttachment` also removes the backing file/object before the row (`store/attachment.go:132-148`) |
| `memo` | The row itself (`store/db/sqlite/memo.go:237`), plus additional `memo` rows for comments: `APIV1Service.DeleteMemo` recursively deletes comment memos found via `memo_relation` type `comment` (`server/router/api/v1/memo_service.go:566-577`) |
| `memo_share` | Not touched by Go code; declared `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` — `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109` |

One caveat worth flagging: the SQLite connection opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so FK enforcement is off there — `memo_share` rows are **not** cascade-deleted on SQLite, leaving them orphaned.

`reaction` rows are read for the webhook payload (`server/router/api/v1/memo_service.go:545`) but no deletion of them appears on this path.
