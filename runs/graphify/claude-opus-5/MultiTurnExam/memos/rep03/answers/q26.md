**memo, memo_relation, attachment, memo_share**

Breakdown by how each is affected:

| Table | How |
|---|---|
| `memo_relation` | Explicit cleanup in `Store.DeleteMemo` — deleted twice, once as `memo_id` and once as `related_memo_id` (`store/memo.go:142`, `:145`) |
| `attachment` | Explicit cleanup — listed by `MemoID` and deleted individually (`store/memo.go:149-157`); each `Store.DeleteAttachment` (`store/attachment.go:132`) also removes the blob from local/S3 storage |
| `memo` | The row itself, via `driver.DeleteMemo` → `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`) |
| `memo_share` | **DB-level cascade** — `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`) |

Additionally, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first deletes each **comment memo** by calling `Store.DeleteMemo` on it (`:566-576`), so the same four tables are hit again for every child memo.

Two caveats worth flagging: `memo_share` is the *only* FK cascade in the schema, and SQLite enforces foreign keys only when `PRAGMA foreign_keys=ON` — so that cascade depends on the connection setting rather than on Go code. And `reaction` rows are **not** deleted: reactions key off `content_id` (the memo's resource name string) with no FK, so they're orphaned by a memo delete.
