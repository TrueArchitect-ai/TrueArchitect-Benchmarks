`Store.DeleteMemo` (`store/memo.go:140-159`) deletes, in order, before calling `driver.DeleteMemo`:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachments linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one (`store/memo.go:149-157`). Each `Store.DeleteAttachment` (`store/attachment.go:132`) also removes the **underlying blob from storage** (local file or S3) before deleting the `attachment` row.

Two things the API handler does on top of the store, which matter if you're looking at end-to-end delete behavior (`server/router/api/v1/memo_service.go:518-591`):

- **Comment memos** are deleted first — the handler lists `memo_relation` rows of type `comment` pointing at this memo and calls `Store.DeleteMemo` on each child memo, which recursively runs the cleanup above (`memo_service.go:566-576`).
- Reactions and attachments are *read* beforehand only to build the webhook payload (`memo_service.go:544-559`), not deleted there.

Notably, **`reaction` rows are not deleted** by either layer — reactions key off `content_id` (the memo resource name) rather than a foreign key, so they're left behind. `memo_share` rows likewise aren't touched by `Store.DeleteMemo`.
