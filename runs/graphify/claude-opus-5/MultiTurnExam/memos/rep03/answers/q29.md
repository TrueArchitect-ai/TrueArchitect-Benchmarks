**web/src/connect.ts; short-lived JWT access token (in-memory) + HttpOnly refresh-token cookie (plus Personal Access Tokens for API clients); server/auth**

**Interceptor.** `authInterceptor` at `web/src/connect.ts:155` is installed on the shared Connect transport (`:189`) used by every service client. On each request it calls `getRequestToken()` (`:124`) and sets `Authorization: Bearer <token>` (`:95`). Two refresh paths:
- *Preflight* — if the token is expired within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30 s), refresh before sending (`:140-147`). The comment there notes this matters for public endpoints like `ListMemos`, where an expired token would silently return guest-scoped data.
- *Reactive* — on a `Code.Unauthenticated` response, refresh once, stamp an `X-Retry` header, and replay; on failure call `redirectOnAuthFailure()` (`:163-177`).

Concurrent refreshes are deduplicated by `tokenRefreshManager` (`:30`, `:87`), and the refresh call itself goes through a **separate transport with no interceptors** to avoid recursion (`:64-72`), using `credentials: "include"` so the refresh cookie is sent.

**Tokens.**
- **Access token** — short-lived JWT, held in memory/storage by `web/src/auth-state.ts` (`getAccessToken`, `setAccessToken`, `isTokenExpired`, `clearAccessToken`), sent as a bearer header.
- **Refresh token** — HttpOnly cookie, never read by JS; exchanged via `AuthService.RefreshToken` (`web/src/connect.ts:73-80`) and rotated server-side.
- **Personal Access Token (PAT)** — prefix-tagged long-lived token for programmatic clients, sent in the same `Authorization` header.

**Backend validation.** `server/auth/` — `Authenticator` in `server/auth/authenticator.go`: `AuthenticateByAccessTokenV2` (:41), `AuthenticateByRefreshToken` (:61, checked against `store.GetUserRefreshTokenByID`), `AuthenticateByPAT` (:102, hash lookup via `GetUserByPATHash` plus expiry check), with `resolveBearer` (:149) branching on the PAT prefix. JWT parsing/signing is in `server/auth/token.go`, header extraction in `extract.go`, context plumbing in `context.go`.

That authenticator is shared by both serving paths — the Connect `NewAuthInterceptor(authorizer)` and the gRPC-Gateway middleware are built from one `NewAuthorizer(s.Store, s.Secret, s.Profile)` in `server/router/api/v1/v1.go:68-69`, with per-method access policy in `server/router/api/v1/authz.go` and `acl_config.go`.
