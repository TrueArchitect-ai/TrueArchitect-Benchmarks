**web/src/connect.ts (`authInterceptor`); short-lived JWT access token + HTTP-only refresh-token cookie (+ Personal Access Tokens for non-browser clients); server/auth**

**Interceptor.** `authInterceptor` at `web/src/connect.ts:155`, installed on the shared transport (`:187`) that every service client is built from. Per request it:
- resolves a token via `getRequestToken()` (`:124`) and sets `Authorization: Bearer <token>` (`:95`);
- pre-emptively refreshes when the access token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry (`:140`) — the comment at `:137-139` notes this matters for public endpoints like `ListMemos`, where an expired token would silently yield guest-scoped data;
- on a `Code.Unauthenticated` response, refreshes once, marks the retry with an `X-Retry` header to prevent loops, and replays; a second failure calls `redirectOnAuthFailure()` (`:164-176`).

Refresh itself goes through `refreshAuthClient` on a **separate transport with no interceptors** (`:64-72`) to avoid recursion, and concurrent refreshes are deduped by `tokenRefreshManager` (`:30-50`) so the proactive on-focus refresh and the reactive 401 path can't race server-side token rotation. Token storage/expiry helpers are in `web/src/auth-state.ts`.

**Token kinds and backend validation** — package `server/auth`:

| Token | Transport | Validator |
|---|---|---|
| Access token (JWT, short-lived) | `Authorization: Bearer` | `Authenticator.AuthenticateByAccessTokenV2` — `server/auth/authenticator.go:41` |
| Refresh token | HTTP-only cookie (`credentials: "include"`), extracted by `ExtractRefreshTokenFromCookie` (`server/auth/extract.go:23`) | `Authenticator.AuthenticateByRefreshToken` — `authenticator.go:61`, checked against the DB |
| Personal Access Token | `Authorization: Bearer memos_pat_…` | `Authenticator.AuthenticateByPAT` — `authenticator.go:102`, hash lookup + expiry check |

`Authenticator.resolveBearer` (`authenticator.go:149`) dispatches on the prefix — PAT vs. JWT — and JWT signing/parsing lives in `server/auth/token.go`. The result is applied to the request context via `auth.ApplyToContext` in the gateway middleware (`server/router/api/v1/v1.go:86-88`); the cookie is set on sign-in at `server/router/api/v1/auth_service_session.go:226`.
