Inside `Store.DeleteMemo` (`store/memo.go:140-159`), in this order, before `driver.DeleteMemo` runs:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID: ...}` and deleted one by one (`store/memo.go:149-157`). Each `Store.DeleteAttachment` also removes the backing blob via `DeleteAttachmentStorage` (`store/attachment.go:132-146`), so local files go too — a local-file failure aborts the delete, other storage types only log a warning.

Two things the *API* handler does around this, not the store layer: it first deletes **comment memos** by looking up `MemoRelationComment` relations and calling `Store.DeleteMemo` recursively for each (`server/router/api/v1/memo_service.go:567-577`), and it reads reactions only to build the webhook payload (`:545-565`) — reaction rows are not deleted on this path.
