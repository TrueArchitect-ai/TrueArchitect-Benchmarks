**memo, memo_relation, attachment** (plus `memo_share` on Postgres/MySQL via a DB-level FK cascade — but *not* on SQLite)

Breakdown of the delete path:

| Table | How | Where |
|---|---|---|
| `memo_relation` | explicit — deleted twice, once as source (`MemoID`) and once as target (`RelatedMemoID`) | `store/memo.go:142,145` |
| `attachment` | explicit — listed by `MemoID`, deleted one by one (blob storage removed too) | `store/memo.go:149-157`, `store/attachment.go:132-146` |
| `memo` | the row itself, plus recursively every comment memo | `store/db/sqlite/memo.go:237`; comment recursion at `server/router/api/v1/memo_service.go:567-577` |
| `memo_share` | DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` | `store/migration/sqlite/LATEST.sql:109` |

Two caveats worth flagging:

- **SQLite opens with foreign keys disabled** — `_pragma=foreign_keys(0)` at `store/db/sqlite/sqlite.go:53` — so that `memo_share` cascade does not actually fire on SQLite, and there is no explicit `DeleteMemoShare` call in the delete path. Share rows are orphaned on the default deployment.
- **`reaction` is not cleaned up.** `DeleteMemo` reads reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); since reactions key off `content_id` (the memo's resource name) with no FK, those rows also survive.
