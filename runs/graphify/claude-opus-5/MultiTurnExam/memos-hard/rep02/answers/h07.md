Notes on the trace:

- **Where the URL comes from.** The browser doesn't guess it — `convertUserFromStore` rewrites the avatar field to `/file/{userpb.Name}/avatar` (`server/router/api/v1/user_service_converters.go:36`), and `userpb.Name` is `users/{username}` (prefix at `server/router/api/v1/resource_name.go:18`), which is what matches the `/file/users/:identifier/avatar` route. This rewrite only happens when the stored value is a data URI; a plain external URL is passed through unchanged (`user_service_converters.go:32-39`).
- **Route wiring.** `FileServerService.RegisterRoutes` is called from `server/server.go:82`, on a service built at `server/server.go:81`.
- **Access control.** Before any lookup, `serveUserAvatar` checks `s.Profile.AllowAnonymous()`; on a private instance a nil viewer gets 401 (`fileserver.go:171-179`). On a public instance, any user's avatar is served without authentication — which is the intended behavior for a public profile image.
- **The data itself never leaves the user row.** There's no attachment or blob hop here: `user.AvatarURL` holds a data URI, and `parseDataURI` (`fileserver.go:737`) splits out the MIME type and decodes the bytes, which are checked against `avatarAllowedTypes` (`fileserver.go:75`, enforced at `:201`) before `c.Blob` writes them.
- **Cache shortcut.** `Store.GetUser` consults `userCache` only when the lookup is by ID (`store/user.go:149-156`). This path looks up by username, so it always falls through to `ListUsers` → driver → SQL, though the result is written back into the cache (`store/user.go:167`).
