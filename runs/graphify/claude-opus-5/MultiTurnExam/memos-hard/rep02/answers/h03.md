**`internal/idp` (abstraction); `internal/idp/oauth2` (implementation)**

- **Abstraction — `internal/idp/idp.go`:** the package is deliberately thin. It defines a single shared type, `IdentityProviderUserInfo` (`internal/idp/idp.go:3-8`), with `Identifier`, `DisplayName`, `Email`, and `AvatarURL`. Note there is no Go `interface` here — the abstraction is the normalized user-info struct that every provider must produce, not a method set. Any future provider is expected to import `internal/idp` and return this type.

- **Implementation — `internal/idp/oauth2/oauth2.go`:** OAuth2 is the only concrete protocol that ships. `IdentityProvider` (`oauth2.go:20-22`) wraps a `storepb.OAuth2Config`; `NewIdentityProvider` (`oauth2.go:27`) requires `clientId`, `clientSecret`, `tokenUrl`, `userInfoUrl`, and `fieldMapping.identifier`. Two methods do the work: `ExchangeToken` (`oauth2.go:47`) trades the auth code for an access token via `golang.org/x/oauth2`, passing `code_verifier` when supplied so PKCE is supported; `UserInfo` (`oauth2.go:83`) fetches the userinfo endpoint with a 10s timeout and maps arbitrary JSON claims onto `idp.IdentityProviderUserInfo` using the configured field mapping, erroring if the identifier claim is missing and falling back to the identifier for display name.

Corroborating the "only one implementation" point: the store enum in `proto/store/idp.proto:11-13` has just `OAUTH2 = 1` (mirrored in `proto/api/v1/idp_service.proto:76-79`), and the single dispatch site — `server/router/api/v1/auth_service_sso.go:120-133` — branches on `storepb.IdentityProvider_OAUTH2` with no other arm, then applies the provider's `identifierFilter` regex before the login is accepted (`auth_service_sso.go:136-145`). OIDC-style providers are served through this generic OAuth2 path rather than a dedicated package.
