**Premise correction: there is no Redis anywhere in this repository.** Grepping the entire tree (Go sources, `go.mod`, YAML/JSON config) for `redis` or `memcache` returns zero hits. There is no external cache server, no connection string, and no configuration surface for one.

**Actual mechanism: a hand-rolled in-process cache.** `store/cache/cache.go` implements `Cache` as a thread-safe in-memory store backed by a `sync.Map` plus an atomic item counter (`store/cache/cache.go:66-73`), with TTL expiry and a background cleanup goroutine. It satisfies a local `Interface` (`store/cache/cache.go:11-32`) — `Set`, `SetWithTTL`, `Get`, `Delete`, `Clear`, `Size`, `Close`.

**Configuration site.** Not a connection — a struct literal in `store.New` (`store/store.go:39-44`):

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

Three independent instances are built from that same config (`store/store.go:50-52`): `instanceSettingCache`, `userCache`, and `userSettingCache`. The values are hardcoded — no flag, env var, or DSN feeds them. `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) declares the identical values but isn't what the store uses.

**TTL for user entries: 10 minutes.** Every user write goes through `userCache.Set` (`store/user.go:98, 122, 132, 143, 167`), and `Set` forwards to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:94`) — nothing in the user path calls `SetWithTTL` with a custom duration. Expired entries are swept every 5 minutes by the cleanup loop, and the cache is capped at 1000 items across all entries.

Two behavioral details worth knowing: the cache is consulted only on ID-keyed lookups (`store/user.go:149-156`), so username-based lookups always hit the database; and `DeleteUser` explicitly evicts the entry rather than waiting for TTL (`store/user_delete.go:40`). Because the cache lives in the process heap, it is not shared across replicas — running multiple memos instances means each has its own copy with up to 10 minutes of staleness.
