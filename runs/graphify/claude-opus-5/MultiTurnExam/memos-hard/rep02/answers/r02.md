**Premise correction: there is no per-user API rate-limiting middleware in this repository — so there is nothing registered and no request limits to report.**

What I checked:

- A repo-wide grep across Go sources and `go.mod` for `rate limit`, `ratelimit`, `throttle`, `tollbooth`, `golang.org/x/time/rate`, `leaky bucket`, and `token bucket` returns exactly one hit, and it's a comment: `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a *future* consideration, not an implementation. No rate-limiting library appears in `go.mod`.
- The Echo middleware stack is tiny and fully enumerable: `echoServer.Use(middleware.Recover())` and `echoServer.Use(newCORSMiddleware(profile))` at `server/server.go:51-52` (CORS config in `server/cors.go:14`). That's the whole global chain — no limiter. The only other request-scoped interception is authentication: the gRPC-Gateway middleware and Connect interceptor built from `NewAuthorizer` in `server/router/api/v1/v1.go:68+`, which enforces identity and anonymous-access policy, not request rates.

What does exist, in case one of these is what you're actually after — these are resource guards, not per-user rate limits:

| Mechanism | Limit | Path |
|---|---|---|
| Thumbnail generation semaphore | 3 concurrent (fileserver: `maxConcurrentThumbnails`) | `server/router/api/v1/v1.go:59`, `server/router/fileserver/fileserver.go:116` |
| Image processing semaphore | 2 concurrent | `server/router/api/v1/v1.go:60` |
| Upload size cap | instance setting `UploadSizeLimitMb`, falling back to `MaxUploadBufferSizeBytes` | `server/router/api/v1/attachment_service.go:121-124` |
| Memo content length cap | instance-configured | `server/router/api/v1/memo_service.go:101-106` |
| Webhook dispatch queue | 128 buffered, 4 workers, overflow dropped | `internal/webhook/webhook.go:39-55, 189-195` |
| Webhook HTTP timeout | 30s | `internal/webhook/webhook.go:27` |

These are process-wide concurrency and size bounds applied without reference to the calling user, so none of them would stop a single authenticated user from issuing unlimited requests. If rate limiting is required for a deployment, it currently has to come from a reverse proxy in front of memos.
