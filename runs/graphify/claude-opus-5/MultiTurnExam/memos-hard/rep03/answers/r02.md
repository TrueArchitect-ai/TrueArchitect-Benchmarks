**Premise correction: there is no per-user API rate-limiting middleware in this repository, and no request limits to report.**

Evidence:

1. **No rate-limiting code or dependency exists.** A case-insensitive grep for `rate.?limit`, `ratelimit`, `throttl`, `limiter`, `golang.org/x/time/rate`, and `tollbooth` across all `.go` files and `go.mod` (excluding `web/`) returns zero matches.

2. **The Echo middleware chain has two entries, neither of which limits rates.** `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:14`).

3. **The Connect/gRPC interceptor chain has four entries, none of which limits rates.** `server/router/api/v1/v1.go:133-138` wires `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor` — header-to-metadata translation, logging, panic recovery, and authentication/authorization respectively (all defined in `server/router/api/v1/connect_interceptors.go`).

**What does exist, and is easy to mistake for rate limiting:**

- **Request body size caps** — `connect.WithReadMaxBytes(maxAPIRequestBytes)` plus `http.MaxBytesHandler` on the Connect mux (`server/router/api/v1/v1.go:140`, `:144`). These bound the size of a single request, not the number of requests.
- **Concurrency semaphores** — `thumbnailSemaphore` (3) and `imageProcessingSemaphore` (2) on the API service (`server/router/api/v1/v1.go:59-60`), and `maxConcurrentThumbnails = 3` in the file server (`server/router/fileserver/fileserver.go:46`, applied at `:116`). These cap simultaneous in-flight work for expensive image operations process-wide; they are not per-user and impose no per-interval quota — callers queue rather than get rejected.
- **A bounded webhook dispatch queue** — 128 slots with drop-on-full (`internal/webhook/webhook.go:39`, `:189-195`). Outbound, not inbound.

So per-user request throttling would have to be provided by a reverse proxy in front of the server; nothing in this codebase implements it.
