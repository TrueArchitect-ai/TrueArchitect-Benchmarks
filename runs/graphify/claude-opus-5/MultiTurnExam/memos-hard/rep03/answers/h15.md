Two patterns are worth separating, because they fail differently:

**Post-hoc gates** (fetch the memo, then authorize): sites 1, 4, 5, 6, 7, 8. The canonical logic is `checkMemoReadAccess` (`server/router/api/v1/memo_service.go:39-67`) — archived memos are creator-only; non-`PUBLIC` requires authentication; `PRIVATE` requires being the creator. Note it does *not* grant admins access to others' private memos, whereas the fileserver's equivalent check does (`server/router/fileserver/fileserver.go:698` allows `store.RoleAdmin`), and the API's attachment/reaction gates use `isSuperUser(user)`. So the same conceptual rule is implemented with three slightly different admin policies.

**Query-scoping** (never load invisible rows): sites 2, 3, 10, 11. `ListMemos` is the interesting one — anonymous callers get `VisibilityList = [PUBLIC]`, while an authenticated caller browsing unscoped gets a CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` appended (`server/router/api/v1/memo_service.go:221`), and a caller scoped to another user's memos gets `[PUBLIC, PROTECTED]`.

**Fan-out filtering** (site 9) is its own surface: `SSEHub.Broadcast` consults `canReceive` per connected client, dropping `PRIVATE` events unless the client is the creator or an admin (`server/router/api/v1/sse_hub.go:136-137`); `PUBLIC`, `PROTECTED`, and empty visibility pass to everyone.

**Share tokens are the one bypass**: `checkAttachmentPermission` returns early for a valid, non-expired `share_token` matching that memo (`server/router/fileserver/fileserver.go:683-688`), and the share-based memo read path validates via `getActiveMemoShare` (`server/router/api/v1/memo_share_service.go:199-208`) instead of `checkMemoReadAccess`.

Sites 12 and 13 are enforcement in a weaker sense — they gate who gets *notified* and how much memo content appears in an email — but they're driven by the same `store.Visibility` values, so I've listed them rather than silently dropping them. The MCP router (`server/router/mcp/`) contains no visibility logic of its own; it goes through the API v1 service.
