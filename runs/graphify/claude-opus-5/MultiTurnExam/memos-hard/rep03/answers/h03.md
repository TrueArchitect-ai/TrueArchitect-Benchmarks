**`internal/idp` (abstraction); `internal/idp/oauth2` (implementation).**

Details:

**Abstraction — `internal/idp/idp.go`**
The package is deliberately thin: it defines a single normalized struct, `IdentityProviderUserInfo` with `Identifier`, `DisplayName`, `Email`, `AvatarURL` (`internal/idp/idp.go:3-8`). Note there is no Go `interface` here — the abstraction is the shared *user-info type* that every provider maps its claims into, plus the `IdentityProvider_Type` enum and `IdentityProviderConfig` oneof on the storage side (`proto/store/idp.proto`, generated at `proto/gen/store/idp.pb.go:24-28`, `:158-159`). The enum currently has exactly two values: `TYPE_UNSPECIFIED` and `OAUTH2`.

**Implementation — `internal/idp/oauth2/oauth2.go`**
The only concrete provider that ships. `NewIdentityProvider` validates required config fields (`clientId`, `clientSecret`, `tokenUrl`, `userInfoUrl`, `fieldMapping.identifier`) at `internal/idp/oauth2/oauth2.go:27-43`. It exposes two methods:
- `ExchangeToken` (`:47`) — authorization-code exchange via `golang.org/x/oauth2`, with optional PKCE `code_verifier` support (`:64-66`).
- `UserInfo` (`:83`) — bearer-token GET against the configured userinfo endpoint (10s timeout), unmarshals claims into `map[string]any`, and maps them onto `idp.IdentityProviderUserInfo` using the configurable `FieldMapping` (`:114-140`). The identifier is required; display name falls back to the identifier; email and avatar are best-effort.

**Wiring**
Both are consumed only by `server/router/api/v1/auth_service_sso.go`. `resolveSSOIdentity` (`:104`) loads the stored provider, and the type dispatch at `:120-121` is a single `if identityProvider.Type == storepb.IdentityProvider_OAUTH2` branch — confirming OAuth2 is the sole implementation. It then applies the optional `identifierFilter` regex (`:136-145`) before `resolveSSOUser` (`:19`) links or provisions the local account.

Since the OAuth2 provider takes an explicit `userInfoUrl` and field mapping rather than doing OIDC discovery or ID-token validation, OIDC providers are supported only insofar as they can be configured as plain OAuth2 — there is no separate OIDC/SAML/LDAP package in this tree.
