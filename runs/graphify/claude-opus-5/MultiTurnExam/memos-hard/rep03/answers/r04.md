**Premise correction: neither. There is no message broker in this repository — no NATS, no RabbitMQ, no AMQP, Kafka, or pub/sub library of any kind.** A case-insensitive grep for `nats`, `rabbit`, `amqp`, `kafka`, `pubsub`, and `streadway` across all Go sources and `go.mod` (excluding `web/`) returns zero hits. There is no external queue and therefore no queue declaration to point at.

**Actual mechanism: an unexported, in-process buffered Go channel with a fixed pool of goroutines.**

The "queue" is declared as a package-level variable in `internal/webhook/webhook.go:39`:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

The "workers" are four goroutines started in that package's `init()` (`internal/webhook/webhook.go:42-55`), each ranging over the channel and calling `Post` (`internal/webhook/webhook.go:120`), logging a warning on failure. Delivery itself is the `safeClient.Do(req)` at `internal/webhook/webhook.go:152`.

Producers call `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking send:

```go
select {
case asyncPostQueue <- requestPayload:
default:
    slog.Warn("Dropped webhook dispatch because the async queue is full", ...)
}
```

Its two call sites are `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

Properties that follow from this being a channel rather than a broker, and that matter operationally:

- **No durability.** The buffer lives in process memory; a restart or crash loses every queued payload. Nothing is persisted to the database or disk.
- **Silent drop under load.** Once 128 payloads are outstanding, new ones are discarded with only a log line — there is no backpressure on the RPC handler and no dead-letter path.
- **No retries.** `Post` returns an error, the worker logs it, and the payload is gone. Retry/redelivery semantics a broker would provide don't exist here.
- **No cross-instance coordination.** Each server process has its own channel and its own four workers, so the pool doesn't scale or share work across replicas.
- **Not shut down cleanly.** The channel is never closed and the workers aren't tracked by `backgroundRunnerWG` (`server/server.go:41`), so in-flight dispatches aren't drained during `Server.Shutdown`.
