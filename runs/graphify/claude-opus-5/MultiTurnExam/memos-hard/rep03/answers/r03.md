**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is not wired into the running server at all — so there is no scheduled time to report.**

Two separate corrections are involved:

**1. No database-cleanup job exists.** Grepping for `cleanup`, `vacuum`, `purge`, `nightly`, and `cron` across `server/`, `cmd/`, and `store/` (excluding tests) turns up no job that prunes, compacts, or vacuums the database. The only "cleanup" hits are unrelated: the in-memory cache's expiry sweeper (`store/cache/cache.go:199`, running every 5 minutes per `store/store.go:42`), best-effort attachment/orphan-row cleanup during user deletion (`server/router/api/v1/user_service.go:421-450`, `server/router/api/v1/auth_service_sso.go:76`), and cascade deletes when a memo is removed (`server/router/api/v1/memo_service.go:579`).

**2. The cron scheduler is dead code.** A cron package does exist — `internal/scheduler/` with a 5-field parser (`internal/scheduler/parser.go`), job registration (`internal/scheduler/scheduler.go`), and middleware (`internal/scheduler/middleware.go`) — but grepping the import path `github.com/usememos/memos/internal/scheduler` across the repo returns only two hits, both tests: `internal/scheduler/integration_test.go:13` and `internal/scheduler/example_test.go:10`. No production file imports it, and there are no `scheduler.New` / `Register` calls anywhere in `server/` or `cmd/`.

**What actually runs on a schedule.** Background work is handled by plain tickers, not cron. `server/runner/` contains exactly two packages:

- `s3presign` — refreshes S3 presigned attachment URLs on a 12-hour `time.Ticker` (`server/runner/s3presign/runner.go:28`, `:30-42`), started from `Server.startBackgroundRunners` (`server/server.go:162-171`) with one immediate run at startup.
- `memopayload` — has a `RunOnce` batch rebuild (`server/runner/memopayload/runner.go:27`) but neither it nor its constructor has any caller, so it never executes.

Neither is a cleanup job, and neither is tied to a wall-clock time — the s3presign interval is relative to process start, so its firing time drifts with restarts.
