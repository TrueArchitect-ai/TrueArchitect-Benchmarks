Supporting detail per hop:

- **URL origin.** The browser gets this path from the API layer, not by guessing: `convertUserFromStore` rewrites `AvatarUrl` to `/file/{name}/avatar` when the stored avatar is a base64 data URI (`server/router/api/v1/user_service_converters.go:31-40`), where `name` is `BuildUserName(user.Username)` = `users/{username}` (`server/router/api/v1/user_service_converters.go:17`, prefix at `server/router/api/v1/resource_name.go:18`). So the `:identifier` path param is a username, matching the `FindUser{Username: ...}` lookup.

- **Wiring.** `FileServerService` is constructed and its routes registered during server setup at `server/server.go:81-82`.

- **`serveUserAvatar`** (`server/router/fileserver/fileserver.go:168-208`) does the access check first: if `!s.Profile.AllowAnonymous()` it requires a resolvable viewer via `s.getCurrentUser` and returns 401 otherwise. Then it 404s on unknown user or empty `AvatarURL`, decodes with `parseDataURI` (`fileserver.go:737`), rejects MIME types outside `avatarAllowedTypes` (`fileserver.go:75`), sets security + `Cache-Control` headers, and writes the bytes with `c.Blob`.

- **Data layer.** The avatar bytes are not a separate blob or file — they live in the `user` row's `avatar_url` column as a base64 data URI, so the "hop to stored data" ends at the user query. `Store.GetUser` only consults `userCache` when `find.ID` is set, so this username-keyed lookup always falls through to `ListUsers` → driver SQL; results are then written into the cache keyed by ID (`store/user.go:142-144,167`).
