**Premise correction: there is no rate-limiting middleware in this repository — per-user or otherwise — so there is no registration site and no request limits to report.**

Evidence:

- A case-insensitive grep across all Go files for `rate.?limit`, `ratelimit`, `throttl`, and `RateLimiter` returns exactly one hit, and it is an aspirational comment, not code: `internal/email/doc.go:86` — `//   - Rate limit email sending to prevent abuse`, listed under future/recommended work.
- No rate-limiting dependency is declared. `go.mod` contains no `golang.org/x/time` (the usual source of `rate.Limiter`), no `tollbooth`, and nothing else matching `rate`/`limiter`/`throttle`.
- The Echo middleware stack has only two entries, neither of which limits request volume: `middleware.Recover()` and `newCORSMiddleware(profile)` at `server/server.go:51-52`. Echo's built-in `middleware.RateLimiter` is not used.
- There is no `server/middleware` package at all — `server/` contains `auth`, `cors.go`, `notification`, `router`, `runner`, and `server.go`.

**What does exist, and is easy to mistake for rate limiting:** bounded *concurrency* limits, not request-rate limits. These are `semaphore.Weighted` gates on expensive media work, applied globally rather than per user:

- `APIV1Service.thumbnailSemaphore` = 3 concurrent thumbnail generations, and `imageProcessingSemaphore` = 2 — `server/router/api/v1/v1.go:59-60`.
- `FileServerService.thumbnailSemaphore` = `maxConcurrentThumbnails` — `server/router/fileserver/fileserver.go:116`.

Also adjacent but not rate limiting: the webhook dispatch queue is bounded at 128 with 4 workers and *drops* overflow (`internal/webhook/webhook.go:39-55, 189-195`), which throttles outbound deliveries, not inbound API requests.

So if per-user API rate limiting is a requirement, it would need to be built; nothing in the current tree enforces it.
