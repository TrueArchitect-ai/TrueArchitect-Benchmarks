**Explicit Go code** — each SQL driver issues an explicit `DELETE FROM reaction` inside the delete-user transaction. There is no database-level cascade for reactions.

What I checked:

**1. The reaction table DDL — no foreign key at all**
`reaction` is declared with a bare `creator_id INTEGER NOT NULL` and `content_id`, plus a `UNIQUE(creator_id, content_id, reaction_type)` constraint, in all three dialects:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

Grepping the LATEST schemas for `FOREIGN KEY` / `REFERENCES` / `ON DELETE` yields exactly one hit per dialect, and it belongs to `memo_share`, not `reaction`: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). So no DB rule can reach reactions.

**2. The Go deletion path — two explicit deletes, per driver**
`deleteUserTargetsTx` runs both, in-transaction, before the user row itself (`store/db/sqlite/user_delete.go:92-104`, mirrored in `store/db/postgres/user_delete.go:96,102` and `store/db/mysql/user_delete.go:96,102`):
- `deleteReactionsByContentIDsTx` — removes reactions *others* left on the deleted user's memos, batching over the collected memo content IDs (`store/db/sqlite/user_delete.go:380-388`; MySQL at `store/db/mysql/user_delete.go:417-425`).
- `deleteReactionsByCreatorTx` — removes reactions the deleted user left *elsewhere*: `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`; MySQL at `store/db/mysql/user_delete.go:437-440`).

So both directions are covered, and all three drivers implement it identically — the logic is duplicated per dialect rather than shared, with the entry point `DeleteUser` (e.g. `store/db/mysql/user_delete.go:29`) satisfying the `store.Driver` interface method at `store/driver.go:48`.
