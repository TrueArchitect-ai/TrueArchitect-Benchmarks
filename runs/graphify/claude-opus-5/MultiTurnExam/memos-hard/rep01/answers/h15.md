Notes on the shape of this:

- **Two enforcement styles.** The single-resource paths check `memo.Visibility` *after* fetching and return `codes.PermissionDenied`/`NotFound`; the list paths instead push visibility into the query as `FindMemo.VisibilityList` or a CEL filter string so non-visible rows never load. The `ListMemos` authed branch builds the predicate as raw text — `fmt.Sprintf("creator_id == %d || visibility in [\"PUBLIC\", \"PROTECTED\"]", currentUser.ID)` (`memo_service.go:222`).

- **The checks are duplicated rather than shared.** `checkMemoReadAccess` exists, but `reaction_service.go`, `attachment_service.go`, and `memo_attachment_service.go` each re-implement the same `!= Public` / `== Private && CreatorID != user.ID` pattern inline, with a subtle difference: those three admit admins via `isSuperUser(user)`, while `checkMemoReadAccess` does **not** — an admin is denied a private memo through `GetMemo` but allowed its reactions and attachments.

- **The fileserver is the only surface with a share-token bypass** (`fileserver.go:681-688`), and the only one gating on `s.Profile.AllowAnonymous()`.

- Two adjacent sites I did **not** count as view enforcement: `server/notification/email.go:313-316` and `server/router/api/v1/memo_mention_helpers.go:62-84`, which use visibility to decide whether to *send a notification*, not whether to serve content.
