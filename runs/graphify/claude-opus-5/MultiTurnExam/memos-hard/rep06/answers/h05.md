**Explicit Go code — two `DELETE FROM reaction` statements inside the transactional `DeleteUser` implementation of each driver. There is no database-level cascade for reactions.**

What I checked:

**1. The delete path.** `DeleteUser` opens a transaction, gathers targets, and calls `deleteUserTargetsTx` — `store/db/mysql/user_delete.go:28` and `:89` (mirrored at `store/db/sqlite/user_delete.go` and `store/db/postgres/user_delete.go`). Two of the ordered steps handle reactions:
- `deleteReactionsByContentIDsTx` (`store/db/mysql/user_delete.go:96` → definition at `:380-388`) removes reactions *on* the user's memos, matching `content_id IN (...)` where the IDs are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs` (`store/db/mysql/user_delete.go`, helper near the end of the file). This catches other people's reactions to the deleted user's content.
- `deleteReactionsByCreatorTx` (`:102` → definition at `:400-403`) removes reactions *authored by* the user via `DELETE FROM reaction WHERE creator_id = ?`.

Both run in batches of 500 (`deleteUserBatchSize`) and inside the same transaction, before the `memo` and `user` rows are deleted. The same two functions exist at identical line numbers in `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/sqlite/user_delete.go:96,102,380,400`, so all three drivers behave alike.

**2. The schema — no cascade.** The `reaction` table has no foreign key at all in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. Each declares only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Grepping `FOREIGN KEY` across the three `LATEST.sql` files returns exactly one match per file, and it's on `memo_share.memo_id` (`store/migration/mysql/LATEST.sql:108`, `postgres/LATEST.sql:108`, `sqlite/LATEST.sql:109`) — not on `reaction`. A cascade would be impossible here anyway, since `reaction.content_id` is a text resource name (`memos/{uid}`), not an integer FK to `memo.id`.

**3. Cascades are off in SQLite regardless.** The SQLite DSN sets `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so even the one declared FK isn't enforced by the engine there.

**4. Test confirmation.** `store/test/user_delete_test.go` seeds reactions by the deleted user and by a peer (`:97-112`), then asserts after deletion that only the peer's reaction on a peer-owned memo survives (`:217-220`) — i.e. the Go code, not the database, is what did the removal.
