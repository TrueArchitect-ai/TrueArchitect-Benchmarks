Two patterns worth flagging:

- **Two enforcement styles.** Single-object reads use post-fetch guards (`memo.Visibility != store.Public` → require user → deny if `Private` and not creator/superuser). List endpoints instead push the constraint into the query via `FindMemo.VisibilityList` or a CEL filter string — e.g. `server/router/api/v1/memo_service.go:222` builds `creator_id == %d || visibility in ["PUBLIC", "PROTECTED"]`. The guards are duplicated rather than centralized, so each is its own site.
- **The file server is the one surface with a bypass.** `checkAttachmentPermission` accepts a valid, non-expired `share_token` query param scoped to that memo (`server/router/fileserver/fileserver.go:684-690`), letting non-public attachments load on a shared memo page; it also requires `s.Profile.AllowAnonymous()` before serving even PUBLIC memos anonymously (`:677`). It uses `store.RoleAdmin` directly where the API layer uses the `isSuperUser` helper.
