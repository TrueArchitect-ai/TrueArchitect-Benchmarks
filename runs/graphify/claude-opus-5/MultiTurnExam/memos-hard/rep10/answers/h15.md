Structural notes:

- **Two enforcement shapes.** Single-memo reads use an imperative gate (`if Visibility != Public → require user; if Private → require creator/admin`), duplicated in six places rather than routed through `checkMemoReadAccess` — compare `memo_service.go:55-65`, `reaction_service.go:30-40`, `memo_attachment_service.go:214-224`, `attachment_service.go:445-452`, `fileserver.go:677-700`. List endpoints instead push the constraint into the query as `VisibilityList` or a CEL filter string, so rows are never loaded.
- **Deliberate bypass.** `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:153`) and the `share_token` query-param branch in the fileserver (`server/router/fileserver/fileserver.go:682-689`) grant access to non-public memos on a valid, unexpired share token — visibility is intentionally not consulted there.
- **Anonymous-instance interaction.** The fileserver's public fast-path also requires `s.Profile.AllowAnonymous()` (`fileserver.go:677`), so on a private instance even PUBLIC memo attachments need a session or share token — a check the gRPC path at `attachment_service.go:445` does not make.
- **Admin asymmetry.** Most sites let admins through via `isSuperUser(user)` / `RoleAdmin`, but `checkMemoReadAccess` does not (`memo_service.go:63` compares only `CreatorID != user.ID`), so an admin is denied a PRIVATE memo through `GetMemo` while being allowed its attachments.
