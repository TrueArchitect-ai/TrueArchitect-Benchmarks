**Explicit Go code — each SQL driver issues its own `DELETE FROM reaction` statements inside the delete-user transaction. There is no database-level cascade, because the `reaction` table has no foreign keys at all.**

What I checked:

**1. The delete path.** `store.DeleteUser` (`store/user.go:171-181`) just delegates to `s.driver.DeleteUser` and then invalidates cache. Each driver implements it identically:

- `store/db/mysql/user_delete.go:29` — opens a tx, collects targets, calls `deleteUserTargetsTx`.
- `store/db/postgres/user_delete.go:96`, `:102` and `store/db/sqlite/user_delete.go:96`, `:102` — same structure and call order.

**2. Two distinct reaction deletions, both explicit.** In `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:92-127`) reactions are removed twice, first in the ordered list:

- `deleteReactionsByContentIDsTx` (`store/db/mysql/user_delete.go:417-425`, called at `:96`) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500, removing *other people's* reactions on the deleted user's memos. The content IDs are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs` (`:549-555`), and the memo set includes descendant comment memos walked via `memo_relation` (`listDeleteUserMemoTreeIterative`, `:133-181`).
- `deleteReactionsByCreatorTx` (`store/db/mysql/user_delete.go:437-440`, called at `:102`) — `DELETE FROM reaction WHERE creator_id = ?`, removing the deleted user's own reactions anywhere.

The postgres and sqlite copies live at the same function names, `user_delete.go:380` and `:400` in both.

**3. No database-level rule exists.** The `reaction` table is declared without any `FOREIGN KEY` clause in all three dialects — `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/sqlite/LATEST.sql:92-99` (and the originals at `store/migration/*/0.20/00__reaction.sql`). `creator_id` is a bare `INT NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Grepping `REFERENCES|ON DELETE` across `store/migration/` shows cascades only on `memo_share.memo_id` and on legacy sqlite tables (`0.5/00__regenerate_foreign_keys.sql`) — never on `reaction`.

So if the Go statements were removed, reactions would be orphaned rather than cleaned up by the engine. Both deletions run inside the same transaction as the user row removal (`deleteUserRowTx`, `store/db/mysql/user_delete.go:498`), so cleanup is atomic with the delete.
