Notes on the hops:

- **Route:** the `/file` group is created in `RegisterRoutes` (`server/router/fileserver/fileserver.go:121-125`); the service itself is constructed and wired into Echo at `server/server.go:81-82`.
- **Auth gate:** before any lookup, `serveUserAvatar` checks `s.Profile.AllowAnonymous()` (`fileserver.go:172-180`) — on a private instance an anonymous request gets 401 via `getCurrentUser`; on a public instance any avatar is served unauthenticated.
- **Lookup key:** the `:identifier` path param is passed straight through as a **username**, not an ID (`fileserver.go:716`: `&store.FindUser{Username: &identifier}`). That matters for caching — `Store.GetUser` only consults `userCache` when `find.ID != nil` (`store/user.go:149-156`), so a username lookup always falls through to `ListUsers` and hits the database, then populates the cache on the way back (`store/user.go:167`).
- **Data source:** the image is *not* a file on disk or in S3 — it's a base64 data URI stored in the `user.avatar_url` column. `serveUserAvatar` decodes it with `parseDataURI` (`fileserver.go:196`), rejects anything outside `avatarAllowedTypes` (PNG/JPEG/GIF/WebP, `fileserver.go:74-75`, checked at `:201`), sets security headers plus `Cache-Control`, and writes the bytes with `c.Blob` (`fileserver.go:207`).
- **Driver layer:** `Store.ListUsers` delegates to the `store.Driver` interface (`store/user.go:137`), whose three implementations each select `avatar_url` and scan it into `store.User.AvatarURL`.
