**Premise correction: neither. There is no message broker in this codebase — no NATS, RabbitMQ/AMQP, Kafka, SQS, or any pub/sub client. A search across all Go files and `go.mod` for `nats`, `rabbitmq`, `amqp`, `kafka`, `streadway`, `pubsub`, and `sqs` returns zero hits. No queue is declared anywhere, because none exists.**

Actual mechanism — an in-process buffered Go channel:

- **The "queue" is a package-level channel** with a fixed capacity of 128: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`). It lives entirely in the server process's memory.
- **The "workers" are four goroutines** started in the package `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post` for every payload, logging a warning on failure. They are started implicitly on package import — there's no explicit lifecycle, and no shutdown path drains or stops them.
- **Producers** call `webhook.PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a `slog.Warn` — no retry, no persistence, no dead-letter. Callers are the memo dispatch helpers at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.
- **Delivery** happens in `webhook.Post` (`internal/webhook/webhook.go:120`), which POSTs JSON to the user-configured URL via `safeClient` (30s timeout, SSRF-blocking dialer) at `internal/webhook/webhook.go:152`.

Practical consequences of it being a channel rather than a broker: deliveries are lost on process restart or crash, they don't survive across replicas (each instance has its own channel), there is no at-least-once guarantee or backoff/retry, and failures are visible only as log warnings. Delivery is bounded to 4 concurrent outbound requests.
