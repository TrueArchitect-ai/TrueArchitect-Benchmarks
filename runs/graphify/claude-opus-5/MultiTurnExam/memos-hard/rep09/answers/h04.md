**No — outside `NewDBDriver`, the MySQL driver is never constructed in non-test code.**

Evidence:

1. **Import graph is the decisive check.** `grep -rn "db/mysql" --include=*.go .` returns exactly one hit across the entire repo: `store/db/db.go:8`. Since Go requires an import to reference a package, no other package can call `mysql.NewDB` or name `mysql.DB`. That single importer is the factory itself.

2. **The only construction site** is `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver` (`store/db/db.go:14-27`), alongside the parallel `sqlite.NewDB` (line 20) and `postgres.NewDB` (line 23) cases.

3. **All callers go through the factory**: `db.NewDBDriver` is invoked at `store/test/store.go:28`, `store/test/store.go:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70` — always by driver name from the profile, never by reaching into the package.

Two things that look like counterexamples but aren't:

- `store/test/containers.go:42,101-105` references `mysql.MySQLContainer` / `mysql.Run` / `mysql.WithDatabase` — that's the **testcontainers-go** MySQL module (spinning up a MySQL server for tests), not `store/db/mysql`.
- `store/db/mysql/mysql.go:17,30,73` references `mysql.Config` / `mysql.ParseDSN` — that's the **go-sql-driver/mysql** DSN parser used inside the driver's own implementation.

One in-package exception worth naming: `store/db/mysql/auth_config_test.go:12` does `db := &DB{}` — a bare zero-value struct literal in a test that lives in `package mysql` itself, so it needs no import. It bypasses `NewDB` (no profile, no connection) to exercise a pure helper. The only other `DB{...}` literal is `store/db/mysql/mysql.go:29`, inside `NewDB` itself.
