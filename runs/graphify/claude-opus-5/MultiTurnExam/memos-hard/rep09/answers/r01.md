**Premise correction: there is no Redis anywhere in this project.** A case-insensitive `grep -rni "redis"` across all `.go` files returns zero hits, and `go.mod` / `go.sum` contain no Redis client dependency (no `go-redis`, `redigo`, or similar). There is no connection string, pool, or client to configure — the cache is entirely in-process.

**Actual mechanism:** a hand-rolled, thread-safe in-memory cache in `store/cache/cache.go`.

- **Implementation** — `Cache` (`store/cache/cache.go:65`) backs entries with a `sync.Map` plus an `atomic.Int64` item counter; each `item` (`cache.go:35`) holds the value, an absolute `expiration` time, and a rough size estimate. A background goroutine started in `New` (`cache.go:74`) sweeps expired entries and is torn down by `Close` (`cache.go:187`). State dies with the process — nothing is shared between instances, so this is not viable for multi-replica deployments.

- **Configuration site** — not a connection, but a `cache.Config` literal in `store.New` at `store/store.go:39-44`: `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil`. That single config value is passed to all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). `cache.DefaultConfig()` (`store/cache/cache.go:56`) declares identical values but is not what the store uses. The values are hardcoded; no flag, env var, or profile field tunes them.

- **TTL for user entries: 10 minutes.** `userCache` is created with the shared `cacheConfig` (`store/store.go:52`), and every write goes through `Set` (`store/user.go:98,122,132,143,167`), which forwards to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). No caller anywhere invokes `SetWithTTL` directly, so the 10-minute default is the only TTL in effect.

Two related details: the cache is keyed by user ID via `userCacheKey` (`store/user.go:88`), so `GetUser` only consults it when looking up by ID (`store/user.go:149-156`) — username lookups always hit the database. And entries are invalidated explicitly on delete (`store/user_delete.go:40`) in addition to expiring.
