**Explicit Go code — two `DELETE FROM reaction` statements inside the per-driver `DeleteUser` transaction. There is no database-level cascade for reactions.**

What I checked:

**1. The deletion code path.** Each driver implements `DeleteUser` identically, wrapping everything in one transaction (`store/db/sqlite/user_delete.go:29`, `store/db/postgres/user_delete.go:29`, `store/db/mysql/user_delete.go:29`). `deleteUserTargetsTx` runs two distinct reaction deletes, first in the ordered sequence:

- `deleteReactionsByContentIDsTx` — removes reactions *others left on the departing user's memos*, keyed by the collected memo content IDs (`store/db/mysql/user_delete.go:96` → impl at `:417`, `DELETE FROM reaction WHERE content_id IN (...)` at `:420`).
- `deleteReactionsByCreatorTx` — removes reactions *the user left on anyone's content* (`store/db/mysql/user_delete.go:102` → impl at `:437`, `DELETE FROM reaction WHERE creator_id = ?` at `:438`).

Mirrored at postgres `:96,:102,:380,:400` and sqlite `:96,:102,:380,:400`. Both run before `deleteMemosTx` and `deleteUserRowTx`, so no orphan rows are left behind.

**2. The schema — ruling out a DB rule.** The `reaction` table in all three `LATEST.sql` files declares no foreign keys at all, only a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/mysql/LATEST.sql`, `store/migration/postgres/LATEST.sql`, `store/migration/sqlite/LATEST.sql`. `creator_id` is a plain `INT/INTEGER NOT NULL` with no `REFERENCES user(id)`. A repo-wide `grep -ri "on delete"` over `store/migration/` shows cascades exist for other tables (e.g. `memo_share` → `memo(id)` in `store/migration/*/LATEST.sql:108-109`), but none on `reaction`. Also note `content_id` is a resource *name* string (`memos/{uid}`), not an integer FK, so a cascade isn't even expressible there.

**3. Behavioral confirmation.** `server/router/api/v1/test/user_service_delete_test.go` seeds four reactions (`:188-209`) and asserts after deletion that reactions on the user's own memo (`:287-289`) and on their comment (`:291-293`) are gone, while a *third party's* reaction on a *foreign* memo survives (`:295-298`) — exactly the two-query scoping above. The rollback test (`:366-431`) confirms the reaction is still present when the transaction aborts at the `DeleteUserFailpointBeforeCommit` failpoint (`store/user_delete.go:14`), proving the removal is transactional rather than incidental.
