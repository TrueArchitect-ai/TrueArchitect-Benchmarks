**Premise correction: there is no per-user API rate-limiting middleware in this repository — it doesn't exist, so there's nothing registered and no request limits to report.**

What I checked:

- A case-insensitive grep across all `.go` files for `ratelimit`, `rate_limit`, `rate limit`, `throttle`, and `golang.org/x/time/rate` returns exactly one hit, and it's an aspirational comment in documentation, not code: `internal/email/doc.go:86` — `//   - Rate limit email sending to prevent abuse`.
- `go.mod` has no rate-limiting dependency (no `golang.org/x/time`, no `echo` rate-limiter helper, no token-bucket library).
- The full set of Echo middleware registered on the server is: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/server.go:51-52`), plus static-file and SPA-fallback middleware on the frontend router (`server/router/frontend/frontend.go:54`, `:59`). Echo ships a `middleware.RateLimiter`, but it is not used here. Auth is enforced by an interceptor/authorizer rather than middleware (`server/router/api/v1/v1.go:95`, `NewAuthorizer`), and it does no counting.

**What does exist, and is easy to mistake for rate limiting** — process-wide *concurrency* caps, not per-user request limits:

- `thumbnailSemaphore` — `semaphore.NewWeighted(3)`: at most 3 concurrent thumbnail generations (`server/router/api/v1/v1.go:59`; a separate one in the file server at `server/router/fileserver/fileserver.go:116`, with `maxConcurrentThumbnails = 3` at `fileserver.go:46`)
- `imageProcessingSemaphore` — `semaphore.NewWeighted(2)` (`server/router/api/v1/v1.go:60`)
- Webhook dispatch queue — bounded 128-slot channel with 4 workers, dropping overflow (`internal/webhook/webhook.go:39`, `:42-55`)
- Page-size clamping on list endpoints via `MaxPageSize` (`server/router/api/v1/memo_service.go:239`)

These bound server resource use globally; none of them tracks requests per user or returns HTTP 429.
