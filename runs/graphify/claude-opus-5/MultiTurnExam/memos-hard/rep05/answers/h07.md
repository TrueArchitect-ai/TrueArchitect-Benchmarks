Notes on the hops that aren't pure pass-through:

- **Auth gate happens first**: if `s.Profile.AllowAnonymous()` is false (private instance — no `InstanceURL`), the handler resolves the caller via `getCurrentUser` and 401s an anonymous viewer (`fileserver.go:171-180`). On an open instance, any browser can fetch any user's avatar. There is no per-user visibility check beyond that.
- **Cache short-circuit**: `Store.GetUser` only consults `userCache` when the lookup is by `ID` (`store/user.go:149-156`). This path looks up by username, so it always falls through to `ListUsers` and hits the database; the row is then written into the cache keyed by ID (`store/user.go:167`).
- **The "stored data" is the user row, not a file**: the avatar lives inline in `user.avatar_url` as a base64 `data:` URI, so there's no attachment/blob-storage hop at all. `dataURIRegex` extracts the MIME type and payload, and only `avatarAllowedTypes` (`fileserver.go:75`) — PNG/JPEG/GIF/WebP — are served (`fileserver.go:201-203`).
- **How the browser gets this URL**: `convertUserFromStore` rewrites the stored base64 blob into the `/file/{user}/avatar` path when converting to protobuf (`server/router/api/v1/user_service_converters.go:32-36`), which is why the client requests this endpoint rather than embedding the data URI.
