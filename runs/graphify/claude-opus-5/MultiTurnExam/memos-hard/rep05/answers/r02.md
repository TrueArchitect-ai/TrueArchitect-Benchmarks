**Premise correction: no per-user API rate-limiting middleware exists in this repository. There is nothing registered, and therefore no request limits to report.**

Evidence:

- A repo-wide case-insensitive grep for `rate.?limit|ratelimit|throttl|limiter`, plus the usual libraries (`golang.org/x/time/rate`, `tollbooth`), across all Go files and `go.mod` returns exactly one hit — and it's an aspirational comment, not code: `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a future consideration.
- The Echo middleware stack is two entries, registered at `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)`. No `middleware.RateLimiter` (Echo ships one; it isn't used here).
- There is no `server/middleware` package — the only interceptor-style code is the auth layer (`NewAuthorizer` / the Connect interceptor wired in `server/router/api/v1/v1.go:64+`), which authenticates and authorizes but does not count or throttle requests.

**What does exist, and is easy to mistake for rate limiting** — concurrency caps, not request-rate limits, and all global rather than per-user:

- `thumbnailSemaphore` — `semaphore.NewWeighted(3)` in `server/router/api/v1/v1.go:59`, and separately `maxConcurrentThumbnails = 3` in `server/router/fileserver/fileserver.go:46` used at `fileserver.go:116`.
- `imageProcessingSemaphore` — `semaphore.NewWeighted(2)` at `server/router/api/v1/v1.go:60`.
- The webhook dispatch queue: a 128-slot buffered channel drained by 4 workers, which *drops* events when full (`internal/webhook/webhook.go:39-55`, `:189-195`).

Those bound simultaneous in-flight work to protect memory; they impose no ceiling on how many requests a given user or token may issue over time. The only per-user constraints anywhere are content-size checks such as the memo content-length limit (`server/router/api/v1/memo_service.go:101-107`).
