**Premise correction: there is no Redis in this repository.** A case-insensitive grep for `redis` across all Go files, `go.mod`, YAML, and Markdown returns zero hits — no client library, no dependency, no config key, no connection string. There is nothing to configure.

**Actual mechanism: a process-local, in-memory cache.**

- **Implementation**: `store/cache/cache.go` — a `Cache` struct backed by `sync.Map` with an atomic item counter (`store/cache/cache.go:66-72`), satisfying the `cache.Interface` contract (`store/cache/cache.go:11-32`). Entries are `item{value, expiration, size}` (`cache.go:35-39`). A `cleanupLoop` goroutine sweeps expired keys on an interval, and `Close()` stops it (`cache.go:187-197`).

- **Configuration site**: `store.New` in `store/store.go:38-45`, where the config is hardcoded — not read from flags, env, or viper:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  Three separate cache instances are built from it (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, `userSettingCache`. The identical defaults also appear in `cache.DefaultConfig()` (`store/cache/cache.go:56-63`), though `store.New` constructs its own copy rather than calling it.

- **TTL for user entries: 10 minutes**, with a 1000-item cap per cache. Every write goes through `Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), which delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:90-92`) — so `expiration = time.Now().Add(10 * time.Minute)` (`cache.go:108-112`). No user code path calls `SetWithTTL` with a custom value, so there is no per-user override. Keys are the user ID as a decimal string (`userCacheKey`, `store/user.go:88-90`).

One behavioral detail that matters more than the TTL in practice: `Store.GetUser` only consults the cache when looking up **by ID** (`store/user.go:149-156`). Lookups by username or email always fall through to the database, then populate the cache on the way back (`store/user.go:167`). And because this is in-process memory, nothing is shared across replicas — a multi-instance deployment has independent caches with independent 10-minute staleness windows.
