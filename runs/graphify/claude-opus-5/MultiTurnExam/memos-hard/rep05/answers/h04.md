**No — in production code the MySQL driver is constructed only inside the factory.** (One test-only exception exists; details below.)

Evidence:

1. **Only one file in the entire repo imports the package.** `grep -rln "usememos/memos/store/db/mysql" --include=*.go .` returns exactly one result: `store/db/db.go` (import at `store/db/db.go:8`). No server code, no command, no test file outside the package itself imports it.

2. **Only one call site of the constructor.** `mysql.NewDB(profile)` appears once, in the `case "mysql"` arm of the driver-selection switch at `store/db/db.go:22` — inside `NewDBDriver`, the factory (`store/db/db.go:14-32`). The other arms construct `sqlite.NewDB` (`db.go:20`) and `postgres.NewDB` (`db.go:24`); an unrecognized `profile.Driver` returns `"unknown db driver"` (`db.go:26`).

3. **The struct literal is confined to the package.** `grep -rn "DB{" store/db/mysql/` yields only two hits: `driver := DB{profile: profile}` inside `NewDB` itself (`store/db/mysql/mysql.go:29`), and `db := &DB{}` in a unit test.

The one exception, which is test-only and doesn't leave the package: `store/db/mysql/auth_config_test.go:12` builds a bare `&DB{}` (no profile, no connection) purely to exercise the pure-function error classifier `IsRetryableAuthenticationMutationError` against MySQL error codes 1213/1205/1062. That's an in-package white-box test, not an alternate construction path.

Worth noting as contrast: `postgres` and `sqlite` *are* referenced outside the factory — `store/deployment_config_test.go` and `store/demo_seed_test.go` reach for them directly. MySQL has no such usage, so the factory is its sole entry point.
