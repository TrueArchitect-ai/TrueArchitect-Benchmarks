**Explicit Go code — two separate `DELETE FROM reaction` statements per driver, inside the delete-user transaction. There is no database-level rule (no FK, no cascade) on the `reaction` table.**

What I checked:

**1. The delete path.** `store.Store.DeleteUser` delegates straight to the driver (`store/user.go:171-172`). Each driver implements it as a single transaction: `store/db/mysql/user_delete.go:29-59`, plus the parallel implementations in `store/db/postgres/user_delete.go` and `store/db/sqlite/user_delete.go`.

**2. The reaction deletes.** `deleteUserTargetsTx` issues two distinct reaction cleanups (`store/db/mysql/user_delete.go:92-104`):
- `deleteReactionsByContentIDsTx` — removes reactions *on* the user's own memos, batched 500 at a time over the collected memo content IDs (`mysql/user_delete.go:417-425`; same at `postgres/user_delete.go:383` and `sqlite/user_delete.go:383`). This catches other people's reactions to the departing user's content.
- `deleteReactionsByCreatorTx` — removes reactions the user *left* on anyone's content: `DELETE FROM reaction WHERE creator_id = ?` (`mysql/user_delete.go:437-440`; `postgres/user_delete.go:401`, `sqlite/user_delete.go:401`).

Both run before `deleteMemosTx` and the final user row delete, all within the same `tx`, so the cleanup is atomic — a failure rolls everything back via the deferred `tx.Rollback()` (`mysql/user_delete.go:34-36`).

**3. Ruled out a database-level rule.** The `reaction` table declares `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and **no** `FOREIGN KEY` clause, in all three current schemas: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. A repo-wide grep for `REFERENCES|CASCADE|FOREIGN KEY` under `store/migration/` shows cascades exist for `memo_share → memo` (e.g. `store/migration/mysql/LATEST.sql:108`) and historically for several tables in `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql`, but `reaction` appears in none of them. Note also that `content_id` is a free-form string, not an integer memo FK, so a cascade on it isn't even expressible.

One consequence worth flagging: because `content_id` is untyped text, reactions are matched by string, and the by-content sweep depends on `listDeleteUserMemoTree` having collected every memo (including comment descendants) — nothing at the database layer would catch a miss.
