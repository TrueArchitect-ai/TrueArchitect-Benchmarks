The browser requests `GET /file/users/{username}/avatar` (the URL the API hands out at `server/router/api/v1/user_service_converters.go:36`). Hops:

```
GET /file/users/:identifier/avatar (route)          — server/router/fileserver/fileserver.go:124
FileServerService.serveUserAvatar                   — server/router/fileserver/fileserver.go:168
FileServerService.getUserByUsername                 — server/router/fileserver/fileserver.go:715
Store.GetUser                                       — store/user.go:148
Store.ListUsers                                     — store/user.go:136
Driver.ListUsers (interface dispatch)               — store/driver.go  →  store/db/{sqlite,mysql,postgres}/user.go
DB.ListUsers — SELECT ... avatar_url ... FROM user  — store/db/sqlite/user.go:88 (query at :151-164)
```

Notes on each hop:

- **Route registration**: `RegisterRoutes` puts both file routes on the `/file` group (`fileserver.go:121-125`); the service is constructed and wired into Echo at `server/server.go:81-82`.
- **`serveUserAvatar`** (`fileserver.go:168-210`) first gates anonymous access: if `!s.Profile.AllowAnonymous()` it requires a session/access-token/PAT via `s.getCurrentUser` and returns 401 otherwise (`fileserver.go:171-180`). So on a public instance, another user's avatar is readable without auth by design.
- **`getUserByUsername`** (`fileserver.go:715-717`) is a one-line wrapper building `&store.FindUser{Username: &identifier}` — note the path param is treated as a *username*, not a user ID.
- **`Store.GetUser`** (`store/user.go:148`) only consults `userCache` when the lookup is by ID; a username lookup always falls through to `ListUsers`, then populates the cache keyed by the resulting ID (`store/user.go:158-168`).
- **`Store.ListUsers`** (`store/user.go:136`) delegates to the driver and warms `userCache` for each row.
- **Data layer**: the per-driver `DB.ListUsers` builds the `WHERE` clause and selects `avatar_url` among the columns (`store/db/sqlite/user.go:88`, query at lines 151-164, scanned into `user.AvatarURL` around line 188). The MySQL and Postgres equivalents live at `store/db/mysql/user.go` and `store/db/postgres/user.go`; which one runs is decided by the factory `db.NewDBDriver` (`store/db/db.go:14`).

Back in the handler, the stored `AvatarURL` is a base64 **data URI**, not a file path — `parseDataURI` (`fileserver.go:737`) regex-splits it and base64-decodes the bytes, the MIME type is checked against `avatarAllowedTypes` (PNG/JPEG/GIF/WebP, `fileserver.go:74-75`) to block XSS-capable types like SVG, then `setSecurityHeaders` + `c.Blob` write the image (`fileserver.go:205-209`). So the "stored data" endpoint is the `user.avatar_url` column itself; no blob store or filesystem is involved.
