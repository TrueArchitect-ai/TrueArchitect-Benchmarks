**Explicit Go code** — two hand-written `DELETE FROM reaction` statements per driver, inside the user-deletion transaction. There is no database-level cascade for reactions.

What I checked:

**1. The deletion path.** `store.DeleteUser` (`store/user.go:171-181`) delegates straight to `s.driver.DeleteUser`. Each driver implements it identically:

- `store/db/mysql/user_delete.go:29` / `store/db/sqlite/user_delete.go` / `store/db/postgres/user_delete.go` — open a transaction, collect targets, call `deleteUserTargetsTx`, commit.
- Inside `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:92-127`, mirrored at `sqlite/user_delete.go:96,102` and `postgres/user_delete.go:96,102`) two reaction deletes run **before** the memos and the user row are removed:
  - `deleteReactionsByContentIDsTx` (`store/db/mysql/user_delete.go:417`) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500, removing *everyone's* reactions on the deleted user's memos. Content IDs are built as `"memos/" + memo.UID` (`user_delete.go:549-555`), matching the `content_id` format reactions are stored under.
  - `deleteReactionsByCreatorTx` (`store/db/mysql/user_delete.go:437`) — `DELETE FROM reaction WHERE creator_id = ?`, removing the departing user's own reactions on *other people's* memos.
- The memo set covered includes the user's own memos plus the whole comment subtree, gathered iteratively via `memo_relation` (`store/db/mysql/user_delete.go:133-181`), so reactions on descendant comments are caught too.

**2. Ruling out a DB-level rule.** In all three schemas the `reaction` table is declared with **no foreign key and no `ON DELETE CASCADE`** — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint:

- `store/migration/mysql/LATEST.sql:91-98`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/sqlite/LATEST.sql:92-99`

`creator_id` is a plain `INT NOT NULL` with no `REFERENCES user(id)`, and `content_id` is a free-form string, not a memo FK. The only `FOREIGN KEY ... ON DELETE CASCADE` in any schema is on `memo_share.memo_id → memo.id` (`store/migration/mysql/LATEST.sql:108`, `postgres/LATEST.sql:108`, `sqlite/LATEST.sql:109`) — which is why reactions need the explicit statements while memo shares would cascade on their own (the code deletes those explicitly anyway, `user_delete.go:442`).

**Consequence**: because it's application-level, correctness depends on the transaction — all deletes share one `tx` that is rolled back on any error (`store/db/mysql/user_delete.go:30-53`), so reaction cleanup can't half-apply.
