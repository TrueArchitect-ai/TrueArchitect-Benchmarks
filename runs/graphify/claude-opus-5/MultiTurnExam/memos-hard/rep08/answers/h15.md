Two shapes of enforcement appear:

- **Post-fetch gates** — load the memo, then compare `memo.Visibility` and `memo.CreatorID` against the caller. `checkMemoReadAccess` is the canonical one (`memo_service.go:39-68`): public passes; otherwise an authenticated user is required, and private demands `CreatorID == user.ID`. It also hides archived memos from non-creators. The attachment/reaction sites repeat this logic inline, adding an `isSuperUser` escape that `checkMemoReadAccess` notably lacks.
- **Pre-query narrowing** — push visibility into `store.FindMemo` so restricted rows never load: `VisibilityList = [PUBLIC]` for anonymous callers, `[PUBLIC, PROTECTED]` when browsing another user, or a CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` for one's own listing (`memo_service.go:219-226`).

Related, worth flagging:

- `memo_mention_helpers.go:62` (`canUserAccessMentionContext`) applies the same rules to decide who may be @-mentioned — an information-leak guard rather than a read gate.
- **Share tokens deliberately bypass visibility**: `server/router/fileserver/fileserver.go:684-689` grants attachment access for a valid, unexpired `share_token` matching that memo, before the private check runs. The `memo_share_service.go` handlers are the issuing side.
- The **MCP surface is not a separate site** — `NewMCPService` (`server/router/mcp/service.go:26`) proxies in-process to the existing API routes (`newAPIAdapter(echoServer)`), so it inherits the API-layer checks.
