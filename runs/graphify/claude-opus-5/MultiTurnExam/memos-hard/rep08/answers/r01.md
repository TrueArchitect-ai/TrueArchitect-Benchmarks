**Premise correction: there is no Redis.** The repository has no Redis client, no Redis configuration, and no Redis dependency — grepping for `redis`/`Redis` across all Go sources returns zero hits, and neither `go.mod` nor `go.sum` contains a Redis module. The cache layer is entirely **in-process and in-memory**.

**Actual mechanism.**

- **Implementation**: `store/cache/cache.go` — a thread-safe in-memory cache built on `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-72`), behind the `cache.Interface` abstraction (`cache.go:10-32`). Entries are `item{value, expiration, size}` (`cache.go:35-39`). A background goroutine started by `cache.New` (`cache.go:75`) sweeps expired entries, and `Close` (`cache.go:187`) stops it. Nothing is shared across processes — a multi-instance deployment gets independent caches.
- **Configuration site**: `store.New` — `store/store.go:38-61`. One `cache.Config` literal (`store/store.go:40-45`) is built inline and reused for all three caches created at `store/store.go:51-53`:

  ```go
  DefaultTTL:      10 * time.Minute
  CleanupInterval: 5 * time.Minute
  MaxItems:        1000
  OnEviction:      nil
  ```

  These values are hard-coded; no flag, env var, or profile field tunes them. `cache.DefaultConfig()` (`store/cache/cache.go:56-63`) declares the identical values but is not what the store uses.

**TTL for user entries: 10 minutes**, with the caveats that (a) it is a per-entry expiry set at write time — `Set` delegates to `SetWithTTL(..., c.config.DefaultTTL)` (`cache.go:94`) — and (b) the 1000-item cap is shared, so under load a user entry can be evicted well before 10 minutes.

The `userCache` (`store/store.go:28`) is written on user create/update/list/get (`store/user.go:98,122,132,143,167`) keyed by `userCacheKey(user.ID)`. Note it is only *read* on ID lookups: `Store.GetUser` consults the cache only when `find.ID != nil` (`store/user.go:149-156`), so a lookup by username — as the avatar endpoint does — always hits the database.
