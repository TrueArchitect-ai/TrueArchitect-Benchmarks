**Premise correction: there is no nightly database-cleanup job, and nothing is scheduled in the cron scheduler at all — the scheduler is never instantiated in production code, so it has no jobs and no run times.**

Evidence:

**1. The cron scheduler exists but is entirely unused outside its own package.** `internal/scheduler/` is a complete implementation — `ParseCronExpression` (`internal/scheduler/parser.go:30`), `Scheduler.Register` (`internal/scheduler/scheduler.go:68`), `Stop` (`:167`), plus middleware (`Recovery`, `Logging`, `Timeout`) and a README. But grepping the whole repo for `internal/scheduler` imports and `scheduler.` references outside the package yields **only test files** — `internal/scheduler/integration_test.go` and the other `*_test.go` files in that directory. No file under `cmd/`, `server/`, or `store/` imports it. `scheduler.New(...)` is never called in production, so `Register` is never reached and no cron expression is ever evaluated at runtime. The `"0 9 * * *"` (9 AM) expression you might find is test data at `internal/scheduler/integration_test.go:183`, not a registered job.

**2. There is no database-cleanup job of any kind, cron-driven or otherwise.** Searching for `cleanup` / `vacuum` / `prune` / `purge` across `server/`, `store/`, and `cmd/` turns up only:
- in-request, transactional deletes — e.g. attachment storage cleanup during user deletion (`server/router/api/v1/user_service.go:421-450`, `store/attachment.go:171`), and memo relation/attachment cleanup on memo delete (`server/router/api/v1/memo_service.go:579`);
- the in-memory cache sweeper, `CleanupInterval: 5 * time.Minute` (`store/store.go:42`), which evicts expired cache entries in RAM and never touches the database.

**3. The only actual background schedule in the server is unrelated to cleanup.** `startBackgroundRunners` (`server/server.go:153-174`) launches exactly one runner: the S3 presign refresher, on a plain `time.Ticker` at a 12-hour interval (`server/runner/s3presign/runner.go:27`, `:29-41`), not a cron expression and not at a fixed wall-clock time — its phase depends on process start time. The only other runner in the tree, `memopayload`, is never constructed.

So if you need periodic DB maintenance, nothing exists to reconfigure: you'd wire `internal/scheduler` into `startBackgroundRunners` (its first production use) or add a ticker alongside the s3presign runner.
