The browser hits a plain REST route (not gRPC/Connect), and the avatar turns out to live in a column on the `user` row, not in blob storage.


Notes on the hops:

- **How the browser learns the URL.** `convertUserFromStore` rewrites the outgoing `avatar_url` field: if the stored value parses as a base64 data URI, the API returns `/file/{user.Name}/avatar` instead of inlining the image (`server/router/api/v1/user_service_converters.go:32-38`). Since `Name` is `users/{username}`, the emitted path matches the route at `fileserver.go:124`. If the stored value is an ordinary URL, it's passed through untouched and no server hop happens at all.
- **Route wiring.** `RegisterRoutes` (`server/router/fileserver/fileserver.go:121-125`) is called from `server/server.go:82`, on the service built at `server/server.go:81`.
- **Access gate.** Only when `!s.Profile.AllowAnonymous()` does the handler require a viewer, via `getCurrentUser` → `authenticator.AuthenticateToUser` (`fileserver.go:173-181`, `:708-712`). On a public instance, another user's avatar is served unauthenticated. Note this checks only *that* a viewer exists — there's no per-target authorization, so any authenticated user may fetch any other user's avatar.
- **Lookup key.** `getUserByUsername` searches strictly by `Username` (`fileserver.go:716`); the `:identifier` param is not accepted as a numeric ID.
- **Cache behaviour.** `Store.GetUser` consults `userCache` only when `find.ID != nil` (`store/user.go:149-156`). This path passes `Username`, so it always falls through to `ListUsers`, which hits the DB and then populates the cache by ID (`store/user.go:137-144`).
- **Data layer.** The SQLite driver selects `avatar_url` among the user columns with `username = ?` (`store/db/sqlite/user.go:88`, query at `:150-170`). The equivalent implementations are `store/db/postgres/user.go:87` and `store/db/mysql/user.go:84`.
- **Response.** Back in the handler, the stored `AvatarURL` data URI is decoded by `parseDataURI` (`fileserver.go:196`, defined `:737`), the MIME type is checked against `avatarAllowedTypes` (`fileserver.go:201`, list at `:75`), security headers and `Cache-Control` are set, and the bytes go out via `c.Blob` (`fileserver.go:205-209`).
