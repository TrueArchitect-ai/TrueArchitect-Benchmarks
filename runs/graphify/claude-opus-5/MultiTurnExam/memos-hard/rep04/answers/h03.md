**`internal/idp` (abstraction) — `internal/idp/oauth2` (implementation, OAuth2 / OAuth2-style OIDC).**

Details:

- **Abstraction — `internal/idp/idp.go`.** The package is deliberately thin: it defines only the provider-neutral result type `IdentityProviderUserInfo` with `Identifier`, `DisplayName`, `Email`, `AvatarURL` (`internal/idp/idp.go:3-8`). Note there is no Go `interface` here — the abstraction is the shared user-info struct plus the `IdentityProvider_Type` enum in the schema, not a polymorphic contract. Callers switch on the enum rather than dispatching through an interface.

- **Implementation — `internal/idp/oauth2/oauth2.go`.** The one concrete protocol that ships. `NewIdentityProvider` validates the required config fields (`clientId`, `clientSecret`, `tokenUrl`, `userInfoUrl`, `fieldMapping.identifier`) at `internal/idp/oauth2/oauth2.go:27-43`. `ExchangeToken` (`:47`) does the authorization-code exchange via `golang.org/x/oauth2`, passing `code_verifier` for PKCE when supplied (`:64-66`). `UserInfo` (`:83`) GETs the userinfo endpoint with a Bearer token and a 10s timeout, then maps raw claims onto `idp.IdentityProviderUserInfo` using the admin-configured `FieldMapping` (`:114-140`), requiring the identifier claim to be non-empty and falling back to identifier for display name.

- **Where it's dispatched.** `resolveSSOIdentity` in `server/router/api/v1/auth_service_sso.go:104` looks up the stored provider and branches on `identityProvider.Type == storepb.IdentityProvider_OAUTH2` (`:120-134`) — that `if` is the only branch, so any other type would fall through with a nil `userInfo`. It then applies the optional `IdentifierFilter` regex (`:136-145`) before `resolveSSOUser` (`:19`) links or provisions the account.

- **Schema.** `IdentityProvider.Type` has exactly one non-default value, `OAUTH2 = 1`, in both `proto/store/idp.proto:13` and `proto/api/v1/idp_service.proto:79` — confirming OAuth2 is the only supported protocol. OIDC providers are supported only insofar as they work through the generic OAuth2 + userinfo flow; there's no dedicated OIDC discovery or ID-token verification implementation.
