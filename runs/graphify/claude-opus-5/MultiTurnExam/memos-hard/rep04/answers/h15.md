Visibility is enforced in three structurally different ways — **per-memo gate checks**, **query-level filtering** (`VisibilityList` on `FindMemo`), and **fan-out/delivery filters**. Every distinct site:

**Per-memo gate checks (API v1, Connect/gRPC)**
```
checkMemoReadAccess (GetMemo / GetMemoByUid / parent-memo check) — server/router/api/v1/memo_service.go:39 (checks at :55-65; callers :356, :367, and server/router/api/v1/memo_service_comments.go:148)
CreateMemoComment — parent-memo gate                             — server/router/api/v1/memo_service_comments.go:41
ListMemoReactions — memo gate                                     — server/router/api/v1/reaction_service.go:30-38
UpsertMemoReaction / DeleteMemoReaction — memo gate               — server/router/api/v1/reaction_service.go:83
ListMemoAttachments — memo gate                                   — server/router/api/v1/memo_attachment_service.go:214-222
checkAttachmentAccess (GetAttachment) — via owning memo           — server/router/api/v1/attachment_service.go:422 (checks at :445-451; caller :256)
```

**Query-level filtering (visibility pinned in the DB query)**
```
ListMemos — VisibilityList = {Public} or {Public, Protected}      — server/router/api/v1/memo_service.go:219-225
ListAllUserStats                                                  — server/router/api/v1/user_service_stats.go:84-90
GetUserStats                                                      — server/router/api/v1/user_service_stats.go:218-220
GetExploreRSS — {Public} only                                     — server/router/rss/rss.go:90
GetUserRSS — {Public} only                                        — server/router/rss/rss.go:141
getSitemapXML (SSR frontend) — {Public} only                      — server/router/frontend/frontend.go:150
```

**Static file surface (separate authenticator, not the gRPC stack)**
```
checkAttachmentPermission — server/router/fileserver/fileserver.go:650 (visibility checks at :677 and :699)
```

**Delivery / fan-out filters (visibility decides who receives, not who may request)**
```
SSEClient.canReceive — per-subscriber event filter                — server/router/api/v1/sse_hub.go:135-141
canViewerAccessMemo — notification recipient filter               — server/router/api/v1/user_service_notifications.go:309-312
canViewerAccessMemo — email recipient filter                      — server/notification/email.go:313-316
canUserAccessMentionContext — mention-notification filter         — server/router/api/v1/memo_mention_helpers.go:62-84
```

Notes on the interesting ones:

- **The fileserver path is the only one with a bypass.** `checkAttachmentPermission` accepts a `share_token` query parameter: a valid, non-expired `MemoShare` whose `MemoID` matches grants access to a private or protected memo's attachments (`server/router/fileserver/fileserver.go:682-688`). It also gates public content on `Profile.AllowAnonymous()` (`:677`), so a private instance still requires a session or share token even for `PUBLIC` memos.
- **`Protected` is enforced implicitly in the gate checks.** `checkMemoReadAccess` (`server/router/api/v1/memo_service.go:55-65`) rejects anonymous callers for anything non-public, then denies only `Private` to non-owners — so `Protected` means "any authenticated user." Note it does *not* grant admins access to others' private memos, unlike the attachment paths, which add `!isSuperUser(user)` / `user.Role != store.RoleAdmin` escapes (`attachment_service.go:451`, `memo_attachment_service.go:222`, `fileserver.go:699`).
- **`canViewerAccessMemo` is duplicated** with identical logic in two packages (`user_service_notifications.go:309` and `notification/email.go:313`) — two separate declarations, hence two sites.
- The MCP router (`server/router/mcp/`) contains no visibility logic of its own; it goes through the API v1 services.
