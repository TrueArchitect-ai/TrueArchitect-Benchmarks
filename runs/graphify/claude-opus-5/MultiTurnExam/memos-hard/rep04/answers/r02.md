**Premise correction: this codebase has no rate-limiting middleware — per-user or otherwise. There is nothing registered, and no request limits exist.**

Evidence:

- Searching all Go sources, `go.mod`, and config files for `rate limit` / `ratelimit` / `throttle` / `golang.org/x/time/rate` returns zero hits. No rate-limiter dependency is present in `go.mod`.
- The Echo middleware stack is exactly two entries: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/server.go:51-52`). Echo v5 ships a `middleware.RateLimiter`, but it is not used.
- The Connect/gRPC interceptor chain is four entries — metadata, logging, recovery, auth (`server/router/api/v1/v1.go:133-138`). No limiter among them.
- The only "rate limit" strings in the repo are aspirational documentation for email sending, not implemented code: `internal/email/README.md:286` ("### 5. Implement Rate Limiting", with a sample snippet) and `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"). Both describe what a caller *could* add.

**What does exist — concurrency caps, not rate limits.** These bound simultaneous in-flight work globally across the process; they don't track requests-per-user or requests-per-time-window, and they impose no per-identity quota:

- `imageProcessingSemaphore` — `semaphore.NewWeighted(2)` (`server/router/api/v1/v1.go:60`), acquired for EXIF stripping (`server/router/api/v1/attachment_service_image.go:68-75`). Exhaustion surfaces as `codes.ResourceExhausted` "too many image processing requests" (`server/router/api/v1/attachment_service.go:160`), which is the closest thing to a 429 in the codebase.
- `thumbnailSemaphore` — `semaphore.NewWeighted(3)` on `APIV1Service` (`server/router/api/v1/v1.go:59`) and a separate one on the file server sized by `maxConcurrentThumbnails` (`server/router/fileserver/fileserver.go:107`, `:116`, acquired at `:448`).
- Request body size is capped via `connect.WithReadMaxBytes(maxAPIRequestBytes)` (`server/router/api/v1/v1.go:141`) — a size limit, not a rate limit.
- The webhook dispatcher has a bounded 128-slot queue and 4 workers (`internal/webhook/webhook.go:39`, `:42-55`), which throttles *outbound* deliveries by dropping overflow.

So if you're looking to add per-user API throttling, there is no existing hook to extend — it would be new middleware in `server/server.go` (for the REST/file surfaces) plus a new interceptor in the chain at `server/router/api/v1/v1.go:133`.
