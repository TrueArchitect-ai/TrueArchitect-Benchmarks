h05.

**Explicit Go code** — inside the delete-user transaction, in each of the three DB drivers. There is no database-level cascade for reactions.

What I checked:

**1. The delete path — explicit `DELETE FROM reaction` statements.** `deleteUserTargetsTx` issues *two* separate reaction deletes, in the same transaction as the rest of the user teardown:

- `deleteReactionsByContentIDsTx` — removes reactions *by anyone* on the deleted user's memos (matched on `content_id`, i.e. memo UID), batched via an `IN` clause: `store/db/sqlite/user_delete.go:380-388`, `store/db/postgres/user_delete.go:380`, `store/db/mysql/user_delete.go:417`.
- `deleteReactionsByCreatorTx` — removes the user's *own* reactions wherever they were left, including on other people's memos: `store/db/sqlite/user_delete.go:400-403`, `store/db/postgres/user_delete.go:400`, `store/db/mysql/user_delete.go:437`.

Both are called from `deleteUserTargetsTx` at `store/db/sqlite/user_delete.go:96` and `:102` (identical line numbers in the postgres and mysql variants). The content-ID set comes from a recursive CTE that walks the user's memos *and* their comment subtree (`store/db/sqlite/user_delete.go:133-147`), so reactions on comments are covered too. Everything runs before `tx.Commit()` at `store/db/sqlite/user_delete.go:51`.

**2. The schema — no foreign key, so no cascade is possible.** The `reaction` table declares `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` as plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `REFERENCES`, no `ON DELETE`: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (original creation: `store/migration/sqlite/0.20/00__reaction.sql:2-9`, `store/migration/postgres/0.20/00__reaction.sql:2-9`). Grepping `REFERENCES|ON DELETE` across all three `LATEST.sql` files returns exactly one hit each — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109` and peers). Reactions are not in that set.

**3. Tests confirm the intended semantics.** `server/router/api/v1/test/user_service_delete_test.go` seeds reactions on the user's own memo, on their comment under a foreign memo, and a third-party reaction on an unrelated foreign memo (`:188-210`), then asserts the first two sets are empty after deletion while the unrelated one survives (`:287-298`). A rollback case verifies the reaction is still present when the transaction aborts at the failpoint (`:366-431`), which also demonstrates the deletes are transactional rather than incidental.
