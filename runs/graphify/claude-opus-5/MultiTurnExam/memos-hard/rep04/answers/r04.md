**Premise correction: neither. There is no message broker in this codebase — no NATS, no RabbitMQ/AMQP, no Kafka, no SQS. There is no queue declaration because there is no external queue.** `go.mod` contains zero broker clients (the direct dependency list is Connect/gRPC, AWS S3, DB drivers, Echo, goldmark, CEL, OpenAI/genai, MCP, testcontainers, and friends), and a case-insensitive search across all Go sources, `go.mod`/`go.sum`, YAML, and Dockerfiles returns no broker references — the single `go.sum` hit is a coincidental substring inside a base64 module hash for `cespare/xxhash`.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool, entirely inside `internal/webhook/webhook.go`.**

- **The "queue" is a package-level channel**, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, holding pointers to in-memory payload structs. It lives in the server process's heap — nothing is persisted, replicated, or acknowledged.

- **The workers are four goroutines started in `init()`** (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post`, logging a warning on failure. Because they're launched from `init()`, they start when the package is first loaded rather than from any explicit server-startup wiring.

- **Producers use a non-blocking send** — `PostAsync` (`internal/webhook/webhook.go:184-196`) does a `select` with a `default` branch, so when the buffer is full the payload is **dropped** with a `slog.Warn`, never retried or persisted. Nil payloads are dropped too (`:185-188`).

- **Delivery itself** happens in `Post` (`internal/webhook/webhook.go:120`), via the shared SSRF-guarded `safeClient.Do(req)` at `:152`, with a 30s timeout (`:27`).

Operational consequences worth knowing, given the premise assumed durable messaging: there is no persistence, no retry, no dead-letter path, and no at-least-once guarantee. A process restart loses every queued webhook, a burst beyond 128 in-flight items silently discards the overflow, and a single failed POST is logged and forgotten — `Post`'s error return is only consumed by the warning log at `internal/webhook/webhook.go:47-51`. Delivery concurrency is capped at 4 regardless of how many webhooks are configured.
