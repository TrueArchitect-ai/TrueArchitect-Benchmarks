h05. Mechanism: explicit Go application code (not a DB-level cascade/trigger) — the `reaction` table has no foreign key at all.

Evidence:
- `store/db/sqlite/user_delete.go:92-127` (`deleteUserTargetsTx`, mirrored in `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go`) explicitly calls `deleteReactionsByContentIDsTx` (line 96, removes reactions on memos the deleted user owned) and `deleteReactionsByCreatorTx` (line 102, removes reactions the user authored), both running `DELETE FROM reaction ...` inside the same transaction as the rest of the user-deletion cascade, before `deleteUserRowTx` (line 123) finally deletes the `user` row.
- `store/migration/{sqlite,mysql,postgres}/LATEST.sql` (`reaction` table, ~lines 91-99): `creator_id` is a plain `INTEGER/INT NOT NULL` column with no `FOREIGN KEY` clause and no `ON DELETE CASCADE` — unlike e.g. `memo_share`, which does declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`. This has been true since the table's origin (`store/migration/sqlite/0.20/00__reaction.sql`).
- No triggers reference `reaction` or user deletion anywhere in `store/migration/**`; the only triggers that ever existed (for `updated_ts` maintenance on other tables) were removed in `store/migration/sqlite/0.7/01__remove_triggers.sql`.
- Covered by tests: `store/test/user_delete_test.go` (`TestDeleteUserCleansRelatedData`) and `server/router/api/v1/test/user_service_delete_test.go`.
