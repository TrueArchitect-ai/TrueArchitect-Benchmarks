**Mechanism:** Explicit Go code (application-level transaction), not a database-level cascade rule. The `reaction` table has no foreign key constraints at all in any backend, so nothing happens automatically at the DB layer — user deletion relies entirely on explicit `DELETE FROM reaction` statements executed before the `user` row is removed, all inside one transaction.

**Evidence locations:**

- User deletion entry point: `server/router/api/v1/user_service.go:393` (`DeleteUser`) → `store/user.go:171` (`Store.DeleteUser`) → per-backend drivers:
  - `store/db/sqlite/user_delete.go`
  - `store/db/mysql/user_delete.go`
  - `store/db/postgres/user_delete.go`

- Explicit reaction cleanup inside the same DB transaction as the user delete (`deleteUserTargetsTx`, e.g. `store/db/sqlite/user_delete.go:92-104`, identical logic in the mysql/postgres equivalents):
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — deletes `DELETE FROM reaction WHERE content_id IN (...)` for reactions **on** memos owned by the deleted user (sqlite `user_delete.go:380`).
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` — deletes `DELETE FROM reaction WHERE creator_id = ?` for reactions the deleted user **made** on others' content (sqlite `user_delete.go:400`).
  - Both run before `deleteUserRowTx` (final `DELETE FROM user`), and the whole thing is wrapped in one `tx.BeginTx` (line 30), so a failure anywhere rolls the reaction deletes back too.

- Reaction schema — no FK/cascade exists: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`. The `reaction` table's `creator_id` is a plain integer column with `UNIQUE(creator_id, content_id, reaction_type)` but **no `FOREIGN KEY`/`REFERENCES`/`ON DELETE`** clause tying it to `user`. Same in the original `store/migration/{sqlite,mysql,postgres}/0.20/00__reaction.sql` migration that created the table.

- Tests confirming this is intentional application behavior: `store/test/user_delete_test.go` (`TestDeleteUserCleansRelatedData`) and `server/router/api/v1/test/user_service_delete_test.go` (`TestDeleteUserSelfDeleteRemovesOwnedResourcesAndMemoSubtrees`, `TestDeleteUserRollbackPreservesAllResources`).

Since there's no DB-level constraint, if this Go cleanup code were ever removed, reactions would be silently orphaned rather than blocked or auto-cascaded by the database.
