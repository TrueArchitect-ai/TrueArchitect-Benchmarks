**Enforcement sites for "who may view a memo" (usememos/memos server):**

- Single-memo fetch (`GetMemo`) — shared helper `checkMemoReadAccess`, `server/router/api/v1/memo_service.go:39-68` (invoked at `memo_service.go:356`)
- Memo listing/search (`ListMemos`) — inline visibility filter built into the store query rather than a post-fetch check, `server/router/api/v1/memo_service.go:218-227`
- Comment listing on a memo (`ListMemoComments`) — reuses `checkMemoReadAccess`, `server/router/api/v1/memo_service_comments.go:148-149`; comment creation has its own inline check, `server/router/api/v1/memo_service_comments.go:33-43`
- Reactions (`ListReactions`/`CreateReaction`) — separate inline visibility check, `server/router/api/v1/reaction_service.go:30-38,83`
- Attachments — two separate inline checks: `server/router/api/v1/memo_attachment_service.go:214-222` and `server/router/api/v1/attachment_service.go:445-451`
- Mention notifications — `server/router/api/v1/memo_mention_helpers.go:62-84` and `server/router/api/v1/user_service_notifications.go:309-312`
- User memo stats/heatmap — visibility-list filtering, `server/router/api/v1/user_service_stats.go:84-90,218-220`
- Real-time SSE event delivery — `SSEClient.canReceive`, `server/router/api/v1/sse_hub.go:134-144`

Notably, `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:153-192`) is a deliberate bypass, not an enforcement site — it grants read access via an opaque share token independent of the memo's `Visibility`.
