Memo visibility ("who may view a memo") is enforced independently in the following distinct server-side locations — the codebase has one shared helper plus at least a dozen places that reimplement or apply the same PUBLIC/PROTECTED/PRIVATE rules inline:

- checkMemoReadAccess (shared helper, used by GetMemo and ListMemoComments) — server/router/api/v1/memo_service.go
- ListMemos query-time visibility filter injection — server/router/api/v1/memo_service.go
- ListMemoReactions inline visibility check — server/router/api/v1/reaction_service.go
- ListMemoAttachments inline visibility check — server/router/api/v1/memo_attachment_service.go
- checkAttachmentAccess (gRPC AttachmentService download) — server/router/api/v1/attachment_service.go
- checkAttachmentPermission (HTTP `/file/...` resource server, plus share-token bypass) — server/router/fileserver/fileserver.go
- ListMemoRelations visibility filter — server/router/api/v1/memo_relation_service.go
- GetExploreRSS / GetUserRSS (RSS feeds, hard-coded to PUBLIC only) — server/router/rss/rss.go
- getSitemapXML (sitemap.xml, hard-coded to PUBLIC only) — server/router/frontend/frontend.go
- User stats/heatmap visibility filter (two spots) — server/router/api/v1/user_service_stats.go
- SSEClient.canReceive (live-update broadcast filtering) — server/router/api/v1/sse_hub.go
- canViewerAccessMemo (notification content redaction) — server/router/api/v1/user_service_notifications.go
- Email notification visibility redaction — server/notification/email.go

Notable related fact: GetMemoByShare (server/router/api/v1/memo_share_service.go) deliberately bypasses visibility entirely in favor of a valid share token — an alternate-authorization path rather than an enforcement site.
