No such middleware exists in this codebase — the premise is incorrect.

I searched the entire repo (this is the "memos" Go/TS project) for rate-limiting logic (`rateLimit`, `throttle`, `RateLimiter`, `x/time/rate`, `express-rate-limit`, etc.) and checked `go.mod`/`go.sum` and `web/package.json` for rate-limiting libraries. None exist.

What actually is registered as request middleware is the Connect-RPC interceptor chain in `server/router/api/v1/v1.go:133-141`:

```go
connectInterceptors := connect.WithInterceptors(
    NewMetadataInterceptor(),
    NewLoggingInterceptor(logStacktraces),
    NewRecoveryInterceptor(logStacktraces),
    NewAuthInterceptor(authorizer),
)
```

(implementations in `server/router/api/v1/connect_interceptors.go`) — these handle header/metadata propagation, logging, panic recovery, and auth, but none of them throttle request rate.

The only things in the repo that even mention "rate limit" are aspirational doc comments with no implementation:
- `internal/email/doc.go:86` — a comment suggesting SMTP sending "should" be rate-limited
- `server/router/api/v1/auth_service_session.go:277` — a comment about "suspicious login attempts"

The one real limit-like control that does exist is a request **body size** cap (not a rate limit): `maxAPIRequestBytes = 256 << 20` in `server/router/api/v1/v1.go:20`, enforced via `http.MaxBytesHandler`/`connect.WithReadMaxBytes`.

There's also no reverse-proxy config (e.g. nginx) in the repo that could impose rate limiting at the gateway level. So if per-user API rate limiting is needed, it isn't implemented anywhere currently — it would need to be added.
