Premise correction: there is no Redis connection in this repo — no Redis client, driver, or config appears anywhere (confirmed via `grep -ri redis` across all `.go` files and a filename search, both empty). The "cache layer" is a self-contained, in-process Go cache with no external dependency at all.

Actual mechanism: it's an in-memory cache built on `sync.Map`, defined in `store/cache/cache.go:67-90` (`Cache` struct, `New`/`NewDefault` constructors). It's instantiated in `store/store.go:38-53`, where `Store.New()` creates three separate cache instances — `instanceSettingCache`, `userCache`, and `userSettingCache` — all sharing one `cache.Config`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

User entries are cached under `userCache` (`store/store.go:28`), keyed by `userCacheKey(userID int32)` (`store/user.go:88`), and set via `s.userCache.Set(ctx, userCacheKey(user.ID), user)` at several points in `store/user.go` (lines 98, 122, 132, 143, 167). Since `Set` calls `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`), user entries get the same **10-minute TTL** as every other entry in that cache instance — there's no per-user or per-entry override; expired items are swept by a background goroutine (`cleanupLoop`) every 5 minutes (`CleanupInterval`), or lazily on `Get` if accessed after expiry.
