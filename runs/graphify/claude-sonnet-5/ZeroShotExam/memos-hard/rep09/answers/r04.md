**Premise correction:** Neither. The webhook delivery workers don't consume from an external message broker (no NATS, no RabbitMQ) — this repo (`usememos/memos`) has no such dependency anywhere in the codebase (`grep -ri "nats\|rabbitmq\|amqp"` across `.go`/`.ts`/`.js`/`.yaml`/`.json` turns up nothing relevant).

**Actual mechanism:** Webhook delivery uses an in-process buffered Go channel as the "queue," declared in `internal/webhook/webhook.go:37`:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

Four worker goroutines are spawned in that file's `init()` (`internal/webhook/webhook.go:40-51`), each ranging over `asyncPostQueue` and calling `Post()` to deliver the webhook via HTTP. Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:187-198`), which does a non-blocking send and drops (with a warning log) if the channel is full — there's no persistence or external broker involved, it's purely an in-memory bounded channel acting as a worker pool queue.
