Premise correction: There is no Redis anywhere in this repository (a `usememos/memos`-style Go app) — a repo-wide search for "redis" returns zero matches. The "cache layer" is not backed by an external Redis instance; it's an in-process, in-memory cache implemented from scratch in Go.

Actual mechanism:
- The cache implementation lives in `store/cache/cache.go` — a thread-safe in-memory cache (`sync.Map` + atomic counters) with per-item expiration, background cleanup goroutine, and max-item eviction. No network connection, no Redis client, no config for host/port/auth.
- It's wired up in `store/store.go:24-58`: the `Store` struct holds three separate `*cache.Cache` instances — `instanceSettingCache`, `userCache`, and `userSettingCache` — all constructed with the same `cacheConfig` in `store.New()`.
- That shared config (`store/store.go:40-45`) sets `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`.
- User entries are written via `s.userCache.Set(...)` (`store/user.go:98,122,132,143,167`), which uses the cache's `Set` method — and `Set` always applies `config.DefaultTTL` (see `store/cache/cache.go:92-95`), not a custom `SetWithTTL` call. So **user cache entries expire after 10 minutes**, the same default TTL as the other two caches.
