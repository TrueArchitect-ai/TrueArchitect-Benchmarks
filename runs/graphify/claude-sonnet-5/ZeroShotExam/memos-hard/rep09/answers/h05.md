Mechanism: explicit Go code (not a database-level rule — no FK/cascade exists on the reaction table).

Evidence:
- Schema: `reaction` table has `creator_id INTEGER NOT NULL` with no `FOREIGN KEY`/`ON DELETE CASCADE` clause — `store/migration/postgres/LATEST.sql:91-98` (identical in `store/migration/mysql/LATEST.sql:91-98` and `store/migration/sqlite/LATEST.sql:92-99`). The only `ON DELETE CASCADE` in the schema is unrelated (`memo_share.memo_id → memo(id)`, `store/migration/postgres/LATEST.sql:108`), so nothing at the DB level would clean up reactions on user deletion.
- User deletion: `store.Store.DeleteUser` (`store/user.go:171-181`) delegates to per-driver implementations that run in a transaction. Each driver's `deleteUserTargetsTx` explicitly deletes reactions in two calls:
  - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` for content owned by the deleted user (`store/db/postgres/user_delete.go:96-104`, `:380-388`)
  - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` for reactions the deleted user made on others' content (`store/db/postgres/user_delete.go:100-104`, `:400-403`)
  - Same pattern in `store/db/mysql/user_delete.go` and `store/db/sqlite/user_delete.go`, all inside the same transaction as the final `DELETE FROM "user"` (`store/db/postgres/user_delete.go:461-464`).

So reactions are cleaned up atomically via hand-written Go/SQL in the `DeleteUser` transaction, precisely because there is no DB-level constraint that would otherwise handle it.
