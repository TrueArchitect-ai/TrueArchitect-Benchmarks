h05.

**Mechanism: explicit Go code (application-level cleanup inside a transaction), not a database-level cascade rule.** The `reaction` table has no foreign key to `user` at all in any supported database.

**Evidence:**

- Deletion entry point: `server/router/api/v1/user_service.go:414-416` (`DeleteUser` handler) → `store/user.go:171-181` (`Store.DeleteUser`) → per-driver `DeleteUser`.
- Explicit reaction cleanup, verified in `store/db/sqlite/user_delete.go`:
  - `deleteUserTargetsTx` (lines 91-124) calls `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` (line 96) and `deleteReactionsByCreatorTx(ctx, tx, userID)` (line 102) — both run *before* `deleteUserRowTx` (line 122).
  - `deleteReactionsByContentIDsTx` (lines 379-386): `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions left on the deleted user's memos.
  - `deleteReactionsByCreatorTx` (lines 400-403): `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the deleted user made on others' memos.
  - The equivalent MySQL (`store/db/mysql/user_delete.go`) and Postgres (`store/db/postgres/user_delete.go`) drivers implement the identical pattern.
- Schema check, `store/migration/sqlite/LATEST.sql:92-99` (same in the Postgres/MySQL `LATEST.sql` equivalents):
  ```sql
  CREATE TABLE reaction (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    created_ts BIGINT NOT NULL DEFAULT (strftime('%s', 'now')),
    creator_id INTEGER NOT NULL,
    content_id TEXT NOT NULL,
    reaction_type TEXT NOT NULL,
    UNIQUE(creator_id, content_id, reaction_type)
  );
  ```
  `creator_id` is a plain `INTEGER` with no `REFERENCES user(id)` / `ON DELETE CASCADE` clause — confirmed no FK exists on this table. (By contrast, `attachment` and `memo_share` do use `FOREIGN KEY ... ON DELETE CASCADE`, showing this is a deliberate omission for `reaction`, not an oversight.)

So if the Go cleanup code path were ever skipped, reactions would be orphaned rather than cascade-deleted — the database provides no safety net here.
