**Tables affected when `DeleteMemo` runs** (`server/router/api/v1/memo_service.go:518` → `store/memo.go:140` → driver `DeleteMemo`):

- **`memo`** — the target memo row is deleted directly (`store/db/sqlite/memo.go:237`, and equivalent postgres/mysql `memo.go`). Additionally, before this, the handler deletes each comment memo (memos linked via `memo_relation` with type `Comment`) by recursively calling `store.DeleteMemo` on them (`server/router/api/v1/memo_service.go:567-577`), so `memo` rows for comments are removed too.
- **`memo_relation`** — explicitly deleted in application code for both directions (`memo_id` and `related_memo_id`) via `driver.DeleteMemoRelation` (`store/memo.go:142-147`).
- **`attachment`** — explicitly deleted in application code: attachments for the memo are listed, then each is removed via `s.DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`), which also deletes the attachment's storage blob/file.
- **`memo_share`** — not touched by Go code, but cascades at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`), so rows are removed automatically when the `memo` row is deleted.

Not affected: **`reaction`** — `DeleteMemo` only `ListReactions` (for the webhook payload) but never deletes reaction rows, and `reaction.content_id` has no FK/cascade to `memo`.
