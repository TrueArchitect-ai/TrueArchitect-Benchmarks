**Tables affected when `DeleteMemo` runs** (server/router/api/v1/memo_service.go:518 → store/memo.go:140):

- **`memo`** — the target memo row is deleted (`store/db/sqlite/memo.go:239`, equiv. in postgres/mysql `memo.go`). Additionally, before deleting the target memo, the handler first deletes any *comment* memos related to it by calling `store.DeleteMemo` recursively for each comment relation (`server/router/api/v1/memo_service.go:567-577`), so `memo` rows for comments are also deleted (with the same cascade below applied to each).
- **`memo_relation`** — all rows where the memo is either `memo_id` or `related_memo_id` are deleted explicitly (`store/memo.go:142-147`, via `driver.DeleteMemoRelation`).
- **`attachment`** — all attachments whose `memo_id` matches the memo are looked up and deleted one-by-one via `Store.DeleteAttachment` (`store/memo.go:149-157`, `store/attachment.go:132-149`), which also removes the underlying attachment storage (local/S3 file), though that isn't a DB table.
- **`memo_share`** — not touched by any Go code, but has a DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three backends (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`), so these rows are cascade-deleted automatically by the database when the `memo` row is removed.

Note: `reaction` rows (matched by `content_id`) are only **read** (`ListReactions`, memo_service.go:545-550) for the webhook payload — they are not deleted by `DeleteMemo`, and the schema has no FK/cascade tying `reaction.content_id` to `memo`, so reaction rows are left orphaned (not "affected" in the delete sense).
