Based on reading the actual store and schema code (not just the graph query, which was too noisy to answer this precisely), here's the full picture:

**`store/memo.go:140` `(s *Store) DeleteMemo`** explicitly touches:
- **`memo`** — the row itself is deleted (`store/db/{postgres,mysql,sqlite}/memo.go`, `DELETE FROM memo WHERE id = ...`)
- **`memo_relation`** — explicitly cleaned up first, in both directions (`memo_id` and `related_memo_id`), via `DeleteMemoRelation` (`store/memo.go:142-147`)
- **`attachment`** — explicitly listed then deleted one-by-one via `DeleteAttachment` (`store/memo.go:149-157`, `store/attachment.go:132`)

**DB-level cascade (schema, not Go code):**
- **`memo_share`** — has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, mirrored in the mysql/sqlite `LATEST.sql`), so rows there are removed automatically when the `memo` row is deleted.

**Caller-level cascade at the API layer**, `server/router/api/v1/memo_service.go:518` `DeleteMemo` (the gRPC handler), before calling `store.DeleteMemo`:
- It first finds child comment memos (`memo_relation` rows of type `MemoRelationComment` where `related_memo_id` = this memo) and recursively calls `s.Store.DeleteMemo` on each comment's memo ID — so those comment rows in **`memo`** (and transitively their own **`memo_relation`**/**`attachment`**/**`memo_share`** rows) are also deleted.

**Notably not deleted:** `reaction` rows are looked up (`ListReactions` by `content_id`) only to build the webhook payload — they are never deleted, and `reaction.content_id` is a plain TEXT column with no FK/cascade, so reactions on a deleted memo become orphaned.

**Answer (table list):** `memo`, `memo_relation`, `attachment`, `memo_share` (the last via DB `ON DELETE CASCADE`, not Go code).
