Tables affected when `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518` → `store.Store.DeleteMemo` in `store/memo.go:140`):

- **`memo`** — the target memo row is deleted directly (`store/db/sqlite/memo.go:237`, equivalent in `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`). Comment-type child memos (rows in `memo_relation` with `type=COMMENT`) are also recursively deleted via `s.Store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`), so each comment's own row is removed from `memo` too.
- **`memo_relation`** — explicitly cleaned in `store/memo.go:142-147` for rows where the memo is either `memo_id` or `related_memo_id`.
- **`attachment`** — explicitly cleaned in `store/memo.go:148-157`, which lists attachments for the memo and calls `DeleteAttachment` for each (also deletes the underlying file via `DeleteAttachmentStorage`, `store/attachment.go:132-148`).
- **`memo_share`** — not touched by app code, but removed via a DB-level `ON DELETE CASCADE` foreign key on `memo_share.memo_id → memo.id` (`store/migration/sqlite/LATEST.sql:105-109`, and identical constraints in `store/migration/postgres/LATEST.sql` and `store/migration/mysql/LATEST.sql`).

Note: `reaction` rows (keyed by `content_id`, not a real FK) are read via `ListReactions` for the deleted-webhook payload (`memo_service.go:545-550`) but are **not** deleted by this code path, so they are not cascaded.
