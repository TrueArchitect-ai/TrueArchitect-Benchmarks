q29. Frontend requests are authenticated via a Connect-RPC interceptor: `authInterceptor` in `web/src/connect.ts:156` (attached to the transport at `web/src/connect.ts:184-189`). It reads/writes tokens through `web/src/auth-state.ts`, manages a short-lived **JWT access token** (stored in-memory + `localStorage` under `memos_access_token`, synced across tabs via `BroadcastChannel`, auto-refreshed on 401 via `refreshAccessToken()`/`web/src/connect.ts:89`, which calls the `AuthService.refreshToken` RPC using an httpOnly **refresh-token cookie** sent with `credentials: "include"`). Separately, the UI also supports long-lived **Personal Access Tokens (PATs)** (see `web/src/components/CreateAccessTokenDialog.tsx`, `AccessTokenSection.tsx`), which users attach manually as Bearer tokens for API access rather than through this interceptor's refresh flow.

On the backend, `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:208`) wraps every unary Connect call, extracts the `Authorization` header, and delegates to the shared `Authorizer` (`server/router/api/v1/authz.go:26`), which wraps `auth.Authenticator`. The actual token validation package is **`server/auth`** (`server/auth/authenticator.go`): `AuthenticateByAccessTokenV2` validates the JWT access token (`ParseAccessTokenV2`), and `AuthenticateByPAT` validates Personal Access Tokens by hashing and looking them up via the store (`GetUserByPATHash`).
