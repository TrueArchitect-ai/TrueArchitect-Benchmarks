Before deleting the memo row itself, the store layer (`store/memo.go:140-159`, `Store.DeleteMemo`) deletes:

1. **Memo relation records** where the memo is the source (`DeleteMemoRelation{MemoID: &delete.ID}`) — store/memo.go:142
2. **Memo relation records** where the memo is the target/related memo (`DeleteMemoRelation{RelatedMemoID: &delete.ID}`) — store/memo.go:145
3. **Attachment records** linked to the memo, deleted one by one via `DeleteAttachment` after listing them with `ListAttachments` — store/memo.go:148-157

Only after these are cleaned up does it call `s.driver.DeleteMemo(ctx, delete)` to remove the memo row itself (store/memo.go:158), which in the DB drivers (e.g. `store/db/sqlite/memo.go:237-248`) is a plain `DELETE FROM memo WHERE id = ?` with no further cascading.

Note: at the API layer (`server/router/api/v1/memo_service.go:567-582`), `DeleteMemo` also recursively deletes comment memos (via `store.DeleteMemo` again, which repeats the same relation/attachment cleanup for each comment) before deleting the parent memo, but that recursion happens in the service layer, not inside the store's `DeleteMemo` itself.
