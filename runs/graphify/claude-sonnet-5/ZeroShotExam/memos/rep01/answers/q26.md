**Tables affected when `DeleteMemo` runs** (`server/router/api/v1/memo_service.go:518-593` → `store/memo.go:140-159` → `store/db/{sqlite,mysql,postgres}/memo.go`):

1. **`memo`** — the target memo row is deleted directly (`driver.DeleteMemo`, e.g. `store/db/sqlite/memo.go:237`). Additionally, before deleting the target memo, `DeleteMemo` in the router first finds all child "comment" relations (`memo_relation` where `type = COMMENT`) and recursively calls `s.Store.DeleteMemo` on each comment memo (`server/router/api/v1/memo_service.go:567-577`), deleting those `memo` rows too (and cascading the same cleanup for each).
2. **`memo_relation`** — explicitly cleaned in `store.Store.DeleteMemo` (`store/memo.go:142-147`), which deletes rows where the memo is either `memo_id` or `related_memo_id`.
3. **`attachment`** — explicitly cleaned in `store.Store.DeleteMemo` (`store/memo.go:148-157`), which lists attachments for the memo and calls `s.DeleteAttachment` for each (also deletes the underlying blob/file storage, not a DB table).
4. **`memo_share`** — not touched by Go code, but cascaded automatically at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, present identically in `store/migration/postgres/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`, and `store/migration/mysql/LATEST.sql:108`.

Note: `reaction` rows referencing the memo (via the string `content_id`) are only *listed* (for webhook payload construction, `memo_service.go:545-550`) but are **never deleted** — they are not a schema-level FK (`content_id` is a plain `TEXT` column), so they become orphaned rather than cascaded.
