**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted directly (`store/db/{sqlite,postgres,mysql}/memo.go: DeleteMemo`). Additionally, any memo-comments (rows related via `memo_relation` with `type = COMMENT`) are recursively deleted the same way, in a loop in `server/router/api/v1/memo_service.go:567-577`.
- **`memo_relation`** — explicitly cleaned up in `store/memo.go:142-147` (`Store.DeleteMemo`), which issues two deletes: one where the memo is the source (`memo_id`) and one where it's the target (`related_memo_id`).
- **`attachment`** — explicitly cleaned up in `store/memo.go:148-157`: attachments are listed by `memo_id` and each is deleted individually via `Store.DeleteAttachment` (which also removes the underlying blob/file storage, but that's not a DB table).
- **`memo_share`** — not touched by explicit Go code, but the schema defines `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` for postgres and mysql (`store/migration/postgres/LATEST.sql:101-109`, `store/migration/mysql/LATEST.sql:101-109`), so rows cascade-delete at the DB level on those backends. Note: the SQLite driver opens its connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so this cascade is **not** enforced on SQLite despite the same `ON DELETE CASCADE` clause being present in `store/migration/sqlite/LATEST.sql:109` — meaning `memo_share` rows can be left orphaned on SQLite.

**Not affected (notable omission):** `reaction` rows tied to the memo (via `content_id`) are looked up in `server/router/api/v1/memo_service.go:545-550` only to build the webhook payload — they are never deleted, and the `reaction` table has no FK to `memo`, so those rows are orphaned after deletion.
