q26. When `Store.DeleteMemo` runs (store/memo.go:140-159), the tables touched are:

- **memo** — the row itself is deleted
- **memo_relation** — explicitly deleted in code, both where the memo is the source (`memo_id`) and where it's the target (`related_memo_id`)
- **attachment** — explicitly deleted (attachments linked via `memo_id` are looked up then removed one by one)
- **memo_share** — deleted implicitly via `ON DELETE CASCADE` foreign key on `memo_share.memo_id` referencing `memo(id)` (see e.g. `store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`)

Additionally, at the API layer (`server/router/api/v1/memo_service.go` `APIV1Service.DeleteMemo`), comment memos (child memos linked by a `memo_relation` of type comment) are deleted recursively before the parent, which touches the same set of tables again for each comment.

Note: `reaction` rows (keyed by `content_id`, not a foreign key to `memo.id`) are **not** cleaned up by any cascade or explicit code in `DeleteMemo`.
