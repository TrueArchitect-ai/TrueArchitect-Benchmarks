By **explicit Go code**; reactions are removed via two separate deletion functions within the user-delete transaction in each database driver:

1. **`deleteReactionsByContentIDsTx`** — deletes reactions whose `content_id` matches any of the user's memos (e.g., `store/db/sqlite/user_delete.go:380–388`, `store/db/mysql/user_delete.go:417–425`, `store/db/postgres/user_delete.go:380–388`). This removes reactions that other users placed on the deleted user's memos.

2. **`deleteReactionsByCreatorTx`** — deletes reactions where `creator_id` matches the deleted user (e.g., `store/db/sqlite/user_delete.go:400–403`, `store/db/mysql/user_delete.go:437–440`, `store/db/postgres/user_delete.go:400–403`). This removes reactions the deleted user placed on others' memos.

Both are called from `deleteUserTargetsTx` (lines 96 and 102 in each driver's `user_delete.go`) inside the same transaction that removes the user row. There are no `ON DELETE CASCADE` or other database-level foreign key rules handling this — the `reaction` table schema does not define such constraints, and the cleanup is done entirely in application code.
