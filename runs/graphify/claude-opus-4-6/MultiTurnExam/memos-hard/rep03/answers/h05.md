**Mechanism:** Explicit Go code — two separate deletion steps within the same transaction.

**Evidence:**

In all three database drivers (`store/db/sqlite/user_delete.go`, `store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`), the `deleteUserTargetsTx` function (line 92 in each) explicitly deletes reactions in two ways:

1. **`deleteReactionsByContentIDsTx`** (e.g., `store/db/sqlite/user_delete.go:96`) — deletes all reactions whose `content_id` matches the user's memos (`DELETE FROM reaction WHERE content_id IN ...`), removing reactions *on* the deleted user's content.

2. **`deleteReactionsByCreatorTx`** (e.g., `store/db/sqlite/user_delete.go:102`) — deletes all reactions where `creator_id` matches the deleted user (`DELETE FROM reaction WHERE creator_id = ?`), removing reactions *by* the deleted user on other people's content.

Both run inside the same transaction as all other user-deletion cleanup (attachments, memos, inbox, settings, identities, memo relations, memo shares, and finally the user row itself). There are no database-level foreign key cascades handling this — it is all done via explicit `DELETE` SQL statements in Go code.
