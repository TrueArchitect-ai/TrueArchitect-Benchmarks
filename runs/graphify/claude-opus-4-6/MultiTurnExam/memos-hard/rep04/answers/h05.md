**Mechanism: explicit Go code** within a transactional user-deletion function — there are no foreign-key / `ON DELETE CASCADE` rules on the `reaction` table.

**Evidence:**

1. **Schema has no FK on `reaction`** — the table is created without any `FOREIGN KEY` or `ON DELETE CASCADE` referencing the user table:
   - `store/migration/sqlite/LATEST.sql:91–99`
   - `store/migration/postgres/LATEST.sql:90–98`
   - `store/migration/mysql/LATEST.sql:90–98`

2. **Go code explicitly deletes reactions in two passes** inside `deleteUserTargetsTx`, within the same transaction that removes the user row. All three drivers are identical in structure:
   - `store/db/sqlite/user_delete.go:96` — `deleteReactionsByContentIDsTx` removes all reactions (by any user) attached to the deleted user's memos.
   - `store/db/sqlite/user_delete.go:102` — `deleteReactionsByCreatorTx` removes all reactions the deleted user placed on others' memos.
   - Same at `store/db/postgres/user_delete.go:96,102` and `store/db/mysql/user_delete.go:96,102`.

3. **Tests verify this** — `server/router/api/v1/test/user_service_delete_test.go:71` (`TestDeleteUserSelfDeleteRemovesOwnedResourcesAndMemoSubtrees`) asserts that reactions on the user's memos and reactions by the user are gone after deletion, while unrelated reactions survive.
