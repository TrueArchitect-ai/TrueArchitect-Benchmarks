The following database tables are affected when `DeleteMemo` runs:

1. **`memo`** — directly deleted via `DELETE FROM memo WHERE id = ?` in the store layer (`store/db/sqlite/memo.go:239`, `store/db/postgres/memo.go:246`). This happens both for the target memo and for any comment memos (related via `memo_relation` with type `COMMENT`), which are deleted first in the service handler (`server/router/api/v1/memo_service.go:573-576`).

2. **`memo_relation`** — affected indirectly: when comment memos are deleted (their `memo` rows are removed), the `memo_relation` rows referencing them as `memo_id` become orphaned. Note that `memo_relation` has no `ON DELETE CASCADE` foreign key constraint in the schema, so these rows are not automatically cleaned up by the database itself, but the comment deletion loop effectively removes the memos that the relations point to.

3. **`memo_share`** — cascade-deleted by the database via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`).

**Table list: `memo`, `memo_relation`, `memo_share`**
