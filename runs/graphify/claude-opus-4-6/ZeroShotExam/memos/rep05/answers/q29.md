The frontend auth interceptor lives at **`web/src/connect.ts`** (the `authInterceptor` function, ~line 156). It is a Connect RPC transport interceptor that attaches an `Authorization: Bearer <token>` header to every outgoing request, with automatic retry-on-401 logic.

**Token kinds managed:**

1. **Access token (JWT v2)** — short-lived (15 min), stored in `localStorage` (`memos_access_token`) and in-memory cache (managed in `web/src/auth-state.ts`), sent as a Bearer header, validated statelessly by signature.
2. **Refresh token (JWT)** — long-lived (30 days, rotated on use), stored in an `HttpOnly` cookie (`memos_refresh`), sent automatically via `credentials: "include"`. A separate `refreshTransport` (no interceptors) is used to call the refresh RPC to avoid recursion.
3. **Personal access token (PAT)** — user-configured expiry, looked up by SHA-256 hash in the database. Not managed by the frontend interceptor itself but accepted by the same backend validation path.

**Backend validation package:** **`server/auth/`** — specifically `server/auth/authenticator.go` (the `Authenticator` struct with `Authenticate()`, `AuthenticateByAccessTokenV2()`, `AuthenticateByRefreshToken()`, `AuthenticateByPAT()`) and `server/auth/token.go` (JWT parsing via `golang-jwt/jwt/v5`). The server-side Connect interceptor that calls into this package is at `server/router/api/v1/connect_interceptors.go`.

**Summary:** `web/src/connect.ts`; access token (JWT v2), refresh token (JWT cookie), personal access token (PAT); `server/auth/`.
