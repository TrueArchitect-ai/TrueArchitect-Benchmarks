**Explicit Go code**; reactions are cleaned up by application-level deletion logic, not by database CASCADE rules.

**Evidence:**

**No database-level CASCADE:** The `reaction` table has no foreign key on `creator_id` referencing the `user` table — checked in all three backends:
- `store/migration/sqlite/LATEST.sql` (~line 91–99)
- `store/migration/postgres/LATEST.sql` (~line 90–98)
- `store/migration/mysql/LATEST.sql` (~line 90–98)

**Explicit Go cleanup in two steps** (identical across all three drivers, e.g. SQLite):

1. **Delete all reactions on the user's memos** (by any reactor) — `store/db/sqlite/user_delete.go` line 96 calls `deleteReactionsByContentIDsTx`, which runs `DELETE FROM reaction WHERE content_id IN (...)` (lines 380–388).

2. **Delete all reactions the user placed on others' memos** — `store/db/sqlite/user_delete.go` line 102 calls `deleteReactionsByCreatorTx`, which runs `DELETE FROM reaction WHERE creator_id = ?` (lines 400–403).

Both operations execute inside a single transaction in `deleteUserTargetsTx`. The same pattern appears in `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`.

**Test verification:** `store/test/user_delete_test.go` (lines 97–114, 216–220) explicitly asserts that both categories of reactions are removed and that unrelated reactions survive.
