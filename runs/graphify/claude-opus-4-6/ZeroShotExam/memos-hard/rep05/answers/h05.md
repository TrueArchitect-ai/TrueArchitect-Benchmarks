**Explicit Go code**; reactions are removed by application-level `DELETE` statements inside a transaction — not by any database-level rule (there are no foreign keys on the `reaction` table at all).

**Evidence:**

1. **No database CASCADE** — The `reaction` table has no foreign key constraints in any of the three schemas:
   - `store/migration/postgres/LATEST.sql` (~lines 91–98)
   - `store/migration/sqlite/LATEST.sql` (~lines 92–99)
   - `store/migration/mysql/LATEST.sql` (~lines 91–98)

   `creator_id` and `content_id` are plain columns with a `UNIQUE` constraint but no `REFERENCES` or `ON DELETE CASCADE`.

2. **Explicit Go deletion in two passes** within `deleteUserTargetsTx`, executed inside the user-deletion transaction in each driver's `user_delete.go`:

   - **`deleteReactionsByContentIDsTx`** — deletes all reactions on the user's memos (`DELETE FROM reaction WHERE content_id IN (...)`) — e.g. `store/db/sqlite/user_delete.go:96–98` (call site), `:380–388` (implementation).
   - **`deleteReactionsByCreatorTx`** — deletes all reactions the user created on any memo (`DELETE FROM reaction WHERE creator_id = ?`) — e.g. `store/db/sqlite/user_delete.go:102–104` (call site), `:400–403` (implementation).

   Identical logic exists in `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`.

3. **Call chain**: `server/router/api/v1/user_service.go:DeleteUser` → `store/user.go:DeleteUser` → driver `DeleteUser` → `deleteUserTargetsTx` (which runs both reaction-deletion functions before deleting memos and the user row).
