**Explicit Go code**; reactions are cleaned up by application-level SQL `DELETE` statements, not by any database-level `CASCADE` rule.

**Evidence:**

**No database-level foreign keys on the `reaction` table:**
- `store/migration/sqlite/LATEST.sql:92-99` — `reaction` table has `creator_id INTEGER NOT NULL` with no `REFERENCES` or `ON DELETE CASCADE`
- Same in `store/migration/postgres/LATEST.sql:91-98` and `store/migration/mysql/LATEST.sql:91-98`

**Explicit Go deletion in two steps** (identical logic across all three DB drivers):

1. **Delete all reactions on the user's memos** (by `content_id`) — `store/db/sqlite/user_delete.go` line ~96 calls `deleteReactionsByContentIDsTx`, which runs `DELETE FROM reaction WHERE content_id IN (...)` (line ~380).

2. **Delete all reactions by the user** (by `creator_id`) — `store/db/sqlite/user_delete.go` line ~102 calls `deleteReactionsByCreatorTx`, which runs `DELETE FROM reaction WHERE creator_id = ?` (line ~400).

Both execute inside a single transaction in `deleteUserTargetsTx`. The same pattern appears in `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`.

**Test verification:** `store/test/user_delete_test.go:216-220` asserts that after user deletion, only a peer's self-reaction survives — confirming both the user's own reactions and others' reactions on the user's content are removed.
