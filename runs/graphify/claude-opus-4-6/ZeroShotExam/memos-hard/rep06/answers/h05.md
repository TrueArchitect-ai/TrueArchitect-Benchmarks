**Explicit Go code**; reactions are cleaned up in application-level Go code within a transaction, not by any database-level rule. The `reaction` table has no foreign key constraints at all.

**Evidence:**

1. **No DB-level cascade:** The `reaction` table schema defines `creator_id INTEGER NOT NULL` with no `FOREIGN KEY` or `ON DELETE CASCADE`:
   - `store/migration/postgres/LATEST.sql:90-98`
   - `store/migration/sqlite/LATEST.sql:91-99`
   - `store/migration/mysql/LATEST.sql:90-98`

2. **Explicit Go deletion in two steps** inside `deleteUserTargetsTx`, within a single transaction:
   - **Reactions on the user's memos** (by any reactor): `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` — e.g. `store/db/sqlite/user_delete.go:96, 380-388`
   - **Reactions the user placed on others' memos**: `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` — e.g. `store/db/sqlite/user_delete.go:102, 400-403`
   - Identical logic in `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`

3. **Test verification:** `store/test/user_delete_test.go:97-114, 216-220` — creates reactions in both directions, deletes the user, and asserts only unrelated reactions survive.
