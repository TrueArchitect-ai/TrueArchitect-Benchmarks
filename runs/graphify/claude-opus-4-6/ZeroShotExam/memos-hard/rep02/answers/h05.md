**Explicit Go code**; reactions are deleted by two targeted SQL `DELETE` statements inside a transaction — there are no database-level foreign key constraints on the `reaction` table.

**Evidence:**

1. **No DB-level cascade.** The `reaction` table schema has no foreign keys at all — `creator_id` and `content_id` are plain columns with no `REFERENCES` or `ON DELETE` clause.
   - `store/migration/postgres/LATEST.sql` (lines ~91–98)
   - `store/migration/sqlite/LATEST.sql` (lines ~92–99)
   - `store/migration/mysql/LATEST.sql` (lines ~91–98)

2. **Explicit Go deletion.** The function `deleteUserTargetsTx` in each DB driver performs two reaction deletions within the user-deletion transaction:
   - **`deleteReactionsByContentIDsTx`** — `DELETE FROM reaction WHERE content_id IN (...)` removes all reactions (by any user) on the deleted user's memos. (`store/db/postgres/user_delete.go:96`, `~380–387`)
   - **`deleteReactionsByCreatorTx`** — `DELETE FROM reaction WHERE creator_id = ?` removes all reactions the deleted user placed on anyone else's memos. (`store/db/postgres/user_delete.go:102`, `~400–402`)
   - Identical logic in `store/db/sqlite/user_delete.go` and `store/db/mysql/user_delete.go` at the same line ranges.

3. **Test coverage.** `store/test/user_delete_test.go` (lines ~97–114, ~216–220) sets up reactions in both directions and asserts that only unrelated reactions survive after user deletion.
