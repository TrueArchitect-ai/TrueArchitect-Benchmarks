Tracing `GET /file/users/:identifier/avatar` from the browser to stored data:

`serveUserAvatar` — `server/router/fileserver/fileserver.go`
`getCurrentUser` — `server/router/fileserver/fileserver.go`
`AuthenticateToUser` — `server/auth/authenticator.go`
`getUserByUsername` — `server/router/fileserver/fileserver.go`
`Store.GetUser` — `store/user.go`
`Store.ListUsers` — `store/user.go`
`driver.ListUsers` — `store/db/sqlite/user.go` (or `mysql/user.go`, `postgres/user.go`)
`parseDataURI` — `server/router/fileserver/fileserver.go`

The route is registered in `server/server.go` where `FileServerService.RegisterRoutes` mounts the Echo group, and in `fileserver.go` at `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)`.

The handler authenticates the request (on private instances), resolves the username to a `store.User` via `GetUser` → `ListUsers` → the DB driver's `ListUsers` which runs `SELECT … avatar_url … FROM user WHERE username = ?`. The `avatar_url` column holds a base64 data URI (`data:image/png;base64,…`). Back in the handler, `parseDataURI` decodes it into raw bytes and MIME type, which are returned to the browser via `c.Blob()`. The API never sends the base64 blob inline in JSON — `convertUserFromStore` in `server/router/api/v1/user_service_converters.go` rewrites it to the `/file/users/{username}/avatar` path so the browser fetches the image separately.
