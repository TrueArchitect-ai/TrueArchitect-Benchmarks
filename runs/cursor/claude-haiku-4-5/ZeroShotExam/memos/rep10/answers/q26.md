When `DeleteMemo` runs, the following database tables are affected:

1. **memo** (directly deleted)
2. **memo_relation** (explicitly deleted via `DeleteMemoRelation` calls - both directions: MemoID and RelatedMemoID)
3. **attachment** (explicitly deleted via loop - `DeleteAttachment` called for each attachment)
4. **memo_share** (implicitly via CASCADE - foreign key constraint `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`)

The deletion process in `/bench/repo/server/router/api/v1/memo_service.go` (lines 518-593):
- First deletes all memo comments (which recursively call `DeleteMemo` for each comment, cleaning their relations and attachments)
- Then calls `s.Store.DeleteMemo()` which:
  - Deletes memo_relation records where the memo is source (`MemoID`)
  - Deletes memo_relation records where the memo is target (`RelatedMemoID`)
  - Deletes all attachments linked to the memo
  - Deletes the memo itself (which cascades to memo_share via database constraint)

Note: The **reaction** table is NOT affected by DeleteMemo - no explicit deletion code exists for reactions when a memo is deleted.
