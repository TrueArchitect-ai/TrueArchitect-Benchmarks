**Premise correction:** Neither NATS nor RabbitMQ is used. This repository (usememos/memos) has no message-broker dependency at all — `go.mod`/`go.sum` contain no NATS, RabbitMQ/AMQP, Kafka, or SQS client libraries, and a repo-wide search for those terms turns up nothing relevant (the only "broker" hits are unrelated identity-provider docs).

**Actual mechanism:** Webhook delivery is implemented purely in-process with a Go channel, not an external broker. In `internal/webhook/webhook.go`:

- An unbuffered-consumer, buffered channel `asyncPostQueue` (capacity 128) acts as the "queue": `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`).
- Four goroutines are spawned in `init()` to range over that channel and call `Post()` for each payload, i.e. they are the "delivery workers" (`internal/webhook/webhook.go:42-55`).
- Producers enqueue work via `PostAsync()`, which does a non-blocking `select`/`send` on `asyncPostQueue`, dropping (and logging) the payload if the channel is full rather than blocking (`internal/webhook/webhook.go:184-196`).
- `Post()` itself performs the actual HTTP `POST` to the webhook URL, including optional Standard-Webhooks HMAC signing (`internal/webhook/webhook.go:119-180`).

So there's no NATS subject, no RabbitMQ queue/exchange declaration, and no broker connection code anywhere in the repo — the "queue" is simply the in-memory Go channel declared at `internal/webhook/webhook.go:39`, consumed by the worker goroutines started at `internal/webhook/webhook.go:42-55`.
