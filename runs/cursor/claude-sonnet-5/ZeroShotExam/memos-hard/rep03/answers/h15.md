Memo visibility is checked independently in at least seven separate server code paths (the logic is duplicated rather than centralized, so each caller re-implements the `Private`/`Protected`/`Public` comparison):

- Core memo read-access check used by `GetMemo` and `ListMemoComments` (`checkMemoReadAccess`) — `server/router/api/v1/memo_service.go` (lines 39-68, called at 356, 367, and from `memo_service_comments.go:148`)
- `ListMemos` query-level visibility filter for anonymous/other users (`memoFind.VisibilityList` / creator-or-public-protected filter) — `server/router/api/v1/memo_service.go` (lines 218-227)
- Comment-creation visibility check, a separate inline duplicate (`CreateMemoComment`) — `server/router/api/v1/memo_service_comments.go` (lines 33-43)
- Reaction service visibility checks (`ListMemoReactions`, `UpsertMemoReaction`) — `server/router/api/v1/reaction_service.go` (lines 29-41, 82-85)
- Attachment gRPC access check (`checkAttachmentAccess`, used when fetching/streaming an attachment via the API) — `server/router/api/v1/attachment_service.go` (lines 419-455)
- Memo-attachment listing check (`ListMemoAttachments`) — `server/router/api/v1/memo_attachment_service.go` (lines 213-225)
- HTTP file-serving server's own permission check (`checkAttachmentPermission`), a wholly separate HTTP surface with its own auth resolution (bearer/cookie/share-token) — `server/router/fileserver/fileserver.go` (lines 649-704)
- SSE real-time broadcast filter (`SSEClient.canReceive`), which decides whether a connected client may receive a live memo/comment/reaction event — `server/router/api/v1/sse_hub.go` (lines 134-144)

Additional lighter-weight sites that also restrict exposure to public memos only (query-scoped rather than a per-request permission check) are the RSS feed (`server/router/rss/rss.go`, `VisibilityList: []store.Visibility{store.Public}` at lines 90 and 141) and the sitemap generator (`server/router/frontend/frontend.go`, line 150).
