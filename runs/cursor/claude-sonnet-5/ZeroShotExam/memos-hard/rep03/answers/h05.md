h05.

**Mechanism: Explicit Go application code** (not a database-level rule). There is no foreign key / `ON DELETE CASCADE` on the `reaction` table in any supported database, so deletion is done entirely by explicit Go statements executed inside a transaction when `DeleteUser` runs.

**Evidence locations:**

1. **No DB-level cascade exists** — the `reaction` table schema declares `creator_id INTEGER NOT NULL` with no `REFERENCES`/foreign-key clause at all, in every dialect:
   - `store/migration/postgres/0.20/00__reaction.sql` (lines 1‑9) and reconfirmed in the consolidated `store/migration/postgres/LATEST.sql` (lines 90‑98)
   - `store/migration/mysql/0.20/00__reaction.sql` (lines 1‑9)
   - `store/migration/sqlite/0.20/00__reaction.sql` (lines 1‑9)

   Since there's no FK on `creator_id` (the reaction's owner) or on `content_id` (which isn't even a real FK, just a string reference like `memos/{uid}`), the database itself has no rule that would cascade-delete reactions when a user row disappears.

2. **Explicit Go deletion code** — each SQL driver's `DeleteUser` implementation runs a hand-written sequence of `DELETE` statements inside a single transaction, and explicitly deletes reactions in two ways before removing the user row itself:
   - `deleteReactionsByContentIDsTx` — deletes reactions attached to all memos (including comment/child memos) owned by the user: `DELETE FROM reaction WHERE content_id IN (...)`
   - `deleteReactionsByCreatorTx` — deletes reactions the user themself made on any content (even other users' memos): `DELETE FROM reaction WHERE creator_id = ?`
   - Both are invoked from `deleteUserTargetsTx`, before `deleteUserRowTx` deletes the `user` row, in:
     - `store/db/postgres/user_delete.go` (functions at lines 380‑388, 400‑403, called from lines 96 and 102 within `deleteUserTargetsTx`)
     - `store/db/sqlite/user_delete.go` (same functions/lines)
     - `store/db/mysql/user_delete.go` (functions at lines 417‑425, 437‑440, called from lines 96 and 102)

3. **Confirmed by tests** — `server/router/api/v1/test/user_service_delete_test.go` explicitly upserts reactions (lines 188‑209) and after deleting the user asserts reactions on the user's own memo/comment are gone (`require.Empty`, lines 287‑293) while a peer's unrelated reaction on someone else's memo survives (lines 295‑298) — confirming the cleanup is scoped/explicit rather than an indiscriminate cascade.

4. **Service entry point** — `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:393-455`) calls `s.Store.DeleteUser`, which dispatches to the driver-specific `DeleteUser` shown above (`store/reaction.go` shows reactions otherwise only have manual `UpsertReaction`/`DeleteReaction` store methods, with no cascade hooks).
