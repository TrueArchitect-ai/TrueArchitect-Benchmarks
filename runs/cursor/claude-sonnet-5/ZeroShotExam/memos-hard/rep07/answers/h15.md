Memo visibility enforcement is duplicated/re-implemented across many independent server surfaces rather than going through one shared gate. Confirmed enforcement sites:

- Core Memo gRPC/API service (`checkMemoReadAccess`, used by `GetMemo`, `GetMemoComments`, parent-memo lookups, and the `ListMemos` visibility filter) — `server/router/api/v1/memo_service.go`
- Memo comments listing reuses the core check but is its own call site — `server/router/api/v1/memo_service_comments.go`
- Memo attachment listing (`ListMemoAttachments`, own inline `memo.Visibility` check, duplicated logic) — `server/router/api/v1/memo_attachment_service.go`
- Standalone Attachment API access check (`checkAttachmentAccess`, used by `GetAttachment`) — `server/router/api/v1/attachment_service.go`
- Reaction API (`ListMemoReactions` / `UpsertMemoReaction`, own inline `memo.Visibility` check) — `server/router/api/v1/reaction_service.go`
- Raw HTTP attachment/file server (`checkAttachmentPermission`, including share-token bypass) — `server/router/fileserver/fileserver.go`
- Real-time SSE event broadcast filtering (`SSEClient.canReceive`) — `server/router/api/v1/sse_hub.go`
- Email notification dispatch gating (`canViewerAccessMemo`) — `server/notification/email.go`
- In-app notification/inbox listing gating (separate `canViewerAccessMemo` implementation) — `server/router/api/v1/user_service_notifications.go`
- RSS feed generation (query-level restriction to `store.Public` only) — `server/router/rss/rss.go`
- Sitemap XML generation (query-level restriction to `store.Public` only) — `server/router/frontend/frontend.go`

The first six are request-time permission checks; the last four are query/broadcast-level filters that restrict which memos are ever surfaced to a given consumer.
