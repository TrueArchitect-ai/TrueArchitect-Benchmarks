**Premise correction:** There is no Redis anywhere in this repository. A full search of the codebase (source, `go.mod`/`go.sum` dependencies, configs, workflows) turns up zero references to Redis — it is not a dependency and no Redis client/connection code exists.

**Actual mechanism:** The "cache layer" for user entries is a custom, in-process, thread-safe in-memory cache (`sync.Map`-based), not an external Redis instance.

- Implementation: `store/cache/cache.go` defines the `Cache` type (backed by `sync.Map`, with a background `cleanupLoop` goroutine for expiry/eviction).
- Wiring/"configuration": `store/store.go` constructs the `Store` with a `cache.Config{DefaultTTL: 10 * time.Minute, CleanupInterval: 5 * time.Minute, MaxItems: 1000}` and instantiates `userCache: cache.New(cacheConfig)` (alongside `instanceSettingCache` and `userSettingCache`), each an independent in-memory cache instance living inside the Go process — there's no network connection, host, port, or credentials to configure since it's not a separate service.
- Usage for users: `store/user.go` sets/reads/invalidates entries via `s.userCache.Set(ctx, userCacheKey(user.ID), user)` / `s.userCache.Get(...)`, and `store/user_delete.go` deletes the entry on user deletion (`deleteUserCache`).
- TTL for user entries: Since `store/user.go` calls the plain `Set` (not `SetWithTTL`), user cache entries use the cache's `DefaultTTL`, which is **10 minutes** (`store/store.go` line ~40), with a background cleanup sweep every 5 minutes (`CleanupInterval`) and a 1000-item cap (`MaxItems`) triggering eviction of oldest entries if exceeded.
