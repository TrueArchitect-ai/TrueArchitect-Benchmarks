h05.

**Mechanism: explicit Go code (application-level deletes inside a DB transaction) — not a database-level rule (there is no `FOREIGN KEY`/`ON DELETE CASCADE` on the `reaction` table in any of the three supported drivers).**

Evidence:

1. **Schema has no cascade constraint.** The `reaction` table in all three dialects declares `creator_id`/`content_id` as plain columns with only a `UNIQUE` constraint — no `FOREIGN KEY ... REFERENCES "user"(id) ON DELETE CASCADE`:

```1:9:/bench/repo/store/migration/postgres/0.20/00__reaction.sql
CREATE TABLE reaction (
  id SERIAL PRIMARY KEY,
  created_ts BIGINT NOT NULL DEFAULT EXTRACT(EPOCH FROM NOW()),
  creator_id INTEGER NOT NULL,
  content_id TEXT NOT NULL,
  reaction_type TEXT NOT NULL,
  UNIQUE(creator_id, content_id, reaction_type)
);
```
Same shape (no FK) in `store/migration/mysql/0.20/00__reaction.sql` and `store/migration/sqlite/0.20/00__reaction.sql`. So the DB engine itself cannot and does not cascade-delete reactions when a user row is removed.

2. **Explicit Go code deletes reactions during `DeleteUser`.** Each database driver's `DeleteUser` implementation runs, inside one transaction, both:
   - a delete of reactions on memos that the deleted user authored (matched by `content_id`), and
   - a delete of reactions the deleted user themself made (matched by `creator_id`):
