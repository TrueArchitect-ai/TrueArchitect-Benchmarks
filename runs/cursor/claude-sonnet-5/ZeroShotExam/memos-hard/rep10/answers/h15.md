Memo visibility (`PRIVATE`/`PROTECTED`/`PUBLIC`) is checked independently in several server surfaces, each with its own duplicated logic rather than a single shared gate:

1. Core memo API (GetMemo/ListMemos/ListMemoComments) — `server/router/api/v1/memo_service.go` (`checkMemoReadAccess`, called again from `server/router/api/v1/memo_service_comments.go:148`)
2. Attachment API (GetAttachment by resource name) — `server/router/api/v1/attachment_service.go` (`checkAttachmentAccess`, lines 422-455)
3. Memo-scoped attachment listing (ListMemoAttachments) — `server/router/api/v1/memo_attachment_service.go` (inline visibility check, lines 213-224)
4. Reaction API (ListMemoReactions/UpsertMemoReaction) — `server/router/api/v1/reaction_service.go` (inline visibility checks at lines 29-41 and 82-85)
5. Raw file/attachment HTTP server — `server/router/fileserver/fileserver.go` (`checkAttachmentPermission`, lines 650-704)
6. Real-time SSE event delivery — `server/router/api/v1/sse_hub.go` (`canReceive`, lines 134-144, filters broadcast events by `Visibility`)
7. RSS/Atom feed generation — `server/router/rss/rss.go` (hardcodes `VisibilityList: []store.Visibility{store.Public}` at lines 90 and 141)
8. Frontend sitemap generation — `server/router/frontend/frontend.go` (hardcodes `VisibilityList: []store.Visibility{store.Public}` at line 150)

Additionally, `server/router/api/v1/memo_service_comments.go` (lines 33-43) enforces the same visibility rule before allowing a comment to be created on a memo.

Each of these re-implements essentially the same rule (`Public` → anyone; `Protected` → any authenticated user; `Private` → creator or admin/superuser only) independently rather than sharing one central check, so any future visibility rule change would need to be applied in all of these locations.
