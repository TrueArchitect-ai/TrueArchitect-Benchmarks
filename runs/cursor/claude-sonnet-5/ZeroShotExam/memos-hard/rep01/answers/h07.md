Trace for a browser request like `GET /file/users/{identifier}/avatar` for another user's profile image:

```121:125:server/router/fileserver/fileserver.go
fileGroup := echoServer.Group("/file")
fileGroup.GET("/attachments/:uid/:filename", s.serveAttachmentFile)
fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)
```

- `(*FileServerService).RegisterRoutes` — `server/router/fileserver/fileserver.go` (registers `GET /file/users/:identifier/avatar`)
- `(*FileServerService).serveUserAvatar` — `server/router/fileserver/fileserver.go` (HTTP handler; reads `:identifier` param, checks anonymous-access policy)
- `(*FileServerService).getUserByUsername` — `server/router/fileserver/fileserver.go` (wraps the store call: `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`)
- `(*Store).GetUser` — `store/user.go` (checks user cache by ID — skipped here since lookup is by username — then delegates)
- `(*Store).ListUsers` — `store/user.go` (calls `s.driver.ListUsers(ctx, find)`)
- `Driver.ListUsers` interface method — `store/driver.go` (interface boundary between store layer and DB driver)
- `(*DB).ListUsers` — `store/db/sqlite/user.go` (builds and runs `SELECT id, username, ..., avatar_url, ... FROM user WHERE username = ?`, scans into `store.User.AvatarURL`) — equivalent implementations exist in `store/db/postgres/user.go` and `store/db/mysql/user.go`, selected based on configured DB driver.

After the data returns, `serveUserAvatar` reads `user.AvatarURL` (a `data:<mime>;base64,...` URI stored directly in the `user` table's `avatar_url` column) and calls `(*FileServerService).parseDataURI` (`server/router/fileserver/fileserver.go`) to decode it before writing the image bytes to the HTTP response via `c.Blob`.

Note: unlike memo/attachment files (which can live on local disk or S3 via `store.Attachment`), the avatar image bytes themselves are stored inline in the `user.avatar_url` column as a base64 data URI — so the "data layer" endpoint here is the `user` table row, not the attachment/blob storage path.
