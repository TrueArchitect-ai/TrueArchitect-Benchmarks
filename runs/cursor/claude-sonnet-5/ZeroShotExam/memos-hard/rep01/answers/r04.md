**Premise correction:** Neither NATS nor RabbitMQ is used. This repository (`memos`) has no external message-broker dependency at all — there's no `nats`, `rabbitmq`, or `amqp` import/reference anywhere in the Go source (confirmed via a repo-wide search of all `.go` files).

**Actual mechanism:** Webhook delivery is handled entirely in-process using a buffered Go channel as an in-memory work queue, not an external broker.

- The "queue" is declared as a package-level buffered channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` in `internal/webhook/webhook.go` (line 39).
- On package `init()` (`internal/webhook/webhook.go`, lines 42–55), 4 goroutines are spawned as workers, each running `for payload := range asyncPostQueue { ... Post(payload) ... }` — this is the "consumer" side.
- Producers call `PostAsync` (`internal/webhook/webhook.go`, lines 184–196), which does a non-blocking send (`select`/`default`) into `asyncPostQueue`; if the channel is full, the webhook dispatch is dropped and a warning is logged rather than blocking.
- Actual delivery happens via `Post` (`internal/webhook/webhook.go`, lines 119–180), which does a plain HTTP `POST` to the target URL, with SSRF protections via a custom `DialContext` (`safeDialContext`, lines 57–77) and optional HMAC signing (Standard Webhooks style).

So there's no queue "declared" in any broker/config sense (no AMQP queue.declare, no NATS subject) — the closest analog is this in-memory Go channel with a fixed capacity of 128 and 4 fixed worker goroutines.
