**Premise correction:** Neither. This repository (the `usememos/memos` app) has no NATS or RabbitMQ (or any AMQP) integration at all — I searched the entire codebase for `nats`, `rabbitmq`, and `amqp` and the only hits were incidental substring matches inside a Catalan locale file (e.g. "predeterminats") in `web/src/locales/ca.json`, not an actual message broker dependency. There's no broker client, connection config, or `go.mod` dependency for either system.

**Actual mechanism:** Webhook delivery is handled entirely in-process using a buffered Go channel, not an external message broker/queue:

- The "queue" is declared as a package-level buffered channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` in `internal/webhook/webhook.go:39`.
- A pool of 4 goroutines is spun up in an `init()` function to consume from that channel and perform the actual HTTP POST delivery via `Post(payload)` (`internal/webhook/webhook.go:42-55`).
- Producers call `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send into `asyncPostQueue`, dropping (and logging a warning for) the payload if the channel is full — there's no persistence or retry beyond that in-memory buffer.

So webhook delivery is an in-memory, single-process worker pool backed by a Go channel, with no external broker involved.
