Premise correction: There is no per-user API rate-limiting middleware in this repository, so it isn't "registered" anywhere and has no request limits.

What actually exists at the API layer (`server/router/api/v1/v1.go:131-141`) is a Connect-RPC interceptor chain — `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor` (defined in `server/router/api/v1/connect_interceptors.go`) — which handles header/metadata propagation, logging, panic recovery, and authentication/authorization respectively. None of these throttle or limit request rate per user.

The only size-related limit nearby is a request **body-size** cap, `maxAPIRequestBytes = 256 << 20` (256 MiB), applied via `http.MaxBytesHandler` to both the gRPC-Gateway and Connect handlers (`server/router/api/v1/v1.go:20,126,141,144`) — this is a payload-size limit, not a rate limit.

A repo-wide search for `ratelimit`, `rate limit`, and `throttle` across all `*.go` files turned up only a single mention, in a doc comment for the unrelated SMTP email package (`internal/email/doc.go:86`, "Rate limit email sending to prevent abuse"), which is aspirational documentation text, not implemented code. There is also a `Middleware` chain in `internal/scheduler/middleware.go`, but that provides `Recovery`, `Logging`, and `Timeout` wrappers for background job execution — unrelated to API requests or per-user limits.

So no such middleware exists to cite limits for.
