I found memo-visibility checks duplicated independently across multiple server surfaces (many re-implementing the same logic instead of sharing a helper). Here is every distinct enforcement site I could locate:

1. Shared read-access guard for `GetMemo`/`ListMemoComments` (`checkMemoReadAccess`) — `server/router/api/v1/memo_service.go` (lines 39–68, called at 356/367)
2. Query-level visibility filter for `ListMemos` (builds `VisibilityList`/filter based on caller) — `server/router/api/v1/memo_service.go` (lines 218–227)
3. Inline visibility check in `CreateMemoComment` before allowing a comment on a memo — `server/router/api/v1/memo_service_comments.go` (lines 33–43)
4. Inline visibility checks in `ListMemoReactions`/`UpsertMemoReaction` before exposing/adding reactions — `server/router/api/v1/reaction_service.go` (lines 29–41, 82–85)
5. Inline visibility check in `ListMemoAttachments` before listing a memo's attachments — `server/router/api/v1/memo_attachment_service.go` (lines 213–225)
6. Real-time SSE delivery filter (`SSEClient.canReceive`) that drops broadcast events for private memos to non-owners/non-admins — `server/router/api/v1/sse_hub.go` (lines 134–144)
7. Attachment download permission check based on the parent memo's visibility (`checkAttachmentPermission`) — `server/router/fileserver/fileserver.go` (lines 649–704)
8. RSS feed generation, which restricts results to `store.Public` memos only — `server/router/rss/rss.go` (lines 88–93, 138–144)
9. Sitemap XML generation, which also restricts results to `store.Public` memos only — `server/router/frontend/frontend.go` (lines 149–151)

That's nine distinct code locations (well beyond the minimum of three), spanning the gRPC/Connect API v1 service (five separate inline checks in different files), the SSE hub, the attachment file server, and two read-only public feeds (RSS and sitemap).
