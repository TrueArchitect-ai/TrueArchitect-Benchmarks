Memo-visibility permission checks are duplicated/implemented independently across at least six server surfaces (not just one shared helper):

1. Core Memo API read-access check (`checkMemoReadAccess`, used by `GetMemo` and memo comments) — `server/router/api/v1/memo_service.go`
2. Memo Reactions API (separate, re-implemented inline check for `ListMemoReactions`/`UpsertMemoReaction`, does not call `checkMemoReadAccess`) — `server/router/api/v1/reaction_service.go`
3. Memo Attachments API (separate, re-implemented inline check for `ListMemoAttachments`) — `server/router/api/v1/memo_attachment_service.go`
4. File/attachment HTTP server (`checkAttachmentPermission`, resolves the parent memo and enforces Public/Protected/Private + share-token bypass before streaming file bytes) — `server/router/fileserver/fileserver.go`
5. Server-Sent Events hub (`canReceive`, filters real-time memo/comment/reaction broadcast events by visibility and recipient) — `server/router/api/v1/sse_hub.go`
6. RSS feed generation (hard-restricts `ListMemos` query to `store.Public` only for both the explore feed and per-user feed) — `server/router/rss/rss.go`

Additional surfaces that also filter by visibility when producing lists of memos (same enforcement pattern, arguably extending the "at least three"):
- Sitemap generation, restricted to public memos — `server/router/frontend/frontend.go`
- User stats/heatmap aggregation, filtering visible memos by viewer relationship to creator — `server/router/api/v1/user_service_stats.go`
- `ListMemos` itself applies its own visibility filter (public-only for anonymous, `creator_id == X || visibility in [PUBLIC, PROTECTED]` otherwise) in the same file as #1 — `server/router/api/v1/memo_service.go`

Note: `GetMemoByShare` (`server/router/api/v1/memo_share_service.go`) intentionally *bypasses* visibility via a share token rather than enforcing it, so it is not counted as an enforcement site.
