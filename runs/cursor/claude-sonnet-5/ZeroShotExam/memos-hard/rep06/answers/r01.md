**Premise correction:** There is no Redis connection anywhere in this codebase — it's the `usememos/memos` Go application, and a repo-wide search (`grep -ril redis .`) turns up zero matches, and `go.mod`/`go.sum` contain no Redis client dependency. The "cache layer" here is not backed by Redis at all; it's a custom in-process, thread-safe in-memory cache (`sync.Map`-based) with its own TTL/eviction logic.

**Actual mechanism:** The cache implementation lives in `store/cache/cache.go`, and it's wired up in `store/store.go`. `store.New()` builds a `cache.Config{DefaultTTL: 10 * time.Minute, CleanupInterval: 5 * time.Minute, MaxItems: 1000}` and constructs three separate in-memory `*cache.Cache` instances from it — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:38-58`).

For user entries specifically, `store/user.go` calls `s.userCache.Set(ctx, userCacheKey(user.ID), user)` (e.g. `store/user.go:98,122,132,143,167`) — the plain `Set` method, not `SetWithTTL`. Per `store/cache/cache.go:92-95`, `Set` always applies the cache's `DefaultTTL`. Since `userCache` was constructed with the config above, **user entries are cached for 10 minutes** (with a background cleanup sweep every 5 minutes purging expired items, per `store/cache/cache.go:56-64,199-215`), all in-process with no external Redis server involved.
