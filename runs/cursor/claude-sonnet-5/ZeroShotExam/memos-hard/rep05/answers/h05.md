**Mechanism: explicit Go application code (not a database-level rule/constraint/trigger).**

Evidence:

1. **No DB-level cascade exists.** The `reaction` table schema has no foreign key on `creator_id`/`content_id` and no cascade/trigger tied to the `user` table:

```91:98:store/migration/postgres/LATEST.sql
CREATE TABLE reaction (
  id SERIAL PRIMARY KEY,
  created_ts BIGINT NOT NULL DEFAULT EXTRACT(EPOCH FROM NOW()),
  creator_id INTEGER NOT NULL,
  content_id TEXT NOT NULL,
  reaction_type TEXT NOT NULL,
  UNIQUE(creator_id, content_id, reaction_type)
);
```

The same definition (no `FOREIGN KEY`/`ON DELETE CASCADE`) appears in `store/migration/sqlite/LATEST.sql` and `store/migration/mysql/LATEST.sql`. Compare this to `memo_share`, which *does* declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the same file — `reaction` has no such clause, confirming there's no DB-level rule for it.

2. **Explicit Go deletion code exists in each DB driver's `DeleteUser` transaction.** In `store/db/postgres/user_delete.go`, `store/db/sqlite/user_delete.go`, and `store/db/mysql/user_delete.go`, the `deleteUserTargetsTx` function explicitly issues two `DELETE FROM reaction` statements before deleting the user row:


- `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` for every memo (and comment) the deleted user owned, removing reactions other users left on the deleted user's content.
- `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user placed on other users' content.

This is identical across `store/db/postgres/user_delete.go:380-403`, `store/db/sqlite/user_delete.go:380-403`, and `store/db/mysql/user_delete.go:417-440`, all wrapped inside the same SQL transaction as the rest of the cleanup (attachments, memo shares, inbox rows, identities, settings, memo relations, memos, and finally the user row itself).
