Tracing a browser request for another user's avatar image (e.g. `GET /file/users/{identifier}/avatar`) down to stored data:

- HTTP route registration — `server/server.go` (registers `fileServerService.RegisterRoutes(echoServer)`)
- Route definition — `server/router/fileserver/fileserver.go` (`RegisterRoutes`: `fileGroup.GET("/file/users/:identifier/avatar", s.serveUserAvatar)`)
- Request handler — `server/router/fileserver/fileserver.go` (`serveUserAvatar`, calls `s.getUserByUsername(ctx, identifier)`)
- Handler-local lookup wrapper — `server/router/fileserver/fileserver.go` (`getUserByUsername` → `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`)
- Store facade (cache-aware) — `store/user.go` (`(*Store).GetUser` checks `userCache`, then calls `s.ListUsers`)
- Store facade list method — `store/user.go` (`(*Store).ListUsers` delegates to `s.driver.ListUsers`)
- Driver interface implementation (SQL query + row scan of `avatar_url`) — `store/db/sqlite/user.go` (`(*DB).ListUsers`, `SELECT ... avatar_url ... FROM user WHERE ...`) — with equivalent implementations in `store/db/postgres/user.go` and `store/db/mysql/user.go` depending on configured driver
- Stored data — the `user` table's `avatar_url` column, defined via migrations e.g. `store/migration/sqlite/0.11/00__user_avatar.sql` (and current schema in `store/migration/sqlite/LATEST.sql`)

Back up the stack, `serveUserAvatar` in `server/router/fileserver/fileserver.go` decodes the returned `user.AvatarURL` data URI (`parseDataURI`) and writes it directly as the HTTP response body/blob to the browser.
