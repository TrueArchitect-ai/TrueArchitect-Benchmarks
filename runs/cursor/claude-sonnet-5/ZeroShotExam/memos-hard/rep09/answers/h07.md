Trace of a browser request for another user's profile image (e.g. `GET /file/users/{identifier}/avatar`) down to stored data:

```
GET /file/users/:identifier/avatar — server/router/fileserver/fileserver.go:124
```

Hop chain:

1. `FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (HTTP handler registered on the `/file` route group; authenticates viewer via `getCurrentUser`/`Authenticator` when the instance isn't anonymous, then resolves the target user)
2. `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715` (looks up the target user, i.e. "another user", by username)
3. `Store.GetUser` — `store/user.go:148` (checks `userCache` first, otherwise delegates to `ListUsers`)
4. `Store.ListUsers` — `store/user.go:136` (calls into the storage driver interface)
5. `Driver.ListUsers` interface — `store/driver.go:10` (dispatches to the concrete DB driver, e.g. SQLite/MySQL/Postgres)
6. `DB.ListUsers` — `store/db/sqlite/user.go:88` (also implemented in `store/db/mysql/user.go:84` and `store/db/postgres/user.go:87`; builds/executes the `SELECT ... FROM user WHERE ...` SQL query, including `avatar_url` column)

Back in `serveUserAvatar` (`server/router/fileserver/fileserver.go:168-209`), the returned `user.AvatarURL` (a `data:<mime>;base64,...` URI stored directly in the `user` table row) is parsed via `parseDataURI` (`fileserver.go:737`) and streamed back to the browser as the image blob.
