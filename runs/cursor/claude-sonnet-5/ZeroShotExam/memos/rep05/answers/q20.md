q20.
- **Mechanism:** Server-Sent Events (SSE) over a long-lived HTTP connection (`text/event-stream`, with periodic heartbeats), not WebSockets.
- **Hub path:** `server/router/api/v1/sse_hub.go` (the `SSEHub` type, with `Subscribe`/`Unsubscribe`/`Broadcast`), wired up via the HTTP endpoint in `server/router/api/v1/sse_handler.go` (`RegisterSSERoutes` / `handleSSE`, exposed at `/api/v1/sse`).
- **Handlers that broadcast through it** (all in `server/router/api/v1`, calling `s.SSEHub.Broadcast(...)`):
  - `CreateMemo` (`memo_service.go:163`) — `memo.created`
  - `UpdateMemo` (`memo_service.go`, via the shared `dispatchMemoUpdatedSideEffects` helper in `memo_update_helpers.go:71`) — `memo.updated`; the same helper is also invoked by `memo_attachment_service.go` and `memo_relation_service.go` when attachments/relations change on a memo
  - `DeleteMemo` (`memo_service.go:585`) — `memo.deleted`
  - `CreateMemoComment` (`memo_service_comments.go:126`) — `memo.comment.created`
  - `UpsertMemoReaction` (`reaction_service.go:106`) — `reaction.upserted`
  - `DeleteMemoReaction` (`reaction_service.go:161`) — `reaction.deleted`

Events are filtered per-subscriber inside the hub (`SSEClient.canReceive` in `sse_hub.go`) based on memo visibility/creator, and consumed client-side (e.g., `web/src/hooks/useLiveMemoRefresh.ts`) to trigger live UI refreshes.
