q29. Frontend API requests are authenticated via a Connect-RPC client interceptor called `authInterceptor`, defined in `web/src/connect.ts` (`authInterceptor` at lines 156–178, wired into the shared `transport` at line 188). On each outgoing request it attaches `Authorization: Bearer <token>` using the short-lived JWT access token obtained from `getRequestToken()`/`auth-state.ts` (`web/src/auth-state.ts`), and if the server responds `Unauthenticated`, it triggers a token refresh (`refreshAccessToken()` → `AuthService.refreshToken`, which relies on an HttpOnly refresh-token cookie sent via `credentials: "include"`) and retries the request once before redirecting to login on failure (`web/src/utils/auth-redirect.ts`).

On the backend, these tokens are validated by the `auth` package: `server/auth/token.go` defines/parses the JWT `AccessTokenClaims` and `RefreshTokenClaims` (plus Personal Access Tokens, prefix `memos_pat_`), and `server/auth/authenticator.go`'s `Authenticator` (methods `AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, `AuthenticateByPAT`) performs the actual validation, used by the Connect/gRPC interceptors in `server/router/api/v1/connect_interceptors.go` and the file server.

Answer format: `web/src/connect.ts` (`authInterceptor`); JWT access token (short-lived, 15 min, Bearer header) + JWT refresh token (long-lived, 30 days, HttpOnly cookie `memos_refresh`) + Personal Access Token (PAT, `memos_pat_` prefix, for programmatic access); `server/auth` (backend package, notably `server/auth/authenticator.go` and `server/auth/token.go`)
