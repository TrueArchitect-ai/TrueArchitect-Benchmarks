**Tables affected when `DeleteMemo` runs:**

1. **`memo`** — the memo row itself is deleted, and (recursively) any comment memos found via `memo_relation` (type `MemoRelationComment`) are deleted too, since the handler calls `s.Store.DeleteMemo` for each comment before deleting the target memo (`server/router/api/v1/memo_service.go:567-582`).
2. **`memo_relation`** — explicitly cleaned up in `store.Store.DeleteMemo`, which deletes rows where the memo is either `memo_id` or `related_memo_id` (`store/memo.go:140-147`).
3. **`attachment`** — explicitly cleaned up in `store.Store.DeleteMemo`, which lists and deletes all attachments belonging to the memo via `s.DeleteAttachment` (`store/memo.go:148-157`, backed by driver `DeleteAttachment`, e.g. `store/db/sqlite/attachment.go:211-221`).
4. **`memo_share`** — not deleted by any Go code path, but removed via an explicit `ON DELETE CASCADE` foreign key from `memo_share.memo_id` to `memo.id` defined in the schema (`store/migration/sqlite/LATEST.sql:101-110`, `store/migration/postgres/LATEST.sql:100-109`, `store/migration/mysql/LATEST.sql:100-109`). Note: SQLite connections are opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so this cascade is inert on SQLite but active on Postgres/MySQL.

Tables explicitly **not** touched by `DeleteMemo` (verified no code/cascade path): `reaction` (only read via `ListReactions` for the webhook payload, never deleted — `server/router/api/v1/memo_service.go:545-550`), and there are no remaining DB triggers on `memo` (the old modification-time trigger was dropped in `store/migration/sqlite/0.7/01__remove_triggers.sql`).
