**Tables affected when `DeleteMemo` runs:** `memo`, `memo_relation`, `attachment`, `memo_share`

Details, tracing the call path `APIV1Service.DeleteMemo` → `store.Store.DeleteMemo` → DB driver:

- **`memo`** — the target memo row is deleted directly (`repo/store/db/sqlite/memo.go:237-248`, and equivalent postgres/mysql drivers). Additionally, before deleting the target memo, `DeleteMemo` in `repo/server/router/api/v1/memo_service.go:567-577` looks up child "comment" memos via `memo_relation` (type `COMMENT`) and recursively calls `store.DeleteMemo` on each, so multiple `memo` rows can be deleted per call.
- **`memo_relation`** — explicitly cleaned up in `store.Store.DeleteMemo` (`repo/store/memo.go:140-147`), which calls the driver's `DeleteMemoRelation` twice: once where the memo is the source (`memo_id`) and once where it's the target (`related_memo_id`), e.g. `repo/store/db/sqlite/memo_relation.go:137-154`.
- **`attachment`** — `store.Store.DeleteMemo` lists attachments tied to the memo (`FindAttachment{MemoID: &delete.ID}`) and deletes each one via `s.DeleteAttachment` (`repo/store/memo.go:148-157`, `repo/store/attachment.go:132-149`), which issues `DELETE FROM attachment WHERE id = ?` (`repo/store/db/sqlite/attachment.go:211-221`).
- **`memo_share`** — not deleted by explicit Go code, but cascaded at the database level: the schema defines `memo_share.memo_id` with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` identically in sqlite, postgres, and mysql (`repo/store/migration/sqlite/LATEST.sql:101-112`, `repo/store/migration/postgres/LATEST.sql:100-111`, `repo/store/migration/mysql/LATEST.sql:100-111`), so deleting the `memo` row cascades to remove its `memo_share` rows.
  - Caveat: the sqlite connection is opened with `_pragma=foreign_keys(0)` (`repo/store/db/sqlite/sqlite.go:53`), which disables FK enforcement, so on sqlite this cascade is declared but not actually enforced at runtime; it is enforced on postgres/mysql.

Not affected: `reaction` rows tied to the memo are only read (`ListReactions`, `repo/server/router/api/v1/memo_service.go:545-550`) for building the webhook payload — they are never deleted, and the `reaction` table has no FK to `memo` (`repo/store/migration/sqlite/LATEST.sql:91-99`), so reactions on a deleted memo are left orphaned.
