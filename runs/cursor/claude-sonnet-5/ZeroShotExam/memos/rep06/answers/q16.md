When the API's `DeleteMemo` handler (`server/router/api/v1/memo_service.go:518-582`) calls into the store, the actual deletion work happens in `Store.DeleteMemo` (`store/memo.go:140-159`). Before deleting the memo row itself (via `s.driver.DeleteMemo`), that function deletes:

1. **Memo relations** — all `memo_relation` rows where the memo is the source (`DeleteMemoRelation{MemoID: &delete.ID}`) and all rows where the memo is the target/related memo (`DeleteMemoRelation{RelatedMemoID: &delete.ID}`), covering both directions of relations like comments/references (`store/memo.go:142-147`).
2. **Attachments** — it lists all attachments linked to the memo (`ListAttachments` with `MemoID`) and deletes each one individually via `DeleteAttachment` (which also removes the underlying attachment storage/file), before the memo row is removed (`store/memo.go:148-157`).

Only after these two cleanup steps does it call `s.driver.DeleteMemo(ctx, delete)` (`store/memo.go:158`), which issues the actual `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237-248`, with equivalent logic in the postgres/mysql drivers).

Note: one level up, the API handler itself also deletes memo *comments* (child memos linked via a `MemoRelationComment` relation) by recursively calling `Store.DeleteMemo` for each comment's `MemoID` before deleting the target memo (`server/router/api/v1/memo_service.go:567-577`), but that recursion just repeats the same relation+attachment cleanup described above for each comment memo — it isn't a distinct record kind at the store layer.
