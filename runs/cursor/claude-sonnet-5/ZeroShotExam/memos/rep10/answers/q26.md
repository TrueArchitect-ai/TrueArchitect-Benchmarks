When `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518-593`, delegating to `store.Store.DeleteMemo` in `store/memo.go:140-159` and the driver-level `DeleteMemo`/`DeleteMemoRelation`/`DeleteAttachment` implementations, e.g. `store/db/sqlite/memo.go:237-248`), the following tables are affected:

- **`memo`** — the target memo row is deleted directly (`DELETE FROM memo WHERE id = ?`); if the memo has comments, each comment memo is also deleted via a recursive call to `store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`).
- **`memo_relation`** — explicitly cleaned up in `store.DeleteMemo` for rows where the memo is either `memo_id` or `related_memo_id` (`store/memo.go:141-147`), and again for each deleted comment memo.
- **`attachment`** — explicitly cleaned up by listing and deleting all attachments tied to the memo (`store/memo.go:148-157`), and again for each deleted comment memo.
- **`memo_share`** — not touched by any Go code, but deleted via an explicit DB-level `ON DELETE CASCADE` foreign key on `memo_share.memo_id → memo.id` (`store/migration/sqlite/LATEST.sql:101-110`, mirrored in the postgres and mysql `LATEST.sql` schemas), so deleting the `memo` row cascades to `memo_share`.

Note: `reaction` rows tied to the memo (via `content_id`) are only read (for the deleted-webhook payload) and are **not** deleted or cascaded — there's no FK/cascade for that table, so they're not included in the affected-tables list.
