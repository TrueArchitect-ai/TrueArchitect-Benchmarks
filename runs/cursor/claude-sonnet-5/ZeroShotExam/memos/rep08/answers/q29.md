q29.

Frontend requests are authenticated via a Connect-RPC `Interceptor` defined in `web/src/connect.ts` (the `authInterceptor`, lines 156-178). On every outgoing call it attaches `Authorization: Bearer <token>` using `setAuthorizationHeader`, pulling the token from `web/src/auth-state.ts` (`getAccessToken`/`getRequestToken`), and on an `Unauthenticated` response it calls `refreshAccessToken()` (which hits `AuthService.refreshToken`) and retries once before falling back to `redirectOnAuthFailure()` (`web/src/utils/auth-redirect.ts`).

Tokens managed:
- **Access token** – short-lived JWT kept in memory + `localStorage` (`memos_access_token` / `memos_token_expires_at` in `web/src/auth-state.ts`), sent as the `Authorization: Bearer` header.
- **Refresh token** – long-lived token stored as an HttpOnly cookie (`memos_refresh`), sent automatically via `credentials: "include"` (`fetchWithCredentials` in `web/src/connect.ts`) and never touched directly by JS.

Backend validation lives in the `github.com/usememos/memos/server/auth` package (`/bench/repo/server/auth`), specifically:
- `server/auth/token.go` – defines JWT claim types (`AccessTokenClaims`, `RefreshTokenClaims`) and `ParseAccessTokenV2`/`ParseRefreshToken` for signature/issuer/audience verification.
- `server/auth/authenticator.go` – the `Authenticator` type (`AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, `AuthenticateByPAT`, `Authenticate`/`AuthenticateToUser`) used by the gRPC/Connect API interceptors and file server to resolve the bearer token or refresh-token cookie into a `store.User`.

**Answer format:** `web/src/connect.ts` (authInterceptor); JWT access token (Bearer header, `web/src/auth-state.ts`) + JWT refresh token (HttpOnly `memos_refresh` cookie) + Personal Access Tokens (PAT, `memos_pat_` prefix, for programmatic API use); `server/auth` (`server/auth/authenticator.go`, `server/auth/token.go`)
