When `DeleteMemo` runs (handler in `server/router/api/v1/memo_service.go:518-593`, calling `store.Store.DeleteMemo` in `store/memo.go:140-159`), the following tables are affected:

- **`memo`** — the target memo row (and, for each comment relation, the comment memo rows) is deleted directly (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).
- **`memo_relation`** — explicitly cascaded in `store.Store.DeleteMemo`, which deletes rows where the memo is either the source (`MemoID`) or target (`RelatedMemoID`) of a relation (`store/memo.go:142-147`, executed via `store/db/sqlite/memo_relation.go:137-152` and the postgres/mysql equivalents). The handler also separately queries `memo_relation` for `MemoRelationComment` rows to find child comment memos to delete (`server/router/api/v1/memo_service.go:568-577`).
- **`attachment`** — explicitly cascaded: `store.Store.DeleteMemo` lists attachments for the memo and deletes each one via `DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`), which also deletes the underlying stored file/object but that's not a DB table.
- **`memo_share`** — cascaded via an explicit `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the schema (`store/migration/postgres/LATEST.sql:108-109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). Note: on SQLite this cascade won't actually fire at runtime because the driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so it's effectively cascade-only on Postgres/MySQL.

Not affected: `reaction` rows are only read (for the webhook payload) in the handler (`server/router/api/v1/memo_service.go:545-550`) but are never deleted, and the `reaction` table has no FK to `memo` (`content_id` is a plain text column, `store/migration/sqlite/LATEST.sql:91-99`), so reactions become orphaned rather than cascade-deleted.
