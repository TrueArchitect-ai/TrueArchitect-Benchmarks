q29.

Frontend requests are authenticated by the Connect-RPC `authInterceptor` defined in `web/src/connect.ts` (lines 156-178). This interceptor attaches a bearer token to every RPC (`setAuthorizationHeader` → `Authorization: Bearer <token>`), obtains it via `getRequestToken()`, and on a `Code.Unauthenticated` response transparently refreshes the token (via `refreshAccessToken()` → `AuthService.refreshToken`) and retries once before redirecting to login on failure (`redirectOnAuthFailure`).

Tokens it manages (state lives in `web/src/auth-state.ts`):
- **Access token** – a short-lived JWT kept in memory + `localStorage` (`memos_access_token`/`memos_token_expires_at`), sent as the `Authorization: Bearer` header on every request.
- **Refresh token** – a long-lived JWT stored as an HTTP-only cookie (`memos_refresh`), sent automatically via `credentials: "include"` and only used by the `AuthService.refreshToken` RPC to mint a new access token.

Backend validation lives in the `server/auth` package (`github.com/usememos/memos/server/auth`), specifically:
- `server/auth/token.go` — JWT constants, `GenerateAccessTokenV2`/`GenerateRefreshToken`, and `ParseAccessTokenV2`/`ParseRefreshToken` (HS256 JWT verification).
- `server/auth/authenticator.go` — the `Authenticator` type (`AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, `AuthenticateByPAT`, `AuthenticateToUser`) that resolves the bearer/cookie into a user; it's shared by the Connect/gRPC interceptors in `server/router/api/v1/connect_interceptors.go` and the file server.

**Answer format:** `web/src/connect.ts` (authInterceptor); access token (short-lived JWT, `Authorization: Bearer` header) and refresh token (long-lived JWT, `memos_refresh` cookie) — plus Personal Access Tokens supported server-side; `server/auth` (`github.com/usememos/memos/server/auth`)
