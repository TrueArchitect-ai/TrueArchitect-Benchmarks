Directly and via explicit cascade code, `DeleteMemo` affects these database tables:

- **`memo`** — the target memo row (and, for each comment reply found via `memo_relation`, those comment memo rows too) is deleted by `store.DeleteMemo`, which issues `DELETE FROM memo WHERE id = ?` (`server/router/api/v1/memo_service.go:567-582`, driver: `store/db/sqlite/memo.go:237-248` and the equivalent postgres/mysql drivers).
- **`memo_relation`** — before deleting the memo row, `store.DeleteMemo` explicitly calls `driver.DeleteMemoRelation` twice, once where the memo is the source (`memo_id`) and once where it's the target (`related_memo_id`), removing all relation rows (comments, references) tied to it (`store/memo.go:140-147`, driver: `store/db/sqlite/memo_relation.go:137-152`).
- **`attachment`** — `store.DeleteMemo` lists all attachments with `memo_id = delete.ID` and calls `s.DeleteAttachment` on each, which deletes the corresponding row via `DELETE FROM attachment WHERE id = ?` (`store/memo.go:148-157`, driver: `store/db/sqlite/attachment.go:211-221`).
- **`memo_share`** — not touched by explicit Go code, but the schema defines `memo_share.memo_id` with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, so the database automatically removes share rows when the memo row is deleted (`store/migration/sqlite/LATEST.sql:101-110`, matching definitions in `store/migration/postgres/LATEST.sql:108` and `store/migration/mysql/LATEST.sql:108`).

Note: `reaction` rows (keyed by `content_id`, no FK) are only read via `ListReactions` for the webhook payload in `DeleteMemo` (`server/router/api/v1/memo_service.go:545-550`) but are never deleted, so the `reaction` table is not affected by this operation.
