I now have full confirmation of the computation site, triggers, and exact extracted properties.

h14.

**Computation site:** `RebuildMemoPayload` — `server/runner/memopayload/runner.go:74-88`, which calls `markdownService.ExtractAll(memo.Content)` (concretely `(*service).ExtractAll` in `internal/markdown/markdown.go:356-422`, a single goldmark AST walk) and assigns the result into `memo.Payload.Tags` and `memo.Payload.Property` (the persisted `storepb.MemoPayload`).

**Triggers (recomputation):**
- `CreateMemo` — `server/router/api/v1/memo_service.go:108`, called on every new memo.
- `UpdateMemo` — `server/router/api/v1/memo_service.go:447`, called only when the update mask includes the `content` path (i.e. the memo's content is actually being changed), inside the `if path == "content"` branch at `server/router/api/v1/memo_service.go:436-451`.

(There's also a standalone `memopayload.Runner.RunOnce` batch job at `server/runner/memopayload/runner.go:27-72` that rebuilds the payload for all memos, but per the earlier finding it's not wired into any production caller — the two triggers above are the ones that actually run.)

**Extracted properties** (via `ExtractAll`, walking the goldmark AST once):
- `Tags` — all `#tag` occurrences (deduplicated, case-preserved) via tag-node detection.
- `Mentions` — all `@mention` occurrences (deduplicated, lower-cased usernames), though these aren't persisted by `RebuildMemoPayload` (only `Tags`/`Property` are stored).
- `Property.Title` — text of the first block-level child if it's an H1 heading.
- `Property.HasLink` — whether the content contains any link node.
- `Property.HasCode` — whether it contains a code block, fenced code block, or code span.
- `Property.HasTaskList` — whether it contains a task checkbox.
- `Property.HasIncompleteTasks` — whether any task checkbox is unchecked.

These derived fields (tags, title, has-link/code/task-list/incomplete-tasks) are what memo list/preview views read instead of user-supplied metadata — the user only supplies `Content`.
