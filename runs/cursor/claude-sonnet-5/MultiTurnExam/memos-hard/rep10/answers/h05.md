**Explicit Go code** — not a database-level rule (no `FOREIGN KEY ... ON DELETE CASCADE` exists on `reaction.creator_id`), and not "not at all" — reactions are actively deleted as part of the user-deletion transaction.

Evidence:

- Schema check: `reaction` table definitions in `store/migration/sqlite/LATEST.sql:92-98`, `store/migration/postgres/LATEST.sql:91-98`, and the equivalent MySQL migration (`store/migration/mysql/0.23/00__reactions.sql`) declare `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no foreign key / `ON DELETE CASCADE` tying reactions to the `user` table. So there is no database-level cascade rule doing this.
- Application code: each SQL driver's `DeleteUser` implementation explicitly removes reactions inside the same transaction as the user deletion:
  - `store/db/sqlite/user_delete.go:96` and `:102` call `deleteReactionsByContentIDsTx` / `deleteReactionsByCreatorTx` from `deleteUserTargetsTx`, implemented at `store/db/sqlite/user_delete.go:380-403` as `DELETE FROM reaction WHERE content_id IN (...)` (removes reactions on the deleted user's own memos) and `DELETE FROM reaction WHERE creator_id = ?` (removes reactions the user made on others' content).
  - Identical logic exists in `store/db/postgres/user_delete.go:96,102,380-401` and `store/db/mysql/user_delete.go:96,102,417-438`.
  - These deletions happen before `deleteUserRowTx` deletes the `user` row itself (e.g. `store/db/sqlite/user_delete.go:92-126`), all within one `BeginTx`/`Commit` transaction in `DeleteUser` (`store/db/sqlite/user_delete.go:29-59`), so reaction cleanup is guaranteed to run alongside user deletion.

Conclusion: reaction removal on user deletion is handled by **explicit Go code** in each driver's `user_delete.go`, not by a database cascade constraint.
