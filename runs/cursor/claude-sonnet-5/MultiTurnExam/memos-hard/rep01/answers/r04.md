**Premise correction:** Neither. The webhook delivery workers don't consume from any external message broker — there is no NATS or RabbitMQ dependency anywhere in this repository (a search of all Go files and `go.mod`/`go.sum` for "nats", "rabbitmq", or "amqp" returns zero matches).

**Actual mechanism:** Webhook dispatch uses a simple in-process, in-memory Go channel as its "queue," entirely within `internal/webhook/webhook.go`:

```25:55:/bench/repo/internal/webhook/webhook.go
var (
	...
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
)

func init() {
	for range 4 {
		go func() {
			for payload := range asyncPostQueue {
				if err := Post(payload); err != nil {
					slog.Warn("Failed to dispatch webhook asynchronously",
						slog.String("url", payload.URL),
						slog.String("activityType", payload.ActivityType),
						slog.Any("err", err))
				}
			}
		}()
	}
}
```

- The "queue" is `asyncPostQueue`, a buffered `chan *WebhookRequestPayload` with capacity 128, declared at `internal/webhook/webhook.go:39`.
- Four worker goroutines are spawned in that same file's package `init()` (`internal/webhook/webhook.go:42-55`) to range over the channel and call `Post` (the actual HTTP-delivery function, see [h02](h02)/[h06](h06)) for each payload.
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking channel send and drops (with a warning log) if the buffer is full — there's no persistence, acknowledgment, or redelivery semantics like a real broker would provide.

So this is purely an in-memory fan-out queue backed by a Go channel and goroutine pool, not a connection to NATS, RabbitMQ, or any other broker — there is no "queue declaration" on an external system to point to.
