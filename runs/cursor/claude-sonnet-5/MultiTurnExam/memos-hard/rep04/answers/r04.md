**Premise correction:** The webhook delivery workers do not consume from NATS, RabbitMQ, or any external message broker. A search of the entire repository (Go source and `go.mod`) for `nats`, `rabbitmq`, `amqp`, and `kafka` returns zero matches — none of these libraries are even dependencies.

**Actual mechanism:** Webhook dispatch uses a simple in-process, unbuffered-to-the-caller Go channel as its "queue" — no broker, no network hop, no persistence. In `internal/webhook/webhook.go:39`, `asyncPostQueue` is declared as `make(chan *WebhookRequestPayload, 128)` — a buffered channel of capacity 128, held entirely in the memos process's memory. Four worker goroutines are spun up once at package initialization (`func init()`, `internal/webhook/webhook.go:42-55`), each running `for payload := range asyncPostQueue { ... Post(payload) ... }`. Producers call `webhook.PostAsync(payload)` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto `asyncPostQueue`, dropping (and logging a warning about) the payload if the channel is full rather than blocking. This queue is local to a single process and is lost on restart — it is not backed by any broker.
