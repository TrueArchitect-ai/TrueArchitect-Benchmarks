**Mechanism:** By explicit Go code (not a database-level cascade rule).

**Evidence locations:**

- `store/reaction.go` — the `reaction` table schema has no documented `ON DELETE CASCADE` foreign key handling in this codebase's Go migrations; deletion is driven entirely by explicit statements in the per-user delete flow.
- `server/router/api/v1/user_service.go:414` — `DeleteUser` handler calls `s.Store.DeleteUser(ctx, &store.DeleteUser{...})`, which dispatches to the driver (`store/user.go:171-172`).
- Each SQL driver's `user_delete.go` runs the whole deletion inside one transaction (`deleteUserTargetsTx`), which explicitly issues **two** separate `DELETE FROM reaction` statements before deleting the user row:
  - `deleteReactionsByContentIDsTx` — removes reactions left by *anyone* on memos/comments owned by the user being deleted (`DELETE FROM reaction WHERE content_id IN (...)`), e.g. `store/db/sqlite/user_delete.go:380-398`, `store/db/postgres/user_delete.go:380-398`, `store/db/mysql/user_delete.go:417-436`.
  - `deleteReactionsByCreatorTx` — removes reactions the deleted user made on any content (`DELETE FROM reaction WHERE creator_id = ?`), e.g. `store/db/sqlite/user_delete.go:400-402`, `store/db/postgres/user_delete.go:400-402`, `store/db/mysql/user_delete.go:438-440`.
  - Both calls are wired into the deletion sequence at `store/db/sqlite/user_delete.go:96` and `:102` (mirrored identically in the `postgres` and `mysql` packages), which run before `deleteUserRowTx` deletes the `user` row — all inside the same transaction as the rest of the cleanup (memos, attachments, memo shares, inbox items, identities, settings).

This pattern is identical across all three supported backends (`store/db/sqlite`, `store/db/postgres`, `store/db/mysql`), confirming it's application-level cleanup rather than a DB-enforced `ON DELETE CASCADE`.
