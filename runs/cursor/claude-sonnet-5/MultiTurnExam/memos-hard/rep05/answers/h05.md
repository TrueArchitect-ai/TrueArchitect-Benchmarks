**Evidence locations:**

1. **Schema check — no DB-level cascade exists.** The `reaction` table definition in all three dialects has no foreign key / `ON DELETE CASCADE` clause on `creator_id` or `content_id` — it's just a plain column plus a `UNIQUE` constraint:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`

   So deleting a `user` row alone would never remove `reaction` rows through the schema.

2. **Explicit Go code performs the removal.** Each driver's `DeleteUser` transaction explicitly deletes reactions in two passes before deleting the user row:
   - Reactions on content the deleted user authored (memos/comments), matched by `content_id`, via `deleteReactionsByContentIDsTx`.
   - Reactions the deleted user personally created on any content, via `deleteReactionsByCreatorTx`.

   Both are called from `deleteUserTargetsTx`, e.g.:

Since the deletion happens inside the same transaction as the user row deletion (`deleteUserRowTx`, e.g. `store/db/sqlite/user_delete.go:461-464`), the reaction cleanup is atomic with the user delete, but it is driven entirely by explicit application code, not a database trigger/foreign-key rule.
