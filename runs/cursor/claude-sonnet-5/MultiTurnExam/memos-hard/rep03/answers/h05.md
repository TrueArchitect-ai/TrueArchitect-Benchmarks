All three drivers (SQLite, Postgres, MySQL) explicitly delete reactions in Go code within the `DeleteUser` transaction, both by content-id (reactions on the deleted user's memos/comments) and by creator (reactions the user made on other memos).

h05.

**Mechanism:** Explicit Go code (application-level deletion inside the `DeleteUser` transaction), not a database-level cascade rule.

**Evidence locations:**

- All three store drivers implement `DeleteUser` with an explicit, ordered sequence of `DELETE` statements executed in application code, calling `deleteReactionsByContentIDsTx` and `deleteReactionsByCreatorTx` before other deletions:
  - `store/db/sqlite/user_delete.go:96-104` (called from `deleteUserTargetsTx`), with the reaction deletes implemented at `store/db/sqlite/user_delete.go:380-403`.
  - `store/db/postgres/user_delete.go:96-104`, implemented at `store/db/postgres/user_delete.go:380-403`.
  - `store/db/mysql/user_delete.go:96-104`, implemented at `store/db/mysql/user_delete.go:417-440`.
- `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` for every memo/comment the user authored (content IDs collected via the recursive/iterative memo-tree walk, e.g. `store/db/sqlite/user_delete.go:129-166`), removing reactions left by *other* users on the deleted user's content.
- `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user themselves made on any memo.
- I checked for a database-level rule (e.g., a `FOREIGN KEY ... ON DELETE CASCADE` on `reaction.creator_id` or `reaction.content_id`) by searching the schema/migration definitions; no such migrations directory or DDL with cascade rules on the `reaction` table was found in this repo — the drivers manage referential cleanup entirely themselves, which is consistent with the explicit `DELETE FROM reaction` statements above being necessary at all (a cascade would make them redundant).
- `store/db/reaction.go`-style helpers weren't otherwise involved; the deletion logic lives solely in the driver-specific `user_delete.go` files, and there is a dedicated test at `store/test/user_delete_test.go` exercising user deletion (consistent with reactions being cleaned up as part of that flow).
