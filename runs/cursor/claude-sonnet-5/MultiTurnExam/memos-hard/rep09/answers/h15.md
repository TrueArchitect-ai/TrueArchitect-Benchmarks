h15.

Memo visibility (`store.Public` / `store.Protected` / `store.Private`) is checked independently in each of these distinct server surfaces:

- **Core gRPC/Connect memo-read gate** — `checkMemoReadAccess` in `server/router/api/v1/memo_service.go:39-64` (denies non-creators access to a `Private` memo; used by `GetMemo`/related-parent lookups).
- **Memo comment service** — `server/router/api/v1/memo_service_comments.go:41-42` (blocks creating a comment on a `Private` memo you don't own), and it separately reuses `checkMemoReadAccess` at `memo_service_comments.go:148` for listing comments.
- **Reaction service** — `server/router/api/v1/reaction_service.go:30-39` and `:83-84` (its own inline `Visibility` checks gating who may list/create reactions on a memo).
- **Attachment service (gRPC/Connect)** — `server/router/api/v1/attachment_service.go:445-452` (own inline check before streaming/serving a memo's attachment through the API service).
- **Memo–attachment relation service** — `server/router/api/v1/memo_attachment_service.go:214-223` (own inline visibility check before exposing attachment associations).
- **Native HTTP file-server surface** — `checkAttachmentPermission` in `server/router/fileserver/fileserver.go:650-703` (a completely separate, non-gRPC HTTP route for serving raw attachment bytes; adds its own public/private/share-token logic distinct from all the gRPC-side checks).
- **RSS feed surface** — `server/router/rss/rss.go:90` and `:141` (enforces visibility not via a permission check but by constraining the store query itself to `VisibilityList: []store.Visibility{store.Public}`, so private/protected memos are never fetched for the feed in the first place).
- **Real-time SSE broadcast surface** — `(*SSEClient).canReceive` in `server/router/api/v1/sse_hub.go:134-144` (filters which connected live-update subscribers receive a given memo event based on `event.Visibility`, independent of the REST/gRPC read path).
