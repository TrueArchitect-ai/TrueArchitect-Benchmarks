When `Store.DeleteMemo` (`repo/store/memo.go:140`) runs, the following tables are affected:

1. **memo** — the target row itself is deleted (final step via `s.driver.DeleteMemo`)
2. **memo_relation** — explicitly deleted in Go code, both where the memo is `memo_id` and where it is `related_memo_id`
3. **attachment** — explicitly deleted in Go code (each attachment linked via `memo_id` is fetched via `ListAttachments` and removed via `DeleteAttachment`, which also removes the underlying storage blob)
4. **memo_share** — has a `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the schema (e.g. `repo/store/migration/sqlite/LATEST.sql:109`, and equivalently in the MySQL/Postgres schemas), so rows cascade-delete at the DB level in MySQL and PostgreSQL. Note: SQLite opens its connection with `_pragma=foreign_keys(0)` (`repo/store/db/sqlite/sqlite.go:53`), which disables FK enforcement, so this cascade does **not** actually fire on SQLite despite being declared in its schema.

Not affected/no cascade found: `reaction` (keyed by `content_id`, a text reference, with no FK to `memo`) is not cleaned up by `DeleteMemo`.
