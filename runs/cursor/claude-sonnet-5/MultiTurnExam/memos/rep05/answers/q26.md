When `Store.DeleteMemo` runs, the following tables are affected:

1. **`memo_relation`** — explicitly deleted in code (both as source `memo_id` and target `related_memo_id`) — `store/memo.go`
2. **`attachment`** — explicitly deleted in code via `ListAttachments`/`DeleteAttachment` for all attachments linked to the memo — `store/memo.go`
3. **`memo_share`** — deleted implicitly via a database-level `ON DELETE CASCADE` foreign key (`memo_id REFERENCES memo(id) ON DELETE CASCADE`) — `store/migration/postgres/LATEST.sql`
4. **`memo`** — the memo row itself is deleted last via `driver.DeleteMemo`

Note: `reaction` rows referencing the memo's content (via `content_id`, e.g. `"memos/xxx"`) have no explicit foreign key or code-level cascade in the schema I found, so they are not automatically cleaned up by `DeleteMemo`.
