When `Store.DeleteMemo` (`store/memo.go:140`) runs, the following tables are affected:

- **memo** — the memo row itself is deleted directly (`s.driver.DeleteMemo`)
- **memo_relation** — rows where the memo is source or target are explicitly deleted first (`s.driver.DeleteMemoRelation` calls, both by `MemoID` and `RelatedMemoID`)
- **attachment** — attachments linked to the memo are explicitly fetched and deleted (`ListAttachments` + `DeleteAttachment` loop)
- **memo_share** — not touched by explicit Go code, but cascades automatically at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`)

Note: I checked the schema for other foreign keys referencing `memo(id)` and found only `memo_share` has an explicit cascading FK; `reaction` references content only loosely via a `content_id` string column (no FK), so it is not affected by the delete.
