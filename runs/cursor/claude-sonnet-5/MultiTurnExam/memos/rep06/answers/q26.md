When `DeleteMemo` runs, the following tables are affected:

- **`memo`** — the target row itself is deleted (`store/db/postgres/memo.go` / equivalent dialect drivers)
- **`memo_relation`** — explicitly cleaned up in `Store.DeleteMemo` (`store/memo.go`, lines 142-147), removing rows where the memo is either the source (`memo_id`) or target (`related_memo_id`)
- **`attachment`** — explicitly cleaned up in `Store.DeleteMemo` (`store/memo.go`, lines 149-157), which lists and deletes each attachment linked via `memo_id`
- **`memo_share`** — affected via an explicit `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` constraint declared in the schema (`store/migration/postgres/LATEST.sql` line 108; same in `mysql/LATEST.sql` and `sqlite/LATEST.sql`), so the database cascades the deletion automatically

(Note: `reaction` rows tied to the memo are **not** cleaned up by cascade or explicit code in `Store.DeleteMemo` — the API handler only reads them for the webhook payload before deletion in `server/router/api/v1/memo_service.go`, so they can be left orphaned by `content_id`.)
