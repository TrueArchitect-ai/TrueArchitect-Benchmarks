**memo, memo_relation, attachment**

From `store.Store.DeleteMemo` (`store/memo.go:140-159`):
- `memo_relation` — explicit `DeleteMemoRelation` calls for both `memo_id` and `related_memo_id` matches
- `attachment` — attachments found via `ListAttachments` are deleted individually via `DeleteAttachment`
- `memo` — the memo row itself is deleted last via `s.driver.DeleteMemo`

The calling handler (`APIV1Service.DeleteMemo`, `server/router/api/v1/memo_service.go:518-593`) also recursively invokes `Store.DeleteMemo` for each memo comment (itself a `memo` row linked via `memo_relation`), touching the same three tables again. It queries the `reaction` table (`ListReactions`) only to build the webhook payload — reactions are not deleted, and there's no foreign-key cascade defined on `reaction` (see `store/migration/postgres/LATEST.sql:91-98`, which has no FK to `memo`), so that table is unaffected by deletion.
