**attachment, memo, memo_relation**

When `Store.DeleteMemo` runs (`store/memo.go`), it explicitly touches these tables:

1. **memo_relation** — deleted where the memo is source or target (`DeleteMemoRelation` in `store/memo.go`; SQL in e.g. `store/db/sqlite/memo_relation.go`)
2. **attachment** — rows with that `memo_id` removed via `DeleteAttachment` (`store/attachment.go`; SQL `DELETE FROM attachment` in e.g. `store/db/sqlite/attachment.go`)
3. **memo** — the memo row itself (`driver.DeleteMemo`; SQL `DELETE FROM memo` in e.g. `store/db/sqlite/memo.go`)

The API `DeleteMemo` handler (`server/router/api/v1/memo_service.go`) first recursively calls `Store.DeleteMemo` on comment memos, but that uses the same three tables.

Tables **not** cleaned by this path include `reaction`, `memo_share`, and `inbox` (reactions are listed for webhooks only; they are not deleted in `DeleteMemo`).
