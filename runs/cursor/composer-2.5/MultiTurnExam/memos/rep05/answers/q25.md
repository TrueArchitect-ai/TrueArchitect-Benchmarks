CEL (via cel-go) memo filter engine — internal/filter; the API validates the filter with `filter.DefaultEngine().CompileToStatement`, stores the string on `FindMemo.Filters`, and each dialect driver calls `filter.AppendConditions`, which parses CEL with `cel-go`, normalizes the AST to a dialect-agnostic IR (`parser.go`/`ir.go`), and renders SQL plus placeholders via `render.go` (`?` for SQLite/MySQL, `$n` for Postgres) into the query `WHERE` clause.

The filter engine lives under `internal/filter/` and is documented in `internal/filter/README.md`:

```3:20:internal/filter/README.md
This package houses the memo-only filter engine that turns standard CEL syntax
into SQL fragments for the subset of expressions supported by the memo schema.
The engine follows a three phase pipeline inspired by systems
such as Calcite or Prisma:

1. **Parsing** – CEL expressions are parsed with `cel-go` and validated against
   the memo-specific environment declared in `schema.go`.
2. **Normalization** – the raw CEL AST is converted into an intermediate
   representation (IR) defined in `ir.go`.
3. **Rendering** – the renderer in `render.go` walks the IR and produces a SQL
   fragment plus placeholder arguments tailored to a target dialect
   (`sqlite`, `mysql`, or `postgres`).
```

Validation happens in `validateFilter` in `server/router/api/v1/shortcut_service.go` (used by `ListMemos` in `memo_service.go`). Dialect drivers invoke `filter.AppendConditions` — for example in `store/db/sqlite/memo.go`, `store/db/postgres/memo.go`, and `store/db/mysql/memo.go` — each passing its dialect constant (`DialectSQLite`, `DialectPostgres`, or `DialectMySQL`).
