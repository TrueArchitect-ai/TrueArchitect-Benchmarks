**memo, memo_relation, attachment**

`Store.DeleteMemo` in `store/memo.go` explicitly removes related rows, then deletes the memo:

```140:158:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	// ...
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

So each `DeleteMemo` call affects:

1. **memo_relation** — rows where the memo is `memo_id` or `related_memo_id`
2. **attachment** — rows linked via `memo_id`
3. **memo** — the memo row itself (`DELETE FROM memo` in e.g. `store/db/sqlite/memo.go`)

The API handler in `server/router/api/v1/memo_service.go` first deletes comment memos recursively (lines 567–577), so the same three tables can be touched multiple times, but no others.

**Not** cleaned up by `DeleteMemo` application code: `reaction`, `memo_share`, `inbox`. `memo_share` has `ON DELETE CASCADE` in `store/migration/*/LATEST.sql`, but SQLite runs with `foreign_keys(0)` in `store/db/sqlite/sqlite.go`, so that cascade does not apply there; Postgres/MySQL may cascade at the DB level when the memo row is deleted.
