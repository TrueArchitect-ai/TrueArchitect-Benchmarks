q26. memo, memo_relation, attachment

`Store.DeleteMemo` in `store/memo.go` explicitly removes rows from these tables before deleting the memo itself:

```140:158:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	// ...
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

That maps to:

- **memo_relation** — via `DeleteMemoRelation` (`store/db/sqlite/memo_relation.go`)
- **attachment** — via `DeleteAttachment` (`store/db/sqlite/attachment.go`)
- **memo** — via the driver’s `DeleteMemo` (`store/db/sqlite/memo.go`)

The API `DeleteMemo` handler in `server/router/api/v1/memo_service.go` also recursively calls `Store.DeleteMemo` on comment memos first, which hits the same three tables again for each comment.

Tables **not** affected by `DeleteMemo`: `reaction`, `memo_share`, and `inbox`. Although `memo_share` defines `ON DELETE CASCADE` in `store/migration/postgres/LATEST.sql` and `store/migration/mysql/LATEST.sql`, `Store.DeleteMemo` does not delete shares explicitly, and SQLite disables foreign keys in `store/db/sqlite/sqlite.go` (`foreign_keys(0)`).
