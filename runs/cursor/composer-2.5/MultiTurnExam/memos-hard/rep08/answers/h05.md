When a user is deleted, emoji reactions are removed by explicit Go `DELETE` statements inside the `DeleteUser` transaction, not by a database foreign-key cascade.

In `deleteUserTargetsTx`, each driver deletes reactions in two steps:

1. **`deleteReactionsByContentIDsTx`** — removes reactions on the deleted user’s memos (`DELETE FROM reaction WHERE content_id IN ...`)
2. **`deleteReactionsByCreatorTx`** — removes reactions the user created on other content (`DELETE FROM reaction WHERE creator_id = ...`)

The same pattern appears in `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go`.

**What I checked for a DB-level rule:** migration schemas show the `reaction` table has no `FOREIGN KEY` on `creator_id` (or `content_id`) to `user`. In `store/migration/sqlite/LATEST.sql`, it only has columns plus `UNIQUE(creator_id, content_id, reaction_type)` — no `ON DELETE CASCADE` for user deletion.

**What I checked for tests:** `store/test/user_delete_test.go` (`TestDeleteUserCleansRelatedData`) verifies that after user deletion:
- the user’s reaction on another user’s memo is removed
- another user’s reaction on the deleted user’s memo is removed
- unrelated reactions on surviving memos remain

**Entry point:** `store/user.go` delegates to `s.driver.DeleteUser`; the API calls that via `server/router/api/v1/user_service.go` → `DeleteUser`. No separate reaction cleanup exists outside the driver `user_delete.go` files.
