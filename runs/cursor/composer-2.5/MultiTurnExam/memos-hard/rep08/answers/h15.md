Memo visibility is not enforced in one place. These are separate server surfaces with their own checks or query filters:

| Site | Mechanism |
|---|---|
| **checkMemoReadAccess** | Blocks `GetMemo`, parent-memo checks, and `ListMemoComments` unless the caller may read the memo (`Public` = open; `Protected`/`Private` require auth; `Private` = creator only). |
| **ListMemos filter** | Restricts listed memos: anonymous users get `PUBLIC` only; authenticated users get a CEL filter or `VisibilityList` excluding others’ private memos. |
| **checkAttachmentAccess** | gRPC attachment APIs inherit linked memo visibility (`attachment_service.go:445-453`). |
| **checkAttachmentPermission** | HTTP `/file/attachments/...` routes apply the same rules, with share-token and anonymous-instance exceptions (`fileserver.go:674-701`). |
| **RSS / sitemap** | Only `PUBLIC` memos are queried (`rss.go:90`, `frontend.go:150`). |
| **SSE canReceive** | Live events for `Private` memos go only to creator/admin (`sse_hub.go:134-143`). |
| **Reactions / memo attachments / comments** | Each sub-API re-checks visibility before exposing data (`reaction_service.go`, `memo_attachment_service.go`, `memo_service_comments.go:41`). |
| **Relations & converter batch loads** | Related memos are filtered via `memoFilter` so non-visible memos don’t appear in relation graphs (`memo_relation_service.go:107-112`, `memo_service_converter.go:182-187`). |
| **Stats & notifications** | Stats queries use `VisibilityList`; inbox/email use `canViewerAccessMemo` so notification content/links respect visibility. |

**Note:** `GetMemoByShare` (`server/router/api/v1/memo_share_service.go`) and file-server `share_token` handling (`fileserver.go:684-688`) use share tokens as an alternate access path rather than the visibility enum checks above.
