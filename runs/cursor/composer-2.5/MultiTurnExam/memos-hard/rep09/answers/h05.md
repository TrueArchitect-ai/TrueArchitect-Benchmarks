Reactions are removed in application code during user deletion, not by a database cascade.

Each driver’s `DeleteUser` flow calls `deleteUserTargetsTx`, which explicitly deletes reactions in two passes:

1. **`deleteReactionsByContentIDsTx`** — reactions on memos owned by the deleted user (`DELETE FROM reaction WHERE content_id IN ...`)
2. **`deleteReactionsByCreatorTx`** — reactions the deleted user left on other users’ content (`DELETE FROM reaction WHERE creator_id = ...`)

**What I checked for database-level rules:** `store/migration/sqlite/LATEST.sql` (and the mysql/postgres equivalents) define the `reaction` table with no foreign key to `user` or `memo` — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. By contrast, `memo_share` does declare `FOREIGN KEY ... ON DELETE CASCADE`.

**Other paths checked:** `store/user.go` delegates to the driver’s `DeleteUser`; `server/router/api/v1/user_service.go` calls `Store.DeleteUser` and does not delete reactions itself. `store/test/user_delete_test.go` verifies that deleting a user removes their reactions and reactions on their memos while keeping unrelated peer reactions.
