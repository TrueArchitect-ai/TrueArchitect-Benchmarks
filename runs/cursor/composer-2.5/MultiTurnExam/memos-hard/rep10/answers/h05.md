When a user is deleted, emoji reactions are removed by explicit Go code in each driver’s `DeleteUser` transaction, not by a database cascade or trigger on `reaction`.

In `deleteUserTargetsTx`, the code runs two DELETE steps:

1. **`deleteReactionsByContentIDsTx`** — removes reactions on memos being deleted (`DELETE FROM reaction WHERE content_id IN ...`) at `store/db/sqlite/user_delete.go:96-97`, `:380-387` (same pattern in mysql/postgres `user_delete.go:96-97`, `:417-424` / `:380-387`).
2. **`deleteReactionsByCreatorTx`** — removes all reactions created by the user (`DELETE FROM reaction WHERE creator_id = ...`) at `store/db/sqlite/user_delete.go:102-103`, `:400-402` (same in mysql/postgres).

That logic is invoked from `DeleteUser` via `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:29-44`), and the store layer delegates to the driver (`store/user.go:171-172`).

**Schema check:** `reaction` in `store/migration/sqlite/LATEST.sql:92-99` (and mysql/postgres `LATEST.sql`) has no `FOREIGN KEY` on `creator_id` or `content_id`. The only `ON DELETE CASCADE` in those schemas is on `memo_share.memo_id` → `memo(id)`, not on `reaction`.

**Test check:** `TestDeleteUserCleansRelatedData` in `store/test/user_delete_test.go` creates reactions from both the deleted user and a peer (`:97-114`), deletes the user (`:184-185`), and asserts only the peer’s unrelated reaction remains (`:216-220`).

**Not checked for reaction cleanup:** server/router API layer (deletion is handled in the store drivers above).
