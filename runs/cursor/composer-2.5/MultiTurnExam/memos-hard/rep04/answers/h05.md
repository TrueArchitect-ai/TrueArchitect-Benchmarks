When a user is deleted, reactions are removed by explicit Go `DELETE` statements inside each driver’s `DeleteUser` transaction, not by database cascade rules.

In `deleteUserTargetsTx`, each driver calls:

1. **`deleteReactionsByContentIDsTx`** — removes reactions on the deleted user’s memos (`DELETE FROM reaction WHERE content_id IN ...`)
2. **`deleteReactionsByCreatorTx`** — removes reactions the user created (`DELETE FROM reaction WHERE creator_id = ...`)

Example from `store/db/sqlite/user_delete.go`:

```92:104:store/db/sqlite/user_delete.go
func deleteUserTargetsTx(ctx context.Context, tx *sql.Tx, userID int32, targets *deleteUserTargetSet) error {
	memoIDs := memoIDsFromRefs(targets.memos)
	contentIDs := memoContentIDsFromRefs(targets.memos)

	if err := deleteReactionsByContentIDsTx(ctx, tx, contentIDs); err != nil {
		return err
	}
	// ...
	if err := deleteReactionsByCreatorTx(ctx, tx, userID); err != nil {
		return err
	}
```

The same pattern exists in `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go`.

**What I checked for DB-level rules:** the `reaction` table definitions in all three `LATEST.sql` migration files define columns and a `UNIQUE(creator_id, content_id, reaction_type)` constraint, but no foreign keys and no `ON DELETE CASCADE`.

**What I checked for tests/entry point:** `store/test/user_delete_test.go` (`TestDeleteUserCleansRelatedData`) creates reactions by the deleted user and on their memos, deletes the user, and asserts only unrelated peer reactions remain. The API path goes through `server/router/api/v1/user_service.go` → `store/user.go` → the driver `DeleteUser` implementations above.
