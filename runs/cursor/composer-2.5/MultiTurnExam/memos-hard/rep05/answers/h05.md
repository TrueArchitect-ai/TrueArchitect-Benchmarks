h05.

**explicit Go code**; **`store/db/sqlite/user_delete.go` (and the matching `user_delete.go` files under `store/db/mysql/` and `store/db/postgres/`)**

When a user is deleted, reactions are removed in the `DeleteUser` transaction by explicit SQL executed from Go — not by database cascades or triggers.

**What I checked:**

1. **Delete-user implementation** — `deleteUserTargetsTx` in `store/db/sqlite/user_delete.go:92-127` calls:
   - `deleteReactionsByContentIDsTx` (`:380-387`) — `DELETE FROM reaction WHERE content_id IN (...)` for reactions on memos in the deleted user’s memo tree
   - `deleteReactionsByCreatorTx` (`:400-403`) — `DELETE FROM reaction WHERE creator_id = ?` for any remaining reactions created by that user

   The same pattern exists in `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go`.

2. **Schema/migrations** — `reaction` in `store/migration/sqlite/LATEST.sql`, `store/migration/mysql/LATEST.sql`, and `store/migration/postgres/LATEST.sql` has no foreign keys, `ON DELETE CASCADE`, or triggers. A repo-wide search under `store/migration/` found no cascade/trigger rules for `reaction`.

3. **Tests** — `store/test/user_delete_test.go:97-114,216-220` creates reactions for both users, deletes one user, and asserts only the peer’s reaction on the kept memo remains (the deleted user’s reaction is gone).
