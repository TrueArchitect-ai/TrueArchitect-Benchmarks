**Mechanism:** explicit Go code (not a database-level rule). When a user is deleted, the store driver runs two explicit `DELETE FROM reaction` steps inside the delete-user transaction: (1) reactions whose `content_id` matches memos in the deleted user’s memo tree, and (2) reactions whose `creator_id` matches the deleted user. Reactions on other users’ memos that the deleted user did not create are left alone.

**Evidence locations:**

1. **Delete-user transaction issues explicit reaction deletes** — `store/db/sqlite/user_delete.go` (same pattern in `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`):
   - `deleteUserTargetsTx` calls `deleteReactionsByContentIDsTx` and `deleteReactionsByCreatorTx` (lines 96–104)
   - `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` (lines 380–387)
   - `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` (lines 400–402)

2. **Call chain from API to store** — `server/router/api/v1/user_service.go` (`DeleteUser` → `s.Store.DeleteUser`, line 414) → `store/user.go` (`DeleteUser` delegates to `s.driver.DeleteUser`, line 172)

3. **No DB-level cascade on reactions** — `store/migration/sqlite/LATEST.sql` (lines 91–99): `reaction` has `creator_id`, `content_id`, and a `UNIQUE(creator_id, content_id, reaction_type)` constraint, but no `FOREIGN KEY` on `creator_id` or `content_id`. Same in `store/migration/sqlite/0.20/00__reaction.sql`.

4. **Behavior verified by test** — `store/test/user_delete_test.go`: after deleting a user, the user’s reaction on a peer memo is gone, reactions on deleted memos are gone, and an unrelated peer reaction remains (lines 97–114, 216–220).
