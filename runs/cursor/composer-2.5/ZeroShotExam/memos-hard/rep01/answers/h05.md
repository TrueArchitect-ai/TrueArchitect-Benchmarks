**Mechanism:** explicit Go code — emoji reactions are removed during `DeleteUser` in the store DB layer, not by database cascade rules.

**Evidence locations:**

1. **`store/db/sqlite/user_delete.go`** (same logic in **`store/db/postgres/user_delete.go`** and **`store/db/mysql/user_delete.go`**) — `deleteUserTargetsTx` calls:
   - `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` for reactions on the deleted user’s memo tree
   - `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` for all reactions created by that user

2. **`store/migration/sqlite/LATEST.sql`** (lines 91–99) — the `reaction` table has no `FOREIGN KEY` / `ON DELETE CASCADE` to `user` or `memo` (only `UNIQUE(creator_id, content_id, reaction_type)`). Contrast: `memo_share` does have `FOREIGN KEY ... ON DELETE CASCADE` (lines 109–110).

3. **`store/user.go`** — `Store.DeleteUser` delegates to `s.driver.DeleteUser` (no separate reaction logic at this layer).

4. **`server/router/api/v1/user_service.go`** — `DeleteUser` calls `s.Store.DeleteUser(...)` and handles attachment storage cleanup only; no reaction-specific code.

5. **Tests confirming behavior:**
   - **`store/test/user_delete_test.go`** — after delete, only the peer’s reaction on the surviving memo remains; the deleted user’s reaction is gone.
   - **`server/router/api/v1/test/user_service_delete_test.go`** — asserts reactions on deleted memos are empty and only peer reactions on foreign memos remain.

**What I checked:** user-delete implementations in sqlite/postgres/mysql DB drivers, reaction table migrations, the store/API delete-user call chain, and delete-user tests that set up reactions before deletion.
