The browser loads another user's avatar after the API returns a URL like `/file/users/{username}/avatar` (rewritten from the stored data URI in `convertUserFromStore` at `server/router/api/v1/user_service_converters.go`). The `<img>` in `UserAvatar` then issues `GET /file/users/{username}/avatar`. That request reaches stored data as follows (avatar bytes live in the `user.avatar_url` DB column as a base64 data URI, not as a separate file):

RegisterRoutes — server/router/fileserver/fileserver.go  
serveUserAvatar — server/router/fileserver/fileserver.go  
getCurrentUser — server/router/fileserver/fileserver.go  
AuthenticateToUser — server/auth/authenticator.go  
getUserByUsername — server/router/fileserver/fileserver.go  
GetUser — store/user.go  
ListUsers — store/user.go  
ListUsers — store/db/sqlite/user.go  
QueryContext (SELECT avatar_url FROM user) — store/db/sqlite/user.go  
parseDataURI — server/router/fileserver/fileserver.go  

Notes:
- Route registration happens in `server/server.go` via `fileServerService.RegisterRoutes(echoServer)`.
- On private instances (`Profile.AllowAnonymous()` is false), `getCurrentUser`/`AuthenticateToUser` must succeed before the lookup proceeds (`internal/profile/profile.go`).
- The DB driver is selected at startup in `store/db/db.go` (`sqlite` by default in `cmd/memos/main.go`; `mysql` and `postgres` use equivalent `ListUsers` in `store/db/mysql/user.go` and `store/db/postgres/user.go`).
- After `avatar_url` is read, `parseDataURI` decodes the data URI into raw image bytes returned by `c.Blob` in `serveUserAvatar`.
