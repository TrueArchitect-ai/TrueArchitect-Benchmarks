**Mechanism:** explicit Go code (not a database-level rule).

**Evidence locations:**

1. **Delete path:** `server/router/api/v1/user_service.go` (`DeleteUser`) calls `store/user.go` (`Store.DeleteUser`), which delegates to per-driver delete logic in `store/db/sqlite/user_delete.go`, `store/db/postgres/user_delete.go`, and `store/db/mysql/user_delete.go`.

2. **Reaction cleanup in Go:** In each driver’s `user_delete.go`, `deleteUserTargetsTx` removes reactions in two passes:
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` for memos in the deleted user’s memo subtree
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` for all reactions the user created

3. **No DB cascade:** `store/migration/sqlite/LATEST.sql` (and the postgres/mysql equivalents) define `reaction` with `creator_id INTEGER NOT NULL` but **no** `FOREIGN KEY` to `user`. Only `memo_share` has an `ON DELETE CASCADE` FK; `reaction` does not. Historical migrations `store/migration/sqlite/0.7/00__remove_fk.sql` and `0.7/01__remove_triggers.sql` removed FKs/triggers from user-related tables.

4. **Tests confirming behavior:** `store/test/user_delete_test.go` (`TestDeleteUserCleansRelatedData`) and `server/router/api/v1/test/user_service_delete_test.go` assert that reactions on deleted memos and reactions created by the deleted user are removed, while unrelated reactions remain.
