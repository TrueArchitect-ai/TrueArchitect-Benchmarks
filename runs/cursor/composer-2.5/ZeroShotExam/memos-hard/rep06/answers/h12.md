**`(DB).CreateMemo`** — `store/db/sqlite/memo.go`

That method builds the `INSERT INTO memo (...)` statement and runs it via `d.db.QueryRowContext` (lines 41–47).

**Determination method:** Traced the save path from the editor through the API and store layers, then used the default driver wiring to pick among the three driver-specific `CreateMemo` implementations.

1. **Save → create (INSERT) vs update (UPDATE):** In `web/src/components/MemoEditor/services/memoService.ts`, `save()` calls `createMemo` only for a new memo (no `memoName`); an existing memo goes through `updateMemo`, which issues an `UPDATE`, not an `INSERT`.

2. **API → store → driver:** `createMemo` hits `APIV1Service.CreateMemo` in `server/router/api/v1/memo_service.go` (line 115: `s.Store.CreateMemo`), which delegates to the driver in `store/memo.go` (line 113: `s.driver.CreateMemo`).

3. **Default driver is SQLite:** With no database flags, `cmd/memos/main.go` sets `viper.SetDefault("driver", "sqlite")` (line 122). `store/db/db.go`’s `NewDBDriver` switches on `profile.Driver` and instantiates `sqlite.NewDB` for that default (lines 18–20).

4. **Eliminating other candidates:** `grep` for `INSERT INTO` on the `memo` table finds three runtime implementations — `store/db/sqlite/memo.go`, `store/db/postgres/memo.go`, and `store/db/mysql/memo.go`. Only the SQLite one is reachable on a default install; postgres and mysql are selected only when `--driver` (or `MEMOS_DRIVER`) is set to those values. Seed SQL in `store/seed/sqlite/01__dump.sql` is demo seed data, not the runtime save path.
