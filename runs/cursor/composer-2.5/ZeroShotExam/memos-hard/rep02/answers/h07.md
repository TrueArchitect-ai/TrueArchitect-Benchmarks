The browser loads another user's avatar after the user API returns a file URL (not raw base64). `convertUserFromStore` rewrites embedded avatars to `/file/users/{username}/avatar`, and `UserAvatar` sets that as the `<img src>`, which triggers `GET /file/users/:identifier/avatar`.

**Serving handler and hops to stored data** (symbol — path):

RegisterRoutes — server/router/fileserver/fileserver.go  
serveUserAvatar — server/router/fileserver/fileserver.go  
getUserByUsername — server/router/fileserver/fileserver.go  
GetUser — store/user.go  
ListUsers — store/user.go  
ListUsers — store/db/sqlite/user.go  
parseDataURI — server/router/fileserver/fileserver.go  

(Postgres and MySQL use the same `ListUsers` symbol in `store/db/postgres/user.go` and `store/db/mysql/user.go` instead of sqlite, selected at startup by `NewDBDriver` in `store/db/db.go`.)

**Stored data:** the `avatar_url` column on the `user` table, read in `ListUsers` via `SELECT ... avatar_url ... FROM user WHERE username = ?` and scanned into `store.User.AvatarURL` (`store/db/sqlite/user.go`). The value is a base64 data URI (e.g. `data:image/png;base64,...`), not a separate filesystem object. `parseDataURI` decodes that string into image bytes returned by `c.Blob` in `serveUserAvatar`.

**Upstream context (how the browser gets the URL):** `useUser` → `userServiceClient.getUser` → `convertUserFromStore` in `server/router/api/v1/user_service_converters.go` sets `avatarUrl` to `/file/users/{username}/avatar` when the stored value is a data URI.
