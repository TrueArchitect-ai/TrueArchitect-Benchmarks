**web/src/connect.ts**; **access token (JWT, sent as `Authorization: Bearer`) and refresh token (HttpOnly cookie, sent via `credentials: "include"` for refresh)**; **server/auth**

The frontend auth interceptor is `authInterceptor` in `web/src/connect.ts`. It runs on the Connect RPC transport, calls `getRequestToken()` to obtain a JWT access token (from in-memory/localStorage via `web/src/auth-state.ts`), sets the `Authorization: Bearer …` header, and on `Unauthenticated` calls `refreshAccessToken()` then retries once. Refresh uses a separate transport with `credentials: "include"` so the HttpOnly refresh cookie reaches `AuthService.refreshToken` without recursion through the auth interceptor.

```156:178:web/src/connect.ts
const authInterceptor: Interceptor = (next) => async (req) => {
  const isRetryAttempt = req.header.get(RETRY_HEADER) === RETRY_HEADER_VALUE;
  const token = await getRequestToken();
  setAuthorizationHeader(req, token);

  try {
    return await next(req);
  } catch (error) {
    if (!shouldHandleUnauthenticatedRetry(error, isRetryAttempt)) {
      throw error;
    }

    try {
      const newToken = await refreshAndGetAccessToken();
      setAuthorizationHeader(req, newToken);
      req.header.set(RETRY_HEADER, RETRY_HEADER_VALUE);
      return await next(req);
    } catch (refreshError) {
      redirectOnAuthFailure();
      throw refreshError;
    }
  }
};
```

On the backend, Connect’s `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go` reads the `Authorization` header and delegates to the shared `Authorizer`, which uses `server/auth.Authenticator` to validate JWT access tokens and Personal Access Tokens (PATs). Refresh tokens are validated separately (e.g. in `AuthService.RefreshToken` via cookie) by `server/auth.Authenticator.AuthenticateByRefreshToken`.
