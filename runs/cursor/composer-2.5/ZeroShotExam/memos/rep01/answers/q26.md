**attachment, memo, memo_relation**

When `DeleteMemo` runs, it goes through `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go`, which deletes comment memos first, then the target memo, each via `Store.DeleteMemo` in `store/memo.go`.

That store method performs explicit cascade cleanup before deleting the memo row:

1. **`memo_relation`** — rows where the memo is source or target are removed via `DeleteMemoRelation` (`store/memo.go`, drivers such as `store/db/postgres/memo_relation.go`).
2. **`attachment`** — linked attachments are removed via `DeleteAttachment` (`store/memo.go`, `store/attachment.go`, drivers such as `store/db/postgres/attachment.go`).
3. **`memo`** — the memo row itself is deleted (`store/db/postgres/memo.go` and equivalents).

Tables **not** affected by `DeleteMemo` (no delete in this path):

- **`reaction`** — listed only for webhook payload assembly in `server/router/api/v1/memo_service.go`, not deleted.
- **`inbox`** — unchanged; notifications remain after memo deletion (`server/router/api/v1/test/user_notification_test.go`).
- **`memo_share`** — no explicit cascade in `DeleteMemo`; schema defines `ON DELETE CASCADE` in `store/migration/sqlite/LATEST.sql`, but SQLite disables foreign keys at runtime in `store/db/sqlite/sqlite.go`.
