**attachment, memo, memo_relation**

When `DeleteMemo` runs, these are the database tables that get rows deleted, either directly or through explicit application cascade logic:

1. **`memo`** — deleted directly by the driver (`DELETE FROM memo`) in `store/db/sqlite/memo.go`, `store/db/postgres/memo.go`, and `store/db/mysql/memo.go`, called from `store/memo.go`. The API handler in `server/router/api/v1/memo_service.go` also recursively deletes comment memos (also `memo` rows) before deleting the target memo.

2. **`memo_relation`** — explicitly cascaded in `store/memo.go`: relations are removed where the memo is either source or target via `DeleteMemoRelation` (`store/db/sqlite/memo_relation.go`, etc.).

3. **`attachment`** — explicitly cascaded in `store/memo.go`: linked attachments are listed and deleted via `DeleteAttachment`, which issues `DELETE FROM attachment` in `store/db/sqlite/attachment.go` (and postgres/mysql equivalents).

**Not affected by explicit cascade code in `DeleteMemo`:**

- **`reaction`** — listed in `server/router/api/v1/memo_service.go` for webhook payload building only; not deleted.
- **`memo_share`** — not deleted in the `DeleteMemo` code path (`store/memo.go`, `server/router/api/v1/memo_service.go`). Although `store/migration/sqlite/LATEST.sql` (and postgres/mysql) define `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` on `memo_share`, that is schema-level cascade, not explicit application code, and SQLite disables foreign keys at runtime (`store/db/sqlite/sqlite.go`: `_pragma=foreign_keys(0)`).
