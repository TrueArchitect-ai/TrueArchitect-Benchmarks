**attachment, memo, memo_relation**

When `DeleteMemo` runs, it goes through `server/router/api/v1/memo_service.go` (which deletes comment memos first, then the target memo via `store.DeleteMemo`) and `store/memo.go` (which performs the explicit cascade cleanup before the final row delete).

| Table | How it is affected |
|---|---|
| **memo** | Rows are deleted directly (`store/db/postgres/memo.go`, and equivalents for sqlite/mysql). Comment memos are deleted first in `server/router/api/v1/memo_service.go` before the parent memo. |
| **memo_relation** | Rows are deleted by explicit cascade code in `store/memo.go` (both where `memo_id` and `related_memo_id` match the deleted memo). |
| **attachment** | Rows are deleted by explicit cascade code in `store/memo.go` via `DeleteAttachment` (`store/attachment.go` → `DELETE FROM attachment` in `store/db/postgres/attachment.go`). |

**Not affected by `DeleteMemo` (including its cascade code):**

- **reaction** — listed in `server/router/api/v1/memo_service.go` only for webhook payload assembly; no delete is performed.
- **memo_share** — no cleanup in the `DeleteMemo` code path; although `store/migration/sqlite/LATEST.sql` defines `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, SQLite runs with foreign keys disabled (`store/db/sqlite/sqlite.go`: `_pragma=foreign_keys(0)`), so this cascade is not applied there.
