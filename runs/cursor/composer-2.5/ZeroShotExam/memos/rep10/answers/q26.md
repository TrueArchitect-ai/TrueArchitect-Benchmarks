**attachment, memo, memo_relation**

When `DeleteMemo` runs, these tables are modified as follows:

1. **`memo_relation`** — Explicit cascade in `store/memo.go`: rows where the memo is source or target are deleted before the memo row (`DeleteMemoRelation` in `store/db/postgres/memo_relation.go`, and equivalents in `store/db/sqlite/memo_relation.go` / `store/db/mysql/memo_relation.go`).

2. **`attachment`** — Explicit cascade in `store/memo.go`: linked attachments are listed and deleted via `DeleteAttachment` (`DELETE FROM attachment` in `store/db/postgres/attachment.go`).

3. **`memo`** — Direct delete in the driver (`DELETE FROM memo` in `store/db/postgres/memo.go`).

The API handler in `server/router/api/v1/memo_service.go` first recursively deletes comment memos via `Store.DeleteMemo`, which repeats the same cascade for each comment row in **`memo`**.

**Not affected by `DeleteMemo`:**

- **`reaction`** — Listed only for webhook conversion in `server/router/api/v1/memo_service.go`; no delete path.
- **`memo_share`** — No application cascade in `DeleteMemo`; cleanup would rely on DB `ON DELETE CASCADE` in `store/migration/postgres/LATEST.sql` / `store/migration/mysql/LATEST.sql`, but SQLite disables foreign keys in `store/db/sqlite/sqlite.go`, so that cascade does not run there.
