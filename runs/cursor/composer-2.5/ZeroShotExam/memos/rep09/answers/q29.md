**`web/src/connect.ts`; access token (JWT Bearer) and refresh token (HttpOnly cookie); `server/auth`**

Frontend Connect RPC calls go through `authInterceptor` in [`web/src/connect.ts`](web/src/connect.ts). It reads the access token via `getRequestToken()` from [`web/src/auth-state.ts`](web/src/auth-state.ts), sets `Authorization: Bearer <token>`, and on `Unauthenticated` calls `refreshAccessToken()` then retries once. Refresh uses a separate transport with `credentials: "include"` (lines 57–72, 74–83) so the refresh token travels as an HttpOnly cookie, not in JS storage.

Token roles:
- **Access token** — stored in `localStorage` (`memos_access_token`), sent on every API request as a Bearer header.
- **Refresh token** — HttpOnly cookie; the interceptor does not read or store it, but uses it indirectly when refreshing (cookie sent with `fetch(..., credentials: "include")`).

On the backend, the Connect `AuthInterceptor` in [`server/router/api/v1/connect_interceptors.go`](server/router/api/v1/connect_interceptors.go) delegates to `Authorizer`, which uses [`server/auth`](server/auth/authenticator.go) (`Authenticator`) to validate Bearer credentials: JWT access tokens (`AuthenticateByAccessTokenV2`) and personal access tokens (`AuthenticateByPAT`). Refresh tokens are validated in the same package via `AuthenticateByRefreshToken` on the `RefreshToken` RPC in [`server/router/api/v1/auth_service_session.go`](server/router/api/v1/auth_service_session.go).
