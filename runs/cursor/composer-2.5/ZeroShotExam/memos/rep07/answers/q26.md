**memo**, **memo_relation**, **attachment**

When `DeleteMemo` runs, it goes through `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go`, which recursively deletes comment memos, then calls `Store.DeleteMemo`. That store method in `store/memo.go` explicitly cascades cleanup before deleting the memo row itself:

1. **`memo_relation`** — deleted via `DeleteMemoRelation` for both `memo_id` and `related_memo_id` matching the memo being removed (`store/memo.go`).
2. **`attachment`** — each linked attachment is deleted via `DeleteAttachment` (`store/memo.go` → `store/db/*/attachment.go`).
3. **`memo`** — the memo row is deleted directly (`store/db/*/memo.go`).

Comment memos are removed first at the API layer (`server/router/api/v1/memo_service.go`), and each comment goes through the same `Store.DeleteMemo` cascade, so those same three tables are affected for comments too.

**Not affected by `DeleteMemo` (directly or by explicit cascade code):**

- **`reaction`** — listed only for webhook payload; never deleted (`server/router/api/v1/memo_service.go`).
- **`memo_share`** — no application cleanup in the delete path; the schema defines `ON DELETE CASCADE` on `memo_id` (`store/migration/sqlite/LATEST.sql`), but SQLite runs with foreign keys disabled (`store/db/sqlite/sqlite.go`), and there is no explicit delete call in the `DeleteMemo` code path.
