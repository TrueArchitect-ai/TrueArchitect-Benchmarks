**attachment, memo, memo_relation**

When `DeleteMemo` runs, these three tables have rows deleted via the application code path:

1. **`memo`** — deleted directly by the driver (`DELETE FROM memo`), and comment memos are deleted recursively first in the API handler (`server/router/api/v1/memo_service.go` lines 567–580).

2. **`memo_relation`** — explicitly cascaded in `store/memo.go` (lines 141–146), which deletes relations where the memo is either `memo_id` or `related_memo_id` (`store/db/postgres/memo_relation.go` line 164: `DELETE FROM memo_relation`).

3. **`attachment`** — explicitly cascaded in `store/memo.go` (lines 148–156), which lists attachments for the memo and calls `DeleteAttachment` (`store/db/postgres/attachment.go` line 212: `DELETE FROM attachment`).

**Not affected by explicit cascade code in `DeleteMemo`:**
- **`reaction`** — listed only for the delete webhook payload (`server/router/api/v1/memo_service.go` lines 545–550); no `DeleteReaction` call in the delete path.
- **`memo_share`** — has `ON DELETE CASCADE` in schema migrations (`store/migration/postgres/LATEST.sql` line 108), but `DeleteMemo` does not explicitly delete share rows; cleanup happens only via the DB foreign-key cascade when the `memo` row is removed.
