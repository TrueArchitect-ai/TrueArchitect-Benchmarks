**attachment, memo, memo_relation**

When `DeleteMemo` runs, these tables are modified as follows:

1. **`memo`** — deleted directly (`DELETE FROM memo` in `store/db/postgres/memo.go`, and the analogous SQLite/MySQL drivers).

2. **`memo_relation`** — deleted by explicit cascade in `store/memo.go` via two `DeleteMemoRelation` calls (where `memo_id` or `related_memo_id` matches the memo).

3. **`attachment`** — deleted by explicit cascade in `store/memo.go`, which lists attachments for the memo and calls `DeleteAttachment` for each (`DELETE FROM attachment` in `store/db/postgres/attachment.go`).

The API handler in `server/router/api/v1/memo_service.go` first deletes comment memos recursively (each through the same `Store.DeleteMemo` cascade), then deletes the target memo.

**Not affected by explicit cascade in `DeleteMemo`:**
- **`reaction`** — listed only for webhook payload; not deleted (`server/router/api/v1/memo_service.go`).
- **`memo_share`** — has `ON DELETE CASCADE` in schema (`store/migration/sqlite/LATEST.sql`), but no explicit delete in the `DeleteMemo` code path.
- **`inbox`** — notifications remain after memo deletion (`server/router/api/v1/test/user_notification_test.go`).
