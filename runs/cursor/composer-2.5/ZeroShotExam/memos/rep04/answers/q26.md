**attachment, memo, memo_relation**

When `DeleteMemo` runs, these three tables have rows deleted:

1. **`memo_relation`** — explicit cascade in `store/memo.go`: `DeleteMemoRelation` runs for both `memo_id` and `related_memo_id` before the memo row is removed. SQL: `store/db/sqlite/memo_relation.go` (and postgres/mysql equivalents).

2. **`attachment`** — explicit cascade in `store/memo.go`: attachments for the memo are listed and each is removed via `DeleteAttachment`. SQL: `store/db/sqlite/attachment.go`.

3. **`memo`** — direct delete in `store/db/sqlite/memo.go` (and postgres/mysql equivalents).

The API handler in `server/router/api/v1/memo_service.go` calls `Store.DeleteMemo` for the target memo and recursively for comment memos; each call follows the same cascade in `store/memo.go`.

**Not affected by explicit cascade code in `DeleteMemo`:**
- **`reaction`** — listed in the API handler for webhook payload only; no delete (`server/router/api/v1/memo_service.go`).
- **`memo_share`** — no delete in the `DeleteMemo` code path; it has `ON DELETE CASCADE` on `memo_id` in `store/migration/sqlite/LATEST.sql`, but that is DB-level, not explicit application cascade code.
