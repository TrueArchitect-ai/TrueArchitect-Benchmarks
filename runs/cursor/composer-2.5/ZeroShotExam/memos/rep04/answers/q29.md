**Format:** `web/src/connect.ts`; access token (JWT Bearer header) and refresh token (HttpOnly cookie); `server/auth`

Frontend API calls go through Connect RPC clients built in `web/src/connect.ts`. The `authInterceptor` there attaches auth to each request and handles refresh/retry.

**Interceptor (`web/src/connect.ts`)**  
The `authInterceptor` Connect interceptor:

1. Calls `getRequestToken()` to obtain a valid access token (from memory/localStorage, or by refreshing first if missing/expired).
2. Sets `Authorization: Bearer <access_token>` on the request.
3. On `Unauthenticated` (401), calls `refreshAccessToken()`, retries once with the new token, or redirects on failure.

Refresh uses a separate transport without the interceptor (`refreshTransport`) to avoid recursion when calling `AuthService.refreshToken`.

**Tokens managed**

| Token | Frontend handling |
|-------|-------------------|
| **Access token (JWT)** | Stored in `web/src/auth-state.ts` (memory + `localStorage` keys `memos_access_token` / `memos_token_expires_at`); sent as `Authorization: Bearer …` |
| **Refresh token** | HttpOnly cookie set by the backend at sign-in; not read in JS. Sent automatically via `fetch(..., { credentials: "include" })` when calling `refreshToken` |

**Backend validation (`server/auth`)**  
The `server/auth` package validates credentials via `Authenticator`:

- **Access Token V2** — stateless JWT validation (`AuthenticateByAccessTokenV2`)
- **Refresh token** — DB-backed validation (`AuthenticateByRefreshToken`), used for token refresh and cookie fallback
- **Personal Access Tokens (PAT)** — also validated here, though the web interceptor does not use them

Connect requests are gated by `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go`, which delegates to `Authorizer` in `server/router/api/v1/authz.go`, which in turn calls `Authenticator.Authenticate` in `server/auth`.
