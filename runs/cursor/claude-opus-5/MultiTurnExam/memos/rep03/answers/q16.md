Ordering the cleanup by where it happens, `Store.DeleteMemo` in `store/memo.go` removes two kinds of records before issuing the memo `DELETE`:

1. **Memo relations where the memo is the source** (`memo_relation.memo_id`)
2. **Memo relations where the memo is the target** (`memo_relation.related_memo_id`)
3. **Attachments linked to the memo** — deleted one at a time via `Store.DeleteAttachment`, which also removes the underlying stored file (local disk or external storage) before the row
4. …then the memo row itself

```140:158:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

Two things happen outside the store method that matter for "deleted through the API." First, `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go` (line 518) first finds all child comments via `memo_relation` rows of type `MemoRelationComment` and calls `Store.DeleteMemo` on each, so every comment memo — and recursively its own relations and attachments — is removed before the parent. Second, `memo_share` rows are cleaned up by the database rather than by Go code: the table declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql` line 109).
