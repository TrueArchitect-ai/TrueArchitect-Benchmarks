**`memo`, `memo_relation`, `attachment`, and `memo_share`**

How each is reached:

- **`memo_relation`** — deleted explicitly by `Store.DeleteMemo`, twice: once for rows where the memo is the source (`memo_id`) and once where it's the target (`related_memo_id`).
- **`attachment`** — every attachment with `memo_id` matching is looked up and removed via `Store.DeleteAttachment`, which also unlinks the underlying stored file.
- **`memo`** — the row itself, last, plus additional `memo` rows for child comments: `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go` (line 518) walks `memo_relation` rows of type `MemoRelationComment` and calls `Store.DeleteMemo` recursively on each.

```140:158:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

The driver's own `DeleteMemo` is a bare single-table `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go` line 237), so all cleanup is in the layer above.

**`memo_share` is the caveat.** No Go code deletes it during `DeleteMemo`; it relies purely on the schema-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql` line 109, and the equivalents in the postgres and mysql schemas). That cascade fires on Postgres and MySQL, but SQLite opens its connection with foreign keys explicitly disabled:

```53:53:store/db/sqlite/sqlite.go
	sqliteDB, err := sql.Open("sqlite", profile.DSN+"?_pragma=foreign_keys(0)&_pragma=busy_timeout(10000)&_pragma=journal_mode(WAL)&_pragma=mmap_size(0)")
```

So on the default SQLite backend, `memo_share` rows are left orphaned rather than cascaded.

Not touched: `reaction`. The handler only reads reactions to build the webhook payload, and `reaction.content_id` is plain `TEXT` with no foreign key, so those rows also survive the delete.
