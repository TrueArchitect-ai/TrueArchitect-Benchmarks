**Mechanism: Server-Sent Events (SSE)**; **hub: `server/router/api/v1/sse_hub.go`**; **handlers: `CreateMemo`, `UpdateMemo`, `DeleteMemo`, `CreateMemoComment`, `SetMemoAttachments`, `SetMemoRelations`, `UpsertMemoReaction`, `DeleteMemoReaction`**

The hub is a plain in-process fan-out: `SSEHub` holds a mutex-guarded set of `SSEClient`s, each with a buffered `events` channel plus the connected user's ID and role, which are used for per-client delivery filtering:

```54:59:server/router/api/v1/sse_hub.go
// SSEHub manages SSE client connections and broadcasts events.
// It is safe for concurrent use.
type SSEHub struct {
	mu      sync.RWMutex
	clients map[*SSEClient]struct{}
	closed  bool
}
```

The same file defines the six event types (`memo.created`, `memo.updated`, `memo.deleted`, `memo.comment.created`, `reaction.upserted`, `reaction.deleted`) and the `SSEEvent` payload, whose `Visibility` and `CreatorID` fields are marked `json:"-"` because they exist only for server-side filtering. Browsers connect at `GET /api/v1/sse`, registered by `RegisterSSERoutes` in `server/router/api/v1/sse_handler.go` with Bearer-token auth.
