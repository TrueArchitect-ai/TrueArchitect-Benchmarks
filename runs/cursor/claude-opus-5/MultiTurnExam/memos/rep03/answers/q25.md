**Engine: CEL (Google's Common Expression Language) via `cel-go`, in `internal/filter/` — entry point `internal/filter/engine.go`**

**Mechanism: a three-phase pipeline — the CEL expression is parsed and schema-validated, normalized into a dialect-agnostic IR of conditions, then rendered by `internal/filter/render.go` into a SQL fragment plus placeholder args for the target dialect, which each driver appends to its `WHERE` clause.**

The engine is built on `cel.NewEnv` at `internal/filter/engine.go` line 25, configured with the memo-specific field schema in `internal/filter/schema.go`, so only declared fields can appear in a filter. The phases map to files: `parser.go` (CEL AST → IR, applying type and operator checks), `ir.go` (the IR nodes), and `render.go` (IR → SQL).

The renderer encapsulates the differences: `?` versus `$n` placeholders, JSON access on `memo.payload` (`json_extract` / `->>` / `JSON_EXTRACT`), tag membership (`LIKE` on SQLite, `JSON_CONTAINS` on MySQL, `@>` on Postgres), `LIKE` versus `ILIKE`, and regex (`REGEXP` versus `~`). Time expressions like `created_ts >= now - duration("24h")` constant-fold to epoch seconds at compile time.

Two related notes: the same engine also backs attachment filters (`DefaultAttachmentEngine`, used in the `attachment.go` drivers), and SQLite regex support relies on a Go-backed `regexp` function registered in `store/db/sqlite/functions.go`. The design and per-dialect caveats are documented in `internal/filter/README.md`.
