**Tables: `memo_relation`, `attachment`, `memo`** — plus **`memo_share`** on MySQL and Postgres via a database-level foreign-key cascade.

The Go-level cascade in `Store.DeleteMemo` deletes, in order, `memo_relation` rows where the memo is the source, `memo_relation` rows where it's the target, then each linked `attachment`, and finally the `memo` row itself:

```140:158:/bench/repo/store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

`memo_share` is the one table affected without any Go code touching it — the schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` at line 109 of `/bench/repo/store/migration/sqlite/LATEST.sql` and the same at line 108 in both the Postgres and MySQL files. Importantly, this cascade does *not* fire on SQLite, because the connection is opened with foreign keys disabled:

```53:53:/bench/repo/store/db/sqlite/sqlite.go
	sqliteDB, err := sql.Open("sqlite", profile.DSN+"?_pragma=foreign_keys(0)&_pragma=busy_timeout(10000)&_pragma=journal_mode(WAL)&_pragma=mmap_size(0)")
```

So on the default SQLite deployment, `memo_share` rows are orphaned rather than removed.

Two side effects beyond table rows. `Store.DeleteAttachment` (line 132 of `/bench/repo/store/attachment.go`) also deletes the backing blob through `DeleteAttachmentStorage` — a local file unlink or S3 delete — and it treats a failed local delete as fatal while only warning for remote storage. And the API handler `APIV1Service.DeleteMemo` at line 518 of `/bench/repo/server/router/api/v1/memo_service.go` first recursively calls `Store.DeleteMemo` on every comment memo, so a memo with comments deletes additional `memo` rows and their own relations and attachments.

The `reaction` table is notably *not* cleaned up: reactions key off a resource-name string in `content_id` rather than a memo foreign key, and nothing in this path deletes them.
