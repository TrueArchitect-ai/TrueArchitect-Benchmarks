The interceptor attaches a token to every outgoing request and handles 401s reactively:

```156:178:repo/web/src/connect.ts
const authInterceptor: Interceptor = (next) => async (req) => {
  const isRetryAttempt = req.header.get(RETRY_HEADER) === RETRY_HEADER_VALUE;
  const token = await getRequestToken();
  setAuthorizationHeader(req, token);

  try {
    return await next(req);
  } catch (error) {
    if (!shouldHandleUnauthenticatedRetry(error, isRetryAttempt)) {
      throw error;
    }

    try {
      const newToken = await refreshAndGetAccessToken();
      setAuthorizationHeader(req, newToken);
      req.header.set(RETRY_HEADER, RETRY_HEADER_VALUE);
      return await next(req);
    } catch (refreshError) {
      redirectOnAuthFailure();
      throw refreshError;
    }
  }
};
```

Refresh happens two ways. Proactively, `getRequestToken` (line 124) refreshes when the access token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry — the comment at line 136 notes this matters for public endpoints like `ListMemos`, where an expired token would silently yield guest-scoped data. Reactively, an `Unauthenticated` response triggers one refresh-and-retry, marked with an `X-Retry` header so it can't loop. Concurrent refreshes are deduplicated by `tokenRefreshManager` (line 51), and the refresh call itself uses a separate interceptor-free transport (`refreshTransport`, line 65) to avoid recursion. The refresh cookie rides along because `fetchWithCredentials` sets `credentials: "include"`.

On the backend, `Authenticator` in `repo/server/auth/authenticator.go` validates all three credential kinds — its own doc comment at lines 22–23 describes JWT access tokens as 15-minute and PATs as long-lived. `AuthenticateToUser` (line 190) checks the `Authorization` header first (access token or PAT), then falls back to the refresh cookie; `AuthenticateByRefreshToken` (line 61) additionally verifies the token against the database for revocation and expiry. Token parsing and cookie extraction live in `token.go` and `extract.go` of the same package.

That authenticator is wired into both protocols: `NewAuthInterceptor(authorizer)` for Connect and `gatewayAuthMiddleware` for the REST gateway, both in `repo/server/router/api/v1/v1.go`, with per-method access policy in `repo/server/router/api/v1/authz.go`.
