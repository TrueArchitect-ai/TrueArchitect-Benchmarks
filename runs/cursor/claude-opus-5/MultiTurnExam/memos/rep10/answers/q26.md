**`memo_relation`, `attachment`, `memo`** — plus **`memo_share`** on MySQL and PostgreSQL via a database-level foreign-key cascade (not on SQLite, see below).

The explicit cascade code in `Store.DeleteMemo` touches three tables in order: `memo_relation` twice (once as source, once as target), `attachment` for every row linked to the memo, then `memo` itself:

```140:158:repo/store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

The driver's own `DeleteMemo` is a plain single-table statement with no cascade of its own — `DELETE FROM memo WHERE id = ?` at `repo/store/db/sqlite/memo.go:239`.

The `memo` table is hit more than once in practice: the API handler first deletes every comment memo (relations of type `MemoRelationComment`) by recursing into `Store.DeleteMemo`, at `repo/server/router/api/v1/memo_service.go:567-577`.

Two caveats worth knowing:

`memo_share` declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`repo/store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). On MySQL and PostgreSQL that cascade fires; on SQLite it does not, because the connection is opened with foreign keys disabled:

```53:53:repo/store/db/sqlite/sqlite.go
	sqliteDB, err := sql.Open("sqlite", profile.DSN+"?_pragma=foreign_keys(0)&_pragma=busy_timeout(10000)&_pragma=journal_mode(WAL)&_pragma=mmap_size(0)")
```

And `reaction` is *not* affected. Reactions are only read to build the webhook payload, so rows keyed to a deleted memo are orphaned. Note also that deleting attachments goes through `Store.DeleteAttachment` (`repo/store/attachment.go:132`), which additionally removes the underlying blob from local or S3 storage before the row.
