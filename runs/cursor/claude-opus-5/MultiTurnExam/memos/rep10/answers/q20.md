**Mechanism: Server-Sent Events (SSE); Hub: `repo/server/router/api/v1/sse_hub.go`; Handlers: CreateMemo, UpdateMemo, DeleteMemo, CreateMemoComment, SetMemoAttachments, SetMemoRelations, UpsertMemoReaction, DeleteMemoReaction**

The transport is plain SSE over the existing HTTP server — the endpoint sets `Content-Type: text/event-stream` in `repo/server/router/api/v1/sse_handler.go:48`, and `RegisterSSERoutes` (line 25) mounts it alongside the rest of `/api/v1` from `repo/server/router/api/v1/v1.go:125`.

The hub in `sse_hub.go` holds `SSEHub` and `SSEClient` types with `Subscribe`, `Unsubscribe`, `Broadcast`, and `Close`. Fan-out is permission-aware: each client records its user ID and role at subscribe time, and `canReceive` (line 134) filters events per client, so private memos aren't leaked.

Broadcasts happen at these call sites:

| Handler | Broadcast site |
|---|---|
| `CreateMemo` | `memo_service.go:163` |
| `DeleteMemo` | `memo_service.go:585` |
| `CreateMemoComment` | `memo_service_comments.go:126` |
| `UpsertMemoReaction` | `reaction_service.go:106` |
| `DeleteMemoReaction` | `reaction_service.go:161` |
| `UpdateMemo`, `SetMemoAttachments`, `SetMemoRelations` | indirect, via `dispatchMemoUpdatedSideEffects` |

Those last three don't call the hub themselves; they route through the shared helper `dispatchMemoUpdatedSideEffects` at `repo/server/router/api/v1/memo_update_helpers.go:66`, which broadcasts on their behalf (called from `memo_service.go:513`, `memo_attachment_service.go:48`, and `memo_relation_service.go:48`).

One nuance in the comment path: `CreateMemoComment` invokes `s.CreateMemo` with `withSuppressSSE(ctx)` (`memo_service_comments.go:56`) so the nested memo creation stays silent, then emits a single `memo.comment.created` event for the parent instead.
