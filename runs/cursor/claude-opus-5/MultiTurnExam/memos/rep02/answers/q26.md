**memo_relation, attachment, memo** — plus **memo_share** via a database-level foreign-key cascade.

The Go-level cleanup in `Store.DeleteMemo` explicitly touches three tables before the memo row: `memo_relation` (twice, once for each direction), `attachment` (row plus the backing file in storage), then `memo` itself:

```140:158:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

The driver method is a bare `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`), so nothing extra happens at that level.

`memo_share` is the one table cleaned up by the schema rather than by code — it's the only foreign key with a cascade in the whole schema:

```109:109:store/migration/sqlite/LATEST.sql
  FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE
```

That's declared identically in all three dialects (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`), but it is **not** actually enforced on SQLite, because the driver opens the connection with foreign keys disabled:

```53:53:store/db/sqlite/sqlite.go
	sqliteDB, err := sql.Open("sqlite", profile.DSN+"?_pragma=foreign_keys(0)&_pragma=busy_timeout(10000)&_pragma=journal_mode(WAL)&_pragma=mmap_size(0)")
```

So on Postgres and MySQL a memo delete also removes its share links, while on the default SQLite backend those rows are left orphaned. Also note the API handler (`server/router/api/v1/memo_service.go:518`) recursively deletes comment memos through the same store method, so the `memo` and `memo_relation` tables are hit once per comment as well; `reaction` rows are read for the webhook payload but never deleted in this path.
