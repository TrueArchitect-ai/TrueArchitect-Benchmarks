**Server-Sent Events (SSE)**; hub at **`server/router/api/v1/sse_hub.go`**; broadcasting memo handlers: **`CreateMemo`, `UpdateMemo`, `DeleteMemo`, `CreateMemoComment`, `SetMemoAttachments`, `SetMemoRelations`, `UpsertMemoReaction`, `DeleteMemoReaction`**.

The mechanism is plain SSE over the existing HTTP server — `server/router/api/v1/sse_handler.go` sets `Content-Type: text/event-stream` (line 48), and the endpoint is mounted alongside the rest of `/api/v1` via `RegisterSSERoutes` in `server/router/api/v1/v1.go` (line 125). There's no WebSocket involved.

`SSEHub` maintains per-client channels with `Subscribe`/`Unsubscribe`/`Broadcast`, and each subscription records the user's ID and role so events can be filtered by visibility. Six event types are defined:

```15:20:server/router/api/v1/sse_hub.go
	SSEEventMemoCreated        SSEEventType = "memo.created"
	SSEEventMemoUpdated        SSEEventType = "memo.updated"
	SSEEventMemoDeleted        SSEEventType = "memo.deleted"
	SSEEventMemoCommentCreated SSEEventType = "memo.comment.created"
	SSEEventReactionUpserted   SSEEventType = "reaction.upserted"
	SSEEventReactionDeleted    SSEEventType = "reaction.deleted"
```

Three of those handlers broadcast directly (`CreateMemo` at `memo_service.go:163`, `DeleteMemo` at line 585, `CreateMemoComment` at `memo_service_comments.go:126`), and the reaction pair broadcasts through `buildMemoReactionSSEEvent` in `reaction_service.go`. `UpdateMemo`, `SetMemoAttachments`, and `SetMemoRelations` all go through the shared helper `dispatchMemoUpdatedSideEffects` in `server/router/api/v1/memo_update_helpers.go` (line 71), which is why an attachment or relation change also surfaces as a `memo.updated` event.

One subtlety in the comment path: `CreateMemoComment` calls `CreateMemo` with a context marked by `withSuppressSSE`, so the nested call skips its own `memo.created` event and only the parent's `memo.comment.created` is emitted.
