Before deleting the memo row, `Store.DeleteMemo` removes:

1. **`memo_relation` rows where the memo is the source** (`MemoID` matches)
2. **`memo_relation` rows where the memo is the target** (`RelatedMemoID` matches)
3. **`attachment` rows linked to the memo** — deleted one at a time, and each also removes the backing file from storage

```140:158:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

The attachment step is not purely a row delete: `Store.DeleteAttachment` in `store/attachment.go` (line 132) first calls `DeleteAttachmentStorage` to remove the underlying blob or file, and a failure there is fatal for `LOCAL` storage but only logged as a warning for other storage types.

Two things happen one level up rather than in the store, in `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go`, line 518): comment memos are found via `memo_relation` rows of type `MemoRelationComment` and each is recursively deleted through `Store.DeleteMemo` before the parent, and a memo-deleted webhook is dispatched beforehand. Reactions are read for the webhook payload but I don't see them deleted in this path, so those rows appear to be left behind.
