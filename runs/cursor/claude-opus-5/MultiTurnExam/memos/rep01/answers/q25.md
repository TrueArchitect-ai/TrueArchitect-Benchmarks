**Engine: Google CEL (Common Expression Language) via `github.com/google/cel-go`, wrapped by the in-repo `internal/filter` package — `internal/filter/engine.go`**

**Mechanism:** the engine compiles the CEL string into a dialect-agnostic condition tree, then a renderer walks that tree and emits a parameterized SQL `WHERE` fragment with per-dialect branches, which each driver appends to its query.

```13:21:internal/filter/engine.go
// Engine parses CEL filters into a dialect-agnostic condition tree.
type Engine struct {
	schema Schema
	env    *cel.Env
```

`Engine.Compile` runs `cel-go`'s `env.Compile` and converts the AST into the intermediate representation in `internal/filter/ir.go`, with the allowed variables and functions declared by the `Schema` in `internal/filter/schema.go`. Rendering happens in `internal/filter/render.go`, where a `renderer` carries a `DialectName` and switches on `DialectSQLite` / `DialectPostgres` / `DialectMySQL` for things like JSON extraction, string length, and placeholder style (`?` vs `$n`).

Drivers plug in through one helper call, so each dialect passes its own name and current arg offset:

`AppendConditions` (`internal/filter/helpers.go:9`) wraps each rendered fragment in parentheses and appends its bound args, skipping trivially-true filters; an unsatisfiable filter renders as `1 = 0`. The Postgres and MySQL drivers make the same call with `filter.DialectPostgres` / `filter.DialectMySQL`. There's also a user-facing filter layer in `server/router/api/v1/user_service_filter.go`, and design notes in `internal/filter/README.md` and `internal/filter/MAINTENANCE.md`.
