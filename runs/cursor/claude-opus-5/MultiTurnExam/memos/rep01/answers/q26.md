**`memo_relation`, `attachment`, `memo`** (plus `memo_share` only on backends that enforce foreign keys)

The store method deletes in this order (`store/memo.go:140-159`): `memo_relation` rows where the memo is the source and where it is the target, then every `attachment` row linked via `MemoID` (each through `Store.DeleteAttachment`, which also removes the underlying local/S3 blob), then the `memo` row itself.

Additional `memo` rows are also removed: `APIV1Service.DeleteMemo` first finds comment relations of type `MemoRelationComment` and calls `Store.DeleteMemo` on each comment, recursing through the same cleanup (`server/router/api/v1/memo_service.go:567-577`).

`memo_share` is a caveat rather than a clean yes. The table declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`), but there is no Go code that deletes shares when a memo is deleted, and the SQLite driver opens the database with foreign keys turned off:

```53:53:store/db/sqlite/sqlite.go
	sqliteDB, err := sql.Open("sqlite", profile.DSN+"?_pragma=foreign_keys(0)&_pragma=busy_timeout(10000)&_pragma=journal_mode(WAL)&_pragma=mmap_size(0)")
```

So under SQLite the cascade does not fire; under Postgres/MySQL it does. (The only explicit `memo_share` cleanup by memo is in the user-deletion path, `store/db/sqlite/user_delete.go:411`.)

Not touched: `reaction`. `APIV1Service.DeleteMemo` lists reactions for the webhook payload only and never deletes them (`server/router/api/v1/memo_service.go:545-550`).
