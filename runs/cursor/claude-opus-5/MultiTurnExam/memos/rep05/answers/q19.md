gRPC-Gateway (REST/JSON over HTTP) — `server/router/api/v1/v1.go`
ConnectRPC — `server/router/api/v1/connect_handler.go` (with the per-RPC wrappers in `server/router/api/v1/connect_services.go`)

Both are wired up from the same `APIV1Service`, so business logic has a single source of truth.

For the gateway, `RegisterGateway` builds a `runtime.NewServeMux` with an auth middleware and registers the service against it, then mounts the mux on Echo at `/api/v1/*` and `/file/*`:

```108:110:/bench/repo/server/router/api/v1/v1.go
	if err := v1pb.RegisterMemoServiceHandlerServer(ctx, gwMux, s); err != nil {
		return err
	}
```

Note this uses the `...HandlerServer` variant, which dispatches in-process rather than dialing a gRPC port, so the REST surface is served directly by the Go service. The generated glue for it is `proto/gen/api/v1/memo_service.pb.gw.go`.

For Connect, which is what the browser clients use, `ConnectServiceHandler` embeds `*APIV1Service` and registers the generated handler on an `http.ServeMux`:

```40:40:/bench/repo/server/router/api/v1/connect_handler.go
		wrap(apiv1connect.NewMemoServiceHandler(s, opts...)),
```

The same file also converts gRPC status errors into Connect errors via `convertGRPCError`, and the actual per-RPC method wrappers (`ConnectServiceHandler.CreateMemo`, `ListMemos`, and so on) live in `connect_services.go`, delegating to the `APIV1Service` methods. Registration is invoked from the tail of `RegisterGateway` in `v1.go` (just past line 133), where the Connect interceptors are assembled.
