**Interceptor: `web/src/connect.ts` (the `authInterceptor`, line 156); tokens: short-lived JWT access tokens plus a long-lived refresh token cookie (with Personal Access Tokens as a third, API-client credential); backend package: `server/auth`**

On the frontend, `authInterceptor` is installed on the shared Connect transport and does three things: fetches a token via `getRequestToken()` and sets `Authorization: Bearer <token>`; pre-emptively refreshes when the stored token is within 30 seconds of expiry (`REQUEST_TOKEN_EXPIRY_BUFFER_MS`), which matters for public endpoints like `ListMemos` that would otherwise silently return guest-scoped data; and on a `Code.Unauthenticated` response, refreshes once, marks the retry with an `X-Retry` header, and replays the request, calling `redirectOnAuthFailure()` if that fails.

Access token state lives in `web/src/auth-state.ts`, persisted in `localStorage` (`getAccessToken`, `setAccessToken`, `isTokenExpired`, `clearAccessToken`). The refresh token is never touched by JS: the transport sets `credentials: "include"` so the `memos_refresh` cookie rides along, and refresh calls go through a separate interceptor-free transport and `refreshAuthClient` to avoid recursion. Concurrent refreshes are deduplicated by `tokenRefreshManager`, since a focus-triggered refresh and a 401-triggered refresh could otherwise race against server-side token rotation.

On the backend, `server/auth` validates everything. `server/auth/token.go` defines and parses the token kinds — `GenerateAccessTokenV2`/`ParseAccessTokenV2`, `GenerateRefreshToken`/`ParseRefreshToken` (30-day lifetime, `type: "refresh"`, cookie name `memos_refresh`), and PAT generation/hashing. `server/auth/authenticator.go` resolves credentials: `resolveBearer` tries an access token then falls back to `AuthenticateByPAT` (hash lookup via `Store.GetUserByPATHash`, expiry check, last-used recording), while `AuthenticateByRefreshToken` additionally checks the DB for revocation and expiry. Header and cookie parsing is in `server/auth/extract.go`, request-context plumbing in `server/auth/context.go`.

The two server entry points both use it: the gRPC-Gateway middleware and the Connect interceptor share one `NewAuthorizer(s.Store, s.Secret, s.Profile)` in `server/router/api/v1/v1.go` (line 68), described there as "one source of truth for authentication and anonymous-access policy."
