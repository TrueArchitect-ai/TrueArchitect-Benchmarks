Before the memo row itself, `Store.DeleteMemo` in `store/memo.go` (line 140) removes, in order:

func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}

Two things extend that cleanup beyond the store method proper. Each attachment deletion goes through `Store.DeleteAttachment` in `store/attachment.go` (line 132), which also deletes the **underlying stored blob or file** via `DeleteAttachmentStorage` before removing the row; a failure there is fatal for `LOCAL` storage but only logged for remote storage. And in the API handler `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go` (line 518), **comment memos** are deleted first: it lists `memo_relation` rows of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each child, so every comment recursively goes through the same relation and attachment cleanup.

One thing this does *not* do: reactions are read at line 545 only to build the webhook payload, and I found no reaction deletion on this path, so `reaction` rows referencing the memo appear to be left behind.
