**`memo_relation`, `attachment`, `memo`, and `memo_share`**

The explicit cascade lives in `Store.DeleteMemo` (`store/memo.go`, line 140), which runs before the row delete:

`memo_relation` — deleted twice, once matching `MemoID` (memo as source) and once matching `RelatedMemoID` (memo as target)
`attachment` — every attachment with `MemoID` set to this memo is listed and deleted individually through `Store.DeleteAttachment`, which also removes the underlying blob or local file
`memo` — the row itself, via the driver's plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go` line 237, `store/db/postgres/memo.go` line 244)

`memo_share` is affected too, but by a database-level foreign key rather than Go code:

```102:110:/bench/repo/store/migration/sqlite/LATEST.sql
CREATE TABLE memo_share (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  uid        TEXT    NOT NULL UNIQUE,
  memo_id    INTEGER NOT NULL,
  creator_id INTEGER NOT NULL,
  created_ts BIGINT  NOT NULL DEFAULT (strftime('%s', 'now')),
  expires_ts BIGINT  DEFAULT NULL,
  FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE
);
```

This is the only `ON DELETE CASCADE` in the schema (same in `store/migration/postgres/LATEST.sql` line 108). Worth flagging that on SQLite this depends on `PRAGMA foreign_keys` being enabled for the connection, so it's less robust than the Go-side cleanup.

Two scope notes. When the delete comes through the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go`, line 518), comment memos are deleted first by looking up `memo_relation` rows of type `MemoRelationComment`, so additional `memo` rows and their own relations, attachments, and shares are affected recursively. And `reaction` rows are *not* deleted on this path; they're only read to build the webhook payload, so reactions pointing at the deleted memo appear to be orphaned.
