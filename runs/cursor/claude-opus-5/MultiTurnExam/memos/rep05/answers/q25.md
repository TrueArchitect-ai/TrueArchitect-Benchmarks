**Engine: CEL (Google Common Expression Language) parsed with `cel-go`, in `internal/filter`** (entry point `filter.DefaultEngine()` in `internal/filter/engine.go`)

**Mechanism, in one sentence:** the CEL expression is parsed and schema-validated into a dialect-agnostic intermediate representation, then a renderer walks that IR and emits a dialect-specific SQL fragment plus placeholder args, which the driver appends to its `WHERE` clause.

The three-phase pipeline and its file layout are documented in `internal/filter/README.md`:

`internal/filter/schema.go` declares the allowed memo fields, their types and backing columns, and the CEL environment, so only schema fields can appear in a filter.
`internal/filter/parser.go` converts the `cel-go` AST into the IR defined in `internal/filter/ir.go`, enforcing operator and type rules.
`internal/filter/render.go` translates the IR into SQL, switching on `DialectSQLite`, `DialectMySQL`, or `DialectPostgres` at roughly forty sites to handle the differences: `?` versus `$n` placeholders, JSON access (`json_extract` vs `->>`), tag membership (`LIKE` vs `JSON_CONTAINS` vs `@>`), `LIKE` vs `ILIKE`, regex (`REGEXP` vs `~`), and date-part extraction (`strftime` vs `YEAR`/`MONTH` vs `EXTRACT`).

Store integration goes through `filter.AppendConditions` in `internal/filter/helpers.go`, which is exactly what the memo drivers call. In the SQLite implementation:

```57:63:/bench/repo/store/db/sqlite/memo.go
	engine, err := filter.DefaultEngine()
	if err != nil {
		return nil, err
	}
	if err := filter.AppendConditions(ctx, engine, find.Filters, filter.DialectSQLite, &where, &args); err != nil {
```

The Postgres and MySQL equivalents in `store/db/postgres/memo.go` and `store/db/mysql/memo.go` pass their own dialect constants. One SQLite-specific detail: regex support depends on a Go-backed `regexp` function registered in `store/db/sqlite/functions.go`, and because each engine uses a different regex flavor, patterns aren't portable across dialects.
