The server starts exactly **one** registered background runner:

`s3presign.Runner` — `server/runner/s3presign/runner.go`; started in `Server.startBackgroundRunners` (`server/server.go:153`) with an immediate `RunOnce(ctx)` at boot, then a long-running `Run(s3Context)` goroutine driven by a `time.NewTicker(12 * time.Hour)` (`runnerInterval`, line 27), refreshing expiring S3 presigned URLs until its dedicated context is cancelled on shutdown.

Two other long-lived goroutine sets are started, though they're not "runners" in the `server/runner` sense:

Webhook async dispatch workers — `internal/webhook/webhook.go:42`; four goroutines started from a package `init()`, driven by arrivals on a 128-slot `asyncPostQueue` channel (event-driven, not timed).
SSE connection loop and heartbeat — `server/router/api/v1/sse_handler.go`; one per connected browser, with a 30-second `sseHeartbeatInterval` keepalive; the hub is closed during shutdown by `closeLongLivedConnections` (`server/server.go:203`).

**Unused scheduling infrastructure:** `server/runner/memopayload` defines a full `Runner` type with `NewRunner` and a batched `RunOnce` that rebuilds the payload of every memo (`server/runner/memopayload/runner.go:14-27`), but **the server never constructs or starts it** — the only reference to `memopayload.NewRunner` anywhere in the repo is its own definition. What the server actually uses from that package is the standalone helper `RebuildMemoPayload` (line 74), called inline from `APIV1Service.CreateMemo` and `UpdateMemo` (`server/router/api/v1/memo_service.go:108` and `:447`). So the backfill runner is dead scheduling infrastructure, presumably left over as a one-shot migration tool.
