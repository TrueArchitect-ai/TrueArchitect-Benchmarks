**`memo`, `memo_relation`, `attachment`, `memo_share`**

Breakdown of how each is reached:

- **`memo_relation`** — deleted explicitly in `Store.DeleteMemo` (`store/memo.go:142` and `:145`), once for `memo_id` and once for `related_memo_id`.
- **`attachment`** — every attachment with `MemoID` matching is listed and removed via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also deletes the underlying local file or object-storage blob before the row (`store/attachment.go:132`).
- **`memo`** — the row itself, via the driver's plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`). Additional `memo` rows are affected when the API handler deletes child comments first, looping over `MemoRelationComment` relations at `server/router/api/v1/memo_service.go:573`, each recursing through the same cascade.
- **`memo_share`** — not touched by Go code; cleaned up by a database-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`).

Worth noting that `reaction` is **not** in the list. `APIV1Service.DeleteMemo` lists reactions at line 545, but only to build the webhook payload — I don't see any delete of reaction rows on this path, so they appear to be orphaned (reactions are keyed by the `content_id` string, not a foreign key, so no database cascade covers them either).
