Three categories of near-miss that a plain search for `GetUser` turns up but which are *not* affected:

`ts.Service.GetUser(ctx, &apiv1.GetUserRequest{...})` in the API test files and `ConnectServiceHandler.GetUser` at `server/router/api/v1/connect_services.go:115` are the **RPC** `APIV1Service.GetUser`, a different method with a protobuf request type. `currentUser.GetUser()` in `user_resource_name_test.go` is a generated protobuf field getter. And `d.GetUser(...)` inside `DB.UpdateUser` at `store/db/mysql/user.go:77` is the MySQL **driver's** own `GetUser`, reached through the `store.Driver` interface (q08) rather than through `Store`.

That last one is the trap worth naming: if the signature change propagates to the `Driver` interface rather than staying on the `Store` wrapper, then all three dialect implementations in `store/db/{mysql,postgres,sqlite}/user.go` change too, and `store/db/mysql/user.go:77` becomes a real call site. As written, `Store.GetUser` is a caching wrapper (it checks `userCache` before delegating), so a change confined to the `Store` layer leaves the drivers alone.
