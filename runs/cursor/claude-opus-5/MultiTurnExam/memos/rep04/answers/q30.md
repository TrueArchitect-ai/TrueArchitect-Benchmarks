All four are defined in `server/router/api/v1/memo_service_webhooks.go` and are invoked from:

| Dispatcher | Call site |
|---|---|
| Created | `server/router/api/v1/memo_service.go:157` (in `CreateMemo`) |
| Updated | `server/router/api/v1/memo_update_helpers.go:67` (in `dispatchMemoUpdatedSideEffects`) |
| Deleted | `server/router/api/v1/memo_service.go:562` (in `DeleteMemo`) |
| Comment created | `server/router/api/v1/memo_service_comments.go:119` (in `CreateMemoComment`) |

**Convergence:** `webhook.PostAsync` → `webhook.Post` in `internal/webhook/webhook.go`

The first three funnel through the shared private helper `dispatchMemoRelatedWebhook` (line 48), which differs only by activity-type string; it resolves the memo's creator and loads that user's hooks. `DispatchMemoCommentCreatedWebhook` is the odd one out — it takes `relatedMemoCreatorID` and notifies the **parent memo's owner** rather than the comment author, but builds the same payload and calls the same delivery function.

Every path ends at `webhook.PostAsync(payload)`, which enqueues onto a buffered channel of capacity 128 drained by four worker goroutines started in `init()` (lines 39–55). Each worker calls `Post`, the synchronous sender that does the HMAC-SHA256 Standard Webhooks signing from q22. Two consequences worth noting: delivery is fire-and-forget, so failures are only logged via `slog.Warn` and never surface to the API caller; and if the queue is full, `PostAsync` takes the `default` branch and **drops the webhook** with a warning rather than blocking the request.

Note the deleted-memo dispatch happens *before* the row is removed (line 562 precedes the delete at 580 in q16/q26), since the payload needs the memo's contents.
