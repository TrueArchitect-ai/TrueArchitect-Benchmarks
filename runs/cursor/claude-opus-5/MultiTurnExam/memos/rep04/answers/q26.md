**memo, memo_relation, attachment, memo_share**

Broken down by how each is reached:

**Directly by explicit cascade code in `Store.DeleteMemo`** (`store/memo.go`, lines 140–158, per q16):
- `memo_relation` — two deletes, one matching `memo_id` and one matching `related_memo_id`, since the table stores a directed pair
- `attachment` — each row found by `FindAttachment{MemoID}` is deleted individually via `Store.DeleteAttachment`
- `memo` — the row itself, last, via `s.driver.DeleteMemo`. The driver SQL is a plain single-row delete with no cascade of its own:

```239:239:/bench/repo/store/db/sqlite/memo.go
	stmt := "DELETE FROM `memo` WHERE " + strings.Join(where, " AND ")
```

**By database-level foreign key cascade:**
- `memo_share` — no Go code deletes it, but the schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`), so rows disappear when the memo row is deleted.

**Additional `memo` rows:** `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go`, lines 567–577) first deletes each child comment by calling `Store.DeleteMemo` on it, so every comment repeats the whole sequence above.

Two things deliberately not in the list. `reaction` rows are **not** deleted — they're only read to build the webhook payload, and because `store.Reaction` links via a generic `ContentID` string rather than a memo foreign key (q15), nothing cleans them up. And attachment deletion also removes data *outside* the database: `Store.DeleteAttachment` calls `DeleteAttachmentStorage` first, which `os.Remove`s the file for `LOCAL` storage before the row is deleted.

One caveat on `memo_share`: the cascade relies on foreign key enforcement being active. SQLite requires `PRAGMA foreign_keys = ON` per connection, so whether the cascade actually fires there depends on the driver's connection setup, which I did not verify.
