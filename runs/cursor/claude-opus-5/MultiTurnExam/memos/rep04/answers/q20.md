**Mechanism:** Server-Sent Events (SSE) over HTTP — `Content-Type: text/event-stream` on a long-lived `GET /api/v1/sse`

**Hub path:** `server/router/api/v1/sse_hub.go`

**Memo handlers that broadcast:** `CreateMemo`, `DeleteMemo`, `CreateMemoComment`, `UpsertMemoReaction`, `DeleteMemoReaction`, and the shared helper `dispatchMemoUpdatedSideEffects`

The hub defines `SSEHub` (line 56) with `Subscribe`/`Unsubscribe`/`Broadcast`/`Close`, the `SSEEvent` payload (line 24), and six event type constants (lines 15–20): `memo.created`, `memo.updated`, `memo.deleted`, `memo.comment.created`, `reaction.upserted`, `reaction.deleted`.

The endpoint lives in `server/router/api/v1/sse_handler.go` — `RegisterSSERoutes` mounts `GET /api/v1/sse` (line 27), and `handleSSE` sets the event-stream header, authenticates, calls `hub.Subscribe(userID, role)`, then flushes each event as it arrives. Subscription is scoped by user ID and role, which is how the hub filters private memos per recipient.

Two structural notes. The `memo.updated` event isn't emitted by `UpdateMemo` directly — it goes through `dispatchMemoUpdatedSideEffects`, which is shared by three callers (`memo_service.go:513`, `memo_attachment_service.go:48`, `memo_relation_service.go:48`), so attachment and relation edits also surface as memo updates. And the comment path relies on suppression rather than a second event: `CreateMemoComment` wraps its inner `CreateMemo` call in `withSuppressSSE` (q11) so the nested creation stays silent, then broadcasts `memo.comment.created` against the parent instead.
