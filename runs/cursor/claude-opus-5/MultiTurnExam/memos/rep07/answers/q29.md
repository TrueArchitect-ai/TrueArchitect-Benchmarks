On the frontend, `authInterceptor` is installed on the shared Connect transport and does three things:

```156:178:web/src/connect.ts
const authInterceptor: Interceptor = (next) => async (req) => {
  const isRetryAttempt = req.header.get(RETRY_HEADER) === RETRY_HEADER_VALUE;
  const token = await getRequestToken();
  setAuthorizationHeader(req, token);

  try {
    return await next(req);
  } catch (error) {
    if (!shouldHandleUnauthenticatedRetry(error, isRetryAttempt)) {
      throw error;
    }

    try {
      const newToken = await refreshAndGetAccessToken();
      setAuthorizationHeader(req, newToken);
      req.header.set(RETRY_HEADER, RETRY_HEADER_VALUE);
      return await next(req);
    } catch (refreshError) {
      redirectOnAuthFailure();
      throw refreshError;
    }
  }
};
```

It attaches `Authorization: Bearer <token>`; refreshes proactively when the stored token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry (the comment notes this matters for public endpoints like `ListMemos`, where an expired token would silently return guest-scoped data); and reactively retries once on a `Code.Unauthenticated` response, redirecting to login if the refresh itself fails. An `X-Retry` header prevents retry loops.

The refresh call goes out on a deliberately separate transport with no interceptors (line 65) so refreshing can't recurse, and `tokenRefreshManager` deduplicates concurrent refreshes — important because a focus-triggered proactive refresh and a 401-triggered one could otherwise race against server-side token rotation. All requests use `credentials: "include"` so the refresh cookie rides along.

On the backend, `server/auth/` holds the validation logic — `authenticator.go` (with `token.go`, `extract.go`, and `context.go`):

- `AuthenticateByAccessTokenV2` (line 41) parses and verifies the JWT access token against the server secret.
- `AuthenticateByRefreshToken` (line 61) parses the refresh token *and* checks it against the database via `GetUserRefreshTokenByID`, so refresh tokens are revocable.
- `AuthenticateByPAT` (line 102) recognizes tokens by the `PersonalAccessTokenPrefix`, looks them up by hash, and records last-used.

`resolveBearer` (line 149) dispatches on that prefix to choose between PAT and JWT. Two entry points differ in policy: `AuthenticateToUser` (line 190) will fall back to the refresh cookie when no bearer header is present, while `Authenticate` (line 213) ignores the cookie entirely. The gRPC-Gateway wires this in through the auth middleware in `server/router/api/v1/v1.go`, which applies the resolved identity to the request context.
