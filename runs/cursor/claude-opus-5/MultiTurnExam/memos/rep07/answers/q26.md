**`memo_relation`, `attachment`, `memo`** — and `memo_share` only on backends that enforce foreign keys.

The three tables touched by explicit code, in execution order inside `Store.DeleteMemo` (`store/memo.go:140`):

1. `memo_relation` — deleted twice, once matching `memo_id` and once matching `related_memo_id`, so links in both directions go away.
2. `attachment` — every row found by `FindAttachment{MemoID}`, each removed via `Store.DeleteAttachment`.
3. `memo` — the row itself, last, via the dialect driver's plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`).

The API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) widens this without adding new tables: it first lists comment relations and recursively calls `Store.DeleteMemo` on each comment memo (lines 567–577), so additional `memo`, `memo_relation`, and `attachment` rows are removed for every comment.

Two caveats worth knowing:

`memo_share` has a database-level cascade rather than explicit Go code — `store/migration/sqlite/LATEST.sql:109` declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`. But the SQLite connection is opened with foreign keys disabled (`_pragma=foreign_keys(0)` in `store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and share rows are left orphaned; on Postgres/MySQL it does.

`reaction` rows are **not** deleted. The handler lists reactions at line 545, but only to build the webhook payload — there is no `DeleteReaction` call anywhere in the delete path, and the `reaction` table has no foreign key to `memo` (it references memos by the string `content_id`). Reactions on a deleted memo therefore persist.
