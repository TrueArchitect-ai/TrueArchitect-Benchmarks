**Server-Sent Events (SSE); `server/router/api/v1/sse_hub.go`; CreateMemo, UpdateMemo, DeleteMemo, CreateMemoComment, SetMemoAttachments, SetMemoRelations, UpsertMemoReaction, DeleteMemoReaction**

The mechanism is SSE, not WebSockets. The hub is `SSEHub` in `server/router/api/v1/sse_hub.go` (type at line 56), with `Subscribe`, `Unsubscribe`, `Broadcast`, and `Close`; subscriptions are keyed by user ID and role so events can be filtered by memo visibility. The HTTP endpoint is wired up in `server/router/api/v1/sse_handler.go` via `RegisterSSERoutes`, mounted alongside the rest of `/api/v1` in `server/router/api/v1/v1.go` at line 125.

Six event types are defined in `sse_hub.go`:

```15:20:server/router/api/v1/sse_hub.go
	SSEEventMemoCreated        SSEEventType = "memo.created"
	SSEEventMemoUpdated        SSEEventType = "memo.updated"
	SSEEventMemoDeleted        SSEEventType = "memo.deleted"
	SSEEventMemoCommentCreated SSEEventType = "memo.comment.created"
	SSEEventReactionUpserted   SSEEventType = "reaction.upserted"
	SSEEventReactionDeleted    SSEEventType = "reaction.deleted"
```

Two details worth knowing. The `memo.updated` event isn't broadcast inline by its handlers — all three route through the shared `dispatchMemoUpdatedSideEffects` helper (called from `memo_service.go:513`, `memo_attachment_service.go:48`, and `memo_relation_service.go:48`), so that single call site covers three RPCs. And `CreateMemo` guards its broadcast with `if !isSSESuppressed(ctx)`, which is how `CreateMemoComment` avoids emitting a spurious `memo.created` for the comment itself while still publishing `memo.comment.created` against the parent memo.
