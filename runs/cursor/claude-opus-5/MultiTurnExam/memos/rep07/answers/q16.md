Two kinds of records, in this order, inside `Store.DeleteMemo` (`store/memo.go`):

1. **`memo_relation` rows** — deleted in both directions, where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`).
2. **`attachment` rows** — every attachment linked to the memo, listed via `FindAttachment{MemoID}` and deleted one at a time.

Only after both does it delete the memo row itself:

```140:159:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

This cleanup is deliberately in the store layer rather than the database, since the dialect method `DB.DeleteMemo` (for example `store/db/sqlite/memo.go:237`) issues a bare `DELETE FROM memo WHERE id = ?` with no cascade.

Separately, the API handler `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go` (line 518) does extra work around this call: before deleting the memo it looks up comment relations and recursively calls `Store.DeleteMemo` on each comment memo, so each comment gets the same relation and attachment cleanup. It also lists reactions and attachments and dispatches a `memo deleted` webhook.
