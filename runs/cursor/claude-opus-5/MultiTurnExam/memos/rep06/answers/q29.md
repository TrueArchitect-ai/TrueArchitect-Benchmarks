**Interceptor: `web/src/connect.ts` (with token storage in `web/src/auth-state.ts`); tokens: short-lived JWT access token in memory/`Authorization: Bearer`, refresh token in an HTTP-only cookie, and Personal Access Tokens for programmatic clients; backend: `server/auth/`**

On the frontend, `authInterceptor` (line 156 of `web/src/connect.ts`) is attached to the shared Connect transport (line 188) and does three things: it attaches the access token as `Authorization: Bearer <token>`, it proactively refreshes when the token is near expiry (`getRequestToken`, lines 124–150), and on a `Code.Unauthenticated` response it refreshes once, replays the request with an `X-Retry` marker, and redirects to login if that fails.

The refresh token is never touched by JavaScript — it rides along as a cookie because the transport uses `fetch` with `credentials: "include"` (line 57–62), and refresh calls go through a separate `refreshTransport` with no interceptors to avoid recursion (line 65). Concurrent refreshes are deduplicated by `tokenRefreshManager` (line 30), which matters because server-side refresh tokens rotate.

On the backend, validation lives in `server/auth/` — `Authenticator` in `server/auth/authenticator.go` exposes `AuthenticateByAccessTokenV2` (JWT signed with the server secret), `AuthenticateByRefreshToken` (parsed, then checked against the stored token row via `GetUserRefreshTokenByID`), and `AuthenticateByPAT` (hash lookup through `GetUserByPATHash`, with expiry and last-used tracking). `AuthenticateToUser` tries the `Authorization` header first and falls back to the refresh cookie. Token minting/parsing is in `server/auth/token.go`, header/cookie extraction in `server/auth/extract.go`, and context plumbing in `server/auth/context.go`.

This authenticator is invoked from both protocol paths: the gateway middleware in `server/router/api/v1/v1.go` and the Connect interceptor chain, with per-RPC public/anonymous exceptions listed in `server/router/api/v1/acl_config.go`.
