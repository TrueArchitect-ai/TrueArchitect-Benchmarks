**`memo_relation`, `attachment`, `memo`** — plus **`memo_share`** via a database-level foreign key cascade.

The explicit cascade in `Store.DeleteMemo` (`store/memo.go:140–159`) runs in this order:

1. `memo_relation` — deleted twice, once for rows where the memo is the source (`MemoID`) and once where it is the target (`RelatedMemoID`).
2. `attachment` — every attachment with `MemoID` equal to this memo is removed through `Store.DeleteAttachment`, which also deletes the underlying blob from local disk or S3 (`store/attachment.go:132–149`) before removing the row.
3. `memo` — the driver finally issues the plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237–248`); it contains no cascade SQL of its own.

`memo_share` rows are removed by the schema rather than by Go code, through the foreign key declared at `store/migration/sqlite/LATEST.sql:109` (same in `store/migration/postgres/LATEST.sql:108`):

```105:109:store/migration/sqlite/LATEST.sql
  memo_id    INTEGER NOT NULL,
  creator_id INTEGER NOT NULL,
  created_ts BIGINT  NOT NULL DEFAULT (strftime('%s', 'now')),
  expires_ts BIGINT  DEFAULT NULL,
  FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE
```

Two things this does *not* touch: `reaction` rows are only read (to build the webhook payload in `server/router/api/v1/memo_service.go`), never deleted; and when the delete goes through the API handler rather than the store directly, comment memos are deleted first as separate memos, so the same three tables are hit again for each child.
