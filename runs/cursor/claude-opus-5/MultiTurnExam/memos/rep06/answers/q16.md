Before the memo row is deleted, the store layer removes two kinds of records:

1. **Memo relations** — both directions: rows where the memo is the source (`MemoID`) and rows where it is the target (`RelatedMemoID`).
2. **Attachments** linked to the memo — listed by `MemoID` and deleted one by one via `Store.DeleteAttachment`.

This cascade lives in `Store.DeleteMemo`:

```140:159:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	if err != nil {
		return err
	}
	for _, attachment := range attachments {
		if err := s.DeleteAttachment(ctx, &DeleteAttachment{ID: attachment.ID}); err != nil {
			return err
		}
	}
	return s.driver.DeleteMemo(ctx, delete)
}
```

One level up, the API handler `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go` adds a third kind of cleanup before calling the store: it finds comment memos (memo relations of type `MemoRelationComment` pointing at this memo) and deletes each of those child memos first (lines 567–577), each of which runs the same relation/attachment cascade. It dispatches the deletion webhook beforehand and broadcasts an SSE event afterward.

Note that reactions are only *listed* in the handler (to build the webhook payload); no explicit reaction deletion happens in this path.
