The browser hits a plain HTTP route (not gRPC), and the image bytes turn out to live in the `user` table itself as a base64 data URI — there's no file on disk or object store involved.

Hops, in order:

- `GET /file/users/{username}/avatar` (URL minted by `convertUserFromStore`) — `server/router/api/v1/user_service_converters.go:36`
- `FileServerService.RegisterRoutes` route registration — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (handler) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks `userCache`, only when looking up by ID) — `store/user.go:148`
- `Store.ListUsers` (populates `userCache`) — `store/user.go:136`
- `Driver.ListUsers` (interface) — `store/driver.go:47`
- `(*DB).ListUsers` — `store/db/sqlite/user.go:88` (MySQL/Postgres equivalents in `store/db/mysql/user.go`, `store/db/postgres/user.go`)
- `SELECT ... avatar_url ... FROM user WHERE username = ?` — `store/db/sqlite/user.go:152-165`

A few details that matter along the way:

**Why the URL exists at all.** When the API converts a user for the wire, it checks whether `AvatarURL` is a base64 data URI; if so it replaces the payload with the `/file/users/{username}/avatar` path so responses don't carry the full image (`server/router/api/v1/user_service_converters.go:31-40`). If the avatar is an ordinary external URL — e.g. one supplied by an OAuth2 provider — it's passed through unchanged and the browser never touches this handler.

**Access control.** `serveUserAvatar` gates on `s.Profile.AllowAnonymous()`: on a private instance the viewer must present a valid session, access token, or PAT, otherwise the request is rejected with 401 (`server/router/fileserver/fileserver.go:173-181`). Beyond that there's no per-user check, so any authenticated viewer can fetch any other user's avatar.

**The route parameter is a username, not an ID.** `getUserByUsername` passes the `:identifier` path segment straight into `store.FindUser{Username: &identifier}`, so the `userCache` fast path in `Store.GetUser` (which only applies when `find.ID != nil`) is skipped; every avatar request reaches `ListUsers` and the database, though the result is written back into the cache at `store/user.go:143`.

**Decoding and hardening.** The handler parses the data URI via `parseDataURI` (`server/router/fileserver/fileserver.go:737`), rejects anything outside `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:75`, the PNG/JPEG/GIF/WebP set also enforced on upload at `server/router/api/v1/user_service.go:343-352`), sets security headers plus `Cache-Control`, and writes the decoded bytes with `c.Blob`.

**Wiring.** The file server is constructed and its routes registered ahead of the gRPC gateway at `server/server.go:81-82`, which is why `/file/...` never reaches the gateway.
