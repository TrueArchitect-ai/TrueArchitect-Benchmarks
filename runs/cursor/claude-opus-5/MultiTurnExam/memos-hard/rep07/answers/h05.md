**Mechanism: explicit Go code — two `DELETE FROM reaction` statements inside the driver-level `DeleteUser` transaction. There is no database-level cascade for reactions.**

What I checked, and what each check showed:

**1. The delete-user transaction (all three drivers).** Each driver's `deleteUserTargetsTx` runs two separate reaction deletions before removing memos and the user row:

The two cover different things: `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400`) removes reactions the deleted user *made*, via `DELETE FROM reaction WHERE creator_id = ?`; `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380`) removes reactions *others* made on the deleted user's content, batching over `content_id IN (...)`. The content IDs are the string form `"memos/" + memo.UID` built in `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go:512`), drawn from the recursive memo tree that also pulls in comment memos (`store/db/sqlite/user_delete.go:134-147`).

The MySQL and Postgres drivers are structurally identical: `store/db/mysql/user_delete.go:96`, `:102`, `:417`, `:437` and `store/db/postgres/user_delete.go:96`, `:102`, `:380`, `:400`.

**2. The schema.** The `reaction` table has no foreign key at all — just an id, `created_ts`, `creator_id`, `content_id`, `reaction_type`, and a uniqueness constraint (`store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`). Note `content_id` is a text value like `memos/<uid>`, not an integer FK, so a cascade wouldn't even be expressible without a schema change.

**3. Every FK in the schemas.** Grepping for `FOREIGN KEY`/`REFERENCES` across all three `LATEST.sql` files returns exactly one constraint per dialect, and it is on `memo_share`, not `reaction`: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`). So database-level cascade is ruled out.

**4. A test that pins the behavior.** `store/test/user_delete_test.go` creates reactions by the doomed user and by a peer, then after deletion asserts only the peer's reaction on the peer's own memo survives (`store/test/user_delete_test.go:97-113` and `:216-220`).

All of this runs in one transaction opened at `store/db/sqlite/user_delete.go:30` and committed at `:51`, so reaction cleanup either fully lands or fully rolls back with the rest of the deletion.
