Visibility is enforced in eleven distinct places across five server surfaces. They fall into two shapes: *gate checks* that reject a request for an already-loaded memo, and *query scoping* that never loads non-visible memos in the first place.

Enforcement sites, one per line:

- `checkMemoReadAccess` (single-memo gate; also blocks archived memos from non-creators) — `server/router/api/v1/memo_service.go:39`
- `ListMemos` query scoping (anonymous → `PUBLIC` only; authenticated → CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`) — `server/router/api/v1/memo_service.go:218`
- User stats query scoping (same public/protected narrowing, applied twice) — `server/router/api/v1/user_service_stats.go:84` and `:218`
- `checkAttachmentPermission` on the HTTP file server, including the `share_token` bypass — `server/router/fileserver/fileserver.go:677`
- Attachment service permission check (gRPC surface) — `server/router/api/v1/attachment_service.go:445`
- `ListMemoAttachments` gate — `server/router/api/v1/memo_attachment_service.go:214`
- Reaction service: listing reactions and upserting a reaction — `server/router/api/v1/reaction_service.go:30` and `:83`
- Comment creation on a private parent memo — `server/router/api/v1/memo_service_comments.go:41`
- SSE delivery filter `SSEClient.canReceive` — `server/router/api/v1/sse_hub.go:134`
- RSS feeds restricted to `PUBLIC` (instance feed and per-user feed) — `server/router/rss/rss.go:90` and `:141`
- Sitemap XML restricted to `PUBLIC` — `server/router/frontend/frontend.go:150`

Notes on how these differ, since the rules are not identical everywhere:

**The canonical gate** treats `PUBLIC` as open, requires authentication for `PROTECTED`, and restricts `PRIVATE` to the creator:

```55:66:server/router/api/v1/memo_service.go
	if memo.Visibility != store.Public {
		user, err := s.fetchCurrentUser(ctx)
		...
		if user == nil {
			return status.Errorf(codes.Unauthenticated, "user not authenticated")
		}
		if memo.Visibility == store.Private && memo.CreatorID != user.ID {
			return status.Errorf(codes.PermissionDenied, "permission denied")
		}
	}
```

It is reused by `GetMemo` (`:356`), the parent-memo check (`:367`), and `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`).

**Admins.** `checkMemoReadAccess` gives admins no override on private memos, but the attachment paths do — both `server/router/api/v1/attachment_service.go:451` and `server/router/fileserver/fileserver.go:699` exempt `store.RoleAdmin`, as does SSE (`server/router/api/v1/sse_hub.go:137`).

**Anonymous access interacts with instance mode.** The file server additionally requires `s.Profile.AllowAnonymous()` before serving even a `PUBLIC` memo's attachment to an unauthenticated visitor (`server/router/fileserver/fileserver.go:677`), and it accepts a valid non-expired `share_token` scoped to that memo as an alternative to authentication (`:684-689`) — a deliberate bypass supporting the shared-memo page.

**Not a read surface but visibility-driven:** mention and email notifications suppress delivery based on visibility (`server/router/api/v1/memo_mention_helpers.go:62-84`, `server/router/api/v1/user_service_notifications.go:309-312`, `server/notification/email.go:313-316`). I left these off the main list since they gate outbound notifications rather than viewing.

The MCP surface (`server/router/mcp/`) has no direct store access — it exposes the OpenAPI spec and proxies through the v1 API — so it inherits the API-layer enforcement rather than adding its own.
