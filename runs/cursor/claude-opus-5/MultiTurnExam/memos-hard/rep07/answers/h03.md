**Abstraction package: `internal/idp` (`internal/idp/idp.go`); implementation package: `internal/idp/oauth2` (`internal/idp/oauth2/oauth2.go`).**

Details:

- **The abstraction** is deliberately thin — `internal/idp` is a single file declaring only the provider-neutral result type that any provider must produce:

```1:8:internal/idp/idp.go
package idp

type IdentityProviderUserInfo struct {
	Identifier  string
	DisplayName string
	Email       string
	AvatarURL   string
}
```

There is no Go `interface` here; the "contract" is that each provider implementation returns `*idp.IdentityProviderUserInfo`. The structural side of the abstraction lives in the protobuf schema, where `IdentityProviderConfig` is a `oneof` and `IdentityProvider.Type` is an enum (`proto/store/idp.proto:11-25`) — both currently having exactly one variant, `OAUTH2` / `oauth2_config`.

- **The one concrete implementation** is OAuth 2.0, in `internal/idp/oauth2`. Its `IdentityProvider` type wraps a `storepb.OAuth2Config` and provides `ExchangeToken` (authorization-code exchange, with optional PKCE `code_verifier`, `internal/idp/oauth2/oauth2.go:47`) and `UserInfo` (bearer-token call to the configured userinfo endpoint, mapping arbitrary JSON claims onto the struct fields via the configured `FieldMapping`, `internal/idp/oauth2/oauth2.go:83`).

- **Where they meet:** the SSO login path dispatches on provider type and is currently a single branch:

```119:134:server/router/api/v1/auth_service_sso.go
	var userInfo *idp.IdentityProviderUserInfo
	if identityProvider.Type == storepb.IdentityProvider_OAUTH2 {
		oauth2IdentityProvider, err := oauth2.NewIdentityProvider(identityProvider.Config.GetOauth2Config())
		...
		token, err := oauth2IdentityProvider.ExchangeToken(ctx, redirectURI, code, codeVerifier)
		...
		userInfo, err = oauth2IdentityProvider.UserInfo(ctx, token)
```

Note there is no OIDC-specific package; OIDC providers are supported only insofar as they can be configured as generic OAuth2 with a userinfo URL and field mappings.
