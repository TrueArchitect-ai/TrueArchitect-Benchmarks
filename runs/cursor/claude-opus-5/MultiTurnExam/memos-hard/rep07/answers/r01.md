**Premise correction: there is no Redis anywhere in this repository — no `redis` import in any Go file, and no Redis (or Memcached/Valkey) module in `go.mod`/`go.sum`. The cache layer is a hand-written, process-local in-memory cache, so there is no connection to configure.**

**The actual mechanism.** `store/cache/cache.go` defines a `Cache` type backed by a `sync.Map` plus an atomic item counter (`store/cache/cache.go:66-73`). Each entry stores its value, an absolute `expiration` timestamp, and a rough size estimate (`store/cache/cache.go:35-39`). A goroutine started in `cache.New` sweeps expired entries on a ticker (`store/cache/cache.go:83`, `:200-215`), and writes that push the cache past `MaxItems` trigger `cleanupOldest`, which drops roughly 20% of capacity (`store/cache/cache.go:117-119`, `:253`).

**The TTL that applies to user entries is 10 minutes**, and it is not user-specific — it comes from the single `cache.Config` the store builds for all three of its caches:

```39:53:store/store.go
	// Default cache settings
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
```

So `userCache`, `instanceSettingCache`, and `userSettingCache` each get a 10-minute default TTL, a 5-minute cleanup interval, and a 1000-item ceiling. That configuration is hardcoded in `store.New` — there is no flag, environment variable, or config file that changes it. The same values appear as the package defaults in `cache.DefaultConfig` (`store/cache/cache.go:57-64`), though `store.New` constructs its own literal rather than calling that helper.

User entries are written through `Store.Set` calls keyed by `userCacheKey(user.ID)` (`store/user.go:88`, with writes at `:98`, `:122`, `:132`, `:143`, `:167`) and read back only in `Store.GetUser` when the lookup is by ID (`store/user.go:150`). Every write goes through `Cache.Set`, which forwards `c.config.DefaultTTL` to `SetWithTTL` (`store/cache/cache.go:93-95`); nothing in the codebase calls `SetWithTTL` directly for users, so the 10-minute value is the only TTL in effect. Explicit invalidation happens on user deletion via `deleteUserCache` (`store/user_delete.go:39-47`).

One practical consequence of it being in-process rather than shared: the cache is per-instance and does not survive restart, so running multiple memos instances against one database would give each its own copy with independent expiry.
