**Mechanism: explicit Go code — deleted inside the driver-level `DeleteUser` transaction, not by any database-level cascade. Evidence: `store/db/sqlite/user_delete.go:96,102,380,400` (plus the mirrored `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`), and the `reaction` table DDL in `store/migration/*/LATEST.sql`, which has no foreign key at all.**

What I checked, and what it shows:

**1. The deletion path.** `DeleteUser` opens a transaction and calls `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:29-59`). That function issues two separate reaction deletes, and they are the first and third statements in the ordered sequence:

```96:104:store/db/sqlite/user_delete.go
	if err := deleteReactionsByContentIDsTx(ctx, tx, contentIDs); err != nil {
		return err
	}
	if err := deleteAttachmentsByIDsTx(ctx, tx, targets.attachmentIDs); err != nil {
		return err
	}
	if err := deleteReactionsByCreatorTx(ctx, tx, userID); err != nil {
		return err
	}
```

Two distinct cases are covered. `deleteReactionsByCreatorTx` (line 400) runs `DELETE FROM reaction WHERE creator_id = ?` — the reactions the user *made*, wherever they live. `deleteReactionsByContentIDsTx` (line 380) runs batched `DELETE FROM reaction WHERE content_id IN (...)` over the `memos/<uid>` content IDs of the user's memo tree (built by `memoContentIDsFromRefs`, line 512) — reactions *other people* left on the user's memos. The memo tree itself comes from a recursive CTE that also pulls in comment descendants (line 134).

**2. All three dialects.** The same two functions exist and are called in the same order in `store/db/postgres/user_delete.go` (lines 96, 102, 380, 400) and `store/db/mysql/user_delete.go` (lines 96, 102, 417, 437), so behavior doesn't diverge by backend.

**3. The schema — no database-level rule.** The `reaction` table is defined at `store/migration/sqlite/LATEST.sql:92`, `store/migration/postgres/LATEST.sql:91`, and `store/migration/mysql/LATEST.sql:91`. In every dialect it is `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type`, and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — `creator_id` is a plain `INTEGER`/`INT` with no `REFERENCES user(id)` and no `ON DELETE CASCADE`. The table's original migration (`store/migration/*/0.20/00__reaction.sql`) defines it the same way, so there was never such a constraint to drop. Searching all migrations for `FOREIGN KEY`/`ON DELETE` turns up cascades only on other tables (for example `memo_share.memo_id` at `store/migration/sqlite/LATEST.sql:109`).

A cascade also couldn't fire on SQLite even if one existed: the connection is opened with foreign keys off, `_pragma=foreign_keys(0)` at `store/db/sqlite/sqlite.go:53`. And `content_id` stores a string like `memos/<uid>`, not a memo row ID, so no FK to `memo` is possible either — which is exactly why the content-ID delete has to be done explicitly in Go.

**4. Test confirmation.** `store/test/user_delete_test.go` seeds reactions by the doomed user and a reaction by a peer on an unrelated memo, then asserts after deletion that the peer's reaction survives (lines 217-220) — confirming the deletion is scoped, not a blanket wipe.
