**Premise correction: there is no Redis anywhere in this repository.** A case-insensitive search for "redis" across the Go sources returns nothing, and neither `go.mod` nor `go.sum` contains a Redis client dependency. There is no external cache server to configure — no connection string, host, port, or auth setting exists.

**Actual mechanism:** the cache layer is a hand-rolled, in-process cache in `store/cache/cache.go`. `Cache` (line 67) is a thread-safe map built on `sync.Map` plus an atomic item counter, with per-entry expiration timestamps and a background cleanup goroutine started in `New` (line 83). It is purely in-memory and per-process, so it is not shared across instances and does not survive a restart.

**TTL for user entries: 10 minutes.** The store creates three separate caches — `instanceSettingCache`, `userCache`, and `userSettingCache` — and passes all three the same config at `store/store.go:40-53`:

```40:45:store/store.go
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}
```

So user entries get no special treatment: 10-minute TTL, sweep for expired entries every 5 minutes, and a 1000-item ceiling per cache, above which `cleanupOldest` (line 253) drops roughly 20% of the oldest entries. The same values are duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57`), though the store builds its own literal rather than calling it.

Two behavioral details worth knowing. Expiry is lazy as well as periodic: `Get` (line 123) checks the timestamp and deletes on read, so a stale entry never gets served even between cleanup ticks. And the user cache is keyed by ID only — `Store.GetUser` (`store/user.go:148-156`) consults it just when the lookup is by `ID`, so lookups by username or email always hit the database while still repopulating the cache on the way back.
