**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never used by the running server, so there is no schedule to report.**

Two separate parts of the premise don't hold:

**The cron scheduler isn't wired up.** A cron package does exist at `internal/scheduler` — it has a cron-expression parser (`internal/scheduler/parser.go:30`), job type (`internal/scheduler/job.go`), middleware for recovery/logging/timeout (`internal/scheduler/middleware.go`), and a `New` constructor (`internal/scheduler/scheduler.go:54`). But the only files importing it are its own tests, `internal/scheduler/example_test.go:10` and `internal/scheduler/integration_test.go:13`. No production code constructs a scheduler or registers a job, so no cron expression is ever evaluated at runtime.

**No database-cleanup job exists.** Searching for cleanup, cron, nightly, and vacuum work across `server/`, `cmd/`, and `store/` turns up only unrelated things: inline cleanup during user and memo deletion (`server/router/api/v1/user_service.go:421-450`, `memo_service.go:579`), a best-effort rollback in the SSO path (`auth_service_sso.go:76`), and a test helper (`server/router/api/v1/test/test_helper.go:65`). None of these are scheduled.

What the server actually runs on a timer is a single background job, and it isn't cleanup: the S3 presign runner, which refreshes presigned attachment URLs. It uses a plain `time.Ticker` at a fixed 12-hour interval rather than a cron expression (`server/runner/s3presign/runner.go:27` and `:29-41`), and it is started from `startBackgroundRunners` at `server/server.go:162-171`, with one immediate pass at startup. Being interval-based, it has no wall-clock time of day — its firing times depend on when the process started.

The only other recurring timer in the backend is the in-memory cache sweep, every 5 minutes (`store/cache/cache.go:200-215`, configured at `store/store.go:42`), which evicts expired cache entries and never touches the database.
