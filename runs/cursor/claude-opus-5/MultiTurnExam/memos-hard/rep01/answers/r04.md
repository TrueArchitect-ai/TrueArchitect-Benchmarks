**Premise correction: neither. There is no message broker in this repository at all — no NATS, no RabbitMQ, no AMQP, Kafka, or pub/sub client. A case-insensitive search for all of those across the Go sources and `go.mod` returns zero hits, so there is no queue declaration to point to.**

**Actual mechanism: an in-process buffered Go channel with a fixed pool of goroutine workers, all in `internal/webhook/webhook.go`.**

The "queue" is a package-level channel with a capacity of 128:

```39:39:internal/webhook/webhook.go
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

The "workers" are four goroutines started in the package's `init` function (lines 42-55); each ranges over the channel and calls `Post` for every payload it receives, logging a warning on failure.

Producers call `PostAsync` (line 184), which does a non-blocking send:

```189:195:internal/webhook/webhook.go
	select {
	case asyncPostQueue <- requestPayload:
	default:
		slog.Warn("Dropped webhook dispatch because the async queue is full",
			slog.String("url", requestPayload.URL),
			slog.String("activityType", requestPayload.ActivityType))
	}
```

Two consequences worth noting, since they're exactly the guarantees a broker would otherwise provide. Delivery is best-effort and lossy: when all 128 slots are occupied the payload is dropped with a warning rather than queued or retried, and there is no retry logic anywhere in `Post` (`internal/webhook/webhook.go:120`) — a non-2xx response just returns an error that the worker logs. And the queue is purely in-memory, so anything still pending is lost on process restart and nothing is shared across multiple server instances.
