**Premise correction: there is no rate-limiting middleware in this repository — per-user or otherwise — so there is no registration site and no request limits to report.**

What I checked:

- A case-insensitive search across all Go sources for `ratelimit`, `rate_limit`, `throttl`, and `limiter` returns exactly one hit, and it is an aspirational comment rather than code: `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a future consideration.
- `go.mod` contains no rate-limiting dependency (no `golang.org/x/time/rate`, no `echo` rate-limit contrib package).
- The complete Echo middleware stack is two entries, registered at `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)`. The only other middleware in the API layer is `gatewayAuthMiddleware` (`server/router/api/v1/v1.go:69`, installed at line 97) and the matching Connect interceptor, both of which do authentication and anonymous-access policy, not throttling.

The nearest things that exist are concurrency caps, not rate limits — they bound how many operations run simultaneously, but impose no ceiling on requests per user over time:

- `thumbnailSemaphore`, a weighted semaphore of 3, in the file server (`server/router/fileserver/fileserver.go:46` and `:116`) and again on the API service (`server/router/api/v1/v1.go:59`).
- `imageProcessingSemaphore`, weight 2 (`server/router/api/v1/v1.go:60`).
- The webhook dispatch queue: a 128-slot buffered channel drained by 4 worker goroutines, which drops events when full (`internal/webhook/webhook.go:39-55`, `:184-196`). That's backpressure on outbound deliveries, not inbound request limiting.

If you're looking to add per-user rate limiting, the natural insertion points would be alongside the existing auth middleware at `server/router/api/v1/v1.go:69` (where the caller identity is already resolved) or as another `echoServer.Use(...)` at `server/server.go:52` for a coarser IP-based limit.
