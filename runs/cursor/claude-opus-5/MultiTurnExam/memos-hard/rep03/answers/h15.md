Notes on the shape of each mechanism:

- **The canonical gate** handles archived memos and the three visibility levels, returning `NotFound` for archived non-owners, `Unauthenticated` for anonymous access to non-public memos, and `PermissionDenied` for private memos owned by someone else:

```55:66:server/router/api/v1/memo_service.go
	if memo.Visibility != store.Public {
		user, err := s.fetchCurrentUser(ctx)
		if err != nil {
			return status.Errorf(codes.Internal, "failed to get user")
		}
		if user == nil {
			return status.Errorf(codes.Unauthenticated, "user not authenticated")
		}
		if memo.Visibility == store.Private && memo.CreatorID != user.ID {
			return status.Errorf(codes.PermissionDenied, "permission denied")
		}
	}
```

- **Listing is enforced in the query, not post-filtered.** Anonymous callers get `VisibilityList = [PUBLIC]`; authenticated callers get a CEL filter `creator_id == N || visibility in ["PUBLIC", "PROTECTED"]`, or `[PUBLIC, PROTECTED]` when browsing another specific user (`server/router/api/v1/memo_service.go:218-227`).

- **The file server is the one surface with a bypass.** Beyond the usual checks it honors a `share_token` query parameter, granting access to private/protected memos' attachments when the token is unexpired and issued for that exact memo (`server/router/fileserver/fileserver.go:684-690`). It also requires `s.Profile.AllowAnonymous()` before serving even public attachments anonymously (`:677`). The matching API-level share path is `GetMemoByShare` with `getActiveMemoShare` (`server/router/api/v1/memo_share_service.go:153`, `:199`).

- **SSE filters on the way out**, per subscribed client: private-memo events go only to the creator or an admin, while public, protected, and unset visibility are broadcast, and unknown values are denied (`server/router/api/v1/sse_hub.go:134-144`).

- **The four inline API checks** (attachments, list-attachments, reactions read/write, comment creation) repeat the same shape as `checkMemoReadAccess` but add `isSuperUser(user)` as an escape hatch, which the central gate does not have — a real behavioral difference between the sites.

- **RSS and the sitemap** enforce by construction rather than by check, hardcoding `VisibilityList: []store.Visibility{store.Public}` in their `FindMemo`, so non-public memos never enter those responses.

- **Notification gating** is arguably a different concern than request authorization, but it does re-derive viewer access from memo visibility before including memo content in emails/inbox messages, and there are two near-duplicate `canViewerAccessMemo` implementations (`server/router/api/v1/user_service_notifications.go:302` and `server/notification/email.go:306`) plus the mention-specific variant.

One thing I did not find: the MCP surface has no visibility logic of its own. Its catalog exposes `MemoService_ListMemos` and `MemoService_GetMemo` (`server/router/mcp/catalog.go:12-14`) and dispatches into the same API v1 handlers, so it inherits the enforcement above rather than duplicating it.
