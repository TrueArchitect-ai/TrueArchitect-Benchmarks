The derived metadata is the memo's `payload.tags` and `payload.property`, computed by a single markdown AST walk. It's written only by `memopayload.RebuildMemoPayload`, which the API calls on memo creation and on content updates — nothing else in production writes those fields.

**Answer: computation site — `memopayload.RebuildMemoPayload` (`server/runner/memopayload/runner.go:74`), delegating the actual extraction to `(*service).ExtractAll` (`internal/markdown/markdown.go:356`); triggers — `CreateMemo` (`server/router/api/v1/memo_service.go:108`) and `UpdateMemo` when the update mask includes `content` (`server/router/api/v1/memo_service.go:447`), plus the unused bulk backfill `memopayload.Runner.RunOnce` (`server/runner/memopayload/runner.go:52`); extracted properties — deduplicated `#tags`, and the `Property` fields `has_link`, `has_code`, `has_task_list`, `has_incomplete_tasks`, and `title` (first H1 heading).**

The writer is small and is the only place these fields are assigned:

```74:88:server/runner/memopayload/runner.go
func RebuildMemoPayload(_ context.Context, memo *store.Memo, markdownService markdown.Service) error {
	if memo.Payload == nil {
		memo.Payload = &storepb.MemoPayload{}
	}

	// Use goldmark service to extract all metadata in a single pass (more efficient)
	data, err := markdownService.ExtractAll([]byte(memo.Content))
	if err != nil {
		return errors.Wrap(err, "failed to extract markdown metadata")
	}

	memo.Payload.Tags = data.Tags
	memo.Payload.Property = data.Property
	return nil
}
```

A grep for assignments to `Payload.Tags` or `Payload.Property` across `server/`, `store/`, and `internal/` returns only lines 85 and 86 above, confirming there's no second computation path.

What `ExtractAll` derives during its single `gast.Walk` (`internal/markdown/markdown.go:356-421`):

| Output | Rule |
|---|---|
| `Tags` | every `#tag` node, deduplicated preserving original case |
| `Property.HasLink` | any `gast.KindLink` node |
| `Property.HasCode` | any code block, fenced code block, or inline code span |
| `Property.HasTaskList` | any task checkbox |
| `Property.HasIncompleteTasks` | any task checkbox with `IsChecked == false` |
| `Property.Title` | text of the first block-level child of the document, only if it is a level-1 heading |

It also collects `Mentions` in the same pass, but `RebuildMemoPayload` discards that field — mentions are consumed separately for notifications via `server/router/api/v1/memo_mention_helpers.go:32`.

On triggers, two details matter. Creation runs the rebuild before the insert, after the content-length check, and location is layered onto the payload afterward (`server/router/api/v1/memo_service.go:101-113`). Update only recomputes inside the `path == "content"` branch of the update-mask loop, and the refreshed payload is attached to the store update alongside the new content (`server/router/api/v1/memo_service.go:439-453`); changing visibility, pinned state, or location therefore leaves the derived metadata untouched, which is correct since none of them affect content-derived values. The third trigger, `Runner.RunOnce`, would rebuild every memo in batches of 100, but its constructor `memopayload.NewRunner` has no call sites, so it never executes in a running server.

On the consumption side, the stored values are surfaced to clients by `convertMemoPropertyFromStore` (`server/router/api/v1/memo_service_converter.go:315-326`), wired in at `server/router/api/v1/memo_service_converter.go:49`. Note that the list/preview `snippet` field is a separate, non-persisted value computed per response from `memo.Content` via `getMemoContentSnippet` (`server/router/api/v1/memo_service_converter.go:76-80`), not part of this stored payload.
