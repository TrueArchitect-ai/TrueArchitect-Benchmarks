**Actual mechanism: webhook delivery uses an in-process buffered Go channel with a fixed pool of four worker goroutines, both declared in `internal/webhook/webhook.go` — the channel at `internal/webhook/webhook.go:39` and the workers in that file's `init` function at `internal/webhook/webhook.go:42-55`.**

The "queue" is a 128-slot channel of payload pointers:

```39:55:internal/webhook/webhook.go
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
)

func init() {
	for range 4 {
		go func() {
			for payload := range asyncPostQueue {
				if err := Post(payload); err != nil {
					slog.Warn("Failed to dispatch webhook asynchronously",
						slog.String("url", payload.URL),
						slog.String("activityType", payload.ActivityType),
						slog.Any("err", err))
				}
			}
		}()
	}
}
```

Producers enqueue with a non-blocking send, so the behavior under load is to **drop** rather than to buffer durably or apply backpressure:

```189:195:internal/webhook/webhook.go
	select {
	case asyncPostQueue <- requestPayload:
	default:
		slog.Warn("Dropped webhook dispatch because the async queue is full",
			slog.String("url", requestPayload.URL),
			slog.String("activityType", requestPayload.ActivityType))
	}
```

Consequences worth noting, since they differ from what a broker would give you:

- The queue lives in the server process's memory, so anything still queued is lost on restart, and it is not shared across replicas.
- There are no retries. A worker logs the failure from `webhook.Post` (`internal/webhook/webhook.go:120`) at warn level and moves on; there is no dead-letter path or redelivery.
- Workers and buffer size are compile-time constants (4 and 128) with no configuration knob.
- Because `init` starts the goroutines at package load, the workers exist as soon as anything imports `internal/webhook`; there's no explicit start/stop wiring in `server/server.go`.

Producers are the memo-related dispatch helpers, which call `webhook.PostAsync` at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.
