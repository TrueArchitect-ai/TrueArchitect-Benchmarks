**Computation site: `memopayload.RebuildMemoPayload` — `server/runner/memopayload/runner.go:74`, delegating the parse to `(*markdown.service).ExtractAll` — `internal/markdown/markdown.go:356`. Triggers: memo creation, and memo update only when `content` is in the update mask. Extracted: `tags` plus five `Property` fields (`title`, `has_link`, `has_code`, `has_task_list`, `has_incomplete_tasks`).**

The computation:

`RebuildMemoPayload` initializes `memo.Payload` if nil, calls `markdownService.ExtractAll([]byte(memo.Content))`, and assigns `memo.Payload.Tags` and `memo.Payload.Property` (`server/runner/memopayload/runner.go:74-88`). Everything is derived in a single goldmark AST walk in `ExtractAll`:

- `Tags` — every `#tag` node, deduplicated with original case preserved (`internal/markdown/markdown.go:376-378`, `:418`)
- `Property.Title` — the text of the first block-level child of the document only if it is an H1 heading (`internal/markdown/markdown.go:383-389`)
- `Property.HasLink` — any link node (line 394)
- `Property.HasCode` — any code block, fenced code block, or inline code span (lines 396-397)
- `Property.HasTaskList` — any task checkbox; and `Property.HasIncompleteTasks` when at least one checkbox is unchecked (lines 399-405)

The field set is defined in `proto/store/memo.proto:15-22` under the comment "The calculated properties from the memo content." Note that `ExtractAll` also returns `Mentions`, but `RebuildMemoPayload` does not persist them — mentions are used separately for notifications (`server/router/api/v1/memo_mention_helpers.go:32`). Likewise `Payload.Location` is user-set, not derived, and is assigned around the rebuild (`server/router/api/v1/memo_service.go:111-113`, `:481-484`).

The two triggers:

- `CreateMemo` — `server/router/api/v1/memo_service.go:108`, before the row is inserted.
- `UpdateMemo` — `server/router/api/v1/memo_service.go:447`, inside the `path == "content"` branch, with the result written through `update.Payload = memo.Payload` at line 451. Other update-mask paths (`visibility`, `pinned`, `state`, `location`, `attachments`, `relations`) do not recompute it, so the derived metadata only changes when content changes.

Because `CreateMemoComment` creates its comment through `s.CreateMemo` (`server/router/api/v1/memo_service_comments.go:56`), comments get the same treatment via the create path.

Consumption confirms the "lists/previews" purpose: `convertMemoFromStoreWithCreators` copies `Payload.Tags` and `Payload.Property` onto the API response (`server/router/api/v1/memo_service_converter.go:47-50`), and user tag statistics aggregate `memo.Payload.Tags` at `server/router/api/v1/user_service_stats.go:138` and `:254`.

One gap worth flagging: `memopayload.Runner.RunOnce` (`server/runner/memopayload/runner.go:27`) exists to backfill payloads across all memos, but as established earlier it has no caller, so there is no bulk recomputation path in a running server — a memo written before a property was added keeps its stale payload until its content is edited.
