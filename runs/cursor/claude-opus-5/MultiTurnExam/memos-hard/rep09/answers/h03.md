**`internal/idp` (`internal/idp/idp.go`); `internal/idp/oauth2` (`internal/idp/oauth2/oauth2.go`)**

Details:

- The abstraction package is deliberately thin: `internal/idp/idp.go` defines only the shared `IdentityProviderUserInfo` struct (`Identifier`, `DisplayName`, `Email`, `AvatarURL`) that every provider normalizes its claims into. There is no Go interface type — the "abstraction" is this common result shape plus the provider-type discriminator in the schema.
- The one concrete protocol implementation is OAuth 2.0 in `internal/idp/oauth2/oauth2.go`. Its `IdentityProvider` wraps a `storepb.OAuth2Config` and exposes `ExchangeToken` (authorization-code exchange via `golang.org/x/oauth2`, with optional PKCE `code_verifier`) and `UserInfo` (bearer-token GET against the configured userinfo endpoint, then claim extraction driven by the configurable `FieldMapping`).
- Dispatch between provider types happens in `resolveSSOIdentity` at `server/router/api/v1/auth_service_sso.go:120-134`, which branches on `identityProvider.Type == storepb.IdentityProvider_OAUTH2` and is the only importer of both packages.
- OAuth2 really is the only shipped option, not just the only one wired up: the stored enum in `proto/store/idp.proto:11-13` has exactly `TYPE_UNSPECIFIED = 0` and `OAUTH2 = 1` (generated as `IdentityProvider_Type` in `proto/gen/store/idp.pb.go`). Note that because the branch is a plain `if`, a provider row with an unspecified type would leave `userInfo` nil and then be dereferenced by the identifier-filter check at line 142.
