**Premise correction: there is no Redis anywhere in this project — the cache layer is a process-local in-memory cache, so there is no connection to configure. User entries live for 10 minutes.**

Evidence that Redis isn't involved: searching the Go sources, `go.mod`, `go.sum`, and all YAML/JSON/Markdown files for "redis" (case-insensitive) returns zero matches, and there's no memcached client either. No external cache dependency exists.

The actual mechanism:

- The cache is `store/cache/cache.go` — a `Cache` struct built on a `sync.Map` with per-item expiration timestamps, described in its own comment as "a thread-safe in-memory cache with TTL and memory management" (`store/cache/cache.go:66-73`). Each instance starts one background `cleanupLoop` goroutine (line 83) and is torn down via `Close` (line 187).
- Configuration is code-level, not connection-level: `store.New` builds a single `cache.Config` and hands it to three separate caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:40-53`). The values are `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil` (`store/store.go:40-45`). The same defaults are duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), though the store doesn't call it.
- **User entry TTL: 10 minutes.** Every user write goes through `s.userCache.Set(...)` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` forwards to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`), stamping `expiration: time.Now().Add(ttl)` (line 112). Nothing calls `SetWithTTL` directly for users, so there is no per-user override.

Two practical consequences worth noting: entries can also be dropped before the TTL expires, because exceeding `MaxItems: 1000` triggers `cleanupOldest()` (`store/cache/cache.go:117-119`); and the user cache is read only on ID-keyed lookups — `Store.GetUser` consults it solely when `find.ID != nil` (`store/user.go:149-156`), so lookups by username or email always hit the database. Deletion invalidates explicitly at `store/user_delete.go:40`. Since the cache is per-process, a multi-instance deployment would not share it.
