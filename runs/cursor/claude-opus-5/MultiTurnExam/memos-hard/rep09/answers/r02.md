**Premise correction: there is no per-user API rate-limiting middleware in this codebase, so there is no registration site and no request limits to report.**

What I checked:

- Searching all Go sources for `ratelimit`, `rate_limit`, "rate limit", `throttl`, `Limiter`, and `golang.org/x/time/rate` (case-insensitive) yields exactly one hit, and it's an aspirational comment in documentation, not code: "Rate limit email sending to prevent abuse" at `internal/email/doc.go:86`. `go.mod` declares no rate-limiting or token-bucket dependency.
- The Echo middleware stack has only two entries, neither rate-related: `middleware.Recover()` and `newCORSMiddleware(profile)` at `server/server.go:51-52`.
- The Connect interceptor chain is likewise limited to metadata, logging, recovery, and auth — `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor` (`server/router/api/v1/connect_interceptors.go:25`, `:103`, `:170`, `:213`), wired at `server/router/api/v1/v1.go:133-138`. The gRPC-Gateway path gets only the auth middleware (`server/router/api/v1/v1.go:69-98`).

What does exist, and may be what the question is reaching for, are per-resource guards rather than per-user request quotas:

- Request body size cap of 256 MiB (`maxAPIRequestBytes` at `server/router/api/v1/v1.go:20`), applied via `http.MaxBytesHandler` to both the gateway and Connect mux and via `connect.WithReadMaxBytes` (`server/router/api/v1/v1.go:126`, `:141`, `:144`).
- Global concurrency semaphores, not per-user: 3 concurrent thumbnail generations and 2 concurrent image processing operations (`server/router/api/v1/v1.go:59-60`), plus an independent `maxConcurrentThumbnails` semaphore in the file server (`server/router/fileserver/fileserver.go:116`, acquired at `:448`).
- A per-memo content length limit enforced from instance settings (`getContentLengthLimit`, used at `server/router/api/v1/memo_service.go:101-107`).

These bound resource usage per request or per process; none of them counts requests per user over time, and none would stop a client from issuing unlimited API calls.
