**Premise correction: there is no Redis anywhere in this repository — no Redis client, no connection configuration, no dependency. Searching the entire Go source, `go.mod`, and `go.sum` for "redis" returns zero matches. The cache layer is a purely in-process, in-memory implementation.**

The actual mechanism:

- The cache is a hand-rolled `Cache` type in `store/cache/cache.go:66`, backed by a `sync.Map` plus an atomic item counter, with a background `cleanupLoop` goroutine started in `New` (`store/cache/cache.go:76`). It satisfies the local `cache.Interface` (`store/cache/cache.go:11`) — that interface is the only abstraction point, and there is no alternative backend implementing it.
- `Store` holds three separate instances as concrete `*cache.Cache` fields — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27`–`29`) — all constructed in `store.New` from one shared `cache.Config` (`store/store.go:40`–`53`).
- **TTL for user entries: 10 minutes.** `store.New` sets `DefaultTTL: 10 * time.Minute` (`store/store.go:41`), and every user write goes through `userCache.Set`, which forwards to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:94`). No call site ever passes a custom TTL for users — `store/user.go:98`, `:122`, `:132`, `:143`, and `:167` all use plain `Set`. The same 10-minute default is also duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57`), though `store.New` builds its config literal rather than calling that helper.
- Supporting settings from the same config: expired entries are swept every 5 minutes (`CleanupInterval`), capacity is capped at 1000 items, and no eviction callback is registered. Because the cache lives in process memory, it is not shared across replicas and is discarded on restart; `Store.Close` stops the cleanup goroutines (`store/store.go:74`–`76`).
- Cache reads are narrower than writes: `Store.GetUser` only consults `userCache` when the lookup is by ID (`store/user.go:150`), so the avatar path that looks users up by username bypasses the cache entirely. Deletion explicitly invalidates the entry at `store/user_delete.go:40`.
