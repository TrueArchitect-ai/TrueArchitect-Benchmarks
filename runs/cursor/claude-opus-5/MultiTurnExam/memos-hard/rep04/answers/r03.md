**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never used at runtime. The `internal/scheduler` package exists — it has cron-expression parsing, job registration, and middleware — but it is dead code: no non-test file anywhere in the repository imports it. Searching for `internal/scheduler` outside of tests returns zero hits, and the only references to `scheduler.New(...)` / `Register(...)` are in the package's own doc comments (`internal/scheduler/doc.go:12`–`28`), its `Register` definition (`internal/scheduler/scheduler.go:70`), and its `*_test.go` files. So no cron schedule of any kind — nightly or otherwise — is registered, and there is no cleanup job to schedule.**

What the server actually runs in the background:

- Exactly one background runner is started, in `Server.startBackgroundRunners` (`server/server.go:153`–`174`): the S3 presign refresher, which runs once at startup and then every 12 hours on a plain `time.Ticker` (`server/runner/s3presign/runner.go:27`–`41`). It refreshes presigned URLs; it deletes nothing.
- The only periodic *cleanup* in the codebase is in-memory, not database: each `cache.Cache` runs a `cleanupLoop` goroutine that evicts expired entries every 5 minutes (`store/cache/cache.go:200`, interval from `CleanupInterval` at `store/store.go:42`). It also sheds the oldest entries when the 1000-item cap is exceeded (`store/cache/cache.go:117`–`118`).
- Database row removal is entirely request-driven rather than scheduled — for example the transactional cascade in `DeleteUser` (`store/db/sqlite/user_delete.go:92`) and attachment/relation cleanup during memo deletion (`server/router/api/v1/memo_service.go:579`, `server/router/api/v1/user_service.go:421`–`450`).
- Also worth noting: `server/runner/memopayload` contains a batch `RunOnce` that would rewrite every memo's payload, but nothing constructs that runner either (`server/runner/memopayload/runner.go:27`), so it never executes.
