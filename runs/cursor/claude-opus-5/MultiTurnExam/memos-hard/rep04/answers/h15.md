Two patterns are worth calling out. Most API-level checks share the same three-step shape — allow if `PUBLIC`, else require an authenticated user, else deny if `PRIVATE` and the viewer is neither creator nor superuser — but they're duplicated per service rather than centralized, so `checkMemoReadAccess`, the reaction gate, the memo-attachment gate, and the attachment gate are genuinely distinct sites with slightly different details (notably `checkMemoReadAccess` also hides archived memos from non-creators and does *not* grant admins access to private memos, while the others do via `isSuperUser`).

The two attachment surfaces differ meaningfully: the HTTP file server additionally requires `Profile.AllowAnonymous()` before serving public-memo attachments to anonymous visitors, and it honors a `share_token` query parameter that grants access to private/protected memos when the token is unexpired and issued for that memo (`server/router/fileserver/fileserver.go:677`–`689`). The gRPC path has no share-token branch.

The MCP router (`server/router/mcp/`) contains no visibility logic of its own; it routes through the API v1 services, inheriting their checks.
