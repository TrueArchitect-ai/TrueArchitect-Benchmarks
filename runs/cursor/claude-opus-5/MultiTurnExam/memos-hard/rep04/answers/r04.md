**Premise correction: neither. There is no message broker in this repository at all — no NATS, no RabbitMQ, and no AMQP/Kafka/SQS client. Searching every Go file plus `go.mod` and `go.sum` for those terms returns zero matches, so there is no external queue and nothing is "declared" in a broker sense.**

The actual mechanism is an in-process buffered Go channel:

- The "queue" is a package-level variable: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` at `internal/webhook/webhook.go:39`. That's the declaration site — a 128-slot buffered channel living in the server process's memory.
- The "workers" are four goroutines started in the package's `init()` (`internal/webhook/webhook.go:42`–`55`). Each ranges over `asyncPostQueue` and calls `Post` for every payload, logging a warning with the URL and activity type on failure rather than retrying.
- Producers call `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking `select` send. On a full queue it takes the `default` branch and **drops the webhook**, logging "Dropped webhook dispatch because the async queue is full" (`internal/webhook/webhook.go:191`–`195`). A nil payload is likewise dropped with a warning.
- Delivery itself happens in `Post` (`internal/webhook/webhook.go:120`): it marshals the payload, optionally attaches Standard Webhooks HMAC-SHA256 headers, and issues the request via the SSRF-guarded `safeClient` with a 30-second timeout.

Consequences of this design worth being aware of: there is no durability, no retry, and no cross-replica coordination. Payloads queued at shutdown are lost — `Server.Shutdown` (`server/server.go:134`) cancels background runners and closes the SSE hub but never drains `asyncPostQueue`, and the worker goroutines aren't tracked by `backgroundRunnerWG`. Producers are the memo webhook dispatchers at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.
