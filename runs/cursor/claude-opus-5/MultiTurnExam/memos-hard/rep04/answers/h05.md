What I checked:

- **The store entry point.** `Store.DeleteUser` (`store/user.go:171`) just delegates to `s.driver.DeleteUser` and then invalidates cache, so all the real work is per-driver.
- **The driver implementation.** Each driver's `DeleteUser` opens one transaction and calls `deleteUserTargetsTx`, which removes reactions in two separate passes (`store/db/sqlite/user_delete.go:92`–`127`):
  - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500, removing reactions *others* left on the deleted user's memos. The content IDs are built as `"memos/" + memo.UID` (`store/db/sqlite/user_delete.go:512`), and the memo set comes from a recursive CTE that also walks `COMMENT` relations (`store/db/sqlite/user_delete.go:133`).
  - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user left on *anyone's* content (`store/db/sqlite/user_delete.go:400`).
  
  Both run before `deleteMemosTx` and `deleteUserRowTx` in the same transaction, so ordering can't orphan rows.
- **All three drivers.** The same two calls appear at line 96 and 102 of `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`, so the behavior isn't SQLite-only.
- **The schema, to rule out a database-level rule.** The `reaction` table has no foreign key at all in any dialect — `creator_id` is a plain `INTEGER`/`INT NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. The only `ON DELETE CASCADE` in the latest schemas is on `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109` and the mysql/postgres equivalents at line 108), which does not cover reactions. So the explicit Go deletes are the sole mechanism.
