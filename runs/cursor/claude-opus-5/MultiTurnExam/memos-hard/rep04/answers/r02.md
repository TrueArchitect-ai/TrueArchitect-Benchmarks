**Premise correction: there is no per-user API rate-limiting middleware in this repository. No rate limiter is registered, and none exists to register — searching all Go source for `ratelimit`, `RateLimiter`, `throttle`, and `golang.org/x/time/rate` yields no implementation, and `go.mod` contains no rate-limiting dependency. The only match anywhere is an aspirational comment in `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"), which describes future work rather than existing code.**

What actually gets registered as middleware:

- On the Echo server, exactly two global middlewares: `middleware.Recover()` and the CORS middleware, both at `server/server.go:51`–`52` (the CORS config itself is `server/cors.go:14`).
- The frontend router adds a static-file handler and an SPA fallback (`server/router/frontend/frontend.go:54` and `:59`).
- The API v1 layer installs authentication/authorization — not rate limiting — via gRPC-Gateway middleware and Connect interceptors (`server/router/api/v1/v1.go:95`, with the shared authorizer set up in `RegisterGateway` at `server/router/api/v1/v1.go:65`).

The closest things to request limiting are concurrency caps on expensive work, which are per-process semaphores rather than per-user quotas and reject nothing — callers simply wait:

- `thumbnailSemaphore`, weight 3, in the file server (`server/router/fileserver/fileserver.go:46` and `:116`).
- `thumbnailSemaphore` weight 3 and `imageProcessingSemaphore` weight 2 in `APIV1Service` (`server/router/api/v1/v1.go:59`–`60`).

There are also unrelated bounded resources that are sometimes mistaken for rate limits: the webhook dispatch queue holds 128 pending payloads with 4 worker goroutines and *drops* overflow (`internal/webhook/webhook.go:39`–`55`, `:189`–`195`), the user cache caps at 1000 items (`store/cache/cache.go:61`), and memo content length is capped per-instance via `getContentLengthLimit` (`server/router/api/v1/memo_service.go:101`). None of these are keyed by user or by request rate.
