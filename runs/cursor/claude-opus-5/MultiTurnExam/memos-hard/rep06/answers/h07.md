The important structural point: avatars are **not** files on disk or in S3. They are stored inline in the `user.avatar_url` column as a base64 data URI, so the "data layer" hop bottoms out in a `SELECT` against the `user` table, not in a blob store.

Hops, in order:

- `GET /file/users/:identifier/avatar` (route registration) — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (serving handler) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` — `store/user.go:148`
- `Store.ListUsers` — `store/user.go:136`
- `Driver.ListUsers` (interface dispatch) — `store/driver.go`
- `(*DB).ListUsers` (SQLite; parallel implementations in `postgres`/`mysql`) — `store/db/sqlite/user.go:88`, with the `SELECT ... avatar_url ... FROM user` at lines 151-165 and `QueryContext` at line 173
- `FileServerService.parseDataURI` (decodes the retrieved column into bytes) — `server/router/fileserver/fileserver.go:737`

A few details that matter for the trace:

The route and service are wired at startup in `server/server.go:81-82`, where `fileserver.NewFileServerService` is constructed and `RegisterRoutes` attaches the `/file` group.

`serveUserAvatar` gates access first: when the instance is private (`!s.Profile.AllowAnonymous()`), it requires a resolvable viewer via `getCurrentUser` → `authenticator.AuthenticateToUser` (lines 173-181, 708-712) and returns 401 otherwise. On a public instance, another user's avatar is served anonymously. Note that lookup is by **username only** — `getUserByUsername` builds `&store.FindUser{Username: &identifier}`, so the `:identifier` path segment is not treated as an ID.

`Store.GetUser` has a cache short-circuit, but it only applies when `find.ID != nil` (`store/user.go:149-156`). Since the avatar path searches by username, that branch is skipped and the request always proceeds to `ListUsers` → driver → SQL. `ListUsers` does populate `s.userCache` keyed by user ID on the way back (lines 142-145).

The final step is decoding rather than fetching: `parseDataURI` matches the column against `dataURIRegex` (`fileserver.go:98`) and base64-decodes the payload; the handler then validates the MIME type against `avatarAllowedTypes` (lines 75-83, checked at 201), sets `nosniff`/`DENY`/CSP security headers plus a one-hour `Cache-Control`, and writes the bytes with `c.Blob` at line 209.
