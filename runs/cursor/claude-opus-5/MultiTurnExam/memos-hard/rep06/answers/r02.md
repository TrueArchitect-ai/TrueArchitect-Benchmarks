**Premise correction: there is no per-user API rate-limiting middleware in this repository, so there is no registration site and no request limits to report.**

Evidence:

A case-insensitive search across all Go files for `ratelimit`, `rate_limit`, `rate limit`, `throttl`, `tollbooth`, and `golang.org/x/time/rate` produces exactly one hit, and it is an aspirational comment rather than an implementation — `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a note. `go.mod` declares no rate-limiting or token-bucket dependency.

The Echo middleware stack has only two entries, both registered in `NewServer`:

```50:53:/bench/repo/server/server.go
	echoServer := echo.New()
	echoServer.Use(middleware.Recover())
	echoServer.Use(newCORSMiddleware(profile))
	s.echoServer = echoServer
```

The Connect/gRPC side has four interceptors (`server/router/api/v1/v1.go:133-138`) — metadata, logging, recovery, and auth. None of them counts or throttles requests. There is no `server/middleware` directory; the only packages under `server/` are `auth`, `notification`, `runner`, and the `router/*` surfaces.

What does exist are related but categorically different protections, which are easy to mistake for rate limiting:

- **Concurrency caps**, not request-rate caps. Weighted semaphores bound simultaneous expensive work: `semaphore.NewWeighted(maxConcurrentThumbnails)` in the file server (`server/router/fileserver/fileserver.go:116`, with the constant set to 3 at line 46), plus `thumbnailSemaphore` of 3 and `imageProcessingSemaphore` of 2 in the API service (`server/router/api/v1/v1.go:59-60`). These make excess requests wait rather than rejecting them, and they are global rather than per-user.
- **Payload size limits.** `connect.WithReadMaxBytes(maxAPIRequestBytes)` at `server/router/api/v1/v1.go:141`, and a configurable memo content-length check in `CreateMemo`/`UpdateMemo` (`server/router/api/v1/memo_service.go:105` and `:443`).
- **A bounded webhook dispatch queue.** The 128-slot channel with 4 workers in `internal/webhook/webhook.go:39-55`, which drops overflow — that is outbound backpressure, not inbound throttling.

So authenticated API calls are limited only by per-user authorization checks, not by any request-per-interval budget. Anything resembling rate limiting in a deployment would have to come from a reverse proxy in front of the server.
