The two passes cover distinct sets, which matters for answering the question precisely:

- `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400`) runs `DELETE FROM reaction WHERE creator_id = ?` — these are the reactions *the deleted user made*, anywhere in the instance.
- `deleteReactionsByContentIDsTx` (line 380) runs `DELETE FROM reaction WHERE content_id IN (...)` in batches of 500 (`deleteUserBatchSize`, line 14) — these are *everyone else's* reactions on the deleted user's memos. The content IDs are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs` (line 512), matching the string `content_id` column, and the memo set comes from the recursive CTE at line 134 that walks the user's memos plus their comment descendants.

All three drivers do this identically: `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`.

**Why it cannot be a database-level rule.** The `reaction` table has no foreign key at all, in any dialect — `creator_id` is a bare `INTEGER NOT NULL` with no `REFERENCES user(id)` and no `ON DELETE` clause:

```92:99:/bench/repo/store/migration/sqlite/LATEST.sql
CREATE TABLE reaction (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_ts BIGINT NOT NULL DEFAULT (strftime('%s', 'now')),
  creator_id INTEGER NOT NULL,
  content_id TEXT NOT NULL,
  reaction_type TEXT NOT NULL,
  UNIQUE(creator_id, content_id, reaction_type)
);
```

The Postgres (`store/migration/postgres/LATEST.sql:91-98`) and MySQL (`store/migration/mysql/LATEST.sql:91-98`) definitions match. A grep for `ON DELETE` across all three `LATEST.sql` files returns exactly one hit per file, and it is `memo_share.memo_id → memo(id) ON DELETE CASCADE` (sqlite:109, postgres:108, mysql:108) — nothing touching `reaction` or `user`. Note also that `content_id` is a text value like `memos/<uid>` rather than a numeric memo FK, so a cascade from `memo` would not be expressible here anyway. Historically the schema moved away from FKs and triggers, per `store/migration/sqlite/0.7/00__remove_fk.sql` and `0.7/01__remove_triggers.sql`.

Because the reaction deletes share the transaction with the final `DELETE FROM user` (`deleteUserRowTx`, line 461) and the commit at line 51, the cleanup is atomic with the user removal — no orphaned reactions on partial failure.
