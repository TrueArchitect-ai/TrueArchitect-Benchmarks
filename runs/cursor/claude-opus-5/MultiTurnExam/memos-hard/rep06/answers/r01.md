**Premise correction: there is no Redis anywhere in this repository — no connection to configure.** Searching for `redis` (case-insensitive) across Go sources, `go.mod`, `go.sum`, and all YAML/JSON/Markdown/TypeScript files returns zero matches. There is no external cache server, no client library, and no configuration flag for one.

**Actual mechanism: a process-local in-memory cache.** The cache layer is `store/cache/cache.go`, a `Cache` struct built on `sync.Map` plus an atomic item counter (lines 66-73), with a background `cleanupLoop` goroutine started in `New` (line 83). It is purely in-process, so each server instance has its own copy and nothing is shared across replicas.

Configuration lives in the store constructor rather than in any config file or environment variable:

```40:45:/bench/repo/store/store.go
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}
```

That single hardcoded config is passed to all three caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`).

**TTL for user entries: 10 minutes.** Every write to the user cache goes through `Set`, never `SetWithTTL` — see `store/user.go:98`, `:122`, `:132`, `:143`, and `:167`. `Cache.Set` forwards to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:93-95`), so entries expire 10 minutes after being written. Note this is a fixed expiry from write time, not a sliding window: `Get` does not refresh the deadline, though a cache hit is only returned while unexpired.

Two additional eviction paths worth knowing: entries can be dropped early when the cache exceeds `MaxItems` of 1000, which triggers `cleanupOldest` (`store/cache/cache.go:117-119`), and user deletion explicitly invalidates the entry via `s.userCache.Delete` (`store/user_delete.go:40`). Also relevant to reasoning about staleness — the user cache is only consulted when looking up by ID (`store/user.go:149-156`), so username-based lookups always hit the database.

The identical `DefaultConfig()` values appear at `store/cache/cache.go:57-64`, but the store builds its config inline rather than calling that helper.
