A few observations that matter for reasoning about this:

The two API paths use different mechanisms. Single reads apply an imperative check after fetching (`checkMemoReadAccess` returns `NotFound` for archived-not-yours, `Unauthenticated` when no user, `PermissionDenied` for someone else's private memo), while list paths push the constraint down into the query via `FindMemo.VisibilityList` or a CEL filter string, so enforcement happens in SQL rather than in Go.

Share tokens are a deliberate bypass rather than an enforcement site: `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:152`) resolves a token and returns the memo *without* calling `checkMemoReadAccess` — the token itself is the authorization. The file server mirrors this at `fileserver.go:684-689`, accepting a valid non-expired token scoped to that specific memo. Note that `getActiveMemoShare` returns `NotFound` for invalid or expired tokens to avoid leaking existence.

MCP is not a separate enforcement site: `server/router/mcp/catalog.go:12` whitelists `MemoService_ListMemos`, so it inherits the API layer's list filtering rather than implementing its own.

The last three bullets (mention, in-app, and email notifications) enforce visibility on *content delivery* rather than direct viewing — for example `notification/email.go:313-316` suppresses or redacts memo content for private and protected memos. I've included them because they gate who sees memo content, but they are a different category from the read-path checks above.
