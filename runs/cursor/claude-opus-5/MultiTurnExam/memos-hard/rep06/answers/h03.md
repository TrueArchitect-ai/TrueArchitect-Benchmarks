**`internal/idp` (`internal/idp/idp.go`); `internal/idp/oauth2` (`internal/idp/oauth2/oauth2.go`)**

The abstraction package is `internal/idp`, and it is deliberately minimal — the entire file defines just one shared type, `IdentityProviderUserInfo`, with the four normalized fields every provider must produce:

```3:8:/bench/repo/internal/idp/idp.go
type IdentityProviderUserInfo struct {
	Identifier  string
	DisplayName string
	Email       string
	AvatarURL   string
}
```

Note that there is no Go `interface` here; the abstraction is the common user-info struct that implementations return, not a polymorphic contract.

OAuth2 is the only concrete protocol implementation that ships. `internal/idp/oauth2/oauth2.go` defines an `IdentityProvider` wrapping a `storepb.OAuth2Config`, with `NewIdentityProvider` validating the required fields (client ID/secret, token URL, userinfo URL, identifier field mapping) at lines 27-43, `ExchangeToken` performing the authorization-code exchange with optional PKCE `code_verifier` support (lines 47-80), and `UserInfo` fetching the userinfo endpoint with a bearer token and projecting arbitrary JSON claims into `idp.IdentityProviderUserInfo` via the configured field mapping (lines 83-142).

Two things confirm OAuth2 is the sole implementation rather than one of several. `internal/idp` contains only `idp.go` and the single `oauth2/` subdirectory, and the SSO login path constructs providers exactly one way:

```121:121:/bench/repo/server/router/api/v1/auth_service_sso.go
		oauth2IdentityProvider, err := oauth2.NewIdentityProvider(identityProvider.Config.GetOauth2Config())
```

The protobuf config mirrors this: `IdentityProviderConfig` is used only through its `Oauth2Config` variant in `server/router/api/v1/idp_service.go` (lines 194 and 229), so there is no SAML, LDAP, or bespoke OIDC provider in the tree. Since generic OIDC providers expose OAuth2 token and userinfo endpoints, they are configured through this same OAuth2 implementation rather than a dedicated one.
