Actual mechanism: an in-process buffered Go channel with a fixed pool of goroutines, all inside `internal/webhook/webhook.go`.

The "queue" is a package-level channel holding at most 128 pending payloads:

```39:39:internal/webhook/webhook.go
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

The "workers" are four goroutines started in the package's `init()`, each looping over that channel and calling `Post` for every payload it receives:

```42:55:internal/webhook/webhook.go
func init() {
	for range 4 {
		go func() {
			for payload := range asyncPostQueue {
				if err := Post(payload); err != nil {
					slog.Warn("Failed to dispatch webhook asynchronously",
						slog.String("url", payload.URL),
						slog.String("activityType", payload.ActivityType),
						slog.Any("err", err))
				}
			}
		}()
	}
}
```

Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which uses a non-blocking `select` with a `default` branch: when the buffer is full it logs a warning and **drops** the event rather than blocking the caller (lines 189-195). The API handlers that trigger deliveries call it from `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

Several properties follow from this design being in-process rather than broker-backed, and they're the practical reason the distinction matters: the queue lives in the server's memory, so anything pending is lost on restart; there is no persistence, no acknowledgement, and no redelivery — a failed `Post` is logged at warn level and discarded with no retry; concurrency is capped at exactly four in-flight deliveries per process; and because `init()` starts the workers, they exist for the lifetime of the process and are not tied to `Server.Start`/`Shutdown` or any of the tracked background runners in `server/server.go`.
