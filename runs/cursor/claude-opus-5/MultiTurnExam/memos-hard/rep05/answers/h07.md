The browser hits `GET /file/users/{username}/avatar` — a plain HTTP route on the Echo server, not the gRPC-Gateway API. That URL is what the API hands out: `convertUserFromStore` rewrites a base64 avatar into `/file/{user.Name}/avatar` (`server/router/api/v1/user_service_converters.go:36`) so the image bytes don't bloat every user payload.

Hops from request to stored data:

`RegisterRoutes` (route `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:124`
`FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go:168`
`FileServerService.getCurrentUser` → `auth.Authenticator.AuthenticateToUser` (only when `Profile.AllowAnonymous()` is false) — `server/router/fileserver/fileserver.go:708`
`FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
`Store.GetUser` (user cache checked only for lookups by ID, so a username lookup always falls through) — `store/user.go:148`
`Store.ListUsers` — `store/user.go:136`
`store.Driver.ListUsers` (interface) — `store/driver.go:47`
`DB.ListUsers` (`SELECT ... avatar_url ... FROM user WHERE username = ?`) — `store/db/sqlite/user.go:88` (SQL at line 150-165, execution at line 173; parallel implementations in `store/db/mysql/user.go` and `store/db/postgres/user.go`)

Back in the handler, the stored value is not a file path or blob reference — `user.AvatarURL` holds a data URI, which `parseDataURI` (`server/router/fileserver/fileserver.go:737`) splits into MIME type and decoded bytes with a regex. The type is checked against `avatarAllowedTypes` (`fileserver.go:75`), then security headers and `Cache-Control` are set and the bytes go out via `c.Blob` (line 209).

Two access-control details worth noting: the `identifier` path segment is matched against `username` only, and anonymous requests are rejected with 401 when the instance has no `InstanceURL` configured (lines 173-181), so on a private instance another user's avatar requires a valid session, access token, or PAT.
