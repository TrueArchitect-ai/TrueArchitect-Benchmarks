**Explicit Go code (no database-level cascade); evidence: `store/db/sqlite/user_delete.go:96,102` with the two `DELETE FROM reaction` statements at lines 380-403, mirrored in `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go`, and confirmed by the absence of any foreign key on the `reaction` table in all three `store/migration/*/LATEST.sql` schemas**

What I checked, and what it showed:

**1. The deletion path.** `Store.DeleteUser` (`store/user.go:171`) just delegates to the driver and then invalidates cache, so the real work is per-driver. Each driver's `DeleteUser` opens one transaction and calls `deleteUserTargetsTx`, which removes reactions in two separate passes before anything else:

```96:104:store/db/sqlite/user_delete.go
	if err := deleteReactionsByContentIDsTx(ctx, tx, contentIDs); err != nil {
		return err
	}
	if err := deleteAttachmentsByIDsTx(ctx, tx, targets.attachmentIDs); err != nil {
		return err
	}
	if err := deleteReactionsByCreatorTx(ctx, tx, userID); err != nil {
		return err

```

The two passes cover different things. `deleteReactionsByCreatorTx` (line 400) issues `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user *made* on anyone's content. `deleteReactionsByContentIDsTx` (line 380) removes reactions *other people made on the deleted user's memos*, batched 500 at a time; the `content_id` values come from `memoContentIDsFromRefs` (line 512), which builds `"memos/" + memo.UID` strings, and the memo set is a recursive CTE (line 134) that walks comment descendants as well as the user's own memos.

**2. That it's uniform across drivers.** The same two functions exist and are called at the same points in `store/db/mysql/user_delete.go` (lines 96, 102, 417, 437) and `store/db/postgres/user_delete.go` (lines 96, 102, 380, 400).

**3. Whether the database could be doing it instead.** It can't. The `reaction` DDL in `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, and `store/migration/postgres/LATEST.sql:91-98` declares only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type`, and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — `creator_id` is a bare `INTEGER NOT NULL` with no `REFERENCES user(id)`. Grepping `FOREIGN KEY` across all three `LATEST.sql` files returns exactly one hit per file, and it's `memo_share.memo_id → memo(id) ON DELETE CASCADE`, not anything on `reaction`.

This design is also why reactions are keyed by the string `content_id` rather than a memo foreign key: a cascade wouldn't be expressible even if `creator_id` had one, so the cleanup has to be explicit in Go.
