**Premise correction: there is no Redis anywhere in this repository — no Redis client dependency, no connection configuration, no Redis references in Go code, `go.mod`, `go.sum`, or any config file. A case-insensitive search for "redis" across all Go, module, YAML, and JSON files returns zero results. The cache layer is a hand-rolled, in-process, in-memory cache with no external service.**

The actual mechanism: `store/cache/cache.go` defines a `Cache` type described as "a thread-safe in-memory cache with TTL and memory management" (line 66), backed by a `sync.Map` plus an atomic item counter. `cache.New` (line 76) starts a background `cleanupLoop` goroutine; there is no dialing, no address, and no serialization, since values are stored as `any` and retrieved with type assertions.

Three separate cache instances are created in `store.New`, all sharing one config literal:

```39:53:store/store.go
	// Default cache settings
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
```

**TTL for user entries: 10 minutes.** Every user write goes through `Cache.Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` forwards to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:93-95`), so users inherit the 10-minute default. Nothing in the codebase calls `SetWithTTL` with a custom duration for users — the only non-interface call sites of `SetWithTTL` are the two inside `cache.go` itself. Note the same 10-minute default is duplicated in `cache.DefaultConfig()` at `store/cache/cache.go:57-64`, but `store.New` builds its own literal rather than calling it.

Two caveats about the TTL that matter in practice. Entries can be dropped before 10 minutes elapse: `MaxItems: 1000` triggers `cleanupOldest()` on insert whenever the count exceeds the cap (`cache.go:117-119`), and the cleanup goroutine sweeps expired entries every 5 minutes, so a logically expired entry may linger until the next sweep unless read. Also, the user cache is only consulted on lookups by ID — `Store.GetUser` checks it only when `find.ID != nil` (`store/user.go:149-156`) — so lookups by username always hit the database.

Because the cache is per-process, a multi-replica deployment gets independent caches with no shared invalidation, which is the practical difference from the Redis setup the question assumed.
