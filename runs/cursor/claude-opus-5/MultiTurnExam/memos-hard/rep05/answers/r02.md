**Premise correction: there is no per-user API rate-limiting middleware in this repository. No rate limiter is registered anywhere, and none exists to configure — so there are no request limits to report.**

Evidence for the absence:

A case-insensitive search across all Go files and `go.mod` for `ratelimit`, `rate_limit`, `rate limit`, `throttl`, `golang.org/x/time/rate`, and Echo's `middleware.RateLimiter` returns exactly one hit, and it is an aspirational comment in package documentation rather than code: `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a suggestion. `golang.org/x/time/rate` is not a dependency.

The full set of middleware registered on the Echo server is four entries: `middleware.Recover()` and `newCORSMiddleware(profile)` at `server/server.go:51-52`, plus static-file serving and an SPA fallback in the frontend router at `server/router/frontend/frontend.go:54` and `:59`. The Connect/gRPC stack has four interceptors — metadata, logging, recovery, and auth (`server/router/api/v1/v1.go:133-137`) — none of which counts or limits requests.

What does exist, and is easy to mistake for rate limiting:

Request **size** caps rather than request **rate** caps: `maxAPIRequestBytes = 256 << 20` (256 MiB) is applied via `http.MaxBytesHandler` on the gateway and Connect handlers and as `connect.WithReadMaxBytes` (`server/router/api/v1/v1.go:20`, `:126`, `:141`, `:144`).

Concurrency semaphores, which bound simultaneous work process-wide rather than per user: three concurrent thumbnail generations and two concurrent image-processing operations in the API service (`server/router/api/v1/v1.go:59-60`), and `maxConcurrentThumbnails = 3` in the file server (`server/router/fileserver/fileserver.go:46`, acquired at line 448). These make callers wait rather than rejecting them, and they are shared across all users.

A bounded webhook dispatch queue of 128 that drops events when full (`internal/webhook/webhook.go:39`) — backpressure on outbound deliveries, not inbound requests.

A per-memo content length limit enforced in `CreateMemo` and `UpdateMemo` via `getContentLengthLimit` (`server/router/api/v1/memo_service.go:101-107` and `:439-445`).

So the server has size and concurrency protections but no notion of requests-per-interval, and no per-user accounting to attach such limits to.
