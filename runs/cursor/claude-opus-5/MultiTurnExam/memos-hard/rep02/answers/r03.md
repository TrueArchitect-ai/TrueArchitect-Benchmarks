There is no nightly database-cleanup job, and no cron schedule of any kind is registered — so there's no time to report. The premise is false on two counts.

**The cron scheduler is never used.** `internal/scheduler` is a fully built package (cron expression parser, job type, middleware for recovery/logging/timeout, plus a README and package docs), but the only files that import `github.com/usememos/memos/internal/scheduler` are its own tests: `internal/scheduler/example_test.go:10` and `internal/scheduler/integration_test.go:13`. There are no calls to `scheduler.New` outside test files and doc comments (`internal/scheduler/doc.go:12`, `:28` are illustrative examples), and no `Register` call anywhere registers a job. So the scheduler is dead code — nothing schedules anything through it at runtime.

**There is also no database-cleanup task to schedule.** Searching the server, store, and cmd trees for cleanup/vacuum/purge/prune work turns up only unrelated things: per-request cleanup of attachments during memo and user deletion (`server/router/api/v1/user_service.go:421-450`, `store/attachment.go:171`), a test teardown helper (`server/router/api/v1/test/test_helper.go:65`), and the in-memory cache's `CleanupInterval` of 5 minutes (`store/store.go:42`) — which is an expired-entry sweep inside `store/cache/cache.go`, not a database job.

**What actually runs on a schedule** is a single background runner, and it uses a plain `time.Ticker` rather than cron: the S3 presign runner in `server/runner/s3presign/runner.go`, with `const runnerInterval = time.Hour * 12` (`server/runner/s3presign/runner.go:27`). It's started at `server/server.go:161-171`, and because it fires on a fixed interval measured from process start, it has no wall-clock time of day — a restart shifts when it runs. It also isn't a cleanup task; it refreshes presigned URLs for S3-backed attachments. That runner is the only entry in `startBackgroundRunners`.
