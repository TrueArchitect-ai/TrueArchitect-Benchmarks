**h07.**

The browser hits a plain HTTP route (not gRPC), and the image bytes come out of the `user.avatar_url` column as a base64 data URI — there's no blob storage involved.

```
GET /file/users/{username}/avatar — server/router/fileserver/fileserver.go:124
FileServerService.serveUserAvatar — server/router/fileserver/fileserver.go:168
FileServerService.getUserByUsername — server/router/fileserver/fileserver.go:715

Store.ListUsers — store/user.go:136
Driver.ListUsers (e.g. sqlite) — store/db/sqlite/user.go:88
```

Notes on the hops:

- **Where the URL comes from.** The API doesn't hand the client raw base64. When converting a user to proto, if `AvatarURL` parses as an inline image it's replaced with a path: `userpb.AvatarUrl = fmt.Sprintf("/file/%s/avatar", userpb.Name)` (`server/router/api/v1/user_service_converters.go:36`). Since `Name` is `users/{username}`, the browser requests `/file/users/{username}/avatar`, matching the route registered at `fileserver.go:124`. The route group and service are wired into startup at `server/server.go:81-82`.

- **Access control before the lookup.** `serveUserAvatar` first checks `s.Profile.AllowAnonymous()`; on a private instance it requires a session/access token/PAT via `getCurrentUser` and returns 401 otherwise (`fileserver.go:173-181`). Note this is instance-level only — once you're authenticated (or the instance is public), *any* user's avatar is fetchable by username.

- **Store hop.** `getUserByUsername` is a one-line pass-through to `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`. Worth noting: `Store.GetUser`'s cache is keyed by user ID and is only consulted when `find.ID` is set, so this username-based lookup always falls through to `ListUsers` and hits the database, then populates the cache on the way back (`store/user.go:148-168`).

- **Driver hop.** `Store.ListUsers` delegates to `s.driver.ListUsers` (`store/user.go:137`), the interface satisfied by the per-backend implementations — `store/db/sqlite/user.go:88`, with MySQL and Postgres equivalents in `store/db/mysql/user.go` and `store/db/postgres/user.go`. The driver builds a `WHERE username = ?` clause and selects `avatar_url` among the columns.

- **Final decode and response.** Back in the handler, `parseDataURI` (`fileserver.go:737`) regex-matches the `data:<mime>;base64,...` form and decodes it; the MIME type must be in `avatarAllowedTypes` (`fileserver.go:75`) or the request is rejected with 400. Then security headers plus `Cache-Control` are set and the bytes go out via `c.Blob` (`fileserver.go:205-209`).
