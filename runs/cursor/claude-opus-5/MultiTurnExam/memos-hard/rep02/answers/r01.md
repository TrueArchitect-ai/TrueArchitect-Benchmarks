There is no Redis in this project — the premise doesn't hold. Searching the entire repository (all files, not just Go) for "redis" case-insensitively returns zero matches, and there is no Redis client in `go.mod`/`go.sum`. There's also no external cache of any kind, and no connection string, host, or port to configure.

**Actual mechanism:** the cache layer is a hand-rolled, in-process cache in `store/cache/cache.go` — `Cache` is a struct holding a `sync.Map` plus an atomic item counter (`store/cache/cache.go:66-73`), created by `cache.New(config)` (`store/cache/cache.go:76`). Because it's in-memory and per-process, it isn't shared across instances and is empty on every restart.

The store creates three separate instances of it, all sharing one config literal:

```39:53:store/store.go
	// Default cache settings
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
	}
```

**TTL for user entries: 10 minutes**, with expired entries swept by a background goroutine every 5 minutes and a 1000-item cap per cache. This comes from `DefaultTTL` above, since every user write goes through `Set` — `store/user.go:98`, `:122`, `:132`, `:143`, `:167` — and `Set` simply forwards the default:

```94:94:store/cache/cache.go
	c.SetWithTTL(ctx, key, value, c.config.DefaultTTL)
```

`SetWithTTL` exists (`store/cache/cache.go:98`) but no caller in production code passes a custom TTL, so users, instance settings, and user settings all inherit the same 10 minutes. Note the same values are independently duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), which the store does not actually call.

Two related details on user entries specifically: the cache is keyed by user ID via `userCacheKey` (`store/user.go:88`), so `Store.GetUser` only reads from it when the lookup is by ID and falls through to the database for username-based lookups (`store/user.go:149-156`); and deletion invalidates explicitly at `store/user_delete.go:40` rather than waiting for the TTL. All three caches are shut down in `Store.Close` (`store/store.go:74-76`) to stop their cleanup goroutines.
