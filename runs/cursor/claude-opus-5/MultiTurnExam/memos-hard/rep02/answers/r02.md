There is no per-user API rate-limiting middleware in this repository, so there's nothing registered and no request limits to report. The premise is false.

What I checked:

- Searching all Go files for `ratelimit`, `rate_limit`, `rate limit`, `throttle`, `RequestsPerMinute`, and the standard `golang.org/x/time/rate` limiter package returns no implementation hits. `go.mod` contains no rate-limiting or limiter dependency, and Echo's `middleware.RateLimiter` is never referenced.

- The complete set of registered middleware is small enough to enumerate. On the main Echo server there are exactly two:

```51:52:server/server.go
	echoServer.Use(middleware.Recover())
	echoServer.Use(newCORSMiddleware(profile))
```

The frontend router adds two more, both for static-asset serving: `middleware.StaticWithConfig` and `spaFallbackMiddleware` (`server/router/frontend/frontend.go:54`, `:59`). Beyond those, the API path applies an auth/authorization middleware and Connect interceptor from `RegisterGateway` (`server/router/api/v1/v1.go:65`), which does authentication and per-RPC access checks — not throttling.

- The only occurrences of the phrase anywhere in the repo are aspirational documentation, not code: `internal/email/README.md:286` ("### 5. Implement Rate Limiting", inside a suggested-improvements section with illustrative snippet) and `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"), listed as a future consideration.

The closest existing mechanisms are **concurrency** limits rather than **rate** limits, and they're global rather than per-user: weighted semaphores capping simultaneous thumbnail generation at 3 and image processing at 2 (`server/router/api/v1/v1.go:59-60`, `server/router/fileserver/fileserver.go:46` and `:116`). Also adjacent but not rate limiting: the webhook dispatch queue is bounded at 128 pending payloads with 4 workers and drops overflow (`internal/webhook/webhook.go:39-55`, `:189-195`).
