**h05.**

Reactions are deleted by explicit Go code inside the `DeleteUser` transaction — there is no database-level cascade for them, because the `reaction` table has no foreign keys at all.

**explicit Go code (two `DELETE FROM reaction` statements per driver, inside the delete-user transaction); evidence: `store/db/sqlite/user_delete.go:96,102,380-403`, `store/db/mysql/user_delete.go:96,102,417-440`, `store/db/postgres/user_delete.go:96,102,380-403`; schema has no FK on `reaction`: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`**

What I checked:

**1. The Go delete path.** `Store.DeleteUser` (`store/user.go:171`) delegates straight to the driver. Each driver's `deleteUserTargetsTx` removes reactions in two passes, both before the memos and user row are deleted:

```96:104:store/db/mysql/user_delete.go
	if err := deleteReactionsByContentIDsTx(ctx, tx, contentIDs); err != nil {
		return err
	}
	if err := deleteAttachmentsByIDsTx(ctx, tx, targets.attachmentIDs); err != nil {
		return err
	}
	if err := deleteReactionsByCreatorTx(ctx, tx, userID); err != nil {
		return err
	}
```

- `deleteReactionsByCreatorTx` (`store/db/mysql/user_delete.go:437`) runs `DELETE FROM reaction WHERE creator_id = ?` — the user's *own* reactions, wherever they were placed.
- `deleteReactionsByContentIDsTx` (`store/db/mysql/user_delete.go:417`) runs `DELETE FROM reaction WHERE content_id IN (...)` in batches of 500 — *other people's* reactions on the deleted user's memos. The content IDs are built as `"memos/" + memo.UID` (`store/db/mysql/user_delete.go:549-555`), and the memo set comes from an iterative walk that also picks up comment descendants via `memo_relation` (`store/db/mysql/user_delete.go:133-181`).

All three drivers implement this identically at the same line offsets, so behavior does not vary by backend. The whole thing is one transaction (`store/db/mysql/user_delete.go:30-53`).

**2. The schema.** The `reaction` table declares only a primary key and a uniqueness constraint:

```92:99:store/migration/sqlite/LATEST.sql
CREATE TABLE reaction (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  created_ts BIGINT NOT NULL DEFAULT (strftime('%s', 'now')),
  creator_id INTEGER NOT NULL,
  content_id TEXT NOT NULL,
  reaction_type TEXT NOT NULL,
  UNIQUE(creator_id, content_id, reaction_type)
);
```

`creator_id` is a plain `INTEGER NOT NULL` with no `REFERENCES user(id)`, and `content_id` is a string resource name rather than a FK. Grepping `FOREIGN KEY`/`REFERENCES` across the MySQL and Postgres `LATEST.sql` files turns up exactly one cascade in each — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`) — and nothing touching `reaction`. So a DB-level rule could not be doing this work. (SQLite also runs with `foreign_keys(0)` per its DSN in `store/db/sqlite/sqlite.go:53`.)
