**h03.**

SSO login is built around a small shared user-info type in `internal/idp`, with OAuth2 as the only concrete provider.

**`internal/idp` (`internal/idp/idp.go`); `internal/idp/oauth2` (`internal/idp/oauth2/oauth2.go`)**

Details:

- The abstraction is deliberately thin — `internal/idp` contains only the provider-neutral result type that every implementation must produce:

```3:8:internal/idp/idp.go
type IdentityProviderUserInfo struct {
	Identifier  string
	DisplayName string
	Email       string
	AvatarURL   string
}
```

There is no Go `interface` here; the contract is "return an `*idp.IdentityProviderUserInfo`." The type-level dispatch lives in the proto enum `IdentityProvider_Type`, which has exactly two values, `TYPE_UNSPECIFIED` and `OAUTH2` (`proto/gen/store/idp.pb.go:24-29`) — confirming OAuth2 is the only protocol that ships.

- `internal/idp/oauth2` provides `IdentityProvider` with the two operations used during login: `ExchangeToken` (`internal/idp/oauth2/oauth2.go:47`, supporting PKCE via `code_verifier`) and `UserInfo` (`internal/idp/oauth2/oauth2.go:83`), which fetches the userinfo endpoint with a 10s timeout and maps arbitrary claims into `idp.IdentityProviderUserInfo` using the configured `FieldMapping`. `NewIdentityProvider` requires `clientId`, `clientSecret`, `tokenUrl`, `userInfoUrl`, and `fieldMapping.identifier`.

- The one consumer is the SSO sign-in path, which branches on the provider type and constructs the OAuth2 implementation:

```120:121:server/router/api/v1/auth_service_sso.go
	if identityProvider.Type == storepb.IdentityProvider_OAUTH2 {
		oauth2IdentityProvider, err := oauth2.NewIdentityProvider(identityProvider.Config.GetOauth2Config())
```

The resulting user info then flows into `resolveSSOUser` (`server/router/api/v1/auth_service_sso.go:19`), which links the external identity to an existing user or provisions a new one subject to the registration gate. Similar OAuth2-only branches appear in `server/router/api/v1/idp_service.go:191,226` and `store/idp.go:223,235`.
