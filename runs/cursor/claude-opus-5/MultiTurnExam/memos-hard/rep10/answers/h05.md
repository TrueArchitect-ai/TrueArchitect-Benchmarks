**Explicit Go code — an in-transaction `DELETE FROM reaction` issued by each driver's `DeleteUser`, not a database cascade.**

What I checked, and what it showed:

**1. The delete path in Go.** `store.DeleteUser` (`store/user.go:171`) delegates to the driver. Each driver's `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which removes reactions in two separate passes before the user row is deleted (`store/db/sqlite/user_delete.go:92-127`):

```96:104:store/db/sqlite/user_delete.go
	if err := deleteReactionsByContentIDsTx(ctx, tx, contentIDs); err != nil {
		return err
	}
	if err := deleteAttachmentsByIDsTx(ctx, tx, targets.attachmentIDs); err != nil {
		return err
	}
	if err := deleteReactionsByCreatorTx(ctx, tx, userID); err != nil {
		return err
	}
```

The two passes cover different things. `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400`) runs `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user *made*. `deleteReactionsByContentIDsTx` (line 380) runs `DELETE FROM reaction WHERE content_id IN (...)` over `memos/<uid>` strings built from the user's memo tree (`memoContentIDsFromRefs`, line 512), removing reactions *other people* left on that user's memos.

**2. All three drivers do the same thing.** Identical helpers exist at `store/db/postgres/user_delete.go:380` and `:400`, and `store/db/mysql/user_delete.go:417` and `:437`, both invoked from the same place in their `deleteUserTargetsTx` (line 96 and 102 in each file).

**3. The schema has no cascade for this.** The `reaction` table in all three dialects declares `creator_id` as a plain `INTEGER`/`INT NOT NULL` with no foreign key at all — see `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, and `store/migration/postgres/LATEST.sql:91-98`. The only `ON DELETE CASCADE` in the entire schema is on `memo_share.memo_id` (`store/migration/sqlite/LATEST.sql:109` and the equivalents at line 108 in the MySQL and Postgres files). Note also that `content_id` is an opaque `memos/<uid>` string, so it could not be a foreign key even in principle.

**4. SQLite couldn't rely on a cascade anyway.** The connection is opened with foreign key enforcement explicitly turned off: `_pragma=foreign_keys(0)` in the DSN at `store/db/sqlite/sqlite.go:53`.

So reaction cleanup is entirely the application's responsibility here, and it is transactional — reactions, attachments, memo shares, inboxes, identities, settings, relations, memos, and finally the user row all commit or roll back together.
