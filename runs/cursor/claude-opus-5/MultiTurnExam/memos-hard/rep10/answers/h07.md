A few things worth noting along the way:

**How the browser learns the URL.** The API never sends raw avatar bytes in JSON. `convertUserToProto` checks whether `user.AvatarURL` is base64 image data and, if so, rewrites the field to the path `/file/{user}/avatar` to keep responses small (`server/router/api/v1/user_service_converters.go:31-38`). Only if the stored value is not a data URI does it pass through as an external URL.

**Access control.** Before any lookup, `serveUserAvatar` checks `s.Profile.AllowAnonymous()`; on a private instance it requires a valid session, access token, or PAT via `getCurrentUser`, returning 401 otherwise (`server/router/fileserver/fileserver.go:173-181`). There is no per-user restriction beyond that, so on a public instance any user's avatar is readable.

**Caching hop.** `Store.GetUser` consults `userCache` only when looking up by ID; this path passes `FindUser{Username: &identifier}`, so it always falls through to `ListUsers` and hits the database, then populates the cache keyed by the resulting user ID (`store/user.go:148-168`).

**Response safety.** After decoding, the handler rejects anything outside `avatarAllowedTypes` (PNG/JPEG/GIF/WebP, `server/router/fileserver/fileserver.go:75`), then sets security headers and `Cache-Control` before writing the blob (lines 201-209).

The service itself is constructed at `server/server.go:81` and registers its routes through `RegisterRoutes` (`server/router/fileserver/fileserver.go:121`).
