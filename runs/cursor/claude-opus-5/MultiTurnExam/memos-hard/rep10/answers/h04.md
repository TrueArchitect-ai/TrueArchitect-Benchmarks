**No — the MySQL driver is constructed only inside the factory.**

Evidence:

- `mysql.NewDB` is the sole constructor for the driver (`store/db/mysql/mysql.go:20`, returning a `store.Driver`), and it has exactly one call site in the entire repository: `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver`.

- A repo-wide search for the import path `github.com/usememos/memos/store/db/mysql` returns only two hits, both in the factory file: the import at `store/db/db.go:8` and the call at line 22. Since Go requires importing the package to reference it, no other file — production or test — can construct the driver directly, including via a struct literal like `&mysql.DB{}`.

- Every other consumer goes through the factory. `db.NewDBDriver` is called from `cmd/memos/main.go:57`, from the store test helpers at `store/test/store.go:28` and `:50`, and from `server/router/api/v1/test/memo_service_benchmark_test.go:70`. Even the MySQL-backed integration tests route through the same driver-selection switch rather than instantiating the MySQL driver themselves.

- Two other kinds of "mysql" references exist but are not the driver in question. `store/db/mysql/auth_config.go:7` and `store/db/mysql/mysql.go:7` import `github.com/go-sql-driver/mysql`, the low-level SQL protocol library used inside the driver package itself. `store/test/containers.go:16` and lines 101-105 use that same library plus the testcontainers MySQL module to spin up a MySQL container for tests; that code provisions a database server and hands back a DSN, it does not build the `store.Driver`.
