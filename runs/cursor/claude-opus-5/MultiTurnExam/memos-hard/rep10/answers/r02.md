**Premise correction: there is no rate-limiting middleware in this codebase — per-user or otherwise — so there is no registration site and no request limits to report.**

What I checked:

- A case-insensitive search across all Go sources for `ratelimit`, `rate_limit`, "rate limit", and `throttle` produces exactly one hit, and it's an aspirational comment rather than code: `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a future consideration.
- No rate-limiting dependency is present. There is no `golang.org/x/time/rate`, no `echo` rate-limiter usage, nothing in `go.mod`.
- The Echo middleware stack is only two entries deep, registered in `NewServer`: `middleware.Recover()` and the CORS middleware, at `server/server.go:51-52`. Nothing else is added via `Use` anywhere in the server. The other request-path interceptors are authentication-related — the gRPC-Gateway auth middleware and Connect interceptor wired in `RegisterGateway` (`server/router/api/v1/v1.go:65` onward) — and they authorize requests without counting them.

**What does exist, and is easy to mistake for rate limiting: concurrency caps, not request-rate caps.** These bound how many operations run *simultaneously* across the whole process; they don't limit how many requests a user may make per unit time, and they're not per-user.

- `thumbnailSemaphore` in the file server, sized by `maxConcurrentThumbnails` (`server/router/fileserver/fileserver.go:107` and `:116`), acquired before thumbnail generation at line 447.
- `thumbnailSemaphore` (weight 3) and `imageProcessingSemaphore` (weight 2) on `APIV1Service` (`server/router/api/v1/v1.go:59-60`), commented as limiting concurrent thumbnail generation to prevent memory exhaustion.

There is also a bounded webhook dispatch queue — a 128-slot channel drained by four workers, which drops payloads when full (`internal/webhook/webhook.go:39-55` and `:184-196`) — but that throttles the server's own outbound deliveries, not inbound API traffic.
