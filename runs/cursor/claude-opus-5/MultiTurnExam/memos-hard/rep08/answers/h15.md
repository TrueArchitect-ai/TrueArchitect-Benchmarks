Observations that matter for reading this list:

The enforcement style splits in two. Single-resource reads *reject* (`checkMemoReadAccess` returns `NotFound` for archived-not-yours, `Unauthenticated` for anonymous on non-public, `PermissionDenied` for private-not-yours). List endpoints instead *filter* by constraining the query — either `memoFind.VisibilityList` or, for the logged-in general case, a CEL filter string `creator_id == N || visibility in ["PUBLIC", "PROTECTED"]` (`server/router/api/v1/memo_service.go:222`). The public surfaces (RSS, sitemap) hard-pin `VisibilityList` to `[]store.Visibility{store.Public}`.

The file server is the one surface with a deliberate bypass: a valid, non-expired `share_token` query param whose `MemoID` matches grants access to attachments on private or protected memos (`server/router/fileserver/fileserver.go:684-689`). The RPC counterpart is `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:152`), which resolves a token via `getActiveMemoShare` (`:199`) and intentionally does **not** consult visibility — it only rejects missing/expired tokens and archived memos, returning `NotFound` uniformly to avoid information leakage. So share links are a sanctioned visibility override, not an enforcement site.

`SSEClient.canReceive` is worth calling out because it fails closed: unknown visibility values are logged and denied, and only `Private` events are restricted (to creator or admin).

Finally, note that `canViewerAccessMemo` is duplicated verbatim in two packages (`server/router/api/v1/user_service_notifications.go:302` and `server/notification/email.go:306`), which is why I list them as separate sites — they're independent copies, not one shared helper. The MCP router (`server/router/mcp/`) contains no visibility logic of its own; it goes through the API service.
