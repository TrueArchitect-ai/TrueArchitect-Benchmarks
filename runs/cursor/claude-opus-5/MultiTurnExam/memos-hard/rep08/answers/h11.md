**1st: `store.User` — 7 packages (5 non-test production packages, ~93 reference lines); 2nd: `store.Memo` — 6 packages (4 production packages, ~64 reference lines).**

Both are defined in the data layer: `store.User` at `store/user.go:29` and `store.Memo` at `store/memo.go:35`.

Where each is referenced from, outside the `store/` tree:

`store.User` appears in `server/auth`, `server/notification`, `server/router/api/v1`, `server/router/fileserver`, `server/router/rss`, plus the test packages `server/router/api/v1/test` and `server/router/frontend` (test file only). Its reach is what you'd expect — it's the currency of authentication (`server/auth`), it's the subject of avatar serving (`server/router/fileserver`, as traced earlier), and it's needed to attribute feeds and notifications.

`store.Memo` appears in `server/notification`, `server/router/api/v1`, `server/router/rss`, `server/runner/memopayload`, and again the two test packages. The distinguishing factor versus `User` is that `Memo` never reaches `server/auth` or `server/router/fileserver`, which costs it two packages.

Third place is `store.Attachment` (`store/attachment.go:16`) at 4 packages / ~43 lines, then `store.Inbox`, `store.MemoRelation`, and `store.MemoShare` at 3 each, `store.Reaction` and `store.UserIdentity` at 2.

Two caveats on methodology worth flagging:

I counted directories (Go packages) containing at least one `store.<Type>` reference, using a pattern that requires a non-identifier character after the type name so that `store.Memo` doesn't absorb `store.MemoRelation` or `store.MemoShare`, and `store.User` doesn't absorb `store.UserSetting` or `store.UserIdentity`. I excluded everything under `store/` itself, since the drivers in `store/db/*` reference every entity by construction and would flatten the ranking.

The apparent hits for `store.IdentityProvider`, `store.InstanceSetting`, and `store.UserSetting` in `proto/gen/store` are false positives and I discarded them. The generated protobuf package there is itself named `store`, so those matches are self-references to protobuf message types, not uses of the data-layer entities. Server code refers to those protobuf types through the `storepb` alias instead, which is why the real persistence-level `UserSetting`/`InstanceSetting`/`IdentityProvider` entities effectively never escape the data layer — access is mediated by `Store` methods returning protobuf payloads.
