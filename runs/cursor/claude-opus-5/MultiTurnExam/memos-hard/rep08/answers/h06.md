**Handlers: `CreateMemo`, `UpdateMemo`, `DeleteMemo`, `CreateMemoComment`, `SetMemoAttachments`, `SetMemoRelations` (six of them). Convergence function: `webhook.Post` — `internal/webhook/webhook.go:120` (the actual request goes out at line 152).**

The six RPC handlers and how each reaches a dispatch:

| Handler | Handler location | Dispatch site |
|---|---|---|
| `CreateMemo` | `server/router/api/v1/memo_service.go:70` | `DispatchMemoCreatedWebhook` at `memo_service.go:157` |
| `UpdateMemo` | `server/router/api/v1/memo_service.go:401` | `dispatchMemoUpdatedSideEffects` at `memo_service.go:513` |
| `DeleteMemo` | `server/router/api/v1/memo_service.go:518` | `DispatchMemoDeletedWebhook` at `memo_service.go:562` |
| `CreateMemoComment` | `server/router/api/v1/memo_service_comments.go:20` | `DispatchMemoCommentCreatedWebhook` at `memo_service_comments.go:119` |
| `SetMemoAttachments` | `server/router/api/v1/memo_attachment_service.go:16` | `dispatchMemoUpdatedSideEffects` at `memo_attachment_service.go:48` |
| `SetMemoRelations` | `server/router/api/v1/memo_relation_service.go:16` | `dispatchMemoUpdatedSideEffects` at `memo_relation_service.go:48` |

The last three rows are the non-obvious ones: `SetMemoAttachments` and `SetMemoRelations` don't mention webhooks at all. They call the shared helper `dispatchMemoUpdatedSideEffects` (`server/router/api/v1/memo_update_helpers.go:66`), which fires `DispatchMemoUpdatedWebhook` alongside the SSE broadcast — so editing a memo's attachments or relations delivers a `memos.memo.updated` webhook just like `UpdateMemo` does.

The funnel below the handlers has two stages. All four `Dispatch*Webhook` methods live in `server/router/api/v1/memo_service_webhooks.go`; three of them delegate to `dispatchMemoRelatedWebhook` (line 48), which resolves the memo creator and loads their webhooks via `s.Store.GetUserWebhooks`, while `DispatchMemoCommentCreatedWebhook` (line 30) instead loads the *related memo owner's* webhooks. Both loops set `payload.URL = hook.Url` plus the signing secret and call `webhook.PostAsync` (lines 43 and 71) — that's the in-process convergence point, but it only enqueues onto the bounded `asyncPostQueue`.

The single function where every path converges immediately before delivery is `webhook.Post` (`internal/webhook/webhook.go:120`), reached from the four queue-draining goroutines started in `init()` (`internal/webhook/webhook.go:42-55`). `Post` marshals the payload, signs it, and issues `safeClient.Do(req)` at line 152 — the only place an outbound webhook request is actually made.

Two things I ruled out. The user-facing webhook CRUD handlers in `server/router/api/v1/user_service_webhooks.go` only *validate* and store URLs (`webhook.ValidateURL` at lines 74, 161, 182) and never dispatch, so there's no "test this webhook" RPC. Separately, `GetLinkMetadata` does fetch a user-supplied URL via `fetchHTMLMeta = httpgetter.GetHTMLMeta` (`server/router/api/v1/memo_service.go:28`), but that's a per-request URL argument rather than a configured webhook target, and it doesn't pass through `webhook.Post`.
