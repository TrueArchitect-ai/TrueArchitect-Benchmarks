**Premise correction: this repository has no rate-limiting middleware at all — per-user or otherwise — so there is no registration site and no request limits to report.**

What I checked to establish that:

A case-insensitive search across all Go files for `ratelimit`, `rate_limit`, `throttle`, and `limiter` produces only two hits, both aspirational documentation rather than code: a suggestion to "Rate limit email sending to prevent abuse" in `internal/email/doc.go:86`, and a "5. Implement Rate Limiting" section sketching example code in `internal/email/README.md:286-295`. Neither is wired into anything. Searching for `429`/`TooManyRequests` across Go, TypeScript, YAML, and Markdown also yields nothing, and `go.mod` contains no rate-limiting dependency (no `golang.org/x/time/rate`, no `echo` rate-limiter middleware package).

The actual middleware stack is short. On the Echo side, `NewServer` registers exactly two global middlewares — `middleware.Recover()` and `newCORSMiddleware(profile)` at `server/server.go:51-52`. On the RPC side, the Connect interceptor chain in `server/router/api/v1/connect_interceptors.go` consists of `MetadataInterceptor` (line 22), `LoggingInterceptor` (line 98), `RecoveryInterceptor` (line 165), and `AuthInterceptor` (line 208). None of these count requests or enforce quotas.

What does exist are *concurrency* and *size* limits, which are easy to mistake for rate limiting but are a different mechanism — they cap simultaneous work or payload size, not requests per unit time:

- `thumbnailSemaphore` and `imageProcessingSemaphore` in `APIV1Service`, limiting concurrent thumbnail generation to 3 and image processing to 2 (`server/router/api/v1/v1.go:57-58`).
- A `thumbnailSemaphore` in the file server (`server/router/fileserver/fileserver.go:107`, bounded by `maxConcurrentThumbnails`).
- Per-memo content length validation via `getContentLengthLimit` (`server/router/api/v1/memo_service.go:595`).
- The bounded webhook dispatch queue (capacity 128, four workers) in `internal/webhook/webhook.go:39-55`, which drops events when full rather than throttling callers.

So if you need per-user API rate limiting, it would have to be added — either as an Echo middleware alongside the CORS/Recover pair at `server/server.go:51-52`, or as an additional Connect interceptor in the chain, where `AuthInterceptor` has already resolved the calling user.
