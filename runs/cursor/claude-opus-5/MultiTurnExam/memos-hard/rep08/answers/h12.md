How I narrowed it down from the three candidates:

**1. Establish the default driver.** With no flags, the driver comes from Viper, and both the default and the flag default are `"sqlite"` — `viper.SetDefault("driver", "sqlite")` at `cmd/memos/main.go:122` and `rootCmd.PersistentFlags().String("driver", "sqlite", ...)` at `cmd/memos/main.go:130`. That value is read into the profile at `cmd/memos/main.go:43` (`Driver: viper.GetString("driver")`). The DSN is also self-configuring: `internal/profile/profile.go:110-117` fills in `<data>/memos_prod.db` when the driver is sqlite and no DSN was given, so a bare install genuinely runs on SQLite rather than failing.

**2. Resolve the interface to a concrete type at the one dispatch point.** `cmd/memos/main.go:57` calls `db.NewDBDriver(instanceProfile)`, and that factory is the only place a driver is constructed (`store/db/db.go:14-32`). Its `switch profile.Driver` sends `"sqlite"` to `sqlite.NewDB(profile)` at `store/db/db.go:20`. The returned `store.Driver` is handed to `store.New(dbDriver, instanceProfile)` at `cmd/memos/main.go:64` and kept as `s.driver`, so every later call is dynamically dispatched to that single instance. As established in a previous question, the MySQL and Postgres packages are imported nowhere else, which is what makes this switch the sole determinant.

**3. Follow the write path.** The API handler calls `s.Store.CreateMemo(ctx, create)` at `server/router/api/v1/memo_service.go:115`. `Store.CreateMemo` (`store/memo.go:109-114`) validates the UID against `base.UIDMatcher` and then delegates straight to `s.driver.CreateMemo(ctx, create)` — no caching or extra logic. `CreateMemo` is declared on the driver interface at `store/driver.go:29`, and the three implementations (`store/db/sqlite/memo.go:16`, `store/db/mysql/memo.go`, `store/db/postgres/memo.go`) are the candidates; step 2 selects the SQLite one.

The SQLite implementation builds the column and placeholder lists dynamically, marshals `create.Payload` to protojson (defaulting to `{}`), optionally appends `created_ts`/`updated_ts` when non-zero, then issues a single `QueryRowContext` with `RETURNING id, created_ts, updated_ts, row_status` and scans those back into the struct. Worth noting because it differs by backend: SQLite and Postgres can use `RETURNING`, whereas the MySQL implementation has to insert and then fetch the generated id separately — so "which one runs" changes the shape of the statement, not just the dialect quoting.
