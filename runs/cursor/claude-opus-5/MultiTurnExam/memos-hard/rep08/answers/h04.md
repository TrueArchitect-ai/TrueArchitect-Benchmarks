**No — outside the factory, `mysql.NewDB` is never called, and the `store/db/mysql` package is imported in exactly one place.**

The evidence, from three complementary searches:

1. **Import graph.** A repo-wide grep for `github.com/usememos/memos/store/db/mysql` returns a single hit: `store/db/db.go:8`. No other Go file in the repository imports the MySQL driver package, so no other file *could* construct it.

2. **Constructor call sites.** Grepping for `NewDB(` across all `.go` files yields five calls, and only one is MySQL: `mysql.NewDB(profile)` at `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver`. The other four are `sqlite.NewDB` (`store/db/db.go:20`, plus two test helpers at `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416`) and `postgres.NewDB` (`store/db/db.go:24`).

3. **Everything else goes through the factory.** All driver acquisition funnels through `db.NewDBDriver`, called at `cmd/memos/main.go:57`, `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70`. Even the store test harness picks MySQL only by setting `profile.Driver`, never by importing the package.

One nuance that doesn't change the answer: there is a bare `DB` struct literal at `store/db/mysql/auth_config_test.go:12` (`db := &DB{}`). That is an in-package test creating a zero-value receiver — no DSN parsing, no `sql.Open`, no connection — purely so it can call the pure helper `IsRetryableAuthenticationMutationError`. It is not a construction of a usable driver, and being in `package mysql` it isn't "outside" the driver package anyway.

For reference, the real constructor is `store/db/mysql/mysql.go:20`, which merges `multiStatements=true` into the DSN, parses it with `mysql.ParseDSN`, and opens the pool.
