Notes on the interesting hops:

The URL the browser requests is generated server-side. When a user is converted for the API, `user_service_converters.go:32-38` checks whether `AvatarURL` holds base64 image data and, if so, replaces it with the path `/file/{user.Name}/avatar` — and since `userpb.Name` is `users/{username}` (`BuildUserName`, `server/router/api/v1/user_resource_name.go:13`), the result is `/file/users/{username}/avatar`. This keeps raw base64 out of API responses.

The route itself is registered on the `/file` group and is deliberately wired *before* the gRPC-Gateway (`server/server.go:81-82`), so avatars are served by native Echo handlers rather than through the RPC stack.

`serveUserAvatar` does two things before touching the data layer: on a private instance (`!s.Profile.AllowAnonymous()`) it requires a valid session/access token/PAT via `getCurrentUser` and returns 401 otherwise (lines 173-181), then it reads the `:identifier` path param as a **username** — `getUserByUsername` builds `store.FindUser{Username: &identifier}`, so lookup is by username, not numeric ID.

The cache hop is worth calling out: `Store.GetUser` only consults `s.userCache` when `find.ID` is set (`store/user.go:149-156`). Because this path searches by username, the cache is always missed on read and the call falls through to `Store.ListUsers` → driver → SQL every time; the fetched user is then written into the cache keyed by ID (`store/user.go:167`).

Finally, the stored value is a data URI, not a file. Back in the handler, `parseDataURI` decodes `user.AvatarURL` into `imageType` and `imageData` (line 196), the MIME type is checked against the `avatarAllowedTypes` allowlist (line 201, declared at line 75) to block XSS-capable types, security and cache headers are set, and the bytes are written with `c.Blob` (line 209). So the "stored data" for a profile image is the base64 payload in the `user.avatar_url` column — no attachment or object-storage lookup is involved.
