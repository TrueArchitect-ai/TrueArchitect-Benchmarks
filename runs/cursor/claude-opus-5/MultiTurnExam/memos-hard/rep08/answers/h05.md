**Explicit Go code — two `DELETE FROM reaction` statements issued inside the delete-user transaction by each driver; there is no database-level rule (the `reaction` table has no foreign key at all).**

What I checked, in order:

**1. The store entry point.** `Store.DeleteUser` (`store/user.go:171-181`) is a thin wrapper: it delegates to `s.driver.DeleteUser(ctx, delete)`, then invalidates caches via `deleteUserCache` (`store/user_delete.go:39-47`). The shared `store/user_delete.go` holds only the result struct and a test failpoint — no reaction logic — so the work lives in the drivers.

**2. The per-driver delete transaction.** Each driver implements `DeleteUser` with a `BeginTx` + deferred rollback, collects targets, then runs `deleteUserTargetsTx`. That function removes reactions in two passes, and they are the *first* and *third* steps:


The two passes cover different things, which is why both are needed:

- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/mysql/user_delete.go:437-440`) removes reactions *the deleted user made*, anywhere.
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (`store/db/mysql/user_delete.go:417-425`) removes reactions *other users made on the deleted user's memos*. The content IDs are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs` (line 549), matching how `reaction.content_id` is stored, and the memo set comes from `listDeleteUserMemoTreeIterative` (line 133), which walks `COMMENT` relations so comment threads under the user's memos are included too. Both run in batches of 500 (`deleteUserBatchSize`, line 14).

All three drivers do the same thing at the same line numbers: `store/db/mysql/user_delete.go:96,102,417,437`, `store/db/sqlite/user_delete.go:96,102,380,400`, and `store/db/postgres/user_delete.go:96,102,380,400`.

**3. Ruled out a database-level rule.** The `reaction` table is declared with no `FOREIGN KEY` clause in any backend — `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (and identically in the original `store/migration/*/0.20/00__reaction.sql`). It has only a primary key and `UNIQUE(creator_id, content_id, reaction_type)`. Grepping the whole migration tree for `FOREIGN KEY`/`ON DELETE`/`CASCADE` shows the only cascade in the current schema is `memo_share.memo_id → memo(id)` (`store/migration/*/LATEST.sql:108-109`, added in `store/migration/*/0.27/04__memo_share.sql`); the other cascades appear only in historical SQLite migrations (0.3–0.5) for other tables, and `reaction` is never among them.

So if the Go code were removed, reactions would be orphaned rather than cleaned up — the explicit statements are the only mechanism.
