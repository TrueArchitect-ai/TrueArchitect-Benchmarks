How it fits together:

**Frontend interceptor** — `authInterceptor` is defined in `web/src/connect.ts` and is registered on the single Connect-RPC transport that every service client is built from (`memoServiceClient`, `userServiceClient`, etc.). On each request it fetches a token via `getRequestToken()`, sets `Authorization: Bearer <token>`, and if the call fails with `Code.Unauthenticated` it refreshes once, retries with an `X-Retry: true` marker, and calls `redirectOnAuthFailure()` if the refresh fails.

**Tokens it manages** — `web/src/auth-state.ts` holds the access token in memory plus `localStorage` (`memos_access_token` / `memos_token_expires_at`), broadcasts refreshes to other tabs over a `BroadcastChannel`, and expires tokens early using a buffer so requests don't go out stale. The refresh token itself is never touched by JS: the transport uses `credentials: "include"` and a separate interceptor-free `refreshTransport` calls `AuthService.RefreshToken`, which relies on the `memos_refresh` cookie set in `server/router/api/v1/auth_service_session.go`.

**Backend validation** — the `server/auth` package (`authenticator.go`, `token.go`, `extract.go`, `context.go`) is the shared validator. `ExtractBearerToken` pulls the credential off the `Authorization` header, `AuthenticateByAccessTokenV2` verifies the 15-minute access-token JWT statelessly, `AuthenticateByPAT` handles `memos_pat_`-prefixed personal access tokens against the store, and `AuthenticateByRefreshToken` checks the 30-day refresh JWT for revocation. It's invoked from the Connect `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go` through the `Authorizer` in `server/router/api/v1/authz.go`, and the same package is reused by the gRPC path (`server/router/api/v1/v1.go`) and the file server.
