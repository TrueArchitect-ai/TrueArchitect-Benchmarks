Before deleting the memo row, `Store.DeleteMemo` cleans up two kinds of records:

- **Memo relations** — deleted twice, once for rows where the memo is the source (`MemoID`) and once for rows where it is the target (`RelatedMemoID`), so both incoming and outgoing links (including comment links) go away.
- **Attachments** — every attachment found via `FindAttachment{MemoID: ...}` is removed one at a time through `Store.DeleteAttachment`, which also deletes the backing file/object in storage before removing the attachment row.

Only after those does it call `s.driver.DeleteMemo`, which is a plain `DELETE FROM memo WHERE id = ?` (see `store/memo.go` lines 140–159, `store/attachment.go` lines 132–149, and `store/db/sqlite/memo.go` lines 237–248).

Worth noting what is *not* handled in the store layer: reactions are never deleted there, and child comment memos are deleted by the API handler itself (`server/router/api/v1/memo_service.go` lines 567–582), which loops over comment relations calling `Store.DeleteMemo` for each before deleting the parent.
