The store's `DeleteMemo` cleans up two kinds of records before deleting the memo row:

- **Memo relations** — both directions: rows where the memo is the source (`MemoID`) and rows where it is the target (`RelatedMemoID`).
- **Attachments** linked to the memo — each attachment found via `ListAttachments(FindAttachment{MemoID: ...})` is removed with `DeleteAttachment`, which also deletes the attachment's backing storage (local file or external object) before the attachment row.

Only then does it call the driver's `DeleteMemo` to remove the memo row itself:

```140:159:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	// ... DeleteAttachment for each ...
	return s.driver.DeleteMemo(ctx, delete)
}
```

Two related points worth noting, since they are handled outside the store's `DeleteMemo`:

- The driver implementations are plain single-table `DELETE FROM memo WHERE id = ?` statements (`store/db/sqlite/memo.go`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go`), so all the cascading logic above really does live in the store layer.
- The API handler `DeleteMemo` in `server/router/api/v1/memo_service.go` first deletes child comment memos (found via comment-type relations) by recursively calling `store.DeleteMemo`. Reaction and `memo_share` rows are not deleted by the store; those rely on `ON DELETE CASCADE` foreign keys in the schema (`store/migration/sqlite/LATEST.sql`).
