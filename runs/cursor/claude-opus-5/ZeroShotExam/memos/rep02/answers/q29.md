**Answer: `web/src/connect.ts` (with token storage in `web/src/auth-state.ts`); short-lived JWT access tokens (localStorage, `Authorization: Bearer`) plus long-lived refresh tokens (HTTP-only `memos_refresh` cookie), with Personal Access Tokens also accepted; `server/auth`**

**Where the interceptor lives.** The Connect-RPC `authInterceptor` is defined in `web/src/connect.ts` and installed on the single `createConnectTransport` that backs every service client (memo, user, auth, attachment, AI, shortcut, IdP, instance). On each request it fetches a token via `getRequestToken()` and sets `Authorization: Bearer <token>`. If the call fails with `Code.Unauthenticated` and hasn't already been retried (tracked by an `X-Retry` header), it refreshes the token, retries once, and otherwise calls `redirectOnAuthFailure()`.

**Tokens it manages.** Access tokens live in `web/src/auth-state.ts`, cached in memory and persisted to `localStorage` under `memos_access_token` / `memos_token_expires_at`, with cross-tab sharing over a `BroadcastChannel` named `memos_token_sync`. Refresh tokens are never touched by JS — the refresh call goes through a separate transport with no interceptors (to avoid recursion) using `credentials: "include"`, so the browser sends the refresh cookie. Refresh is deduplicated through a `tokenRefreshManager` so the proactive path in `web/src/hooks/useTokenRefreshOnFocus.ts` and the reactive 401 path can't race.

**Backend validation.** The `server/auth` package validates them. `server/auth/token.go` defines the JWT constants — issuer `memos`, audiences `user.access-token` (15 min) and `user.refresh-token` (30 days), cookie name `memos_refresh`, and the `memos_pat_` PAT prefix. `server/auth/authenticator.go` provides `AuthenticateByAccessTokenV2` (stateless JWT parse, no DB hit) and `AuthenticateByRefreshToken` (parses the JWT *and* checks `GetUserRefreshTokenByID` for revocation). `server/auth/extract.go` pulls the bearer token out of the header and the refresh token out of the cookie.

The Connect interceptor at `server/router/api/v1/connect_interceptors.go:222` calls `Authenticate(ctx, authHeader)` and applies the result to the context; `server/router/fileserver/fileserver.go` reuses the same package so HTTP file access behaves identically.
