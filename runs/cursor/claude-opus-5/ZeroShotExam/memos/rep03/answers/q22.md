**`(*APIV1Service).DispatchMemoCreatedWebhook` — `server/router/api/v1/memo_service_webhooks.go`; `internal/webhook` (`webhook.PostAsync`/`webhook.Post` in `internal/webhook/webhook.go`); HMAC-SHA256 Standard Webhooks signatures**

How it fits together:

- `CreateMemo` in `server/router/api/v1/memo_service.go` (line 157) calls `s.DispatchMemoCreatedWebhook(ctx, memoMessage)` and only logs a warning on failure, so webhook problems don't fail memo creation.
- That method (`server/router/api/v1/memo_service_webhooks.go`) delegates to the shared `dispatchMemoRelatedWebhook` helper with activity type `memos.memo.created`. The helper resolves the memo's creator, loads that user's webhooks via `s.Store.GetUserWebhooks`, and for each hook builds a `webhook.WebhookRequestPayload` carrying the memo, target URL, and the hook's signing secret.
- Delivery is handled by the `internal/webhook` package. `webhook.PostAsync` pushes the payload onto a bounded channel (capacity 128, dropped with a warning if full) that four background goroutines drain by calling `webhook.Post`, which does the actual `http.POST`. The HTTP client blocks dialing reserved/private IPs to guard against SSRF and DNS rebinding.
- Signing follows the Standard Webhooks spec: when a signing secret is present, `Post` derives the key (base64-decoding `whsec_`-prefixed secrets), computes `HMAC-SHA256` over `msgID + "." + timestamp + "." + body`, and sets the `webhook-id`, `webhook-timestamp`, and `webhook-signature: v1,<base64>` headers. Secrets are generated by `webhook.GenerateSigningSecret` from 32 random bytes.
