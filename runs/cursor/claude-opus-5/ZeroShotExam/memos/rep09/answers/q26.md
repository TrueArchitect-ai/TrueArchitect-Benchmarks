**Tables written: `memo`, `memo_relation`, `attachment`.** Plus `memo_share`, but only via a database-level `ON DELETE CASCADE` foreign key — there is no Go code that cleans it up, and on SQLite that cascade is disabled. Notably, `reaction` rows are **not** deleted.

How the deletion path works:

The API handler deletes comment memos first, then the memo itself, both through `store.DeleteMemo`:


The explicit cascade logic lives in the store wrapper, which removes `memo_relation` rows on both sides and each linked `attachment` before deleting the `memo` row itself:

```140:159:store/memo.go

	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
```

Each driver's `DeleteMemo` is a single-table `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`), `DeleteMemoRelation` only touches `memo_relation` (`store/db/sqlite/memo_relation.go:137`), and `DeleteAttachment` only touches `attachment` plus the underlying local/S3 blob (`store/db/sqlite/attachment.go:211`, `store/attachment.go:132`).

Two details worth flagging:

- `memo_share` is declared with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). However, the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite share rows are orphaned rather than cascaded. Contrast this with user deletion, which *does* explicitly clean shares (`store/db/sqlite/user_delete.go:406`).
- `reaction` is read (to build the webhook payload at `server/router/api/v1/memo_service.go:545`) but never deleted. Reactions key off `content_id` (the memo resource name string) with no foreign key to `memo`, so they are left behind.

Reads only, with no writes: `reaction`, and `user_setting` via `GetUserWebhooks` during webhook dispatch (`server/router/api/v1/memo_service_webhooks.go:25`).
