**Background workers the server actually starts**

- **s3presign runner** (`server/runner/s3presign/runner.go`, started at `server/server.go:153-174`) — runs `RunOnce` synchronously once at startup, then a goroutine loops on a `time.NewTicker` with `runnerInterval = 12h`; exits when its per-runner `context.CancelFunc` is fired during `Shutdown`, tracked by `backgroundRunnerWG`.
- **Store cache cleanup loops, 3 of them** (`store/cache/cache.go:83`, `cleanupLoop` at line 200) — one goroutine per cache (`instanceSettingCache`, `userCache`, `userSettingCache` in `store/store.go:47-53`), each driven by a `time.NewTicker(config.CleanupInterval)` = 5 minutes, with `DefaultTTL` 10 minutes (`store/store.go:40-45`). Started implicitly by `store.New`, which `cmd/memos/main.go:64` calls before the server is built.
- **Webhook async dispatch pool, 4 goroutines** (`internal/webhook/webhook.go`, `init()` around lines 42-54) — not time-scheduled; each goroutine blocks reading the buffered `asyncPostQueue` channel (capacity 128), so work is queue/event-driven.
- **Email async send pool, 2 goroutines** (`internal/email/email.go:14-20`) — same pattern, driven by the buffered `asyncEmailQueue` channel rather than a timer.
- **HTTP serve goroutine** (`server/server.go:124`) and the **signal-handler goroutine** (`cmd/memos/main.go:99`) are the only other long-lived goroutines; the latter is triggered by SIGINT/SIGTERM, not a schedule.

Two other timers exist but are per-request rather than background workers: the SSE heartbeat ticker created per connection (`server/router/api/v1/sse_handler.go:64`) and the fire-and-forget PAT last-used update (`server/auth/authenticator.go:180`).

**Unused scheduling infrastructure**

- `internal/scheduler` is a complete cron-style job scheduler (`scheduler.go` with `Register`/`Start`/`runJobWithSchedule`, `parser.go` with `ParseCronExpression`, `job.go`, `middleware.go`, plus a README advertising it as "production-ready") and it is **never wired into the server**. The only imports of `github.com/usememos/memos/internal/scheduler` are its own `example_test.go` and `integration_test.go`; no production code references it, so no cron expression drives anything at runtime.
- `server/runner/memopayload` is likewise **not started as a runner**. Its `Runner`/`NewRunner`/`RunOnce` (`server/runner/memopayload/runner.go:19-72`) have no callers; only the standalone helper `RebuildMemoPayload` is used, and it is invoked inline on the request path in `server/router/api/v1/memo_service.go:108` and `:447`. `server/server.go` does not import the package at all.
