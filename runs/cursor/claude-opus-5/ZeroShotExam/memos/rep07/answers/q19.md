MemoService is exposed twice from the same `APIV1Service` implementation — once as REST/HTTP-JSON through grpc-gateway, and once as Connect RPC. There is no standalone gRPC server process (`grpc.NewServer` appears nowhere outside generated code); both surfaces are mounted on the same Echo server.

- **gRPC-Gateway (REST / HTTP+JSON transcoding)** — `server/router/api/v1/v1.go`, where `RegisterGateway` registers the service against the gateway mux and mounts it on Echo:

```108:129:server/router/api/v1/v1.go
	if err := v1pb.RegisterMemoServiceHandlerServer(ctx, gwMux, s); err != nil {
		return err
	}
	// ... other services ...
	handler := echo.WrapHandler(http.MaxBytesHandler(gwMux, maxAPIRequestBytes))

	gwGroup.Any("/api/v1/*", handler)
	gwGroup.Any("/file/*", handler)
```

The generated transcoding code it depends on is `proto/gen/api/v1/memo_service.pb.gw.go`.

- **Connect RPC (connect-go, used by the browser client in place of grpc-web)** — `server/router/api/v1/connect_handler.go`, where the `ConnectServiceHandler` wrapper registers the Connect handler:

```40:40:server/router/api/v1/connect_handler.go
		wrap(apiv1connect.NewMemoServiceHandler(s, opts...)),
```

The per-method wrapping that adapts Connect request/response types to the gRPC method signatures lives in `server/router/api/v1/connect_services.go` (see the `// MemoService` section, lines 304-464), the mux is mounted at `/memos.api.v1.*` in `server/router/api/v1/v1.go` (lines 139-144), and the generated Connect stubs are in `proto/gen/api/v1/apiv1connect/memo_service.connect.go`.

Worth noting since it can look like a third protocol: `server/router/mcp/catalog.go` lists `MemoService_*` operation IDs, but that is an MCP tool catalog built on top of the OpenAPI spec rather than a separate registration of the service itself.
