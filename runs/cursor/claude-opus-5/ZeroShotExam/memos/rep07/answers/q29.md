**Answer: `web/src/connect.ts` (the `authInterceptor`, with token storage in `web/src/auth-state.ts`); short-lived JWT access tokens (localStorage, `Authorization: Bearer`) plus a long-lived HttpOnly refresh-token cookie (`memos_refresh`), and Personal Access Tokens (`memos_pat_…`) as an equivalent Bearer credential for API clients; validated by `server/auth`.**

How it fits together:

**Frontend interceptor** — `authInterceptor` in `web/src/connect.ts` is installed on the Connect-Web transport that backs every service client (`memoServiceClient`, `userServiceClient`, etc.). On each request it calls `getRequestToken()`, sets `Authorization: Bearer <token>`, and on a `Code.Unauthenticated` response refreshes once, marks the retry with an `X-Retry` header, and replays the call; if the refresh fails it calls `redirectOnAuthFailure()`.

**Tokens it manages** — `web/src/auth-state.ts` holds the access token in memory plus `localStorage` (`memos_access_token` / `memos_token_expires_at`), and syncs newly refreshed tokens across tabs over a `BroadcastChannel`. The refresh token is never touched by JS: `fetchWithCredentials` sends `credentials: "include"` so the `memos_refresh` cookie rides along, and a separate `refreshTransport` with no interceptors calls `AuthService.refreshToken` to avoid recursion. Refreshes are deduplicated by `tokenRefreshManager`, shared with the proactive `web/src/hooks/useTokenRefreshOnFocus.ts` path.

**Backend validation** — the `server/auth` package. `server/auth/token.go` defines the token kinds and parsers (`ParseAccessTokenV2`, `ParseRefreshToken`, HS256 with `kid: v1`, 15-minute access / 30-day refresh lifetimes, `HashPersonalAccessToken`), and `server/auth/authenticator.go` resolves credentials: stateless access-token validation, DB-backed refresh-token revocation checks, and PAT lookup by hash. The Connect interceptor at `server/router/api/v1/connect_interceptors.go:222` calls `authorizer.Authenticate` and stores the result via `auth.ApplyToContext`.
