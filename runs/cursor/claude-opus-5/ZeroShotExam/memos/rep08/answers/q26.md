**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share` (the last only via DB-level `ON DELETE CASCADE`, which is *not* enforced on SQLite).**

How that breaks down:

**Directly deleted by explicit code** — `store.DeleteMemo` (`store/memo.go:140-159`) does the cleanup before removing the memo itself:

```140:159:store/memo.go
func (s *Store) DeleteMemo(ctx context.Context, delete *DeleteMemo) error {
	// Clean up memo_relation records where this memo is either the source or target.
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {
		return err
	}
	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID}); err != nil {
		return err
	}
	// Clean up attachments linked to this memo.
	attachments, err := s.ListAttachments(ctx, &FindAttachment{MemoID: &delete.ID})
	...
	return s.driver.DeleteMemo(ctx, delete)
}
```

- `memo_relation` — both directions (`memo_id` and `related_memo_id`).
- `attachment` — each linked attachment row is deleted through `Store.DeleteAttachment` (`store/attachment.go:132-149`), which also removes the underlying local/S3 blob.
- `memo` — the row itself, via the driver (e.g. `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

The API layer `DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) additionally recurses: it lists comment relations and calls `Store.DeleteMemo` for every comment memo, so extra rows in the same three tables are removed for each comment.

**Affected by database cascade:** `memo_share` declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). There is no Go code that deletes shares by memo ID — `store.DeleteMemoShare` only accepts an ID or UID (`store/memo_share.go:24-27`). Worth flagging: the SQLite driver opens the DB with foreign keys turned off (`store/db/sqlite/sqlite.go:53`, `_pragma=foreign_keys(0)`), so on SQLite deployments this cascade does **not** fire and `memo_share` rows are left orphaned.

**Notably not touched:** `reaction`. The API handler reads reactions (`memo_service.go:545-550`) purely to build the webhook payload, and nothing in either the handler or the store deletes them. Since `reaction.content_id` is a plain `TEXT` column with no foreign key, those rows survive the memo. `inbox` rows created by mention notifications are likewise left in place.
