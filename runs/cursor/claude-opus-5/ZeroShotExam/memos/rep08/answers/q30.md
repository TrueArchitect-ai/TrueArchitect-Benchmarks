**Delivery convergence:** `webhook.PostAsync` → `webhook.Post` in `internal/webhook/webhook.go`

Details on how they converge: the three plain lifecycle events are thin wrappers over a shared helper, `dispatchMemoRelatedWebhook` in `server/router/api/v1/memo_service_webhooks.go`, which resolves the memo creator, loads that user's webhooks via `s.Store.GetUserWebhooks`, stamps the activity type/URL/signing secret onto a `webhook.WebhookRequestPayload`, and calls `webhook.PostAsync`. The comment event skips that helper because it targets the *parent* memo owner rather than the comment's creator, so it loads `GetUserWebhooks(ctx, relatedMemoCreatorID)` itself, but it builds the same payload and also ends at `webhook.PostAsync`.

From there, `PostAsync` enqueues onto a buffered channel (`asyncPostQueue`, capacity 128, dropping with a warning when full), and four worker goroutines started in `init()` each call `webhook.Post`, which does the actual HTTP POST with the Standard Webhooks HMAC-SHA256 headers over a shared SSRF-guarded client (`internal/webhook/webhook.go`).

Call sites, for reference: created in `server/router/api/v1/memo_service.go:157`, deleted at `server/router/api/v1/memo_service.go:562`, updated in `dispatchMemoUpdatedSideEffects` at `server/router/api/v1/memo_update_helpers.go:67`, and comment-created at `server/router/api/v1/memo_service_comments.go:119`. Every call site logs failures via `slog.Warn` rather than failing the request.
