`store.DeleteMemo` in `store/memo.go` (lines 140–159) removes two kinds of records before issuing the memo row delete:

- **Memo relations, in both directions** — one call with `MemoID` set (relations where this memo is the source) and one with `RelatedMemoID` set (relations where this memo is the target), so comment/reference links pointing either way are cleaned up. See `store/memo.go` lines 141–147, backed by `DeleteMemoRelation` in `store/memo_relation.go` and each driver's implementation (e.g. `store/db/sqlite/memo_relation.go`).
- **Attachments linked to the memo** — it lists attachments via `FindAttachment{MemoID: ...}` and deletes each one through `store.DeleteAttachment` (`store/memo.go` lines 148–157). That path also deletes the underlying stored file/blob before the attachment row, per `store/attachment.go` lines 132–149 and `deleteAttachmentStorageImpl`.

Only after both of those does it call `s.driver.DeleteMemo(ctx, delete)` for the memo row itself.

Two related notes for context: child comment memos are deleted by the API layer, not the store — `APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go` (lines 567–577) lists comment relations and calls `store.DeleteMemo` for each comment first. And reactions and memo shares are not deleted by the store layer; `memo_share` relies on a `ON DELETE CASCADE` foreign key (`store/migration/sqlite/LATEST.sql` line 109), while `reaction` rows are keyed by `content_id` text with no foreign key or explicit cleanup in this path.
