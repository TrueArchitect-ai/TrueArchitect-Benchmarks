MemoService is exposed over **REST/HTTP+JSON (via grpc-gateway)** and **Connect RPC (connectrpc.com/connect)** — there is no native gRPC listener in this repo (no `grpc.NewServer` or `RegisterMemoServiceServer` call outside generated code).

- **REST/HTTP JSON via grpc-gateway** — `server/router/api/v1/v1.go`. The service is registered in-process on the gateway mux at line 108 with `v1pb.RegisterMemoServiceHandlerServer(ctx, gwMux, s)`, and that mux is mounted onto Echo at `/api/v1/*` and `/file/*` (lines 123–129). The generated gateway glue it relies on is `proto/gen/api/v1/memo_service.pb.gw.go`, and `APIV1Service` embeds `v1pb.UnimplementedMemoServiceServer` (line 26).

- **Connect RPC** — `server/router/api/v1/connect_handler.go`. `RegisterConnectHandlers` registers `apiv1connect.NewMemoServiceHandler(s, opts...)` (line 40) onto an `http.ServeMux`, which `v1.go` mounts on Echo under `/memos.api.v1.*` (lines 139–144). The per-method Connect wrappers that unwrap `connect.Request`/rewrap `connect.Response` and translate gRPC status codes live in `server/router/api/v1/connect_services.go` under the `// MemoService` section starting at line 304, with the generated handler in `proto/gen/api/v1/apiv1connect/memo_service.connect.go`.

Both paths delegate to the same `APIV1Service` methods, so business logic has a single implementation; the Connect layer is purely an adapter, as its doc comment on `ConnectServiceHandler` describes.
