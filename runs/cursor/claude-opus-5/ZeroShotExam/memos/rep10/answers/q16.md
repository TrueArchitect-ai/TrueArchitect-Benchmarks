Before removing the `memo` row, `Store.DeleteMemo` in `store/memo.go` (lines 140–158) cleans up two kinds of records:

- **`memo_relation` rows** — deleted twice, once for rows where the memo is the source (`memo_id`) and once for rows where it is the target (`related_memo_id`), so both inbound and outbound relations (including comment links) go away. These run through `driver.DeleteMemoRelation`, e.g. `store/db/sqlite/memo_relation.go:137`.
- **`attachment` rows linked to the memo** — it lists attachments via `ListAttachments(&FindAttachment{MemoID: ...})` and calls `Store.DeleteAttachment` for each. Note that this path also removes the underlying stored file, since `Store.DeleteAttachment` (`store/attachment.go:132`) calls `DeleteAttachmentStorage` before deleting the row.

Only after both of those does it call `driver.DeleteMemo` to delete the memo row itself.

Two things worth flagging about the surrounding API flow in `server/router/api/v1/memo_service.go`: the API handler `DeleteMemo` (line 518) first lists comment relations and calls `Store.DeleteMemo` for each child comment memo (lines 567–577), so each comment's relations and attachments are cleaned up by the same store logic. Reactions and memo shares are *not* deleted by the store layer here — the handler only reads reactions to build the webhook payload.
