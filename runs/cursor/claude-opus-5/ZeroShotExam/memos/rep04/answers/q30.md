- memo created (`memos.memo.created`): `APIV1Service.DispatchMemoCreatedWebhook`
- memo updated (`memos.memo.updated`): `APIV1Service.DispatchMemoUpdatedWebhook`
- memo deleted (`memos.memo.deleted`): `APIV1Service.DispatchMemoDeletedWebhook`
- memo comment created (`memos.memo.comment.created`): `APIV1Service.DispatchMemoCommentCreatedWebhook`
- delivery: `webhook.PostAsync` → `webhook.Post` in `internal/webhook/webhook.go`

All four are defined in `server/router/api/v1/memo_service_webhooks.go`. The created/updated/deleted trio are thin wrappers over the shared helper `dispatchMemoRelatedWebhook`, which resolves the memo creator, loads that user's webhooks via `s.Store.GetUserWebhooks`, and enqueues one payload per hook. The comment case is separate because it targets the *parent* memo's owner (`relatedMemoCreatorID`) instead of the comment author, so it builds the payload inline rather than reusing the helper — but it still ends in the same `webhook.PostAsync` call.

Convergence happens inside `internal/webhook/webhook.go`: `PostAsync` pushes the payload onto the bounded `asyncPostQueue` (capacity 128, dropping with a warning when full), and four worker goroutines started in `init()` drain that queue and call `Post`, which marshals the JSON body, adds Standard Webhooks HMAC-SHA256 headers when a signing secret is present, and sends via the shared SSRF-guarded `safeClient`.

Call sites, for reference: `memo_service.go:157` (create), `memo_update_helpers.go:67` (update), `memo_service.go:562` (delete), and `memo_service_comments.go:119` (comment).
