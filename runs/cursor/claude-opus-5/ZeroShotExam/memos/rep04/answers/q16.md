Before deleting the memo row, `Store.DeleteMemo` in `store/memo.go` (lines 140–159) explicitly cleans up two kinds of records:

1. **Memo relations, in both directions** — `driver.DeleteMemoRelation` is called twice, once with `MemoID` set to the memo being deleted (relations where it is the source) and once with `RelatedMemoID` set (relations where it is the target).
2. **Attachments linked to the memo** — it lists attachments via `FindAttachment{MemoID: ...}` and calls `Store.DeleteAttachment` for each. That per-attachment path (`store/attachment.go`, lines 132–149) also removes the underlying stored file/blob through `DeleteAttachmentStorage` before deleting the attachment row.

Only after those does it call `s.driver.DeleteMemo(ctx, delete)` to remove the memo row itself.

Two related points for context: the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go`, lines 567–582) first deletes comment memos (memos joined by a `MemoRelationComment` relation) by recursively calling `Store.DeleteMemo` on each, so their relations and attachments get cleaned up by the same store logic. Reactions and memo shares are *not* deleted by the store layer; `memo_share` relies on a `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the schema (e.g. `store/migration/sqlite/LATEST.sql:109`, `store/migration/sqlite/0.27/04__memo_share.sql:11`), and reactions are keyed by content name rather than a memo foreign key.
