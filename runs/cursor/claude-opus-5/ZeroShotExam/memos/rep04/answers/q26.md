**Tables affected: `memo`, `memo_relation`, `attachment` (plus `memo_share` only on Postgres/MySQL, via the database-level `ON DELETE CASCADE`).**

How that breaks down:

The API handler in `server/router/api/v1/memo_service.go` (`DeleteMemo`, lines 518–593) first finds comment memos through `memo_relation` and calls `Store.DeleteMemo` on each of them, then calls `Store.DeleteMemo` for the memo itself. Everything else it does — listing reactions/attachments, dispatching the webhook, broadcasting the SSE event — is read-only or non-database work.

The actual writes happen in `store/memo.go`:

	if err := s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID}); err != nil {

- `memo_relation` — two `DELETE FROM memo_relation` statements (as `memo_id` and as `related_memo_id`), e.g. `store/db/sqlite/memo_relation.go:137`.
- `attachment` — `Store.DeleteAttachment` (`store/attachment.go:132`) removes the stored file and then issues `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go:211`).
- `memo` — the final `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`), executed once per comment memo plus once for the target memo.

Two caveats worth knowing:

`memo_share` is only cleaned up by the schema, not by code. All three schemas declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`), but the SQLite driver opens the database with foreign keys disabled — `_pragma=foreign_keys(0)` in `store/db/sqlite/sqlite.go:53` — so on SQLite deployments share rows are left orphaned.

The `reaction` table is never touched. `DeleteMemo` lists reactions only to build the webhook payload, and reactions are keyed by the string `content_id` (`memos/{uid}`) with no foreign key, so those rows survive the deletion in every backend.
