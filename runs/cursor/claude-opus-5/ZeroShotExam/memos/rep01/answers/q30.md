memos.memo.created: `DispatchMemoCreatedWebhook`
memos.memo.updated: `DispatchMemoUpdatedWebhook`
memos.memo.deleted: `DispatchMemoDeletedWebhook`
memos.memo.comment.created: `DispatchMemoCommentCreatedWebhook`

Delivery: `webhook.PostAsync` → `asyncPostQueue` → `webhook.Post` in `internal/webhook/webhook.go`

All four dispatchers live in `server/router/api/v1/memo_service_webhooks.go`. The first three are thin wrappers over the shared helper `dispatchMemoRelatedWebhook`, which just passes the activity type string; the comment case is separate because it looks up webhooks belonging to the *parent* memo's creator (`relatedMemoCreatorID`) rather than the comment author, and sets `payload.ActivityType = "memos.memo.comment.created"` inline.

Convergence happens in two stages. Both the shared helper and the comment dispatcher build a payload via `convertMemoToWebhookPayload`, attach the hook's URL and signing secret, and call `webhook.PostAsync` — those are the only two call sites of that function in the repo. `PostAsync` enqueues onto the buffered `asyncPostQueue` (capacity 128, dropping with a warning when full), and four worker goroutines started in `init()` drain the queue and call `webhook.Post`, which does the actual HTTP POST with the Standard Webhooks HMAC-SHA256 headers over the SSRF-guarded `safeClient`.

Worth noting on the update event: it is triggered from three places, all funneling through `dispatchMemoUpdatedSideEffects` in `server/router/api/v1/memo_update_helpers.go` — the main `UpdateMemo` path (`memo_service.go:513`) plus attachment and relation changes (`memo_attachment_service.go:48`, `memo_relation_service.go:48`), so editing a memo's attachments also emits `memos.memo.updated`.
