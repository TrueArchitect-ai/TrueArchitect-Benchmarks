Before deleting the memo row, `Store.DeleteMemo` cleans up two other kinds of records:

1. **Memo relation records** (`memo_relation`) — deleted twice, once for rows where the memo is the source (`MemoID`) and once for rows where it is the target (`RelatedMemoID`).
2. **Attachments linked to the memo** — it lists attachments via `FindAttachment{MemoID: ...}` and deletes each one through `Store.DeleteAttachment`, which also removes the underlying stored file/blob (`Store.DeleteAttachmentStorage`, deleting the local file for `LOCAL` storage) before removing the attachment row.

Only after those does it call `s.driver.DeleteMemo(ctx, delete)`, which is a plain `DELETE FROM memo WHERE id = ?` in each driver.

One nuance about the API path in `server/router/api/v1/memo_service.go` (`APIV1Service.DeleteMemo`, lines 518–593): before calling the store, the service itself deletes the memo's **comment memos** — it lists `memo_relation` rows of type `comment` pointing at the memo and calls `Store.DeleteMemo` for each, so each comment goes through the same relation/attachment cleanup.
