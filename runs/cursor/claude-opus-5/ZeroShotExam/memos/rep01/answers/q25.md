**Engine:** Google CEL (`github.com/google/cel-go v0.28.1`, declared in `go.mod:13`), wrapped by memos' own filter engine package at `internal/filter/` — `engine.go` (entry point `filter.DefaultEngine()`), `schema.go` (CEL env/field declarations), `parser.go` (CEL AST → IR), `ir.go` (dialect-agnostic condition tree), `render.go` (IR → SQL), `helpers.go` (store glue).

**Mechanism (one sentence):** `ListMemos` validates the CEL string via `s.validateFilter` (`server/router/api/v1/memo_service.go:211-216`, implemented in `server/router/api/v1/shortcut_service.go:336`) and stashes it in `store.FindMemo.Filters` (`store/memo.go:72`); each driver then calls `filter.DefaultEngine()` + `filter.AppendConditions(ctx, engine, find.Filters, <dialect>, &where, &args)` (`store/db/sqlite/memo.go:57-61`, `store/db/postgres/memo.go:54-58`, `store/db/mysql/memo.go:65-69`), which runs `Engine.Compile` — cel-go compiles the expression against the memo schema env and `parser.buildCondition` normalizes the AST into an IR tree — followed by `Program.Render`, where the dialect-aware renderer in `internal/filter/render.go` emits a parenthesized SQL fragment plus placeholder args appended to the query's `WHERE`.

Dialect differences live entirely in the renderer: placeholders are `$n` for Postgres and `?` for SQLite/MySQL (`internal/filter/render.go:842-849`), and JSON access, boolean coercion, tag membership (`LIKE` / `JSON_CONTAINS` / `@>`), regex (`REGEXP` / `~`), and string length (`LENGTH` / `CHAR_LENGTH`) each switch on `DialectName` (defined in `internal/filter/schema.go:11-16`). The RPC's `filter` field is documented as a CEL expression in `proto/api/v1/memo_service.proto:326-339`, and `internal/filter/README.md` describes the three-phase parse/normalize/render pipeline.
