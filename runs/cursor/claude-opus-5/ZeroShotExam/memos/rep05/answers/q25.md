**Engine:** Google CEL (`github.com/google/cel-go`), wrapped by the in-repo filter engine at `internal/filter/` — `engine.go` (`Engine`, `Compile`, `CompileToStatement`, `DefaultEngine`), `schema.go` (allowed variables/dialects), `parser.go` (CEL AST → IR), `ir.go` (dialect-agnostic condition tree), `render.go` (IR → SQL), `helpers.go` (`AppendConditions`).

**Mechanism:** `ListMemos` in `server/router/api/v1/memo_service.go` (line 178) validates `request.Filter` via `validateFilter` (defined in `server/router/api/v1/shortcut_service.go:336`) and pushes it onto `store.FindMemo.Filters`; each driver's `ListMemos` (`store/db/sqlite/memo.go:57`, `store/db/postgres/memo.go:54`, `store/db/mysql/memo.go:65`) then calls `filter.DefaultEngine()` plus `filter.AppendConditions(...)` with its own `DialectSQLite`/`DialectPostgres`/`DialectMySQL` constant, which compiles the CEL string against the memo schema into the IR and renders it to a dialect-specific SQL fragment with bound placeholders (`?` for SQLite/MySQL, `$n` with an offset for Postgres) that is ANDed into the query's `WHERE` clause.

Supporting detail: the three-phase pipeline (parse with `cel-go` against the schema env in `internal/filter/schema.go`, normalize into the IR, render per dialect) is documented in `internal/filter/README.md`. Dialect differences are localized in `render.go` — for example tag membership becomes `LIKE` patterns on SQLite, `JSON_CONTAINS` on MySQL, and `@>` on Postgres; regex becomes `REGEXP` versus `~`; `contains`/`startsWith` become `LIKE` versus `ILIKE`. Timestamp expressions using `now`/`duration()`/`timestamp()` are constant-folded to epoch seconds at compile time, with `now` frozen once per `Compile` (`internal/filter/engine.go:62`). The server also injects its own CEL filter for visibility scoping (`creator_id == N || visibility in ["PUBLIC", "PROTECTED"]`) through the same path.
