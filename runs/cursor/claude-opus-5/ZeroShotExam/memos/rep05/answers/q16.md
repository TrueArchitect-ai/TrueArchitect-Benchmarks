`Store.DeleteMemo` in `store/memo.go` (lines 140–159) cleans up two kinds of records before issuing the `DELETE FROM memo`:

- **Memo relations, in both directions** — one call with `MemoID` set (rows where this memo is the source) and a second with `RelatedMemoID` set (rows where this memo is the target). Both go through `s.driver.DeleteMemoRelation` (`store/memo_relation.go`, e.g. `store/db/sqlite/memo_relation.go`).
- **Attachments linked to the memo** — it lists attachments via `FindAttachment{MemoID: ...}` and deletes each with `s.DeleteAttachment`, which also removes the backing local/S3 file before deleting the DB row (`store/attachment.go` lines 132–149).

Only after those does it call `s.driver.DeleteMemo`, whose driver implementations are a plain single-row delete on the `memo` table with no additional cleanup (`store/db/sqlite/memo.go` line 237, and the Postgres/MySQL equivalents).

Two related points worth noting: comment memos are not handled by the store — the API layer (`server/router/api/v1/memo_service.go` lines 567–582) first lists comment-type relations and calls `Store.DeleteMemo` on each child memo, then deletes the parent. And reactions and memo shares are read for the webhook payload but are not explicitly deleted by `Store.DeleteMemo`.
