The explicit cascade lives in the store layer, `store/memo.go` lines 140–159: it deletes `memo_relation` rows on both sides (`memo_id` and `related_memo_id`), then deletes every `attachment` row linked to the memo via `Store.DeleteAttachment`, and finally the `memo` row itself.

- `memo_relation` deletes are plain `DELETE FROM memo_relation` statements (`store/db/sqlite/memo_relation.go` line 137 onward, with postgres/mysql equivalents).
- `attachment` deletes go through `Store.DeleteAttachment` (`store/attachment.go` lines 132–149), which also removes the underlying blob/local file/S3 object, then issues `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go` line 211).
- `memo` is deleted by the driver with a single `DELETE FROM memo WHERE id = ?` and no extra statements (`store/db/sqlite/memo.go` line 237, `store/db/postgres/memo.go` line 244, `store/db/mysql/memo.go` line 259).

Two caveats worth flagging:

`memo_share` is declared with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql` line 109, `store/migration/postgres/LATEST.sql` line 108, `store/migration/mysql/LATEST.sql` line 108), so Postgres and MySQL drop share rows automatically. SQLite opens its connection with foreign keys turned off (`store/db/sqlite/sqlite.go` line 53 sets `_pragma=foreign_keys(0)`), so on SQLite those `memo_share` rows are orphaned rather than deleted. No Go code deletes them on the memo-delete path — `memo_share` cleanup by `memo_id` exists only in the user-deletion path (`store/db/sqlite/user_delete.go` line 411).

`reaction` rows are read but never deleted. The handler lists reactions by content ID just to build the webhook payload (lines 545–550), and nothing in `Store.DeleteMemo` or the drivers removes them, so reactions keyed to the deleted memo's resource name stay behind.

Tables only read, not modified: `user` and `user_setting` (for permission checks and webhook lookup via `GetUserWebhooks` in `store/user_setting.go` line 312) and `system_setting`/instance settings during attachment storage cleanup. The SSE broadcast at the end touches no tables.
