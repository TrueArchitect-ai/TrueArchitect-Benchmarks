**No** — outside the driver-selection factory, nothing in the codebase constructs the MySQL driver.

Evidence:

- The only import of the driver package anywhere is in the factory itself. `grep -rn "store/db/mysql" --include=*.go .` returns exactly one hit: `store/db/db.go:8`, and the only call to its constructor is `store/db/db.go:22`.

```18:27:/bench/repo/store/db/db.go
	switch profile.Driver {
	case "sqlite":
		driver, err = sqlite.NewDB(profile)

		driver, err = mysql.NewDB(profile)
	case "postgres":
		driver, err = postgres.NewDB(profile)

	}
```

- Every other caller goes through the factory rather than the MySQL package: `cmd/memos/main.go:57`, `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70` all call `db.NewDBDriver(...)`.
- This is unlike the other two drivers, which *are* constructed directly outside the factory: `sqlite.NewDB(p)` in `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416`, and `&DB{db: db}` literals in `store/db/postgres/user_setting_test.go` (lines 36, 194, 257).

One nuance worth noting: the MySQL `DB` struct is instantiated once inside its own package, in a unit test that only needs a zero-value receiver for a pure helper method — `db := &DB{}` at `store/db/mysql/auth_config_test.go:12`, used to call `IsRetryableAuthenticationMutationError`. That is an in-package test literal, not a real driver construction (no DSN, no `sql.Open`), so it doesn't create a working driver outside the factory.

The MySQL `mysql.` references in `store/test/containers.go` (lines 42, 101–105) are the testcontainers `modules/mysql` package and the `go-sql-driver/mysql` package, not the repo's `store/db/mysql` driver.
