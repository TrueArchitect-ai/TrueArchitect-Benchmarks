**Mechanism: explicit Go code** — reactions are removed by hand-written `DELETE FROM reaction` statements inside the driver-level `DeleteUser` transaction, not by any database cascade. The `reaction` table has no foreign keys at all in the current schema, so nothing would happen automatically.

Two deletes run for every user deletion, covering both directions:

```96:104:store/db/sqlite/user_delete.go
	if err := deleteReactionsByContentIDsTx(ctx, tx, contentIDs); err != nil {
		return err
	}
	if err := deleteAttachmentsByIDsTx(ctx, tx, targets.attachmentIDs); err != nil {
		return err
	}
	if err := deleteReactionsByCreatorTx(ctx, tx, userID); err != nil {
		return err
	}
```

The first removes reactions *left by anyone* on the deleted user's memos — `contentIDs` comes from `memoContentIDsFromRefs`, which maps the recursive memo tree (the user's memos plus their comment descendants) to `"memos/"+uid` strings matching `reaction.content_id`. The second, `deleteReactionsByCreatorTx`, removes the deleted user's own reactions wherever they were placed, including on other people's memos: `DELETE FROM reaction WHERE creator_id = ?`.

**What I checked:**

- `store/db/sqlite/user_delete.go` (the two helpers at lines 380–403, called from `deleteUserTargetsTx`), and the identical implementations in `store/db/postgres/user_delete.go:380,400` and `store/db/mysql/user_delete.go:417,437`. All three drivers behave the same; the whole sequence runs in one transaction opened in `DeleteUser` and committed at the end.
- Schema for cascade rules: `CREATE TABLE reaction` in `store/migration/sqlite/LATEST.sql:92`, `store/migration/postgres/LATEST.sql:91`, and `store/migration/mysql/LATEST.sql:91` — columns are `creator_id`/`content_id` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint, no `REFERENCES` clause. The original `store/migration/sqlite/0.20/00__reaction.sql` was likewise FK-free, and the 0.23 migrations only rewrite `reaction_type` values to emoji. A repo-wide search for `REFERENCES`/`ON DELETE` in `store/migration/` returns hits only for memo, user_setting, memo_relation, memo_share, etc. — never `reaction`. Note also that `content_id` is a text name like `memos/abc123`, which couldn't carry a foreign key to `memo(id)` anyway.
- Call path: `server/router/api/v1/user_service.go:414` calls `Store.DeleteUser`, which delegates to the driver at `store/user.go:171`. No reaction cleanup happens at the service layer.
- Tests confirming the intended behavior: `server/router/api/v1/test/user_service_delete_test.go:287-298` asserts reactions on the user's own memo and on their comment are gone while a peer's reaction on a foreign memo survives, and `store/test/user_delete_test.go:217-220` makes the same assertion at the store level. `user_service_delete_test.go:429` checks a reaction is restored when the transaction rolls back via the `before_commit` failpoint, which also demonstrates the delete is transactional.
