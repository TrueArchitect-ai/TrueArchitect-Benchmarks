The premise is wrong: neither NATS nor RabbitMQ is involved, and there is no message broker anywhere in this repository. Grepping `go.mod`, `go.sum`, `web/package.json`, `scripts/`, and `.github/` for NATS, RabbitMQ/AMQP, Kafka, Celery, Sidekiq, and BullMQ returns nothing, and there is no broker service in the Docker build (`scripts/Dockerfile` builds a single monolithic `memos` binary, with no compose file or sidecar). So there is no externally declared queue to point to.

The actual mechanism is an in-process, in-memory Go channel with a fixed pool of goroutines. The "queue" is declared as a package-level buffered channel in `internal/webhook/webhook.go`, and the four workers that drain it are started in that same file's `init()`:

```39:55:/bench/repo/internal/webhook/webhook.go
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
)

func init() {
	for range 4 {
		go func() {
			for payload := range asyncPostQueue {
				if err := Post(payload); err != nil {
					slog.Warn("Failed to dispatch webhook asynchronously",
						slog.String("url", payload.URL),
						slog.String("activityType", payload.ActivityType),
						slog.Any("err", err))
				}
			}
		}()
	}
}
```

Producers enqueue via `PostAsync` (lines 182-196 of the same file), which does a non-blocking send and simply logs and drops the payload when the 128-slot buffer is full. Each worker then calls `Post`, which does a plain HTTP POST with a 30-second timeout through an SSRF-guarded client (`safeDialContext`, same file; private IPs are only permitted when `webhook.AllowPrivateIPs` is set from the `allow-private-webhooks` flag in `cmd/memos/main.go`).

Upstream, the API handlers trigger dispatch inline during the request. `server/router/api/v1/memo_service_webhooks.go` loads the creator's webhook list from the database and calls `webhook.PostAsync` per hook for activity types like `memos.memo.created`; `server/router/api/v1/memo_service.go` and `server/router/api/v1/memo_update_helpers.go` invoke those dispatch functions.

Worth noting for anyone expecting broker-like durability: the webhook *configuration* is persisted in user settings (`Store.GetUserWebhooks` in `store/user_setting.go`, keyed by `UserSetting_WEBHOOKS`), but the delivery queue itself is not persisted. A dedicated `webhook` table did exist once and was dropped — see `store/migration/mysql/0.25/00__remove_webhook.sql`. Since the queue is RAM-only, in-flight deliveries are lost on restart, there are no retries, and each server instance has its own independent queue.
