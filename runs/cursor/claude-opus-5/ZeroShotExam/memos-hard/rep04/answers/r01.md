**Premise correction:** There is no Redis connection in this repository. Memos has no Redis dependency at all — `redis` appears in zero files (not in `go.mod`/`go.sum`, not in `web/package.json`, and not in any source file). The only external datastore Memos connects to is its own relational database (SQLite, MySQL, or PostgreSQL), configured via `Driver`/`DSN` in `internal/profile/profile.go`. So there is no Redis host, port, or connection string to point you at.

**Actual mechanism:** The cache layer is a hand-rolled, in-process, in-memory cache that lives entirely inside the server process.

The implementation is `store/cache/cache.go`. It's a `sync.Map` guarded by an atomic item counter, with per-entry expiration timestamps and a background goroutine that periodically sweeps expired entries:

```66:73:/bench/repo/store/cache/cache.go
// Cache is a thread-safe in-memory cache with TTL and memory management.
type Cache struct {
	itemCount  atomic.Int64 // Use atomic operations to track item count
	data       sync.Map
	config     Config
	stopChan   chan struct{}
	closedChan chan struct{}
}
```

Configuration happens in `store.New` in `store/store.go`, where a single `cache.Config` is built and reused to instantiate three separate caches — one for instance settings, one for users, and one for user settings:

```39:53:/bench/repo/store/store.go

		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
```

**TTL for user entries: 10 minutes.** All user writes go through `Set`, which applies the cache's `DefaultTTL` rather than a custom value:

```92:95:/bench/repo/store/cache/cache.go
// Set adds a value to the cache with the default TTL.
func (c *Cache) Set(ctx context.Context, key string, value any) {
	c.SetWithTTL(ctx, key, value, c.config.DefaultTTL)
}
```

`SetWithTTL` exists for custom TTLs, but nothing in the non-test codebase calls it directly — the only callers are `Set` itself and the cache's own tests. So users inherit the 10-minute default with no override anywhere.

A few details worth knowing about the user cache specifically, in `store/user.go`:

- Keys are just the stringified user ID (`userCacheKey`, line 88), so the cache is only consulted on lookups by ID. `GetUser` checks the cache only when `find.ID != nil` (line 149); lookups by username or other filters always hit the database.
- Entries are populated on `CreateUser`, `CreateUserIfNoUsers`, `UpdateUser`, `GetUser`, and on every `ListUsers` call, which warms the cache for each returned user (line 143).
- Invalidation is explicit on delete via `deleteUserCache` in `store/user_delete.go`, which drops the user entry plus its associated user-setting entries.

Two consequences of this design: the 10-minute TTL is a backstop rather than the primary freshness mechanism, since updates and deletes refresh or evict entries immediately. And because the cache is per-process memory with no shared backend, running multiple Memos replicas gives each one its own independent cache with no cross-instance invalidation. Capacity is bounded at 1000 items per cache, with `cleanupOldest` shedding roughly 20% when that limit is exceeded.
