**Premise correction:** There is no Redis in this repository. Grepping the whole tree (excluding `go.sum`) for `redis`, `valkey`, or `memcache` returns zero matches, and `go.mod` has no client library for any external cache. There is also no connection string, host/port, or environment variable for a cache backend anywhere — the cache layer is entirely in-process, in-memory, and lives inside the `Store`.

**Actual mechanism**

The cache implementation is a hand-rolled, thread-safe in-memory cache in `store/cache/cache.go`. It stores entries in a `sync.Map` where each `item` holds the value plus an absolute `expiration` timestamp, with a background goroutine (`cleanupLoop`) sweeping expired entries and a `cleanupOldest` path that evicts roughly 20% of `MaxItems` when the cache grows past its limit.

Configuration happens at store construction rather than in any config file or environment variable. `store.New` builds one `cache.Config` and hands the same values to three separate cache instances:

```40:53:/bench/repo/store/store.go
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
```

**TTL for user entries: 10 minutes.** User entries get no special TTL of their own. Every write in `store/user.go` (`CreateUser`, `CreateUserIfNoUsers`, `UpdateUser`, `ListUsers`, and the read-through in `GetUser`) calls plain `s.userCache.Set(ctx, userCacheKey(user.ID), user)`, and `Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go` lines 93-95). `SetWithTTL` is never called directly by any non-test code, so the 10-minute `DefaultTTL` from `store.New` is the effective user TTL. Note that the same 10-minute default also duplicates the value in `cache.DefaultConfig()` (`store/cache/cache.go` lines 57-64), but `store.New` does not use `DefaultConfig` — it declares its own identical literal.

Two related details worth knowing: the cache key is just the stringified user ID (`userCacheKey` in `store/user.go` line 88-90), so `GetUser` only hits the cache when the lookup is by `ID` — lookups by username or email always fall through to the database. And staleness is bounded by more than the TTL, since mutations write through on update and `deleteUserCache` in `store/user_delete.go` explicitly evicts the user plus their settings entries on deletion.
