**`internal/idp`; `internal/idp/oauth2`**

The abstraction lives in `internal/idp`, which is a deliberately thin package: it only declares the provider-neutral user shape that any identity provider must produce.

```1:8:internal/idp/idp.go
package idp

type IdentityProviderUserInfo struct {
	Identifier  string
	DisplayName string
	Email       string
	AvatarURL   string
}
```

The only concrete protocol implementation is OAuth2, in `internal/idp/oauth2` (`internal/idp/oauth2/oauth2.go`, tested by `internal/idp/oauth2/oauth2_test.go`). It wraps `golang.org/x/oauth2`, supports PKCE via a `codeVerifier` on `ExchangeToken`, and maps the provider's user-info response into `idp.IdentityProviderUserInfo` using the configured field mapping.

Two things confirm OAuth2 is the sole implementation rather than one of several:

- The stored provider type enum has exactly one non-unspecified value, and the config `oneof` has exactly one variant (`proto/store/idp.proto` lines 11-25, mirrored in the API surface at `proto/api/v1/idp_service.proto`). There is no OIDC or SAML variant.
- The only consumer outside the package itself is the SSO login path in `server/router/api/v1/auth_service_sso.go`, which imports both `internal/idp` and `internal/idp/oauth2` directly and hands the resulting `*idp.IdentityProviderUserInfo` to `resolveSSOUser` for account linking or just-in-time user creation.

Note that OIDC providers are still usable in practice, but only by configuring them as generic OAuth2 (authorization URL, token URL, user-info URL, scopes, field mapping); there is no dedicated OIDC discovery or ID-token-validating implementation in the codebase.
