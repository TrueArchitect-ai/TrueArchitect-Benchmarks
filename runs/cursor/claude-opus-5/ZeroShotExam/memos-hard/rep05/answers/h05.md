**Mechanism: explicit Go code.** Reactions are deleted by hand-written `DELETE FROM reaction` statements inside the driver-level `DeleteUser` transaction. There is no database-level cascade, because the `reaction` table has no foreign keys at all.

**What I checked**

The same pair of calls exists in the other two drivers: `store/db/postgres/user_delete.go` (lines 96, 102, 380, 400) and `store/db/mysql/user_delete.go` (lines 96, 102, 417, 437). All three run inside a single transaction that commits only at the end, so a failure rolls the reaction deletes back.

For the database side, the `reaction` table definition in `store/migration/sqlite/LATEST.sql` (lines 92-99), `store/migration/postgres/LATEST.sql` (lines 91-98), and `store/migration/mysql/LATEST.sql` (lines 91-98) declares only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint. `creator_id` and `content_id` are plain columns with no `REFERENCES` clause. Grepping the schemas for `FOREIGN KEY`, `ON DELETE`, and `CREATE TRIGGER` turns up exactly one match per dialect, and it is `memo_share.memo_id REFERENCES memo(id) ON DELETE CASCADE` — nothing touching `reaction`. The original table creation in `store/migration/*/0.20/00__reaction.sql` is likewise FK-free.
