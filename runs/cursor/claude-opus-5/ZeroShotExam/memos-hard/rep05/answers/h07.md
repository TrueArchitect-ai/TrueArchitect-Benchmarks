The image URL the browser loads is not the raw data URI: `convertUserFromStore` rewrites a base64 avatar into the path `/file/users/{username}/avatar` (`server/router/api/v1/user_service_converters.go:31-40`), and `UserAvatar` renders that as an `<img src>` (`web/src/components/UserAvatar.tsx:14`). That GET then travels this path:

`RegisterRoutes` (route `GET /file/users/:identifier/avatar`) — server/router/fileserver/fileserver.go:121-125 (wired in server/server.go:81-82)
`(*FileServerService).serveUserAvatar` — server/router/fileserver/fileserver.go:168-210
`(*FileServerService).getCurrentUser` → `(*auth.Authenticator).AuthenticateToUser` — server/router/fileserver/fileserver.go:708-712 (only when the instance disallows anonymous access)
`(*FileServerService).getUserByUsername` — server/router/fileserver/fileserver.go:715-717
`(*Store).GetUser` (checks `userCache`, declared at store/store.go:28) — store/user.go:148-169
`(*Store).ListUsers` — store/user.go:136-146
`(*DB).ListUsers` (driver; `SELECT ... avatar_url ... FROM user WHERE username = ?`) — store/db/sqlite/user.go:88-205, with MySQL and PostgreSQL equivalents in store/db/mysql/user.go and store/db/postgres/user.go

The bytes themselves live in the `user.avatar_url` column as a `data:<mime>;base64,...` URI. Back in the handler, `(*FileServerService).parseDataURI` (server/router/fileserver/fileserver.go:737-750) splits the MIME type and decodes the base64, the type is checked against `avatarAllowedTypes`, and the decoded bytes go out via `c.Blob` with `Cache-Control: public, max-age=3600`. There is no filesystem or S3 hop for avatars — unlike attachments, they are served straight from the database row.
