Neither. The premise of the question is incorrect: this repository (Memos) has no external message broker at all. There is no NATS or RabbitMQ dependency in `go.mod`, and the only "rabbit" match anywhere in the tree is the CodeRabbit sponsor blurb in `README.md`. Webhook delivery is entirely in-process.

The actual mechanism is a buffered Go channel serving as the queue, declared as a package-level variable in `internal/webhook/webhook.go`:

```39:40:internal/webhook/webhook.go
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
)
```

The "workers" are four goroutines started from that package's `init()`, each ranging over the channel and calling `Post` for every payload, logging a warning on failure:

```42:55:internal/webhook/webhook.go
func init() {
	for range 4 {
		go func() {
			for payload := range asyncPostQueue {
				if err := Post(payload); err != nil {
					slog.Warn("Failed to dispatch webhook asynchronously", ...)
				}
			}
		}()
	}
}
```

Enqueueing happens in `PostAsync` (same file, lines 184–196), which does a non-blocking `select` send and drops the payload with a warning if the 128-slot buffer is full — so delivery is best-effort with no persistence, retries, or acknowledgements, and anything queued is lost on process restart.

Producers call `webhook.PostAsync` from the API layer, specifically `server/router/api/v1/memo_service_webhooks.go`, which loads a user's webhooks via `s.Store.GetUserWebhooks` and enqueues one payload per hook for activity types like `memos.memo.created`, `memos.memo.updated`, `memos.memo.deleted`, and `memos.memo.comment.created`. `Post` itself sends a plain HTTP POST through a shared `http.Client` whose transport blocks reserved and private IPs to prevent SSRF, and optionally adds Standard Webhooks HMAC-SHA256 headers when a signing secret is configured.
