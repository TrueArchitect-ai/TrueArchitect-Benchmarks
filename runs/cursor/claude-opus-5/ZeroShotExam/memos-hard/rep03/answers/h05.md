**Mechanism:** explicit Go code. Each database driver's `DeleteUser` implementation runs two `DELETE FROM reaction` statements inside the delete-user transaction — one keyed on the deleted user's memo content IDs (so other people's reactions on the removed memos go away too) and one keyed on `creator_id` (so the user's own reactions on memos that survive go away). There is no foreign key, `ON DELETE CASCADE`, or trigger on the `reaction` table in any of the three schemas, so nothing would happen at the database level without this code.

**What I checked to rule out a database-level rule**

The `reaction` table has no foreign key or cascade in any schema — only `creator_id`/`content_id` columns plus a uniqueness constraint (`store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`), and it was created that way originally in `store/migration/sqlite/0.20/00__reaction.sql` and its postgres/mysql counterparts. Grepping the migration tree for `FOREIGN KEY`, `ON DELETE CASCADE`, and `TRIGGER` turns up cascades only for other tables, and the historical user cascades were dropped by `store/migration/sqlite/0.7/00__remove_fk.sql` and `01__remove_triggers.sql`. The only surviving cascade in `LATEST.sql` is `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109`).
