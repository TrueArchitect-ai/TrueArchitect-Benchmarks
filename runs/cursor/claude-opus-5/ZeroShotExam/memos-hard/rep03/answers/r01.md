**Premise correction:** There is no Redis anywhere in this repository. A case-insensitive search across every file (excluding `.git` and `node_modules`) returns zero matches for "redis" — no client dependency in `go.mod`, no connection string, no env var, no docker-compose service. The cache layer is a hand-rolled, in-process, in-memory cache with no external server or connection to configure.

**Actual mechanism:**

The cache implementation lives in `store/cache/cache.go`. It's a thread-safe in-memory cache built on `sync.Map` plus an `atomic.Int64` item counter, with a background goroutine (`cleanupLoop`) that periodically evicts expired entries.

Because the cache is per-process memory, "configuration" means constructing a `cache.Config` struct rather than dialing a server. That happens in exactly one place, `store.New` in `store/store.go`:

```40:53:/bench/repo/store/store.go
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
```

**TTL for user entries: 10 minutes.** All three caches (instance settings, users, user settings) share the identical config, so users get the same 10-minute `DefaultTTL` as everything else. Every write path in `store/user.go` calls the plain `Set` method — `CreateUser` (line 98), `CreateUserIfNoUsers` (line 122), `UpdateUser` (line 132), `ListUsers` (line 143), and `GetUser` (line 167) — and `Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go` line 94). Nothing in the user code path calls `SetWithTTL` directly, so there is no user-specific TTL override.

Two details worth knowing since they affect behavior more than the TTL does:

- Expiration is lazy plus swept. `Get` checks `time.Now().After(itm.expiration)` on read and deletes the entry, and the `CleanupInterval` sweep runs every 5 minutes, so an entry can survive in memory up to ~5 minutes past its nominal expiry until it is read or swept.
- The 1000-item `MaxItems` cap will often evict user entries well before the 10-minute TTL. `cleanupOldest` drops 20% of `MaxItems` at once when the cap is exceeded.

Also note the cache is only consulted on lookup by ID — `GetUser` checks `userCache` only when `find.ID != nil` (`store/user.go` lines 149-156); lookups by username or other fields always hit the database. Invalidation on delete is in `store/user_delete.go` (lines 40-45), and the caches are shut down in `Store.Close` (`store/store.go` lines 74-76).

The TTL values are hardcoded constants with no env var or config-file override; `cache.DefaultConfig()` in `store/cache/cache.go` (lines 57-64) declares the same 10m/5m/1000 values but is unused by the store, which builds its own identical literal.
