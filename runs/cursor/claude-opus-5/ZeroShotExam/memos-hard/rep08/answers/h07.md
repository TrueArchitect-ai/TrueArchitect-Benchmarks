Avatars are stored as base64 data URIs in the `user.avatar_url` column, so the "image request" is really a user row lookup that gets decoded and blobbed back. The chain:

`UserAvatar` (`<img src={avatarUrl}>`) — `web/src/components/UserAvatar.tsx`
`convertUserFromStore` (rewrites the data URI to `/file/users/{username}/avatar`) — `server/router/api/v1/user_service_converters.go`
`FileServerService.RegisterRoutes` (`GET /file/users/:identifier/avatar`, wired at `server/server.go:81-82`) — `server/router/fileserver/fileserver.go`
`FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go`
`FileServerService.getCurrentUser` → `Authenticator.AuthenticateToUser` (only when `Profile.AllowAnonymous()` is false) — `server/router/fileserver/fileserver.go`, `server/auth/authenticator.go`
`FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go`
`Store.GetUser` — `store/user.go`
`Store.ListUsers` — `store/user.go`
`Driver.ListUsers` (interface) — `store/driver.go`
`DB.ListUsers` (`SELECT ... avatar_url ... FROM user WHERE username = ?`) — `store/db/sqlite/user.go`, `store/db/mysql/user.go`, `store/db/postgres/user.go`
`FileServerService.parseDataURI` (base64-decodes the stored URI, then `c.Blob`) — `server/router/fileserver/fileserver.go`

Two details worth noting. The `userCache` in `Store.GetUser` is only consulted when the find has an `ID`; this path passes `Username`, so every avatar request goes through `ListUsers` to the driver and only populates the cache afterward. And the MIME type from the stored data URI is checked against `avatarAllowedTypes` in `server/router/fileserver/fileserver.go` before serving.

There is also a `/memos.api.v1.UserService/GetUserAvatar` entry in `server/router/api/v1/acl_config.go`, but no Go implementation of that RPC exists in `server/`, so browser traffic uses the `/file/...` route above.
