The premise is incorrect: this repository (the Memos server) has no per-user API rate-limiting middleware at all, so there is nothing registered and no request limits to report. A search across the Go server, frontend, protos, and configs turns up no rate limiter, no throttling logic, no HTTP 429 responses, and no rate-limiting dependency in `go.mod` (the only hits are aspirational notes in `internal/email/README.md` and `internal/email/doc.go`, which suggest adding rate limiting to email sending as a future improvement).

What actually is registered on the request path:

- Echo-level middleware in `server/server.go` (lines 51–52): only `middleware.Recover()` and `newCORSMiddleware(profile)` from `server/cors.go`.
- Connect RPC interceptors in `server/router/api/v1/v1.go` (lines 133–137): `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor`, all defined in `server/router/api/v1/connect_interceptors.go` and `server/router/api/v1/auth_interceptor.go`-style files. The gRPC-gateway path gets a similar auth-only middleware at `server/router/api/v1/v1.go` line 69.

The closest thing to a "limit" in the API layer is a request *size* cap, not a request *rate* cap:

```20:20:server/router/api/v1/v1.go
const maxAPIRequestBytes = 256 << 20
```

It is applied via `http.MaxBytesHandler` for the gateway and Connect mux, and via `connect.WithReadMaxBytes` for Connect handlers (`server/router/api/v1/v1.go` lines 126, 141, 144), capping each request body at 256 MiB. Per-user throttling, if needed, would have to be added — today it does not exist in this codebase.
