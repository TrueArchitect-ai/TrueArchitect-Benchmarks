**Mechanism: explicit Go code.** Reaction rows are deleted by hand-written `DELETE FROM reaction` statements inside each driver's `DeleteUser` transaction — there is no foreign key, cascade, or trigger on the `reaction` table.

**What I checked**

- Call path: `server/router/api/v1/user_service.go:414` calls `store.DeleteUser`, which at `store/user.go:171-172` delegates straight to `s.driver.DeleteUser` (interface declared at `store/driver.go:48`). The shared file `store/user_delete.go` only holds the result struct, a test failpoint, and cache invalidation — no SQL.
- All three drivers implement the same two deletes: `store/db/sqlite/user_delete.go`, `store/db/mysql/user_delete.go:96,102,417,437`, and `store/db/postgres/user_delete.go:96,102,380,400`.
- Schema: the `reaction` table in `store/migration/sqlite/LATEST.sql:91-99` (and the mysql/postgres equivalents at line 90-97 of each) has `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` with only a uniqueness constraint — no `REFERENCES`. Grepping all three `LATEST.sql` files for foreign keys turns up exactly one cascade, `memo_share.memo_id → memo(id)`, which is unrelated. A `content_id` foreign key isn't even possible here since it stores a resource name string like `memos/<uid>` rather than a memo ID. Triggers only ever existed for modification timestamps and were dropped in `store/migration/sqlite/0.7/01__remove_triggers.sql`.
- Tests confirm the intent and the scoping: `server/router/api/v1/test/user_service_delete_test.go:287-298` asserts reactions on the deleted user's memos and comments are gone while a peer's reaction on a foreign memo survives, and lines 429-431 verify a reaction is still present after a rolled-back delete, showing the deletes are transactional.
