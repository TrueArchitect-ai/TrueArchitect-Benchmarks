**Premise correction:** There is no Redis anywhere in this repository — no Redis client, no connection string, no config option. A case-insensitive search across all source, config, and dependency files (including `go.mod`/`go.sum`) returns zero matches. The cache layer is a hand-rolled, in-process, in-memory cache, so there is nothing to connect to and no external cache server involved.

**Actual mechanism:** The cache implementation lives in `store/cache/cache.go`. It's a thread-safe map-based cache built on `sync.Map` plus an `atomic.Int64` item counter, with per-entry absolute expiration timestamps and a background goroutine that periodically sweeps expired entries:

```66:73:/bench/repo/store/cache/cache.go
// Cache is a thread-safe in-memory cache with TTL and memory management.
type Cache struct {
	itemCount  atomic.Int64 // Use atomic operations to track item count
	data       sync.Map
	config     Config
	stopChan   chan struct{}
	closedChan chan struct{}
}
```

The "configuration" you're looking for is the `cache.Config` struct literal constructed in `store.New` in `store/store.go`, which is where the three caches (instance settings, users, and user settings) are instantiated:

**TTL for user entries: 10 minutes.** All three caches share that same config, so users get the same `DefaultTTL` as instance settings and user settings. There is no user-specific override: `store/user.go` always uses the plain `Set` method (for example at lines 98, 122, 132, 143, and 167), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go` line 94). `SetWithTTL` exists on the interface but is never called with a custom duration anywhere in non-test code, so 10 minutes is the effective TTL for every cached entity.

Two details worth knowing about the eviction behavior:

- Expiration is lazy plus swept. `Get` checks `time.Now().After(itm.expiration)` and evicts on read, and `cleanupLoop` sweeps every 5 minutes, so a stale user can linger in the map up to 5 minutes past its TTL until it's read or swept.
- The 1000-item `MaxItems` cap triggers `cleanupOldest`, which drops roughly 20% of capacity. Because entries all share one TTL, expiration time is effectively insertion order, so this approximates oldest-first eviction. Note that user entries are keyed only by user ID (`userCacheKey` is `strconv.Itoa`, `store/user.go` line 88) and each cache is a separate `Cache` instance, so the three caches don't contend for the same 1000-item budget.

Invalidation is explicit rather than TTL-driven for the paths that matter: `store/user_delete.go` calls `deleteUserCache` to purge the user entry and its associated user-setting keys on deletion, and `UpdateUser` overwrites the cached entry immediately.

Separately, if you were thinking of a different cache: `server/router/api/v1/instance_stats.go` has an unrelated single-value mutex-guarded memo cache for instance stats with its own `instanceStatsCacheTTL` of 60 seconds. That one is independent of the store cache layer and doesn't hold user entries. There's also a frontend cache in `web/src/components/MemoEditor/services/cacheService.ts`, which is browser-side draft persistence and likewise unrelated.
