The derived metadata is the memo's **payload** (`tags` plus the calculated `property` block), computed by `memopayload.RebuildMemoPayload`, which delegates the actual parsing to the goldmark-backed markdown service.

**Computation site.** `RebuildMemoPayload` in `server/runner/memopayload/runner.go` (lines 74-88) ensures `memo.Payload` exists, calls `markdownService.ExtractAll([]byte(memo.Content))`, and assigns `Payload.Tags` and `Payload.Property` from the result. The real work happens in `service.ExtractAll` in `internal/markdown/markdown.go` (lines 356-422), which parses the content once and walks the AST in a single pass. (`ExtractTags` and `ExtractProperties` in the same file are the equivalent single-purpose variants.) The markdown service is constructed with the tag and mention extensions in `server/router/api/v1/v1.go:48`.

**Triggers.** Only two call sites in production code, both in `server/router/api/v1/memo_service.go`:

- `CreateMemo` — line 108, on every memo creation, before the store insert. Note that user-supplied `location` is written into the payload *after* the rebuild (line 112), so it is not clobbered.
- `UpdateMemo` — line 447, but only inside the `path == "content"` branch of the update mask loop; the freshly built payload is then put on `update.Payload` (line 451). Updating visibility, pinned state, timestamps, etc. does not recompute anything.

There is also a batch rebuild-everything path, `Runner.RunOnce` in `server/runner/memopayload/runner.go` (lines 27-72), which pages through all memos 100 at a time and rewrites each payload — but `memopayload.NewRunner` is never called anywhere in the repo, so it is currently unwired maintenance code rather than an active trigger.

**Extracted properties.** From `ExtractAll` and the schema in `proto/store/memo.proto`:

- `tags` — text of every `#tag` node not nested inside a link or image (`asMemoTagNode`), deduplicated with case preserved.
- `property.title` — plain text of the first block-level child of the document, only if it is an H1 heading (`extractHeadingText`).
- `property.has_link` — true if any `KindLink` node is present.
- `property.has_code` — true for code blocks, fenced code blocks, or inline code spans.
- `property.has_task_list` — true if any GFM task checkbox exists.
- `property.has_incomplete_tasks` — true if any of those checkboxes is unchecked.

`ExtractedData` also collects lowercased `Mentions`, but `RebuildMemoPayload` discards them; they are not persisted on the memo.

Two related things that are *not* part of this payload: the `snippet` shown in lists and relation previews is generated on the fly per request via `getMemoContentSnippet` (`server/router/api/v1/memo_service_webhooks.go:83`, 64-char limit through `GenerateSnippet`), and `payload.location` is user-set. The stored property block is surfaced to the API by `convertMemoPropertyFromStore` (`server/router/api/v1/memo_service_converter.go:315`) and aggregated for user stats in `server/router/api/v1/user_service_stats.go`.
