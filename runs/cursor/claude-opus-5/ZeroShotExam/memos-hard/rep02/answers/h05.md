**Mechanism: explicit Go code.** Reactions are removed by hand-written `DELETE FROM reaction` statements inside the per-driver `DeleteUser` transaction. There is no database-level cascade or trigger that could do it, because the `reaction` table has no foreign keys at all.

**How the deletion happens**

The API handler at `server/router/api/v1/user_service.go:414` calls `s.Store.DeleteUser`, which delegates straight to the active driver (`store/user.go:171-181`). Each driver's `DeleteUser` opens one transaction and runs an ordered list of deletes, two of which target reactions:

```96:104:store/db/sqlite/user_delete.go
	if err := deleteReactionsByContentIDsTx(ctx, tx, contentIDs); err != nil {
		return err
	}
	if err := deleteAttachmentsByIDsTx(ctx, tx, targets.attachmentIDs); err != nil {
		return err
	}
	if err := deleteReactionsByCreatorTx(ctx, tx, userID); err != nil {
		return err
	}
```

Those two helpers cover both directions of ownership, which matters because a reaction row links a creator to a memo by string content ID rather than by a memo foreign key:

- `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-388`) removes *everyone's* reactions on the deleted user's memos. The content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + uid` values (line 512-518) from the recursive memo tree query at lines 133-166, so comments under the user's memos are included too.
- `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`) removes the deleted user's own reactions on memos belonging to other people.

The same two statements exist in the other two drivers: `store/db/postgres/user_delete.go:383` and `:401`, and `store/db/mysql/user_delete.go:420` and `:438`.

**Why it can't be a database rule**

The `reaction` table is declared with no foreign key and no `ON DELETE` clause in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`, and likewise in the original creating migration `store/migration/sqlite/0.20/00__reaction.sql`. Grepping the whole `store/migration` tree for `FOREIGN KEY`, `REFERENCES`, `ON DELETE`, and `TRIGGER` turns up cascades only for `memo_share`, `user_setting`, `memo_relation`, and similar tables, never `reaction`. Two further points reinforce this: SQLite is opened with foreign keys disabled outright (`store/db/sqlite/sqlite.go:53`, `_pragma=foreign_keys(0)`), and a cascade would be structurally impossible for the content-ID side anyway since `content_id` is free-form text, not a memo reference.

**Tests that pin the behavior**

`server/router/api/v1/test/user_service_delete_test.go:287-298` asserts that reactions on the deleted user's own memo and on their comment are empty afterward, while a peer's reaction on an unrelated foreign memo survives. `store/test/user_delete_test.go:217-220` makes the same store-level assertion. Lines 366-431 of the service test confirm that with the `before_commit` failpoint the reaction is still present, verifying the deletes are transactional rather than incidental.
