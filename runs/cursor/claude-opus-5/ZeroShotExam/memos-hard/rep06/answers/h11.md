**1st: `User` (~7 packages); 2nd: `Memo` (~6 packages)**

The data layer here is the `store` package (`/bench/repo/store/`), whose persistent entity structs are `User`, `Memo`, `Attachment`, `Inbox`, `MemoRelation`, `MemoShare`, `Reaction`, `UserSetting`, `UserIdentity`, `IdentityProvider`, and `InstanceSetting`. Counting the distinct Go packages outside the `store/` tree (including `store/db/*` and `store/test`, which are part of that layer) that name each type:

| Type | External packages | Raw references |
| --- | --- | --- |
| `store.User` (`store/user.go:29`) | 7 | 99 |
| `store.Memo` (`store/memo.go:35`) | 6 | 73 |
| `store.Attachment` (`store/attachment.go:16`) | 4 | 43 |

`User` is referenced from `server/auth`, `server/notification`, `server/router/api/v1`, `server/router/api/v1/test`, `server/router/fileserver`, `server/router/frontend`, and `server/router/rss`. `Memo` is referenced from `server/notification`, `server/router/api/v1`, `server/router/api/v1/test`, `server/router/frontend`, `server/router/rss`, and `server/runner/memopayload`.

The distinguishing packages are worth noting: `User` reaches into `server/auth` (`server/auth/authenticator.go`, `server/auth/context.go`) because authentication resolves the current user, while `Memo` instead reaches `server/runner/memopayload`, which post-processes memo payloads. Both share the API, RSS, frontend, and notification packages.

Two caveats on methodology. If you exclude the dedicated test package `server/router/api/v1/test`, the counts become 6 and 5 respectively, so the ranking is unchanged. Also, `IdentityProvider`, `InstanceSetting`, and `UserSetting` initially appear to have external references in `proto/gen/store`, but those are protobuf descriptor strings like `memos.store.IdentityProvider` inside generated files, not real Go references; outside `store/` those entity structs are only reached through their query parameter types such as `store.FindUserSetting`.
