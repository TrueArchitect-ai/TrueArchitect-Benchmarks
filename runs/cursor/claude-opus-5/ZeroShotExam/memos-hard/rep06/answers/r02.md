The premise is incorrect: this repository has no per-user API rate-limiting middleware, so there is no registration site and no request limits to report. Rate limiting is only mentioned as an unimplemented suggestion in documentation — `internal/email/README.md` (line 286, "### 5. Implement Rate Limiting", in a sample code snippet) and `internal/email/doc.go` (line 86, a bullet recommending you "Rate limit email sending to prevent abuse"). Neither is wired into the server. There's also no rate-limiter dependency in use; `golang.org/x/time` appears in `go.mod` only as an indirect dependency.

What actually is registered on the HTTP stack, in `server/server.go`, is `middleware.Recover()` and the CORS middleware from `server/cors.go` (lines 51-52). The API layer in `server/router/api/v1/v1.go` adds a gRPC-Gateway auth middleware (line 69) and four Connect interceptors (lines 133-138): metadata, logging, recovery, and auth. None of them count requests per user.

The only request "limits" that exist are size and concurrency caps, not rate limits:

- `maxAPIRequestBytes = 256 << 20` (256 MiB) in `server/router/api/v1/v1.go` line 20, applied via `http.MaxBytesHandler` to the gateway and Connect muxes and via `connect.WithReadMaxBytes` (lines 126, 141, 144).
- `MaxUploadBufferSizeBytes = 32 << 20` (32 MiB) in `server/router/api/v1/attachment_service.go` line 27, used as the upload size limit at line 122.
- `maxConcurrentThumbnails = 3` in `server/router/fileserver/fileserver.go` line 46, enforced globally with a semaphore (line 116), not per user.

If you want per-user throttling, it would need to be added — most naturally as a new Connect interceptor alongside the ones in `server/router/api/v1/v1.go`, keyed off the user from the auth context in `server/auth/context.go`.
