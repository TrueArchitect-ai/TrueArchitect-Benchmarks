**How I determined it among the candidates**

There are three identically-named candidates — `store/db/sqlite/memo.go:16`, `store/db/mysql/memo.go:16`, and `store/db/postgres/memo.go:16` — each a method on its package's `DB` type satisfying the `store.Driver` interface. Text search alone can't pick the winner, and it's actively misleading here: the only literal `"INSERT INTO memo"` string in the memo path belongs to the *Postgres* driver, because SQLite and MySQL backtick-quote the table name. The selection is a runtime interface dispatch, not a static call edge, so I resolved it by tracing configuration rather than the call graph:

1. **Default config.** With no flags, the driver comes from viper, which defaults to `sqlite` in both the default and the flag definition (`cmd/memos/main.go:122` and `:130`). Only `MEMOS_DRIVER` (via `viper.SetEnvPrefix("memos")` + `AutomaticEnv`, `cmd/memos/main.go:167-169`) or `--driver` could change it, and a default install sets neither. `profile.Validate` then confirms SQLite is the default-path assumption by auto-deriving a DSN of `<data>/memos_prod.db` only when `Driver == "sqlite"` (`internal/profile/profile.go:110-117`).
2. **Driver construction.** `db.NewDBDriver` switches on `profile.Driver` and returns `sqlite.NewDB(profile)` for that value (`store/db/db.go:18-27`), so the interface value stored in the app is concretely `*sqlite.DB` (`store/db/sqlite/sqlite.go`).
3. **No intervening layer.** `store.New` stores the driver as-is with no decorator or cache wrapper around it (`store/store.go:38-61`; the caches there cover only instance settings, users, and user settings), and `Store.CreateMemo` validates the UID then delegates straight through to `s.driver.CreateMemo` (`store/memo.go:109-114`). The API handler `APIV1Service.CreateMemo` calls that store method (`server/router/api/v1/memo_service.go:114`).
4. **Ruled out compile-time swaps.** `grep` for `go:build` across `store/`, `internal/`, and `cmd/` returned nothing, and the `sqlite` package defines `CreateMemo` exactly once, so no build tag or duplicate definition can substitute a different implementation.

One caveat on method: I verified this statically only. There's no Go toolchain in this environment (`go version` → command not found), so I could not run the server or a reflection probe to print the concrete type at runtime as a cross-check.
