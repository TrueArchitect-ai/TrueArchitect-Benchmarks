The browser never fetches avatar bytes over the API; the user API replaces base64 avatars with a `/file/users/{username}/avatar` URL, and a native Echo handler in the file server reads that user row from the store.

On the way back, `serveUserAvatar` decodes `user.AvatarURL` via `FileServerService.parseDataURI` (server/router/fileserver/fileserver.go:737), rejects MIME types outside `avatarAllowedTypes` (fileserver.go:75), and writes the bytes with `c.Blob` plus a one-hour `Cache-Control`. Note the avatar is stored inline as a base64 data URI in the `user.avatar_url` column (added by store/migration/sqlite/0.11/00__user_avatar.sql), so there is no blob/S3 hop as with attachments. If the stored value is not a data URI, the converter passes it through unchanged and the browser fetches it from that external URL instead, bypassing this path entirely.
