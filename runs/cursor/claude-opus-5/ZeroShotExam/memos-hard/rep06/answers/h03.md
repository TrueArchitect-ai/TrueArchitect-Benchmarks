**`internal/idp`; `internal/idp/oauth2`**

The abstraction lives in `internal/idp/idp.go`, which is a deliberately thin package defining only the provider-neutral user shape that any identity provider must produce:

```3:8:internal/idp/idp.go
type IdentityProviderUserInfo struct {
	Identifier  string
	DisplayName string
	Email       string
	AvatarURL   string
}
```

The one concrete protocol implementation that ships is OAuth2, in `internal/idp/oauth2/oauth2.go`. It wraps `golang.org/x/oauth2`, is constructed from a `storepb.OAuth2Config` via `NewIdentityProvider`, and exposes `ExchangeToken` (with optional PKCE `code_verifier` support) plus `UserInfo`, which maps arbitrary provider claims onto `idp.IdentityProviderUserInfo` using the configured `FieldMapping`.

Both packages are consumed only by the SSO login path in `server/router/api/v1/auth_service_sso.go`, which imports `internal/idp` and `internal/idp/oauth2` and nothing else provider-related. There is no SAML, LDAP, or dedicated OIDC implementation in the tree — OIDC-style providers are handled through the same generic OAuth2 provider by pointing `authUrl`/`tokenUrl`/`userInfoUrl` at the provider's endpoints. Note that the abstraction is a shared data type rather than a Go interface; there is no `IdentityProvider` interface that implementations satisfy, so adding a second protocol would require touching the SSO handler directly.
