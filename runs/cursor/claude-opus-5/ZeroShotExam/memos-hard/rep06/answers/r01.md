**Premise correction:** There is no Redis anywhere in this repository. Nothing named `redis` appears in any source file, and `go.mod`/`go.sum` contain no Redis (or Memcached/Valkey) client dependency. So there is no Redis connection to configure — no host, port, DSN, or connection-pool settings exist, and there is no environment variable or config flag to point the cache at an external server.

**Actual mechanism:** The cache layer is a process-local, in-memory cache implemented from scratch in `store/cache/cache.go`. It's a `sync.Map` guarding `item` structs that each carry an absolute `expiration` timestamp, with an `atomic.Int64` item counter and a background goroutine (`cleanupLoop`) that sweeps expired entries on a ticker. Because it lives inside the Go process heap, the cache is not shared across instances and is lost on restart.

Configuration happens in code at store construction, not in a config file. `store.New` builds a `cache.Config` literal and creates three separate cache instances from it:

```40:53:/bench/repo/store/store.go
	// Default cache settings
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
```

**TTL for user entries: 10 minutes.** Users are stored in `userCache` exclusively via `Set` (in `CreateUser`, `CreateUserIfNoUsers`, `UpdateUser`, `ListUsers`, and `GetUser` in `store/user.go`), keyed by the stringified user ID from `userCacheKey`. `Set` always delegates to `SetWithTTL` using `c.config.DefaultTTL`, and `SetWithTTL` is never called directly outside the cache package's own test, so users get no TTL of their own — they inherit the same 10-minute default as instance settings and user settings.

Two details worth knowing beyond the raw TTL:

- Expiry is not the only way a user entry disappears. `MaxItems: 1000` triggers `cleanupOldest`, which drops roughly 20% of entries once the count is exceeded, so a busy instance can evict users well before 10 minutes. Deletes also invalidate explicitly through `deleteUserCache` in `store/user_delete.go`, and every write path re-`Set`s the user, which refreshes the expiration.
- The 10-minute value is hardcoded twice: once in the `store.New` literal above and once in `cache.DefaultConfig()` at `store/cache/cache.go:59`. The store does not call `DefaultConfig()`/`NewDefault()`, so changing the TTL requires editing `store/store.go` — editing only `DefaultConfig` would have no effect on the user cache.
