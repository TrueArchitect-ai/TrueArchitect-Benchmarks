h15.

Memo visibility is not centralized in one guard — each surface that can expose memo content applies its own check. Here is every distinct enforcement site I found.

Core memo read paths (gRPC/Connect API):

`checkMemoReadAccess` shared read gate (archived-only-to-creator, private-only-to-creator, protected requires auth); called by `GetMemo` and `ListMemoComments` — `server/router/api/v1/memo_service.go` (lines 39–68, 356, 367) and `server/router/api/v1/memo_service_comments.go:148`
`ListMemos` query scoping: anonymous gets `VisibilityList = [PUBLIC]`, authenticated gets a CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` — `server/router/api/v1/memo_service.go` (lines 218–227)
`CreateMemoComment` pre-check plus comment-list visibility filter — `server/router/api/v1/memo_service_comments.go` (lines 41–43, 156–161)
Memo relation expansion filter (hides related/linked memos the viewer can't see) — `server/router/api/v1/memo_service_converter.go` (lines 182–187) and `server/router/api/v1/memo_relation_service.go` (lines 107–112)
Reaction read and write checks — `server/router/api/v1/reaction_service.go` (lines 30–41, 83–85)
Memo attachment listing check — `server/router/api/v1/memo_attachment_service.go` (lines 213–225)
Attachment API access check `checkAttachmentAccess` — `server/router/api/v1/attachment_service.go` (lines 419–455)
User memo-stats scoping — `server/router/api/v1/user_service_stats.go` (lines 78–90, 216–220)
Share-token resolution, the deliberate bypass of visibility gated on token validity and expiry instead — `server/router/api/v1/memo_share_service.go` (`GetMemoByShare`, lines 151–208)

Non-gRPC HTTP surfaces:

Raw file/attachment blob serving `checkAttachmentPermission`, including anonymous-instance rule and `share_token` fallback — `server/router/fileserver/fileserver.go` (lines 649–704)
RSS feeds (explore and per-user) restricted to `VisibilityList = [PUBLIC]` — `server/router/rss/rss.go` (lines 88–93, 138–144)
`sitemap.xml` restricted to public memos — `server/router/frontend/frontend.go` (lines 149–151)

Push/notification fan-out:

SSE broadcast delivery filter `SSEClient.canReceive` (private events only to creator or admin) — `server/router/api/v1/sse_hub.go` (lines 134–144), with event visibility populated in `server/router/api/v1/sse_event_helpers.go` (lines 29–37)
In-app notification payload gating `canViewerAccessMemo` — `server/router/api/v1/user_service_notifications.go` (lines 302–316, used at 337, 342, 370, 385)
Email notification gating, a second independent copy of `canViewerAccessMemo` — `server/notification/email.go` (lines 306–320, used at 155, 187)
Mention notification eligibility `canUserAccessMentionContext` / `shouldSkipMentionInbox` — `server/router/api/v1/memo_mention_helpers.go` (lines 56–89)

Underlying mechanism (not a policy decision, but where the filters become SQL): `VisibilityList` and the CEL memo filters are translated per-dialect in `store/db/sqlite/memo.go` (line 96), `store/db/postgres/memo.go` (line 89), and `store/db/mysql/memo.go` (line 104), with the field defined in `store/memo.go:69`.

Two things worth flagging: the private/protected logic is duplicated inline in at least five API files rather than routed through `checkMemoReadAccess`, and `canViewerAccessMemo` exists as two separate implementations (`user_service_notifications.go` uses `isSuperUser`, `email.go` checks `store.RoleAdmin` directly), so they can drift.
