**Premise correction:** The question assumes an external message broker, but this repository (Memos — a self-hosted note-taking app, Go backend + React frontend) uses **neither NATS nor RabbitMQ**. There is no message broker of any kind anywhere in the codebase: `go.mod`/`go.sum` contain no NATS, AMQP/RabbitMQ, Kafka, NSQ, or Redis-queue dependencies, and `scripts/compose.yaml` defines only the single `memos` container with no broker service alongside it. Consequently there is no queue declared in the broker sense — no AMQP `queue_declare`/exchange binding, no JetStream stream or subject subscription.

**Actual mechanism:** Webhook delivery is handled entirely in-process by a bounded Go buffered channel drained by a fixed pool of goroutines, all declared in `internal/webhook/webhook.go`. The "queue" is a package-level channel with capacity 128, and four worker goroutines are started in that package's `init()`:

```39:55:/bench/repo/internal/webhook/webhook.go
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
)

func init() {
	for range 4 {
		go func() {
			for payload := range asyncPostQueue {
				if err := Post(payload); err != nil {
					slog.Warn("Failed to dispatch webhook asynchronously",
						slog.String("url", payload.URL),
						slog.String("activityType", payload.ActivityType),
						slog.Any("err", err))
				}
			}
		}()
	}
}
```

Producers enqueue through `PostAsync` in the same file, which does a non-blocking send and **drops the webhook with a warning if the buffer is full** — there is no persistence, retry, or redelivery, which is the main behavioral difference from a real broker:

```182:196:/bench/repo/internal/webhook/webhook.go
func PostAsync(requestPayload *WebhookRequestPayload) {
	if requestPayload == nil {
		slog.Warn("Dropped webhook dispatch because payload is nil")
		return
	}
	select {
	case asyncPostQueue <- requestPayload:
	default:
		slog.Warn("Dropped webhook dispatch because the async queue is full", ...)
	}
}
```

Each worker calls `Post`, which performs a synchronous HTTP POST using a shared `safeClient` whose transport blocks reserved and private IP ranges at dial time to prevent SSRF and DNS rebinding (`internal/webhook/webhook.go` lines 29–37 and 57+). Enqueueing is triggered from the API layer in `server/router/api/v1/memo_service_webhooks.go` for the activity types `memos.memo.created`, `memos.memo.updated`, `memos.memo.deleted`, and `memos.memo.comment.created`, with call sites in `server/router/api/v1/memo_service.go`, `memo_update_helpers.go`, and `memo_service_comments.go`. Webhook endpoints themselves are stored per-user in the database via user settings (`store/user_setting.go`), not registered with any broker.

This channel-plus-goroutine pattern is the repo's general approach to async work rather than a webhook-specific choice — `internal/email/email.go` uses an identical `asyncEmailQueue` channel of capacity 128 with two workers, and the background runners under `server/runner/` are ticker-driven goroutines.
