h15.

Memo visibility is not centralized: each surface re-implements the "public → anyone / protected → any authenticated user / private → creator (plus admin, in most places)" rule inline. Here are the distinct enforcement sites.

**Core API v1 (Connect/gRPC) read gates**

Single-memo read gate (`checkMemoReadAccess`, also covers archived-only-for-creator and re-checks the parent memo) — `server/router/api/v1/memo_service.go:39-68`, called from `GetMemo` at `:356` and `:367`, and from `ListMemoComments` at `server/router/api/v1/memo_service_comments.go:148`

List-query scoping in `ListMemos` (anonymous gets `VisibilityList = [PUBLIC]`; authenticated gets a CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`) — `server/router/api/v1/memo_service.go:218-227`

Comment listing filter, a second independent copy of the same list rule applied through `ListMemoRelations.MemoFilter` — `server/router/api/v1/memo_service_comments.go:156-161`

Comment creation gate (private parent memo blocks commenting; comment inherits parent visibility) — `server/router/api/v1/memo_service_comments.go:33-43,52`

User stats scoping (both `ListAllUserStats` and the per-user variant) — `server/router/api/v1/user_service_stats.go:83-92` and `:217-221`

Reactions: listing and upserting a reaction re-check memo visibility — `server/router/api/v1/reaction_service.go:29-41` and `:82-85`

Memo attachment listing — `server/router/api/v1/memo_attachment_service.go:213-225`

Attachment access via the API service (`checkAttachmentAccess`; unlinked attachments are creator-only, linked ones follow the memo) — `server/router/api/v1/attachment_service.go:419-455`

**Non-gRPC HTTP surfaces**

Raw file/blob serving (`checkAttachmentPermission`) — `server/router/fileserver/fileserver.go:650-704`; note this one also honors an `AllowAnonymous()` profile check for public memos and accepts a `share_token` query param as a bypass

SSE broadcast delivery filter (`SSEClient.canReceive`; private events go only to the creator or an admin, and the endpoint itself requires auth at `server/router/api/v1/sse_handler.go:39-43`) — `server/router/api/v1/sse_hub.go:134-144`

RSS feeds (explore and per-user), restricted to `store.Public` — `server/router/rss/rss.go:88-93` and `:136-144`

Sitemap generation, restricted to `store.Public` — `server/router/frontend/frontend.go:149-151`

**Notification/mention paths (content exposure, same rule)**

Notification payload redaction (`canViewerAccessMemo`) — `server/router/api/v1/user_service_notifications.go:302-316`

A duplicate `canViewerAccessMemo` for outbound email — `server/notification/email.go:306-320`

Mention notification gating (`canUserAccessMentionContext` / `shouldSkipMentionInbox`) — `server/router/api/v1/memo_mention_helpers.go:56-89`

Two things worth flagging. `GetMemoByShare` deliberately bypasses visibility entirely, relying only on token validity and expiry, so a share link is the sanctioned escape hatch (`server/router/api/v1/memo_share_service.go:151-208`). And `store/db/sqlite/memo.go:96`, `store/db/postgres/memo.go:89`, `store/db/mysql/memo.go:104` only translate `FindMemo.VisibilityList` into SQL — the store enforces nothing on its own, so any caller that forgets to set the filter gets unrestricted rows.
