The premise is incorrect: there is no per-user API rate-limiting middleware in this repository, so there are no request limits to report. Nothing in the Go code implements or registers a rate limiter, and `go.mod` pulls in no rate-limiting library (no `golang.org/x/time/rate`, no tollbooth, no `ulule/limiter`).

**Where request handling is actually wired up**

The Echo server registers only two global middlewares:

```51:52:server/server.go
	echoServer.Use(middleware.Recover())
	echoServer.Use(newCORSMiddleware(profile))
```

The API v1 Connect interceptor chain contains four interceptors — metadata, logging, recovery, and auth — and none of them counts or throttles requests:

```133:138:server/router/api/v1/v1.go
	connectInterceptors := connect.WithInterceptors(
		NewMetadataInterceptor(), // Convert HTTP headers to gRPC metadata first
		NewLoggingInterceptor(logStacktraces),
		NewRecoveryInterceptor(logStacktraces),
		NewAuthInterceptor(authorizer),
	)
```

The gRPC-Gateway path is similar: its only middleware is `gatewayAuthMiddleware` (`server/router/api/v1/v1.go`, lines 69–98). The remaining middleware in the tree is static-file serving and SPA fallback in `server/router/frontend/frontend.go`.

The only mentions of rate limiting anywhere are aspirational documentation, not implementation: `internal/email/README.md` (around line 286, "Implement Rate Limiting", with an illustrative `golang.org/x/time/rate` snippet) and a suggestion in `internal/email/doc.go` line 86 to "Rate limit email sending to prevent abuse."

**What limits do exist, in case one of these is what you were thinking of**

These are size and concurrency caps rather than per-user request rates:

| Limit | Value | Location |
| --- | --- | --- |
| Max API request body | 256 MiB | `server/router/api/v1/v1.go` (const at line 20, applied at 126, 141, 144) |
| Attachment upload size | instance setting `UploadSizeLimitMb`, default 32 MiB | `server/router/api/v1/attachment_service.go` lines 27, 120–126 |
| Image pixel cap | 50,000,000 pixels | `server/router/api/v1/attachment_service.go` line 36 |
| Audio transcription size | 25 MiB | `server/router/api/v1/ai_service.go` line 24 |
| Concurrent image (EXIF) processing | 2 | `server/router/api/v1/v1.go` line 60, helper in `server/router/api/v1/attachment_service_image.go` lines 67–78 |
| Concurrent thumbnail generation | 3 | `server/router/api/v1/v1.go` line 59 and `server/router/fileserver/fileserver.go` line 46 |

The image-processing semaphore is the one place that returns a `ResourceExhausted` error with the message "too many image processing requests" (`server/router/api/v1/attachment_service.go` lines 158–161), which can look like rate limiting in logs. It is a global concurrency gate shared across all users, not a per-user rate limit, and it never rejects based on how many requests a given user has made over time.
