**Premise correction:** There is no Redis anywhere in this repository. `grep -ri redis` across the entire tree (excluding `.git`) returns zero matches, and `go.mod` has no Redis client dependency. There is no Redis connection to configure, no connection string, and no cache-related environment variables. The caching layer is a hand-rolled, in-process, in-memory cache that lives and dies with the server process.

**The actual mechanism:** The cache is implemented in `store/cache/cache.go` as a `Cache` struct backed by a `sync.Map` plus an `atomic.Int64` item counter. Entries are stored as an `item` holding the value, an absolute `expiration` timestamp, and a rough size estimate. A background goroutine (`cleanupLoop`) started in `cache.New` sweeps expired entries on a ticker, and `Get` also lazily evicts an entry it finds past expiration.

Configuration happens in Go code, not in any config file. The `Store` constructor builds one `cache.Config` and hands the same settings to three separate cache instances:

```40:53:/bench/repo/store/store.go
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
```

**TTL for user entries: 10 minutes.** Users go into `userCache` exclusively through `Set`, which in `store/cache/cache.go` delegates to `SetWithTTL` using `c.config.DefaultTTL` — and that default is the 10 minutes configured above. Nothing in the codebase calls `SetWithTTL` with a custom duration outside of `store/cache/cache_test.go`, so users get no special TTL treatment; they share the identical policy as instance settings and user settings. Note that `cache.DefaultConfig()` in `store/cache/cache.go` independently declares the same 10-minute/5-minute/1000-item values, but the store does not call it — it duplicates the literals.

Two caveats worth knowing about the effective lifetime of user entries. First, the TTL is a hard expiry from write time, not a sliding window: `SetWithTTL` computes `time.Now().Add(ttl)` and `Get` never extends it, so a frequently read user is still evicted 10 minutes after its last write. However, `GetUser` falls through to `ListUsers` on a miss, and `ListUsers` re-`Set`s every returned user (`store/user.go` lines 136–146), so the entry is transparently repopulated. Second, the 1000-item cap can evict users well before 10 minutes: `SetWithTTL` calls `cleanupOldest` once the count exceeds `MaxItems`, dropping roughly 20% of entries.

Explicit invalidation exists alongside the TTL: writes refresh the entry (`CreateUser`, `UpdateUser`, `GetUser` in `store/user.go`), and `deleteUserCache` in `store/user_delete.go` removes the user key plus its associated user-setting keys.

One unrelated cache to avoid confusion: `server/router/api/v1/instance_stats.go` defines `instanceStatsCacheTTL = 60 * time.Second`, a separate mutex-guarded single-value memo for instance stats. That 60-second TTL does not apply to user entries.
