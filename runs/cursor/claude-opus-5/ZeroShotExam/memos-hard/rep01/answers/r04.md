**Premise correction:** Neither. This repository (memos) has no external message broker at all — there is no NATS, RabbitMQ, AMQP, or Kafka dependency in `go.mod`, and no broker client code anywhere in the tree. Webhook delivery is entirely in-process.

**Actual mechanism:** The "queue" is a plain buffered Go channel with a fixed capacity of 128, declared as a package-level variable in `internal/webhook/webhook.go`:

```39:40:/bench/repo/internal/webhook/webhook.go
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
)
```

The "workers" are four goroutines started from that package's `init()` function, each ranging over the same channel and calling `Post` for every payload; failures are logged with `slog.Warn` and dropped (no retry, no dead-letter):

```42:55:/bench/repo/internal/webhook/webhook.go
func init() {
	for range 4 {
		go func() {
			for payload := range asyncPostQueue {
				if err := Post(payload); err != nil {
					slog.Warn("Failed to dispatch webhook asynchronously", ...)
				}
			}
		}()
	}
}
```

Enqueueing happens in `PostAsync` (`internal/webhook/webhook.go`, lines 184–196) via a non-blocking `select` with a `default` branch, so when the channel is full the payload is discarded outright with a "Dropped webhook dispatch because the async queue is full" warning rather than applying backpressure to the caller.

Producers are the API layer: `server/router/api/v1/memo_service_webhooks.go` looks up the user's registered webhooks via `s.Store.GetUserWebhooks` and calls `webhook.PostAsync` for each one on memo created/updated/deleted and comment-created events.

Two practical consequences of this being a channel rather than a broker: the queue lives only in the server process's memory, so anything pending is lost on restart, and delivery is not durable or retried. `Post` itself does the actual HTTP dispatch through a shared `http.Client` whose transport blocks connections to reserved/private IPs (SSRF protection) and optionally adds Standard Webhooks HMAC-SHA256 signature headers.
