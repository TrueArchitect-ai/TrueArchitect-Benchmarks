**Mechanism: explicit Go code.** Reactions are removed by hand-written `DELETE FROM reaction` statements inside the store-layer `DeleteUser` transaction, not by any foreign key or cascade — the `reaction` table has no foreign keys at all.

Two separate deletes run, so both directions are covered:

- Reactions *the deleted user left anywhere* — deleted by `creator_id`.
- Reactions *anyone left on the deleted user's memos* (including comment memos in the user's memo tree) — deleted by `content_id`, built as `"memos/" + memo.UID` from the recursive memo-tree query.

What I checked:

- **Driver implementations** (all three are parallel implementations of the same logic): `store/db/sqlite/user_delete.go` (`deleteReactionsByContentIDsTx` at line 380, `deleteReactionsByCreatorTx` at line 400), `store/db/postgres/user_delete.go` (lines 383, 401), and `store/db/mysql/user_delete.go` (lines 420, 438). Everything runs in one transaction opened in `DeleteUser` and committed only at the end, so reaction cleanup rolls back with the rest if anything fails.
- **Schema, to rule out a database-level rule**: `CREATE TABLE reaction` in `store/migration/sqlite/LATEST.sql:92`, `store/migration/postgres/LATEST.sql:91`, and `store/migration/mysql/LATEST.sql:91`, plus the original `store/migration/*/0.20/00__reaction.sql`. The table declares only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint. `creator_id` is a plain `INTEGER`/`INT` with no `REFERENCES user(id)`, and `content_id` is text rather than a memo id, so no cascade is possible. A repo-wide search for `FOREIGN KEY`/`ON DELETE` in `store/migration/` returns hits only for `memo`, `user_setting`, `memo_share`, and older `0.5` regeneration files — never for `reaction`. The `0.23/00__reactions.sql` migrations only rewrite `reaction_type` values to emoji.
- **Service layer**: `server/router/api/v1/user_service.go:393` (`DeleteUser`) delegates all row deletion to `s.Store.DeleteUser` and afterwards only handles attachment blob cleanup, so there is no second reaction cleanup path there.
