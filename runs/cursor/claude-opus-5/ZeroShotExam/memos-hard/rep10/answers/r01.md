**Premise correction:** There is no Redis in this repository. There is no Redis connection to configure, no Redis client dependency (`go.mod` and `go.sum` contain zero matches for "redis"), and no connection string, environment variable, or config field anywhere in the codebase. The cache layer is a hand-rolled, in-process, in-memory cache.

**Actual mechanism**

The cache is implemented in `store/cache/cache.go` as a thread-safe in-memory store built on `sync.Map` plus an atomic item counter. Entries are `item` structs holding the value, an absolute `expiration` timestamp, and a rough size estimate. A background goroutine (`cleanupLoop`) sweeps expired entries on a ticker, and `Get` also lazily evicts an entry it finds past its expiration. Because state lives in the process heap, nothing is shared across instances — each server process has its own independent cache, which is why there is no connection to configure.

Configuration happens in the `Store` constructor rather than in any config file or environment variable:

```40:53:store/store.go
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
```

**TTL for user entries: 10 minutes.** The three caches (`instanceSettingCache`, `userCache`, `userSettingCache`) all share that single `cacheConfig` value, so users get the same 10-minute TTL as instance settings and user settings. There is no user-specific TTL. The `Cache` type does expose a `SetWithTTL` method for per-entry overrides, but grepping the whole tree shows it is only ever called from `Set` itself (`store/cache/cache.go:94`) and from `store/cache/cache_test.go` — no production code overrides the default. The identical literal in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) is a separate default that the store does not use; it happens to carry the same values.

Two practical caveats on user entries beyond the TTL. First, entries can be evicted well before 10 minutes: `MaxItems` is 1000, and exceeding it triggers `cleanupOldest`, which drops roughly 20% of entries. Second, the TTL is rarely the thing that actually bounds staleness, because writes refresh the cache eagerly. `CreateUser`, `CreateUserIfNoUsers`, `UpdateUser`, `ListUsers`, and `GetUser` all call `s.userCache.Set` (`store/user.go:98,122,132,143,167`), and `deleteUserCache` explicitly evicts the user plus its settings on deletion (`store/user_delete.go:39-47`).

One correctness note worth flagging: the read path in `GetUser` only consults the cache when the lookup is by ID.

```148:156:store/user.go
func (s *Store) GetUser(ctx context.Context, find *FindUser) (*User, error) {
	if find.ID != nil {
		if cache, ok := s.userCache.Get(ctx, userCacheKey(*find.ID)); ok {
			user, ok := cache.(*User)
			if ok {
				return user, nil
			}
		}
	}
```

Lookups by username or other fields always hit the database, since the cache key is just the numeric user ID (`userCacheKey`, `store/user.go:88-90`).
