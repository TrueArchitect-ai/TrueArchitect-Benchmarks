h15.

Memo visibility is enforced independently in each server surface that can surface memo content — there is no single choke point in the store layer (`store.FindMemo.VisibilityList` is caller-supplied, so every caller must set it). Here are the distinct enforcement sites:

Single-memo read gate for the gRPC/Connect API (`checkMemoReadAccess`: archived → creator only; non-public → requires auth; private → creator only), called from `GetMemo` for both the memo and its parent — `server/router/api/v1/memo_service.go` (lines 39–68, 356, 367)

List-query visibility filter in `ListMemos` (anonymous gets `PUBLIC` only; authenticated gets `creator_id == me || visibility in ["PUBLIC","PROTECTED"]`) — `server/router/api/v1/memo_service.go` (lines 218–227)

Comment surface: read gate before listing comments plus a per-child visibility filter, and a private-parent check before creating a comment — `server/router/api/v1/memo_service_comments.go` (lines 33–41, 148, 155–161)

Reactions: visibility check before listing reactions and before upserting one — `server/router/api/v1/reaction_service.go` (lines 29–41, 83)

Attachment metadata/binary over the API (`checkAttachmentAccess`, following the linked memo's visibility) — `server/router/api/v1/attachment_service.go` (lines 419–455)

Listing a memo's attachments — `server/router/api/v1/memo_attachment_service.go` (lines 213–225)

Raw attachment HTTP file server (`checkAttachmentPermission`, including the anonymous-instance rule and the `share_token` fallback) — `server/router/fileserver/fileserver.go` (lines 650–704)

SSE live-event delivery filter (`SSEClient.canReceive`, private events only to creator or admin, unknown visibility denied) — `server/router/api/v1/sse_hub.go` (lines 134–144), with the event's visibility populated in `server/router/api/v1/sse_event_helpers.go` (lines 29–37)

RSS feeds (explore and per-user), restricted to `store.Public` — `server/router/rss/rss.go` (lines 88–93, 138–144)

Sitemap generation, restricted to `store.Public` — `server/router/frontend/frontend.go` (lines 149–151)

User stats/activity aggregation visibility filter — `server/router/api/v1/user_service_stats.go` (lines 84–90, 218–220)

Notification/inbox rendering (`canViewerAccessMemo`) — `server/router/api/v1/user_service_notifications.go` (lines 302–316)

Mention fan-out eligibility (`canUserAccessMentionContext` / `shouldSkipMentionInbox`) — `server/router/api/v1/memo_mention_helpers.go` (lines 56–88)

Email notification dispatch (`canViewerAccessMemo`, a second copy of the same rules) — `server/notification/email.go` (lines 306–320)

One related site is a deliberate bypass rather than an enforcement of visibility: `GetMemoByShare` resolves an opaque share token and returns the memo without any visibility check, gating only on token validity/expiry and non-archived state — `server/router/api/v1/memo_share_service.go` (lines 153–207). The file server honors the same token via the `share_token` query parameter.
