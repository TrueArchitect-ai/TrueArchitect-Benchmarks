**`internal/idp`; `internal/idp/oauth2`**

The abstraction lives in `internal/idp/idp.go`, which is a tiny shared package defining the provider-neutral result type that every identity provider must produce:

```1:9:/bench/repo/internal/idp/idp.go
package idp

type IdentityProviderUserInfo struct {
	Identifier  string
	DisplayName string
	Email       string
	AvatarURL   string
}
```

The only concrete protocol implementation that ships is OAuth2, in `internal/idp/oauth2/oauth2.go`. It defines `IdentityProvider` backed by a `storepb.OAuth2Config`, with `NewIdentityProvider`, `ExchangeToken` (including PKCE support via a code verifier), and a user-info fetch that maps provider fields into `idp.IdentityProviderUserInfo` using the configured `FieldMapping`.

Two things corroborate that OAuth2 is the sole implementation:

- `internal/idp` contains only `idp.go` plus the `oauth2/` subdirectory (`oauth2.go` and `oauth2_test.go`) — no SAML, LDAP, or dedicated OIDC package.
- The stored config protobuf has a single oneof variant, `IdentityProviderConfig_Oauth2Config` in `proto/gen/store/idp.pb.go`, so the schema itself admits only OAuth2 today.

The wiring is in `server/router/api/v1/auth_service_sso.go`, which imports both packages: it constructs the OAuth2 provider from the stored config, then passes the returned `*idp.IdentityProviderUserInfo` into `resolveSSOUser` to link or create the local account. OIDC providers are supported in practice by configuring the generic OAuth2 endpoints rather than by a separate package.
