The premise is incorrect: this repository (Memos, a Go backend) has no per-user API rate-limiting middleware at all, so there is no registration site and no request limits to report. A case-insensitive search for `rate limit`, `throttle`, `TooManyRequests`, `429`, and rate-limiter libraries turns up nothing in the server code — the only hits are aspirational prose in `internal/email/README.md` (line 286, "Implement Rate Limiting", inside a guide for writing your own email sender) and `internal/email/doc.go` (line 86, a best-practice bullet). `go.mod` pulls in no rate-limiting dependency such as `golang.org/x/time/rate`.

What actually is registered as middleware:

- HTTP layer in `server/server.go` (lines 51-52): only `middleware.Recover()` and `newCORSMiddleware(profile)`.
- Connect RPC layer in `server/router/api/v1/v1.go` (lines 133-138): `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor`. The gRPC-Gateway path gets an equivalent auth middleware defined at lines 69-93 of the same file. All four interceptors live in `server/router/api/v1/connect_interceptors.go`, and none of them counts or limits requests.

The closest things to "limits" in the codebase are not rate limits and are not per-user:

- Request body size cap of 256 MiB (`maxAPIRequestBytes = 256 << 20` in `server/router/api/v1/v1.go` line 20), applied via `http.MaxBytesHandler` and `connect.WithReadMaxBytes` at lines 126, 141, and 144.
- Global concurrency semaphores, which bound simultaneous work rather than request rate: 3 concurrent thumbnail generations and 2 concurrent image processing operations (`server/router/api/v1/v1.go` lines 59-60), plus a separate `maxConcurrentThumbnails = 3` in `server/router/fileserver/fileserver.go` line 46. When the image semaphore can't be acquired, `server/router/api/v1/attachment_service.go` line 160 returns `ResourceExhausted` with "too many image processing requests", which is the only error in the codebase that superficially resembles rate-limit rejection — but it is triggered by concurrency across all users, not by any per-user request budget.

If you want per-user rate limiting, it would need to be added, most naturally as a new Connect interceptor in `connect_interceptors.go` registered alongside the others in `v1.go`, plus equivalent coverage on the gRPC-Gateway and file-server routes since those bypass the Connect interceptor chain.
