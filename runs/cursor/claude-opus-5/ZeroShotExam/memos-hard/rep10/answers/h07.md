h07.

The browser never fetches raw image bytes over gRPC: the API rewrites a base64 avatar into the URL `/file/users/{username}/avatar`, and a plain HTTP handler serves it by reading the `user.avatar_url` column (a base64 data URI) and decoding it. There is no filesystem or S3 involvement for avatars — the image lives in the user row.

Hops:

`convertUserFromStore` (emits `/file/{user.Name}/avatar` as `avatarUrl`) — `server/router/api/v1/user_service_converters.go`
`UserAvatar` (`<img src={avatarUrl}>` triggers the HTTP GET) — `web/src/components/UserAvatar.tsx`
`FileServerService.RegisterRoutes` (`GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go`
`FileServerService.serveUserAvatar` (serving handler) — `server/router/fileserver/fileserver.go`
`FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go`
`Store.GetUser` (ID-keyed cache only; username lookups always fall through) — `store/user.go`
`Store.ListUsers` — `store/user.go`
`Driver.ListUsers` (interface dispatch) — `store/driver.go`
`DB.ListUsers` (`SELECT ... avatar_url ... FROM user WHERE username = ?`) — `store/db/sqlite/user.go` (parallel implementations in `store/db/postgres/user.go` and `store/db/mysql/user.go`)
`user.avatar_url` column — `store/migration/sqlite/LATEST.sql`

Back in the handler, `FileServerService.parseDataURI` (`server/router/fileserver/fileserver.go`) splits the stored `data:image/png;base64,...` value, the MIME type is checked against `avatarAllowedTypes`, and the decoded bytes go out via `c.Blob` with a one-hour `Cache-Control`.

One access-control note relevant to "another user's" image: when `s.Profile.AllowAnonymous()` is false, `serveUserAvatar` first calls `getCurrentUser` → `auth.Authenticator.AuthenticateToUser` (`server/auth`) and rejects unauthenticated requests. Otherwise any avatar is public, with no per-user check.
