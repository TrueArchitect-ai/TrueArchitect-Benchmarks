The premise is incorrect: this repository (the Memos server) has **no per-user API rate-limiting middleware at all**, so there is no registration site and no request limits to report.

What I verified:

- The only HTTP middleware registered globally is panic recovery and CORS, in `server/server.go`:

```50:53:/bench/repo/server/server.go
	echoServer := echo.New()
	echoServer.Use(middleware.Recover())
	echoServer.Use(newCORSMiddleware(profile))
	s.echoServer = echoServer
```

- The API v1 stack registers exactly four Connect interceptors — metadata, logging, recovery, and auth — and a single auth middleware for the gRPC-Gateway mux; none of them count or limit requests (`server/router/api/v1/v1.go` lines 69–98 and 131–141, with the interceptors themselves defined in `server/router/api/v1/connect_interceptors.go`).
- A repo-wide search for `rate limit`, `throttle`, `RateLimiter`, `429`, `TooManyRequests`, and `golang.org/x/time/rate` turns up no implementation. `golang.org/x/time v0.15.0` appears in `go.mod` only as an indirect dependency and is never imported. The only textual hits are aspirational notes in `internal/email/README.md` (line 286) and `internal/email/doc.go` (line 86) suggesting that email sending *should* be rate limited.

Things that might be mistaken for rate limiting, and what they actually are:

- **Concurrency caps, not rate limits.** `APIV1Service` holds two counting semaphores: 3 concurrent thumbnail generations and 2 concurrent image-processing (EXIF-strip) operations (`server/router/api/v1/v1.go` lines 59–60). The file server has its own `maxConcurrentThumbnails` semaphore (`server/router/fileserver/fileserver.go` lines 45, 106–116). These bound simultaneous work process-wide, not requests per user over time; exceeding the image-processing cap returns `ResourceExhausted` with "too many image processing requests" (`server/router/api/v1/attachment_service.go` line 160), which is the closest thing in the codebase to a 429 but is global rather than per-user.
- **Payload and page-size limits.** `maxAPIRequestBytes = 256 << 20` bounds request body size (`server/router/api/v1/v1.go` line 20), memo content length is checked against an instance setting (`server/router/api/v1/memo_service.go` lines 101–106), and list endpoints clamp to `MaxPageSize`. These are per-request size limits, not request-frequency limits.

If you want per-user rate limiting, it would need to be added — the natural insertion points are a new Connect interceptor in the `connect.WithInterceptors(...)` list in `RegisterGateway`, plus the `gatewayAuthMiddleware` chain for REST traffic, since those are the two paths where the authenticated identity is resolved.
