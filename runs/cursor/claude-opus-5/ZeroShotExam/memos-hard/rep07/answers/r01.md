**Premise correction:** There is no Redis in this repository. `go.mod` has no Redis (or memcached/ristretto/bigcache) dependency, and a case-insensitive grep for "redis" across the tree returns zero hits — there is no connection string, no client, no config field, and no environment variable for one. The cache layer is a hand-rolled, in-process, in-memory cache, so there is nothing to "connect" to.

**Actual mechanism:**

The cache implementation lives in `store/cache/cache.go`. It is a `sync.Map` guarded by an atomic item counter, with per-entry expiration timestamps and a background cleanup goroutine started in `cache.New`.

Configuration happens at store construction in `store/store.go`, not through any external service config. `store.New` builds a `cache.Config` literal and hands the same config to three separate cache instances:

```40:53:/bench/repo/store/store.go
	cacheConfig := cache.Config{
		DefaultTTL:      10 * time.Minute,
		CleanupInterval: 5 * time.Minute,
		MaxItems:        1000,
		OnEviction:      nil,
	}

	store := &Store{
		driver:               driver,
		profile:              profile,
		cacheConfig:          cacheConfig,
		instanceSettingCache: cache.New(cacheConfig),
		userCache:            cache.New(cacheConfig),
		userSettingCache:     cache.New(cacheConfig),
	}
```

**TTL for user entries: 10 minutes.** Every write path for users in `store/user.go` (`CreateUser`, `CreateUserIfNoUsers`, `UpdateUser`, `ListUsers`, `GetUser`) calls `s.userCache.Set(...)`, and `Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go` line 94). Nothing in the user code path calls `SetWithTTL` directly, so the 10-minute default is the only TTL that applies. `cache.DefaultConfig()` in `store/cache/cache.go` declares the same 10m/5m/1000 values, but it is unused by `store.New`, which inlines its own identical literal.

Three details worth knowing beyond the raw TTL:

- Entries can disappear before 10 minutes. `MaxItems` is 1000, and `SetWithTTL` calls `cleanupOldest` on overflow, which drops roughly 20% of entries by soonest expiration. The user cache shares that 1000-item budget with nothing else (each of the three caches is its own instance), but a busy instance with more than 1000 users will evict early.
- Expiry is lazy plus swept: `Get` checks `time.Now().After(itm.expiration)` and deletes on read, while the `cleanupLoop` ticker sweeps every 5 minutes.
- The TTL is not the only invalidation. `store/user_delete.go` line 40 explicitly calls `s.userCache.Delete`, and updates overwrite the entry, so the 10 minutes is a staleness ceiling for changes made outside this process rather than for changes made through it. Since the cache is per-process memory, a multi-replica deployment gives each replica its own independent copy with its own 10-minute window.

Read cache hits only occur in `GetUser` when the lookup is by ID (`store/user.go` lines 148-156); lookups by username or other fields always fall through to the database and merely repopulate the cache.
