**Mechanism: explicit Go code.** Each SQL driver's `DeleteUser` runs two `DELETE FROM reaction` statements inside the delete transaction — one for reactions the deleted user authored, and one for reactions anyone left on the deleted user's memos. There is no database-level foreign key or cascade on the `reaction` table in any of the three schemas.

The `content_id` list comes from `memoContentIDsFromRefs`, which formats the recursively-collected memo tree (the user's memos plus their comment descendants) as `"memos/" + uid`, matching how reactions store their target. The MySQL equivalents are at lines 417 and 437 of `store/db/mysql/user_delete.go`; Postgres at lines 380 and 400.

**Why it isn't a database rule:** the `reaction` table carries no foreign key in any schema — only a uniqueness constraint. See `store/migration/sqlite/LATEST.sql` lines 92-99, `store/migration/postgres/LATEST.sql` lines 91-98, and `store/migration/mysql/LATEST.sql` lines 91-98. Grepping `FOREIGN KEY`/`ON DELETE` across `store/migration` turns up cascades only for `memo_share`, `memo_resource`, and pre-0.7 tables; SQLite's `store/migration/sqlite/0.7/00__remove_fk.sql` stripped the older user-referencing cascades, and `reaction` (introduced in `0.20/00__reaction.sql`) never had one.
