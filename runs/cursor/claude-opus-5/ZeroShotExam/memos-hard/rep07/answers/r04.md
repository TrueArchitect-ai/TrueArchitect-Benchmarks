**Premise correction:** Neither. This repository (Memos) has no message broker at all — no NATS, RabbitMQ, Kafka, Redis, or SQS client appears anywhere in `go.mod`/`go.sum` or `web/package.json`. So there is no broker-declared queue to point to.

**Actual mechanism:** Webhook delivery is entirely in-process, using a buffered Go channel and a fixed pool of goroutines. The "queue" is a plain Go channel declared as a package-level variable in `internal/webhook/webhook.go`:

```39:55:/bench/repo/internal/webhook/webhook.go
	asyncPostQueue = make(chan *WebhookRequestPayload, 128)
)

func init() {
	for range 4 {
		go func() {
			for payload := range asyncPostQueue {
				if err := Post(payload); err != nil {
					slog.Warn("Failed to dispatch webhook asynchronously",
						slog.String("url", payload.URL),
						slog.String("activityType", payload.ActivityType),
						slog.Any("err", err))
				}
			}
		}()
	}
}
```

The flow works like this. When a memo is created, updated, deleted, or commented on, the API handlers in `server/router/api/v1/memo_service.go`, `memo_update_helpers.go`, and `memo_service_comments.go` call the dispatch helpers in `server/router/api/v1/memo_service_webhooks.go`. Those helpers load the user's configured webhooks via `s.Store.GetUserWebhooks(...)` and call `webhook.PostAsync(payload)` for each one (lines 43 and 71).

`PostAsync` (lines 184–196 of `internal/webhook/webhook.go`) does a non-blocking send into `asyncPostQueue`; if the 128-slot buffer is full, the delivery is **silently dropped** with just a warning log. The four `init()`-spawned worker goroutines read from that channel and call `Post`, which does a synchronous HTTP POST with a 30-second timeout, optional HMAC-SHA256 Standard Webhooks signing, and an SSRF-blocking dialer.

Two consequences worth noting, since they're the sort of thing people assume a broker would give them: there are **no retries** (a failed `Post` is logged once and discarded — no backoff logic exists in `internal/webhook/`), and there is **no durability**. The old `webhook` database table was removed in v0.25 (`store/migration/*/0.25/00__remove_webhook.sql`); webhook *configuration* now lives in user settings (`WebhooksUserSetting` in `proto/store/user_setting.proto`), but pending *deliveries* exist only in memory and are lost on restart.

The same pattern is used for email in `internal/email/email.go` (channel of 128, 2 workers), which confirms this is a deliberate house style rather than an oversight in the webhook package.
