h07.

A browser loading another user's avatar hits the native file server route `GET /file/users/:identifier/avatar`, which reads the user row from the store and decodes the base64 data URI held in the `user.avatar_url` column. Note the avatar is not a file on disk or in S3: it is stored inline in the user table, so the "data layer" hop is a `SELECT` against `user`.

Details worth knowing:

- Access control is coarse: on an instance with an `InstanceURL` configured (`Profile.AllowAnonymous()` true) any anonymous visitor can fetch any user's avatar; on a private instance a valid session, access token, or PAT is required, but any authenticated viewer may fetch any other user's avatar (`server/router/fileserver/fileserver.go:171-181`).
- `Store.GetUser` only consults `userCache` when the lookup is by ID, so this username-based lookup always reaches the driver, though results are written back into the cache (`store/user.go:136-168`).
- Serving is hardened by a MIME allowlist (`avatarAllowedTypes`, `server/router/fileserver/fileserver.go:75`) plus `Cache-Control: public, max-age=3600`; the same allowlist is enforced on upload in `UpdateUser` (`server/router/api/v1/user_service.go:335-354`).
- `"/memos.api.v1.UserService/GetUserAvatar"` appears in `server/router/api/v1/acl_config.go:25`, but no such RPC is defined or implemented anywhere — it is a stale ACL entry, not a second serving path.
