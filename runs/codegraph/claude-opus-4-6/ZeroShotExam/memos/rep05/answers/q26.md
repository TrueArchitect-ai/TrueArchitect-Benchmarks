When `DeleteMemo` runs, the following database tables are affected (directly or by explicit cascade code):

1. **`memo_relation`** — deleted via `s.driver.DeleteMemoRelation()` for both `MemoID` and `RelatedMemoID` matching the memo (`store/memo.go:142-147`)
2. **`attachment`** — deleted via `s.DeleteAttachment()` for each attachment linked to the memo (`store/memo.go:149-157`, which calls `s.driver.DeleteAttachment` at `store/attachment.go:148`)
3. **`memo`** — the memo row itself is deleted via `s.driver.DeleteMemo()` (`store/memo.go:158`; SQL at `store/db/postgres/memo.go:246`, `store/db/mysql/memo.go:261`)

Additionally, the API-level `DeleteMemo` in `server/router/api/v1/memo_service.go:518-593` recursively deletes **comment memos** before deleting the target memo:

4. **`memo`** (comment rows) — for each `memo_relation` of type `COMMENT` pointing to the memo, `Store.DeleteMemo` is called on the comment memo (`memo_service.go:568-577`), which in turn triggers the same cascade (cleaning up that comment's `memo_relation`, `attachment`, and `memo` rows).

So the three tables are: **`memo`**, **`memo_relation`**, **`attachment`**.
