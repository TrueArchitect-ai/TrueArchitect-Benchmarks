**Frontend interceptor:** `web/src/connect.ts` — the `authInterceptor` (line 156) is a Connect RPC `Interceptor` that attaches an `Authorization: Bearer <token>` header to every outgoing request. It reads the current access token via `getAccessToken()` from `web/src/auth-state.ts`, proactively refreshes it if near expiry, and on a `CodeUnauthenticated` response retries once after refreshing. The refresh itself calls the `AuthService.RefreshToken` RPC using a separate credential-including transport (cookie-based, line 65–72).

**Token kinds managed:**
1. **Short-lived JWT access tokens** — stored in-memory and localStorage (`web/src/auth-state.ts`), sent as `Bearer` tokens in the `Authorization` header, stateless validation on the server (15-minute lifetime).
2. **Refresh tokens** — stored in an HttpOnly cookie, sent automatically with `credentials: "include"`, validated against the database for revocation. Used to obtain new access tokens.
3. **Personal Access Tokens (PATs)** — long-lived tokens prefixed `memos_pat_`, also sent as `Bearer` tokens; validated server-side via SHA-256 hash lookup in the database.

**Backend validation package:** `server/auth` (`server/auth/authenticator.go`). The `Authenticator` struct provides `Authenticate()`, `AuthenticateByAccessTokenV2()`, `AuthenticateByRefreshToken()`, and `AuthenticateByPAT()`. It is wrapped by `Authorizer` in `server/router/api/v1/authz.go`, which is used by the server-side `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go` (line 208) to enforce authentication and access policy on every Connect RPC call.
