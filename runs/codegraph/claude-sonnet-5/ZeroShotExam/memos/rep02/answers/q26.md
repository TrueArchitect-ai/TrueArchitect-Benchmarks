**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted directly (`store/db/{sqlite,mysql,postgres}/memo.go: DeleteMemo`, called from `store/memo.go:158`). Comment memos (rows in `memo_relation` with `type='COMMENT'` pointing at this memo) are also deleted, since the RPC handler recursively calls `store.DeleteMemo` for each comment first (`server/router/api/v1/memo_service.go:567-582`).
- **`memo_relation`** — explicitly cleaned up in `store.DeleteMemo` (`store/memo.go:142-147`) via two `DeleteMemoRelation` calls, once where the memo is the source (`memo_id`) and once where it's the target (`related_memo_id`). This runs for the memo itself and again for each deleted comment memo.
- **`attachment`** — explicitly cleaned up: `store.DeleteMemo` lists attachments by `memo_id` and deletes each one (`store/memo.go:149-157` → `store/attachment.go: DeleteAttachment`), including the underlying file/S3 object cleanup (no DB cascade needed since `attachment` has no FK to `memo`).
- **`memo_share`** — not touched by any Go code path, but cascades at the database level: the schema defines `memo_share.memo_id` with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, and equivalently in `store/migration/postgres/LATEST.sql:108` and `store/migration/mysql/LATEST.sql:108`), so share rows for the memo are removed automatically when the `memo` row is deleted.

**Not affected:** `reaction` rows referencing the memo are only read (via `ListReactions`, for the deletion webhook payload) — the code never deletes them, and the `reaction` table has no FK constraint to `memo` (`content_id` is a free-form string), so no DB-level cascade cleans them up either. They are effectively orphaned by this path.
