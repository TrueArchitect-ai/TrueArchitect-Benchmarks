Tables affected when `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518`):

- **`memo`** — the target memo row is deleted, and (via the pre-loop over `memo_relation` rows of type `COMMENT`) each comment memo is also deleted recursively through `store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-582`).
- **`memo_relation`** — inside `store.DeleteMemo` (`store/memo.go:140-158`), rows where `memo_id = deletedID` and rows where `related_memo_id = deletedID` are both explicitly deleted.
- **`attachment`** — also inside `store.DeleteMemo` (`store/memo.go:148-157`), all attachments with `memo_id = deletedID` are looked up and deleted one by one via `store.DeleteAttachment` (`store/attachment.go:132-149`), which also removes the underlying storage blob/file/S3 object (not a DB table).

Note: `reaction` rows tied to the memo are only **listed** (`ListReactions`, for the webhook payload) at `server/router/api/v1/memo_service.go:545-550` — they are not deleted by `DeleteMemo`, unlike the full user-deletion path (`store/db/mysql/user_delete.go:96` `deleteReactionsByContentIDsTx`), which does cascade into `reaction`. So `reaction` is not affected by `DeleteMemo`.
