**Directly deleted / explicitly cascaded tables when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted (`store/db/mysql/memo.go:259-270`, `store/db/postgres/memo.go:244-255`), and this repeats recursively for every comment memo attached to it, since `server/router/api/v1/memo_service.go:567-577` first looks up all `COMMENT`-type relations pointing at the memo and calls `store.DeleteMemo` on each comment's ID before deleting the parent (`server/router/api/v1/memo_service.go:580-582`).
- **`memo_relation`** — `store.DeleteMemo` (`store/memo.go:140-158`) explicitly deletes relation rows where the memo is either the source (`MemoID`) or target (`RelatedMemoID`) via two `DeleteMemoRelation` calls (`store/memo.go:142-147`). This runs once for the memo itself and again for each comment memo deleted in the loop above.
- **`attachment`** — `store.DeleteMemo` lists all attachments tied to the memo and calls `DeleteAttachment` on each (`store/memo.go:148-157`), which deletes the row from `attachment` (`store/db/mysql/attachment.go:230-241`, `store/db/postgres/attachment.go`) plus the underlying blob/file storage (`store/attachment.go:132-149`). This also runs per comment memo via the recursive `DeleteMemo` calls.

**Notable non-cascade:** reactions on the memo are only fetched via `ListReactions` for the webhook payload (`server/router/api/v1/memo_service.go:545-550`) — there is no explicit delete of `reaction` rows in the `DeleteMemo` path, so that table is read but not written/cascaded here (source: `store/reaction.go`, `store/db/mysql/reaction.go`, `store/db/postgres/reaction.go` show no caller from `DeleteMemo`).

Table list: `memo`, `memo_relation`, `attachment`
