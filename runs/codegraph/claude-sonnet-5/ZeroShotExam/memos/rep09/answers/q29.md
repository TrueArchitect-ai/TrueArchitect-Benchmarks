- **Interceptor path**: `web/src/connect.ts` — `authInterceptor` (a Connect-RPC `Interceptor`, lines 156–178), wired into the shared `createConnectTransport` at line 184–189. It attaches `Authorization: Bearer <token>` on every request (`setAuthorizationHeader`), and on a `Code.Unauthenticated` response transparently refreshes the token once (`refreshAndGetAccessToken`) and retries before falling back to `redirectOnAuthFailure()`. Token storage/expiry helpers live alongside it in `web/src/auth-state.ts`.

- **Token kinds**: two token types are managed:
  1. **JWT access token ("Access Token V2")** — short-lived, kept in memory + `localStorage` (`memos_access_token` / `memos_token_expires_at`, see `web/src/auth-state.ts:6-7`), sent as the `Authorization: Bearer` header.
  2. **Refresh token** — longer-lived, stored as an HTTP-only cookie (not touched by JS directly; sent automatically via `credentials: "include"` in `fetchWithCredentials`, `web/src/connect.ts:57-62`), used only to mint new access tokens via `AuthService.RefreshToken`.
  
  (Personal Access Tokens (PATs) are also supported for programmatic API access but are not something the frontend interceptor manages — they're a separate bearer-token path validated server-side.)

- **Backend package that validates them**: `server/auth` (specifically `server/auth/authenticator.go`, the `Authenticator` type — `AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, `AuthenticateByPAT`, `Authenticate`). This is invoked per-request via `server/router/api/v1/authz.go`'s `Authorizer` (constructed with `auth.NewAuthenticator`), which is itself wired into Connect RPCs through the `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go`.
