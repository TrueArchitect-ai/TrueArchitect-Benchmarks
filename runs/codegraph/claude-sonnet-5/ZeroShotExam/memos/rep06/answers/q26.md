**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target row is deleted directly (`store/db/{sqlite,mysql,postgres}/memo.go: DeleteMemo`, e.g. `store/db/mysql/memo.go:259`).
- **`memo_relation`** — explicitly cascaded in code: `store/memo.go:140-158` calls `driver.DeleteMemoRelation` twice (once for `memo_id = ID`, once for `related_memo_id = ID`) before deleting the memo. This also covers `COMMENT`-type relations; the handler in `server/router/api/v1/memo_service.go:567-577` additionally recurses `Store.DeleteMemo` for each comment memo found via this table.
- **`attachment`** — explicitly cascaded in code: `store/memo.go:148-157` lists attachments for the memo (`ListAttachments`) and deletes each one (`DeleteAttachment`), which also removes the underlying blob/S3 object.
- **`memo_share`** — not touched in Go code, but cascaded at the DB layer via an explicit `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` constraint present in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`).

**Not affected:** the `reaction` table is *not* cascaded — it stores `content_id` (a resource-name string) with no foreign key to `memo`, and `server/router/api/v1/memo_service.go:545-550` only reads reactions (for the webhook payload) without deleting them, so reaction rows become orphaned after a memo delete.
