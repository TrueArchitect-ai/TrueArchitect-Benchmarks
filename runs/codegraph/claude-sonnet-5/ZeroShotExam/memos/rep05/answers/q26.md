**Tables affected when `DeleteMemo` runs** (server/router/api/v1/memo_service.go:518 → store/memo.go:140/store.DeleteMemo → driver):

1. **`memo`** — the target memo row is deleted directly (`store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`), and recursively for each of its comment-memos, which the handler explicitly deletes first (`server/router/api/v1/memo_service.go:567-577`).
2. **`memo_relation`** — explicitly cascaded in code: `store.DeleteMemo` (store/memo.go:142-147) deletes all relation rows where the memo is either `memo_id` or `related_memo_id` (covers comment/reference relations).
3. **`attachment`** — explicitly cascaded in code: `store.DeleteMemo` (store/memo.go:148-157) lists attachments for the memo and calls `DeleteAttachment` on each (`store/attachment.go:132`, SQL delete at `store/db/mysql/attachment.go:230`).
4. **`memo_share`** — cascaded implicitly at the DB level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/mysql/LATEST.sql:108, store/migration/postgres/LATEST.sql:108, store/migration/sqlite/LATEST.sql:109), so share-link rows are removed automatically when the `memo` row is deleted.

Not affected: `reaction` — `DeleteMemo` only reads reactions (`ListReactions`, memo_service.go:545-550) for the webhook payload; it is never deleted, and `reaction.content_id` is a string reference with no FK/cascade, so reaction rows are left orphaned rather than removed.
