- **memo_relation** — explicitly deleted for both directions (`MemoID = id` and `RelatedMemoID = id`) via `driver.DeleteMemoRelation` (store/memo.go:142-147), for the target memo and for each deleted comment memo.
- **attachment** — explicitly deleted via `s.ListAttachments` + `s.DeleteAttachment` for every attachment whose `memo_id` matches the deleted memo (store/memo.go:149-157), again for the target and each comment memo. (This also triggers non-DB side effects: local file/S3 object deletion.)
- **memo_share** — not touched by application code, but has a DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/sqlite/LATEST.sql:103-108, mirrored in the mysql/postgres LATEST.sql), so rows are cascade-deleted by the database when the `memo` row is deleted.

Note: `reaction` rows tied to the memo are only *read* (`s.Store.ListReactions`, for webhook payload purposes) but are **never deleted** — there is no `DeleteReaction` call in `DeleteMemo`, and the `reaction` table has no FK to `memo` (it references `content_id` as a loose string), so reaction rows are left orphaned.
