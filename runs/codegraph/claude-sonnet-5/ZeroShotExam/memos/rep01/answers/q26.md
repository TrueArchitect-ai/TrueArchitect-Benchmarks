**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted (`store/db/{mysql,postgres,sqlite}/memo.go:*` `DELETE FROM memo WHERE id = ...`), and additionally every child "comment" memo is fetched via `memo_relation` and deleted the same way, since `server/router/api/v1/memo_service.go:567-577` explicitly loops over comment relations and calls `store.DeleteMemo` for each before deleting the parent.
- **`memo_relation`** — `store.DeleteMemo` (`store/memo.go:142-147`) explicitly deletes relation rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`), for the parent memo and, recursively, for each deleted comment memo.
- **`attachment`** — `store.DeleteMemo` (`store/memo.go:148-157`) lists attachments with `MemoID = delete.ID` and calls `store.DeleteAttachment` for each, which issues `DELETE FROM attachment WHERE id = ...` (`store/db/{mysql,postgres,sqlite}/attachment.go`), in addition to removing on-disk/S3 blob storage and derived cache files (not DB tables).

Not affected by explicit code in this path: the `reaction` table — the handler only calls `ListReactions` (to build the webhook payload), with no corresponding delete of reaction rows for the memo (`server/router/api/v1/memo_service.go:545-550`).
