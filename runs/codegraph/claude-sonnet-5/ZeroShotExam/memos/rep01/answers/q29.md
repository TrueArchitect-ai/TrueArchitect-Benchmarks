- **Interceptor path**: `web/src/connect.ts` — `authInterceptor` (lines 156–178), attached to the Connect-RPC transport at line 188. It reads the access token via `getRequestToken()` (backed by `web/src/auth-state.ts`, referenced but not opened here), sets `Authorization: Bearer <token>` on outgoing requests (`setAuthorizationHeader`, line 97), and on a `401 Unauthenticated` response transparently refreshes the token and retries once (falling back to `redirectOnAuthFailure()` on failure).
- **Token kinds**: two JWT types plus one opaque type, all defined in `server/auth/token.go` and reflected in this interceptor's flow:
  - **Access token** — short-lived (15 min), sent as the `Authorization: Bearer` header, cached client-side and refreshed proactively/reactively by `authInterceptor`.
  - **Refresh token** — long-lived (30 days), stored as an HttpOnly cookie (`memos_refresh`), sent automatically via `credentials: "include"` (`fetchWithCredentials`, line 57) rather than through the auth interceptor; used by `refreshAuthClient.refreshToken()` (line 75) to mint new access tokens.
  - **Personal Access Token (PAT)** — long-lived, user-generated (`memos_pat_` prefix), for programmatic/API use (`server/router/api/v1/user_service_access_tokens.go`).
- **Backend package that validates them**: `server/auth` (specifically `server/auth/token.go` for JWT generation/parsing — `ParseAccessTokenV2`, `ParseRefreshToken`, `verifyJWTKeyFunc` — and `server/auth/authenticator.go` for the `Authenticator`/`AuthenticateByAccessTokenV2`/`AuthenticateByRefreshToken` logic), invoked from the Connect interceptor chain via `AuthInterceptor`/`Authenticate` in `server/router/api/v1/connect_interceptors.go` and `server/router/api/v1/authz.go`.
