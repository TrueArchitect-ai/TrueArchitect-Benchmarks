**Tables affected when `DeleteMemo` runs:**

1. **`memo`** — the target memo row is deleted (`DELETE FROM memo WHERE id = ?` in `store/db/{sqlite,mysql,postgres}/memo.go`, called from `store/memo.go:158`). Additionally, before deleting the memo itself, the service layer (`server/router/api/v1/memo_service.go:567-577`) finds all comment memos (`memo_relation` rows of type `COMMENT` where `related_memo_id` = the memo) and recursively calls `store.DeleteMemo` on each one — so comment memos are also deleted from `memo`.

2. **`memo_relation`** — explicitly cleaned up in `store.DeleteMemo` (`store/memo.go:142-147`): deletes rows where `memo_id = target` and rows where `related_memo_id = target` (covers both relation/reference edges and comment edges).

3. **`attachment`** — explicitly cleaned up in `store.DeleteMemo` (`store/memo.go:149-157`): lists all attachments with `memo_id = target` and calls `DeleteAttachment` for each, which issues `DELETE FROM attachment WHERE id = ?` (`store/db/mysql/attachment.go:230`, and sqlite/postgres equivalents), plus removes associated blob/storage files.

4. **`memo_share`** — not touched by any Go code path, but cascades automatically at the database level: `memo_share.memo_id` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`), so share-link rows for the deleted memo are removed by the DB engine when the `memo` row is deleted.

**Not affected (worth noting):** the `reaction` table is *read* in `DeleteMemo` (`server/router/api/v1/memo_service.go:545-550`, via `ListReactions`) for webhook-payload purposes only — it is never deleted, and `reaction.content_id` is a string reference rather than a foreign key, so no DB-level cascade removes reactions either. This looks like a potential orphan-row gap but is outside the scope of "affected tables."
