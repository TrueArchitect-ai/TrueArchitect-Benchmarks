Premise correction: neither. This codebase (usememos/memos) has no NATS or RabbitMQ integration anywhere in the webhook path — there's no external message broker at all.

Actual mechanism: webhook delivery uses an in-process, in-memory Go channel as the "queue," not a broker.

- `internal/webhook/webhook.go:39` declares `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a buffered channel of capacity 128, the only "queue" in the system.
- `internal/webhook/webhook.go:42-55` (`init()`) spawns 4 goroutine workers that range over `asyncPostQueue` and call `Post(payload)` for each item — these are the "delivery workers."
- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send into `asyncPostQueue`, dropping (and logging a warning for) the payload if the channel is full rather than blocking.
- Callers like `dispatchMemoRelatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:48-74`) and `DispatchMemoCommentCreatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:29-46`) call `webhook.PostAsync(payload)` to enqueue webhook deliveries.
- `Post()` (`internal/webhook/webhook.go:120-180`) performs the actual outbound HTTP POST with HMAC signing.

So there's no queue *declaration* on a broker (no exchange/queue bindings, no NATS subject/stream config) to point to — it's a fixed-size Go channel declared as a package-level var in `internal/webhook/webhook.go:39`.
