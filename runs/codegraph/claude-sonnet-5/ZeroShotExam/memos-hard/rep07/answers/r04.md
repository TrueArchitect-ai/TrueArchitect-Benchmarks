Premise correction: this repo has no message broker at all — neither NATS nor RabbitMQ is used for webhook delivery.

Actual mechanism: webhook dispatch is done with a plain in-process Go channel, not an external broker. In `internal/webhook/webhook.go:39`, `asyncPostQueue` is declared as `make(chan *WebhookRequestPayload, 128)` — a buffered in-memory channel. On package `init()` (`internal/webhook/webhook.go:42-55`), 4 goroutine workers range over that channel and call `Post(payload)` (line 46) to deliver the HTTP webhook. Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184-195`), which does a non-blocking `select` send into `asyncPostQueue`, dropping and logging a warning if the channel is full (no persistence, no external broker, no durability across restarts). Callers are in `server/router/api/v1/memo_service_webhooks.go` (`dispatchMemoRelatedWebhook`, `DispatchMemoCommentCreatedWebhook`).

The same pattern (bounded Go channel + fixed worker pool) is reused for email delivery in `internal/email/email.go:14` (`asyncEmailQueue`), confirming this is the project's general convention for async fan-out rather than something broker-backed.
