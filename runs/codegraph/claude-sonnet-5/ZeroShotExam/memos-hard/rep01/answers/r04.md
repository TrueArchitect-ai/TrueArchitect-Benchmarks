**Premise correction:** The premise is false — webhook delivery in this codebase (`usememos/memos`) doesn't use either NATS or RabbitMQ. There is no external message broker in the webhook delivery path.

**Actual mechanism:** Delivery is handled by an in-process, in-memory Go channel that acts as a small worker pool:

- `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a buffered Go channel (capacity 128) declared as a package-level var.
- `internal/webhook/webhook.go:42-55` (`init()`) — spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)` to actually deliver the HTTP webhook request.
- `internal/webhook/webhook.go:184-196` (`PostAsync`) — the enqueue side: does a non-blocking `select` send into `asyncPostQueue`, dropping (and logging a warning for) the payload if the channel is full rather than blocking.
- Callers like `dispatchMemoRelatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:48-74`) and `DispatchMemoCommentCreatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:30-46`) build the payload and call `webhook.PostAsync(payload)`.

So "the queue" is a Go `chan` with 4 consumer goroutines inside the same process — there's no NATS subject, no RabbitMQ exchange/queue declaration, and no separate broker process anywhere in this delivery path.
