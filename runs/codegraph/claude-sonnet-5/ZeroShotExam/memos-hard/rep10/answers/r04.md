**Premise correction:** This codebase (usememos/memos) doesn't use either NATS or RabbitMQ for webhook delivery — there is no external message broker involved at all.

**Actual mechanism:** Webhook delivery uses an in-process, in-memory Go channel as a worker queue. In `internal/webhook/webhook.go:39`, `asyncPostQueue` is declared as `make(chan *WebhookRequestPayload, 128)` — a buffered channel holding up to 128 pending payloads. `init()` at `internal/webhook/webhook.go:42-55` spawns 4 goroutines that range over this channel and call `Post()` (the actual HTTP POST to the webhook URL, `internal/webhook/webhook.go:120`) for each payload. Producers call `PostAsync()` (`internal/webhook/webhook.go:184-195`), which does a non-blocking `select` send into `asyncPostQueue`, dropping (and logging a warning for) the payload if the channel is full rather than blocking. Callers are `dispatchMemoRelatedWebhook` and `DispatchMemoCommentCreatedWebhook` in `server/router/api/v1/memo_service_webhooks.go`.

Note there's an analogous, separate pattern for email in `internal/email/email.go` (`asyncEmailQueue`, a 128-buffered channel with 2 worker goroutines) — same in-memory-channel design, unrelated to webhooks.
