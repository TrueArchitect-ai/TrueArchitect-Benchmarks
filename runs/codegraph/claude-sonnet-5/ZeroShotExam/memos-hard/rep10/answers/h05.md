**Mechanism:** Explicit Go code (application-level transaction), not a database-level cascade rule.

**Evidence locations:**
- `store/db/{mysql,postgres,sqlite}/user_delete.go`, function `deleteUserTargetsTx` (mysql: lines 92–127) explicitly calls two reaction-deletion steps before deleting the user row:
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — deletes reactions on the deleted user's memos (`DELETE FROM reaction WHERE content_id IN (...)`), at `store/db/mysql/user_delete.go:417-425` (same in postgres:380-388, sqlite:380-388).
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` — deletes reactions the user themselves made on any memo (`DELETE FROM reaction WHERE creator_id = ?`), at `store/db/mysql/user_delete.go:437-440` (same in postgres:400-403, sqlite:400-403).
- Both run inside the same SQL transaction as `deleteUserRowTx` (the final step in `deleteUserTargetsTx`), so reaction cleanup and user-row deletion are atomic.
- Confirmed no DB-level cascade exists: the `reaction` table schema (`store/migration/{mysql,postgres,sqlite}/LATEST.sql`, e.g. mysql line 97 / postgres line 97 / sqlite line 98) defines only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY ... ON DELETE CASCADE` tying `reaction.creator_id` (or `content_id`) to the `user` table.
- The generic `store.DeleteReaction`/driver `DeleteReaction` method (`store/reaction.go:39`, `store/driver.go:74`) is a separate, single-row deletion path used by the reaction API (`server/router/api/v1/reaction_service.go`), not part of user deletion — user deletion uses the bespoke bulk `deleteReactionsBy*Tx` helpers instead.
