Mechanism: **Explicit Go code, within the same DB transaction as the rest of the user-deletion cascade** (not a database-level trigger/FK cascade rule).

Evidence:
- `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:92-127`, and identical logic in `store/db/postgres/user_delete.go` and `store/db/sqlite/user_delete.go`) is called from `DeleteUser` and explicitly invokes:
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — deletes reactions attached to the user's memos (by `content_id`)
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` — deletes reactions the user themself created on any content
- `deleteReactionsByContentIDsTx` (mysql: `store/db/mysql/user_delete.go:417-425`; postgres: `store/db/postgres/user_delete.go:380-388`; sqlite: `store/db/sqlite/user_delete.go:380-388`): runs `DELETE FROM reaction WHERE content_id IN (...)` in batches for the memo/content IDs owned by the deleted user.
- `deleteReactionsByCreatorTx` (mysql: `store/db/mysql/user_delete.go:437-440`; postgres: `store/db/postgres/user_delete.go:400-403`; sqlite: `store/db/sqlite/user_delete.go:400-403`): runs `DELETE FROM reaction WHERE creator_id = ?` for the deleted user's own reactions on any memo.

Both deletes happen inside the same `sql.Tx` as the rest of the cascade (memos, attachments, memo_share, inbox, user_identity, user_setting, memo_relation, and finally the user row itself via `deleteUserRowTx`), before the transaction is committed in `DeleteUser` (`store/db/mysql/user_delete.go:29-59`, mirrored in the postgres/sqlite equivalents). I checked all three backend implementations (mysql, postgres, sqlite) and found the same explicit `DELETE FROM reaction` statements in each — no schema/migration-level `ON DELETE CASCADE` was found governing this; the cleanup is done purely in application code.
