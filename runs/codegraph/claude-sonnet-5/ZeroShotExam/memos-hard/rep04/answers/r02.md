The premise is incorrect: this repository (usememos/memos) has **no per-user API rate-limiting middleware**. I checked both via CodeGraph and direct grep (`ratelimit`, `rate_limit`, `rate-limit`, `throttle`, `Limiter`) across the Go and web source, and found none.

What actually exists around the API request pipeline:
- **Connect RPC interceptors** registered in `server/router/api/v1/v1.go:133-138` (`RegisterGateway`): `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` — defined in `server/router/api/v1/connect_interceptors.go`. These handle header propagation, logging, panic recovery, and authentication/authorization — not rate limiting.
- **gRPC-Gateway auth middleware** (`gatewayAuthMiddleware`, `server/router/api/v1/v1.go:69-93`) — again authentication/authorization, not throttling.
- The only "limit" mechanisms present are unrelated to per-user API throttling: a global request body size cap (`maxAPIRequestBytes = 256 << 20`, `v1.go:20`) and two concurrency semaphores in `APIV1Service` (`thumbnailSemaphore` capped at 3, `imageProcessingSemaphore` capped at 2, `v1.go:59-60`) that bound concurrent thumbnail/image processing work, not per-user request rates.
- A `Middleware` type also exists in `internal/scheduler/middleware.go`, but that's for background job scheduling (`Recovery`, `Logging`, `Timeout` middlewares), unrelated to the HTTP/API layer.

So there is no per-user rate limiter to point to, and consequently no request-limit numbers to report.
