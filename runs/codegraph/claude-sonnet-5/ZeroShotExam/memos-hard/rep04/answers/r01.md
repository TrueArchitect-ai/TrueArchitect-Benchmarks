**Premise correction:** There is no Redis connection in this repository — this is the `usememos/memos` codebase, and it has no Redis client, dependency, or config anywhere (`grep -ri redis` across the repo returns nothing). The cache layer is a pure in-process, in-memory cache, not backed by any external Redis instance.

**Actual mechanism:** The cache is implemented at `store/cache/cache.go:67` as `Cache`, a thread-safe in-memory store built on `sync.Map` with TTL expiration and periodic cleanup (goroutine loop, `cache.go:200-215`).

It's wired up in `store/store.go:38-58` (`store.New`), which constructs a shared `cache.Config` with `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store/store.go:40-45`), and instantiates three separate in-memory caches from that same config: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`).

User entries specifically go through `userCache`, keyed by `userCacheKey(userID)` (`store/user.go:88`) and populated via `s.userCache.Set(...)` (e.g. `store/user.go:98,122,132,143,167`), which uses the cache's default `Set` method — so **user entries get the 10-minute `DefaultTTL`**, with no custom per-entry TTL override (`SetWithTTL` is defined in the interface but not called for users).
