Mechanism: explicit Go code (application-level, within a DB transaction) — not a database-level cascade/trigger.

Evidence:
- `deleteUserTargetsTx` in each driver (`store/db/mysql/user_delete.go:92-127`, `store/db/postgres/user_delete.go:92-127`, `store/db/sqlite/user_delete.go:92-127`) explicitly calls two reaction-deletion helpers as part of the `DeleteUser` transaction:
  - `deleteReactionsByContentIDsTx` (mysql:417-425, postgres:380-388, sqlite:380-388) — `DELETE FROM reaction WHERE content_id IN (...)` for the content IDs of memos/comments owned by the user being deleted (removes reactions *on* the user's content, made by anyone).
  - `deleteReactionsByCreatorTx` (mysql:437-440, postgres:400-403, sqlite:400-403) — `DELETE FROM reaction WHERE creator_id = ?` (removes reactions *made by* the user being deleted, on anyone's content).
- Both calls happen inside `DeleteUser` (mysql:29-59, postgres/sqlite same shape), which runs in a single `*sql.Tx` (`d.db.BeginTx` ... `tx.Commit()`), so reaction cleanup is committed atomically with the rest of user deletion.
- No `ON DELETE CASCADE` or trigger was found governing this — the code manually issues `DELETE FROM reaction` statements rather than relying on FK cascade behavior at the schema level (I did not find/inspect the raw SQL schema/migration files to double-check `reaction`'s FK constraints, but the presence of explicit, batched `DELETE FROM reaction` calls guarded by app logic — including batching via `deleteUserBatches`/`deleteUserInClause` — indicates this is intentionally handled in Go rather than left to the DB).

So: covers both directions (reactions the deleted user made, and reactions on the deleted user's content) via explicit Go-level DELETE statements inside the transaction.
