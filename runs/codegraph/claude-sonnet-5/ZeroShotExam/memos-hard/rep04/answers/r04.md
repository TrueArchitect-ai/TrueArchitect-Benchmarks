Neither — this codebase (usememos/memos) uses no external message broker at all for webhook delivery. There is no NATS or RabbitMQ integration anywhere in the webhook path.

**Actual mechanism:** Webhook delivery is handled by an in-process, in-memory Go channel used as a bounded worker queue:

- `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a buffered channel (capacity 128) declared as a package-level var.
- `internal/webhook/webhook.go:42-55` (`init()`) — spawns 4 goroutines that range over `asyncPostQueue` and call `Post(payload)` for each item; this is the "worker pool."
- `internal/webhook/webhook.go:184-196` (`PostAsync`) — the producer side: does a non-blocking `select` send into `asyncPostQueue`, dropping (and logging a warning for) the payload if the channel is full rather than blocking.
- Callers such as `dispatchMemoRelatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:48`) and `DispatchMemoCommentCreatedWebhook` (`server/router/api/v1/memo_service_webhooks.go:30`) enqueue payloads via `webhook.PostAsync(payload)`.
- `Post` itself (`internal/webhook/webhook.go:120`) does a plain `http.NewRequest("POST", ...)` + `safeClient.Do(req)` to deliver the webhook over HTTP directly to the configured URL — no broker, no persistent queue, no cross-process delivery guarantee.

So "queue" here means a Go channel inside the single memos server process, not a message broker's declared queue/exchange.
