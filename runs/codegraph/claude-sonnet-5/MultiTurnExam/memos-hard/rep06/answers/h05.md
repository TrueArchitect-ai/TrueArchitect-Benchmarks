**Evidence locations:**
- `deleteUserTargetsTx` in each driver's `user_delete.go` explicitly calls two reaction-deletion steps before deleting anything else:

  Present identically in all three backends:
  - `store/db/mysql/user_delete.go:96,102`
  - `store/db/postgres/user_delete.go:96,102`
  - `store/db/sqlite/user_delete.go:96,102`

- These run inside `DeleteUser` (`store/db/{mysql,postgres,sqlite}/user_delete.go:29-59`), which wraps the whole deletion in a single `sql.Tx` (`d.db.BeginTx` at line 30, committed at line 51), so reaction cleanup is transactional with the rest of the user deletion — consistent with there being no DB-level `ON DELETE CASCADE` doing this implicitly (the code wouldn't need to explicitly delete rows a cascade already removes, and the manual ordering — reactions before memos/attachments/settings/user row — is exactly what's needed when no cascade exists).
