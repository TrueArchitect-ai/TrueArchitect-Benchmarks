Combining `store.Memo` deletion path (memo_relation cleanup, attachment deletion) with the DB-level schema cascade for memo_share:

q26.
- `memo` — the row itself is deleted (`DELETE FROM memo WHERE id = ?`, e.g. store/db/sqlite/memo.go:237)
- `memo_relation` — explicitly deleted by app code before the memo row, both directions (`store.DeleteMemoRelation` calls in store/memo.go:142-147)
- `attachment` — explicitly deleted by app code (`s.ListAttachments`/`s.DeleteAttachment` loop, store/memo.go:149-157)
- `memo_share` — cascades automatically at the DB level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/sqlite/LATEST.sql:109)
- child comment `memo` rows — deleted recursively by the API handler before the parent (`server/router/api/v1/memo_service.go:567-577`, which itself repeats the `memo`/`memo_relation`/`attachment` cascade for each comment)

Note: `reaction` rows referencing the memo are only read (for the webhook payload) in the handler, not explicitly deleted — no cascade/FK for `reaction.content_id` was found in the schema, so this may be a latent orphan-row gap rather than an intentional omission.
