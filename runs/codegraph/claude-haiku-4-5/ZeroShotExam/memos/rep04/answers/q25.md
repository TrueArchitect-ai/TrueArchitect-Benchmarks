The filter is parsed using **CEL (Common Expression Language)**, implemented in `internal/filter/engine.go`. The mechanism is: CEL parses the filter expression into an AST, which is converted into a dialect-agnostic condition tree via `buildCondition()` (internal/filter/parser.go), then the condition tree is rendered into dialect-specific SQL by `renderer.Render()` (internal/filter/render.go) which handles SQLite, MySQL, and PostgreSQL dialects differently based on `DialectName`.

**Engine location**: `internal/filter/engine.go:14` (the `Engine` struct which wraps a CEL environment)

**Process flow**:
1. `Engine.Compile()` parses filter string using CEL → AST → ParsedExpr
2. `buildCondition()` converts ParsedExpr to condition tree (Condition interface with multiple implementations)
3. `Program.Render()` converts condition tree to SQL via `renderer.Render()` which dispatches on condition type and dialect

**Dialect handling**: `RenderOptions.Dialect` (type `DialectName` at internal/filter/schema.go:11) controls SQL generation; the renderer generates appropriate SQL syntax for each dialect (DialectSQLite, DialectMySQL, DialectPostgres) in internal/filter/render.go.
