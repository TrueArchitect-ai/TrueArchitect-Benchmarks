**Premise correction:** There is no Redis connection for the cache layer. The repository does not use Redis.

**Actual mechanism:** The cache layer has two distinct implementations:

1. **RSS feed cache** (`server/router/rss/rss.go:35-50`) — an in-process, in-memory cache using a Go map (`cache map[string]*cacheEntry`) with a **1-hour TTL** (`defaultCacheDuration = 1 * time.Hour` at line 25). This cache stores RSS feed content with ETags and has a maximum of 50 cached entries with LRU eviction (lines 378-390).

2. **User cache** (`store/user.go:88-90, 98, 122, 132, 143, 167`) — a generic cache interface (`s.userCache`) used to cache user objects by ID. The cache key is the user ID as a string (`userCacheKey(user.ID)` at line 88). The actual TTL configuration for user entries is not defined in the user-facing code; it depends on the concrete cache implementation injected into the `Store` struct (likely configured via `store/cache/cache.go`), but no Redis configuration is visible in the codebase—this appears to be an in-process memory cache with a configurable default TTL set elsewhere.
