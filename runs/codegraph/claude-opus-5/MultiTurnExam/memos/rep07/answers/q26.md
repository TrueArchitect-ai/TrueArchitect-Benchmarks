**Tables written to when `DeleteMemo` runs:**

- **`memo`** — the row itself, plus (via the API handler) the rows of any comment memos, which are deleted recursively through the same path. `store/memo.go:158`, `store/db/sqlite/memo.go:237`; comment sweep at `server/router/api/v1/memo_service.go:566-577`.
- **`memo_relation`** — all rows where the memo is either `memo_id` or `related_memo_id`, deleted explicitly before the memo row. `store/memo.go:142-147`.
- **`attachment`** — every attachment with `memo_id = <memo>`, deleted one by one (each also removes the backing file/object from local or S3 storage). `store/memo.go:148-157`, `store/attachment.go:132-149`.
- **`memo_share`** — by DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:106`). Caveat worth flagging: the SQLite driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade is not enforced and `memo_share` rows are left orphaned — there is no explicit `DeleteMemoShare` call in the delete path.

**Not touched:** `reaction` — reactions are only read at the API layer to build the webhook payload (`server/router/api/v1/memo_service.go:545`), never deleted, and the `reaction.content_id` link has no FK.
