`Store.DeleteMemo` (`store/memo.go:140-159`) removes, in this order, before issuing the `DELETE FROM memo`:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `FindAttachment{MemoID:…}` and deleted one by one (`store/memo.go:148-157`); each `Store.DeleteAttachment` (`store/attachment.go:132`) also deletes the underlying stored file/object via `DeleteAttachmentStorage` before removing the `attachment` row.

Only then does it call the driver's `DeleteMemo`, which is a plain `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237`).

Above that, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first finds all comment memos (`memo_relation` rows of type `COMMENT` pointing at this memo) and deletes each of those memos through the same `Store.DeleteMemo` path, so their relations and attachments go too (`server/router/api/v1/memo_service.go:566-577`). Reactions are read at the API layer only to build the webhook payload — they are not explicitly deleted.
