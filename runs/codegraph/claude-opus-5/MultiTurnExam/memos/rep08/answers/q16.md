`Store.DeleteMemo` (`store/memo.go:140-159`) performs these cleanups before calling the driver's row delete:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `FindAttachment{MemoID: ...}` and deleted one by one (`store/memo.go:149-157`)

Only then does it call `s.driver.DeleteMemo(ctx, delete)` (`store/memo.go:158`), whose dialect implementations issue a plain `DELETE FROM memo WHERE id = ?` with no further cascading (e.g. `store/db/sqlite/memo.go:237-248`).

One thing to note: reactions are *not* deleted here. The API handler at `server/router/api/v1/memo_service.go:518` lists reactions only to build the webhook payload (`:545`), so `reaction` rows keyed on the memo's resource name are left behind by this path.
