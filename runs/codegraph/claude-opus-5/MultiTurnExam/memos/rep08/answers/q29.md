**web/src/connect.ts; short-lived JWT access tokens (in-memory, `Authorization: Bearer …`) + an HttpOnly refresh-token cookie — with Personal Access Tokens as a third kind the backend accepts; server/auth**

**Interceptor** — `authInterceptor` at `web/src/connect.ts:156`, installed on the shared Connect transport (`:188`). Per request it fetches a token via `getRequestToken()` (`:124`), sets `Authorization: Bearer <token>` (`:97-100`), and on a `Code.Unauthenticated` response refreshes once and replays the request with an `X-Retry` header to prevent loops (`:164-177`), redirecting to sign-in if the refresh fails.

**Tokens it manages:**
- *Access token* — held in memory by `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`/`isTokenExpired`), refreshed proactively when within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry (`connect.ts:140`) and reactively on 401.
- *Refresh token* — an HttpOnly cookie, never read by JS; sent because the transport uses `credentials: "include"` (`:57-62`). Refresh goes through `refreshAuthClient.refreshToken({})` on a separate interceptor-free transport to avoid recursion (`:65-83`), deduplicated by `tokenRefreshManager` (`:30-51`).

**Backend validation — `server/auth/`** (`server/auth/authenticator.go`): `AuthenticateByAccessTokenV2` (`:41`), `AuthenticateByRefreshToken` (`:61`, checked against the DB), and `AuthenticateByPAT` (`:102`, prefix-matched and hash-looked-up). `resolveBearer` (`:149`) picks JWT vs. PAT by prefix; `AuthenticateToUser` (`:190`) tries the Authorization header then falls back to the refresh cookie. Token parsing/minting lives in `server/auth/token.go`, header/cookie extraction in `server/auth/extract.go`.

This is invoked from the API layer at `server/router/api/v1/authz.go:44` (`Authenticate`), wired into the Connect path via `server/router/api/v1/connect_interceptors.go` and the gRPC-Gateway path via the middleware in `server/router/api/v1/v1.go`.
