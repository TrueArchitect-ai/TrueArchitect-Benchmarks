`Store.DeleteMemo` (`store/memo.go`) does the following, in order, before the memo row:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}`
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}`
3. **`attachment` rows linked to the memo** — listed via `ListAttachments{MemoID}`, then each removed with `Store.DeleteAttachment`, which also **deletes the backing file/object in storage** (`DeleteAttachmentStorage`, `store/attachment.go`) before the DB row
4. Finally `driver.DeleteMemo` deletes the `memo` row itself.

One level up, `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first deletes **comment memos** — it lists `memo_relation` rows of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each child (`memo_service.go:567-577`), so every comment goes through the same relation + attachment cascade before the parent is removed.

Worth flagging: reactions are *not* deleted. The handler lists them (`memo_service.go:545`) only to build the webhook payload, and `reaction` rows key off `ContentID` (the memo resource name) with no cascade in either layer — so they're left orphaned after a memo delete.
