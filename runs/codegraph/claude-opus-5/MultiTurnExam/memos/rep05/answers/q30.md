All four are defined in `server/router/api/v1/memo_service_webhooks.go:15,20,25,30`. Call sites:

| Event | Dispatched from |
|---|---|
| created | `APIV1Service.CreateMemo` — `server/router/api/v1/memo_service.go:157` |
| updated | `dispatchMemoUpdatedSideEffects` — `server/router/api/v1/memo_update_helpers.go:67`, reached from `UpdateMemo` (`memo_service.go:513`), `SetMemoAttachments` (`memo_attachment_service.go:48`), and `SetMemoRelations` (`memo_relation_service.go:48`) |
| deleted | `APIV1Service.DeleteMemo` — `server/router/api/v1/memo_service.go:562` (fired *before* the rows are removed, so the payload can still be built) |
| comment created | `APIV1Service.CreateMemoComment` — `server/router/api/v1/memo_service_comments.go:119`, targeting the parent memo's creator |

**Convergence:** the first three funnel through the shared helper `dispatchMemoRelatedWebhook` (`memo_service_webhooks.go:48`), which resolves the memo creator and loads their hooks; the comment variant (`:30`) does the same lookup against the parent memo's creator ID instead. Both then build a `webhook.WebhookRequestPayload` per hook and call **`webhook.PostAsync`** (`memo_service_webhooks.go:43` and `:71`) — the single delivery entry point, in **`internal/webhook/webhook.go:184`**, which enqueues onto a bounded channel drained by four worker goroutines that invoke `webhook.Post` (`internal/webhook/webhook.go:120`) for the actual signed HTTP POST.

Note there is no reaction webhook — reaction events go only to SSE, not to webhooks.
