The only entry in `startBackgroundRunners` (`server/server.go:153-174`) is the s3presign runner: `RunOnce(ctx)` inline at :163 (so presigned S3 URLs are refreshed immediately at boot), then `Run(s3Context)` in a tracked goroutine at :167. `Run` is a plain `time.NewTicker(12h)` select loop (`s3presign/runner.go:29-40`). Shutdown cancels the stored context and waits on the WaitGroup (`server.go:140-143`).

The webhook workers are a different shape — `init()` in `internal/webhook/webhook.go:42-54` spawns 4 permanent goroutines consuming `asyncPostQueue`; they have no scheduling and no shutdown hook (the queue drops with a warning when full).

**Unused scheduling infrastructure — two items:**

1. **`internal/scheduler`** is a complete cron-style scheduler package — `Schedule`/`fieldMatcher` cron parser supporting 5- and 6-field expressions (`parser.go:13-24`), plus `scheduler.go`, `job.go`, `middleware.go`, a `README.md` and `doc.go` — and **nothing in the server imports it**. The only importers are its own `example_test.go` and `integration_test.go`.
2. **`memopayload.Runner`** (`server/runner/memopayload/runner.go:14`) exists with a batched `RunOnce` that rebuilds every memo's payload, but `memopayload.NewRunner` is never called anywhere. Only the package's standalone helper `RebuildMemoPayload` is used, inline from the API layer (`server/router/api/v1/memo_service.go:108` and `:447`). So `server/runner/` contains two runners while the server starts just one.
