**Tables written by a `DeleteMemo`: `memo_relation`, `attachment`, `memo`** (plus `memo_share` only on engines that enforce foreign keys — see the caveat below).

Ordered by what runs, per `Store.DeleteMemo` (`store/memo.go`) and `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):

| Table | How it's affected |
|---|---|
| `memo_relation` | Two explicit deletes — rows where the memo is the source (`MemoID`) and where it's the target (`RelatedMemoID`) |
| `attachment` | Rows with `memo_id` = this memo, listed then deleted one-by-one via `Store.DeleteAttachment` (`store/attachment.go`), which also removes the backing file/object from storage |
| `memo` | The row itself — `DELETE FROM memo WHERE id = ?` in `store/db/sqlite/memo.go` (and mysql/postgres equivalents). Comment memos are additional `memo` rows: the API handler deletes each child memo through the same cascade first (`memo_service.go:567-577`) |
| `memo_share` | Declared `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the schema (`store/migration/sqlite/LATEST.sql:109`), so it cascades at the DB level — but **not on SQLite**, where the connection opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`). There is no explicit Go-side cleanup of `memo_share` in the delete path, so on the default SQLite deployment those rows are orphaned |

Also worth flagging: `reaction` rows are **not** touched. The handler lists them (`memo_service.go:545`) only to build the webhook payload, and the table keys off `content_id` (the memo resource name) with no FK and no explicit delete — so reactions survive the memo they belong to on all three dialects.
