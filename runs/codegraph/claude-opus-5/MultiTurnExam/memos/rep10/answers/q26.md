**Tables written by the delete path:** memo, memo_relation, attachment

Breakdown:
- **memo_relation** — deleted twice in `Store.DeleteMemo`, once as source (`MemoID`) and once as target (`RelatedMemoID`): `store/memo.go:142,145`
- **attachment** — every attachment with `MemoID` is deleted individually (`store/memo.go:149-157`), which also removes the underlying local/S3 blob via `Store.DeleteAttachment` (`store/attachment.go:132-148`)
- **memo** — the row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`, plus the postgres/mysql equivalents)

The API handler deletes comment memos first (relations of type `comment`), so the same three tables are hit again per comment: `server/router/api/v1/memo_service.go:566-577`.

Two caveats worth noting:
- **memo_share** has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`), but SQLite opens the connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite those rows are **not** cascaded — they're orphaned; on Postgres/MySQL they are removed by the engine.
- **reaction** rows are keyed by the memo's resource name (`content_id`) with no FK and no explicit delete, so they are left behind; the handler only reads them to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`).
