**Interceptor: `web/src/connect.ts` (the `authInterceptor`, lines 156-178, installed on the shared Connect transport at lines 184-189); token kinds: short-lived JWT access token (in-memory/localStorage, sent as `Authorization: Bearer …`) + long-lived refresh token (HttpOnly cookie, sent via `credentials: "include"`), with Personal Access Tokens as an alternative bearer for programmatic clients; backend package: `server/auth/`**

How it works:
- `authInterceptor` calls `getRequestToken()` (`web/src/connect.ts:124`), which preflight-refreshes when the access token is expired or missing, sets `Authorization: Bearer <token>`, and on a `Code.Unauthenticated` response refreshes once and retries with an `X-Retry` marker, redirecting on failure (`redirectOnAuthFailure`). Token storage/expiry helpers are in `web/src/auth-state.ts`.
- Refresh goes through a dedicated interceptor-free transport and `refreshAuthClient.refreshToken({})` (`web/src/connect.ts:65-91`), deduplicated by `tokenRefreshManager`; the refresh token itself rides in the cookie because `fetchWithCredentials` sets `credentials: "include"` (line 57).
- **Backend validation: `server/auth/`** — `Authenticator.AuthenticateByAccessTokenV2` (JWT, `authenticator.go:41`), `AuthenticateByRefreshToken` (validated against the DB, line 61), `AuthenticateByPAT` (hash lookup + expiry, line 102), and `AuthenticateToUser`/`Authenticate` (line 190/210) which try the Authorization header first, then the refresh-token cookie. JWT signing/parsing and PAT hashing live in `server/auth/token.go`, header/cookie extraction in `server/auth/extract.go`.
- It's hooked into request handling by `server/router/api/v1/authz.go:44` (`Authenticate`), used by the Connect interceptors (`server/router/api/v1/connect_interceptors.go`) and the gRPC-Gateway middleware in `server/router/api/v1/v1.go`. The sign-in/refresh RPCs that mint these tokens are in `server/router/api/v1/auth_service.go` and `auth_service_session.go`.
