`Store.DeleteMemo` (`store/memo.go`) performs this cleanup before calling `driver.DeleteMemo` on the memo row:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}`
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}`
3. **Attachments linked to the memo** — it lists them via `FindAttachment{MemoID: ...}` and calls `Store.DeleteAttachment` on each; that in turn deletes the backing blob/file from storage (`DeleteAttachmentStorage`, `store/attachment.go`) before removing the `attachment` row.

Additional context on the API path (`APIV1Service.DeleteMemo`, `server/router/api/v1/memo_service.go:518`): before invoking the store, it dispatches the memo-deleted webhook, then deletes each **comment memo** (memos related by `MemoRelationComment`) via its own `Store.DeleteMemo` call — so each comment gets the same relation + attachment cleanup — and finally broadcasts an SSE delete event.

Note that reactions are only *read* there (to build the webhook payload); neither the handler nor `Store.DeleteMemo` deletes `reaction` rows, so reactions keyed to the memo's resource name are left behind.
