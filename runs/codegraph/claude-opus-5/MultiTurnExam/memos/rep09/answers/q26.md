Tables written when `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518` → `store/memo.go:140`):

```
memo             (the memo row itself, plus each comment memo — deleted recursively)
memo_relation    (rows where memo_id = id AND rows where related_memo_id = id)
attachment       (all rows with memo_id = id)
memo_share       (DB-level ON DELETE CASCADE — postgres/mysql only; see caveat)
```

Where each happens:

- **memo** — `store/memo.go:158` (`DELETE FROM memo`, e.g. `store/db/sqlite/memo.go:237`); comment memos are deleted first by the handler looping over comment relations at `server/router/api/v1/memo_service.go:567-577`, each re-entering the same cascade.
- **memo_relation** — both directions cleaned at `store/memo.go:142` and `:145`.
- **attachment** — listed and deleted at `store/memo.go:148-157` via `Store.DeleteAttachment` (`store/attachment.go:132`), which also removes the underlying local file or S3 object before the row.
- **memo_share** — no Go code deletes these; it relies on `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`).

Two caveats worth flagging:

- **On SQLite that cascade does not fire.** The connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`, deliberate per the comment at `:39-41`), so `memo_share` rows are left orphaned there.
- **`reaction` is never touched.** Reactions are keyed by `content_id` (the memo resource name) with no foreign key, and nothing in the delete path removes them — `server/router/api/v1/memo_service.go:545` only reads them for the webhook payload.
