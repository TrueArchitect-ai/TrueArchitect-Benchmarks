Before the `memo` row is deleted, the store layer removes:

1. **Comment memos** (child memos linked by a `comment` relation) — the API handler lists `memo_relation` rows of type comment pointing at this memo and calls `Store.DeleteMemo` on each, recursively applying the same cleanup: `server/router/api/v1/memo_service.go:567-577`
2. **memo_relation rows where this memo is the source** (`memo_id = id`) — `store/memo.go:142`
3. **memo_relation rows where this memo is the target** (`related_memo_id = id`) — `store/memo.go:145`
4. **attachment rows linked to the memo**, each via `Store.DeleteAttachment` — `store/memo.go:148-157`
5. **The attachment's stored blob/file** (local file removed from disk, or the S3 object), done inside `Store.DeleteAttachment` → `DeleteAttachmentStorage` before the DB row goes: `store/attachment.go:141-148`, `store/attachment.go:202-223`

Only then does `Store.DeleteMemo` call the driver's `DELETE FROM memo` (`store/memo.go:158`, e.g. `store/db/sqlite/memo.go:237`).

Worth noting: **reactions are not deleted.** `server/router/api/v1/memo_service.go:545` lists them only to build the webhook payload, and nothing in this path removes `reaction` rows — they're keyed by `content_id` (the memo resource name) with no FK, so they're left orphaned.
