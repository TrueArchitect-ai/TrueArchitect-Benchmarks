`Store.DeleteMemo` (`store/memo.go:140-158`) performs this cleanup before calling `driver.DeleteMemo` on the memo row:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments{MemoID}` and deleted one by one (`store/memo.go:149-157`); each `Store.DeleteAttachment` also removes the backing file/object from storage first (`store/attachment.go:132-148`)

Additionally, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) deletes **comment memos** before deleting the target memo: it lists `memo_relation` rows of type `comment` pointing at this memo and calls `Store.DeleteMemo` on each child memo (`server/router/api/v1/memo_service.go:566-576`), so each comment goes through the same relation/attachment cascade.

Note: reaction rows are only *read* there (to build the webhook payload, `server/router/api/v1/memo_service.go:544`); nothing in this path deletes them.
