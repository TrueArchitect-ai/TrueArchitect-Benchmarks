**Premise correction: there is no Redis anywhere in this repository.** No Redis client dependency in `go.mod`, and a case-insensitive grep for "redis" across all Go, mod, and YAML files returns zero hits. The cache layer is a hand-rolled, process-local in-memory cache — nothing is configured, connected, or persisted externally.

**Actual mechanism:**

- **Implementation**: `store/cache/cache.go` — a `Cache` struct backed by `sync.Map` plus an `atomic.Int64` item counter (line 66), satisfying a local `cache.Interface` (line 11). Entries are `item{value, expiration, size}` (line 34). A background goroutine sweeps expired entries on `CleanupInterval`, and `Close()` (line 187) stops it.
- **Configuration site**: `store.New` — `store/store.go:38-53`. The config is a hard-coded literal, not read from flags, env, or settings:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  - `OnEviction: nil`

  The same `cacheConfig` value constructs all three caches: `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`, fields declared at `:27-29`). `cache.DefaultConfig()` (`store/cache/cache.go:57`) happens to carry identical values but is not what the store uses.

- **TTL for user entries: 10 minutes**, inherited from `DefaultTTL`. Every user write goes through `Set` (not `SetWithTTL`), so no per-entry override exists: `store/user.go:98`, `:122`, `:132`, `:143`, `:167`, all keyed by `userCacheKey(user.ID)` (`store/user.go:88`).
- **Invalidation beyond TTL**: reads only hit the cache on ID lookups (`Store.GetUser`, `store/user.go:150`) — username/email lookups always fall through to the database. Deletion evicts explicitly (`store/user_delete.go:40`), and entries can also be dropped early by the 1000-item cap.

Consequence worth noting: because this is in-process memory, the cache is not shared across replicas — a horizontally scaled deployment would have each instance holding its own copy with up to 10 minutes of staleness.
