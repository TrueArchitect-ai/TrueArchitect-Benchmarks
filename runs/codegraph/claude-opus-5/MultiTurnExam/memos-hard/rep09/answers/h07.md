Notes on each hop:

- **Wiring**: the service is constructed and its routes registered at `server/server.go:81-82` (`fileserver.NewFileServerService(s.Profile, s.Store, s.Secret)`).
- **`serveUserAvatar`** (line 168) does an access gate first: if `s.Profile.AllowAnonymous()` is false, it requires a valid viewer via `getCurrentUser` and returns 401 otherwise (lines 173-181). So on a public instance, another user's avatar is served without authentication.
- **`getUserByUsername`** (line 715) is a one-line pass-through: `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})` — the `:identifier` path param is matched against `username`, not ID.
- **`Store.GetUser`** (`store/user.go:148`) consults `userCache` only when looking up by `ID`; a username lookup always falls through to `ListUsers`, then populates the cache keyed by the resolved ID (line 167).
- **`Store.ListUsers`** (`store/user.go:136`) delegates to the driver and warms the cache for each row.
- **Data layer**: the per-dialect `ListUsers` builds the `WHERE username = ?` query and scans `avatar_url` into `store.User.AvatarURL` (`store/db/sqlite/user.go:88-200`; equivalents in `store/db/postgres/user.go` and `store/db/mysql/user.go:147`).

The bytes never leave the `user` table: the avatar is stored inline as a base64 data URI in `user.avatar_url`, which the handler decodes with `parseDataURI` (fileserver.go:196), rejects unless the MIME type is in `avatarAllowedTypes` (fileserver.go:75, 201), then writes with security headers and `Cache-Control` via `c.Blob` (lines 205-209). No attachment/blob-storage hop is involved.
