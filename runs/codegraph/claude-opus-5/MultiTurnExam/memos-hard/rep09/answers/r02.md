**Premise correction: there is no per-user API rate-limiting middleware in this repository, so there is nothing to register and no request limits to report.**

What I checked:

- A case-insensitive grep for `ratelimit|rate_limit|rate limit|throttle|golang.org/x/time/rate` across all Go files returns exactly one hit, and it is a comment describing future work, not code: `internal/email/doc.go:86` — "Rate limit email sending to prevent abuse."
- `go.mod` has no rate-limiter dependency (no `golang.org/x/time`, no `echo`-contrib limiter, no `ulule/limiter`).
- The Echo middleware stack is two entries and neither limits requests: `middleware.Recover()` and `newCORSMiddleware(profile)` — `server/server.go:51-52`. No `middleware.RateLimiter` from Echo's own package is used.
- The Connect/gRPC interceptor chain is metadata → logging → recovery → auth, with no limiter: `server/router/api/v1/v1.go:133-138`.
- Login is not throttled either: no failed-attempt counter, lockout, or backoff exists in `server/router/api/v1/auth_service*.go` — the only near-match is a comment about identifying suspicious logins at `auth_service_session.go:277`.

**The related mechanisms that do exist** (concurrency caps and payload caps, not per-user request rates):

- `semaphore.NewWeighted(3)` for thumbnail generation and `semaphore.NewWeighted(2)` for image processing on the API service — `server/router/api/v1/v1.go:59-60`.
- `semaphore.NewWeighted(maxConcurrentThumbnails)` on the file server — `server/router/fileserver/fileserver.go:116`.
- A request body cap via `connect.WithReadMaxBytes(maxAPIRequestBytes)` — `server/router/api/v1/v1.go:141`.
- A bounded webhook dispatch queue (128 slots, drops when full) — `internal/webhook/webhook.go:39`.

These bound concurrent work and payload size process-wide; none of them tracks or limits requests per user, so a single authenticated account can issue unlimited API calls as far as this codebase is concerned. Rate limiting, if required, would have to come from a reverse proxy in front of the server.
