The URL the browser hits is `/file/users/{username}/avatar` — produced by the API when converting a user to protobuf: `userpb.AvatarUrl = fmt.Sprintf("/file/%s/avatar", userpb.Name)` at `server/router/api/v1/user_service_converters.go:36` (base64 data URIs are swapped for this URL to keep responses small).

Notes on each hop:

- **Route registration** — `FileServerService.RegisterRoutes` mounts the `/file` group and binds the avatar route (`fileserver.go:121-125`). The service is constructed and wired at `server/server.go:81-82`.
- **`serveUserAvatar`** (`fileserver.go:168-210`) — first applies an access gate: if `s.Profile.AllowAnonymous()` is false, it resolves the caller via `getCurrentUser` and 401s if there's no valid session/access token/PAT (`fileserver.go:173-181`). Then it takes the `:identifier` path param.
- **`getUserByUsername`** (`fileserver.go:715-717`) — a one-line wrapper issuing `store.FindUser{Username: &identifier}`. Note the route param is treated as a *username*, not the `users/{id}` resource name.
- **The data itself is not a file on disk.** The avatar lives in the user row's `avatar_url` column as a base64 data URI; `parseDataURI` (`fileserver.go:737`) splits out the MIME type and decodes the bytes, `avatarAllowedTypes` (`fileserver.go:75`) restricts them to PNG/JPEG/GIF/WebP, and the bytes go out via `c.Blob` (`fileserver.go:209`). So "stored data" here means the `user` table, not the attachment/blob store.
- **`Store.GetUser`** (`store/user.go:148`) — checks `userCache` only when looking up by ID; a username lookup always falls through to `ListUsers`.
- **`Store.ListUsers`** (`store/user.go:136`) — delegates to `s.driver.ListUsers` and populates the cache.
- **Driver dispatch** — `store.Driver` is the interface; the concrete implementation is selected by `db.NewDBDriver` (`store/db/db.go:14`). The SQLite implementation builds the `WHERE username = ?` clause at `store/db/sqlite/user.go:88` onward, with parallel implementations in `store/db/mysql/user.go` and `store/db/postgres/user.go`.
