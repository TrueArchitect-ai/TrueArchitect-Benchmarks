h05.

**Explicit Go code — two `DELETE FROM reaction` statements issued per driver inside the user-deletion transaction. No database-level cascade exists for reactions.**

Evidence:

**1. The explicit deletes.** `deleteUserTargetsTx` runs two reaction deletions before removing the user row:

- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the deleted user *made*.
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 — removes reactions *others* made on the deleted user's memos. The content IDs are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go:512`), matching how the `reaction.content_id` column stores memo references.

Both are called from `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:96` and `:102`), inside the single transaction opened by `DB.DeleteUser` (`store/db/sqlite/user_delete.go:29-59`).

**2. All three drivers do it, in parallel implementations** (this logic is duplicated per driver, not shared):
- sqlite — `store/db/sqlite/user_delete.go:380` (by content) / `:400` (by creator)
- mysql — `store/db/mysql/user_delete.go:417` / `:437`, called at `:96` / `:102`
- postgres — `store/db/postgres/user_delete.go:380` / `:400`, called at `:96` / `:102`

**3. No DB-level rule could be doing it.** The `reaction` table is declared with no foreign keys at all — `creator_id` is a plain `INTEGER`/`INT` column in every schema:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`
- original creation: `store/migration/postgres/0.20/00__reaction.sql:2-8`, `store/migration/mysql/0.20/00__reaction.sql:2-8`

Grepping `REFERENCES|CASCADE` across `store/migration/` shows cascades exist for other tables (e.g. `memo_share.memo_id → memo(id) ON DELETE CASCADE`, `store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`) but never on `reaction`. Historical SQLite migrations did have user cascades on some tables (`store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql`), but `reaction` postdates that file and was never given one — hence the explicit Go deletes.

One consequence worth flagging: because the content-ID delete keys on `"memos/"+UID`, it covers reactions on memos, and the creator delete covers everything that user reacted to. So both directions are handled — but only by Go code, meaning any future path that deletes a user row without going through `DB.DeleteUser` would orphan reaction rows.
