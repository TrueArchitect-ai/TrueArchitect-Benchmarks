**Premise correction: there is no Redis anywhere in this repository.** Grepping case-insensitively for `redis` across all Go sources, `go.mod`, and YAML config files returns zero hits — no client library, no connection string, no config key. The cache layer is entirely in-process.

**Actual mechanism.** Caching is a hand-rolled in-memory cache in `store/cache/cache.go`:

- `cache.Cache` (`store/cache/cache.go:66-72`) is a thread-safe map (`sync.Map` + an atomic item counter) behind the `cache.Interface` (`cache.go:11-32`), with a background cleanup goroutine stopped by `Close` (`cache.go:187`).
- `Config` (`cache.go:41-54`) carries `DefaultTTL`, `CleanupInterval`, `MaxItems`, and an `OnEviction` hook.

**Configuration site and user TTL.** The store builds one config and shares it across three caches in `store.New` (`store/store.go:38-58`):

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
...
instanceSettingCache: cache.New(cacheConfig),
userCache:            cache.New(cacheConfig),
userSettingCache:     cache.New(cacheConfig),
```

So **user entries expire 10 minutes after being written**, with a sweep every 5 minutes and a 1000-item cap per cache. There's no user-specific override: every `s.userCache.Set(...)` call (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`) uses `Cache.Set`, which forwards `c.config.DefaultTTL` to `SetWithTTL` (`store/cache/cache.go:93-95`). `cache.DefaultConfig()` (`cache.go:57-64`) declares the same values but isn't what the store uses — `store.New` constructs its own identical literal.

Two consequences worth noting: these values are hardcoded, not configurable by flag or env var; and because the cache is per-process, a multi-instance deployment would have independent caches with no cross-node invalidation — the very thing Redis would normally provide.
