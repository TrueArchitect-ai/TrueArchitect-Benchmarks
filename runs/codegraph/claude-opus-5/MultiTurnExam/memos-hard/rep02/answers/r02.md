**Premise correction: there is no rate-limiting middleware in this codebase — per-user or otherwise. No registration site and no limits exist to report.**

Evidence:

1. A case-insensitive grep for `rate.?limit|throttl|ratelimiter` plus `golang.org/x/time/rate` across all Go sources and `go.mod` returns exactly one hit, and it's a comment describing future work — not code: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"). There is no `x/time/rate` dependency and no third-party limiter package.
2. The full set of Echo middleware registered on the server is two entries, neither a limiter: `middleware.Recover()` and `newCORSMiddleware(profile)` — `server/server.go:51-52`. The only other `.Use(...)` calls in the backend are the frontend static-file handlers at `server/router/frontend/frontend.go:54` and `:59`.
3. The RPC interceptor chain has no limiter either — only `MetadataInterceptor` (`server/router/api/v1/connect_interceptors.go:22`), `LoggingInterceptor` (`:98`), and the auth/authz interceptors (`server/router/api/v1/authz.go`).

**What does exist, and is easy to mistake for rate limiting** — concurrency caps, which bound simultaneous work rather than request rate, and are global rather than per-user:

- `thumbnailSemaphore` — `semaphore.NewWeighted(3)`, at `server/router/api/v1/v1.go:59` and `server/router/fileserver/fileserver.go:116` (constant `maxConcurrentThumbnails = 3`, `fileserver.go:46`).
- `imageProcessingSemaphore` — `semaphore.NewWeighted(2)` at `server/router/api/v1/v1.go:60`.
- The webhook dispatch queue is bounded at 128 with 4 workers and drops on overflow (`internal/webhook/webhook.go:39-55`) — backpressure on outbound calls, not inbound throttling.

So a client can issue unlimited API requests as far as this server is concerned; any rate limiting would have to come from a reverse proxy in front of it.
