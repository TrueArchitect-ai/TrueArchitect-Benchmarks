Enforcement is spread across eight distinct surfaces, using three different mechanisms: **per-memo gate checks**, **query-level filters injected before the store call**, and **push-delivery filters**.

Notes on the semantics, since the sites don't all agree:

- **`checkMemoReadAccess`** (`memo_service.go:39-67`) is the canonical gate: archived memos are creator-only; non-public memos require authentication; `PRIVATE` requires being the creator. Notably it does **not** grant admins access to others' private memos.
- **Other sites do grant admin override** — `fileserver.go:699` (`user.Role != store.RoleAdmin`), `sse_hub.go:136` (`c.role == store.RoleAdmin`), `canViewerAccessMemo` (`isSuperUser`), and the reaction/attachment gates (`isSuperUser(user)`). That inconsistency with `checkMemoReadAccess` is real, not a reading artifact.
- **Share tokens are a deliberate bypass**: `fileserver.go:684-690` allows attachment access for a valid, non-expired `share_token` matching that memo, and `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:153`) serves a memo by token rather than by visibility.
- **The filter-based sites push enforcement into SQL** via `memoFind.VisibilityList` or a CEL-style `Filters` string, so they never load disallowed rows — as opposed to the gate sites, which load then reject.
- `server/notification/email.go:313-316` applies the same PRIVATE/PROTECTED test when deciding how much memo content to put in an outbound email; it's content redaction rather than access control, so I've listed it separately here rather than as an enforcement site.
