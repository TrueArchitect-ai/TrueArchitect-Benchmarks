**No. `mysql.NewDB` has exactly one call site, and it is inside the factory.**

Evidence:

1. `grep -rn "NewDB" --include=*.go .` across the repo returns a single call to `mysql.NewDB` — `store/db/db.go:22`, inside the `case "mysql":` arm of `NewDBDriver` (`store/db/db.go:14-31`). The definition itself is `store/db/mysql/mysql.go:20`.
2. `store/db/mysql` is imported by exactly one file outside its own package: `store/db/db.go:8`. Grepping for `db/mysql` and `mysql.` while excluding `store/db/mysql/` produces no other package-level reference.
3. Everything else goes through the factory. Test setup uses `db.NewDBDriver(profile)` — `store/test/store.go:28`, `store/test/store.go:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70`.

Two near-misses that are *not* counterexamples:

- `store/db/mysql/mysql.go:17,30,73` reference `mysql.Config` / `mysql.ParseDSN` — that's the upstream `github.com/go-sql-driver/mysql` package used inside our own mysql package, not our driver being constructed.
- `store/test/containers.go:42,101-105` uses `mysql.Run`, `mysql.WithDatabase`, etc. — that identifier resolves to `github.com/testcontainers/testcontainers-go/modules/mysql` (import at `store/test/containers.go:21`); the go-sql-driver import in that file is aliased `mysqldriver` (`containers.go:16`). It spins up a MySQL container, not our driver.

For contrast, the sibling SQLite driver *is* constructed directly outside the factory in two tests — `store/deployment_config_test.go:416` and `store/demo_seed_test.go:24` (`sqlite.NewDB(p)`) — which shows the grep would have surfaced such a call for MySQL had one existed.
