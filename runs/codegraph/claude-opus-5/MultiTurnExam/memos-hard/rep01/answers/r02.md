**Premise correction: there is no per-user API rate-limiting middleware in this codebase — it doesn't exist, so there is nothing registered and no request limits to report.**

What I checked:

- A case-insensitive grep for `ratelimit|rate_limit|rate limit|throttl|Limiter|golang.org/x/time/rate` across all Go sources and `go.mod` returns exactly one hit, and it's a comment describing future work, not code: `internal/email/doc.go:86` — "Rate limit email sending to prevent abuse". No `golang.org/x/time/rate` or any rate-limiter dependency is in `go.mod`.
- **Echo middleware actually registered** (`echoServer.Use`): only `middleware.Recover()` and `newCORSMiddleware(profile)` at `server/server.go:51-52`, plus static-file and SPA-fallback middleware on the frontend router at `server/router/frontend/frontend.go:54` and `:59`.
- **Connect/gRPC interceptor chain** — the full list is at `server/router/api/v1/v1.go:133-137`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor`. Those four are the only interceptor types declared in `server/router/api/v1/connect_interceptors.go` (lines 22, 98, 165, 208). None does rate limiting.

The limits that *do* exist are different mechanisms, in case one of them is what you were thinking of:

- **Request body size** — `connect.WithReadMaxBytes(maxAPIRequestBytes)` and `http.MaxBytesHandler(..., maxAPIRequestBytes)` at `server/router/api/v1/v1.go:140` and `:145`. That's a per-request byte cap, not a request-rate cap.
- **Concurrency caps on expensive work** — `thumbnailSemaphore: semaphore.NewWeighted(3)` and `imageProcessingSemaphore: semaphore.NewWeighted(2)` at `server/router/api/v1/v1.go:59-60`. These bound simultaneous image work process-wide; they're not per-user and impose no rate.
- **Webhook async queue** — a bounded 128-slot channel with 4 workers (`internal/webhook/webhook.go:39-55`), which sheds load by dropping, and is outbound rather than inbound.

If you want per-user rate limiting, it would need to be added — the natural insertion point is a new interceptor in the chain at `server/router/api/v1/v1.go:133`, since `AuthInterceptor` there already resolves the calling user.
