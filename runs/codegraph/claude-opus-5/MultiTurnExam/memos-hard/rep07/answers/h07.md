Notes on the path:

- **Wiring**: the file server is constructed and its routes registered at `server/server.go:81-82`.
- **Access check first**: when the instance is private (`!s.Profile.AllowAnonymous()`), `serveUserAvatar` requires an authenticated viewer via `s.getCurrentUser` before any lookup (`fileserver.go:173-181`).
- **Lookup key**: the `:identifier` path segment is used as a *username*, not an ID — `getUserByUsername` calls `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})` (`fileserver.go:716`).
- **Cache behavior**: `Store.GetUser` only short-circuits on the in-process user cache when `find.ID` is set (`store/user.go:149-156`). Since this path filters by username, it always falls through to `Store.ListUsers` → driver → SQL (`SELECT ... avatar_url ... FROM user WHERE username = ?`), then repopulates the cache (`store/user.go:142-144`, `:167`).
- **The stored data is the avatar itself**: `store.User.AvatarURL` (`store/user.go:43`) holds a base64 data URI, so the DB row *is* the image source — no filesystem or S3 hop. `parseDataURI` (`fileserver.go:737`) splits it into MIME type + bytes, the type is checked against `avatarAllowedTypes` (`fileserver.go:75`, `:201`), and the bytes go out via `c.Blob` with security and cache headers (`fileserver.go:205-209`). If `AvatarURL` is instead an external URL, the converter leaves it as-is (`user_service_converters.go:38`) and the browser never touches this handler.
