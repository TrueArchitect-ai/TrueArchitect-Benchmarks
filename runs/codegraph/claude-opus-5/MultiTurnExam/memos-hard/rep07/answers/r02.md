**Premise correction: there is no per-user API rate-limiting middleware in this repository — nothing to register, and no request limits to report.**

Evidence:

- A case-insensitive sweep for `ratelimit`, `rate_limit`, "rate limit", `throttl`, `Limiter`, and `golang.org/x/time/rate` across all Go files and `go.mod` returns exactly one hit, and it's an aspirational comment in package docs, not code: `internal/email/doc.go:86` — `//   - Rate limit email sending to prevent abuse`.
- The HTTP middleware chain is two entries long: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/server.go:51-52`). Nothing else is registered with `echoServer.Use`.
- The Connect/gRPC interceptor chain is likewise limited to metadata conversion, logging, panic recovery, and auth — `connect.WithInterceptors(NewMetadataInterceptor(), NewLoggingInterceptor(...), NewRecoveryInterceptor(...), NewAuthInterceptor(authorizer))` at `server/router/api/v1/v1.go:133-138`. No limiter interceptor exists.

What does exist, and may be what you're thinking of — these are resource guards, not per-user request-rate limits:

- **Request body size caps**: `http.MaxBytesHandler(..., maxAPIRequestBytes)` applied to the gRPC-gateway routes (`server/router/api/v1/v1.go:126-129`) and to the Connect mux (`:144`), plus `connect.WithReadMaxBytes(maxAPIRequestBytes)` (`:141`).
- **Concurrency semaphores**, which bound simultaneous work instance-wide rather than per user: thumbnail generation capped at 3 (`server/router/fileserver/fileserver.go:46`, `:116`), and in the API service `thumbnailSemaphore`/`imageProcessingSemaphore` weighted 3 and 2 (`server/router/api/v1/v1.go:58-59`).
- **A bounded webhook dispatch queue** (128 slots, 4 workers) that drops events under load (`internal/webhook/webhook.go:39`, `:42-55`) — outbound, not inbound.

If you need per-user rate limiting, it would have to be added; there's no existing site to configure.
