**`internal/idp` (abstraction); `internal/idp/oauth2` (implementation).**

- `internal/idp/idp.go` is the abstraction layer — it's a tiny package defining just `IdentityProviderUserInfo` (`Identifier`, `DisplayName`, `Email`, `AvatarURL`), the provider-neutral shape every IdP implementation must produce.
- `internal/idp/oauth2/oauth2.go` is the only concrete protocol implementation that ships. It defines `IdentityProvider` over `storepb.OAuth2Config` with `NewIdentityProvider` (`:27`), `ExchangeToken` (`:47`, including PKCE `code_verifier` support), and `UserInfo` (`:83`), which maps arbitrary userinfo claims into `idp.IdentityProviderUserInfo` via the configured `FieldMapping`.

Corroborating that OAuth2 is the only one: the stored provider type enum has exactly two values, `TYPE_UNSPECIFIED` and `OAUTH2` (`proto/gen/store/idp.pb.go:27-28`), and the SSO sign-in path branches on only that one case — `if identityProvider.Type == storepb.IdentityProvider_OAUTH2` in `server/router/api/v1/auth_service_sso.go:120-134`, the sole importer of `internal/idp/oauth2`.

Note that `internal/idp` defines no Go `interface` — the "abstraction" is the shared user-info struct plus the enum-driven dispatch in `auth_service_sso.go`, so adding a second protocol (OIDC, SAML) would mean a new enum value and a new branch there rather than satisfying an existing interface.
