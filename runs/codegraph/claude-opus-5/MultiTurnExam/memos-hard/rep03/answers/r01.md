**Premise correction: there is no Redis anywhere in this repository — no Redis client, no connection config, no dependency. The cache layer is a hand-rolled, in-process, in-memory cache. User entries get the shared default TTL of 10 minutes.**

Evidence for the correction:

- `grep -rni redis` across all Go/mod/yaml files returns zero hits, and `go.mod` has no Redis driver (no `go-redis`, `redigo`, etc.). There is no external cache process to configure — no host, port, DSN, or auth setting exists.

The actual mechanism:

- **Implementation**: `store/cache/cache.go` — a `Cache` struct backed by a `sync.Map` plus an atomic item counter (`store/cache/cache.go:66-72`), satisfying the local `cache.Interface` (`store/cache/cache.go:11-32`). Entries are `item{value, expiration, size}` (`cache.go:34-38`); a background goroutine sweeps expired entries on `CleanupInterval` and is torn down by `Close` (`store/cache/cache.go:187`).
- **Configuration site**: `store.New` in `store/store.go:37-45` — the config is a hardcoded literal, not read from flags, env, or a config file:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  - `OnEviction: nil`
  The same `cacheConfig` value is passed to all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:50-52`). `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) declares identical values but isn't what `store.New` calls; the literal is duplicated.
- **TTL for user entries**: **10 minutes.** Every user write goes through `s.userCache.Set(...)` — `store/user.go:98,122,132,143,167` — and `Set` forwards to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:94`). Nothing in the store calls `SetWithTTL` directly, so users have no custom TTL. Cache keys are `userCacheKey(user.ID)`, and note that `GetUser` only consults the cache when looking up by ID (`store/user.go:149-156`) — username/email lookups always hit the database.
- **Invalidation**: explicit deletion on user delete, `s.userCache.Delete(ctx, userCacheKey(userID))` at `store/user_delete.go:40`; plus size-based eviction once `MaxItems` is exceeded.

Practical consequence: because the cache is per-process memory, a multi-instance deployment does not share it, and stale user data can persist up to 10 minutes on instances that didn't perform the write.
