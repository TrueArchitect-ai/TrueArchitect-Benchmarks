**Premise correction: neither. There is no message broker in this codebase — no NATS, no RabbitMQ, no AMQP, Kafka, SQS, or Pub/Sub client — and therefore no queue declaration to point to. Grepping `nats|rabbitmq|amqp|kafka|sqs|pubsub` across every Go file and `go.mod` returns zero hits.**

Actual mechanism — an in-process, unbuffered-durability Go channel with a fixed worker pool, all inside `internal/webhook/webhook.go`:

- **The "queue"** is a package-level buffered channel of 128 payloads, declared at `internal/webhook/webhook.go:39`:
  `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`
- **The workers** are 4 goroutines started in the package `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. There is no consumer group, ack, or redelivery — a failed delivery is logged and dropped.
- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184-196`), called from the memo webhook dispatchers (`server/router/api/v1/memo_service_webhooks.go:43,71`). It does a non-blocking `select` send: if the buffer is full, the payload is **discarded** with a "Dropped webhook dispatch because the async queue is full" warning (`webhook.go:191-195`). A nil payload is likewise dropped (`webhook.go:185-188`).
- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`), which signs the body (Standard Webhooks HMAC headers) and issues the POST via the SSRF-guarded `safeClient` (`webhook.go:152`), with a 30s timeout.

Operational consequences that follow from there being no broker: the queue is per-process and in-memory, so pending webhooks are lost on restart or crash; there is no persistence, no retry/backoff, no dead-letter path, and no cross-instance distribution — each server instance delivers only what its own handlers enqueued. Concurrency is capped at 4 in-flight deliveries regardless of load.
