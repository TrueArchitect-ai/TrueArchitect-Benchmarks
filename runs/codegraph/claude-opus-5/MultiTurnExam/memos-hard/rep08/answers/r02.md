**Premise correction: there is no per-user API rate-limiting middleware in this repository — none is registered anywhere, and no request limits exist.**

Evidence:

- A repo-wide grep for `ratelimit` / `rate_limit` / `rate limit` / `throttl` / `golang.org/x/time/rate` across all Go files and `go.mod` returns exactly one hit, and it's an aspirational comment in documentation, not code: `internal/email/doc.go:86` — `//   - Rate limit email sending to prevent abuse`. There is no rate-limiter dependency in `go.mod`.
- The Echo middleware stack is short and fully enumerable: `middleware.Recover()` and `newCORSMiddleware(profile)` at `server/server.go:51-52`, plus static-file and SPA-fallback middleware in the frontend router (`server/router/frontend/frontend.go:54,59`). Nothing else is registered.
- The Connect/gRPC interceptor chain is likewise complete and contains no limiter — `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor` at `server/router/api/v1/v1.go:133-137` (definitions in `server/router/api/v1/connect_interceptors.go`).

What does exist, and is easy to mistake for rate limiting — these are **concurrency caps and payload size caps, not per-user request rates**:

- **`imageProcessingSemaphore`** — `semaphore.NewWeighted(2)` (`server/router/api/v1/v1.go:60`), acquired non-blockingly in `server/router/api/v1/attachment_service_image.go:68-75`. On contention it returns `codes.ResourceExhausted, "too many image processing requests"` (`server/router/api/v1/attachment_service.go:160`). This is a global limit of 2 in-flight image operations for the whole process, shared across all users.
- **`thumbnailSemaphore`** — `semaphore.NewWeighted(3)` in the API service (`server/router/api/v1/v1.go:59`) and `semaphore.NewWeighted(maxConcurrentThumbnails)` in the file server (`server/router/fileserver/fileserver.go:116`, acquired at `:448`). Again process-global, and it *blocks* rather than rejecting.
- **`connect.WithReadMaxBytes(maxAPIRequestBytes)`** — `server/router/api/v1/v1.go:141`, a per-request body size ceiling.
- **`webhook.asyncPostQueue`** — a 128-slot outbound queue with 4 workers (`internal/webhook/webhook.go:39-55`) that drops overflow; this bounds outbound webhook delivery, not inbound API traffic.

So the operative facts: no middleware to point at, no per-user accounting (nothing keys any limiter on user ID or IP), and no configurable request limits. Any rate limiting for a memos deployment would have to come from a reverse proxy in front of the server.
