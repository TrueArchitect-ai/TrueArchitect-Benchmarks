**Explicit Go code — two `DELETE FROM reaction` statements issued inside the per-driver `DeleteUser` transaction. There is no database-level cascade for reactions.**

Evidence locations:

**1. The explicit deletes.** Each driver's `DeleteUser` runs `deleteUserTargetsTx`, which removes reactions twice, in two different senses:
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing *everyone's* reactions on the deleted user's memos. Called at `store/db/sqlite/user_delete.go:96`, `store/db/postgres/user_delete.go:96`, `store/db/mysql/user_delete.go:96`; defined at `store/db/sqlite/user_delete.go:380`, `store/db/postgres/user_delete.go:380`, `store/db/mysql/user_delete.go:417`. The `content_id` values are built as `"memos/"+memo.UID` by `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go`, near the end of the file), batched 500 at a time (`deleteUserBatchSize`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing *the deleted user's own* reactions wherever they were left. Called at `store/db/sqlite/user_delete.go:102` (and `:102` in the postgres and mysql files); defined at `store/db/sqlite/user_delete.go:400`, `store/db/postgres/user_delete.go:400`, `store/db/mysql/user_delete.go:437`.

Both run before `deleteMemosTx` and `deleteUserRowTx` in the same `tx` opened at the top of `DeleteUser` (`store/db/sqlite/user_delete.go:29`), so the cleanup commits atomically with the user row.

**2. Why it can't be a DB rule.** The `reaction` table is declared with no foreign keys at all — `creator_id` and `content_id` are plain columns:
- `store/migration/sqlite/LATEST.sql:91-98` (and the original `store/migration/sqlite/0.20/00__reaction.sql`)
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

A repo-wide grep for `FOREIGN KEY` / `ON DELETE` across the `LATEST.sql` files returns exactly one hit per driver, and it is on a different table — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Note also that `content_id` is a text resource name (`memos/{uid}`), not an integer key, so a cascade from `memo` would not be expressible anyway — which is exactly why the Go code has to resolve memo UIDs to content IDs itself.

**3. Coverage.** The behavior is exercised by `store/test/user_delete_test.go` and `server/router/api/v1/test/user_service_delete_test.go`, both of which reference reactions.
