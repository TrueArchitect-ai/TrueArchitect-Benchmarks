Notes on the path:

- **Wiring:** the service is constructed and its routes registered during server startup — `fileserver.NewFileServerService(...)` / `RegisterRoutes(echoServer)` at `server/server.go:81-82`, deliberately before the gRPC-gateway.
- **The image isn't a file on disk.** The avatar is stored inline in the `user.avatar_url` column as a base64 data URI; `serveUserAvatar` reads `user.AvatarURL` (`fileserver.go:192`) and decodes it with `parseDataURI` (`fileserver.go:196`, definition at `:737`), then checks the MIME type against `avatarAllowedTypes` (`fileserver.go:75`, checked at `:201`) before writing the blob with security headers and `Cache-Control` (`fileserver.go:205-209`). So the data layer touched is the `user` table, not the attachment/blob path.
- **Caching hop:** `Store.GetUser` consults `s.userCache` only when looking up by ID (`store/user.go:149-156`); this lookup is by `Username`, so it always falls through to `ListUsers` → the driver, then populates the cache on the way back (`store/user.go:167`).
- **Access control:** on an instance with no `InstanceURL`, anonymous requests are rejected before the lookup (`fileserver.go:173-181`); when anonymous access is allowed, any user's avatar is public. There is a separate gRPC handler for the same data, `UserService/GetUserAvatar`, which is listed as an unauthenticated method in `server/router/api/v1/acl_config.go:25`.
