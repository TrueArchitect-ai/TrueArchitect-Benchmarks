**Premise correction: there is no Redis anywhere in this repository — no `redis` dependency in `go.mod`, no Redis import, config key, or connection code in any Go file. The cache layer is a hand-rolled in-process in-memory cache. User entries get a 10-minute TTL.**

The actual mechanism:

**Implementation.** `store/cache/cache.go` defines a self-contained thread-safe cache: an `Interface` (line 11) with `Set`/`SetWithTTL`/`Get`/`Delete`/`Clear`/`Size`/`Close`, and a `Cache` struct (line 66) backed by a `sync.Map` plus an `atomic.Int64` item counter. Entries are `item{value, expiration, size}` (line 35). A background goroutine sweeps expired entries on `CleanupInterval` and is stopped via `Close()` (`store/cache/cache.go:187`). Nothing crosses a network boundary — state is per-process and lost on restart.

**"Configuration"** is a plain Go struct literal, not a connection string. `cache.Config` (line 41) has `DefaultTTL`, `CleanupInterval`, `MaxItems`, `OnEviction`. It's set in exactly one production place — `store.New` at `store/store.go:39-44`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

These values are hardcoded — no flag, env var, or `Profile` field feeds them, so they can't be tuned at deploy time. `cache.DefaultConfig()` (`store/cache/cache.go:57`) returns the identical values but has no production caller; `store.New` duplicates the literal instead.

**Three caches, one shared config**, all constructed at `store/store.go:51-53`: `instanceSettingCache`, `userCache`, and `userSettingCache` (fields at `store/store.go:26-29`).

**TTL for user entries: 10 minutes.** `userCache` is created with that same `cacheConfig`, and every write goes through `Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), which forwards to `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:93-95`). No call site uses `SetWithTTL` with a custom duration, so 10 minutes applies uniformly. Entries can also leave early via the 1000-item cap or explicit invalidation — `s.userCache.Delete(...)` on user deletion (`store/user_delete.go:40`).

One behavioral detail worth knowing: the user cache is keyed by ID only (`userCacheKey`, `store/user.go:88`), and `Store.GetUser` consults it *only* when the lookup is by `ID` (`store/user.go:149-156`) — lookups by username or email always hit the database and then repopulate the cache.
