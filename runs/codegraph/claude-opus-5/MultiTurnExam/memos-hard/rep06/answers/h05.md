**Explicit Go code — in the `DeleteUser` transaction of each SQL driver; there is no FK/cascade on the `reaction` table.**

What I checked:

**1. The delete path.** `Store.DeleteUser` (`store/user.go:171`) just delegates to `s.driver.DeleteUser`. Each driver implements it as one transaction: `store/db/sqlite/user_delete.go:29`, `store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`. The work happens in `deleteUserTargetsTx` (e.g. `store/db/sqlite/user_delete.go:89`), which deletes reactions in **two** explicit steps, before the memos and the user row are removed:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500, over the `memos/{uid}` content IDs of the user's whole memo tree (including comment descendants gathered by the recursive CTE at `store/db/sqlite/user_delete.go:128`). Definition: `store/db/sqlite/user_delete.go:377`; called at `:92`.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user left on *other* people's memos. Definition: `store/db/sqlite/user_delete.go:398`; called at `:98`.

Both exist identically in the other two drivers: `store/db/mysql/user_delete.go:417,437` (called at `:96,:102`) and `store/db/postgres/user_delete.go:380,400` (called at `:96,:102`).

**2. The schema, to rule out a database-level rule.** The `reaction` table carries no foreign key or `ON DELETE CASCADE` in any dialect — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:90-98`, `store/migration/mysql/LATEST.sql:91-98`, and originally `store/migration/sqlite/0.20/00__reaction.sql:2-9`. A repo-wide grep for `FOREIGN KEY|REFERENCES|ON DELETE` across `store/migration/` returns cascades only for `memo_share.memo_id` (`store/migration/*/LATEST.sql:108-109`, `store/migration/postgres/0.27/04__memo_share.sql:11`) and for the pre-0.20 tables in `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql` — `reaction` postdates that migration and was never given one. Note also that `content_id` is a text `memos/{uid}` reference, not an integer FK, so a cascade wouldn't be expressible there anyway.

So removal is entirely application-driven; if a row were inserted outside this code path it would be orphaned rather than cleaned up by the database.
