**Premise correction: there is no per-user API rate-limiting middleware in this repository — no rate limiter of any kind, so there are no request limits to report.**

Evidence:

- A case-insensitive grep across all Go files and `go.mod` for `ratelimit`, `rate_limit`, "rate limit", `throttl`, and `golang.org/x/time/rate` yields exactly one hit, and it's an aspirational comment, not code: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"). Echo's `middleware.RateLimiter` is never imported or used.
- The full Echo middleware stack is two entries, registered in `NewServer`: `middleware.Recover()` at `server/server.go:51` and `newCORSMiddleware(profile)` at `server/server.go:52` (`server/cors.go:13`). The frontend service adds only static-file and SPA-fallback middleware (`server/router/frontend/frontend.go:54,59`).
- The API's Connect/gRPC interceptor chain is likewise limiter-free — `server/router/api/v1/v1.go:133-138`: `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor`. Authentication and ACL run there (`server/router/api/v1/acl_config.go`), but nothing counts requests per user or per IP.

What does exist, and may be what you're thinking of — these are **concurrency** caps, not rate limits, and they're global rather than per-user:

- `thumbnailSemaphore = semaphore.NewWeighted(3)` and `imageProcessingSemaphore = semaphore.NewWeighted(2)` on `APIV1Service` — `server/router/api/v1/v1.go:59-60`.
- `maxConcurrentThumbnails = 3` in the file server — `server/router/fileserver/fileserver.go:46`, applied at `:116`.
- A request body size cap via `connect.WithReadMaxBytes(maxAPIRequestBytes)` — `server/router/api/v1/v1.go:141`.
- A bounded 128-slot webhook dispatch queue that *drops* overflow rather than throttling — `internal/webhook/webhook.go:38,189-195`.

So abuse protection at the request-frequency level would have to come from a reverse proxy in front of memos; nothing in the server enforces it.
