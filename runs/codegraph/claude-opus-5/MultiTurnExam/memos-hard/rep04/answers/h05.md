**Explicit Go code — two `DELETE FROM reaction` statements per driver inside the user-deletion transaction; there is no database-level cascade for reactions.**

Evidence locations:

**1. Explicit deletes (all three drivers, identical structure)** — `deleteUserTargetsTx` runs both, first thing in the transaction:
- `deleteReactionsByContentIDsTx` — removes reactions *on* the user's memos (and comment descendants), batched 500 at a time: `store/db/sqlite/user_delete.go:380`, `store/db/postgres/user_delete.go:380`, `store/db/mysql/user_delete.go:417`. Called at line `:96` in each.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user *left on other people's* memos: `store/db/sqlite/user_delete.go:400`, `store/db/postgres/user_delete.go:400`, `store/db/mysql/user_delete.go:437`. Called at line `:102` in each.

The content-ID form is needed because `reaction.content_id` is a string resource name, not a numeric FK — it's built as `"memos/" + memo.UID` in `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go`, near the bottom of the file), from the recursive memo tree collected by `listDeleteUserMemoTreeRecursive`.

**2. No database-level rule** — the `reaction` table has no foreign key at all: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` declare only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Grepping `FOREIGN KEY|REFERENCES|ON DELETE` across all three `LATEST.sql` files yields exactly one hit per file — and it's on `memo_share.memo_id` (`sqlite:109`, `postgres:108`, `mysql:108`), not on `reaction`.

So if the explicit Go deletes were removed, reactions would be orphaned rather than cascaded. Both are wrapped in the same transaction as the user row deletion (`DeleteUser`, `store/db/sqlite/user_delete.go:28`), so the cleanup is atomic with the delete.
