**Premise correction: there is no per-user API rate-limiting middleware in this codebase — no registration site and no request limits to report.**

Evidence:

- A case-insensitive grep for `ratelimit`, `rate_limit`, `rate limit`, `throttle`, and `Limiter` across all Go sources yields exactly one hit, and it's an aspirational comment in documentation, not code: `// - Rate limit email sending to prevent abuse` in `internal/email/doc.go:86`.
- `go.mod` has no rate-limiting dependency — no `golang.org/x/time/rate`, no `echo` rate-limiter middleware package.
- The Echo middleware stack is two entries total: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/server.go:51-52`). The only other request-path interceptors are the auth ones — the gRPC-Gateway middleware and Connect interceptor built from `NewAuthorizer` (`server/router/api/v1/v1.go:66-70`) — which do authentication/authorization, not throttling.
- Nothing returns HTTP 429 or `codes.ResourceExhausted` for request-frequency reasons anywhere in the server.

**What does exist, and is easy to mistake for rate limiting:**

1. **Concurrency semaphores** (not per-user, not time-based — they bound simultaneous in-flight work process-wide): `thumbnailSemaphore` at 3 and `imageProcessingSemaphore` at 2 (`server/router/api/v1/v1.go:59-60`), plus a separate `thumbnailSemaphore` in the file server (`server/router/fileserver/fileserver.go:116`). Exceeding image-processing concurrency returns `codes.ResourceExhausted, "too many image processing requests"` (`server/router/api/v1/attachment_service.go:160`) — a 429-ish response, but triggered by concurrency, not by a per-user request budget.

2. **Batch-size caps** on individual RPCs — e.g. `maxBatchGetUsers` (`server/router/api/v1/user_service.go:145`), `maxBatchGetInstanceSettings` (`server/router/api/v1/instance_service.go:78`), `maxBatchGetLinkMetadata` (`server/router/api/v1/memo_service_link_metadata.go:24`), `maxBatchDeleteAttachments` (`server/router/api/v1/attachment_service.go:355`). These limit items per request, not requests per user.

3. **A write-contention retry**, `authenticationMutationMaxAttempts = 3` with a short backoff (`store/auth_config.go:13, 74-82`) — an optimistic-concurrency retry loop on auth-config updates, unrelated to client request limits.

There is also no login-attempt throttling or account lockout: nothing in `server/router/api/v1/auth_service_session.go` or `server/auth/` counts failed sign-ins. If you need rate limiting for a deployment, it would have to come from a reverse proxy in front of memos, or be added as new Echo middleware at `server/server.go:51`.
