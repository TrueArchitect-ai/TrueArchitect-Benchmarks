**Premise correction: neither. There is no message broker in this codebase — no NATS, no RabbitMQ/AMQP, no Kafka, no external pub/sub of any kind. A case-insensitive grep for `nats`, `rabbitmq`, `amqp`, `kafka`, and `pubsub` across all Go sources and `go.mod` returns zero hits, so there is no queue declaration to point to.**

**Actual mechanism: an in-process Go channel with a fixed worker pool, entirely inside `internal/webhook/webhook.go`.**

- **The "queue"** is a package-level buffered channel holding 128 payloads: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`). It lives in the server's own memory — nothing is persisted or brokered.
- **The workers** are 4 goroutines started in the package's `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post(payload)`, logging a warning on failure. Since they're started in `init()`, the pool comes up whenever the package is linked in, not from any explicit server wiring.
- **Enqueue** is `PostAsync` (`internal/webhook/webhook.go:184`), called from the memo dispatchers at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`. It's a non-blocking send with a `default:` branch — **if the buffer is full, the payload is dropped** and only a warning is logged (`webhook.go:189-195`). There is no retry, no dead-letter path, and no persistence, so a webhook lost this way is lost permanently.
- **Delivery** is `Post` (`internal/webhook/webhook.go:120`), which marshals the payload, optionally signs it with Standard Webhooks HMAC headers, and issues the POST via the SSRF-guarded `safeClient` with a 30-second timeout (`webhook.go:152`).

Two consequences worth noting given the premise: because the queue is in-process, webhooks in flight are lost on restart, and they are not shared or load-balanced across multiple memos instances the way a broker-backed queue would be.
