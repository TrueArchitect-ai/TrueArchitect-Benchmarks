**Explicit Go code — two targeted `DELETE FROM reaction` statements inside the delete-user transaction, hand-written per driver. There is no database-level cascade.**

What I checked:

**1. The delete path.** `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which deletes reactions in two passes (`store/db/sqlite/user_delete.go:92-127`):
- `deleteReactionsByContentIDsTx` (line 96, defined at line 380) — `DELETE FROM reaction WHERE content_id IN (...)`, removing *everyone's* reactions on the deleted user's memos. The content IDs come from `memoContentIDsFromRefs` (line 512), which builds `"memos/" + memo.UID`, matching how `reaction.content_id` is stored. The memo set is the recursive comment tree from `listDeleteUserMemoTreeRecursive` (line 133), so reactions on comments under those memos go too.
- `deleteReactionsByCreatorTx` (line 102, defined at line 400) — `DELETE FROM reaction WHERE creator_id = ?`, removing the deleted user's own reactions on *other* people's memos.

Both run before `deleteMemosTx` (line 120) and `deleteUserRowTx` (line 461), all in the same transaction, so it's atomic.

**2. All three drivers.** The same two calls and functions exist identically in each backend: `store/db/mysql/user_delete.go:96,102,417,437` and `store/db/postgres/user_delete.go:96,102,380,400`. No driver relies on the database to do it.

**3. The schema — no cascade exists to fall back on.** The `reaction` table has no foreign keys at all in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. `creator_id` and `content_id` are plain `INTEGER`/`TEXT` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. A grep for `FOREIGN KEY`/`CASCADE` on any `reaction` line across all three `LATEST.sql` files returns nothing. (Contrast `memo_share`, which *does* have `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` at `store/migration/sqlite/LATEST.sql:109` — so the Go-code approach for reactions is a deliberate difference, and note `content_id` is a `"memos/{uid}"` string, which couldn't be an FK anyway.)

Test confirmation.** `store/test/user_delete_test.go` seeds three reactions (lines 97-112) and asserts at lines 217-220 that after deletion exactly one survives — `peerReactionToKeep`, a third party's reaction on a memo the deleted user didn't own — verifying both deletes hit their intended scope and nothing wider.
