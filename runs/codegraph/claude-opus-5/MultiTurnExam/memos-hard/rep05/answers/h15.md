Two distinctions worth drawing out, since they're structurally different kinds of enforcement:

- **Post-fetch gates** (`checkMemoReadAccess`, `checkAttachmentPermission`, `canReceive`, the reaction/attachment checks) load the memo first, then reject with `PermissionDenied`/`NotFound`/403. **Query-level filters** (`ListMemos`, `ListMemoComments`, the stats handlers, RSS, sitemap) instead push visibility into the store query via `FindMemo.VisibilityList` or an injected CEL filter such as `creator_id == %d || visibility in ["PUBLIC", "PROTECTED"]`, so restricted rows are never returned. Both are real enforcement, but only the second kind scales to list endpoints.
- **One documented bypass:** `checkAttachmentPermission` (`fileserver.go:681-687`) accepts a `share_token` query param and grants access to a Private or Protected memo's attachments when the token matches a non-expired `MemoShare` for that exact memo. That's the only place visibility is deliberately overridden by a capability token.
