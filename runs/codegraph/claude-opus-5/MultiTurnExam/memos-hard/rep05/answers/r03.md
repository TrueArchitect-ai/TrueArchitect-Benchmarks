**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never used by the server at all — so there is no scheduled time to report.**

Two separate parts of the premise fail:

**1. The cron scheduler is dead code.** `internal/scheduler/` is a complete, well-tested package — cron expression parser (`internal/scheduler/parser.go`), job registry (`internal/scheduler/job.go`), scheduler with `New`/`Register`/`Start`/`Stop` (`internal/scheduler/scheduler.go:54,70,91,169`), middleware (`internal/scheduler/middleware.go`), even a README and doc.go. But a search for imports of `github.com/usememos/memos/internal/scheduler` finds only two, both inside the package's own tests (`internal/scheduler/example_test.go:10`, `internal/scheduler/integration_test.go:13`). No production code constructs a `Scheduler` or calls `Register`, so no cron job of any kind is scheduled.

**2. No database-cleanup job exists anywhere**, scheduled or otherwise. Searching for `cleanup`, `vacuum`, `prune`, `purge`, and `retention` across the backend turns up only unrelated things:

- `store/cache/cache.go:199` — `cleanupLoop`, an in-memory cache expiry sweep every 5 minutes (`store/store.go:42`), not a database operation.
- `server/router/api/v1/user_service.go:421-450` — attachment blob cleanup that runs inline when a user is deleted, not on a schedule.
- `server/router/api/v1/memo_service.go:579` — a comment noting that `store.DeleteMemo` handles relation/attachment cleanup as part of the delete call.

**What actually runs on a schedule.** Exactly one background runner is wired into startup: the S3 presign runner, which re-signs S3 attachment URLs. It uses a plain `time.Ticker` at 12-hour intervals (`server/runner/s3presign/runner.go:27,29-41`), not cron, and is started from `startBackgroundRunners` at `server/server.go:162-171`. There is no wall-clock time-of-day scheduling in the server — the ticker fires 12 hours after process start and every 12 hours thereafter, so the actual times drift with restarts.
