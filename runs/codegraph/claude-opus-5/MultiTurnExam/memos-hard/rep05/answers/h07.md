Notes on the trace:

- **Where the URL comes from.** The browser never requests raw avatar bytes from the API. `convertUserFromStore` (`server/router/api/v1/user_service_converters.go:31-39`) checks whether the stored `AvatarURL` is a base64 data URI; if so it rewrites the field to `/file/{user.Name}/avatar` (line 36), where `Name` is `users/{username}` from `BuildUserName` (`server/router/api/v1/user_resource_name.go:13`). So the `:identifier` path param is the **username**, which is why the lookup is `FindUser{Username: &identifier}`. If the stored value isn't a data URI (e.g. an external URL from SSO), it's passed through unchanged and the browser fetches it directly — no server hop at all.
- **Route registration.** `RegisterRoutes` (`server/router/fileserver/fileserver.go:121-125`) mounts the `/file` group; it's wired at `server/server.go:80-81`, deliberately *before* the gRPC-Gateway so these paths are served natively rather than through gRPC.
- **Access control.** On a private instance (`!s.Profile.AllowAnonymous()`), `serveUserAvatar` requires a session/access token/PAT via `getCurrentUser` and returns 401 otherwise (`fileserver.go:173-181`). On an open instance any visitor may fetch any user's avatar — there is no per-user authorization check beyond that.
- **The "stored data" is the user row itself.** The avatar is not an attachment or a file on disk: it lives in the `user.avatar_url` column as a data URI. After the lookup, `parseDataURI` (`fileserver.go:737`) splits it into MIME type and bytes, `avatarAllowedTypes` (`fileserver.go:75`) restricts it to PNG/JPEG/GIF/WebP, and `c.Blob` writes it out (`fileserver.go:209`).
- **Cache short-circuit.** `Store.GetUser` only consults `userCache` when the lookup is by ID (`store/user.go:149-156`). This path looks up by username, so it always falls through to `ListUsers` → driver → SQL, then populates the cache on the way back (`store/user.go:142-144,167`).
