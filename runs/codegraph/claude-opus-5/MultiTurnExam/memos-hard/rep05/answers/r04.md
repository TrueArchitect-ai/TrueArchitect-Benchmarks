**Premise correction: neither. There is no message broker in this repository — no NATS, no RabbitMQ, no Kafka, no AMQP of any kind — so there is no queue declaration to point to.**

Verification: a case-insensitive search across all Go sources for `nats`, `rabbitmq`, `amqp`, `kafka`, `nsq`, and `streadway` yields 11 hits, and every one is the substring `nSQ` inside identifiers like `openMigrationSQLDB` and `execMigrationSQL` in `store/test/migrator_upgrade_test.go` — false positives. `go.mod` contains no broker client dependency, and there is no `pubsub` reference anywhere in the backend. Nothing in `cmd/memos/main.go` accepts a broker URL or connection flag.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool, in `internal/webhook/webhook.go`.**

- **The "queue"** is a package-level channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A 128-slot buffer, holding pointers to in-memory structs — no serialization, no persistence, no external hop.
- **The workers** are four goroutines started in `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post(payload)`, logging a warning on failure. Because this is `init()`, they spin up on package import rather than through any explicit server wiring — there's no start/stop control and they live for the process lifetime.
- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184-196`), called from the memo webhook dispatchers (`server/router/api/v1/memo_service_webhooks.go:43,71`).
- **Overflow behavior** is a non-blocking `select` with a `default` branch (lines 189-195): when all 128 slots are full, the payload is **dropped** with a warning and the RPC still returns success.

Practical consequences worth flagging, since they're exactly what a broker would otherwise provide:

- **No durability.** A process restart or crash loses every queued-but-undelivered webhook; nothing is written to disk or to the database.
- **No retries.** `Post` returns an error on failure and the worker only logs it (`internal/webhook/webhook.go:46-51`) — there is no redelivery, backoff, or dead-letter path.
- **No cross-instance coordination.** The queue is per-process, so a multi-instance deployment has N independent queues rather than one shared work stream.
- **Delivery is best-effort under load**, given the silent drop at capacity.
