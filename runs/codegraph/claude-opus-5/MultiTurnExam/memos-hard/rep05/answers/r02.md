**Premise correction: there is no per-user API rate-limiting middleware in this repository. Nothing throttles request volume per user, per token, or per IP — so there is no registration site and there are no request limits to report.**

What I checked:

- A case-insensitive search across all Go sources for `ratelimit`, `rate_limit`, "rate limit", `throttl`, `limiter`, and `golang.org/x/time/rate` returns exactly one hit, and it's a comment describing future work — `internal/email/doc.go:86`: "Rate limit email sending to prevent abuse." No implementation accompanies it.
- `go.mod` contains no rate-limiting dependency (no `golang.org/x/time`, no `ulule/limiter`, no `tollbooth`).
- The full middleware stack is short and contains nothing of the kind. On the Echo side: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/server.go:51-52`), plus static-file and SPA-fallback middleware for the frontend (`server/router/frontend/frontend.go:54,59`). Echo's built-in `middleware.RateLimiter` is available in the framework but is never used.
- On the RPC side, the interceptor chain is `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor` (`server/router/api/v1/v1.go:133-137`), and the gRPC-Gateway path installs only `gatewayAuthMiddleware` (`server/router/api/v1/v1.go:95-97`). All of these are authentication, logging, or panic recovery — none counts requests.

What does exist, and is sometimes mistaken for rate limiting:

| Control | Location | What it actually bounds |
|---|---|---|
| Request body size cap | `server/router/api/v1/v1.go:124,141` — `http.MaxBytesHandler(gwMux, maxAPIRequestBytes)` and `connect.WithReadMaxBytes(maxAPIRequestBytes)` | bytes per request, not requests per user |
| Thumbnail concurrency | `server/router/fileserver/fileserver.go:46,116` (`maxConcurrentThumbnails = 3`) and `server/router/api/v1/v1.go:59` | simultaneous in-flight work, instance-wide |
| Image-processing concurrency | `server/router/api/v1/v1.go:60` — `semaphore.NewWeighted(2)` | same |
| Webhook async queue | `internal/webhook/webhook.go:39` — 128-slot channel, 4 workers | outbound dispatch, drops on overflow |
| Memo content length | `server/router/api/v1/memo_service.go:100-106` (instance setting) | characters per memo |

These are concurrency and size guards that protect memory; they're instance-wide semaphores with no per-identity accounting, so a single authenticated user can issue unlimited requests as fast as the server will serve them. If per-user rate limiting is a requirement, it would need to be added — the natural insertion points would be a new Echo middleware alongside `server/server.go:51-52` or a new interceptor in the chain at `server/router/api/v1/v1.go:133-137`, where the authenticated identity is already resolved.
