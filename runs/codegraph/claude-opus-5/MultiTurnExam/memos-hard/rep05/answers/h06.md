The funnel, from the outside in:

1. The three `Dispatch*Webhook` wrappers (`server/router/api/v1/memo_service_webhooks.go:15,20,25`) all delegate to `dispatchMemoRelatedWebhook` (line 48), differing only in `activityType` (`memos.memo.created` / `.updated` / `.deleted`). The three `SetMemo*`/`UpdateMemo` handlers reach it via the shared helper `dispatchMemoUpdatedSideEffects` (`server/router/api/v1/memo_update_helpers.go:66`).
2. `CreateMemoComment` takes a parallel branch — `DispatchMemoCommentCreatedWebhook` (`memo_service_webhooks.go:30`) — because it looks up webhooks belonging to the *related memo's owner* (`relatedMemoCreatorID`) rather than the memo creator, but it's otherwise identical.
3. Both branches load the target user's webhooks via `s.Store.GetUserWebhooks` and set `payload.URL = hook.Url` — the user-configured URL, registered through `CreateUserWebhook`/`UpdateUserWebhook` (`server/router/api/v1/user_service_webhooks.go:53,106`) — then call `webhook.PostAsync` (`memo_service_webhooks.go:43` and `:71`).
4. `PostAsync` (`internal/webhook/webhook.go:184`) only enqueues onto a bounded 128-slot channel; four worker goroutines started in `init()` (`internal/webhook/webhook.go:42-55`) drain it, and every one of them calls **`Post`**. That is the single function where all six handler paths converge before the request goes out — it marshals the body, signs it, and issues the request through the SSRF-guarded `safeClient`.

One consequence worth noting: because delivery is async through a shared queue, a full queue silently drops the dispatch with only a warning (`internal/webhook/webhook.go:192`), so the handler returns success regardless.
