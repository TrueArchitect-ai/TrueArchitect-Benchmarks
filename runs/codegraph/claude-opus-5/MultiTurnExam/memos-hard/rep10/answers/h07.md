Notes on the path:

- **Wiring**: the file server is constructed and mounted at server startup — `fileserver.NewFileServerService(s.Profile, s.Store, s.Secret)` then `RegisterRoutes(echoServer)` at `server/server.go:81-82`. This is a plain Echo route, not a gRPC/Connect RPC — there is no `GetUserAvatar` RPC.
- **Access control** (`fileserver.go:173-181`): if the instance is not anonymous-accessible (`s.Profile.AllowAnonymous()` false), the request must authenticate via `getCurrentUser` → `auth.Authenticator.AuthenticateToUser` (Bearer access token / PAT, or refresh-token cookie). Otherwise any visitor may fetch any user's avatar.
- **Where the data actually lives**: the avatar is *not* an attachment or a file on disk — it's stored inline on the user row as a base64 `data:` URI in `user.avatar_url` (`store.User.AvatarURL`, `store/user.go:29`). `serveUserAvatar` reads it off the user record, decodes it with `parseDataURI` (`fileserver.go:737`, regex at `fileserver.go:98`), rejects MIME types outside `avatarAllowedTypes` (`fileserver.go:75-83`, checked at `:201`), sets security + cache headers (`setSecurityHeaders` at `:758`, `cacheMaxAge` 1 hour), and writes the bytes.
- **Cache layer**: `Store.GetUser` only consults `userCache` when looking up by ID; this lookup is by username (`FindUser{Username: &identifier}`), so it always falls through to `Store.ListUsers` → the driver, and the result is then cached by ID (`store/user.go:143`).
