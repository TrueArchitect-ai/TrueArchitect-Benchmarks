**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never started by the server — so there is no scheduled time to report.**

Two separate premise failures:

**1. No database-cleanup job exists.** Nothing in the codebase registers any job that vacuums, purges, prunes, or otherwise cleans the database on a schedule. Searching non-test Go code for `cleanup|vacuum|purge|prune` turns up only unrelated things: per-request attachment-storage cleanup during user deletion (`server/router/api/v1/user_service.go:421-450`, `store/attachment.go:171`), a best-effort rollback of a provisional SSO user row (`server/router/api/v1/auth_service_sso.go:76`), and the in-memory cache's `CleanupInterval: 5 * time.Minute` (`store/store.go:42`) — which expires cache entries in RAM, not database rows.

**2. `internal/scheduler` is dead code — nothing in the running server uses it.** The package is fully built out (`job.go`, `parser.go` with a 5/6-field cron parser and IANA timezone support, `scheduler.go`, `middleware.go`, plus a README and `doc.go`), but the only files that import `github.com/usememos/memos/internal/scheduler` are its own tests: `internal/scheduler/integration_test.go:13` and `internal/scheduler/example_test.go:10`. No production file references `scheduler.New`, `Scheduler.Register`, or `Scheduler.Start`.

Every cron expression in the repo is in a test or a doc comment — e.g. `"0 2 * * *"` appears as `// 2 AM daily` in `internal/scheduler/doc.go:16` and in `internal/scheduler/example_test.go:100`, and `"0 0 * * *" (daily at midnight)` is an example in the `Job.Schedule` field comment (`internal/scheduler/job.go:21`). These are illustrations of the API, not registered jobs. If a stale answer cites 2 AM, that's this doc comment being mistaken for configuration.

**What background work the server actually runs.** Exactly one runner, and it's interval-based rather than cron-based: `s3presign.Runner`, which re-presigns S3 attachment URLs every 12 hours (`runnerInterval = time.Hour * 12`, `server/runner/s3presign/runner.go:27`) plus one immediate pass at startup. It is wired in `Server.startBackgroundRunners` at `server/server.go:162-171`, called from `Server.Start` at `server/server.go:129`. A second runner package, `server/runner/memopayload`, exists but is likewise never constructed in production.
