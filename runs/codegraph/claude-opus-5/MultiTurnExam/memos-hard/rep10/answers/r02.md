**Premise correction: there is no per-user API rate-limiting middleware in this repository. No rate limiter is registered anywhere, and no request limits exist to report.**

Evidence:

- A case-insensitive search of all Go sources for `ratelimit`, `rate_limit`, `rate limit`, `throttl`, `RateLimiter`, and the usual token-bucket dependency `golang.org/x/time/rate` returns exactly one hit, and it's a comment describing future work, not code: `internal/email/doc.go:86` — `//   - Rate limit email sending to prevent abuse`. `go.mod` pulls in no rate-limiting library.
- The complete global middleware stack is two entries, registered in `server.NewServer`: `middleware.Recover()` (`server/server.go:51`) and `newCORSMiddleware(profile)` (`server/server.go:52`, defined in `server/cors.go:14`). Echo's `middleware.RateLimiter`/`RateLimiterWithConfig` is never used; the only other `middleware.` reference is `middleware.StaticWithConfig` for serving frontend assets (`server/router/frontend/frontend.go:54`).
- The API interceptor chain has no limiter either: the Connect handlers are wired with `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, and `NewAuthInterceptor` (`server/router/api/v1/v1.go:133-137`), and the gRPC-Gateway path gets the same shared authorizer as auth middleware (`v1.go:67`, `:95`).

What does exist — related but not rate limiting, in case one of these is what you were after:

- **Request body size cap**: `connect.WithReadMaxBytes(maxAPIRequestBytes)` on the Connect mux (`server/router/api/v1/v1.go:141`) — a per-request byte ceiling, not a per-user request-frequency limit.
- **Concurrency semaphores**: thumbnail generation is capped at 3 concurrent operations (`server/router/fileserver/fileserver.go:46`, `:116`), and `APIV1Service` holds `thumbnailSemaphore` (3) and `imageProcessingSemaphore` (2) (`server/router/api/v1/v1.go:63-64`). These bound in-flight work process-wide; they don't track or limit anything per user.
- **Content/upload size limits**: memo content length (`server/router/api/v1/memo_service.go:101-106`) and attachment upload size (`server/router/api/v1/attachment_service.go:120-124`), both instance settings.
- **Webhook queue backpressure**: the async dispatch channel holds 128 items and drops with a warning when full (`internal/webhook/webhook.go:39`, `:189-195`) — a queue bound, not a limiter.

So an abusive authenticated client is bounded only by these size and concurrency caps; nothing restricts how many API calls a given user may make per unit time.
