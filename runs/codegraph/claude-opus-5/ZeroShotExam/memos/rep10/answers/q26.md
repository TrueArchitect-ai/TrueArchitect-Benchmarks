**DB-level cascade** — `memo_share` declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). Note this only actually fires on Postgres/MySQL: the SQLite driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite `memo_share` rows are left orphaned.

**Not touched:** `reaction` — its `content_id` is a resource-name string with no FK and no cleanup code in either the handler or `store.DeleteMemo`, so reactions on a deleted memo are orphaned on every backend. (Contrast with user deletion, which has explicit reaction cleanup in `store/db/*/user_delete.go`.)
