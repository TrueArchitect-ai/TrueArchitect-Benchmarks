`Store.DeleteMemo` (`store/memo.go:140-159`) removes the following before calling `driver.DeleteMemo` on the memo row:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments{MemoID: &delete.ID}` and deleted one by one with `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the attachment's backing storage (local file / S3 object) via `DeleteAttachmentStorage` before deleting the row (`store/attachment.go:132-149`).

Notes on scope:
- Reactions are **not** deleted here — the API handler only *lists* them for the webhook payload (`server/router/api/v1/memo_service.go:545-550`); nothing deletes `reaction` rows for the memo.
- Comment memos are deleted by the API layer before the parent, not by the store: the handler finds child relations of type `COMMENT` and calls `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:567-577`), which recursively applies the same relation + attachment cleanup.
- The per-driver `DeleteMemo` implementations only issue `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).
