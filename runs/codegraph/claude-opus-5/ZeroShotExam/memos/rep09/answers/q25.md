**Engine:** Google CEL (`cel-go`), wrapped by the in-repo filter engine at `internal/filter/` — entry point `filter.DefaultEngine()` in `internal/filter/engine.go:111`.

**Mechanism (one sentence):** `Engine.Compile` parses the filter with `cel-go` against a memo-specific CEL environment declared in `internal/filter/schema.go` (`Engine.env.Compile`, `internal/filter/engine.go:48-71`), `buildCondition` in `internal/filter/parser.go:18` normalizes the CEL AST into a dialect-agnostic condition IR (`internal/filter/ir.go`) while enforcing schema rules, and `renderer.Render` in `internal/filter/render.go:32` walks that IR emitting a dialect-specific SQL fragment plus bound args (`Statement{SQL, Args}`) selected by `RenderOptions.Dialect` (`sqlite` / `mysql` / `postgres`).

**Wiring into ListMemos:**
- `server/router/api/v1/memo_service.go:211-215` — the RPC's `request.Filter` is validated and appended to `memoFind.Filters`.
- `internal/filter/helpers.go:9` — `filter.AppendConditions` compiles each filter with a given `DialectName` and appends `(<sql>)` to the WHERE list and its args, using `PlaceholderOffset: len(*args)` so placeholder numbering composes with the pre-existing args.
- Each driver calls it with its own dialect: `store/db/sqlite/memo.go:54` (`DialectSQLite`), `store/db/postgres/memo.go:58` (`DialectPostgres`), `store/db/mysql/memo.go:69` (`DialectMySQL`).

**Where the dialects diverge:** inside the renderer/schema, not the callers — `qualifyColumn` (`render.go:919`, backticks vs bare `table.col` for Postgres), `jsonExtractExpr`/`jsonArrayExpr` (`render.go:932-954`: `JSON_EXTRACT` for SQLite/MySQL vs `->`/`->>` accessors for Postgres), `jsonBoolPredicate` (`render.go:798`), placeholders (`?` vs `$n`, via `addArg`/`placeholderOffset`), and per-dialect SQL templates on schema fields (`schema.go:105-145`). `internal/filter/README.md` documents this three-phase parse → normalize → render pipeline, including tag handling (`LIKE` on SQLite, `JSON_CONTAINS` on MySQL, `@>` on Postgres).
