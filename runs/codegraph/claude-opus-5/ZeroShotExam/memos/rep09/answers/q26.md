**Tables affected: `memo`, `memo_relation`, `attachment` — plus `memo_share` via DB-level `ON DELETE CASCADE` (Postgres/MySQL only). `reaction` is *not* touched.**

Details:

**Explicit cascade code in `store.DeleteMemo` (`store/memo.go:140-159`)**, in order:
1. `memo_relation` — deleted twice, once where the memo is the source (`MemoID`) and once where it's the target (`RelatedMemoID`) (`store/memo.go:142-147`).
2. `attachment` — every attachment with `MemoID = delete.ID` is listed and deleted one by one via `s.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying blob/local file (`store/attachment.go:133-148`).
3. `memo` — the row itself, via the driver (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

**Extra cascade at the API layer (`server/router/api/v1/memo_service.go:518-593`)**: before deleting the memo, it lists comment relations (`MemoRelationComment` with `RelatedMemoID = memo.ID`) and calls `store.DeleteMemo` on each comment memo (lines 567-577) — so additional `memo`, `memo_relation`, and `attachment` rows for the direct comments are removed too (one level only; grandchild comments aren't walked).

**DB-level cascade**: `memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). Caveat: SQLite opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does **not** fire and `memo_share` rows are orphaned.

**Not affected**: `reaction`. The API reads reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); nothing deletes them, and the `reaction` table has no FK to `memo` (`store/migration/sqlite/LATEST.sql:92`), so reaction rows keyed by the memo's resource name are left behind.
