**`web/src/connect.ts` (the `authInterceptor`, lines 156–178, wired into the Connect transport at line 188); JWT access token (in-memory + `localStorage`, 15 min) + HttpOnly `memos_refresh` refresh-token cookie (plus PATs accepted on the same header); `server/auth/`**

**Frontend — how it works**

- `web/src/connect.ts:156` defines `authInterceptor`, installed on the single `createConnectTransport` (`web/src/connect.ts:184-189`) that backs every service client (`memoServiceClient`, `userServiceClient`, …). All Connect-RPC calls therefore pass through it.
- Per request it calls `getRequestToken()` (`web/src/connect.ts:124`) and sets `Authorization: Bearer <token>` (`setAuthorizationHeader`, line 97). `getRequestToken` does a *preflight* refresh when the token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30 s) of expiry, and reactively refreshes once on a `Code.Unauthenticated` response, marking the retry with an `X-Retry: true` header so it can't loop; on repeat failure it calls `redirectOnAuthFailure()` (`web/src/utils/auth-redirect.ts`).
- Refresh goes through a *separate* transport with no interceptors (`web/src/connect.ts:65-72`) to avoid recursion, calling `AuthService.RefreshToken` with `credentials: "include"` so the HttpOnly cookie is sent. Concurrent refreshes are deduped by `tokenRefreshManager` (line 30).

**Tokens it manages**

- **Access token** — short-lived JWT, held in memory and mirrored to `localStorage` under `memos_access_token` / `memos_token_expires_at`, with cross-tab sync via a `memos_token_sync` `BroadcastChannel` (`web/src/auth-state.ts`). Set on sign-in/sign-up/OAuth callback (`web/src/components/PasswordSignInForm.tsx:49`, `web/src/pages/SignUp.tsx:72`, `web/src/pages/AuthCallback.tsx:113`).
- **Refresh token** — never touched by JS; it's the HttpOnly cookie `memos_refresh` (`server/auth/token.go:49`), 30-day lifetime, exchanged for new access tokens. Proactive refresh on tab focus via `web/src/hooks/useTokenRefreshOnFocus.ts` (2-min buffer).
- The backend additionally accepts **Personal Access Tokens** (`memos_pat_` prefix) on the same `Authorization` header for programmatic clients.

**Backend validation**

- Package `server/auth` (`github.com/usememos/memos/server/auth`): `Authenticator.Authenticate` (`server/auth/authenticator.go:213`) extracts the bearer token (`server/auth/extract.go:11`) and routes it to `AuthenticateByAccessTokenV2` (stateless JWT parse, `token.go:220`) or `AuthenticateByPAT` (SHA-256 hash lookup in the store); `AuthenticateByRefreshToken` validates the cookie against the DB for revocation.
- It's invoked from the Connect server interceptor `AuthInterceptor.WrapUnary` in `server/router/api/v1/connect_interceptors.go:217`, which delegates to the shared `Authorizer` in `server/router/api/v1/authz.go` (`Authenticate` + `CheckAccess`), the same `Authorizer` used by the gRPC-Gateway path and SSE handler.
