**Tables affected by `DeleteMemo`:** `memo`, `memo_relation`, `attachment`, and `memo_share` (FK cascade, MySQL/Postgres only).

**Direct writes — API layer** (`server/router/api/v1/memo_service.go:518-593`):
- Deletes each comment memo first via `store.DeleteMemo` (line 574), then the memo itself (line 580). Each of those calls does the full cleanup below.

**Direct writes — store layer** (`store/memo.go:140-159`):
1. `memo_relation` — two deletes, once matching `memo_id` and once matching `related_memo_id` (lines 142-147).
2. `attachment` — every attachment with `memo_id = <id>` is fetched and deleted one by one (lines 149-157) via `Store.DeleteAttachment` (`store/attachment.go:132-149`) → `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go:211`, `store/db/mysql/attachment.go:230`, `store/db/postgres/attachment.go:211`).
3. `memo` — the row itself (`store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).

**DB-level cascade:**
- `memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`). Caveat: the SQLite driver opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite this cascade does **not** fire and `memo_share` rows are orphaned; it does fire on MySQL/Postgres.

**Notably not deleted:** `reaction`. The handler lists reactions only to build the webhook payload (`memo_service.go:545-550`); the `reaction` table keys on a text `content_id` with no FK to `memo` (`store/migration/sqlite/LATEST.sql:92-99`), so reaction rows survive the delete.

Non-DB side effects of the attachment deletions: local files / S3 objects and thumbnail & motion caches are removed (`store/attachment.go:202-293`).
