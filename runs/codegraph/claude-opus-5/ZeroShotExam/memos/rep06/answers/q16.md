`Store.DeleteMemo` (`store/memo.go:140-159`) performs this cleanup before calling the driver's `DeleteMemo`, which issues the actual `DELETE FROM memo` (`store/db/sqlite/memo.go`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`):

- **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
- **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
- **`attachment` rows linked to the memo** — listed via `ListAttachments{MemoID: &delete.ID}` and removed one by one with `Store.DeleteAttachment` (`store/memo.go:149-157`). That call also deletes the attachment's backing storage — the local file or S3 object — plus its derived thumbnail/motion caches (`store/attachment.go:132-148`, `store/attachment.go:202-293`).

Two related deletions that are *not* done by the store layer, for contrast: the API handler `APIV1Service.DeleteMemo` deletes child comment memos first, by listing `MemoRelationComment` relations and recursively calling `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:567-577`); and reaction records are only read for the webhook payload, not deleted, in this path (`server/router/api/v1/memo_service.go:545-550`).
