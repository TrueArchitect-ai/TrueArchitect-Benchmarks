The store-layer `Store.DeleteMemo` (`store/memo.go:140-159`) removes two other kinds of records before issuing the `DELETE FROM memo`:

1. **Memo relations** — both directions:
   - rows where the memo is the source (`DeleteMemoRelation{MemoID: &delete.ID}`)
   - rows where the memo is the target/related memo (`DeleteMemoRelation{RelatedMemoID: &delete.ID}`)
2. **Attachments linked to the memo** — it lists them via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and calls `DeleteAttachment` on each (`store/attachment.go` defines these types; deletion also cleans up the stored blob/thumbnail).

Only then does it call `s.driver.DeleteMemo(...)`, which is the plain `DELETE FROM memo WHERE id = ?` in each driver (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

Two related deletions happen **above** the store layer, in `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`): comment memos are found via comment-type relations and deleted first (each recursing through the same store cleanup). Reactions are only *listed* there for the webhook payload — no reaction rows are deleted on the memo-delete path.
