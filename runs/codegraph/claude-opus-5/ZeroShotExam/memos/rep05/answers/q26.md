**Written (DELETE) directly or via explicit cascade code**

| Table | Where | How |
|---|---|---|
| `memo_relation` | `store/memo.go:142-147` | `Store.DeleteMemo` explicitly deletes relations where the memo is the source (`MemoID`) *and* where it is the target (`RelatedMemoID`), before deleting the memo. SQL at `store/db/sqlite/memo_relation.go:149`, and the mysql/postgres equivalents. |
| `attachment` | `store/memo.go:148-157` | `Store.DeleteMemo` lists attachments by `MemoID` and deletes each via `Store.DeleteAttachment` (`store/attachment.go:132-149`), which also removes the local/S3 blob and thumbnail/motion caches. SQL at `store/db/sqlite/attachment.go:212`. |
| `memo` | `store/memo.go:158` | `s.driver.DeleteMemo` → `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:239`, `store/db/mysql/memo.go:259-270`, `store/db/postgres/memo.go:244-255`). The API layer additionally deletes each **comment child memo** first (`server/router/api/v1/memo_service.go:567-577`), so this row plus one level of comment rows are removed — and each of those recurses through the same relation/attachment cleanup. |
| `memo_share` | `store/migration/*/LATEST.sql` | DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `mysql/LATEST.sql:108`, `postgres/LATEST.sql:108`). There is no Go code deleting shares on memo delete. |

**Read but not deleted**

- `reaction` — `server/router/api/v1/memo_service.go:545-550` lists reactions only to build the webhook payload. Nothing deletes them, and the table has no FK to `memo` (it keys off a `content_id` text column, `store/migration/sqlite/LATEST.sql:92-100`), so reaction rows are left orphaned after a memo is deleted.
- `user` (via `fetchCurrentUser`) and `memo` itself are read for the permission check.

**One caveat worth flagging:** the `memo_share` cascade does not fire on SQLite — the driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), which disables FK enforcement entirely. So on SQLite deployments, `memo_share` rows are orphaned like `reaction` rows; only MySQL and Postgres actually cascade.
