`store.DeleteMemo` (`store/memo.go:140-159`) removes these before issuing the `DELETE FROM memo`:

1. **Memo relation rows where the memo is the source** — `DeleteMemoRelation(&DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **Memo relation rows where the memo is the target/related memo** — `DeleteMemoRelation(&DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **Attachment rows linked to the memo** — each one found by `ListAttachments(&FindAttachment{MemoID: &delete.ID})` is removed via `s.DeleteAttachment` (`store/memo.go:149-157`), which also deletes the attachment's backing storage/blob (local file, etc.) before the DB row (`store/attachment.go:132-147`)

Only then does it call `s.driver.DeleteMemo` to delete the memo row itself (`store/memo.go:158`; e.g. `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

Two related notes on the API path (`server/router/api/v1/memo_service.go:518-582`): the handler first deletes comment memos (each through the same `store.DeleteMemo`, so their relations and attachments go too), and **reactions are not deleted** — they're only listed for the webhook payload, so `reaction` rows keyed by the memo name are left behind.
