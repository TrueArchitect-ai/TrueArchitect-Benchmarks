**`web/src/connect.ts` (authInterceptor, lines 156–178, wired into the Connect transport at line 188) + `web/src/auth-state.ts` for token storage; access token (JWT, localStorage `memos_access_token`) + refresh token (HttpOnly cookie `memos_refresh`) + PAT (`memos_pat_` prefix) as an alternate bearer; validated by the Go package `server/auth/`**

How it works:

- **Interceptor** — `web/src/connect.ts:156` defines `authInterceptor`, registered on the `@connectrpc/connect-web` transport (`web/src/connect.ts:184-189`, `fetch` wrapped with `credentials: "include"` so the refresh cookie rides along). Every service client (memo, user, auth, attachment, AI, …) is created from that transport, so all frontend RPCs pass through it.
- **What it does** — calls `getRequestToken()` (`web/src/connect.ts:124`), which reads the in-memory/localStorage access token and *preflight-refreshes* if it's within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30 s) of expiry; sets `Authorization: Bearer <token>`; and on a `Code.Unauthenticated` response refreshes once, retries with an `X-Retry: true` marker, and otherwise calls `redirectOnAuthFailure()` (`web/src/utils/auth-redirect.ts`). Refresh goes through `refreshAccessToken()` (`web/src/connect.ts:89`) over a *separate* transport with no interceptors to avoid recursion, and through a dedup manager so concurrent refreshes collapse into one.
- **Tokens managed** — `web/src/auth-state.ts` holds the short-lived JWT **access token** (`memos_access_token` + `memos_token_expires_at` in localStorage, mirrored to other tabs over a `memos_token_sync` BroadcastChannel). The **refresh token** is never touched by JS — it's an HttpOnly cookie (`memos_refresh`) sent via `credentials: "include"` and exchanged by `AuthService.RefreshToken`. **PATs** exist for programmatic clients and travel in the same `Authorization: Bearer` header.
- **Backend validation** — `server/auth/` (`authenticator.go`, `token.go`, `extract.go`): access tokens are stateless signature-checked (`AuthenticateByAccessTokenV2`, 15 min lifetime), refresh tokens are parsed *and* checked against the DB for revocation (`AuthenticateByRefreshToken`, 30 days), PATs are hash-looked-up (`AuthenticateByPAT`). It's driven by `Authorizer` in `server/router/api/v1/authz.go:44` and applied per-RPC by `AuthInterceptor.WrapUnary` in `server/router/api/v1/connect_interceptors.go:217`, which reads the `Authorization` header, then `auth.ApplyToContext`. `MetadataInterceptor` forwards the `Cookie` header into gRPC metadata so `RefreshToken` can find the cookie (`connect_interceptors.go:54-57`).
