**Tables affected: `memo`, `memo_relation`, `attachment`** (plus `memo_share` on MySQL/Postgres only, via DB-level FK cascade — not code).

**Direct writes — `store.DeleteMemo` (`store/memo.go:140-159`)**, in order:

1. `memo_relation` — two explicit deletes, clearing rows where the memo is either side of the relation:
   - `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
   - `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
   - SQL: `store/db/sqlite/memo_relation.go:137`, `store/db/postgres/memo_relation.go:153`, `store/db/mysql/memo_relation.go:126`
2. `attachment` — lists attachments with `MemoID = id` and deletes each via `s.DeleteAttachment` (`store/memo.go:149-157`); that also removes the blob from local/S3 storage (`store/attachment.go:132-149`).
3. `memo` — the driver `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

**Service layer — `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`)** adds recursion, not new tables: it lists comment relations and calls `store.DeleteMemo` on each comment memo (`memo_service.go:568-577`), so the same three tables are hit again for every child memo. It only *reads* `reaction` and `attachment` beforehand to build the webhook payload.

**DB-level cascade:** `memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Note this does **not** fire on SQLite — the connection opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so shares are orphaned there.

**Not touched:** `reaction` — reactions key off `content_id` (the memo resource name string, `store/reaction.go:12`) with no FK and no cleanup call in either `store.DeleteMemo` or the service handler, so reaction rows survive memo deletion.
