The store layer uses hand-written SQL (no ORM tags), so the mapping is defined by the driver files that scan each table into a struct.

| table | Struct — path |
|---|---|
| `user` | `store.User` — `store/user.go:29` |
| `attachment` | `store.Attachment` — `store/attachment.go:16` |
| `reaction` | `store.Reaction` — `store/reaction.go:7` |

Supporting evidence — the per-driver SQL that binds each struct to its table:

- **user**: `store/db/sqlite/user.go:17`, `store/db/mysql/user.go:18` (`INSERT INTO user (...)`), `store/db/postgres/user.go`; `ListUsers` scans directly into `store.User` (e.g. `store/db/mysql/user.go:147-175`, selecting `FROM \`user\``).
- **attachment**: `store/db/sqlite/attachment.go:34`, `store/db/mysql/attachment.go:34`, `store/db/postgres/attachment.go:33` — all `INSERT INTO attachment` returning `*store.Attachment`.
- **reaction**: `store/db/sqlite/reaction.go:16`, `store/db/mysql/reaction.go:16`, `store/db/postgres/reaction.go:13` — all `INSERT INTO reaction` returning `*store.Reaction`.

Each of these structs also has companion `Find*`/`Update*`/`Delete*` query structs in the same file (e.g. `FindUser`, `FindAttachment`, `FindReaction`), which are query parameters rather than row mappings.
