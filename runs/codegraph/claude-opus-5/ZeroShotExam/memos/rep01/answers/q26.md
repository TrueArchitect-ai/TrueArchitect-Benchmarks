**`memo_share` — DB cascade, engine-dependent**

`memo_share.memo_id` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). There is no Go code deleting share rows on memo deletion — the only `Store.DeleteMemoShare` caller is the explicit revoke RPC (`server/router/api/v1/memo_share_service.go:145`). On SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the cascade does **not** fire there and share rows are orphaned.

**Not touched: `reaction`.** Reactions key off `content_id` (the memo resource name string), have no FK to `memo`, and nothing in the delete path removes them — they are read for the webhook and then left behind.
