**Premise correction:** Neither. This repository (memos) has no message broker at all — no NATS, RabbitMQ, AMQP, Kafka, Redis, or task-queue dependency. A repo-wide grep for those terms across Go sources, `go.mod`, and config files returns exactly one hit, `web/src/locales/ca.json`, which is an incidental substring match in Catalan translation text, not a broker reference. There is also no separate "worker" process or queue declaration anywhere.

**Actual mechanism:** Webhook delivery is entirely in-process, using a buffered Go channel as the queue and goroutines as the workers.

- **Queue declaration** — `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A package-level buffered channel with capacity 128, declared in the same `var` block as the shared SSRF-guarded `http.Client`.

- **Workers** — `internal/webhook/webhook.go:42-55`: a package `init()` spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)` for every item, logging a warning on failure. These start when the package is first loaded; there is no explicit lifecycle or shutdown.

- **Producer** — `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send onto the channel. If the buffer is full, the `default` branch **drops the webhook** and logs `"Dropped webhook dispatch because the async queue is full"`. Delivery is therefore best-effort with no persistence, no retry, and no redelivery across restarts.

- **Callers** — `server/router/api/v1/memo_service_webhooks.go:43` and `:71` invoke `webhook.PostAsync(payload)` for the memo created/updated/deleted and comment-created activity types.

- **Delivery itself** — `Post` (`internal/webhook/webhook.go:120-180`) does a plain HTTP POST of the JSON payload, optionally adding Standard Webhooks HMAC-SHA256 headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) when a signing secret is set.
