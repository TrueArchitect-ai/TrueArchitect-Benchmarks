**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the user-delete transaction, in all three drivers. There is no database-level rule (the `reaction` table declares no foreign key at all, so no `ON DELETE CASCADE` applies).

**What I checked**

1. **The delete-user transaction body.** `deleteUserTargetsTx` runs two reaction deletions before touching memos/user:
   - `store/db/sqlite/user_delete.go:96` and `:102`
   - `store/db/postgres/user_delete.go:96` and `:102`
   - `store/db/mysql/user_delete.go:96` and `:102`

2. **The two helpers** (same shape in each driver):
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`store/db/sqlite/user_delete.go:380`, `store/db/postgres/user_delete.go:380`, `store/db/mysql/user_delete.go:417`). The content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + memo.UID` (`store/db/sqlite/user_delete.go:512`) over the memo tree collected by `listDeleteUserMemoTree` (the user's memos plus descendant `COMMENT` memos). So reactions *other people left on the deleted user's memos* are removed too.
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400`, `store/db/postgres/user_delete.go:400`, `store/db/mysql/user_delete.go:437`). This is the user's own reactions, including ones on memos they don't own.

3. **Schema, to rule out a DB-level cascade.** The `reaction` table has only an `id` PK and a `UNIQUE(creator_id, content_id, reaction_type)` — no `FOREIGN KEY` on `creator_id` or `content_id`:
   - `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`
   - original creation migrations: `store/migration/sqlite/0.20/00__reaction.sql`, `store/migration/postgres/0.20/00__reaction.sql`, `store/migration/mysql/0.20/00__reaction.sql` — same, no FK.
   - A grep for `REFERENCES|CASCADE` across `store/migration/` returns hits only for `user_setting`, `memo`, `memo_relation`, `memo_organizer`, `memo_share`, etc. — never `reaction`. (Also note `content_id` is a string like `memos/<uid>`, not an integer memo id, so an FK isn't even expressible against `memo(id)`.)

4. **The store wrapper** `Store.DeleteUser` (`store/user.go:171`) just delegates to the driver and then invalidates cache — no additional reaction handling there.

Both deletions happen inside the same transaction that deletes the memos and the user row (`deleteUserTargetsTx`, e.g. `store/db/sqlite/user_delete.go:92-127`), so they commit atomically with the rest of the deletion.
