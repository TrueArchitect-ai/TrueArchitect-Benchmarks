**Premise correction: this repository has no per-user API rate-limiting middleware.** There is no rate limiter registered anywhere — no requests-per-minute/hour quotas, no per-user or per-IP request counting, and no `429 Too Many Requests` path. A repo-wide search for `rate.NewLimiter` / `golang.org/x/time/rate`, `RateLimit`, `limiter`, `throttle`, and `429` turns up nothing, and `golang.org/x/time` is not a dependency in `go.mod`.

**What is actually registered**

The complete Echo middleware stack is two entries, in `server/server.go:51-52`:
- `middleware.Recover()`
- `newCORSMiddleware(profile)`

Plus static-file and SPA-fallback middleware from the frontend service (`server/router/frontend/frontend.go:54-59`).

The API interceptor chain is Connect-based, registered in `server/router/api/v1/v1.go:133-138` — `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor`. None of these count or limit requests; `AuthInterceptor` (`server/router/api/v1/connect_interceptors.go:217-231`) only authenticates and applies identity to the context.

**The limits that do exist** (none are per-user, and none are rate limits)

| Limit | Value | Location |
|---|---|---|
| Max API request body size | `256 << 20` (256 MiB), applied via `http.MaxBytesHandler` to `/api/v1/*`, `/file/*`, and Connect routes, plus `connect.WithReadMaxBytes` | `server/router/api/v1/v1.go:20`, `126`, `141`, `144` |
| Concurrent thumbnail generation | 3 (process-wide semaphore) | `server/router/api/v1/v1.go:59`, `server/router/fileserver/fileserver.go:46`, `116` |
| Concurrent image (EXIF) processing | 2 (process-wide semaphore) | `server/router/api/v1/v1.go:60` |

The image-processing semaphore is the only thing that returns a resource-exhaustion error — `codes.ResourceExhausted, "too many image processing requests"` at `server/router/api/v1/attachment_service.go:160`. That is a global concurrency gate on in-flight work, not a per-user request quota: it blocks while a slot frees rather than counting requests over a time window, and it's shared by all users of the instance.

If you need per-user rate limiting, it would have to be added — the natural insertion point is a new Connect interceptor in the chain at `server/router/api/v1/v1.go:133`, after `AuthInterceptor` so the user identity is already on the context.
