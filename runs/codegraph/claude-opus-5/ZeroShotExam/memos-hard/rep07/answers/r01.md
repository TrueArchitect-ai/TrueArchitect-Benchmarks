**r01.**

**Premise correction:** There is no Redis anywhere in this repository. A case-insensitive search for "redis" across the whole tree (excluding `node_modules`/`.git`/`dist`) returns zero hits, and `go.mod`/`go.sum` list no Redis client. There is no external cache server, no connection string, and nothing to configure — caching is entirely in-process.

**Actual mechanism**

**1. The cache layer is a hand-rolled in-memory cache** — `store/cache/cache.go`
- `Cache` (`store/cache/cache.go:67`) is a thread-safe `sync.Map` with an atomic item counter, per-item expiration, and a background `cleanupLoop` goroutine (`store/cache/cache.go:200`) driven by `CleanupInterval`.
- `Config` (`store/cache/cache.go:42`) holds `DefaultTTL`, `CleanupInterval`, `MaxItems`, `OnEviction`. `DefaultConfig()` (`store/cache/cache.go:57`) = 10 min TTL / 5 min cleanup / 1000 items.
- Expiry is lazy-plus-sweep: `Get` (`store/cache/cache.go:123`) drops an entry whose `expiration` has passed, and the cleanup ticker sweeps the rest. Over `MaxItems`, `cleanupOldest` (`store/cache/cache.go:253`) evicts ~20%.

**2. Where it's "configured"** — `store/store.go:38-61`, in `store.New()`, not from any config file or env var. The TTL is a hardcoded literal:
```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
The same `cacheConfig` value is passed to three separate `cache.New` instances (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, `userSettingCache`. They're closed in `Store.Close()` (`store/store.go:72-79`).

**3. TTL for user entries: 10 minutes.** Every user write path calls `s.userCache.Set(...)` — `CreateUser` (`store/user.go:98`), `CreateUserIfNoUsers` (:122), `UpdateUser` (:132), `ListUsers` (:143), `GetUser` (:167) — and `Set` (`store/cache/cache.go:93`) delegates to `SetWithTTL` with `c.config.DefaultTTL`. Nothing in the user paths calls `SetWithTTL` with a custom duration, so the 10-minute default applies uniformly. Key is just the stringified user ID (`userCacheKey`, `store/user.go:88`); the read path only hits cache when `find.ID` is set (`store/user.go:149-156`) — lookups by username/email always go to the driver. Deletes invalidate explicitly via `deleteUserCache` (`store/user_delete.go:40`).

User *settings* use the same 10-minute TTL in a separate map, keyed `"<userID>-<settingKey>"` (`store/cache.go:7`, used in `store/user_setting.go:59,78,86,106`).

**Unrelated second cache, if that's what you meant:** RSS feeds are cached in a plain `map[string]*cacheEntry` guarded by a `sync.RWMutex` on `RSSService` (`server/router/rss/rss.go:42-50`), with `defaultCacheDuration = 1 * time.Hour` and `maxCacheSize = 50` (`server/router/rss/rss.go:23-27`). Per-user feeds are keyed `"user:"+username` (`server/router/rss/rss.go:114`) — so if "user entries" meant these, the TTL is **1 hour**, enforced in `getFromCache` (`server/router/rss/rss.go:357`) and also emitted as the `Cache-Control: max-age` header (`server/router/rss/rss.go:405`).

Both caches are per-process: in a multi-replica deployment each instance keeps its own copy, and there is no cross-instance invalidation.
