**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the delete-user transaction, in all three DB drivers. There is no database-level rule (no FK, no `ON DELETE CASCADE`) on the `reaction` table.

**What I checked**

1. **The delete-user transaction body.** `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`, and the identical functions in the postgres/mysql drivers) runs two separate reaction deletions before the user row is removed:
   - `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:379-388`) — removes reactions *on* the deleted user's memos (and comment descendants), keyed by `content_id`;
   - `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`) — `DELETE FROM reaction WHERE creator_id = ?`, i.e. the user's own reactions left on other people's memos.

   Same code in `store/db/postgres/user_delete.go:383` and `:401`, and `store/db/mysql/user_delete.go:420` and `:438`. The whole thing runs in one `tx` opened in `DeleteUser` (`store/db/sqlite/user_delete.go:29-59` et al.).

   `content_id` is the API-style memo name, built as `"memos/" + uid` in `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go:512-518`), which is why the by-content deletion needs the memo UIDs collected in `collectDeleteUserTargets`.

2. **The schema, for a cascade rule.** The `reaction` table is declared with no foreign keys in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` — only `creator_id INTEGER NOT NULL` and a `UNIQUE(creator_id, content_id, reaction_type)`. The original creation migrations match (`store/migration/sqlite/0.20/00__reaction.sql:2-9` and the postgres/mysql equivalents). A repo-wide grep for `FOREIGN KEY`/`CASCADE` under `store/migration/` returns hits only for `memo_share`, `user_setting`, `memo`, `memo_resource`, etc. — never `reaction`.

3. **Tests confirming the behavior.** `store/test/user_delete_test.go` seeds three reactions (lines 97-113) and asserts after deletion that only the peer's reaction on the peer's own memo survives (lines 217-220). `server/router/api/v1/test/user_service_delete_test.go:366,429-431` checks the reaction is still present when the transaction is rolled back at the pre-commit failpoint — confirming the removal is transactional Go work, not a DB rule.
