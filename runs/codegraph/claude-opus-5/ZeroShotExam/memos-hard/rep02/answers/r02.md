**Premise correction: this repo has no per-user API rate-limiting middleware.** There is no rate limiter of any kind — no request-per-window counting, no per-user or per-IP quota, no `golang.org/x/time/rate`, `tollbooth`, or similar dependency in `go.mod`. So there are no "request limits" to report.

What actually sits in the middleware/interceptor chain, registered in `server/router/api/v1/v1.go:RegisterGateway`:

- **gRPC-Gateway path** (`/api/v1/*`, `/file/*`): a single `gatewayAuthMiddleware` closure (`server/router/api/v1/v1.go:69-98`) that authenticates and enforces anonymous-access policy via the shared `Authorizer` (`server/router/api/v1/authz.go`).
- **Connect path** (`/memos.api.v1.*`): four interceptors registered at `server/router/api/v1/v1.go:133-138`, all defined in `server/router/api/v1/connect_interceptors.go` — `MetadataInterceptor` (headers → gRPC metadata, plus no-cache response headers), `LoggingInterceptor`, `RecoveryInterceptor` (panic → internal error), and `AuthInterceptor` (auth/access policy).
- **Process-wide Echo middleware**: only `middleware.Recover()` and CORS (`server/server.go:51-52`, `server/cors.go:13`).

The limits that do exist are size/concurrency caps, not rate limits, and none of them are per-user:

| Limit | Value | Location |
|---|---|---|
| Max API request body | `256 << 20` (256 MiB), applied to both gateway and Connect muxes | `server/router/api/v1/v1.go:20`, used at lines 126, 141, 144 |
| Concurrent thumbnail generation | 3 (global semaphore) | `server/router/api/v1/v1.go:59` |
| Concurrent image processing | 2 (global semaphore) | `server/router/api/v1/v1.go:60` |
| List page size | default 50, max 1000 | `server/router/api/v1/common.go:15-17` |

The only signal that resembles rate limiting is `connect.CodeResourceExhausted` appearing in the logging interceptor's client-error classification list (`server/router/api/v1/connect_interceptors.go:153`) — that's just an error-to-log-level mapping, and nothing in the codebase returns that code from a rate limiter.
