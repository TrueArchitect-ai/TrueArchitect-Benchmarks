**Premise correction:** Neither. There is no external message broker in this repository — no NATS, RabbitMQ, Kafka, or Redis client appears anywhere in `go.mod` or the Go sources. There are also no separate "delivery worker" processes; webhook dispatch happens entirely in-process inside the single memos server binary.

**Actual mechanism:** an in-memory buffered Go channel drained by a fixed pool of goroutines.

- **The "queue"** is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, holding `*WebhookRequestPayload` values (`internal/webhook/webhook.go:79`).

- **The "workers"** are 4 goroutines started from `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post` on every payload; failures are only logged via `slog.Warn` — there is no retry, no ack, and no persistence.

- **Producers**: `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full the payload is **dropped** with a warning, and a nil payload is dropped too. It's called from the memo activity path at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

- **Delivery itself** is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120-180`) using a shared `http.Client` with a 30s timeout and an SSRF-guarding `DialContext` (`internal/webhook/webhook.go:32-37`, `:59-77`), optionally signed with Standard Webhooks HMAC-SHA256 headers.

Consequence of the real design: because the queue is an unbounded-lifetime-free in-memory channel, anything still queued is lost on process restart, and bursts beyond 128 pending deliveries are silently dropped rather than backpressured. The same pattern is used for email at `internal/email/email.go:14-19`.
