**Premise correction:** There is no Redis anywhere in this repository — no `redis` dependency in `go.mod`, no client, no connection string, no config field or env var. My grep for `redis` across all Go, TS/TSX, YAML, and mod files returned zero hits. The cache layer is entirely **in-process, in-memory Go maps**, so there is nothing to connect to and no external server involved.

**Actual mechanism**

The cache is a hand-rolled, TTL'd, size-bounded map in `store/cache/cache.go`:

- `cache.Interface` (`store/cache/cache.go:11-32`) — `Set` / `SetWithTTL` / `Get` / `Delete` / `Clear` / `Size` / `Close`.
- Entries are `item{value, expiration, size}` (`store/cache/cache.go:35-39`); expiry is enforced lazily on `Get` plus a background `cleanupLoop`/`cleanup` goroutine (`store/cache/cache.go:218`), which is why `Close()` exists.
- `Set` just delegates: `c.SetWithTTL(ctx, key, value, c.config.DefaultTTL)` (`store/cache/cache.go:94`).

**"Connection" configuration** is the `cache.Config` literal built in `store.New` (`store/store.go:38-61`) — the closest thing to a connection setup:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That one config is shared by three independent per-process caches on `Store` (`store/store.go:27-29`): `instanceSettingCache`, `userCache`, `userSettingCache`. Package defaults match (`store/cache/cache.go:59`).

**TTL on user entries: 10 minutes.** Every user write path calls `s.userCache.Set(...)` — never `SetWithTTL` — so users inherit `DefaultTTL`: `CreateUser` (`store/user.go:98`), `CreateUserIfNoUsers` (`store/user.go:122`), `UpdateUser` (`store/user.go:132`), `ListUsers` (`store/user.go:143`), and `GetUser` (`store/user.go:167`). Keys are just the stringified user ID (`userCacheKey`, `store/user.go:88`). Reads are cached only when looking up by ID (`store/user.go:149-156`); lookups by username/email always hit the DB. Invalidation on delete is explicit in `deleteUserCache` (`store/user_delete.go:39-47`), which drops the user key and its user-setting keys. User *settings* use the same 10-minute TTL via `userSettingCache` with key `"<userID>-<settingKey>"` (`store/cache.go:7`).

Two caveats worth noting since they're easy to confuse with "the cache layer":

- **RSS feed cache** (`server/router/rss/rss.go:23-27`) is a *separate* map on `RSSService` with `defaultCacheDuration = 1 * time.Hour`, `maxCacheSize = 50`, and its own naive LRU-by-age eviction in `putInCache` (`server/router/rss/rss.go:369`). Per-user feeds are keyed `"user:"+username` (`server/router/rss/rss.go:114`) — so if you meant "TTL for user entries" in the RSS sense, that's **1 hour**, not 10 minutes.
- **Editor draft cache** (`web/src/components/MemoEditor/services/cacheService.ts`) is browser `localStorage` with no TTL at all — only a 500 ms debounce.

Because all of these are in-process, they are per-instance and not shared across replicas — a horizontal-scaling consideration that a Redis-backed design would have removed.
