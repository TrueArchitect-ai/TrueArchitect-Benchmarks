**Mechanism: explicit Go code, inside the user-deletion transaction — not a database-level rule.** Reactions are removed on two axes: reactions *authored by* the deleted user, and reactions *on* the deleted user's memos (including comment descendants).

## Explicit Go deletion

`DeleteUser` opens a transaction, collects targets, then runs `deleteUserTargetsTx`, which calls two reaction deletes among the first steps:

- `store/db/sqlite/user_delete.go:96` — `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)`
- `store/db/sqlite/user_delete.go:102` — `deleteReactionsByCreatorTx(ctx, tx, userID)`

The bodies:

- `store/db/sqlite/user_delete.go:400` — `DELETE FROM reaction WHERE creator_id = ?` (reactions the user left elsewhere)
- `store/db/sqlite/user_delete.go:380` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`deleteUserBatchSize`, line 14)

`content_id` is not a memo ID — `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go:512`) builds `"memos/" + memo.UID` strings from the memo set, which is gathered by `listDeleteUserMemoTreeIterative` (`store/db/sqlite/user_delete.go:133`) — a BFS over `memo_relation` with `type = 'COMMENT'`, so reactions on descendant comment threads are covered too.

All three drivers are identical in structure and SQL:
- `store/db/mysql/user_delete.go:96,102,417,437`
- `store/db/postgres/user_delete.go:96,102,380,400`
- `store/db/sqlite/user_delete.go:96,102,380,400`

Entry point is `store/user.go:171`, which delegates to `s.driver.DeleteUser` and then invalidates cache.

## Why it is *not* database-level

The `reaction` table declares no foreign key at all — `creator_id` is a bare `INTEGER NOT NULL`:

- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

Same in the original creation migrations (`store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql`) — the table was added in 0.20, after the 0.5 foreign-key regeneration pass, and was never given one. A grep for `FOREIGN KEY|CASCADE|REFERENCES` across `store/migration/` returns hits for `memo`, `memo_share`, `user_setting`, `memo_resource`, etc., but **no** row for `reaction`. So even on SQLite with `foreign_keys` enabled, nothing cascades here; the Go code is the only mechanism.

One consequence worth noting: because the match is on the string `memos/{uid}` rather than a key relationship, correctness depends on the UID list being complete and on that content-ID format staying in sync with wherever reactions are written.
