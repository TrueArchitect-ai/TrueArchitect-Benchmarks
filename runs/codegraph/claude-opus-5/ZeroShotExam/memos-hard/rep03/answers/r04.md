**Premise correction:** Neither. This repository (memos) has no external message broker — there is no NATS, RabbitMQ/AMQP, Kafka, or any other broker dependency anywhere in the Go code or `go.mod`. (The only grep hit for those terms across the repo is an incidental substring in `web/src/locales/ca.json`.) There are also no separate "delivery worker" processes; webhook delivery happens in-process inside the single `memos` server binary.

**Actual mechanism — an in-process buffered Go channel:**

- **The "queue" is declared at `internal/webhook/webhook.go:39`:**
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A package-level buffered channel with capacity 128, holding `*WebhookRequestPayload` values.

- **The "workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`** — each ranges over `asyncPostQueue` and calls `Post(payload)`; failures are only logged via `slog.Warn`, never retried or dead-lettered.

- **Producers:** `webhook.PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send onto the channel; if the buffer is full the payload is **dropped** with a warning (`default:` branch, lines 191-195). Callers are the memo lifecycle dispatchers in `server/router/api/v1/memo_service_webhooks.go` (`dispatchMemoRelatedWebhook` at line 71, `DispatchMemoCommentCreatedWebhook` at line 43).

- **Delivery itself** is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120-180`) using a shared `safeClient` with a 30s timeout and an SSRF-guarding `DialContext` (`internal/webhook/webhook.go:32-37`, `59-77`), optionally signed with Standard Webhooks HMAC-SHA256 headers.

Practical consequence: because the queue is an in-memory channel, queued webhooks are lost on process restart, and there is no cross-process fan-out or persistence.
