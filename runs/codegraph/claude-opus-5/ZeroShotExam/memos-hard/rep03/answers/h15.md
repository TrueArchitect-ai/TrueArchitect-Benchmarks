h15.

Memo visibility is enforced independently in a number of places — there is no single choke point. The gRPC/Connect API has one shared helper (`checkMemoReadAccess`) but most other surfaces re-implement the rule.

**Core API (memo service)**
- `checkMemoReadAccess` — public passes; non-public requires auth; private requires creator — `server/router/api/v1/memo_service.go:39` (callers: `GetMemo` at :356, parent-memo check at :367, `ListMemoComments` at `server/router/api/v1/memo_service_comments.go:148`)
- `ListMemos` query-scoping — anonymous → `VisibilityList=[PUBLIC]`; authed → CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`; other-user listing → `[PUBLIC, PROTECTED]` — `server/router/api/v1/memo_service.go:213-227`

**Other API surfaces that re-check independently**
- `ListMemoReactions` / `UpsertMemoReaction` — `server/router/api/v1/reaction_service.go:30,38,83`
- `ListMemoAttachments` — `server/router/api/v1/memo_attachment_service.go:214-224`
- `checkAttachmentAccess` (attachment reads via API, resolves the owning memo) — `server/router/api/v1/attachment_service.go:422-453`
- `CreateMemoComment` (parent-memo read gate + comment inherits parent visibility) — `server/router/api/v1/memo_service_comments.go:41,52`
- `GetUserStats` / `ListAllUserStats` — visibility list scoping so stats don't leak private memos — `server/router/api/v1/user_service_stats.go:84,90,218,220`
- `GetMemoByShare` — deliberate bypass: a valid, unexpired share token authorizes viewing regardless of visibility (archived/missing still 404) — `server/router/api/v1/memo_share_service.go:151-192`

**Non-gRPC HTTP surfaces**
- `checkAttachmentPermission` — raw file/blob serving, including anonymous-instance rule and `share_token` query-param fallback — `server/router/fileserver/fileserver.go:650-704`
- RSS feeds (explore + per-user) — hard-restricted to `[PUBLIC]` — `server/router/rss/rss.go:90,141`
- Sitemap XML — hard-restricted to `[PUBLIC]` — `server/router/frontend/frontend.go:149-152`

**Push/notification delivery**
- SSE broadcast filter `SSEClient.canReceive` — private events only to creator or admin — `server/router/api/v1/sse_hub.go:135-142` (event visibility populated at `server/router/api/v1/sse_event_helpers.go:29-37`)
- `canViewerAccessMemo` for in-app notification recipients — `server/router/api/v1/user_service_notifications.go:302-316`
- `canViewerAccessMemo` duplicated for email notifications — `server/notification/email.go:307-320`
- Mention-notification gating (private memos/relations don't notify non-creators) — `server/router/api/v1/memo_mention_helpers.go:62,67,84`

**Store layer (mechanism, not policy)**
- `FindMemo.VisibilityList` translated to a SQL `visibility IN (...)` predicate — `store/memo.go:69`, `store/db/sqlite/memo.go`, `store/db/mysql/memo.go:104-111`, `store/db/postgres/memo.go:89-96`

Note the duplication: `canViewerAccessMemo` exists twice with identical logic (`user_service_notifications.go` uses `isSuperUser`, `email.go` inlines `user.Role == store.RoleAdmin`), and `checkMemoReadAccess` (API) vs. `checkAttachmentPermission` (fileserver) apply the same rule with different admin handling — the API helper does *not* grant admins access to private memos, while the fileserver and attachment paths do.
