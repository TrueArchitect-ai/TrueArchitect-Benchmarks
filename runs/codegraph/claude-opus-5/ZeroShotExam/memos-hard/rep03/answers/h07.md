The avatar URL the browser loads is minted by the API converter (`AvatarUrl = "/file/" + userpb.Name + "/avatar"` → `/file/users/{username}/avatar`, `server/router/api/v1/user_service_converters.go:31-39`), rendered by `UserAvatar` (`web/src/components/UserAvatar.tsx`) as a plain `<img src>`. That GET is served entirely outside gRPC, by the Echo file server:

Details worth noting:

- The `:identifier` path segment is treated strictly as a **username** — `getUserByUsername` builds `&store.FindUser{Username: &identifier}`; there's no ID fallback (`server/router/fileserver/fileserver.go:715-717`).
- `Store.GetUser` consults `userCache` **only when `find.ID` is set**, so an avatar request always falls through to `ListUsers` → the driver → SQL; the row is written back into the cache afterwards (`store/user.go:148-169`).
- The stored data is the `user.avatar_url` column itself, holding a `data:<type>;base64,<...>` URI — not a file on disk. `parseDataURI` (regex at `fileserver.go:98`) splits it, and the MIME type is checked against `avatarAllowedTypes` before `c.Blob` writes the bytes with `nosniff` security headers and a long cache-control (`fileserver.go:196-209`).
- Access control for *another* user's avatar: on a private instance (`!s.Profile.AllowAnonymous()`) any authenticated viewer suffices — session cookie, access token, or PAT via `authenticator.AuthenticateToUser`; there is no per-user check. On a public instance the endpoint is anonymous.
