**Premise correction: there is no per-user API rate-limiting middleware in this repository.** No interceptor, Echo middleware, or handler enforces a per-user request rate or quota, and no rate-limiting dependency (`golang.org/x/time/rate`, tollbooth, ulule/limiter, etc.) appears in `go.mod`. A grep for rate/limit/throttle terms across `server/`, `internal/`, and `store/` turns up only pagination limits and the unrelated items below.

**What actually is registered on the API chain** (`server/router/api/v1/v1.go:133-144`), in order:

- `NewMetadataInterceptor()` — HTTP headers → gRPC metadata
- `NewLoggingInterceptor(logStacktraces)`
- `NewRecoveryInterceptor(logStacktraces)`
- `NewAuthInterceptor(authorizer)` — authentication/authorization only

Plus `middleware.Recover()` and the CORS middleware at `server/server.go:51-52`, and a gRPC-Gateway auth middleware at `server/router/api/v1/v1.go:69-98`.

**The abuse-control limits that do exist** are size- and concurrency-based, not rate-based:

- Request body cap of 256 MiB — `maxAPIRequestBytes` (`server/router/api/v1/v1.go:20`), applied via `http.MaxBytesHandler` and `connect.WithReadMaxBytes` (`v1.go:126,141,144`)
- Global (not per-user) concurrency semaphores: 3 concurrent thumbnail generations, 2 concurrent image-processing ops (`server/router/api/v1/v1.go:59-60`); 3 in the file server (`server/router/fileserver/fileserver.go:46,116`). Exceeding image processing returns `ResourceExhausted` (`server/router/api/v1/attachment_service.go:160`)
- Per-request batch size caps: 100 users (`user_service.go:23`), 100 instance settings (`instance_service.go:22`), 100 attachment deletes (`attachment_service.go:35`), 10 link-metadata URLs (`memo_service.go:26`)

The only mention of rate limiting as a concept is an aspirational doc comment about email sending at `internal/email/doc.go:86`; it is not implemented.
