**Premise correction:** Neither. This repository (memos) has no message broker at all — no NATS, RabbitMQ, AMQP, or Kafka dependency exists anywhere in the Go module or config. There is also no separate "worker" service or process; webhook delivery happens in-process inside the main server binary.

**Actual mechanism:** an in-memory buffered Go channel with a fixed pool of goroutines.

- **The "queue"** is declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A buffered channel of capacity 128, in the package-level `var` block alongside the shared `safeClient`.

- **The "workers"** are started in `internal/webhook/webhook.go:42-55` — a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)` for every item, logging a warning on failure. They live for the process lifetime; the channel is never closed.

- **Producers:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send onto the channel. If the buffer is full, the payload is **dropped** with a warning — there is no retry, persistence, or dead-letter path. Callers are `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, from the memo created/updated/deleted and comment-created dispatchers.

- **Delivery itself** is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120-180`), using an SSRF-guarded `http.Client` (`safeDialContext`, line 59) with a 30s timeout, optionally signed with Standard Webhooks HMAC-SHA256 headers (`webhook-id` / `webhook-timestamp` / `webhook-signature`).

Consequence worth noting: because the queue is in-process memory, anything buffered is lost on restart or crash, and bursts beyond 128 pending deliveries are silently dropped rather than backpressured.
