**Premise correction:** Neither. This repo (memos) has no external message broker at all — there is no NATS, RabbitMQ, AMQP, Kafka, or Redis dependency anywhere in the Go module or config (a repo-wide grep for those terms returns nothing). Webhook delivery is entirely in-process.

**Actual mechanism:**

- **The "queue" is a buffered Go channel**, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, holding `*WebhookRequestPayload` values directly — no serialization, no network hop.

- **The "workers" are 4 goroutines** started in the package `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. They live for the process lifetime and vanish with it — nothing is durable.

- **Producers** call `webhook.PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking `select` send: if the buffer is full, the payload is **dropped** with a `slog.Warn` (line 189-195). There is no retry, no dead-letter, no persistence. Callers are the memo dispatch helpers in `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

- **Delivery itself** is `Post` (`internal/webhook/webhook.go:120`): a plain JSON HTTP POST via a shared `safeClient` with a 30s timeout and an SSRF-guarding `DialContext` (`internal/webhook/webhook.go:32-37`, `:59`), optionally signed with Standard Webhooks HMAC-SHA256 headers (`webhook-id` / `webhook-timestamp` / `webhook-signature`).

The same in-process pattern is used for email at `internal/email/email.go:14` (`asyncEmailQueue`, same 128 buffer + drop-on-full behavior), which confirms it's a deliberate house pattern rather than a broker integration that's missing.
