**Premise correction: there is no per-user API rate-limiting middleware in this repository.** No middleware, interceptor, or handler enforces a per-user (or per-IP) request-rate limit, and there is no request-limit configuration to report.

Evidence:

- **The full server middleware chain is short and contains no limiter.** `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware(profile)`. The only other `e.Use(...)` calls in the codebase are the frontend static-file and SPA-fallback middlewares at `server/router/frontend/frontend.go:54,59`.
- **The Connect RPC interceptor stack has no limiter either.** `server/router/api/v1/v1.go:133-138` wires exactly four interceptors — `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor` — all defined in `server/router/api/v1/connect_interceptors.go`. The gRPC-Gateway mux at `server/router/api/v1/v1.go:96-98` registers a single middleware, `gatewayAuthMiddleware`, which does authentication/authorization only.
- **No rate-limiting dependency is used.** `golang.org/x/time` appears in `go.mod:151` marked `// indirect`, and no source file imports `golang.org/x/time/rate`. The only mention of `rate.NewLimiter` in the tree is illustrative documentation for a feature that is not implemented: `internal/email/README.md:286-295` ("### 5. Implement Rate Limiting"), echoed as a to-do note in `internal/email/doc.go:86`.

What does exist, and is easy to mistake for rate limiting — these are **global concurrency and payload-size caps, not per-user request rates**:

| Limit | Value | Location |
|---|---|---|
| Max API request body | 256 MiB (`256 << 20`) | `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` at lines 126, 144 and `connect.WithReadMaxBytes` at line 141 |
| Concurrent thumbnail generation (API service) | 3 | `server/router/api/v1/v1.go:59` |
| Concurrent image processing | 2 | `server/router/api/v1/v1.go:60`, acquired at `server/router/api/v1/attachment_service_image.go:68-75` |
| Concurrent thumbnail generation (file server) | 3 (`maxConcurrentThumbnails`) | `server/router/fileserver/fileserver.go:45-46`, used at line 116 and acquired at line 448 |

These are process-wide `semaphore.Weighted` gates shared by all callers; they throttle simultaneous work, not a user's requests per unit time. The one user-visible rejection they can produce is `codes.ResourceExhausted, "too many image processing requests"` at `server/router/api/v1/attachment_service.go:160`, which fires when the global image-processing semaphore is saturated — regardless of which user or how many requests that user has made.
