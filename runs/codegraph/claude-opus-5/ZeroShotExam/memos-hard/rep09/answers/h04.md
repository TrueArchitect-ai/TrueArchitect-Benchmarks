**No** — outside the factory, the MySQL driver is never constructed in production code. The only exception is a zero-value struct literal in a unit test.

Evidence:

- The factory is `NewDBDriver` in `store/db/db.go:14`, whose `case "mysql":` at `store/db/db.go:22` calls `mysql.NewDB(profile)`. That is the **only** call site of `mysql.NewDB` in the repo — a repo-wide grep for `mysql.NewDB` returns exactly one hit (`store/db/db.go:22`), and the only file importing `github.com/usememos/memos/store/db/mysql` is `store/db/db.go:8`. Since the package is imported nowhere else, no other package can construct it.
- The constructor itself is `store/db/mysql/mysql.go:20` (`func NewDB(profile *profile.Profile) (store.Driver, error)`), which builds `driver := DB{profile: profile}` at `store/db/mysql/mysql.go:29`.
- Callers that need a driver go through the factory: `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70` all call `db.NewDBDriver(...)`.
- The one direct construction of the `DB` type outside `NewDB` is in-package test code: `db := &DB{}` at `store/db/mysql/auth_config_test.go:12`, a zero-value struct used only to invoke the pure method `IsRetryableAuthenticationMutationError` (no connection opened). The same pattern exists for postgres (`store/db/postgres/auth_config_test.go:12`).
- For contrast, sibling drivers *are* constructed directly outside the factory in a couple of places (`sqlite.NewDB` at `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416`); MySQL has no such call.
- `store/test/containers.go` references `github.com/go-sql-driver/mysql` and the testcontainers `mysql` module (lines 16, 20, 101–131, 145) — that's the third-party SQL driver and container harness, not the repo's `store/db/mysql` driver type.
