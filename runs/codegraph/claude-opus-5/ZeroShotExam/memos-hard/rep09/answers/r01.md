**Premise correction:** There is no Redis anywhere in this repository. `go.mod`/`go.sum` contain no Redis client (no `go-redis`, `redigo`, etc.), and there are no Redis references in Go, TS, config, or compose files. There is therefore no "Redis connection to configure" — no host/port/DSN, no env var, no connection pool. The cache layer is a purely **in-process, in-memory** cache, so it is per-server-process and is lost on restart (and is not shared across replicas).

**Actual mechanism:**

*The cache implementation* — `store/cache/cache.go`. `Cache` is a thread-safe map (`sync.Map`) with per-item expiration: `item` holds `value`, `expiration`, `size` (lines 34–39), and `SetWithTTL` stamps `expiration: time.Now().Add(ttl)` (line 112). `Get` treats an entry past its expiration as a miss and deletes it (lines 135–144). A background `cleanupLoop` goroutine sweeps expired items on `CleanupInterval` (lines 200–250), plus a `cleanupOldest` size-based eviction when `MaxItems` is exceeded.

*Where it's "configured"* — `store.New` in `store/store.go:38–60`, not a connection string. It builds one `cache.Config` literal (lines 40–45) and hands the same config to three separate caches (lines 51–53):

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

`instanceSettingCache`, `userCache`, `userSettingCache`. `store/cache/cache.go:56–63` (`DefaultConfig`) has the identical values, but `store.New` does not call it — it duplicates the literal.

**TTL for user entries: 10 minutes**, with no per-user override. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98, 122, 132, 143, 167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93–95`) — nothing in the user path calls `SetWithTTL` directly. Keys are the plain user ID (`userCacheKey`, `store/user.go:88–90`), and only `GetUser` lookups **by ID** hit the cache (`store/user.go:149–156`); lookups by username/email always fall through to the driver. Staleness is bounded well under 10 minutes in practice because updates overwrite the entry and `store/user_delete.go:39` (`deleteUserCache`) evicts on delete.

Two unrelated things that might be the source of the "cache layer" framing:
- `server/router/rss/rss.go` has its own independent in-memory feed cache — `defaultCacheDuration = 1 * time.Hour`, `maxCacheSize = 50` (lines 23–27), keyed `"user:"+username` for per-user feeds (line 114). That's a 1-hour TTL, and it does not use `store/cache` at all.
- `web/src/components/MemoEditor/services/cacheService.ts` is a browser `localStorage` draft cache with **no TTL** — entries persist until overwritten or cleared.
