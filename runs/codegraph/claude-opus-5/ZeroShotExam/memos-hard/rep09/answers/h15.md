Memo read-visibility is enforced in several independent places — there is no single chokepoint. Distinct enforcement sites:

**Core gRPC/Connect API (memo service)**

1. Single-memo read gate `checkMemoReadAccess` (archived → creator only; non-PUBLIC → auth required; PRIVATE → creator only) — `server/router/api/v1/memo_service.go:39-66`; called from `GetMemo` (`:355`), the parent-memo check for comments (`:367`), and `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`)
2. `ListMemos` query scoping — anonymous → `VisibilityList = [PUBLIC]`; authed → CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` — `server/router/api/v1/memo_service.go:218-227`
3. Memo-relation expansion filter (so related/comment memos you can't see aren't leaked) — `server/router/api/v1/memo_service_converter.go:183-187` (`batchConvertMemoRelations`), `server/router/api/v1/memo_relation_service.go:108-112`, `server/router/api/v1/memo_service_comments.go:156-161`
4. User stats aggregation scoping — `server/router/api/v1/user_service_stats.go:82-92` (`ListAllUserStats`) and `:216-221` (`GetUserStats`)
5. Reaction read/write gate — `server/router/api/v1/reaction_service.go:29-40` and `:82-85`
6. Comment creation gate on the parent memo — `server/router/api/v1/memo_service_comments.go:33-43`
7. Notification viewer check `canViewerAccessMemo` (PRIVATE → creator, PROTECTED → any authed, super-user bypass) — `server/router/api/v1/user_service_notifications.go:302-316`; related mention-eligibility checks in `server/router/api/v1/memo_mention_helpers.go:62-84`

**Attachment/blob surfaces**

8. Attachment access derived from the linked memo's visibility — `server/router/api/v1/attachment_service.go:436-455`, and `server/router/api/v1/memo_attachment_service.go:213-224`
9. Raw file serving (separate Echo router, own auth path, plus a share-token fallback) — `server/router/fileserver/fileserver.go:665-703` (`checkAttachmentPermission`)

**Non-RPC / push surfaces**

10. SSE live-event fan-out filter — `server/router/api/v1/sse_hub.go:134-143` (`SSEClient.canReceive`: PRIVATE events only to creator or admin; unknown visibility denied)
11. RSS feeds — public-only via `VisibilityList: []store.Visibility{store.Public}` — `server/router/rss/rss.go:90` (explore) and `:141` (per-user)
12. Sitemap generation — public-only — `server/router/frontend/frontend.go:150`
13. Email notification content gating — `server/notification/email.go:313`

**Related, for completeness**

- `GetMemoByShare` deliberately *bypasses* visibility: the share token is the authorization, so only archived/missing memos are rejected — `server/router/api/v1/memo_share_service.go:153-192`. Share *management* (create/list/delete) is creator-or-superuser only (`:43`, `:92`, `:133`).
- The ACL layer explicitly delegates: `GetMemo`/`ListMemos`/`ListMemoComments`/`GetMemoByShare` are listed as public methods with the comment "visibility filtering done in service layer" — `server/router/api/v1/acl_config.go:32-41`.
- The store layer itself enforces nothing; it only applies whatever `FindMemo.VisibilityList`/`Filters` the caller supplies — `store/memo.go:116-131`, `store/db/sqlite|mysql|postgres/memo.go`.
