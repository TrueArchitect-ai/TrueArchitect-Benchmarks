**Premise correction:** Neither. There is no message broker in this repository at all — no NATS, RabbitMQ, Kafka, Redis, or Asynq client appears in `go.mod`/`go.sum`, and there are no "webhook delivery workers" as a separate process. (The only grep hits for "nats" are Catalan words like "eliminats" in `web/src/locales/ca.json`.)

**Actual mechanism:** webhook delivery is fully in-process, backed by a plain buffered Go channel.

- **The "queue"** is declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  a package-level buffered channel with capacity 128, in the same `var` block as the shared SSRF-guarded `safeClient`.

- **The "workers"** are 4 goroutines started in the package `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)` (`internal/webhook/webhook.go:120`), which marshals the payload, optionally adds Standard Webhooks HMAC headers (`webhook-id`/`webhook-timestamp`/`webhook-signature`), and POSTs it. Failures are only logged via `slog.Warn` — no retry, no dead-letter.

- **Producers** call `PostAsync` (`internal/webhook/webhook.go:184`), a non-blocking `select` send: if the buffer is full, the payload is **dropped** with a warning ("Dropped webhook dispatch because the async queue is full"). Call sites are in `server/router/api/v1/memo_service_webhooks.go:43` and `:71` (`dispatchMemoRelatedWebhook`, `DispatchMemoCommentCreatedWebhook`), reached from memo create/update/delete/comment paths.

Practical consequences of this design versus a broker: the queue is not durable (a restart loses buffered deliveries), delivery is at-most-once with no retry or backoff, and it does not fan out across multiple server instances — each process has its own channel and its own 4 workers.
