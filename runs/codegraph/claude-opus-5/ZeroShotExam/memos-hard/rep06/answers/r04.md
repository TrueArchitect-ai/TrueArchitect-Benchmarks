**Premise correction:** Neither. This repository (memos) has no external message broker at all — there is no NATS, RabbitMQ, AMQP, Kafka, or Redis dependency anywhere (`go.mod`/`go.sum` contain none, and no Go source references them). There is also no separate "webhook delivery worker" process; delivery happens in-process inside the single server binary.

**Actual mechanism — an in-process buffered Go channel:**

- The "queue" is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The "workers" are 4 goroutines started in `func init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure.
- `Post` (`internal/webhook/webhook.go:120`) does the actual HTTP POST via a shared `http.Client` (`safeClient`, line 32) whose `DialContext` is SSRF-guarded (`safeDialContext`, line 59), and signs the request with Standard Webhooks HMAC-SHA256 headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) when a signing secret is present.
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking `select` send: if the 128-slot buffer is full, the payload is **dropped** with a warning ("Dropped webhook dispatch because the async queue is full"). There is no persistence, retry, or redelivery.
- Callers are the memo lifecycle dispatchers in `server/router/api/v1/memo_service_webhooks.go` (`DispatchMemoCreatedWebhook`, `...Updated...`, `...Deleted...`, `DispatchMemoCommentCreatedWebhook` → `webhook.PostAsync`), reached from `server/router/api/v1/memo_service.go` and `memo_update_helpers.go`.

Practical consequence: because the queue is an unpersisted in-memory channel with a drop-on-full policy, webhook deliveries are best-effort and are lost on server restart or under burst load.
