**Premise correction: this repository has no per-user API rate-limiting middleware.** There is no rate limiter registered anywhere in the request path, and no rate-limiting library is a direct dependency (`golang.org/x/time` appears in `go.mod:151` only as an indirect dependency; nothing imports it).

What actually is registered:

- **Echo HTTP middleware** — `server/server.go:51-52`: only `middleware.Recover()` and `newCORSMiddleware(profile)`.
- **Connect RPC interceptors** — `server/router/api/v1/v1.go:133-137`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). Auth/authz only — no per-user request accounting.
- **gRPC-Gateway middleware** — `server/router/api/v1/v1.go:69-97`: a single auth middleware.

The only limits that exist are global (process-wide), not per user, and none of them count requests over time:

- **Request body size**: `maxAPIRequestBytes = 256 << 20` (256 MiB) — `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` and `connect.WithReadMaxBytes` at lines 126, 141, 144.
- **Concurrency semaphores** (server-wide, shared by all users) — `server/router/api/v1/v1.go:59-60`: `thumbnailSemaphore` = 3 concurrent thumbnail generations, `imageProcessingSemaphore` = 2 concurrent EXIF-strip operations. Exceeding the latter blocks until a slot frees or the context ends; on context cancellation the upload fails with `ResourceExhausted "too many image processing requests"` (`server/router/api/v1/attachment_service.go:158-161`, helper at `server/router/api/v1/attachment_service_image.go:67-77`). This throttles concurrency, not request rate, and is not scoped per user.
- **Image pixel cap**: `maxImagePixels` validated in `server/router/api/v1/attachment_service_image.go:79-90`.

Rate limiting is only mentioned as a non-implemented suggestion in a doc comment: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse").
