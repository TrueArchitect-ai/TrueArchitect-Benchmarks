**Premise correction: this repository has no rate-limiting middleware at all** — no per-user limit, no per-IP limit, no request-count/window limits anywhere. A repo-wide grep for `rate.?limit|ratelimit|throttl|429|TooManyRequests` turns up only aspirational documentation (`internal/email/doc.go:86` "Rate limit email sending to prevent abuse" and a suggested-future-work snippet in `internal/email/README.md:286-295`), and there is no rate-limiter dependency in `go.mod` (no `golang.org/x/time/rate`, tollbooth, ulule/limiter, etc.).

What actually is registered on the request path:

- **Echo-level middleware** — `server/server.go:51-52`: only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`).
- **Connect RPC interceptors** — `server/router/api/v1/v1.go:133-138`, in order: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor`. Definitions in `server/router/api/v1/connect_interceptors.go`. The auth one enforces identity/anonymous-access policy, not request volume.
- **gRPC-Gateway auth middleware** — `server/router/api/v1/v1.go:69-98`, again authentication/authorization only.

The only "limits" enforced per request are size and concurrency caps, which are what the question may be reaching for:

| Limit | Value | Location |
|---|---|---|
| Max API request body | 256 MiB (`maxAPIRequestBytes = 256 << 20`) | `server/router/api/v1/v1.go:20`, applied at :126, :141, :144 |
| Upload buffer cap | 32 MiB default (`MaxUploadBufferSizeBytes = 32 << 20`) when no instance setting | `server/router/api/v1/attachment_service.go:27,121-122` |
| Concurrent image (EXIF-strip) processing | 2 in flight, global | `server/router/api/v1/v1.go:60`; returns `ResourceExhausted "too many image processing requests"` at `attachment_service.go:158-160` |
| Concurrent thumbnail generation | 3 in flight, global | `server/router/api/v1/v1.go:59` and `server/router/fileserver/fileserver.go:45-46,116,448` |
| Max page size for list RPCs | 1000 (`MaxPageSize`) | `server/router/api/v1/common.go:16-17,52-53` |

Note those two semaphores are process-wide, not per-user — they bound concurrency (excess requests block on `Acquire` until ctx cancellation), not request rate, so a single user can still issue unlimited requests over time.
