**Premise correction:** Neither. This repo (memos) has no external message broker at all — no NATS, no RabbitMQ, no AMQP/Kafka client. `go.mod` contains no broker dependency, and the only repo-wide match for "nats" is the Catalan word inside `web/src/locales/ca.json`. There is also no "webhook delivery worker" service/process; delivery happens in-process inside the single Go server binary.

**Actual mechanism — an in-process buffered Go channel:**

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel with capacity 128.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`; failures are only logged via `slog.Warn`.
- **Producer:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning — there is no retry, persistence, or dead-letter path.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` (`dispatchMemoRelatedWebhook` and `DispatchMemoCommentCreatedWebhook`) enqueue one payload per registered user webhook.
- **Actual delivery:** `Post` (`internal/webhook/webhook.go:120`) does a plain `http.Client` POST using the shared `safeClient` (`:32`), which has a 30s timeout and an SSRF-guarding `DialContext`, plus optional Standard-Webhooks HMAC-SHA256 signing headers.

The same in-process channel pattern is used for email at `internal/email/email.go:14` (`asyncEmailQueue`), which reinforces that this codebase deliberately avoids an external broker.

Consequence worth noting: because the queue is an unpersisted in-memory channel, any webhooks still buffered are lost on process restart, and bursts beyond 128 pending deliveries are silently dropped.
