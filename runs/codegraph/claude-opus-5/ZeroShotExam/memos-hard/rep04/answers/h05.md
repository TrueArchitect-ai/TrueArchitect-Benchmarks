**Mechanism: explicit Go code** — not a database-level rule. Reactions are deleted by hand-written `DELETE FROM reaction` statements inside the user-deletion transaction, in all three drivers. There is no foreign key or `ON DELETE CASCADE` on the `reaction` table.

**What I checked**

1. **The deletion orchestrator.** `deleteUserTargetsTx` explicitly deletes reactions twice, in two directions:
   - `store/db/sqlite/user_delete.go:96` / `:102` (and identically `store/db/mysql/user_delete.go:96,102`, `store/db/postgres/user_delete.go:96,102`)
   - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — removes reactions *on* the user's memos (including comment descendants), where `contentIDs` are `"memos/<uid>"` strings built by `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go:512-518`).
   - `deleteReactionsByCreatorTx(ctx, tx, userID)` — removes reactions the user *made* on anyone's content.

2. **The statement bodies.**
   - `deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 — `store/db/sqlite/user_delete.go:380`, `store/db/mysql/user_delete.go:417`, `store/db/postgres/user_delete.go:380`.
   - `deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = ?` — `store/db/sqlite/user_delete.go:400`, `store/db/mysql/user_delete.go:437`, `store/db/postgres/user_delete.go:400`.

3. **The schema, to rule out a DB-level rule.** The `reaction` table has no foreign keys at all — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`
   - original creation: `store/migration/{sqlite,mysql,postgres}/0.20/00__reaction.sql`

   A repo-wide grep for `REFERENCES` / `ON DELETE` across `store/migration/` returns cascades only for `memo_share`, `user_setting`, `memo_resource`, `memo`, etc. — never for `reaction`. (Note `content_id` is a text string like `memos/<uid>`, not an integer FK, so it couldn't cascade anyway.)

4. **The call path above it.** `Store.DeleteUser` (`store/user.go:171-181`) just delegates to the driver and then updates caches — no additional reaction cleanup there. The whole driver-level delete runs in one transaction that commits at `store/db/mysql/user_delete.go:51` (same shape in the other two drivers), so reaction removal is atomic with the user row deletion.
