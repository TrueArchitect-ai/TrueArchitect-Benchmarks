**Premise correction: there is no nightly database-cleanup job in this repository.** The question presupposes a registered job that doesn't exist.

What actually exists:

**1. The cron scheduler is a standalone library with zero registered jobs.** `internal/scheduler/` (`scheduler.go`, `parser.go`, `job.go`, `middleware.go`) implements a generic cron scheduler — `Scheduler.Register(*Job)`, a 5/6-field cron expression parser, timezone and middleware support. But `github.com/usememos/memos/internal/scheduler` is imported by exactly two files, both tests: `internal/scheduler/example_test.go:10` and `internal/scheduler/integration_test.go:13`. No production code anywhere in `cmd/`, `server/`, or `store/` constructs a scheduler or registers a job, so no job of any kind — cleanup or otherwise — is scheduled at runtime.

**2. The "2 AM daily cleanup" you may be thinking of is documentation, not a job.** Illustrative snippets use a `daily-cleanup` job at `"0 2 * * *"`:
- `internal/scheduler/doc.go:15-16` — `Name: "daily-cleanup"`, `Schedule: "0 2 * * *", // 2 AM daily`
- `internal/scheduler/README.md:34-35` — the same example
- `internal/scheduler/example_test.go:99-100` — a `cleanup` job at `"0 2 * * *"` inside `Example_multipleJobs`, which prints text rather than touching a database

These are sample code demonstrating the API. `README.md:241-245` shows a different fictional example (`stale-session-cleanup` at `"0 3 * * *"`), which is a good illustration that these times are arbitrary documentation choices, not a configured schedule.

**3. The only real cleanup loop in the codebase isn't cron-driven and isn't database-related.** `store/cache/cache.go:200-215` runs `cleanupLoop()`, an in-memory cache expiry sweeper driven by a `time.Ticker` on `config.CleanupInterval` — an interval timer, not a cron expression, and it evicts expired entries from a `sync.Map`, not database rows.

So: nothing cleans the database on a schedule here. If you're looking for where such a job *would* go, the scheduler library at `internal/scheduler/` is wired up and tested but never instantiated by the server.
