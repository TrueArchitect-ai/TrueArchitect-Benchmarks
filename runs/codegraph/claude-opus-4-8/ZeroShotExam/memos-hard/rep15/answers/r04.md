**Premise correction:** The premise is false in both directions — the webhook delivery workers consume from neither NATS nor RabbitMQ. Memos has no external message broker for webhooks at all; there is no declared queue on any broker.

**Actual mechanism:** Webhook delivery is handled entirely in-process using a buffered Go channel as the queue.

- The "queue" is a plain buffered channel declared as a package-level variable in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  (capacity 128, in-memory only).

- The "delivery workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post()` to fire the HTTP POST:
  ```go
  for range 4 {
      go func() {
          for payload := range asyncPostQueue {
              if err := Post(payload); err != nil { ... }
          }
      }()
  }
  ```

- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto the channel and simply **drops** the payload (with a warning log) if the buffer is full. There is no persistence, no ack, and no cross-process broker.

- `Post()` (`internal/webhook/webhook.go:120`) then delivers each webhook as a direct HTTP `POST` (JSON body, optional HMAC-SHA256 "Standard Webhooks" signature) using a shared SSRF-guarded `http.Client`.

So the whole path is: gRPC handlers in `server/router/api/v1/memo_service_webhooks.go` → `webhook.PostAsync` → in-memory buffered channel `asyncPostQueue` → 4 goroutine workers → `webhook.Post` HTTP delivery. No NATS or RabbitMQ is involved anywhere in the codebase.
