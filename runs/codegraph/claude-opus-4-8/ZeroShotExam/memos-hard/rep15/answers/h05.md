**Mechanism: Explicit Go code** (not a DB-level cascade). A user's own emoji reactions are removed by an explicit `DELETE FROM reaction WHERE creator_id = ?` statement run inside the delete-user transaction.

**Evidence locations**

Each SQL backend's `DeleteUser` runs `deleteUserTargetsTx`, whose ordered list of deletes explicitly calls `deleteReactionsByCreatorTx`:

- `store/db/sqlite/user_delete.go` — `deleteUserTargetsTx` calls `deleteReactionsByCreatorTx(ctx, tx, userID)`, defined as:
  ```go
  func deleteReactionsByCreatorTx(ctx context.Context, tx *sql.Tx, userID int32) error {
      _, err := tx.ExecContext(ctx, `DELETE FROM reaction WHERE creator_id = `+deleteUserPlaceholder(1), userID)
      return err
  }
  ```
- `store/db/postgres/user_delete.go` — identical `deleteReactionsByCreatorTx` (`DELETE FROM reaction WHERE creator_id = $1`), called from `deleteUserTargetsTx`.
- `store/db/mysql/user_delete.go` — same structure (`DeleteUser` → `deleteUserTargetsTx`), confirmed via CodeGraph.

Note there are actually **two** explicit reaction-deletion steps in `deleteUserTargetsTx`, both in Go:
1. `deleteReactionsByCreatorTx` — reactions the user *authored* (their emoji reactions), keyed on `creator_id`.
2. `deleteReactionsByContentIDsTx` — reactions *on* the user's memos, keyed on `content_id` (`"memos/"+uid`), so reactions others left on the deleted user's memos are also removed.

**What I checked**

- The three per-dialect `DeleteUser` implementations and their shared `deleteUserTargetsTx` orchestration (sqlite/postgres/mysql `user_delete.go`) — reactions are handled there explicitly rather than left to the DB.
- The final `deleteUserRowTx` just does `DELETE FROM user WHERE id = ?` — it does not rely on an `ON DELETE CASCADE` for reactions; the reaction cleanup is a separate explicit statement executed *before* the user row is removed. This confirms the mechanism is application code, not a database-level cascade rule.
