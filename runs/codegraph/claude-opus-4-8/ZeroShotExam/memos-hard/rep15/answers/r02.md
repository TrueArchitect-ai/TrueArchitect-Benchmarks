**Premise correction: this repository has no per-user API rate-limiting middleware.** There is nothing to register and no request limits to report, so the question's premise doesn't hold.

I verified this by examining the full API interceptor/middleware chain and searching the entire Go backend for any limiter/throttle logic:

- The complete interceptor chain is registered in `server/router/api/v1/v1.go` (`RegisterGateway`, lines 133–138 for Connect and lines 69–98 for the gRPC-Gateway). It consists of exactly four interceptors — `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). **None of them does rate limiting**, per-user or otherwise.
- A repo-wide search for `rate`/`limiter`/`throttle`/`golang.org/x/time/rate`/`tollbooth`/`429` across `server/` and `internal/` turns up no rate-limiting implementation. The only literal "rate limit" reference is an aspirational bullet in a doc comment — `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse") — which describes a concern, not implemented middleware.

What the code *does* enforce (easily mistaken for rate limiting, but neither per-user nor request-rate based):

- **Request body size cap**, not request rate: `maxAPIRequestBytes = 256 << 20` (256 MiB) in `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` and `connect.WithReadMaxBytes` (lines 126, 141, 144).
- **Global concurrency limits** via semaphores in `server/router/api/v1/v1.go:59–60`: `thumbnailSemaphore` (3 concurrent thumbnail generations) and `imageProcessingSemaphore` (2 concurrent). These bound in-flight work server-wide, not per user, and cap concurrency rather than request frequency.

So if you need per-user API rate limiting, it would have to be added — it does not currently exist in this codebase.
