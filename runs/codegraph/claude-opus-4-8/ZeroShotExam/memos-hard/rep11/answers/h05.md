**Mechanism: explicit Go code** — when a user is deleted, their emoji reactions are removed by two explicit `DELETE FROM reaction` statements inside the delete-user transaction, not by any database-level cascade rule.

**Evidence:**

1. **The delete orchestration** — `store/db/{postgres,mysql,sqlite}/user_delete.go`, in `deleteUserTargetsTx`, explicitly calls reaction cleanup as part of the transaction (postgres/mysql/sqlite `user_delete.go:96-104`):
   - `deleteReactionsByContentIDsTx(...)` — deletes reactions on the deleted user's memos (by `content_id`)
   - `deleteReactionsByCreatorTx(...)` — deletes reactions the user themselves authored (by `creator_id`)

2. **The two reaction-delete functions** (present identically in all three DB backends):
   - `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` — e.g. `store/db/postgres/user_delete.go:380-388`, `store/db/mysql/user_delete.go:420`, `store/db/sqlite/user_delete.go:383`
   - `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` — e.g. `store/db/postgres/user_delete.go:400-403`, `store/db/mysql/user_delete.go:438`, `store/db/sqlite/user_delete.go:401`

3. **Ruling out a DB-level rule** — the `reaction` table schema has no foreign key or `ON DELETE CASCADE`; `creator_id` and `content_id` are plain `INTEGER`/`TEXT NOT NULL` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. See `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98` (and the mysql equivalent). So the database would not remove reactions on its own — the Go code is what does it.

Both deletes run inside the same transaction opened in `DeleteUser` (`store/db/*/user_delete.go:29-59`), which is committed only after all target rows are removed.
