A browser requests `GET /file/users/:identifier/avatar`. The avatar image is not a separate file — it's stored inline as a data-URI string in the user's `avatar_url` column, so "reaching stored data" means loading the user row from the database and decoding the embedded bytes.

Route registration: `RegisterRoutes` wires `GET /users/:identifier/avatar` → `serveUserAvatar` (`server/router/fileserver/fileserver.go:124`).

Hops from serving handler to data layer:

serveUserAvatar — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
Driver.ListUsers (interface) — store/driver.go:47
DB.ListUsers (SQL `SELECT ... avatar_url ... FROM user`) — store/db/mysql/user.go:84 (and the SQLite/Postgres equivalents in `store/db/sqlite/user.go`, `store/db/postgres/user.go`)

Back in the handler, the loaded `user.AvatarURL` data URI is split into type + bytes by `parseDataURI` and written to the response via `c.Blob` (`server/router/fileserver/fileserver.go:196`, `209`).

Note: `Store.GetUser` reaches the DB through `Store.ListUsers` → `driver.ListUsers` (it does not call a `driver.GetUser`); the per-ID cache path in `GetUser` is skipped here because the lookup is by `Username`, not `ID`.
