**Premise correction: this repository has no per-user API rate-limiting middleware, so there is nothing to register and no request limits to report.**

I traced the entire server middleware/interceptor registration and found no rate limiter of any kind — per-user or otherwise:

- **Echo HTTP middleware** (`server/server.go:51-52`) registers only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`). No rate-limit middleware.
- **Connect/gRPC interceptor chain** (`server/router/api/v1/v1.go:133-138`) is exactly four interceptors: `NewMetadataInterceptor()`, `NewLoggingInterceptor(...)`, `NewRecoveryInterceptor(...)`, and `NewAuthInterceptor(authorizer)` (all defined in `server/router/api/v1/connect_interceptors.go`). None throttle requests.
- **gRPC-Gateway** (`server/router/api/v1/v1.go:95-97`) wires only an auth middleware (`gatewayAuthMiddleware`).

A repo-wide search for `rate.?limit|throttle|limiter|quota|429|too many requests` in Go source turns up no rate-limiting component. The only near-matches are unrelated:

- `internal/email/doc.go:86` — a comment listing "Rate limit email sending to prevent abuse" as a *future consideration*, not implemented code.
- `server/router/api/v1/attachment_service.go:160` — a `ResourceExhausted` "too many image processing requests" error, but that comes from a **concurrency semaphore on image processing**, not a per-user API request-rate limit.
- Various `"too many ..."` errors (e.g. `user_service.go:145`, `memo_service_link_metadata.go:24`) are **batch-size caps** on a single request's payload, not request-rate limits.

So the middleware described in the question does not exist in this codebase.
