**Mechanism: Removed by explicit Go code inside the delete-user transaction — not by a database-level cascade.**

When a user is deleted, `deleteUserTargetsTx` explicitly issues two reaction-deleting statements:

- `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the deleted user *made*.
- `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on* the deleted user's memos (content_ids of the form `memos/<uid>`, gathered via the memo tree).

There is no DB-level rule doing this: the `reaction` table declares `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY` / `ON DELETE CASCADE`.

Evidence locations:
- `store/db/sqlite/user_delete.go:96,102` (calls) and `:380-388`, `:400-403` (the two DELETE statements)
- `store/db/postgres/user_delete.go:96,102` and `:380`, `:400` (same two functions — parity confirmed)
- `store/db/mysql/user_delete.go:96,102` (same call sites)
- Schema (no cascade): `store/migration/sqlite/LATEST.sql:92-99`; also `store/migration/postgres/LATEST.sql:91-97` and `store/migration/mysql/LATEST.sql:91-97`, plus the original `.../0.20/00__reaction.sql` migrations — all define `reaction` with only a `UNIQUE(...)` constraint and no foreign key on `creator_id`.

Note: this runs in the transaction opened in `DeleteUser` (`store/db/sqlite/user_delete.go:29-59`), so the reaction deletes commit atomically with the user-row delete.
