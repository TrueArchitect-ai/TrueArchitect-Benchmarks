**Premise correction: this repository has no per-user API rate-limiting middleware, so there is nothing registered and no request limits to report.**

Evidence:

- The API server's interceptor chain is registered in `server/router/api/v1/v1.go:134-137`, and it contains exactly four interceptors, none of which do rate limiting:
  - `NewMetadataInterceptor()`
  - `NewLoggingInterceptor(logStacktraces)`
  - `NewRecoveryInterceptor(logStacktraces)`
  - `NewAuthInterceptor(authorizer)`

  These are wired into the Connect handler at `server/router/api/v1/v1.go:141` via `connect.WithReadMaxBytes(maxAPIRequestBytes)`. All four interceptor implementations live in `server/router/api/v1/connect_interceptors.go` (metadata, logging, recovery, auth) — there is no rate-limiting/throttling interceptor among them.

- The Echo-level middleware is limited to `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/server.go:51-52`), plus static-file/SPA middleware in `server/router/frontend/frontend.go:54,59`. None of these throttle requests.

- A repo-wide search for `rate limit` / `throttle` / `ratelimit` / rate-limiter libraries (`golang.org/x/time/rate`, `tollbooth`, `limiter`) in non-test Go code turns up only a single comment — an aspirational note in `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"), which is documentation of a possible future email feature, not implemented middleware and not per-user API request limiting.

Two related mechanisms exist but are not rate limiting:
- A request **size** cap (`connect.WithReadMaxBytes(maxAPIRequestBytes)`) at `server/router/api/v1/v1.go:141` — bounds body bytes, not request rate.
- An `internal/scheduler` middleware chain (`internal/scheduler/middleware.go`) — for background-job scheduling, unrelated to HTTP/API request throttling.

So no such middleware is registered, and no per-user request limits are defined.
