**Premise correction:** Neither. The webhook delivery workers do **not** consume from a message broker at all — there is no NATS and no RabbitMQ anywhere in this path. The question's premise (that a broker-backed queue exists) is false.

**Actual mechanism:** Webhook delivery uses an **in-process, in-memory Go channel** with a small pool of goroutine workers — everything lives inside the single application process.

- The "queue" is a buffered Go channel declared as a package-level variable in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  It holds up to 128 pending payloads.

- The "delivery workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over that channel and calling `Post()` to fire the actual outbound HTTP `POST` (`internal/webhook/webhook.go:120`).

- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184`), a non-blocking `select` send that drops the payload with a warning if the channel is full. Callers are the memo webhook dispatchers in `server/router/api/v1/memo_service_webhooks.go` (e.g. `dispatchMemoRelatedWebhook` at line 48, `DispatchMemoCommentCreatedWebhook` at line 30), which loop over the user's registered webhooks and call `webhook.PostAsync(payload)`.

So the whole thing is a bounded channel + goroutine worker pool delivering HTTP POSTs — no external broker, no durable queue, and delivery is best-effort (dropped when the buffer is full, lost on restart).
