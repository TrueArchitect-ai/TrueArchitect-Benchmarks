**Premise correction:** The webhook delivery workers don't consume from *either* NATS or RabbitMQ — the repository uses **no external message broker at all**. There is no queue "declared" in any broker; the premise of a broker-backed delivery pipeline is incorrect.

**Actual mechanism:** Webhook delivery is handled entirely **in-process** via a buffered Go channel plus a fixed pool of goroutine workers, all in `internal/webhook/webhook.go`:

- The "queue" is a package-level buffered channel with capacity 128, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The `init()` function (`internal/webhook/webhook.go:42-55`) spins up **4 worker goroutines**, each ranging over `asyncPostQueue` and calling `Post(payload)` to make the actual HTTP POST to the webhook endpoint.
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto the channel and *drops* the payload (logging a warning) if the buffer is full — there is no persistence, no ack, no external broker.
- `PostAsync` is invoked from the API layer in `server/router/api/v1/memo_service_webhooks.go`.

So delivery is: API handler → `PostAsync` → in-memory buffered channel `asyncPostQueue` → 4 goroutine workers → `Post` (HTTP request via the SSRF-guarded `safeClient`). No NATS, no RabbitMQ, no AMQP/NATS dependency involved.

Sources: `internal/webhook/webhook.go` (lines 39, 42–55, 120, 184–196), `server/router/api/v1/memo_service_webhooks.go`.
