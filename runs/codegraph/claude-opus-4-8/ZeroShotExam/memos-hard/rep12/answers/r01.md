**Premise correction:** This repository does not use Redis anywhere for its cache layer. There is no Redis connection to configure — the codebase (the `usememos/memos` server) has no Redis client, no Redis connection string, and no external cache server. The caching is entirely **in-process, in-memory Go**.

**Actual mechanism:**

- **Cache implementation** — `store/cache/cache.go` defines a thread-safe in-memory cache (`Cache` struct at `store/cache/cache.go:66`) backed by a `sync.Map`, with a background `cleanupLoop` goroutine for TTL expiration and item eviction. No network/Redis is involved.

- **Where it's "configured"** — the store wires up three of these in-memory caches in `store/store.go:38` (`New`). The config is a hardcoded literal (`store/store.go:40-45`):
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  
  The same defaults appear in `cache.DefaultConfig()` at `store/cache/cache.go:57`.

- **TTL applied to user entries** — user records go into `s.userCache` (`store/user.go`, e.g. `Set` calls at lines 98, 132, 143, 167). These calls use `Cache.Set` (`store/cache/cache.go:93`), which applies the cache's `DefaultTTL`. Since the user cache is created with the config above, **user entries expire after 10 minutes** (`store/store.go:41`). There is no per-user custom TTL — `SetWithTTL` is only used internally to route through the default.

Note: the RSS layer in `server/router/rss/rss.go` has a *separate* ad-hoc in-memory cache (a `map[string]*cacheEntry`, `rss.go:35`) with its own `defaultCacheDuration = 1 * time.Hour` (`rss.go:25`) for cached feeds — also not Redis, and unrelated to the user-entry cache.
