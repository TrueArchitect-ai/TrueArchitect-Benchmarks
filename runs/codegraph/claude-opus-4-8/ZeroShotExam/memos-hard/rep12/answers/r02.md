**Premise correction: this repository (Memos) has no per-user API rate-limiting middleware.** There is nothing to register, and therefore no request limits to report.

I verified this by examining every place middleware/interceptors are wired up, and by searching the whole Go codebase for rate-limiting constructs:

- **Connect/gRPC interceptor chain** — `server/router/api/v1/v1.go:133-137` registers exactly four interceptors: `NewMetadataInterceptor()`, `NewLoggingInterceptor()`, `NewRecoveryInterceptor()`, and `NewAuthInterceptor()`. None is a rate limiter. (Defined in `server/router/api/v1/connect_interceptors.go`.)
- **Echo HTTP middleware** — `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware()` (the latter in `server/cors.go`). The frontend router adds only static-file and SPA-fallback middleware (`server/router/frontend/frontend.go:54-59`).
- **Codebase-wide search** — grepping for `rate.?limit`, `ratelimit`, `throttl`, `golang.org/x/time/rate`, `tollbooth`, `limiter` across all `.go` files yields a single hit: a documentation comment in `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse") — an aspirational note in package docs, not an implemented middleware, and about email rather than API requests.

The only request-bound guardrails that do exist are unrelated to per-user rate limiting:
- A global request body-size cap via `connect.WithReadMaxBytes(maxAPIRequestBytes)` at `server/router/api/v1/v1.go:141`.
- A concurrency semaphore limiting simultaneous thumbnail generation in the file server (`server/router/fileserver/fileserver.go:107,116,448`), which throttles concurrency, not per-user request rates.

So there is no per-user API rate-limiting middleware registered anywhere, and no associated request limits.
