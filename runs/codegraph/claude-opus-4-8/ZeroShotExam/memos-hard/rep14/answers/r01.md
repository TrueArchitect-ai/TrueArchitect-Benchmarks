**Premise correction:** There is no Redis anywhere in the cache layer. The repository (Memos) uses a **thread-safe in-process, in-memory Go cache** — a `sync.Map`-backed store with TTL expiration and a background cleanup goroutine. No external cache server, connection string, or Redis client is involved. (The word "cache" also appears in an unrelated browser-side editor draft cache in `web/src/components/MemoEditor/services/cacheService.ts`, which just uses `localStorage`, and in an RSS-feed cache in `server/router/rss/rss.go`, which is a separate ad-hoc map — neither is Redis either.)

**Actual mechanism:**

- **Cache implementation:** `store/cache/cache.go` — `Cache` is a `sync.Map` with per-item `expiration` timestamps (`item` struct, lines 34–39). `New(config)` (line 76) starts a `cleanupLoop` goroutine that periodically evicts expired entries. There is no connection to configure; it's created purely in memory.

- **Where it's "configured"/wired up:** `store/store.go`, `New()` (lines 38–61). The `Store` holds three caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (lines 27–29) — each constructed via `cache.New(cacheConfig)` (lines 51–53). The config is defined inline at lines 40–45:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`

  (This mirrors `cache.DefaultConfig()` at `store/cache/cache.go:57`.)

- **TTL for user entries:** User records are cached in `userCache` keyed by user ID (`store/user.go`: `userCacheKey`, and `s.userCache.Set(...)` in `CreateUser`/`UpdateUser`/`ListUsers`/`GetUser`, lines 98, 132, 143, 167). Those `Set` calls use the default TTL — `Cache.Set` delegates to `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:93–95`). So **user entries expire 10 minutes after they are written** (`DefaultTTL = 10 * time.Minute`, `store/store.go:41`). No code path uses `SetWithTTL` to give users a custom TTL, so 10 minutes applies uniformly. The same 10-minute default applies to the `userSettingCache` entries as well.
