**Mechanism: removed by explicit Go code** (there is no database-level cascade rule).

When a user is deleted, `DeleteUser` runs a transaction that calls `deleteUserTargetsTx`, which issues explicit `DELETE FROM reaction ...` statements covering two cases:

1. **Reactions the user authored** — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`.
2. **Reactions on the deleted user's memos** — `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` over the user's memo tree collected earlier.

This is implemented identically across all three DB backends.

**Evidence locations:**
- `store/db/sqlite/user_delete.go:400-403` (creator reactions), `:380-388` (content_id reactions), invoked from `deleteUserTargetsTx` at `:92` / `DeleteUser` at `:29-59`
- `store/db/mysql/user_delete.go:438` and `:420` (same two deletes)
- `store/db/postgres/user_delete.go:401` and `:383` (same two deletes)
- Entry point: `server/router/api/v1/user_service.go:414` calls `s.Store.DeleteUser`
- **No DB cascade:** the `reaction` table has no foreign keys / `ON DELETE CASCADE` — see `store/migration/sqlite/LATEST.sql:92-99` (and the identical `postgres/LATEST.sql:91-97`, `mysql/LATEST.sql:91-97`); it stores plain `creator_id`/`content_id` columns with only a `UNIQUE` constraint.

So the cleanup depends entirely on the Go code above; nothing in the schema would remove these rows automatically.
