**Premise correction:** Neither. The webhook delivery workers don't consume from NATS or RabbitMQ — there is no external message broker in this system at all. No AMQP/NATS client is imported; `internal/webhook/webhook.go` depends only on the Go standard library plus `uuid`/`errors`.

**Actual mechanism:** Delivery runs entirely in-process over a **buffered Go channel**.

- The "queue" is a package-level buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The workers are **4 goroutines** started in `init()` (`internal/webhook/webhook.go:42-55`), each ranging over `asyncPostQueue` and calling `Post()` for every payload it receives.
- `Post()` (`internal/webhook/webhook.go:120`) simply does an HTTP `POST` of the JSON payload directly to the subscriber's webhook URL via a shared `http.Client` (SSRF-guarded dialer), optionally adding Standard-Webhooks HMAC-SHA256 signature headers.
- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184`), a non-blocking send with a `default` branch that drops (and logs) the delivery if the 128-slot buffer is full.

So the whole pipeline — queue, workers, and dispatch — lives inside a single process; nothing is consumed from a broker.

Registered webhook endpoints themselves are stored in user settings (`WebhooksUserSetting_Webhook` in `proto/gen/store/user_setting.pb.go:910`), not in any messaging system.
