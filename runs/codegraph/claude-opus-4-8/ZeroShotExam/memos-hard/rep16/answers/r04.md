**Premise correction:** The webhook delivery workers don't consume from a message broker at all — neither NATS nor RabbitMQ. The premise that an external broker sits behind webhook delivery is false; there is no broker in this codebase.

**Actual mechanism:** Webhook delivery is handled entirely in-process using a buffered Go channel and a fixed pool of goroutines.

In `internal/webhook/webhook.go`:
- The "queue" is a package-level buffered channel, declared at line 39:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  (a bounded buffer of 128 payloads — not a durable broker queue).
- An `init()` function (lines 42–55) spawns **4 worker goroutines**, each ranging over `asyncPostQueue` and calling `Post(payload)` to make the actual HTTP POST to the webhook endpoint.
- `PostAsync` (lines 184–196) is the enqueue side: it does a non-blocking `select` send onto the channel, and if the buffer is full it **drops** the webhook (logging a warning) rather than blocking.

Producers are in `server/router/api/v1/memo_service_webhooks.go` — `dispatchMemoRelatedWebhook` (line 71) and `DispatchMemoCommentCreatedWebhook` (line 43) call `webhook.PostAsync(payload)` when memos are created/updated/deleted or commented on.

So delivery is an in-memory channel + goroutine worker pool local to the single server process — meaning queued-but-undelivered webhooks are lost on restart, and there is no cross-process or persistent messaging layer.
