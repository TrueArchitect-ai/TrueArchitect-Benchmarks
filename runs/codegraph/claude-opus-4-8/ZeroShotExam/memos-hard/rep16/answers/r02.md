**Premise correction: there is no per-user API rate-limiting middleware in this repository.** The question assumes one exists and asks for its request limits, but no such middleware is registered anywhere.

The API's HTTP/RPC middleware chain is registered in `server/router/api/v1/v1.go` in `RegisterGateway` (lines 65–146), and it contains no rate limiter. The only interceptors/middleware present are:

- **gRPC-Gateway** (`/api/v1/*`, `/file/*`): a single `gatewayAuthMiddleware` doing authentication/access-policy checks (`server/router/api/v1/v1.go:69-98`).
- **Connect** (`/memos.api.v1.*`): a four-interceptor chain — `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (`server/router/api/v1/v1.go:133-138`), all defined in `server/router/api/v1/connect_interceptors.go`. None of these throttle by user or by request rate.

The only limits in this layer are **not** per-user rate limits:

- **Request body size cap:** `maxAPIRequestBytes = 256 << 20` (256 MiB), applied via `http.MaxBytesHandler` and `connect.WithReadMaxBytes` (`server/router/api/v1/v1.go:20, 126, 141, 144`). This bounds bytes per request, not request frequency.
- **Global concurrency semaphores** (not per-user, and not request-rate): `thumbnailSemaphore` = 3 and `imageProcessingSemaphore` = 2 concurrent operations (`server/router/api/v1/v1.go:59-60`).

A repository-wide search for `rate.?limit`/`throttl`/`limiter`/`golang.org/x/time/rate` turned up no rate-limiting implementation or dependency — only an aspirational comment in `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"), which describes email sending, not an API middleware.

So: no per-user rate-limiting middleware is registered, and consequently there are no per-user request limits to report.
