**Premise correction:** There is no Redis in this repository. A repo-wide search for `redis` across all Go source and `go.mod` returns zero matches — the cache layer is **not** backed by Redis (or any external cache server). The premise that "the Redis connection for the cache layer" exists is false, so there is nothing to configure and no separate connection endpoint.

**Actual mechanism:**

The cache is a **thread-safe, in-memory Go cache** (built on `sync.Map`), defined in `store/cache/cache.go`. There is no network connection — it lives inside the running process.

- **Where it's "configured":** in `store/store.go:38-58` (`store.New`). The store builds one `cache.Config` and instantiates three separate in-memory caches from it:
  - `instanceSettingCache`
  - `userCache` — cache for users
  - `userSettingCache` — cache for user settings
  
  Each is created via `cache.New(cacheConfig)` (`store/store.go:51-53`).

- **TTL for user entries:** User entries do **not** get a special TTL. They are written with `Set(...)`, which uses the cache's `DefaultTTL` (`store/cache/cache.go:92-95` → `SetWithTTL`). That default is **10 minutes**, set in two places that agree:
  - `store/store.go:41` (the config passed to `userCache`/`userSettingCache`): `DefaultTTL: 10 * time.Minute`
  - `store/cache/cache.go:57-64` (`DefaultConfig`): same 10-minute default.

  User settings are `Set` in `store/user_setting.go` (e.g., lines 59, 78, 106), all using the default TTL. Cleanup runs every 5 minutes (`CleanupInterval`), with a 1000-item cap.

**Note on the separate RSS cache:** There's an unrelated feed cache in `server/router/rss/rss.go` — a plain `map[string]*cacheEntry` guarded by a mutex, with a `defaultCacheDuration = 1 * time.Hour` (`rss.go:25`). Its `user:<username>` RSS-feed keys (`rss.go:114`) expire after **1 hour** (`getFromCache`, `rss.go:357`). This is HTTP-response caching for RSS feeds, still purely in-memory and unrelated to Redis or to the store's user-record cache.
