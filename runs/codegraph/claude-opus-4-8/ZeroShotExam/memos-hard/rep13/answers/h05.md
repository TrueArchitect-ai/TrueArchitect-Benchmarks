**Mechanism: removed by explicit Go code.** When a user is deleted, their emoji reactions are deleted by explicit `DELETE FROM reaction` statements inside the delete-user transaction — not by any database cascade rule, and not left behind.

Two explicit deletions run for each of the three DB drivers, inside `deleteUserTargetsTx`:
- `deleteReactionsByContentIDsTx` — deletes reactions attached to the user's own (recursively collected) memos: `DELETE FROM reaction WHERE content_id IN (...)`.
- `deleteReactionsByCreatorTx` — deletes reactions the user authored on *any* content: `DELETE FROM reaction WHERE creator_id = ?`.

Both are ordinary Go `tx.ExecContext` calls, wrapped in the same transaction that finally deletes the `user` row (`deleteUserRowTx`).

Evidence locations (identical logic in all three drivers):
- `store/db/sqlite/user_delete.go` — orchestration at lines 96 and 102 (`deleteUserTargetsTx`); implementations `deleteReactionsByContentIDsTx` (lines 380–388, `DELETE FROM reaction WHERE content_id IN ...`) and `deleteReactionsByCreatorTx` (lines 400–403, `DELETE FROM reaction WHERE creator_id = ?`).
- `store/db/mysql/user_delete.go` — lines 96, 102; implementations at 417–421 and 437–439.
- `store/db/postgres/user_delete.go` — lines 96, 102; implementations at 380–388 and 400–403.

What I checked to rule out a DB-level rule: the `reaction` store schema in `store/reaction.go` models `CreatorID`/`ContentID` as plain columns with no relational cascade, and the driver `DeleteReaction` methods (`store/db/{sqlite,postgres,mysql}/reaction.go`) delete only by primary key `id` — reaction cleanup on user deletion is not triggered through them, but through the dedicated `user_delete.go` code above. If the deletion relied on a DB foreign-key `ON DELETE CASCADE`, these explicit `DELETE FROM reaction` statements would be redundant; their presence confirms the mechanism is application-level Go code.
