The image bytes for another user's profile picture are **stored inline in the `user.avatar_url` column** as a data-URI (e.g. `data:image/png;base64,...`), not as a separate file. A browser requests `GET /file/users/:identifier/avatar`, and the handler decodes that column back into image bytes. The hops:

- `RegisterRoutes` (registers `GET /file/users/:identifier/avatar`) — server/router/fileserver/fileserver.go:124
- `serveUserAvatar` (serving handler; resolves user, decodes `user.AvatarURL` via `parseDataURI`, writes `c.Blob`) — server/router/fileserver/fileserver.go:168
- `getUserByUsername` (wraps the store lookup by username) — server/router/fileserver/fileserver.go:715
- `Store.GetUser` (cache check, else delegates to ListUsers) — store/user.go:148
- `Store.ListUsers` (calls the DB driver, populates user cache) — store/user.go:136
- `Driver.ListUsers` (driver interface) — store/driver.go:47
- `DB.ListUsers` (SQL `SELECT ... avatar_url ... FROM user WHERE username = ?`, scans into `user.AvatarURL`) — store/db/sqlite/user.go:88 (and store/db/postgres/user.go:87, store/db/mysql/user.go:84)

The stored data itself is the `avatar_url` column of the `user` table, which `serveUserAvatar` turns back into image bytes with `parseDataURI` (server/router/fileserver/fileserver.go:196).
