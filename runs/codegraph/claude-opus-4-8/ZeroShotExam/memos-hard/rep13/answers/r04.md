**Premise correction:** Neither. This repository (the `memos` project) does not use NATS *or* RabbitMQ — there is no external message broker involved in webhook delivery at all. The premise that webhook workers "consume from a message broker" is false.

**Actual mechanism:** Webhook delivery is handled entirely in-process using a bounded Go channel and a fixed pool of goroutine workers.

- The "queue" is an in-memory buffered channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  It holds up to 128 pending payloads.

- The workers are 4 goroutines spun up in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` (an HTTP POST to the webhook URL) for every payload received.

- Enqueueing happens in `PostAsync()` at `internal/webhook/webhook.go:184-196`, which does a non-blocking `select` send onto the channel and simply **drops** the dispatch (logging a warning) if the queue is full — there is no persistence, retry, or broker-backed acknowledgement.

So the "broker" is process-local: a `chan *WebhookRequestPayload` in `internal/webhook/webhook.go`, consumed by 4 goroutines started in that file's `init()`. If the process restarts or the buffer fills, queued/overflow webhooks are lost — a plain in-memory queue, not NATS or RabbitMQ.
