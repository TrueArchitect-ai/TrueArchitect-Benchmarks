**Premise correction:** There is no Redis anywhere in the cache layer. This project (Memos) uses a **thread-safe in-memory cache** built on `sync.Map` — no external cache server, no network connection, no Redis client. There is nothing to "connect."

**Actual mechanism:**

- **Cache implementation:** `store/cache/cache.go` — `Cache` is an in-process store (`sync.Map` + an atomic item counter) with per-entry expiration and a background cleanup goroutine (`cleanupLoop`/`cleanup`, `store/cache/cache.go:199-250`). It implements the `Interface` defined at `store/cache/cache.go:11`.

- **Where it's "configured":** `store/store.go:38` (`New`). The `Store` holds three separate in-memory caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`) — each created via `cache.New(cacheConfig)` (`store/store.go:51-53`). The config is a literal built inline in `New`:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  (`store/store.go:40-45`; the same defaults are also in `DefaultConfig()` at `store/cache/cache.go:57`.)

- **TTL for user entries:** **10 minutes.** User entries go into `userCache` (and user *settings* into `userSettingCache`) via `Set`, which delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:92-95`) — i.e. the `DefaultTTL: 10 * time.Minute` from the config above. There is no user-specific TTL override; the only place a custom TTL could apply is `SetWithTTL`, which the user/user-setting paths don't call (`store/user_setting.go` uses plain `Set`, e.g. lines 59, 78, 106).

**Note on a red herring:** `server/router/rss/rss.go` has its *own, unrelated* in-memory RSS feed cache (`cacheEntry`, `getFromCache`/`putInCache`) with a separate `defaultCacheDuration = 1 * time.Hour` (`server/router/rss/rss.go:25`). That is the RSS HTTP-response cache, not the store's user cache, and also has nothing to do with Redis.
