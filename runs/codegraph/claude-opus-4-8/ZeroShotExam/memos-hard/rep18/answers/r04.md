**Premise correction:** The webhook delivery workers consume from *neither* NATS nor RabbitMQ. This repository (usememos/memos) has no external message broker in its webhook path at all — there's no broker connection, no queue declaration on any broker server.

**Actual mechanism:** Webhook delivery is entirely in-process, using a buffered Go channel drained by goroutine workers.

- The "queue" is an in-memory buffered channel, declared as a package-level variable in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128; it holds `*WebhookRequestPayload` values.

- The "workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)` (`webhook.go:120`), which does a plain `net/http` POST to the webhook's target URL via `safeClient` (an SSRF-guarded HTTP client, `webhook.go:32-37`).

- Enqueueing happens in `PostAsync` (`internal/webhook/webhook.go:184-196`) via a non-blocking `select`: if the channel is full, the dispatch is *dropped* with a warning log rather than blocked — behavior that only makes sense for an in-memory channel, not a durable broker.

- Producers are the memo dispatch handlers in `server/router/api/v1/memo_service_webhooks.go` (e.g. `dispatchMemoRelatedWebhook:48` and `DispatchMemoCommentCreatedWebhook:30`), which build payloads and call `webhook.PostAsync(...)`.

So delivery is a bounded in-process producer/consumer using a Go channel and 4 goroutine workers — there is no NATS, no RabbitMQ, and no broker-side queue declaration anywhere in the flow.
