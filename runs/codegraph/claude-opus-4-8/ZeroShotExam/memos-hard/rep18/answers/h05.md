**Mechanism: Removed by explicit Go code** (a `DELETE FROM reaction` statement inside the delete-user transaction), *not* by any database-level cascade rule.

When a user is deleted, `DeleteUser` runs `deleteUserTargetsTx`, which explicitly deletes reactions in two ways:
1. `deleteReactionsByCreatorTx` — deletes reactions the user *made* (`DELETE FROM reaction WHERE creator_id = ?`).
2. `deleteReactionsByContentIDsTx` — deletes reactions *on the user's own memos* (`DELETE FROM reaction WHERE content_id IN (...)`), covering the user's memo subtree.

There is no foreign key or `ON DELETE CASCADE` on the `reaction` table, so the database would not remove them automatically — the Go code is the only mechanism.

  - Same structure in `store/db/postgres/user_delete.go:92-127` and `store/db/mysql/user_delete.go:92-127`
- Reaction-delete helper bodies (explicit SQL):
  - `store/db/sqlite/user_delete.go:380` — `deleteReactionsByContentIDsTx` (batched `DELETE FROM reaction WHERE content_id IN ...`)
  - `store/db/sqlite/user_delete.go:400` — `deleteReactionsByCreatorTx` (`DELETE FROM reaction WHERE creator_id = ?`)
- Entry path: `store/user.go:171` (`Store.DeleteUser`) → `store/driver.go:48` → driver `DeleteUser` (`store/db/sqlite/user_delete.go:29`), all within a single transaction (`BeginTx`/`Commit`).
- No DB cascade: `reaction` table has no foreign keys or `ON DELETE` clause — `store/migration/sqlite/LATEST.sql:92`, `store/migration/postgres/LATEST.sql:91`, `store/migration/mysql/LATEST.sql:91` (columns `creator_id`/`content_id` are plain `INTEGER`/`TEXT`, only a `UNIQUE` constraint).

Both reaction cleanups run inside the delete transaction, so they are committed atomically with the user row deletion (`deleteUserRowTx`).
