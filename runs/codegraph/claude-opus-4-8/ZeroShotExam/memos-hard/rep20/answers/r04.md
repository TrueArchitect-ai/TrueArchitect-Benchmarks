**Premise correction:** Neither. The webhook delivery workers do not consume from NATS *or* RabbitMQ — there is no message broker in this codebase at all. Webhook delivery is entirely in-process.

**Actual mechanism:** Delivery runs on an in-memory Go channel with a fixed pool of goroutines, all inside `internal/webhook/webhook.go`:

- The "queue" is a buffered Go channel declared as a package-level variable at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The workers are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` for every payload.
- `PostAsync()` (`internal/webhook/webhook.go:184-196`) enqueues onto that channel with a non-blocking `select`, dropping the payload (with a warning log) if the buffer of 128 is full.
- `Post()` (`internal/webhook/webhook.go:120`) does the actual delivery: a plain HTTP `POST` of the JSON payload to the subscriber's URL via a shared, SSRF-guarded `http.Client`, optionally adding Standard Webhooks HMAC-SHA256 signature headers.

Producers are the memo dispatch methods in `server/router/api/v1/memo_service_webhooks.go` (e.g. `dispatchMemoRelatedWebhook` at line 48), which fetch the user's registered webhooks from the store and call `webhook.PostAsync(payload)` for each.

So the "queue" is a bounded in-process channel (`asyncPostQueue`), not a broker-declared queue.
