A browser hits `GET /file/users/:identifier/avatar`; the handler looks the user up by username through the store → cache/driver → SQL, reads the `avatar_url` column (a data URI), decodes it to bytes, and writes the image. Hops:

- `GET /file/users/:identifier/avatar` route registration — server/router/fileserver/fileserver.go:124
- `FileServerService.serveUserAvatar` (serving handler) — server/router/fileserver/fileserver.go:168
- `FileServerService.getUserByUsername` (builds `store.FindUser{Username}`) — server/router/fileserver/fileserver.go:715
- `Store.GetUser` (checks `userCache`, else delegates) — store/user.go:148
- `Store.ListUsers` (calls `s.driver.ListUsers`) — store/user.go:136
- `Driver.ListUsers` interface hop — store/driver.go (dispatched to the configured DB driver)
- `DB.ListUsers` (SQL `SELECT ... avatar_url ... FROM user WHERE username = ?`, scans into `User.AvatarURL`) — store/db/sqlite/user.go (and equivalents store/db/postgres/user.go, store/db/mysql/user.go:84)
- back in handler: `FileServerService.parseDataURI(user.AvatarURL)` decodes the stored data URI to `imageData`, then `c.Blob(...)` writes it — server/router/fileserver/fileserver.go:196

Stored data is the `user.avatar_url` column, which holds the avatar as a base64 data URI (no filesystem/S3 hop for avatars). The `FindUser{Username}` path has no `ID`, so the `userCache` fast-path is skipped and the query always reaches the DB.
