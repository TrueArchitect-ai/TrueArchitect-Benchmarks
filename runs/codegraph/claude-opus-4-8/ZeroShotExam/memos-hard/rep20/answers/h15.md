Memo visibility (who may view a memo) is enforced at several distinct server surfaces:

Single-memo read access (`checkMemoReadAccess`, gates GetMemo/ListMemoComments/etc.) — server/router/api/v1/memo_service.go:39
Memo list filtering (ListMemos injects a creator/visibility filter based on the current user) — server/router/api/v1/memo_service.go:218
Memo comment surface (CreateMemoComment checks parent-memo visibility; ListMemoComments/GetMemoComment call `checkMemoReadAccess`) — server/router/api/v1/memo_service_comments.go:41
Attachment binary access (blocks fetching a non-public memo's attachment unless viewer is creator/superuser) — server/router/api/v1/memo_attachment_service.go:214
Reaction service (blocks listing/creating reactions on a memo the viewer can't see) — server/router/api/v1/reaction_service.go:30
RSS feed (only PUBLIC memos are included) — server/router/rss/rss.go:90
Frontend SSR/metadata rendering (only PUBLIC memos are fetched) — server/router/frontend/frontend.go:150

The strongest three core enforcement sites are `checkMemoReadAccess` (memo_service.go:39), the ListMemos visibility filter (memo_service.go:218), and the comment enforcement (memo_service_comments.go:41); the attachment, reaction, RSS, and frontend surfaces enforce it independently as well.

Note: the store layer (store/db/mysql/memo.go, store/db/postgres/memo.go) only applies whatever `VisibilityList`/filters are passed in — it does not itself decide who may view, so it isn't an independent enforcement site.
