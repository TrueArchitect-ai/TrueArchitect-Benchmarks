**Premise correction:** There is no Redis connection anywhere in this repository. A search for `redis` across all Go and module files returns zero matches. The cache layer is **not** backed by Redis (or any external cache server) — it is a self-contained, thread-safe **in-process in-memory cache** built on `sync.Map`.

**Actual mechanism:**

- The cache implementation lives in `store/cache/cache.go`. It defines a `Cache` struct backed by a `sync.Map`, with per-entry expiration timestamps, a background `cleanupLoop`, and a `MaxItems` eviction cap — no network client, no connection string, nothing to "configure a connection" to.
- User entries are stored in a dedicated `userCache` field on the `Store` (`store/store.go:28`). It is constructed in `store.New` at `store/store.go:52` via `cache.New(cacheConfig)`, sharing one `cacheConfig` (`store/store.go:40-45`) across the instance-setting, user, and user-setting caches.
- **TTL for user entries: 10 minutes.** User records are written with the default TTL (`s.userCache.Set(...)` in `store/user.go:98,122,132,143,167`, which routes through `Cache.Set → SetWithTTL` using `config.DefaultTTL`). That `DefaultTTL` is set to `10 * time.Minute` in `store/store.go:41` (matching the library default in `cache.DefaultConfig()` at `store/cache/cache.go`). Cleanup runs every 5 minutes and the cache holds at most 1000 items.

So: no Redis — user data is cached in Go process memory with a 10-minute TTL configured in `store/store.go`.

Note: the frontend has a separate, unrelated notion of freshness — TanStack Query's `staleTime` of 5 minutes for `useUser` in `web/src/hooks/useUserQueries.ts:44` — but that is client-side query caching, not the server cache layer.
