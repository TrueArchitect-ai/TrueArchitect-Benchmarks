**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by two explicit `DELETE FROM reaction` statements executed inside the delete-user transaction — not by any DB cascade rule. There are actually two dimensions of removal:

1. **Reactions the user authored** — deleted by `creator_id`.
2. **Reactions on the user's memos** (i.e., reactions others left on content being removed) — deleted by `content_id` for every memo in the user's memo tree.

Both run inside `deleteUserTargetsTx`, before the memos and the user row are deleted, so they don't rely on foreign-key `ON DELETE` behavior.

**Evidence locations** (SQLite driver; MySQL and Postgres are structurally identical):

- `store/db/sqlite/user_delete.go:92-127` — `deleteUserTargetsTx` orchestrates the deletes, calling `deleteReactionsByContentIDsTx` (line 96) and `deleteReactionsByCreatorTx` (line 102).
- `store/db/sqlite/user_delete.go:380-388` — `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` for the deleted user's memos (content IDs built as `"memos/"+uid` in `memoContentIDsFromRefs`, line 512).
- `store/db/sqlite/user_delete.go:400-403` — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`.
- `store/db/mysql/user_delete.go:96,102` and `store/db/postgres/user_delete.go:96,102` — the same two calls appear in the same order in the other two backends (confirmed in the shared source above).

I verified there's no reliance on a DB-level cascade: the memo rows are deleted separately in `deleteMemosTx` (line 451) and the user row in `deleteUserRowTx` (line 461), with reaction cleanup done first by explicit code.
