**Premise correction:** This repository (memos) has no per-user API rate-limiting middleware, so there is nothing registered and there are no request-per-time limits to report. The premise that such middleware exists is incorrect.

What actually exists in the API request-handling chain:

- **Echo-level middleware** — registered in `server/server.go:51-52`: only `middleware.Recover()` and a CORS middleware (`newCORSMiddleware`). No rate limiter.
- **Connect RPC interceptors** — registered in `server/router/api/v1/v1.go:133-138` via `connect.WithInterceptors(...)`. The full chain is exactly four interceptors, all defined in `server/router/api/v1/connect_interceptors.go`:
  1. `MetadataInterceptor` — copies HTTP headers into gRPC metadata
  2. `LoggingInterceptor` — request logging
  3. `RecoveryInterceptor` — panic recovery
  4. `AuthInterceptor` — authentication / access-policy enforcement

None of these throttle or count requests per user.

The only request-side limit present is a **payload size cap**, not a rate limit: `maxAPIRequestBytes` is enforced via `http.MaxBytesHandler` / `connect.WithReadMaxBytes` at `server/router/api/v1/v1.go:126,141,144`.

I also searched the entire Go codebase for `rate.?limit`, `throttl`, `limiter`, `429`, `too many requests`, etc. — the sole hit is an aspirational doc comment in `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"), which describes email-sending guidance, not an implemented API middleware.

So: no per-user API rate limiting exists in this repo, and consequently no configured request limits.
