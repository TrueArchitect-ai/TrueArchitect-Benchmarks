**Mechanism: removed by explicit Go code** (two DELETE statements run inside the user-deletion transaction — not left to a DB cascade rule).

When a user is deleted, `DeleteUser` runs `deleteUserTargetsTx`, which explicitly deletes reactions in two ways:

1. **Reactions *on* the deleted user's memos** — `deleteReactionsByContentIDsTx` issues `DELETE FROM reaction WHERE content_id IN (...)`, where the content IDs are `memos/<uid>` for the user's whole memo subtree.
2. **Reactions *made by* the deleted user** (on anyone's memos) — `deleteReactionsByCreatorTx` issues `DELETE FROM reaction WHERE creator_id = ?`.

Both are called at the top of the delete sequence, before the memo/user rows are removed, all within the same transaction (`tx`).

Evidence locations (SQLite driver, `store/db/sqlite/user_delete.go`):
- `deleteUserTargetsTx` calls both reaction deletes — lines 96 (`deleteReactionsByContentIDsTx`) and 102 (`deleteReactionsByCreatorTx`).
- `deleteReactionsByContentIDsTx` — lines 380–388 (`DELETE FROM reaction WHERE content_id IN ...`).
- `deleteReactionsByCreatorTx` — lines 400–403 (`DELETE FROM reaction WHERE creator_id = ...`).
- Content IDs derived from the memo tree via `memoContentIDsFromRefs` — lines 512–518.

The MySQL and Postgres drivers do the same: `store/db/mysql/user_delete.go` (`deleteReactionsByCreatorTx` at line 437, and the corresponding content-ID delete) and `store/db/postgres/user_delete.go` carry the identical `deleteUserTargetsTx` structure.

So it is not a database-level cascade rule and it is definitely not "not at all" — it is explicit Go code, covering both reactions the user authored and reactions attached to the user's memos.
