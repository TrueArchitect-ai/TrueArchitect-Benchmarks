**Premise correction:** Neither. There is no external message broker — no NATS and no RabbitMQ — involved in webhook delivery anywhere in this repository. The "workers" are plain in-process Go goroutines, and the "queue" is an in-memory buffered channel, not a broker-managed queue.

**Actual mechanism** (all in `internal/webhook/webhook.go`):

- The queue is declared as a package-level buffered Go channel at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  It holds pointers to `WebhookRequestPayload` with a fixed buffer of 128.

- The workers are 4 goroutines spun up in the package `init()` function at `internal/webhook/webhook.go:42-55`. Each loops with `for payload := range asyncPostQueue` and calls `Post(payload)` (line 46), which does an HTTP POST to the webhook's target URL (`Post` at line 120).

- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184-196`), a non-blocking `select` send: if the channel buffer is full, the payload is **dropped** with a warning ("Dropped webhook dispatch because the async queue is full") rather than blocking.

- Callers are the memo dispatch methods in `server/router/api/v1/memo_service_webhooks.go` (e.g. `dispatchMemoRelatedWebhook` at line 71 and `DispatchMemoCommentCreatedWebhook` at line 43), which each call `webhook.PostAsync(payload)`.

So delivery is entirely in-process (bounded channel + goroutine pool) and lives only within a single server instance — there is no broker, no persistence, and no cross-process queue.
