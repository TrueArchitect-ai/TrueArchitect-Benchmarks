**Premise correction:** Neither. There is no external message broker involved in webhook delivery — no NATS, no RabbitMQ/AMQP anywhere in the codebase (`grep -rni "nats|rabbitmq|amqp|streadway"` over the Go sources and `go.mod` returns nothing). There is no "queue declared" in any broker.

**Actual mechanism:** Webhook delivery uses an in-process, in-memory Go channel with a fixed pool of goroutine workers — all inside `internal/webhook/webhook.go`:

- The "queue" is a buffered channel of capacity 128: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`).
- The "workers" are 4 goroutines started in `init()`, each ranging over that channel and calling `Post` for delivery: `for range 4 { go func() { for payload := range asyncPostQueue { ... Post(payload) } }() }` (`internal/webhook/webhook.go:42-55`).
- Producers enqueue via `PostAsync`, a non-blocking send that drops the payload (with a warning log) if the buffer is full: `select { case asyncPostQueue <- requestPayload: default: ... }` (`internal/webhook/webhook.go:184-195`).

So the webhook workers "consume from" a local buffered channel in the same process, not a broker; the queue lives entirely in Go memory and is declared at `internal/webhook/webhook.go:39`. (This is process-local and non-durable — payloads are lost on restart or buffer overflow.)
