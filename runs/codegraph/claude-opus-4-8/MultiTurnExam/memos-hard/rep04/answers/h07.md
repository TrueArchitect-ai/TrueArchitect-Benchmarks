h07.

A browser GET for another user's avatar (`/file/users/{identifier}/avatar`) is served by the **fileserver**, not the gRPC `UserService`. The avatar bytes live inside the user row's `AvatarURL` (a base64 data-URI), so the trace ends at the `SELECT` in the user driver.

Hops:

```
route GET /users/:identifier/avatar → serveUserAvatar — server/router/fileserver/fileserver.go:124 (registration), :168 (handler)
serveUserAvatar → getUserByUsername — server/router/fileserver/fileserver.go:185
getUserByUsername → Store.GetUser(FindUser{Username}) — server/router/fileserver/fileserver.go:715
Store.GetUser → Store.ListUsers — store/user.go:148 → :158
Store.ListUsers → driver.ListUsers (Driver interface) — store/user.go:137 ; store/driver.go:47
driver.ListUsers (concrete SQL SELECT of user incl. avatar_url) — store/db/sqlite/user.go:88 (also store/db/postgres/user.go:87, store/db/mysql/user.go:84)
```

After the store returns the `*store.User`, the handler reads `user.AvatarURL`, decodes the data-URI via `parseDataURI` (`server/router/fileserver/fileserver.go:196`), validates the MIME type, and writes the image with `c.Blob(...)` (`server/router/fileserver/fileserver.go:209`).

Note: `Store.GetUser` only consults the in-memory `userCache` when the lookup is by `ID`; this path looks up by `Username`, so it always falls through to `ListUsers` → the driver SQL query (`store/user.go:149-158`).
