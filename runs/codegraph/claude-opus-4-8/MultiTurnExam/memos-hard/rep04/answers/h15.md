Memo view-visibility is enforced across several server surfaces. Distinct enforcement sites:

- **`checkMemoReadAccess` (single-memo gRPC read gate, used by `GetMemo`)** — `server/router/api/v1/memo_service.go:39` (core check at :54-65: non-`PUBLIC` requires auth; `PRIVATE` requires owner).
- **`ListMemos` visibility filter (gRPC list)** — `server/router/api/v1/memo_service.go:217-226` (anonymous → `PUBLIC` only; authed non-owner → `PUBLIC`+`PROTECTED`; own → all).
- **RSS feed service** — `server/router/rss/rss.go:90` and `:141` (`VisibilityList = [Public]`).
- **Frontend SSR / sitemap service** — `server/router/frontend/frontend.go:150` (`VisibilityList = [Public]`).
- **File server (raw attachment/content serving)** — `server/router/fileserver/fileserver.go:677` and `:699` (gates blob access by the parent memo's visibility + viewer identity).
- **Attachment API `GetAttachmentBlob`** — `server/router/api/v1/attachment_service.go:445-451` (re-checks parent memo visibility before returning bytes).
- **Reaction service** — `server/router/api/v1/reaction_service.go:30-38` and `:83` (list/create reactions gated by memo visibility).
- **Memo comments service** — `server/router/api/v1/memo_service_comments.go:41` (private related-memo restricted to owner/superuser).
- **User stats service** — `server/router/api/v1/user_service_stats.go:84-90` and `:218-220` (visibility-filtered aggregates per viewer).

The first five are the primary "who may view a memo" surfaces (API single-read, API list, RSS, frontend SSR, and file/attachment serving); the remaining ones re-enforce the same memo-visibility rule when exposing memo-derived resources (attachment bytes, reactions, comments, stats). Note the memo-share path (`GetMemoByShare`, `server/router/api/v1/memo_share_service.go:153`) is the deliberate exception that grants view access via a share token/expiry rather than the visibility field.
