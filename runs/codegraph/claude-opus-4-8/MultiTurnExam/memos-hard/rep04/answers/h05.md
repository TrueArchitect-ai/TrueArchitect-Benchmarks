**Mechanism: explicit Go code** (not a database rule). A user's emoji reactions are removed in two ways during `DeleteUser`, both by hand-written SQL inside the delete-user transaction — there is no foreign key / `ON DELETE CASCADE` on the `reaction` table.

Evidence locations:

**Explicit Go deletion** — inside `deleteUserTargetsTx`, each driver runs two reaction deletes (`store/db/sqlite/user_delete.go:96,102`, and identically `store/db/postgres/user_delete.go:96,102` and `store/db/mysql/user_delete.go:96,102`):
- `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — removes reactions *on the deleted user's memos* (by the memos' content IDs).
- `deleteReactionsByCreatorTx(ctx, tx, userID)` — removes reactions *the user authored*. The body is a literal `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`; same at `store/db/postgres/user_delete.go:400` and `store/db/mysql/user_delete.go:437`).

This whole sequence runs in a single transaction opened in `DB.DeleteUser` (`store/db/sqlite/user_delete.go:29-59`), reached via `store.DeleteUser` (`store/user.go:171`) from the API handler `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:414`).

**No database-level rule** — the `reaction` table schema declares `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and **no foreign key**: `store/migration/sqlite/LATEST.sql:92-99` (and `store/migration/sqlite/0.20/00__reaction.sql`). Grepping the migrations for `foreign` / `references` / `on delete` against reaction tables returned nothing, so cascade deletion is not delegated to the database.

Because there's no FK cascade, the explicit `deleteReactionsByCreatorTx` call is what actually removes a deleted user's own reactions.
