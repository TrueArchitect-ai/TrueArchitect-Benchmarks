**Concrete method: `sqlite.DB.CreateMemo` — `store/db/sqlite/memo.go:16`** (it builds and executes `INSERT INTO memo (...) VALUES (...)` at `store/db/sqlite/memo.go:41-49`).

**How I determined which of the three candidates runs** (there are identical-signature `CreateMemo` methods for sqlite, mysql, and postgres):

1. **Default driver value.** The CLI defaults the `driver` setting to `"sqlite"` when no flag is given — `viper.SetDefault("driver", "sqlite")` (`cmd/memos/main.go:122`) and the flag default `rootCmd.PersistentFlags().String("driver", "sqlite", ...)` (`cmd/memos/main.go:130`). This becomes `profile.Driver` (`cmd/memos/main.go:43`; field at `internal/profile/profile.go:30`).
2. **Driver-selection factory.** `NewDBDriver` switches on `profile.Driver`: the `"sqlite"` case calls `sqlite.NewDB(profile)` (`store/db/db.go:18-20`), which returns a `*sqlite.DB` satisfying the `store.Driver` interface (`store/db/sqlite/sqlite.go:24`). So with a default install the interface value held in `Store.driver` is concretely `*sqlite.DB`, not the mysql/postgres structs.
3. **Interface dispatch at save time.** Saving a memo calls `Store.CreateMemo` (`store/memo.go:109`), whose body delegates to `s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`). Because `s.driver` is the sqlite driver from step 2, that dynamic-dispatch call resolves to `sqlite.DB.CreateMemo` (`store/db/sqlite/memo.go:16`).

The mysql (`store/db/mysql/memo.go:16`) and postgres (`store/db/postgres/memo.go:16`) `CreateMemo` implementations are the other candidates; they are ruled out because `NewDBDriver` only instantiates them when `profile.Driver` is `"mysql"` or `"postgres"`, which requires explicitly passing `--driver`.
