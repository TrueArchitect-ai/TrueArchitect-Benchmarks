**Premise correction:** There is no Redis in this project. The cache layer is **not** backed by Redis (or any external cache/network connection) — a repo-wide search for "redis" in Go sources returns nothing. It is a purely in-process, in-memory cache.

**Actual mechanism:** The cache is a homegrown in-memory implementation in `store/cache/cache.go` (package `cache`), storing values in a Go map with per-item expiration (`item.expiration`, store/cache/cache.go:34-38) and a background cleanup goroutine — no connection to configure. It is instantiated per cache in `store.New` via `cache.New(cacheConfig)` (store/store.go:51-53), which creates three separate caches: `instanceSettingCache`, `userCache`, and `userSettingCache` (store/store.go:27-29).

**TTL for user entries:** The `userCache` is built from the shared `cacheConfig` defined in `store.New` at store/store.go:40-45, with `DefaultTTL: 10 * time.Minute` (store/store.go:41). So user entries expire **10 minutes** after being set (with cleanup running every 5 minutes, `MaxItems: 1000`). This matches the package default in `cache.DefaultConfig()` (store/cache/cache.go:56-59), though the store supplies its own explicit config. Writes go through `Store.CreateUser`/`UpdateUser`/`GetUser`/`ListUsers` which call `s.userCache.Set(...)` (store/user.go:98, :132, :143, :167), using the default TTL — none of them override it via `SetWithTTL`.
