**Determination method (why sqlite, not the mysql/postgres candidates):**

There are three candidate implementations of the same `Driver.CreateMemo` method — `store/db/sqlite/memo.go:16`, `store/db/postgres/memo.go:16`, and `store/db/mysql/memo.go:16`. I resolved which one actually runs by tracing the dynamic-dispatch chain back to configuration:

1. The store facade `Store.CreateMemo` (`store/memo.go:109`) delegates through the interface: `return s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`). So the concrete method is whatever implements the `store.Driver` interface.
2. The interface is bound to a concrete type by the factory `NewDBDriver` (`store/db/db.go:14`), which `switch`es on `profile.Driver`: `"sqlite"` → `sqlite.NewDB`, `"mysql"` → `mysql.NewDB`, `"postgres"` → `postgres.NewDB` (`store/db/db.go:18-24`).
3. The default value of `profile.Driver` with no DB flags is `"sqlite"`: set in `cmd/memos/main.go` via `viper.SetDefault("driver", "sqlite")` (`cmd/memos/main.go:122`) and the flag default `String("driver", "sqlite", ...)` (`cmd/memos/main.go:130`). (Corroborated by `internal/profile/profile.go:110`, which special-cases the empty-DSN default for the sqlite driver.)

Therefore, on a default install the factory constructs the SQLite `*DB`, and dynamic dispatch on `s.driver.CreateMemo` lands in `store/db/sqlite/memo.go:16` — the postgres and mysql versions are never instantiated.
