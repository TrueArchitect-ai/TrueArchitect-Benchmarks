**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written SQL `DELETE` statements executed inside the delete-user transaction — not by a database cascade rule, and not left orphaned. In fact reactions are deleted along two axes: reactions the user *authored* (by `creator_id`), and reactions *on the deleted user's content/memos* (by `content_id`).

**Evidence locations** (implemented identically across all three DB drivers):

- SQLite — `store/db/sqlite/user_delete.go`:
  - Orchestration in `deleteUserTargetsTx` calls `deleteReactionsByContentIDsTx` (line 96) and `deleteReactionsByCreatorTx` (line 102).
  - `deleteReactionsByContentIDsTx` (line 380): `DELETE FROM reaction WHERE content_id IN (...)` — the content IDs are the deleted user's memos, built as `"memos/"+memo.UID` in `memoContentIDsFromRefs`.
  - `deleteReactionsByCreatorTx` (line 400): `DELETE FROM reaction WHERE creator_id = ?`.
- Postgres — `store/db/postgres/user_delete.go`: same two calls at lines 96 and 102; implementations at lines 380 and 400.
- MySQL — `store/db/mysql/user_delete.go`: same two calls at lines 96 and 102; implementations at lines 417 and 437.

Supporting checks:
- The whole operation runs in a single transaction (`DeleteUser` in each `user_delete.go`), so reaction deletion is atomic with the user row deletion (`deleteUserRowTx`).
- The `reaction` model and its store methods live in `store/reaction.go` / `store/driver.go:71-74`; the store-level `DeleteReaction` is a separate single-reaction API and is *not* what user-deletion uses — user-deletion uses the dedicated transactional helpers above.
- I did not find any `ON DELETE CASCADE` foreign key wiring reactions to users being relied upon here; the removal is explicit Go/SQL code.
