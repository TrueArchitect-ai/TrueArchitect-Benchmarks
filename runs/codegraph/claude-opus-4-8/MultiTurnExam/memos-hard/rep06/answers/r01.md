**Premise correction:** There is no Redis in this codebase. A repo-wide search for `redis` across all Go files returns zero matches. The cache layer is **not** backed by Redis and there is no Redis connection to configure — it is a purely **in-process, in-memory cache** implemented in `store/cache/cache.go` (a `map`-backed `*cache.Cache` with a background cleanup goroutine, `store/cache/cache.go`).

**Actual mechanism:**
- The caches are constructed in the store constructor `store.New` at `store/store.go:38`, which builds a single `cache.Config` (`store/store.go:40-45`) and passes it to `cache.New(...)` for three separate in-memory caches, including the user cache: `userCache: cache.New(cacheConfig)` at `store/store.go:52`. The field is declared at `store/store.go:28`.
- Configuration is compile-time constants, not connection settings:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  - `OnEviction: nil`
- **TTL for user entries:** user entries are stored via `Store.ListUsers`/`GetUser` calling `userCache.Set(...)` (`store/user.go:143`, `:166`), and `cache.Set` applies the config's `DefaultTTL` (`store/cache/cache.go:94`: `c.SetWithTTL(ctx, key, value, c.config.DefaultTTL)`). So user entries expire **10 minutes** after being cached (and are proactively purged by the 5-minute cleanup sweep once expired). The same 10-minute default also applies to the instance-setting and user-setting caches, since all three share `cacheConfig`.

Note: `store/cache/cache.go` also defines its own `DefaultConfig()` with an identical 10-minute `DefaultTTL` (`store/cache/cache.go:59`), but the store does not use it — it constructs its own `cacheConfig` inline in `store/store.go:40`.
