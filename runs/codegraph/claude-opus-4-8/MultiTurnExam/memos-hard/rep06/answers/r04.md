**Premise correction:** Neither. The webhook delivery workers do not consume from NATS or RabbitMQ — there is no external message broker in this codebase at all. A repo-wide search for `nats`, `rabbitmq`, `amqp`, `rabbit`, and `streadway` across all Go files returns zero matches, and `go.mod` declares no such dependency. So there is no broker-declared queue to point to.

**Actual mechanism:** Webhook delivery uses a purely **in-process Go buffered channel** as its work queue — no network broker, no durability. In `internal/webhook/webhook.go`:

- The "queue" is a package-level buffered channel of capacity 128, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The "workers" are 4 goroutines started once in `init()` (`internal/webhook/webhook.go:42-55`), each ranging over `asyncPostQueue` and calling `Post` to perform the outbound HTTP delivery.
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking send onto the channel and **drops** the payload (logging a warning) if the buffer is full — there is no persistence or redelivery, confirming this is an in-memory channel, not a broker-backed queue.

The RPC handlers that feed this queue (`CreateMemo`/`UpdateMemo`/`DeleteMemo`/`CreateMemoComment`) do so through `dispatchMemoRelatedWebhook` / `DispatchMemoCommentCreatedWebhook` → `webhook.PostAsync` in `server/router/api/v1/memo_service_webhooks.go`.
