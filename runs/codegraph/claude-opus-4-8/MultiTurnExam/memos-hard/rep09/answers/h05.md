**Mechanism: explicit Go code** (not a database rule). Reactions are deleted in two ways during user deletion — those the user *authored* (by `creator_id`) and those *on the user's content/memos* (by `content_id`) — all inside the delete-user transaction. There is no DB-level cascade.

Evidence locations:

- `store/db/sqlite/user_delete.go` — `deleteUserTargetsTx` explicitly calls two reaction-deletion steps:
  - `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` for the user's memos (content IDs built as `"memos/"+uid` in `memoContentIDsFromRefs`).
  - `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` for reactions the user made on others' content.
- The same explicit deletions exist in the other two drivers: `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go` (per the blast-radius listing, `deleteUserMemoRef`/delete helpers are defined in all three driver packages), so behavior is consistent across SQLite/MySQL/Postgres.
- **No database-level rule:** the `reaction` table schema (`store/migration/sqlite/LATEST.sql`, and equivalently `mysql`/`postgres` `LATEST.sql`) declares `creator_id` and `content_id` as plain columns with no `FOREIGN KEY`/`REFERENCES`/`ON DELETE CASCADE`. A grep for `cascade|foreign|references` against the reaction definitions returned nothing, confirming cleanup relies entirely on the Go code above.
