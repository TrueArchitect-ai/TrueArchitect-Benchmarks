**Premise correction:** Neither. The webhook delivery workers do **not** consume from NATS or RabbitMQ — there is no external message broker in this codebase at all. A repo-wide search for `nats`, `rabbitmq`, `amqp`, etc. (in Go sources and `go.mod`) returns nothing. The premise of a broker-backed queue is false.

**Actual mechanism:** Webhook delivery uses an **in-process, buffered Go channel** as the queue, drained by a fixed pool of goroutine workers — all inside `internal/webhook/webhook.go`:

- **Queue declaration:** `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39` (a bounded in-memory channel with capacity 128).
- **Workers:** an `init()` starts 4 goroutines, each looping `for payload := range asyncPostQueue { Post(payload) }` — `internal/webhook/webhook.go:42-45`.
- **Producer:** `PostAsync` non-blockingly enqueues onto the channel (`case asyncPostQueue <- requestPayload:` at `internal/webhook/webhook.go:190`), dropping the delivery with a warning if the buffer is full.

So the "queue" is a single process-local channel; it is not declared on any broker, and delivery state is not durable across restarts.
