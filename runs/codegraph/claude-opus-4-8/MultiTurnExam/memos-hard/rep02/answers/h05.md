**Mechanism: explicit Go code.** A user's emoji reactions are removed by hand-written statements inside the `DeleteUser` transaction — both reactions the user *authored* and reactions *on the user's own memos* — in all three database drivers. It is not left to a database cascade or skipped.

Evidence locations (what I checked):

- **`store/user_service.go` → store layer entry:** `APIV1Service.DeleteUser` (server/router/api/v1/user_service.go:393) calls `s.Store.DeleteUser` (server/router/api/v1/user_service.go:414), which delegates to the driver via `store/user.go:171-172`.

- **The explicit deletes (per driver):** Each driver's `deleteUserTargetsTx` runs two reaction deletions inside the delete-user transaction:
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — removes reactions attached to the deleted user's memos.
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` — removes reactions the user created on anyone's content.

  Found identically at:
  - store/db/mysql/user_delete.go:96 and :102
  - store/db/postgres/user_delete.go:96 and :102
  - store/db/sqlite/user_delete.go:96 and :102

- These run within the `BeginTx`/`Commit` transaction opened in each driver's `DeleteUser` method (e.g. store/db/sqlite/user_delete.go:29-59), alongside explicit deletion of attachments, memo shares, inboxes, identities, settings, relations, and memos — reinforcing that cleanup is driven by explicit Go code, not DB-level cascade rules.

So reactions are deleted by explicit Go statements (`deleteReactionsByCreatorTx` for authored reactions and `deleteReactionsByContentIDsTx` for reactions on the user's memos) in the transactional `DeleteUser` path of every driver.
