**Premise correction:** There is no Redis anywhere in this codebase. A repo-wide search for `redis` in Go source returns zero matches. The cache layer is not backed by Redis (or any external store) and has no connection to configure.

**Actual mechanism:** The cache is a purely in-process, in-memory map with per-entry expiration, implemented in `store/cache/cache.go` (a `Cache` struct guarding a map; `Set` → `SetWithTTL` stamps `expiration: time.Now().Add(ttl)` at store/cache/cache.go:98-112, with a background cleanup goroutine).

- **Configuration site:** `store.New` builds the cache config and instantiates the caches — store/store.go:40-53. The config is:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
  }
  ...
  userCache: cache.New(cacheConfig),
  ```
  (defaults defined at store/cache/cache.go:59). There are three such in-memory caches: `instanceSettingCache`, `userCache`, `userSettingCache`.

- **TTL for user entries:** **10 minutes.** User rows are cached via `s.userCache.Set(ctx, userCacheKey(user.ID), user)` in `CreateUser`/`UpdateUser`/`ListUsers`/`GetUser` (store/user.go:98, :132, :143, :167). `Cache.Set` applies no explicit TTL, so it falls back to `config.DefaultTTL` (store/cache/cache.go:93-94), which is the `10 * time.Minute` set in `store.New`. Entries are swept by the cleanup goroutine on the 5-minute `CleanupInterval`.

So: no Redis; user cache entries live in memory with a 10-minute default TTL configured in store/store.go.
