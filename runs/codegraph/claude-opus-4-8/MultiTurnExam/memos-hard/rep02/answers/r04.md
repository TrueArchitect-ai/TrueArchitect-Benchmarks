**Premise correction: Neither. The webhook delivery workers do not consume from any external message broker — there is no NATS, no RabbitMQ (no `nats`, `amqp`, `rabbitmq`, `kafka` dependency anywhere in the Go source). There is no broker-declared queue.**

**Actual mechanism:** Delivery is handled entirely in-process via a buffered Go channel and a fixed goroutine worker pool, all in `internal/webhook/webhook.go`:

- **Queue declaration:** a package-level buffered channel, `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — internal/webhook/webhook.go:39. That's the whole "queue": an in-memory channel with capacity 128, living inside the server process.
- **Workers:** `init()` starts 4 goroutines that range over the channel — internal/webhook/webhook.go:42-55 (`for payload := range asyncPostQueue { Post(payload) }` at :45-46). Each drained payload is delivered by `Post` (internal/webhook/webhook.go:120) via `safeClient.Do`.
- **Producer:** `PostAsync` enqueues onto the channel with a non-blocking send — internal/webhook/webhook.go:184-195 (`case asyncPostQueue <- requestPayload:` at :190); if the buffer is full it drops the delivery and logs a warning (the `default` branch), rather than blocking or persisting.

So the "workers" are goroutines consuming a bounded in-memory channel, not consumers of NATS/RabbitMQ. Consequently the delivery queue is ephemeral (lost on restart) and there is no external broker or durable queue to point to.
