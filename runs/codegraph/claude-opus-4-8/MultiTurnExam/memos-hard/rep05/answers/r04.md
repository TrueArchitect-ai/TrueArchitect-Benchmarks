**Premise correction:** Neither. The webhook delivery workers do **not** consume from any external message broker — there is no NATS and no RabbitMQ (nor AMQP) anywhere in the codebase. A repo-wide search for `nats`, `rabbitmq`, `amqp`, `streadway` finds zero hits in Go source and no such dependency in `go.mod`. So there is no broker-declared queue.

**Actual mechanism:** Delivery is handled entirely in-process using a **buffered Go channel** plus a fixed pool of worker goroutines, all in `internal/webhook/webhook.go`:
- The "queue" is a package-level buffered channel `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — capacity 128 (`internal/webhook/webhook.go:39`).
- A package `init()` starts **4 worker goroutines** that range over that channel and call `Post` for each payload (`internal/webhook/webhook.go:42-55`).
- Producers enqueue via `PostAsync`, which does a non-blocking send onto the channel and drops the event (with a warning log) if the buffer is full (`internal/webhook/webhook.go:184-196`). Callers are the memo webhook dispatchers in `server/router/api/v1/memo_service_webhooks.go`.
- Each worker's `Post` performs the actual HTTP POST via the SSRF-guarded `safeClient` (`internal/webhook/webhook.go:120`, `:152`).

**Answer:** No message broker exists — the webhook workers consume from an in-memory buffered channel `asyncPostQueue` (size 128) drained by 4 goroutines, declared and started in `internal/webhook/webhook.go:39` (channel) and `:42-55` (`init` worker pool).
