**Explicit Go code.** A user's emoji reactions are removed by hand-written SQL statements executed inside the user-deletion transaction — not by an ON DELETE CASCADE rule, and not left orphaned.

What I checked:
- The user-deletion entry point `store.DeleteUser` delegates to the driver (`store/user.go:171`), reached from the API handler `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:414`).
- Each driver's `DeleteUser` runs everything in one transaction via `deleteUserTargetsTx`. That function explicitly deletes reactions in **two** passes:
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — reactions attached to the user's own memos (by content ID).
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` — reactions the user *authored* on anyone's content (by creator). This is the one that removes "their" reactions.
  - Seen identically in all three backends: `store/db/sqlite/user_delete.go:96,102`, `store/db/mysql/user_delete.go:96,102`, `store/db/postgres/user_delete.go:96,102`.
- Because the Go code deletes reactions explicitly (and ordered before the memo/user rows are removed), removal does not depend on a database FK cascade. The reaction table has no `creator_id` foreign key doing this work — the deletion is driven by application code, which is why a dedicated `deleteReactionsByCreatorTx` exists in each driver.

**Answer:** explicit Go code; evidence — `deleteUserTargetsTx` calls `deleteReactionsByCreatorTx` (user's authored reactions) and `deleteReactionsByContentIDsTx` (reactions on the user's memos) inside the delete transaction: `store/db/sqlite/user_delete.go:92-102`, `store/db/mysql/user_delete.go:92-102`, `store/db/postgres/user_delete.go:92-102`; invoked from `store.DeleteUser` (`store/user.go:171`) via the handler `server/router/api/v1/user_service.go:414`.
