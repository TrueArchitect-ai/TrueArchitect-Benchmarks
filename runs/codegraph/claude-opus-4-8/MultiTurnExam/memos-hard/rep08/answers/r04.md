**Premise correction:** Neither. The webhook delivery workers do not consume from any external message broker — there is no NATS, RabbitMQ, AMQP, or Kafka in this codebase (a repo-wide search of source and `go.mod` for `nats`, `rabbitmq`, `amqp`, `kafka` returns zero hits). There is no external queue to declare.

**Actual mechanism:** Webhook dispatch uses an **in-process, in-memory buffered Go channel** with a small pool of goroutine workers, all inside `internal/webhook/webhook.go`:

- **Queue declaration:** `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a buffered channel holding up to 128 pending payloads (`internal/webhook/webhook.go:39`).
- **Workers:** a package `init()` starts **4 goroutines** that each range over the channel and call `Post` to perform the HTTP delivery (`internal/webhook/webhook.go:42-55`).
- **Producer:** `PostAsync` enqueues onto the channel with a non-blocking `select` — if the buffer is full the payload is dropped with a warning (`internal/webhook/webhook.go:184-196`, send at `:190`). Producers are the memo webhook dispatchers in `server/router/api/v1/memo_service_webhooks.go`.

So delivery is decoupled purely via an in-memory channel within the single server process; the "queue" lives at `internal/webhook/webhook.go:39` and is not backed by any broker. (Consequences: pending webhooks are not durable — they are lost on restart or when the 128-slot buffer overflows.)
