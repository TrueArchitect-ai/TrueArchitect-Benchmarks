**Premise correction:** There is no Redis in this codebase. The cache layer is **not** backed by Redis (or any external cache server) — there is no Redis connection to configure. A repo-wide search finds zero `redis` references in Go code and no Redis dependency in `go.mod`. The premise that "the Redis connection for the cache layer" exists is false.

**Actual mechanism:**

- The cache is a **process-local, in-memory cache** implemented in `store/cache/cache.go` — a "thread-safe in-memory cache with TTL and memory management" backed by a `sync.Map` (`store/cache/cache.go:66-73`) with a background cleanup goroutine. There is no network connection, DSN, or host/port to configure; instances are created in-process via `cache.New(config)` (`store/cache/cache.go:75`).

- Cache "configuration" is just a `cache.Config` struct constructed in code, not from any Redis/connection settings. The `Store` builds one config and instantiates three separate caches from it in `store.New` (`store/store.go:40-53`): `instanceSettingCache`, **`userCache`**, and `userSettingCache`.

- **TTL for user entries:** user records are held in `userCache` (`store/store.go:28`), created with `cacheConfig`, whose `DefaultTTL` is **10 minutes** (`store/store.go:41`). Writes to the user cache go through `s.userCache.Set(...)` (e.g. `store/user.go:98,122,132,143,167`), and `Cache.Set` applies the default TTL (`store/cache/cache.go:93-94`: `SetWithTTL(ctx, key, value, c.config.DefaultTTL)`). So each user entry expires **10 minutes** after it is written. (The same config also sets a 5-minute cleanup interval and a 1000-item cap — `store/store.go:42-43`.)

So: no Redis connection exists to point at; user cache entries live in memory with a 10-minute TTL, configured entirely in Go at `store/store.go:40-52`.
