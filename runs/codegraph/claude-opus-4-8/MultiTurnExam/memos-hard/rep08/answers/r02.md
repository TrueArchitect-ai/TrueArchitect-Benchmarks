**Premise correction:** There is no per-user API rate-limiting middleware in this codebase — so there is no registration site and no request limits to report. The premise is false.

Evidence:

- A repo-wide search for rate-limiting (`ratelimit`, `limiter`, `throttle`, `golang.org/x/time/rate`) finds **no implementation** in Go server code. The only textual hit is an aspirational comment in `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse") — a design note about email, not an implemented API rate limiter. (`golang.org/x/time` appears in `go.mod:151` but only as an **indirect** transitive dependency; it is not used by application code.)

- The complete middleware/interceptor stack contains no rate limiter:
  - Echo HTTP middleware: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/server.go:51-52`), plus static-file and SPA-fallback middleware for the frontend (`server/router/frontend/frontend.go:54,59`).
  - Connect/gRPC interceptors: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (`server/router/api/v1/v1.go:133-137`).
  - gRPC-gateway: a `gatewayAuthMiddleware` (`server/router/api/v1/v1.go:69,97`).

  None of these count requests or enforce a per-user request rate.

The closest *actual* protective limits are of a different kind (not rate/frequency limits):
- **Request body size cap:** `connect.WithReadMaxBytes(maxAPIRequestBytes)` on the Connect handlers (`server/router/api/v1/v1.go:141`).
- **Memo content-length limit:** enforced in `UpdateMemo`/create via `getContentLengthLimit` (`server/router/api/v1/memo_service.go:595-601`).
- **Concurrency caps (not per-user):** semaphores limiting concurrent thumbnail/image processing (`server/router/api/v1/v1.go` — `semaphore.NewWeighted(3)`/`(2)`) and the webhook async queue depth.

So: no per-user API rate-limiting middleware exists, hence no registration location and no configured request limits.
