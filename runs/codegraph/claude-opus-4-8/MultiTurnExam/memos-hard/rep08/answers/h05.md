**Mechanism: explicit Go code.** A user's emoji reactions are removed by explicit `DELETE` statements inside the user-deletion transaction — there is no database-level cascade rule for the `reaction` table.

Evidence locations:

- **The transaction orchestrator runs two explicit reaction deletes.** In every driver's `deleteUserTargetsTx`, reactions are removed by hand: `deleteReactionsByContentIDsTx` (reactions *on* the deleted user's content) and `deleteReactionsByCreatorTx` (reactions *authored by* the deleted user — "their" reactions). See `store/db/sqlite/user_delete.go:96` and `:102`, mirrored in `store/db/postgres/user_delete.go:96,102` and `store/db/mysql/user_delete.go:96,102`.
- **The "their reactions" delete is by `creator_id`.** `deleteReactionsByCreatorTx` executes `DELETE FROM reaction WHERE creator_id = ?` — e.g. `store/db/sqlite/user_delete.go:400-402` (and the postgres/mysql equivalents at `:400`, mysql at `:437`).
- **This all runs in one transaction from `DeleteUser`.** `(*DB).DeleteUser` begins a tx and calls `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:29-59`), reached from `store.DeleteUser` (`store/user.go:171`) and the API handler `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:414`).
- **No DB-level rule exists.** The `reaction` table schema in all three dialects declares only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and *no* foreign key on `creator_id` — so nothing cascades from the `user` row. See `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. (By contrast, the adjacent `memo_share` table *does* have `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, confirming cascades are used elsewhere but deliberately absent on `reaction`.)

So: reactions authored by a deleted user are cleaned up only because `deleteReactionsByCreatorTx` explicitly deletes them; if that Go call were removed, they would be orphaned, since the database enforces no cascade.
