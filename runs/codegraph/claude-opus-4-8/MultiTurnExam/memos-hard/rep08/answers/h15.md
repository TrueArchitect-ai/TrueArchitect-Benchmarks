Memo view-visibility is enforced across these distinct server surfaces:

GetMemo RPC (single-memo read: Public→anyone, Protected→any authenticated user, Private→owner only) — server/router/api/v1/memo_service.go:55-64

ListMemos RPC (list filtering: anonymous→PUBLIC only; authenticated→own memos + PUBLIC/PROTECTED via visibility filter) — server/router/api/v1/memo_service.go:217-227

ListMemoComments RPC (private parent memo → only owner/superuser may list its comments) — server/router/api/v1/memo_service_comments.go:41-42

Attachment/file serving (checkAttachmentPermission gates blob access by the owning memo's visibility, incl. anonymous-public and share-token cases) — server/router/fileserver/fileserver.go:649-701

SSE live-event delivery (SSEHub.canReceive filters push events; Private events go only to owner/admin) — server/router/api/v1/sse_hub.go:135-141 (event visibility populated in server/router/api/v1/sse_event_helpers.go:29-38)

Share-token access (GetMemoByShare / getActiveMemoShare — an alternate grant path: a valid, non-expired share token exposes an otherwise Private/Protected memo, bypassing normal visibility) — server/router/api/v1/memo_share_service.go:153-210

RSS feeds (explore & user feeds list only Public memos) — server/router/rss/rss.go:90 and :141

Sitemap (only Public memos are emitted) — server/router/frontend/frontend.go:149-151

Notes:
- The core read paths (GetMemo, ListMemos) plus the file server's `checkAttachmentPermission` are the three primary enforcement sites; the SSE hub, comment listing, share-token, RSS, and sitemap are additional distinct surfaces that each independently apply visibility rules.
- Enforcement splits into two mechanisms: **explicit permission checks** returning `PermissionDenied`/`NotFound` (GetMemo, comments, fileserver, share) and **query-scoping filters** that never return disallowed memos (ListMemos `VisibilityList`/filter, RSS, sitemap), with SSE doing per-subscriber delivery filtering.
