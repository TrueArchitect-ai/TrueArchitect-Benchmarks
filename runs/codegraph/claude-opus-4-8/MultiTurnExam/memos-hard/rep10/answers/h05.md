**mechanism — explicit Go code (no database-level cascade exists); evidence locations**

The `reaction` table is deleted by explicit Go code inside the user-deletion transaction, not by any DB rule.

What I checked:
- **Go delete path** (`store/db/sqlite/user_delete.go`): `deleteUserTargetsTx` (line 92) invokes two reaction deletes — `deleteReactionsByContentIDsTx` (line 96 → SQL at line 380-388: `DELETE FROM reaction WHERE content_id IN (...)`, covering reactions on the deleted user's memos) and `deleteReactionsByCreatorTx` (line 102 → SQL at line 400-403: `DELETE FROM reaction WHERE creator_id = ?`, covering the user's own reactions). The MySQL and Postgres drivers mirror this (`store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go` — both have the same two `deleteReactions*Tx` functions, per the blast-radius callers).
- **Schema / DB-level rule** (`store/migration/{sqlite,mysql,postgres}/LATEST.sql`, `CREATE TABLE reaction` at line ~91): the `reaction` table has only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and **no foreign key** on `creator_id` (or `content_id`) — hence no `ON DELETE CASCADE`. (The `memo` table's FK to `memo(id)` with cascade at line ~108 is a different table.) So the database would not remove reactions on its own.

Conclusion: reactions are removed by explicit Go code (two `DELETE FROM reaction` statements per driver), because there is no database-level cascade to do it.
