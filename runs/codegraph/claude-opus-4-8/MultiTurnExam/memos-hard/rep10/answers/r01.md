**Premise correction: there is no Redis in this codebase.** The cache layer is not backed by Redis at all — a repo-wide search for `redis`/`Redis` returns zero matches. There is no Redis connection to configure.

**Actual mechanism:** The cache is a thread-safe, process-local in-memory cache implemented with `sync.Map` — `store/cache/cache.go` (`Cache` struct, `New`, `Set`/`Get` on an internal `data sync.Map`, with a background `cleanupLoop` goroutine for TTL expiry). No external store, no network connection.

- **Where it's "configured":** in `store.New` (store/store.go:38-53), which builds a single `cache.Config` and creates three in-memory caches, including the user cache: `userCache: cache.New(cacheConfig)` (store/store.go:52). The config is `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (store/store.go:40-45) — identical to `cache.DefaultConfig()` (store/cache/cache.go:57-64).
- **TTL for user entries:** user entries are written via `s.userCache.Set(...)` (e.g. in `Store.GetUser`/`CreateUser`/`UpdateUser`, store/user.go), and `Cache.Set` applies the default TTL (`SetWithTTL(..., c.config.DefaultTTL)`, store/cache/cache.go:93-94). So **user entries live for 10 minutes** (with lazy expiry on `Get` plus the 5-minute background cleanup sweep). No per-user custom TTL is used.
