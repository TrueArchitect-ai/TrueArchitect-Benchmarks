**Mechanism: explicit Go code** — a deleted user's emoji reactions are removed by an explicit SQL statement issued from Go inside the delete-user transaction, in each of the three DB drivers. (There is no DB-level cascade doing this; the code deletes reactions explicitly.)

What I checked:
- The store-facing entry `Store.DeleteUser` (`store/user.go:171`) delegates to the driver's `DeleteUser`. The API handler `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:393`) calls it but does nothing with reactions itself.
- Each driver's `DeleteUser` runs `deleteUserTargetsTx` in a transaction (`store/db/sqlite/user_delete.go:43`, `store/db/postgres/user_delete.go:43`, `store/db/mysql/user_delete.go:43`).
- Inside `deleteUserTargetsTx`, reactions are deleted by two explicit calls:
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — reactions attached to the user's own memos (line 96 in all three: `store/db/sqlite/user_delete.go:96`, `store/db/postgres/user_delete.go:96`, `store/db/mysql/user_delete.go:96`).
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` — the reactions **the user authored** (their emoji reactions on any memo), at line 102 in all three drivers (`store/db/sqlite/user_delete.go:102`, `store/db/postgres/user_delete.go:102`, `store/db/mysql/user_delete.go:102`).

So the user's emoji reactions are removed by explicit Go code (the `deleteReactionsByCreatorTx` call), not by a database cascade rule and not left in place.

Answer: explicit Go code; `store/db/{sqlite,postgres,mysql}/user_delete.go:102` (`deleteReactionsByCreatorTx`, the user's authored reactions) and `:96` (`deleteReactionsByContentIDsTx`, reactions on the user's memos), both invoked from `deleteUserTargetsTx` (`:92`) within the transactional `DeleteUser` (`:29`), reached via `store/user.go:171`.
