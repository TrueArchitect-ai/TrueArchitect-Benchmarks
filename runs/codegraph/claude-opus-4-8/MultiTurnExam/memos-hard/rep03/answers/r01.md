**Premise correction:** There is no Redis anywhere in this codebase. A repository-wide search for `redis` (case-insensitive, all `.go` files) returns zero matches. The cache layer is a **process-local, in-memory** cache — not backed by Redis or any external store — so there is no "Redis connection" to configure.

**Actual mechanism:**
- The cache is implemented as an in-memory, TTL-based `Cache` (a `sync.Map` with a background cleanup goroutine) — `store/cache/cache.go` (type `Cache` at `store/cache/cache.go:66`, constructor `New` at `:76`).
- It is "configured" not with connection details but with a `cache.Config` created in the store constructor `store.New` — `store/store.go:38`–`:45`: `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`. Three caches are instantiated from this same config, including the user cache: `userCache: cache.New(cacheConfig)` — `store/store.go:52`.
- **TTL for user entries:** user records are written with `s.userCache.Set(...)` (e.g. `store/user.go:98`, `:132`, `:143`, `:167`), and `Cache.Set` applies the config's default TTL (`store/cache/cache.go:93-94`, `Set` → `SetWithTTL(..., c.config.DefaultTTL)`). Since the user cache is built with `DefaultTTL = 10 * time.Minute`, **user entries expire after 10 minutes** (with expired entries reaped by the 5-minute cleanup loop, `store/cache/cache.go:200`). No code path calls `SetWithTTL` with a custom TTL for users, so the 10-minute default is what applies.

Answer: the "Redis connection" premise is incorrect — the cache is an in-process in-memory `cache.Cache` configured in `store/store.go:40-45` (constructed at `store/store.go:52`), and user entries use the default TTL of **10 minutes** (`store/store.go:41`, applied via `store/cache/cache.go:93-94`).
