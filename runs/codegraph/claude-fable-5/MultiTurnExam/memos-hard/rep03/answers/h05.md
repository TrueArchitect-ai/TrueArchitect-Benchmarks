**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside the user-deletion transaction, not by any database-level rule.

Evidence:

1. **Go deletion code**: each database driver's user-delete routine explicitly deletes reactions twice — reactions *on* the user's content (`DELETE FROM reaction WHERE content_id IN ...`) and reactions *made by* the user (`DELETE FROM reaction WHERE creator_id = ?`):
   - `store/db/sqlite/user_delete.go:383` and `store/db/sqlite/user_delete.go:401`
   - `store/db/mysql/user_delete.go:420` and `store/db/mysql/user_delete.go:438`
   - `store/db/postgres/user_delete.go:383` and `store/db/postgres/user_delete.go:401`

2. **No database-level rule**: the `reaction` table schema has no foreign key at all — just a plain `creator_id INTEGER NOT NULL` with a UNIQUE constraint (`store/migration/sqlite/LATEST.sql:92-99`, and equivalents in the mysql/postgres schemas). In fact each schema file contains exactly one foreign key in total, and it's on `memo_id` referencing `memo` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`) — unrelated to reactions or users. So no `ON DELETE CASCADE` could remove reactions; the explicit Go code is what does it.
