**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside each database driver's user-deletion transaction, not by any database-level rule.

What I checked:

1. **The Go deletion code.** Each of the three drivers has a `user_delete.go` that, as part of the `DeleteUser` transaction, runs two explicit deletes: `deleteReactionsByContentIDsTx` (`DELETE FROM reaction WHERE content_id IN (...)` — removes reactions on the deleted user's memos) and `deleteReactionsByCreatorTx` (`DELETE FROM reaction WHERE creator_id = ?` — removes reactions the user made on anyone's content). Locations:
   - `store/db/sqlite/user_delete.go:380-403` (called from lines 96 and 102 of the same file)
   - `store/db/postgres/user_delete.go:383` and `:401`
   - `store/db/mysql/user_delete.go:420` and `:438`

2. **The schemas, to rule out a database-level rule.** The `reaction` table DDL in all three dialects has no foreign key at all — just a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — so no `ON DELETE CASCADE` could apply: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. (The only `ON DELETE CASCADE` foreign keys in the schemas are on other tables, e.g. `memo_organizer`'s `memo_id → memo(id)` around line 108 of each LATEST.sql — none reference the `user` table from `reaction`.)
