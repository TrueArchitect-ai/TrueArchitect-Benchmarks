The browser requests `GET /file/users/{username}/avatar`. That route is registered by `FileServerService.RegisterRoutes` (`server/router/fileserver/fileserver.go:124`), which is wired into the Echo server in `NewServer` (`server/server.go:81-82`). The avatar bytes are not a file on disk — they live in the `user` table's `avatar_url` column as a base64 data URI, which the handler decodes and serves. Hop by hop:

- `serveUserAvatar` (handler; checks anonymous access, looks up the user, decodes the data URI, writes the blob) — `server/router/fileserver/fileserver.go:168`
- `getUserByUsername` (wraps the username into a `store.FindUser`) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks the in-process user cache, else falls through) — `store/user.go:148`
- `Store.ListUsers` (delegates to the active database driver, populates the cache) — `store/user.go:136`
- `driver.ListUsers` via the `store.Driver` interface — `store/driver.go`, implemented per database, e.g. `(*DB).ListUsers` in `store/db/mysql/user.go:84` (equivalents in `store/db/sqlite/user.go` and `store/db/postgres/user.go`), which runs `SELECT ... avatar_url ... FROM user` and scans rows into `store.User.AvatarURL`

Back in the handler, `parseDataURI` splits the stored `data:image/...;base64,...` value into MIME type and raw bytes, the type is checked against `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:75`), and the image is returned with `c.Blob(...)` (`server/router/fileserver/fileserver.go:211`).

Note the access control detail: on an instance that doesn't allow anonymous access, the handler first requires a valid session/token via `getCurrentUser` (`server/router/fileserver/fileserver.go:172-180`), but any authenticated user can fetch any other user's avatar — the lookup is purely by the `:identifier` path parameter.
