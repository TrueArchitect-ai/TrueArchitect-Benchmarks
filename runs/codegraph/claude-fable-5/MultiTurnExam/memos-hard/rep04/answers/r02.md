**Premise correction: there is no per-user API rate-limiting middleware in this codebase.** A repo-wide search for rate-limit/throttle/limiter terms in the Go sources finds nothing but a docs bullet suggesting operators rate-limit email sending (`internal/email/doc.go:86`). The only HTTP middleware registered on the server is panic recovery and CORS — `echoServer.Use(middleware.Recover())` and `echoServer.Use(newCORSMiddleware(profile))` at `server/server.go:51-52` — and there are no gRPC interceptors doing request-rate accounting either.

What the server does have are *capacity/size* guards, not request-rate limits, which may be what the question is thinking of:

- Concurrency semaphores: 3 concurrent thumbnail generations and 2 concurrent image-processing operations in the API service (`server/router/api/v1/v1.go`, `semaphore.NewWeighted(3)` / `NewWeighted(2)`), and a thumbnail semaphore in the file server (`server/router/fileserver/fileserver.go`).
- Memo content length limit checked per request (`getContentLengthLimit` in `server/router/api/v1/memo_service.go:100-107`).
- A bounded async webhook queue (128 entries, 4 workers) that drops excess dispatches (`internal/webhook/webhook.go:39-55`).
- Batch caps like `maxBatchGetUsers` (`server/router/api/v1/user_service.go:144`), and SSE events silently dropped for slow clients (`server/router/api/v1/sse_hub.go:126-129`).

None of these count requests per user per time window; if per-user rate limiting is needed, it would have to be added (or handled by a reverse proxy in front of the server).
