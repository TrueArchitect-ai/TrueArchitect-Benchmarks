The profile-image (avatar) request is `GET /file/users/:identifier/avatar`, served natively over HTTP (not via the gRPC gateway). The chain:

1. `FileServerService.RegisterRoutes` (route registration: `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)`) — `server/router/fileserver/fileserver.go:121-125`, wired into the Echo server from `NewServer` at `server/server.go:81-82`
2. `serveUserAvatar` (handler: enforces auth on private instances via `Profile.AllowAnonymous`, then looks up the target user) — `server/router/fileserver/fileserver.go:168`
3. `getUserByUsername` (wraps the lookup as `store.FindUser{Username: ...}`) — `server/router/fileserver/fileserver.go:715`
4. `Store.GetUser` (cache check by ID, else delegates to list) — `store/user.go:148`
5. `Store.ListUsers` (dispatches through the `store.Driver` interface and populates the user cache) — `store/user.go:136`
6. `DB.ListUsers` (driver implementation; SQL `SELECT` on the `user` table including the `avatar_url` column) — `store/db/sqlite/user.go` (equivalently `store/db/mysql/user.go` / `store/db/postgres/user.go` depending on the configured driver)

Back in the handler, the stored data is materialized for the browser: the avatar lives in the user row's `AvatarURL` field as a base64 data URI, which `serveUserAvatar` decodes via `parseDataURI` (regex at `server/router/fileserver/fileserver.go:100`), validates against `avatarAllowedTypes` (`fileserver.go:76-84`), and returns as an image blob with cache and security headers (`fileserver.go:203-208`). So the "stored data" hop terminates in the `user.avatar_url` column (schema in `store/migration/*/LATEST.sql`), not in the attachment/blob storage used for memo files.
