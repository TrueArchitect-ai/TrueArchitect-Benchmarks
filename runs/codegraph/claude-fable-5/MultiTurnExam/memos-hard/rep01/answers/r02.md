**Premise correction: there is no per-user API rate-limiting middleware in this codebase.** A repo-wide search for rate-limit/throttle/limiter terms in the Go code finds nothing (the only hit is a documentation comment in `internal/email/doc.go:86` *recommending* rate-limiting email sends — advice, not implementation).

What the server actually registers:

- **Echo middleware** (`server/server.go:51-52`): only `middleware.Recover()` and a CORS middleware — no rate limiter.
- **Connect/gRPC interceptors** (`server/router/api/v1/v1.go:133-137`): metadata conversion, logging, panic recovery, and authentication (`NewAuthInterceptor`) — again, no rate limiting.

The closest things to request throttling that do exist are resource-protection bounds, not per-user rate limits:

- Request body size cap `maxAPIRequestBytes` on the Connect handlers (`server/router/api/v1/v1.go:141`).
- Concurrency semaphores: max 3 concurrent thumbnail generations in the file server (`server/router/fileserver/fileserver.go:46,116`) and thumbnail/image-processing semaphores in the API service (`server/router/api/v1/v1.go`, `NewAPIV1Service` — weights 3 and 2).
- A bounded async webhook queue (128 entries, 4 workers) that drops on overflow (`internal/webhook/webhook.go:39-55`).

So if per-user request quotas are required for a deployment, they'd have to be enforced by a reverse proxy in front of memos — the application itself has none.
