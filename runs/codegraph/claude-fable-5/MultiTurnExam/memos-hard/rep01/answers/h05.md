h05.

**Mechanism: explicit Go code — reactions are deleted by hand-written SQL inside each database driver's user-deletion transaction, not by any database-level rule.**

Evidence:

1. **Explicit Go deletion.** Each driver's `DeleteUser` runs a transaction whose `deleteUserTargetsTx` step explicitly deletes reactions two ways: `deleteReactionsByCreatorTx` removes reactions the deleted user authored, and `deleteReactionsByContentIDsTx` removes reactions (by anyone) on the deleted user's memos. This appears identically in all three drivers:
   - SQLite: `store/db/sqlite/user_delete.go:96,102` (call sites) and lines 380/400 (implementations)
   - Postgres: `store/db/postgres/user_delete.go:96,102` and lines 380/400
   - MySQL: `store/db/mysql/user_delete.go:96,102` and lines 417/437

2. **No database-level rule.** The `reaction` table schema has no foreign key at all — just a plain `creator_id` column and a uniqueness constraint, so there's no `ON DELETE CASCADE` that could do this. Checked in all three schemas: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-97`, `store/migration/mysql/LATEST.sql:91-97`.

3. The transaction is invoked from the API layer's `DeleteUser` handler at `server/router/api/v1/user_service.go:414` via `s.Store.DeleteUser`, and there are tests exercising the behavior (e.g., `server/router/api/v1/test/reaction_service_test.go`, whose `TestListMemoReactionsSkipsMissingCreators` covers reaction/creator cleanup interplay).
