**Premise correction: there is no per-user API rate-limiting middleware in this codebase.** Nothing registers one, and no request-per-user limits exist.

What I checked:

- The Echo middleware stack is assembled in `NewServer` (`server/server.go:50-52`) and consists only of `middleware.Recover()` and a CORS middleware (`newCORSMiddleware`). No rate limiter (Echo's `middleware.RateLimiter` or any third-party limiter) is registered there or anywhere else.
- Repo-wide searches for `ratelimit`, `rate limit`, `throttle`, `limiter`, `429`, and `TooManyRequests` in non-test Go code turn up nothing that limits request rates. The only hit even mentioning rate limiting is a documentation comment suggesting it as a good practice for email sending (`internal/email/doc.go:86`) — it is not implemented.

The closest existing mechanisms, which are not per-user rate limits:

- **Concurrency caps** via semaphores in `APIV1Service` — 3 concurrent thumbnail generations and 2 concurrent image-processing operations (`server/router/api/v1/v1.go:58-59`); exceeding the latter returns `ResourceExhausted` ("too many image processing requests", `server/router/api/v1/attachment_service.go:160`).
- **Batch-size caps** on individual RPCs (e.g. max usernames per batch get, `server/router/api/v1/user_service.go:145`; max attachment names per batch delete, `server/router/api/v1/attachment_service.go:355`).

Neither counts requests per user over time, so if per-user API rate limiting is desired, it would have to be added (e.g. as an Echo middleware in `server/server.go` or an interceptor in `server/router/api/v1/v1.go`).
