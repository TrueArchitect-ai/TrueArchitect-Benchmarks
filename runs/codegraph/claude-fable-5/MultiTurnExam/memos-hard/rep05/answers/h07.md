The avatar is stored as a data URI in the user row's `avatar_url` column, so "stored data" here is the `user` table reached through the store's user path. Hop by hop:

- `FileServerService.RegisterRoutes` (registers `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:121` (route at line 124)
- `FileServerService.serveUserAvatar` (serving handler; anonymous-access check, then decodes and returns the image) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` (resolves `:identifier` to a user) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (cache check via `userCache`, else falls through) — `store/user.go:148`
- `Store.ListUsers` (delegates to the driver interface) — `store/user.go:136`
- `(*DB).ListUsers` (driver SQL that reads the `user` row, including `avatar_url`) — `store/db/sqlite/user.go:88` / `store/db/mysql/user.go:84` / `store/db/postgres/user.go:87` (selected at startup via `NewDBDriver`, `store/db/db.go`)
- Back in the handler, `FileServerService.parseDataURI` decodes `user.AvatarURL` (`data:image/...;base64,...`) into MIME type + bytes, which are returned with `c.Blob` after the `avatarAllowedTypes` check — `server/router/fileserver/fileserver.go:196-209`

Note there is no separate blob store for avatars — the image bytes live inline in the user record, so the data layer terminates at the `user` table query.
