**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside each database driver's user-deletion transaction, not by any database-level rule.

Evidence checked:

1. **Go deletion code** — each of the three drivers has a dedicated pair of helpers run inside the `DeleteUser` transaction:
   - `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` (removes the user's own reactions), and `deleteReactionsByContentIDsTx` runs batched `DELETE FROM reaction WHERE content_id IN (...)` (removes reactions left on the user's memos):
     - SQLite: `store/db/sqlite/user_delete.go:380-403` (lines 383 and 401)
     - MySQL: `store/db/mysql/user_delete.go:420` and `:438`
     - Postgres: `store/db/postgres/user_delete.go:383` and `:401`

2. **Schema (ruling out a database-level rule)** — the `reaction` table DDL in the latest schemas has **no foreign key and no `ON DELETE CASCADE`**; `creator_id` and `content_id` are plain columns with only a UNIQUE constraint:
   - `store/migration/sqlite/LATEST.sql` (`CREATE TABLE reaction ...`)
   - `store/migration/postgres/LATEST.sql` (same shape)
   - Introduced in `store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql`, also without constraints.

So without the explicit Go deletes, reactions would be orphaned — there is no cascade at the database level.
