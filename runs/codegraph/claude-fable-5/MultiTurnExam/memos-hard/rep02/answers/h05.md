**Mechanism: explicit Go code — the user-deletion transaction deletes reactions with direct SQL; there is no database-level rule (the schema has no foreign keys / ON DELETE CASCADE on the reaction table).**

Evidence:

1. **Explicit Go deletion, in all three drivers.** Each driver's user-deletion transaction removes reactions two ways — reactions the user made anywhere (`DELETE FROM reaction WHERE creator_id = ?`) and reactions from anyone on the user's own content (`DELETE FROM reaction WHERE content_id IN (...)`):
   - SQLite: `store/db/sqlite/user_delete.go:96,102` (calls), with the SQL in `deleteReactionsByContentIDsTx` at line 380-383 and `deleteReactionsByCreatorTx` at line 400-401.
   - MySQL: `store/db/mysql/user_delete.go:96,102`, functions at lines 417-420 and 437-438.
   - Postgres: `store/db/postgres/user_delete.go:96,102`, functions at lines 380-383 and 400-401.
2. **No database-level rule.** The `reaction` table definitions in the schema files declare `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` as plain columns with no `FOREIGN KEY ... ON DELETE CASCADE` (checked `store/migration/sqlite/LATEST.sql:92-97`, `store/migration/postgres/LATEST.sql:91-96`, and the corresponding `store/migration/mysql/LATEST.sql`), so the database itself would not clean these rows up.
