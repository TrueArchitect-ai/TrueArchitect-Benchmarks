The browser requests `GET /file/users/{identifier}/avatar` (the URL the frontend's `UserAvatar` component puts in `<img src>`, `web/src/components/UserAvatar.tsx`). The route is registered in `FileServerService.RegisterRoutes` (`server/router/fileserver/fileserver.go:124`), and each hop from handler to data is:

- `serveUserAvatar` (serving handler; anonymous-access check, then looks up the user) — `server/router/fileserver/fileserver.go:168`
- `getUserByUsername` (wraps the lookup as `s.Store.GetUser(ctx, &store.FindUser{Username: ...})`) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (cache check, delegates to list) — `store/user.go:148`
- `Store.ListUsers` (calls the selected DB driver via `s.driver.ListUsers`) — `store/user.go:136`
- `DB.ListUsers` (driver SQL query that reads the user row, including `avatar_url`) — `store/db/sqlite/user.go:88` / `store/db/mysql/user.go:84` / `store/db/postgres/user.go:87` (whichever driver is configured)

Back in `serveUserAvatar`, the stored `user.AvatarURL` — a data URI kept in the user row — is decoded by `parseDataURI` (`fileserver.go:196`), type-checked against `avatarAllowedTypes`, and returned as an image blob. So the avatar bytes come from the user table itself, not from the attachment/blob storage path.
