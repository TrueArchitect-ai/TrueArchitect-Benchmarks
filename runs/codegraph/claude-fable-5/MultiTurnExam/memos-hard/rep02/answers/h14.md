**Computation site: `memopayload.RebuildMemoPayload` — `server/runner/memopayload/runner.go:74`; triggers: `CreateMemo` and content updates in `UpdateMemo` (and everything routed through them, e.g. `CreateMemoComment`); extracted: `#tags` plus content properties — has-link, has-task-list, has-code, has-incomplete-tasks, and a title from the first H1.**

Details:

- **Computation site:** `RebuildMemoPayload` (`server/runner/memopayload/runner.go:74`) runs the memo's raw content through `markdown.Service.ExtractAll` (`internal/markdown/markdown.go`) in a single goldmark parse and writes the results into `memo.Payload.Tags` and `memo.Payload.Property`, which are persisted with the memo row.
- **Triggers:**
  - `CreateMemo` — `server/router/api/v1/memo_service.go:108`, right after content-length validation.
  - `UpdateMemo` — `server/router/api/v1/memo_service.go:447`, but only when the update mask includes the `content` path (visibility/pinned changes don't recompute).
  - Indirectly, `CreateMemoComment` (`server/router/api/v1/memo_service_comments.go:56`) — it creates the comment by calling `CreateMemo` internally, so comments get the same treatment.
  - There's also a bulk-rebuild path, `memopayload.Runner.RunOnce` (`server/runner/memopayload/runner.go:27`), which would recompute every memo's payload in batches — but as established earlier, nothing in production code invokes it.
- **What's extracted** (`ExtractedData`, `internal/markdown/markdown.go:21`, stored as `MemoPayload_Property`, `proto/store/memo.proto:16-19` / `proto/gen/store/memo.pb.go:85`):
  - `Tags` — all `#tag` tokens in the content.
  - `Property.HasLink`, `HasTaskList`, `HasCode`, `HasIncompleteTasks` — boolean content flags used for list filtering.
  - `Property.Title` — text of the first H1 heading, if present (used for previews).
  - (`ExtractAll` also returns `Mentions`, but `RebuildMemoPayload` doesn't store those in the payload — mentions are handled separately by the notification flow in `memo_mention_helpers.go`.)
