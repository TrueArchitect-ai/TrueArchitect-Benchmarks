When `Store.DeleteMemo` (`store/memo.go:140-159`) runs, the tables affected are:

- **memo_relation** — explicitly deleted first, for rows where the memo is either `memo_id` or `related_memo_id` (`store/memo.go:142-147`)
- **attachment** — every attachment linked to the memo is deleted via `Store.DeleteAttachment` (`store/memo.go:149-157`, `store/attachment.go:132-148`; this also removes the file from local/S3 storage, which is not a table)
- **memo** — the memo row itself, via the driver's plain `DELETE FROM memo` (`store/memo.go:158`; e.g. `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`)

When invoked through the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go`), comment memos are deleted first by calling `Store.DeleteMemo` for each comment relation (lines 567-577) — this touches the same three tables again for each comment. Notably, `reaction` rows are listed for the deletion webhook payload but are **not** deleted by any explicit cascade code in this path.
