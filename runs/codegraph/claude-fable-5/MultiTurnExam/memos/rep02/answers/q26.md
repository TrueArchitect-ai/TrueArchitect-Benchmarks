Tables affected when DeleteMemo runs:

- **memo_relation** — explicitly deleted (both directions: where the memo is `memo_id` and where it is `related_memo_id`) in `Store.DeleteMemo` (`store/memo.go:142-147`)
- **attachment** — explicitly deleted via `DeleteAttachment` for every attachment linked to the memo (`store/memo.go:148-157`; also removes the stored file/S3 object)
- **memo** — the memo row itself via the driver (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`), plus comment memos: the API handler `APIV1Service.DeleteMemo` first runs `Store.DeleteMemo` for every comment-type relation child (`server/router/api/v1/memo_service.go:568-577`), each of which repeats the cascade above
- **memo_share** — via a database-level `ON DELETE CASCADE` foreign key on `memo_id` (`store/migration/sqlite/LATEST.sql:109`)

Notably, the `reaction` table is *not* cleaned up in this path — the handler lists reactions only to build the webhook payload; there is no explicit reaction delete and no FK cascade on `reaction`.
