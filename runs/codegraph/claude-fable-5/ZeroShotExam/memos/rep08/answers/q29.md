`web/src/connect.ts`; short-lived JWT access tokens + long-lived refresh tokens (plus SHA-256-hashed personal access tokens for API clients); `server/auth`

How it works: the frontend uses Connect-RPC over HTTP, and all service clients are created on a transport whose interceptor list contains `authInterceptor`, defined in `web/src/connect.ts:156`. On each request it fetches the current **access token** (a short-lived JWT kept in memory/local state via `web/src/auth-state.ts`) and sets it as an `Authorization: Bearer` header, proactively refreshing it before expiry. On a 401 (`Code.Unauthenticated`) it calls `AuthService.refreshToken` through a separate interceptor-free transport with `credentials: "include"` — so the long-lived **refresh token** rides in an HTTP-only cookie — then retries the request once (marked with an `X-Retry` header) before redirecting to sign-in on failure.

On the backend, validation lives in the `server/auth` package (`server/auth/token.go`): `ParseAccessTokenV2` verifies the HS256-signed access-token JWT, `ParseRefreshToken` verifies refresh tokens (checked against the database for revocation), and `HashPersonalAccessToken` supports the `memos_pat_`-prefixed personal access tokens managed in `server/router/api/v1/user_service_access_tokens.go`. The API layer wires this in via the `Authenticate` interceptor at `server/router/api/v1/authz.go:44`, which calls into `server/auth`.
