Tables affected when `DeleteMemo` runs:

- **`memo`** — the memo row itself (and rows for any comment memos, deleted first). Driver delete: `store/db/sqlite|mysql|postgres/memo.go` (`DeleteMemo`); comment cleanup in `server/router/api/v1/memo_service.go:567-577`.
- **`memo_relation`** — explicit cascade code deletes relations where the memo is either source or target, in `store/memo.go:140-147` (`Store.DeleteMemo` calls `driver.DeleteMemoRelation` twice).
- **`attachment`** — explicit cascade code lists and deletes attachments linked to the memo, in `store/memo.go:148-157` (via `Store.DeleteAttachment` → `driver.DeleteAttachment`, which also removes the file from local/S3 storage).
- **`memo_share`** — cleaned up by a database-level `ON DELETE CASCADE` foreign key on `memo_id`, not Go code: `store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108` (introduced in `store/migration/*/0.27/04__memo_share.sql`).

Because the comment memos are deleted through the same `Store.DeleteMemo`, each comment's `memo_relation`, `attachment`, and `memo_share` rows are cascaded too.

Notably **not** affected: the `reaction` table. The API handler (`server/router/api/v1/memo_service.go:545-550`) only *lists* reactions to build the webhook payload — no `DeleteReaction` call exists in the delete path, and the `reaction` table has no foreign key to `memo`, so reaction rows for the deleted memo are left orphaned.
