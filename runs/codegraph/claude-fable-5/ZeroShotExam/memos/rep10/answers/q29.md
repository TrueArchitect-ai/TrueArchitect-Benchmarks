**web/src/connect.ts; short-lived JWT access tokens + cookie-based refresh tokens; server/auth**

How it works:

- **Interceptor**: `authInterceptor` in `web/src/connect.ts:156` is a Connect RPC `Interceptor` registered on the transport (`web/src/connect.ts:184-189`) that all service clients (memo, user, auth, etc.) share. It attaches `Authorization: Bearer <token>` to every request via `setAuthorizationHeader` (`web/src/connect.ts:97`).

- **Tokens it manages**:
  - A **short-lived JWT access token** (15-minute lifetime), cached in memory/localStorage by `web/src/auth-state.ts` and refreshed proactively before expiry (`getRequestToken`, `web/src/connect.ts:124`).
  - A **long-lived refresh token** (30 days) held in the HTTP-only cookie `memos_refresh` — the interceptor doesn't read it directly, but sends it via `credentials: "include"` and, on a preflight-expired token or an `Unauthenticated` error, calls `AuthService.refreshToken` over a separate un-intercepted transport (`doRefreshAccessToken`, `web/src/connect.ts:74`), then retries the request once (marked with an `X-Retry` header) or redirects to sign-in on failure.

- **Backend validation**: the `server/auth` package (`server/auth/token.go`) validates them — `ParseAccessTokenV2` checks the access token's HS256 signature, issuer, and `user.access-token` audience; `ParseRefreshToken` validates refresh tokens (plus a database revocation check). It's wired into the API through the server-side `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:208`, which delegates to the shared `Authorizer` (`server/router/api/v1/authz.go`). The same `server/auth` package also handles Personal Access Tokens (`memos_pat_` prefix) for programmatic clients, though the web frontend uses JWTs, not PATs.
