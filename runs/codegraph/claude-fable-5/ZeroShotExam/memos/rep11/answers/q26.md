**Tables affected by explicit code when DeleteMemo runs: `memo`, `memo_relation`, `attachment`.**

The cascade logic lives in `Store.DeleteMemo` (`store/memo.go:140-159`), which the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) calls — once per comment memo and once for the memo itself:

- **`memo_relation`** — deleted twice, for rows where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`), via `driver.DeleteMemoRelation` (`store/memo.go:142-147`; SQL in e.g. `store/db/mysql/memo_relation.go:126`).
- **`attachment`** — each attachment linked to the memo is removed via `Store.DeleteAttachment` (`store/memo.go:149-157` → `store/attachment.go:132`; SQL `DELETE FROM attachment` in `store/db/sqlite/attachment.go:212`). This also deletes the underlying blob storage/local file, but table-wise it's `attachment`.
- **`memo`** — the memo row itself, plus any comment memos: the API handler first lists COMMENT relations pointing at the memo and runs `Store.DeleteMemo` on each comment (`server/router/api/v1/memo_service.go:567-577`), so each comment's `memo` row and its own `memo_relation`/`attachment` rows are cleaned up through the same code path.

Two adjacent tables are worth flagging for completeness:

- **`memo_share`** is affected, but by a database-level foreign key (`FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in `store/migration/sqlite/LATEST.sql:109`, and the postgres/mysql equivalents), not by any Go cascade code. Include it if schema cascades count.
- **`reaction`** is *not* deleted: the handler only lists reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); no deletion of reaction rows occurs anywhere in this path.

So the strict answer to "directly or by explicit cascade code" is: **memo, memo_relation, attachment** (with memo_share cascaded only via the DB schema's foreign key).
