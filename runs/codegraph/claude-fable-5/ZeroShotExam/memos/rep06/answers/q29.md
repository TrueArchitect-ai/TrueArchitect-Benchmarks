Frontend API requests are authenticated by a Connect RPC interceptor defined in **`web/src/connect.ts`** (`authInterceptor`, `web/src/connect.ts:156`). It works like this:

- Before each request it calls `getRequestToken()` to fetch the current **short-lived JWT access token** (15-minute lifetime, kept in client auth state via `web/src/auth-state.ts`) and sets it as an `Authorization: Bearer <token>` header. It proactively refreshes the token if it's expired or near expiry.
- If a request still fails with `Unauthenticated`, it uses the **refresh token** — a long-lived (30-day) JWT stored in the `memos_refresh` cookie, sent via `credentials: "include"` on a separate no-interceptor `refreshTransport` — to call `AuthService.refreshToken`, obtain a new access token, and retry the request once (guarded by an `X-Retry` header). On refresh failure it redirects to sign-in.

On the backend, tokens are validated by the **`server/auth`** package: `server/auth/token.go` defines the JWT claims and `ParseAccessTokenV2`/`ParseRefreshToken`, and `server/auth/authenticator.go` provides `AuthenticateByAccessTokenV2` (stateless signature check), `AuthenticateByRefreshToken` (checked against the database for revocation), and `AuthenticateByPAT` for `memos_pat_`-prefixed personal access tokens. These are invoked from the API interceptors in `server/router/api/v1` (e.g. `authz.go` / `connect_interceptors.go`).

Answer: `web/src/connect.ts` (authInterceptor); JWT access tokens (15 min, Bearer header) + JWT refresh tokens (30 days, `memos_refresh` cookie) — with personal access tokens (`memos_pat_…`) also supported server-side; `server/auth` (`authenticator.go`, `token.go`).
