**Tables affected: `memo`, `memo_relation`, `attachment`**

When the API handler `DeleteMemo` runs (server/router/api/v1/memo_service.go:518), it calls `store.DeleteMemo` (store/memo.go:140) — once per comment memo and once for the memo itself. That store method performs an explicit application-level cascade:

1. **`memo_relation`** — deleted twice via `driver.DeleteMemoRelation`, once where the memo is the source (`MemoID`) and once where it is the target (`RelatedMemoID`) (store/memo.go:141-147).
2. **`attachment`** — every attachment linked to the memo is deleted via `s.DeleteAttachment` (store/memo.go:148-157), which ends in `driver.DeleteAttachment` issuing a `DELETE FROM attachment` (store/attachment.go:132-149; the storage/blob and thumbnail cleanup is filesystem/S3, not a database table).
3. **`memo`** — the memo row itself, via the driver's `DELETE FROM memo` (store/db/sqlite/memo.go:237, store/db/mysql/memo.go:259, store/db/postgres/memo.go:244).

The comment-deletion loop in the API handler (memo_service.go:567-577) hits the same three tables recursively for each comment memo.

Notably, the **`reaction`** table is *not* affected: the handler only lists reactions (memo_service.go:545-550) to build the webhook payload — there is no reaction deletion anywhere in the `DeleteMemo` path.
