Three tables are touched by explicit code when `DeleteMemo` runs; a fourth is cleaned up by a database-level foreign-key cascade:

| Table | How it's affected |
|---|---|
| `memo` | The memo itself, and any comment memos first (the API handler loops over COMMENT relations and calls `Store.DeleteMemo` for each) — `server/router/api/v1/memo_service.go:567-582`; the actual `DELETE FROM memo` is in `store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244` |
| `memo_relation` | Explicit cascade in `store/memo.go:141-147` — `DeleteMemoRelation` is called twice, removing rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`) |
| `attachment` | Explicit cascade in `store/memo.go:148-157` — attachments linked to the memo are listed and each deleted via `Store.DeleteAttachment` (which issues `DELETE FROM attachment`, e.g. `store/db/mysql/attachment.go:230`) |
| `memo_share` | Not deleted by Go code, but cleaned up by the schema's `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` — `store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/0.27/04__memo_share.sql:11` |

Note that `reaction` rows are only *listed* in the handler (to build the webhook payload, `memo_service.go:545-550`) — there is no reaction deletion in this path, and the reaction table has no foreign key to memo (it references memos by a `content_id` string), so reactions are not affected.

**Table list:** `memo`, `memo_relation`, `attachment` (explicit code), plus `memo_share` (DB-level cascade).
