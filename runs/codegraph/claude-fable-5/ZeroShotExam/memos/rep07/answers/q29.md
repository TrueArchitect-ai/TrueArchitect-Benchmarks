**Interceptor path:** `web/src/connect.ts` — the `authInterceptor` (web/src/connect.ts:156) is attached to the Connect-Web transport (web/src/connect.ts:184-189) that all service clients (memo, user, auth, etc.) are built on.

**Token kinds it manages:**
- **JWT access token** — short-lived (15 min), attached to every RPC as an `Authorization: Bearer <token>` header; stored client-side via `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`, `isTokenExpired`).
- **JWT refresh token** — long-lived (30 days), held in the `memos_refresh` HTTP-only cookie and sent automatically because the transport uses `credentials: "include"`. The interceptor uses it to refresh: proactively before requests when the access token is expired (`getRequestToken`), and reactively on a `401 Unauthenticated` by calling `AuthService.refreshToken` over a separate interceptor-free transport, then retrying once (marked with an `X-Retry` header). A `tokenRefreshManager` dedupes concurrent refreshes, redirecting to sign-in if refresh fails.

**Backend package that validates them:** `server/auth` (`server/auth/token.go`) — `ParseAccessTokenV2` and `ParseRefreshToken` validate the HS256-signed JWTs (issuer `memos`, audiences `user.access-token` / `user.refresh-token`), and it also handles Personal Access Tokens (`memos_pat_` prefix, SHA-256 hashed). This package is consumed by the API interceptors in `server/router/api/v1` (e.g. `Authenticate` in `server/router/api/v1/authz.go`, wired through `server/router/api/v1/connect_interceptors.go`).

**Answer:** `web/src/connect.ts`; JWT access tokens (Bearer header) + JWT refresh tokens (`memos_refresh` cookie); `server/auth`.
