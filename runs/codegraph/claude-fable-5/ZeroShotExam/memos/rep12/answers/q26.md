**Tables affected: `memo`, `memo_relation`, `attachment`**

The API handler `DeleteMemo` (server/router/api/v1/memo_service.go:518) first deletes any comment memos (each via `store.DeleteMemo`), then deletes the memo itself. The store-level `Store.DeleteMemo` (store/memo.go:140) performs the explicit cascade:

- **memo_relation** — deleted twice, for rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`) (store/memo.go:142-147; driver `DeleteMemoRelation`).
- **attachment** — each attachment linked to the memo is deleted via `Store.DeleteAttachment` (store/memo.go:149-157 → store/attachment.go:132, `DELETE FROM attachment` in the drivers), which also removes the blob from local/S3 storage (filesystem/object storage, not a DB table).
- **memo** — the memo row itself via the driver's `DeleteMemo` (`DELETE FROM memo` in store/db/sqlite/memo.go, store/db/mysql/memo.go:259, store/db/postgres/memo.go:244). Comment memos are additional rows deleted from this same table.

Two clarifying notes:

- **`memo_share`** is affected too, but by a database-level `ON DELETE CASCADE` foreign key (`FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in store/migration/{sqlite,mysql,postgres}/LATEST.sql:108 and 0.27/04__memo_share.sql), not by explicit Go code. Include it if schema cascades count.
- **`reaction`** is *not* deleted — the handler only lists reactions to build the webhook payload (server/router/api/v1/memo_service.go:545), so reaction rows are left orphaned.
