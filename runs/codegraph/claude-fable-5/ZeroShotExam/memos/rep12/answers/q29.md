**Answer:** `web/src/connect.ts` (the `authInterceptor` at line 156); it manages short-lived JWT **access tokens** (attached as `Authorization: Bearer …`, persisted via `web/src/auth-state.ts` under `memos_access_token` in localStorage) and long-lived **refresh tokens** (sent as the `memos_refresh` HTTP-only cookie via `credentials: "include"`, used by `refreshAccessToken()` to obtain new access tokens on expiry or 401 retry); validation happens in the backend `server/auth` package.

Details:

- **Interceptor** — `web/src/connect.ts:156` defines `authInterceptor`, a Connect RPC `Interceptor` installed on the transport at `web/src/connect.ts:184-189` that all service clients (memo, user, auth, etc.) share. Before each request it calls `getRequestToken()`, which pre-emptively refreshes an expired/near-expiry access token; on an `Unauthenticated` error it refreshes once and retries (marked with an `X-Retry` header), redirecting to sign-in if the refresh fails. A separate `refreshTransport` without the interceptor (`web/src/connect.ts:65`) avoids recursion when calling `AuthService.refreshToken`.
- **Tokens** — access tokens are 15-minute JWTs stored/broadcast across tabs by `web/src/auth-state.ts`; refresh tokens are 30-day JWTs kept in the `memos_refresh` cookie. (A third kind, `memos_pat_…` personal access tokens, exists for programmatic clients but isn't managed by the web interceptor.)
- **Backend validation** — the `server/auth` package (`server/auth/token.go`) defines and validates all three kinds (`ParseAccessTokenV2`, `ParseRefreshToken`, `HashPersonalAccessToken`); it's consumed by the API interceptors in `server/router/api/v1` (e.g. `Authenticate` in `server/router/api/v1/authz.go`, wired through `server/router/api/v1/connect_interceptors.go`).

**Format line:** `web/src/connect.ts`; JWT access tokens + refresh tokens (plus PATs for non-browser clients); `server/auth`
