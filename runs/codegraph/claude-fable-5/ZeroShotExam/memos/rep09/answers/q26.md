**Tables affected: `memo`, `memo_relation`, `attachment`.**

Tracing the flow when the API's `DeleteMemo` (`server/router/api/v1/memo_service.go:518`) runs:

1. **`memo`** — the memo row itself is deleted by the driver's `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`). The API handler also explicitly deletes all comment memos first (rows in the same `memo` table) by listing `COMMENT`-type relations and calling `Store.DeleteMemo` for each (`server/router/api/v1/memo_service.go:567-577`).

2. **`memo_relation`** — `Store.DeleteMemo` (`store/memo.go:140-147`) explicitly cascades by calling `driver.DeleteMemoRelation` twice, removing rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`).

3. **`attachment`** — `Store.DeleteMemo` (`store/memo.go:148-157`) lists attachments linked to the memo and deletes each via `Store.DeleteAttachment`, which executes `DELETE FROM attachment WHERE id = ?` in the drivers (e.g. `store/db/mysql/attachment.go:230`, `store/db/postgres/attachment.go:211`).

Notably **not** affected: the `reaction` table — reactions are listed in the handler only to build the webhook payload (`server/router/api/v1/memo_service.go:545`), and no reaction deletion occurs in the cascade. The attachment cleanup also removes local files, S3 objects, and thumbnail/motion cache files (`store/attachment.go:284-293`), but those are filesystem/object-storage side effects, not database tables.
