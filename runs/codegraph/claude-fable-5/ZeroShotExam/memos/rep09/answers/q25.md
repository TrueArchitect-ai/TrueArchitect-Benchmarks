**Engine:** Google CEL (Common Expression Language), via `github.com/google/cel-go`, wrapped by the repo's own filter engine in `internal/filter/` (`engine.go`, `parser.go`, `ir.go`, `render.go`, `schema.go`, `helpers.go`).

**Mechanism:** `ListMemos` in `server/router/api/v1/memo_service.go:178` validates the filter and passes it in `store.FindMemo.Filters`; each store driver (`store/db/sqlite/memo.go:54`, `store/db/mysql/memo.go:62`, `store/db/postgres/memo.go:51`) calls `filter.DefaultEngine()` and `filter.AppendConditions(...)` with its dialect constant. `Engine.Compile` (`internal/filter/engine.go:48`) uses a `cel.Env` built from the schema to compile the expression into a CEL AST, which `buildCondition` (`internal/filter/parser.go:18`) lowers into a dialect-agnostic `Condition` IR tree (`internal/filter/ir.go`); the renderer (`internal/filter/render.go`) then walks that tree with `RenderOptions{Dialect: DialectSQLite | DialectMySQL | DialectPostgres}` to emit a dialect-specific parameterized SQL fragment plus args (`Statement`), which the driver appends to its WHERE clause.

In one sentence: the CEL text is compiled by cel-go, translated to an internal condition IR, and rendered per-dialect (column quoting, JSON extraction, placeholders, date-part functions) by `internal/filter/render.go` — the SQL is never built directly from the CEL AST.
