**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements executed inside the user-deletion transaction in each database driver. There is no database-level rule doing it — the `reaction` table has no foreign key at all, so no `ON DELETE CASCADE` could apply.

What I checked:

1. **The deletion flow.** `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:393`) calls `Store.DeleteUser` (`store/user.go:171`), which dispatches to a driver-specific `DeleteUser` that collects targets and runs `deleteUserTargetsTx` in a single transaction (`store/db/sqlite/user_delete.go:29`, and the parallel implementations in `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go`).

2. **Explicit reaction deletes in Go.** Each driver deletes reactions two ways inside that transaction:
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (reactions the user made): `store/db/sqlite/user_delete.go:401`, `store/db/mysql/user_delete.go:438`, `store/db/postgres/user_delete.go:401`.
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (reactions on the user's memos, batched): `store/db/sqlite/user_delete.go:383`, `store/db/mysql/user_delete.go:420`, `store/db/postgres/user_delete.go:383`.

3. **No database-level rule.** The `reaction` table DDL in all three schemas defines only a primary key and a UNIQUE constraint — no foreign keys, so no cascade is possible: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`.

There is also test coverage exercising this path (e.g. `TestDeleteUserCleansRelatedData` and reaction-related tests in `server/router/api/v1/test/reaction_service_test.go`, per the call graph).
