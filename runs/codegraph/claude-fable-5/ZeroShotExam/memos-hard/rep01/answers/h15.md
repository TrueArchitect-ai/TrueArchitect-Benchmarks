Memo visibility is enforced independently on several server surfaces (this is the usememos/memos codebase):

gRPC/API v1 memo reads — `checkMemoReadAccess` gates `GetMemo` (and its parent memo), and `ListMemos` injects visibility filters (anonymous → PUBLIC only; non-creator → PUBLIC/PROTECTED) — server/router/api/v1/memo_service.go (checkMemoReadAccess at server/router/api/v1/memo_service.go:39, applied at lines 218–227, 356, 367; also reused for comment listing at server/router/api/v1/memo_service_comments.go:148)

Attachment/file-serving HTTP endpoint — before streaming a memo's attachment bytes, the file server re-checks the owning memo's visibility (public + anonymous allowed, share-token fallback, otherwise authenticated user must be creator/admin for PRIVATE) — server/router/fileserver/fileserver.go (check around server/router/fileserver/fileserver.go:677–702)

SSE real-time event stream — `SSEClient.canReceive` drops events for PRIVATE memos unless the subscriber is the creator or an admin, so live updates don't leak — server/router/api/v1/sse_hub.go (server/router/api/v1/sse_hub.go:134–145)

RSS feed — feed queries are hard-restricted to `VisibilityList: []store.Visibility{store.Public}` — server/router/rss/rss.go (lines 90 and 141)

Frontend/sitemap surface — the sitemap (and public memo listing) only queries PUBLIC memos — server/router/frontend/frontend.go (server/router/frontend/frontend.go:150)

Additional API-side sites that enforce the same rule for adjacent RPCs (same gRPC surface, distinct code paths): reaction listing/creation checks PRIVATE-memo access at server/router/api/v1/reaction_service.go:38 and :83; attachment-to-memo binding checks at server/router/api/v1/attachment_service.go:451 and server/router/api/v1/memo_attachment_service.go:222; user memo stats restrict visibility at server/router/api/v1/user_service_stats.go:84–90 and 218–220; mention notifications suppress private memos at server/router/api/v1/memo_mention_helpers.go:62–67 and server/notification/email.go:313.

The three clearly distinct surfaces the question is after are the API v1 service (`checkMemoReadAccess` in memo_service.go), the file server (fileserver.go), and the RSS feed (rss.go) — with the SSE hub and frontend sitemap as further independent enforcement points.
