**Premise correction:** This repository (Memos) has no Redis at all — a case-insensitive search across Go, TypeScript, config, and docs files finds zero references to Redis, and there is no Redis client dependency or connection configuration anywhere. So there is no "Redis connection for the cache layer" to point to.

**Actual mechanism:** The cache layer that does exist is an in-process, in-memory map inside the RSS feed service, defined in `server/router/rss/rss.go`:

- The `RSSService` struct holds `cache map[string]*cacheEntry` guarded by a `sync.RWMutex` (`server/router/rss/rss.go:42-50`), initialized in `NewRSSService` (`server/router/rss/rss.go:58-65`). No external store is involved.
- Per-user feed entries are cached under the key `"user:" + username` in `GetUserRSS` (`server/router/rss/rss.go:114`), alongside a single `"explore"` key for the public feed.
- The TTL for these entries — user and explore alike — is **1 hour**, set by `defaultCacheDuration = 1 * time.Hour` (`server/router/rss/rss.go:25`). Expiry is enforced lazily in `getFromCache` (`server/router/rss/rss.go:357`), which deletes an entry when `time.Since(entry.createdAt)` exceeds that duration. The same 1-hour value is also echoed to clients as `Cache-Control: public, max-age=3600` in `setRSSHeaders` (`server/router/rss/rss.go:405`).
- The cache is additionally bounded to 50 entries (`maxCacheSize`, `server/router/rss/rss.go:26`) with a simple evict-oldest policy in `putInCache` (`server/router/rss/rss.go:378-390`).

So: no Redis configuration exists; user cache entries live in a mutex-protected Go map with a 1-hour lazy-expiration TTL.
