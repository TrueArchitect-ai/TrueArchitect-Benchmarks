A browser requesting another user's avatar hits the native HTTP file-serving route, which loads that user's row from the store; the image bytes themselves live inline in the user record as a data URI (`AvatarURL`), so "stored data" is the users table column — decoded and streamed back as a blob. Trace, top to bottom:

GET /file/users/:identifier/avatar → serveUserAvatar — server/router/fileserver/fileserver.go:124 (route registered in RegisterRoutes)
serveUserAvatar — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
Driver.ListUsers (interface) — store/driver.go:10
ListUsers (driver impl, per backend) — store/db/sqlite/user.go, store/db/postgres/user.go, store/db/mysql/user.go:84 (SQL SELECT against the `user` table)

Back in the handler, the returned `user.AvatarURL` (a `data:` URI holding the image) is decoded by `parseDataURI` (server/router/fileserver/fileserver.go:196) and written to the response via `c.Blob` (line 209). No separate attachment/blob storage is involved for avatars — the image data is stored directly in the user row's `avatar_url` column.
