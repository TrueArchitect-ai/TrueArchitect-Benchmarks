**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE` statements executed inside the user-deletion transaction in each database driver — not by any database-level rule. The `reaction` table has no foreign key or `ON DELETE CASCADE` at all, so the schema could not do it.

What I checked:

1. **The user-deletion path in Go.** The API handler `DeleteUser` in `server/router/api/v1/user_service.go:393` calls `Store.DeleteUser` (`store/user.go:171`), which dispatches to the driver. Each driver's `DeleteUser` runs `deleteUserTargetsTx`, which explicitly deletes reactions twice — once for reactions *on* the user's memos and once for reactions *made by* the user:
   - `store/db/sqlite/user_delete.go:96` (`deleteReactionsByContentIDsTx`) and `:102` (`deleteReactionsByCreatorTx`)
   - `store/db/mysql/user_delete.go:96` and `:102`
   - `store/db/postgres/user_delete.go:96` and `:102`

2. **The actual SQL.** For example, `deleteReactionsByCreatorTx` at `store/db/sqlite/user_delete.go:400-403` runs `DELETE FROM reaction WHERE creator_id = ?` inside the same transaction as the user-row delete.

3. **The schema, to rule out a database-level rule.** The `reaction` table definitions contain no foreign key constraints and no cascade rules — just plain columns and a unique constraint:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - Original migrations, e.g. `store/migration/sqlite/0.20/00__reaction.sql` and `store/migration/postgres/0.20/00__reaction.sql`, likewise define `creator_id INTEGER NOT NULL` with no `REFERENCES ... ON DELETE CASCADE`.

So the cleanup happens entirely in application code (per-driver Go SQL inside the delete transaction); the database itself enforces nothing.
