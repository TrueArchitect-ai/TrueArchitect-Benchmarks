**Mechanism: explicit Go code** — deleted inside the user-delete transaction, not by any database rule.

**Evidence:**

1. **Go deletion code.** Each database driver's `DeleteUser` runs `deleteUserTargetsTx`, which explicitly calls two reaction cleanups:
   - `deleteReactionsByCreatorTx` — removes reactions the deleted user made: `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400`, and the calls at `store/db/sqlite/user_delete.go:102`, `store/db/mysql/user_delete.go:102` (definition at line 437), `store/db/postgres/user_delete.go:102` (definition at line 400)).
   - `deleteReactionsByContentIDsTx` — removes reactions on the user's own memos (by content ID): `store/db/sqlite/user_delete.go:96` and `:380`, with mirror implementations in the mysql (`:417`) and postgres (`:380`) drivers.
   These run inside a single transaction begun in each driver's `DeleteUser` (`store/db/{sqlite,mysql,postgres}/user_delete.go:29-59`), which `store/user.go:171` (`Store.DeleteUser`) dispatches to.

2. **No database-level rule.** The `reaction` table schema has no foreign key at all — `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint, so there is no `ON DELETE CASCADE` possible (`store/migration/sqlite/LATEST.sql:92-99`; the mysql and postgres `LATEST.sql` and the `0.20/00__reaction.sql` / `0.23/00__reactions.sql` migrations define the table the same way, without FKs).

So reactions are removed by the explicit `DELETE` statements in the Go store drivers; the schema itself would leave them orphaned.
