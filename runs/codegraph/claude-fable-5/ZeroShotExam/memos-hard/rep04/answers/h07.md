The browser hits `GET /file/users/:identifier/avatar`. Unlike attachments (which live in a separate blob store), a user's avatar is stored **inline** as a base64 data URI in the `user` table's `avatar_url` column, so the data layer here is the user row itself. The handler reads it, decodes the data URI, and serves the bytes.

`serveUserAvatar` (`/file/users/:identifier/avatar`) — server/router/fileserver/fileserver.go:168 (route registered at fileserver.go:124)
`(*FileServerService).getUserByUsername` — server/router/fileserver/fileserver.go:715
`(*Store).GetUser` — store/user.go:148
`(*Store).ListUsers` — store/user.go:136
`(*DB).ListUsers` (driver, e.g. SQLite; also postgres/mysql) — store/db/sqlite/user.go (SQL `SELECT ... avatar_url ... FROM user`; MySQL equivalent at store/db/mysql/user.go:84)

The row's `AvatarURL` (store/user.go:43) is then decoded back in the handler by `(*FileServerService).parseDataURI` and written out via `c.Blob` (fileserver.go:196–209).

Note: the returned `AvatarURL` is a base64 data URI (`data:image/...;base64,...`); `parseDataURI` splits the MIME type and decodes the base64 payload into the image bytes that are served. The gRPC `UserService` never serves the image bytes — `convertUserFromStore` (server/router/api/v1/user_service_converters.go:16) merely rewrites the API `avatar_url` field to the `/file/{name}/avatar` URL that the browser then requests through the path above.
