**Mechanism: explicit Go code (application-level SQL in the user-delete transaction), not a database-level rule.**

When a user is deleted, each database driver's `DeleteUser` runs a transaction whose `deleteUserTargetsTx` explicitly deletes reactions in two ways:

1. `deleteReactionsByCreatorTx` — removes reactions **the user made**: `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`, called at `store/db/sqlite/user_delete.go:102`; identical calls in `store/db/mysql/user_delete.go:102` and `store/db/postgres/user_delete.go:102`).
2. `deleteReactionsByContentIDsTx` — removes reactions **on the user's memos** (by the memos' content IDs): `DELETE FROM reaction WHERE content_id IN (...)` (`store/db/sqlite/user_delete.go:380-388`, called at line 96 in all three drivers).

The transaction is invoked from `Store.DeleteUser` (`store/user.go:171`), which is called by the API handler `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:414`).

**Ruling out a database-level rule:** the `reaction` table schema has no foreign keys at all — only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — so there is no `ON DELETE CASCADE` to do this work. Checked `store/migration/sqlite/LATEST.sql:92-99`, plus `store/migration/postgres/LATEST.sql:91` and `store/migration/mysql/LATEST.sql:91` (same shape), and the original `store/migration/*/0.20/00__reaction.sql` migrations.

There is also test coverage exercising this path (e.g. `TestDeleteUserCleansRelatedData` and `TestListMemoReactionsSkipsMissingCreators` in `server/router/api/v1/test/`).
