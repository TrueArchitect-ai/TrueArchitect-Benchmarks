Memo visibility is enforced independently on four server surfaces (plus several parallel checks within the gRPC API):

- gRPC API v1 — single-memo read check `checkMemoReadAccess` (Public/Protected/Private + creator/auth rules) and the `VisibilityList`/filter narrowing in `ListMemos` — `server/router/api/v1/memo_service.go` (checkMemoReadAccess at line 39, list filtering at lines 218–226)
- File server (HTTP attachment/blob serving) — `checkAttachmentPermission` re-derives access from the owning memo's visibility, with share-token and anonymous-instance fallbacks — `server/router/fileserver/fileserver.go` (lines 650–702)
- RSS feeds — both the site feed and per-user feed query with `VisibilityList: []store.Visibility{store.Public}` so only public memos are ever published — `server/router/rss/rss.go` (lines 90 and 141)
- Frontend router (sitemap.xml) — `getSitemapXML` lists only `store.Public` memos when generating sitemap URLs — `server/router/frontend/frontend.go` (line 150)

Within the gRPC API surface, the same visibility rule is also re-enforced at additional distinct call sites, if you count them separately: `server/router/api/v1/reaction_service.go` (lines 30–38, 83, for listing/adding reactions), `server/router/api/v1/attachment_service.go` (lines 445–451) and `server/router/api/v1/memo_attachment_service.go` (lines 214–222) for attachment metadata, `server/router/api/v1/memo_service_comments.go` (line 41, commenting on a memo), and `server/router/api/v1/user_service_stats.go` (lines 84–90, 218–220, user stats aggregation).
