**Yes — but only in a unit test inside the mysql package itself; no production code ever constructs it outside the factory.**

Evidence:

1. **The factory** is `NewDBDriver` in `store/db/db.go:14-27`, which switches on `profile.Driver` and calls `mysql.NewDB(profile)` for the `"mysql"` case (`store/db/db.go:22`). The package-level constructor `NewDB` lives at `store/db/mysql/mysql.go:20` and internally builds the `&DB{...}` value.

2. **Only one direct construction exists outside that path**: `store/db/mysql/auth_config_test.go:12` does `db := &DB{}` (a zero-value struct literal) to unit-test `IsRetryableAuthenticationMutationError` against `go-sql-driver/mysql` error codes. Since `DB` is unexported... rather, since the struct is only accessible within the package, this in-package test literal is the sole direct instantiation. (The postgres package has analogous test-only constructions, e.g. `store/db/postgres/auth_config_test.go:12`.)

3. **No other code can construct it**: a repo-wide grep shows the only file importing `github.com/usememos/memos/store/db/mysql` is the factory itself, `store/db/db.go:8`. The integration-test harness also goes through the factory — `store/test/store.go:28` and `store/test/store.go:50` call `db.NewDBDriver(profile)`; `store/test/containers.go` uses the testcontainers `mysql` module and raw `sql.Open("mysql", dsn)` for container setup, not the driver type.

So in production code the MySQL driver is reachable only via `NewDBDriver` → `mysql.NewDB`; the single direct construction is the zero-value `&DB{}` in the driver's own unit test.
