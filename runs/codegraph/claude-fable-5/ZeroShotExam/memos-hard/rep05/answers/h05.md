**Mechanism: explicit Go code.** When a user is deleted, their reactions are removed by hand-written `DELETE` statements inside the user-deletion transaction — not by any database rule, since the `reaction` table has no foreign key at all.

What I checked:

1. **The deletion transaction.** Each database driver's `DeleteUser` runs `deleteUserTargetsTx`, which explicitly calls two reaction cleanups: `deleteReactionsByCreatorTx` (reactions the user made, `DELETE FROM reaction WHERE creator_id = ?`) and `deleteReactionsByContentIDsTx` (reactions on the user's memos). Evidence:
   - `store/db/sqlite/user_delete.go:96,102` (calls) and `store/db/sqlite/user_delete.go:400-403` (the actual `DELETE FROM reaction WHERE creator_id = ...` SQL)
   - Same pattern in `store/db/mysql/user_delete.go:96,102,437` and `store/db/postgres/user_delete.go:96,102,400`
   - The transaction is driven from `store/user.go:171` (`Store.DeleteUser`) and invoked by the API handler at `server/router/api/v1/user_service.go:414`.

2. **The schema, to rule out a database-level rule.** The `reaction` table definitions contain no `FOREIGN KEY` / `ON DELETE CASCADE` clause in any backend — just a unique constraint on `(creator_id, content_id, reaction_type)`:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`

So a cascade couldn't happen at the database level even in principle; the explicit Go statements are the only removal mechanism. There's also test coverage exercising this path (`server/router/api/v1/test/reaction_service_test.go`, `TestDeleteUserCleansRelatedData`).
