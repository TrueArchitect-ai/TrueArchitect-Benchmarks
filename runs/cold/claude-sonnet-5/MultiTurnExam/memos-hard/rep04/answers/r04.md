**Premise correction:** Neither. The repo has no NATS or RabbitMQ dependency at all (no hits in `go.mod`/`go.sum`), and no external message broker is used for webhook delivery.

**Actual mechanism:** Webhook workers consume from an in-process, buffered Go channel, not a broker. It's declared as `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` in `internal/webhook/webhook.go:35`. Four consumer goroutines are spawned in that package's `init()` (`internal/webhook/webhook.go:38-48`), each looping `for payload := range asyncPostQueue { ... Post(payload) ... }`. Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:187`, `select { case asyncPostQueue <- requestPayload: default: /* drop + log warning if full */ }`), called from the RPC handlers in `server/router/api/v1/memo_service_webhooks.go`. There is no persistence or durability beyond process memory — if the process restarts, any queued-but-undelivered payloads are lost, and a full queue silently drops new webhook dispatches (logged via `slog.Warn`).
