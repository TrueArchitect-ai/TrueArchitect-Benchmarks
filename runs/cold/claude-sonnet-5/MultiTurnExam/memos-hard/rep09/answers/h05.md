h05.

**Mechanism: Explicit Go code** (not a database-level cascade rule).

**Evidence checked:**

1. **Schema has no FK/cascade** — `store/migration/sqlite/0.20/00__reaction.sql:2-9` (also mirrored in `store/migration/postgres/0.20/00__reaction.sql` and `store/migration/mysql/0.20/00__reaction.sql`) defines the `reaction` table with plain `creator_id`/`content_id` columns, no `FOREIGN KEY` / `REFERENCES` / `ON DELETE CASCADE` clause tying it to `user`. Grepping all reaction-related migrations for `FOREIGN KEY`, `REFERENCES`, `CASCADE` across sqlite/postgres/mysql migration dirs returned nothing.

2. **Explicit deletion in Go** — each driver's `store/db/{sqlite,mysql,postgres}/user_delete.go` implements `DeleteUser`, which inside a transaction calls two reaction-deleting helpers as part of `deleteUserTargetsTx`:
   - `deleteReactionsByContentIDsTx` — deletes reactions left *on* memos owned by the user being deleted (`DELETE FROM reaction WHERE content_id IN (...)`, keyed off the user's memo content IDs), e.g. `store/db/sqlite/user_delete.go:380-388`, `store/db/mysql/user_delete.go:417-425`, `store/db/postgres/user_delete.go:380-388`.
   - `deleteReactionsByCreatorTx` — deletes reactions the user themselves made on any content (`DELETE FROM reaction WHERE creator_id = ?`), e.g. `store/db/sqlite/user_delete.go:400-403`, `store/db/mysql/user_delete.go:437-439`, `store/db/postgres/user_delete.go:400-402`.
   
   Both are invoked from `deleteUserTargetsTx` before the memos and user row themselves are deleted (`store/db/sqlite/user_delete.go:96,102`, and identically at `store/db/mysql/user_delete.go:96,102` / `store/db/postgres/user_delete.go:96,102`).

All three supported database drivers (sqlite, mysql, postgres) implement this identically, confirming it's a deliberate application-level cleanup step rather than relying on any database-enforced cascade.
