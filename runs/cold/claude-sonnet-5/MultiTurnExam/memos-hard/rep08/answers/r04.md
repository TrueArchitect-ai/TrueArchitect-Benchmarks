**Premise correction:** Neither. There is no external message broker (NATS or RabbitMQ) involved in webhook delivery — a repo-wide search for "nats", "rabbitmq", "amqp" turns up no matches, and no such dependency exists in `go.mod`.

**Actual mechanism:** The "queue" is a plain in-process Go buffered channel, `asyncPostQueue`, declared in `internal/webhook/webhook.go:39` as `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`. `PostAsync` (`internal/webhook/webhook.go:184-196`) enqueues payloads onto this channel (dropping them with a warning log if it's full, `internal/webhook/webhook.go:189-194`). Four in-process worker goroutines, spawned in `init()` (`internal/webhook/webhook.go:42-55`), range over `asyncPostQueue` and call `Post` (`internal/webhook/webhook.go:120-180`) to perform the actual HTTP delivery. This queue lives entirely in the server's memory — it is not durable, not shared across processes, and is lost on restart.
