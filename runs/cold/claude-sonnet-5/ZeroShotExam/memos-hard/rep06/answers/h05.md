h05.
Mechanism: Explicit Go application code (not a database-level cascade rule). When a user is deleted, reactions are removed transactionally by the store layer before/alongside the hard delete of the user row.

Evidence locations:
- `server/router/api/v1/user_service.go:393-455` — `DeleteUser` handler calls `s.Store.DeleteUser`.
- `store/user.go:171-181` — `Store.DeleteUser` delegates to the SQL driver.
- `store/db/sqlite/user_delete.go`, `store/db/postgres/user_delete.go`, `store/db/mysql/user_delete.go` — each driver implements `deleteUserTargetsTx`, which within a single transaction calls:
  - `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` for reactions left on the deleted user's memos/comments,
  - `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` for reactions the deleted user made,
  - then `deleteUserRowTx` → `DELETE FROM user WHERE id = ?` (a genuine hard delete; `user` has a `row_status` field for archiving, but `DeleteUser` doesn't use it — no `deleted_at`/soft-delete path here).
- `store/reaction.go:7-14` — `Reaction` struct, plain `CreatorID`/`ContentID` ints/strings.
- `store/migration/sqlite/LATEST.sql:92-99` (and equivalent postgres/mysql `LATEST.sql`) — `CREATE TABLE reaction (...)` has **no `FOREIGN KEY`/`REFERENCES`/`CASCADE` clause** on `creator_id` or `content_id`; the only `ON DELETE CASCADE` in the schema is unrelated (`attachment.memo_id → memo(id)`, e.g. `store/migration/sqlite/LATEST.sql:109`).
- `store/test/user_delete_test.go:~97-112, 217-220` — tests confirm the deleted user's own reactions and reactions on their memos are removed, while an unrelated peer's reaction on an unrelated memo is kept.

So cleanup is entirely application-managed (duplicated per SQL backend) rather than enforced by a DB constraint.
