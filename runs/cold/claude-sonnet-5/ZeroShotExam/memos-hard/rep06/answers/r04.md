**Premise correction:** Neither. This repository (usememos/memos) does not use NATS or RabbitMQ for webhook delivery — there is no external message broker involved at all.

**Actual mechanism:** Webhook dispatch is handled by an in-process, in-memory Go channel, not a message broker.

- The "queue" is declared as a buffered Go channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` in `internal/webhook/webhook.go:39`.
- Four worker goroutines are spawned in an `init()` function to consume from it (`internal/webhook/webhook.go:42-55`), each ranging over `asyncPostQueue` and calling `Post(payload)` to deliver the webhook via HTTP.
- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send into the channel and drops (with a warning log) if the channel is full — there's no persistence, retry queue, or external broker backing this.

So delivery is entirely process-local and ephemeral: if the process restarts, any in-flight queued payloads are lost. No `nats`, `amqp`, or `rabbitmq` dependencies exist anywhere in the codebase (confirmed via repo-wide grep).
