**Mechanism:** Explicit Go code (application-level cascade, run inside the user-deletion DB transaction). There is no database-level `ON DELETE CASCADE` for reactions — the `reaction` table has no foreign-key constraints at all.

**Evidence locations:**
- `store/db/sqlite/user_delete.go:29` (and identical `store/db/postgres/user_delete.go:29`, `store/db/mysql/user_delete.go:29`) — `DeleteUser` runs in a transaction and calls `deleteUserTargetsTx` (lines ~92–127 in each driver file).
- Inside `deleteUserTargetsTx`, two explicit deletion calls cover both directions:
  - `deleteReactionsByContentIDsTx` (sqlite/postgres line 380, mysql line 417) — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions left by others on the deleted user's memos/comments.
  - `deleteReactionsByCreatorTx` (sqlite/postgres line 400, mysql line 437) — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user made on others' memos.
  - These run before `deleteMemosTx` and `deleteUserRowTx`, confirming a deliberate ordering.
- Schema check: `store/migration/{sqlite,postgres,mysql}/LATEST.sql` (`reaction` table, ~lines 91–99) has no `FOREIGN KEY` clause on `creator_id` or `content_id`; `grep -rn "FOREIGN KEY" store/migration/` shows CASCADE constraints exist for `memo`, `user_setting`, `memo_resource`/`resource`, and `memo_share`, but never for `reaction`.
- Model/store layer: `store/reaction.go:7-41` defines `Reaction` and the `DeleteReaction`/driver plumbing used by the above.
- Test confirming behavior: `store/test/user_delete_test.go` (`TestDeleteUserCleansRelatedData`, lines ~97–220) creates reactions in both directions plus one that should survive, then asserts only the unrelated reaction remains after `DeleteUser`.
