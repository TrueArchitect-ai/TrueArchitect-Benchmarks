**Premise correction:** There is no Redis anywhere in this repository (github.com/usememos/memos) — a full case-insensitive search for "redis" across the codebase returns zero matches. The cache layer is a pure in-process, in-memory cache, not backed by any external key-value store.

**Actual mechanism:** The cache is implemented in `store/cache/cache.go` as a thread-safe in-memory cache (`sync.Map` + atomic counters) with TTL-based expiration and a background cleanup goroutine.

It's instantiated and wired up in `store/store.go:38-58`. The `Store` struct holds three separate in-memory cache instances — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`) — each created via `cache.New(cacheConfig)`.

The TTL applied to user entries (and all other cached entries, since they all share the same `cacheConfig`) is defined at `store/store.go:40-45`:
```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
So user entries in `userCache` expire after **10 minutes** (the `DefaultTTL`), with a background sweep every 5 minutes (`CleanupInterval`) to evict expired items, and a cap of 1000 items per cache (`MaxItems`) enforced via LRU-ish eviction of the oldest 20% when exceeded (`store/cache/cache.go:252-313`). Individual calls can override the TTL per-entry via `SetWithTTL` (`store/cache/cache.go:97-120`), but the standard `Set` path used for users defaults to this 10-minute TTL.
