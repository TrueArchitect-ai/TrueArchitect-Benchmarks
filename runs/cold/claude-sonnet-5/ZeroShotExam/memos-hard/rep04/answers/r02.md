**Premise correction:** There is no per-user API rate-limiting middleware in this codebase — the premise of the question is incorrect.

What I checked:
- The API's Connect-RPC interceptor chain is defined in `server/router/api/v1/connect_interceptors.go` and registered in `server/router/api/v1/v1.go:133-141`. It consists only of `NewMetadataInterceptor()`, `NewLoggingInterceptor()`, `NewRecoveryInterceptor()`, and `NewAuthInterceptor()` — no rate-limiting interceptor is wired in.
- Repo-wide search for `ratelimit`/`rate_limit`/`throttle`/`limiter` turns up no application middleware; matches are all false positives (editor `debounce`/`delimiter` code) or an unrelated illustrative code snippet in `internal/email/README.md:286-296` showing how one *could* rate-limit outbound emails — never implemented or wired anywhere.
- The only actual "resource exhausted" limiting in the server is a concurrency semaphore for EXIF-stripping on image uploads (`server/router/api/v1/attachment_service.go:158-160`, `acquireImageProcessingSlot`), which caps concurrent image-processing work, not per-user request rates.
- No rate-limiting Go dependency (e.g. `golang.org/x/time/rate`) appears in `go.mod`, and there's no Express/Node middleware since this is a Go backend.

So there's no request-per-minute/hour limit configured anywhere, per-user or otherwise, for the API.
