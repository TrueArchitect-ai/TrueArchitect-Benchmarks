The premise is incorrect: this repository (usememos/memos — Go backend with Connect-RPC API + React/Vite frontend) has **no per-user API rate-limiting middleware** anywhere.

What I checked:
- Searched the entire codebase for rate-limit/throttle/429/ResourceExhausted patterns — no hits in real code (only an unused transitive dependency `golang.org/x/time` in `go.mod`/`go.sum`, and a documentation example in `internal/email/README.md`).
- The Connect-RPC interceptor chain (`server/router/api/v1/v1.go:133-141`) registers only `NewMetadataInterceptor()`, `NewLoggingInterceptor()`, `NewRecoveryInterceptor()`, and `NewAuthInterceptor()` — no rate-limit interceptor.
- The Echo-level middleware in `server/server.go:51-52` registers only `middleware.Recover()` and CORS — nothing else.
- No nginx/reverse-proxy config or Dockerfile/`scripts/compose.yaml` rules add rate limiting at the deployment layer.

The closest related mechanisms are **global concurrency semaphores** (not per-user, time-window rate limits):
- `imageProcessingSemaphore` (max 2 concurrent) and `thumbnailSemaphore` (max 3 concurrent) in `server/router/api/v1/v1.go:39-60`, used by `attachment_service.go`/`attachment_service_image.go` to cap simultaneous image-processing work (returns `codes.ResourceExhausted` when exhausted).
- A separate thumbnail-generation semaphore in `server/router/fileserver/fileserver.go:106-116, 427-451`.

These bound total simultaneous expensive operations system-wide — they aren't keyed by user/IP/API key and have no request-count-per-time-window limits. So there's no answer to give for "request limits" because no such per-user rate limiter exists in this codebase.
