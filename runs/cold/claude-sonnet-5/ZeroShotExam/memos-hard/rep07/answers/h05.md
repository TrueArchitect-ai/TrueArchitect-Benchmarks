**Mechanism: explicit Go application code (in an explicit DB transaction), not a database-level cascade.**

The `reaction` table has **no foreign key constraint** at all (unlike e.g. `memo_share`, which explicitly declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`). So there is no DB-level rule that would remove reactions when a user row is deleted — the cleanup is done entirely in application code, run inside the same transaction as the user delete.

**Evidence:**

1. **Schema — no FK on `reaction`** (confirms no DB-level cascade is possible):
   - `/bench/repo/store/migration/sqlite/LATEST.sql` — `CREATE TABLE reaction (... creator_id INTEGER NOT NULL, content_id TEXT NOT NULL, ...)`, no `FOREIGN KEY` clause.
   - `/bench/repo/store/migration/postgres/LATEST.sql` — same, `CREATE TABLE reaction (...)` with no FK.
   - `/bench/repo/store/migration/mysql/LATEST.sql` — same, `CREATE TABLE \`reaction\` (...)` with no FK.
   - Contrast: the `memo_share` table right below each of these *does* declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, showing the schema authors use FK cascades elsewhere when intended — they deliberately did not for `reaction`.

2. **Explicit Go deletion logic**, identical across all three DB drivers (`DeleteUser` transaction):
   - `/bench/repo/store/db/sqlite/user_delete.go:96` and `:380-388` — `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` for every memo (and memo-tree/comment) the deleted user authored.
   - `/bench/repo/store/db/sqlite/user_delete.go:102` and `:400-403` — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user themselves placed on *anyone's* memo.
   - Same two functions at identical line numbers/logic in `/bench/repo/store/db/postgres/user_delete.go:96,102,380-388,400-403` and `/bench/repo/store/db/mysql/user_delete.go:96,102,417-425,437-440`.
   - Both calls happen inside `deleteUserTargetsTx` (called from `DeleteUser`, e.g. `/bench/repo/store/db/sqlite/user_delete.go:29-59`), before the `user` row itself is deleted at `deleteUserRowTx` (`:461-464`), all wrapped in one SQL transaction (`tx.BeginTx` / `tx.Commit`).

So reactions are cleaned up twice over for a deleted user: reactions *received* on their memos (via `content_id`), and reactions *given* by them on others' memos (via `creator_id`) — both by hand-written `DELETE` statements in Go, not by a database trigger or FK cascade.
