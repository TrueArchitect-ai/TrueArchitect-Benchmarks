**Evidence locations:**

- **Schema has no FK/cascade on `reaction`:** `store/migration/postgres/LATEST.sql:91-98`, `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98` all define `reaction` with a plain `creator_id INTEGER NOT NULL` / `content_id TEXT NOT NULL` — no `REFERENCES`, no `ON DELETE CASCADE`. (Contrast with `memo_share.memo_id REFERENCES memo(id) ON DELETE CASCADE` in the same files, e.g. `LATEST.sql:109`, showing the schema authors use cascades elsewhere but deliberately not here.) This repo uses raw SQL via `database/sql`, no ORM, so there's no ORM-level cascade either — `store/reaction.go:7-14`.

- **Explicit deletion in `DeleteUser`:**
  - API handler: `server/router/api/v1/user_service.go:393` → calls `s.Store.DeleteUser` (line 414)
  - Store layer: `store/user.go:171` → delegates to `s.driver.DeleteUser`
  - Per-dialect drivers, each running inside one transaction (`deleteUserTargetsTx`): `store/db/postgres/user_delete.go`, `store/db/sqlite/user_delete.go`, `store/db/mysql/user_delete.go`. Each explicitly calls two helper functions:
    - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions left by others on the deleted user's memos/comments (e.g. postgres `user_delete.go:96` in the `deleteUserTargetsTx` sequence)
    - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user placed on any content (postgres `user_delete.go:104`)

- **No separate cron/cleanup job** was found (searched for cron/scheduler/cleanup patterns) — all reaction cleanup happens synchronously inside the `DeleteUser` transaction.

- **Test confirmation:** `store/test/user_delete_test.go:97-220` exercises exactly this — a reaction by the deleted user on their own memo, a reaction by the deleted user on a peer's memo, and a peer's reaction on the deleted user's memo — and verifies the deleted user's reactions are gone while unrelated peer reactions on surviving content remain.

**Caveat:** because there's no DB-level FK, this cleanup relies entirely on all user-deletion paths going through this one `DeleteUser` transaction; a hypothetical direct `DELETE FROM "user"` bypassing this code path would orphan reactions silently.
