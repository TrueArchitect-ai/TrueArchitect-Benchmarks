When `Store.DeleteMemo` (store/memo.go:140-159) runs, before the driver deletes the `memo` row itself it deletes:

1. **`memo_relation` records where the memo is the source** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` (store/memo.go:142)
2. **`memo_relation` records where the memo is the target** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID})` (store/memo.go:145)
3. **`attachment` records (and their underlying storage/files) linked to the memo** — listed via `ListAttachments` and removed one-by-one via `DeleteAttachment` (store/memo.go:149-157, which internally also calls `DeleteAttachmentStorage` in store/attachment.go:132-148 to remove the on-disk/blob file before deleting the DB row)

Only after these are cleaned up does it call `s.driver.DeleteMemo(ctx, delete)` (store/memo.go:158) to remove the memo row.

One layer up, in the API handler (`server/router/api/v1/memo_service.go:518-582`), memo **comments** (child memos linked via `memo_relation` of type `MemoRelationComment`) are also recursively deleted through `s.Store.DeleteMemo` before the parent memo is deleted (lines 567-577) — but that recursion is handled at the service layer, not inside the store's `DeleteMemo` itself.
