**Tables affected when `DeleteMemo` runs:**

1. **`memo`** — the target memo row is deleted directly; also, any child "comment" memos are found via `ListMemoRelations` (type `Comment`) and deleted recursively through `store.DeleteMemo` before the parent, so `memo` rows are removed for the memo itself and all of its comments (`server/router/api/v1/memo_service.go:567-582`, `store/memo.go:140-159`).

2. **`memo_relation`** — explicitly cleaned up by `Store.DeleteMemo`, which calls `driver.DeleteMemoRelation` once for rows where the deleted memo is the source (`memo_id`) and once for rows where it's the target (`related_memo_id`) (`store/memo.go:141-147`).

3. **`attachment`** — explicitly cleaned up: `Store.DeleteMemo` lists attachments via `ListAttachments{MemoID}` and calls `DeleteAttachment` for each, which also removes the underlying blob/storage (`store/memo.go:148-157`, `store/attachment.go:132-149`).

4. **`memo_share`** — not touched by Go code, but cascades at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, defined identically in the Postgres, MySQL, and SQLite schemas (`store/migration/postgres/LATEST.sql:101-109`, `store/migration/mysql/LATEST.sql:100-109`, `store/migration/sqlite/LATEST.sql:~109`).

**Not deleted (worth noting):** `reaction` rows tied to the memo are only `List`ed (for the webhook payload), never deleted — `content_id` has no FK/cascade to `memo`, so reactions are left orphaned (`server/router/api/v1/memo_service.go:545-550`).
