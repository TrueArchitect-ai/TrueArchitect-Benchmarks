**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted directly (`store/memo.go:158` → `store/db/{sqlite,postgres,mysql}/memo.go` `DeleteMemo`), and recursively for any child memos that are "comment" relations of it (`server/router/api/v1/memo_service.go:567-577`).
- **`memo_relation`** — explicitly deleted for rows where the memo is either the source or target (`store/memo.go:142-147`, via `driver.DeleteMemoRelation`).
- **`attachment`** — all attachments tied to the memo are explicitly loaded and deleted one by one (`store/memo.go:149-157` → `store/attachment.go:132-149` `DeleteAttachment`), which also removes the underlying attachment storage/blob.
- **`memo_share`** — cascaded at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Note: for the SQLite driver this cascade is effectively inert since the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite orphaned `memo_share` rows can remain; Postgres/MySQL enforce it.

Not touched despite being related: `reaction` rows for the memo are only read (`ListReactions`, for the webhook payload) but never deleted, so they become orphaned by `content_id`.
