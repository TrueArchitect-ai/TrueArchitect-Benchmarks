Confirmed: `DeleteReaction` is never invoked from the memo deletion path, so `reaction` rows tied to a deleted memo are orphaned rather than cascaded.

## q26.

Tables affected when `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518` → `store.Store.DeleteMemo` at `store/memo.go:140`):

- **`memo`** — the target memo row is deleted directly (`store/db/sqlite/memo.go:237`, and equivalent postgres/mysql drivers). Before that, the service layer (`memo_service.go:567-577`) finds all comment memos via `memo_relation` (type `COMMENT`) and recursively calls `store.DeleteMemo` on each, so every comment memo row is deleted from `memo` too.
- **`memo_relation`** — explicitly cleaned up in `store.DeleteMemo` (`store/memo.go:142-147`) for both directions (`memo_id` and `related_memo_id`), for the target memo and, recursively, for each deleted comment memo.
- **`attachment`** — explicitly cleaned up in `store.DeleteMemo` (`store/memo.go:148-157`, via `ListAttachments`/`DeleteAttachment`), again for the target memo and each deleted comment memo.
- **`memo_share`** — not touched by application code, but cascades at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:102-110`, same in `store/migration/postgres/LATEST.sql:101-109` and the MySQL equivalent).

Notably **not** cascaded: `reaction` rows referencing the memo (via `content_id`) are read for the webhook payload (`memo_service.go:545-550`) but never deleted — there's no FK and no explicit `DeleteReaction` call anywhere in the delete path, so they're orphaned rather than cascaded.
