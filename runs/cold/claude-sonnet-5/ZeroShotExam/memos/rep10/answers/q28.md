**Runners actually started by the server** (`cmd/memos/main.go` → `server.NewServer()` → `s.Start(ctx)` in `server/server.go`):

- S3 presign runner — `time.NewTicker(12 * time.Hour)` ticker loop; started in `startBackgroundRunners` (`server/server.go:153-174`, runner instantiated at `server/server.go:162`, goroutine loop at `server/server.go:167-171`), ticker defined in `server/runner/s3presign/runner.go:27-41`. Re-presigns S3 attachment URLs nearing expiration; wired into graceful shutdown.
- In-memory cache cleanup loops (instanceSettingCache, userCache, userSettingCache) — each driven by its own `time.NewTicker(c.config.CleanupInterval)` = 5 minutes (`store/cache/cache.go:83,201`); spawned as a side effect of `store.New()` called once at boot (`cmd/memos/main.go:64`, `store/store.go:51-53`).
- Webhook dispatch worker pool (4 goroutines) — driven by a buffered Go channel (`asyncPostQueue`, cap 128), consumer blocks on channel receive, not time-based; started in a package `init()` in `internal/webhook/webhook.go:42-52`, linked in via `cmd/memos/main.go:49` and router notification code.
- Email dispatch worker pool (2 goroutines) — same pattern, buffered channel `asyncEmailQueue` (cap 128); started in package `init()` in `internal/email/email.go:16-19`, linked in via `server/notification/email.go` and `server/router/api/v1`.
- SSE heartbeat ticker — `time.NewTicker(30s)` (`server/router/api/v1/sse_handler.go:17,64`), but created per SSE connection rather than once at server boot, so it's a per-connection timer, not a global scheduled job.

**Unused scheduling infrastructure:**
- `internal/scheduler` package — a complete cron-style scheduler (cron expression parsing, timezones, logging/recovery/metrics middleware; `internal/scheduler/scheduler.go`, `job.go`, `parser.go`, `middleware.go`) is only referenced from its own test files (`example_test.go`, `integration_test.go`). No production code imports or instantiates it.
- `memopayload.Runner` / `RunOnce` (`server/runner/memopayload/runner.go`) — a batch job that rebuilds markdown-derived payloads for all memos, but is never constructed or invoked by the server. Only the unrelated synchronous helper `memopayload.RebuildMemoPayload(...)` is called directly from request handlers (`server/router/api/v1/memo_service.go:108,447`) on memo create/update — that's inline request handling, not a scheduled background job.
