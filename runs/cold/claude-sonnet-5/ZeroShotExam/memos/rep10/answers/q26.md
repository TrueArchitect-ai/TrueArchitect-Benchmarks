**Tables affected when `DeleteMemo` runs** (`server/router/api/v1/memo_service.go:518` → `store.Store.DeleteMemo` at `store/memo.go:140`):

- **`memo`** — the target memo row is deleted directly (`store/db/sqlite/memo.go:237`, and equivalents in `store/db/postgres/memo.go`, `store/db/mysql/memo.go`). Additionally, any child "comment" memos are looked up via `memo_relation` and deleted first in a loop (`server/router/api/v1/memo_service.go:567-577`), so `memo` rows are removed both for the target and recursively for its comments.
- **`memo_relation`** — explicitly cleaned up in `store.Store.DeleteMemo` for both directions (`memo_id = ?` and `related_memo_id = ?`) via `driver.DeleteMemoRelation` (`store/memo.go:142-147`, e.g. `store/db/sqlite/memo_relation.go:137`).
- **`attachment`** — explicitly cleaned up: all attachments for the memo are listed and each deleted via `s.DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`).
- **`memo_share`** — not touched by any Go code, but removed via a DB-level `ON DELETE CASCADE` foreign key to `memo(id)` defined in the schema (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`), which is explicit cascade behavior triggered when the `memo` row is deleted.

Note: `reaction` rows referencing the memo (via `content_id`, a plain text column with no FK — `store/migration/sqlite/LATEST.sql:92-98`) are read via `ListReactions` for the webhook payload but are **not** deleted, and there is no FK/cascade for that table, so they're left orphaned (not part of the affected-tables list, but worth flagging as a likely gap).
