Tables affected when `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518` → `store.Store.DeleteMemo` at `store/memo.go:140`):

- **`memo`** — the target memo row is deleted (`store/db/sqlite/memo.go:237-248`, and equivalents in `store/db/postgres/memo.go`, `store/db/mysql/memo.go`); comment-type child memos found via `memo_relation` are also deleted here recursively (`server/router/api/v1/memo_service.go:567-577`).
- **`memo_relation`** — rows where the memo is either `memo_id` or `related_memo_id` are explicitly deleted (`store/memo.go:142-147`, e.g. `store/db/sqlite/memo_relation.go:137-151`).
- **`attachment`** — attachments linked via `memo_id` are looked up and deleted one by one (`store/memo.go:148-157`, `store/db/sqlite/attachment.go:211-221`).
- **`memo_share`** — not touched explicitly in Go code, but cascades automatically via the `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` constraint (`store/migration/sqlite/LATEST.sql:102-110`, mirrored in `store/migration/postgres/LATEST.sql` and `store/migration/mysql/LATEST.sql`).

Note: `reaction` rows tied to the memo (via `content_id`) are only read for the deletion webhook payload (`server/router/api/v1/memo_service.go:545-550`) but are **not** deleted — there's no FK cascade or explicit `DeleteReaction` call, so the `reaction` table is not actually affected.
