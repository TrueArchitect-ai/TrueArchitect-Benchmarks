Confirmed the SQLite pragma. Both background agents corroborate my direct findings. One useful refinement worth flagging:

**Update to my answer:** SQLite opens its connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), which disables FK enforcement entirely — so on SQLite, even the `memo_share` `ON DELETE CASCADE` never actually fires. That table's cleanup on memo delete is effectively DB-dependent (works on Postgres/MySQL where FKs are enforced, silently doesn't happen on SQLite unless something else prunes it), and in no case is it triggered by explicit Go code.

This doesn't change the core answer — **`memo`, `memo_relation`, `attachment`** remain the only tables `DeleteMemo` touches via explicit application code — but it sharpens the caveat about `memo_share` and confirms `reaction` rows are genuinely orphaned (read-only, never deleted, no FK exists for that table at all).
