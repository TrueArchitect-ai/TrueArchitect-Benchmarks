In `store.DeleteMemo` (`store/memo.go:140-159`), before deleting the memo row itself (`store/memo.go:158`), the store layer deletes:

- **memo_relation** rows where the memo is the source (`MemoID`) — `store/memo.go:142`
- **memo_relation** rows where the memo is the target (`RelatedMemoID`) — `store/memo.go:145`
- **attachment** rows (and their underlying file/S3 storage via `DeleteAttachment`) linked to the memo — `store/memo.go:149-156` (deletion logic in `store/attachment.go:132-149`)

Note: comment memos (child memos linked via `memo_relation` of type `MemoRelationComment`) are deleted one level up, in the API handler `server/router/api/v1/memo_service.go:568-577`, before it calls into the store's `DeleteMemo` for the parent — each comment deletion recurses through the same store-layer cleanup above. `memo_share` rows are cleaned up via a DB-level `ON DELETE CASCADE` foreign key rather than explicit store code, and `reaction` rows are not deleted by this code path at all.
