When deleting a memo via the API (`APIV1Service.DeleteMemo` in `server/router/api/v1/memo_service.go:518`), the store layer's `Store.DeleteMemo` (`store/memo.go:140`) deletes the following record types before deleting the memo row itself:

1. **Memo relations** — twice: once where the memo is the source (`MemoID`) and once where it is the target (`RelatedMemoID`), via `s.driver.DeleteMemoRelation` (`store/memo.go:142` and `:145`), which calls into `store/memo_relation.go:51`.
2. **Attachments** — all attachments linked to the memo are listed (`ListAttachments`) and then deleted one by one via `s.DeleteAttachment` (`store/memo.go:149-157`, implemented in `store/attachment.go:132`), which also removes the underlying attachment blob/file storage.

Only after these two cleanups does it call `s.driver.DeleteMemo` (the per-DB driver `DELETE FROM memo ...`, e.g. `store/db/sqlite/memo.go:237`).

Additionally, one layer up, `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:567-582`) first finds all comment memos referencing this memo (`MemoRelation` of type `COMMENT`) and recursively calls `Store.DeleteMemo` on each comment memo — so comment memos (and, transitively, their own relations/attachments) are deleted before the parent memo.

Note: `memo_share` rows are cleaned up via an `ON DELETE CASCADE` foreign key at the schema level rather than application code, and `reaction` rows are not deleted by this code path at all (left orphaned).
