When `store.DeleteMemo` (store/memo.go:140-158) runs, before it issues the final `DELETE FROM memo` (via the driver's `DeleteMemo`, e.g. store/db/sqlite/memo.go:237), it deletes the following record types:

1. **`memo_relation` records where this memo is the source** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` (store/memo.go:142)
2. **`memo_relation` records where this memo is the target/related memo** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID})` (store/memo.go:145)
3. **Attachments linked to the memo** — listed via `s.ListAttachments(...)` and each deleted individually via `s.DeleteAttachment(...)` (store/memo.go:149-157), which in turn (store/attachment.go:132-148) also deletes the attachment's underlying storage (local file or external) before removing the `attachment` row itself.

Additionally, one level up, at the API handler layer (`server/router/api/v1/memo_service.go:518-582`), before `store.DeleteMemo` is called on the memo itself, any **comment memos** (child memos linked via a `memo_relation` of type `MemoRelationComment`) are recursively deleted by calling `s.Store.DeleteMemo` on each comment's memo ID first (memo_service.go:567-577) — each of those recursive calls goes through the same relation/attachment cleanup described above.

So, in order, before the memo row is deleted:
- Comment memos (recursively, via repeated `store.DeleteMemo` calls) — handler layer, memo_service.go:567-577
- `memo_relation` rows where the memo is the source — store/memo.go:142
- `memo_relation` rows where the memo is the target — store/memo.go:145
- `attachment` rows (and their underlying storage/files) linked to the memo — store/memo.go:148-157, store/attachment.go:132-148
