Before the `memo` row is removed, `Store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) deletes, in order:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (line 142)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (line 145)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments{MemoID}` and deleted one by one (lines 149-157); each `Store.DeleteAttachment` (`/bench/repo/store/attachment.go:132-149`) also deletes the **underlying stored file/blob** (local file removal or external storage object) before the DB row
4. **the `memo` row itself** — `s.driver.DeleteMemo` (line 158), e.g. `/bench/repo/store/db/sqlite/memo.go:237`, which is a plain `DELETE FROM memo` with no further cascade

One level up, the API handler `APIV1Service.DeleteMemo` (`/bench/repo/server/router/api/v1/memo_service.go:518-591`) first deletes **child comment memos** — it lists relations of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each (lines 567-577), so every comment goes through the same relation/attachment cleanup before the parent. It also dispatches the memo-deleted webhook and broadcasts an SSE event, but note that `reaction` rows are only *read* (to build the webhook payload, lines 545-550) — they are not deleted here.
