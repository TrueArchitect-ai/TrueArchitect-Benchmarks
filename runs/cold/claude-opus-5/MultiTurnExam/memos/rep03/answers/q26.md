**memo, memo_relation, attachment, memo_share**

- **`memo_relation`** — deleted first by `Store.DeleteMemo`, both directions: `MemoID` and `RelatedMemoID` (`/bench/repo/store/memo.go:142, 145`).
- **`attachment`** — rows linked to the memo are listed and deleted individually (`/bench/repo/store/memo.go:149-157`); each `Store.DeleteAttachment` (`/bench/repo/store/attachment.go:132`) also removes the underlying local file or object-storage blob.
- **`memo`** — the row itself via `s.driver.DeleteMemo` (`/bench/repo/store/memo.go:158`), e.g. the plain `DELETE FROM memo` at `/bench/repo/store/db/sqlite/memo.go:237`. Through the API handler `APIV1Service.DeleteMemo` (`/bench/repo/server/router/api/v1/memo_service.go:518`), **additional `memo` rows** are removed too: every child comment memo is deleted first via the same store path (lines 567-577).
- **`memo_share`** — by DB-level `ON DELETE CASCADE` on the `memo_id` foreign key (`/bench/repo/store/migration/sqlite/LATEST.sql:109`, and the same in the postgres and mysql `LATEST.sql`). Worth flagging: SQLite opens its connection with `_pragma=foreign_keys(0)` (`/bench/repo/store/db/sqlite/sqlite.go:53`), so that cascade does **not** fire on SQLite, and there is no explicit `memo_share` cleanup in `Store.DeleteMemo` — only the user-deletion path deletes shares explicitly (`/bench/repo/store/db/sqlite/user_delete.go:406-411`).

Not touched: **`reaction`** rows are only read to build the webhook payload (`memo_service.go:545-550`), never deleted; likewise `inbox` and `user_setting` are unaffected.
