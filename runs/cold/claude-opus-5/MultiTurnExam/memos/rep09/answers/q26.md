**memo_relation, attachment, memo, memo_share**

- **memo_relation** — `Store.DeleteMemo` deletes rows in both directions: `MemoID` and `RelatedMemoID` (`store/memo.go:142,145`).
- **attachment** — attachments with `memo_id = <id>` are listed and deleted individually via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying file/blob (`store/attachment.go:132-148`).
- **memo** — the row itself (`store/memo.go:158` → e.g. `store/db/sqlite/memo.go:237`), plus additional `memo` rows for each comment: the API handler first deletes every memo related by `MemoRelationComment` through the same path (`server/router/api/v1/memo_service.go:567-577`).
- **memo_share** — only by DB-level cascade: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). There is no explicit Go cleanup code for it.

Two caveats worth flagging. On SQLite that cascade does **not** fire — the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so `memo_share` rows are left behind on that backend. And the **reaction** table is not touched at all: `DeleteMemo` reads reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545`), and `reaction.content_id` stores the memo resource name with no foreign key, so reaction rows outlive the deleted memo.
