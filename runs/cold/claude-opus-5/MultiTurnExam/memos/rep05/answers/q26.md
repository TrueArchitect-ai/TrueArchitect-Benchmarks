**memo, memo_relation, attachment, memo_share**

How each is touched when `Store.DeleteMemo` runs (`store/memo.go`), driven from `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):

| Table | How |
|---|---|
| `memo_relation` | Two explicit deletes — rows where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`) |
| `attachment` | Explicit: `ListAttachments{MemoID}` then `Store.DeleteAttachment` per row (also removes the local/S3 blob, `store/attachment.go`) |
| `memo` | The row itself (`store/db/sqlite/memo.go` and postgres/mysql equivalents); additionally, comment memos are deleted as separate `memo` rows by the handler at `server/router/api/v1/memo_service.go:567-577`, each recursing through the same cleanup |
| `memo_share` | Only by DB-level `ON DELETE CASCADE` — `store/migration/{sqlite,postgres,mysql}/LATEST.sql:~108`; there is no Go code deleting shares on memo deletion |

Two caveats worth flagging:

- **`memo_share` cascade does not fire on SQLite.** The connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the FK constraint is inert and share rows are orphaned there. The cascade does apply on Postgres and MySQL.
- **`reaction` is never cleaned up.** `DeleteMemo` lists reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); the table keys off a `content_id` string with no FK, so its rows survive the deletion.
