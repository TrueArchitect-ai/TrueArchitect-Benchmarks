Deletion happens in two layers.

**In the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-591`), before deleting the memo itself:**
- **Comment memos** — every memo related to this one by `MemoRelationComment` is deleted via a recursive `Store.DeleteMemo` call (`server/router/api/v1/memo_service.go:567-577`), which in turn runs the store-level cleanup below for each comment.

**In `Store.DeleteMemo` (`store/memo.go`), before `driver.DeleteMemo`:**
- **memo_relation rows where the memo is the source** (`MemoID` match)
- **memo_relation rows where the memo is the target** (`RelatedMemoID` match)
- **attachments linked to the memo** — listed via `ListAttachments{MemoID}` and removed one by one with `Store.DeleteAttachment`, which also deletes the **underlying stored file/blob** (local disk or S3) via `DeleteAttachmentStorage` (`store/attachment.go`)

Then the `memo` row itself is deleted (`store/db/sqlite/memo.go`, and the postgres/mysql equivalents).

Two things that are *not* explicitly deleted by this path:
- **Reactions** are only listed (for the webhook payload, `server/router/api/v1/memo_service.go:545-550`), never deleted — the `reaction` table keys off a `content_id` string with no FK, so reaction rows for a deleted memo are left behind.
- **memo_share** rows are removed by the database, not the Go code: `store/migration/sqlite/LATEST.sql:109` declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`.
