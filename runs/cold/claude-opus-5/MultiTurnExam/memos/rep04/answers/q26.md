**memo_relation, attachment, memo** — plus **memo_share** on MySQL/Postgres only, via a DB-level FK cascade.

Breakdown of `Store.DeleteMemo` (`store/memo.go:140-159`):

- **`memo_relation`** — deleted twice, once by `MemoID` and once by `RelatedMemoID` (lines 142, 145).
- **`attachment`** — rows found by `FindAttachment{MemoID}` are deleted individually (lines 149-157); each `Store.DeleteAttachment` (`store/attachment.go:132`) also removes the underlying local file or S3 object, which is outside the DB.
- **`memo`** — the row itself, via `driver.DeleteMemo` (e.g. `store/db/sqlite/memo.go:237`, a plain `DELETE FROM memo WHERE id = ?`).
- **`memo`, `memo_relation`, `attachment` again for comments** — the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:567-578`) first calls `Store.DeleteMemo` on each child comment memo, so the same three tables are hit once per comment.

`memo_share` is declared with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:107`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`), but there is no explicit cascade code for it in the delete path. Worth flagging: the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and share rows are left behind when a memo is deleted.

`reaction` is **not** deleted — it's only read in the handler to build the webhook payload (`server/router/api/v1/memo_service.go:545`), and it has no FK to `memo` (it keys off a `content_id` text column).
