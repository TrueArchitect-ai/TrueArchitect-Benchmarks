**Interceptor path:** `web/src/connect.ts` (the `authInterceptor`, line 156)
**Token kinds:** short-lived JWT **access token** (Bearer header, 15 min) + long-lived JWT **refresh token** (httpOnly `memos_refresh` cookie, 30 days); the backend additionally accepts **Personal Access Tokens** (`memos_pat_` prefix) on the same Authorization header
**Backend package:** `server/auth`

How it fits together:

- The interceptor is installed on the Connect transport (`web/src/connect.ts:188`). On each request it calls `getRequestToken()` (line 124) and sets `Authorization: Bearer <token>` (line 97). It refreshes proactively when the access token is within its expiry buffer (line 140) and reactively on a `Code.Unauthenticated` response, retrying once with an `X-Retry` marker (lines 164-172); repeated failure triggers `redirectOnAuthFailure`.
- The refresh token is never touched by JS — the transport uses `fetch` with `credentials: "include"` (`web/src/connect.ts:57-62`), so the `memos_refresh` cookie rides along. Refresh goes through a *separate* interceptor-free transport and `refreshAuthClient` to avoid recursion (lines 65-72), with concurrent refreshes deduplicated by `tokenRefreshManager` (line 30). Access-token storage lives in `web/src/auth-state.ts`.
- Validation happens in **`server/auth`**: constants and JWT parsing in `server/auth/token.go` (audiences `user.access-token` / `user.refresh-token`, cookie name at line 49, PAT prefix at line 52), the `Authenticator` in `server/auth/authenticator.go` (`AuthenticateByRefreshToken` at line 61 does a DB revocation + expiry check; `AuthenticateByPAT` at line 100 looks up a SHA-256 hash), cookie extraction in `server/auth/extract.go:23`, and context plumbing in `server/auth/context.go`. It's wired into the REST path as the gateway auth middleware in `server/router/api/v1/v1.go` and used by `server/router/fileserver` and the SSE endpoint (`server/router/api/v1/sse_handler.go:36`).
