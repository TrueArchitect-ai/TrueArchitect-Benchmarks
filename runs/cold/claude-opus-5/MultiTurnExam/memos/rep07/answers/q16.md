Inside `Store.DeleteMemo` (`store/memo.go:140-158`), two kinds of records are removed before the memo row:

1. **`memo_relation` rows — both directions.** One delete where the memo is the source (`MemoID`) and one where it is the target (`RelatedMemoID`) — `store/memo.go:142-147`.
2. **`attachment` rows linked to the memo**, each via `Store.DeleteAttachment` — `store/memo.go:149-157`. That call also removes the underlying stored blob (local file or external storage object) before the DB row, at `store/attachment.go:141-148`.

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`).

One level up, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally deletes **child comment memos** first — it lists relations of type `comment` pointing at this memo and calls `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:567-577`), so each comment gets the same relation/attachment cleanup. Note that reactions are only *read* there (`:545`, for the webhook payload) — they are not explicitly deleted in either layer.
