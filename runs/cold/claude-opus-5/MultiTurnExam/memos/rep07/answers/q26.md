**memo, memo_relation, attachment** (plus **memo_share** via a DB-level foreign-key cascade on Postgres/MySQL only)

Breakdown of what runs:

- **`memo_relation`** — deleted explicitly in both directions (`MemoID` and `RelatedMemoID`) at `store/memo.go:142-147`.
- **`attachment`** — every attachment linked to the memo is deleted via `Store.DeleteAttachment` at `store/memo.go:149-157`; that path also removes the backing local file or object-storage blob (`store/attachment.go:141-148`).
- **`memo`** — the row itself, last: `store/memo.go:158` → `store/db/sqlite/memo.go:237` (`DELETE FROM memo WHERE id = ?`). Child **comment memos** are additional `memo` rows deleted first by the API handler at `server/router/api/v1/memo_service.go:567-577`, each recursing through the same relation/attachment cleanup.
- **`memo_share`** — no explicit delete code; it relies on `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:102-110`). Note this cascade does **not** fire on SQLite, since the connection opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`) — so `memo_share` rows are orphaned there but cascaded on Postgres/MySQL.

**`reaction` is not touched.** The delete handler only *reads* reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545`), and the table has no FK to `memo` (it keys off a free-form `content_id`, `store/migration/sqlite/LATEST.sql:92-99`), so reaction rows for a deleted memo are left behind in every dialect.
