**memo, memo_relation, attachment** — plus **memo_share** on Postgres/MySQL only, via a declared FK cascade.

Breakdown:

- **`memo_relation`** — explicitly deleted twice, for rows where the memo is the source and where it's the target (`store/memo.go:142`, `:145`).
- **`attachment`** — every attachment linked to the memo is deleted via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the backing blob from storage (`store/attachment.go:141`).
- **`memo`** — the row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`). When the API handler is the entry point, this also covers **child comment memos**, which are looked up by `MemoRelationComment` relation and deleted recursively (`server/router/api/v1/memo_service.go:567-577`) — same three tables again, one level down.
- **`memo_share`** — `memo_share.memo_id` is declared `REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`), and there is no explicit share-deletion code in the memo delete path. Important caveat: on SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so FK enforcement is off and that cascade does **not** fire there — orphaned `memo_share` rows would remain. The MySQL schema declares `memo_share` at `store/migration/mysql/LATEST.sql:101` but without the FK clause, so it wouldn't cascade there either.

Not touched: **`reaction`** — reactions on the memo are read for the webhook payload (`server/router/api/v1/memo_service.go:545`) but never deleted.
