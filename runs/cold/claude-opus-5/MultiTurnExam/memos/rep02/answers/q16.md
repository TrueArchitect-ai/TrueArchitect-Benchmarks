Before the `memo` row is deleted, `Store.DeleteMemo` (`store/memo.go:140-158`) removes, in order:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo**, one by one via `Store.DeleteAttachment` (`store/memo.go:149-157`) — and that call also deletes the backing blob from storage first (`store/attachment.go:141`, local-file failures are fatal, remote ones only warn)

Then `s.driver.DeleteMemo` issues the plain `DELETE FROM memo` (e.g. `store/db/sqlite/memo.go:237`).

Two things happen at the API layer, not the store layer, and are worth separating out: `APIV1Service.DeleteMemo` first recursively deletes **comment memos** (child memos found via `MemoRelationComment` relations) by calling `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:567-577`). And reactions are *listed* there only to build the webhook payload (`:545`) — I found no code deleting `reaction` rows on memo deletion, so those appear to be left behind.
