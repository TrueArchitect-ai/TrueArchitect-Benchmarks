**Mechanism:** Server-Sent Events (SSE) — a long-lived `GET /api/v1/sse` stream, Bearer-token authenticated (`server/router/api/v1/sse_handler.go:25-37`), registered on the Echo group in `server/router/api/v1/v1.go:125`.

**Hub:** `server/router/api/v1/sse_hub.go` — the `SSEHub` type (:54) manages client registration and `Broadcast`, with a small per-client buffer so a slow reader can't block the broadcaster (:73, :114). Event types are defined at :15-20: `memo.created`, `memo.updated`, `memo.deleted`, `memo.comment.created`, `reaction.upserted`, `reaction.deleted`. Helpers for building events are in `server/router/api/v1/sse_event_helpers.go`.

**Handlers that broadcast:**

| Handler | File | Event |
|---|---|---|
| `CreateMemo` | `memo_service.go:163` | `memo.created` |
| `DeleteMemo` | `memo_service.go:585` | `memo.deleted` |
| `CreateMemoComment` | `memo_service_comments.go:126` | `memo.comment.created` |
| `UpsertMemoReaction` | `reaction_service.go:106` | `reaction.upserted` |
| `DeleteMemoReaction` | `reaction_service.go:161` | `reaction.deleted` |

Plus `memo.updated`, which is emitted indirectly through the shared helper `dispatchMemoUpdatedSideEffects` (`memo_update_helpers.go:66-71`), called by three handlers: `UpdateMemo` (`memo_service.go:513`), `SetMemoAttachments` (`memo_attachment_service.go:48`), and `SetMemoRelations` (`memo_relation_service.go:48`).

One detail worth noting: `CreateMemo`'s broadcast can be suppressed via a context flag (`withSuppressSSE`, `memo_service.go:22`) — `CreateMemoComment` uses this so the parent memo's `memo.comment.created` event fires instead of a generic `memo.created`.
