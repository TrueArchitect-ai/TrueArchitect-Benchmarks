**Engine: CEL (Google Common Expression Language, via `cel-go`) — `internal/filter/`**

**Mechanism:** `filter.DefaultEngine()` parses the expression with `cel-go` against a memo-specific CEL environment (`internal/filter/schema.go`, which declares the allowed variables — `content`, `creator`, `tag`, `pinned`, `visibility`, `has_task_list`, etc.), normalizes the AST into a dialect-agnostic IR (`internal/filter/parser.go` → `internal/filter/ir.go`), then renders that IR into a SQL `WHERE` fragment plus placeholder args for the target dialect (`internal/filter/render.go`, dialects `DialectSQLite`/`DialectMySQL`/`DialectPostgres` at `internal/filter/schema.go:14-16`) — so each driver just calls `filter.AppendConditions(ctx, engine, find.Filters, filter.Dialect…, &where, &args)`, e.g. `store/db/sqlite/memo.go:57-61`, with the same two lines in `store/db/postgres/memo.go` and `store/db/mysql/memo.go`.

Dialect differences (JSON access, boolean semantics, `?` vs `$n` placeholders, `LIKE` vs `ILIKE`, string concat) are encapsulated in per-dialect templates in the schema and renderer helpers — see `internal/filter/schema.go:105-135` and the pipeline description in `internal/filter/README.md`. The API-layer glue that pulls `request.Filter` into `store.FindMemo` is `server/router/api/v1/memo_service_filter.go`; the same engine also backs attachment and memo-relation filtering (`store/db/*/attachment.go`, `store/db/*/memo_relation.go`).
