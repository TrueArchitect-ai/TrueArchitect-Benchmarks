**web/src/connect.ts; short-lived JWT access tokens + an HTTP-only refresh-token cookie (backend also accepts Personal Access Tokens); server/auth/**

**Interceptor** — `authInterceptor` at `web/src/connect.ts:155`, installed on the shared Connect transport (`:184-188`). Per request it: fetches a token via `getRequestToken()`, sets `Authorization: Bearer <token>`, and on a `Code.Unauthenticated` response refreshes once and retries, marked with an `X-Retry` header to prevent loops; if the refresh fails it calls `redirectOnAuthFailure()`.

**Tokens it manages:**
- **Access token** — short-lived JWT kept in `localStorage` via `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`, with an expiry timestamp). The interceptor pre-emptively refreshes when it's within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry (`connect.ts:140`), specifically so public endpoints like `ListMemos` don't silently return guest-scoped data.
- **Refresh token** — never touched by JS; it rides as a cookie, which is why every transport uses `fetchWithCredentials` (`credentials: "include"`, `connect.ts:57`). Refresh goes through `AuthService.refreshToken` on a *separate* interceptor-free transport (`connect.ts:64-72`) to avoid recursion, and concurrent refreshes are deduplicated by `tokenRefreshManager` (`:30-51`).

**Backend validation** — the `server/auth` package (`server/auth/authenticator.go`): `AuthenticateByAccessTokenV2` (:41) verifies the JWT, `AuthenticateByRefreshToken` (:61) checks the refresh token against the DB, and `AuthenticateByPAT` (:102) handles prefixed, hashed Personal Access Tokens for programmatic clients; `resolveBearer` (:149) dispatches between JWT and PAT. It's wired into the Connect path by `NewAuthInterceptor` (`server/router/api/v1/connect_interceptors.go`) and into the REST gateway by `gatewayAuthMiddleware` (`server/router/api/v1/v1.go:96`); the SSE stream authenticates with the same Bearer header (`server/router/api/v1/sse_handler.go:34-37`).
