**memo_relation, attachment, memo, memo_share** (plus the comment memos' own rows in `memo` / `memo_relation` / `attachment`)

Breakdown:

- **memo_relation** — deleted twice by explicit code in `Store.DeleteMemo`: rows where the memo is the source (`store/memo.go:142`) and where it's the target (`store/memo.go:145`).
- **attachment** — attachments linked to the memo are listed and deleted individually (`store/memo.go:149-157`), each via `Store.DeleteAttachment` (`store/attachment.go:132`), which also removes the underlying blob from local/S3 storage before the row.
- **memo** — the row itself, via the driver's `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237`). Comment memos are deleted first by the API handler, each recursing through the same path (`server/router/api/v1/memo_service.go:567-577`).
- **memo_share** — not touched by any Go code; it's removed by a DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` declared in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Worth flagging: the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade is not enforced and `memo_share` rows are left orphaned.

**Not affected:** `reaction` — the delete handler only *reads* reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`), and the `reaction` table has no FK to `memo` (`store/migration/sqlite/LATEST.sql:93-99`), so reaction rows survive memo deletion.
