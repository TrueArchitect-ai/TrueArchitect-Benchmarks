**`/bench/repo/web/src/connect.ts` (with token storage in `/bench/repo/web/src/auth-state.ts`); short-lived JWT access tokens + a long-lived refresh-token cookie (`memos_refresh`), plus `memos_pat_` personal access tokens for programmatic clients; `/bench/repo/server/auth`**

**Interceptor.** `authInterceptor` at `web/src/connect.ts:155` is attached to the shared Connect transport (line 189). Per request it resolves a token via `getRequestToken()` (line 124) and sets `Authorization: Bearer <token>`; it proactively refreshes when the access token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry, and reactively refreshes once on a `Code.Unauthenticated` response, replaying the request with an `X-Retry` marker to prevent loops, then `redirectOnAuthFailure()` if that fails. Refresh itself goes through `refreshAuthClient` on a separate interceptor-free transport (line 72) calling `AuthService.RefreshToken`, deduplicated by `tokenRefreshManager` (line 30). All transports use `credentials: "include"` so the HttpOnly refresh cookie rides along.

**Token kinds** (`/bench/repo/server/auth/token.go`): JWT **access tokens**, 15 min, audience `user.access-token` (lines 37-40); JWT **refresh tokens**, 30 days, audience `user.refresh-token`, delivered in the `memos_refresh` cookie (lines 43-49); **personal access tokens** prefixed `memos_pat_` (line 52). The frontend only holds the access token in memory/storage (`auth-state.ts:52,78`).
