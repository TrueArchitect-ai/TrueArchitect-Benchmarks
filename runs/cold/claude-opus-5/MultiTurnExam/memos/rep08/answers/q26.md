**memo, memo_relation, attachment** — plus **memo_share** via declared FK cascade (not enforced on SQLite).

Breakdown, following `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) → `Store.DeleteMemo` (`store/memo.go:140`):

| Table | How |
|---|---|
| `memo_relation` | Explicit cleanup, both directions: `MemoID` then `RelatedMemoID` (`store/memo.go:142`, `:145`) |
| `attachment` | Explicit: listed by `MemoID`, deleted one at a time via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying blob/file (`store/attachment.go:141`) |
| `memo` | The memo row itself (`store/memo.go:158`), plus one row per child comment memo — the API layer finds relations of type `MemoRelationComment` and recursively calls `Store.DeleteMemo` on each (`memo_service.go:567-577`), so each comment repeats the whole cleanup |
| `memo_share` | Declared `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`) — there is no explicit delete-by-memo call in the delete path |

Two caveats worth flagging:

- **The `memo_share` cascade does not fire on SQLite.** The connection is opened with `_pragma=foreign_keys(0)` at `store/db/sqlite/sqlite.go:53`, so SQLite ignores the FK entirely and share rows are left orphaned; Postgres and MySQL do enforce it. That's a real behavioral divergence between dialects.
- **`reaction` rows are not deleted.** `DeleteMemo` reads them (`memo_service.go:545`) only to build the webhook payload. Because `reaction.content_id` stores the memo *resource name* as a string rather than an FK (`store/reaction.go:7`), there's no cascade either — reactions for a deleted memo persist.
