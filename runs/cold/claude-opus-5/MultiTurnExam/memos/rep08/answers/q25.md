**CEL (Common Expression Language) via `github.com/google/cel-go` — internal/filter/ (engine at `internal/filter/engine.go`)**

**Mechanism:** the filter string is compiled by CEL into an AST, lowered into a dialect-agnostic condition tree (IR), and then rendered per dialect into a parameterized SQL `WHERE` fragment plus args, which each driver appends to its query.

The stages:

- **Compile** — `Engine.Compile` (`internal/filter/engine.go:47`) runs `env.Compile(filter)` on a `cel.Env` built from a `Schema`, then converts the AST via `cel.AstToParsedExpr`. `nowFunc` is frozen once per compile so a single filter observes one instant.
- **IR** — the parsed expression becomes a condition tree (`internal/filter/ir.go`, `parser.go`): `LogicalCondition`, `NotCondition`, `FieldPredicateCondition`, `ComparisonCondition`, etc.
- **Schema** — `internal/filter/schema.go` declares the allowed fields and, per field, a `map[DialectName]string` of SQL expression templates. Dialect constants are `DialectSQLite`/`DialectMySQL`/`DialectPostgres` (lines 14-16). That map is where dialect divergence is encoded — e.g. creator name is `('users/' || %s)` on SQLite/Postgres but `CONCAT('users/', %s)` on MySQL (lines 104-107), and timestamps use `UNIX_TIMESTAMP(%s)` only on MySQL (line 132).
- **Render** — `internal/filter/render.go` walks the tree emitting SQL with placeholders offset by `PlaceholderOffset` (so it composes with args already accumulated), and collapses results to `"1 = 0"` when unsatisfiable or `""` when trivially true.
- **Driver hookup** — `filter.AppendConditions` (`internal/filter/helpers.go:9`) calls `CompileToStatement` and pushes each non-empty fragment into the query's `where`/`args`. Call sites: `store/db/sqlite/memo.go:57-61`, plus the Postgres and MySQL equivalents in `store/db/*/memo.go`. `server/router/api/v1/user_service_filter.go` uses the same engine for user filters.

`internal/filter/README.md` and `MAINTENANCE.md` document the supported grammar and how to add fields.
