**No.** `store/db/db.go` is the only place in the entire repository that constructs the MySQL driver.

Evidence:

1. **Import graph.** `grep -rn "usememos/memos/store/db/mysql"` across all `*.go` files returns exactly one hit: `store/db/db.go:8`. No other file — production or test — imports the package, so no other file can call into it.
2. **Constructor callers.** `mysql.NewDB(` appears once, at `store/db/db.go:22`, inside the `case "mysql":` branch of the `switch profile.Driver` in `NewDBDriver` (`store/db/db.go:14-31`). The only other `NewDB` call sites outside the factory are `sqlite.NewDB` in two tests (`store/demo_seed_test.go:24`, `store/deployment_config_test.go:416`) — SQLite, not MySQL.
3. **No struct-literal back door.** `store/db/mysql/mysql.go:20` is the sole exported constructor, and there is no `&mysql.DB{...}` or similar composite literal anywhere outside the package.

Two near-misses worth ruling out, since they look like counterexamples in a grep:

- `store/test/containers.go:16,20` imports `github.com/go-sql-driver/mysql` and `testcontainers-go/modules/mysql` — the upstream SQL driver and the testcontainers module, not the repo's `store/db/mysql` package. Test suites reach the driver through the factory (`store/test/store.go:88` selects by driver name).
- `store/db/mysql/mysql.go:7` and `store/db/mysql/auth_config.go:7` import `go-sql-driver/mysql` — that's the package importing its own upstream dependency, i.e. inside the driver, not outside it.
