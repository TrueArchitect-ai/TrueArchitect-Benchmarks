Two enforcement shapes recur: a *post-fetch permission check* on a single memo, and a *pre-query filter* that narrows `FindMemo.VisibilityList` so invisible rows are never read.

Two things worth flagging, since they're policy divergences rather than copies of one rule:

- **The file server is the only surface with a share-token bypass.** `checkAttachmentPermission` (`server/router/fileserver/fileserver.go:684-689`) accepts a `?share_token=` query param and, if it resolves to a non-expired `MemoShare` for that exact memo, grants access to a private/protected memo's attachment. Nothing in the v1 API does this.
- **`AllowAnonymous` is mixed into the check** at `server/router/fileserver/fileserver.go:677` — on an instance with no `InstanceURL`, even `PUBLIC` memos' attachments require an authenticated viewer. The API's `checkMemoReadAccess` has no equivalent clause; anonymous access there is gated upstream by the authorizer.

The three notification predicates are near-duplicates of each other (`user_service_notifications.go:309` and `notification/email.go:313` are the same function name and logic in two packages), which is worth noting if this list is being used to plan a consolidation.
