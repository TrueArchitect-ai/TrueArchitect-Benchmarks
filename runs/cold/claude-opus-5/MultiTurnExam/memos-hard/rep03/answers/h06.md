The last three of those funnel through `dispatchMemoUpdatedSideEffects` (`server/router/api/v1/memo_update_helpers.go:66`), which calls `DispatchMemoUpdatedWebhook` at line 67 — so attachment and relation edits emit `memos.memo.updated` just like a direct update.

All four `Dispatch*` methods (`server/router/api/v1/memo_service_webhooks.go:14-46`) load the target user's webhooks via `s.Store.GetUserWebhooks` and call `webhook.PostAsync` — at line 71 for the created/updated/deleted trio via the shared `dispatchMemoRelatedWebhook`, and at line 43 for the comment case. `PostAsync` is therefore the single chokepoint: it enqueues onto a 128-slot buffered channel, and four worker goroutines started in `init()` (`internal/webhook/webhook.go:42-55`) drain it into `Post`, which issues the POST through the SSRF-guarded `safeClient`.

The URL is user-configured — it comes from `hook.Url` on the creator's stored webhook list, set through `user_service_webhooks.go` (validated at `:74`, `:161`, `:182`).

One near-miss worth excluding: the webhook CRUD handlers themselves (`CreateUserWebhook`/`UpdateUserWebhook`) call `webhook.ValidateURL`, which performs a DNS resolution but no HTTP request, so they don't belong on the list.
