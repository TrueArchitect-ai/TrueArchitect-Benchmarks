**Explicit Go code** — there is no database-level rule that could do it. Reactions are deleted in two passes inside the `DeleteUser` transaction: reactions *authored by* the user, and reactions *left by others on* the user's memos.

What I checked:

**1. The delete path.** `store.DeleteUser` (`store/user.go:171`) delegates to the per-driver `DeleteUser`, implemented identically in all three drivers: `store/db/sqlite/user_delete.go:29`, `store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`. Everything runs in one `BeginTx`/`Commit` transaction (`store/db/sqlite/user_delete.go:30-53`).

**2. The two reaction deletes**, both called from `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92`):
- `deleteReactionsByContentIDsTx` at line 96 → `DELETE FROM reaction WHERE content_id IN (...)` (`store/db/sqlite/user_delete.go:380-388`), batched 500 at a time. The content IDs come from `memoContentIDsFromRefs` (line 512), which formats them as `"memos/" + memo.UID` — matching how `reaction.content_id` is stored. The memo set is the recursive comment tree rooted at the user's memos (`listDeleteUserMemoTreeRecursive`, line 133). This clears *other people's* reactions on the deleted user's content.
- `deleteReactionsByCreatorTx` at line 102 → `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`). This clears the deleted user's own reactions everywhere, including on memos they don't own.

Same two functions exist at `store/db/mysql/user_delete.go:417,437` and `store/db/postgres/user_delete.go:380,400`, invoked at line 96/102 in each.

**3. Ruled out a DB-level rule.** The `reaction` table has *no* foreign keys in any dialect — `creator_id` and `content_id` are bare `INTEGER`/`TEXT` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (originally `store/migration/*/0.20/00__reaction.sql`). Grepping all migration SQL for a FK touching `reaction` returns nothing. The only `ON DELETE CASCADE` in the schema is on `memo_share.memo_id → memo(id)`. Also note `content_id` is a string like `memos/{uid}`, not a numeric FK, so a cascade wouldn't be expressible anyway — which is why the Go code has to reconstruct those IDs by hand.
