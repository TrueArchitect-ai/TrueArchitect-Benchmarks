```
RSS feed queries (VisibilityList = Public only, two feeds) — server/router/rss/rss.go:90,141
sitemap.xml generation (VisibilityList = Public only) — server/router/frontend/frontend.go:150
```

Two patterns are worth separating. Sites that **filter at query time** pin `FindMemo.VisibilityList` so the SQL never returns invisible rows (`store/db/sqlite/memo.go:96` and peers translate it to a `visibility IN (...)` clause): `ListMemos`, user stats, RSS, sitemap. Sites that **gate after fetch** load the memo and then compare `memo.Visibility` against the caller: `checkMemoReadAccess`, reactions, attachments, comments, fileserver.

Two related-but-adjacent checks I did not count as visibility enforcement: `server/notification/email.go:313-316` and `server/router/api/v1/user_service_notifications.go:309-312` use visibility to decide how much memo content to include in outbound notification emails (redaction, not access control), and `server/router/api/v1/memo_mention_helpers.go:62-84` uses it to decide whether a mentioned user gets notified.

One asymmetry stands out in the fileserver path: `checkAttachmentPermission` accepts a `share_token` query parameter that bypasses the visibility check entirely for private and protected memos (`server/router/fileserver/fileserver.go:686-692`), whereas the API-side attachment checks have no equivalent fallback.
