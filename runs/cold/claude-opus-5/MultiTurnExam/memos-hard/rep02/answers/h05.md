**Explicit Go code — two separate `DELETE FROM reaction` statements inside the user-deletion transaction, in all three drivers. There is no database-level rule that would do it.**

What I checked:

**1. The delete path.** `Store.DeleteUser` (`store/user.go:171-181`) delegates straight to `s.driver.DeleteUser`. Each driver runs the whole teardown in one transaction and calls `deleteUserTargetsTx`, which removes reactions in two passes (`store/db/mysql/user_delete.go:88-99`, and the identical sequence at `store/db/sqlite/user_delete.go:96,102` and `store/db/postgres/user_delete.go:96,102`):

- `deleteReactionsByContentIDsTx` — reactions *on* the user's memos, i.e. other people's reactions to their content. Content IDs are built as `"memos/"+memo.UID` (`store/db/mysql/user_delete.go:508-514`) from the full memo tree (roots plus `COMMENT`-related descendants, `listDeleteUserMemoTreeIterative`), then deleted with `DELETE FROM reaction WHERE content_id IN (...)` in batches of 500 (`store/db/mysql/user_delete.go:397-405`).
- `deleteReactionsByCreatorTx` — reactions *by* the user on anyone's content: `DELETE FROM reaction WHERE creator_id = ?` (`store/db/mysql/user_delete.go:417-420`).

Both run before the memo rows and the `user` row are deleted, within the same `tx`.

**2. Ruled out a database-level rule.** The `reaction` table carries no foreign key at all — `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` are plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Same in all three dialects: `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:90-98`, `store/migration/mysql/LATEST.sql` (reaction block), and the original `0.20/00__reaction.sql` files. Grepping `FOREIGN KEY|REFERENCES|CASCADE` across all `LATEST.sql` files yields exactly one cascade in each dialect, and it's on `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109`), not on `reaction`. Additionally, `content_id` is a string like `memos/<uid>` rather than a numeric memo id, so an FK cascade wouldn't be expressible there anyway.

**3. Even if a constraint existed, SQLite wouldn't enforce it** — the connection opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), which is consistent with the codebase handling referential cleanup in Go rather than relying on the engine.
