**How I determined it was the SQLite one rather than the Postgres or MySQL sibling** — the call path is interface-dispatched, so the concrete target isn't visible from the call site. I resolved it by following the value that gets bound at startup:

1. **Call site is abstract.** The handler `CreateMemo` calls `s.Store.CreateMemo` (`server/router/api/v1/memo_service.go:115`), which validates the UID and delegates to `s.driver.CreateMemo` (`store/memo.go:109-114`). `s.driver` is typed `store.Driver` (`store/driver.go`) — an interface with three implementations: `store/db/sqlite/memo.go:16`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go`.

2. **The interface value is assigned once, in the factory.** `NewDBDriver` switches on `profile.Driver` and returns `sqlite.NewDB` / `mysql.NewDB` / `postgres.NewDB` (`store/db/db.go:14-28`). That driver is handed to `store.New(dbDriver, instanceProfile)` at `cmd/memos/main.go:63` and never reassigned — grepping for imports of `store/db/mysql` and `store/db/postgres` confirms `store/db/db.go` is their only importer, so no other construction site exists.

3. **The default value of `profile.Driver` is `"sqlite"`.** Set twice in the CLI: `viper.SetDefault("driver", "sqlite")` (`cmd/memos/main.go:122`) and the flag default `rootCmd.PersistentFlags().String("driver", "sqlite", ...)` (`cmd/memos/main.go:130`), bound together at `cmd/memos/main.go:151`. The profile is populated from `viper.GetString("driver")` at `cmd/memos/main.go:43`. `Profile.Validate` (`internal/profile/profile.go:70`) defaults the data dir but doesn't alter `Driver`, so with no flags/env the switch takes `case "sqlite"`.

So on a default install the chain is: `CreateMemo` handler → `Store.CreateMemo` → `Driver.CreateMemo` (interface) → `(*sqlite.DB).CreateMemo`. The Postgres and MySQL `CreateMemo` methods are compiled in but unreachable unless `--driver` (or the corresponding env/config value) says otherwise.
