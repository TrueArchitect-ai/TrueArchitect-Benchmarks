**Premise correction: neither. There is no message broker in this codebase and no queue is declared anywhere.** A case-insensitive grep for `nats|rabbit|amqp|kafka|pubsub|sqs` across all Go sources, `go.mod`, and YAML config returns zero hits — no client library is imported, no connection is configured, no exchange/subject/queue is declared.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool, all inside `internal/webhook/webhook.go`.**

- **The "queue"** is a package-level channel holding 128 payloads: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`). That declaration is the closest analogue to a queue declaration — it lives in a `var` block, not in any broker setup.
- **The workers** are four goroutines started in `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post` for every payload, logging a warning on failure. They start when the package is first loaded, not from any explicit server wiring.
- **Producing** goes through `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning — there is no persistence, retry, dead-letter, or redelivery. Callers are the memo webhook dispatchers at `server/router/api/v1/memo_service_webhooks.go:43,71`.
- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`), which marshals the JSON body, optionally signs it with Standard Webhooks HMAC-SHA256 headers, and issues `safeClient.Do(req)` (line 152) through the SSRF-guarded transport.

Practical consequences of it being a channel rather than a broker: the queue is per-process (nothing is shared across replicas), it is entirely in memory (a restart or crash loses whatever is buffered), delivery is at-most-once with no retry on failure, and concurrency is capped at exactly four in-flight deliveries per instance.
