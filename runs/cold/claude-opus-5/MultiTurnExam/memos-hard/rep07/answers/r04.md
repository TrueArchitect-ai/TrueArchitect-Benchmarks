**Premise correction: neither. There is no message broker in this repository at all — no NATS, no RabbitMQ, and no AMQP/Kafka/SQS/PubSub client. A case-insensitive search for all of those terms across the Go sources, `go.mod`, and YAML config returns zero hits. Consequently there is no queue declaration to point to.**

**Actual mechanism — an in-process buffered Go channel with a fixed worker pool, all in `internal/webhook/webhook.go`:**

- **The "queue"** is a package-level channel: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` at `internal/webhook/webhook.go:39`. Capacity 128, in-memory, per-process.
- **The "workers"** are 4 goroutines started in the package `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure (`:46-51`). They live for the life of the process; there is no shutdown path that drains or stops them.
- **The "producer"** is `PostAsync` (`internal/webhook/webhook.go:184-196`). It's a non-blocking enqueue: a `select` with a `default` branch that **drops the payload and logs a warning** when the buffer is full (`:189-195`). So there's no backpressure onto the RPC handler, and no persistence, retry, redelivery, or dead-letter handling — a dropped webhook is simply lost, as is anything still buffered when the process exits.
- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`), which marshals the payload, adds Standard Webhooks HMAC headers, and sends via the SSRF-guarded `safeClient` (`:32-37`).
- **Callers** are the memo RPC handlers, via `webhook.PostAsync` at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

Two design consequences worth noting: because the queue is process-local, a multi-instance deployment gives each instance its own independent buffer and worker pool; and because `init()` starts the workers, they exist even in tests and in any binary that imports the package.
