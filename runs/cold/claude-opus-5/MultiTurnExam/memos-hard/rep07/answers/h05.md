**Explicit Go code — an in-transaction `DELETE FROM reaction WHERE creator_id = ?` issued by each driver's `DeleteUser`; there is no FK or cascade on the `reaction` table.**

What I checked:

**1. The Go delete path.** `store.DeleteUser` (`store/user.go:171-181`) just delegates to `s.driver.DeleteUser`. Each driver implements it in `user_delete.go`, running everything in one transaction (`store/db/sqlite/user_delete.go:29-59`). The ordered cleanup list `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`) removes reactions **twice**, deliberately:

- `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-388`) — `DELETE FROM reaction WHERE content_id IN (...)`, deleting *everyone's* reactions on the deleted user's memos. The content IDs are built as `"memos/"+memo.UID` (`store/db/sqlite/user_delete.go:512-518`) from a recursive memo tree that also picks up comment descendants (`:133-166`).
- `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`) — `DELETE FROM reaction WHERE creator_id = ?`, deleting the user's own reactions on *other people's* memos.

**2. All three drivers do the same thing** — identical pair of statements at `store/db/postgres/user_delete.go:383` and `:401`, and `store/db/mysql/user_delete.go:420` and `:438`.

**3. The schema has no database-level rule.** `CREATE TABLE reaction` declares `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`, no `ON DELETE CASCADE`, in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (originals in `store/migration/*/0.20/00__reaction.sql`). For contrast, the adjacent `memo_share` table *does* carry `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`) — so the absence on `reaction` is a real difference, not an artifact of how the schema is written.
