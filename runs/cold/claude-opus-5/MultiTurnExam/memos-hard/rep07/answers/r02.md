**Premise correction: there is no per-user API rate-limiting middleware in this repository — it does not exist, so there is no registration site and no request limits to report.**

Evidence:

- A case-insensitive search across all Go sources and `go.mod` for `ratelimit`, `rate_limit`, `rate limit`, `throttle`, `RateLimiter`, and the usual token-bucket dependency `golang.org/x/time/rate` returns exactly one hit — a comment in documentation prose: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"), which describes a possible future safeguard, not implemented code.
- The Echo middleware stack is registered in `NewServer` and consists of just two entries: `middleware.Recover()` at `server/server.go:51` and `newCORSMiddleware(profile)` at `server/server.go:52`. Echo's built-in `middleware.RateLimiter` is never used.
- The only per-request cross-cutting interception is authentication/authorization: the shared `NewAuthorizer` wired into both the gRPC-Gateway middleware and the Connect interceptor in `RegisterGateway` (`server/router/api/v1/v1.go:64-70` onward). It gates *who* may call, not *how often*.

What does exist, and may be what the question is reaching for, is **concurrency limiting** — a different mechanism, global to the process rather than per user, and it rejects nothing (callers block until a slot frees):

- `thumbnailSemaphore: semaphore.NewWeighted(3)` and `imageProcessingSemaphore: semaphore.NewWeighted(2)` in `NewAPIV1Service` — `server/router/api/v1/v1.go:59-60`.
- `thumbnailSemaphore: semaphore.NewWeighted(maxConcurrentThumbnails)` in the file server — `server/router/fileserver/fileserver.go:116`.

There are also a few unrelated bounded resources that are not rate limits: the 128-slot webhook dispatch queue that *drops* overflow (`internal/webhook/webhook.go:39`, `:189-195`), a per-request content-length cap on memos (`getContentLengthLimit`, used at `server/router/api/v1/memo_service.go:100-106`), and the 1000-item cache ceiling in `store/store.go:43`.
