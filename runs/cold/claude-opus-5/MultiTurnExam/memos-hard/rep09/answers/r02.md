**Premise correction: there is no per-user API rate-limiting middleware in this repository — it doesn't exist, so it has no registration site and no request limits.**

What I checked:

1. **No rate-limiting code.** A case-insensitive grep for `ratelimit`, `rate_limit`, `rate limit`, `throttle`, `golang.org/x/time/rate`, and `middleware.RateLimiter` across all Go files returns exactly one hit — a comment in an unimplemented-ideas list: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"). That's a TODO-style note, not code.
2. **No dependency.** `go.mod` contains no rate-limiter or `golang.org/x/time` entry.
3. **The actual middleware stack is two entries.** `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`). Nothing else is attached via `echoServer.Use`.
4. **No RPC-layer limiter.** The Connect/gRPC interceptors are `MetadataInterceptor` (`server/router/api/v1/connect_interceptors.go:22`) and `LoggingInterceptor` (`:98`), plus the shared `Authorizer` used by both the Connect interceptor and the gRPC-Gateway middleware (`server/router/api/v1/authz.go:21`, `acl_config.go`). Those handle header translation, logging, and authn/authz — no quota or counter logic.

**The closest existing thing, which is not rate limiting:** three concurrency semaphores that cap simultaneous expensive operations process-wide, not per user, and block rather than reject:

- `thumbnailSemaphore` — `server/router/fileserver/fileserver.go:116` (weight `maxConcurrentThumbnails`)
- `thumbnailSemaphore` — `server/router/api/v1/v1.go:59` (weight 3)
- `imageProcessingSemaphore` — `server/router/api/v1/v1.go:60` (weight 2)

There's also a bounded 128-slot webhook dispatch queue that drops overflow (`internal/webhook/webhook.go:39`, `:189-195`), again a backpressure mechanism rather than a per-user limit.
