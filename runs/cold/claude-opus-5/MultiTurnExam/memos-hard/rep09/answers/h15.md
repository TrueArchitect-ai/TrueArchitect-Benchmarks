Visibility is enforced in **13 distinct sites** across five surfaces (gRPC/Connect API, file server, SSE, RSS, frontend), plus notification gating. Each is independent code — there is no single chokepoint.

**Core API — per-memo read check**
```
checkMemoReadAccess — server/router/api/v1/memo_service.go:39
  (callers: GetMemo memo_service.go:356, parent-memo check :367, ListMemoComments memo_service_comments.go:148)
```

Notes:

- The four "inline re-implementations" plus `checkMemoReadAccess` express the same PUBLIC → open / PROTECTED → any authenticated user / PRIVATE → creator rule, but each is written out separately; only the reaction/attachment variants also grant access to super-users via `isSuperUser` (e.g. `reaction_service.go:38`), whereas `checkMemoReadAccess` does not — an admin cannot read another user's private memo through `GetMemo`.
- `checkMemoReadAccess` additionally enforces an archived-memo rule (creator-only, `memo_service.go:44-53`) on top of visibility.
- Share tokens are a deliberate bypass, honored in two places: `server/router/fileserver/fileserver.go:687-691` (attachment requests carrying `?share_token=`) and `getActiveMemoShare` in `server/router/api/v1/memo_share_service.go:199-208`, which serves a shared memo without any visibility check once the token is valid and unexpired.
- The MCP router (`server/router/mcp/`) contains no visibility logic of its own — it dispatches to the same API v1 handlers (`server/router/mcp/catalog.go:12`), so it inherits enforcement rather than adding a site.
