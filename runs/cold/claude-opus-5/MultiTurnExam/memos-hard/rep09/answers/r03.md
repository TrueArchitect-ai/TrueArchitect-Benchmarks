**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never used at runtime — so there's no schedule to report.**

Two separate parts of the premise fail:

**1. The cron scheduler exists but is dead code.** `internal/scheduler/` is a complete package — `scheduler.go`, `job.go`, `parser.go` (`ParseCronExpression`), `middleware.go` (Recovery/Logging/Timeout), plus a README and `doc.go`. But grepping for imports of `github.com/usememos/memos/internal/scheduler` across the repo returns only its own tests: `internal/scheduler/example_test.go:10` and `internal/scheduler/integration_test.go:13`. No production file constructs a `Scheduler` or registers a `Job`, and nothing in `cmd/memos/main.go` or `server/server.go` references it.

**2. There is no database-cleanup job at all**, cron-scheduled or otherwise. The only background work wired into startup is `Server.startBackgroundRunners` (`server/server.go:153`), which starts exactly one runner: the S3 presign refresher (`server/server.go:162-171`), on a 12-hour ticker, not a cron expression (`server/runner/s3presign/runner.go:27`). The only other runner in the tree, `memopayload.Runner` (`server/runner/memopayload/runner.go`), is never constructed in production.

**What "cleanup" does exist, for completeness** — all of it is event-driven or in-memory, none of it scheduled nightly:

- **Cache expiry**, not database: the in-memory caches run a cleanup loop every 5 minutes (`CleanupInterval` at `store/store.go:42` and `store/cache/cache.go:60`, loop at `store/cache/cache.go:83`).
- **Cascading deletes on user removal**, executed inline in the delete transaction rather than by a job — `store/db/sqlite/user_delete.go` and its MySQL/Postgres twins; the S3/local blob cleanup that follows is in `server/router/api/v1/user_service.go:421-450`.
- **Attachment storage cleanup** triggered by deletes, in `store/attachment.go:171` / `:262`.

So nothing in this codebase sweeps the database on a timer.
