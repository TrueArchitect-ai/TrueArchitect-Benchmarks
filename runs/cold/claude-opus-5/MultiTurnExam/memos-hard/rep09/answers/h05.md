**Explicit Go code — not a database rule; there is no FK or cascade on the `reaction` table.**

Evidence, and what I checked:

**1. The explicit deletes (the actual mechanism).** Each driver's `DeleteUser` runs everything in one transaction (`store/db/mysql/user_delete.go:29-59`) and `deleteUserTargetsTx` issues two separate reaction deletions:
- `deleteReactionsByContentIDsTx` — removes reactions *on* the user's memos (and their comment subtree), keyed by `content_id` of the form `memos/<uid>`: called at `store/db/mysql/user_delete.go:96`, defined at `:417-425`; content IDs built in `memoContentIDsFromRefs` (`:549-555`).
- `deleteReactionsByCreatorTx` — removes reactions the user *made* on anyone's content: called at `store/db/mysql/user_delete.go:102`, defined at `:437-440` (`DELETE FROM reaction WHERE creator_id = ?`).

Both run before the memo/user rows are deleted (`:120`, `:123`), so ordering doesn't rely on any DB behavior.

**2. All three drivers do the same thing** — this isn't MySQL-only: `store/db/sqlite/user_delete.go:96,102` (defs at `:380`, `:400`) and `store/db/postgres/user_delete.go:96,102` (defs at `:380`, `:400`).

**3. The schema rules out a database-level rule.** The `reaction` table declares `creator_id INTEGER NOT NULL` and `content_id` as plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no foreign key, no `ON DELETE CASCADE`: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`.

Grepping `FOREIGN KEY|REFERENCES|ON DELETE|CASCADE|TRIGGER` across all three `LATEST.sql` files returns exactly one match per file, and it's on `memo_share.memo_id`, not `reaction` (`store/migration/sqlite/LATEST.sql:109`, `mysql/LATEST.sql:108`, `postgres/LATEST.sql:108`). So no DB-level cleanup exists for reactions.

Note `content_id` is a string reference (`"memos/" + uid`), which structurally could not carry a foreign key to `memo.id` anyway — hence the explicit content-ID sweep in Go.
