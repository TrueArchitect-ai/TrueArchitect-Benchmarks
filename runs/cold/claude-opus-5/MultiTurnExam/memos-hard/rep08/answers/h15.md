Notes worth flagging:

- **The rules are not uniform.** The API gates treat `PROTECTED` as "any authenticated user" and `PRIVATE` as "creator or superuser" (`memo_service.go:55-66`), while RSS, the sitemap, and stats-for-others reduce to `PUBLIC`-only. The SSE filter is the loosest: `canReceive` returns `true` for `PUBLIC`, `PROTECTED`, *and* the empty visibility string (`sse_hub.go:138`), so only `PRIVATE` events are restricted.
- **The file server has an extra bypass the API path doesn't:** a valid, unexpired `share_token` query param matching the memo grants access to attachments on private/protected memos (`server/router/fileserver/fileserver.go:684-690`). It also requires `s.Profile.AllowAnonymous()` before serving public-memo attachments anonymously (`:677`).
- **`checkMemoReadAccess` is the only shared helper** — the other API gates re-implement essentially the same three-way check inline, which is why the count is this high.
- **Not counted as visibility enforcement**, though they branch on `memo.Visibility`: notification-eligibility logic in `server/notification/email.go:313-316`, `server/router/api/v1/user_service_notifications.go:309-312`, and `server/router/api/v1/memo_mention_helpers.go:62-84` — these decide who gets *notified*, not who may view.
- **MCP is not a separate surface here:** `server/router/mcp/catalog.go:12-14` merely allowlists `MemoService_ListMemos` / `MemoService_GetMemo`, which route through the API v1 handlers above.
