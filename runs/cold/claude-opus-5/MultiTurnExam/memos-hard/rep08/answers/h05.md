**Explicit Go code — two `DELETE FROM reaction` statements per driver, inside the user-deletion transaction. There is no database-level rule that could do it.**

What I checked:

**1. The deletion orchestration.** `DeleteUser` opens a transaction, collects targets, then calls `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:29-58`). That function issues two separate reaction deletes:
- `deleteReactionsByContentIDsTx` (called at `store/db/mysql/user_delete.go:93`, defined at `:380`) — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions *on* the user's memos (including comment descendants). The content IDs are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs` (`store/db/mysql/user_delete.go:~`, the helper near the file's end), matching the `content_id` resource-name format.
- `deleteReactionsByCreatorTx` (called at `:102`, defined at `:400`) — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user left *on other people's* memos.

Both run before `deleteMemosTx` and `deleteUserRowTx`, and the whole set commits atomically (`store/db/mysql/user_delete.go:50-53`).

**2. All three drivers do the same.** Identical call sites and implementations in `store/db/sqlite/user_delete.go:96,102,380,400` and `store/db/postgres/user_delete.go:96,102,380,400`. So the behavior doesn't depend on which backend is selected.

**3. The schema has no cascade for reactions.** In every `LATEST.sql`, the `reaction` table declares `creator_id` as a plain `INTEGER`/`INT NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no foreign key to `user`:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

Grepping each `LATEST.sql` for `REFERENCES|CASCADE|FOREIGN KEY` returns exactly one hit apiece, and it's on `memo_share`, not `reaction`: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). A grep across all versioned migration SQL for reaction-related FK/cascade clauses returns nothing.

So the reaction cleanup is entirely application-level; if those two Go statements were removed, reactions would be orphaned rather than cascaded away.
