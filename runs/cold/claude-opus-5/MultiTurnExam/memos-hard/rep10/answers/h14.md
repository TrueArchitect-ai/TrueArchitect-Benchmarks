There is a third, dormant trigger: `memopayload.Runner.RunOnce` (`runner.go:27`) rebuilds payloads for *all* memos in batches of 100 — but nothing constructs that runner, so it never executes (see the earlier `RunOnce` finding).

**What it extracts.** `RebuildMemoPayload` calls `markdownService.ExtractAll(memo.Content)` and assigns two fields onto `memo.Payload` (`runner.go:85-86`), leaving `Payload.Location` (user-set) untouched:

- **`Payload.Tags`** — `[]string` of `#tag` names, deduplicated preserving original case (`markdown.go:376-378`, `:418`). Tags nested inside a link or image are deliberately skipped (`isTagNodeInLinkOrImage`, `markdown.go:122`).
- **`Payload.Property`** (`storepb.MemoPayload_Property`, defined in `proto/proto/store/memo.proto`):
  - `title` — text of the first H1 heading, only if it's the document's first block child (`markdown.go:384-389`)
  - `has_link` — any `KindLink` node
  - `has_code` — any code block, fenced code block, or inline code span
  - `has_task_list` — any task checkbox
  - `has_incomplete_tasks` — any *unchecked* task checkbox (`markdown.go:392-405`)

All of this happens in a **single AST walk** — that's the point of `ExtractAll` versus the separate `ExtractTags`/`ExtractProperties` methods. `ExtractAll` also collects `Mentions`, but `RebuildMemoPayload` ignores that field; mentions are consumed separately for notifications (`/bench/repo/server/router/api/v1/memo_mention_helpers.go:32`).

**Related but distinct:** the list/preview `snippet` is *not* stored in the payload. It's computed on read at response-conversion time via `getMemoContentSnippet` → `MarkdownService.GenerateSnippet(content, 64)` (`/bench/repo/server/router/api/v1/memo_service_webhooks.go:83-89`, used at `memo_service_converter.go:76` and `:225`).
