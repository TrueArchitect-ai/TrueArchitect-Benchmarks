**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never wired into the running server — so nothing is scheduled at any time.**

Two separate false premises here:

**1. No database-cleanup job exists.** Grepping the backend for `cleanup`, `nightly`, `purge`, and `vacuum` turns up no scheduled maintenance task. Every hit is something else:
- Cache eviction sweeps — `store/cache/cache.go:83` (`cleanupLoop`), configured with `CleanupInterval: 5 * time.Minute` at `store/store.go:42` and `store/cache/cache.go:60`. In-memory only, nothing to do with the database.
- Inline, request-scoped cleanup of attachment blobs during user/memo deletion — `server/router/api/v1/user_service.go:421-450`, `store/attachment.go:171`. These run synchronously inside an RPC, not on a schedule.

**2. The cron scheduler is dead code.** The `internal/scheduler` package exists and is fully featured — a 5-field cron parser (`internal/scheduler/parser.go`), `Job` with validation (`internal/scheduler/job.go`), `Scheduler.Start`/`Stop` (`internal/scheduler/scheduler.go:169`), plus `Recovery`, `Logging`, and `Timeout` middleware (`internal/scheduler/middleware.go`) and a README. But grepping the whole repo for the import path `github.com/usememos/memos/internal/scheduler` yields **zero hits outside the package itself** — only its own tests and `example_test.go`. Nothing constructs a `Scheduler`, registers a `Job`, or calls `Start`.

**What actually runs on a timer in this server** is one background runner, not a cron job: `s3presign.Runner`, which re-signs S3 attachment URLs every 12 hours (`server/runner/s3presign/runner.go:27`), started from `Server.startBackgroundRunners` at `server/server.go:162-171`. It's driven by a plain `time.Ticker` with no wall-clock alignment — the first pass runs at process startup and subsequent passes fall 12 hours after that, so its firing times depend on when the server was last restarted rather than on any fixed hour.
