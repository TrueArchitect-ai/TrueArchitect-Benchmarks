**Premise correction: there is no per-user API rate-limiting middleware in this repository — none is registered, and no request limits exist.** 

What I checked:

- A case-insensitive grep across all Go files and `go.mod` for `ratelimit`, `rate_limit`, "rate limit", `throttl`, `Limiter`, and `golang.org/x/time/rate` returns exactly one hit, and it's an aspirational comment in a doc file: `/bench/repo/internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"). No limiter library is a dependency.
- **Echo middleware chain** (`/bench/repo/server/server.go:51-52`) registers only two entries: `middleware.Recover()` and `newCORSMiddleware(profile)`. Nothing else is `Use`d at the server level.
- **Connect/gRPC interceptor chain** (`/bench/repo/server/router/api/v1/v1.go:133-138`) is four interceptors — `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (defined in `/bench/repo/server/router/api/v1/connect_interceptors.go`). None counts requests or tracks per-user quotas.
- No `429`/`StatusTooManyRequests` is ever returned; no login-attempt counter, lockout, or backoff exists in the auth paths (`/bench/repo/server/router/api/v1/auth_service_session.go`).

**What does exist** — these are resource caps, not rate limits, and none is per-user or time-windowed:

- **Concurrency semaphores** in `APIV1Service` (`/bench/repo/server/router/api/v1/v1.go:59-60`): `thumbnailSemaphore` = 3 concurrent thumbnail generations, `imageProcessingSemaphore` = 2. Exceeding these returns `ResourceExhausted` ("too many image processing requests", `/bench/repo/server/router/api/v1/attachment_service.go:160`). The file server has its own separate limit of 3 (`/bench/repo/server/router/fileserver/fileserver.go:44`, `maxConcurrentThumbnails`).
- **Request body size cap**: `connect.WithReadMaxBytes(maxAPIRequestBytes)` (`/bench/repo/server/router/api/v1/v1.go:141`).
- **Batch-size caps** on individual RPCs, e.g. `maxBatchGetUsers` (`user_service.go:145`), `maxBatchDeleteAttachments` (`attachment_service.go:355`), `maxBatchGetInstanceSettings` (`instance_service.go:78`), `maxBatchGetLinkMetadata` (`memo_service_link_metadata.go:24`).
- **Webhook async queue depth** of 128 with 4 workers (`/bench/repo/internal/webhook/webhook.go:39-55`), which drops overflow rather than throttling callers.

If per-user rate limiting is needed, it would have to be added — the natural insertion points are a new Connect interceptor in the chain at `v1.go:133-138` (which has authenticated-user context available) or an Echo middleware at `server.go:51`.
