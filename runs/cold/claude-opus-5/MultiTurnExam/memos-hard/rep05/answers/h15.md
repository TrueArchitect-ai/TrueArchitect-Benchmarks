Two enforcement *shapes* are in play, which is why the count is high:

- **Post-fetch gates** — load the memo, then reject: `checkMemoReadAccess` (`memo_service.go:39-68`) denies archived memos to non-creators, requires auth for anything non-`Public`, and 403s on `Private` unless the caller is the creator. The attachment, comment, and reaction gates repeat this shape independently rather than calling the shared helper.
- **Query-scoping** — never fetch what the caller can't see: anonymous callers get `VisibilityList = [Public]`; authenticated callers get the CEL filter `creator_id == N || visibility in ["PUBLIC", "PROTECTED"]` (`memo_service.go:222`, `memo_service_converter.go:186`, `memo_relation_service.go:111`, `user_service_stats.go:87`).

Worth noting: the two `canViewerAccessMemo` functions (`user_service_notifications.go:302` and `notification/email.go:306`) are near-duplicate implementations in different packages — one uses `isSuperUser(viewer)`, the other compares `viewer.Role == store.RoleAdmin` directly. Also, the file server is the only surface that honors a `share_token` query param as an alternative to visibility (`fileserver.go:~681-688`), checked against `store.GetMemoShare` and expiry.

MCP exposes `MemoService_ListMemos` (`server/router/mcp/catalog.go:12`) but adds no visibility logic of its own — it routes through the API v1 handler, inheriting its scoping.
