**Explicit Go code — every driver issues its own `DELETE FROM reaction` statements inside the delete-user transaction. There is no database-level cascade for reactions.**

What I checked:

**1. The delete path.** `Store.DeleteUser` (`store/user.go:171-181`) delegates to the driver's `DeleteUser`. Each driver implements it as a single transaction: `store/db/mysql/user_delete.go:29`, `store/db/postgres/user_delete.go`, `store/db/sqlite/user_delete.go`.

**2. Explicit reaction deletion — two separate sweeps.** `deleteUserTargetsTx` calls both, before the memos and the user row are removed:
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`store/db/mysql/user_delete.go:417-425`, called at `:96`). This removes reactions *other people left on the deleted user's memos*; the content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + uid` strings (`mysql/user_delete.go:549-555`) over the user's full memo tree including comment descendants (`:133-181`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/mysql/user_delete.go:437-440`, called at `:102`). This removes *the deleted user's own reactions on anyone's content* — the direct answer to the question.

Identical logic exists in the other two drivers: `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/sqlite/user_delete.go:96,102,380,400`.

**3. Ruled out a database-level rule.** The `reaction` table carries no foreign key on `creator_id` in any dialect — it's just `creator_id INTEGER NOT NULL` with a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:90-98`, `store/migration/mysql/LATEST.sql:90-98`. Same at the table's introduction, `store/migration/sqlite/0.20/00__reaction.sql:2-8`. A repo-wide grep for `FOREIGN KEY`/`ON DELETE` across `store/migration/` returns hits only for `memo_share`, `memo_relation`, and the legacy SQLite 0.3–0.5 tables — never `reaction`. (The old SQLite FK-cascade era at `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql` predates the reaction table entirely.)

So the explicit Go code is load-bearing: without it, reactions would be orphaned rows, since nothing in the schema would clean them up.
