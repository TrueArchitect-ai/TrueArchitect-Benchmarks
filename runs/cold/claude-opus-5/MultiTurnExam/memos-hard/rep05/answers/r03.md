**Premise correction: there is no nightly database-cleanup job, and no cron expression is scheduled anywhere in the running server.** Nothing in this codebase runs on a wall-clock time (there is no "2am"-style schedule to report).

Two separate corrections:

**1. The cron scheduler exists but is never used in production.** `internal/scheduler/` is a complete, self-contained package — cron-expression parser (`internal/scheduler/parser.go`), job type (`job.go`), middleware chain (`middleware.go`), and `Scheduler` with `Register`/`Start`/`Stop` (`scheduler.go`) — with its own README and tests. But grepping the repo for imports of `github.com/usememos/memos/internal/scheduler` outside the package itself returns only two hits, both tests: `internal/scheduler/integration_test.go:13` and `internal/scheduler/example_test.go:10`. No server, command, or runner ever constructs or starts it. It's currently unwired library code.

**2. The only recurring background work is an interval ticker, not a cron job, and it isn't cleanup.** `server.startBackgroundRunners` (`server/server.go:153-174`) starts exactly one recurring runner: the S3 presign refresher (`server/runner/s3presign/runner.go`). It runs once synchronously at startup (`server/server.go:163`), then every **12 hours** via `time.NewTicker(runnerInterval)` where `runnerInterval = time.Hour * 12` (`server/runner/s3presign/runner.go:27,29-41`). Because it's a relative-interval ticker anchored to process start, its fire times drift with restarts — it has no fixed time of day. Its job is refreshing presigned S3 URLs before expiry, not deleting or compacting anything.

What cleanup does exist happens **inline, on demand** — never on a timer:

- Memo deletion cascades relations and attachments at request time (`server/router/api/v1/memo_service.go:579`).
- User deletion removes reactions, attachments, inboxes, settings, identities, memos, and shares in one transaction (`store/db/{sqlite,mysql,postgres}/user_delete.go`), with S3 object cleanup following in `server/router/api/v1/user_service.go:421-451`.
- The in-memory cache has a 5-minute `CleanupInterval` sweep (`store/store.go:42`, loop at `store/cache/cache.go:83,118`) — that's expiring cache entries in RAM, not touching the database.

There's also a dormant batch runner, `memopayload.Runner.RunOnce` (`server/runner/memopayload/runner.go:27`), which would rebuild all memo payloads — but `NewRunner` has no callers, so it never executes either.
