The last three of those funnel through the shared helper `dispatchMemoUpdatedSideEffects` (`server/router/api/v1/memo_update_helpers.go:66-78`), which calls `DispatchMemoUpdatedWebhook` — so editing a memo, swapping its attachments, or rewiring its relations all emit `memos.memo.updated`.

**Convergence.** All four `Dispatch*Webhook` methods (`server/router/api/v1/memo_service_webhooks.go:15-46`) load the target user's webhooks via `s.Store.GetUserWebhooks` and call `webhook.PostAsync` (`memo_service_webhooks.go:43` for comments, `:71` for the shared memo path). `PostAsync` (`internal/webhook/webhook.go:184`) only enqueues onto a bounded channel; the actual delivery for every one of these paths is performed by **`webhook.Post`** at `internal/webhook/webhook.go:120`, invoked by the four worker goroutines at `webhook.go:46`. The URL is the user-configured `hook.Url` (`memo_service_webhooks.go:41,67`), stored per-user and managed by `server/router/api/v1/user_service_webhooks.go`.

Two clarifications worth stating:

- **`GetLinkMetadata` / `BatchGetLinkMetadata`** (`server/router/api/v1/memo_service_link_metadata.go:14,19`) also make outbound HTTP to a caller-supplied URL, via `getLinkMetadata` → `fetchHTMLMeta` → `httpgetter.GetHTMLMeta` (`memo_service.go:28`, `internal/httpgetter/html_meta.go`). If you count "user-configured URL" broadly, these qualify — but they are a *separate* path with its own SSRF checks, and they do not converge on `webhook.Post`. The single convergence point exists only for the webhook family above.

- The webhook-management RPCs in `server/router/api/v1/user_service_webhooks.go` (lines 74, 161, 182) perform DNS resolution during `webhook.ValidateURL`, not an HTTP request, so they aren't part of this set.
