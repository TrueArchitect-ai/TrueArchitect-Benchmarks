**Premise correction: there is no rate-limiting middleware in this repository — per-user or otherwise.** Searching all Go, TypeScript, proto, and Markdown sources (excluding `node_modules`) for `rate limit`, `ratelimit`, `throttle`, `429`, `too many requests`, `golang.org/x/time/rate`, and `tollbooth` returns zero hits. `go.mod` pulls in no rate-limiting dependency, and Echo's `middleware.RateLimiter` is never used.

What the server actually registers as middleware is short — `server/server.go:51-52`:

- `middleware.Recover()` — panic recovery
- `newCORSMiddleware(profile)` — CORS

Plus auth interceptors wired separately for the gRPC-Gateway and Connect handlers in `server/router/api/v1/v1.go` (`RegisterGateway`, using `NewAuthorizer` at `v1.go:68`). Those authenticate and authorize; they don't count or limit requests.

The only request-volume controls that exist are **concurrency limiters, not rate limits** — they bound how many operations run simultaneously, with no per-user accounting, no time window, and no rejection (callers block until a slot frees):

- `thumbnailSemaphore` — `semaphore.NewWeighted(3)` in the API service (`server/router/api/v1/v1.go:59`) and `semaphore.NewWeighted(maxConcurrentThumbnails)` (= 3) in the file server (`server/router/fileserver/fileserver.go:116`, constant at `fileserver.go:46`), acquired at `fileserver.go:448`.
- `imageProcessingSemaphore` — `semaphore.NewWeighted(2)` (`server/router/api/v1/v1.go:60`), acquired at `server/router/api/v1/attachment_service_image.go:71`.

Both are process-global memory-exhaustion guards on image work, unrelated to API abuse prevention.

Adjacent bounded resources, for completeness: the webhook dispatch queue caps at 128 pending payloads with 4 workers and drops overflow (`internal/webhook/webhook.go:39-55`), SSE broadcasts drop events for clients with full buffers (`server/router/api/v1/sse_hub.go:127-131`), `BatchGetLinkMetadata` caps URLs per request (`server/router/api/v1/memo_service_link_metadata.go:23-25`), and memo content length is capped per instance setting (`server/router/api/v1/memo_service.go:101-107`). None of these throttle a user's request rate.

If you're looking for rate limiting in a Memos deployment, it would have to come from a reverse proxy in front of the binary (nginx, Caddy, Cloudflare), not from the application.
