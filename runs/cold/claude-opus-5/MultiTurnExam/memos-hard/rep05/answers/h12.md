**How I determined it's the SQLite one, not MySQL or Postgres.** The call site is polymorphic, so reading `store/memo.go` alone can't answer it:

1. `Store.CreateMemo` (`store/memo.go:109-114`) validates the UID and then calls `s.driver.CreateMemo(ctx, create)` — an interface method declared at `store/driver.go:29`. Three types implement it: `store/db/sqlite/memo.go:16`, `store/db/mysql/memo.go`, `store/db/postgres/memo.go`. Nothing at this layer picks one.

2. The implementation is chosen at startup by `db.NewDBDriver`, which switches on `profile.Driver` (`store/db/db.go:14-27`): `"sqlite"` → `sqlite.NewDB`, `"mysql"` → `mysql.NewDB`, `"postgres"` → `postgres.NewDB`. It's called once in `cmd/memos/main.go:57` and the result is handed to the `Store`, so the `s.driver` field is fixed for the process lifetime.

3. `profile.Driver` comes from `viper.GetString("driver")` (`cmd/memos/main.go:43`). With no flags set, that resolves to the default `"sqlite"` — declared twice, as a viper default (`cmd/memos/main.go:122`) and as the `--driver` flag default (`cmd/memos/main.go:130`, bound at `:151`). So a default install takes the `case "sqlite"` branch.

4. Corroborating: `Profile.Validate` auto-derives the DSN only for SQLite when none is given — `memos_prod.db` under the data dir (`internal/profile/profile.go:110-117`) — which is what makes a flagless install work at all. MySQL and Postgres have no such fallback and would fail without an explicit `--dsn`.

Same reasoning applies to `mysql.NewDB` / `postgres.NewDB` being unreachable in that configuration; they're live only when `--driver`/`MEMOS_DRIVER` says otherwise.
