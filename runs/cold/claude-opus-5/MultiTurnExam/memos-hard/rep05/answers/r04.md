**Premise correction: neither. There is no message broker in this repository at all.** A case-insensitive search across all Go sources, `go.mod`, and `go.sum` for `nats`, `rabbitmq`, `amqp`, `kafka`, `streadway`, and `pubsub` returns zero hits — no broker client is even a dependency. Consequently there is no queue *declared* in the AMQP/JetStream sense: no exchange, no binding, no durable stream, nothing that survives a process restart.

**Actual mechanism — an in-process buffered Go channel:**

- **The "queue"** is a package-level channel in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, holding pointers to in-memory payload structs. It lives in the server process's heap.

- **The workers** are 4 goroutines started in the package's `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post` for every payload, logging a warning on failure. There are no retries, no acknowledgements, and no dead-letter path — a failed delivery is logged and dropped.

- **Producing** goes through `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send: if the buffer is full, the payload is **discarded** with a `"Dropped webhook dispatch because the async queue is full"` warning. So backpressure is handled by shedding load rather than blocking the request or persisting the event.

- **Delivery** is `Post` (`internal/webhook/webhook.go:120`), issuing the HTTP POST via the SSRF-guarded shared client at `webhook.go:152`.

- **Producers** are the memo lifecycle dispatchers in `server/router/api/v1/memo_service_webhooks.go:43,71`, fed by `CreateMemo`, `UpdateMemo`, `DeleteMemo`, `CreateMemoComment`, `SetMemoAttachments`, and `SetMemoRelations`.

Two practical consequences of this design: webhook events are **not durable** — anything still queued when the process exits is lost, and there's no shutdown drain (the workers aren't tracked by the server's `backgroundRunnerWG` in `server/server.go`) — and delivery is **at-most-once**, since neither a full buffer nor an HTTP failure triggers redelivery. That's consistent with Memos' single-binary, no-external-services design (same reason there's no Redis).
