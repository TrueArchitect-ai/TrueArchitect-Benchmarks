Details per hop:

- **Route registration** — `fileGroup := echoServer.Group("/file")` then `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` (`server/router/fileserver/fileserver.go:122-125`). The service is constructed and mounted at server startup: `server/server.go:81-82`.

- **How the browser knows this URL** — `convertUserFromStore` rewrites a stored base64 data-URI avatar into the path `/file/{user.Name}/avatar` before sending the user proto to the client (`server/router/api/v1/user_service_converters.go:31-40`), specifically to keep raw base64 out of API responses. A non-base64 `AvatarURL` is passed through as-is (an external URL, no server hop).

- **`serveUserAvatar`** (`fileserver.go:168-210`) — on a private instance (`!s.Profile.AllowAnonymous()`) it first requires a viewer via `s.getCurrentUser` and 401s otherwise (`:170-182`); reads the `:identifier` path param; 404s if the user is missing or `AvatarURL` is empty; decodes the stored data URI with `parseDataURI` (`fileserver.go:737`, regex-based); rejects anything outside `avatarAllowedTypes` — png/jpeg/jpg/gif/webp (`fileserver.go:75-81`, checked at `:201`); then sets security headers, `Content-Type`, `Cache-Control: public, max-age=3600` (`fileserver.go:49`) and writes the bytes with `c.Blob`.

- **`getUserByUsername`** (`fileserver.go:715-717`) — a one-line adapter issuing `store.FindUser{Username: &identifier}`. Note the lookup is by *username*, while the URL the converter emits is `/file/users/{username}/avatar` via `BuildUserName`.

- **`Store.GetUser`** (`store/user.go:148-169`) — consults `userCache` only when finding by ID; a username lookup always falls through to `ListUsers`, then populates the cache keyed by the resolved ID.

- **`Store.ListUsers`** (`store/user.go:136-146`) — delegates to `s.driver` and warms the cache for each row.

- **Driver `ListUsers`** — dialect-specific SQL against the `user` table, e.g. `store/db/sqlite/user.go:88` (with `store/db/mysql/user.go` and `store/db/postgres/user.go` mirroring it), selected at runtime by `db.NewDBDriver` (`store/db/db.go:14`). The avatar bytes live in the `user.avatar_url` column as a data URI — there is no separate blob table or filesystem path for avatars.

One thing worth noting: the `GetUserAvatar` gRPC method appears in the public-access allowlist (`server/router/api/v1/acl_config.go:25`), but no such handler is implemented in `server/router/api/v1/` — the HTTP `/file` route above is the live path.
