The browser gets the URL `/file/users/{username}/avatar` from the user API (`convertUserToProto` rewrites a base64 data-URI avatar into that path — `server/router/api/v1/user_service_converters.go:31-40`), then requests it. Hops:

What happens at each stage:

- **Route** — registered in `RegisterRoutes` (`fileserver.go:121-125`), wired into the Echo server at `server/server.go:81-82` via `NewFileServerService`.
- **`serveUserAvatar`** (`fileserver.go:168-210`) — if the instance is private (`!s.Profile.AllowAnonymous()`) it first requires a viewer via `getCurrentUser` and returns 401 otherwise (`fileserver.go:173-181`); otherwise avatars are public. Then it reads `:identifier`, fetches the user, 404s if the user is missing or `AvatarURL` is empty, decodes the stored value with `parseDataURI` (`fileserver.go:737`), rejects any MIME type not in `avatarAllowedTypes` (`fileserver.go:75`, 400), sets security + cache headers, and writes the bytes with `c.Blob`.
- **`getUserByUsername`** (`fileserver.go:715-717`) — a one-line adapter calling `Store.GetUser` with `&store.FindUser{Username: &identifier}`.
- **`Store.GetUser`** (`store/user.go:148`) — the memory cache is only consulted when the lookup is by `ID`, so a username lookup always falls through to `ListUsers`; the result is then written into `userCache` keyed by ID.
- **`Store.ListUsers`** (`store/user.go:136`) — delegates to the driver and populates the cache.
- **Driver** (`store/driver.go:47`) — dialect implementation selected by `db.NewDBDriver` (`store/db/db.go:14`). SQLite's `ListUsers` builds `username = ?` into the WHERE clause (`store/db/sqlite/user.go:120-125` region) and selects `avatar_url` among the columns, scanning it into `store.User.AvatarURL`. Postgres and MySQL have equivalent implementations in `store/db/postgres/user.go` and `store/db/mysql/user.go`.

Key detail: the image is **not** a file on disk or in object storage — it's stored inline in the `user.avatar_url` TEXT column as a base64 data URI (`store/migration/sqlite/LATEST.sql:20`), which is why the handler's last step is a regex decode of that string rather than a storage read.
