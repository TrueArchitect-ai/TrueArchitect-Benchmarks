**Computation site: `memopayload.RebuildMemoPayload` — `server/runner/memopayload/runner.go:74`, delegating to `(*markdown.service).ExtractAll` — `internal/markdown/markdown.go:356`; Triggers: `CreateMemo` (and `CreateMemoComment` through it) and `UpdateMemo` when the `content` field is in the update mask; Extracted: `tags` plus the five `Property` fields — `has_link`, `has_code`, `has_task_list`, `has_incomplete_tasks`, `title`**

**Where it's computed.** `RebuildMemoPayload(ctx, memo, markdownService)` (`server/runner/memopayload/runner.go:74-88`) ensures `memo.Payload` is non-nil, calls `markdownService.ExtractAll([]byte(memo.Content))`, and assigns `memo.Payload.Tags = data.Tags` and `memo.Payload.Property = data.Property`. The actual parsing is a single goldmark AST walk in `ExtractAll` (`internal/markdown/markdown.go:356-421`). The result is persisted as the memo's `payload` column (marshalled as JSON in `store/db/sqlite/memo.go:21-26` and its Postgres/MySQL counterparts).

**Triggers.** Only two production call sites exist (`grep -rn RebuildMemoPayload`):

1. `CreateMemo` — `server/router/api/v1/memo_service.go:107-109`, run after the content-length check and before `Store.CreateMemo`. Note that `Location` is set on the payload *after* the rebuild (`memo_service.go:110-112`) — it's user-supplied, not derived.
2. `UpdateMemo` — `server/router/api/v1/memo_service.go:446-449`, inside the `if path == "content"` branch of the update-mask loop, so the payload is recomputed **only** when content actually changes; a visibility-only or pinned-only update leaves it untouched.
3. `CreateMemoComment` inherits this — it delegates to `s.CreateMemo` (`server/router/api/v1/memo_service_comments.go:55`), so comments get their payload built by path 1.

A third, dormant trigger exists: `memopayload.Runner.RunOnce` (`server/runner/memopayload/runner.go:27-72`) would rebuild payloads for all memos in batches of 100, but that runner is never constructed or invoked anywhere — it's dead code.

**What's extracted** (`internal/markdown/markdown.go:363-420`, schema at `proto/store/memo.proto:7-22`):

- `tags` — every `#tag` node, deduplicated with original case preserved via `uniquePreserveCase`. Tags inside links/images are excluded (`asMemoTagNode`, `isTagNodeInLinkOrImage`).
- `property.title` — text of the first block-level child of the document if it's an H1 heading (`markdown.go:383-389`).
- `property.has_link` — any `KindLink` node.
- `property.has_code` — any code block, fenced code block, or code span.
- `property.has_task_list` — any task checkbox.
- `property.has_incomplete_tasks` — any task checkbox that is unchecked.

`ExtractAll` also returns `Mentions`, but `RebuildMemoPayload` doesn't store them — mentions are consumed separately for notifications.

**One thing worth separating out:** the memo `snippet` used in list/preview responses is *not* part of this stored payload. It's computed on the fly at response-conversion time by `getMemoContentSnippet` → `MarkdownService.GenerateSnippet(content, 64)` (`server/router/api/v1/memo_service_webhooks.go:83-90`), called from `memo_service_converter.go:76`, `:225`, `:248`, `memo_relation_service.go:154,162`, and the notification path (`user_service_notifications.go:323`). So if "used for lists/previews" points you at the snippet, that's a per-request derivation with no triggers and no persistence.
