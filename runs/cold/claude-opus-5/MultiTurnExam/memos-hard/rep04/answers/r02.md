**Premise correction: there is no per-user API rate-limiting middleware in this repository, so there is no registration site and no request limits to report.**

What I checked:

- A case-insensitive grep for `ratelimit`, `rate_limit`, `rate limit`, `throttle`, and the usual token-bucket dependency `golang.org/x/time/rate` across all Go sources and `go.mod` returns exactly one hit, and it's a comment listing unimplemented future work: `internal/email/doc.go:86` — `//   - Rate limit email sending to prevent abuse`.
- The full Echo middleware stack is two entries, registered in `NewServer` at `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:14`). Nothing else calls `echoServer.Use` at the root; the only other `Use` calls are the static-file and SPA-fallback handlers in the frontend router (`server/router/frontend/frontend.go:54,59`).
- The gRPC-Gateway and Connect paths have an auth interceptor/middleware only (`server/router/api/v1/v1.go:95` onward, wrapping `NewAuthorizer`) — authentication and access-policy checks, no request counting or quota.

What does exist, and might be what you're thinking of — these are **concurrency limiters, not rate limits**. They cap simultaneous work globally, not requests per user over time, and they never reject a request with 429:

- `thumbnailSemaphore` — `semaphore.NewWeighted(3)` in the file server (`server/router/fileserver/fileserver.go:46,116`), acquired around thumbnail generation (`fileserver.go:447-449`).
- `thumbnailSemaphore` (3) and `imageProcessingSemaphore` (2) on the API service — `server/router/api/v1/v1.go:53-58` region, in `NewAPIV1Service`.
- A bounded webhook dispatch queue of 128 with 4 workers, which *drops* overflow rather than throttling (`internal/webhook/webhook.go:39,42-55,189-195`).
- A batch cap of 10 on link-metadata lookups (`maxBatchGetLinkMetadata`, `server/router/api/v1/memo_service.go:26`).

If you need per-user rate limiting, it would have to be added — the natural registration point is alongside the existing middleware at `server/server.go:51-52`, or inside the shared authorizer at `server/router/api/v1/v1.go` where the caller's identity is already resolved.
