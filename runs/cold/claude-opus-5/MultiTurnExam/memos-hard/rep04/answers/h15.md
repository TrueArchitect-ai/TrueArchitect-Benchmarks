Two structural points worth noting:

- The checks come in **two shapes**. Post-fetch gates (`checkMemoReadAccess`, `checkAttachmentPermission`, `canReceive`) load the memo and then reject; query-level filters (`ListMemos`, the stats handlers, RSS, sitemap) instead constrain `store.FindMemo.VisibilityList` so restricted rows never leave the database. Both are real enforcement, but only the first kind returns a permission error.
- The three-tier rule is consistent across sites: `Public` → anyone (subject to `Profile.AllowAnonymous()` in the fileserver, `fileserver.go:677`); `Protected` → any authenticated user; `Private` → creator only, with an admin/superuser bypass in several places (`isSuperUser` in the API sites, `user.Role != store.RoleAdmin` at `fileserver.go:699`) but **not** in `checkMemoReadAccess` itself (`memo_service.go:63`), which is creator-only. `checkMemoReadAccess` additionally enforces an orthogonal rule — archived memos are creator-only (`memo_service.go:44-53`).

One deliberate exception: `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:153`) contains no visibility check — share links are a capability that intentionally bypasses visibility, gated instead by share existence/expiry via `getActiveMemoShare` (`memo_share_service.go:199`).
