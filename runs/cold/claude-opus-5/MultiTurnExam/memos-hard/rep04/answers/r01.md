**Premise correction: there is no Redis in this repository — no Redis client, no connection config, no dependency.** A case-insensitive grep for `redis` across all Go sources, `go.mod`, `go.sum`, and YAML/JSON config files returns zero matches. The cache layer is a hand-rolled, in-process, in-memory cache.

**Actual mechanism:**

- **Implementation** — `store/cache/cache.go`. `Cache` (line 66-72) is a `sync.Map` guarded by an atomic item counter, with per-entry expiration timestamps, a background cleanup goroutine, and a rough size estimator. It satisfies the local `cache.Interface` (line 11-32). Nothing crosses a process boundary, so the cache is per-instance and lost on restart.

- **Where it's "configured"** — in code, not in a config file: `store.New` builds a `cache.Config` literal at `store/store.go:39-45` and constructs three caches with it (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, `userSettingCache`. There are no flags or env vars for any of this. `cache.DefaultConfig()` (`store/cache/cache.go:56-63`) declares the same values but isn't what `store.New` uses — it duplicates them inline.

- **TTL for user entries — 10 minutes.** `DefaultTTL: 10 * time.Minute` (`store/store.go:41`). Every user write goes through `s.userCache.Set(...)` (`store/user.go:98, 122, 132, 143, 167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:92-95`); no user path calls `SetWithTTL` with a custom value. Expiry is enforced lazily on read — `Get` deletes and reports a miss once `time.Now()` passes the entry's expiration (`cache.go:134-141`) — and proactively by the cleanup loop every `CleanupInterval` = 5 minutes (`store/store.go:42`).

- **Other eviction paths that can shorten that 10 minutes:** `MaxItems: 1000` (`store/store.go:43`) triggers `cleanupOldest()` when exceeded (`cache.go:115-118`), and user deletion explicitly invalidates the entry via `s.userCache.Delete` in `deleteUserCache` (`store/user_delete.go:40`).

- **Caching caveat worth knowing:** `Store.GetUser` only consults the cache when looking up by ID (`store/user.go:149-156`); a lookup by username or email always hits the database and then repopulates the cache keyed by ID (`store/user.go:167`).
