**1st: `store.User` — ~7 packages outside the store layer (6 excluding test packages); 2nd: `store.Memo` — ~6 packages (4 excluding test packages)**

Method: I enumerated the persistent entity structs declared in `store/*.go` (`Attachment`, `IdentityProvider`, `Inbox`, `InstanceSetting`, `Memo`, `MemoRelation`, `MemoShare`, `Reaction`, `User`, `UserIdentity`, `UserSetting` — excluding the `Find*`/`Update*`/`Delete*` query-parameter structs), then counted distinct package directories outside the `store/` tree that reference each as `store.<Type>`. Word-boundary matching keeps `store.User` from absorbing `store.UserSetting`/`store.UserIdentity`, and `store.Memo` from absorbing `store.MemoRelation`/`store.MemoShare`.

**`store.User`** (defined in `store/user.go`) — referenced from:

**`store.Memo`** (defined in `store/memo.go`) — referenced from:

Full ranking (packages outside `store/`, all files / non-test only): User 7/6, Memo 6/4, Attachment 4/3, MemoShare 3/2, Inbox 3/2, MemoRelation 3/1, UserIdentity 2/1, Reaction 2/1, then UserSetting, InstanceSetting, and IdentityProvider at 1/1 each.

Two notes on interpretation: `store.User` wins on package spread largely because it's the identity type threaded through auth (`server/auth`) and every permission check, whereas `store.Memo` is more concentrated — it has a comparable raw file count inside `server/router/api/v1` but reaches fewer distinct packages. If you instead count the store's own dialect implementations (`store/db/{sqlite,postgres,mysql}`) as "outside," both types gain three more packages each and the ordering is unchanged.
