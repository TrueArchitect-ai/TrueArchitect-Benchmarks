**Premise correction: there is no per-user API rate-limiting middleware in this codebase. No such component is registered anywhere, so there are no request limits to report.**

What I checked:

- **No implementation or dependency.** Searching the Go sources for `ratelimit`, `rate_limit`, `rate limit`, `throttl`, `golang.org/x/time/rate`, and `middleware.RateLimiter` across `server/`, `internal/`, `store/`, and `cmd/` returns exactly one hit — a comment in `internal/email/doc.go:86` listing "Rate limit email sending to prevent abuse" as a *future* consideration, not code. `go.mod` contains no rate-limiting or `x/time` dependency, and Echo's own `middleware.RateLimiter` is never referenced.

- **The full middleware chain is two entries.** `NewServer` registers only `middleware.Recover()` and `newCORSMiddleware(profile)` on the Echo instance (`server/server.go:51-52`). The other cross-cutting interceptors added later are authentication/authorization, not throttling: the shared `NewAuthorizer` used by both the gRPC-Gateway middleware and the Connect interceptor (`server/router/api/v1/v1.go:64-70`).

What *does* exist, and is easy to mistake for rate limiting — three concurrency caps, all per-process and not per-user:

- `thumbnailSemaphore` — `semaphore.NewWeighted(maxConcurrentThumbnails)` where the constant is 3 (`server/router/fileserver/fileserver.go:116`, `:44`), acquired at `fileserver.go:448`.
- `thumbnailSemaphore` on the API service — `semaphore.NewWeighted(3)` (`server/router/api/v1/v1.go:59`).
- `imageProcessingSemaphore` — `semaphore.NewWeighted(2)` (`server/router/api/v1/v1.go:60`), acquired at `server/router/api/v1/attachment_service_image.go:71`.

These bound simultaneous CPU/memory-heavy image work to prevent exhaustion; they block rather than reject, apply globally across all callers, and impose no request-per-interval limit on any user.

Other bounded resources in the same spirit: the webhook dispatch queue caps at 128 pending payloads with 4 workers and drops overflow (`internal/webhook/webhook.go:39-55`, `:189-195`), and memo content length is capped per instance setting (`server/router/api/v1/memo_service.go:100-106`). Again, neither is per-user request throttling.
