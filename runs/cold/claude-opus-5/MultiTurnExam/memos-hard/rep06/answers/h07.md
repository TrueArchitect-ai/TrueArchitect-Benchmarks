Notes on the hops:

- **Wiring**: the service is constructed and its routes registered during server setup at `server/server.go:81-82`.
- **Access control** (`fileserver.go:165-175`): if `s.Profile.AllowAnonymous()` is false — i.e. no `InstanceURL` is set, meaning a private instance — an authenticated viewer (session, access token, or PAT) is required. On a public instance, anyone can fetch any user's avatar. Note there is no per-user authorization beyond this: any authenticated viewer may fetch any other user's avatar.
- **Lookup key**: the `:identifier` path param is treated strictly as a username — `getUserByUsername` builds `&store.FindUser{Username: &identifier}` (`fileserver.go:715-717`).
- **Cache behavior**: `Store.GetUser` only consults `userCache` when `find.ID` is set (`store/user.go:149-156`). Since this path filters by username, the read always falls through to `ListUsers` → the driver → SQL, though the result is then written into the cache keyed by ID (`store/user.go:143`, `167`).
- **Storage form**: the avatar is not a file on disk or in S3 — it's stored inline in the `user.avatar_url` column as a base64 data URI (selected in the driver query, e.g. `store/db/sqlite/user.go:14,159`). `parseDataURI` splits it with `dataURIRegex` (`fileserver.go:93`) and base64-decodes the payload.
- **Response hardening**: the decoded MIME type must be in `avatarAllowedTypes` (`fileserver.go:73-81`, checked at `:200`), then `setSecurityHeaders` plus `Cache-Control: public, max-age=3600` are applied before `c.Blob` writes the bytes (`fileserver.go:204-208`).
