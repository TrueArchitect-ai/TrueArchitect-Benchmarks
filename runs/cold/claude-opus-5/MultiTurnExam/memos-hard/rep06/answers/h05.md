**Explicit Go code — two `DELETE FROM reaction` statements per driver, inside the delete-user transaction. There is no DB-level cascade for reactions (the `reaction` table has no foreign keys at all).**

What I checked:

**1. The Go delete path.** `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which removes reactions in two passes (`store/db/mysql/user_delete.go:90-124`, mirrored in `store/db/postgres/user_delete.go:96,102` and `store/db/sqlite/user_delete.go:96,102`):

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`store/db/postgres/user_delete.go:380-388`). This removes *everyone's* reactions on the deleted user's memos. The content IDs come from `listDeleteUserMemoTree`, which walks the memo tree iteratively through `memo_relation` rows of type `COMMENT` (`store/db/mysql/user_delete.go:128-176`), so reactions on descendant comment memos are covered too.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/mysql/user_delete.go:437-440`, `postgres/user_delete.go:400-403`, `sqlite/user_delete.go:400`). This removes the deleted user's own reactions on *other* people's memos.

Both run before the `user` row itself is deleted (`deleteUserRowTx`, ordered last in `deleteUserTargetsTx`), and everything commits atomically (`store/db/mysql/user_delete.go:29-58`).

**2. The schema.** The `reaction` table is defined at `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/sqlite/LATEST.sql:92-99`. In all three drivers it declares only `id`, `created_ts`, `creator_id`, `content_id`, `reaction_type`, and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — **no `FOREIGN KEY`, no `ON DELETE CASCADE`**. Note `content_id` is a string, not an integer FK to `memo.id`, so a cascade isn't even expressible here.

**3. Confirming cascades exist elsewhere (so their absence is meaningful).** `grep -rn "ON DELETE CASCADE" store/migration/*/LATEST.sql` returns exactly one hit per driver, and it's on `memo_share`, not `reaction`: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/mysql/LATEST.sql:108`, `postgres/LATEST.sql:108`, `sqlite/LATEST.sql:109`). So the codebase does use DB-level cascades — just not for reactions.

Consistent across all three drivers; there's also a dedicated test file at `store/db/mysql/user_delete_test.go`.
