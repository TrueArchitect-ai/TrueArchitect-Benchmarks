**`webhook.Post` — `internal/webhook/webhook.go:120` (the actual `safeClient.Do(req)` send is at `internal/webhook/webhook.go:152`); dial-time reserved/private-IP guard `safeDialContext` + `isReservedIP` — `internal/webhook/webhook.go:59` and `internal/webhook/validate.go:44`**

How it fits together:

- **Delivery path**: memo create/update/delete handlers call `webhook.PostAsync` (`server/router/api/v1/memo_service_webhooks.go:43,71`), which enqueues onto a bounded 128-slot channel (`internal/webhook/webhook.go:39`, drops with a warning when full). Four worker goroutines started in `init()` (`internal/webhook/webhook.go:42-55`) drain that queue and call `Post`, which marshals the payload, adds Standard Webhooks HMAC-SHA256 headers (`webhook-id` / `webhook-timestamp` / `webhook-signature`) when a signing secret is set, and issues the POST through the shared `safeClient` (`internal/webhook/webhook.go:152`).

- **Protection**: `safeClient`'s `http.Transport` uses `safeDialContext` (`internal/webhook/webhook.go:32-37`, `59-77`). At dial time it resolves the host itself and refuses the connection if *any* resolved IP is in a reserved range — checking at dial rather than only at config time is what defeats DNS rebinding (noted in the comment at `internal/webhook/webhook.go:30-31`). The ranges are the parsed `reservedCIDRs` list in `internal/webhook/validate.go:14-23`: IPv4 loopback, all three RFC-1918 blocks, 169.254.0.0/16 (cloud IMDS), plus IPv6 loopback/ULA/link-local.

- **Second, earlier layer**: `webhook.ValidateURL` (`internal/webhook/validate.go:62`) rejects a webhook URL at *registration* time — non-absolute URLs, non-http(s) schemes, and hostnames resolving to reserved IPs — called from the user webhook create/update handlers (`server/router/api/v1/user_service_webhooks.go:74,161,182`).

One thing worth flagging: the escape hatch `webhook.AllowPrivateIPs` (`internal/webhook/validate.go:41`) that disables both layers is declared but never assigned anywhere in the codebase — no flag, env var, or profile field writes it, so it is effectively always `false`. It's documented as being for self-hosted deployments targeting LAN services, but there is currently no way for an operator to turn it on.
