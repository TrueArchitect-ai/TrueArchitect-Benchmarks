Visibility (`PUBLIC` / `PROTECTED` / `PRIVATE`) is enforced at eleven distinct sites across five server surfaces:

```
checkMemoReadAccess (single-memo read gate: GetMemo, parent-memo checks) — server/router/api/v1/memo_service.go:39 (called at :356, :367)
ListMemos query scoping (anonymous → PUBLIC only; user → own + PUBLIC/PROTECTED) — server/router/api/v1/memo_service.go:217-226
User stats query scoping (ListMemoStats / user stats) — server/router/api/v1/user_service_stats.go:84,90,218,220
Reaction access checks (list + upsert reactions) — server/router/api/v1/reaction_service.go:30-40, :83
Attachment metadata access check — server/router/api/v1/attachment_service.go:445-451
Memo-attachment listing access check — server/router/api/v1/memo_attachment_service.go:214-222
Comment creation gate (private parent memo) — server/router/api/v1/memo_service_comments.go:41
checkAttachmentPermission (binary file serving, incl. share_token bypass) — server/router/fileserver/fileserver.go:650-704 (:677, :684-690, :699)
SSEClient.canReceive (server-side event delivery filtering) — server/router/api/v1/sse_hub.go:134-144
RSS feed queries (instance feed + per-user feed, PUBLIC only) — server/router/rss/rss.go:90, :141
Sitemap generation (PUBLIC only) — server/router/frontend/frontend.go:150
canViewerAccessMemo (email notification recipients) — server/notification/email.go:305-319
```

Two structurally different enforcement styles are in play:

- **Post-fetch gates** — load the memo, then reject: `checkMemoReadAccess`, `checkAttachmentPermission`, `canViewerAccessMemo`, and the reaction/attachment/comment checks. These typically follow the pattern "PUBLIC → allow; else require auth; PRIVATE → require creator (or admin/superuser)."
- **Pre-query scoping** — never fetch the rows at all, by setting `FindMemo.VisibilityList` or appending a CEL filter: the `ListMemos`, stats, RSS, and sitemap sites. Those constraints are translated to SQL `WHERE visibility IN (...)` by each driver (`store/db/sqlite/memo.go`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go`), which is the mechanism, not an independent policy decision.

Two related paths worth distinguishing from the above: **share tokens** are an *alternate authorization* route that intentionally bypasses visibility — `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:151`) resolves a token with no auth and no visibility check, and `fileserver.go:684-690` honors the same token for attachments. And on a private instance, `Profile.AllowAnonymous()` gates access *before* visibility is consulted (`server/router/fileserver/fileserver.go:677`).
