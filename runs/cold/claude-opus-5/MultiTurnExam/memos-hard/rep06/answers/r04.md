**Premise correction: neither. There is no message broker in this codebase — no NATS, RabbitMQ, AMQP, Kafka, SQS, or pub/sub dependency appears in any Go file, `go.mod`, or YAML config. Webhook delivery uses an in-process buffered Go channel, and there is no queue "declaration" in the broker sense.**

The actual mechanism, all in `internal/webhook/webhook.go`:

- **The queue** is a package-level buffered channel with capacity 128: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`). It's a plain in-memory Go channel — process-local, unshared, and not persisted.

- **The workers** are four goroutines started in the package's `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. They're started implicitly at import time rather than by explicit server wiring, and there is no shutdown path that drains or closes the channel.

- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184-196`), called from the memo webhook dispatchers (`server/router/api/v1/memo_service_webhooks.go:43,71`). It does a non-blocking `select` send: if the buffer is full, the `default` branch **drops the payload** with a warning (`internal/webhook/webhook.go:191-195`) rather than blocking the RPC handler.

- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`), which signs the body and POSTs via the SSRF-guarded `safeClient` (`internal/webhook/webhook.go:152`).

Consequences worth being explicit about, since they're exactly what a broker would otherwise provide: there is **no durability** (a restart loses everything buffered), **no retry** (a failed `Post` is logged and discarded — no backoff or dead-letter), **no cross-instance distribution** (each replica has its own channel and workers), and **no delivery guarantee** under burst load beyond the 128-slot buffer.
