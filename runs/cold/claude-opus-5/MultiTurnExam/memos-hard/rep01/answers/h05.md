**Explicit Go code — two hand-written `DELETE FROM reaction` statements per driver, executed inside the user-deletion transaction. No database-level cascade exists for reactions.**

What I checked:

**1. The deletion code path.** Each driver's `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which issues two distinct reaction deletes:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing *everyone's* reactions on the deleted user's memos (`store/db/mysql/user_delete.go:417-425`, `store/db/postgres/user_delete.go:380`, `store/db/sqlite/user_delete.go:380`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing the user's own reactions on *other people's* content (`store/db/mysql/user_delete.go:437-440`, `store/db/postgres/user_delete.go:400`, `store/db/sqlite/user_delete.go:400`).

Both are invoked at `store/db/mysql/user_delete.go:96` and `:102` (mirrored at the same line numbers in the postgres and sqlite files). Ordering matters and is deliberate: reactions are deleted *before* the memos at `:120` and the user row at `:123`, since the content-ID lookup depends on memo UIDs (`memoContentIDsFromRefs`, `store/db/mysql/user_delete.go:549`, which builds `"memos/" + uid`). The whole thing commits atomically at `:51`.

**2. The schema — no cascade to fall back on.** The `reaction` table carries no foreign key at all in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. Each declares only `creator_id`/`content_id` columns plus a `UNIQUE(creator_id, content_id, reaction_type)` constraint. A repo-wide grep for `ON DELETE` across `store/migration/` shows the only surviving cascade in the current schema is `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109`). The historical `ON DELETE CASCADE` constraints appear only in old migrations (e.g. `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql`) and were dropped by `store/migration/sqlite/0.7/00__remove_fk.sql`.

Note also that `content_id` stores a string of the form `memos/{uid}`, not a numeric memo ID — so a foreign key to `memo(id)` could not have been expressed here anyway. Explicit Go code is the only thing preventing orphaned reaction rows.
