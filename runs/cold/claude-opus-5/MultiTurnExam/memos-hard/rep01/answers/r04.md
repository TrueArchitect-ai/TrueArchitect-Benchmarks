**Premise correction: neither. There is no message broker in this repository at all** — a search across all Go sources, `go.mod`, and `go.sum` for `nats`, `rabbitmq`, `amqp`, `kafka`, and `streadway` returns zero hits. No broker client is a dependency, so there is no queue declaration to point to.

**Actual mechanism — an in-process buffered Go channel with a fixed worker pool, all in `internal/webhook/webhook.go`:**

- **The "queue"** is a package-level buffered channel of 128 slots: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`).
- **The workers** are four goroutines started in the package `init()` function, each ranging over the channel and calling `Post` (`internal/webhook/webhook.go:42-55`). They start automatically when the package is first imported — there's no explicit startup wiring or lifecycle management.
- **Enqueue** happens in `PostAsync` (`internal/webhook/webhook.go:184`), called from the memo webhook dispatchers (`server/router/api/v1/memo_service_webhooks.go:43`, `:71`).
- **Delivery** is `Post` (`internal/webhook/webhook.go:120`), which issues the HTTP POST via `safeClient.Do` at `:152`.

Three consequences of this design worth being explicit about, since they differ sharply from broker-backed delivery:

1. **No durability.** The queue lives in process memory. A restart or crash drops every pending webhook; nothing is persisted or replayed.
2. **Overflow is a silent-ish drop, not backpressure.** `PostAsync` uses a `select` with a `default` branch — when all 128 slots are full, the payload is discarded with a `slog.Warn` and the caller proceeds as if it succeeded (`internal/webhook/webhook.go:189-195`).
3. **No retries.** A failed delivery is logged at warn level by the worker (`internal/webhook/webhook.go:47-51`) and never re-attempted; there is no dead-letter path.
