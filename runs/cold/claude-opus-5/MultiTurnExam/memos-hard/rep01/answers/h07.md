Notes on the hops:

- **Where the URL comes from.** The browser doesn't guess this path — `convertUserToProto` rewrites a base64 avatar into `/file/{user.Name}/avatar` before sending the user proto (`server/router/api/v1/user_service_converters.go:36`). Non-base64 avatar URLs are passed through verbatim and never touch this handler.
- **Wiring.** The service is constructed and its routes registered at `server/server.go:81-82`.
- **Access control.** On a private instance (`!s.Profile.AllowAnonymous()`), the handler requires a resolvable viewer via `getCurrentUser` and returns 401 otherwise (`fileserver.go:171-179`). On a public instance, any user's avatar is anonymously readable.
- **Cache short-circuit.** `Store.GetUser` consults `userCache` only when the lookup is by `ID` (`store/user.go:149-156`). This path looks up by `Username`, so it always falls through to `ListUsers` and hits the database; the result is then written into the cache keyed by ID (`store/user.go:167`).
- **The data itself.** There's no blob storage involved — the avatar lives in the `user.avatar_url` column as a data URI, decoded in-handler by `parseDataURI` (`fileserver.go:737`), MIME-checked against `avatarAllowedTypes` (`fileserver.go:75`, `:201`), and written with `c.Blob` (`fileserver.go:207`).

There is no `GetUserAvatar` gRPC handler implemented in this tree despite the ACL entry at `server/router/api/v1/acl_config.go:25` — the file route above is the serving path.
