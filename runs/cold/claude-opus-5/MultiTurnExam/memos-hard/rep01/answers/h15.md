Two structural notes:

- **Two enforcement styles.** Single-object reads check `memo.Visibility` *after* fetching (`checkMemoReadAccess`, the attachment and reaction gates), while list endpoints push the constraint into the query via `FindMemo.VisibilityList` or a CEL filter (`memo_service.go:221` builds `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`). The list path never loads a memo the caller can't see.
- **The share token is the one deliberate bypass.** `GetMemoByShare` (`memo_share_service.go:151`) returns a private or protected memo with no authentication, gated only on token validity and expiry (`getActiveMemoShare`, `:199`; `isMemoShareExpired`, `:195`). `checkAttachmentPermission` honors the same token via the `share_token` query param (`fileserver.go:683-690`) so shared pages can load their images.

MCP is not a separate enforcement site — `server/router/mcp/catalog.go:12-14` exposes `MemoService_ListMemos`/`GetMemo` as tool proxies onto the same API handlers, inheriting their checks.
