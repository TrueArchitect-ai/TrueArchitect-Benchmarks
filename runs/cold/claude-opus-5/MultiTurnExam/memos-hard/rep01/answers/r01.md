**Premise correction: there is no Redis anywhere in this repository.** A case-insensitive search for "redis" across all Go sources, `go.mod`, YAML, and Markdown returns zero hits. The cache layer is a hand-rolled, in-process, in-memory cache — no external cache server, no connection to configure. Nothing persists across a restart, and in a multi-replica deployment each process holds its own independent copy.

**Actual mechanism:**

- **Implementation** — `store/cache/cache.go`, a `Cache` struct built on `sync.Map` plus an atomic item counter (`store/cache/cache.go:66-72`), created by `cache.New` (`:75`).
- **Configuration site** — `store.New` in `store/store.go:40-44`, which builds one `cache.Config` literal and passes it to all three caches (`store/store.go:51-53`):
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  - `OnEviction: nil`

  These values duplicate `cache.DefaultConfig()` (`store/cache/cache.go:56-63`), which is not actually called by the store.
- **TTL for user entries — 10 minutes.** `userCache` (`store/store.go:28`) is written only through `Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). No caller anywhere uses `SetWithTTL` with a custom duration for users, so the 10-minute default is the effective TTL. Entries can also leave early via the 5-minute cleanup sweep, the 1000-item cap, or explicit invalidation on user deletion (`store/user_delete.go:40`).

One behavioral detail worth knowing: the user cache is keyed by ID (`userCacheKey`), and `Store.GetUser` only consults it when the lookup is by `ID` (`store/user.go:149-156`) — lookups by username or email always hit the database and merely populate the cache afterward.
