### Path breakdown

**API layer — `server/router/api/v1/memo_service.go:518-593` (`APIV1Service.DeleteMemo`)**
- Reads only (no writes): `memo` (`GetMemo`), `reaction` (`ListReactions` for the webhook payload), `attachment`, `memo_relation`.
- `memo_service.go:567-577`: finds comment relations (`type = COMMENT`, `related_memo_id = memo.ID`) and calls `store.DeleteMemo` for each **child comment memo** — so every table below is hit once per comment as well as for the memo itself.
- `memo_service.go:580`: calls `store.DeleteMemo` for the memo.

**Store layer — `store/memo.go:140-159` (`Store.DeleteMemo`)**
1. `memo_relation` — two explicit deletes, `memo_id = ID` and `related_memo_id = ID` (`store/memo.go:142-147`, drivers at `store/db/sqlite/memo_relation.go`, `postgres/memo_relation.go`, `mysql/memo_relation.go`).
2. `attachment` — lists attachments with `memo_id = ID` and calls `Store.DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the backing file/object storage (`store/attachment.go:132-149`).
3. `memo` — the row itself (`store/memo.go:158` → `store/db/sqlite/memo.go:237`, `postgres/memo.go:244`, `mysql/memo.go:259`; plain `DELETE FROM memo WHERE id = ?`).

**DB-level cascade — `memo_share`**
`memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). There is no Go code deleting shares on memo deletion.

Caveat worth flagging: SQLite opens its connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does **not** fire and `memo_share` rows are left orphaned; it only takes effect on Postgres/MySQL.

### Not affected
- `reaction` — read for the webhook payload but never deleted; the schema (`reaction.content_id` is a free-form TEXT name, no FK) leaves reaction rows orphaned after a memo delete.
- `inbox`, `user`, `user_setting`, `system_setting`, `idp`, `user_identity` — untouched.
