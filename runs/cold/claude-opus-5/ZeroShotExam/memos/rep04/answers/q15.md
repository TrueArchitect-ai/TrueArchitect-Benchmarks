There's no ORM/tag-based mapping here — the store uses hand-written SQL per driver, so the mapping is struct → driver SQL statements.

| Table | Struct — path |
| --- | --- |
| `user` | `store.User` — `store/user.go:29` |
| `attachment` | `store.Attachment` — `store/attachment.go:16` |
| `reaction` | `store.Reaction` — `store/reaction.go:7` |

Evidence of the table binding in the driver layer (each driver has a matching file):

- `user` → `store/db/sqlite/user.go:17` (`INSERT INTO user ...`), `store/db/postgres/user.go:16` (`INSERT INTO "user" ...`), plus `store/db/mysql/user.go`
- `attachment` → `store/db/sqlite/attachment.go:34`, `store/db/postgres/attachment.go:33`
- `reaction` → `store/db/sqlite/reaction.go:16`, `store/db/postgres/reaction.go:13`

Note that `store/user.go` also holds `UpdateUser`/`FindUser`/`DeleteUser` (and the equivalents in the other two files) — those are query-parameter structs, not row mappings.
