`store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) deletes, in order, before calling `s.driver.DeleteMemo` (the actual `DELETE FROM memo` row, e.g. `/bench/repo/store/db/sqlite/memo.go:237`):

1. **Memo relation records where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`).
2. **Memo relation records where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`).
3. **Attachment records linked to the memo** — it lists them via `ListAttachments{MemoID: ...}` and deletes each with `s.DeleteAttachment` (`store/memo.go:148-157`), which also removes the underlying stored file/blob before deleting the row (`store/attachment.go:132-149`).

Notes on the boundary: comment memos are deleted by the API layer, not the store — `APIV1Service.DeleteMemo` first lists `MemoRelationComment` relations and calls `store.DeleteMemo` on each child memo, then deletes the memo itself (`server/router/api/v1/memo_service.go:567-582`). Reactions and memo shares are read for the webhook payload but are not deleted by `store.DeleteMemo`.
