**q26.**

**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`.**

Path through the code:

**API layer — `server/router/api/v1/memo_service.go:518` (`APIV1Service.DeleteMemo`)**
- Lists comment relations and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`), then deletes the memo itself (`memo_service.go:580`). So the cascade below applies once per comment plus once for the target memo.

**Store layer — `store/memo.go:140` (`Store.DeleteMemo`)** does the explicit cascade:
1. `memo_relation` — deleted twice, once by `MemoID` and once by `RelatedMemoID` (`store/memo.go:142-147`), so rows in either direction go away.
2. `attachment` — lists attachments with `MemoID` and calls `Store.DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the underlying blob/local file before the row delete (`store/attachment.go:132-149`).
3. `memo` — the driver's `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

**`memo_share` — by DB-level FK cascade, not code.** The schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Two caveats worth flagging:
- On SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so that cascade does **not** fire — `memo_share` rows are orphaned on SQLite deployments. The explicit `memo_share` cleanup that does exist lives only in the user-deletion path (`store/db/sqlite/user_delete.go:405-411`), not the memo path.

**Not affected: `reaction`.** `DeleteMemo` only *reads* reactions to build the webhook payload (`memo_service.go:545-550`); nothing deletes them. `reaction.content_id` is a plain `TEXT` column with no FK (`store/migration/sqlite/LATEST.sql:92-98`), so reactions on a deleted memo are left orphaned on every backend.
