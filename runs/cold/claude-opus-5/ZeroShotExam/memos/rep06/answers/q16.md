`store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) deletes the following before issuing the memo row delete (`s.driver.DeleteMemo`):

1. **Memo relations where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **Memo relations where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — lists via `ListAttachments{MemoID: &delete.ID}` and deletes each with `s.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying stored file/blob (`store/attachment.go:132-148`, `DeleteAttachmentStorage`)

Notes on the surrounding layers, since they affect what actually gets removed on an API delete:

- The API handler `APIV1Service.DeleteMemo` (`/bench/repo/server/router/api/v1/memo_service.go:518-592`) first walks comment relations (`MemoRelationComment`) and calls `store.DeleteMemo` on each comment memo, then deletes the memo itself — so comment memos (and their own relations/attachments) go too, but that loop lives in the service layer, not the store.
- Reactions and memo shares are only *read* by the handler (for the webhook payload); neither `store.DeleteMemo` nor the handler explicitly deletes them — those rely on the DB schema, not the store layer.
