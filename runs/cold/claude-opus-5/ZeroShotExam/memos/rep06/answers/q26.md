**Tables affected: `memo`, `memo_relation`, `attachment`** — plus **`memo_share`** via DB-level FK cascade (Postgres/MySQL only).

**Direct/explicit cascade code path**

`store.DeleteMemo` (`store/memo.go:140-159`) does, in order:
1. `memo_relation` — two deletes, one matching `memo_id`, one matching `related_memo_id` (`store/db/sqlite/memo_relation.go:149`, and the postgres/mysql equivalents).
2. `attachment` — lists attachments with `MemoID` and calls `DeleteAttachment` for each (`store/attachment.go:132-149` → `store/db/sqlite/attachment.go:212`). This also removes the backing file/object from storage, which is not a table.
3. `memo` — the row itself (`store/db/sqlite/memo.go:237-248`).

The API layer `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) additionally finds all comment relations (`MemoRelationComment` with `RelatedMemoID = memo.ID`) and calls `store.DeleteMemo` on each comment memo, so the same three tables are hit again for every comment.

**By DB cascade, not code**

`memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). There is no explicit `DeleteMemoShare` call in the delete path. Note that on SQLite this cascade does **not** fire — the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so share rows are left orphaned there.

**Not affected:** `reaction`. `DeleteMemo` lists reactions only to build the webhook payload (`memo_service.go:545-550`); reactions are keyed by a `content_id` string with no FK, so those rows survive the memo deletion.
