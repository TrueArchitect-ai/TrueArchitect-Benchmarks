**Tables written to: `memo`, `memo_relation`, `attachment`** (plus `memo_share` on Postgres/MySQL only, via DB-level FK cascade — see caveat).

**Direct path** — `Store.DeleteMemo` at `store/memo.go:140-159` explicitly cascades before deleting the row:
1. `memo_relation` — two deletes, once by `MemoID` and once by `RelatedMemoID`, so both incoming and outgoing relations go (`store/memo.go:142-147`; SQL at `store/db/sqlite/memo_relation.go:149` and the postgres/mysql equivalents).
2. `attachment` — lists attachments with `MemoID` and calls `Store.DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the underlying local/S3 blob before the row delete (`store/attachment.go:132-149`, `store/db/postgres/attachment.go:212`).
3. `memo` — the driver's own `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`, `store/db/postgres/memo.go:246`, `store/db/mysql/memo.go:261`).

**Comment recursion** — the API layer at `server/router/api/v1/memo_service.go:567-582` first lists `MemoRelationComment` relations pointing at the memo and calls `Store.DeleteMemo` for each child memo, so the same three tables are hit again per comment.

**`memo_share`** — there is *no* explicit cleanup code. The `memo_share.memo_id` column carries `FOREIGN KEY … REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`), so rows are removed on Postgres/MySQL. On SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), which disables FK enforcement — those share rows are left orphaned there.

**Not touched:** `reaction`. `DeleteMemo` reads reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); `reaction.content_id` is a plain TEXT column with no FK (`store/migration/sqlite/LATEST.sql:92-100`), so reaction rows survive the memo's deletion.
