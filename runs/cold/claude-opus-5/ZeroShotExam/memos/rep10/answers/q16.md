`Store.DeleteMemo` (`store/memo.go:140-159`) performs these cleanups before calling `s.driver.DeleteMemo` on the memo row itself:

1. **Memo relations where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`).
2. **Memo relations where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`).
3. **Attachments linked to the memo** — lists them via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and deletes each with `DeleteAttachment` (`store/memo.go:149-157`). That call also removes the underlying stored blob/local file via `DeleteAttachmentStorage` before deleting the attachment row (`store/attachment.go:132-149`).

Notes on what is *not* in this list:
- `memo_share` rows are not deleted explicitly — they go away via the `ON DELETE CASCADE` foreign key on `memo_share.memo_id` (`store/migration/sqlite/LATEST.sql:109`, and the equivalents in the postgres/mysql `LATEST.sql` and `0.27/04__memo_share.sql` migrations).
- Reactions and comment memos are handled one layer up in the API service, not in `Store.DeleteMemo`: `DeleteMemo` in `server/router/api/v1/memo_service.go:518` lists reactions (for the webhook payload) and recursively deletes comment memos (`server/router/api/v1/memo_service.go:567-576`) before deleting the memo.
