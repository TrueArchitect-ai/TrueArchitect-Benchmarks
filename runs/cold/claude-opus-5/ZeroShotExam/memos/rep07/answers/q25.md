**Engine:** Google CEL (`github.com/google/cel-go` v0.28.1, `go.mod:13`), wrapped by the in-repo filter engine at **`/bench/repo/internal/filter/`** — `engine.go` (compile entry + `DefaultEngine()`), `schema.go` (CEL env + memo field metadata), `parser.go` (AST→IR), `ir.go` (IR nodes), `render.go` (IR→SQL), `helpers.go` (`AppendConditions`).

**Mechanism (one sentence):** `Engine.Compile` runs the filter string through `cel-go`'s `env.Compile`/`AstToParsedExpr` against the memo schema's declared identifiers, `parser.go` normalizes the CEL AST into a dialect-agnostic IR condition tree (validating fields, types, and allowed operators, and folding `now` to a frozen instant), then `render.go` walks that IR per target dialect to emit a parameterized SQL fragment + args, which `filter.AppendConditions` appends to the query's WHERE clause.

**Wiring:**
- Request validation: `server/router/api/v1/memo_service.go:211-215` calls `validateFilter`, defined at `server/router/api/v1/shortcut_service.go:336-360` — it picks `DialectMySQL`/`DialectPostgres`/`DialectSQLite` from `s.Profile.Driver` and does a trial `CompileToStatement`; the raw filter string is then passed through as `memoFind.Filters`.
- SQL generation happens in the store drivers, each passing its own dialect constant: `store/db/sqlite/memo.go:57-61`, `store/db/mysql/memo.go:65-69`, `store/db/postgres/memo.go:54-58`.
- `helpers.go:9-25` threads `PlaceholderOffset: len(*args)` so Postgres `$N` numbering stays correct across multiple filters.

**Dialect differences** are encapsulated in `render.go` switches: JSON access (`memo.payload->'property'->>'hasTaskList'` for PG vs `json_extract`/`JSON_EXTRACT` for SQLite/MySQL), boolean semantics, `LIKE` vs `ILIKE`, placeholder style (`?` vs `$N`, `render.go:845`), and timestamp component extraction (`strftime` / `EXTRACT ... to_timestamp` / MySQL date functions, `render.go:225-245`). Special results: an unsatisfiable tree renders `1 = 0`, a trivially-true one renders `""` and is skipped (`render.go:31-56`, `helpers.go:18-20`).

The design is documented in `/bench/repo/internal/filter/README.md` as a three-phase parse → normalize → render pipeline.
