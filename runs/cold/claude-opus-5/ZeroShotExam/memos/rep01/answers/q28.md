**Runners the server explicitly starts** (`server/server.go:148` `startBackgroundRunners`, called from `Start` at `server/server.go:126`):

- **s3presign runner** (`server/runner/s3presign/runner.go`) — one synchronous `RunOnce(ctx)` at startup (`server/server.go:157`), then a goroutine on a `time.Ticker` fixed at `runnerInterval = 12h` (`server/runner/s3presign/runner.go:28-42`). Per-attachment work is additionally gated by a staleness check: it re-presigns only when `LastPresignedTime` is older than 4 days (5-day URL expiry) (`server/runner/s3presign/runner.go:88-93`). Tracked in `backgroundRunnerCancels`/`backgroundRunnerWG` and cancelled on shutdown (`server/server.go:150-166`, `176-181`).

That is the *only* runner in `startBackgroundRunners`. Three other long-lived goroutine sets exist but are started implicitly, not by that function:

- **Webhook async dispatch pool** (`internal/webhook/webhook.go:42-54`) — 4 worker goroutines started in package `init()`, so they exist as soon as the package is linked in. Trigger is event-driven, not timed: they drain the 128-buffered `asyncPostQueue`, fed by `webhook.PostAsync` from memo create/update/delete paths (`server/router/api/v1/memo_service_webhooks.go:43,71`). Non-blocking send — payloads are dropped when the queue is full (`internal/webhook/webhook.go:184-192`). No shutdown hook.
- **Store cache cleanup loops** (`store/cache/cache.go:83`, `200-213`) — one goroutine per cache, on a `CleanupInterval = 5m` ticker. Three are created by `store.New` (`store/store.go:41-53`: instance-setting, user, user-setting caches), which `cmd/memos/main.go:62` calls before the server is built. Stopped via `Cache.Close`, not by the server's runner machinery.
- **SSE heartbeat** (`server/router/api/v1/sse_handler.go:64`) — a 30s ticker, but per-connection inside the request handler, so it's request-scoped rather than a background worker. The `SSEHub` itself (`server/router/api/v1/sse_hub.go`) has no goroutine; the server only closes it on shutdown (`server/server.go:196-201`).

**Unused scheduling infrastructure:**

- **`internal/scheduler/`** — a complete cron scheduler (5/6-field parser, timezone support, middleware, graceful shutdown; `scheduler.go`, `parser.go`, `job.go`, `middleware.go`, plus `doc.go` and `README.md`) is **not wired into the server at all**. `grep` for `usememos/memos/internal/scheduler` matches only its own tests (`internal/scheduler/example_test.go:10`, `internal/scheduler/integration_test.go:13`). Nothing in `cmd/` or `server/` imports it, and the one real periodic job (s3presign) uses a hand-rolled `time.Ticker` instead.
- **`server/runner/memopayload` `Runner`** — the type and its `RunOnce` batch rebuild (`server/runner/memopayload/runner.go:16-79`) are never constructed or invoked by the server; `NewRunner` has no non-test callers. Only the standalone helper `memopayload.RebuildMemoPayload` is used, inline on the request path (`server/router/api/v1/memo_service.go:108,447`). So the memopayload *runner* is dead as a background worker even though the package it lives in is used.
