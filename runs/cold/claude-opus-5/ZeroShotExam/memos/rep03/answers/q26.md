**Tables affected by `DeleteMemo`:** `memo`, `memo_relation`, `attachment`, and `memo_share` (DB-level cascade, Postgres/MySQL only).

**Direct/explicit cascade code** — `store.DeleteMemo` at `store/memo.go:140-159`:
- `memo_relation` — two explicit deletes, one where the memo is the source (`MemoID`) and one where it is the target (`RelatedMemoID`) (`store/memo.go:142-147`)
- `attachment` — lists attachments with `MemoID` and calls `DeleteAttachment` per row (`store/memo.go:149-157`), which deletes the row via the driver plus the underlying blob/local file (`store/attachment.go:132-149`)
- `memo` — the final driver delete (`store/memo.go:158`; e.g. `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`), which are plain single-table `DELETE FROM memo WHERE id = ?` statements

**DB-level cascade:**
- `memo_share` — `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in `store/migration/postgres/LATEST.sql:108` and `store/migration/mysql/LATEST.sql:108`. The same constraint exists in `store/migration/sqlite/LATEST.sql:109`, but the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite the cascade does **not** fire and `memo_share` rows are left orphaned.

**API-layer additions** — `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-591`) first deletes comment memos (relations of type `COMMENT` pointing at this memo) by calling `store.DeleteMemo` on each (`memo_service.go:567-577`), so the same four tables are hit again for every comment.

**Not touched:** `reaction` rows are only *read* for the webhook payload (`memo_service.go:545-550`); nothing deletes them, and the `reaction` table has no FK to `memo` (it keys off a `content_id` string — `store/migration/sqlite/LATEST.sql:92-99`), so reactions on a deleted memo are left orphaned.
