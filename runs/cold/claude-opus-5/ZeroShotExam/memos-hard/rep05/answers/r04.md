**Premise correction:** Neither. This repository (memos) has no message broker at all — no NATS, RabbitMQ, AMQP, Kafka, or Redis client appears in `go.mod`, and there is no broker connection code anywhere in the tree. The only text match for "nats" in the whole repo is inside a Catalan UI string in `web/src/locales/ca.json`.

**Actual mechanism:** webhook delivery uses an in-process Go channel as the queue, with a fixed pool of goroutines started at package init.

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a buffered channel of capacity 128 declared in the package-level `var` block.
- **Workers:** `internal/webhook/webhook.go:42-55` — an `init()` function spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`; failures are only logged via `slog.Warn`, with no retry or dead-lettering.
- **Producer:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send; if the buffer is full the payload is **dropped** with a warning rather than blocking or persisting.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` enqueue payloads for memo created/updated/deleted and comment-created events.

Practical consequences of this design: delivery is best-effort and non-durable — queued webhooks are lost on process restart, on buffer overflow, and on any HTTP failure, since nothing is persisted. Actual HTTP delivery happens in `Post` (`internal/webhook/webhook.go:120`) over a shared `safeClient` whose transport blocks reserved/private IPs to prevent SSRF (`webhook.go:32-37`, `safeDialContext` at `:59`).
