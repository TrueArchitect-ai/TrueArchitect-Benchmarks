**Premise correction: this repository has no per-user API rate-limiting middleware.** There is no such registration and therefore no request limits to report.

What I checked and found:

**The full HTTP middleware chain** (`server/server.go:51-52`) is only two entries:
- `middleware.Recover()`
- `newCORSMiddleware(profile)` (defined in `server/cors.go:13`)

**The full API interceptor/middleware set** for the v1 API:
- gRPC-Gateway: a single `gatewayAuthMiddleware` (auth/anonymous-access policy only), registered at `server/router/api/v1/v1.go:69-97`
- Connect RPC: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` — all in `server/router/api/v1/connect_interceptors.go`. None does rate limiting.

**Repo-wide searches confirm the absence.** Case-insensitive greps for `rate limit`, `ratelimit`, `throttle`, `429`, `too many requests`, `RESOURCE_EXHAUSTED`, and `quota` across all Go/TS/proto sources return only two hits, both aspirational documentation, not code:
- `internal/email/README.md:286` — a "### 5. Implement Rate Limiting" section describing something a *caller* could build
- `internal/email/doc.go:86` — a comment listing "Rate limit email sending to prevent abuse" as a suggestion

No rate-limiting library is used either: `golang.org/x/time` appears in `go.mod:151` marked `// indirect`, and there is no `tollbooth`, `ulule/limiter`, or similar in `go.mod`/`web/package.json`.

**The closest thing that actually exists** is a concurrency limiter, not a rate limiter, and it is global rather than per-user: `imageProcessingSemaphore: semaphore.NewWeighted(2)` in `server/router/api/v1/v1.go:60`, which caps simultaneous image-processing operations at 2 across the whole instance.
