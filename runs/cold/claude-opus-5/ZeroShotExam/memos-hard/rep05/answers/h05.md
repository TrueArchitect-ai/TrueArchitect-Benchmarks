**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside each driver's `DeleteUser` transaction. There is no database-level cascade for them.

## What I checked

**1. The delete path, API → store → driver**
- `server/router/api/v1/user_service.go:393-416` — `DeleteUser` resolves the user, checks permission, then calls `s.Store.DeleteUser`.
- `store/user.go:171-172` — thin wrapper delegating to `s.driver.DeleteUser`.
- Driver implementations: `store/db/sqlite/user_delete.go`, `store/db/postgres/user_delete.go`, `store/db/mysql/user_delete.go` (all three mirror each other).

**2. The explicit deletes** (sqlite line numbers; postgres identical, mysql at 417/437)

`deleteUserTargetsTx` runs two separate reaction deletions inside the transaction (`store/db/sqlite/user_delete.go:96` and `:102`):
- `deleteReactionsByContentIDsTx` (`:380-388`) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500, removing *everyone's* reactions on the deleted user's memos. Content IDs are built as `"memos/" + uid` in `memoContentIDsFromRefs` (`:512-518`), matching the resource-name format stored in `reaction.content_id`.
- `deleteReactionsByCreatorTx` (`:400-403`) — `DELETE FROM reaction WHERE creator_id = ?`, removing the user's own reactions on other people's memos.

Both run before `deleteMemosTx` and `deleteUserRowTx` in the same transaction, so a failure rolls the whole thing back.

**3. Ruled out a database-level rule**

The `reaction` table has no foreign key at all — no `REFERENCES user(id)`, no `ON DELETE CASCADE`:
- `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`
- Original creation migrations `store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql` — also FK-free from the start.

A repo-wide grep for `FOREIGN KEY|REFERENCES|ON DELETE` in `store/migration/` returns cascades only for `memo_share`→`memo` (`LATEST.sql:108-109`) and legacy pre-0.5 sqlite tables — never for `reaction`.

**4. Tests confirming the behavior**
- `server/router/api/v1/test/user_service_delete_test.go:188-209, 287-298` — after deletion, reactions on the user's own memo and on their comment are empty, while a peer's reaction on a foreign memo survives (`:295-298`).
- `store/test/user_delete_test.go:97-112, 217-220` — same assertion at the store layer.
- `server/router/api/v1/test/user_service_delete_test.go:366-431` — with the pre-commit failpoint, the reaction is still present after rollback, confirming the deletes are transactional rather than incidental.
