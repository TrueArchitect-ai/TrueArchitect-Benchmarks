**Premise correction:** There is no Redis in this repository. A case-insensitive search for "redis" across the whole tree (excluding `.git`/`node_modules`) returns zero hits, and `go.mod` contains no Redis client dependency. There is also no external/shared cache of any kind and no cache-related configuration knob — `internal/profile/profile.go` only carries `Driver`/`DSN` for the primary database (SQLite, MySQL, or PostgreSQL). So there is nothing to "configure a connection" to.

**Actual mechanism:** The cache layer is a process-local, in-memory cache built on `sync.Map`, defined in `store/cache/cache.go`.

- `store/cache/cache.go:66-90` — `Cache` struct: a `sync.Map` plus an atomic item counter, with per-item `expiration time.Time` (`store/cache/cache.go:35-39`). A background goroutine (`cleanupLoop`, `store/cache/cache.go:200-250`) sweeps expired entries on a ticker; `cleanupOldest` (`store/cache/cache.go:253`) evicts when over `MaxItems`.
- `store/store.go:38-61` — this is the "configuration" site. `New()` builds one `cache.Config` literal and hands the *same* config to three separate cache instances declared at `store/store.go:27-29`: `instanceSettingCache`, `userCache`, and `userSettingCache`.

**TTL for user entries:** **10 minutes**, from the shared `cacheConfig.DefaultTTL` at `store/store.go:41`. There is no user-specific TTL — users, user settings, and instance settings all get the identical 10-minute default (cleanup interval 5 minutes, `MaxItems` 1000). `cache.DefaultConfig()` at `store/cache/cache.go:57-64` declares the same values, but `store.New()` does not call it; it duplicates the literal.

Nothing in the codebase calls `SetWithTTL` outside the cache package itself, so the 10-minute default is never overridden. User entries are written via `s.userCache.Set(...)` on create, update, list, and get (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), keyed by the plain user ID string (`userCacheKey`, `store/user.go:88-90`), read back only when the lookup is by ID (`store/user.go:149-156`), and explicitly invalidated on delete via `deleteUserCache` (`store/user_delete.go:39-46`), which also drops that user's setting keys.

One consequence worth flagging: because this cache lives in the server process, a multi-replica Memos deployment gives each replica its own independent copy, and an update on one replica is not invalidated on the others — stale user data can persist there for up to the 10-minute TTL.
