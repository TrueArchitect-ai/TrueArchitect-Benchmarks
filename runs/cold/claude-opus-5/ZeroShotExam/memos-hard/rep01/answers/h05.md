**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the driver-level delete-user transaction. There is no database-level cascade for reactions.

## What I checked

**1. The delete-user transaction (all three drivers, identical structure)**

`store/db/sqlite/user_delete.go`, `store/db/postgres/user_delete.go`, `store/db/mysql/user_delete.go`

`DeleteUser` opens a transaction, collects targets, then runs `deleteUserTargetsTx`, which fires two reaction deletes *before* deleting the memos and the user row (`store/db/sqlite/user_delete.go:91-125`):

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`store/db/sqlite/user_delete.go:380-389`). The content IDs come from the recursively-collected memo tree (memos + comments) owned by the user, formatted as `"memos/"+uid` (`store/db/sqlite/user_delete.go:512-518`). This removes *other people's* reactions on the deleted user's content.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`). This removes the deleted user's own reactions on anyone's content.

Postgres and MySQL mirror this at lines 96/102 and 380-403 / 417-440 of their respective files.

**2. Schema — no FK, so no DB-level rule**

The `reaction` table has no foreign key at all, in current schema or at creation:
- `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` — only `UNIQUE(creator_id, content_id, reaction_type)`.
- `store/migration/sqlite/0.20/00__reaction.sql:2-9` — the table was introduced without any FK.
- Grepping `REFERENCES|CASCADE|FOREIGN KEY` across `store/migration/` shows exactly one FK per LATEST.sql, and it's `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109`). Note `content_id` is a string like `memos/<uid>`, not an integer FK, so it couldn't cascade from `memo` either.

**3. Call path and tests confirming the behavior**

- `server/router/api/v1/user_service.go:414` calls `s.Store.DeleteUser`, which delegates to the driver (`store/user.go:171-172`).
- `server/router/api/v1/test/user_service_delete_test.go:287-298`: after deletion, reactions on the user's own memo and on their comment are empty, while a third party's reaction on a *foreign* memo survives (only the deleted user's row on it goes away).
- `store/test/user_delete_test.go:97-112, 217-220`: same assertions at the store layer.
- `server/router/api/v1/test/user_service_delete_test.go:366-431`: with the `before_commit` failpoint (`store/user_delete.go:13-14`), the reaction is still present after rollback — confirming the deletes are transactional Go-issued statements, not a DB rule.
