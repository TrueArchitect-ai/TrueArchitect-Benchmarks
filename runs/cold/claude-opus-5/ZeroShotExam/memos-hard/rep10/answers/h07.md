**Where the URL comes from:** the API never ships another user's raw avatar bytes — `convertUserFromStore` rewrites `AvatarUrl` to `/file/users/{username}/avatar` when the stored value is a base64 data URI (`server/router/api/v1/user_service_converters.go:32-40`, with `BuildUserName` at `server/router/api/v1/user_resource_name.go:13`). The browser then hits that path, which the file server owns.

**Hops from the request to stored data:**


Notes on the path:
- Before the lookup, `serveUserAvatar` gates anonymous access on `s.Profile.AllowAnonymous()`, falling back to `getCurrentUser` → `auth.Authenticator.AuthenticateToUser` (`server/router/fileserver/fileserver.go:173-181, 708-712`).
- `Store.GetUser` only consults `userCache` when the find is by ID; a username lookup always falls through to `ListUsers`, which repopulates the cache (`store/user.go:142-144`, cache field at `store/store.go:28`).
- The avatar is not a file or blob row — it lives in the `user.avatar_url` column as a `data:<type>;base64,...` URI, decoded back to bytes by `parseDataURI` (`server/router/fileserver/fileserver.go:737`) and written with `c.Blob` after a MIME allowlist check against `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:75-83, 201-209`).
