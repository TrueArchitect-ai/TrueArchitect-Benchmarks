h15.

Memo visibility (PUBLIC / PROTECTED / PRIVATE, plus the archived-only-to-creator rule) is not enforced by a single chokepoint — each server surface that can surface memo data re-implements the rule. The distinct enforcement sites:

**Per-memo read gates (single memo fetched by name/ID)**

- `checkMemoReadAccess` — central gRPC/Connect read gate, used by `GetMemo` (incl. the parent memo of a comment) and `ListMemoComments` — `server/router/api/v1/memo_service.go:39-66`, callers at `:356`, `:367`, and `server/router/api/v1/memo_service_comments.go:148`
- `CreateMemoComment` parent-memo check — `server/router/api/v1/memo_service_comments.go:41`
- `ListMemoAttachments` inline check — `server/router/api/v1/memo_attachment_service.go:213-226`
- `checkAttachmentAccess` (attachment metadata API; derives access from the linked memo) — `server/router/api/v1/attachment_service.go:422-455`
- Reactions: `ListMemoReactions` `server/router/api/v1/reaction_service.go:29-41`, `UpsertMemoReaction` `:82-85`, and the delete path in the same file
- `checkAttachmentPermission` — raw blob/file HTTP serving, independent of the API layer, incl. anonymous-instance rule and `share_token` fallback — `server/router/fileserver/fileserver.go:650-704` (visibility branches at `:677`, `:699`)
- `GetMemoByShare` — share-token surface that deliberately bypasses visibility (token itself is the authorization); expiry/archived checks only — `server/router/api/v1/memo_share_service.go:153-192`, helper `getActiveMemoShare` `:199-212`

**Query-level filter injection (list/aggregate surfaces)**

- `ListMemos` — `server/router/api/v1/memo_service.go:212-227`
- `ListMemoComments` comment filter — `server/router/api/v1/memo_service_comments.go:156-161`
- Memo relations: `ListMemoRelations` `server/router/api/v1/memo_relation_service.go:107-112`, and the batch relation converter `server/router/api/v1/memo_service_converter.go:182-187`
- User stats: `ListAllUserStats` `server/router/api/v1/user_service_stats.go:82-92` and `GetUserStats` `:216-221`
- RSS feeds (explore + per-user, public only) — `server/router/rss/rss.go:90`, `:141`
- Sitemap (public only) — `server/router/frontend/frontend.go:150`

**Push / out-of-band delivery**

- SSE broadcast filter `SSEClient.canReceive` — `server/router/api/v1/sse_hub.go:134-143`, with event visibility/creator populated in `server/router/api/v1/sse_event_helpers.go:24-40`
- Inbox/notification rendering `canViewerAccessMemo` — `server/router/api/v1/user_service_notifications.go:302-318` (used at `:337`, `:342`, `:370`, `:385`)
- Email notifications `canViewerAccessMemo` — a second, separate copy in `server/notification/email.go:306-319` (used at `:155`, `:187`)
- Mention notification targeting `canUserAccessMentionContext` / `shouldSkipMentionInbox` — `server/router/api/v1/memo_mention_helpers.go:56-88`

Two things worth flagging: `canViewerAccessMemo` is duplicated verbatim-ish in `user_service_notifications.go` and `notification/email.go`, and the two differ in their admin check (`isSuperUser(viewer)` vs. `viewer.Role == store.RoleAdmin`). Also, the per-memo gates are copy-pasted rather than routed through `checkMemoReadAccess` — only `memo_service.go` and `memo_service_comments.go:148` use the shared helper, and only that helper enforces the archived-memo rule.
