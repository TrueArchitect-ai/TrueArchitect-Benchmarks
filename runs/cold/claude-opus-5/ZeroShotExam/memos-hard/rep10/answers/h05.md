## What I checked

**1. The delete path.** `DeleteUser` API → store → driver:
- `server/router/api/v1/user_service.go:414` calls `s.Store.DeleteUser(...)`
- `store/user.go:171-172` delegates to `s.driver.DeleteUser(...)`
- Each driver implements it in a single transaction: `store/db/sqlite/user_delete.go`, `store/db/postgres/user_delete.go`, `store/db/mysql/user_delete.go`

**2. The explicit reaction deletes.** In `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:96` and `:102`, mirrored at the same lines in the postgres and mysql files), two separate calls run *before* the memos and the user row are deleted:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`sqlite/user_delete.go:380-388`; mysql at `:417`). This removes reactions *anyone* left on the deleted user's memos, keyed on the memos' content IDs (`memos/<uid>`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`sqlite/user_delete.go:400-403`; mysql at `:437`). This removes reactions the deleted user left on *other people's* memos.

Ordering matters here: content-ID deletion happens before `deleteMemosTx`, while the memo rows (and their UIDs) still exist to be collected.

**3. Ruled out a DB-level rule.** The `reaction` table has no foreign key at all — `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`
- Original creation: `store/migration/*/0.20/00__reaction.sql`

A repo-wide grep for `FOREIGN KEY|REFERENCES|ON DELETE` across `store/migration/` returns hits only for `memo_share → memo`, and for legacy 0.3–0.5 tables (`memo`, `user_setting`, `resource`, etc.). The reaction table postdates the 0.5 `regenerate_foreign_keys` migration and was never given one. Note also that `content_id` is a text reference (`memos/<uid>`), not an integer FK to `memo` — a cascade wouldn't be expressible there anyway.
