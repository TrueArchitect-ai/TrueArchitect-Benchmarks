**Premise correction: this repository has no per-user API rate-limiting middleware.** There is nothing to register and no request limits to report.

Evidence:

- **The full API interceptor chain is at `server/router/api/v1/v1.go:133-138`**, and it contains exactly four interceptors — `NewMetadataInterceptor()`, `NewLoggingInterceptor()`, `NewRecoveryInterceptor()`, `NewAuthInterceptor()`. All four are defined in `server/router/api/v1/connect_interceptors.go`; none does rate limiting.
- **The Echo-level middleware stack is `server/server.go:51-52`** — only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`).
- A repo-wide search for `rate limit` / `ratelimit` / `throttle` matches only two files, both in `internal/email/`, and both are prose rather than code: `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a future consideration, and `internal/email/README.md:286-297` shows a *suggested* `rate.NewLimiter(rate.Every(time.Second), 10)` snippet in a "Best Practices" section. That 10/sec figure is illustrative example code for email sending — not an implemented API limit.
- No rate-limiting dependency is present: `go.mod` has no `golang.org/x/time/rate`, `ulule/limiter`, `tollbooth`, or similar. Searching the Go sources for `Limiter`, `TooManyRequests`, and `429` returns zero hits, so no handler ever emits a rate-limit response.

What likely prompted the question — the request limits that *do* exist are size- and time-based, not per-user rate limits:

- **Request body size cap:** `maxAPIRequestBytes = 256 << 20` (256 MiB), declared at `server/router/api/v1/v1.go:20` and applied via `http.MaxBytesHandler` to the gateway routes (`v1.go:126`), the Connect mux (`v1.go:144`), and as `connect.WithReadMaxBytes` (`v1.go:141`).
- **Background job timeouts:** `internal/scheduler/middleware.go:74` provides a `Timeout(duration)` middleware, but that wraps scheduler jobs, not user API requests.
