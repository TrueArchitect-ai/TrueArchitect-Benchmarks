**No** — outside `NewDBDriver`, the MySQL driver is never constructed in production code. The only exception is a zero-value struct literal in an in-package unit test.

**Evidence:**

1. **Sole factory call site:** `store/db/mysql.NewDB(profile)` is invoked exactly once in the whole repo, inside the driver-selection switch at `store/db/db.go:22`:
   ```go
   case "mysql":
       driver, err = mysql.NewDB(profile)
   ```
   `grep -rn "mysql\.NewDB\|db/mysql" --include="*.go" .` returns only `store/db/db.go:8` (the import) and `store/db/db.go:22` (the call).

2. **Package import graph:** `github.com/usememos/memos/store/db/mysql` is imported by exactly one file — `store/db/db.go`. No other Go file in the repo imports it, so no external package can construct `mysql.DB` at all. (By contrast, `store/db/sqlite` is imported directly by `store/demo_seed_test.go:13` and `store/deployment_config_test.go:19` — so the "only via factory" property genuinely holds for MySQL but not for SQLite.)

3. **Struct-literal construction:** `grep -rn "DB{" store/db/mysql/` finds only two sites:
   - `store/db/mysql/mysql.go:29` — `driver := DB{profile: profile}`, which *is* the body of `NewDB` itself.
   - `store/db/mysql/auth_config_test.go:12` — `db := &DB{}`, an in-package test that builds a zero-value receiver purely to call the pure method `IsRetryableAuthenticationMutationError`. It never opens a connection and is unexported-package-local, not a real driver instantiation.

4. **Test infrastructure also goes through the factory:** the integration test harness does not bypass it — `store/test/store.go:28` and `store/test/store.go:50` both call `db.NewDBDriver(profile)`. `store/test/containers.go` only spins up a MySQL *container* and builds DSN strings (`testcontainers-go/modules/mysql`, plus a raw `sql.Open("mysql", dsn)` at line 145 for readiness probing); it never constructs the `store/db/mysql` driver type.
