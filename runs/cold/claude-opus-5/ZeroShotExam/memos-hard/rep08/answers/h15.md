h15.

Memo visibility is not centralized — each surface that can expose memo content re-implements the check. Distinct enforcement sites:

**Core API (gRPC/Connect, `server/router/api/v1/`)**

`checkMemoReadAccess` — single-memo read gate (archived → creator only; non-public → auth required; private → creator only); used by `GetMemo` (incl. the parent memo of a comment) and `ListMemoComments` — server/router/api/v1/memo_service.go:39-66 (callers :356, :367; server/router/api/v1/memo_service_comments.go:148)

`ListMemos` query-level filter — anonymous gets `VisibilityList = [PUBLIC]`; authed gets CEL `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`, or `[PUBLIC, PROTECTED]` when scoped to another creator — server/router/api/v1/memo_service.go:218-227

`ListMemoComments` child-comment filter — same CEL/public-only filter applied to the comments themselves after the parent gate — server/router/api/v1/memo_service_comments.go:157-162

`CreateMemoComment` write-side visibility gate on the parent memo — server/router/api/v1/memo_service_comments.go:33-42

`batchConvertMemoRelations` — `MemoFilter` passed to `ListMemoRelations` so related-memo UIDs/snippets are hidden — server/router/api/v1/memo_service_converter.go:178-187

`ListMemoRelations` RPC — same `memoFilter` construction — server/router/api/v1/memo_relation_service.go:103-112

Reactions — `ListMemoReactions` (:29-41) and `UpsertMemoReaction` (:82-85) — server/router/api/v1/reaction_service.go

`checkAttachmentAccess` — attachment access follows the linked memo's visibility — server/router/api/v1/attachment_service.go:422-455 (caller :256)

`ListMemoAttachments` — server/router/api/v1/memo_attachment_service.go:213-225

User stats (`ListAllUserStats`, `GetUserStats`) — visibility list / CEL filter on the counted memos — server/router/api/v1/user_service_stats.go:84-91, 217-221

SSE fan-out — `SSEClient.canReceive` drops private-memo events for non-creator/non-admin clients — server/router/api/v1/sse_hub.go:123, 134-146 (event visibility stamped in server/router/api/v1/sse_event_helpers.go:29-37)

Inbox notifications — `canViewerAccessMemo` redacts notification content/snippets — server/router/api/v1/user_service_notifications.go:302-322 (callers :337, :342, :370, :385)

Mention notifications — `canUserAccessMentionContext` / `shouldSkipMentionInbox` — server/router/api/v1/memo_mention_helpers.go:56-89

**Non-gRPC HTTP surfaces**

Raw file server (`/file/...`) — its own duplicate of the rule: public + anonymous-allowed short-circuit, valid `share_token` bypass, then private → creator/admin — server/router/fileserver/fileserver.go:650-703

RSS feeds (explore + per-user) — hard-coded `VisibilityList = [PUBLIC]` — server/router/rss/rss.go:90, 141

Sitemap XML — hard-coded `VisibilityList = [PUBLIC]` — server/router/frontend/frontend.go:149-151

Email notifications — a second, independent copy of `canViewerAccessMemo` (uses `Role == RoleAdmin` rather than `isSuperUser`) — server/notification/email.go:306-321 (callers :155, :187)

**Deliberate bypass worth noting:** `GetMemoByShare` resolves an unexpired share token to a memo with no visibility check at all — the token itself is the grant; it only rejects expired tokens and archived memos — server/router/api/v1/memo_share_service.go:152-190 (share creation/listing/deletion is restricted to creator/admin at :42, :91, and the fileserver honors the same token at fileserver.go:684-690).
