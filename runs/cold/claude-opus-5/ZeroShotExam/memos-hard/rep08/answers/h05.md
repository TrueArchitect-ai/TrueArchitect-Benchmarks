**Mechanism: explicit Go code** (SQL `DELETE` statements issued in the delete-user transaction), not a database cascade.

**Evidence**

**1. The explicit deletes** — each driver's `DeleteUser` runs two reaction deletions inside one transaction:

- `store/db/sqlite/user_delete.go:96` → `deleteReactionsByContentIDsTx` (defined at :380) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500. The content IDs come from `memoContentIDsFromRefs` (:512-517), which builds `"memos/" + memo.UID` for every memo in the user's memo tree (`listDeleteUserMemoTree`, :127) — so reactions *on* the deleted user's memos/comments go too.
- `store/db/sqlite/user_delete.go:102` → `deleteReactionsByCreatorTx` (:400) — `DELETE FROM reaction WHERE creator_id = ?`, removing the user's reactions on *other* people's memos.

Identical structure at the same line numbers in `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`. All of it runs in the tx opened in `DeleteUser` and committed at the end, so a failure rolls the reactions back with everything else (`store/db/sqlite/user_delete.go:29-58`; test at `server/router/api/v1/test/user_service_delete_test.go:429-431` asserts the reaction survives a rollback).

**2. Ruling out a DB-level rule** — the `reaction` table is declared with no foreign key in any dialect:

- `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` — columns `creator_id`, `content_id` are plain `INTEGER`/`TEXT` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint.
- The original creation migrations (`store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql`) are the same, and no later migration adds a constraint (`grep -rn reaction store/migration/*/*/*.sql` only turns up 0.20 creation and the 0.23 emoji-value rewrite).
- The only `ON DELETE CASCADE` in the current schemas is `memo_share.memo_id → memo(id)` (`store/migration/*/LATEST.sql:108-109`) — nothing touching `reaction`. Also note `content_id` is a string like `memos/abc`, which couldn't be an FK to `user` or `memo` anyway.

**3. Tests confirming the behavior** — `store/test/user_delete_test.go:97-112, 217-220` and `server/router/api/v1/test/user_service_delete_test.go:188-209, 287-298`: after deletion, reactions on the user's own memo and on their comment are empty, while a third party's reaction on a foreign memo (`peerReactionOnForeignMemo`) is retained.

**Answer:** explicit Go code — `store/db/{sqlite,postgres,mysql}/user_delete.go` (`deleteReactionsByContentIDsTx`, `deleteReactionsByCreatorTx`); no FK/cascade exists on `reaction` in `store/migration/*/LATEST.sql`.
