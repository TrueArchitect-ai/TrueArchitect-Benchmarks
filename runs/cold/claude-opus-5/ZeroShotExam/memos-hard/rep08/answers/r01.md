**Premise correction:** There is no Redis connection in this repository, and no external cache server of any kind. A case-insensitive search for `redis`/`memcach` across all Go, Markdown, YAML, JSON, and TypeScript sources returns zero hits, and `go.mod` contains no Redis client dependency. This is Memos, which ships as a single Go binary — the cache layer is entirely in-process.

**Actual mechanism:**

The cache is a hand-rolled, thread-safe in-memory cache at `store/cache/cache.go`. It's backed by a `sync.Map` with an `atomic.Int64` item counter (`store/cache/cache.go:66-73`), and each entry stores an absolute `expiration` timestamp plus a rough size estimate (`store/cache/cache.go:35-39`).

Configuration lives in `store.New()` at `store/store.go:38-61`, not in any connection string:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That single config is shared by three separate cache instances (`store/store.go:27-29`, 51-53): `instanceSettingCache`, `userCache`, and `userSettingCache`. The same values are duplicated in `cache.DefaultConfig()` at `store/cache/cache.go:56-64`, though `store.New()` builds its own literal rather than calling it.

**TTL for user entries: 10 minutes.** Every write path for users calls `s.userCache.Set(...)` — `CreateUser` (`store/user.go:98`), `CreateUserIfNoUsers` (:122), `UpdateUser` (:132), `ListUsers` (:143), and `GetUser` (:167) — and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). No user code path calls `SetWithTTL` with a custom duration, so the 10-minute default is the effective user TTL. Keys are just the stringified user ID (`store/user.go:88-90`).

Two details worth noting about expiry:

- **Lazy + periodic eviction.** `Get` checks `time.Now().After(itm.expiration)` and drops the entry on read (`store/cache/cache.go:135-144`); a background goroutine started in `cache.New` sweeps expired entries every 5 minutes (`store/cache/cache.go:200-250`). So a stale user entry can outlive its TTL in memory until read or swept, but is never *served* past it.
- **Capacity eviction independent of TTL.** Exceeding `MaxItems: 1000` triggers `cleanupOldest`, which drops ~20% of max items (`store/cache/cache.go:117-119`, 253-313), so user entries can also be evicted early under load.

Invalidation is explicit on delete: `deleteUserCache` removes the user key and the associated per-setting keys (`store/user_delete.go:39-45`). All three caches' cleanup goroutines are stopped in `Store.Close()` (`store/store.go:72-79`).

Since the cache is per-process, it is not shared across replicas — a consideration only if you were planning to scale Memos horizontally, which is presumably what motivated the Redis question.
