**Premise correction:** There is no Redis in this repository. `grep -ri redis` across the entire tree returns nothing, and `go.mod` has no Redis client dependency (no `go-redis`, `redigo`, etc.). So there is no "Redis connection for the cache layer" to configure — no host, port, DSN, or `REDIS_*` env var exists.

**Actual mechanism — in-process in-memory cache**

The cache layer is a hand-rolled, thread-safe in-memory cache in `store/cache/cache.go`:

- `Cache` (`store/cache/cache.go:67`) wraps a `sync.Map` plus an `atomic.Int64` item counter. Each `item` (`store/cache/cache.go:35`) holds the value, an absolute `expiration` time, and a rough size estimate.
- Expiry is enforced lazily on `Get` (`store/cache/cache.go:135`) and eagerly by a background `cleanupLoop` goroutine (`store/cache/cache.go:200`) started in `New`.
- Capacity is bounded by `MaxItems`; overflow triggers `cleanupOldest`, which drops ~20% of `MaxItems` (`store/cache/cache.go:253`).

**Configuration** is a plain Go struct literal, not env/config-file driven. `store.New` builds it inline at `store/store.go:40-45`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

Three separate cache instances share that same config (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, `userSettingCache`. These values duplicate `cache.DefaultConfig()` (`store/cache/cache.go:57`) rather than calling it. Nothing reads a flag or env var to override them, so the TTL is compile-time fixed.

**TTL for user entries: 10 minutes.** Every write to `userCache` uses `Set`, never `SetWithTTL` — `store/user.go:98, 122, 132, 143, 167` — and `Set` applies `c.config.DefaultTTL` (`store/cache/cache.go:94`), which is the 10 minutes from `store/store.go:41`. In fact `SetWithTTL` has no non-test callers anywhere in the repo, so *every* cache entry in the system uses the 10-minute default.

Two related details:

- The cache is per-process, so it is not shared across replicas — a multi-instance deployment gets independent caches with up to 10 minutes of skew.
- Staleness is mitigated by explicit invalidation rather than short TTLs: user mutations re-`Set` the entry immediately, and `store/user_delete.go:40` calls `s.userCache.Delete`. The user cache key is just the stringified user ID (`store/user.go:88`).
