**Premise correction:** Neither. This repo (usememos/memos) has no message broker at all — there's no NATS, RabbitMQ/AMQP, Kafka, or Redis dependency anywhere in `go.mod`, and a repo-wide grep for `nats|rabbitmq|amqp` returns only one incidental hit in a Catalan UI translation string (`web/src/locales/ca.json`). There are also no separate "delivery worker" processes; it's a single Go binary.

**Actual mechanism — an in-process buffered Go channel:**

The "queue" is declared at `internal/webhook/webhook.go:39`:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are only logged (`slog.Warn`); there is no retry or dead-lettering.
- **Producer:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the 128-slot buffer is full, the payload is **dropped** with a warning — delivery is best-effort, not durable.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` fan out one `PostAsync` per user webhook registered in the store (`s.Store.GetUserWebhooks`).
- **Delivery itself:** `Post` (`internal/webhook/webhook.go:120`) does an HTTP POST via a shared `safeClient` with a 30s timeout and an SSRF-guarding dialer (`safeDialContext`, line 59), optionally adding Standard Webhooks HMAC headers (`webhook-id` / `webhook-timestamp` / `webhook-signature`).

Practical consequence: because the queue lives in process memory, pending webhooks are lost on restart, and the queue is not shared across replicas.
