**Premise correction: there is no per-user API rate-limiting middleware in this repository.** The question presupposes a component that doesn't exist, so it has no registration site and no request limits.

## What I verified

This is the **memos** project (Go backend + React frontend), not a Node/Express app. I checked every plausible location:

- **No rate-limiting dependency.** `go.mod` has no `golang.org/x/time/rate`, `tollbooth`, `ulule/limiter`, or equivalent. No `rate.NewLimiter`, `.Allow()`, or `Burst` call appears anywhere in the Go sources.
- **Echo middleware chain** (`server/server.go:51-52`) registers exactly two: `middleware.Recover()` and `newCORSMiddleware(profile)`.
- **Connect RPC interceptor chain** (`server/router/api/v1/v1.go:133-138`) registers four: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` — all defined in `server/router/api/v1/connect_interceptors.go`. None does rate limiting.
- **`internal/scheduler/middleware.go`** is job-scheduler middleware (`Recovery`, `Logging`, `Timeout`), unrelated to HTTP requests.
- **`internal/email/README.md:286-295`** discusses rate limiting, but only as a *suggested* practice in prose, with an example snippet that is not implemented anywhere.

## What likely prompted the question

There are resource limits, but they are **global concurrency caps and size limits — not per-user request-rate limits**:

| Limit | Location | Value |
|---|---|---|
| Concurrent thumbnail generation | `server/router/api/v1/v1.go:59` | `semaphore.NewWeighted(3)` |
| Concurrent image/EXIF processing | `server/router/api/v1/v1.go:60` | `semaphore.NewWeighted(2)` |
| Max API request body | `server/router/api/v1/v1.go:20` | `256 << 20` (256 MiB) |
| Default upload buffer | `server/router/api/v1/attachment_service.go:27` | `32 << 20` (32 MiB) |

The image semaphore is the closest match: `acquireImageProcessingSlot` (`server/router/api/v1/attachment_service_image.go:67-77`) blocks on acquisition, and `attachment_service.go:158-161` maps failure to `codes.ResourceExhausted` with `"too many image processing requests"`. That error string reads like rate limiting, but the mechanism differs in three ways that matter:

1. **Not per-user** — the semaphore lives on the shared `APIV1Service` struct, so all users contend for the same 2 slots.
2. **Not rate-based** — it caps *simultaneous in-flight* operations, not requests per time window. A single user can issue unlimited sequential uploads.
3. **Not middleware** — it's called inline inside the `CreateAttachment` handler, not registered in any interceptor chain.

Only requests that trip `shouldStripExif` (JPEG, TIFF, WebP, HEIC, HEIF) reach it at all; the failure is also non-blocking in the sense that acquisition only errors on context cancellation/deadline, not on contention.

**Bottom line:** if you need per-user API rate limiting here, it would have to be built — the natural insertion point is a new interceptor added to the `connect.WithInterceptors` list at `server/router/api/v1/v1.go:133`, placed after `NewAuthInterceptor` so the authenticated user identity is available to key the limiter on.
