**Answer: by explicit Go code** — reactions are deleted with explicit `DELETE FROM reaction` statements inside the user-deletion transaction, in each of the three DB drivers. There is no FK/cascade or trigger on the `reaction` table.

**Two explicit deletes, both in the same transaction:**

1. Reactions *on* the deleted user's memos (including reactions left by other users) — matched by `content_id` (`"memos/" + memo.UID`):
   - `store/db/sqlite/user_delete.go:380-388` (`deleteReactionsByContentIDsTx`), content IDs built at `:512-518` (`memoContentIDsFromRefs`)
   - postgres `store/db/postgres/user_delete.go:383`, mysql `store/db/mysql/user_delete.go:420`
2. Reactions *by* the deleted user on anyone's content — matched by `creator_id`:
   - `store/db/sqlite/user_delete.go:400-403` (`deleteReactionsByCreatorTx`), postgres `:401`, mysql `:438`

Both are invoked from `deleteUserTargetsTx` — sqlite `store/db/sqlite/user_delete.go:92-127` (lines 96 and 102), postgres `store/db/postgres/user_delete.go:92-104`, mysql `store/db/mysql/user_delete.go:92-104`. That runs inside the tx opened by `DB.DeleteUser` (`store/db/sqlite/user_delete.go:29-59`), so reaction removal commits atomically with the user row (and rolls back with it — see the `before_commit` failpoint at `:47`).

Entry points: `store.Store.DeleteUser` (`store/user.go:171-181`) → driver; called from `server/router/api/v1/user_service.go:414` and `server/router/api/v1/auth_service_sso.go:77`.

**What I checked to rule out a database-level rule:**

- `reaction` table DDL has no foreign key at all — `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (columns `creator_id`, `content_id`, `reaction_type` + a UNIQUE constraint; no `REFERENCES`).
- Grepping `FOREIGN KEY|REFERENCES|ON DELETE` across all three `LATEST.sql` files yields exactly one FK in the whole schema, and it's unrelated: `memo_share.memo_id → memo(id) ON DELETE CASCADE` (sqlite `:109`, postgres `:108`, mysql `:108`).
- Even that FK isn't enforced on SQLite — the driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`).
- No triggers touch `reaction`: the only triggers ever defined were modification-time triggers in `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql`, dropped in `store/migration/sqlite/0.7/01__remove_triggers.sql`.
- The reaction migrations (`0.20/00__reaction.sql`, `0.23/00__reactions.sql`) only create the table / rewrite `reaction_type` values to emoji — no constraints added.

One note on completeness: the `content_id` sweep only covers memos owned by the deleted user (the memo tree collected at `store/db/sqlite/user_delete.go:129-166`), and the `creator_id` sweep covers everything that user reacted to — so between the two, all rows referencing the deleted user are removed.
