**`internal/idp`; `internal/idp/oauth2`**

- **Abstraction package — `internal/idp`** (`internal/idp/idp.go`): defines the provider-neutral `IdentityProviderUserInfo` struct (`Identifier`, `DisplayName`, `Email`, `AvatarURL`) that any IdP integration must produce. The store-side abstraction mirrors this in `proto/store/idp.proto`, where `IdentityProvider.Type` and the `IdentityProviderConfig` oneof are the extension points.

- **Implementation package — `internal/idp/oauth2`** (`internal/idp/oauth2/oauth2.go`): the only concrete protocol shipped. `NewIdentityProvider(*storepb.OAuth2Config)` validates config, `ExchangeToken` performs the code exchange (with optional PKCE `codeVerifier`), and the userinfo response is mapped into `idp.IdentityProviderUserInfo` via the configured `FieldMapping`.

Wiring: `server/router/api/v1/auth_service_sso.go:13` imports `internal/idp/oauth2` and dispatches on the provider type in `resolveSSOIdentity` (line 104); persistence lives in `store/idp.go` with per-driver code in `store/db/{sqlite,postgres,mysql}/idp.go`.

Notably, `proto/store/idp.proto` declares only `TYPE_UNSPECIFIED` and `OAUTH2` in the `Type` enum and only `oauth2_config` in the config oneof — there is no SAML or dedicated OIDC implementation in the tree (OIDC providers are supported only insofar as they can be configured as generic OAuth2 endpoints).
