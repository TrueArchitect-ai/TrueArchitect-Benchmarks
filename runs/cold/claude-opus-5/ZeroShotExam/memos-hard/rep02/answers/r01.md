**Premise correction:** There is no Redis in this repository. A repo-wide search for `redis`/`memcached` (Go, Markdown, YAML, JSON, TS/TSX) returns zero hits, and `go.mod` has no Redis client dependency. There is no external cache server, no connection string, and no cache-related environment variable to configure. The cache layer is a hand-rolled, **in-process, in-memory** cache.

**Actual mechanism**

*Implementation* — `store/cache/cache.go` defines a thread-safe in-memory cache built on `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-85`). Entries are `item` structs carrying the value, an absolute `expiration` time, and a rough size estimate (`store/cache/cache.go:35-39`). Expiry is enforced both lazily on `Get` (`store/cache/cache.go:135-144`) and by a background `cleanupLoop` goroutine ticking on `CleanupInterval` (`store/cache/cache.go:200-250`). When `MaxItems` is exceeded, `cleanupOldest` evicts roughly 20% of capacity by soonest expiration (`store/cache/cache.go:253-313`).

*Configuration* — There is no connection setup; the cache is constructed in-process in `store.New` (`store/store.go:38-61`). One `cache.Config` literal is built there and shared by all three caches:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

It backs `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`, `store/store.go:51-53`). These values are hardcoded — not read from env, flags, or config files. `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) holds an identical duplicate set of values but is not used by the store.

*TTL for user entries* — **10 minutes**, inherited from the shared `DefaultTTL`. Every user write path calls plain `Set`, which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`): `CreateUser` (`store/user.go:98`), `CreateUserIfNoUsers` (`store/user.go:122`), `UpdateUser` (`store/user.go:132`), and the list/get paths (`store/user.go:143`, `store/user.go:167`). Keys are the plain user ID as a string (`store/user.go:88-90`). Nothing in the codebase calls `SetWithTTL` directly, so user entries never get a per-entry TTL override. Staleness is bounded in practice by write-through updates on every mutation and explicit invalidation on delete via `deleteUserCache`, which drops the user key and its associated user-setting keys (`store/user_delete.go:39-47`).

*Scope caveat* — Because this is per-process memory, the cache is not shared across instances; a multi-replica deployment would have independent caches with independent 10-minute expiries.

**Other caches** (unrelated to user entries, for completeness): `userSettingCache` keyed `"<userID>-<settingKey>"` (`store/cache.go:7-9`), and a separate single-value instance-stats memo with its own 60-second TTL at `server/router/api/v1/instance_stats.go:21`.
