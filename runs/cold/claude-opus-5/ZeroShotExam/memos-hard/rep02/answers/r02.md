**Premise correction: this repository has no per-user API rate-limiting middleware.** There is no rate limiter registered anywhere — no interceptor, no Echo middleware, no limiter library (`golang.org/x/time/rate`, tollbooth, etc. are absent from `go.mod`), and no per-user request counters or 429/`ResourceExhausted` throttling keyed on identity.

What actually exists at the middleware layer:

- **Echo middleware** — `server/server.go:51-52`: only `middleware.Recover()` and `newCORSMiddleware(profile)`.
- **Connect RPC interceptor chain** — `server/router/api/v1/v1.go:133-138`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). Auth/authorization only — no throttling.

The limits that do exist are **size and global-concurrency caps, not per-user request rates**:

| Limit | Value | Location |
|---|---|---|
| Max API request body | 256 MiB (`256 << 20`) | `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` and `connect.WithReadMaxBytes` at `v1.go:126,141,144` |
| Upload size | instance setting `UploadSizeLimitMb`, defaulting to 32 MiB | `server/router/api/v1/attachment_service.go:27,120-131` |
| Concurrent thumbnail generation | 3 (process-wide semaphore) | `server/router/api/v1/v1.go:59`; also `server/router/fileserver/fileserver.go:46,116` |
| Concurrent image/EXIF processing | 2 (process-wide semaphore) | `server/router/api/v1/v1.go:60`, acquired in `attachment_service_image.go:67-78`, used at `attachment_service.go:157-161` |

Those semaphores are the only source of a `ResourceExhausted` ("too many image processing requests") error, and they're global across all users — a single client can occupy all slots.

The only mention of rate limiting in the codebase is aspirational documentation for email sending: `internal/email/doc.go:86` and `internal/email/README.md:286-295` list it as a suggested future hardening step, not implemented code.
