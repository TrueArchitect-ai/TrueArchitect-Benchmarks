**Premise correction:** Neither. This repo (memos, a Go monolith) has no message broker at all — `go.mod` and `go.sum` contain zero matches for NATS, RabbitMQ/AMQP, Kafka, or Redis. There is no external queue to declare and no separate worker process; webhook delivery happens inside the single server binary.

**Actual mechanism — an in-process buffered Go channel:**

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel with capacity 128.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` starts a fixed pool of **4 goroutines**, each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are logged with `slog.Warn` only; there is no retry or dead-letter path.
- **Producer:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning ("Dropped webhook dispatch because the async queue is full") — delivery is best-effort, not durable. Nil payloads are dropped too.
- **Delivery itself:** `Post` (`internal/webhook/webhook.go:120`) does a plain `http.Client` POST via `safeClient` (30s timeout, SSRF-guarded dialer at `webhook.go:59` that rejects reserved/private IPs), optionally signing with Standard Webhooks HMAC-SHA256 (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers).
- **Call sites (enqueuers):** `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, plus user webhook config in `server/router/api/v1/user_service_webhooks.go`.

Practical consequence: because the queue lives in process memory, anything still buffered is lost on restart or crash, and bursts beyond 128 pending payloads are silently discarded.
