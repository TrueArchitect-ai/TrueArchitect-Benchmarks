h15.

Memo visibility is enforced in **ten** distinct places across the Go server (plus the store-level filter that all list queries funnel through). They are independent implementations, not one shared helper.

**Core API (Connect/gRPC) — single-memo read gate**
`checkMemoReadAccess` (public → open; non-public → must be authenticated; PRIVATE → must be creator; archived → creator only) — `server/router/api/v1/memo_service.go:39-66`, called from `GetMemo` and its parent-memo check (`:356`, `:367`) and from `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`)

**Core API — list-query filter injection**
`ListMemos` injects `VisibilityList`/CEL filter based on caller (anon → PUBLIC; other user's memos → PUBLIC+PROTECTED; own → all) — `server/router/api/v1/memo_service.go:217-226`, plus the comment-list filter at `server/router/api/v1/memo_service_comments.go:155-165`

**Core API — user stats/tag aggregation**
Same anon/other-user visibility narrowing, re-implemented for stats — `server/router/api/v1/user_service_stats.go:84-92` and `:216-221`

**Comment creation gate**
Blocks commenting on a PRIVATE memo you don't own — `server/router/api/v1/memo_service_comments.go:35-43`

**Reactions**
`ListMemoReactions` (`:29-41`) and `UpsertMemoReaction` (`:81-85`) re-derive access from the parent memo's visibility — `server/router/api/v1/reaction_service.go`

**Attachment metadata via API**
`checkAttachmentAccess` — linked attachments inherit the memo's visibility — `server/router/api/v1/attachment_service.go:422-455`; and `ListMemoAttachments` does its own copy — `server/router/api/v1/memo_attachment_service.go:213-226`

**Raw file/blob serving (non-gRPC HTTP surface)**
`checkAttachmentPermission` — separate rules: PUBLIC only served anonymously if `AllowAnonymous()`, plus a `share_token` query-param bypass, then PRIVATE → creator or admin — `server/router/fileserver/fileserver.go:650-703`

**SSE live-event delivery filter**
`SSEClient.canReceive` — PRIVATE events only to creator or admin; unknown visibility denied — `server/router/api/v1/sse_hub.go:134-143` (event visibility populated in `server/router/api/v1/sse_event_helpers.go:29-37`)

**Anonymous public surfaces (hard-coded PUBLIC only)**
RSS explore + per-user feeds — `server/router/rss/rss.go:90` and `:141`; sitemap — `server/router/frontend/frontend.go:150`

**Notifications**
`canViewerAccessMemo` — two independent copies: in-app notifications `server/router/api/v1/user_service_notifications.go:302-321` (used at `:337`, `:342`, `:370`, `:385`) and email `server/notification/email.go:306-321` (used at `:155`, `:187`); mention fan-out has its own variant `canUserAccessMentionContext` — `server/router/api/v1/memo_mention_helpers.go:56-89`

**Share-token bypass (deliberate hole in the above)**
`GetMemoByShare` resolves a token straight to the memo with no visibility check — the token is the authorization; only expiry/archived are checked — `server/router/api/v1/memo_share_service.go:152-192`

**Underlying mechanism (not a policy site)**
`FindMemo.VisibilityList` — `store/memo.go:69`, rendered to SQL per driver in `store/db/sqlite/memo.go:96`, `store/db/postgres/memo.go:89`, `store/db/mysql/memo.go:104`

One note: the MCP surface (`server/router/mcp/`) contains no visibility logic of its own — `server/router/mcp/adapter.go:27-92` forwards tool calls to the HTTP API with the caller's `Authorization` header, so it inherits the API v1 checks rather than duplicating them.
