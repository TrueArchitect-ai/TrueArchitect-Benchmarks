**No** — outside `NewDBDriver`, the MySQL driver is never constructed in production code. The only other direct construction is a `&DB{}` zero-value literal inside the package's own unit test.

**Evidence:**

1. **The factory is the sole caller of the constructor.** `store/db/db.go:22` calls `mysql.NewDB(profile)` inside `NewDBDriver`. A repo-wide grep for `mysql.NewDB` / imports of `github.com/usememos/memos/store/db/mysql` returns exactly two hits, both in that one file:
   - `store/db/db.go:8` (the import)
   - `store/db/db.go:22` (the call)

   No other package — including `cmd/`, `server/`, and the test helpers — imports `store/db/mysql`.

2. **All test paths go through the factory too.** `store/test/store.go:28` and `store/test/store.go:50`, plus `server/router/api/v1/test/memo_service_benchmark_test.go:70`, obtain their driver via `db.NewDBDriver(profile)`, driven by the driver name (`store/test/main_test.go:25` iterates `[]string{"sqlite", "mysql", "postgres"}`). They never touch the `mysql` package directly.

3. **Struct-literal construction of `mysql.DB`** (which would bypass `NewDB`) occurs in only two places:
   - `store/db/mysql/mysql.go:29` — `driver := DB{profile: profile}`, i.e. inside `NewDB` itself.
   - `store/db/mysql/auth_config_test.go:12` — `db := &DB{}`, an in-package unit test for `IsRetryableAuthenticationMutationError`, which only needs a receiver and no live connection. Since the field `db *sql.DB` is unexported, this is only possible from within the `mysql` package.

So the driver-selection factory in `store/db/db.go` is the single construction point; the lone exception is a package-internal test using an empty struct rather than the constructor. (The same pattern holds for Postgres: `store/db/postgres/auth_config_test.go:12`.)
