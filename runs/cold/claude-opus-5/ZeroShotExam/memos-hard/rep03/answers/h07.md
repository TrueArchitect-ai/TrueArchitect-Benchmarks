The browser hits `GET /file/users/{username}/avatar` — that URL is what the API hands back in `User.avatar_url` when the stored avatar is a base64 data URI. Avatar bytes live in the `user.avatar_url` column as a data URI (no blob store, no S3), so the "data layer" hop is a plain user row read.

Two details worth noting:

- **The user cache is bypassed here.** `Store.GetUser` only consults `s.userCache` when `find.ID != nil` (store/user.go:149-156); the handler looks up by `Username`, so every avatar request falls through to `ListUsers` → driver → SQL. The row is written into the cache on the way back (store/user.go:143, 167), but never read from it on this path.
- **Access control is coarse.** Any user's avatar is served to anyone on a public instance (`Profile.AllowAnonymous()`); on a private instance any authenticated viewer suffices — there's no per-target-user check, unlike `checkAttachmentPermission` for attachments.
