**Mechanism: explicit Go code** — the `reaction` table has no foreign key, cascade, or trigger in any schema, so cleanup happens entirely in hand-written SQL inside the driver's `DeleteUser` transaction, in two passes: reactions *on* the deleted user's memos (by `content_id`) and reactions *left by* the user elsewhere (by `creator_id`).

**What I checked**

1. **Delete path.** `store.Store.DeleteUser` (`store/user.go:171`) just delegates to `s.driver.DeleteUser`. Each driver implements it identically:
   - `store/db/sqlite/user_delete.go`
   - `store/db/postgres/user_delete.go`
   - `store/db/mysql/user_delete.go`

2. **The two reaction deletes**, both called from `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`, same structure in the other two drivers):
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (`sqlite/user_delete.go:380-388`, `postgres:380`, `mysql:417`). Content IDs come from `memoContentIDsFromRefs` (`sqlite/user_delete.go:512`), which builds `"memos/" + uid` from the recursive memo tree (`listDeleteUserMemoTreeRecursive`, line 133) — so reactions on the user's memos *and* their comment descendants go too.
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`sqlite/user_delete.go:400-403`, `postgres:400`, `mysql:437`), removing the user's reactions on other people's memos.
   
   Both run inside the transaction opened in `DeleteUser` and committed only after the `user` row is deleted, so a failure rolls the reactions back.

3. **No DB-level rule.** Grepping `REFERENCES|FOREIGN KEY|ON DELETE` across `store/migration/{sqlite,postgres,mysql}/LATEST.sql` returns exactly one hit per dialect — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (e.g. `store/migration/sqlite/LATEST.sql:109`). The `reaction` table (`sqlite/LATEST.sql:92-99`, `postgres:91-98`, `mysql:91-98`) declares only a PK and a `UNIQUE(creator_id, content_id, reaction_type)` — no FK on `creator_id` or `content_id` (`content_id` is a text resource name, so it couldn't cascade anyway). The original creation migrations `store/migration/*/0.20/00__reaction.sql` are identical — the table never had an FK. No triggers touch `reaction`.

4. **Tests confirm the behavior.** `server/router/api/v1/test/user_service_delete_test.go:287-298` asserts reactions on the deleted user's memo and on their comment are empty while a third party's reaction on a foreign memo survives; `store/test/user_delete_test.go:217-220` asserts the same at the store layer. `user_service_delete_test.go:429-431` checks the reaction is still present after a forced rollback, confirming it's transactional.
