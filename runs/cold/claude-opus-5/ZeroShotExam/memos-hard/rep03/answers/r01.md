**Premise correction:** There is no Redis connection in this repository, and nothing to configure. Memos ships as a single Go binary whose only external datastore is the SQL database (SQLite/MySQL/Postgres — see `go.mod` drivers). A grep for `redis` across the entire tree returns zero hits, and there is no Redis dependency in `go.mod`. The cache layer is a hand-rolled, in-process, in-memory cache — so there is no connection string, host, port, or password anywhere.

**Actual mechanism**

*The cache implementation* — `store/cache/cache.go`:
- A thread-safe in-memory cache built on `sync.Map` plus an atomic item counter (`Cache`, line 67).
- Each entry (`item`, line 35) stores the value, an absolute `expiration` time, and a rough size estimate.
- A background goroutine (`cleanupLoop`, line 200) ticks on `CleanupInterval` and evicts expired entries; `Get` (line 123) also lazily evicts on read when `time.Now().After(itm.expiration)`.
- Over-capacity writes trigger `cleanupOldest` (line 253), which drops ~20% of `MaxItems`.

*Where it's "configured"* — `store/store.go`, in `New()`. The config is hardcoded in Go, not read from env or a config file:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That same struct is passed to all three caches held on `Store`: `instanceSettingCache`, `userCache`, and `userSettingCache`. (`cache.DefaultConfig()` at `store/cache/cache.go:57` declares the identical values independently, but the store does not call it.)

*TTL for user entries* — **10 minutes**, with expiry observed within up to 5 minutes of slack by the sweeper (or immediately on the next `Get`). Every user write path calls plain `Set`, which delegates to `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:93-95`) — no caller anywhere in the codebase invokes `SetWithTTL` directly, so users get no special TTL. Populating call sites are in `store/user.go`: `CreateUser` (:98), `CreateUserIfNoUsers` (:122), `UpdateUser` (:132), `ListUsers` (:143, warms the cache for every listed user), and `GetUser` (:167). The cache key is just the decimal user ID (`userCacheKey`, `store/user.go:88`).

Note the TTL is mostly a backstop rather than the primary consistency mechanism: `GetUser` only consults the cache on ID lookups (`store/user.go:149-156`), writes refresh the entry eagerly, and deletion invalidates explicitly via `deleteUserCache` (`store/user_delete.go:39-47`), which also clears that user's per-setting entries keyed by `getUserSettingCacheKey` (`store/cache.go:6-8`).

One consequence worth flagging since it follows directly from there being no Redis: this cache is per-process and unshared, so a multi-replica Memos deployment behind a load balancer can serve up to 10-minute-stale user data from replicas that didn't handle the write.
