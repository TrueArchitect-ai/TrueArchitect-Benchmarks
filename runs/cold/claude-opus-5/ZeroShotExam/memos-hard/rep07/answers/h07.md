The browser gets an avatar URL like `/file/users/{username}/avatar` (the API converter rewrites base64 avatars into that path), then requests it; the fileserver resolves the user row and decodes the stored data URI.

**Origin of the URL the browser requests**
- `convertUserFromStore` — `server/router/api/v1/user_service_converters.go:36` (rewrites base64 `AvatarURL` to `/file/{users/{username}}/avatar`, name built by `BuildUserName` — `server/router/api/v1/user_resource_name.go:13`)
- `UserAvatar` — `web/src/components/UserAvatar.tsx:12` (`<img src={avatarUrl}>` issues the GET)

**Serving path**
- `FileServerService.RegisterRoutes` — `server/router/fileserver/fileserver.go:124` (route `GET /file/users/:identifier/avatar`; wired in `server/server.go:81-82`)
- `FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go:164` (auth gate for private instances via `getCurrentUser` → `auth.Authenticator.AuthenticateToUser`, fileserver.go:600)
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:608`
- `Store.GetUser` — `store/user.go:148` (checks `userCache` only when finding by ID; username lookups fall through)
- `Store.ListUsers` — `store/user.go:136` (delegates to `s.driver`, then populates `userCache`)
- `Driver.ListUsers` — `store/driver.go:47` (interface; driver set in `store/store.go:38-48`)
- `DB.ListUsers` — `store/db/sqlite/user.go:88` (SQL `SELECT ... avatar_url ... FROM user WHERE username = ?`; MySQL/Postgres equivalents at `store/db/mysql/user.go`, `store/db/postgres/user.go`)

**Back out to bytes**
- `FileServerService.parseDataURI` — `server/router/fileserver/fileserver.go:630` (base64-decodes `user.AvatarURL`), then MIME check against `avatarAllowedTypes` (fileserver.go:73) and `c.Blob` response with `nosniff`/CSP headers.

So the avatar image is not a file on disk or in S3 — it is stored inline as a base64 data URI in the `user.avatar_url` column, unlike attachments which go through `serveAttachmentFile` and local/S3/blob storage.
