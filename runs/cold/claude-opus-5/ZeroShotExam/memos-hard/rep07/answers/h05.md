**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the driver-level `DeleteUser` transaction. There is no DB-level cascade for reactions.

## What happens

`Store.DeleteUser` (`store/user.go:171`) delegates to the driver's `DeleteUser`, which opens a transaction and calls `deleteUserTargetsTx`. That function issues **two** distinct reaction deletes (`store/db/sqlite/user_delete.go:91-104`):

1. `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`sqlite/user_delete.go:380-388`). The content IDs are `"memos/" + memo.UID` for every memo in the deleted user's memo tree, including their comments (`memoContentIDsFromRefs`, `sqlite/user_delete.go:512-518`; tree gathered by `listDeleteUserMemoTreeRecursive`). This removes *everyone's* reactions on the departing user's memos.
2. `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`sqlite/user_delete.go:400-403`). This removes the departing user's reactions left on *other* people's memos.

Both run before the memo and user rows are deleted, all inside one transaction that is committed at `sqlite/user_delete.go:52`.

The same code exists per driver:
- `store/db/sqlite/user_delete.go:96, 102, 380, 400`
- `store/db/postgres/user_delete.go:96, 102, 380, 400`
- `store/db/mysql/user_delete.go:96, 102, 417, 437`

## Why it is not a DB rule

- The `reaction` table has **no foreign key at all** on `creator_id` or `content_id` in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. `content_id` is a text resource name (`memos/<uid>`), so it could not be a FK anyway.
- Historic FKs were dropped in `store/migration/sqlite/0.7/00__remove_fk.sql`; the only remaining `ON DELETE CASCADE` in the current schema is `memo_share.memo_id → memo.id` (`LATEST.sql:109`), unrelated to reactions.
- Even if a FK existed, SQLite runs with enforcement disabled: `store/db/sqlite/sqlite.go:53` opens the DSN with `_pragma=foreign_keys(0)`.

## Test evidence

- `store/test/user_delete_test.go:97-112, 217-220` — seeds reactions, asserts the peer's reaction on a peer memo survives.
- `server/router/api/v1/test/user_service_delete_test.go:188-209, 287-298` — asserts reactions on the deleted user's own memo and on their comment are empty, while a peer's reaction on a foreign memo is retained.
- `server/router/api/v1/test/user_service_delete_test.go:366-431` — with the `before_commit` failpoint (`store/user_delete.go:14`), the reaction is still present after rollback, confirming the deletes are transactional rather than driven by a separate DB rule.
