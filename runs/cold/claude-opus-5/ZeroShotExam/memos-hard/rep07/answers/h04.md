**No** — in production code the MySQL store driver is only ever constructed by the factory. The one exception is a single unit test that builds a zero-value struct in-package.

Evidence:

- `store/db/db.go:14-32` — `NewDBDriver(profile)` is the sole selection factory; line 22 (`driver, err = mysql.NewDB(profile)`) is the only call to `mysql.NewDB` in the repo.
- `store/db/mysql/mysql.go:20` is the only exported constructor (`func NewDB(profile *profile.Profile) (store.Driver, error)`), and it internally builds `DB{profile: profile}` at line 29.
- `grep -rn "usememos/memos/store/db/mysql"` across all `*.go` returns exactly one hit: `store/db/db.go:8`. No other package imports the MySQL driver package, so it cannot be constructed elsewhere from outside.
- All other driver acquisition goes through the factory, e.g. the test harness at `store/test/store.go:28` and `store/test/store.go:50` call `db.NewDBDriver(profile)` and pick MySQL only via `profile.Driver` (`store/test/store.go:88`).

The one direct construction:

- `store/db/mysql/auth_config_test.go:12` — `db := &DB{}`, an in-package zero-value struct used purely to invoke `IsRetryableAuthenticationMutationError` on MySQL error codes. It never opens a connection, so it isn't a functioning driver instance.

Not to be confused with driver construction: `store/test/containers.go:145` calls `sql.Open("mysql", dsn)` and `store/test/containers.go:363` calls `mysqldriver.ParseDSN`. Those use the third-party `go-sql-driver/mysql` package for testcontainer setup, not the memos `store/db/mysql` driver.
