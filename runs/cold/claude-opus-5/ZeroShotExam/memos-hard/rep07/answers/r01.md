**Premise correction:** There is no Redis anywhere in this repository. `go.mod` has no Redis (or Memcached) dependency, and a case-insensitive search for `redis` across Go, TypeScript, Markdown, YAML, and JSON files returns zero hits. There is no external cache server, no connection string, and no cache-related environment variable to configure. Memos ships as a single Go binary, and its cache layer is a purely in-process, in-memory one.

**Actual mechanism:**

*The cache implementation* — `store/cache/cache.go` defines a thread-safe in-memory cache built on `sync.Map` plus an `atomic.Int64` item counter. Each entry (`item`, line 35) stores the value, an absolute `expiration` time, and a rough size estimate. A background goroutine (`cleanupLoop`, line 200) ticks on `CleanupInterval` and evicts expired entries; `Get` (line 123) also lazily evicts on read when `time.Now().After(itm.expiration)`. When the item count exceeds `MaxItems`, `cleanupOldest` (line 253) drops roughly 20% of the cap.

*Where it's "configured"* — in Go code, not config files: `store/store.go:40-45`, in `store.New()`. The literal `cache.Config` there is the only place cache behavior is set:

- `DefaultTTL: 10 * time.Minute`
- `CleanupInterval: 5 * time.Minute`
- `MaxItems: 1000`
- `OnEviction: nil`

That same config value is handed to all three caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`) — so they are separate `*cache.Cache` instances that happen to share identical settings. (`cache.DefaultConfig()` at `store/cache/cache.go:57` returns the same three values, but the store doesn't call it; it duplicates the literal.)

**TTL for user entries: 10 minutes**, inherited from `DefaultTTL`. Nothing in the user path calls `SetWithTTL` — every write goes through `Set`, which forwards to `SetWithTTL(..., c.config.DefaultTTL)` (`store/cache/cache.go:93-95`). In fact `SetWithTTL` is never called outside of `store/cache/cache_test.go`, so 10 minutes is the effective TTL for all cached data.

Two details worth knowing about the user cache specifically:

- The key is just the stringified user ID (`userCacheKey`, `store/user.go:88`), so the cache is only consulted when `find.ID` is set (`store/user.go:150`); lookups by username or email always hit the database.
- The TTL rarely governs freshness in practice, because writes and invalidations are explicit: `CreateUser`, `CreateUserIfNoUsers`, `UpdateUser`, `ListUsers`, and `GetUser` all re-`Set` the entry (`store/user.go:98,122,132,143,167`), and `store/user_delete.go:40` calls `userCache.Delete`. The 10-minute expiry is the backstop, not the primary consistency mechanism.

One consequence of the in-memory design: since the cache lives in the process rather than in a shared store, it is not coherent across multiple Memos instances pointed at the same database.
