**`internal/idp`; `internal/idp/oauth2`**

- `internal/idp/idp.go` — the abstraction package. It's deliberately minimal: it defines only the provider-neutral `IdentityProviderUserInfo` struct (`Identifier`, `DisplayName`, `Email`, `AvatarURL`) that every provider must produce.
- `internal/idp/oauth2/oauth2.go` — the sole concrete protocol implementation. Package comment: "implements the OAuth2 identity provider integration." It exposes `NewIdentityProvider(*storepb.OAuth2Config)`, `ExchangeToken` (with optional PKCE `code_verifier`), and `UserInfo`, which maps arbitrary claims onto `idp.IdentityProviderUserInfo` via the configured `FieldMapping`.

Supporting evidence:
- The proto enums list exactly one provider type: `OAUTH2 = 1` in both `proto/store/idp.proto:13` and `proto/api/v1/idp_service.proto:79` — no SAML/OIDC variants ship.
- `server/router/api/v1/auth_service_sso.go:12-13` is the only consumer, importing both packages and constructing the provider at line 121 via `oauth2.NewIdentityProvider(identityProvider.Config.GetOauth2Config())`.

One caveat on the phrasing "provider abstraction": there is no Go `interface` type here. `internal/idp` is a shared data-contract package rather than a polymorphic dispatch point, and the SSO handler calls the OAuth2 constructor directly instead of selecting an implementation behind an interface. So the abstraction is structural (a common user-info shape) rather than behavioral.
