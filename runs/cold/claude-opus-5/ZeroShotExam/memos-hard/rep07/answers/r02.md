**The premise is incorrect — this repository (Memos, a Go/Echo + Connect/gRPC-Gateway app) has no per-user API rate-limiting middleware at all.** There is nothing registered, and therefore no request limits to report.

**What I checked:**

- **The Echo middleware stack** — `server/server.go:51-52` registers exactly two: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:13`). Plus static/SPA-fallback middleware for the frontend at `server/router/frontend/frontend.go:54-63`.
- **The API interceptor chain** — `server/router/api/v1/v1.go:133-138` wires four Connect interceptors: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). The gRPC-Gateway path has one middleware, `gatewayAuthMiddleware` (`server/router/api/v1/v1.go:69-97`), which does authentication/ACL only — no counting or quota.
- **No limiter dependency in use** — `golang.org/x/time` appears in `go.mod:151` but is marked `// indirect`, and no Go file calls `rate.NewLimiter`. There are no `tollbooth`, `ulule/limiter`, or `throttled` dependencies, and no code anywhere returns HTTP 429 / `ResourceExhausted`.

**Where the "rate limiting" phrase does appear** — both are documentation suggesting it as a practice a *caller* might adopt, not implemented code:

- `internal/email/README.md:286-297` — a "### 5. Implement Rate Limiting" section with an illustrative snippet (`rate.NewLimiter(rate.Every(time.Second), 10)`, i.e. 10 emails/sec). This is example prose about SMTP sending, not an HTTP middleware, and the snippet is not wired into anything.
- `internal/email/doc.go:86` — a security-considerations bullet: "Rate limit email sending to prevent abuse."

**The limits that do exist** are per-request size and global concurrency caps, not per-user request rates:

- `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` to `/api/v1/*` and `/file/*` (line 126), to the Connect mux (line 144), and as `connect.WithReadMaxBytes` (line 141).
- Process-wide concurrency semaphores at `server/router/api/v1/v1.go:59-60` — 3 concurrent thumbnail generations, 2 concurrent image processings — and `server/router/fileserver/fileserver.go:116`. These are shared across all users, so they bound server load but do not limit any individual user's request rate.

If you're looking to add per-user rate limiting, the natural insertion point would be a new interceptor in the `connect.WithInterceptors(...)` chain at `server/router/api/v1/v1.go:133`, placed after `NewAuthInterceptor` so the caller's identity is already on the context — though note the gRPC-Gateway path at line 97 is a separate chain and would need its own middleware to be covered.
