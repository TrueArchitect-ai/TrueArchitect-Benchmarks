Memo visibility is enforced in many separate places — there is no single chokepoint. The distinct enforcement sites:

**Core memo read path (Connect/gRPC API v1)**
- `checkMemoReadAccess` — shared per-memo gate (archived → creator only; non-public → must be authed; private → creator only). Used by `GetMemo` (incl. the parent memo of a comment) and `ListMemoComments` — `server/router/api/v1/memo_service.go:39-67`, called at `:356`, `:367`, and `server/router/api/v1/memo_service_comments.go:148`
- `ListMemos` query scoping — anonymous ⇒ `VisibilityList = [PUBLIC]`; authed ⇒ CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` — `server/router/api/v1/memo_service.go:218-228`
- `ListMemoComments` child-memo scoping (separate from the parent gate above) — `server/router/api/v1/memo_service_comments.go:155-161`
- `CreateMemoComment` pre-check on the parent memo — `server/router/api/v1/memo_service_comments.go:34-42`
- `ListMemoRelations` related-memo scoping — `server/router/api/v1/memo_relation_service.go:107-112`
- User stats (`ListAllUserStats` and `GetUserStats`) — `server/router/api/v1/user_service_stats.go:77-91` and `:217-221`

**Memo-adjacent resources**
- Reactions: `ListMemoReactions` (`:29-42`) and `UpsertMemoReaction` (`:82-84`) — `server/router/api/v1/reaction_service.go`
- `ListMemoAttachments` — `server/router/api/v1/memo_attachment_service.go:213-225`
- `checkAttachmentAccess` (attachment reached via its owning memo) — `server/router/api/v1/attachment_service.go:422-455`

**Non-gRPC HTTP surfaces**
- Raw file/blob serving `checkAttachmentPermission`, including the anonymous-instance rule and the `share_token` bypass — `server/router/fileserver/fileserver.go:650-703`
- SSE broadcast fan-out `SSEClient.canReceive` (private events only to creator or admin) — `server/router/api/v1/sse_hub.go:134-144`, event visibility stamped in `server/router/api/v1/sse_event_helpers.go:29-37`
- RSS feeds (explore + per-user), hardcoded `VisibilityList = [PUBLIC]` — `server/router/rss/rss.go:90` and `:141`
- Sitemap XML, `VisibilityList = [PUBLIC]` — `server/router/frontend/frontend.go:150`
- Share links: `GetMemoByShare` intentionally bypasses visibility on a valid unexpired token; create/list/delete restricted to creator/admin — `server/router/api/v1/memo_share_service.go:42-44`, `:88-90`, `:133-135`, `:152-185`

**Notification/outbound paths (duplicated logic)**
- `canViewerAccessMemo` for rendering notification payloads — `server/router/api/v1/user_service_notifications.go:302-316`
- A second, independent `canViewerAccessMemo` copy for outbound email — `server/notification/email.go:306-320`
- `canUserAccessMentionContext` / `shouldSkipMentionInbox` for mention delivery — `server/router/api/v1/memo_mention_helpers.go:56-89`

**Storage layer (mechanism, not policy)**
- `FindMemo.VisibilityList` / CEL filters translated to SQL — `store/memo.go:69`, `store/db/sqlite/memo.go:96`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go`; `visibility` field defined in `internal/filter/schema.go:162-166`

Two notes: the MCP surface is not a separate site — `server/router/mcp/catalog.go:12` proxies `MemoService_ListMemos` into the same API v1 service, so it inherits those checks. And ACL config explicitly defers to the service layer rather than gating at the router (`server/router/api/v1/acl_config.go:32`, `server/router/api/v1/v1.go:74`), which is why the checks are spread this widely.
