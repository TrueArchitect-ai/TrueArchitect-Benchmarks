**Mechanism: explicit Go code.** Reactions are deleted by hand-written `DELETE FROM reaction` statements inside the driver-level `DeleteUser` transaction — there is no foreign key or `ON DELETE CASCADE` on the `reaction` table in any of the three dialects.

**Two explicit deletes, run in the same transaction as the user delete:**

Each driver's `deleteUserTargetsTx` calls both, before the memo/user rows go away:
- `deleteReactionsByContentIDsTx` — removes *all* reactions (by anyone) on the deleted user's memo tree, keyed on `content_id IN ('memos/<uid>', …)`, batched at 500.
- `deleteReactionsByCreatorTx` — removes the deleted user's own reactions on *other* people's memos, via `DELETE FROM reaction WHERE creator_id = ?`.

The memo tree fed to the first delete is gathered recursively (comments on comments included) by `listDeleteUserMemoTree`, and converted to `memos/<uid>` content IDs by `memoContentIDsFromRefs` (e.g. `store/db/sqlite/user_delete.go:512-518`).

**What I checked to rule out a DB-level rule:**
- The `reaction` table DDL has no FK at all — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (same in the original `0.20/00__reaction.sql` migrations).
- Grepped for `CASCADE`/`FOREIGN KEY` across `store/`: the only cascade in current schema is `memo_share.memo_id → memo(id)` (`store/migration/*/LATEST.sql:108-109`). Legacy user FKs were dropped in `store/migration/sqlite/0.7/00__remove_fk.sql`.
- SQLite additionally opens the DB with foreign keys disabled — `_pragma=foreign_keys(0)` at `store/db/sqlite/sqlite.go:53` — so even a declared FK wouldn't cascade there.
- No triggers on `reaction` anywhere in the migration tree.
