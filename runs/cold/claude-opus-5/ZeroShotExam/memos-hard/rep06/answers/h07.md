**Details worth knowing:**

- The avatar is not a file on disk or in S3 — it's a base64 **data URI stored inline in the `user.avatar_url` column**. `serveUserAvatar` decodes it with `parseDataURI` (fileserver.go:737), validates the MIME type against `avatarAllowedTypes` (fileserver.go:75), and writes it with `c.Blob` (fileserver.go:209).
- The URL the browser requests is manufactured server-side: the gRPC/REST `User` message never ships raw base64 to the client — `convertUserFromStore` swaps `user.AvatarURL` for `/file/{name}/avatar` where `name` is `users/{username}` from `BuildUserName`, so any user list/get response makes the frontend fetch the file route.
- **Auth on the other-user case:** only gated by instance openness — `s.Profile.AllowAnonymous()` (fileserver.go:173). On a public instance any avatar is served to anonymous callers; on a private instance any authenticated viewer (session cookie, access token, or PAT via `getCurrentUser` → `auth.Authenticator.AuthenticateToUser`, fileserver.go:708) may fetch *any* user's avatar. There is no per-user ownership check.
- **Cache hop:** `Store.GetUser` only consults `userCache` when `find.ID` is set (store/user.go:149). The fileserver looks up by `Username`, so this path always falls through to `ListUsers` → driver → SQL, then populates the cache by ID.
- Wiring: `server/server.go:81-82` constructs the service and registers the routes.

The route is exercised end-to-end in `server/router/fileserver/fileserver_test.go:506` (`TestServeUserAvatar_PrivateInstanceRequiresAuth`).
