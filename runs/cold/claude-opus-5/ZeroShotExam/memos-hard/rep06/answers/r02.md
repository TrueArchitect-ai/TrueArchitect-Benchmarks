**Premise correction: this repository (Memos) has no per-user API rate-limiting middleware.** There is no rate limiter registered anywhere, and therefore no per-user request limits to report. `golang.org/x/time` (which would provide `rate.Limiter`) appears in `go.mod:151` only as an **indirect** dependency, with zero imports in the Go source.

**What is actually registered on the request path:**

- Echo middleware — `server/server.go:51-52`: only `middleware.Recover()` and `newCORSMiddleware(profile)`.
- Connect RPC interceptors — `server/router/api/v1/v1.go:133-138`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). Auth only; no throttling.
- Frontend middleware — `server/router/frontend/frontend.go:54,59`: static file serving and SPA fallback.
- A gateway auth wrapper for the grpc-gateway routes — `server/router/api/v1/v1.go:69`.

**The limits that do exist are global, not per-user**, and are best described as concurrency and size caps:

| Limit | Value | Location |
|---|---|---|
| Concurrent image (EXIF-strip) processing | 2 | `server/router/api/v1/v1.go:60` |
| Concurrent thumbnail generation (API) | 3 | `server/router/api/v1/v1.go:59` |
| Concurrent thumbnail generation (fileserver) | 3 | `server/router/fileserver/fileserver.go:46,116` |
| Max API request body | 256 MiB | `server/router/api/v1/v1.go:20,126,141,144` |
| Page size (default / max) | 50 / 1000 | `server/router/api/v1/common.go:15-17` |

The only `ResourceExhausted` response in the codebase — `server/router/api/v1/attachment_service.go:160`, `"too many image processing requests"` — comes from failing to acquire that process-wide semaphore of 2 (`server/router/api/v1/attachment_service_image.go:68-75`), not from any per-user quota; a single user's requests simply queue on it.

Rate limiting is mentioned only as an unimplemented suggestion for outbound email in `internal/email/doc.go:86` and `internal/email/README.md:286-295`.
