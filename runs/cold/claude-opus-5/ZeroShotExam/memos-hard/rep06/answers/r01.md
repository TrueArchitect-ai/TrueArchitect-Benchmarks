**Premise correction:** There is no Redis in this repository. `memos` (Go, `module github.com/usememos/memos`, `go.mod:1`) has no Redis/Valkey/Memcached client in `go.mod`, and a repo-wide search for `redis|valkey|memcache` across `.go`/`.yaml`/`.md`/config files returns zero hits. There is no connection string, host/port, or env var to configure — the cache layer is purely in-process.

**Actual mechanism:**

**1. The cache implementation** — `store/cache/cache.go`

A hand-rolled, thread-safe in-memory cache backed by `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). Each entry (`item`, line 35-39) stores the value, an absolute `expiration` time, and a rough size estimate. A background goroutine (`cleanupLoop`, line 199) ticks on `CleanupInterval` and evicts expired entries; `Get` also lazily evicts on read when `time.Now().After(itm.expiration)` (line 133-141). `Close()` stops the goroutine.

**2. Where it's "configured"** — `store/store.go:38-61`

Not from config files or env — the config is a hardcoded literal in `store.New()`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

The same `cacheConfig` value is used for three separate cache instances (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. Note this duplicates `cache.DefaultConfig()` (`store/cache/cache.go:56-64`), which has identical values but isn't the one actually used by the store. Nothing anywhere in the codebase overrides `cacheConfig` or `DefaultTTL` after construction.

**3. TTL for user entries: 10 minutes**

All user writes go through `s.userCache.Set(...)` (`store/user.go:98, 122, 132, 143, 167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:89-91`). `SetWithTTL` is never called directly for users — there is no per-entry TTL override anywhere outside tests — so user entries get exactly the 10-minute default.

Two caveats on lifetime:
- **Capacity eviction can cut it short.** With `MaxItems: 1000`, exceeding the limit triggers `cleanupOldest` (`store/cache/cache.go:245`), which drops ~20% of max items by soonest expiration, regardless of the 10-minute window.
- **Explicit invalidation.** User deletion removes the entry directly via `s.userCache.Delete(ctx, userCacheKey(userID))` (`store/user_delete.go:40`).

Cache keys are the plain user ID (`userCacheKey`, `store/user.go:88-90`); the related user-setting cache uses `"<userID>-<key>"` (`store/cache.go:6-8`). Reads are served from cache only in `GetUser` and only when looked up by ID (`store/user.go:148-156`) — lookups by username or other fields always hit the driver.

Practical implication: because the cache is per-process and in-memory, running multiple memos instances behind a load balancer gives each its own unsynchronized copy, with up to 10 minutes of staleness across nodes.
