**Protection mechanism — two layers:**

1. **Dial-time SSRF guard (the real enforcement)** — `safeDialContext` at `internal/webhook/webhook.go:59`, installed as the `Transport.DialContext` of the shared `safeClient` (`internal/webhook/webhook.go:32`). It splits host/port, resolves the hostname itself, and rejects the connection if *any* resolved address is reserved. Because the check happens at dial time rather than at URL-save time, it also defeats DNS rebinding.

2. **Up-front URL validation** — `webhook.ValidateURL` at `internal/webhook/validate.go:62`, called when a user creates/updates a webhook (`server/router/api/v1/user_service_webhooks.go:74`, `:161`, `:182`). Requires an absolute `http`/`https` URL and no reserved resolution, returning gRPC `InvalidArgument`.

Both layers share `isReservedIP` (`internal/webhook/validate.go:44`) over the `reservedCIDRs` list at `internal/webhook/validate.go:14` — IPv4 loopback, RFC-1918 ranges, link-local `169.254.0.0/16` (cloud IMDS), plus IPv6 `::1/128`, `fc00::/7`, `fe80::/10`.

One thing worth flagging: the escape hatch `webhook.AllowPrivateIPs` (`internal/webhook/validate.go:41`) short-circuits `isReservedIP` to always return false, disabling *both* layers. In this tree it is only ever assigned in `internal/webhook/webhook_test.go:91` and `:142` — no `cmd/` or config code sets it, so the `--allow-private-webhooks` flag referenced in `CHANGELOG.md:121` is not wired up in the current source.
