**Premise correction:** There is no Redis anywhere in this repository. No `redis` import, dependency, config key, env var, or connection string exists — `go.mod` (`/bench/repo/go.mod`) has no Redis client, and a case-insensitive search for "redis" across the tree returns zero hits. The cache layer is a hand-rolled, in-process, in-memory cache. There is also no separate "cache layer" service; caching lives inside the store package.

**Actual mechanism**

*Implementation* — `store/cache/cache.go`: a `Cache` struct backed by `sync.Map` plus an `atomic.Int64` item counter. Each entry (`item`, line 35) stores the value, an absolute `expiration` time, and a rough size estimate. A background goroutine (`cleanupLoop`, line 200) ticks on `CleanupInterval` and evicts expired entries; `Get` (line 123) also lazily evicts on read if `time.Now().After(itm.expiration)`. When `MaxItems` is exceeded, `cleanupOldest` (line 253) drops ~20% of `MaxItems` by earliest expiration.

*Configuration* — `store/store.go:40-54`, in `store.New()`. The config is a hardcoded Go literal, not read from env or a config file:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

Three independent cache instances are created from that same config (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. All three are shut down in `Store.Close()` (`store/store.go:69-73`).

**TTL for user entries: 10 minutes**, with 1000 entries max per cache. Every write path for users calls plain `Set`, which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — there is no user-specific override. `SetWithTTL` is never called outside the cache package's own tests. The user write paths are `CreateUser`, `CreateUserIfNoUsers`, `UpdateUser`, and `ListUsers` (`store/user.go:98,122,132,143`), keyed by user ID via `userCacheKey` (`store/user.go:88`); `GetUser` reads the cache only when looking up by ID (`store/user.go:148-156`).

Two details worth noting:
- Expiration is absolute, not sliding — a read via `Get` does not extend the deadline, so a user entry expires 10 minutes after its last write regardless of read traffic.
- `cache.DefaultConfig()` (`store/cache/cache.go:57`) declares the same 10m/5m/1000 values, but the store does not call it; it re-declares an identical literal. Changing `DefaultConfig` alone would not affect the user cache.

Deletion is explicit rather than TTL-driven where correctness matters: `deleteUserCache` (`store/user_delete.go:39-46`) removes the user entry and its associated user-setting entries on user deletion.

**Consequence of the in-process design:** the cache is per-server-process and non-shared. Multiple Memos replicas would each hold independent copies, so a user update on one replica leaves stale data on the others for up to 10 minutes — the invalidation in `user_delete.go` is local only. That's the tradeoff a Redis-backed layer would address, but this codebase doesn't make it.
