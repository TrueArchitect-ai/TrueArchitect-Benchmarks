**Mechanism: explicit Go code** — two hand-written `DELETE FROM reaction` statements inside the DeleteUser transaction, one per driver. There is no database-level cascade for reactions.

**What I checked**

1. **Schema — no FK on `reaction`.** The table declares only a `UNIQUE(creator_id, content_id, reaction_type)` constraint; `creator_id` and `content_id` are plain columns with no `REFERENCES`/`ON DELETE`:
   - `store/migration/sqlite/LATEST.sql:91-99`
   - `store/migration/postgres/LATEST.sql:90-98`
   - `store/migration/mysql/LATEST.sql:90-98`

   Grepping `REFERENCES|FOREIGN KEY|ON DELETE` across all three `LATEST.sql` files returns exactly one hit each — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:108` and peers). So the only cascade in the schema is for memo shares, not reactions.

2. **Deletion path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver's `DeleteUser`, which runs one transaction (`store/db/sqlite/user_delete.go:29`). Inside `deleteUserTargetsTx` reactions are removed first, in two passes:
   - `deleteReactionsByContentIDsTx` — `store/db/sqlite/user_delete.go:96` → definition at `:380`, `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500. This removes *everyone's* reactions on the deleted user's memos (`content_id` is the `memos/<uid>` resource name, built by `memoContentIDsFromRefs` from the collected memo tree).
   - `deleteReactionsByCreatorTx` — `store/db/sqlite/user_delete.go:102` → definition at `:400`, `DELETE FROM reaction WHERE creator_id = ?`. This removes the deleted user's own reactions on anyone's memos.

   The same two calls and functions exist in `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`.

3. **Test confirmation.** `store/test/user_delete_test.go` seeds reactions by the deleted user on a peer's memo and by the peer on the deleted user's memo (lines 97-113), then asserts that after deletion the peer's memo retains only the one unrelated reaction (`peerReactionToKeep`) — lines 216-220.

So: reactions are cleaned up, but by application code in each SQL driver, not by referential integrity. If a user row were ever removed outside `DeleteUser`, orphan reactions would remain.
