**`internal/idp`; `internal/idp/oauth2`**

- **Abstraction package — `internal/idp`** (`internal/idp/idp.go`): a single package-level `idp` namespace defining the provider-agnostic contract, `IdentityProviderUserInfo` (`Identifier`, `DisplayName`, `Email`, `AvatarURL`). This is the normalized shape every provider must produce, and it's what the server code consumes rather than any provider-specific type.

- **Implementation package — `internal/idp/oauth2`** (`internal/idp/oauth2/oauth2.go`): "Package oauth2 implements the OAuth2 identity provider integration." It exposes `IdentityProvider` backed by `storepb.OAuth2Config`, with `NewIdentityProvider`, `ExchangeToken` (supporting PKCE via `codeVerifier`), and user-info fetching that maps remote fields into `idp.IdentityProviderUserInfo` via the configured `FieldMapping`. It is the only subpackage under `internal/idp`.

Supporting evidence:
- The stored provider type enum has exactly one concrete member: `IdentityProvider_OAUTH2 = 1` alongside `TYPE_UNSPECIFIED` (`proto/gen/store/idp.pb.go:27-28`).
- The SSO sign-in path dispatches on that single type — `if identityProvider.Type == storepb.IdentityProvider_OAUTH2 { oauth2.NewIdentityProvider(identityProvider.Config.GetOauth2Config()) }` (`server/router/api/v1/auth_service_sso.go:120-121`), and it's the only file importing both `internal/idp` and `internal/idp/oauth2` (`server/router/api/v1/auth_service_sso.go:12-13`).

Note that the abstraction here is a shared data type rather than a Go `interface` — there is no `Provider` interface to implement, so a second protocol (e.g. SAML/OIDC) would need its own package plus a new enum value and a branch in the SSO handler.
