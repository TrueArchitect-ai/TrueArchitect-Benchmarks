**`*markdown.service` (goldmark-backed, the only implementation) — built once by `markdown.NewService(...)` inside `NewAPIV1Service` — held by `APIV1Service`, `RSSService`, and `memopayload.Runner`.**

### The interface
`markdown.Service` at `internal/markdown/markdown.go:31-55` — `ExtractAll`, `ExtractTags`, `ExtractProperties`, `RenderMarkdown`, `RenderHTML`, `GenerateSnippet`, `ValidateContent`, `RenameTag`.

### Implementations that execute at runtime
Exactly one: the unexported `service` struct (`internal/markdown/markdown.go:57-60`), wrapping a `goldmark.Markdown` instance. There are no mocks, fakes, or alternate implementations anywhere in the repo — tests use the real one. (The `MarkdownRenderer` at `internal/markdown/renderer/markdown_renderer.go`, used by `RenderMarkdown`/`RenameTag`, is a concrete helper, not a second implementation of `Service`.)

### Construction
- Factory: `markdown.NewService(opts ...Option) Service` — `internal/markdown/markdown.go:85-113`. Always installs `extension.GFM` + `parser.WithAutoHeadingID()`; `WithTagExtension()` / `WithMentionExtension()` add the custom `#tag` / `@mention` extensions.
- The single production call site is `NewAPIV1Service` — `server/router/api/v1/v1.go:48-51` — with **both** tag and mention extensions enabled, assigned to `APIV1Service.MarkdownService`.
- That same instance is then handed to RSS in `server/server.go:85`: `rss.NewRSSService(s.Profile, s.Store, apiV1Service.MarkdownService)` (the comment there notes it "needs markdown service from apiV1Service"). So one shared instance serves the whole server.
- Test-only constructions: `server/router/api/v1/test/test_helper.go:44-46` (tags + mentions), `server/router/rss/rss_test.go:54` (no extensions), `server/router/fileserver/fileserver_test.go:427` (tags only).

Two notes on the third holder: `memopayload.NewRunner` has no caller — the runner struct is never instantiated in production wiring (`server/server.go` only starts `s3presign.NewRunner`), so at runtime the interface reaches that code via the package-level `RebuildMemoPayload(ctx, memo, s.MarkdownService)` function, which takes `markdown.Service` as a parameter rather than through the struct field. Also, `RenameTag`, `RenderMarkdown`, `ExtractTags`, `ExtractProperties`, and `ValidateContent` have no non-test callers — only `ExtractAll`, `RenderHTML`, and `GenerateSnippet` are exercised in production.

Separately, the web client does its own markdown rendering with markdown-it (`web/src/components/MemoContent/MemoMarkdownRenderer.tsx`); that's a parallel frontend path, not an implementation of the Go `Service` interface — as the interface doc comment at `markdown.go:28-30` states, backend `RenderHTML` exists for RSS and other server-side rendering needs.
