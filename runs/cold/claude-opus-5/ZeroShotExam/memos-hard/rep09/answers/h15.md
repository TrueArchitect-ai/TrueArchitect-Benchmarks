Memo read-visibility is not centralized in one guard — it's re-implemented per surface. Distinct enforcement sites:

**Core API (Connect/gRPC, `server/router/api/v1/`)**
- `checkMemoReadAccess` — shared guard for single-memo reads (GetMemo, parent-memo resolution, ListMemoComments) — `server/router/api/v1/memo_service.go:39` (callers at `:356`, `:367`, and `server/router/api/v1/memo_service_comments.go:148`)
- ListMemos query scoping (anonymous → PUBLIC only; authed → `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`) — `server/router/api/v1/memo_service.go:217-227`
- ListMemoComments per-comment filter (separate from the parent check above) — `server/router/api/v1/memo_service_comments.go:155-164`
- CreateMemoComment (may you comment on this memo) — `server/router/api/v1/memo_service_comments.go:33-45`
- ListMemoRelations filter — `server/router/api/v1/memo_relation_service.go:103-112`
- ListMemoAttachments — `server/router/api/v1/memo_attachment_service.go:213-226`
- GetAttachment / attachment read permission — `server/router/api/v1/attachment_service.go:440-455`
- ListMemoReactions and UpsertMemoReaction — `server/router/api/v1/reaction_service.go:29-40` and `:83`
- User stats (ListAllUserStats, GetUserStats) visibility scoping — `server/router/api/v1/user_service_stats.go:84-92` and `:216-221`
- Share-token path — deliberate bypass of visibility, gated only on token validity/expiry and non-archived state — `server/router/api/v1/memo_share_service.go:153-166` (helper `getActiveMemoShare` at `:199`)

**Non-API HTTP surfaces**
- File server attachment serving (`checkAttachmentPermission`: public+anonymous-allowed, share-token fallback, then private/creator/admin check) — `server/router/fileserver/fileserver.go:650-702`
- RSS feeds (explore + per-user), PUBLIC only — `server/router/rss/rss.go:90` and `:141`
- Sitemap generation, PUBLIC only — `server/router/frontend/frontend.go:149-151`

**Push / notification surfaces**
- SSE fan-out filter (`SSEClient.canReceive`) — `server/router/api/v1/sse_hub.go:130-143` (event visibility populated in `server/router/api/v1/sse_event_helpers.go:29-37`)
- In-app notification/inbox rendering (`canViewerAccessMemo`) — `server/router/api/v1/user_service_notifications.go:302-316`
- Email notifications (a second, independent `canViewerAccessMemo`, using `RoleAdmin` instead of `isSuperUser`) — `server/notification/email.go:306-320`
- Mention notification targeting (`canUserAccessMentionContext` / `shouldSkipMentionInbox`) — `server/router/api/v1/memo_mention_helpers.go:56-89`

Two notes: the MCP router is *not* a separate enforcement site — it replays requests through the same echo server with the caller's Authorization header (`server/router/mcp/adapter.go:27-44`), so it inherits the API checks for the `MemoService_ListMemos`/`GetMemo` tools listed in `server/router/mcp/catalog.go:12-14`. And the two `canViewerAccessMemo` functions (`user_service_notifications.go` and `notification/email.go`) are duplicated logic that has already drifted on the admin check.
