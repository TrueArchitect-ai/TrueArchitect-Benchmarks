**Premise correction:** Neither. The webhook delivery workers do not consume from NATS or RabbitMQ — there is no external message broker in this codebase at all. A repo-wide search finds no references to NATS, RabbitMQ/AMQP, Kafka, or any broker client, and `go.mod` declares no such dependency.

**Actual mechanism:** Webhook dispatch uses a purely in-process, bounded Go channel with a fixed pool of goroutine workers — all within `internal/webhook/webhook.go`:
- The "queue" is a buffered channel declared as a package variable: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`).
- Its workers are 4 goroutines started in `init()` that range over the channel and call `Post` for each payload (`internal/webhook/webhook.go:42-55`).
- Producers enqueue via `PostAsync`, which does a non-blocking send into the channel and drops the event (with a warning) if the buffer is full (`internal/webhook/webhook.go:184-196`).
- Each dequeued payload is delivered by `Post` over HTTP using the SSRF-guarded `safeClient` (`internal/webhook/webhook.go:120`, actual send at `:152`).

So it's an in-memory channel-backed worker pool (capacity 128, 4 workers), not a broker-backed queue; there is no queue "declared" in NATS/RabbitMQ.
