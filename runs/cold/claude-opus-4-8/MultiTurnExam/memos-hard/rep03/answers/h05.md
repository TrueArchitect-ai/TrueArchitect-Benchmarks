**Mechanism:** By explicit Go code — there is no database-level rule.

**Evidence:**

Two explicit `DELETE FROM reaction` statements run inside the user-deletion transaction, covering both directions:
- Reactions on the deleted user's own content: `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` — `store/db/mysql/user_delete.go:380-388` (and the `contentIDs` are built as `"memos/"+uid` in `memoContentIDsFromRefs`, same file).
- Reactions the user placed on anyone's content: `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` — `store/db/mysql/user_delete.go:400-403`.

Both are invoked from the deletion orchestrator `deleteUserTargetsTx` — `store/db/mysql/user_delete.go:96` and `:102` (calls at the top of that function, `store/db/mysql/user_delete.go:97,103`).

The same two functions and call sites exist in the other drivers: `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/sqlite/user_delete.go:96,102,380,400`.

There is **no** database cascade backing this: the `reaction` table has no foreign key or `ON DELETE` clause — it only has a primary key and a uniqueness constraint (`store/migration/mysql/LATEST.sql:91-98`, and identically `store/migration/postgres/LATEST.sql:91` / `store/migration/sqlite/LATEST.sql:92`). By contrast, tables that do rely on cascades declare them explicitly (e.g. `memo_share`'s `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, `store/migration/mysql/LATEST.sql:107`), confirming reactions are cleaned up only by the Go code above.
