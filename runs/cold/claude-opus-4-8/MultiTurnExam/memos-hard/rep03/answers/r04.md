**Premise correction:** Neither. The webhook delivery workers do not consume from any message broker — there is no NATS and no RabbitMQ/AMQP in this codebase. `go.mod` declares no `nats`, `rabbitmq`, `amqp`, or `streadway` dependency, and grepping all Go source for those terms returns zero hits. So there is no externally-declared queue.

**Actual mechanism:** Webhook delivery is fully in-process, backed by a buffered Go channel. In `internal/webhook/webhook.go:39` the queue is declared as `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a bounded (capacity-128) in-memory channel. A package `init()` (`internal/webhook/webhook.go:42-55`) spins up **4 worker goroutines** that range over that channel and call `Post` (the actual HTTP delivery, `internal/webhook/webhook.go:120`) for each payload. Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking send and drops the request with a warning if the channel is full. This all lives in the server process; nothing is published to or consumed from an external broker.
