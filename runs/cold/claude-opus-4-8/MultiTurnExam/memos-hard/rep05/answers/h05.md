**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction ...` statements inside the user-deletion transaction — there is no database-level cascade rule, because the `reaction` table has no foreign key at all.

Evidence locations:

- **Explicit Go deletion (the mechanism):** In each driver's `user_delete.go`, `deleteUserTargetsTx` runs two reaction deletions inside the delete transaction:
  - `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ...` (removes reactions the deleted user *made*): `store/db/sqlite/user_delete.go:102,400-401`, `store/db/postgres/user_delete.go:102,400-401`, `store/db/mysql/user_delete.go:102,437-438`.
  - `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` (removes reactions *on* the deleted user's content): `store/db/sqlite/user_delete.go:96,380-383`, `store/db/postgres/user_delete.go:96,380-383`, `store/db/mysql/user_delete.go:96,417-420`.
  - Both are wired into the deletion flow at `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-102` and the postgres/mysql equivalents).

- **Not a DB rule — schema shows no FK/cascade:** The `reaction` table definition has `creator_id` and `content_id` as plain `NOT NULL` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `REFERENCES`/`ON DELETE CASCADE`: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98` (mysql `LATEST.sql` is the same shape). So the database would not remove these rows on its own; the Go code must do it.

(The `store.Store.DeleteReaction` API at `store/reaction.go:39-40` deletes a single reaction by `id` and is unrelated to user deletion.)
