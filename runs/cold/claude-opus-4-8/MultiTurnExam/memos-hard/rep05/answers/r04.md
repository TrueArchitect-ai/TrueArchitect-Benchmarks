**Premise correction:** Neither. The webhook delivery workers do **not** consume from a message broker at all — there is no NATS, RabbitMQ, AMQP, Kafka, or any external broker in this project. A repo-wide search finds zero references to `nats`, `rabbitmq`, `amqp`, `kafka`, or `broker` in the Go sources, and `go.mod` declares no such dependency.

**Actual mechanism:** Webhook delivery uses a purely in-process Go buffered channel as its "queue" — no external infrastructure.

- The queue is a package-level buffered channel declared in `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (capacity 128).
- The "workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` (`webhook.go:45`) and calling `Post` to perform the actual HTTP delivery.
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking send `case asyncPostQueue <- requestPayload` (`webhook.go:190`) and drops the payload with a warning if the buffer is full (`webhook.go:191-195`).

So it is an ephemeral, single-process channel-and-goroutine-pool — messages live only in memory and are lost on restart or buffer overflow; there is no broker and no externally declared queue.
