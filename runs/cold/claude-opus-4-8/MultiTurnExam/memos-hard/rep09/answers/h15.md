Memo-visibility view enforcement is spread across these distinct server surfaces (all `PUBLIC`/`PROTECTED`/`PRIVATE` gating on who may see a memo or its dependents):

- API single-memo read gate (`checkMemoReadAccess`, used by GetMemo) — server/router/api/v1/memo_service.go:47-70 (checks at :55/:63)
- API list scoping (`ListMemos` builds a visibility-restricted find/filter) — server/router/api/v1/memo_service.go:216-226
- API memo relations/comments scoping (visibility filter for related memos) — server/router/api/v1/memo_relation_service.go:109-111 and server/router/api/v1/memo_service_converter.go:184-186
- API user stats scoping (visibility-restricted memo find) — server/router/api/v1/user_service_stats.go:84-90, :218-220
- API reaction access (must be able to view the memo to list/add reactions) — server/router/api/v1/reaction_service.go:30-38, :83
- API attachment access (memo visibility gates attachment binary) — server/router/api/v1/attachment_service.go:445-451
- File server attachment serving (memo visibility + share-token fallback) — server/router/fileserver/fileserver.go:677, :699
- SSE real-time event delivery (`canReceive` drops private memo events to non-owners) — server/router/api/v1/sse_hub.go:135-141
- RSS feed (public-only memos) — server/router/rss/rss.go:90, :141
- Frontend SSR/metadata (public-only memos) — server/router/frontend/frontend.go:150

The two most central "who may view this memo" gates are `checkMemoReadAccess` (single-memo API reads) and the `ListMemos` scoping filter (both in server/router/api/v1/memo_service.go); the fileserver, attachment, reaction, SSE, RSS, and frontend surfaces each re-enforce visibility independently for their own delivery path.
