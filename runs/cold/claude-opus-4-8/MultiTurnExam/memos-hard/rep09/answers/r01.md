**Premise correction:** There is no Redis anywhere in this codebase — no `redis` import, no dependency in `go.mod`, no configuration for it. The cache layer is a self-contained, in-process **in-memory cache**, not backed by Redis (or any external store). So "where the Redis connection is configured" has no answer because no such connection exists.

**Actual mechanism:**

- The cache implementation is a thread-safe in-memory map with TTL, size limits, and a background cleanup goroutine — `store/cache/cache.go` (see the `Cache` struct at `store/cache/cache.go:67` and `New(...)` at `:76`). It is described in-code as "a thread-safe in-memory cache with TTL and memory management" (`cache.go:66`).

- The `Store` holds three such caches, including `userCache`, all constructed with the same config in `store.New(...)` — `store/store.go:47-53`. The config (`store/store.go:40-45`) sets `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`.

- **TTL for user entries:** 10 minutes. User records are written via `s.userCache.Set(...)` (`store/user.go:143` in `ListUsers`, and `:167` in `GetUser`), and `Cache.Set` applies the cache's `DefaultTTL` (`store/cache/cache.go:93-94`), which for the `userCache` is the 10-minute default from `store/store.go:41`. There is no per-user custom TTL (`SetWithTTL`) override for user entries.

So: cache is in-memory (`store/cache/cache.go`), configured in `store/store.go:40-53`, and user entries expire after 10 minutes (with cleanup sweeping every 5 minutes, capped at 1000 items).
