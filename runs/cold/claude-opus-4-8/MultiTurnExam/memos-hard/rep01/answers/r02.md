**Premise correction: there is no per-user API rate-limiting middleware in this codebase — it doesn't exist, so there is no registration site and no configured request limits.**

Evidence:

- A repo-wide search for rate-limiting turns up nothing: no matches for `rate limit` / `ratelimit` / `throttle` / `limiter` in the Go source, and no rate-limiting library in `go.mod` (no `golang.org/x/time/rate`, `ulule/limiter`, `tollbooth`, etc.). The only `limit`/`rate` hits are unrelated — DB query batch sizes (`server/runner/s3presign/runner.go:59`, `server/runner/memopayload/runner.go:34`), the RSS item cap `maxRSSItemCount` (`server/router/rss/rss.go:87`), and token-generation functions (`server/auth/token.go`).

- The actual middleware stack is small and contains no limiter. On the root Echo server, `server/server.go:51-52` registers only `middleware.Recover()` and the CORS middleware (`newCORSMiddleware`, defined in `server/cors.go:14`). The frontend router adds static-file and SPA-fallback middleware (`server/router/frontend/frontend.go:54`, `:59`). The API layer (`server/router/api/v1/v1.go`) wires an **auth/authorization** middleware into the gRPC-Gateway mux (`v1.go:95`) — that enforces authentication and per-request authorization, but it is not a rate limiter and imposes no request-count/quota limits.

So the question's premise is mistaken: request throttling / per-user rate limits are simply not implemented at the server surface here. (Any such limiting would have to come from an external reverse proxy in front of the app, which is outside this repository.)
