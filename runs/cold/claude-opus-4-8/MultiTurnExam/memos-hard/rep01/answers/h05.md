**Mechanism — explicit Go code (not a DB cascade). Their reactions are removed by hand-written `DELETE FROM reaction` statements inside the `DeleteUser` transaction, in all three drivers.**

What I checked:

1. **The delete flow.** `Store.DeleteUser` (`store/user.go:171`) dispatches to each driver's `DB.DeleteUser`. In SQLite (`store/db/sqlite/user_delete.go:29`), the transaction body `deleteUserTargetsTx` explicitly calls two reaction-deleting functions:
   - `deleteReactionsByContentIDsTx` — `store/db/sqlite/user_delete.go:96` → removes reactions *on* the user's deleted memos/content.
   - `deleteReactionsByCreatorTx` — `store/db/sqlite/user_delete.go:102` → removes reactions the user *made*.

2. **The actual SQL.** Both resolve to explicit `DELETE FROM reaction` statements:
   - `store/db/sqlite/user_delete.go:383` (`... WHERE content_id IN (...)`) and `store/db/sqlite/user_delete.go:401` (`... WHERE creator_id = ?`).
   - Same pattern in Postgres (`store/db/postgres/user_delete.go:383` and `:401`) and MySQL (`store/db/mysql/user_delete.go:420` and `:438`).

3. **Ruled out a DB-level cascade.** I checked the `reaction` table schema (`store/migration/sqlite/0.20/00__reaction.sql`, and `store/migration/sqlite/LATEST.sql:98`). The table has a `UNIQUE(creator_id, content_id, reaction_type)` constraint but no `FOREIGN KEY ... REFERENCES user ... ON DELETE CASCADE` on `creator_id` — so nothing at the database level removes reactions automatically. The removal depends entirely on the explicit Go code above.

So: emoji reactions are removed by explicit Go code executed within the user-deletion transaction, covering both reactions the user authored and reactions attached to the user's deleted content.
