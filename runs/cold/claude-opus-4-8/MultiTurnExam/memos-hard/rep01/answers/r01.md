**Premise correction: there is no Redis in this project.** The cache layer is not backed by Redis (or any external store) — a repo-wide search for `redis` finds zero references in the Go code and no such dependency in `go.mod`. There is therefore no Redis connection to configure.

**Actual mechanism:** the cache is a **thread-safe in-process, in-memory cache** implemented in `store/cache/cache.go` (`Cache` struct, "thread-safe in-memory cache with TTL and memory management," `store/cache/cache.go:66`). It stores values in a Go map guarded by a mutex, with per-item expiration and a background cleanup goroutine — no network connection involved.

- **Where it's "configured":** in `store.New`, which builds a single `cache.Config` and instantiates three caches from it — including the user cache — at `store/store.go:38-53`. The config is `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store/store.go:40-45`). The `userCache` field is declared at `store/store.go:28` and created at `store/store.go:52`.

- **TTL for user entries:** **10 minutes.** User entries are written via `s.userCache.Set(...)` in `Store.GetUser` (`store/user.go`), and `Cache.Set` uses the configured `DefaultTTL` (`store/cache/cache.go:92-94`), which is 10 minutes per the config above. There's no user-specific override — user entries get the default 10-minute TTL, and stale entries are also swept every 5 minutes by the cleanup interval (and bounded to 1000 items). (The same defaults are echoed in `cache.DefaultConfig`, `store/cache/cache.go:59`, though `store.New` supplies its own copy.)

Note: cache entries are also invalidated explicitly on user mutation/deletion (e.g. `deleteUserCache`), so the 10-minute TTL is the upper bound on staleness, not a fixed lifetime.
