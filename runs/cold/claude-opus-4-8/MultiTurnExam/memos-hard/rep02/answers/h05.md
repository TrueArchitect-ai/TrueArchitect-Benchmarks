**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the `DeleteUser` transaction — there is no database-level cascade.

Evidence locations:

1. **Explicit deletion in the delete-user transaction.** For each driver, `deleteUserTargetsTx` calls two reaction-cleanup helpers:
   - `deleteReactionsByContentIDsTx` — deletes reactions *on* the deleted user's memos (`DELETE FROM reaction WHERE content_id IN (...)`).
   - `deleteReactionsByCreatorTx` — deletes reactions the user *authored* on any content (`DELETE FROM reaction WHERE creator_id = ?`).
   
   Both are invoked from `deleteUserTargetsTx` and defined in each driver:
   - SQLite: `store/db/sqlite/user_delete.go:95,102` (invocation), `:397` (`deleteReactionsByContentIDsTx`), `:409` (`deleteReactionsByCreatorTx`).
   - Postgres: `store/db/postgres/user_delete.go:96,102` (invocation), `:380`, `:400`.
   - MySQL: `store/db/mysql/user_delete.go:96,102` (invocation), `:417`, `:437`.

2. **No database-level rule.** The `reaction` table schema has no foreign key to `user` and no `ON DELETE CASCADE` — `creator_id` and `content_id` are plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Confirmed in `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-97`, and `store/migration/mysql/LATEST.sql:91-97`. So removal cannot happen at the DB level; it relies entirely on the Go code above.

Note the two-pronged Go cleanup matters because reactions are keyed by an opaque `content_id` (e.g. `"memos/<uid>"`) rather than a FK, so both the user's own reactions (`creator_id`) and reactions others left on the user's now-deleted memos (`content_id`) are explicitly cleared.
