**Concrete method: `(*DB).CreateMemo` in the SQLite driver — `store/db/sqlite/memo.go:16`** (the `INSERT INTO \`memo\` … RETURNING …` executes at `store/db/sqlite/memo.go:41-42`).

How I determined which of the three candidate drivers (`sqlite`, `postgres`, `mysql`, each declaring a `(*DB).CreateMemo`) actually runs:

1. **Resolved the default driver.** With no DB flags, the `driver` config defaults to `"sqlite"`: `viper.SetDefault("driver", "sqlite")` and the persistent flag default `"sqlite"` at `cmd/memos/main.go:122` and `cmd/memos/main.go:130`; this feeds `Profile.Driver` (`cmd/memos/main.go:43`).

2. **Followed the driver-selection factory.** `store/db/db.go` `NewDBDriver` switches on `profile.Driver`; `case "sqlite":` constructs `sqlite.NewDB(profile)` (`store/db/db.go:20-21`). So the `store.Driver` implementation at runtime is the SQLite `*DB`.

3. **Traced the save path to the interface, then to the concrete impl.** Saving a memo goes `Store.CreateMemo` (`store/memo.go:109`), which after validation delegates to `s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`). `driver` is the `store.Driver` interface (`CreateMemo` declared at `store/driver.go:29`), so the call dispatches to whichever concrete type the factory built — the SQLite `*DB` in a default install. Its `CreateMemo` (`store/db/sqlite/memo.go:16`) builds and runs the actual SQL `INSERT`.

The `postgres` and `mysql` `CreateMemo` methods (`store/db/postgres/memo.go`, `store/db/mysql/memo.go`) exist but are never constructed unless `--driver=postgres`/`mysql` (or the env/config equivalent) is set.
