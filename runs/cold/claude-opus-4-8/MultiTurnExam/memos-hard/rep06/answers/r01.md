**Premise correction:** There is no Redis in this codebase. A repo-wide grep for `redis` in Go sources returns nothing — the cache layer is a custom **thread-safe in-process in-memory cache**, not a Redis-backed one, so there is no Redis connection to configure.

**Actual mechanism:**
- The cache implementation is `store/cache/cache.go` — a `Cache` struct storing items in a map with per-entry expiration and a background cleanup goroutine (`store/cache/cache.go:66`, cleanup loop at `:199`). It has no network/connection configuration; it lives entirely in the server process.
- It is "configured" (constructed) in `store.New` at `store/store.go:39-52`: a single `cache.Config{DefaultTTL: 10*time.Minute, CleanupInterval: 5*time.Minute, MaxItems: 1000}` is used to create three caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-52`). (The same defaults are also defined in `cache.DefaultConfig()` at `store/cache/cache.go:57`.)
- **TTL for user entries:** user records are written via `s.userCache.Set(...)` (e.g. `store/user.go:98,122,132,143,167`), and `Set` applies the cache's `DefaultTTL` (`store/cache/cache.go:92-94`). Since `userCache` is built with the config above, **user entries expire 10 minutes after being cached** (with expired items reclaimed by the 5-minute cleanup loop, and LRU-style eviction once `MaxItems` = 1000 is exceeded). No user-specific `SetWithTTL` override is used.
