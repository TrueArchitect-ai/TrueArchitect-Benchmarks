**Mechanism: explicit Go code** (not a database-level rule).

Evidence:
- **Explicit deletion in Go.** Each driver's `DeleteUser` transaction explicitly removes reactions in two ways:
  - `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` — removing reactions the deleted user *made*: `store/db/sqlite/user_delete.go:400-401`, `store/db/postgres/user_delete.go:400-401`, `store/db/mysql/user_delete.go:437-438`.
  - `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` — removing reactions *on* the user's deleted content: `store/db/sqlite/user_delete.go:380-383` (and the postgres/mysql equivalents).
  - These are invoked from `collectDeleteUserTargets`/the delete flow at `store/db/sqlite/user_delete.go:96` and `:102` (mirrored in postgres/mysql `user_delete.go`).
- **No database-level rule.** The `reaction` table schema has only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and no foreign key or `ON DELETE CASCADE` referencing the user table: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (and the original `0.20/00__reaction.sql` migrations). So the DB would not remove reactions on its own — the Go code is what does it.
