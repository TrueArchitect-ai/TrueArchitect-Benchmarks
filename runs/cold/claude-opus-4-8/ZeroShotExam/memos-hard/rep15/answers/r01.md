**Premise correction:** There is no Redis in this repository, and there is no external cache store of any kind. This is the Go project `usememos/memos`, and a full search turns up zero references to `redis`, `ioredis`, `REDIS_*` env vars, redis client imports, or connection URLs anywhere in the source, `go.mod`/`go.sum`, `scripts/compose.yaml`, `scripts/Dockerfile`, or docs. (`golang-lru/v2` sits in `go.sum` as a transitive dependency but is never imported.) So there is no "Redis connection for the cache layer" to point at.

**Actual mechanism:** Caching is entirely in-process — a custom, thread-safe in-memory TTL cache built on `sync.Map` + a background cleanup goroutine.

- **Implementation:** `store/cache/cache.go`. The `Config` struct (lines 41–54) and `DefaultConfig()` (lines 57–64) define `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`. Each `item` carries a per-entry `expiration` (lines 34–39); `Get` lazily evicts expired entries and `cleanupLoop` purges them periodically.
- **Wiring:** `store/store.go` holds three cache instances on the `Store` struct — `instanceSettingCache`, `userCache`, `userSettingCache` (lines 27–29) — all constructed in `New()` with an inline config (lines 40–45) using the same values: 10-minute TTL, 5-minute cleanup, 1000-item cap.

**TTL on user entries:** There is no user-specific TTL. In `store/user.go`, `userCache.Set(...)` is called on create/update/list/get (lines 98, 122, 132, 143, 167) using plain `Set` — never `SetWithTTL` — so user entries inherit the shared **10-minute `DefaultTTL`**. `SetWithTTL` has no production caller anywhere; it's only exercised in `store/cache/cache_test.go`. User entries are invalidated explicitly on delete via `deleteUserCache` in `store/user_delete.go:39–45`.

So the honest answer: no Redis connection exists; user cache entries live in an in-memory `sync.Map` cache configured in `store/store.go` (backed by `store/cache/cache.go`), expiring after a fixed 10-minute default TTL.
