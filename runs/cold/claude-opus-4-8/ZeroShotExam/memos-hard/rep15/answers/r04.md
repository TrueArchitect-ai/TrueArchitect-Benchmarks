**Premise correction:** Neither. The webhook delivery workers don't consume from NATS *or* RabbitMQ — this repository (Memos) has no external message broker at all. There is no `nats`, `amqp`, `rabbitmq`, `redis`, or `kafka` dependency anywhere in the Go codebase.

**Actual mechanism:** Webhook delivery is handled entirely in-process using a **buffered Go channel** consumed by a fixed pool of goroutines.

- The queue is declared in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  It's a package-level buffered channel with capacity 128.

- The "delivery workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` (an HTTP POST) for every payload.

- Producers enqueue via `PostAsync()` at `internal/webhook/webhook.go:184-196`, which does a non-blocking `select` send onto `asyncPostQueue` and drops the payload (logging a warning) if the buffer is full.

So the flow is a classic in-memory worker pool: `PostAsync` → buffered channel `asyncPostQueue` → 4 consumer goroutines → HTTP dispatch via `Post`. No broker, no queue declared on any broker — the "queue" is the Go channel declared at `internal/webhook/webhook.go:39`.
