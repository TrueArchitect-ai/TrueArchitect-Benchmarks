**Mechanism: explicit Go code** — a user's emoji reactions are removed by explicit `DELETE FROM reaction` statements executed inside the user-deletion transaction. There is **no** database-level rule (no foreign key, `ON DELETE CASCADE`, or trigger) on the `reaction` table.

**Evidence locations**

- **Delete-user flow (call sites):** `store/db/sqlite/user_delete.go` (and identical `postgres/user_delete.go`, `mysql/user_delete.go`), inside `deleteUserTargetsTx` (~line 92), which calls:
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` (~line 96) — removes reactions placed on the deleted user's memos.
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` (~line 102) — removes reactions the user themselves placed.
- **The store helpers that issue the deletes** (same files):
  - `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)`
  - `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?`
- **API entry point:** `server/router/api/v1/user_service.go:393` (`DeleteUser`), calling `s.Store.DeleteUser(...)` at line ~414; store interface in `store/user_delete.go`.
- **Schema confirms no DB-level rule:** `store/migration/sqlite/0.20/00__reaction.sql` — `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` are plain columns with no `REFERENCES`/cascade/trigger (postgres/mysql 0.20 migrations equivalent).
- **Naming note:** this repo (Memos) has no `PermanentDeleteUser`/`PermanentDeleteByUser`; the equivalent is the `DeleteUser` store path. The public reaction store interface (`store/reaction.go`) only exposes `UpsertReaction`, `ListReactions`, `GetReaction`, `DeleteReaction`; the bulk deletes are private helpers in `user_delete.go`.

What was checked: the user-deletion flow across all three DB drivers, the reaction store interface, and the `reaction` table migration schema for any cascade/trigger. Cleanup depends entirely on the explicit Go code above — removing it would orphan reactions rather than cascade them.
