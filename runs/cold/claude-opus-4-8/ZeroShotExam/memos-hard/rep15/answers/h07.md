h07.

A browser requesting another user's profile image hits `GET /file/users/:identifier/avatar`. The avatar bytes are **not** a separate blob/file — they are stored inline in the user row's `avatar_url` column as a base64 data URI, which the handler decodes and serves. The hops from serving handler to that stored data:

**serveUserAvatar — server/router/fileserver/fileserver.go:168** (route registered at fileserver.go:124; parses `user.AvatarURL` via `parseDataURI` at fileserver.go:196/737)
**getUserByUsername — server/router/fileserver/fileserver.go:715**
**Store.GetUser — store/user.go:148** (checks `userCache`, then falls through)
**Store.ListUsers — store/user.go:136**
**driver.ListUsers — store/driver.go:47** (interface dispatch)
**DB.ListUsers — store/db/sqlite/user.go:88** (and postgres/user.go:87, mysql equivalent — runs the SQL selecting `avatar_url` from the `user` table)

The stored data reached is the `avatar_url` field of the `user` row (a `data:<mime>;base64,...` URI), decoded to raw image bytes in `serveUserAvatar` and returned via `c.Blob` (fileserver.go:209).

Note on authorization: on a non-anonymous instance the handler first requires a valid viewer via `getCurrentUser` → `authenticator.AuthenticateToUser` (fileserver.go:173–181, 708), but any authenticated viewer may fetch any user's avatar — there is no per-owner check on this route.
