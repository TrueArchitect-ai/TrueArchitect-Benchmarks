Memo visibility is enforced across several distinct server surfaces. The primary distinct enforcement sites:

**Core per-memo read gate (the central helper)**
- `checkMemoReadAccess` — `server/router/api/v1/memo_service.go` (called by `GetMemo` and, for comment parents, re-checked; also reused by `ListMemoComments`)

**List-query visibility scoping (builds the visibility WHERE-clause the store enforces)**
- `ListMemos` visibility-scope construction — `server/router/api/v1/memo_service.go`
- `ListMemoComments` comment-list filter — `server/router/api/v1/memo_service_comments.go`
- Store SQL builder that turns `VisibilityList`/`CreatorID` into `WHERE ... visibility IN (...)` — `store/db/sqlite/memo.go`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go`

**Child-resource re-checks against the parent memo's visibility**
- Reactions (`UpsertMemoReaction` / delete / list) — `server/router/api/v1/reaction_service.go`
- Memo attachments list — `server/router/api/v1/memo_attachment_service.go`
- `checkAttachmentAccess` helper — `server/router/api/v1/attachment_service.go`

**Separate raw-file streaming surface**
- `checkAttachmentPermission` (anonymous + share-token + private logic for blob/thumbnail streaming) — `server/router/fileserver/fileserver.go`

**Public-only scoping surfaces**
- RSS feeds (global + `GetUserRSS`), forced to `[Public]` — `server/router/rss/rss.go`
- Sitemap (`getSitemapXML`), forced to `[Public]` — `server/router/frontend/frontend.go`

The three "at least three" the question asks about are most clearly: (1) the `checkMemoReadAccess` single-memo gate in `memo_service.go`, (2) the list-query visibility filtering realized by the store SQL builder in `store/db/*/memo.go`, and (3) the independent streaming gate `checkAttachmentPermission` in `fileserver.go` — with RSS/sitemap, reactions, and attachment checks as additional distinct sites.
