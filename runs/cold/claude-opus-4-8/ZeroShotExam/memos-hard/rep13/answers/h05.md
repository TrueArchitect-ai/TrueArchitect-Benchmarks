**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements in the Go deletion path — not by any database-level cascade rule. (This is the memos project; user deletion is a hard delete.)

**Evidence:**

1. **The reaction table has no foreign key / no `ON DELETE CASCADE`** — so the DB cannot remove reactions on its own. `creator_id` and `content_id` are plain columns with no references:
   - `store/migration/postgres/0.20/00__reaction.sql`
   - `store/migration/sqlite/0.20/00__reaction.sql`
   - `store/migration/mysql/0.20/00__reaction.sql`
   
   A grep for `foreign`/`references`/`cascade` across the reaction migrations returned nothing.

2. **Explicit deletion in the user-delete transaction.** In each DB backend's `user_delete.go`, `DeleteUser` runs a transaction (`DeleteUser` → `deleteUserTargetsTx`) that explicitly deletes reactions in two ways:
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (reactions *made by* the user)
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (reactions *on the deleted user's memos*)

   Locations (identical pattern in all three backends):
   - `store/db/postgres/user_delete.go` — call sites at lines 96 & 102 (`deleteUserTargetsTx`); implementations at lines 380–388 (`deleteReactionsByContentIDsTx`) and 400–403 (`deleteReactionsByCreatorTx`)
   - `store/db/mysql/user_delete.go` — same statements at lines 420 (`content_id IN`) and 438 (`creator_id =`)
   - `store/db/sqlite/user_delete.go` — same pattern (the `reaction` deletes appear in its `deleteUserTargetsTx`)

**What I checked:** the reaction store/schema files (`store/reaction.go`, `store/db/*/reaction.go`, and all reaction migrations) for any FK cascade → none exist; the user-deletion code path (`store/user_delete.go` plus each backend's `store/db/*/user_delete.go`) for explicit reaction handling → found the two `DELETE FROM reaction` statements wired into the delete transaction.
