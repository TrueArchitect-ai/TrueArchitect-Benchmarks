A browser GET to `/file/users/{identifier}/avatar` (another user's profile image) reaches stored data through these hops:

1. `GET /file/users/:identifier/avatar` route — `server/router/fileserver/fileserver.go:124` (registered in `RegisterRoutes`)
2. `FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (serving handler; auth-gates on private instances, then looks up the target user and decodes the avatar data URI)
3. `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715` (builds `store.FindUser{Username: &identifier}`)
4. `Store.GetUser` — `store/user.go:148` (checks user cache, then delegates)
5. `Store.ListUsers` — `store/user.go:136` (calls the DB driver, populates cache)
6. `DB.ListUsers` (driver) — `store/db/sqlite/user.go:88` (builds `WHERE username = ?` and runs `SELECT ... avatar_url ... FROM user` via `QueryContext`, scanning `user.AvatarURL`)

The stored data is the `avatar_url` column of the `user` table (a base64 data URI), which the handler decodes and returns as an image blob (`fileserver.go:196-209`).

Notes:
- The identical driver query exists for the other backends: `store/db/postgres/user.go` and `store/db/mysql/user.go` — the active one depends on configured DB driver.
- `GetUser`'s cache short-circuit only applies when `find.ID` is set; the username lookup here always falls through to `ListUsers` → the driver.
