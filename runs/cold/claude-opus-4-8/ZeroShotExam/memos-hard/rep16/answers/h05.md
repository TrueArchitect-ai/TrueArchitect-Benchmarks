**Mechanism: by explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements in the delete-user transaction — not by any database-level cascade rule. The removal covers reactions on two axes: reactions the user *created* (`creator_id`) and reactions on the user's own memos/content (`content_id`).

**Evidence locations:**

1. **Explicit Go deletion** — in each driver's `deleteUserTargetsTx`, two reaction deletes are invoked:
   - `store/db/sqlite/user_delete.go:96` (by content) and `:102` (by creator), implemented at `:380-388` (`deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)`) and `:400-403` (`deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?`).
   - `store/db/postgres/user_delete.go:96,102` and helpers at `:380`, `:400` — same logic.
   - `store/db/mysql/user_delete.go:96,102` and helpers at `:417`, `:437` — same logic.
   - All three run inside a single transaction (e.g. `sqlite/user_delete.go:29-59`) that also deletes the `user` row itself (`deleteUserRowTx`).

2. **No database-level rule** — the `reaction` table schema declares no foreign key or `ON DELETE CASCADE`; it only has a `UNIQUE(creator_id, content_id, reaction_type)` constraint:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-97`
   - `store/migration/mysql/LATEST.sql:91-97`
   - (plus the original `0.20/00__reaction.sql` files) — `creator_id` is a plain `INTEGER NOT NULL` with no `REFERENCES`.

So without the explicit Go deletes, the reactions would be orphaned — confirming the removal depends entirely on the application code, not the DB.
