**Premise correction:** The question assumes the webhook delivery workers consume from an external message broker (NATS or RabbitMQ). Neither is used — this repository (memos) has no message broker at all. `go.mod`/`go.sum` contain no references to nats, rabbitmq, amqp, jetstream, or kafka.

**Actual mechanism:** Webhook delivery is entirely in-process, using a **buffered Go channel** drained by a fixed pool of **4 goroutine workers**. All of it lives in `internal/webhook/webhook.go`:

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (buffer capacity 128).
- **Workers / consume side:** `internal/webhook/webhook.go:42-55` — an `init()` spins up 4 goroutines, each doing `for payload := range asyncPostQueue` (line 45) and calling `Post()` to make the outbound HTTP POST.
- **Enqueue side:** `PostAsync()` at `internal/webhook/webhook.go:189-195` pushes onto the channel via a non-blocking `select`/`default`, so payloads are **dropped** (with a warning) when the buffer is full rather than blocking.

So the "queue" is an intra-process Go channel, not a broker-managed queue — nothing crosses a process or network boundary.
