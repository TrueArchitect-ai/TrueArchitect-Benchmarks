Memo view-visibility is enforced across many surfaces. The distinct enforcement sites, grouped from the central gate outward:

**Core API read gates**
- `checkMemoReadAccess` per-memo read gate (used by `GetMemo` for memo + parent, and `ListMemoComments`) — server/router/api/v1/memo_service.go:39-68
- `ListMemos` list-level visibility filter (anon → PUBLIC only; user → own OR PUBLIC/PROTECTED) — server/router/api/v1/memo_service.go:218-227

**Store-layer SQL (where the filter is actually applied)**
- `VisibilityList` → `visibility IN (...)` clause — store/db/sqlite/memo.go:96-103 (mirrored store/db/postgres/memo.go, store/db/mysql/memo.go)
- Relation `MemoFilter` → `memo_id/related_memo_id IN (SELECT id FROM memo WHERE <visibility>)` — store/db/sqlite/memo_relation.go:80-94 (mirrored postgres/mysql)

**Related API surfaces**
- Comments create — server/router/api/v1/memo_service_comments.go:41-43
- Reactions (list + upsert) — server/router/api/v1/reaction_service.go:30-41, 83-85
- Memo attachments (v1 memo RPC list) — server/router/api/v1/memo_attachment_service.go:214-225
- Attachment service `checkAttachmentAccess` — server/router/api/v1/attachment_service.go:422-455
- List memo relations RPC filter — server/router/api/v1/memo_relation_service.go:108-112
- Embedded/related memo rendering `batchConvertMemoRelations` — server/router/api/v1/memo_service_converter.go:182-187

**Non-gRPC / delivery surfaces**
- Raw file/blob server `checkAttachmentPermission` — server/router/fileserver/fileserver.go:650-704 (esp. 677, 699)
- RSS feeds (Explore + User, PUBLIC-only) — server/router/rss/rss.go:90, 141
- Sitemap XML (PUBLIC-only) — server/router/frontend/frontend.go:149-151
- SSE live-event delivery filter `canReceive` — server/router/api/v1/sse_hub.go:134-144

Notable gap (not an enforcement, but relevant to visibility): `GetMemoByShare` does not call `checkMemoReadAccess` — a valid share token bypasses PRIVATE/PROTECTED by design — server/router/api/v1/memo_share_service.go:153-192.
