**Delivery function — `internal/webhook/webhook.go`**

The outbound HTTP delivery actually executes in the `Post` function (`internal/webhook/webhook.go:120`), where it marshals the payload, builds a `POST` request, optionally HMAC-signs it, and fires the request via `safeClient.Do(req)` at `webhook.go:152`. Content-change triggers enqueue payloads through `PostAsync` (`webhook.go:184`), which a pool of worker goroutines drains, calling `Post` for each (`webhook.go:42-55`).

**Protection mechanism — `internal/webhook/webhook.go` (dial-time) + `internal/webhook/validate.go` (IP ranges)**

The real protection lives at dial time. `safeClient` is configured with a custom transport whose `DialContext` is `safeDialContext` (`webhook.go:32-37`, `webhook.go:59`). On every connection, `safeDialContext` resolves the target hostname via `net.DefaultResolver.LookupHost` and rejects any address that `isReservedIP` flags as reserved/private, refusing the dial (`webhook.go:65-74`). Because this check happens at connect time on the resolved IP, it also defeats DNS-rebinding.

The reserved-range logic itself is in `internal/webhook/validate.go`: `isReservedIP` (`validate.go:44`) tests the IP against `reservedNetworks`, parsed from `reservedCIDRs` (`validate.go:14-23`) — loopback, RFC-1918 private ranges, link-local/cloud IMDS (169.254.0.0/16), and their IPv6 equivalents. There's also an upfront `ValidateURL` check (`validate.go:62`) applied when a webhook URL is configured, and an `AllowPrivateIPs` escape hatch (`validate.go:41`) that disables the protection for self-hosted deployments.

So the answer:
- **delivery function** — `Post` (dispatched async via `PostAsync`) in `internal/webhook/webhook.go`
- **protection mechanism** — `safeDialContext` dial-time check calling `isReservedIP` against `reservedCIDRs`, in `internal/webhook/webhook.go` + `internal/webhook/validate.go` (with pre-validation in `ValidateURL`).
