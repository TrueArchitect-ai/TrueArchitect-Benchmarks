The question's premise is incorrect: **there is no per-user API rate-limiting middleware in this repository**, so there is no registration site and no request limits to report.

This is the Memos project (Go backend, `go.mod` → `github.com/usememos/memos`), using the Echo web framework plus Connect-RPC. I verified the complete request-handling middleware chains, and none of them include rate limiting:

- **Connect-RPC API interceptor chain** — registered in `server/router/api/v1/v1.go:133-141`, consisting only of `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). No rate/throttle interceptor.
- **Top-level Echo middleware** — registered in `server/server.go:51-52`, only `middleware.Recover()` and `newCORSMiddleware` (`server/cors.go:13`).
- **Frontend router middleware** — `server/router/frontend/frontend.go:54-59`, only static-file and SPA-fallback handling.

Supporting evidence:
- No rate-limiting library is imported (no `golang.org/x/time/rate`, `tollbooth`, `ulule/limiter`, etc. in `go.mod`/`go.sum`).
- No `429`/`TooManyRequests` handling exists anywhere.
- The only textual match is an aspirational doc comment — `internal/email/doc.go:86`: `// - Rate limit email sending to prevent abuse` — which is unimplemented.

The closest actual protection is a **request payload size cap** (not a frequency limit): `connect.WithReadMaxBytes(maxAPIRequestBytes)` / `http.MaxBytesHandler` at `server/router/api/v1/v1.go:126,141,144`. That bounds body size per request, not the number of requests per user.

So: no per-user rate limiter is registered anywhere, and there are no associated request limits.
