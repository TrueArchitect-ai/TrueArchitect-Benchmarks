h07.

A browser GET to `/file/users/{username}/avatar` is served by Memos' file server. The avatar is not a separate blob — it's stored inline as a data URI in the `avatar_url` column of the `user` row, decoded in the handler.

Route + hops to the data layer:

`RegisterRoutes` (GET `/file/users/:identifier/avatar` → `serveUserAvatar`) — server/router/fileserver/fileserver.go:124
`FileServerService.serveUserAvatar` — server/router/fileserver/fileserver.go:168
`FileServerService.getUserByUsername` — server/router/fileserver/fileserver.go:715
`Store.GetUser` — store/user.go:148
`Store.ListUsers` — store/user.go:136
`(*DB).ListUsers` (SQLite driver; `SELECT ... avatar_url ... FROM user WHERE username = ?`) — store/db/sqlite/user.go:88

Stored data: the `user.avatar_url` column, scanned into `User.AvatarURL` (store/db/sqlite/user.go:159,189). Back in the handler, `serveUserAvatar` decodes that data URI via `FileServerService.parseDataURI` (server/router/fileserver/fileserver.go:196 → :737) and writes the bytes with `c.Blob` (fileserver.go:209).

Notes:
- `Store.GetUser` consults `userCache` only when looking up by ID; the avatar lookup is by `Username`, so it always falls through to `ListUsers` → driver (store/user.go:149-158).
- `s.driver` is the `driver.Driver` interface; the concrete implementation shown is SQLite (the default). Equivalent implementations exist at store/db/postgres/user.go and store/db/mysql/user.go.
- Access control: on a non-anonymous instance the handler first requires a valid viewer (fileserver.go:173-181); otherwise any user's avatar is served by username.
