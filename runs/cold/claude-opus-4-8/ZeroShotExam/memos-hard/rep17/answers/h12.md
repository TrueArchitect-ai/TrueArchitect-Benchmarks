**Concrete method:** `(*sqlite.DB).CreateMemo` — `store/db/sqlite/memo.go:16`. It builds and runs the statement `INSERT INTO `memo` (…) VALUES (…) RETURNING …` via `d.db.QueryRowContext` at `store/db/sqlite/memo.go:41-42`.

**How I determined it was this candidate (and not the mysql/postgres ones):**

The store layer is driver-agnostic. `(*store.Store).CreateMemo` (`store/memo.go:109-113`) simply delegates: `return s.driver.CreateMemo(ctx, create)`. There are three implementations of that `store.Driver` interface method — `store/db/sqlite/memo.go`, `store/db/mysql/memo.go`, and `store/db/postgres/memo.go` — so "which runs" depends entirely on how `s.driver` is constructed.

The concrete driver is chosen in `NewDBDriver` (`store/db/db.go:13-28`) by a `switch profile.Driver` — `"sqlite"` → `sqlite.NewDB`, `"mysql"` → `mysql.NewDB`, `"postgres"` → `postgres.NewDB`.

`profile.Driver` comes from the `driver` config value, whose default is set in the CLI entrypoint:
- `cmd/memos/main.go:122` — `viper.SetDefault("driver", "sqlite")`
- `cmd/memos/main.go:130` — the `--driver` flag also defaults to `"sqlite"`.

So with no database flags, `profile.Driver == "sqlite"`, `NewDBDriver` returns `*sqlite.DB`, and `s.driver.CreateMemo` resolves to `(*sqlite.DB).CreateMemo`, which executes the actual `INSERT INTO memo`. The mysql and postgres `CreateMemo` methods exist but are never reached in a default install because that switch branch isn't taken.
