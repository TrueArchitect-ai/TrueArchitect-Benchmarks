**Premise correction:** The webhook delivery workers consume from *neither* NATS nor RabbitMQ. The question presents a false dichotomy — this repository (`usememos/memos`) has no external message broker at all. A repo-wide search of source files and `go.mod`/`go.sum` for `nats`, `jetstream`, `amqp`, `rabbit`, `kafka`, `redis`, etc. returns zero matches; there is no broker client dependency.

**Actual mechanism:** Webhook delivery is fully in-process, using a buffered Go channel drained by a fixed pool of goroutines — all declared in `internal/webhook/webhook.go`:

- **"Queue" declaration** — `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A buffered channel with capacity 128. This is the entire queue.

- **Workers consuming** — `internal/webhook/webhook.go:42-55` (`init()`): a loop `for range 4` spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)` to do the actual `net/http` delivery (via an SSRF-guarded `safeClient`).

- **Producer side** — `PostAsync` does a non-blocking `select` send onto `asyncPostQueue`, dropping the payload (with a warning) if the buffer is full.

So the "message broker" and "queue" are an in-memory `chan *WebhookRequestPayload` (cap 128) and its 4 consuming goroutines, all in `internal/webhook/webhook.go` — not a broker-backed queue.
