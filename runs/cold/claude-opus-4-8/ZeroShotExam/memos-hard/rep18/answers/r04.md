**Premise correction:** The question's premise is false — the webhook delivery workers consume from *neither* NATS nor RabbitMQ. This repository (a Memos-style Go app) uses no external message broker at all for webhooks.

**Actual mechanism:** Webhook delivery is an in-process Go worker pool draining a buffered channel.

- The "queue" is a package-level buffered Go channel with capacity 128, declared in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- An `init()` function (`internal/webhook/webhook.go:42-55`) spawns 4 goroutine workers, each consuming from that channel (`for payload := range asyncPostQueue` at line 45) and calling `Post()` to perform the actual HTTP delivery.
- Producers enqueue non-blockingly via `PostAsync()` (`internal/webhook/webhook.go:184-196`), using a `select { case asyncPostQueue <- ...: default: /* drop + warn */ }` so a full buffer drops the webhook rather than blocking (line 190 enqueue, line 192 drop-warning).
- Callers enqueue on memo events via `webhook.PostAsync(...)` in `server/router/api/v1/memo_service_webhooks.go:43` and `:71`. The database only stores webhook endpoint configs (`s.Store.GetUserWebhooks`), not delivery jobs.
- `go.mod` confirms there are no broker client libraries (no `nats.go`, no `amqp`/RabbitMQ, no Kafka/Redis).

Because the queue is purely in-memory, any queued-but-undelivered webhooks are lost on process restart.
