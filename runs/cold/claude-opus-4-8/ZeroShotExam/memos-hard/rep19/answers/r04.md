**Premise correction:** The question's premise is false — the webhook delivery workers consume from **neither NATS nor RabbitMQ**. This repository (memos) uses **no external message broker at all** for webhook delivery.

**Actual mechanism:** Webhook dispatch is handled entirely in-process using a buffered **Go channel** as the queue, with a pool of goroutine workers.

- The "queue" is declared as a package-level buffered channel in `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- The delivery workers are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` to dispatch the HTTP request:
  ```go
  func init() {
      for range 4 {
          go func() {
              for payload := range asyncPostQueue {
                  if err := Post(payload); err != nil { ... }
              }
          }()
      }
  }
  ```
- Enqueueing happens in `PostAsync()` at `internal/webhook/webhook.go:184-196`, which does a non-blocking send onto the channel (`select { case asyncPostQueue <- ...: default: ...drop... }`), dropping the payload with a warning if the buffer (capacity 128) is full.

So the "broker" is a bounded in-memory channel, and the "workers" are goroutines — there is no NATS/JetStream subscription, no AMQP connection, exchange, or queue declaration anywhere in the webhook path. (A grep of the repo for `nats`, `amqp`, or `rabbitmq` in the webhook/server code turns up nothing driving this.)
