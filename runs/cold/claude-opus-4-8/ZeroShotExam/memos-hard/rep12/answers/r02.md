**Premise correction:** The question assumes this repository has per-user API rate-limiting middleware. It does not. No rate-limiting middleware, interceptor, or handler exists anywhere in the codebase — not per-user, not per-IP, not per-token, not global. Nothing returns HTTP 429 / `CodeResourceExhausted` based on request frequency, so there is no registration point and no request limits to report.

What the request pipeline actually enforces:

- **Echo HTTP middleware** (`server/server.go:51-52`): panic recovery (`middleware.Recover()`) and CORS (`newCORSMiddleware`). Static/SPA serving in `server/router/frontend/frontend.go:54,59`.
- **Connect RPC interceptors** (registered in `server/router/api/v1/v1.go:133-141`): metadata copying, logging, recovery, and authentication (`NewAuthInterceptor`) — implemented in `server/router/api/v1/connect_interceptors.go`. None does rate limiting.
- The only per-request "limit" is a **body-size cap**, not a rate limit: `const maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied at lines 126, 141, 144. This bounds payload size per request, not request frequency.

Things that might be mistaken for rate limiting but aren't:
- `server/router/api/v1/auth_service_session.go:99,108,134` — "sliding window" refers to 30-day session/refresh-token rotation, not API throttling.
- `internal/email/README.md:286-295` and `internal/email/doc.go:86` — only *suggest* email-send rate limiting as a future idea (`rate.NewLimiter(...)` example); not implemented.
- `go.mod:151` — `golang.org/x/time` is an *indirect* transitive dependency, not imported by any application code.

If per-user rate limiting were desired, it would be a net-new interceptor added to the Connect chain around `server/router/api/v1/v1.go:133`.
