A profile avatar in Memos is **not** stored as a file/blob — it's stored as a base64 **data URI in the `user.avatar_url` column**. A browser hitting `GET /file/users/:identifier/avatar` reaches that column through this chain:

1. `serveUserAvatar` — server/router/fileserver/fileserver.go:168
 (route `GET /file/users/:identifier/avatar` registered at server/router/fileserver/fileserver.go:124; serving handler)
2. `getUserByUsername` — server/router/fileserver/fileserver.go:715
 (wraps the lookup: `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`)
3. `(*store.Store).GetUser` — store/user.go:148
 (cache check, then delegates to ListUsers)
4. `(*store.Store).ListUsers` — store/user.go:136
 (calls `s.driver.ListUsers`)
5. `(*sqlite.DB).ListUsers` — store/db/sqlite/user.go:88
 (final data layer: `SELECT ... avatar_url ... FROM user WHERE ...`, scanned into `user.AvatarURL` at store/db/sqlite/user.go:186)
 (equivalent drivers: store/db/postgres/user.go, store/db/mysql/user.go:147)

The handler then turns the stored value into response bytes at the top level: `parseDataURI(user.AvatarURL)` (server/router/fileserver/fileserver.go:196, defined at :737) base64-decodes the data URI, and `c.Blob(...)` (server/router/fileserver/fileserver.go:209) writes the image.

Note: because the avatar is a column on the user row, the "data layer" is the `user` table read (hop 5), not the attachment/blob storage path (`getAttachmentBlob` / S3 / local file) used for memo attachments.
