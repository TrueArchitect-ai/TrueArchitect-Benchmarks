**Mechanism:** By explicit Go code (SQL `DELETE` statements run inside the user-delete transaction). There is no database-level cascade rule, and it is not "not at all."

This is the `memos` project (`github.com/usememos/memos`). Emoji reactions live in the `reaction` table (its `reaction_type` column holds the emoji). When a user is deleted, the store's `DeleteUser` transaction explicitly removes reactions in two ways — reactions *made by* the deleted user, and reactions *on* the deleted user's memos.

**Evidence locations:**

1. **No DB-level rule.** The `reaction` table schema has `creator_id`/`content_id` but no foreign key and no `ON DELETE CASCADE`:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`
   - A grep for `cascade`/`foreign key`/`references` against the reaction table returned nothing.

2. **Explicit Go deletion**, invoked from the delete-user transaction `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`, calls at lines 96 and 102):
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions on the deleted user's memos: `store/db/sqlite/user_delete.go:380-388`
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user authored: `store/db/sqlite/user_delete.go:400-403`

3. **All three DB drivers do the same** (mirrored implementations):
   - Postgres: `store/db/postgres/user_delete.go:96,102,380-403`
   - MySQL: `store/db/mysql/user_delete.go:96,102,417-438`
