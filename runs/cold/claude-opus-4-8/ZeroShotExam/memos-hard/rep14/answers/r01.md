**Premise correction:** There is no Redis. A repo-wide search for `redis` returns zero matches, and `go.mod`/`go.sum` contain no Redis (or memcached) client dependency. So there is no Redis connection to configure for the cache layer.

**Actual mechanism:** The cache is a custom, thread-safe **in-memory** cache built on Go's `sync.Map`, with per-item TTL and a background cleanup goroutine — it lives entirely in process memory, with no network connection or config file/env vars.

- Implementation: `store/cache/cache.go` — the `Cache` struct backed by `sync.Map` (`cache.go:66-73`), with `Config`/`DefaultConfig` (`cache.go:41-64`) and lazy + periodic expiration (`cache.go:135-144`, `217-250`).
- Wiring / "configuration": `store/store.go` declares a dedicated `userCache` (`store.go:28`) and builds the cache config inline in `Store.New` with hard-coded values `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000` (`store.go:40-45`); all three caches are created via `cache.New(cacheConfig)` (`store.go:51-53`).

**TTL for user entries: 10 minutes.** User writes all go through the plain `Set` method, which applies the cache's `DefaultTTL` — e.g. `store/user.go:98, 122, 132, 143, 167` (`s.userCache.Set(...)`). No `SetWithTTL` override exists for users, so the 10-minute default from `store/store.go:41` applies.

(Note: `golang-lru/v2` appears in `go.sum` as an available dependency but does not back this cache layer.)
