The premise is incorrect — webhook delivery workers use **neither NATS nor RabbitMQ**. There is no external message broker involved at all.

The actual mechanism is a **buffered in-process Go channel** with a pool of goroutine workers, declared entirely in **`internal/webhook/webhook.go`**:

- **Queue declaration** (line ~39): `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a package-level buffered channel with capacity 128.
- **Worker pool** (lines ~42–55, in `init()`): 4 goroutines are spawned at package init time, each consuming from the channel in a `for payload := range asyncPostQueue` loop and calling `Post()` to make the outbound HTTP request.
- **Enqueue** (lines ~184–196, `PostAsync`): a non-blocking `select` send on the channel; if the buffer is full, the webhook is silently dropped with a warning log — no retry, no persistence, no dead-letter queue.

There are no dependencies on NATS, RabbitMQ, Redis, Kafka, or any other external broker in `go.mod`. The entire dispatch path is in-memory and in-process.
