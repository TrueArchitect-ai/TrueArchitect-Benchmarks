**What I checked:**

1. **Database schema** — The `reaction` table has no foreign key on `creator_id` referencing `users`, so there is no `ON DELETE CASCADE`.
   - `store/migration/postgres/0.20/00__reaction.sql` (and equivalent sqlite/mysql migrations)
   - `store/migration/postgres/LATEST.sql:91-98`

2. **Go deletion code** — `deleteUserTargetsTx` in each driver explicitly removes reactions in two steps within the same transaction:
   - **Step A** — delete all reactions on the deleted user's memos (by `content_id`): `store/db/sqlite/user_delete.go:96` calls `deleteReactionsByContentIDsTx`, implemented at lines 380–388 (`DELETE FROM reaction WHERE content_id IN ...`).
   - **Step B** — delete all reactions the user placed on anyone's content (by `creator_id`): `store/db/sqlite/user_delete.go:102` calls `deleteReactionsByCreatorTx`, implemented at lines 400–402 (`DELETE FROM reaction WHERE creator_id = ?`).
   - Identical logic in `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`.

3. **Tests confirm the behavior** — `store/test/user_delete_test.go:97-114` and `server/router/api/v1/test/user_service_delete_test.go:188-211` create reactions by both the target user and a peer, then assert after deletion that only the peer's reaction on the peer's own memo survives.

**Mechanism: explicit Go code**; both the user's own reactions and all reactions on the user's content are deleted transactionally before the user row itself is removed.
