h07.

Request: `GET /file/users/:identifier/avatar`

```
serveUserAvatar         — server/router/fileserver/fileserver.go
getUserByUsername        — server/router/fileserver/fileserver.go
Store.GetUser           — store/user.go
Store.ListUsers         — store/user.go
Driver.ListUsers        — store/driver.go (interface)
DB.ListUsers            — store/db/sqlite/user.go (or postgres/mysql equivalents)
```

**Details per hop:**

1. **`serveUserAvatar`** — `server/router/fileserver/fileserver.go` — HTTP handler registered on `GET /file/users/:identifier/avatar`. Extracts the username from the path, looks up the user, parses the `AvatarURL` field (a base64 data URI), and writes the decoded bytes as the response.
2. **`getUserByUsername`** — `server/router/fileserver/fileserver.go` — Helper that wraps the store call, constructing a `FindUser{Username: &identifier}` and calling `s.Store.GetUser(...)`.
3. **`Store.GetUser`** — `store/user.go` — Checks an in-memory `userCache` (keyed by ID; misses here since the query is by username), then delegates to `s.ListUsers(ctx, find)` and returns the first result.
4. **`Store.ListUsers`** — `store/user.go` — Thin wrapper that calls `s.driver.ListUsers(ctx, find)` and caches each returned user by ID.
5. **`Driver.ListUsers`** — `store/driver.go` — Interface method satisfied by concrete database backends.
6. **`DB.ListUsers`** — `store/db/sqlite/user.go` (line 88; analogues in `postgres/user.go` and `mysql/user.go`) — Builds and executes `SELECT ... avatar_url ... FROM user WHERE username = ?`, scanning `avatar_url` into `user.AvatarURL`.

The avatar is stored inline as a base64 data URI in the `avatar_url` column of the `user` table — not as a separate file. The handler decodes it via `parseDataURI` (`server/router/fileserver/fileserver.go`) before serving.
