The premise is incorrect — webhook delivery workers consume from **neither NATS nor RabbitMQ**. There is no external message broker involved at all.

The actual mechanism is a **plain Go buffered channel** used as an in-memory async dispatch queue, declared entirely in `internal/webhook/webhook.go`:

- **Line 39** declares the queue: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a buffered channel with capacity 128.
- **Lines 42–55** (`init()` function) spawn **4 goroutine workers**, each looping over the channel via `for payload := range asyncPostQueue` and calling `Post()` to make the HTTP delivery.
- **Lines 184–196** (`PostAsync()`) enqueue payloads with a non-blocking `select`; if the channel is full, the webhook is silently dropped with a warning log.

There is no external broker dependency in `go.mod`, no NATS/RabbitMQ/Kafka/Redis configuration anywhere in the codebase. The buffer size (128) and worker count (4) are hardcoded constants — no external configuration. Webhook dispatch is triggered from `server/router/api/v1/memo_service_webhooks.go`, which calls `webhook.PostAsync()` to enqueue payloads onto the channel.
