The browser requests `GET /file/users/:identifier/avatar`. Here is each hop from the route to stored data:

1. `FileServerService.RegisterRoutes` — `server/router/fileserver/fileserver.go:124` — registers the route on the `/file` group
2. `FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go:168` — HTTP handler; extracts the `:identifier` param, optionally authenticates, then delegates to find the user
3. `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715` — thin helper that calls `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`
4. `Store.GetUser` — `store/user.go:148` — checks the in-memory user cache (by ID only), then falls through to `s.ListUsers()`
5. `Store.ListUsers` — `store/user.go:136` — delegates to `s.driver.ListUsers(ctx, find)`
6. `DB.ListUsers` — `store/db/sqlite/user.go:88` (also `store/db/postgres/user.go`, `store/db/mysql/user.go`) — builds and executes `SELECT … avatar_url … FROM user WHERE username = ?`, scans `avatar_url` (a base64 data URI) into `user.AvatarURL`
7. `FileServerService.parseDataURI` — `server/router/fileserver/fileserver.go:737` — back in the handler, decodes the data URI via regex + `base64.StdEncoding.DecodeString` into raw image bytes and MIME type, which `serveUserAvatar` returns via `c.Blob()`

The avatar is stored inline in the `avatar_url` column of the `user` table as a `data:<mime>;base64,…` string — no filesystem or object-storage hop is involved.
