The browser hits `GET /file/users/:identifier/avatar`. Each hop:

1. `serveUserAvatar` — `server/router/fileserver/fileserver.go:168` — the Echo HTTP handler; extracts the `:identifier` param and orchestrates auth, lookup, and response.
2. `getUserByUsername` — `server/router/fileserver/fileserver.go:715` — thin helper that wraps the store call with a `FindUser{Username: &identifier}`.
3. `Store.GetUser` — `store/user.go:148` — checks the in-memory `userCache` (by ID only), then delegates to `ListUsers`.
4. `Store.ListUsers` — `store/user.go:136` — calls `s.driver.ListUsers(ctx, find)` through the `Driver` interface.
5. `Driver.ListUsers` (interface) — `store/driver.go:47` — the database-driver contract.
6. `DB.ListUsers` (sqlite impl) — `store/db/sqlite/user.go:88` — builds and executes `SELECT … avatar_url … FROM user WHERE username = ?`, scanning `avatar_url` (a base64 data-URI stored inline in the row) into `store.User.AvatarURL`.

Back in `serveUserAvatar`, the handler calls `parseDataURI` (same file, line 196) to decode the base64 data-URI into raw bytes and a MIME type, then writes them to the response with `c.Blob()`. The image is stored entirely in the database column — there is no filesystem or object-storage hop for avatars.
