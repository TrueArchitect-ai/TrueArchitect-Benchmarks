**Explicit Go code**; reactions are removed by two explicit `DELETE` statements in the user-deletion transaction, not by any database-level cascade or foreign key rule.

Evidence locations (the same pattern is replicated across all three drivers):

1. **`deleteReactionsByContentIDsTx`** — deletes reactions on the user's memos by content ID (`DELETE FROM reaction WHERE content_id IN ...`):
   - `store/db/sqlite/user_delete.go:380-388`
   - `store/db/mysql/user_delete.go:417-425`
   - `store/db/postgres/user_delete.go` (same structure)

2. **`deleteReactionsByCreatorTx`** — deletes reactions the user themselves created (`DELETE FROM reaction WHERE creator_id = ?`):
   - `store/db/sqlite/user_delete.go:400-403`
   - `store/db/mysql/user_delete.go:437-439`

3. Both are called from **`deleteUserTargetsTx`** within the delete-user transaction:
   - `store/db/sqlite/user_delete.go:96` and `:102`
   - `store/db/mysql/user_delete.go:96` and `:102`

So when a user is deleted, their reactions are cleaned up in two passes of explicit Go code: first, all reactions targeting the user's memos (by `content_id`), then all reactions the user authored elsewhere (by `creator_id`). Both run inside the same database transaction that deletes the user row.
