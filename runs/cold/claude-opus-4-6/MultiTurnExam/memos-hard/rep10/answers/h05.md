**Mechanism: explicit Go code**; reactions are removed by two separate DELETE statements executed within the user-deletion transaction — no database-level CASCADE is involved.

**Evidence locations:**

1. **Reactions on the user's memos** — `deleteReactionsByContentIDsTx` deletes all reactions whose `content_id` matches the user's memo UIDs: `store/db/sqlite/user_delete.go:380–388`, `store/db/postgres/user_delete.go:383`, `store/db/mysql/user_delete.go:420`.

2. **Reactions created by the user** (on anyone's content) — `deleteReactionsByCreatorTx` deletes all reactions where `creator_id` matches the user: `store/db/sqlite/user_delete.go:400–403`, `store/db/postgres/user_delete.go:401`, `store/db/mysql/user_delete.go:438`.

3. Both are called from `deleteUserTargetsTx` at `store/db/sqlite/user_delete.go:96` and `:102` (and equivalently in the postgres/mysql drivers), inside a single transaction that also removes the user's memos, attachments, settings, identities, inbox entries, and the user row itself.

4. **No foreign-key CASCADE** — a grep for `ON DELETE CASCADE` referencing the `reaction` table across all migration SQL files found nothing; the reaction table has no foreign key constraints that would auto-delete rows.
