**Tables affected: `memo`, `memo_relation`, `attachment`, `memo_share`**

Details of how each is touched:

- **`memo`** — deleted directly. The store layer runs `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`, with equivalents in `store/db/postgres/memo.go:244` and `store/db/mysql/memo.go:259`). The API handler also cascades to comment memos first: `APIV1Service.DeleteMemo` lists relations of type `COMMENT` and calls `store.DeleteMemo` for each comment memo before deleting the target (`server/router/api/v1/memo_service.go:567-582`).
- **`memo_relation`** — explicit cascade in Go: `Store.DeleteMemo` deletes relation rows where the memo is either source (`MemoID`) or target (`RelatedMemoID`) (`store/memo.go:140-147`).
- **`attachment`** — explicit cascade in Go: `Store.DeleteMemo` lists attachments linked to the memo and deletes each via `DeleteAttachment` (`store/memo.go:148-157`), which removes the storage object and then the `attachment` row (`store/attachment.go:132-148`, `store/db/sqlite/attachment.go:212`).
- **`memo_share`** — deleted by an explicit `ON DELETE CASCADE` foreign key on `memo_share.memo_id → memo.id` in all three database schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). This is a schema-level cascade rather than Go code.

Notably, the `reaction` table is **not** cleaned up — the API handler lists reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); nothing deletes them during memo deletion.
