Runners actually started, and their triggers:

- **S3 presign runner** — the only runner launched by `Server.startBackgroundRunners` (`server/server.go:153-174`, called from `Start`). It first does a synchronous `RunOnce` at boot, then loops in a goroutine on a `time.NewTicker` with a 12-hour interval (`server/runner/s3presign/runner.go:27-30`), re-presigning stale S3 attachment URLs.
- **Cache cleanup loops (×3)** — started as a side effect of `store.New` (`store/store.go:51-53`), each cache spawns `go c.cleanupLoop()` (`store/cache/cache.go:83`) driven by a `time.NewTicker` at a 5-minute interval (`store/cache/cache.go:201`, interval set in `store/store.go:41`).
- **Webhook dispatch pool (×4 goroutines)** — started by package `init()` in `internal/webhook/webhook.go:42-55`; purely event-driven, consuming a buffered channel (cap 128) fed by `PostAsync`. No timer; never stopped on shutdown.
- **Email sender pool (×2 goroutines)** — started by package `init()` in `internal/email/email.go:16-36`; event-driven off a buffered channel (cap 128) fed by `SendAsync`. Also never stopped on shutdown.

(Per-request only, not boot-started: a 30-second SSE heartbeat ticker per connection in `server/router/api/v1/sse_handler.go:64`.)

Unused scheduling infrastructure:

- **`internal/scheduler` is completely unused by the server.** It's a full cron engine (~640 LOC) with a hand-written cron-expression parser (`internal/scheduler/parser.go`), timezone-aware jobs, and a middleware chain (`internal/scheduler/middleware.go`) — but the only importers in the entire repo are its own tests (`example_test.go`, `integration_test.go`). Nothing in `cmd/`, `server/`, or `store/` ever calls `scheduler.New`/`Register`/`Start`, even though `AGENTS.md:69` advertises it.
- Additionally, **`memopayload.Runner`** (`server/runner/memopayload/runner.go:14-72`) is a dead runner type — `NewRunner` has zero callers. The package is imported only for the free function `RebuildMemoPayload`, called synchronously inline from `server/router/api/v1/memo_service.go`, so despite living under `server/runner/`, no background memopayload runner exists.
- There are no third-party scheduling/job-queue dependencies in `go.mod` (no robfig/cron, gocron, asynq, etc.) — all scheduling is hand-rolled tickers and channels.
