**Tables affected: `memo`, `memo_relation`, `attachment`** (via explicit cascade code), plus **`memo_share`** (via a schema-level `ON DELETE CASCADE`, not Go code).

Details:

- `Store.DeleteMemo` (`store/memo.go:140-159`) explicitly cascades before the final delete:
  - `memo_relation` — deleted twice via `driver.DeleteMemoRelation`, once where the memo is the source (`MemoID`) and once where it is the target (`RelatedMemoID`) (`store/memo.go:142-147`).
  - `attachment` — all attachments linked to the memo are listed and deleted one by one via `DeleteAttachment` (`store/memo.go:149-157`), which removes the row in `store/db/sqlite/attachment.go:212` (and also deletes the underlying file/S3 object, which is storage, not a table).
  - `memo` — the row itself, via `driver.DeleteMemo` (`store/memo.go:158`; SQL in `store/db/sqlite/memo.go:239`, and equivalents in `store/db/postgres/memo.go:246` and `store/db/mysql/memo.go:261` — all plain `DELETE FROM memo`).
- The API handler (`server/router/api/v1/memo_service.go:518-593`) additionally deletes all comment memos first by calling `store.DeleteMemo` for each comment relation (`memo_service.go:567-577`), which touches the same three tables for each comment.
- `memo_share` rows are removed by the database itself: the schema defines `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, same in `postgres/LATEST.sql:108` and `mysql/LATEST.sql:108`). There is no Go code deleting shares in the memo-delete path.
- Notably **not** affected: `reaction` — the handler lists reactions only to build the webhook payload (`memo_service.go:545-550`); nothing deletes them (reaction cleanup exists only in the user-deletion path, `store/db/sqlite/user_delete.go:383`).
