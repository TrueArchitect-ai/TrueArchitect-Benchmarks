**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share` (the last via a schema-level `ON DELETE CASCADE`).**

Details:

- `memo` — the row itself is deleted by the driver's `DeleteMemo` (`store/db/sqlite/memo.go:237`, plus the postgres/mysql equivalents), invoked from `store.DeleteMemo` in `store/memo.go:140`. The API handler (`server/router/api/v1/memo_service.go:518`) also recursively deletes comment memos (more `memo` rows) before deleting the parent.
- `memo_relation` — explicit cascade code in `store/memo.go` calls `driver.DeleteMemoRelation` twice, once for `MemoID` and once for `RelatedMemoID`, before deleting the memo.
- `attachment` — explicit cascade code in `store/memo.go` lists attachments linked to the memo and deletes each via `store.DeleteAttachment` (`store/attachment.go:132`), which removes the row through `driver.DeleteAttachment` (e.g. `store/db/sqlite/attachment.go:211`). (It also deletes the attachment's blob from storage, but that's not a table.)
- `memo_share` — not touched by Go code, but its rows are deleted automatically by the database: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`).

Notably *not* cleaned up by DeleteMemo: `reaction` rows (the handler only lists them for the webhook payload) and `memo_organizer`.
