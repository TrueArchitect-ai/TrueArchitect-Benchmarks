**Answer:** `web/src/connect.ts`; short-lived Bearer access tokens (JWT) plus the HTTP-only refresh-token cookie used to renew them; `server/auth`.

Details:

- **Interceptor:** `authInterceptor` in `web/src/connect.ts:156` is a Connect RPC `Interceptor` installed on the transport (`web/src/connect.ts:184-189`) used by all service clients. On each request it attaches `Authorization: Bearer <token>` (`web/src/connect.ts:97-100`), does a preflight refresh if the token is expired/near expiry, and on a `Code.Unauthenticated` error refreshes once and retries (marked with an `X-Retry` header), redirecting to login if refresh fails.
- **Tokens it manages:**
  - An **access token** with expiry, stored in memory/localStorage and synced across tabs via BroadcastChannel (`web/src/auth-state.ts`).
  - A **refresh token**, held as an HTTP-only cookie — the interceptor's refresh path calls `AuthService.refreshToken` over a separate transport with `credentials: "include"` (`web/src/connect.ts:57-83`), and deduplicates concurrent refreshes via `tokenRefreshManager`.
- **Backend validation:** the Go package `server/auth` — `server/auth/authenticator.go` exposes `AuthenticateByAccessTokenV2` (JWT access-token claims), `AuthenticateByRefreshToken`, and `AuthenticateByPAT` (personal access tokens), with bearer/cookie extraction in `server/auth/extract.go` and token logic in `server/auth/token.go`.
