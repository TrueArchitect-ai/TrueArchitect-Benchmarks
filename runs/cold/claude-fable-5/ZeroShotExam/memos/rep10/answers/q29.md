**Answer:** `web/src/connect.ts`; short-lived JWT access tokens (sent as `Authorization: Bearer`, ~15 min) plus a long-lived refresh token (httpOnly cookie, used to mint new access tokens); `server/auth`.

Details:

- **Interceptor:** The `authInterceptor` (a Connect RPC `Interceptor`) lives in `web/src/connect.ts:156`. It's attached to the Connect transport used by all service clients. On each request it obtains an access token via `getRequestToken()` and sets the `Authorization: Bearer <token>` header; on a `Code.Unauthenticated` error it refreshes the token once (marking the retry with an `X-Retry` header) and retries, redirecting to login on failure.
- **Tokens managed:** A short-lived **JWT access token** kept in memory/storage (`web/src/auth-state.ts`, storage key `memos_access_token`, shared across tabs via BroadcastChannel) and a long-lived **refresh token** carried in the `memos_refresh` cookie (requests use `credentials: "include"`, and `refreshAccessToken()` calls `AuthService.refreshToken` over a separate interceptor-free transport to avoid recursion). Preflight refresh happens when the access token is near expiry, deduplicated by a token-refresh manager.
- **Backend validation:** The `server/auth` Go package (`server/auth/token.go`, `server/auth/authenticator.go`). Its `Authenticator` does stateless JWT validation of access tokens (`AuthenticateByAccessTokenV2` / `ParseAccessTokenV2`, audience `user.access-token`, 15-minute lifetime), validates refresh tokens against the database (audience `user.refresh-token`, 30-day lifetime), and also supports long-lived Personal Access Tokens (`memos_pat_` prefix). This package is consumed by the gRPC/Connect interceptors in `server/router/api/v1` and the file server.
