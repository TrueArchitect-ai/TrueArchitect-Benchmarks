**Tables affected by explicit code: `memo`, `memo_relation`, `attachment`**

The call chain is `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) → `Store.DeleteMemo` (`store/memo.go:140`), which does the cascade in code:

- **`memo_relation`** — `store/memo.go:142-147` deletes relation rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`), executed as `DELETE FROM memo_relation` in the drivers (e.g. `store/db/sqlite/memo_relation.go:137`).
- **`attachment`** — `store/memo.go:149-157` lists attachments for the memo and deletes each via `Store.DeleteAttachment` (`store/attachment.go:132`), which removes blob storage and then the `attachment` row (`store/db/sqlite/attachment.go:212`).
- **`memo`** — the driver's `DeleteMemo` runs `DELETE FROM memo` (`store/db/sqlite/memo.go:237`). The API layer also first deletes all comment memos (rows in `memo` related via a `COMMENT` relation), each going through the same `Store.DeleteMemo` cascade (`server/router/api/v1/memo_service.go:567-577`).

One caveat: **`memo_share`** rows are also removed when a memo is deleted, but by a database-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` constraint in the schema (`store/migration/sqlite/LATEST.sql:109`, likewise in the postgres/mysql migrations), not by explicit cascade code. Reactions are listed before deletion only to build the webhook payload — the `reaction` table is not cleaned up by this path.
