**Mechanism: explicit Go code** — reactions are deleted by SQL statements the drivers run inside the `DeleteUser` transaction, not by any database-level cascade.

**Evidence:**

1. **Explicit Go deletion.** Each database driver's `DeleteUser` calls `deleteUserTargetsTx`, which removes reactions in two ways before deleting the user row:
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (reactions the user made): `store/db/sqlite/user_delete.go:400-403`, invoked at line 102 of the same file.
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (reactions on the user's memos, using `"memos/"+uid` content IDs built in `memoContentIDsFromRefs`, `store/db/sqlite/user_delete.go:512-518`): `store/db/sqlite/user_delete.go:380-388`, invoked at line 96.
   - The same two functions exist and are invoked in the Postgres driver (`store/db/postgres/user_delete.go:96,102,380,400`) and the MySQL driver (`store/db/mysql/user_delete.go:96,102,417,437`). The store layer entry point is `Store.DeleteUser` in `store/user.go:171`.

2. **No database-level rule for reactions.** The `reaction` table has no foreign keys at all — just a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — in the current schemas: `store/migration/sqlite/LATEST.sql:92-98`, `store/migration/postgres/LATEST.sql:91-97`, and the original creation migrations (`store/migration/{sqlite,postgres}/0.20/00__reaction.sql`). I also grepped the migrations for `CASCADE`; the `ON DELETE CASCADE` rules that exist apply to other tables (e.g. old `memo`, `user_setting`, `memo_resource` definitions), never to `reaction`. So without the explicit Go deletes, reaction rows would be orphaned rather than cleaned up by the database.
