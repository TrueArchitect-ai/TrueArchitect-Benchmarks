Memo visibility is enforced independently in each of these server surfaces:

- gRPC/Connect API memo reads — `checkMemoReadAccess` in `server/router/api/v1/memo_service.go:39` (public/protected/private + archived checks, used by GetMemo, `memo_service_comments.go:148`, etc.), plus list-side filtering that constrains `VisibilityList` for anonymous/other-user queries at `server/router/api/v1/memo_service.go:219-225`
- API reaction endpoints — per-memo visibility checks in `server/router/api/v1/reaction_service.go:30-38,83`
- API attachment endpoints — `checkAttachmentAccess` in `server/router/api/v1/attachment_service.go:422-451` and equivalent checks in `server/router/api/v1/memo_attachment_service.go:214-222`
- Static file server (attachment blobs) — `checkAttachmentPermission` in `server/router/fileserver/fileserver.go:650-704` (anonymous public access, share-token fallback, private-memo creator/admin check)
- RSS feeds — hard-coded to public-only memos via `VisibilityList: []store.Visibility{store.Public}` in `server/router/rss/rss.go:90,141`
- Frontend sitemap — only public memos listed in `getSitemapXML`, `server/router/frontend/frontend.go:149-151`
- SSE real-time event delivery — `SSEClient.canReceive` filters broadcasts by event visibility (private events only to creator/admin) in `server/router/api/v1/sse_hub.go:134-144`
- In-app notifications — `canViewerAccessMemo` in `server/router/api/v1/user_service_notifications.go:302-316` gates notification payloads; mention notifications are additionally gated by `canUserAccessMentionContext` in `server/router/api/v1/memo_mention_helpers.go:56`
- Email notifications — a separate `canViewerAccessMemo` copy in `server/notification/email.go:306-320`, applied before sending at `email.go:155,187`

So beyond the primary API check, visibility is re-enforced in the fileserver, RSS, sitemap, SSE hub, and both notification pipelines (in-app and email), with per-resource duplicates in the reaction and attachment services.
