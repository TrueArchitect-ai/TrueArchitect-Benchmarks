A browser hits `GET /file/users/:identifier/avatar`, and the avatar bytes are stored as a base64 data URI in the `user.avatar_url` DB column. Each hop from serving handler down to that column:

1. `FileServerService.serveUserAvatar` — server/router/fileserver/fileserver.go:168 (route registered at :124; serves the decoded blob after `parseDataURI` at :196)
2. `FileServerService.getUserByUsername` — server/router/fileserver/fileserver.go:715
3. `Store.GetUser` — store/user.go:148
4. `Store.ListUsers` — store/user.go:136 (calls `s.driver.ListUsers`)
5. `Driver.ListUsers` (interface) — store/driver.go
6. `DB.ListUsers` — store/db/sqlite/user.go:88 (SQL `SELECT ... avatar_url ... FROM user`, scanned into `user.AvatarURL` at :189; Postgres/MySQL equivalents in store/db/postgres/user.go and store/db/mysql/user.go)

The stored data is the `avatar_url` column of the `user` table, holding a `data:<mime>;base64,...` URI that `serveUserAvatar` decodes via `parseDataURI` (fileserver.go:737) and returns with `c.Blob`.

Note on authorization: the handler does not restrict which user's avatar you may fetch — on a public instance it's served to anyone, and on a private instance it only requires *any* authenticated viewer (fileserver.go:173-181), then looks up the target by username (`FindUser{Username: &identifier}`), so "another user's" profile image is reachable by design.
