**Mechanism: explicit Go code.** Each database driver's `DeleteUser` runs, inside a single transaction, explicit `DELETE FROM reaction ...` statements — it could not be a database-level rule, because the `reaction` table has no foreign keys at all.

Evidence I checked:

1. **Explicit deletes in the driver code.** The store `DeleteUser` (`store/user.go:171`) delegates to per-database drivers. In each driver's `deleteUserTargetsTx`, reactions are deleted in two ways before the user row itself is deleted:
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (reactions the user made): `store/db/sqlite/user_delete.go:400-403`, `store/db/postgres/user_delete.go:400-403`, `store/db/mysql/user_delete.go:438`.
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (reactions on the user's memos and their comment tree): `store/db/sqlite/user_delete.go:380-388`, `store/db/postgres/user_delete.go:380-388`, `store/db/mysql/user_delete.go:420`.
   - Both are invoked from `deleteUserTargetsTx` (e.g. `store/db/sqlite/user_delete.go:96-104`) within the same transaction that finally deletes the `user` row (`deleteUserRowTx`).

2. **No database-level rule possible.** The `reaction` table definition has no foreign key, so no `ON DELETE CASCADE` (or trigger) exists — just plain columns and a unique constraint: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (same in the original `0.20/00__reaction.sql` migrations).

So: reactions are removed by explicit Go code in the DeleteUser transaction of each driver (SQLite, Postgres, MySQL), covering both reactions authored by the deleted user and reactions left by others on that user's content.
