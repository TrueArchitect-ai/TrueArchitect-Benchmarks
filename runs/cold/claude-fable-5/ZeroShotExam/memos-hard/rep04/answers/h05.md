**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE` statements inside the user-deletion transaction — not by any database cascade. The `reaction` table has no foreign keys at all, so a DB-level rule couldn't do it.

What I checked:

**Explicit Go code (all three DB drivers):**
- `store/db/sqlite/user_delete.go:92-127` — `deleteUserTargetsTx` runs inside the `DeleteUser` transaction and calls two reaction cleanups:
  - `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`): `DELETE FROM reaction WHERE creator_id = ?` — removes the reactions the deleted user made.
  - `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-388`): `DELETE FROM reaction WHERE content_id IN (...)` — removes anyone's reactions on the deleted user's memos (content IDs built as `"memos/"+uid` at `store/db/sqlite/user_delete.go:512-518`).
- The Postgres and MySQL drivers have the same functions: `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`.
- Entry point: `Store.DeleteUser` at `store/user.go:171` dispatches to the driver's `DeleteUser` (`store/db/sqlite/user_delete.go:29`), which wraps everything in one transaction.

**No database-level rule:**
- The `reaction` table definitions have no `FOREIGN KEY` / `ON DELETE` clauses — just a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, and the original migrations `store/migration/{sqlite,postgres}/0.20/00__reaction.sql`.

There's also an integration test covering this path at `server/router/api/v1/test/user_service_delete_test.go`.
