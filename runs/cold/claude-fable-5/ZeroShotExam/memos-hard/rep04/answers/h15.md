Memo visibility is enforced independently on several server surfaces, each re-implementing the same rule (public → anyone; protected → any authenticated user; private → creator or admin only):

- gRPC/REST memo API (GetMemo access check + ListMemos visibility filter) — `server/router/api/v1/memo_service.go` (visibility check at `server/router/api/v1/memo_service.go:55-66`, list filtering to `Public`/`Protected` for non-owners at `:219-225`)
- Related API-v1 endpoints that repeat the same check per-resource — `server/router/api/v1/reaction_service.go:30-40,83`, `server/router/api/v1/attachment_service.go:445-451`, `server/router/api/v1/memo_attachment_service.go:214-222`, `server/router/api/v1/memo_service_comments.go:41`
- Raw attachment/file downloads (Echo file server, including share-token fallback) — `server/router/fileserver/fileserver.go:660-702`
- RSS/Atom feeds (queries only `Public` memos) — `server/router/rss/rss.go:90,141`
- Frontend sitemap generation (only `Public` memo URLs are emitted) — `server/router/frontend/frontend.go:150`
- SSE real-time event delivery (server-side per-client filtering in `canReceive`: private events only to creator/admin) — `server/router/api/v1/sse_hub.go:134-144`

So beyond the primary API check in `memo_service.go`, the fileserver, RSS router, frontend sitemap, and SSE hub each enforce visibility separately because they bypass the memo API path.
