**Mechanism: explicit Go code.** When a user is deleted, each database driver's `DeleteUser` implementation runs explicit `DELETE FROM reaction ...` statements inside the delete-user transaction — there is no database-level cascade involved, because the `reaction` table has no foreign keys at all.

**Evidence:**

1. **Explicit Go deletes** — in `store/db/sqlite/user_delete.go`, `deleteUserTargetsTx` removes reactions in two ways before deleting the user row:
   - `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:96,380`) — `DELETE FROM reaction WHERE content_id IN (...)`, covering reactions (from any user) on the deleted user's memos and their comment tree.
   - `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:102,400`) — `DELETE FROM reaction WHERE creator_id = ?`, covering reactions the deleted user made anywhere.

   The Postgres and MySQL drivers have identical logic: `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`. All run inside a single transaction begun in each driver's `DeleteUser` (e.g. `store/db/sqlite/user_delete.go:29-59`).

2. **No database-level rule** — the `reaction` table schema has no `FOREIGN KEY` / `ON DELETE CASCADE` clauses in any backend: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-96` (same in the original `0.20/00__reaction.sql` migrations). A grep for `FOREIGN KEY|REFERENCES` across `store/migration/` shows cascades on other tables (memo, user_setting, etc.) but none on `reaction`, so a DB rule could not remove them — the explicit Go deletes are what does it.
