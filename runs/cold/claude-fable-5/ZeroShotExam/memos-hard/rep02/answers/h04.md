**Yes — but only in one place, a unit test inside the MySQL package itself; no production code outside the factory ever constructs it.**

Evidence:

- The driver-selection factory is `store/db/db.go` (`NewDBDriver`), which is the sole call site of the constructor: `mysql.NewDB(profile)` at `store/db/db.go:22`. The constructor itself is `store/db/mysql/mysql.go:20` (`func NewDB(...)`), which builds the struct literal `DB{profile: profile}` at `store/db/mysql/mysql.go:29`.
- A repo-wide grep for any construction of the driver (`mysql.NewDB`, `mysql.DB{`, `&DB{`) finds exactly one direct construction outside the factory: `store/db/mysql/auth_config_test.go:12` — `db := &DB{}` in `TestIsRetryableAuthenticationMutationError`, which instantiates a zero-value driver to test the `IsRetryableAuthenticationMutationError` method (no real DB connection).
- Confirming nothing else can construct it externally: the only file in the entire repo that imports the `store/db/mysql` package is `store/db/db.go`. The integration tests in `store/test/` reference MySQL only as a config/container string and go through the factory, not the driver type directly. (The matching `&DB{}` hits in `store/db/postgres/*_test.go` are the Postgres driver, not MySQL.)

So the answer is yes in the strict sense — the test file `store/db/mysql/auth_config_test.go:12` constructs the `DB` struct directly — but all non-test code obtains the MySQL driver exclusively via the `NewDBDriver` factory in `store/db/db.go`.
