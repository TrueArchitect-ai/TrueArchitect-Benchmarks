The browser loads another user's avatar from `GET /file/users/:identifier/avatar`, and the image bytes live as a base64 data-URI in the database `user.avatar_url` column (not on disk or S3 like attachments). The hops:

```
serveUserAvatar — server/router/fileserver/fileserver.go:168        (serving handler for GET /file/users/:identifier/avatar, registered at :124)
getUserByUsername — server/router/fileserver/fileserver.go:715      (calls Store.GetUser with FindUser{Username: identifier})
Store.GetUser — store/user.go:148                                    (checks userCache, else delegates)
Store.ListUsers — store/user.go:136                                  (delegates to the DB driver)
DB.ListUsers — store/db/sqlite/user.go:88                            (SELECT ... avatar_url FROM user, scans into User.AvatarURL — line 159/189)
d.db.QueryContext — store/db/sqlite/user.go:173                      (executes the SQL against the database)
```

Notes:
- After the store returns the `User`, the handler reads `user.AvatarURL` (fileserver.go:192), decodes the `data:<type>;base64,...` value via `parseDataURI` (fileserver.go:737), and writes it with `c.Blob` (fileserver.go:209). So the "stored data" is the `avatar_url` text column, and the DB read is the terminal hop.
- The SQLite driver is shown; the equivalent driver hop exists for Postgres (`store/db/postgres/user.go:87`) and MySQL (`store/db/mysql/user.go:84`), selected at runtime.
- Authorization gate before the store call: on a non-anonymous instance, `serveUserAvatar` requires a valid viewer via `getCurrentUser` → `authenticator.AuthenticateToUser` (fileserver.go:173, 708); there's no per-target ACL beyond that, since avatars are treated as effectively public once you're allowed in.
