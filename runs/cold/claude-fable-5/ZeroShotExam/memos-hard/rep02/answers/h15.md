Memo visibility is enforced independently in seven places across the server. Distinct enforcement sites:

- gRPC MemoService read access — `checkMemoReadAccess` in `server/router/api/v1/memo_service.go:39` (called from `GetMemo` at `memo_service.go:356` and for comment parents in `server/router/api/v1/memo_service_comments.go:148`), plus list-time filtering in `ListMemos` (`memo_service.go:219-226`, restricting anonymous users to `PUBLIC` and other users to `PUBLIC/PROTECTED` or own memos)
- gRPC ReactionService — its own inline visibility check before listing/mutating reactions on a memo — `server/router/api/v1/reaction_service.go:29-40` (and again at line 83)
- gRPC AttachmentService — inline check of the linked memo's visibility before returning attachment metadata/content — `server/router/api/v1/attachment_service.go:445-453`
- HTTP file server (raw attachment bytes) — checks the owning memo's visibility, anonymous-access setting, share-token fallback, and private-memo creator/admin rule — `server/router/fileserver/fileserver.go:677-701`
- RSS feeds — queries only `store.Public` memos via `VisibilityList` — `server/router/rss/rss.go:90` and `rss.go:141`
- Frontend router (sitemap.xml) — lists only `store.Public` memos — `server/router/frontend/frontend.go:150`
- SSE hub (real-time events) — per-client delivery filter `canReceive` drops `Private` memo events unless the client is the creator or an admin — `server/router/api/v1/sse_hub.go:134-143`

Notably, the gRPC surfaces (MemoService, ReactionService, AttachmentService) each re-implement the check rather than sharing one helper, and the fileserver applies a slightly different rule set (it honors share tokens and the instance's anonymous-access profile).
