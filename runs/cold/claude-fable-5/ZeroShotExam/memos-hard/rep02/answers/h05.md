**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL `DELETE` statements inside the user-deletion transaction in each database driver; there is no database-level rule (the `reaction` table has no foreign keys, so no `ON DELETE CASCADE` is possible).

What I checked:

1. **The store-level user delete flow**: `store/user.go:171` (`Store.DeleteUser`) delegates to the driver, with shared types in `store/user_delete.go`.

2. **The driver implementations** — each runs two explicit reaction deletes inside the transaction (called from `deleteUserTargetsTx`):
   - Reactions **created by** the user: `DELETE FROM reaction WHERE creator_id = ?` in `deleteReactionsByCreatorTx` — `store/db/sqlite/user_delete.go:400-403`, `store/db/postgres/user_delete.go:400-401`, `store/db/mysql/user_delete.go:437-438`.
   - Reactions **on the user's memos** (including the recursive comment tree): `DELETE FROM reaction WHERE content_id IN (...)` in `deleteReactionsByContentIDsTx` — `store/db/sqlite/user_delete.go:380-388`, `store/db/postgres/user_delete.go:383`, `store/db/mysql/user_delete.go:420`. The `content_id` values are built as `"memos/" + uid` in `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go:512-518`).
   - Both are invoked from `deleteUserTargetsTx` at `store/db/sqlite/user_delete.go:96` and `:102` (postgres/mysql at `:102` likewise), before the `user` row itself is deleted.

3. **The schema, to rule out a DB-level rule**: `CREATE TABLE reaction` has no foreign key or cascade — just columns and a UNIQUE constraint — in `store/migration/sqlite/LATEST.sql:92-99` and `store/migration/postgres/LATEST.sql:91-98` (mysql schema matches).

So: **explicit Go code**, in the per-driver `user_delete.go` files, covering both reactions the user made and reactions others left on the user's memos; the schema itself would not clean anything up.
