Tables affected when DeleteMemo runs: **memo, memo_relation, attachment**

Details:

- **memo_relation** — `Store.DeleteMemo` (`store/memo.go:142-147`) explicitly deletes relation rows where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`).
- **attachment** — the same function lists the memo's attachments and deletes each row via `Store.DeleteAttachment` (`store/memo.go:148-157`; also removes the stored file, per `store/attachment.go`).
- **memo** — the memo row itself is deleted last via `driver.DeleteMemo` (`store/memo.go:158`, e.g. `DELETE FROM memo` in `store/db/sqlite/memo.go`). Additionally, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go`) first deletes all comment memos (child rows in the same `memo` table) by calling `Store.DeleteMemo` for each comment relation — which recursively touches the same three tables for each comment.

Notably, `reaction` and `memo_share` rows are *not* deleted by any explicit cascade code in this path (reactions are only listed for the webhook payload).
