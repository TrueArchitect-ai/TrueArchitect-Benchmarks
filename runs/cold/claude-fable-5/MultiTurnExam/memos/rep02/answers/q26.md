Tables affected by `Store.DeleteMemo` (`store/memo.go:140-159`) and its explicit cascade code:

1. **`memo_relation`** — rows where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`) are deleted first (`store/memo.go:142-147`).
2. **`attachment`** — every attachment linked to the memo is deleted via `Store.DeleteAttachment` (`store/memo.go:149-157`, `store/attachment.go:132-148`; this also removes the backing file/object from local or external storage, which is not a table).
3. **`memo`** — the memo row itself is deleted last via the dialect driver (`store/memo.go:158`; e.g. `store/db/sqlite/memo.go:237`, which is a plain `DELETE FROM memo` with no further DB-level cascades).

When deletion happens through the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:568-582`), comment memos (relations of type `COMMENT`) are also deleted through the same `Store.DeleteMemo` path first — so the same three tables are hit again for each comment. Reactions are only listed for the webhook payload, not deleted, and no other tables (e.g. `reaction`) are touched by explicit cascade code.
