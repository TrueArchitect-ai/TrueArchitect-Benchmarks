The browser hits `GET /file/users/{username}/avatar`, and each hop to the data layer is:

- `FileServerService.RegisterRoutes` (route `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (handler: optional auth check on private instances, then loads the user and writes the decoded image) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` (wraps the lookup in a `store.FindUser{Username}`) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks the in-memory user cache, falls through to a list query) — `store/user.go:148`
- `Store.ListUsers` (delegates to the configured driver, populates the cache) — `store/user.go:136`
- `store.Driver.ListUsers` (driver interface) — `store/driver.go:47`
- Driver implementation, e.g. `(*DB).ListUsers` — `store/db/sqlite/user.go:88` (or `store/db/mysql/user.go:84` / `store/db/postgres/user.go:87` depending on the configured database)

The "stored data" itself is the user row's `avatar_url` column, which holds the image as a data URI: `serveUserAvatar` decodes it with `parseDataURI` (`fileserver.go:196`), enforces the `avatarAllowedTypes` MIME allowlist (`fileserver.go:75,201`), and returns the bytes with `c.Blob` — so no separate file/S3 fetch happens for avatars, unlike memo attachments.
