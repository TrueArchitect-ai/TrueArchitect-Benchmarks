**Mechanism: explicit Go code** — each database driver's user-deletion transaction issues direct `DELETE FROM reaction` statements; there is no database-level rule (the `reaction` table has no foreign keys at all).

What I checked:

1. **The deletion code path:** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver. Each of the three drivers has a `user_delete.go` implementing a multi-table cleanup transaction, and each explicitly deletes reactions two ways — reactions *on* the user's content and reactions *made by* the user:
   - SQLite: `store/db/sqlite/user_delete.go:96,102`, with the SQL at lines 380–383 (`DELETE FROM reaction WHERE content_id IN ...`) and 400–401 (`DELETE FROM reaction WHERE creator_id = ?`)
   - MySQL: `store/db/mysql/user_delete.go:420,438` (same two statements)
   - Postgres: `store/db/postgres/user_delete.go:383,401` (same two statements)

2. **The schema, to rule out a database-level rule:** the `reaction` table DDL in `store/migration/sqlite/LATEST.sql:92-99` (and its Postgres/MySQL counterparts) defines no foreign key and no `ON DELETE CASCADE` — just a UNIQUE constraint on `(creator_id, content_id, reaction_type)`. The only `ON DELETE CASCADE` in any `LATEST.sql` belongs to a different table (`memo_share`'s `memo_id` FK, e.g. `store/migration/sqlite/LATEST.sql:109`), so nothing at the database level would remove reactions on user deletion.
