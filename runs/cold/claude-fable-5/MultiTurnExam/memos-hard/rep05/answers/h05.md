**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside each database driver's user-deletion transaction, not by any database-level rule.

Evidence I checked:

1. **Go deletion code**: Each driver's `DeleteUser` transaction explicitly removes reactions two ways — reactions *on* the deleted user's memos (`deleteReactionsByContentIDsTx`, `DELETE FROM reaction WHERE content_id IN ...`) and reactions *made by* the user (`deleteReactionsByCreatorTx`, `DELETE FROM reaction WHERE creator_id = ?`):
   - `store/db/sqlite/user_delete.go:96,102,380-401`
   - `store/db/postgres/user_delete.go:96,102,380-401`
   - `store/db/mysql/user_delete.go:96,102,417-438`

2. **No database-level rule**: The `reaction` table schema has no foreign keys at all — only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — so there is no `ON DELETE CASCADE` (or any FK) that could clean up rows when a user row is deleted. Checked `store/migration/sqlite/LATEST.sql:92-98`, `store/migration/postgres/LATEST.sql:91-97`, and the original creation migrations (`store/migration/sqlite/0.20/00__reaction.sql`, `store/migration/postgres/0.20/00__reaction.sql`); the MySQL schema is equivalent.
