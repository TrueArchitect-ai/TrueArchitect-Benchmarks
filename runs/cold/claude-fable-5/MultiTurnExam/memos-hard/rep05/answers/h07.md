The browser hits `GET /file/users/{identifier}/avatar`. The avatar isn't a file on disk — it's stored as a data URI in the user row's `avatar_url` column, so the "data layer" hop is the user query. The chain:

1. `FileServerService.RegisterRoutes` (routes `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:121-124`
2. `FileServerService.serveUserAvatar` (handler: anonymous-access check, then looks up the target user) — `server/router/fileserver/fileserver.go:168`
3. `FileServerService.getUserByUsername` (wraps the identifier into a `store.FindUser`) — `server/router/fileserver/fileserver.go:715`
4. `Store.GetUser` (checks the in-memory user cache, else falls through) — `store/user.go:148`
5. `Store.ListUsers` (delegates to the selected driver, populates cache) — `store/user.go:136-137`
6. `DB.ListUsers` (driver SQL `SELECT` that includes the `avatar_url` column) — `store/db/sqlite/user.go:88` (equivalents: `store/db/mysql/user.go:84`, `store/db/postgres/user.go:87`)

Back in the handler, the stored `user.AvatarURL` data URI is decoded by `FileServerService.parseDataURI` (`server/router/fileserver/fileserver.go:737`), validated against `avatarAllowedTypes` (`fileserver.go:75,201`), and the raw image bytes are written to the response via `c.Blob` (`fileserver.go:209`).
