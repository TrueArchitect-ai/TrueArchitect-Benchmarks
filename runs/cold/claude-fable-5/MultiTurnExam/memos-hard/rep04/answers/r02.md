**Premise correction: no per-user API rate-limiting middleware exists in this codebase.** There is nothing to register and no request limits to report.

What I checked:

- A repo-wide search for rate-limit/throttle/limiter terms finds only a documentation aspiration in `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse" — a suggested best practice in a comment, not implemented middleware).
- The Echo server registers only `middleware.Recover()` and a CORS middleware (`server/server.go:51-52`); Echo's `RateLimiter` middleware is not used.
- The Connect RPC interceptor chain (`server/router/api/v1/connect_interceptors.go`) contains metadata, logging, and auth-related interceptors — no rate limiting.
- The closest things to request limiting are concurrency semaphores, which bound parallel work rather than per-user request rates: thumbnail generation (`server/router/fileserver/fileserver.go:107,116` — `maxConcurrentThumbnails`) and thumbnail/image processing in the API service (`server/router/api/v1/v1.go:40-41`, weights 3 and 2 at construction in `v1.go`). There's also a bounded webhook dispatch queue (`internal/webhook/webhook.go:39`), again a concurrency bound, not a rate limit keyed to users.
