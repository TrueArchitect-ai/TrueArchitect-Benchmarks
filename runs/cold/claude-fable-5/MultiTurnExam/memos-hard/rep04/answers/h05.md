h05.

**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside the driver-level `DeleteUser` transaction, not by any database rule.

Evidence:

1. **Explicit deletion code.** Each database driver's `DeleteUser` runs a transaction that removes the user's data in a fixed order via `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`, with parallel implementations in `store/db/postgres/user_delete.go` and `store/db/mysql/`). Reactions are removed in two explicit steps:
   - `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`) — `DELETE FROM reaction WHERE creator_id = ?`, removing all reactions the user made.
   - `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-388`) — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions on the user's memos (content IDs built as `memos/<uid>` at `user_delete.go:512-518`).
   The store layer entry point is `Store.DeleteUser` at `store/user.go:171`.

2. **No database-level rule for reactions.** The `reaction` table schema has no foreign keys at all — just a UNIQUE constraint — in every dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, and the original migrations (`store/migration/sqlite/0.20/00__reaction.sql`, `store/migration/postgres/0.20/00__reaction.sql`). A grep for `CASCADE` shows `ON DELETE CASCADE` clauses exist for other tables (e.g., `user_setting`, `memo_resource`) but never on `reaction`, so the DB could not clean these rows up itself.
