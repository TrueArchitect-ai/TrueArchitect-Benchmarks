h05.

**Mechanism: explicit Go code in each database driver's user-deletion transaction — not a database-level rule.**

Evidence:

- **Explicit deletes in Go:** each driver's `user_delete.go` deletes reactions inside the `DeleteUser` transaction, in two passes — reactions *on* the user's memos (`deleteReactionsByContentIDsTx`, e.g. `DELETE FROM reaction WHERE content_id IN ...`) and reactions *made by* the user (`deleteReactionsByCreatorTx`, `DELETE FROM reaction WHERE creator_id = ?`). Call sites and implementations:
  - MySQL: `store/db/mysql/user_delete.go:96,102` (calls), `:417` and `:437` (implementations)
  - SQLite: `store/db/sqlite/user_delete.go:96,102` and `:380` onward
  - Postgres: same pattern in `store/db/postgres/user_delete.go`
- **No database-level rule exists for reactions:** the `reaction` table schema has no foreign keys at all — just a `UNIQUE(creator_id, content_id, reaction_type)` constraint — in all three dialects (`store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-96`). Since `content_id` is a text UID rather than a memo FK, a cascade couldn't apply anyway. The only `ON DELETE CASCADE` in the schemas belongs to a different table referencing `memo(id)` (e.g. `store/migration/sqlite/LATEST.sql:109`), not to `reaction`, and it cascades from memo deletion, not user deletion.
