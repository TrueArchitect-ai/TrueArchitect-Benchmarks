The browser hits `GET /file/users/{username}/avatar`; the avatar bytes live in the `user` row's `avatar_url` column as a data URI, which the handler decodes and serves. Hops:

- Route registration `fileGroup.GET("/users/:identifier/avatar", ...)` — `server/router/fileserver/fileserver.go:124`
- `serveUserAvatar` (handler: optional auth check on private instances, then lookup, data-URI decode, MIME allowlist, response) — `server/router/fileserver/fileserver.go:168`
- `getUserByUsername` (wraps the lookup as `store.FindUser{Username}`) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks/populates the user cache, delegates to list) — `store/user.go:148`
- `Store.ListUsers` (calls the DB driver, warms the cache) — `store/user.go:136`
- Driver `ListUsers` (SQL `SELECT ... FROM user`, returns `AvatarURL` with the stored data URI) — `store/db/sqlite/user.go:88` / `store/db/mysql/user.go:84` / `store/db/postgres/user.go:87`, whichever driver the deployment uses
- Back in the handler, `parseDataURI` decodes `user.AvatarURL` into raw image bytes (`server/router/fileserver/fileserver.go:196`), the type is checked against `avatarAllowedTypes` (`fileserver.go:75`), and the image is returned via `c.Blob`.

So the stored data is reached entirely through the user store — the avatar is embedded in the user record rather than the attachment/blob storage path.
