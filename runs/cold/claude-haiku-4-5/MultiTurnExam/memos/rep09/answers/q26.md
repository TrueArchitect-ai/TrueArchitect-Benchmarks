q26. memo, memo_relation, attachment, memo_share, reaction

When DeleteMemo runs, the following database tables are affected:

1. **memo** — deleted directly (the target memo row)
2. **memo_relation** — deleted explicitly via `s.driver.DeleteMemoRelation()` in two calls (lines 142-146 in `/bench/repo/store/memo.go`):
   - Deletes relations where this memo is the source (MemoID)
   - Deletes relations where this memo is the target (RelatedMemoID)
3. **attachment** — deleted explicitly via loop calling `s.DeleteAttachment()` (lines 149-157 in `/bench/repo/store/memo.go`)
4. **memo_share** — deleted automatically via foreign key constraint `ON DELETE CASCADE` from the memo table (defined in `/bench/repo/store/migration/sqlite/LATEST.sql`)
5. **reaction** — while reactions are queried/listed in the API layer (line 545 in `/bench/repo/server/router/api/v1/memo_service.go`), they are not explicitly deleted in code but may cascade if there's a content_id reference to the memo name. However, based on the schema, reactions use `content_id` (text) rather than a foreign key to memo.id, so they are NOT automatically cascaded and remain in the database.

The directly affected tables are: **memo, memo_relation, attachment, memo_share**
