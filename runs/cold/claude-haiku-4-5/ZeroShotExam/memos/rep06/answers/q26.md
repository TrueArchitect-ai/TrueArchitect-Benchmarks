When `DeleteMemo` runs, the following database tables are affected:

1. **memo** - The memo record itself is deleted directly (store/db/sqlite/memo.go:237-248, store/db/mysql/memo.go:259-270, store/db/postgres/memo.go - similar structure)

2. **memo_relation** - Deleted in two ways:
   - Relations where this memo is the source (memo_id) are deleted (store/memo.go:142)
   - Relations where this memo is the target (related_memo_id) are deleted (store/memo.go:145)

3. **attachment** - All attachments linked to this memo are deleted (store/memo.go:149-157, store/attachment.go)

4. **memo_share** - Cascaded delete via foreign key constraint `ON DELETE CASCADE` (store/migration/sqlite/LATEST.sql:109, store/migration/mysql/LATEST.sql:108, store/migration/postgres/LATEST.sql:108)

Additionally, as seen in the DeleteMemo service implementation (server/router/api/v1/memo_service.go:567-577), when deleting a memo that is a parent of comments, it recursively calls DeleteMemo on each comment first, which means those comment memos' attachments and relations are also cleaned up.

The **reaction** table is not directly affected by cascade logic - reactions remain orphaned references with content_id values pointing to the deleted memo's name, though the code does list and fetch reactions before deletion for webhook purposes.
