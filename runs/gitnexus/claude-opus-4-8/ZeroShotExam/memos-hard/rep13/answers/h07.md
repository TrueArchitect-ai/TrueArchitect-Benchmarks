The avatar is served from route `GET /file/users/:identifier/avatar`. The image bytes are **not** an attachment on disk/S3 — they live inline in the `user.avatar_url` column as a base64 data URI, so the data-layer hop is the user query, and decoding happens in the handler.

Notes:
- The route is registered at server/router/fileserver/fileserver.go:124 (`fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)`).
- `Store.GetUser` delegates to `Store.ListUsers`, which calls `s.driver.ListUsers` (store/user.go:137); the SQLite driver's `ListUsers` scans `avatar_url` into `user.AvatarURL` (store/db/sqlite/user.go:189). The MySQL/Postgres drivers mirror this.
- No cross-user authorization check exists on this path beyond the anonymous-instance gate at fileserver.go:173 — any username is served (the `identifier` is looked up by username only, fileserver.go:716), which is how "another user's" avatar is reachable.
