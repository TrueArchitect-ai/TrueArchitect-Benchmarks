**Mechanism: explicit Go code.** A deleted user's emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the `DeleteUser` transaction, in each database driver. There is no database-level cascade — the `reaction` table is declared with no foreign keys or `ON DELETE` rules.

Reactions are removed on **two** axes within the delete transaction:
1. Reactions *created by* the deleted user (`WHERE creator_id = ?`).
2. Reactions *on the deleted user's memos* (`WHERE content_id IN (...)`, where `content_id` is `"memos/"+uid` of each memo owned by the user — including comment-tree descendants).

Evidence locations:

- **Orchestration** — `store/db/sqlite/user_delete.go:92` (`deleteUserTargetsTx`) calls both `deleteReactionsByContentIDsTx` (line 96) and `deleteReactionsByCreatorTx` (line 102).
- **The actual DELETEs (sqlite)** — `store/db/sqlite/user_delete.go:380-388` (`DELETE FROM reaction WHERE content_id IN ...`) and `store/db/sqlite/user_delete.go:400-403` (`DELETE FROM reaction WHERE creator_id = ?`). The content IDs come from `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go:512-518`).
- **Same logic in the other two drivers** — postgres: `store/db/postgres/user_delete.go:96`, `:102`, `:380-401`; mysql: `store/db/mysql/user_delete.go:96`, `:102`, `:417-438`.
- **No DB-level rule** — the `reaction` table schema has no foreign key / cascade in any dialect: `store/migration/sqlite/0.20/00__reaction.sql`, `store/migration/postgres/0.20/00__reaction.sql`, `store/migration/mysql/0.20/00__reaction.sql` (columns only + a `UNIQUE(creator_id, content_id, reaction_type)` constraint). A grep for `REFERENCES`/`FOREIGN KEY` against reaction migrations returned nothing.
