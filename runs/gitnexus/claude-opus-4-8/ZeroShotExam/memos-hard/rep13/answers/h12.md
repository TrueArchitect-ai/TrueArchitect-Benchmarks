**Concrete method:** `sqlite.(*DB).CreateMemo` — `store/db/sqlite/memo.go:16`. It builds and runs `INSERT INTO \`memo\` (...) VALUES (...) RETURNING ...` via `d.db.QueryRowContext` (store/db/sqlite/memo.go:41).

**Determination method:**

The call path has one interface indirection, resolved at runtime by the configured driver:

1. **Store layer is driver-agnostic.** `Store.CreateMemo` (store/memo.go:109) just delegates: `return s.driver.CreateMemo(ctx, create)`, where `s.driver` is the `store.Driver` interface. Three concrete types satisfy it — `sqlite`, `mysql`, `postgres` — each with its own `CreateMemo` (the multiple candidates).

2. **The concrete driver is picked by a switch on `profile.Driver`.** `NewDBDriver` (store/db/db.go) selects `sqlite.NewDB` / `mysql.NewDB` / `postgres.NewDB` based on `profile.Driver`.

3. **The default value of `profile.Driver` is `"sqlite"`.** Set in two places in cmd/memos/main.go — `viper.SetDefault("driver", "sqlite")` (line 122) and the flag default `rootCmd.PersistentFlags().String("driver", "sqlite", ...)` (line 130). With no DB flags passed, this default holds, so the switch lands on the `sqlite` case.

Therefore, with a default install, `s.driver` is the sqlite `*DB`, and `s.driver.CreateMemo` dispatches to `store/db/sqlite/memo.go:16` — the code that actually executes the INSERT. (The mysql/postgres `CreateMemo` implementations exist but are only reached when `--driver mysql`/`postgres` is set.)
