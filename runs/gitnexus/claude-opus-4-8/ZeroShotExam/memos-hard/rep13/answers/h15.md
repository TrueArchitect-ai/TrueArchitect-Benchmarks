h15.

Memo visibility (who may **view** a memo) is enforced at multiple distinct server surfaces:

Single-memo read gate (`checkMemoReadAccess`, used by GetMemo + comment parent + ListMemoComments) — server/router/api/v1/memo_service.go:39
Memo list per-user visibility filter (`ListMemos`) — server/router/api/v1/memo_service.go:218
User-stats memo visibility filter (`ListAllUserStats` / `GetUserStats`) — server/router/api/v1/user_service_stats.go:84
Store SQL WHERE-clause filter that turns `VisibilityList` into `visibility IN (...)` (`listMemos`) — store/db/sqlite/memo.go:96, store/db/postgres/memo.go:89, store/db/mysql/memo.go:104
Reactions read gate (`ListMemoReactions` / `UpsertMemoReaction`) — server/router/api/v1/reaction_service.go:30
Comment creation read gate (`CreateMemoComment`) — server/router/api/v1/memo_service_comments.go:41
Memo-attachment listing gate (`ListMemoAttachments`) — server/router/api/v1/memo_attachment_service.go:214
Attachment access gate following memo visibility (`checkAttachmentAccess`) — server/router/api/v1/attachment_service.go:445
Raw file/blob serving gate (`checkAttachmentPermission`) — server/router/fileserver/fileserver.go:677
RSS/Atom feeds hardcoded to Public (`GetExploreRSS` / `GetUserRSS`) — server/router/rss/rss.go:90
Sitemap hardcoded to Public (`getSitemapXML`) — server/router/frontend/frontend.go:150

The three most central are the single-memo gate (`checkMemoReadAccess`), the `ListMemos` per-user filter, and the store-level SQL `visibility IN (...)` filter; the attachment/fileserver, reactions, comments, feed, and sitemap surfaces each enforce it independently as well. (Note the predicates differ subtly — API-v1 services use `!isSuperUser(user)`, the fileserver uses `user.Role != store.RoleAdmin`, and `checkMemoReadAccess` has no super-user bypass.)
