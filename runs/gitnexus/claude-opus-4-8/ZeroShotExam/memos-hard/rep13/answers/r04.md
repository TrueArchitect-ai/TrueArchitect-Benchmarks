**Premise correction:** The premise is false. Memos does not use any external message broker — neither NATS nor RabbitMQ. There is no AMQP/NATS/broker dependency anywhere in the codebase (a search for `nats`/`rabbitmq`/`amqp` returns zero hits).

**Actual mechanism:** Webhook delivery is handled entirely in-process using a **buffered Go channel** as the queue, with a fixed pool of goroutine workers.

In `internal/webhook/webhook.go`:

- The "queue" is a package-level buffered channel, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  (capacity 128).

- The workers are **4 goroutines** started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` (which does an HTTP POST via `safeClient`) for every payload.

- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), a non-blocking `select` that drops the payload (logging a warning) if the channel buffer is full.

The API layer feeds this queue from `server/router/api/v1/memo_service_webhooks.go` — e.g. `dispatchMemoRelatedWebhook` (line 48) loops over a user's registered webhooks and calls `webhook.PostAsync(payload)` (line 71). Webhook target URLs are stored per-user in the database (retrieved via `s.Store.GetUserWebhooks`), not consumed from any broker topic/queue.

So: no broker involved; delivery is an in-memory channel (`asyncPostQueue`, cap 128) drained by 4 worker goroutines, declared in `internal/webhook/webhook.go`.
