**Premise correction:** The webhook delivery workers consume from *neither* NATS nor RabbitMQ. There is no external message broker anywhere in this stack — `go.mod` has no NATS, RabbitMQ/amqp, Redis, or job-queue dependency, and there is no docker-compose or config declaring such a broker.

**Actual mechanism:** Webhook delivery uses an **in-process, non-durable buffered Go channel** drained by a fixed goroutine worker pool, in `internal/webhook/webhook.go`:

- **Queue declaration:** `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — a buffered channel of capacity 128 (`internal/webhook/webhook.go:39`).
- **Consumers (workers):** an `init()` function spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post()` to deliver via HTTP (`internal/webhook/webhook.go:42-55`).
- **Producer/enqueue:** `PostAsync()` does a non-blocking `select` send with a drop-on-full default (`internal/webhook/webhook.go:184-196`), called from the API layer at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

Because the "queue" is a process-local channel, it isn't persisted — pending webhooks are lost on restart and don't coordinate across instances. So the choice between NATS and RabbitMQ is moot: delivery is handled entirely in-process.
