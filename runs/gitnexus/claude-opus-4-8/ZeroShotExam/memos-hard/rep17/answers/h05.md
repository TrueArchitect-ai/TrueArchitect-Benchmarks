**Mechanism: by explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the delete-user transaction — there is **no** database-level foreign key / `ON DELETE CASCADE` rule that would do it automatically.

## What I checked

**1. The delete-user code path (all three drivers).** Each driver's `DeleteUser` runs `deleteUserTargetsTx`, which explicitly deletes reactions in two ways before removing the user row:
- `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on* the deleted user's memos (and their comment subtree). Content IDs are built as `"memos/"+uid`.
- `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the user *made* on anyone's content.

Evidence (identical logic per driver):
- `store/db/sqlite/user_delete.go:96`, `:102`, and the functions at `:380-388` and `:400-403`
- `store/db/postgres/user_delete.go:96`, `:102`, and `:380-388`, `:400-403`
- `store/db/mysql/user_delete.go:96`, `:102`, and `:417-425`, `:437-440`

Both run inside the transaction begun in `DeleteUser` (`store/db/sqlite/user_delete.go:29-59`, and the same in postgres/mysql), so reaction removal is atomic with the user deletion.

**2. The reaction table schema — confirmed no DB-level rule.** The `reaction` table declares `creator_id` and `content_id` as plain `NOT NULL` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — **no foreign key, no `ON DELETE CASCADE`** in any driver:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

For contrast, the adjacent `memo_share` table (mysql) *does* have `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/mysql/LATEST.sql:108`) — reaction has nothing comparable, confirming that reaction cleanup depends entirely on the explicit Go deletes above.
