The avatar bytes are **not** stored as a file or attachment blob — they live inline in the `users` table as a base64 data URI in the `avatar_url` column. So the browser request resolves to a normal user-record read.

**Route:** `GET /file/users/:identifier/avatar` (registered in `RegisterRoutes` — `server/router/fileserver/fileserver.go:124`)

Hops from serving handler to the data layer:

serveUserAvatar — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
DB.ListUsers (driver, e.g. SQLite) — store/db/sqlite/user.go:88

Notes:
- The handler resolves the target ("another user") purely by the URL path param `identifier` via `getUserByUsername` → `store.FindUser{Username}`; the only auth gate is on private instances (`AllowAnonymous()` false requires any authenticated viewer via `getCurrentUser`), with no check that the viewer may see *that* user.
- The stored bytes are read from `user.AvatarURL` (`store/user.go` `User.AvatarURL`), decoded by `parseDataURI` (`server/router/fileserver/fileserver.go:737`), and written back with `c.Blob` (line 209). `Store.GetUser` may short-circuit on the in-memory `userCache` when found by ID, but the username lookup here always goes through `ListUsers` → `driver.ListUsers` to the DB.
