My delegated search corroborated the answer and surfaced two additional distinct surfaces I had missed. Adding them for completeness:

**File server (attachment blob serving)** — server/router/fileserver/fileserver.go:677,699 (`checkAttachmentPermission`) — serves a raw attachment blob only if the parent memo's visibility permits the requester (Public+anonymous allowed, else share-token or authenticated creator/admin). This is a separate plain-HTTP surface from the gRPC `attachment_service.go` gate.

**ListMemoComments comment scoping** — server/router/api/v1/memo_service_comments.go:157-161 — beyond calling `checkMemoReadAccess` on the parent, it additionally scopes the comment list itself to `visibility == "PUBLIC"` (anonymous) or own-OR-PUBLIC/PROTECTED (authenticated).

So the full inventory of distinct VIEW-access enforcement sites is:

1. `checkMemoReadAccess` (single-memo gRPC gate; used by GetMemo, ListMemoComments) — server/router/api/v1/memo_service.go:39-68
2. `ListMemos` scoping — server/router/api/v1/memo_service.go:218-227
3. `ListMemoComments` scoping — server/router/api/v1/memo_service_comments.go:157-161
4. User-stats scoping — server/router/api/v1/user_service_stats.go:84,218
5. Store SQL WHERE builder (`VisibilityList` → `visibility IN (...)`) — store/db/sqlite/memo.go:96, store/db/postgres/memo.go:89, store/db/mysql/memo.go:104
6. gRPC attachment access (`checkAttachmentAccess`) — server/router/api/v1/attachment_service.go:445-453
7. gRPC memo-attachment listing (`ListMemoAttachments`) — server/router/api/v1/memo_attachment_service.go:214-225
8. File-server blob gate (`checkAttachmentPermission`) — server/router/fileserver/fileserver.go:677,699
9. Reaction read (`ListMemoReactions`) — server/router/api/v1/reaction_service.go:30-41
10. SSE delivery gate (`SSEClient.canReceive`) — server/router/api/v1/sse_hub.go:134-143
11. RSS feeds — server/router/rss/rss.go:90 (`GetInstanceRSS`), rss.go:141 (`GetUserRSS`)
12. Frontend sitemap SSR — server/router/frontend/frontend.go:150 (`getSitemapXML`)

(The MCP router adds no independent check — it forwards to the gRPC API, so it inherits sites 1–2.)

The three "core" surfaces the question anchors on are the **gRPC API gate** (`checkMemoReadAccess` + `ListMemos`), the **store SQL WHERE builder**, and the **plain-HTTP routers** (file server / RSS / frontend sitemap / SSE). As noted before, these are hand-written per-site checks rather than one shared authorizer, so the exact rules differ (e.g., `isSuperUser`/admin bypass exists on attachment, reaction, and SSE paths but not in `checkMemoReadAccess`).
