**Premise correction:** Neither. The webhook delivery workers don't consume from NATS *or* RabbitMQ — this project (memos) uses no external message broker at all. Neither `nats`, `rabbitmq`, nor `amqp` appears in `go.mod`/`go.sum` or anywhere in the source.

**Actual mechanism:** In-process delivery via a buffered Go channel drained by a fixed goroutine pool.

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a single buffered channel (capacity 128). That is the entire "queue."
- **Workers consume:** `internal/webhook/webhook.go:42-55` — an `init()` spawns 4 goroutines that each `range` over the channel (consume point at line 45) and deliver via a plain `net/http` POST (`Post()`).
- **Enqueue:** `internal/webhook/webhook.go:184-196` (`PostAsync`), with a non-blocking send at line 190 (`case asyncPostQueue <- payload:`). Called from `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

One behavioral note: the send uses a `default` case (line 191), so jobs are **silently dropped** when the buffer is full, and the queue is purely in-memory — not durable across restarts. The webhook target URLs come from user config in the store (`s.Store.GetUserWebhooks`), not from any broker subject/topic.
