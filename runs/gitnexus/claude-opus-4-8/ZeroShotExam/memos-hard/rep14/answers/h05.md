**Mechanism: by explicit Go code.** Reactions are removed inside the `DeleteUser` transaction in the store layer — there is *no* database-level cascade for the `reaction` table.

Two distinct explicit deletions run per user deletion:

1. **Reactions the user *authored*** — `DELETE FROM reaction WHERE creator_id = ?` via `deleteReactionsByCreatorTx`.
2. **Reactions *on the user's memos*** (any user's reactions on the deleted memos) — `DELETE FROM reaction WHERE content_id IN (...)`, where `content_id` is `"memos/"+uid` of each memo in the user's memo tree, via `deleteReactionsByContentIDsTx`.

Both are orchestrated by `deleteUserTargetsTx` (calls at lines 96 and 102 in each driver) inside a single transaction, before the user row itself is deleted.

**Evidence locations:**
- `store/db/sqlite/user_delete.go:96,102` (dispatch), `:380-388` (`deleteReactionsByContentIDsTx`), `:400-403` (`deleteReactionsByCreatorTx`)
- `store/db/postgres/user_delete.go:96,102`, `:380-388`, `:400-403`
- `store/db/mysql/user_delete.go:96,102`, `:417-425`, `:437-440`

**Why not a DB rule:** The `reaction` table schema declares **no foreign keys / `ON DELETE CASCADE`** on `creator_id` or `content_id` — confirmed in `store/migration/{sqlite,postgres,mysql}/LATEST.sql` (the `CREATE TABLE reaction` block has only a `UNIQUE` constraint; contrast `memo_share` just below it, which *does* declare `FOREIGN KEY ... ON DELETE CASCADE`). So the cleanup depends entirely on the Go code above.
