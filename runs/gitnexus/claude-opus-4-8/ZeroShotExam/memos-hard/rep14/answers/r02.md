**Premise correction: There is no per-user API rate-limiting middleware in this repository.** The question assumes one exists and is registered somewhere with configured request limits; that assumption is false for the memos codebase as indexed.

What I actually found:

- The Connect/gRPC API middleware chain is registered in `server/router/api/v1/v1.go:133-137` via `connect.WithInterceptors(...)`, and it contains exactly four interceptors — none of which rate-limit:
  - `NewMetadataInterceptor()` — HTTP-header → gRPC-metadata conversion
  - `NewLoggingInterceptor(...)` — request logging
  - `NewRecoveryInterceptor(...)` — panic recovery
  - `NewAuthInterceptor(...)` — authentication / anonymous-access policy

  All four are defined in `server/router/api/v1/connect_interceptors.go`. There is no rate-limiting interceptor in that file or in the chain.

- The only request-size control applied there is `connect.WithReadMaxBytes(maxAPIRequestBytes)` at `server/router/api/v1/v1.go:141` — a per-request byte cap, not a per-user request-rate limit.

- A repository-wide search for `ratelimit` / `rate limit` / `throttle` / `limiter` in Go code turns up **no implementation**. The only mentions are documentation/advice, not code:
  - `internal/email/doc.go:86` — a Security Considerations bullet: *"Rate limit email sending to prevent abuse"* (aspirational guidance about SMTP, not an API middleware).
  - `internal/email/README.md` references `golang.org/x/time/rate` only as an illustrative example.

- `golang.org/x/time` appears in `go.mod` marked `// indirect`, i.e., it is not a directly-used rate-limiting dependency.

So no such middleware is registered anywhere, and consequently there are no configured per-user request limits to report. If per-user API rate limiting is a requirement, it would need to be added (e.g., as a new Connect interceptor in `connect_interceptors.go` wired into the chain in `v1.go`).
