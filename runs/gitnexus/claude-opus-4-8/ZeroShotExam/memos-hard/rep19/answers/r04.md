**Premise correction:** The webhook delivery workers in memos consume from *neither* NATS nor RabbitMQ. There is no external message broker anywhere in the codebase — grepping for `nats`, `rabbitmq`, `amqp`, etc. across the Go source and `go.mod` returns nothing. The question's framing assumes a broker-based architecture that doesn't exist here.

**Actual mechanism:** Webhook delivery is entirely in-process, using a buffered Go channel drained by worker goroutines that make direct HTTP POSTs.

- **The "queue" is a buffered Go channel**, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  (capacity 128, holding pointers to webhook payloads — not a broker queue).

- **The workers** are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` for every payload.

- **Producer side:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking send into the channel; if the channel is full it drops the webhook and logs a warning.

- **Delivery:** `Post` (`internal/webhook/webhook.go:120-180`) issues a direct `http.POST` of the JSON payload to the user-configured webhook URL via a shared SSRF-guarded client (`safeClient`), optionally adding Standard-Webhooks HMAC-SHA256 signature headers.

- **Trigger/enqueue sites:** `server/router/api/v1/memo_service_webhooks.go` — memo create/update/delete and comment-created events fetch the user's registered webhooks (`s.Store.GetUserWebhooks`) and call `webhook.PostAsync(payload)` (lines ~43 and ~71).

So: no broker consumption at all — it's an in-memory buffered channel (`asyncPostQueue`, cap 128) with 4 background goroutines making direct HTTP calls.
