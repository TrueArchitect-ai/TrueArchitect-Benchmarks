A browser fetching another user's profile image hits `GET /file/users/:identifier/avatar`. The avatar is not a file on disk — it is stored inline as a base64 `data:` URI in the `user.avatar_url` column, so the "data layer" is a SQL read of the user row, then a decode of that data URI.

Hops (handler → data layer):

serveUserAvatar — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
driver.ListUsers (SELECT ... avatar_url FROM user) — store/db/sqlite/user.go:88 (equivalently store/db/postgres/user.go:87, store/db/mysql/user.go:84)

Return path back through the handler that turns the stored data into image bytes:

parseDataURI (base64-decode `user.AvatarURL`) — server/router/fileserver/fileserver.go:737
c.Blob (writes decoded image bytes to the response) — server/router/fileserver/fileserver.go:209

Route registration is at server/router/fileserver/fileserver.go:124 (`fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)`). Note the request never reaches attachment/S3/local-disk storage for avatars — that path (`serveAttachmentFile`) is separate; avatars live entirely in the `user` table's `avatar_url` field.
