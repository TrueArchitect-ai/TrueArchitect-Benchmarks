Memo visibility is enforced independently at multiple server surfaces (enforcement is decentralized — each surface re-implements the Public / Private-creator / superuser check rather than routing through one shared gate):

checkMemoReadAccess — central per-memo read gate (GetMemo, parent-memo, comment creation) — server/router/api/v1/memo_service.go:39-68
ListMemos RPC visibility scoping (anonymous→[Public]; other user→[Public,Protected]; CEL filter for self) — server/router/api/v1/memo_service.go:178-227
Store SQL VisibilityList → `visibility IN (...)` WHERE clause — store/db/sqlite/memo.go:96-103, store/db/postgres/memo.go, store/db/mysql/memo.go
CreateMemoComment visibility check — server/router/api/v1/memo_service_comments.go:41-52
Reaction service (ListMemoReactions / UpsertMemoReaction) — server/router/api/v1/reaction_service.go:30-83
ListMemoAttachments RPC — server/router/api/v1/memo_attachment_service.go:214-224
checkAttachmentAccess — gRPC attachment binary gate — server/router/api/v1/attachment_service.go:422-455
checkAttachmentPermission — HTTP fileserver raw-byte streaming gate — server/router/fileserver/fileserver.go:650-704
RSS feed handlers (GetExploreRSS / GetUserRSS force [Public]) — server/router/rss/rss.go:90,141
Frontend sitemap (getSitemapXML forces [Public]) — server/router/frontend/frontend.go:143-167
SSE live-delivery filter (SSEClient.canReceive) — server/router/api/v1/sse_hub.go:134-144

The three architecturally primary sites the question anticipates are the `checkMemoReadAccess` RPC gate (memo_service.go), the `ListMemos`→store `VisibilityList` query path (memo_service.go + store/db/*/memo.go), and the separate HTTP binary-serving gate `checkAttachmentPermission` (fileserver.go). The rest re-enforce visibility at every additional content surface.

Note: enforcement is not perfectly uniform — e.g. `checkMemoReadAccess` does not grant admins access to private memos, whereas the attachment/fileserver gates do (`Role != Admin` / `isSuperUser`).
