**Premise correction:** The question presupposes a message broker (NATS or RabbitMQ). Neither is used — this repository (`memos`) has no external message broker anywhere in the webhook delivery path. There are no AMQP/NATS/Kafka/Redis/SQS client libraries in `go.mod`.

**Actual mechanism:** Webhook delivery is entirely **in-process**, using a bounded Go channel as the "queue" and a fixed pool of goroutines as the "workers." All of it lives in `internal/webhook/webhook.go`:

- **Queue declaration** — a buffered channel with capacity 128, at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- **Workers** — 4 goroutines started in `init()` that range over the channel and call `Post` (`internal/webhook/webhook.go:42-55`).
- **Enqueue** — `PostAsync` does a non-blocking send onto the channel, dropping the job if the buffer is full (`internal/webhook/webhook.go`, `PostAsync`).
- **Delivery** — `Post` marshals the payload to JSON and sends a plain HTTP POST via a shared, SSRF-guarded `http.Client`.

Producers that enqueue jobs are the memo/comment event dispatchers in `server/router/api/v1/memo_service_webhooks.go`, which call `webhook.PostAsync(...)` per registered user webhook.

Note this queue is purely in-memory and non-durable: pending items are lost on process restart, and overflow items are dropped when the 128-slot buffer is full.
