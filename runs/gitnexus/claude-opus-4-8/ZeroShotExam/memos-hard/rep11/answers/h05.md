**Mechanism: removed by explicit Go code** (not a database cascade rule).

When a user is deleted, `DeleteUser` runs a transaction that explicitly issues `DELETE FROM reaction` statements. Two paths are covered:

1. **Reactions the user authored** — deleted by `creator_id`:
   `store/db/postgres/user_delete.go:400-403` (`deleteReactionsByCreatorTx`), invoked at `store/db/postgres/user_delete.go:102`.
2. **Reactions on the user's own content** (their deleted memos) — deleted by `content_id`:
   `store/db/postgres/user_delete.go:380-388` (`deleteReactionsByContentIDsTx`), invoked at `store/db/postgres/user_delete.go:96`.

The same logic is duplicated per driver: SQLite (`store/db/sqlite/user_delete.go:383,401`) and MySQL (`store/db/mysql/user_delete.go:420,438`).

**Why it's not a DB-level rule:** the `reaction` table schema declares `creator_id INTEGER NOT NULL` with no foreign key and no `ON DELETE CASCADE` — see `store/migration/postgres/LATEST.sql:91-98` (mirrored in `store/migration/sqlite/LATEST.sql:92` and `store/migration/mysql/LATEST.sql:91`). Since there's no FK constraint tying `reaction.creator_id` to the user table, the database would not remove these rows on its own; the explicit Go statements are what do it.
