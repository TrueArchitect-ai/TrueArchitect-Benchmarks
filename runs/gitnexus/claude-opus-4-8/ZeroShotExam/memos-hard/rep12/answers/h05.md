**Mechanism: removed by explicit Go code** (inside the `DeleteUser` transaction), not by a database-level rule.

When a user is deleted, reactions are purged in two distinct passes, run within the same transaction that deletes the user's memos and other data:

1. **Reactions *on* the deleted user's memos** — `deleteReactionsByContentIDsTx` issues `DELETE FROM reaction WHERE content_id IN (...)`, where the content IDs are `"memos/"+uid` for the user's (recursively collected) memo tree. This removes reactions authored by *other* users on the deleted user's memos.
2. **Reactions *authored by* the deleted user** — `deleteReactionsByCreatorTx` issues `DELETE FROM reaction WHERE creator_id = ?`. This removes the user's own reactions left on anyone's content.

Both are wired into `deleteUserTargetsTx`, which runs before the final `DELETE FROM "user"`.

There is **no** database-level cascade doing this: the `reaction` table declares no foreign keys and no `ON DELETE CASCADE` in any dialect — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint.
