h07.

A browser requesting another user's profile image (avatar) hits `GET /file/users/:identifier/avatar`. The avatar image isn't a separate file — it's stored inline as a base64 data-URI in the `user.avatar_url` column, so the "data layer" hop reads that user row and the handler decodes the data URI into bytes.

Serving handler → each hop to stored data:

```
serveUserAvatar — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
DB.ListUsers (SELECT avatar_url FROM user) — store/db/sqlite/user.go:88
parseDataURI (decode user.AvatarURL data-URI → image bytes) — server/router/fileserver/fileserver.go:737
```

Notes:
- Route registration: `fileGroup.GET("/file/users/:identifier/avatar", s.serveUserAvatar)` at `server/router/fileserver/fileserver.go:124`.
- The stored data is the `avatar_url` TEXT column of the `user` table (a `data:<mime>;base64,...` URI), selected/scanned at `store/db/sqlite/user.go:159` and `:189` (Postgres/MySQL drivers under `store/db/postgres/user.go` and `store/db/mysql/user.go` are equivalent).
- The handler then decodes it via `parseDataURI` (fileserver.go:196/737) and returns the raw bytes with `c.Blob` (fileserver.go:209). There is no filesystem/S3 hop for avatars — unlike attachments, avatar bytes live entirely in the DB row.
