**Premise correction:** The webhook delivery workers consume from **neither NATS nor RabbitMQ** — no external message broker exists anywhere in this repository. `go.mod`/`go.sum` contain no NATS, AMQP, or RabbitMQ dependencies (the only textual "nats"/"amqp" hits are substrings of Catalan words in `web/src/locales/ca.json`).

**Actual mechanism:** Delivery is handled entirely in-process by a **buffered Go channel drained by a pool of goroutine workers**, all in `internal/webhook/webhook.go`:

- **Queue declared** — `internal/webhook/webhook.go:39`: a package-level bounded in-memory channel
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- **Workers** — `internal/webhook/webhook.go:42-55`: the package `init()` spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post` (a direct SSRF-guarded HTTP POST, lines 119-180).
- **Enqueue side** — `PostAsync` at `internal/webhook/webhook.go:184-196` does a non-blocking send and drops the payload if the buffer of 128 is full.
- **Producers** — the API request path enqueues jobs synchronously via `webhook.PostAsync(...)` in `server/router/api/v1/memo_service_webhooks.go` (lines 43 and 71).

So the "queue" is a single 128-slot in-memory Go channel declared at `internal/webhook/webhook.go:39`, consumed by 4 goroutines in the same process as the API server — not a message broker at all.
