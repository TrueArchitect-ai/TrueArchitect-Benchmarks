**Mechanism: explicit Go code.** A deleted user's emoji reactions are removed by application code inside the `DeleteUser` transaction — there is **no** database-level foreign key or `ON DELETE CASCADE` for the `reaction` table (and for SQLite, foreign-key enforcement is disabled anyway).

**Evidence locations:**

1. **No DB-level rule.** The `reaction` table has only a `UNIQUE` constraint — no foreign keys on `creator_id` or `content_id` in any driver:
   - `store/migration/sqlite/LATEST.sql:92-99` (verified — `creator_id INTEGER NOT NULL` with no FK)
   - `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98` (same shape)
   - The only `ON DELETE CASCADE` in these schemas is on `memo_share.memo_id`, not reactions.
   - SQLite FKs are globally off: `store/migration/sqlite/0.7/00__remove_fk.sql:1` (`PRAGMA foreign_keys = off;`), and triggers were removed in `store/migration/sqlite/0.7/01__remove_triggers.sql`. The reaction table was added later (0.20) already FK-free.

2. **Explicit deletion in Go.** `deleteUserTargetsTx` runs two reaction-deleting statements inside the delete transaction (verified in `store/db/sqlite/user_delete.go`, mirrored in the mysql/postgres `user_delete.go`):
   - `store/db/sqlite/user_delete.go:96,380-383` → `deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on the deleted user's memos*.
   - `store/db/sqlite/user_delete.go:102,400-401` → `deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = ?` — removes reactions *authored by the deleted user*.
   - Store wrapper: `store/user.go` delegates to `s.driver.DeleteUser(...)`.

**Implication:** Because there's no cascade backstop, correctness depends entirely on those two Go statements. Any future code path that deletes a user without them (or if they were removed) would orphan reaction rows.
