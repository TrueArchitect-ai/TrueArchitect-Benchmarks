The browser request `GET /file/users/:identifier/avatar` (registered in `RegisterRoutes`, `server/router/fileserver/fileserver.go:120`) traces to stored data through these hops:

```
serveUserAvatar — server/router/fileserver/fileserver.go:167
getUserByUsername — server/router/fileserver/fileserver.go:714
Store.GetUser — store/user.go:147
Store.ListUsers — store/user.go:135
driver.ListUsers — store/db/sqlite/user.go:87 (also store/db/postgres/user.go:86, store/db/mysql/user.go:83)
```

**How it reaches the stored bytes:** `serveUserAvatar` takes the `identifier` path param and calls `getUserByUsername`, which issues `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`. `Store.GetUser` (cache-miss path) delegates to `Store.ListUsers`, which calls the DB `driver.ListUsers` — the data layer that queries the `user` table. The returned `*store.User` carries `AvatarURL` (`store/user.go`), a stored data URI. Back in the handler, `parseDataURI` (`server/router/fileserver/fileserver.go`) decodes that stored string into `imageType`/`imageData`, which is written out via `c.Blob(...)`.

So the actual "stored data" is the `User.AvatarURL` column value, retrieved via the driver's `ListUsers` SQL query and decoded in-handler — the avatar bytes live inline in the user record, not on a separate blob/file store.

Note: `serveUserAvatar` gates anonymous access on private instances (`Profile.AllowAnonymous()` → `getCurrentUser`) but does not restrict *which* user's avatar an authenticated/permitted viewer may fetch — any `identifier` is served.
