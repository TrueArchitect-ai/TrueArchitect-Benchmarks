**Premise correction:** There is no Redis in this repository, and there is no external cache layer to configure a Redis connection for. This is the **memos** app — a Go backend fronting a SQL database (SQLite/MySQL/Postgres under `store/db/`). A grep for `redis`/`ioredis` across `go.mod` and `web/package.json` returns nothing; the only `createClient` calls (`web/src/connect.ts`) are `@connectrpc/connect` gRPC-web clients, unrelated to caching.

**Actual mechanism:** The cache is a hand-rolled, thread-safe **in-memory cache backed by `sync.Map`**, defined in `store/cache/cache.go`. There is no connection string or endpoint to configure — it's instantiated in-process.

- **Where it's "configured":** `store/store.go:40-45` builds a `cache.Config` and `New()` (lines 47-58) creates three cache instances on the `Store` struct (`store/store.go:23-30`): `instanceSettingCache`, `userCache`, and `userSettingCache`. The defaults come from `DefaultConfig()` in `store/cache/cache.go:56-64`: **DefaultTTL = 10 min, CleanupInterval = 5 min, MaxItems = 1000**.
- **TTL for user entries:** User records live in `userCache`, keyed by user ID (`userCacheKey`, `store/user.go:88-90`), written through on create/update/list and read through only on ID lookups (`store/user.go:149-167`), with explicit invalidation on delete (`store/user_delete.go:39-47`). All writes go through `Set` (never `SetWithTTL`), so **every user entry gets the default 10-minute TTL**. Expiry is enforced lazily on read (`Get`, `cache.go:135-144`) plus a background `cleanupLoop` sweep every 5 minutes (`cache.go:199-250`). Entries may also be dropped early if the 1000-item cap is exceeded (`cleanupOldest`, `cache.go:252-313`) or overwritten/deleted. There is no per-user or configurable TTL override in production code.

(User *settings* share the same story in `userSettingCache` — same 10-min default TTL, keyed `"{userID}-{settingKey}"`, `store/user_setting.go`.)
