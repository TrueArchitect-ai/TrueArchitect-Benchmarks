**Premise correction:** The question assumes webhooks are delivered by workers consuming from a message broker (NATS or RabbitMQ). Neither is used — memos has **no message broker at all**. Grepping the entire repo (`.go`, `go.mod`, `go.sum`) for `nats`, `rabbitmq`, `amqp`, `streadway`, `kafka`, `pubsub` returns zero matches.

**Actual mechanism:** Webhook delivery is entirely in-process — direct HTTP POST dispatched by a fixed pool of goroutines draining an in-memory buffered channel. There is no queue "declared" in a broker sense; the closest analog is a package-level Go channel.

- **The "queue":** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a buffered channel holding up to 128 pending payloads.
- **The workers:** `internal/webhook/webhook.go:42-55` — an `init()` spawns 4 worker goroutines, each looping over `asyncPostQueue` and calling `Post(payload)`.
- **Enqueue:** `internal/webhook/webhook.go:184-196` — `PostAsync()` does a non-blocking `select` send onto the channel; if full, it drops the webhook and logs a warning (no persistence, no retry).
- **Delivery:** `internal/webhook/webhook.go:119-180` — `Post()` performs a plain `net/http` POST with a JSON body (30s timeout, optional Standard Webhooks HMAC-SHA256 signing, SSRF-guarded dialer).
- **Triggers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` call `webhook.PostAsync(...)` for memo comment/created/updated/deleted events.

Bottom line: no NATS, no RabbitMQ, no external broker — just a 128-slot in-memory channel drained by 4 goroutines doing direct HTTP POSTs.
