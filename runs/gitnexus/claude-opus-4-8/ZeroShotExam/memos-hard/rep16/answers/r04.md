**Premise correction:** Neither. The webhook delivery workers don't consume from NATS *or* RabbitMQ — there is no external message broker in this codebase at all. Webhook delivery is entirely in-process.

**Actual mechanism:** Delivery runs off a bounded, buffered **Go channel** with a pool of goroutine workers, all in `internal/webhook/webhook.go`:

- The "queue" is a plain in-memory channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  (capacity 128 payloads)

- The consuming "workers" are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over that channel and calling `Post` (the actual HTTP POST) for every payload:
  ```go
  for range 4 {
      go func() {
          for payload := range asyncPostQueue {
              if err := Post(payload); err != nil { ... }
          }
      }()
  }
  ```

- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send onto `asyncPostQueue` and drops the payload (logging a warning) if the channel is full — so no persistence, no redelivery, no broker.

The actual network send is a synchronous `http.Client.Do` inside `Post` (`internal/webhook/webhook.go:120-180`), using an SSRF-guarded shared client.

So the delivery pipeline is: `PostAsync` → in-memory buffered channel `asyncPostQueue` → 4 worker goroutines → `Post` HTTP call. No NATS, no RabbitMQ, no AMQP/Kafka dependency exists.
