h07.

The browser hits `GET /file/users/:identifier/avatar` (registered at `server/router/fileserver/fileserver.go:124`). The avatar bytes are not stored as a separate file/attachment — they live inline in the user record's `avatar_url` column as a base64 data URI, so the "stored data" is reached through the user lookup:

```
serveUserAvatar — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
driver.ListUsers (DB) — store/db/sqlite/user.go:~145 (reads avatar_url column)
```

Then, back in `serveUserAvatar`, the retrieved `user.AvatarURL` (store/user.go:43) is decoded by `parseDataURI` and written to the response via `c.Blob` (fileserver.go:196–209).

Notes on the path:
- `store.GetUser` first checks `userCache` only when looking up by ID; this call is by `Username`, so it always falls through to `ListUsers` → the DB driver (store/user.go:148–168).
- The DB hop is the `driver.ListUsers` implementation (SQLite shown; Postgres/MySQL equivalents exist under `store/db/*/user.go`), which selects the `avatar_url` field (store/db/sqlite/user.go:14, 159).
- Access control for "another user's" image happens before the lookup: on a private instance `getCurrentUser` (fileserver.go:708) must resolve a valid viewer; otherwise any username's avatar is public.
