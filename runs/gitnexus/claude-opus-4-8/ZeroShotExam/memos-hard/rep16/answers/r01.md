**Premise correction:** There is no Redis connection anywhere in this repository — the cache layer is not backed by Redis (or any external store). A search for `redis` across the codebase returns zero matches. The premise that a Redis connection is configured for the cache is incorrect.

**Actual mechanism:**

The cache is a thread-safe, **in-process in-memory** cache implemented entirely in Go at `store/cache/cache.go`. It uses a `sync.Map` for storage plus a background cleanup goroutine (`cleanupLoop`) — no network client, no connection string, nothing to configure for a remote server.

- **Where it's "configured":** in `store/store.go:38-53`, `Store.New()` builds a `cache.Config` literal (not a Redis DSN):
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  
  This one config is passed to three separate in-memory cache instances: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). The same defaults are also defined in `cache.DefaultConfig()` at `store/cache/cache.go:57-64`.

- **TTL for user entries:** User records are written to `userCache` via plain `Set(...)` (e.g. `store/user.go:98,122,132,143,167`), which delegates to `SetWithTTL(ctx, key, value, c.config.DefaultTTL)` (`store/cache/cache.go:93-95`). Since the user cache is constructed with the default config, **user entries expire after 10 minutes** (the `DefaultTTL`). Expiry is enforced lazily on `Get` (`cache.go:135`) and proactively by the cleanup goroutine every 5 minutes (`cache.go:218-250`). The cache key is just the stringified user ID (`userCacheKey`, `store/user.go:88-90`).

There is no per-entry override for users — they always use the default 10-minute TTL. `SetWithTTL` exists but isn't called for user records.
