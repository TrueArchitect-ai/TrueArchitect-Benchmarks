**Premise correction: there is no per-user API rate-limiting middleware in this repository, so there is nothing registered and no request limits to report.**

This is the **memos** project (Go backend using Connect RPC over the Echo v5 HTTP framework). I checked the HTTP middleware chain, the Connect RPC interceptor chain, dependencies, server setup, and Docker/proxy config — there is no rate limiter, throttler, or `429/TooManyRequests` handler anywhere, and no rate-limiting library in `go.mod`/`go.sum`.

What the request premise likely conflates with rate limiting:

- **HTTP middleware** (`server/server.go:51-52`) — only `middleware.Recover()` and a CORS middleware. No limiter.
- **Connect RPC interceptors** (`server/router/api/v1/v1.go:133-137`) — metadata, logging, recovery, and auth (`NewAuthInterceptor`) only. No rate/throttle interceptor.
- **Global request body-size cap** (`server/router/api/v1/v1.go:126,141,144`) — `maxAPIRequestBytes` via `http.MaxBytesHandler` / `connect.WithReadMaxBytes`. This is a per-request *byte-size* cap, not a request-frequency limit, and not per-user.
- **Global concurrency semaphores** (`server/router/api/v1/v1.go:59-60`) — `thumbnailSemaphore` (3) and `imageProcessingSemaphore` (2) bound *concurrent* image work process-wide; exhaustion returns `ResourceExhausted` "too many image processing requests" (`server/router/api/v1/attachment_service.go:160`). Shared across all users, not rate-based, not per-user.
- **Per-request batch-size validation** — various `"too many ..."` `InvalidArgument` checks (e.g. `server/router/api/v1/user_service.go:145`) cap items in a single payload, not request rate.

If per-user rate limiting is required, it does not currently exist and would need to be added — e.g. a new Connect interceptor keyed on the authenticated user from `NewAuthInterceptor`, or a reverse proxy in front of the service.
