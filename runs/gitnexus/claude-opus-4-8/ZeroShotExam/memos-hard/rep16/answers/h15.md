Memo visibility (who may view a memo) is enforced at several distinct server surfaces. The distinct enforcement sites:

gRPC API v1 — single-memo read gate (`checkMemoReadAccess`, private→creator-only) — server/router/api/v1/memo_service.go:39,63
gRPC API v1 — `ListMemos` visibility filter (anonymous→PUBLIC; others→PUBLIC/PROTECTED + CEL creator filter) — server/router/api/v1/memo_service.go:219,225
File/attachment server — `checkAttachmentPermission` (private blob→creator/admin only) — server/router/fileserver/fileserver.go:699
RSS feeds — explore & per-user feeds forced to PUBLIC only — server/router/rss/rss.go:90,141
Frontend SSR/meta fetch — memo for HTML meta tags forced to PUBLIC only — server/router/frontend/frontend.go:150
Store/SQL layer — `VisibilityList` compiled into `visibility IN (...)` WHERE clause backing every filter above — store/db/sqlite/memo.go (mirrored in store/db/postgres/memo.go, store/db/mysql/memo.go)

Additional per-feature gates reuse the same `Visibility == store.Private && CreatorID != user.ID` pattern, e.g.:
Reactions — server/router/api/v1/reaction_service.go
Comments (list + create) — server/router/api/v1/memo_service_comments.go
Memo relations — server/router/api/v1/memo_relation_service.go
SSE real-time delivery (`SSEClient.canReceive`) — server/router/api/v1/sse_hub.go

The intentional bypass is the share-token path (`GetMemoByShare` — server/router/api/v1/memo_share_service.go, and the share_token fallback in fileserver.go), which grants view access regardless of visibility.

The three primary/most-distinct surfaces, if you want the minimal list, are: the gRPC API v1 memo service (memo_service.go), the file/attachment server (fileserver.go), and the RSS feed handler (rss.go) — all ultimately backed by the store SQL `visibility IN (...)` filter (store/db/*/memo.go).
