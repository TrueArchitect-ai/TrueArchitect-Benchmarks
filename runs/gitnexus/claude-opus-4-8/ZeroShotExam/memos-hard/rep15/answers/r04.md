**Premise correction:** The question assumes webhook delivery workers consume from an external message broker (NATS or RabbitMQ). Neither is used — memos has **no external message broker at all**. `go.mod` has no `nats`, `amqp`/`rabbitmq`, `kafka`, or `redis` dependency, and a repo-wide grep for those imports returns nothing.

**Actual mechanism:** Webhook delivery uses an **in-process buffered Go channel** drained by a fixed pool of goroutines — the "queue" never leaves the process.

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a buffered channel with capacity 128.
- **Workers/consumers:** `internal/webhook/webhook.go:42-55` — an `init()` spawns **4 worker goroutines**, each ranging over `asyncPostQueue` (line 45) and calling `Post(payload)` (line 46) to perform the direct HTTP POST.
- **Enqueue (producer):** `PostAsync(...)` in the same file does a non-blocking `select` send onto the channel, dropping the delivery with a warning if the buffer is full (rather than blocking).
- **Upstream triggers:** `server/router/api/v1/memo_service_webhooks.go` (`dispatchMemoRelatedWebhook`, `DispatchMemoCommentCreatedWebhook`) calls `webhook.PostAsync(...)` synchronously from memo create/update/delete/comment lifecycle events.

So there is no NATS/RabbitMQ queue declaration to point to — the "queue" is the Go channel at `internal/webhook/webhook.go:39`, consumed by goroutine workers in the same file.
