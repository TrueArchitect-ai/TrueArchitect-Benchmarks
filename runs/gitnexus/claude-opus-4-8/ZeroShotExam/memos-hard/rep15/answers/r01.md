**Premise correction:** There is no Redis anywhere in this codebase — a repo-wide search for `redis` returns zero matches, and there is no external cache layer at all. The cache is a **thread-safe in-memory cache** (Go `sync.Map`), not a Redis-backed one, so there is no Redis connection string, host, or client to configure.

**Actual mechanism:**

- The cache implementation lives in `store/cache/cache.go` — a `Cache` struct backed by `sync.Map` with per-item `expiration` timestamps and a background `cleanupLoop` goroutine that sweeps expired entries (`store/cache/cache.go:66-215`).
- It is "configured" not via a connection but via a `cache.Config` literal constructed in the store constructor `New` at `store/store.go:39-53`. Three separate in-memory cache instances are created there — `instanceSettingCache`, `userCache`, and `userSettingCache` — all sharing the same config:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  (The same defaults also appear in `cache.DefaultConfig()` at `store/cache/cache.go:57-64`.)

**TTL for user entries:** User records are cached in `userCache`. Every write goes through `s.userCache.Set(...)` (e.g. `store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` applies the cache's `DefaultTTL` (`store/cache/cache.go:92-95`). So **user entries expire 10 minutes after they are written** (keyed by user ID via `userCacheKey`, `store/user.go:88-90`). No code path uses `SetWithTTL` for users, so there is no user-specific TTL override — it is the global 10-minute default. Expired entries are evicted lazily on `Get` and proactively by the 5-minute cleanup sweep.
