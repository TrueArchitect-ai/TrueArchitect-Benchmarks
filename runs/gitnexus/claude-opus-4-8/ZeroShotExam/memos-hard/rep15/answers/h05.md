**Mechanism: removed by explicit Go code, inside the `DeleteUser` transaction — not by a database rule.**

When a user is deleted, their own emoji reactions are removed by an explicit `DELETE` statement in Go, executed within the delete-user transaction. There is no database-level cascade for the `reaction` table.

What I checked:

- **`store/db/sqlite/user_delete.go:400-403`** — `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` with the deleted user's ID. This is what removes the reactions the user *made*.
- **`store/db/sqlite/user_delete.go:380-388`** — `deleteReactionsByContentIDsTx` additionally runs `DELETE FROM reaction WHERE content_id IN (...)` for the deleted user's memos, removing reactions *on* their content (including reactions others left).
- **`store/db/sqlite/user_delete.go:92-127`** — `deleteUserTargetsTx` orchestrates both calls (lines 96 and 102) inside the transaction begun in `DeleteUser` (lines 29-59), before the user row itself is deleted (`deleteUserRowTx`, lines 461-464).
- **`store/migration/sqlite/LATEST.sql:91-99`** — the `reaction` table definition has **no foreign key and no `ON DELETE CASCADE`**. Contrast with `memo_share` (lines 102-110), which *does* declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`. So there is no DB rule that would clean up reactions automatically; the Go code must do it.
- The same pattern exists for the other backends: `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go` are the sibling implementations (and `store/migration/postgres/0.23/00__reactions.sql` / `store/migration/sqlite/0.23/00__reactions.sql` define the table).

So: user-authored reactions → deleted by explicit Go (`deleteReactionsByCreatorTx`); reactions on the user's memos → deleted by explicit Go (`deleteReactionsByContentIDsTx`); the database schema itself does nothing on user deletion.
