A browser requesting another user's profile image hits `GET /file/users/:identifier/avatar`. The avatar is stored inline as a base64 data URI in the `user.avatar_url` column, so the path ends at a `SELECT ... avatar_url ... FROM user`.

Notes:
- Route registered at `server/router/fileserver/fileserver.go:124` (`fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)`).
- The identifier is looked up by username (`store.FindUser{Username: &identifier}`), so any user's avatar is reachable by username; on a private instance the handler first requires a valid viewer (lines 173–181).
- After the fetch, the handler decodes the data URI via `parseDataURI` (`fileserver.go:737`) and returns the bytes with `c.Blob` (line 209) — no separate blob store or filesystem hop; the image bytes live in the `user` row itself.
- `store.GetUser`/`ListUsers` also consult/populate `userCache`, but cache is keyed only by ID, so a username lookup always reaches the driver/SQL.
- The driver is an interface; `store/db/mysql/user.go:84` and `store/db/postgres/user.go:87` are the equivalent implementations for those backends.
