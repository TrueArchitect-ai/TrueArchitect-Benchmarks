h04.

**Yes — once, and only in a unit test.** Outside the driver-selection factory, the MySQL driver is directly constructed exactly one place: as a zero-value struct literal in the mysql package's own test. Everywhere else it goes through the factory.

Evidence:
- **The normal constructor path is factory-only.** The MySQL driver's constructor is `mysql.NewDB(profile)` (`store/db/mysql/mysql.go:20`), whose sole call site in the entire repo is the factory's `switch`: `case "mysql": driver, err = mysql.NewDB(profile)` at `store/db/db.go:22`. The `store/db/mysql` package is imported by exactly one file — `store/db/db.go` — so no other package can even reference the driver type. Tests reach MySQL only via the factory: `store/test/store.go:28` and `store/test/store.go:50` call `db.NewDBDriver(profile)`.

- **The one direct construction outside the factory:** `store/db/mysql/auth_config_test.go:12` — `db := &DB{}`. Because this test is in `package mysql` itself, it can name the unexported `DB` type directly and build a zero-value instance. It's not a working driver — no DSN, no `profile`, no `sql.Open` (contrast `store/db/mysql/mysql.go:29`, the real `driver := DB{profile: profile}` *inside* `NewDB`). It exists only to invoke the pure method `IsRetryableAuthenticationMutationError` on error values (lines 13–15).

So: no direct use of the `mysql.NewDB` constructor exists outside the factory, but a bare `&DB{}` struct literal is constructed once, in `auth_config_test.go`, for an in-package unit test.
