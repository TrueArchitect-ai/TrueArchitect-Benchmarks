Memo visibility (who may view a memo) is enforced at these distinct server surfaces:

Single-memo read gate (gRPC/REST GetMemo) — `checkMemoReadAccess` in server/router/api/v1/memo_service.go
List-memos filter construction — `ListMemos` in server/router/api/v1/memo_service.go
Store-level SQL visibility filter (backs all list/filter paths) — `listMemos` in store/db/sqlite/memo.go (Postgres twin: store/db/postgres/memo.go)
Attachment/blob byte serving over HTTP — `checkAttachmentPermission` in server/router/fileserver/fileserver.go
Attachment listing API — `ListMemoAttachments` in server/router/api/v1/memo_attachment_service.go
Comments (create gate + list filter) — `CreateMemoComment` / `ListMemoComments` in server/router/api/v1/memo_service_comments.go
RSS feed rendering (Public-only) — `GetRSS` / `GetUserRSS` in server/router/rss/rss.go
Public sitemap rendering (Public-only) — `getSitemapXML` in server/router/frontend/frontend.go
Notification/email view gate — `canViewerAccessMemo` in server/router/api/v1/user_service_notifications.go (duplicated in server/notification/email.go)

The three primary independent per-memo enforcement sites are `checkMemoReadAccess` (memo_service.go), the list filter → SQL `visibility IN (...)` pair (memo_service.go + store/db/sqlite/memo.go), and the fileserver `checkAttachmentPermission` (fileserver.go); the rest are additional distinct surfaces. Note one asymmetry worth flagging: the fileserver, attachment-listing, and comment checks grant a super-user/admin bypass, but the primary `checkMemoReadAccess` gate does not.
