**Premise correction:** There is no Redis in this codebase. Memos is a self-hosted single Go binary and its cache layer is **in-process, in-memory** — not a Redis (or any external) connection. A full search for `redis` across the repo returns zero matches, and `go.mod`/`go.sum` pull in no Redis client. So there is nothing to "configure a Redis connection" for; the question's premise doesn't hold.

**Actual mechanism:**

- The cache is a hand-rolled thread-safe in-memory cache built on `sync.Map` with a background TTL-cleanup goroutine, defined in `store/cache/cache.go` (the `Cache` type, `New`, `Set`/`SetWithTTL`, `cleanupLoop`).
- It's "configured" — not connected — in `store/store.go:40-53`. `store.New()` builds one `cache.Config` and instantiates three separate in-memory caches from it: `instanceSettingCache`, `userCache`, and `userSettingCache`. They're torn down via `Close()` on their cleanup goroutines in `store/store.go:74-76`.
- The config values (`store/store.go:41-44`): `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, no eviction callback. These mirror the library defaults in `store/cache/cache.go:57-64` (`DefaultConfig`).

**TTL for user entries:** User records are written to `userCache` via plain `s.userCache.Set(...)` (e.g. `store/user.go:98,122,132,143,167`), and `Set` applies the cache's `DefaultTTL` (`store/cache/cache.go:93-95`). So user entries expire **10 minutes** after they're written. There is no per-user `SetWithTTL` override, so users don't get a custom TTL — they inherit the 10-minute default, with expired entries reaped lazily on `Get` (`cache.go:135-144`) and by the 5-minute cleanup sweep. On writes/deletes the cache is invalidated explicitly (`store/user.go`, `store/user_delete.go:40`).

Cache key format for user entries: `userCacheKey` in `store/user.go:88`.
