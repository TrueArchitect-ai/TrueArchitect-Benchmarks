**Premise correction:** The question's premise is false — memos uses *neither* NATS nor RabbitMQ. There is no external message broker anywhere in the codebase (no `nats`, `rabbitmq`, or `amqp` references, and `go.mod` declares no broker dependency).

**Actual mechanism:** Webhook delivery is entirely in-process, built on a bounded Go channel and worker goroutines, all in `internal/webhook/webhook.go`:

- **The "queue" is an in-memory buffered channel**, not a broker-declared queue: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` at `internal/webhook/webhook.go:39` (capacity 128).
- **Four worker goroutines** drain it — `init()` spawns `for range 4` workers that range over the channel and call `Post()` for each payload (`internal/webhook/webhook.go:42-55`).
- **Enqueue is fire-and-forget with drop-on-overflow**: `PostAsync()` does a non-blocking `select` — `case asyncPostQueue <- requestPayload:` on success, `default:` logs "Dropped webhook dispatch because the async queue is full" and discards (`internal/webhook/webhook.go:184-196`). No retry, no persistence.
- **Actual delivery is a synchronous, HMAC-signed, SSRF-guarded HTTP POST** inside `Post()` (`internal/webhook/webhook.go:120-180`), using a 30s-timeout client (`safeClient`, lines 32-37).

Dispatch is triggered from `server/router/api/v1/memo_service_webhooks.go` (e.g. `webhook.PostAsync(...)` at line 71 for memo events and line 43 for comment events).

So: there are no "webhook delivery workers consuming from a message broker" — they are goroutine workers consuming from an in-process Go channel declared at `internal/webhook/webhook.go:39`.
