**Mechanism: Explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the user-deletion transaction — not by any database-level cascade. There is no `FOREIGN KEY`/`ON DELETE CASCADE` on the reaction table, so the DB does nothing automatically.

The Go code removes reactions along **two** dimensions, both inside the same transaction (`deleteUserTargetsTx`):
1. Reactions the user **received** — reactions on the user's memos, matched by `content_id` (`memos/<uid>`) via `deleteReactionsByContentIDsTx`.
2. Reactions the user **authored** — matched by `creator_id` via `deleteReactionsByCreatorTx`.

**Evidence locations:**

- Explicit deletion, SQLite driver — `store/db/sqlite/user_delete.go`:
  - Orchestration in `deleteUserTargetsTx`: line 96 (`deleteReactionsByContentIDsTx`) and line 102 (`deleteReactionsByCreatorTx`).
  - `deleteReactionsByContentIDsTx` — lines 380–388: `DELETE FROM reaction WHERE content_id IN (...)`.
  - `deleteReactionsByCreatorTx` — lines 400–403: `DELETE FROM reaction WHERE creator_id = ?`.
- Same logic in the other two drivers:
  - `store/db/postgres/user_delete.go:96,102,380–401`.
  - `store/db/mysql/user_delete.go:96,102,417–438`.
- No DB-level rule — reaction table DDL has `creator_id INTEGER NOT NULL` / `content_id TEXT NOT NULL` with **no** `REFERENCES`/foreign-key/cascade clause, in all three schemas: `store/migration/sqlite/LATEST.sql`, `store/migration/postgres/LATEST.sql`, `store/migration/mysql/LATEST.sql` (the `CREATE TABLE reaction` blocks shown above). A grep for `FOREIGN`/`REFERENCES` near `reaction` in those files returned nothing.
