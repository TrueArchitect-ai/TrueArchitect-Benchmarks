**Mechanism: explicit Go code** (a `DELETE FROM reaction WHERE creator_id = ?` run inside the user-delete transaction in each driver) — **not** a database-level cascade. Consistent across all three drivers (sqlite/mysql/postgres); no discrepancy.

What I checked:

1. **Schema — no FK/cascade.** The `reaction` table's `creator_id` is a plain `INTEGER/INT NOT NULL` with no `FOREIGN KEY ... REFERENCES user(id)` and no `ON DELETE CASCADE`, in all three schemas:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-97`
   The only `ON DELETE CASCADE` in the LATEST schemas is on `memo_share.memo_id`; nothing references `user(id)`. So the DB would orphan reactions on user deletion if left to itself.

2. **Explicit driver-level deletion.** Each driver's `DeleteUser` runs a transaction calling `deleteUserTargetsTx`, which explicitly removes reactions two ways — by creator and by the user's memo content:
   - `store/db/sqlite/user_delete.go` — `deleteReactionsByCreatorTx` (`DELETE FROM reaction WHERE creator_id = ?`, ~line 396) and `deleteReactionsByContentIDsTx` (~line 380), both invoked from `deleteUserTargetsTx` (~lines 100–102)
   - `store/db/mysql/user_delete.go:96,102,417-439`
   - `store/db/postgres/user_delete.go:96,102,380-401`

3. **Service layer delegates.** `server/router/api/v1/user_service.go:393-419` (`DeleteUser`) does permission checks then calls `s.Store.DeleteUser`; `store/user.go:171-181` is a thin pass-through to `driver.DeleteUser`. The cascade lives in the driver, not the API service.

4. **General `DeleteReaction` unused here.** `store/reaction.go:39` and the per-driver `DeleteReaction` (e.g. `store/db/sqlite/reaction.go:133`) delete a single reaction by id and are **not** called during user deletion; the user-delete path uses its own transaction-scoped SQL so it commits atomically with the user row.
