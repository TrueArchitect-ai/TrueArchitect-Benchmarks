Every distinct site that enforces memo *view* visibility:

```
checkMemoReadAccess — GetMemo read gate (PRIVATE→non-creator PermissionDenied, non-PUBLIC→auth required) — server/router/api/v1/memo_service.go:39-68 (called at :356 and :367)
ListMemos caller-based visibility filter (anonymous→PUBLIC only; other creator→PUBLIC/PROTECTED; self→+own) — server/router/api/v1/memo_service.go:218-227
CreateMemoComment parent-memo PRIVATE check (inlined, not via helper) — server/router/api/v1/memo_service_comments.go:41-42
RSS feeds restricted to PUBLIC only (GetRSS and GetUserRSS) — server/router/rss/rss.go:90 and :141
checkAttachmentPermission parent-memo visibility gate before serving an attachment (PRIVATE→403 for non-creator/non-admin) — server/router/fileserver/fileserver.go:650-704 (checks at :677, :699)
Store SQL visibility filter (visibility IN (...) built from FindMemo.VisibilityList) — store/db/sqlite/memo.go:96-103; store/db/postgres/memo.go:89; store/db/mysql/memo.go:104
```

Notes:
- Sites #2 (ListMemos) and #4 (RSS) express their policy by setting `FindMemo.VisibilityList`, which is turned into the actual `visibility IN (...)` WHERE clause by site #6 (the store/SQL layer). I've listed the SQL filter separately because it's a distinct enforcement surface across all three DB backends.
- `checkMemoReadAccess` is the single shared API read gate, reused for both the target memo and, for comments, its parent.
- Excluded from the list (they're ownership/write checks, not view-visibility): `UpdateMemo` (`memo_service.go:426-427`) and `DeleteMemo` (`memo_service.go:541-542`), which enforce `CreatorID != user.ID && !isSuperUser`.
