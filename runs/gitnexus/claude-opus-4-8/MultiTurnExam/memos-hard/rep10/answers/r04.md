**Premise correction: neither. The webhook workers do not consume from any message broker — there is no NATS, no RabbitMQ, no AMQP anywhere in the codebase (a repo-wide grep for `nats`/`rabbitmq`/`amqp`/`streadway` returns zero hits).**

Actual mechanism — an in-process buffered Go channel:

- The "queue" is a package-level buffered channel declared at `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — capacity 128, entirely in-memory within the server process.
- Four worker goroutines are spawned in the package `init()` (`internal/webhook/webhook.go:42-46`); each loops `for payload := range asyncPostQueue` and calls `Post(payload)` to perform the HTTP delivery.
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), a non-blocking `select`: `case asyncPostQueue <- requestPayload:` on success, and on a full queue it drops the dispatch and logs a warning (`webhook.go:190-192`).

So delivery is handled by a bounded in-process channel + goroutine worker pool, not an external broker. Consequences worth noting: the queue is not durable (pending webhooks are lost on restart) and it silently drops deliveries when full — there is nothing to configure or connect to for NATS/RabbitMQ.
