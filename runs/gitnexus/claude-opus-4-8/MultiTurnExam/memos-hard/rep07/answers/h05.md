**Mechanism: explicit Go code** (not a DB-level cascade).

Evidence locations:

- **Explicit deletion in the delete-user transaction** — `store/db/sqlite/user_delete.go`:
  - `deleteReactionsByCreatorTx` (line 400): `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the deleted user *made*.
  - `deleteReactionsByContentIDsTx` (line 380): `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on* the deleted user's content.
  - Parallel implementations exist per dialect (`store/db/mysql/user_delete.go`, `store/db/postgres/user_delete.go`).
- **No database-level rule backs this up** — the `reaction` table schema has no foreign key / `ON DELETE CASCADE` on `creator_id` or `content_id`. Checked `store/migration/sqlite/LATEST.sql:92-99` (bare `creator_id INTEGER NOT NULL`, only a `UNIQUE` constraint; contrast the adjacent `memo_share` table at lines 102-110 which *does* declare `FOREIGN KEY ... ON DELETE CASCADE`). The same holds for the mysql/postgres `LATEST.sql` reaction definitions.

So reactions are removed only because `DeleteUser`'s Go transaction explicitly issues the `DELETE FROM reaction` statements; nothing in the schema would remove them automatically.
