**Mechanism: explicit Go code (no DB-level cascade).**

A deleted user's emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the `DeleteUser` transaction in each driver — the `reaction` table has no foreign keys and no `ON DELETE CASCADE`.

Evidence locations:

**Explicit Go deletion** (within the `DeleteUser` transaction, each driver runs a delete-by-creator plus a delete-by-content):
- Store wrapper: `store/user.go:171` — delegates to `s.driver.DeleteUser(...)`.
- SQLite `store/db/sqlite/user_delete.go` — `deleteUserTargetsTx` (line 92) calls `deleteReactionsByContentIDsTx` (line 380, `DELETE FROM reaction WHERE content_id IN ...`) and `deleteReactionsByCreatorTx` (line 400, `DELETE FROM reaction WHERE creator_id = ...`).
- MySQL `store/db/mysql/user_delete.go` — same two functions at lines 417 and 437.
- Postgres `store/db/postgres/user_delete.go` — same two functions at lines 380 and 400.

**Reaction table schema — no FK / no cascade** (only a UNIQUE constraint; `creator_id` is a plain column):
- `store/migration/sqlite/LATEST.sql:91-99`
- `store/migration/mysql/LATEST.sql:90-98`
- `store/migration/postgres/LATEST.sql:90-98`
- Original migrations `store/migration/{sqlite,mysql,postgres}/0.20/00__reaction.sql` — identical, no FK.
- The only `ON DELETE CASCADE` in the schema is on `memo_share.memo_id → memo(id)` (e.g. sqlite LATEST.sql:109), not on `reaction`.

So: without the explicit Go code, a deleted user's reactions would be orphaned — the database would not remove them.
