**Premise correction: there is no Redis in this codebase.** A repo-wide search for `redis` across all `.go` files returns zero matches. The cache layer is a purpose-built, thread-safe **in-memory** cache — `store/cache/cache.go` (`type Cache is a thread-safe in-memory cache with TTL and memory management`, line 66). So there is no Redis connection to configure.

**Actual mechanism:**
- **Configuration site:** The caches are created in `Store.New` at `store/store.go:38-53`, using a single `cache.Config` (lines 40-45): `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`. This config builds three in-memory caches — `instanceSettingCache`, `userCache`, and `userSettingCache` (each `cache.New(cacheConfig)`). Defaults also live in `cache.DefaultConfig()` (`store/cache/cache.go:57`, same 10-min TTL).
- **TTL for user entries:** User entries are written via `s.userCache.Set(...)` (e.g. `store/user.go:98, 122, 132, 143, 167`). `Set` uses the cache's default TTL (`cache.go:92-94` → `SetWithTTL(..., c.config.DefaultTTL)`), so **user cache entries expire after 10 minutes** (`store/store.go:41`), with expired items reaped every 5 minutes by the cleanup loop (`cache.go:199`). None of the user `Set` calls pass a custom TTL, so no per-entry override applies.
