h05.

**Mechanism: explicit Go code.** A user's emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the delete-user transaction, not by any database cascade.

Evidence:

- **Explicit Go deletion** — in the SQLite driver's `DeleteUser` path, `deleteUserTargetsTx` calls two reaction deletes: `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` (removes reactions the user made), and `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN (...)` (removes reactions on the user's own memos). See `store/db/sqlite/user_delete.go` — the calls are in `deleteUserTargetsTx` (the `deleteReactionsByContentIDsTx` and `deleteReactionsByCreatorTx` calls), and the functions themselves are defined lower in the same file. The MySQL and Postgres drivers have the parallel implementations at `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go`.

- **No database-level rule** — the `reaction` table declares no foreign key on `creator_id` at all (only a `UNIQUE(creator_id, content_id, reaction_type)` constraint), so there is no `ON DELETE CASCADE` to remove reactions when a `user` row is deleted. Verified in all three dialect schemas: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, and `store/migration/mysql/LATEST.sql:91-98`. (For contrast, `memo_share` in those same files *does* carry `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, showing cascades are used elsewhere but deliberately not on `reaction`.)
