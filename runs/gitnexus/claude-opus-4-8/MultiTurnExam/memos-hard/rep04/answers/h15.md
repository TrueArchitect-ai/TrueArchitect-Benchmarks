Memo visibility (who may *view* a memo) is enforced at these distinct server surfaces:

- Memo gRPC/Connect API — single-memo read guard `checkMemoReadAccess` (used by `GetMemo`) — server/router/api/v1/memo_service.go:55 (function spanning ~:38–68)
- Memo gRPC/Connect API — list query visibility scoping in `ListMemos` (builds `VisibilityList` from the viewer) — server/router/api/v1/memo_service.go:219 and :225
- RSS feed service — restricts feed to `store.Public` memos only — server/router/rss/rss.go:90 and :141
- Frontend SSR sitemap — lists only `store.Public` memos — server/router/frontend/frontend.go:150
- SSE realtime event hub — `SSEClient.canReceive` gates event fan-out by visibility — server/router/api/v1/sse_hub.go:134 (case at :136–:138)
- File server — `checkAttachmentPermission` gates serving a memo's attachment content by the parent memo's visibility — server/router/fileserver/fileserver.go:677 and :699
- User stats API — scopes aggregated memo stats by visibility relative to the viewer — server/router/api/v1/user_service_stats.go:84/90 and :218/220

The underlying mechanism for the query-based sites (ListMemos/RSS/frontend/stats) is the store's `FindMemo.VisibilityList` filter compiled into the SQL `WHERE` clause by each DB driver (e.g. store/db/sqlite/memo.go), while the read guard, SSE hub, and fileserver perform explicit per-memo checks.

(Related visibility checks also exist that gate *actions* rather than viewing — e.g. reactions `server/router/api/v1/reaction_service.go:30/38/83`, comments `memo_service_comments.go:41`, adding attachments `memo_attachment_service.go:214/222`, and mention notifications `memo_mention_helpers.go:62/67` — listed here for completeness but they enforce who may act/notify, not who may view.)
