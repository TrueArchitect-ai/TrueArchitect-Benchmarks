Chain from the browser's request to stored data (avatar is served as raw bytes by the Echo fileserver, not gRPC):

- `GET /file/users/:identifier/avatar` (route registration) — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (handler; reads `user.AvatarURL`, decodes data URI, `c.Blob`) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` (handler helper) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` — `store/user.go:148`
- `Store.ListUsers` — `store/user.go:136`
- `DB.ListUsers` (SQLite driver; `SELECT ... avatar_url ... FROM user`, scans into `user.AvatarURL`) — `store/db/sqlite/user.go:88` (query at `:151-165`, scan at `:189`; equivalent Postgres `store/db/postgres/user.go:150`, MySQL `store/db/mysql/user.go:147`)

Where the data lives: the profile image is stored inline as a base64 **data URI** in the `avatar_url` **column of the `user` table** — not a file/attachment. The handler base64-decodes it via `parseDataURI` (`server/router/fileserver/fileserver.go:737-747`). (The gRPC `UserService` converter rewrites the raw blob to the `/file/{name}/avatar` URL — `server/router/api/v1/user_service_converters.go:31-38` — which points back at this same fileserver endpoint.)
