**Mechanism: explicit Go code** — reactions are removed by hand-written `DELETE FROM reaction ...` statements in the `DeleteUser` transaction. There is no database-level cascade or trigger, and it is not left uncleaned.

Evidence I checked:

- **Go delete path:** `Store.DeleteUser` (`store/user.go:171`) delegates to per-dialect drivers (`store/db/{sqlite,mysql,postgres}/user_delete.go:29`), which run `deleteUserTargetsTx` and explicitly delete reactions **two ways**:
  - reactions the user authored — `DELETE FROM reaction WHERE creator_id = ?` (`deleteReactionsByCreatorTx`, e.g. sqlite `store/db/sqlite/user_delete.go:380-403`, mirrored mysql `:417-439`, postgres `:380-402`);
  - reactions others left on the user's memos — `DELETE FROM reaction WHERE content_id IN (...)` (`deleteReactionsByContentIDsTx`).
- **Reaction schema (no FK):** `creator_id` is a plain `INTEGER/INT NOT NULL` with no `REFERENCES user(id)` / `ON DELETE CASCADE` in any dialect — `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`. By contrast the adjacent `memo_share` table does declare `ON DELETE CASCADE`, confirming the absence on `reaction` is deliberate.
- **SQLite FK enforcement disabled anyway:** the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), and migrations `store/migration/sqlite/0.7/00__remove_fk.sql` / `0.7/01__remove_triggers.sql` stripped FKs/triggers historically — so even declared FKs wouldn't fire at runtime for SQLite.
- **No trigger** deletes reactions on user deletion (the only trigger migrations predate the 0.20 reaction feature).
- Behavior is covered by test `store/test/user_delete_test.go:13` (`TestDeleteUserCleansRelatedData`).

Dialect differences: none in behavior — all three rely solely on the explicit Go deletes; the Go code is the only guarantor of cleanup.
