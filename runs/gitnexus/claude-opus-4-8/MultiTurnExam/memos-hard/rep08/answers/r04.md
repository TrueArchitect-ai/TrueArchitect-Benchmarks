**Premise correction:** Neither. The webhook delivery workers do not consume from any external message broker — there is no NATS and no RabbitMQ in this codebase. A repo-wide search finds zero references to `nats`, `rabbitmq`, `amqp`, or `kafka` in any `.go` file or in `go.mod`. There is therefore no broker-declared queue.

**Actual mechanism:** Webhook delivery uses an in-process Go **buffered channel**, entirely within the `internal/webhook` package:
- The "queue" is a buffered channel declared as a package-level variable: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39` (capacity 128).
- **4 worker goroutines** are started in the package `init()` (`internal/webhook/webhook.go:42-54`); each ranges over `asyncPostQueue` and calls `Post` (the outbound HTTP delivery, `webhook.go:46`).
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), a non-blocking send: if the channel buffer is full it drops the webhook and logs a warning (`webhook.go:189-195`) rather than blocking.

So it's a bounded, in-memory, single-process worker pool over a channel — the queue "declaration" is the `make(chan ...)` at `internal/webhook/webhook.go:39`. Note this means pending webhooks are not durable and are lost on restart.
