**Premise correction:** Neither. The webhook delivery workers do not consume from any external message broker — there is no NATS, RabbitMQ/AMQP, Kafka, or Redis in the codebase (a repo-wide search for `nats`, `rabbitmq`, `amqp`, `kafka`, `redis` across all `.go` files returns zero matches). So there is no broker-declared queue to point to.

**Actual mechanism:** Delivery is handled entirely in-process using a bounded Go channel and a fixed pool of goroutine workers, all in `internal/webhook/webhook.go`:
- The "queue" is a buffered channel declared as a package variable: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39` (capacity 128).
- Workers are started in `init()`: a loop spawning **4** goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)` to perform the HTTP delivery — `internal/webhook/webhook.go:42-55`.
- Producers enqueue via `PostAsync`, which does a non-blocking send onto the channel and **drops** the event (logging a warning) if the buffer is full — `internal/webhook/webhook.go:184-196`. Callers such as `dispatchMemoRelatedWebhook` invoke `webhook.PostAsync` (`server/router/api/v1/memo_service_webhooks.go:43, :71`).

So it's an in-memory, single-process channel-plus-worker-pool design — no external broker, and nothing survives a process restart.
