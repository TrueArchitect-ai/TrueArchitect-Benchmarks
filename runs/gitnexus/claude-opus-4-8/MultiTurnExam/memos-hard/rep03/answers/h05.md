**Mechanism: explicit Go code.** A user's emoji reactions are removed by an explicit `DELETE` statement in the user-deletion transaction, not by any database-level cascade rule.

Evidence locations:

1. **Explicit Go deletion.** `deleteUserTargetsTx` calls `deleteReactionsByCreatorTx(ctx, tx, userID)` as part of the delete transaction — `store/db/sqlite/user_delete.go:102` (mirrored in `store/db/mysql/user_delete.go` and `store/db/postgres/user_delete.go`). That helper runs `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`). (It additionally removes reactions *on* the deleted user's memos via `deleteReactionsByContentIDsTx`, line 96.) `deleteUserTargetsTx` is invoked from the driver's `DeleteUser` (`store/db/sqlite/user_delete.go:29`), which the store's `DeleteUser` (`store/user.go:171`) delegates to.

2. **No DB-level rule.** The `reaction` table's DDL declares `creator_id` as a plain `INTEGER/INT NOT NULL` with no foreign key and no `ON DELETE CASCADE` in any backend — `store/migration/sqlite/LATEST.sql`, `store/migration/mysql/LATEST.sql`, `store/migration/postgres/LATEST.sql` (reaction `CREATE TABLE` blocks shown above). So the database would not remove reactions on its own; the Go code is what does it.

3. Behavior is covered by a test: `TestDeleteUserCleansRelatedData` in `store/test/user_delete_test.go`.
