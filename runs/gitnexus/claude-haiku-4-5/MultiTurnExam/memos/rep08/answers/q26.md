The store layer DeleteMemo just deletes the memo row. So when a parent memo is deleted:

1. **Explicitly** via API: comments (memos linked via MemoRelationComment) are deleted first by recursively calling DeleteMemo
2. When each comment memo is deleted (by its own DeleteMemo call):
   - The comment memo row is deleted from the memo table
   - Any attachments with memo_id = comment_id are left in the attachment table
   - Any memo_relation rows with memo_id = comment_id are left in memo_relation table
3. When the parent memo row is deleted:
   - memo_share rows are CASCADE deleted (because of the FK constraint)
   - Any memo_relation rows with memo_id = parent_id are left
   - Any attachment rows with memo_id = parent_id are left

So the affected tables are: memo (primary), memo_share (cascade), and potentially memo_relation and attachment (via orphaned rows).
