**memo, memo_relation, attachment** — plus **memo_share** only where the database enforces its foreign key.

Directly, by explicit code in `Store.DeleteMemo` (`store/memo.go:140-159`):

| Table | Where |
|---|---|
| `memo_relation` | deleted twice — rows where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`), `store/memo.go:142,145` |
| `attachment` | rows with `MemoID` listed then deleted individually (`store/memo.go:149-157`); `Store.DeleteAttachment` (`store/attachment.go:132`) also removes the backing file from local/external storage |
| `memo` | the row itself via `s.driver.DeleteMemo` (`store/memo.go:158`); at the API layer, `APIV1Service.DeleteMemo` first recurses into child **comment memos** (`server/router/api/v1/memo_service.go:568-577`), so additional `memo` rows and their relations/attachments go too |

`memo_share` is the edge case: `store/migration/sqlite/LATEST.sql:109` declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, but the SQLite driver opens the connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`, deliberate per the comment at lines 40-42), so on SQLite that cascade does **not** fire and share rows are left orphaned; on PostgreSQL/MySQL, where FKs are always enforced, `memo_share` rows are removed by the engine. No Go code in the delete path touches `memo_share`.

Not affected: `reaction` rows for the memo are only read to build the webhook payload (`server/router/api/v1/memo_service.go:545`) and are never deleted.
