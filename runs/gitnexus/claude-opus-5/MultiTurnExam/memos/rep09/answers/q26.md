q26.

Tables touched by a `DeleteMemo`:

```
memo_relation
attachment
memo
```

Evidence — `Store.DeleteMemo` (`store/memo.go:140-159`):
- `memo_relation` — two explicit deletes, for rows where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`), lines 142 and 145.
- `attachment` — attachments with `MemoID` are listed and deleted individually via `Store.DeleteAttachment` (lines 148-157), which also removes the underlying file/object from storage (`store/attachment.go:132-149`).
- `memo` — the row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`).

Additional rows in the same `memo` table come from the API layer: `APIV1Service.DeleteMemo` first deletes every comment memo (relations of type `MemoRelationComment`) by recursing through `Store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`), so each comment's relations and attachments go too.

Two caveats:
- `memo_share` declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`), but the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and share rows are left orphaned; on Postgres/MySQL the FK is enforced and `memo_share` is cascaded.
- `reaction` is **not** cleaned up — the handler only reads reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545`), leaving rows keyed by the memo's resource name behind.
