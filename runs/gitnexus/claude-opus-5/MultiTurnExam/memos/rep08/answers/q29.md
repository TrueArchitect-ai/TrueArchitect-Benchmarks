**`web/src/connect.ts` (with token state in `web/src/auth-state.ts`); short-lived JWT access token in memory + HTTP-only refresh-token cookie, plus Personal Access Tokens for non-browser clients; `server/auth/`**

**Interceptor.** `authInterceptor` is defined at `web/src/connect.ts:155` and installed on the shared Connect transport at line 188. Per request it calls `getRequestToken()` (line 124) and sets `Authorization: Bearer <token>`. Two refresh paths:

- *Proactive* — if the in-memory token is missing or `isTokenExpired(REQUEST_TOKEN_EXPIRY_BUFFER_MS)` (30 s buffer), it refreshes before sending. The comment at lines 138-141 explains why this matters: on public endpoints like `ListMemos`, an expired token would silently be treated as anonymous and return guest-scoped data.
- *Reactive* — on `Code.Unauthenticated` it refreshes, re-sends once with an `X-Retry: true` marker to prevent loops (`shouldHandleUnauthenticatedRetry`, line 101), and on failure calls `redirectOnAuthFailure()`.

Refresh calls go through `refreshAuthClient` on a **separate transport with no interceptors** (`web/src/connect.ts:65-72`) to avoid recursion, and are deduplicated by `tokenRefreshManager` (line 30) so a tab-focus refresh and a 401 refresh can't race against server-side token rotation. All requests use `credentials: "include"` (`fetchWithCredentials`, line 57) so the refresh cookie is sent.

**Token kinds:**
- **Access token** — short-lived JWT, held in memory/`auth-state.ts` (`getAccessToken`/`setAccessToken`/`isTokenExpired`/`clearAccessToken`), sent as a Bearer header. Minted by `GenerateAccessTokenV2` (`server/auth/token.go:134`).
- **Refresh token** — HTTP-only cookie, never read by JS; exchanged via `AuthService.RefreshToken` (`web/src/connect.ts:74`). Minted by `GenerateRefreshToken` (`server/auth/token.go:163`), extracted server-side by `ExtractRefreshTokenFromCookie` (`server/auth/extract.go:23`).
- **Personal Access Tokens** — the third accepted Bearer credential, for API/CLI clients rather than the web app; validated by `AuthenticateByPAT` (`server/auth/authenticator.go:102`), with usage recorded via `recordPATUsage` (line 179).

**Backend validation.** `server/auth/` — `Authenticator` (`server/auth/authenticator.go:32`) with `AuthenticateByAccessTokenV2` (line 41), `AuthenticateByRefreshToken` (line 61), `AuthenticateByPAT` (line 102), and `resolveBearer` (line 149) which decides whether a Bearer value is a JWT or a PAT. `Authenticate` (line 213) returns an `AuthResult` applied to the request context by `ApplyToContext` (`server/auth/context.go:88`).

One `Authorizer` instance wraps this and is shared by both serving paths — created at `server/router/api/v1/v1.go:68` and passed to the gRPC-Gateway middleware and to `NewAuthInterceptor(authorizer)` for Connect — so the per-method access policy in `server/router/api/v1/acl_config.go` is enforced identically regardless of protocol. The SSE endpoint authenticates separately from the same package (`handleSSE`, `server/router/api/v1/sse_handler.go:34`).
