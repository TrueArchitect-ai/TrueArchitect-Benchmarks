**`memo_relation`, `attachment`, `memo`** — plus **`memo_share`** if you count the database-level FK cascade.

Explicit cascade code in `Store.DeleteMemo` (`store/memo.go:140-159`), in execution order:

1. **`memo_relation`** — two deletes, one per direction: `DeleteMemoRelation{MemoID: ...}` then `DeleteMemoRelation{RelatedMemoID: ...}` (`store/memo.go:142-147`).
2. **`attachment`** — listed by `FindAttachment{MemoID: ...}` and removed one at a time via `Store.DeleteAttachment` (`store/memo.go:149-157`), which issues `DELETE FROM attachment WHERE id = $1` (`store/db/postgres/attachment.go:212`). This path also deletes the backing blob from local/remote storage (`store/attachment.go:141`) — filesystem, not a table.
3. **`memo`** — the row itself, via `s.driver.DeleteMemo` (`store/memo.go:158`) → `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:239`, `store/db/postgres/memo.go:246`). The `memo` table is hit repeatedly when the memo has comments, since `APIV1Service.DeleteMemo` deletes each comment memo through the same `Store.DeleteMemo` first (`server/router/api/v1/memo_service.go`, "Delete memo comments first" block), recursing through steps 1–3 per child.

**`memo_share`** is removed by the database rather than by code: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, declared in all three dialects (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Include it if "cascade" covers schema-level cascades; exclude it if you mean only Go code. One caveat: SQLite enforces this only when `foreign_keys` pragma is on, so the guarantee isn't uniform across dialects.

Not touched: **`reaction`**. It's the one gap — reactions key off a string `ContentID` with no FK to `memo.id` (`store/reaction.go:7`, and no `REFERENCES memo` in the reaction DDL), and the handler only *reads* reactions to build the webhook payload. Rows for a deleted memo are orphaned.
