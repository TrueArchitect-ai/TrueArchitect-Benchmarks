Two kinds, both in `Store.DeleteMemo` (`store/memo.go:140-159`), in this order:

1. **`memo_relation` rows — in both directions.** Two calls: `DeleteMemoRelation{MemoID: &delete.ID}` then `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:142-147`), so links where the memo is either the source or the target are cleaned up.
2. **`attachment` rows linked to the memo.** It lists them via `FindAttachment{MemoID: &delete.ID}` and deletes each through `Store.DeleteAttachment` (`store/memo.go:149-157`). That path also removes the underlying blob storage — `DeleteAttachmentStorage` at `store/attachment.go:141`, which hard-errors for `LOCAL` files and only warns for remote storage.

Only then does it call `s.driver.DeleteMemo(ctx, delete)` for the memo row (`store/memo.go:158`).

Two things the API handler does around this, which are worth separating from the store layer since the question asks specifically about the store:

- **Comment memos** are deleted first by the handler, not the store: `APIV1Service.DeleteMemo` lists relations of type `MemoRelationComment` pointing at the memo and calls `Store.DeleteMemo` on each child (`server/router/api/v1/memo_service.go`, the "Delete memo comments first" block). Each of those recurses through the same relation+attachment cleanup.
- **Reactions and memo shares are not deleted by the store.** The handler reads reactions only to build the webhook payload. `memo_share` rows are removed by the database instead — `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` at `store/migration/sqlite/LATEST.sql:109`. `reaction` has no such FK (it keys off a string `ContentID`), so reaction rows for a deleted memo are left behind.
