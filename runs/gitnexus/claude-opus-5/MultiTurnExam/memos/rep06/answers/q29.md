**`web/src/connect.ts`; short-lived JWT access token (in-memory) + HTTP-only refresh-token cookie — plus Personal Access Tokens for programmatic clients; `server/auth`**

How it fits together:

**Frontend interceptor** — `authInterceptor` at `web/src/connect.ts:154`, installed on the shared Connect transport (`:184-188`). Per request it calls `getRequestToken()` (`:123`) and sets `Authorization: Bearer <token>`. It manages two tokens:

- **Access token** — short-lived JWT held in memory by `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`). The interceptor does a *preflight* refresh when `isTokenExpired(REQUEST_TOKEN_EXPIRY_BUFFER_MS)` (30 s buffer), which matters for public endpoints like `ListMemos` that would otherwise silently return guest-scoped data.
- **Refresh token** — an HTTP-only cookie, never read by JS; sent because every transport uses `fetch` with `credentials: "include"` (`:56-61`). On a `Code.Unauthenticated` response the interceptor refreshes once, retries with an `X-Retry` marker to prevent loops, and calls `redirectOnAuthFailure()` if that fails. The refresh call goes over a *separate* `refreshTransport` with no interceptors (`:65-72`) to avoid recursion, and concurrent refreshes are deduped by `tokenRefreshManager` (`:30-50`).

**Backend validation** — the `server/auth` package (`server/auth/authenticator.go`, `token.go`, `extract.go`, `context.go`). `Authenticator.resolveBearer` (:149) branches on the token prefix: `AuthenticateByAccessTokenV2` (:41) verifies the JWT signature via `ParseAccessTokenV2`, while `AuthenticateByPAT` (:102) hashes the token and looks it up with `Store.GetUserByPATHash`, checking expiry. `AuthenticateByRefreshToken` (:61) validates the cookie's JWT *and* checks the token record still exists in the DB. This is invoked from the Connect interceptor and gRPC-gateway middleware in `server/router/api/v1/`, with the public-endpoint allowlist in `server/router/api/v1/acl_config.go`.
