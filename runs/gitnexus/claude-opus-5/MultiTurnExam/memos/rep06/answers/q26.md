**memo, memo_relation, attachment, memo_share**

Breakdown by how each is reached, for `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) → `Store.DeleteMemo` (`store/memo.go:140`):

| Table | How |
|---|---|
| `memo_relation` | Explicit cascade — deleted twice, once by `MemoID` and once by `RelatedMemoID` (`store/memo.go:142`, `:145`) |
| `attachment` | Explicit cascade — listed by `MemoID`, deleted one at a time (`store/memo.go:149-157`); each also removes the stored file/blob via `DeleteAttachmentStorage` (`store/attachment.go:141`) |
| `memo` | The row itself — `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`). Also deleted once per comment memo, since the handler recurses into comment relations first (`server/router/api/v1/memo_service.go:567-577`), re-running the whole cascade for each comment |
| `memo_share` | DB-level FK cascade, not application code — `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`) |

Two caveats worth knowing:

- **`memo_share` does not actually cascade on SQLite.** The connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the FK is inert there, and no Go code deletes `memo_share` rows on memo deletion. On Postgres and MySQL the cascade fires. That's a real behavioral divergence between dialects.
- **`reaction` rows are left behind on every dialect.** The handler only *reads* reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); there's no `DeleteReaction` call and no FK on that table.
