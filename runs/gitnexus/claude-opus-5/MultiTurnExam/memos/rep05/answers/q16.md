Deleting a memo goes through `Store.DeleteMemo` (`store/memo.go:140`), which cleans up three things before issuing the memo `DELETE`:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one at a time (`store/memo.go:149-157`). Each `Store.DeleteAttachment` (`store/attachment.go:132`) also removes the **underlying stored blob** first — the local file via `os.Remove`, or the S3 object (`store/attachment.go:202-228`) — before the row.

Only then does it call `s.driver.DeleteMemo` (`store/memo.go:158`).

Above that, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first deletes **comment memos** — every memo joined to this one by a `MemoRelationComment` relation — by recursing into `Store.DeleteMemo` for each (`memo_service.go:567-577`), so each comment's own relations and attachments are cleaned up too.

Two things not handled by that Go path:
- **`memo_share` rows** are removed by the database, via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:107`).
- **`reaction` rows are not deleted.** The handler lists them (`memo_service.go:545`) only to build the webhook payload; reactions key off a string `ContentID` with no FK, and the sole `DeleteReaction` call site is the reaction API (`server/router/api/v1/reaction_service.go:141`). They're left orphaned.
