**memo, memo_relation, attachment, memo_share**

Broken down by how each is reached:

| Table | How |
|---|---|
| `memo_relation` | Explicit cascade code in `Store.DeleteMemo` — deleted twice, once by `MemoID` and once by `RelatedMemoID` (`store/memo.go:142` and `:145`) |
| `attachment` | Explicit cascade code — listed by `FindAttachment{MemoID}` and deleted per-row via `Store.DeleteAttachment` (`store/memo.go:149-157`) |
| `memo` | The row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`); also hit repeatedly for **comment memos**, which the API handler deletes first by recursing into `Store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`) |
| `memo_share` | Database-level `ON DELETE CASCADE` on the `memo_id` FK (`store/migration/sqlite/LATEST.sql:108`, `postgres/LATEST.sql:107`, `mysql/LATEST.sql:108`) — no Go code deletes it on this path |

Two caveats worth flagging:

- **The `memo_share` cascade does not fire on SQLite.** The connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so FK constraints aren't enforced; the cascade only takes effect on Postgres and MySQL. On SQLite those rows are orphaned.
- **`reaction` is not touched.** The handler lists reactions only to build the webhook payload (`memo_service.go:545`); reactions key off a string `ContentID` with no FK, and the only `DeleteReaction` call site is the reaction API (`server/router/api/v1/reaction_service.go:141`).

Outside the database, `Store.DeleteAttachment` also removes each attachment's stored blob — the local file or S3 object (`store/attachment.go:202-228`).
