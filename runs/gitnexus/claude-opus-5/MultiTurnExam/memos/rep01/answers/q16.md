Inside `Store.DeleteMemo` (`store/memo.go:140-159`), before the `memo` row is deleted:

1. **memo_relation rows where this memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where this memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachment rows linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one (`store/memo.go:148-157`); each `Store.DeleteAttachment` also removes the underlying stored blob/file first (`store/attachment.go:132-149`, `deleteAttachmentStorageImpl` at line 202)

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`; e.g. the plain `DELETE FROM memo WHERE id = ?` at `store/db/sqlite/memo.go:237-248`).

Additionally, at the API layer above this, `APIV1Service.DeleteMemo` first deletes **comment memos** — memos linked to this one by a `MemoRelationComment` relation — each through the same `Store.DeleteMemo` path (`server/router/api/v1/memo_service.go:566-577`).

Note what is *not* cleaned up in this path: `reaction` rows are only read (to build the webhook payload, `server/router/api/v1/memo_service.go:544-548`), never deleted, and `memo_share` rows aren't touched either.
