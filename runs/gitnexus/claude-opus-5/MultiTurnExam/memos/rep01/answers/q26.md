**memo, memo_relation, attachment** (plus **memo_share** via a DB-level `ON DELETE CASCADE`, which does *not* fire on SQLite)

Breakdown of `Store.DeleteMemo` (`store/memo.go:140-159`) as invoked by `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):

- **memo_relation** — two explicit deletes, once as `memo_id` and once as `related_memo_id` (`store/memo.go:142`, `:145`)
- **attachment** — rows found by `FindAttachment{MemoID}` deleted individually (`store/memo.go:148-157`); each also removes the underlying blob/local file or S3 object first (`store/attachment.go:132-149`)
- **memo** — the row itself (`store/memo.go:158` → e.g. `store/db/sqlite/memo.go:237`), and additionally one row per **comment memo**, since the API handler recursively deletes memos linked by a `MemoRelationComment` relation before deleting the parent (`server/router/api/v1/memo_service.go:566-577`)
- **memo_share** — no application-level delete exists; it relies on `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Worth flagging: the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade is disabled and `memo_share` rows are orphaned.

Not touched: **reaction** — the handler only reads reactions to build the webhook payload (`server/router/api/v1/memo_service.go:544-548`), and no code or FK deletes them, so reaction rows for a deleted memo are also left orphaned.
