**memo, memo_relation, attachment, memo_share**

Breakdown by how each is reached:

| Table | How |
|---|---|
| `memo_relation` | Explicit cleanup in `Store.DeleteMemo` — rows where the memo is the source and where it's the target (`store/memo.go:142`, `:145`) |
| `attachment` | Explicit cleanup — attachments with `memo_id` are listed and deleted one by one, along with their stored files (`store/memo.go:149-157`, `store/attachment.go:132-149`) |
| `memo` | The row itself (`store/memo.go:158` → e.g. `store/db/sqlite/memo.go:237`); additionally, when called from the API, every comment memo is deleted through the same path first (`server/router/api/v1/memo_service.go:567-577`) |
| `memo_share` | Not touched by Go code in this path; removed by the DB via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`) |

Two caveats worth flagging:

- On SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so that cascade does **not** fire there — `memo_share` rows for a deleted memo are left orphaned on SQLite, while Postgres/MySQL cascade them. (The explicit `DELETE FROM memo_share WHERE memo_id IN …` only exists in the user-deletion path, `store/db/sqlite/user_delete.go:411`.)
- `reaction` rows are **not** deleted — the delete handler only reads them to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`), and the table has no FK to `memo` (it keys off a string `content_id`).
