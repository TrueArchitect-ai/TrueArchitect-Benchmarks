**web/src/connect.ts (`authInterceptor`, `:156`, with token state in `web/src/auth-state.ts`); short-lived JWT access token (Bearer header) + HTTP-only refresh-token cookie — the backend additionally accepts Personal Access Tokens on the same header; server/auth**

How it works:

- **Interceptor** — `authInterceptor` in `web/src/connect.ts:156` is attached to the shared Connect transport (`:188`). Per request it calls `getRequestToken()` (`:124`), sets `Authorization: Bearer <token>`, and on a `Code.Unauthenticated` response refreshes once and retries with an `X-Retry` marker, redirecting to login if the refresh fails (`:163-177`).
- **Tokens** — the access token (a JWT, expiry tracked) is held in memory/`localStorage` and shared across tabs over a `BroadcastChannel` (`web/src/auth-state.ts:1-40`); it's refreshed proactively when within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (`web/src/connect.ts:140`) or on tab focus. The refresh token itself is never read by JS — it rides as an HTTP-only cookie, which is why every request uses `credentials: "include"` (`web/src/connect.ts:57-62`) and refresh goes through a separate interceptor-free transport to avoid recursion (`:65-72`, `refreshAccessToken` at `:89`).
- **Backend validation** — package `server/auth`: `Authenticator.AuthenticateByAccessTokenV2` (`server/auth/authenticator.go:41`), `AuthenticateByRefreshToken` (`:61`, checked against the DB), and `AuthenticateByPAT` (`:102`, prefix + hash lookup), dispatched by `resolveBearer`/`AuthenticateToUser` (`:149`, `:190`). JWT parsing/minting lives in `server/auth/token.go`, header/cookie extraction in `server/auth/extract.go`. It's wired into requests as the gateway auth middleware in `server/router/api/v1/v1.go` and via Connect interceptors.
