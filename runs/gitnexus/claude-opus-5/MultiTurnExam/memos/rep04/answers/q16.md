Inside `Store.DeleteMemo` (`store/memo.go:140-159`), before the `memo` row is deleted, it removes:

- **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
- **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
- **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID}` then deleted one by one (`store/memo.go:149-157`); each `Store.DeleteAttachment` also deletes the underlying stored blob/local file before the row (`store/attachment.go:132-149`)

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`; e.g. the plain `DELETE FROM memo WHERE id = ?` in `store/db/sqlite/memo.go:237`).

The API handler adds one more layer above that: `APIV1Service.DeleteMemo` first finds all comment memos (`memo_relation` of type `COMMENT` pointing at this memo) and deletes each of those memos through the same `Store.DeleteMemo` path — so their relations and attachments go too (`server/router/api/v1/memo_service.go:567-577`).

Not deleted: `reaction` rows are only *read* for the webhook payload (`server/router/api/v1/memo_service.go:545-550`), not removed, and `memo_share` rows aren't touched in this path either.
