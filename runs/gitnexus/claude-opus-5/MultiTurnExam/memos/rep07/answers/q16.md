Inside `Store.DeleteMemo` (`store/memo.go:140-159`), before the `DELETE FROM memo` in the driver:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachments linked to the memo** — listed via `FindAttachment{MemoID:...}` then deleted one by one (`store/memo.go:149-157`)

Then `s.driver.DeleteMemo` removes the memo row itself (`store/db/sqlite/memo.go:237`, plus the mysql/postgres equivalents).

The API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) adds one step ahead of that: it lists `MemoRelationComment` relations pointing at the memo and calls `Store.DeleteMemo` on each **comment memo** first (`:567-577`), so each comment goes through the same relation/attachment cleanup.

Two records that are *not* explicitly deleted: **reactions** (the handler only lists them at `:545` to build the webhook payload — `reaction.content_id` has no FK, `store/migration/sqlite/LATEST.sql:92`), and **memo_share** rows, which are removed by the database via `ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:108`).
