Inside `Store.DeleteMemo` (`store/memo.go:140`), in order, before the `memo` row is removed:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one through `Store.DeleteAttachment` (`store/memo.go:149-157`), which also handles blob/file cleanup

Only then does it call `driver.DeleteMemo` (`store/memo.go:158`), whose dialect implementation is a plain `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237`).

Two things happen outside that store method:

- **Comment memos** are deleted first by the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`): it lists `MemoRelationComment` relations pointing at the memo and calls `Store.DeleteMemo` recursively on each child, so each comment goes through the same relation/attachment cleanup.
- **`memo_share` rows** are removed by the database, not the store — the table declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`).

Note that `reaction` rows are *not* deleted. The handler lists reactions (`server/router/api/v1/memo_service.go:545`) only to build the webhook payload, and `reaction.content_id` is a string with no FK to `memo`, so reactions on a deleted memo are left orphaned.
