Details:

- **`s3presign.Runner`** — the only thing `Server.startBackgroundRunners` (`server/server.go:153`) launches. It calls `RunOnce(ctx)` synchronously at startup (`server/server.go:165`), then runs `Run` in a goroutine under its own cancellable context (lines 167-172). `Run` (`server/runner/s3presign/runner.go:29`) ticks on `runnerInterval = 12h` (line 27) and re-presigns S3 attachment URLs whose last presign is older than 4 days (line 88). Shutdown is via the stored cancel func in `stopBackgroundRunners` (`server/server.go:176`).
- **Cache janitors** — `cleanupLoop` (`store/cache/cache.go:200`) evicts expired entries on a `CleanupInterval` ticker. Three instances start as a side effect of `cache.New` in `store/store.go:51-53` (instance settings, users, user settings). Not registered as "runners", but they are long-lived background goroutines.
- **SSE heartbeat** — `sseHeartbeatInterval` ticker at `server/router/api/v1/sse_handler.go:64`, per open client connection rather than a server-wide job.

**Unused infrastructure:** `server/runner/memopayload` ships a full runner — `NewRunner` (`server/runner/memopayload/runner.go:19`) and `RunOnce` (line 27, a backfill that rebuilds payloads across all memos) — but nothing constructs it. Grep for `memopayload.NewRunner` returns zero hits outside its own file; `server/server.go` never imports the package. Only the standalone helper `RebuildMemoPayload` (line 74) is used, called inline on the request path from `APIV1Service.CreateMemo` (`server/router/api/v1/memo_service.go:108`) and `UpdateMemo` (line 447). So the batch runner is dead scheduling infrastructure.

There is also no cron library in the project — `go.mod` has no `cron`/`gocron`/`quartz` dependency; all scheduling is hand-rolled `time.Ticker`.
