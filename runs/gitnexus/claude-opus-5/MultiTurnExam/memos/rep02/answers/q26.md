**memo, memo_relation, attachment, memo_share**

Breakdown by how each is touched, tracing `Store.DeleteMemo` (`store/memo.go:140`) and the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):

| Table | How |
|---|---|
| `memo_relation` | Explicit cascade code — two deletes, once as source (`MemoID`) and once as target (`RelatedMemoID`) — `store/memo.go:142,145` |
| `attachment` | Explicit cascade code — listed by `FindAttachment{MemoID}` and deleted individually via `Store.DeleteAttachment` — `store/memo.go:149-157` |
| `memo` | The row itself (`DELETE FROM memo WHERE id = ?`, e.g. `store/db/sqlite/memo.go:237`), plus each comment memo, deleted recursively by the handler at `server/router/api/v1/memo_service.go:573-577` — each child re-entering the same relation/attachment cleanup |
| `memo_share` | Database-level FK cascade, not code: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`) |

Two things outside the table list: `Store.DeleteAttachment` also removes the backing blob from local disk or S3 before the row delete (`store/attachment.go:141`, `store/attachment.go:202`) — filesystem/object-storage side effects, not SQL. And `reaction` rows are **not** deleted; `reaction.content_id` is a plain string with no FK to `memo`, and the handler only reads reactions to build the webhook payload (`server/router/api/v1/memo_service.go:545`), so they are left orphaned.
