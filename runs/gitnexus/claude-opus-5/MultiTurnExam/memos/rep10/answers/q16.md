Inside `Store.DeleteMemo` (`store/memo.go:140-158`), before the memo row is deleted:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachments linked to the memo** — listed via `ListAttachments{MemoID}` and deleted one by one (`store/memo.go:149-157`); each `Store.DeleteAttachment` also removes the underlying blob from storage (local file / S3) before deleting the `attachment` row (`store/attachment.go:132-148`, `deleteAttachmentStorageImpl` at `store/attachment.go:202`)

Only then does it call `s.driver.DeleteMemo` for the `memo` row itself (`store/memo.go:158`).

One level up, the API handler `APIV1Service.DeleteMemo` first deletes the memo's **comment memos** — it lists `memo_relation` rows of type comment pointing at this memo and calls `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:567-577`), so each comment goes through the same relation/attachment cleanup.
