**memo, memo_relation, attachment** — plus **memo_share** by DB-level FK cascade on PostgreSQL/MySQL only.

Breakdown:
- **memo_relation** — deleted explicitly in both directions (`MemoID` and `RelatedMemoID`) at `store/memo.go:142` and `:145`.
- **attachment** — every attachment with `memo_id` = this memo is deleted row-by-row (`store/memo.go:149-157`), each also removing the backing blob via `Store.DeleteAttachment` (`store/attachment.go:132`).
- **memo** — the row itself, via `s.driver.DeleteMemo` (`store/memo.go:158`). The API handler additionally deletes all comment memos first (`server/router/api/v1/memo_service.go:567-577`), so those comments' `memo`/`memo_relation`/`attachment` rows go too.
- **memo_share** — declared `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/postgres/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`). Worth flagging: the SQLite driver opens the connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and share rows are left orphaned — there is no explicit `DeleteMemoShare` call in the delete path.

Not touched: `reaction`. Reactions are keyed by `content_id` (the memo resource name, e.g. `memos/abc`) with no FK to `memo`; `DeleteMemo` only *reads* them to build the webhook payload (`server/router/api/v1/memo_service.go:545`), so reaction rows survive the memo's deletion.
