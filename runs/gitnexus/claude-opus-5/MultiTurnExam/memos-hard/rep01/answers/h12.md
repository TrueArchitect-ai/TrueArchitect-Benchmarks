## Why sqlite and not the other two

Three types declare `CreateMemo(ctx, *store.Memo)` against the database — `store/db/sqlite/memo.go:16`, `store/db/mysql/memo.go:16`, `store/db/postgres/memo.go:16` — and the caller, `Store.CreateMemo` (`store/memo.go:109`), reaches them through `s.driver.CreateMemo(ctx, create)` at `store/memo.go:113`, an interface call on `store.Driver`. So the concrete target is fixed at startup, not at the call site. I resolved it by following the value:

1. **Default flag value.** `driver` defaults to `"sqlite"` in two places in the entrypoint — `viper.SetDefault("driver", "sqlite")` (`cmd/memos/main.go:122`) and the persistent flag default (`cmd/memos/main.go:130`), bound together at `:151`. With no flags, env, or config file, `viper.GetString("driver")` yields `"sqlite"`.
2. **Into the profile.** That value lands in `Profile.Driver` (`cmd/memos/main.go:43`). `Profile.Validate` confirms the default path is sqlite-aware: it synthesizes a DSN of `<data>/memos_prod.db` only when `p.Driver == "sqlite" && p.DSN == ""` (`internal/profile/profile.go:110-118`).
3. **Through the factory.** `db.NewDBDriver(instanceProfile)` (`cmd/memos/main.go:57`) switches on `profile.Driver` and returns `sqlite.NewDB(profile)` for `"sqlite"` (`store/db/db.go:18-27`, sqlite branch at `:20`). That's the only place any driver is constructed — the MySQL and Postgres constructors have no other callers.
4. **Bound into the store.** The returned `store.Driver` is handed to `store.New(dbDriver, instanceProfile)` (`cmd/memos/main.go:64`) and stored as the `driver` field that `store/memo.go:113` dispatches on.

## The full save path

`APIV1Service.CreateMemo` (`server/router/api/v1/memo_service.go:70`) → `Store.CreateMemo` (`store/memo.go:109`, which validates the UID against `base.UIDMatcher` first) → `(*sqlite.DB).CreateMemo` (`store/db/sqlite/memo.go:16`). The insert always writes `uid`, `creator_id`, `content`, `visibility`, `payload` (payload marshaled as protojson, defaulting to `"{}"` — `:17-27`), conditionally appends `created_ts`/`updated_ts` when non-zero (`:30-39`), and uses SQLite's `RETURNING` clause to populate the generated `id`, timestamps, and `row_status` back onto the struct via `QueryRowContext(...).Scan(...)` (`:41-49`).

One caveat on "default installation": this holds when nothing overrides the flag. Viper also reads env/config, so `--driver` or a `MEMOS_DRIVER` setting would select `store/db/mysql/memo.go:16` or `store/db/postgres/memo.go:16` instead — same call site, different concrete method.
