**Premise correction: there is no Redis in this repository.** A case-insensitive search for "redis" across the entire tree (excluding `node_modules`/`.git`) returns zero hits — no Go source, no `go.mod`/`go.sum` dependency, no config or compose file. There is no external cache server to configure, and no connection string, host, port, or DSN for one.

**Actual mechanism: a process-local in-memory cache.** `store/cache/cache.go` implements `Cache` as a `sync.Map` with per-item expiry and an atomic item counter (`store/cache/cache.go:66-73`). It's constructed with a plain `Config` struct — `DefaultTTL`, `CleanupInterval`, `MaxItems`, `OnEviction` (`store/cache/cache.go:41-54`) — not connection parameters. A background goroutine started in `New` (`store/cache/cache.go:83`) sweeps expired entries on a ticker (`cleanupLoop`, `:200-215`), and `Close` stops it (`:187`).

**Configuration site:** `store.New` (`store/store.go:36`) hardcodes one `cache.Config` and hands the same values to three separate caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:38-52`). The values are literals in code; nothing reads them from flags, env, or a config file:

- `DefaultTTL: 10 * time.Minute`
- `CleanupInterval: 5 * time.Minute`
- `MaxItems: 1000`

(`store/cache/cache.go:57-64` defines an identical `DefaultConfig()`, but `store.New` doesn't call it — it re-declares the same numbers inline.)

**TTL for user entries: 10 minutes.** Every write to `userCache` uses the plain `Set` — `store/user.go:98`, `:122`, `:132`, `:143`, `:167` — and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). `SetWithTTL` never receives a custom duration anywhere in the codebase, so users expire 10 minutes after their last write. Expiry is checked lazily on read (`Get` deletes and misses if `time.Now().After(itm.expiration)`, `store/cache/cache.go:135-144`) as well as by the 5-minute sweeper.

Two behaviors worth knowing, since they affect staleness more than the TTL does: the cache is keyed by user ID only (`userCacheKey`), so `Store.GetUser` short-circuits solely for `find.ID` lookups — a lookup by username or email always hits the database (`store/user.go:148-157`). And entries are invalidated eagerly on delete via `s.userCache.Delete` (`store/user_delete.go:40`), so the 10-minute window is an upper bound on staleness for untouched rows, not a fixed delay.

Because the cache lives in-process, it is not shared across replicas — each server instance keeps its own copy with its own 10-minute clock.
