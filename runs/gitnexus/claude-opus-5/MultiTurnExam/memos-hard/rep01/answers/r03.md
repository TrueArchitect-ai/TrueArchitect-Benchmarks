**Premise correction: no nightly database-cleanup job exists, and the cron scheduler is never started by the server — so there is no scheduled time to report.**

Two separate corrections are needed here:

**1. The scheduler is dead code in this build.** `internal/scheduler` is a complete, self-contained cron implementation — `Scheduler` with `New`/`Register`/`Start`/`Stop` (`internal/scheduler/scheduler.go`), a 5- and 6-field cron expression parser (`internal/scheduler/parser.go`), jobs (`internal/scheduler/job.go`), and middleware (`internal/scheduler/middleware.go`). But grepping for imports of `github.com/usememos/memos/internal/scheduler` across the whole repo returns only two hits, both inside the package's own tests: `internal/scheduler/example_test.go:10` and `internal/scheduler/integration_test.go:13`. Nothing in `cmd/memos/main.go` or `server/` ever constructs it, so no job of any kind is registered or fired at runtime.

**2. The "2 AM daily cleanup" is documentation, not configuration.** The likely source of the premise is the package doc example at `internal/scheduler/doc.go:15-21`:

```go
//	s.Register(&scheduler.Job{
//		Name:     "daily-cleanup",
//		Schedule: "0 2 * * *", // 2 AM daily
```

That's an illustrative snippet in a comment block showing the API's usage — `"0 2 * * *"` is a sample expression, not a schedule this server runs. The same example shape appears in `internal/scheduler/README.md`.

**What actually runs on a timer.** The server's only background scheduling is the plain ticker loop in the S3 presign runner: `runnerInterval = time.Hour * 12` (`server/runner/s3presign/runner.go:27`), driven by `Run` (`:29-41`) and started from `startBackgroundRunners` (`server/server.go:162-171`) after one synchronous `RunOnce` at boot (`server/server.go:163`). It's interval-based from process start, not wall-clock-anchored — there's no "2 AM" or any fixed time of day — and it refreshes presigned attachment URLs rather than cleaning the database.

The nearest thing to periodic cleanup is the in-memory cache sweeper: a `CleanupInterval` of 5 minutes per cache (`store/store.go:42`), evicting expired entries via `cleanupLoop` (`store/cache/cache.go:200-215`). That touches process memory only, never the database.

Database-side cleanup in this codebase is entirely event-driven rather than scheduled — for example, deleting a user cascades through reactions, attachments, inboxes, and memos inside one transaction (`store/db/postgres/user_delete.go:92-127`), and S3 objects for deleted attachments are removed on the delete path (`store/attachment.go:171`).
