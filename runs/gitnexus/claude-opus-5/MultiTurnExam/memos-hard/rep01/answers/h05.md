**Explicit Go code — two targeted `DELETE FROM reaction` statements inside the per-driver `DeleteUser` transaction. There is no database-level rule for reactions.**

## What I checked

**1. The deletion path.** `store.DeleteUser` (`store/user.go:170`) just delegates to `s.driver.DeleteUser` then evicts caches. The real work is per-driver, and all three implementations are structurally identical: `store/db/postgres/user_delete.go:29`, `store/db/sqlite/user_delete.go`, `store/db/mysql/user_delete.go`. Everything runs in one `BeginTx`/`Commit` transaction (`postgres/user_delete.go:30-53`).

**2. The reaction deletes.** `deleteUserTargetsTx` (`postgres/user_delete.go:92`) calls two separate reaction cleanups, and the pair covers both directions of the relationship:

- `deleteReactionsByContentIDsTx` (`postgres/user_delete.go:96`, defined at `:380`) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`:14`). The content IDs are `"memos/" + uid` for every memo in the user's memo tree (`memoContentIDsFromRefs`, `:512-518`), where the tree is a recursive CTE that also pulls in other users' comment memos hanging off the deleted user's memos (`listDeleteUserMemoTreeRecursive`, `:133-147`). This removes *everyone's* reactions on the deleted user's content.
- `deleteReactionsByCreatorTx` (`postgres/user_delete.go:102`, defined at `:400`) — `DELETE FROM reaction WHERE creator_id = $1`. This removes the deleted user's own reactions on content that survives.

Both exist in all three drivers: `store/db/mysql/user_delete.go:417`/`:437`, `store/db/sqlite/user_delete.go:380`/`:400`, called at `:96`/`:102` in each.

Ruling out a database-level rule.** The `reaction` table is declared with no foreign keys at all in any dialect — `store/migration/postgres/LATEST.sql:91-98`, `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`. Its `creator_id` and `content_id` are plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Grepping the whole schema for `REFERENCES|CASCADE|FOREIGN KEY` returns exactly one hit per dialect, and it's `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`postgres/LATEST.sql:108`, `sqlite/LATEST.sql:109`, `mysql/LATEST.sql:108`) — not reactions.

Two details reinforce that the Go code is load-bearing rather than belt-and-braces: SQLite opens its connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so even declared FKs wouldn't cascade there; and the ordering in `deleteUserTargetsTx` deliberately deletes reactions (`:96`, `:102`) *before* the memo rows (`:120`) and the user row (`:123`), which is what you'd need if nothing downstream cleans up.
