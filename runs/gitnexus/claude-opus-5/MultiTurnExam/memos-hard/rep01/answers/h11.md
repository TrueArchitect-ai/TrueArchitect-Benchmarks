## Method

The data layer is the `store` package (entity structs declared in `store/user.go:29`, `store/memo.go:35`, `store/attachment.go:16`, `store/reaction.go:7`, `store/inbox.go:24`, `store/memo_relation.go:16`, `store/memo_share.go:6`, etc.). I counted distinct Go packages *outside* `store/...` — so excluding the driver packages `store/db/{sqlite,mysql,postgres}` and `store/test`, which are themselves part of that layer — that name each type as `store.<Type>`.

**`store.User` — 7 packages:**
- `server/router/api/v1` (19 files)
- `server/router/api/v1/test` (3)
- `server/router/rss` (2)
- `server/router/fileserver` (2)
- `server/auth` (2)
- `server/router/frontend` (1)
- `server/notification` (1)

**`store.Memo` — 6 packages:**
- `server/router/api/v1` (13 files)
- `server/router/api/v1/test` (3)
- `server/router/rss` (2)
- `server/runner/memopayload` (1)
- `server/router/frontend` (1)
- `server/notification` (1)

The two differ by exactly one package: `store.User` additionally reaches `server/auth` and `server/router/fileserver`, while `store.Memo` additionally reaches `server/runner/memopayload`. That asymmetry is structural — authentication resolves a principal (`server/auth/authenticator.go:190` returns `*store.User`), and the avatar handler needs a user row (`server/router/fileserver/fileserver.go:715`), neither of which touches memos.

**Rest of the field, same measure:** `store.Attachment` 4 packages (`server/router/api/v1`, `.../v1/test`, `server/router/fileserver`, `server/router/rss`); `store.Inbox`, `store.MemoRelation`, `store.MemoShare` 3 each; `store.Reaction` and `store.UserIdentity` 2 each; `store.UserSetting`, `store.IdentityProvider`, `store.InstanceSetting` 1 each.

Two caveats on precision. If you drop the test package `server/router/api/v1/test`, the counts become 6 and 5 — the ordering is unchanged. And the gap between first and second is a single package, so this is a narrow lead rather than a decisive one; by raw file count the separation is wider (30 vs 21).
