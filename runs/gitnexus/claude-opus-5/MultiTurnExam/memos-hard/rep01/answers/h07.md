The browser hits `GET /file/users/{username}/avatar` — that URL is minted server-side in the user converter (`server/router/api/v1/user_service_converters.go:36`, `fmt.Sprintf("/file/%s/avatar", userpb.Name)` where `Name` is `users/{username}`), used whenever the stored `avatar_url` is a base64 data URI rather than an external link.

**On the way back out**, the handler decodes and validates before writing bytes: `parseDataURI` splits the stored `data:<mime>;base64,<payload>` value via `dataURIRegex` (`fileserver.go:737`, regex at `:98`), the MIME type is checked against `avatarAllowedTypes` — PNG/JPEG/GIF/WebP/HEIC/HEIF (`fileserver.go:201`, map at `:75-83`) — then `setSecurityHeaders` adds `nosniff`, `X-Frame-Options: DENY`, and a restrictive CSP (`fileserver.go:205`, `:758`), and `c.Blob` writes the image with `Cache-Control: public, max-age=3600` (`fileserver.go:207-209`).

Worth noting: the avatar bytes live in the `user` row itself as a data URI, so there's no attachment/S3/local-file path here — the "stored data" is the `user.avatar_url` column, and none of the storage-backend branches used by `serveAttachmentFile` are involved.
