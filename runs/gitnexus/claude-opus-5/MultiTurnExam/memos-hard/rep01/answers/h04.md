Evidence, three independent checks:

1. **Constructor call sites.** Grepping `NewDB` across all `.go` files (including tests) yields one MySQL call: `store/db/db.go:22`, inside `NewDBDriver`'s `case "mysql":` branch (`store/db/db.go:14-27`). The other `NewDB` hits are the sibling definitions (`store/db/sqlite/sqlite.go:24`, `store/db/postgres/postgres.go:21`, `store/db/mysql/mysql.go:20`) and three *sqlite*-only direct calls in tests (`store/demo_seed_test.go:24`, `store/deployment_config_test.go:416`) — none for MySQL.

2. **Package import graph.** `github.com/usememos/memos/store/db/mysql` is imported by exactly one file in the repo: `store/db/db.go:8`. Since no other package imports it, no other package can call `mysql.NewDB` or build its exported `DB` type (`store/db/mysql/mysql.go:14`) — struct-literal construction like `&mysql.DB{...}` is likewise impossible from outside, and the struct's fields are all unexported anyway.

3. **How MySQL is reached in tests.** The test helpers that exercise MySQL go through the factory rather than around it: `store/test/store.go:28` and `:50` call `db.NewDBDriver(profile)`, with the driver chosen by profile string (`store/test/store.go:88`, driver list at `store/test/main_test.go:25`).
