## How they converge

The four `Dispatch*Webhook` entry points (`memo_service_webhooks.go:15`, `:20`, `:25`, `:30`) collapse into two bodies: the created/updated/deleted trio all delegate to `dispatchMemoRelatedWebhook` (`memo_service_webhooks.go:48`), while the comment case has its own loop (`:30-46`) because it notifies the *parent* memo's owner rather than the actor. Both bodies do the same thing: load the target user's webhooks via `s.Store.GetUserWebhooks` (`:31`, `:57`), then per hook set `payload.URL = hook.Url` and `payload.SigningSecret = hook.SigningSecret` — this is where the user-configured URL enters — and call `webhook.PostAsync(payload)` (`memo_service_webhooks.go:43` and `:71`).

`webhook.PostAsync` (`internal/webhook/webhook.go:184`) is the single narrow waist: it's the only symbol both bodies share, and the only caller of the outbound machinery from the API layer. It enqueues onto a 128-slot buffered channel, dropping with a warning if full (`:189-195`). Four worker goroutines started in `init` (`internal/webhook/webhook.go:42-55`) drain that queue and invoke `Post` (`internal/webhook/webhook.go:120`), which is where the HTTP request is actually built, HMAC-signed, and sent via `safeClient.Do` (`:152`).

So if you want the last function on the request path before the socket, that's `Post`; if you want the point where all six handler paths merge, that's `PostAsync`. Note the queue boundary means webhook failures never surface to the RPC caller — every handler already logs-and-continues on dispatch error (e.g. `memo_service.go:158`, `memo_service_comments.go:120`).
