The browser hits `/file/users/{username}/avatar`, which the API hands out in place of raw base64 (`server/router/api/v1/user_service_converters.go:36`). Hops:

```
RegisterRoutes (route: GET /file/users/:identifier/avatar) — server/router/fileserver/fileserver.go:124
serveUserAvatar                                            — server/router/fileserver/fileserver.go:168
FileServerService.getUserByUsername                        — server/router/fileserver/fileserver.go:715
Store.GetUser                                              — store/user.go:148
Store.ListUsers                                            — store/user.go:136
Driver.ListUsers (interface dispatch)                      — store/driver.go
DB.ListUsers (SELECT … avatar_url … FROM user WHERE username = ?) — store/db/sqlite/user.go:88
```

Notes on each hop:

- **`serveUserAvatar`** (`fileserver.go:168`) — gates anonymous access first: if `s.Profile.AllowAnonymous()` is false it requires a session/access token/PAT via `getCurrentUser` and returns 401 otherwise (`:173-181`). Beyond that gate there is no per-user authorization, so on a public instance any viewer can fetch any user's avatar by username.
- **`getUserByUsername`** (`fileserver.go:715`) — a one-line wrapper building `&store.FindUser{Username: &identifier}`. The path param is treated as a username, not an ID.
- **`Store.GetUser`** (`store/user.go:148`) — the `userCache` fast path only applies when `find.ID` is set, so this username lookup always falls through to the DB.
- **`Store.ListUsers`** (`store/user.go:136`) — delegates to `s.driver.ListUsers` and populates `userCache` keyed by ID.
- **Driver** — `store.Driver` interface (`store/driver.go`), resolved to one of the three backends by `NewDBDriver` (`store/db/db.go`). SQLite shown; equivalents are `store/db/postgres/user.go` and `store/db/mysql/user.go`.
- **`DB.ListUsers`** (`store/db/sqlite/user.go:88`) — appends `username = ?` as a bound parameter (`:128-130`) and selects `avatar_url` among the columns (`:159`), scanned into `user.AvatarURL` (`:189`).

Back in the handler, the stored `AvatarURL` is a data URI, not a file path: `parseDataURI` (`fileserver.go:737`) regex-splits it into MIME type and decoded bytes, the type is checked against `avatarAllowedTypes` (`fileserver.go:75`, enforced at `:201`), then security headers plus `Cache-Control` are set and the bytes are written with `c.Blob` (`:205-209`). So the image content lives in the `user.avatar_url` column itself — there is no attachment or object-storage hop.
