Two distinct enforcement *styles* run here, and they aren't equivalent:

- **Post-fetch rejection** — load the memo, then deny: `PUBLIC` passes unless anonymous access is off; `PRIVATE` requires creator or super-user. That's `checkMemoReadAccess` (`memo_service.go:55-63`), the reaction/attachment/comment gates, and the file server's `checkAttachmentPermission` (`fileserver.go:677-699`, which uses `user.Role != store.RoleAdmin` rather than the `isSuperUser` helper the API layer uses).
- **Pre-query narrowing** — never fetch what the caller can't see, by constraining `FindMemo.VisibilityList`: `ListMemos` (`memo_service.go:219-225`, public-only anonymous, public+protected authenticated), both stats RPCs, and the two surfaces hardcoded to `[]store.Visibility{store.Public}` — RSS (`rss.go:90,141`) and the sitemap (`frontend.go:150`).

The SSE hub is a third shape: it filters at *delivery* time rather than at query or fetch time, evaluating each subscriber against the event's visibility (`sse_hub.go:134`), and fails closed on an unrecognized visibility value (`:141-142`).

The notification check is the only one that isn't a read gate — `canViewerAccessMemo` (`server/notification/email.go:313`) suppresses outbound email about a memo the recipient couldn't view. Note it's duplicated rather than shared: `user_service_notifications.go:309-312` reimplements the same private/protected logic independently.
