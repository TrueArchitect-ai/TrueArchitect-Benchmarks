**Premise correction: there is no Redis anywhere in this repository.** A case-insensitive search for `redis` across all Go sources, `go.mod`/`go.sum`, and YAML/JSON config returns zero hits — no client library, no connection string, no config key. There is nothing to point at, so the question's premise doesn't hold.

**Actual mechanism: a process-local, in-memory cache.**

- **Implementation** — `store/cache/cache.go`. `Cache` (`:67`) is a `sync.Map` guarded by an atomic item counter, with per-entry expiration timestamps (`item`, `:35`) and a background `cleanupLoop` goroutine started in `New` (`:83`). It's purely in-process: no network client, no serialization, values stored as `any` and type-asserted on read. Nothing is shared between server instances, so a multi-replica deployment gets independent caches with no invalidation between them.

- **Where it's "configured"** — in code, not in any config file: `store.New` builds a literal `cache.Config` at `store/store.go:40-45` and passes it to three separate `cache.New` calls at `:51-53` (`instanceSettingCache`, `userCache`, `userSettingCache`, declared `:27-29`). The values are `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil` — identical to `cache.DefaultConfig()` (`store/cache/cache.go:57`), just re-specified inline. No flag, env var, or profile field feeds any of these.

**TTL for user entries: 10 minutes.** Every user write goes through `s.userCache.Set(...)` (`store/user.go:98, 122, 132, 143, 167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:94`). `SetWithTTL` is never called directly anywhere in `store/` or `server/`, so users get no special TTL — they inherit the shared 10-minute default, same as instance settings and user settings.

Two related details worth knowing: entries can also be dropped early if the 1000-item cap trips `cleanupOldest` (`store/cache/cache.go:117`), and user deletion explicitly invalidates via `s.userCache.Delete` (`store/user_delete.go:40`). Also note the read path only consults the cache when looking up by ID — `Store.GetUser` checks `userCache` solely under `if find.ID != nil` (`store/user.go:149-156`), so username-based lookups always hit the database.
