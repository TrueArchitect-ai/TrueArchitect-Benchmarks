Notes on the shape of this:

- `checkMemoReadAccess` (`server/router/api/v1/memo_service.go:39`) is the closest thing to a canonical gate — it handles archived-memo hiding, requires auth for anything non-`Public`, and denies `Private` to non-creators. But it has only three callers (`memo_service.go:356`, `:367`, `memo_service_comments.go:148`); the other API surfaces re-implement the same predicate inline rather than calling it, which is why the logic appears duplicated across `reaction_service.go`, `attachment_service.go`, and `memo_attachment_service.go`.
- The two anonymous-facing HTTP surfaces (RSS, frontend prerender) enforce by *restricting the query* to `store.Public` rather than by checking after load — a different mechanism with the same effect.
- The fileserver path is the only one with a **share-token bypass**: a valid, unexpired `share_token` matching that memo grants access to a private/protected memo's attachments (`server/router/fileserver/fileserver.go:684-690`). The corresponding API entry point is `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:151`), documented "No authentication required" — it deliberately performs no visibility check, relying on token possession instead.
- `isSuperUser(user)` / `store.RoleAdmin` is an escape hatch present in most of the per-memo gates but notably absent from `checkMemoReadAccess` itself (`memo_service.go:63` checks only creator identity).
