**Explicit Go code — two separate `DELETE FROM reaction` statements inside the delete-user transaction, per dialect. There is no database-level rule; the `reaction` table has no foreign keys at all.**

What I checked:

**1. The delete-user transaction.** `store.DeleteUser` (`store/user.go:171`) delegates to the driver's `DeleteUser`, e.g. `store/db/sqlite/user_delete.go:29`, which opens a tx, collects targets, and calls `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92`). That function issues, in order, two reaction deletions:

- `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380`) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`deleteUserBatchSize`, line 14). This removes *other people's* reactions on the deleted user's memos, using the memo UIDs gathered by the recursive memo-tree walk (`listDeleteUserMemoTree`, line 129).
- `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400`) — `DELETE FROM reaction WHERE creator_id = ?`. This removes the deleted user's own reactions, including those left on *other* users' memos.

So the answer to the literal question ("their emoji reactions") is the second one, at `store/db/sqlite/user_delete.go:400-403`.

**2. All three dialects do the same thing**, at essentially identical line numbers:

| dialect | by content_id | by creator_id |
|---|---|---|
| sqlite | `store/db/sqlite/user_delete.go:383` | `store/db/sqlite/user_delete.go:401` |
| postgres | `store/db/postgres/user_delete.go:383` | `store/db/postgres/user_delete.go:401` |
| mysql | `store/db/mysql/user_delete.go:420` | `store/db/mysql/user_delete.go:438` |

**3. No DB-level cascade exists to fall back on.** The `reaction` DDL declares only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`, no `ON DELETE CASCADE` — in all three schemas: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (same in the original `0.20/00__reaction.sql` migrations). By contrast `memo_share` right below it *does* carry `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`), which confirms the omission on `reaction` is structural rather than an artifact of how the file is written.

Also worth noting: even where FKs are declared, SQLite opens with them disabled — `_pragma=foreign_keys(0)` in the DSN at `store/db/sqlite/sqlite.go:53` — so the explicit Go deletes are the only mechanism in play regardless.

Note that `reaction.content_id` is a memo **UID string**, not a numeric id, which is why the code passes `memoContentIDsFromRefs(targets.memos)` (`store/db/sqlite/user_delete.go:94`) rather than the memo ID list — a plain FK on that column wouldn't have been straightforward anyway.
