**Premise correction: there is no Redis in this repository.** Grepping every file (excluding `node_modules` and the pnpm lockfile) for `redis` or `memcache` returns zero hits — nothing in `go.mod`, `go.sum`, Go sources, config, or docs. The cache layer is a hand-rolled **in-process, in-memory** cache; there is no external cache server, no connection string, and nothing to configure at deploy time.

**Actual mechanism.**

The implementation is `store/cache/cache.go` — a `sync.Map`-style store of `item{value, expiration, size}` (`store/cache/cache.go:35-38`) behind an `Interface` (`:11-31`), with a background cleanup goroutine. It's configured by a plain struct, not a URL:

```go
Config{ DefaultTTL, CleanupInterval, MaxItems, OnEviction }   // store/cache/cache.go:42-54
```

**Where it's "configured"** — in Go code at construction, `store.New` (`store/store.go:38-45`):

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That one config value is shared by all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). It's hardcoded; no flag, env var, or profile field feeds it. (`cache.DefaultConfig()` at `store/cache/cache.go:57` declares the same values but isn't what `store.New` calls.)

**TTL for user entries: 10 minutes.** Every write to `userCache` uses `Set` rather than `SetWithTTL` — `store/user.go:98`, `:122`, `:132`, `:143`, `:167` — and `Set` delegates with the default: `c.SetWithTTL(ctx, key, value, c.config.DefaultTTL)` (`store/cache/cache.go:93-95`), stamping `expiration: time.Now().Add(ttl)` (`:112`). So each entry expires 10 minutes after it was last written; it's an absolute expiry, not a sliding one — reads (`:135`) only check expiry, they don't extend it.

Three other details that matter more than a Redis config would:

- **Eviction pressure**: `MaxItems: 1000` per cache, so a busy instance can evict user entries well before the TTL (the eviction routine at `store/cache/cache.go:268-292` samples candidates and drops the newest-expiring among them).
- **Explicit invalidation**: user deletion purges the entry directly — `s.userCache.Delete(ctx, userCacheKey(userID))` (`store/user_delete.go:40`).
- **Read path asymmetry**: `Store.GetUser` only consults the cache when looking up by ID (`store/user.go:149-156`); a username lookup always hits the database, then populates the cache keyed by ID (`:167`). This is why the avatar path in h07 doesn't benefit from the cache.

Because the cache is per-process, a multi-replica deployment gets no shared invalidation — each instance holds its own copy for up to 10 minutes.
