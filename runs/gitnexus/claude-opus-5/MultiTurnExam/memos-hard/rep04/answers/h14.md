**Computation site: `memopayload.RebuildMemoPayload` — `server/runner/memopayload/runner.go:74`, delegating to `markdown.Service.ExtractAll` — `internal/markdown/markdown.go:356`; Triggers: `CreateMemo` and the `content` field of `UpdateMemo`; Extracted: `Tags` plus five `Property` fields — `Title`, `HasLink`, `HasCode`, `HasTaskList`, `HasIncompleteTasks`.**

**Where it's computed.** `RebuildMemoPayload` (`server/runner/memopayload/runner.go:74-88`) initializes `memo.Payload` if nil, calls `markdownService.ExtractAll([]byte(memo.Content))`, then assigns exactly two fields — `memo.Payload.Tags = data.Tags` (`:85`) and `memo.Payload.Property = data.Property` (`:86`). The actual work happens in `(*service).ExtractAll` (`internal/markdown/markdown.go:356`), which parses the content once and does a **single** `gast.Walk` over the goldmark AST, collecting everything in one pass rather than re-parsing per property.

**Triggers — two, both in the memo service:**

1. `CreateMemo` — `server/router/api/v1/memo_service.go:107`, after the content-length check and before `s.Store.CreateMemo`.
2. `UpdateMemo` — `server/router/api/v1/memo_service.go:447`, only inside the `path == "content"` branch of the field-mask loop; the recomputed payload is then written via `update.Payload = memo.Payload` (`:451`).

Note what does *not* trigger it: `SetMemoAttachments` and `SetMemoRelations` fire memo-updated webhooks (h06) but never touch content, so no recomputation. And `memopayload.Runner.RunOnce` (`server/runner/memopayload/runner.go:27`), which would rebuild every memo in batches, is dead code with no callers (h08) — so there's no backfill path; payloads are only refreshed when a memo is created or its content edited.

**What's extracted** (all in the one walk, `internal/markdown/markdown.go:370-411`):

| output | source | line |
|---|---|---|
| `Tags []string` | `MemoTagNode`s, deduped case-preserving via `uniquePreserveCase` | `:377`, `:418` |
| `Property.Title` | text of the first block-level child **only if** it's an H1 | `:383-389` |
| `Property.HasLink` | any `gast.KindLink` | `:393` |
| `Property.HasCode` | `KindCodeBlock`, `KindFencedCodeBlock`, or `KindCodeSpan` | `:396` |
| `Property.HasTaskList` | any `east.KindTaskCheckBox` | `:399` |
| `Property.HasIncompleteTasks` | a task checkbox with `!IsChecked` | `:401-403` |

The `Property` struct is `storepb.MemoPayload_Property` (`proto/gen/store/memo.pb.go:85-95`). `ExtractAll` also collects `Mentions` (`:380`), but `RebuildMemoPayload` discards them — they're returned in `ExtractedData` and used elsewhere, not persisted in the payload.

**Where the derived data is consumed for lists/previews:** `memo.Payload.Tags` surfaces as `memoMessage.Tags` in the API converter (`server/router/api/v1/memo_service_converter.go:48`) and drives tag counts in user stats (`server/router/api/v1/user_service_stats.go:138`, `:254`).

One distinction worth drawing: the memo **snippet** shown in lists is *not* part of this persisted payload. It's computed on the fly per response by `getMemoContentSnippet` → `MarkdownService.GenerateSnippet(content, 64)` (`server/router/api/v1/memo_service_webhooks.go:83`), called from `memo_service_converter.go:76` and `memo_relation_service.go:154`/`:162`. So snippets are derived-but-ephemeral, while tags and properties are derived-and-stored.
