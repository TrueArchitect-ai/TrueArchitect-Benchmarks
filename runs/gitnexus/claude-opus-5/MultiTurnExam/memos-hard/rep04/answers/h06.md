**Handlers: `CreateMemo`, `UpdateMemo`, `DeleteMemo`, `CreateMemoComment`, `SetMemoAttachments`, `SetMemoRelations` (six total); convergence function — `webhook.PostAsync`, `internal/webhook/webhook.go:184`** (which hands off to `webhook.Post`, `internal/webhook/webhook.go:120`, where the request is actually issued).

The six paths, each from the `APIV1Service` method down to the dispatch:

| RPC handler | path | reaches webhook via |
|---|---|---|
| `CreateMemo` — `server/router/api/v1/memo_service.go:70` | `:157` | `DispatchMemoCreatedWebhook` |
| `UpdateMemo` — `server/router/api/v1/memo_service.go:401` | `:513` → `dispatchMemoUpdatedSideEffects` | `DispatchMemoUpdatedWebhook` |
| `DeleteMemo` — `server/router/api/v1/memo_service.go:518` | `:562` | `DispatchMemoDeletedWebhook` |
| `CreateMemoComment` — `server/router/api/v1/memo_service_comments.go:20` | `:119` | `DispatchMemoCommentCreatedWebhook` |
| `SetMemoAttachments` — `server/router/api/v1/memo_attachment_service.go:16` | `:48` → `dispatchMemoUpdatedSideEffects` | `DispatchMemoUpdatedWebhook` |
| `SetMemoRelations` — `server/router/api/v1/memo_relation_service.go:16` | `:48` → `dispatchMemoUpdatedSideEffects` | `DispatchMemoUpdatedWebhook` |

The last three of those share an intermediate hop, `dispatchMemoUpdatedSideEffects` (`server/router/api/v1/memo_update_helpers.go:66`), which calls `DispatchMemoUpdatedWebhook` at line 67 — so `SetMemoAttachments` and `SetMemoRelations` fire memo-updated webhooks even though they aren't nominally "update memo" RPCs. All six are also exposed as Connect RPCs by thin wrappers in `server/router/api/v1/connect_services.go` (lines 306, 330, 338, 346, 362, 378) that delegate to the `APIV1Service` methods above.

**Convergence.** The four `Dispatch*Webhook` functions live in `server/router/api/v1/memo_service_webhooks.go`; three of them route through `dispatchMemoRelatedWebhook` (`:48`) while the comment one is standalone (`:30`). Both look up the target user's registered hooks via `s.Store.GetUserWebhooks` and then call `webhook.PostAsync` — `memo_service_webhooks.go:43` and `:71`, the only two call sites in the repo. `PostAsync` (`internal/webhook/webhook.go:184`) is therefore the single funnel: every path narrows to it before anything leaves the process.

It enqueues onto a 128-slot buffered channel, dropping with a warning if full; four worker goroutines started in `init` (`internal/webhook/webhook.go:42-55`) drain it and call `webhook.Post` (`:120`), which performs the actual `POST` to the user-configured URL at `:152`. If you read "convergence before delivery" as the last function that itself performs the delivery, that's `Post`; `PostAsync` is where the six handler paths merge.

The URL is user-supplied (stored per-user, validated at registration by `webhook.ValidateURL` in `server/router/api/v1/user_service_webhooks.go:74`), and the outbound dial is SSRF-guarded by `safeDialContext` (`internal/webhook/webhook.go:59`) as covered in h02.
