Per-hop notes:

- **`serveUserAvatar`** (`fileserver.go:168`) first applies an access gate: when `s.Profile.AllowAnonymous()` is false, it requires a resolvable viewer via `s.getCurrentUser` and 401s otherwise (`fileserver.go:173-180`). It then takes `:identifier` from the path (`fileserver.go:183`).
- **`getUserByUsername`** (`fileserver.go:715`) is a one-line adapter building `&store.FindUser{Username: &identifier}` — note the route param is treated as a *username*, not a UID.
- **`Store.GetUser`** (`store/user.go:148`) consults `userCache` only when the find is by ID; a username lookup always falls through to `ListUsers` and takes `list[0]`, then populates the cache (`store/user.go:149-170`).
- **`Store.ListUsers`** (`store/user.go:135`) delegates straight to `s.driver`, warming the cache for each row.
- **Driver `ListUsers`** builds the `WHERE username = ?` predicate (`store/db/sqlite/user.go:127-129`) and scans `avatar_url` into `user.AvatarURL` (`store/db/sqlite/user.go:158`, `:189`).

Back in the handler, the stored value is a data URI: `parseDataURI` (`fileserver.go:737`) regex-splits and base64-decodes it, the MIME type is checked against `avatarAllowedTypes` (`fileserver.go:75`, enforced at `:201`), security headers plus `Cache-Control` are set, and the bytes are written with `c.Blob` (`fileserver.go:207`). So the image never touches the filesystem or S3 — it lives inline in the `user.avatar_url` column.

There is also a gRPC `UserService/GetUserAvatar` method (allow-listed for anonymous access at `server/router/api/v1/acl_config.go:25`), but the `<img src>` the web client renders points at the `/file/...` route above.
