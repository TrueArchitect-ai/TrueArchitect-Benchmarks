**Premise correction: there is no per-user API rate-limiting middleware in this repository — nothing to register, and no request limits to report.**

Evidence:

- A case-insensitive search across all Go sources for `ratelimit`, `rate_limit`, `rate limit`, `throttle`, and the usual limiter dependency `golang.org/x/time/rate` returns exactly one hit, and it's an aspirational comment in documentation, not code: "Rate limit email sending to prevent abuse" in `internal/email/doc.go:86`.
- `go.mod` declares no rate-limiting or throttling library.
- The full Echo middleware stack is two entries, registered at `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:13`). No `middleware.RateLimiter`, no custom limiter.
- The Connect/gRPC interceptor chain is likewise limited to `MetadataInterceptor`, `LoggingInterceptor`, and `RecoveryInterceptor` (`server/router/api/v1/connect_interceptors.go`), plus the auth middleware wired in `RegisterGateway` (`server/router/api/v1/v1.go:95`). None of them count or bucket requests.
- Nothing anywhere returns HTTP 429 or gRPC `ResourceExhausted` for request frequency.

**What does exist, and is easy to mistake for rate limiting** — all of it per-request or per-process, never per-user-over-time:

- **Concurrency caps via semaphores**: 3 concurrent thumbnail generations (`server/router/fileserver/fileserver.go:46`, `:116`; also `server/router/api/v1/v1.go:59`) and 2 concurrent image-processing operations (`server/router/api/v1/v1.go:60`). Exceeding the image cap yields `ResourceExhausted` "too many image processing requests" (`server/router/api/v1/attachment_service.go:160`) — but this is an instance-wide in-flight limit, not a per-user quota.
- **Batch-size caps on individual calls**: max URLs per link-metadata batch (`server/router/api/v1/memo_service_link_metadata.go:24`), max instance-setting names (`instance_service.go:78`), max usernames (`user_service.go:145`), max attachment deletions (`attachment_service.go:355`).
- **Pagination and content caps**: `MaxPageSize` in memo listing, and the configurable memo content-length limit (`server/router/api/v1/memo_service.go:100-106`).
- **A DB retry loop** with 3 attempts on auth-config mutation (`store/auth_config.go:13`, `:74`) — retry backoff, unrelated to request limiting.

There is also no sign-in attempt throttling or account lockout, so repeated failed logins are not rate-limited either. If you need per-user limits, they would have to be added — the natural insertion points are the Echo `Use` chain at `server/server.go:51` for HTTP surfaces and the interceptor list in `server/router/api/v1/v1.go` for Connect/gRPC.
