**Premise correction: there is no Redis in this repository.** Searching every Go source file, `go.mod`, `go.sum`, and the YAML/JSON config files for `redis` (case-insensitive) returns zero matches — no client library, no connection string, no config key. So there is nothing to point at for "where the Redis connection is configured."

**Actual mechanism: a hand-rolled, in-process, in-memory cache — `store/cache/cache.go`.**

- `cache.Cache` (`store/cache/cache.go:67-73`) is a thread-safe map (`sync.Map`) with per-item expiration, an atomic item counter, and a background cleanup goroutine (`cleanupLoop`, `store/cache/cache.go:200`). It's process-local: nothing is shared across instances, and everything is lost on restart.
- **Configuration site** — not a connection, but a `cache.Config` literal in `store.New` at `store/store.go:39-44`:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  - `OnEviction: nil`
  
  That single config is used to construct all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:50-53`). The same values are duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), though `store.New` builds its own literal rather than calling it.

**TTL for user entries: 10 minutes**, inherited from `DefaultTTL`. Every write goes through `Set` (`store/cache/cache.go:93`), which forwards to `SetWithTTL` with `c.config.DefaultTTL` — the user cache never calls `SetWithTTL` directly, so no user entry gets a custom TTL. Population/invalidation points are `store/user.go:98`, `:122`, `:132`, `:143`, `:167` (writes, keyed by `userCacheKey(user.ID)` at `store/user.go:88`), the read at `store/user.go:150`, and the explicit delete on user deletion at `store/user_delete.go:40`.

Two behavioral details worth knowing: expiry is lazy-plus-swept — `Get` evicts on read if past expiration (`store/cache/cache.go:135-144`), and the ticker sweeps every 5 minutes (`:218`). And the user cache is only consulted for lookups **by ID** (`store/user.go:149-156`); a lookup by username always hits the database.
