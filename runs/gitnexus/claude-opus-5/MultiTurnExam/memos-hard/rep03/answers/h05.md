**Explicit Go code — in each SQL driver's `DeleteUser` transaction; there is no database-level rule (the `reaction` table has no foreign key at all).**

What I checked:

**1. The delete path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver. Each of the three drivers implements it identically in structure — `DeleteUser` opens a transaction and calls `deleteUserTargetsTx` (`store/db/mysql/user_delete.go:29` / `:92`, and the same shape at `store/db/sqlite/user_delete.go` and `store/db/postgres/user_delete.go`).

**2. Two explicit reaction deletes, per driver.** Inside `deleteUserTargetsTx` there are two separate statements, both before the memo and user rows are removed:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`store/db/mysql/user_delete.go:96` → `:417-425`; `sqlite/user_delete.go:96` → `:380`; `postgres/user_delete.go:96` → `:380`). This removes reactions *other people left on the deleted user's memos* — the content IDs are `"memos/"+uid` strings built by `memoContentIDsFromRefs` (`mysql/user_delete.go:549`) over the user's whole memo tree including comment descendants (`listDeleteUserMemoTreeIterative`, `:133`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`mysql/user_delete.go:102` → `:437-440`; `sqlite/user_delete.go:102` → `:400`; `postgres/user_delete.go:102` → `:400`). This removes *the deleted user's own reactions on anyone's memos*.

**3. No database-level rule.** The `reaction` table DDL declares only a primary key and `UNIQUE(creator_id, content_id, reaction_type)` — no `FOREIGN KEY`, no `ON DELETE CASCADE` — in all three current schemas: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` (and the original `0.20/00__reaction.sql` in each dialect). Grepping `FOREIGN KEY|REFERENCES|CASCADE` across `store/migration/` returns hits only for `memo_share`, `user_setting`, `memo_resource`, etc. — never `reaction`. A cascade would not be possible anyway: `reaction.content_id` is a text resource name (`"memos/{uid}"`), not an integer FK to `memo.id`, which is exactly why the content-side cleanup has to be done in Go.

So both directions are covered, deliberately and in application code, atomically within the delete transaction.
