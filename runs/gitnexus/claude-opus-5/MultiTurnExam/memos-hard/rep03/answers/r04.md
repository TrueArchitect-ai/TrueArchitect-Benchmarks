**Premise correction: neither. There is no message broker in this repository — no NATS, no RabbitMQ, no AMQP, Kafka, SQS, or pub/sub of any kind, and therefore no queue declaration to point at.** A case-insensitive search across all Go sources, `go.mod`, and the YAML configs for `nats|rabbitmq|amqp|kafka|streadway|sqs|pubsub` returns zero matches.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool, entirely inside `internal/webhook/webhook.go`.**

- **The "queue"** is a package-level channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A 128-slot buffer, in memory, in the server process.
- **The "workers"** are four goroutines started in the package `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. They start when the package is first loaded, not from any explicit server wiring.
- **Enqueue** happens in `PostAsync` (`internal/webhook/webhook.go:184-196`), via a non-blocking `select` with a `default` branch: if the buffer is full, the payload is **dropped** with a warning rather than blocking the caller. Producers are the memo webhook dispatchers at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.
- **Delivery** is `Post` (`internal/webhook/webhook.go:120`), which signs the payload and issues the HTTP request through the SSRF-guarded `safeClient` at `internal/webhook/webhook.go:152`.

Worth being explicit about the consequences, since broker semantics are what the question presumes: this queue has **no durability, no retries, no acknowledgements, and no cross-process delivery**. Pending webhooks are lost on restart, a failed POST is logged and discarded (`webhook.go:47-51`), and a burst beyond 128 queued payloads sheds load silently apart from the log line. Nothing coordinates delivery across multiple server instances.
