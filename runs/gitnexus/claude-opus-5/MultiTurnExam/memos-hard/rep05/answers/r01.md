**Premise correction: there is no Redis in this repository — no client, no dependency, no configuration.** Grepping case-insensitively for `redis` across the whole tree (excluding `node_modules`/`.git`) returns zero files, and neither `go.mod` nor `go.sum` contains a Redis or memcache driver. There is no external cache server to point at.

**Actual mechanism: a process-local in-memory cache.** `store/cache/cache.go` implements `Cache` as "a thread-safe in-memory cache with TTL and memory management" (`cache.go:66-73`) — a `sync.Map` plus an atomic item counter and a background cleanup goroutine started in `New` (`cache.go:83`). Nothing crosses a network, and nothing survives a restart; in a multi-replica deployment each process has its own independent copy.

**Where it's "configured."** Not from any flag, env var, or config file — the settings are a hardcoded literal in `Store.New` (`store/store.go:38-44`):

- `DefaultTTL: 10 * time.Minute`
- `CleanupInterval: 5 * time.Minute`
- `MaxItems: 1000`
- `OnEviction: nil`

That one `cacheConfig` is handed to all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). Note this duplicates, rather than uses, `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), which returns the identical values.

**TTL for user entries: 10 minutes.** Every user write goes through `Cache.Set` (`store/user.go:98,122,132,143,167`), which applies `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — the 10-minute value above. `SetWithTTL` exists for custom per-entry TTLs (`cache.go:98`) but no user code path calls it, so 10 minutes is uniform.

Two caveats on that TTL. Expiry is lazy plus swept: `Get` checks `time.Now().After(itm.expiration)` and evicts on read (`cache.go:135-144`), while the cleanup loop sweeps every 5 minutes. And entries can be evicted *early*, before the TTL, when the cache exceeds `MaxItems: 1000` and `cleanupOldest` runs (`cache.go:117-119`). Explicit invalidation also happens on user deletion (`store/user_delete.go:40`).

One asymmetry worth knowing: `Store.GetUser` only consults the cache when looking up by ID (`store/user.go:149-156`); a lookup by username — such as the avatar path — always hits the database, though it populates the cache afterward.
