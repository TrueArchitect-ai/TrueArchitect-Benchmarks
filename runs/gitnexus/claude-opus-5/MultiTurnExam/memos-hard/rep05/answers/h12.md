**How I determined it's the SQLite one, not the Postgres or MySQL sibling.** Three `CreateMemo` implementations exist — `store/db/sqlite/memo.go:16`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go` — all satisfying the `store.Driver` interface (`store/driver.go`). Selection is runtime, not compile-time, so I followed the value that picks it:

1. **Call chain is interface-dispatched.** The RPC handler `CreateMemo` calls `s.Store.CreateMemo` (`server/router/api/v1/memo_service.go:115`), which validates the UID and immediately delegates to `s.driver.CreateMemo(ctx, create)` (`store/memo.go:113`) — an interface call, so the concrete target depends entirely on what's in `Store.driver`.
2. **The factory is the only place the driver is chosen.** `NewDBDriver` switches on `profile.Driver` and constructs exactly one of the three (`store/db/db.go:18-27`); `mysql.NewDB` is reached only at `store/db/db.go:22`, `sqlite.NewDB` only at `:20`.
3. **The default value of that field is `"sqlite"`.** The profile is populated from `viper.GetString("driver")` (`cmd/memos/main.go:43`), and both the viper default (`cmd/memos/main.go:122`) and the flag default (`cmd/memos/main.go:130`) are `"sqlite"`. With no flags set, the switch takes the `sqlite` branch.

Corroborating detail: with no `--dsn` either, `Profile` fills in a file path under the data dir for SQLite (`internal/profile/profile.go:110-116`) — a code path that only makes sense for the SQLite default, confirming that's the untouched-install configuration.
