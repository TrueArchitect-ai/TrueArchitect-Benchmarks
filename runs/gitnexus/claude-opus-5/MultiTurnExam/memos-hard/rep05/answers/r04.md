**Premise correction: neither. There is no message broker in this repository — no NATS, no RabbitMQ, no AMQP, Kafka, or SQS client — and therefore no queue declaration to point at.** A case-insensitive grep for `nats`, `rabbitmq`, `amqp`, `kafka`, `streadway`, `pubsub`, and `sqs` across all Go source and `go.mod` returns zero matches. Nothing is consumed from an external system.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool**, entirely inside `internal/webhook/webhook.go`.

- **The "queue"** is a package-level buffered channel holding 128 payloads: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`). That line is the only place it's declared — it's a private variable in the `webhook` package, not infrastructure.
- **The "workers"** are 4 goroutines started in the package `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post` for every payload, logging a warning on failure. There is no ack, retry, or dead-letter handling — a failed delivery is logged and dropped.
- **Producers** call `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking `select` send: if the buffer is full, the payload is discarded with a `"Dropped webhook dispatch because the async queue is full"` warning (`:189-195`). Enqueue never blocks the RPC handler.
- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`), which signs the body and issues the HTTP POST via the SSRF-guarded `safeClient` (`:152`).

The practical consequences of this being a channel rather than a broker: the queue is per-process (each replica has its own), it does not survive a restart — anything buffered at shutdown is lost, and nothing drains it during `Server.Shutdown` — and backpressure is handled by dropping rather than blocking or persisting. Producers are the memo RPC handlers covered earlier (`server/router/api/v1/memo_service_webhooks.go:43,71`).
