**Explicit Go code — not a database rule.** Reactions are deleted by hand-written SQL inside the `DeleteUser` transaction in every driver; there is no foreign key or `ON DELETE CASCADE` on the `reaction` table.

What I checked:

**1. The delete path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver. Each driver's `DeleteUser` opens one transaction and calls `deleteUserTargetsTx`, which removes reactions in *two* passes before the user row goes away:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500, where the content IDs are `"memos/" + uid` for every memo in the user's memo tree (`memoContentIDsFromRefs`). This clears *other people's* reactions on the deleted user's memos.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`. This clears the deleted user's own reactions on memos that survive.

Call sites and implementations, identical across all three drivers:
- `store/db/sqlite/user_delete.go:96,102` → `:380`, `:400`
- `store/db/postgres/user_delete.go:96,102` → `:380`, `:400`
- `store/db/mysql/user_delete.go:96,102` → `:417`, `:437`

**2. The schema — no DB-level rule.** The `reaction` DDL has only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint; `creator_id` is a bare `INTEGER`/`INT` with no `REFERENCES` clause:
- `store/migration/sqlite/LATEST.sql:92-98`
- `store/migration/postgres/LATEST.sql:91-97`
- `store/migration/mysql/LATEST.sql:91-98`

Grepping `REFERENCES` across all migration SQL turns up no foreign key touching `reaction` at all, and none referencing the `user` table. By contrast, `memo_share` right below it *does* carry `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/mysql/LATEST.sql:108`) — so cascades exist in this schema, just not for reactions. Note also that `content_id` is a string like `memos/{uid}`, not an integer FK, so a cascade from `memo` isn't even expressible here.

**3. Test coverage confirms the intent.** `store/test/user_delete_test.go:97-112` seeds three reactions, and `:217-220` asserts that after the delete exactly one survives — the peer's reaction on a peer-owned memo — verifying both deletion passes and that they don't over-delete.
