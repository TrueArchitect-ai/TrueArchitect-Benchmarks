**No — the MySQL driver is only ever constructed inside the factory.**

Evidence:

1. **Exactly one call site for the constructor.** `grep -rn "mysql.NewDB\|db/mysql\"" --include=*.go` over the whole repo returns two lines, both in the factory file: the import at `store/db/db.go:8` and the call `driver, err = mysql.NewDB(profile)` at `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver`.

2. **Exactly one importer of the package.** `grep -rln "usememos/memos/store/db/mysql"` matches only `store/db/db.go`. No other file in the repo — production, test, or tooling — imports `store/db/mysql`, so nothing else can reach `NewDB` or the `DB` type from outside.

3. **No struct-literal bypass from outside.** The `DB` struct (`store/db/mysql/mysql.go:14-18`) has only unexported fields (`db`, `profile`, `config`), so it couldn't be usefully built outside the package even if imported. Searching `&DB{` repo-wide finds one MySQL hit, `store/db/mysql/auth_config_test.go:12` — but that is *inside* `package mysql` itself, and it's a zero-value `&DB{}` used purely to call the pure-function error classifier `IsRetryableAuthenticationMutationError`, not a live driver.

4. **Tests go through the factory too.** The MySQL-related code in `store/test/` never touches `store/db/mysql`: `store/test/store.go:88` only picks a DSN string and returns a `*profile.Profile` with `Driver: "mysql"`, and `store/test/containers.go` uses the upstream `go-sql-driver/mysql` and testcontainers packages for the container/DSN plumbing. Driver selection still funnels through `NewDBDriver`.

The one nuance worth naming: `store/db/mysql/mysql.go:29` does `driver := DB{profile: profile}` — a direct struct construction — but that is `NewDB`'s own body, i.e. the factory's target, not a bypass.
