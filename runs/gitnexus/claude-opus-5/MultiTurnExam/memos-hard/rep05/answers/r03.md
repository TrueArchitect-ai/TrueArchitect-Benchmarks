**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is not running at all. Nothing is scheduled, so there is no time to report.**

Two separate corrections:

**1. The cron scheduler is dead code.** `internal/scheduler` is a complete, well-tested cron package — `New` (`internal/scheduler/scheduler.go:53`), `Register` (`:69`), `Start` (`:90`), `Stop` (`:168`), with a cron-expression parser at `internal/scheduler/parser.go:29`. But grepping for importers of `usememos/memos/internal/scheduler` returns only two files, both inside the package's own test suite: `internal/scheduler/example_test.go` and `internal/scheduler/integration_test.go`. No production code constructs a scheduler or registers a job; the only non-test `scheduler.New()` / `.Register(` occurrences in the repo are commented-out illustrations in `internal/scheduler/doc.go:12-28`. So the scheduler never starts in a running server.

**2. No database-cleanup job exists anywhere**, cron-driven or otherwise. Searching for `cleanup` / `vacuum` / `purge` / `nightly` / `midnight` across `server/`, `store/`, and `cmd/` turns up nothing resembling a periodic database maintenance task — only unrelated matches: the in-memory cache's expiry sweep, a test helper, and best-effort row cleanup inside the SSO flow.

**What actually runs on a schedule** is a single background runner, and it isn't cron-based and doesn't clean anything:

- **S3 presign runner** — `server/runner/s3presign/runner.go` — a `time.Ticker` at `runnerInterval = 12 * time.Hour` (`runner.go:27`), started at `server/server.go:162-171`. It refreshes expiring presigned attachment URLs. Because it's an interval ticker anchored to process start — not a wall-clock cron expression — it has no fixed time of day; it fires 12 and 24 hours after boot, whenever that was.

Two other periodic loops exist, both interval-based and in-process: the cache expiry sweep every 5 minutes (`store/cache/cache.go:200-210`) and the webhook dispatch workers (`internal/webhook/webhook.go:42-55`).

Deletion of stored data in this codebase is entirely event-driven rather than scheduled — for example the cascading removal in `DeleteUser` (`store/db/sqlite/user_delete.go:29`), which runs synchronously when a user is deleted.
