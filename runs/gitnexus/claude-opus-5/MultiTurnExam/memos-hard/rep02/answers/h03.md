**Abstraction package: `github.com/usememos/memos/internal/idp` (`/bench/home/work/internal/idp/idp.go`); implementation package: `github.com/usememos/memos/internal/idp/oauth2` (`/bench/home/work/internal/idp/oauth2/oauth2.go`).**

Details:

- **`internal/idp`** is deliberately minimal — `internal/idp/idp.go` is the entire package and defines just one type, `IdentityProviderUserInfo` (`Identifier`, `DisplayName`, `Email`, `AvatarURL`). It's a shared normalized-user-info contract rather than a Go `interface`; there is no `Provider` interface to implement, so the "abstraction" is the common return shape every provider maps its claims into.
- **`internal/idp/oauth2`** is the only concrete protocol implementation that ships. It provides `IdentityProvider` (`oauth2.go:20`), built by `NewIdentityProvider` from a `storepb.OAuth2Config` with required-field validation (`oauth2.go:27`), plus `ExchangeToken` (`oauth2.go:47`, supporting PKCE via `code_verifier`) and `UserInfo` (`oauth2.go:83`), which fetches the userinfo endpoint and maps claims into `idp.IdentityProviderUserInfo` using the configured `FieldMapping`.

Two things confirm OAuth2 is the sole implementation: `internal/idp/` contains only the `oauth2` subdirectory, and the stored config oneof `isIdentityProviderConfig_Config` has exactly one variant, `IdentityProviderConfig_Oauth2Config` (`/bench/home/work/proto/gen/store/idp.pb.go:210-214`).

The consumer is `/bench/home/work/server/router/api/v1/auth_service_sso.go` — `resolveSSOIdentity` (line 104) constructs the provider at line 121 via `oauth2.NewIdentityProvider(identityProvider.Config.GetOauth2Config())`, then hands the resulting `*idp.IdentityProviderUserInfo` to `resolveSSOUser` (line 19). Generic OIDC providers are supported through this same OAuth2 path by configuring the token/userinfo URLs and field mappings — there is no separate OIDC package.
