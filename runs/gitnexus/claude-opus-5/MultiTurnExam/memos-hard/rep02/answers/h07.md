Notes on the path:

- **Registration**: the `/file` group is wired at server startup — `fileserver.NewFileServerService(...)` then `RegisterRoutes(echoServer)` at `server/server.go:81-82`.
- **Access control** happens before any lookup: if the instance disallows anonymous access (`s.Profile.AllowAnonymous()` false), `serveUserAvatar` requires a valid session/access token/PAT via `s.getCurrentUser` and returns 401 otherwise (`fileserver.go:173-181`). On a public instance, any user's avatar is served unauthenticated by design.
- **The data is not a file on disk or in S3.** `getUserByUsername` is a one-liner passing `&store.FindUser{Username: &identifier}` to the store; the image lives in the `user.AvatarURL` column as a base64 data URI. `serveUserAvatar` decodes it in-process with `s.parseDataURI` (`fileserver.go:196`, impl at `fileserver.go:737`), rejects any MIME type outside `avatarAllowedTypes` (`fileserver.go:201`, set at `fileserver.go:75`), sets security headers plus a 1-hour `Cache-Control`, and writes the bytes with `c.Blob` (`fileserver.go:209`).
- **Cache layer**: `Store.GetUser` consults `userCache` only when looking up by ID (`store/user.go:149-156`). This lookup is by username, so it always falls through to `ListUsers` → driver → SQL; the result is then populated into the cache (`store/user.go:167`).
