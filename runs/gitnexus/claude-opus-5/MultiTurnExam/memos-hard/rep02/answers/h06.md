The last three are the non-obvious ones: `SetMemoRelations` and `SetMemoAttachments` don't mention webhooks at all — they reach delivery through the shared `dispatchMemoUpdatedSideEffects` helper (`server/router/api/v1/memo_update_helpers.go:66`), which calls `DispatchMemoUpdatedWebhook`.

**How they converge.** All four `Dispatch*Webhook` methods live in `server/router/api/v1/memo_service_webhooks.go`; three of them delegate to `dispatchMemoRelatedWebhook` (line 48) and the comment one has its own loop (line 30). Both loops read the target from `s.Store.GetUserWebhooks(...)` and set `payload.URL = hook.Url` — the user-configured URL — then call `webhook.PostAsync` (lines 43 and 71).

`PostAsync` (`internal/webhook/webhook.go:184`) only enqueues onto the bounded `asyncPostQueue`; four worker goroutines started in `init()` (`webhook.go:42-55`) drain it and call **`webhook.Post`**, which is where the request is built, HMAC-signed, and executed via `safeClient.Do` (`webhook.go:152`). So `Post` is the single funnel every path passes through before an outbound request leaves the process.

One scoping note: I read "user-configured URL" as the webhook URL a user saves on their own account. If you also count admin/instance-configured endpoints, the S3 presign runner (`server/runner/s3presign/runner.go`) and the link-preview fetcher in `internal/httpgetter` make outbound requests too, but those don't route through `webhook.Post` and aren't RPC-handler-triggered in the same way.
