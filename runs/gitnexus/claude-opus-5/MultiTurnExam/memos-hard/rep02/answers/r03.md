**Premise correction: there is no nightly database-cleanup job — and the cron scheduler isn't running at all.** Nothing is scheduled, so there's no time to report.

Two separate corrections, both load-bearing:

**1. The scheduler exists but is never wired into the server.** `internal/scheduler/` is a complete, working cron package — `Scheduler` with `New`/`Register`/`Start`/`Stop` (`internal/scheduler/scheduler.go:54`, `:70`, `:91`, `:169`), a cron-expression parser (`internal/scheduler/parser.go`), and middleware for logging/recovery/timeout (`internal/scheduler/middleware.go`). But the only files importing `github.com/usememos/memos/internal/scheduler` are its own tests: `internal/scheduler/integration_test.go:13` and `internal/scheduler/example_test.go:10`. No production code constructs a `Scheduler`, registers a `Job`, or calls `Start`. The package is dead code, and the `New`/`Register` examples in `internal/scheduler/doc.go:12-28` are documentation comments, not registrations.

**2. There is no database-cleanup job anywhere**, scheduled or otherwise. Grepping `server/`, `store/`, and `cmd/` for `cleanup`/`vacuum`/`purge`/`prune` turns up only:
- **Cache** cleanup — the in-memory `Cache`'s expiry goroutine on a 5-minute interval (`store/cache/cache.go:83`, `CleanupInterval` at `store/store.go:42`). In-process only, touches no database.
- **Inline, event-driven** cleanup — attachment-storage deletion during user deletion (`server/router/api/v1/user_service.go:421-450`, `store/attachment.go:171`) and relation/attachment cleanup on memo deletion (`server/router/api/v1/memo_service.go:579`). These run as part of a request, not on a timer.

**What actually runs on a schedule in the server:** exactly one background runner — the S3 presign refresher, on a 12-hour `time.Ticker` (`server/runner/s3presign/runner.go:27`), started from `startBackgroundRunners` at `server/server.go:162-171`. It uses a plain ticker, not the cron scheduler, and it refreshes presigned URLs rather than cleaning up data.
