**Premise correction: there is no per-user API rate-limiting middleware in this repository.** It isn't registered anywhere, so there are no request limits to report.

Evidence:

- A case-insensitive grep across all `.go` files for `ratelimit` / `rate_limit` / `rate limit` / `throttl` / `golang.org/x/time/rate` returns exactly one hit, and it's an aspirational comment, not code: `internal/email/doc.go:86` lists "Rate limit email sending to prevent abuse" as a future consideration.
- `go.mod` declares no rate-limiting dependency — no `golang.org/x/time`, no Echo rate-limiter, nothing equivalent.
- The full set of Echo middleware registered on the server is two entries: `middleware.Recover()` and `newCORSMiddleware(profile)` at `/bench/home/work/server/server.go:51-52`, plus static-file and SPA-fallback middleware for the frontend at `server/router/frontend/frontend.go:54` and `:59`. None of these limits request rates.
- Request-path auth is handled by the authorizer/interceptor in `server/router/api/v1/v1.go` (gateway middleware and Connect interceptor) and `server/auth`, which enforce authentication and access policy — not throughput.

What does exist, and is easy to mistake for rate limiting, is **concurrency limiting on expensive image work** — counting semaphores, not per-user request quotas:

- `thumbnailSemaphore: semaphore.NewWeighted(3)` and `imageProcessingSemaphore: semaphore.NewWeighted(2)` in `NewAPIV1Service` (`server/router/api/v1/v1.go:59-60`).
- `thumbnailSemaphore: semaphore.NewWeighted(maxConcurrentThumbnails)` in the file server (`server/router/fileserver/fileserver.go:116`, constant `maxConcurrentThumbnails = 3` at `fileserver.go:45`).

These are process-wide caps on simultaneous in-flight operations to bound memory; they're not keyed by user, don't count requests over time, and don't reject requests — callers block until a slot frees. Similarly, the webhook dispatcher's bounded queue (`internal/webhook/webhook.go:39`, 128 slots with 4 workers) shapes outbound traffic, not inbound API requests.
