**Mechanism: explicit Go code — there is no database-level rule that could do it.** Reactions are deleted by hand-written `DELETE` statements inside the `DeleteUser` transaction, in all three drivers.

What I checked:

**1. The explicit Go deletions.** Each driver's `DeleteUser` runs `deleteUserTargetsTx`, which issues *two* separate reaction deletes:
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the deleted user *made* on anyone's memos: `/bench/home/work/store/db/mysql/user_delete.go:414`, `/bench/home/work/store/db/sqlite/user_delete.go:401`, `/bench/home/work/store/db/postgres/user_delete.go:401`.
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions *other users* left on the deleted user's memos: `/bench/home/work/store/db/mysql/user_delete.go:396`, `/bench/home/work/store/db/sqlite/user_delete.go:383`, `/bench/home/work/store/db/postgres/user_delete.go:383`.

The `content_id` values are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs` (`store/db/mysql/user_delete.go`), over the full memo tree — roots plus all `COMMENT`-related descendants collected by `listDeleteUserMemoTreeIterative`. Both deletes are batched at 500 IDs (`deleteUserBatchSize`) and run inside the single transaction opened in `DeleteUser` (`store/db/mysql/user_delete.go:32`), so reaction cleanup commits atomically with the user row.

**2. Ruled out a database-level rule.** The `reaction` table is declared with no foreign keys at all — `creator_id` and `content_id` are plain `INTEGER`/`TEXT` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint:
- `/bench/home/work/store/migration/sqlite/LATEST.sql:92-99`
- `/bench/home/work/store/migration/mysql/LATEST.sql:91-98`
- `/bench/home/work/store/migration/postgres/LATEST.sql:91-98`
- and the original `store/migration/*/0.20/00__reaction.sql` in each dialect — the table never had an FK.

Grepping every migration for `FOREIGN KEY` / `ON DELETE CASCADE` / `CREATE TRIGGER` turns up only two cascades in current schemas, both on `memo_share.memo_id → memo(id)` (`sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`) — neither touches `reaction`. The historical user-referencing cascades in `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql` predate the reaction table (0.20) and were removed wholesale by `store/migration/sqlite/0.7/00__remove_fk.sql`.

Note also that `content_id` is a string like `memos/{uid}`, not a numeric memo reference, so an FK-based cascade isn't even expressible here — the Go code is necessarily the only mechanism.
