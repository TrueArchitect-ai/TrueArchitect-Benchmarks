**No — outside `NewDBDriver`, the MySQL driver is never constructed anywhere in production code.** The only construction outside the factory is a zero-value `&DB{}` inside the package's own unit test.

Evidence:

1. **The constructor is `mysql.NewDB`** at `/bench/home/work/store/db/mysql/mysql.go:20`, returning `store.Driver`.
2. **Exactly one call site exists.** `grep` for `mysql.NewDB` / `mysql.DB{` / `&mysql.DB` across all `.go` files returns a single hit: `/bench/home/work/store/db/db.go:22`, inside the `case "mysql":` arm of `NewDBDriver`.
3. **Exactly one file imports the package.** `github.com/usememos/memos/store/db/mysql` is imported only by `/bench/home/work/store/db/db.go:8`. Since the package is otherwise un-imported, no other file *could* construct it — this is the strongest form of the evidence, stronger than the call-site grep alone.
4. **Everything else goes through the factory.** Only two files import `store/db` at all — `/bench/home/work/store/test/store.go:18` and `/bench/home/work/server/router/api/v1/test/memo_service_benchmark_test.go:15` — and both obtain a driver via `NewDBDriver`, including the MySQL testcontainer path in `/bench/home/work/store/test/containers.go`.

Two clarifications worth stating so the "no" isn't overclaimed:

- **In-package test exception:** `/bench/home/work/store/db/mysql/auth_config_test.go:12` does `db := &DB{}`. That's a direct composite-literal construction of the driver struct, but it's inside `package mysql` itself (not an external construction), and it builds an empty struct with no `*sql.DB` connection purely to call a method under test — it never becomes a live driver.
- **Don't confuse with the third-party package:** `github.com/go-sql-driver/mysql` is imported by `store/db/mysql/mysql.go`, `store/db/mysql/auth_config.go`, `store/db/mysql/auth_config_test.go`, and `store/test/containers.go`. That's the upstream SQL driver registration/DSN library, not this repo's `store.Driver` implementation.
