**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never started by the server — so there is no scheduled time to report.**

Two separate corrections:

**1. No database-cleanup job exists.** Grepping the server, store, and cmd trees for `cron|nightly|cleanup|vacuum|purge` turns up no scheduled maintenance task. The only "cleanup" hits are unrelated: inline attachment-storage cleanup during user deletion (`server/router/api/v1/user_service.go:421-450`), best-effort removal of a provisional SSO user row (`server/router/api/v1/auth_service_sso.go:76`), cascade deletes inside `DeleteMemo` (`server/router/api/v1/memo_service.go:579`), a test helper (`server/router/api/v1/test/test_helper.go:65`), and the in-memory cache's expiry sweep (`store/cache/cache.go:200`, every 5 minutes — a goroutine ticker, not cron, and it touches no database).

**2. The cron scheduler is unused in production.** `internal/scheduler` is a complete, GitHub-Actions-inspired cron implementation — `Scheduler` with `New`/`Register`/`Start`/`Stop` (`internal/scheduler/scheduler.go:70`, `:167`), a cron-expression parser (`internal/scheduler/parser.go`), `Job` type (`internal/scheduler/job.go`), and Recovery/Logging middleware (`internal/scheduler/middleware.go`). But the package is imported in exactly two places, both tests: `internal/scheduler/example_test.go:10` and `internal/scheduler/integration_test.go:13`. Nothing in `server/`, `cmd/`, or `store/` imports it, so no `Scheduler` is ever constructed or started in the running binary. The cron expressions you'll find in `internal/scheduler/doc.go` and `README.md` are documentation examples, not registered jobs.

**What the server actually runs on a schedule.** The only recurring background work is `startBackgroundRunners` (`server/server.go:153-174`), which starts exactly one runner: the S3 presign refresher (`server/runner/s3presign/runner.go`). It's interval-based rather than wall-clock-scheduled — `runnerInterval = 12 * time.Hour` via a `time.Ticker` (`server/runner/s3presign/runner.go:27`, `:29-41`), plus one immediate pass at startup (`server/server.go:163`). Because it's an interval from process start, its fire times drift with restarts and it never lands at a fixed nightly hour.

There's also a second runner type, `memopayload.Runner` (`server/runner/memopayload/runner.go`), which does bulk memo-payload rebuilds — but `NewRunner` is never called, so it too is dead code.
