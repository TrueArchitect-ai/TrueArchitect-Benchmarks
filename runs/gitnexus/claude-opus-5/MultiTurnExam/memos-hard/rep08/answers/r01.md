**Premise correction: there is no Redis in this codebase.** A case-insensitive grep for `redis`/`memcach` across all Go, mod, YAML, and JSON files returns zero hits, and `go.mod` has no Redis client dependency. The cache layer is a hand-rolled, in-process, in-memory cache — nothing is configured for an external cache server, and there's no connection to configure.

**Actual mechanism.**

- **Implementation:** `store/cache/cache.go` — a `Cache` struct (`:67-73`) built on `sync.Map` plus an `atomic.Int64` item counter, satisfying the `cache.Interface` at `:11-32`. Entries are `item{value, expiration, size}` (`:35-39`).
- **Where it's "configured":** `store.New` in `store/store.go:38-57`. It builds one `cache.Config` literal (`:39-44`) and passes it to three separate `cache.New(...)` instances (`:51-53`): `instanceSettingCache`, `userCache`, `userSettingCache`. Note this literal duplicates `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) rather than calling it — the values are identical, but they're two independent copies.

**TTL for user entries: 10 minutes**, from `DefaultTTL: 10 * time.Minute` at `store/store.go:40`. Every user write goes through `userCache.Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with the config default (`store/cache/cache.go:93-95`), stamping `expiration = time.Now().Add(ttl)` (`:112`). Nothing calls `SetWithTTL` directly with a custom TTL, so 10 minutes applies uniformly to all three caches.

Other bounds worth knowing, since they can evict a user entry well before its TTL:

- **`CleanupInterval: 5 * time.Minute`** (`store/store.go:41`) — a background goroutine per cache (`cleanupLoop`, `store/cache/cache.go:200`) sweeps expired items. Expiry is also enforced lazily on read (`Get`, `:135-144`), so a stale entry is never returned even between sweeps.
- **`MaxItems: 1000`** (`store/store.go:42`) — on exceeding this, `cleanupOldest` (`:253`) drops roughly 20% of capacity. So on an instance with more than ~1000 active users, user entries can be evicted early.
- **Explicit invalidation:** `userCache.Delete` on user deletion (`store/user_delete.go:40`).

Two consequences of it being in-process rather than Redis: the cache is empty on every restart, and in a multi-replica deployment each replica has its own copy with no cross-instance invalidation — a user updated on replica A can stay stale on replica B for up to 10 minutes. Also note `Store.GetUser` only consults the cache when looking up by ID (`store/user.go:149-156`); lookups by username or email always hit the database.
