Notes on the trace:

- **Where the browser gets the URL.** The avatar is stored as a base64 data URI in the `user.avatar_url` column, so the API doesn't inline it. `convertUserFromStore` rewrites the field to `/file/{userName}/avatar` (`server/router/api/v1/user_service_converters.go:36`) when `extractImageInfo` confirms it's base64. `userpb.Name` is `users/{username}` via `BuildUserName` (`server/router/api/v1/user_resource_name.go:13`), so the emitted path is `/file/users/{username}/avatar` — which is why `:identifier` is the username and `getUserByUsername` looks up by `Username`. If the stored value isn't base64 (an external URL), the browser goes straight to that host and none of this path runs.

- **Route wiring.** `RegisterRoutes` on the `/file` group (`server/router/fileserver/fileserver.go:121-125`), constructed and mounted at server startup in `server/server.go:81-82`.

- **Access control before the lookup.** On a private instance (`!s.Profile.AllowAnonymous()`), `serveUserAvatar` requires a session/access token first (`server/router/fileserver/fileserver.go:173-181`); on a public instance any browser can request another user's avatar.

- **Cache short-circuit.** `Store.GetUser` only consults `userCache` when `find.ID` is set (`store/user.go:149-156`); this path searches by username, so it always falls through to `Store.ListUsers` → driver → SQL, then populates the cache (`store/user.go:167`).

- **Response.** Decoded bytes are returned via `c.Blob` with the sniffed MIME type, gated by `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:201`) and security headers (`:205-209`).
