**The funnel.** All the `Dispatch*Webhook` methods (`server/router/api/v1/memo_service_webhooks.go:15`, `:20`, `:25`, `:30`) collapse into `dispatchMemoRelatedWebhook` (`:48`) — except the comment variant, which inlines the same loop at `:31-45`. Each reads the target user's stored webhook rows via `s.Store.GetUserWebhooks` and sets `payload.URL = hook.Url` (`:67` / `:41`) — that's the user-configured URL — then calls `webhook.PostAsync` (`:71` / `:43`).

`PostAsync` (`internal/webhook/webhook.go:184`) only enqueues onto a 128-slot channel; the four worker goroutines started in `init` (`internal/webhook/webhook.go:42-55`) are what actually invoke **`webhook.Post`** (`internal/webhook/webhook.go:120`), where the request is built, HMAC-signed, and sent via `safeClient.Do` at `internal/webhook/webhook.go:152`. So `Post` is the single convergence point before delivery — it's also the only place the SSRF-guarded client is used.

**Two related paths I checked and excluded:** `CreateUserWebhook` / `UpdateUserWebhook` (`server/router/api/v1/user_service_webhooks.go:53`, `:106`) touch a user-configured URL but only *validate* it via `webhook.ValidateURL` (DNS resolution, no HTTP request) and persist it. And `internal/httpgetter` fetches link metadata from a URL supplied per-request rather than a stored configuration, so it doesn't route through `webhook.Post`.
