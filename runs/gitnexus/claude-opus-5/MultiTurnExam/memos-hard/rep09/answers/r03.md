**Premise correction: there is no nightly database-cleanup job, and the cron scheduler has no registered jobs at all — so there's no scheduled time to report.**

Two separate corrections are needed here.

## 1. The cron scheduler exists but is never used in production

`internal/scheduler` is a complete, self-contained cron package — `Scheduler` with `Register`/`Start`/`Stop` (`internal/scheduler/scheduler.go:70`, `:91`, `:169`), a 5-field cron expression parser supporting wildcards, ranges, lists, and steps (`internal/scheduler/parser.go:30`, matchers at `:182-220`), timezone support (`WithTimezone`, `scheduler.go:33`), and middleware for recovery/logging/timeout (`internal/scheduler/middleware.go`).

But grepping for its import path `github.com/usememos/memos/internal/scheduler` across the repo returns exactly two files, **both tests**:

- `internal/scheduler/integration_test.go:13`
- `internal/scheduler/example_test.go:10`

No production file imports it. `scheduler.New` is never called outside tests, so no `Job` is ever registered and `Start` never runs in the server. The package is currently dead code — presumably built ahead of a use case that hasn't landed.

## 2. Background work that does run uses a plain ticker, not cron

The server's only real background job is the S3 presign refresher, and it doesn't involve the scheduler at all. `s3presign.Runner.Run` uses a bare `time.NewTicker` on a fixed 12-hour interval (`server/runner/s3presign/runner.go:27`, `:29-41`), wired directly into startup at `server/server.go:162-163` — no cron expression, no wall-clock time, so it fires 12 hours after process start and every 12 hours thereafter, whenever that happens to fall.

The only other runner, `memopayload.Runner` (`server/runner/memopayload/runner.go:27`), has no callers either.

## 3. Cleanup is event-driven, not scheduled

Data cleanup happens inline on the triggering request, not on a timer:

- User deletion cascades in one transaction — reactions, attachments, memo shares, inboxes, identities, settings, relations, memos (`store/db/sqlite/user_delete.go:96-120` and the mysql/postgres equivalents), with S3 object cleanup afterward in `server/router/api/v1/user_service.go:421-451`.
- Memo deletion handles its own relation/attachment cleanup (`server/router/api/v1/memo_service.go:579`).
- A failed SSO provisioning does best-effort row removal (`server/router/api/v1/auth_service_sso.go:76`).

The only recurring "cleanup" in the process is the in-memory cache sweep every 5 minutes (`store/store.go:42`, loop at `store/cache/cache.go:200`), which touches no database.
