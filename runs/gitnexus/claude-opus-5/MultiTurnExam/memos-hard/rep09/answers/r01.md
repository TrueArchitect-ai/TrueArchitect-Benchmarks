**Premise correction: there is no Redis in this project.** No Redis client, no connection config, no dependency — `grep -rni "redis"` across all Go, TypeScript, config, and Markdown files (excluding `node_modules`) returns zero hits, and `go.mod` has no Redis or Memcached module. The cache is a process-local, in-memory implementation with no external server.

## The actual mechanism

**Implementation.** `store/cache/cache.go` defines a thread-safe in-memory cache: a `sync.Map` of `item{value, expiration, size}` (`cache.go:35-39`, `:67-73`) guarded by an atomic item counter. `New` (`cache.go:76`) starts one `cleanupLoop` goroutine per cache instance. It's per-process, so in a multi-replica deployment each instance has its own independent copy — there's no shared cache tier.

**Where it's configured.** `store.New` (`store/store.go:38`) constructs the config inline at `store/store.go:40-45`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

and uses it for all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`, fields declared at `:27-29`). These values are hard-coded; no flag, env var, or config file overrides them. `cache.DefaultConfig()` (`cache.go:57`) has identical values but isn't the path used here.

## TTL for user entries

**10 minutes.** Every user write goes through `Cache.Set`, which forwards to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — i.e. `10 * time.Minute`. There is no per-entry override anywhere; `SetWithTTL` is never called directly outside the package.

Population sites, all keyed by `userCacheKey(user.ID)`: `store/user.go:98`, `:122`, `:132`, `:143` (bulk from `ListUsers`), and `:167` (from `GetUser`). Invalidation on delete is explicit at `store/user_delete.go:40`.

Two behavioral details:
- **Expiry is lazy plus swept.** `Get` checks `time.Now().After(itm.expiration)` and evicts on read (`cache.go:135-144`); the background `cleanupLoop` sweeps expired entries every 5 minutes (`cache.go:200-215`).
- **Capacity eviction can drop entries early.** With `MaxItems: 1000`, exceeding the cap triggers `cleanupOldest` (`cache.go:117-119`, `:253`), which removes roughly 20% of max. So on a busy instance a user entry may be dropped well before its 10 minutes elapse.

Note also that the user cache is only consulted for ID lookups — `Store.GetUser` short-circuits on cache only when `find.ID != nil` (`store/user.go:149-156`), so username-based lookups always hit the database.
