## What I checked

**1. The delete path.** `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:393`) → `Store.DeleteUser` (`store/user.go:171`) → the driver's `DeleteUser`.

**2. The driver implementations.** Each of the three drivers has its own `user_delete.go`, and all three run reaction cleanup as the *first* steps of `deleteUserTargetsTx` — before memos are removed, since the reaction rows are found via the memos:

| | file | by content | by creator |
|---|---|---|---|
| MySQL | `store/db/mysql/user_delete.go` | `:96` → helper at `:410` | `:102` → helper at `:430` |
| Postgres | `store/db/postgres/user_delete.go` | `:96` → helper at `:380` | `:102` → helper at `:400` |
| SQLite | `store/db/sqlite/user_delete.go` | `:96` → helper at `:380` | `:102` → helper at `:400` |

Two distinct sweeps, because reactions link to users and memos by different columns:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500, over content IDs built as `"memos/" + memo.UID` (`memoContentIDsFromRefs`, e.g. `store/db/mysql/user_delete.go`). This removes *other people's* reactions to the deleted user's memos, including comment memos reached transitively via `listDeleteUserMemoTreeIterative`.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`. This removes the deleted user's own reactions on memos that survive.

All of it runs inside the single `tx` opened in `DeleteUser` and committed at the end, so it's atomic with the user row removal.

The schema — ruling out a DB rule.** The `reaction` table is declared without any foreign key in all three dialects: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`. Each declares `creator_id` and `content_id` as plain `INTEGER`/`TEXT` columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. Grepping the original reaction migrations (`store/migration/{sqlite,mysql,postgres}/0.20/00__reaction.sql` and `0.23/00__reactions.sql`) for `FOREIGN`, `REFERENCES`, or `CASCADE` returns nothing. Each `LATEST.sql` contains just one `REFERENCES`/`FOREIGN KEY` occurrence in the whole file, and it isn't on `reaction` — so a cascade could not be doing this work. (`content_id` is a string like `memos/{uid}`, not an integer FK, so it couldn't cascade even in principle.)
