## Method

The data layer is the `store` package (entities declared in `store/*.go`) plus its driver subpackages under `store/db/` and its own tests under `store/test/`. I counted distinct directories *outside* that tree (`server/`, `internal/`, `cmd/`) containing at least one `store.<Type>` reference.

The ordering is stable whether or not you count test packages: excluding `_test.go` files and `/test/` directories gives `User` 5 packages vs `Memo` 4. `User` leads because it's the currency of authentication — `server/auth` and `server/router/fileserver` both need it (e.g. `getCurrentUser` at `server/router/fileserver/fileserver.go:708`) while neither is memo-centric in the same way.

**The rest of the field:** `store.Attachment` 4 packages, then `store.MemoShare`, `store.MemoRelation`, and `store.Inbox` at 3 each, `store.UserIdentity` and `store.Reaction` at 2.

One finding worth flagging: `store.UserSetting`, `store.InstanceSetting`, and `store.IdentityProvider` have **zero** references outside the store tree. Those aren't unused — server code works with the protobuf forms (`storepb.UserSetting`, `storepb.IdentityProvider`, e.g. `server/router/api/v1/auth_service_sso.go`) because the store methods return proto messages directly, so the Go struct wrappers stay internal to the data layer.
