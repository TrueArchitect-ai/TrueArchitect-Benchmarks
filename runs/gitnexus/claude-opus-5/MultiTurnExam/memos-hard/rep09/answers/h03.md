## The abstraction

`internal/idp/idp.go` is the whole abstraction package — it defines a single shared type, `IdentityProviderUserInfo` (`internal/idp/idp.go:3-8`), with `Identifier`, `DisplayName`, `Email`, and `AvatarURL`. It's a common *result* type rather than a Go interface: each provider implementation is expected to normalize its own user-info response into this struct, and the SSO layer consumes only that.

## The implementation

`internal/idp/oauth2` is the only concrete protocol that ships. `internal/idp/oauth2/oauth2.go` provides:

- `IdentityProvider` struct + `NewIdentityProvider(config *storepb.OAuth2Config)` (`oauth2.go:20`, `:27`)
- `ExchangeToken(ctx, redirectURL, code, codeVerifier)` — authorization-code exchange, with PKCE verifier support (`oauth2.go:47`)
- `UserInfo(ctx, token)` — fetches the userinfo endpoint and returns `*idp.IdentityProviderUserInfo` (`oauth2.go:83`)

That single-implementation status is corroborated in two places: the stored provider type enum has exactly one real value, `IdentityProvider_OAUTH2 = 1` alongside `TYPE_UNSPECIFIED` (`proto/gen/store/idp.pb.go:27-28`), and the SSO login path branches on it to construct an OAuth2 provider and nothing else — `oauth2.NewIdentityProvider(identityProvider.Config.GetOauth2Config())` in `resolveSSOIdentity` (`server/router/api/v1/auth_service_sso.go:121`), which then hands the resulting `*idp.IdentityProviderUserInfo` to `resolveSSOUser` (`auth_service_sso.go:19`).

Note that OIDC isn't a separate implementation here — OIDC providers are configured as generic OAuth2 with the appropriate auth/token/userinfo endpoints.
