Notes on the data layer and the tail of the request:

- **Where the image actually lives**: not on disk or in object storage — it's a base64 data URI in the `user.avatar_url` column, selected as part of the ordinary user row. `parseDataURI` (`server/router/fileserver/fileserver.go:737`) splits it with `dataURIRegex` and base64-decodes the payload.
- **Caching hop**: `Store.GetUser` consults `s.userCache` only when looking up by ID (`store/user.go:149-156`). This path passes `FindUser{Username: &identifier}`, so it always falls through to `ListUsers` → driver → SQL; the row is written back into the cache afterward (`store/user.go:167`).
- **Response**: after a MIME allowlist check against `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:75`, enforced at `:201`), it sets security headers and cache-control and writes the bytes with `c.Blob` (`:209`). Missing user → 404; empty `AvatarURL` → 404 "avatar not found".
