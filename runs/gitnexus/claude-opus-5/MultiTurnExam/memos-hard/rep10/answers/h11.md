**1st: `store.User` (~6 packages outside the data layer); 2nd: `store.Memo` (~4).**

Method: I enumerated the entity structs declared in `store/*.go` — `User`, `Memo`, `Attachment`, `Reaction`, `Inbox`, `MemoRelation`, `MemoShare`, `UserIdentity`, `UserSetting`, `InstanceSetting`, `IdentityProvider` (excluding the `Find*`/`Update*`/`Delete*` parameter structs) — then counted distinct non-test packages referencing `store.<Type>` from outside the `store/` tree.

**`store.User` — 6 packages:**
- `server/auth` (`server/auth/token.go`, authenticator returns `*store.User`)
- `server/notification`
- `server/router/api/v1` (user service, converters, authz)
- `server/router/fileserver` (`server/router/fileserver/fileserver.go:715` `getUserByUsername`)
- `server/router/rss`
- `server/router/api/v1/test` (test-support package, no `_test.go` suffix)

**`store.Memo` — 4 packages:** `server/notification`, `server/router/api/v1`, `server/router/rss`, `server/runner/memopayload` (`RebuildMemoPayload` takes `*store.Memo`).

Runner-up context: `store.Attachment` reaches 3 (`server/router/api/v1`, `server/router/fileserver`, `server/router/rss`); everything else is 1–2. `store.User` leads mainly because auth and permission checks thread a `*store.User` through nearly every entry point, whereas `store.Memo` is largely converted to its protobuf form at the API boundary.

Two notes on counting choices:
- I excluded the three driver packages `store/db/{sqlite,mysql,postgres}`, which reference *every* entity type (they implement `store.Driver`, `store/driver.go`) — they're part of the data layer, not consumers of it. Counting them adds a flat +3 to each type and doesn't change the ranking: `User` 9, `Memo` 7, `Attachment` 6.
- `proto/gen/store` hits for `UserSetting`/`InstanceSetting`/`IdentityProvider` are generated protobuf types that merely share names; they're not references to the Go store structs.
