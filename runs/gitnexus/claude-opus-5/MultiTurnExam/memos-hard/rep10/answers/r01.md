**Premise correction: there is no Redis in this repo — no Redis client, no connection config, nothing to configure. The cache layer is a hand-rolled, in-process, in-memory cache. User entries get a 10-minute TTL.**

Evidence that Redis isn't involved: a case-insensitive grep for `redis` across all `.go` files, `go.mod`, and YAML config returns zero hits. There is no external cache dependency of any kind — no memcached or similar either.

**The actual mechanism:**

- **Implementation**: `store/cache/cache.go` — a `Cache` struct backed by a `sync.Map` with an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). Each entry stores its value, an absolute `expiration` time, and a rough size estimate (`:34-39`). It satisfies the local `cache.Interface` (`:11-32`).
- **Where "connection" config would be — `cache.Config`**: `DefaultTTL`, `CleanupInterval`, `MaxItems`, `OnEviction` (`store/cache/cache.go:41-54`). Purely local knobs; no address, credentials, or pool settings exist.
- **Where it's configured for the app**: `store.New` in `store/store.go:38-58`, which hardcodes `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, `OnEviction: nil`, and builds three caches with it — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). These values are not exposed via flags or env; `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) carries the same numbers.

**User-entry TTL: 10 minutes.** Every write to the user cache goes through `Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), which forwards to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — i.e. the 10 minutes from `store/store.go:41`. No user-cache call site uses `SetWithTTL` with a custom value.

Two behavioral details worth knowing:

- Expiry is lazy plus swept: `Get` evicts an expired entry on read (`store/cache/cache.go:135-144`), and a background `cleanupLoop` goroutine sweeps every 5 minutes (`:200-215`). It's stopped by `Cache.Close`, called from `Store.Close` (`store/store.go:74-76`).
- Entries can also be evicted early regardless of TTL: exceeding `MaxItems: 1000` triggers `cleanupOldest`, which drops ~20% of the cap (`store/cache/cache.go:117-119`, `:253-255`). Deletions on user removal are explicit (`store/user_delete.go:40`).
- Because this is per-process memory, a multi-instance deployment does not share cache state or invalidations — the trade-off a Redis layer would normally address.
