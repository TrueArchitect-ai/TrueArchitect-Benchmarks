**Explicit Go code — two `DELETE FROM reaction` statements inside the delete-user transaction, in each of the three drivers. There is no database-level cascade for reactions.**

Evidence locations:

**1. Explicit deletion, per driver.** `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which fires two reaction deletes:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing *everyone's* reactions on the deleted user's memos (content IDs built as `"memos/"+memo.UID` by `memoContentIDsFromRefs`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing the user's own reactions on anyone's memos.

Call sites and definitions:
- MySQL: `store/db/mysql/user_delete.go:93` and `:99` (calls); definitions at `store/db/mysql/user_delete.go:392` and `:412`.
- SQLite: `store/db/sqlite/user_delete.go:96`, `:102`; definitions at `:380`, `:400`.
- Postgres: `store/db/postgres/user_delete.go:96`, `:102`; definitions at `:380`, `:400`.

Both run before `deleteMemosTx` and `deleteUserRowTx` in the same transaction, so a failure rolls the whole thing back.

**2. No DB-level rule could do it.** The `reaction` table declares no foreign keys in any dialect — `creator_id` is a bare `INTEGER/INT NOT NULL`:
- `store/migration/sqlite/LATEST.sql:92-98`
- `store/migration/postgres/LATEST.sql:91-97`
- `store/migration/mysql/LATEST.sql:91-97`
- Original creation: `store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql` — same, only a `UNIQUE(creator_id, content_id, reaction_type)` constraint.

A repo-wide grep for `FOREIGN KEY` / `ON DELETE CASCADE` in `store/migration/` shows cascades on `memo`, `memo_relation`, `attachment`, `user_setting`, etc., but none on `reaction`. Also note `content_id` is a string (`"memos/{uid}"`), not an integer FK, so a cascade from `memo` isn't even expressible — which is exactly why the content-ID delete is done in Go.
