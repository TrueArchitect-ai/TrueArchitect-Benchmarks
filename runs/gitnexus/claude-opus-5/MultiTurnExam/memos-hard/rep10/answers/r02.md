**Premise correction: there is no per-user API rate-limiting middleware in this repository. Nothing is registered, so there are no request limits to report.**

What I checked:

- A case-insensitive grep for `ratelimit`, `rate_limit`, `rate limit`, and `throttl` across all `.go` files returns exactly one hit — a comment in a doc file listing a *future* idea: "Rate limit email sending to prevent abuse" (`internal/email/doc.go:86`). No implementation.
- `go.mod` has no rate-limiting dependency: no `golang.org/x/time/rate`, no `github.com/ulule/limiter`, and Echo's `middleware.RateLimiter` is never referenced.
- The full set of globally registered Echo middleware is two entries — `middleware.Recover()` and `newCORSMiddleware(profile)` — at `server/server.go:51-52` (CORS config in `server/cors.go:14`). Route groups add only auth: the gRPC-Gateway auth middleware and Connect interceptor built in `APIV1Service.RegisterGateway` (`server/router/api/v1/v1.go:65-93`), backed by `NewAuthorizer` (`server/router/api/v1/authz.go`).

**What does exist, and is easy to mistake for rate limiting** — concurrency caps and size limits, none of which are per-user or time-windowed:

| Control | Value | Path |
|---|---|---|
| Concurrent thumbnail generation | 3 | `server/router/api/v1/v1.go:59` |
| Concurrent image processing | 2 | `server/router/api/v1/v1.go:60` |
| Concurrent thumbnails (file server) | `maxConcurrentThumbnails` | `server/router/fileserver/fileserver.go:116` |
| Memo content length | instance setting `ContentLengthLimit` | enforced at `server/router/api/v1/memo_service.go:104` and `:443` |
| Webhook async queue depth | 128, with drop-on-full | `internal/webhook/webhook.go:39`, `:189-195` |
| Webhook response body read | 1 MiB | `internal/webhook/webhook.go:158` |

These are `semaphore.Weighted` gates protecting memory, applied process-wide across all callers — they don't count requests per user or reject with 429.
