**No — outside `NewDBDriver`, no production code constructs the MySQL driver. The only other construction site is an in-package unit test.**

Evidence:

1. **Only one importer of the package.** `grep -rn "usememos/memos/store/db/mysql" --include=*.go .` returns exactly one hit: `store/db/db.go:8`. Since `DB` and `NewDB` are only reachable from outside via that import path, no other package in the repo — server, API layer, cmd, tests — can construct it.

2. **Only one call to the constructor.** The single `mysql.NewDB(profile)` call is in the factory's `switch` on `profile.Driver`, at `store/db/db.go:22` (alongside `sqlite.NewDB` at `:20` and `postgres.NewDB` at `:24`). `NewDB` itself is defined at `store/db/mysql/mysql.go:20` and returns the `store.Driver` interface, not the concrete type.

3. **Everything upstream goes through the factory.** The only driver-acquisition sites are `db.NewDBDriver(...)` — `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70`. Direct `sqlite.NewDB` calls do exist in tests (`store/demo_seed_test.go:24`, `store/deployment_config_test.go:416`), but there is no MySQL equivalent.

4. **One caveat — an in-package test literal.** `store/db/mysql/auth_config_test.go:12` does `db := &DB{}`, constructing a zero-valued driver directly. This is inside `package mysql` itself (so it doesn't need the import), has no `*sql.DB` connection, and exists only to exercise the pure error-classification method `IsRetryableAuthenticationMutationError`. If "outside the factory" is read strictly as "anywhere in the codebase," that's the one hit; if it means outside the driver package in real code paths, there are none.
