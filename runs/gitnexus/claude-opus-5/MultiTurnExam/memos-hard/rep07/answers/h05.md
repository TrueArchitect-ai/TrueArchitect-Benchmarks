**Explicit Go code — there is no database-level cascade for reactions. Each SQL driver deletes them by hand inside the `DeleteUser` transaction, via two separate statements.**

What I checked:

**1. The delete path itself.** `Store.DeleteUser` (`store/user.go:171-181`) just delegates to `s.driver.DeleteUser` and then invalidates cache. The real work is per-driver, and all three implementations are structurally identical — `deleteUserTargetsTx` calls two reaction cleanups:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`store/db/mysql/user_delete.go:388-397`, `store/db/postgres/user_delete.go:380`, `store/db/sqlite/user_delete.go:380`). This removes reactions *other people* left on the deleted user's memos. The content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + memo.UID` strings (`store/db/mysql/user_delete.go` — see the helper near the file end), matching how reactions reference content by resource name rather than by numeric FK.
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/mysql/user_delete.go:404-407`, and line `400` in both the postgres and sqlite files). This removes reactions the deleted user left on *anyone's* memos.

Both are invoked from `deleteUserTargetsTx` at `store/db/mysql/user_delete.go:96` and `:102` (same line numbers in `store/db/postgres/user_delete.go` and `store/db/sqlite/user_delete.go`), inside the transaction opened at `store/db/mysql/user_delete.go:30` and committed at `:51`, so reaction cleanup is atomic with the user row deletion.

**2. Ruled out a DB-level rule.** The `reaction` table is declared with no foreign keys at all — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — in all three current schemas: `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/sqlite/LATEST.sql:92-99` (originals at `store/migration/*/0.20/00__reaction.sql`). Grepping `FOREIGN KEY|ON DELETE|REFERENCES` across `store/migration/` shows cascades only on `memo_share.memo_id` and on legacy sqlite tables — never on `reaction`. A cascade would be impossible for the `content_id` half anyway, since it stores a `memos/{uid}` string, not a memo ID.

Worth noting: the ordering is deliberate — reactions are deleted *before* the memos (`deleteMemosTx`) and the user row (`deleteUserRowTx`), because the content-ID lookup depends on the memo tree collected earlier by `listDeleteUserMemoTreeIterative`, which also walks `COMMENT` relations so reactions on the deleted user's comment memos are covered too.
