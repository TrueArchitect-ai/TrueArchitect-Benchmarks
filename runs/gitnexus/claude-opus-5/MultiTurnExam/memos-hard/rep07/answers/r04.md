**Premise correction: neither. There is no message broker in this project — no NATS, no RabbitMQ, no Kafka, no AMQP client of any kind, and therefore no queue declaration.** A case-insensitive search for `nats|rabbitmq|amqp|kafka|nsq|streadway` across the Go sources returns only false positives (the substring `nSQ` inside `openMigrationSQLDB` in `store/test/migrator_upgrade_test.go:157`), and `go.mod` lists no broker client library.

**Actual mechanism — an in-process buffered Go channel with a fixed worker pool, all inside `internal/webhook/webhook.go`:**

- **The "queue"** is a package-level buffered channel holding 128 payloads: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`. That line is the closest thing to a queue declaration.
- **The "workers"** are 4 goroutines started in the package `init()` — `internal/webhook/webhook.go:42-55`. Each ranges over the channel and calls `Post(payload)`, logging a warning on failure.
- **Producing** happens in `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send: if the buffer is full the payload is **dropped** with a warning (`:191-195`) rather than blocking the RPC handler. Producers are the memo webhook dispatchers at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.
- **Consuming/delivery** is `Post` (`internal/webhook/webhook.go:120`), which marshals the JSON body, adds Standard Webhooks HMAC headers, and issues the request via `safeClient.Do` at `:152`.

Consequences worth knowing, since they differ sharply from broker-backed delivery: the queue lives only in process memory, so pending webhooks are lost on restart; there is no persistence, no acknowledgement, no retry, and no dead-letter path — a failed `Post` is logged and discarded; and overflow silently drops events once 128 are backed up. Concurrency is fixed at 4 in-flight deliveries, each with a 30-second timeout (`internal/webhook/webhook.go:27`).
