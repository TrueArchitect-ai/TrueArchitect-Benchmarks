**Premise correction: there is no Redis in this project.** `grep -rni "redis"` across all Go sources returns nothing, and `go.mod` has no Redis client dependency. There is no external cache server, no connection string, and no cache-related config flag — nothing in `cmd/memos/main.go` or `internal/profile/profile.go` mentions a cache endpoint.

**Actual mechanism:** the cache layer is a hand-rolled, in-process, in-memory cache.

- **Implementation** — `store/cache/cache.go`: a `Cache` struct backed by a `sync.Map` plus an atomic item counter (`store/cache/cache.go:65-72`), satisfying a local `Interface` (`:10-32`). Entries are `item{value, expiration, size}` (`:34-38`), and a background goroutine sweeps expired entries on a ticker (stopped by `Cache.Close`, `:187`).
- **Where it's "configured"** — `store.New` (`store/store.go:38-61`), not a connection setup. It builds one `cache.Config` literal at `store/store.go:40-45` and uses it for all three caches: `instanceSettingCache`, `userCache`, `userSettingCache` (`:51-53`, fields declared at `:27-29`).

**TTL for user entries: 10 minutes.** `cacheConfig.DefaultTTL = 10 * time.Minute` (`store/store.go:41`). Every user write goes through `Cache.Set`, which forwards the default TTL to `SetWithTTL` (`store/cache/cache.go:93-95`), stamping `expiration: time.Now().Add(ttl)` (`:112`). No caller anywhere in the repo uses `SetWithTTL` directly, so users get exactly the default — same as the other two caches. The user-cache writes are at `store/user.go:98`, `:122`, `:132`, `:143`, and `:167`, all keyed by `userCacheKey(user.ID)`.

Two related settings from the same config: `CleanupInterval: 5 * time.Minute` (`store/store.go:42`) and `MaxItems: 1000` (`:43`), so entries can also be evicted by capacity before their TTL expires. And note the cache is keyed by user **ID** only — `Store.GetUser` short-circuits on the cache solely when `find.ID != nil` (`store/user.go:149-156`), so username-based lookups always hit the database regardless of TTL.
