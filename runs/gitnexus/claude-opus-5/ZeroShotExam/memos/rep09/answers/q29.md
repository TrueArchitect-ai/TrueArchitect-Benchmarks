## Frontend: `web/src/connect.ts`

`authInterceptor` (`web/src/connect.ts:156-178`) is a `@connectrpc/connect` `Interceptor` installed on the single shared `createConnectTransport` (`web/src/connect.ts:184-189`), from which every service client (memo, user, attachment, AI, shortcut, IdP, instance, auth) is created. So all RPCs go through it.

Its flow:
1. `getRequestToken()` (`connect.ts:124-150`) returns the current access token, and *proactively* refreshes it if `isTokenExpired(REQUEST_TOKEN_EXPIRY_BUFFER_MS)` — important for public endpoints like `ListMemos` where an expired token would silently downgrade to guest-scoped data.
2. Sets `Authorization: Bearer <token>` (`connect.ts:97-100`).
3. On a `Code.Unauthenticated` response, refreshes once and retries, marking the retry with an `X-Retry: true` header to prevent loops; if the refresh fails it calls `redirectOnAuthFailure()` (`web/src/utils/auth-redirect.ts`).

Refresh itself uses a **separate transport with no interceptors** (`connect.ts:65-72`) to avoid recursion, and all callers funnel through `tokenRefreshManager` (`connect.ts:30-51`, exported as `refreshAccessToken`) so concurrent refreshes dedupe — this matters because `web/src/hooks/useTokenRefreshOnFocus.ts` also refreshes proactively on tab focus. All fetches use `credentials: "include"` (`connect.ts:57-62`) so the refresh cookie is sent.

Token storage lives in `web/src/auth-state.ts`: access token + expiry in `localStorage` under `memos_access_token` / `memos_token_expires_at`, mirrored in memory, and synced across tabs via a `BroadcastChannel` named `memos_token_sync` so only one tab hits the refresh endpoint.

## Token kinds

- **Access token (JWT)** — 15 min, audience `user.access-token`, stateless signature validation. Held by the frontend in localStorage, sent as `Authorization: Bearer`. (`server/auth/token.go:37-40,133-160`)
- **Refresh token (JWT)** — 30 days, audience `user.refresh-token`, carried in the HttpOnly cookie `memos_refresh`, validated against the DB for revocation via its `tid` claim. Never touched by JS. (`server/auth/token.go:42-49,162-187`; store side: `store/user_setting.go` `GetUserRefreshTokens`/`AddUserRefreshToken`)
- **Personal Access Token** — prefix `memos_pat_`, SHA-256 hashed at rest, long-lived, for programmatic clients rather than the web UI. (`server/auth/token.go:51-52,189-203`)

## Backend: `server/auth/`

The package doc at `server/auth/token.go:1-11` states it explicitly. `Authenticator.resolveBearer` (`server/auth/authenticator.go:149-175`) branches on the `memos_pat_` prefix: PAT → DB lookup, otherwise Access Token V2 → `ParseAccessTokenV2` (`token.go:219-233`), which enforces HS256, `kid: v1`, issuer `memos`, audience, and `type: "access"`. `AuthenticateToUser` (`authenticator.go:190-208`) falls back to the refresh cookie via `ExtractRefreshTokenFromCookie` (`server/auth/extract.go`).

It's wired into the API through `Authorizer` in `server/router/api/v1/authz.go:27,36,44` (`auth.NewAuthenticator(store, secret)`), which then runs `CheckAccess` against the method lists in `server/router/api/v1/acl_config.go`.
