**Tables written: `memo`, `memo_relation`, `attachment` (+ `memo_share` via DB-level FK cascade on MySQL/Postgres only).**

### Write path

`store.Store.DeleteMemo` (`store/memo.go:140-159`) is the cascade point — it does the cleanup in application code before deleting the row:

1. **`memo_relation`** — two `DeleteMemoRelation` calls, one on `MemoID`, one on `RelatedMemoID`, so both directions are cleared (`store/memo.go:142-147`; SQL at `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — lists attachments by `MemoID` and calls `Store.DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the blob/local file before the row delete (`store/attachment.go:132-148`, SQL at `store/db/sqlite/attachment.go:212`).
3. **`memo`** — the driver `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).

The API layer `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) additionally lists comment relations and calls `store.DeleteMemo` for each comment memo first (`:568-577`), so the same three tables are hit once per comment as well.

### Cascade caveat: `memo_share`

`memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`). On MySQL/Postgres the engine cascades. On SQLite it does **not** — the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so FK enforcement is off and `memo_share` rows are orphaned. There's no explicit share-cleanup code in `Store.DeleteMemo`.

### Read-only / not deleted

- **`reaction`** is read but never deleted. `memo_service.go:545-550` lists reactions only to build the webhook payload; nothing removes them, and `reaction.content_id` is an opaque string (`memos/{uid}`) with no FK, so reaction rows survive the memo. This is the same orphaning class as `memo_share` on SQLite.
- `memo`, `user`, `attachment`, `memo_relation`, and the instance-setting table are also read during permission checks and webhook/SSE payload construction.
