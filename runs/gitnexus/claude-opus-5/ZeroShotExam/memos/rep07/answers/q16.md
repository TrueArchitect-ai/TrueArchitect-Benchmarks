`store.DeleteMemo` (`/bench/home/work/store/memo.go:140-158`) deletes, in order, before calling `s.driver.DeleteMemo`:

1. **`memo_relation` rows where this memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (memo.go:142)
2. **`memo_relation` rows where this memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (memo.go:145)
3. **Attachment records linked to the memo** — listed via `ListAttachments{MemoID: &delete.ID}` and removed one-by-one with `s.DeleteAttachment` (memo.go:149-156). Each `DeleteAttachment` also removes the attachment's underlying stored blob/local file first (`/bench/home/work/store/attachment.go:132-149`, `deleteAttachmentStorageImpl` at attachment.go:202).

Note on scope: comment memos are not handled here — the API layer deletes child comment memos before calling the store (`/bench/home/work/server/router/api/v1/memo_service.go:566-580`), and each of those recurses through the same store cleanup. Reactions and memo shares are not deleted by `store.DeleteMemo`; the API only *reads* reactions for the webhook payload (memo_service.go:544).
