**Engine:** Google CEL (`github.com/google/cel-go`), wrapped by the in-repo memo filter engine at **`internal/filter/`** — `engine.go`, `schema.go`, `parser.go`, `ir.go`, `render.go` (documented in `internal/filter/README.md`).

**Mechanism (one sentence):** The CEL string is compiled by `cel-go` against a memo-specific env/schema (`internal/filter/schema.go:NewSchema`, exposed via `filter.DefaultEngine()` in `internal/filter/engine.go:110`), the resulting CEL AST is normalized by `internal/filter/parser.go:buildCondition` into a dialect-agnostic IR condition tree (`internal/filter/ir.go`), and the renderer in `internal/filter/render.go` walks that IR to emit a dialect-specific `WHERE` fragment plus bound args — with per-dialect column expressions from the schema's `Expressions` map and per-dialect placeholders (`$n` for Postgres, `?` otherwise, `render.go:842 addArg`).

**Request path:**
- `proto/api/v1/memo_service.proto:326` declares `ListMemosRequest.filter` as a CEL expression.
- `server/router/api/v1/memo_service.go:211-215` validates it (`validateFilter`, defined at `server/router/api/v1/shortcut_service.go:336`, which compiles against the driver's dialect) and appends it to `memoFind.Filters`.
- Each driver then compiles+renders it with its own dialect via `filter.AppendConditions` (`internal/filter/helpers.go:9`): `store/db/sqlite/memo.go:57-61` (`DialectSQLite`), `store/db/postgres/memo.go:54-58` (`DialectPostgres`), `store/db/mysql/memo.go:65-69` (`DialectMySQL`).

Dialect differences are encapsulated in the renderer: JSON access (`json_extract` / `JSON_EXTRACT` / `->>`), tag membership (SQLite `LIKE`, MySQL `JSON_CONTAINS`, Postgres `@>`), timestamp extraction (`strftime` / `EXTRACT` / MySQL date funcs, `render.go:222`), and string length (`CHAR_LENGTH` on MySQL, `render.go:298`).
