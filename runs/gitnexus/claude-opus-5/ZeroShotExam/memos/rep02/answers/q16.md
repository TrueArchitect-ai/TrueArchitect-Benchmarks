`store.DeleteMemo` (`store/memo.go:140-159`) removes these before calling `s.driver.DeleteMemo` on the memo row:

1. **Memo relations where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **Memo relations where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments{MemoID: &delete.ID}` and deleted one by one with `s.DeleteAttachment` (`store/memo.go:149-157`), which also deletes the underlying stored file/blob before the attachment row (`store/attachment.go:132-149`)

Notes on the surrounding call path: the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) first deletes each comment memo via a separate `store.DeleteMemo` call (`memo_service.go:567-577`) — so comment memos and their own relations/attachments go first, but that's the service layer, not the store. Reactions and memo shares are *not* deleted by `store.DeleteMemo`; the handler only reads reactions for the webhook payload (`memo_service.go:545-550`).
