**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share` (DB-level FK cascade, MySQL/Postgres only).**

**Explicit cascade code in `store.Store.DeleteMemo`** (`store/memo.go:140-159`), in order:

1. **`memo_relation`** — two deletes, one matching `memo_id`, one matching `related_memo_id` (`store/memo.go:142-147` → `store/db/sqlite/memo_relation.go:137`, and the postgres/mysql equivalents).
2. **`attachment`** — lists attachments by `MemoID` and deletes each via `Store.DeleteAttachment` (`store/memo.go:149-157` → `store/attachment.go:132-149` → `store/db/sqlite/attachment.go:211`). This also removes the underlying blob/local file, which is not a table.
3. **`memo`** — the row itself (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:243`, `store/db/mysql/memo.go:259`). All three drivers issue a plain single-row `DELETE FROM memo`.

**API-layer cascade** in `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`): before deleting the target memo it looks up comment relations and calls `Store.DeleteMemo` on each comment memo (`memo_service.go:567-577`), so the same three tables are hit once per comment as well.

**`memo_share`** — declared `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`). Caveat worth flagging: SQLite opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does **not** fire and `memo_share` rows are left orphaned; it only takes effect on Postgres/MySQL.

**Not affected: `reaction`.** `DeleteMemo` lists reactions by `ContentID` (`memo_service.go:545-550`) but only to build the webhook payload — no delete is issued, so reaction rows keyed to the deleted memo's resource name survive.
