`Store.DeleteMemo` (`store/memo.go:140-159`) performs this cleanup before issuing the `DELETE FROM memo` row delete:

1. **`memo_relation` rows where the memo is the source** — `driver.DeleteMemoRelation(&DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`).
2. **`memo_relation` rows where the memo is the target/related memo** — `driver.DeleteMemoRelation(&DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`).
3. **`attachment` rows linked to the memo** — it lists them via `ListAttachments(&FindAttachment{MemoID: &delete.ID})` and deletes each with `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying blob/local file via `DeleteAttachmentStorage` before deleting the row (`store/attachment.go:132-148`).

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`; SQL at `store/db/sqlite/memo.go:237` and `store/db/postgres/memo.go:244`).

Two things not done by the store layer, for contrast: **comment memos** are deleted by the API handler before it calls `Store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`), and **reactions** are only read for the webhook payload (`memo_service.go:545-550`) — the store's `DeleteMemo` does not delete reaction records.
