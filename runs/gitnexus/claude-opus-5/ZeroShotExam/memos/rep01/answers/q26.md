**Tables affected: `memo`, `memo_relation`, `attachment` (+ `memo_share` via DB-level FK cascade on MySQL/Postgres only)**

**Explicit cascade code** — `Store.DeleteMemo` at `store/memo.go:140-159` does, in order:
1. `memo_relation` — two `DeleteMemoRelation` calls, one matching `memo_id`, one matching `related_memo_id` (`store/memo.go:142-147`; SQL at `store/db/sqlite/memo_relation.go:149`).
2. `attachment` — lists attachments with `MemoID` and deletes each via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying file/object storage (`store/attachment.go:132-148`) before the row delete (`store/db/sqlite/attachment.go:212`).
3. `memo` — the driver delete itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`, plus the mysql/postgres equivalents).

**API layer** (`server/router/api/v1/memo_service.go:518-593`) adds one more `memo` effect: before deleting the target memo it lists comment relations and calls `Store.DeleteMemo` for each comment memo (lines 567-577), so additional `memo` rows (and their own `memo_relation`/`attachment` rows) go too — one level deep only, not recursive.

**`memo_share`** is deleted only by the database, via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). Note this does **not** fire on SQLite — the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so SQLite deployments leave orphaned `memo_share` rows.

**Not touched:** `reaction`. `DeleteMemo` lists reactions only to build the webhook payload (`memo_service.go:545-550`); nothing deletes them, and the `reaction` table has no FK to `memo` (it keys off a string `content_id`, `store/migration/sqlite/LATEST.sql:92-99`), so reaction rows are orphaned on every backend.
