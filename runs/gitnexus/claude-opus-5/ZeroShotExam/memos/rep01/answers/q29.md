**Frontend interceptor — `web/src/connect.ts:156`**

A Connect-RPC `Interceptor` attached to the shared transport (`web/src/connect.ts:184-189`), which backs every generated service client (memo, user, attachment, AI, shortcut, IdP…). Per request it:

1. Calls `getRequestToken()` (`connect.ts:124`) and sets `Authorization: Bearer <token>` (`connect.ts:97`).
2. **Preflight refresh** — if the token expires within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30s, `auth-state.ts:18`), it refreshes first. The comment at `connect.ts:136-139` explains why: on public endpoints like `ListMemos` an expired token would silently return guest-scoped data instead of 401'ing.
3. **Reactive retry** — on `Code.Unauthenticated`, refresh once, re-send with an `X-Retry: true` header guard against loops, and `redirectOnAuthFailure()` if the refresh fails (`connect.ts:163-177`).

Refresh itself goes through a *separate* transport with no interceptors (`connect.ts:65-70`) to avoid recursion, and through `tokenRefreshManager` (`connect.ts:30-51`) which dedupes concurrent refreshes — needed because `web/src/hooks/useTokenRefreshOnFocus.ts` also refreshes proactively on tab focus and would otherwise race server-side token rotation.

**Tokens managed — `web/src/auth-state.ts`**

| Token | Storage | Lifetime |
|---|---|---|
| Access token (JWT) | in-memory + `localStorage["memos_access_token"]` / `memos_token_expires_at` | 15 min (`server/auth/token.go:40`) |
| Refresh token (JWT) | HttpOnly cookie `memos_refresh`, sent via `credentials: "include"` — never touched by JS | 30 days (`token.go:43`) |
| PAT | not browser-side; `memos_pat_` prefix for API clients | configurable |

`auth-state.ts` also syncs freshly refreshed tokens across tabs over a `BroadcastChannel` (`memos_token_sync`, lines 26-50) so only one tab hits the refresh endpoint. Note `getAccessToken()` deliberately does *not* evict expired tokens (lines 64-68) — `hasStoredToken()` needs them present to decide a refresh is worth attempting.

**Backend validation — `server/auth/`**

- `token.go` — JWT mint/parse. HS256, `iss: memos`, `kid: v1`, audience-separated: `user.access-token` vs `user.refresh-token`, with an explicit `type` claim check so an access token can't be swapped for a refresh token (`token.go:229`, `:245`).
- `authenticator.go` — `Authenticator.Authenticate()` resolves the Bearer token: access tokens validate **statelessly** by signature (`:41`); refresh tokens additionally hit the DB for revocation and expiry (`:61-99`); PATs validate by SHA-256 hash lookup (`:102`).
- `extract.go` — pulls the bearer token from the header and the refresh token from the cookie.
- `context.go` — stashes `UserClaims` / `AccessToken` on the request context.

Wired into the API at `server/router/api/v1/connect_interceptors.go:222` (`in.authorizer.Authenticate(ctx, authHeader)` → `auth.ApplyToContext`), with unauthenticated method allowlists in `server/router/api/v1/acl_config.go` (`PublicMethods`, `AuthBootstrapMethods`). The same package is reused by `server/router/fileserver`, so attachment downloads authenticate identically.
