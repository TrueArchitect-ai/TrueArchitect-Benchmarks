`Store.DeleteMemo` (`store/memo.go:140-159`) — reached from the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`, calling the store at line 580) — deletes these before issuing the `DELETE FROM memo` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`):

1. **Memo relations where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **Memo relations where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments{MemoID}` and removed one by one with `Store.DeleteAttachment` (`store/memo.go:149-157`); that call also deletes the attachment's underlying stored file/blob via `DeleteAttachmentStorage` before removing the attachment row (`store/attachment.go:132-148`).

Two things the store layer does *not* do, for contrast:

- **Comment memos** are deleted by the API layer, not the store: the handler lists `MemoRelationComment` relations pointing at the memo and calls `Store.DeleteMemo` on each comment first (`server/router/api/v1/memo_service.go:567-577`), which recursively applies the same relation/attachment cleanup.
- **Reactions** are only *read* in the delete path (for the webhook payload, line 545); no reaction rows are deleted by `Store.DeleteMemo`.
