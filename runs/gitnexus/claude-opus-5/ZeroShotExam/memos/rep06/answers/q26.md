**Tables affected: `memo`, `memo_relation`, `attachment` — plus `memo_share` via DB-level FK cascade (Postgres/MySQL only).**

**Path:** `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) → for each comment child memo and then the memo itself → `Store.DeleteMemo` (`store/memo.go:140`) → driver `DeleteMemo`.

Per deleted memo id, `Store.DeleteMemo` (`store/memo.go:140-159`) does, in order:

1. **`memo_relation`** — two explicit cascade deletes, `MemoID = id` and `RelatedMemoID = id` (`store/memo.go:142-147`; SQL in `store/db/sqlite/memo_relation.go:137`, and the postgres/mysql equivalents).
2. **`attachment`** — lists attachments with `MemoID = id` and deletes each via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the backing blob/local file before the row (`store/attachment.go:132-149`).
3. **`memo`** — `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:236`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

The service layer additionally repeats this whole sequence for every child comment memo before deleting the parent (`memo_service.go:567-582`), so extra `memo` / `memo_relation` / `attachment` rows go with the comments.

**`memo_share`** — declared `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:101-109`, `postgres/LATEST.sql:101-109`, `mysql/LATEST.sql:101-109`). There is no Go code deleting it on this path, so it only clears on Postgres and MySQL. On SQLite the connection is opened with `?_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the cascade does not fire and `memo_share` rows are left orphaned.

**Not touched: `reaction`.** `DeleteMemo` lists reactions only to build the webhook payload (`memo_service.go:545-565`); no delete follows, and `reaction` has no FK to `memo` (it keys off a text `content_id`). Reaction rows are only cleaned up by per-reaction deletes (`store/reaction.go:39`) or user deletion (`store/db/*/user_delete.go:383`), so deleting a memo leaves its reaction rows behind on every backend.
