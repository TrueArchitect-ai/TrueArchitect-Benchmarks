`Store.DeleteMemo` (`store/memo.go:140-159`) deletes, in order, before calling `s.driver.DeleteMemo`:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments{MemoID: &delete.ID}` and removed one by one with `Store.DeleteAttachment` (`store/memo.go:149-157`), which also deletes the attachment's underlying stored file/blob (`store/attachment.go:132-148`, via `DeleteAttachmentStorage`).

Only then does it issue the `DELETE FROM memo` row delete in the driver (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`).

Note that comment memos are *not* handled here — the API layer (`server/router/api/v1/memo_service.go:567-575`) first lists comment relations and recursively calls `Store.DeleteMemo` on each comment memo; reactions are likewise cleaned up in the service layer, not in `store.DeleteMemo`.
