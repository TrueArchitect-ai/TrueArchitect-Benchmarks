**Tables affected: `memo`, `memo_relation`, `attachment`, `memo_share` (Postgres/MySQL only, via FK cascade).**

### Call path
`ConnectServiceHandler.DeleteMemo` (`server/router/api/v1/connect_services.go:338`) → `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) → `Store.DeleteMemo` (`store/memo.go:140`) → driver `DeleteMemo`.

### Per table

| Table | How it's hit |
|---|---|
| `memo` | The target row: `DELETE FROM memo WHERE id = ?` in each driver (`store/db/sqlite/memo.go:236`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`). Additionally, comment memos are deleted first — the service lists `MemoRelationComment` relations pointing at the memo and calls `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:568-577`). |
| `memo_relation` | Explicit cascade in `store/memo.go:142-147`: two `DeleteMemoRelation` calls, one by `memo_id`, one by `related_memo_id`, so both sides of every relation are removed (`store/db/sqlite/memo_relation.go:137`). |
| `attachment` | Explicit cascade in `store/memo.go:149-157`: lists attachments by `MemoID` and calls `Store.DeleteAttachment` per row (`store/attachment.go:132`), which also removes the backing local file or S3 object before the DB delete. |
| `memo_share` | FK cascade only: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:106`. There is no explicit `memo_share` delete in the memo path — the only explicit ones are in the user-delete path (`store/db/*/user_delete.go:406,411`). |

### Two things worth flagging

- **On SQLite the `memo_share` cascade does not fire.** The connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`, deliberately, per the comment at lines 39-41), so the FK declared in the schema is inert and `memo_share` rows are orphaned on SQLite deployments. Postgres and MySQL enforce it.
- **`reaction` is *not* touched.** `DeleteMemo` lists reactions at `server/router/api/v1/memo_service.go:545-550`, but only to build the webhook payload — nothing deletes them. `reaction.content_id` is a text key (`memos/{uid}`) with no FK (`store/migration/sqlite/LATEST.sql:89-97`), and the only `DeleteReaction` callers are the reaction service (`server/router/api/v1/reaction_service.go:141`) and the user-delete path. So reactions on a deleted memo are left behind.
