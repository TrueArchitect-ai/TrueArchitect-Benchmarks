`Store.DeleteMemo` (`store/memo.go:140-159`) deletes, in order, before issuing the `DELETE FROM memo`:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachment records linked to the memo** — it lists them via `ListAttachments{MemoID}` and calls `DeleteAttachment` per attachment (`store/memo.go:148-157`); each of those also removes the backing file/object from storage first (`store/attachment.go:132-148`) before deleting the `attachment` row.

Then the memo row itself: `s.driver.DeleteMemo` (`store/memo.go:158`), which is just `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237-248`).

Notes on scope:
- The store layer does **not** delete reactions or memo shares here — the API handler only *lists* reactions for the webhook payload (`server/router/api/v1/memo_service.go:544-549`).
- Child comment memos are deleted by the API handler before the parent, in a loop that calls `Store.DeleteMemo` on each comment (`server/router/api/v1/memo_service.go:566-576`), so each comment goes through the same relation + attachment cleanup.
