**Tables affected: `memo`, `memo_relation`, `attachment`** (plus `memo_share` only via DB-level FK cascade, which is disabled on SQLite).

**Trace**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) does reads only for the webhook payload (`ListReactions`, `ListAttachments`, `ListMemoRelations`), then:
- lists comment relations and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:569-577`)
- calls `Store.DeleteMemo` for the memo itself (`memo_service.go:580`)

`Store.DeleteMemo` (`store/memo.go:140-159`) is where the explicit cascade lives:
1. `memo_relation` — two `DeleteMemoRelation` calls, by `memo_id` and by `related_memo_id` (`store/memo.go:142-147`)
2. `attachment` — lists attachments for the memo and deletes each via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying file/blob storage (`store/attachment.go:132-149`) — that's filesystem/S3, not a table
3. `memo` — the row itself, via `driver.DeleteMemo` (`store/db/sqlite/memo.go:237-248`, `store/db/postgres/memo.go:244-255`; both are a bare `DELETE FROM memo WHERE id = ?`)

**Not touched by code:**
- `memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the Postgres (`store/migration/postgres/LATEST.sql:108`) and MySQL (`store/migration/mysql/LATEST.sql`) schemas, and in SQLite (`store/migration/sqlite/LATEST.sql:109`) — but SQLite opens its connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the cascade does **not** fire there. So memo_share rows are removed on Postgres/MySQL and left orphaned on SQLite.
- `reaction` — reactions are keyed by `content_id` (the memo resource name string) with no FK and no delete call, so reaction rows are orphaned on every backend. `DeleteMemo` reads them (`memo_service.go:545`) only to build the webhook payload.
- `inbox` — memo-related notifications are not cleaned up.
