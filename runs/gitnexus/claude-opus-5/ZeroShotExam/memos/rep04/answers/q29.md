### The interceptor — `web/src/connect.ts:156`

`authInterceptor` is a Connect-RPC `Interceptor` wired into the single shared transport at `web/src/connect.ts:184-189`; every service client (`memoServiceClient`, `userServiceClient`, etc., lines 192-203) is created from that transport, so all frontend API calls pass through it. Its flow:

1. Calls `getRequestToken()` (`connect.ts:124`) and sets `Authorization: Bearer <token>` (`setAuthorizationHeader`, line 97).
2. **Preflight refresh**: if the token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30s) of expiry it refreshes first — deliberately, so public endpoints like ListMemos don't silently return guest-scoped data (`connect.ts:136-147`).
3. **Reactive refresh**: on a `Code.Unauthenticated` error it refreshes, retries once marked with an `X-Retry` header, and on failure calls `redirectOnAuthFailure()` (`connect.ts:161-177`).

Refresh itself goes through a separate `refreshTransport` with **no** interceptors to avoid recursion (`connect.ts:65-72`), and all callers funnel through `tokenRefreshManager` (`connect.ts:30-51`) to dedupe concurrent refreshes racing with `web/src/hooks/useTokenRefreshOnFocus.ts`.

### Tokens it manages

- **Access token (JWT)** — held in `web/src/auth-state.ts`: in-memory plus `localStorage` keys `memos_access_token` / `memos_token_expires_at`, with cross-tab sync over a `memos_token_sync` BroadcastChannel (`auth-state.ts:26-50`). This is what the interceptor puts in the `Authorization` header.
- **Refresh token** — never touched by JS; it's the `memos_refresh` HttpOnly cookie (`server/auth/token.go:49`, cookie built at `server/router/api/v1/auth_service_session.go:224`). The frontend only rides it via `credentials: "include"` on the fetch wrapper (`connect.ts:57-62`) when calling `RefreshToken`.
- The same `Authorization` header also accepts **Personal Access Tokens** (`memos_pat_`-prefixed) for programmatic clients.

### Backend validation — `server/auth/`

`server/auth/authenticator.go` is the shared validator used by the Connect interceptor, gRPC interceptor, and file server:

- `AuthenticateByAccessTokenV2` (line 41) — stateless HS256 JWT parse via `ParseAccessTokenV2` (`server/auth/token.go:220`), checking issuer `memos` and audience `user.access-token`.
- `AuthenticateByRefreshToken` (line 61) — parses, then does a DB revocation + expiry check against `store.GetUserRefreshTokenByID`.
- `AuthenticateByPAT` (line 102) — hash lookup for personal access tokens.
- `resolveBearer` (line 149) dispatches on the `memos_pat_` prefix.

The HTTP entry point is `AuthInterceptor.WrapUnary` in `server/router/api/v1/connect_interceptors.go:218`, which reads the `Authorization` header, calls `Authenticate`, enforces `CheckAccess` against the ACL in `server/router/api/v1/acl_config.go`, and returns `CodeUnauthenticated` — the exact error the frontend interceptor traps to trigger its retry.
