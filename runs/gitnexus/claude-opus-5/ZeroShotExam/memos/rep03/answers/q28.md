**Runners the server actually starts**

- **s3presign runner (`server/runner/s3presign/runner.go`)** — the only entry in `Server.startBackgroundRunners` (`server/server.go:153-174`). Trigger: one synchronous `RunOnce(ctx)` pass at startup (`server/server.go:163`), then a goroutine running `Run(s3Context)`, a plain `time.NewTicker` loop at a hardcoded `runnerInterval = 12h` (`server/runner/s3presign/runner.go:27-41`). Cancelled via its own `context.CancelFunc` stored in `backgroundRunnerCancels` and awaited by `waitBackgroundRunners` on shutdown. Note the startup `RunOnce` is passed the *parent* `ctx`, not `s3Context`.
- **Store cache janitors ×3 (`store/cache/cache.go:83`, `cleanupLoop` at :199-215)** — started implicitly, not by `startBackgroundRunners`: `store.New` constructs three caches (`instanceSettingCache`, `userCache`, `userSettingCache`) at `store/store.go:51-53`, and each `cache.New` launches a `cleanupLoop` goroutine. Trigger: `time.NewTicker(CleanupInterval)` = 5 minutes (`store/store.go:42`), stopped by `Cache.Close()`.
- **Webhook dispatch workers ×4 (`internal/webhook/webhook.go:42-52`)** — started by a package `init()`, so they exist as soon as the package is linked in. Trigger: not time-based — they block on the `asyncPostQueue` channel (cap 128) and fire per enqueued webhook payload.
- **Email dispatch workers ×2 (`internal/email/email.go:16-26`)** — same pattern, package `init()`. Trigger: consume `asyncEmailQueue` (cap 128), per enqueued message.
- **Per-connection SSE heartbeat (`server/router/api/v1/sse_handler.go:64`)** — not a background runner, but a ticker worth naming: 30s (`sseHeartbeatInterval`, :17), lives for the duration of each SSE request, driven by the request context.
- **PAT last-used writer (`server/auth/authenticator.go:179-185`)** — fire-and-forget goroutine per authenticated PAT request, not a scheduled worker.

**Unused scheduling infrastructure**

- **`internal/scheduler/` is dead code from the server's perspective.** It's a full cron implementation — cron parser (`parser.go`), job registry/validation (`job.go`), `Scheduler.Start`/`runJobWithSchedule` (`scheduler.go:90-164`), timezone support, and middleware (`Recovery`, `Logging`, `Timeout` in `middleware.go`). Its only importers are its own tests: `internal/scheduler/example_test.go` and `internal/scheduler/integration_test.go`. Nothing in `server/`, `cmd/`, or `store/` imports it, and no runner uses cron expressions — s3presign uses a raw ticker instead. `internal/scheduler/README.md` documents it as production-ready, which overstates its current role.
- Secondary note: **`server/runner/memopayload/` is not a runner** despite living under `server/runner/`. `RebuildMemoPayload` is called synchronously inline in request handling (`server/router/api/v1/memo_service.go:108` and `:447`); nothing schedules or backgrounds it.
