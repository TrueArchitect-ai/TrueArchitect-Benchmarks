**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share` (cascade, Postgres/MySQL only).**

How each is reached, starting from `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):

| Table | How it's hit |
|---|---|
| `memo` | `DELETE FROM memo WHERE id = ?` in each driver — `store/db/sqlite/memo.go:236`, `store/db/postgres/memo.go:243`, `store/db/mysql/memo.go:258`. Hit once for the target memo (`memo_service.go:580`) **and once per comment memo**, which the API layer enumerates via `ListMemoRelations` with type `COMMENT` and deletes in a loop (`memo_service.go:568-577`). |
| `memo_relation` | Explicit cascade in `store.DeleteMemo` (`store/memo.go:142-147`) — two `DeleteMemoRelation` calls, one on `memo_id`, one on `related_memo_id`, so rows where the memo is either side are removed. |
| `attachment` | Explicit cascade in `store/memo.go:149-157` — `ListAttachments({MemoID})` then `DeleteAttachment` per row, which issues `DELETE FROM attachment WHERE id = ?` (e.g. `store/db/sqlite/attachment.go:211`). This also deletes the underlying local/S3 blob (`store/attachment.go:141`), not just the row. |
| `memo_share` | Not touched by any Go code in this path; relies on the schema FK `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/{sqlite,postgres,mysql}/LATEST.sql:108-109`). |

Two caveats worth flagging:

- **`memo_share` does not actually cascade on SQLite.** The SQLite connection is opened with `?_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), which disables FK enforcement, so the `ON DELETE CASCADE` is inert and share rows are orphaned. Postgres and MySQL enforce FKs by default, so the cascade works there. (The separate user-deletion path compensates with an explicit `DELETE FROM memo_share WHERE memo_id IN (...)` — `store/db/sqlite/user_delete.go:411` — but `DeleteMemo` has no equivalent.)
- **`reaction` is *not* affected.** `DeleteMemo` reads reactions at `memo_service.go:545` only to build the webhook payload; nothing deletes them. The `reaction` table has no FK to `memo` in any of the three schemas (it keys off a text `content_id`), so reaction rows for a deleted memo are left orphaned. Only the user-deletion path cleans them (`store/db/sqlite/user_delete.go:383`).

`inbox` is untouched by this path.
