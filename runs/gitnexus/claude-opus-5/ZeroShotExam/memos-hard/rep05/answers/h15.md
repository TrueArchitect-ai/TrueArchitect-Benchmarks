h15.

Memo visibility is enforced independently in several places — there is **no single chokepoint**. Distinct enforcement sites:

**1. Single-memo read gate (Connect/gRPC API v1)** — `server/router/api/v1/memo_service.go:39` (`checkMemoReadAccess`). Archived → creator only; non-public → requires auth; `PRIVATE` → creator only. Called from `GetMemo` (`:356`), parent-memo resolution (`:367`), and `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`).

**2. List-query visibility filter (API v1 ListMemos)** — `server/router/api/v1/memo_service.go:219-227`. Anonymous → `VisibilityList = [PUBLIC]`; authenticated → CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`, or `[PUBLIC, PROTECTED]` when scoped to another creator.

**3. Relation/backlink filter** — `server/router/api/v1/memo_service_converter.go:178-187` (`batchConvertMemoRelations`) builds its own `memoFilter` so related-memo snippets don't leak private/protected memos.

**4. User-stats aggregation** — `server/router/api/v1/user_service_stats.go:84-91` (`ListAllUserStats`) and `:218-221` (`GetUserStats`) re-derive the same visibility predicate independently of ListMemos.

**5. Attachment access (API v1)** — `server/router/api/v1/attachment_service.go:445-452` (linked attachments inherit the memo's visibility), and `server/router/api/v1/memo_attachment_service.go:214-225` (`ListMemoAttachments`).

**6. Reactions (API v1)** — `server/router/api/v1/reaction_service.go:30-40` (`ListMemoReactions`) and `:83` (upsert path).

**7. Comment creation** — `server/router/api/v1/memo_service_comments.go:41` gates commenting on the parent memo's visibility, and `:52` forces the comment to inherit it.

**8. Raw file server (non-gRPC HTTP surface)** — `server/router/fileserver/fileserver.go:677-700`. Its own rules: `PUBLIC` + anonymous-allowed → open; valid non-expired `share_token` for that memo → open; otherwise auth required and `PRIVATE` → creator or `RoleAdmin`.

**9. Share-token bypass** — `server/router/api/v1/memo_share_service.go:153` (`GetMemoByShare`) deliberately skips the visibility check: a valid, non-expired share grants read access regardless of visibility (archived/missing still 404). Share creation/deletion is creator-or-superuser gated at `:43`, `:92`, `:133`.

**10. SSE broadcast delivery filter** — `server/router/api/v1/sse_hub.go:133-142` (`SSEClient.canReceive`): `PRIVATE` events go only to the creator or an admin; unknown visibility is denied.

**11. RSS feeds** — `server/router/rss/rss.go:90` (instance feed) and `:141` (per-user feed), both hard-pinned to `VisibilityList = [PUBLIC]`.

**12. Sitemap** — `server/router/frontend/frontend.go:150`, public-only memo listing.

**13. Notification/inbox and email delivery** — `server/router/api/v1/user_service_notifications.go:304` and `server/notification/email.go:307`, two separate copies of `canViewerAccessMemo` (they differ: the API one uses `isSuperUser`, the email one checks `RoleAdmin` directly). Mention notifications use a third variant, `canUserAccessMentionContext` / `shouldSkipMentionInbox` at `server/router/api/v1/memo_mention_helpers.go:56-89`.

Not a separate site: the MCP surface (`server/router/mcp/adapter.go:27-34`) replays requests through the same Echo server, so it inherits the API v1 checks rather than implementing its own.
