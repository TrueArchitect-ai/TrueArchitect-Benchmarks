Notes worth flagging:

- **The image bytes never touch the filesystem or S3.** Unlike attachments, the avatar is stored inline as a base64 data URI in the `user.avatar_url` column, so the "data layer" terminates at the SQL row — `parseDataURI` (fileserver.go:737) is what turns the column value into image bytes. The `Profile`/`s3` storage machinery in the same file is only for `serveAttachmentFile`.
- **The user cache is bypassed here.** `Store.GetUser` (store/user.go:149) only reads `userCache` when `find.ID` is set; this path passes `FindUser{Username: &identifier}`, so every avatar request falls through to `ListUsers` → driver → DB (the result is then written into the cache at store/user.go:143,167).
- **No per-user authorization on the target.** Past the anonymous check, any user's avatar is served to any requester — for a public instance, to anonymous visitors too. That's deliberate for public profiles, not an oversight I found evidence against.
- The service is wired into the echo server at `server/server.go:81-82`, registered before the gRPC gateway.
