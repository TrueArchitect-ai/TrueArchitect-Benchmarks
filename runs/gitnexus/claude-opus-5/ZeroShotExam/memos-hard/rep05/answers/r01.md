**Premise correction:** There is no Redis in this repository. `redis` appears nowhere in the Go source, and there is no Redis client in `go.mod` — no `go-redis`, `redigo`, or equivalent. There is no external cache service, no connection string, no cache host/port config, and no environment variable to point the cache at a server. Nothing connects anywhere.

**Actual mechanism:** the cache is an in-process, in-memory cache living entirely inside the server binary.

**Implementation** — `store/cache/cache.go`:
- `Cache` (`store/cache/cache.go:67`) is a thread-safe map built on `sync.Map` plus an `atomic.Int64` item counter. Each entry (`store/cache/cache.go:35`) holds the value, an absolute `expiration` time, and a rough size estimate.
- Eviction is by wall-clock expiry, checked lazily on `Get` (`store/cache/cache.go:135`) and eagerly by a background `cleanupLoop` goroutine (`store/cache/cache.go:200`) that sweeps on a ticker. A separate `cleanupOldest` (`store/cache/cache.go:253`) drops ~20% of entries when `MaxItems` is exceeded.
- State is per-process, so it is not shared across replicas and is lost on restart.

**Configuration** — `store/store.go:40-45`, in `store.New()`. Values are hardcoded Go literals, not read from config or env:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

The same `cacheConfig` value is used for all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). An identical set of defaults is also defined in `cache.DefaultConfig()` (`store/cache/cache.go:57`), but `store.New` builds its own literal rather than calling it.

**TTL for user entries: 10 minutes.** Every write to `userCache` in `store/user.go` goes through `Set` — `CreateUser` (`:98`), `CreateUserIfNoUsers` (`:122`), `UpdateUser` (`:132`), `ListUsers` (`:143`), `GetUser` (`:167`) — and `Set` (`store/cache/cache.go:93`) delegates to `SetWithTTL` with `c.config.DefaultTTL`. There is no per-user or per-entry TTL override: `SetWithTTL` is exported and tested, but outside of `Set` itself no production call site invokes it, so the 10-minute default is the only TTL any user entry ever receives.

Two details worth noting on top of the TTL:
- The TTL is a refreshed absolute deadline, not a fixed lifetime from first insert. Each `Set` recomputes `time.Now().Add(ttl)` (`store/cache/cache.go:112`), and because `GetUser` falls through to `ListUsers` on a miss and re-`Set`s, a frequently-read user's entry is repeatedly re-stamped.
- Deletion is explicit, not TTL-dependent: `deleteUserCache` (`store/user_delete.go:39`) removes the user key and its associated user-setting keys immediately.
