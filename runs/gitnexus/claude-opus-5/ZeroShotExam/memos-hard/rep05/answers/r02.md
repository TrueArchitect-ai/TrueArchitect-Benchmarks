**Premise correction: memos has no per-user API rate-limiting middleware.** There is nothing in the repo that counts requests per user (or per IP) and rejects over a threshold — no limiter, no token bucket, no throttling interceptor. So there are no request limits to report.

What actually exists on the request path:

**Echo-level middleware** (`server/server.go:51-52`):
- `middleware.Recover()`
- `newCORSMiddleware(profile)` — `server/cors.go`

**Connect/gRPC interceptor chain** (`server/router/api/v1/v1.go:133-137`), the full set, in order:
1. `NewMetadataInterceptor()` — HTTP headers → gRPC metadata
2. `NewLoggingInterceptor(logStacktraces)`
3. `NewRecoveryInterceptor(logStacktraces)`
4. `NewAuthInterceptor(authorizer)` — authentication and anonymous-access policy

All four are defined in `server/router/api/v1/connect_interceptors.go`. None does rate limiting.

**The only per-request limit is a size cap, not a rate cap:** `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` on the gateway mux (line 126) and the Connect mux (line 144), and via `connect.WithReadMaxBytes` on the Connect handlers (line 141). That bounds the size of a single request body, per request — it does not restrict how many requests a user may make.

Two things that can look like rate limiting but aren't:
- `store/auth_config.go:13` `authenticationMutationMaxAttempts = 3` — an optimistic-concurrency retry loop for config writes (`store/auth_config.go:74-82`), not a login-attempt limiter.
- `internal/email/doc.go:86` — a comment listing "Rate limit email sending to prevent abuse" as a consideration; it is documentation, not an implementation.

If you need per-user rate limiting, it would be a new interceptor added to the chain at `server/router/api/v1/v1.go:133`.
