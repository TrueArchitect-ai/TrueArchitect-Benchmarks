**Mechanism: explicit Go code — two DELETE statements per driver, inside the delete-user transaction. There is no database-level rule doing it.**

## What removes them

`deleteUserTargetsTx` runs two reaction deletes before the memos and the user row are dropped:

1. **`deleteReactionsByContentIDsTx`** — deletes *everyone's* reactions on the deleted user's memos (and on the recursively-collected `COMMENT` subtree), keyed by `content_id IN ('memos/<uid>', …)`, batched 500 at a time.
2. **`deleteReactionsByCreatorTx`** — deletes the user's own reactions on *anyone's* content: `DELETE FROM reaction WHERE creator_id = ?`.

Identical logic in all three drivers:
- `store/db/sqlite/user_delete.go:96` and `:102`; implementations at `:380` and `:400`
- `store/db/postgres/user_delete.go:96` and `:102`; implementations at `:380` and `:400`
- `store/db/mysql/user_delete.go:96` and `:102`; implementations at `:417` and `:437`

All of it runs in one transaction opened in `DeleteUser` (`store/db/sqlite/user_delete.go:29-59`), reached via the store wrapper `store/user.go:171`.

## Why it isn't a DB-level rule (what I checked)

- The `reaction` table DDL has **no foreign key at all** — just `creator_id INTEGER NOT NULL` and a `UNIQUE(creator_id, content_id, reaction_type)`, in every dialect: `store/migration/sqlite/LATEST.sql`, `store/migration/postgres/LATEST.sql`, `store/migration/mysql/LATEST.sql` (and the original `store/migration/*/0.20/00__reaction.sql`, `0.23/00__reactions.sql`).
- `content_id` is a text resource name (`"memos/" + uid`, built at `store/db/sqlite/user_delete.go:512`), so it *can't* carry an FK to `memo` anyway.
- Grepping the whole `store/migration/` tree for `CASCADE|FOREIGN KEY|REFERENCES|CREATE TRIGGER` returns hits only for `memo`, `user_setting`, `memo_share`, `memo_organizer`, etc. — never `reaction`. No triggers touch reactions.
- Even the FKs that do exist are inert on SQLite: the DSN sets `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so cascade cleanup is deliberately the application's job.

## Tests pinning the behavior

- `server/router/api/v1/test/user_service_delete_test.go:287-298` — reactions on the deleted user's memo and on their comment are empty afterward, while a peer's reaction on a foreign memo survives.
- `store/test/user_delete_test.go:217-220` — same survivor assertion at the store layer.
- `server/router/api/v1/test/user_service_delete_test.go:429-431` — with the `DeleteUserFailpointBeforeCommit` failpoint (`user_delete.go:47`), the reaction is still present, confirming the deletes are transactional rather than incidental.

One consequence worth noting: because cleanup is code-driven with no FK backstop, any future write path that inserts reactions outside this flow — or a new dialect driver — has to replicate both deletes; the database will not catch an omission.
