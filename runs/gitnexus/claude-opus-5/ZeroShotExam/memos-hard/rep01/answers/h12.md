**How I determined which of the three candidates runs:**

There are exactly three non-test implementations of `Driver.CreateMemo` — `store/db/sqlite/memo.go:15`, `store/db/mysql/memo.go:15`, `store/db/postgres/memo.go:15` (I enumerated them with GitNexus `context({name: "CreateMemo"})`, which returned 17 candidates, and cross-checked with a grep for `INSERT INTO memo` across `store/`). The selection is a single runtime switch, not build tags or DI:

- `db.NewDBDriver` — `store/db/db.go:14` — switches on `profile.Driver`: `"sqlite"` → `sqlite.NewDB`, `"mysql"` → `mysql.NewDB`, `"postgres"` → `postgres.NewDB`, default → error.
- `profile.Driver` comes from `viper.GetString("driver")` — `cmd/memos/main.go:43`.
- With no flags/env set, that resolves to the default registered in two places: `viper.SetDefault("driver", "sqlite")` — `cmd/memos/main.go:122` — and the flag default `rootCmd.PersistentFlags().String("driver", "sqlite", ...)` — `cmd/memos/main.go:130`. Both are `sqlite`, so a default install takes the `"sqlite"` branch.
- Corroborating: `Profile.Validate` — `internal/profile/profile.go:110` — has a SQLite-only fallback that synthesizes the DSN (`<data>/memos_prod.db`) when `Driver == "sqlite" && DSN == ""`, i.e. the zero-config path is explicitly the SQLite one. The MySQL/Postgres drivers have no such fallback and require an explicit DSN.

So the discriminator is config, resolved at startup: `viper` default `sqlite` → `NewDBDriver`'s switch → `sqlite.DB` → its `CreateMemo` runs the INSERT. The Postgres variant (`store/db/postgres/memo.go:38`) and MySQL variant are compiled in but never instantiated unless `--driver` / `MEMOS_DRIVER` says otherwise.

One note on the SQL itself: the SQLite path uses `RETURNING id, created_ts, updated_ts, row_status` with `QueryRowContext`, so the insert and the read-back of generated columns are a single statement.
