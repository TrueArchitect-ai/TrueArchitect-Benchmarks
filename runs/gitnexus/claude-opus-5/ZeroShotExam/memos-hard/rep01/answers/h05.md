**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside the per-driver `DeleteUser` transaction. There is no database-level rule: the `reaction` table has no foreign key and no `ON DELETE CASCADE` in any of the three dialects.

## What I checked

**1. The delete path.** `store.DeleteUser` (`store/user.go:171`) just delegates to `s.driver.DeleteUser`, so the real work is per-driver. Callers are `server/router/api/v1/user_service.go:414` and `server/router/api/v1/auth_service_sso.go:77`.

**2. The driver implementations.** Each driver has a `user_delete.go` that opens one transaction and runs an ordered list of deletes (`deleteUserTargetsTx`). Two of those steps target reactions:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, removing reactions *others left on the deleted user's memos*. The content IDs are built as `"memos/"+uid` by `memoContentIDsFromRefs`, over the recursive memo tree (the user's memos plus comment descendants).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user left *on anyone's* content.

Locations:
- `store/db/sqlite/user_delete.go:95,101` (calls), `:392` and `:414` (implementations)
- `store/db/mysql/user_delete.go:96,102` (calls), `:417`, `:437`
- `store/db/postgres/user_delete.go:96,102` (calls), `:380`, `:400`

**3. The schema — ruling out a DB-level rule.** I dumped the `reaction` CREATE TABLE from all three `LATEST.sql` files:

- `store/migration/sqlite/LATEST.sql`, `store/migration/mysql/LATEST.sql`, `store/migration/postgres/LATEST.sql`

In all three, `reaction` is `(id, created_ts, creator_id, content_id, reaction_type)` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — `creator_id` is a bare `INTEGER`/`INT` with no `REFERENCES user(id)`. Grepping `REFERENCES|ON DELETE` across all three schemas returns exactly one hit each (line ~108), and it's `memo_id REFERENCES memo(id) ON DELETE CASCADE` on a different table — not `reaction`. A cascade on `content_id` isn't even possible here, since it stores a resource name string (`memos/<uid>`), not a numeric memo FK.

**4. Test confirmation of the intended semantics.** Both the store-level and service-level tests assert the two-sided cleanup *and* that unrelated reactions survive:
- `server/router/api/v1/test/user_service_delete_test.go:287-298` — reactions on the deleted user's own memo and on their comment are empty, while a peer's reaction on a foreign memo is retained.
- `store/test/user_delete_test.go:217-220` — same "keep the peer's reaction" assertion.
- `server/router/api/v1/test/user_service_delete_test.go:429-431` — with the `before_commit` failpoint, the reaction is still present after rollback, confirming the deletes ride in the same transaction as the user row delete.

One consequence worth noting: because this is code-driven rather than FK-enforced, any path that removes a `user` row without going through `driver.DeleteUser` would orphan reactions — the database itself will not clean them up.
