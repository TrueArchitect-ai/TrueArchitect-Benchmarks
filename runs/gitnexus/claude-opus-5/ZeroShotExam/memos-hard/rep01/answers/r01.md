**Premise correction:** There is no Redis in this repository. `grep -ril "redis"` across the entire tree returns nothing, and `go.mod` has no Redis client (or any third-party cache library — no `ttlcache`, `golang-lru`, `go-cache`). The cache layer is a hand-rolled, in-process, in-memory cache. There is nothing to connect to and no connection to configure.

**Actual mechanism**

The cache is implemented in `store/cache/cache.go` — a thread-safe in-memory cache built on `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). Each entry is an `item` struct holding the value, an absolute `expiration time.Time`, and a rough size estimate (`store/cache/cache.go:35-39`).

Configuration is not external (no env var, no config file, no connection string). It's a `cache.Config` literal constructed in Go at store creation, `store/store.go:38-61`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That single config value is passed to all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`). An identical default lives in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), used by `NewDefault()`, but `store.New` builds its own copy rather than calling it.

**TTL for user entries: 10 minutes.** Every write path for users calls `s.userCache.Set(...)`, never `SetWithTTL`, so they all take the `DefaultTTL`:
- `CreateUser` — `store/user.go:98`
- `CreateUserIfNoUsers` — `store/user.go:122`
- `UpdateUser` — `store/user.go:132`
- `ListUsers` (caches each result) — `store/user.go:143`
- `GetUser` — `store/user.go:167`

`Set` simply delegates to `SetWithTTL(ctx, key, value, c.config.DefaultTTL)` (`store/cache/cache.go:93-95`), stamping `expiration: time.Now().Add(ttl)`. Cache keys are just the stringified user ID (`userCacheKey`, `store/user.go:88-90`).

Two details worth knowing about the 10-minute figure:

1. **Expiry is lazy plus swept.** `Get` checks `time.Now().After(itm.expiration)` and deletes on read (`store/cache/cache.go:135-144`); a background `cleanupLoop` goroutine sweeps expired entries every `CleanupInterval` (5 min) (`store/cache/cache.go:200-250`). So an entry can outlive its TTL in memory until read or swept, but it is never *served* past 10 minutes.

2. **Entries can be dropped early.** With `MaxItems: 1000`, exceeding the cap triggers `cleanupOldest`, which evicts ~20% of max items (`store/cache/cache.go:253-313`). On an instance with more than 1000 users, user entries get evicted well before 10 minutes. Explicit invalidation also happens on user deletion — `s.userCache.Delete` at `store/user_delete.go:40`, with the user's settings purged at `store/user_delete.go:45`.

Because this cache is per-process and in-memory, it is not shared across replicas — each server instance keeps its own copy with its own 10-minute clock.
