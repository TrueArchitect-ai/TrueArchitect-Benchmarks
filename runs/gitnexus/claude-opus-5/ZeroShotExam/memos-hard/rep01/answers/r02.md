**Premise correction: there is no per-user API rate-limiting middleware in this repo.** No middleware, interceptor, or handler enforces per-user (or per-IP) request limits, and nothing returns HTTP 429. So there are no "request limits" to report.

What I checked:

- **Echo middleware chain** — `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`). No `middleware.RateLimiter`.
- **Connect RPC interceptors** — `server/router/api/v1/v1.go:133-137` registers exactly four: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). The auth interceptor enforces identity/anonymous-access policy only — no counting or throttling.
- **Repo-wide search** — no `golang.org/x/time/rate` usage (it's only an indirect dependency in `go.mod:151`), and the only textual hits for "rate limit" are aspirational docs: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse", listed as a future consideration) and `internal/email/README.md:286-295` ("### 5. Implement Rate Limiting" with an example sketch). Neither is implemented.

What likely prompted the question — the codebase does have **global concurrency limiters**, which are per-process, not per-user, and gate work in progress rather than request rate:

- `server/router/api/v1/v1.go:59-60` — `thumbnailSemaphore = semaphore.NewWeighted(3)` and `imageProcessingSemaphore = semaphore.NewWeighted(2)`.
- `server/router/api/v1/attachment_service_image.go:68-75` — `acquireImageProcessingSlot`, used at `server/router/api/v1/attachment_service.go:157-160` around EXIF stripping; on failure it returns gRPC `ResourceExhausted` ("too many image processing requests"), the only limit-like error in the API.
- `server/router/fileserver/fileserver.go:45-46,116,447-451` — `maxConcurrentThumbnails = 3` guarding thumbnail generation.

These are shared across all users: two concurrent image-processing operations and three concurrent thumbnail generations server-wide, with callers blocking until a slot frees or the context ends.
