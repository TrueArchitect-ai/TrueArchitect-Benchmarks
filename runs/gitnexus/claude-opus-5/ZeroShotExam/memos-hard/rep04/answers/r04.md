**Premise correction:** Neither. This repo (memos) has no external message broker at all — there is no NATS, RabbitMQ, AMQP, Kafka, or Redis dependency anywhere. `go.mod` contains no broker client library, and grepping the Go sources for `nats`/`rabbit`/`amqp` returns zero hits.

**Actual mechanism:** webhook delivery is handled entirely in-process by a buffered Go channel plus a fixed pool of goroutines, all inside `internal/webhook/webhook.go`.

- **"Queue" declaration** — `internal/webhook/webhook.go:38`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A package-level buffered channel with capacity 128, declared in the same `var` block as the SSRF-guarded `safeClient`.

- **"Workers"** — `internal/webhook/webhook.go:41-53`: a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`, logging a warning on failure. There is no persistence, no retry, and no ack — a process restart loses anything still buffered.

- **Producer** — `PostAsync` (`internal/webhook/webhook.go:184`) does a non-blocking `select` send onto the channel; if the buffer is full it **drops** the payload and logs `"Dropped webhook dispatch because the async queue is full"` (`webhook.go:190-194`). Nil payloads are dropped similarly.

- **Call sites** — only `server/router/api/v1/memo_service_webhooks.go:43` and `:71` enqueue work (memo create/update/delete activity).

Actual delivery is a plain `http.POST` in `Post` (`internal/webhook/webhook.go:117`), optionally HMAC-SHA256 signed per the Standard Webhooks spec (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers), over an HTTP client whose `DialContext` rejects reserved/private IPs to block SSRF and DNS rebinding.
