Memo visibility is enforced independently in each of these places — there is no single chokepoint; each surface re-implements the same PUBLIC/PROTECTED/PRIVATE rule.

**Core API read gate (single-memo reads)** — `checkMemoReadAccess` — `server/router/api/v1/memo_service.go:39-68` (called from `GetMemo` at :356 and again for the parent memo at :367, and from `ListMemoComments` at `server/router/api/v1/memo_service_comments.go:148`)
**List query filter (predicate pushed into the store)** — `ListMemos` — `server/router/api/v1/memo_service.go:218-227` (sets `FindMemo.VisibilityList` / a `creator_id == N || visibility in [...]` filter), plus the comment sub-list filter at `server/router/api/v1/memo_service_comments.go:156-161`; the predicate is turned into SQL in `store/db/sqlite/memo.go:98-102`, `store/db/mysql/memo.go:106-110`, `store/db/postgres/memo.go:91-95`
**SSE live-event delivery filter** — `SSEClient.canReceive` — `server/router/api/v1/sse_hub.go:134-144` (visibility carried on the event by `server/router/api/v1/sse_event_helpers.go:29-37`)
**Raw attachment/file HTTP serving** — `FileServerService.checkAttachmentPermission` — `server/router/fileserver/fileserver.go:650-704` (includes the `share_token` bypass at :684-689)
**Attachment API access check** — `APIV1Service.checkAttachmentAccess` — `server/router/api/v1/attachment_service.go:422-455`
**Per-memo attachment listing** — `ListMemoAttachments` — `server/router/api/v1/memo_attachment_service.go:213-227`
**Reactions** — `ListMemoReactions` / `UpsertMemoReaction` / `DeleteMemoReaction` — `server/router/api/v1/reaction_service.go:29-41, 82-85, 111+`
**Comment creation gate** — `CreateMemoComment` — `server/router/api/v1/memo_service_comments.go:33-43` (also forces the comment's visibility to the parent's at :52)
**Notification/inbox payload rendering** — `canViewerAccessMemo` — `server/router/api/v1/user_service_notifications.go:302-316` (applied at :337, :342, :370, :385)
**Email notification dispatch** — `canViewerAccessMemo` (separate copy) — `server/notification/email.go:306-321` (applied at :155, :187)
**Mention notification targeting** — `canUserAccessMentionContext` / `shouldSkipMentionInbox` — `server/router/api/v1/memo_mention_helpers.go:56-89`
**User stats aggregation** — `ListAllUserStats` / `GetUserStats` — `server/router/api/v1/user_service_stats.go:83-92, 217-221`
**RSS feeds (public-only)** — `GetRSS` / `GetUserRSS` — `server/router/rss/rss.go:90, 141`
**Sitemap (public-only)** — `getSitemapXML` — `server/router/frontend/frontend.go:149-151`

Two notes on the edges of this list:

- `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:153-192`) is a deliberate *bypass*: a valid, unexpired share token grants read access regardless of visibility (only archived/missing memos are refused). Its fileserver counterpart is the `share_token` branch above. Share creation/listing/deletion is gated on ownership instead (`:43, :92, :133`).
- The MCP router (`server/router/mcp/`) contains no visibility logic of its own — it dispatches through the v1 handlers, so it inherits the checks above rather than adding a site.

The duplication is the risk here: `canViewerAccessMemo` exists twice with slightly different super-user tests (`isSuperUser(viewer)` in the API copy vs. `viewer.Role == store.RoleAdmin` in the email copy), and the "PROTECTED means any authenticated user" rule is re-spelled in roughly eight places.
