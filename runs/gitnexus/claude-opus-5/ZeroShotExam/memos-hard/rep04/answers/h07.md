Notes on the hops:

- **Auth gate** (`fileserver.go:173-181`): if `Profile.AllowAnonymous()` is false (private instance, no `InstanceURL`), the request must carry a session/access token/PAT — resolved via `FileServerService.getCurrentUser` (`fileserver.go:708`). On a public instance, another user's avatar is served without any viewer check, and no per-user authorization is applied either way beyond that gate.
- **Lookup key** is the username only — `getUserByUsername` passes `&store.FindUser{Username: &identifier}` (`fileserver.go:714-716`), so the `:identifier` path segment maps directly to `WHERE username = ?` (`store/db/sqlite/user.go:128-130`).
- **Cache**: `Store.GetUser` only hits `userCache` when `find.ID` is set (`store/user.go:149-156`); a username lookup always falls through to `ListUsers` → DB, then populates the cache keyed by ID (`store/user.go:142-144`).
- **Storage form**: the avatar is not a file on disk or in S3 — it's stored inline in the `user.avatar_url` column as a base64 data URI, scanned into `store.User.AvatarURL` (`store/db/sqlite/user.go:188`, `store/user.go:43`). `serveUserAvatar` decodes it with `parseDataURI` (`fileserver.go:737`), rejects MIME types outside `avatarAllowedTypes` (`fileserver.go:75`, `:201`), then writes the bytes via `c.Blob` with security + cache headers (`fileserver.go:205-209`).

On the browser side, `UserAvatar` (`web/src/components/UserAvatar.tsx`) just renders `<img src={avatarUrl}>` from the `User.avatar_url` field returned by the v1 API (`proto/gen/api/v1/user_service.pb.go:248`), so whether this file-server path is exercised depends on whether that field holds the `/file/users/.../avatar` URL or the inline data URI.
