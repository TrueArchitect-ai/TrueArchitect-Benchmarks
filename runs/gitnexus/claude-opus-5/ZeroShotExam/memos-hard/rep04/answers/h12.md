## How I determined which candidate runs

There are three implementations of `CreateMemo` behind the `store.Driver` interface, all satisfying the same signature — the interface method is declared at `store/driver.go:29`:

- `store/db/sqlite/memo.go:16` — `INSERT INTO \`memo\` … RETURNING …`, single round trip
- `store/db/mysql/memo.go:16` — `INSERT` via `ExecContext`, then `LastInsertId()` + a follow-up `GetMemo` (no `RETURNING` support)
- `store/db/postgres/memo.go:38` — `INSERT INTO memo … RETURNING …` with `$n` placeholders

Selection is by string switch on `profile.Driver` in `NewDBDriver` — `store/db/db.go:18-26`. That value is plain runtime config, so static call-graph analysis can't resolve it; I resolved it by following the config default instead:

1. `cmd/memos/main.go:122` — `viper.SetDefault("driver", "sqlite")`, and `main.go:130` sets the same default on the `--driver` persistent flag. With no flags and no `MEMOS_DRIVER` env var, both paths yield `"sqlite"`.
2. `cmd/memos/main.go:43` — that value is read into `instanceProfile.Driver` and passed to `db.NewDBDriver` at `main.go:57`.
3. `internal/profile/profile.go:110` corroborates that sqlite is the default-install path: it auto-fills a DSN (`<data>/memos_prod.db`) only when `Driver == "sqlite" && DSN == ""` — the other drivers have no such fallback and require an explicit DSN.

The call chain into it, from the API down:

`APIV1Service.CreateMemo` (`server/router/api/v1/memo_service.go:70`) → `s.Store.CreateMemo` (`memo_service.go:115`) → `Store.CreateMemo` (`store/memo.go:109`), which validates the UID and then delegates to the interface field `s.driver.CreateMemo` (`store/memo.go:113`) — the dynamic dispatch point that lands on the sqlite implementation.

Caveat worth stating: this is the default-install answer only. A deployment that sets `--driver`/`MEMOS_DRIVER` to `mysql` or `postgres` runs a genuinely different method with different semantics — notably MySQL does a two-statement insert-then-read rather than `RETURNING`.
