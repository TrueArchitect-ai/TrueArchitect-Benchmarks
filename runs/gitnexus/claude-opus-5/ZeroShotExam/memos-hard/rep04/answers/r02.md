**Premise correction: there is no per-user API rate-limiting middleware in this repository.** No rate limiter is registered anywhere, and no rate-limiting library (`golang.org/x/time/rate`, tollbooth, etc.) is in `go.mod`. A repo-wide search for `rate limit` / `throttle` / `limiter` turns up exactly one hit — a documentation comment, not code: `internal/email/doc.go:86` (`- Rate limit email sending to prevent abuse`, under "Security Considerations"). Nothing in the codebase returns HTTP 429.

What actually is registered on the request path:

**Echo-level middleware** (`server/server.go:51-52`): `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:13`).

**Connect RPC interceptor chain** (`server/router/api/v1/v1.go:133-138`) — four interceptors, none of them a limiter:
- `NewMetadataInterceptor()` — HTTP headers → gRPC metadata
- `NewLoggingInterceptor(logStacktraces)`
- `NewRecoveryInterceptor(logStacktraces)`
- `NewAuthInterceptor(authorizer)`

**gRPC-Gateway middleware** (`server/router/api/v1/v1.go:69-97`): a single `gatewayAuthMiddleware` doing authentication/authorization only.

The only limits that exist are size and concurrency caps, all **global/per-process, not per-user**:

| Limit | Value | Location |
|---|---|---|
| Max API request body | `256 << 20` (256 MiB) | `server/router/api/v1/v1.go:20`, applied at `:126`, `:141`, `:144` |
| Concurrent thumbnail generation | 3 | `server/router/fileserver/fileserver.go:46`, and `server/router/api/v1/v1.go:59` |
| Concurrent image (EXIF) processing | 2 | `server/router/api/v1/v1.go:60` |

The image-processing semaphore is the only one that surfaces an error to clients: `codes.ResourceExhausted` / "too many image processing requests" (`server/router/api/v1/attachment_service.go:160`), which Connect maps via `connect.CodeResourceExhausted` (`server/router/api/v1/connect_interceptors.go:153`). That's a global concurrency backstop against memory exhaustion — it does not track requests per user or over time.
