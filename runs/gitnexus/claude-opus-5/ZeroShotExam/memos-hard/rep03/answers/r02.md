**Premise correction: this repository has no per-user API rate-limiting middleware.** There is no rate limiter registered anywhere, and no rate-limiting dependency in `go.mod`/`go.sum` — so there are no request limits to report.

What is actually registered:

**Echo HTTP middleware** — `server/server.go:51-52`:
- `middleware.Recover()`
- `newCORSMiddleware(profile)` (`server/cors.go:14`)

**Connect RPC interceptor chain** — `server/router/api/v1/v1.go:133-138`, all defined in `server/router/api/v1/connect_interceptors.go`:
- `NewMetadataInterceptor()` — HTTP headers → gRPC metadata
- `NewLoggingInterceptor(logStacktraces)`
- `NewRecoveryInterceptor(logStacktraces)`
- `NewAuthInterceptor(authorizer)` — authentication / anonymous-access policy

The only per-request limit in the API layer is a **payload size** cap, not a rate cap: `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` to the gateway routes (`/api/v1/*`, `/file/*`, lines 126-129), and via both `http.MaxBytesHandler` and `connect.WithReadMaxBytes` to the Connect routes (lines 141, 144).

The only rate-limiting mentions in the tree are aspirational docs for a different subsystem — `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse", listed as a future consideration) and `internal/email/README.md:286-295`, which sketches a `rate.NewLimiter` example that is not implemented in code.
