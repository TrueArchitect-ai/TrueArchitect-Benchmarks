**Premise correction:** Neither. This repo (memos) has no external message broker at all — no NATS, no RabbitMQ, no Kafka or Redis. `grep -i` for `nats|rabbit|amqp|kafka|nsq|redis` across `go.mod`/`go.sum` returns zero matches, and there are no broker client dependencies anywhere in the tree.

**Actual mechanism:** Webhook delivery uses an in-process Go channel with a fixed pool of goroutines, entirely within the single memos binary.

- **The "queue" is a buffered Go channel**, declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, in the package-level `var` block alongside the shared `safeClient`.

- **The "workers" are 4 goroutines** started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over `asyncPostQueue` and calls `Post(payload)`, logging a warning on failure. There is no retry, no persistence, and no dead-letter path — a failed delivery is logged and dropped.

- **Enqueue is non-blocking with drop-on-full semantics** — `PostAsync` (`internal/webhook/webhook.go:184-196`) uses a `select` with a `default` branch, so when the 128-slot buffer is full the payload is discarded with a `"Dropped webhook dispatch because the async queue is full"` warning. A nil payload is likewise dropped.

- **Producers** are the memo webhook dispatchers in `server/router/api/v1/memo_service_webhooks.go:43` (comment-created) and `:71` (memo created/updated/deleted), which load each user's hooks via `s.Store.GetUserWebhooks` and enqueue one payload per hook.

Actual delivery (`Post`, `internal/webhook/webhook.go:120`) is a plain `net/http` POST over a shared client with a 30s timeout, an SSRF-guarding `DialContext` that rejects reserved/private IPs at dial time, and optional Standard Webhooks HMAC-SHA256 signing (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers).

Because the queue lives in process memory, anything still buffered is lost on restart, and the queue is not shared across replicas.
