**Premise correction:** There is no Redis in this repository. A case-insensitive search for `redis` across the whole tree (excluding `.git`/`node_modules`) returns zero files, and `go.mod` has no Redis client dependency (no `go-redis`, no `redigo`). There is no connection string, no host/port config, and no external cache process to configure.

**Actual mechanism:** the cache layer is a hand-rolled, in-process, in-memory cache.

**Implementation** — `store/cache/cache.go`:
- `Cache` (line 67) is backed by a `sync.Map` plus an atomic item counter. Each `item` (line 35) holds the value, an absolute `expiration` time, and a rough size estimate.
- TTL is enforced lazily on read (`Get`, line 135: `time.Now().After(itm.expiration)` → delete + miss) and eagerly by a background `cleanupLoop` goroutine (line 200) ticking at `CleanupInterval`.
- `MaxItems` overflow triggers `cleanupOldest` (line 253), which drops roughly 20% of capacity by earliest expiration.
- `cache.DefaultConfig()` (line 57) is `DefaultTTL: 10m`, `CleanupInterval: 5m`, `MaxItems: 1000`.

**Where it's "configured"** — `store/store.go:38-61`, in `store.New()`. Not from env vars or a config file; the values are hardcoded in Go:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That one config is shared by three separate `cache.New(cacheConfig)` instances (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. All three are torn down in `Store.Close()` (line 72).

**TTL for user entries:** **10 minutes**, from the shared `DefaultTTL` above — there is no user-specific TTL. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98, 122, 132, 143, 167`), and `Set` (`store/cache/cache.go:93`) delegates to `SetWithTTL` with `c.config.DefaultTTL`. Nothing in the store calls `SetWithTTL` with a custom duration; that method is exercised only in `store/cache/cache_test.go:26`.

Two behavioral details worth knowing:
- The user cache is keyed by ID only (`userCacheKey` = `strconv.Itoa(userID)`, `store/user.go:88`), and `GetUser` only consults it when `find.ID != nil` (`store/user.go:149`). Lookups by username or email always hit the database.
- Staleness is bounded well below 10 minutes in practice because entries are refreshed on every `UpdateUser`/`ListUsers` and explicitly invalidated on delete (`store/user_delete.go:40`, which also purges that user's setting keys at line 45).

Since this cache lives in the process heap, it is per-instance — running multiple memos replicas gives each its own copy with no cross-node invalidation.
