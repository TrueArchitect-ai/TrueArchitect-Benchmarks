**No** — in production code the MySQL driver is only ever constructed through the factory. The one exception is a single in-package unit test that builds a bare struct literal.

Evidence:

1. **Constructor is `mysql.NewDB`, defined at `store/db/mysql/mysql.go:20`**, returning `store.Driver`. The only place it builds the value is `store/db/mysql/mysql.go:29` (`driver := DB{profile: profile}`), i.e. inside the constructor itself.

2. **The only call site of `mysql.NewDB` is the factory.** `grep -rn "NewDB(" --include=*.go` across the repo returns exactly one MySQL call: `store/db/db.go:22`, inside `NewDBDriver`'s driver switch:
   ```go
   case "mysql":
       driver, err = mysql.NewDB(profile)
   ```

3. **Only one file in the entire repo imports the package.** `grep -rn "db/mysql" --include=*.go` matches a single line: `store/db/db.go:8`. Since `DB` can only be named via that import path from outside, no other package can construct it directly — everything else goes through the `store.Driver` interface returned by `NewDBDriver`.

4. **One direct struct construction exists, in-package and test-only:** `store/db/mysql/auth_config_test.go:12` does `db := &DB{}` to exercise `IsRetryableAuthenticationMutationError` without a live connection. It bypasses `NewDB` (leaving `profile` and the `*sql.DB` nil), but it is a test in `package mysql`, not production wiring.

For contrast, the sibling drivers *do* have direct non-factory production-adjacent construction in tests outside their package — `sqlite.NewDB` is called directly at `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416`. MySQL has no equivalent.
