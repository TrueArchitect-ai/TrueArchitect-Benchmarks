**No** — in production code the MySQL driver is only ever constructed via the factory. The one exception is a same-package unit test that builds a zero-value struct.

Evidence:

1. **Only one caller of the constructor.** `mysql.NewDB` (`store/db/mysql/mysql.go:20`) is invoked exactly once in the whole repo: `store/db/db.go:22`, inside the `switch profile.Driver` factory `NewDBDriver`.

2. **Only one importer of the package.** `grep -rn "db/mysql" --include=*.go` returns a single hit: `store/db/db.go:8`. No other package — not `cmd/`, `server/`, `internal/`, nor the integration tests — imports `github.com/usememos/memos/store/db/mysql`, so `mysql.DB` cannot be constructed from outside it. Test helpers go through the factory too: `store/test/store.go:28` and `:50` call `db.NewDBDriver(profile)` with a driver-specific profile from `getTestingProfileForDriver` (`store/test/store.go:75`).

3. **Struct-literal construction of `DB`.** Within the `mysql` package there are two: `store/db/mysql/mysql.go:29` (`driver := DB{profile: profile}`, inside `NewDB` itself), and `store/db/mysql/auth_config_test.go:12` (`db := &DB{}`). The latter is a direct construction outside the factory, but it's an unexported-field zero value used only as a receiver for the pure error-classification helper `IsRetryableAuthenticationMutationError` — no connection is opened, `d.db` stays nil. The same pattern exists for Postgres (`store/db/postgres/auth_config_test.go:12`, `user_setting_test.go:36`, `:194`, `:257`).

So: no direct construction in any non-test code path; the sole direct construction anywhere is the in-package test at `store/db/mysql/auth_config_test.go:12`.
