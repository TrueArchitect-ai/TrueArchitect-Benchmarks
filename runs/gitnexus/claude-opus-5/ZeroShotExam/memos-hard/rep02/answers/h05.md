**Mechanism: explicit Go code** — two `DELETE FROM reaction` statements inside the user-deletion transaction, one for reactions the user *authored* and one for reactions *on the user's memos*. There is no database-level rule (no foreign key, no `ON DELETE CASCADE`, no trigger) on the `reaction` table.

## Evidence

**1. No DB-level rule exists.** The `reaction` table is declared with no foreign key on `creator_id` (it isn't even a FK to `user`; `content_id` is a text resource name, not an ID):

- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/mysql/LATEST.sql:91-98`
- `store/migration/postgres/LATEST.sql:91-98`
- Original creation migrations agree: `store/migration/{sqlite,mysql,postgres}/0.20/00__reaction.sql`

Grepping `FOREIGN KEY|REFERENCES|ON DELETE` across all three `LATEST.sql` files yields exactly one hit each — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109` and peers). Nothing touches `reaction`. The only triggers in the repo are `updated_ts` bumps (`store/migration/sqlite/0.6/00__recreate_triggers.sql`).

**2. Explicit Go deletion, per driver.** `store/db/sqlite/user_delete.go:92-127` (`deleteUserTargetsTx`) runs both calls inside the transaction:

- `deleteReactionsByContentIDsTx` — `store/db/sqlite/user_delete.go:380-388`: `DELETE FROM reaction WHERE content_id IN (…)`, batched. The content IDs come from `memoContentIDsFromRefs` (`:512-518`), which formats each memo UID as `"memos/"+uid` to match the stored `content_id`. The memo set is the recursive comment tree from `listDeleteUserMemoTreeRecursive` (`:133-165`), so reactions left by *other* users on the deleted user's memos and comment subtree also go.
- `deleteReactionsByCreatorTx` — `store/db/sqlite/user_delete.go:400-403`: `DELETE FROM reaction WHERE creator_id = ?`, covering the user's own reactions on anyone's memos.

Identical code in the other two drivers: `store/db/mysql/user_delete.go:96,102,417-421,437-439` and `store/db/postgres/user_delete.go:96,102,380-388,400-403`.

**3. Call path.** `server/router/api/v1/user_service.go:414` → `store/user.go:171` `(*Store).DeleteUser` → `s.driver.DeleteUser` → the per-driver transaction above. Being in-transaction means a failure rolls the reactions back with everything else.

**4. Tests assert this behavior.** `store/test/user_delete_test.go:97-113, 217-220` and `server/router/api/v1/test/user_service_delete_test.go:188-209, 287-298` create reactions by the deleted user, by a peer on the deleted user's memo, and by a peer on a foreign memo, then assert the first two are gone and the third survives. `user_service_delete_test.go:366-431` asserts a reaction is preserved when the delete transaction rolls back.
