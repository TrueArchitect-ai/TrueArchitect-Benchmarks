**Premise correction: this repository has no per-user API rate-limiting middleware.** There is nothing registered, so there are no request limits to report.

What I checked:

- **The Connect/gRPC interceptor chain** — `server/router/api/v1/v1.go:133-138` registers exactly four interceptors: `NewMetadataInterceptor`, `NewLoggingInterceptor`, `NewRecoveryInterceptor`, `NewAuthInterceptor`. All four are defined in `server/router/api/v1/connect_interceptors.go` (lines 22, 98, 165, 208); none does rate limiting.
- **The Echo HTTP middleware stack** — `server/server.go:51-52` registers only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:14`). The frontend router adds static-file and SPA-fallback middleware (`server/router/frontend/frontend.go:54,59`).
- **Repo-wide grep** for `rate limit`, `ratelimit`, `throttle`, `golang.org/x/time/rate`, `tollbooth`, `ulule/limiter` across Go, TS, and config files — the only hits are documentation, not code.

The two things that could be mistaken for the premise:

1. **`internal/email/README.md:286-296`** has a section titled "Implement Rate Limiting" with a `rate.NewLimiter(rate.Every(time.Second), 10)` snippet — "10 emails per second." This is a *suggested best practice* in prose for consumers of the email package, not registered middleware, not per-user, and not on the API path. `internal/email/doc.go:86` similarly lists "Rate limit email sending to prevent abuse" as a recommendation. `golang.org/x/time` appears in `go.mod:151` only as an **indirect** dependency, confirming no first-party use of `rate`.

2. **A request *size* limit does exist**, which is the closest real thing: `maxAPIRequestBytes` is enforced via `http.MaxBytesHandler` on the gateway routes (`server/router/api/v1/v1.go:126`), the Connect routes (line 145), and as `connect.WithReadMaxBytes` on the Connect handlers (line 143). That caps bytes per request, not requests per user per unit time.

If you want per-user rate limiting, the natural insertion point is a new interceptor in `connect_interceptors.go` placed after `NewAuthInterceptor` in the chain at `v1.go:133` (so the user identity is already resolved), plus equivalent coverage for the `/api/v1/*` gateway group.
