h15.

Memo visibility is enforced independently in several server surfaces — there is no single choke point; each surface re-implements the rule (PUBLIC → anyone; PROTECTED → any authenticated user; PRIVATE → creator, plus admin/superuser in most but not all sites).

**gRPC/Connect API v1 — memo read gate (`checkMemoReadAccess`)** — `server/router/api/v1/memo_service.go:39-66`, called from `GetMemo` (`memo_service.go:356`, plus the parent-memo check at `:367`) and `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`)

**gRPC/Connect API v1 — list-query visibility predicate (`ListMemos`)** — `server/router/api/v1/memo_service.go:218-226` (anonymous → `VisibilityList = [PUBLIC]`; authenticated → CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`)

**gRPC/Connect API v1 — memo-relation / comment-relation filter** — `server/router/api/v1/memo_relation_service.go:107-111` and `server/router/api/v1/memo_service_comments.go:157-162` (`MemoFilter` string passed into `ListMemoRelations`)

**gRPC/Connect API v1 — user stats surfaces** — `server/router/api/v1/user_service_stats.go:82-92` (`ListAllUserStats`) and `:217-221` (per-user stats)

**gRPC/Connect API v1 — memo sub-resource services (each re-checks the parent memo)** — `server/router/api/v1/memo_attachment_service.go:213-226` (`ListMemoAttachments`), `server/router/api/v1/attachment_service.go:437-454` (attachment access via linked memo), `server/router/api/v1/reaction_service.go:29-41` (`ListMemoReactions`) and `:83-85` (`UpsertMemoReaction`), `server/router/api/v1/memo_service_comments.go:41` (`CreateMemoComment`)

**SSE broadcast fan-out (`SSEClient.canReceive`)** — `server/router/api/v1/sse_hub.go:133-143`, with event visibility/creator resolution in `server/router/api/v1/sse_event_helpers.go`

**File server (attachment blobs, thumbnails, media streams)** — `server/router/fileserver/fileserver.go:649-703` (`checkAttachmentPermission`; includes the anonymous-instance rule at `:677` and the `share_token` bypass at `:683-689`)

**Share-token surface (`GetMemoByShare` / `getActiveMemoShare`)** — `server/router/api/v1/memo_share_service.go:152-208` — deliberately bypasses visibility: a valid, non-expired token grants read access regardless of PRIVATE/PROTECTED (only archived/missing is denied)

**RSS feeds** — `server/router/rss/rss.go:90` (explore) and `:141` (per-user) — hard-restricted to `VisibilityList = [PUBLIC]`

**Sitemap (frontend router)** — `server/router/frontend/frontend.go:150` — public-only memo list

**Notification payload rendering (API)** — `server/router/api/v1/user_service_notifications.go:302-321` (`canViewerAccessMemo`), applied at `:337`, `:342`, `:370`, `:385`

**Email notification rendering** — `server/notification/email.go:306-321` (a second, separate `canViewerAccessMemo` — note it checks `viewer.Role == store.RoleAdmin` rather than `isSuperUser`), applied at `:155` and `:187`

Two notes worth flagging: the MCP surface (`server/router/mcp/`) is **not** a distinct enforcement site — `server/router/mcp/adapter.go` proxies tool calls back through the HTTP API, so it inherits the API v1 checks. And the store layer (`store/memo.go`, `store/db/{sqlite,postgres,mysql}/memo.go`) only applies whatever `VisibilityList`/`Filters` the caller supplies — it enforces nothing on its own, which is why every surface above must set the predicate itself.
