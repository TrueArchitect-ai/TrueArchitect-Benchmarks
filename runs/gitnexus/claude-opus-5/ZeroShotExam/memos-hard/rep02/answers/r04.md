**Premise correction:** Neither. This repo (memos) has no message broker at all — there is no NATS, RabbitMQ, AMQP, or Kafka dependency in `go.mod`/`go.sum`, and no broker client anywhere in the Go source. The only "nats" string matches in the tree are Catalan words in `web/src/locales/ca.json` (e.g. "seleccionats").

**Actual mechanism:** Webhook delivery is handled entirely in-process by a buffered Go channel and a fixed pool of goroutines, all in `internal/webhook/webhook.go`:

- **Queue declaration** — `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, declared in the package-level `var` block.
- **Workers** — `internal/webhook/webhook.go:41-53`: the package `init()` starts 4 goroutines (`for range 4`), each ranging over `asyncPostQueue` and calling `Post(payload)`, logging a warning on failure.
- **Producer** — `PostAsync` (`internal/webhook/webhook.go:184-197`) does a non-blocking `select` send; when the 128-slot buffer is full the payload is **dropped** with a `slog.Warn` ("Dropped webhook dispatch because the async queue is full"). Nil payloads are also dropped.
- **Call sites** — `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, which fan out one `PostAsync` per registered user webhook for memo created/updated/deleted and comment-created events.

Consequences of this design worth noting: the queue is per-process and in-memory, so it does not survive a restart, there is no retry/backoff (a failed `Post` is logged and discarded), and no delivery guarantee under load. Actual HTTP delivery in `Post` (`internal/webhook/webhook.go:114`) uses a shared client with a 30s timeout, SSRF-guarded dialer, and Standard Webhooks HMAC-SHA256 signing headers.

The same pattern is used for email (`internal/email/email.go:14`, a 128-slot `asyncEmailQueue`), confirming this is the codebase's general approach rather than a webhook-specific fallback.
