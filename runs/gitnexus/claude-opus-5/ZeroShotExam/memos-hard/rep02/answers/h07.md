Two things worth flagging about "another user's profile image":

1. **The stored data is the row itself, not a file.** Avatars never touch the attachment/blob/S3 path that `serveAttachmentFile` uses — they live inline as a base64 data URI in the `user.avatar_url` column, written via `UpdateUser` (`server/router/api/v1/user_service.go:335-354`). So the data layer terminates at the SQL row; there is no filesystem or object-store hop.

2. **The main React path doesn't call this endpoint at all.** `UserAvatar` (`web/src/components/UserAvatar.tsx:14`) renders `src={avatarUrl}` directly — the data URI arrives already embedded in the `User` message from the gRPC-gateway API, so the browser decodes it inline with no second request. The `/file/users/:identifier/avatar` route is the separate, directly-addressable path (used by external consumers and covered by `fileserver_test.go:508`).

Also note the only authorization on this handler is instance-level: if `Profile.AllowAnonymous()` is true (an `InstanceURL` is configured), *any* user's avatar is served unauthenticated — there is no per-user check, unlike `checkAttachmentPermission` at `fileserver.go:650`.
