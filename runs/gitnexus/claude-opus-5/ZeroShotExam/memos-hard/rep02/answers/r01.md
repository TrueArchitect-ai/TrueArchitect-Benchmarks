**Premise correction:** There is no Redis in this repository. `grep -rni "redis"` across the whole tree (including `go.mod`, `go.sum`, `web/package.json`, and `docs/`) returns zero hits — no Redis client dependency, no connection string, no config knob. The cache layer is a hand-rolled, in-process, in-memory cache. Nothing is configured for an external cache server, so there is no host/port/DB/auth to point at.

**Actual mechanism**

- **Implementation:** `store/cache/cache.go` — a `Cache` struct backed by a `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66`). Entries are `item{value, expiration, size}` (`store/cache/cache.go:34`). It satisfies the `Interface` at `store/cache/cache.go:10`.
- **Where it's "configured":** `store/store.go:37` in `New()`. The config is a hardcoded literal, not read from env or a config file:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  Three separate caches are constructed from that same config (`store/store.go:50-52`): `instanceSettingCache`, `userCache`, `userSettingCache`. An identical set of defaults is duplicated in `cache.DefaultConfig()` at `store/cache/cache.go:56`, but `store.New` builds its own literal rather than calling it.

**TTL for user entries: 10 minutes.** Every write path for users calls `Set` (never `SetWithTTL`), and `Set` delegates to `SetWithTTL(..., c.config.DefaultTTL)` at `store/cache/cache.go:94` — so user entries inherit the 10-minute `DefaultTTL` with no per-entry override anywhere. The user cache writes are in `store/user.go`: `CreateUser` (:98), `UpsertUser`-style path (:122), `UpdateUser` (:132), `ListUsers` (:143, refreshing every listed user), and `GetUser` (:167). Keys are the plain decimal user ID (`userCacheKey`, `store/user.go:88`).

Two details on how expiry actually behaves:

- **Lazy expiry on read:** `Get` (`store/cache/cache.go:123`) checks `time.Now().After(itm.expiration)` and deletes + reports a miss, so a stale user is never returned even between cleanup ticks.
- **Background sweep every 5 minutes** via `cleanupLoop`, plus an eager `cleanupOldest()` when the 1000-item `MaxItems` cap is exceeded (`store/cache/cache.go:114`) — so under heavy user load a user entry can be evicted well before its 10 minutes are up.

Invalidation is explicit on delete only: `store/user_delete.go:40` calls `s.userCache.Delete(...)`. `Close()` (`store/store.go:75`) stops all three cleanup goroutines.

For contrast, the other TTL in the codebase is unrelated to this layer: `instanceStatsCacheTTL = 60 * time.Second` in `server/router/api/v1/instance_stats.go:21`, a separate single-value memoization struct with its own `get`/`set`.
