## Mechanism

`reaction` rows are deleted by hand-written `DELETE` statements inside the same transaction that removes the user row. Each of the three drivers implements the identical sequence in `deleteUserTargetsTx`:

- `store/db/sqlite/user_delete.go:92-127` (calls at `:96` and `:102`)
- `store/db/postgres/user_delete.go:96`, `:102`
- `store/db/mysql/user_delete.go:96`, `:102`

Two separate deletes cover two different notions of "their reactions":

1. **Reactions the user authored** — `deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`, `postgres/user_delete.go:400-403`, `mysql/user_delete.go:437-440`).
2. **Reactions anyone left on the user's memos** — `deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)` (`store/db/sqlite/user_delete.go:380-388`, and the peers). The content IDs come from the recursive memo tree (the user's memos plus their comment subtree, `listDeleteUserMemoTreeRecursive` at `store/db/sqlite/user_delete.go:133-166`), mapped to `"memos/"+uid` by `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go:512-518`).

Ordering matters and is deliberate: the content-ID delete runs *before* `deleteMemosTx` (`:120`), since the content IDs are derived from memo UIDs.

The API layer does not touch reactions itself — `server/router/api/v1/user_service.go:414` just calls `s.Store.DeleteUser`, which dispatches to the driver (`store/driver.go:48`).

## Why it is *not* a database rule

- The `reaction` table has **no foreign key at all** in any dialect — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`, and the original `store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql`. A grep for `REFERENCES|CASCADE|FOREIGN KEY` across `store/migration/` returns hits only for `memo_share`, `user_setting`, `memo_resource`, etc. — never `reaction`.
- Even the FKs that *do* exist would not fire on SQLite: the connection is opened with `_pragma=foreign_keys(0)` at `store/db/sqlite/sqlite.go:53`.

## Tests that pin this behavior

- `server/router/api/v1/test/user_service_delete_test.go:287-298` — asserts reactions on the deleted user's own memo and on their comment are gone, while a peer's reaction on a *foreign* memo survives (so the sweep is scoped, not global).
- `server/router/api/v1/test/reaction_service_test.go:228-234` — after `Store.DeleteUser(reactor)`, `ListMemoReactions` on another user's memo returns empty, confirming the `creator_id` sweep.
- `server/router/api/v1/test/user_service_delete_test.go:366-429` — the rollback failpoint test confirms the reaction delete is inside the transaction: on abort before commit, the reaction is still retrievable.
