**Premise correction:** There is no Redis connection anywhere in this repository — no Redis client dependency, no connection string, no config option. A case-insensitive grep for "redis" across the whole tree (excluding `.git`/`node_modules`) returns zero hits, including in `go.mod`. The cache layer is entirely **in-process, in-memory**, and nothing about it is externally configurable.

**Actual mechanism**

The cache is a hand-rolled `sync.Map`-backed store in `store/cache/cache.go`:

- `cache.Config` (`store/cache/cache.go:42-54`) holds `DefaultTTL`, `CleanupInterval`, `MaxItems`, and an optional `OnEviction` callback.
- Each entry stores an absolute `expiration` timestamp (`store/cache/cache.go:110-114`). Expiry is enforced lazily on `Get` (`store/cache/cache.go:135`) and by a background `cleanupLoop` goroutine ticking on `CleanupInterval` (`store/cache/cache.go:200-215`). A `MaxItems` overflow triggers `cleanupOldest`, which drops ~20% of capacity (`store/cache/cache.go:253`).

**Where it's configured:** `store.New` in `store/store.go:39-58` — the config is a hardcoded literal, not read from env or profile:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

The same `cacheConfig` value is used to construct three separate cache instances (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. All three are closed in `Store.Close` (`store/store.go:72-79`). Note `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) has identical values but is not what `store.New` calls — it duplicates them inline.

**TTL for user entries: 10 minutes**, inherited from `DefaultTTL`. Every user write path calls `Set` (not `SetWithTTL`), which forwards `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). `SetWithTTL` is never called anywhere outside the cache package itself, so no per-entry TTL override exists in practice.

User cache touch points, keyed by stringified user ID (`userCacheKey`, `store/user.go:88-90`):
- `CreateUser` — `store/user.go:98`
- `CreateUserIfNoUsers` — `store/user.go:122`
- `UpdateUser` — `store/user.go:132`
- `ListUsers` — caches every returned user, `store/user.go:143`
- `GetUser` — reads cache only when `find.ID` is set, otherwise falls through to `ListUsers`; `store/user.go:148-168`
- `DeleteUser` — invalidates via `Delete`, `store/user_delete.go:40`

Because it's per-process memory, these caches are not shared across replicas and are lost on restart.

**Two unrelated caches** exist elsewhere with their own TTLs, in case one of them was the target of the question: the RSS cache at `server/router/rss/rss.go:25` (`defaultCacheDuration = 1 * time.Hour`) and the instance-stats memoization at `server/router/api/v1/instance_stats.go:21` (`instanceStatsCacheTTL = 60 * time.Second`). Neither uses `store/cache`, and neither uses Redis.
