**Premise correction:** Neither. This repo has no message broker at all — no NATS, no RabbitMQ, no AMQP. `go.sum` contains zero matches for `nats-io`, `rabbitmq`, `streadway`, or `amqp091`, and there is no broker service in any deployment file (the only container file is `scripts/Dockerfile`). There are also no "webhook delivery workers" as a separate deployable process. The single `nats`/`amqp` grep hit in the tree is a false positive: Catalan words in `web/src/locales/ca.json` like "elimi**nats**" and "predetermi**nats**".

**Actual mechanism — an in-process buffered Go channel**, all in `internal/webhook/webhook.go`:

- **The "queue" is declared at `internal/webhook/webhook.go:39`** — a package-level buffered channel holding 128 payloads:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- **The "workers" are 4 goroutines** started in `init()` at `internal/webhook/webhook.go:42-55`. Each ranges over the channel and calls `Post()`, logging a warning on failure. There is no retry and no dead-letter path — a failed delivery is logged and dropped.
- **Producing** happens via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send. If the buffer is full, the payload is **silently dropped** with a `slog.Warn` rather than blocking the caller.
- **Delivery** itself is a plain HTTP POST in `Post()` (`internal/webhook/webhook.go:120-180`), using a shared `safeClient` (`:32-37`) with a 30s timeout and an SSRF-guarding `DialContext` that rejects reserved/private IPs (`:59-77`). Optional HMAC-SHA256 signing follows the Standard Webhooks spec (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers, `:133-150`).

Callers are the API layer: `server/router/api/v1/memo_service_webhooks.go` fans out over each user's registered webhooks and calls `webhook.PostAsync(payload)` (`:43` and `:71`) for activity types `memos.memo.created` / `.updated` / `.deleted` / `.comment.created`.

Two consequences worth noting, since they're what a broker would normally buy you: this queue is **in-memory and per-process**, so pending webhooks are lost on restart and the design assumes a single server instance; and under burst load beyond 128 queued items, deliveries are dropped rather than backpressured.
