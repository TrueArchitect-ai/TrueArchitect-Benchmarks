Notes that matter for the trace:

- **The stored data is the `avatar_url` column of the `user` table**, holding a base64 `data:<mime>;base64,...` URI — not a file on disk or in S3. There is no attachment/blob-storage hop; `parseDataURI` (`fileserver.go:737`, regex at `:98`) decodes the column value directly into the response body.
- `Store.GetUser` only consults `userCache` when the lookup is **by ID** (`store/user.go:149-156`). This path looks up by username, so it always falls through to `ListUsers` → driver → SQL; the row is then written into `userCache` (`store/user.go:143,167`).
- Two gates before the data hop: on a private instance (`!s.Profile.AllowAnonymous()`) `getCurrentUser` → `s.authenticator.AuthenticateToUser` (`fileserver.go:708-712`, `server/auth`) must resolve a viewer, else 401. Beyond that there is **no per-user authorization** — any authenticated viewer (or anyone at all on a public instance) may fetch any other user's avatar by username. The MIME type is then whitelist-checked against `avatarAllowedTypes` (`fileserver.go:75-83`, `:201`).
- `server/server.go:81-82` wires the service (`NewFileServerService`) and mounts the routes on the echo server.
