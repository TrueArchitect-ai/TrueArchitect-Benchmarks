**Mechanism: explicit Go code** — two hand-written `DELETE FROM reaction` statements inside the `DeleteUser` transaction, duplicated per driver. There is no database-level rule: the `reaction` table has no foreign key, no `ON DELETE CASCADE`, and no trigger.

## Evidence locations

**The explicit deletes** — `deleteUserTargetsTx` runs two reaction deletions, and they cover different things:

| Function | Statement | Removes |
|---|---|---|
| `deleteReactionsByContentIDsTx` | `DELETE FROM reaction WHERE content_id IN (…)` | *all* reactions (from anyone) on the deleted user's memos and their comment subtree |
| `deleteReactionsByCreatorTx` | `DELETE FROM reaction WHERE creator_id = ?` | the deleted user's own reactions, including those left on *other* users' memos |

Identical implementations in all three drivers:
- `store/db/sqlite/user_delete.go:96` / `:102`, defined at `:380` and `:400`
- `store/db/postgres/user_delete.go:96` / `:102`, defined at `:380` and `:400`
- `store/db/mysql/user_delete.go:96` / `:102`, defined at `:417` and `:437`

The `content_id` variant works on strings built as `"memos/" + memo.UID` (`memoContentIDsFromRefs`, sqlite `:512`), matching how the reaction table stores its target. Both run inside the transaction opened at `DeleteUser` (sqlite `:29`), before the memo and user rows are deleted, so the whole thing commits or rolls back atomically. Entry points: `store/user.go:171` → `server/router/api/v1/user_service.go:414`.

**Why it can't be the database** — `reaction` is declared with no FK at all in every dialect:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

The contrast is directly below in the same files: `memo_share` (sqlite `:102-110`) does declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`. So cascade is used deliberately elsewhere but not here. Grepping the whole `store/migration/` tree for `reaction` alongside `foreign|references|cascade|trigger` returns nothing; the only triggers that ever existed were `updated_ts` bookkeeping on user/memo/shortcut/resource, dropped in `store/migration/sqlite/0.7/01__remove_triggers.sql`. FKs were stripped repo-wide in `store/migration/sqlite/0.7/00__remove_fk.sql`.

**Test confirming behavior** — `store/test/user_delete_test.go`: three reactions are seeded (`:97-114`), then after deletion the assertion at `:216-220` checks the peer's memo retains exactly one reaction, `peerReactionToKeep`. The deleted user's `"heart"` reaction on the *peer's surviving memo* is gone, which is specifically the `creator_id` path — a cascade from the user row could not be what removed it, since none exists.
