**Premise correction: this repository has no per-user API rate-limiting middleware.** There is nothing to register and no request limits to report — no limiter is wired into either the HTTP middleware chain or the Connect RPC interceptor chain, and the repo has no rate-limiting dependency (`golang.org/x/time/rate`, tollbooth, etc.) in `go.mod`.

What actually exists at those two registration points:

- **Echo HTTP middleware** — `server/server.go:51-52`: only `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go:13`). Static/SPA middleware is added separately in `server/router/frontend/frontend.go:54-59`.
- **Connect RPC interceptors** — `server/router/api/v1/v1.go:133-137`, the full chain: `NewMetadataInterceptor()`, `NewLoggingInterceptor(logStacktraces)`, `NewRecoveryInterceptor(logStacktraces)`, `NewAuthInterceptor(authorizer)`. All four are defined in `server/router/api/v1/connect_interceptors.go`; `AuthInterceptor` does authentication/anonymous-access policy only (`connect_interceptors.go:205-231`), not throttling.

The only rate-limit mentions anywhere in the codebase are aspirational docs for the email subsystem, not implemented code:

- `internal/email/doc.go:86` — a future-work bullet, "Rate limit email sending to prevent abuse".
- `internal/email/README.md:286-295` — a suggested-implementation snippet (`rate.NewLimiter(rate.Every(time.Second), 10)`, i.e. 10 emails/sec). This is example prose in a README; the package does not import `golang.org/x/time/rate`, and even as written it would be a global email-send limiter, not per-user API rate limiting.

There is also `internal/scheduler/middleware.go`, but that is job-handler middleware (`Chain`, `Recovery`, `Logging`, `Timeout`) for background jobs — unrelated to API requests.
