**Premise correction:** Neither. This repo (memos) has no message broker at all — no NATS, no RabbitMQ, no AMQP/Kafka/Redis client. `go.mod` and `go.sum` contain zero matches for `nats`, `amqp`, `rabbit`, `kafka`, `redis`, or any task-queue library. There is also no separate "worker" process or deployment; webhook delivery happens inside the single memos server binary.

**Actual mechanism — an in-process buffered Go channel with a fixed goroutine pool:**

- **Queue declaration:** `internal/webhook/webhook.go:39`
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A package-level buffered channel holding 128 payloads.

- **"Workers":** `internal/webhook/webhook.go:42-55` — a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`, logging a warning on failure. There's no retry, no ack, no dead-letter — a failed delivery is dropped after one attempt.

- **Enqueue:** `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a `"Dropped webhook dispatch because the async queue is full"` warning — backpressure is shed, not queued.

- **Producers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` call `webhook.PostAsync(payload)` for memo created/updated/deleted and comment-created events, after loading endpoints via `s.Store.GetUserWebhooks`.

- **Delivery:** `Post` (`internal/webhook/webhook.go:120`) does a plain `net/http` POST via a shared `safeClient` with a 30s timeout and an SSRF-guarding dialer (`safeDialContext`, `internal/webhook/webhook.go:59`), optionally signing with Standard Webhooks HMAC-SHA256 headers.

Practical consequence of the real design: because the queue lives in process memory, anything still buffered is lost on server restart or crash, and burst traffic above 128 pending deliveries is silently discarded.
