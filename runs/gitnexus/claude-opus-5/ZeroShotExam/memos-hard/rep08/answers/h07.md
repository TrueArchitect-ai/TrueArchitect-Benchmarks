The browser hits `GET /file/users/{username}/avatar`. The URL itself is minted server-side: `convertUserFromStore` rewrites a base64 avatar into that path so the API response stays small (`server/router/api/v1/user_service_converters.go:32-40`), and `UserAvatar.tsx` just renders it as an `<img src>` (`web/src/components/UserAvatar.tsx:14`).

Two things worth noting about where the data actually lives:

- Avatar bytes are **not** in attachment storage (no local file / S3 / blob branch like `serveAttachmentFile` has). They're stored inline in the `user.avatar_url` column as a base64 data URI, so the "data layer" terminates at that column scan.
- The `userCache` in `Store.GetUser` is bypassed here: it's only consulted when `find.ID != nil` (store/user.go:149), and this lookup is by `Username`, so every avatar request reaches the DB driver.

Authorization detail: past the private-instance gate there is no per-user check — any authenticated viewer (or any anonymous visitor on a public instance) can fetch any user's avatar by username. That appears intentional, matching the test `TestServeUserAvatar_PrivateInstanceRequiresAuth` (server/router/fileserver/fileserver_test.go:508).
