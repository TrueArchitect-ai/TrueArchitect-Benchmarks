**Premise correction:** There is no Redis anywhere in this repository. `grep -ri redis` across the whole tree (excluding `node_modules`/`.git`) returns nothing, and `go.mod`/`go.sum` contain no Redis (or Memcached/Valkey) client dependency. There is also no external cache server, no connection string, and no cache-related config file or environment variable.

**Actual mechanism:** The cache layer is a hand-rolled, in-process, in-memory cache built on `sync.Map`, with no network or connection configuration at all.

- **Implementation:** `store/cache/cache.go` — a `Cache` struct holding a `sync.Map` of `item{value, expiration, size}`, an atomic item counter, and a background `cleanupLoop` goroutine (`store/cache/cache.go:66-85`, `store/cache/cache.go:200-250`).
- **Where it's "configured":** `store/store.go:38-61`. `New()` builds a single `cache.Config` literal in code and hands the same config to three separate cache instances — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:27-29`, `store/store.go:51-53`). The values are hardcoded — not read from env, flags, or a config file:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`
  - `OnEviction: nil`
  
  `store/cache/cache.go:57-64` (`DefaultConfig()`) declares the same three values, but the store doesn't call it — it duplicates the literal.

**TTL for user entries: 10 minutes.** Every write to `userCache` goes through `Set()` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — i.e. the 10 minutes from `store/store.go:41`. `SetWithTTL` is never called with a custom duration anywhere in non-test code, so users get no special TTL; they share the same 10-minute default as instance settings and user settings.

Two details worth noting about expiry, since they affect what "10 minutes" means in practice:
- Expiry is lazy plus swept: `Get` checks `time.Now().After(itm.expiration)` and evicts on read (`store/cache/cache.go:135-144`), and the background loop sweeps every 5 minutes (`store/cache/cache.go:218-250`). So a stale user entry can physically live up to ~15 minutes, but is never *served* past 10.
- The TTL is not the only eviction path — once the cache exceeds `MaxItems: 1000`, `cleanupOldest` drops roughly 20% of entries (`store/cache/cache.go:253-313`), so user entries can be evicted well before their 10 minutes on a busy instance.

Cache keys for users are the plain user ID as a string (`userCacheKey`, `store/user.go:88-90`); user *settings* use a separate `userID-key` composite (`getUserSettingCacheKey`, `store/cache.go:7-9`).

Because the cache is per-process and in-memory, it is not shared across replicas — running multiple memos instances against one database means each has its own independent, independently-stale user cache. That's the practical consequence of there being no Redis.
