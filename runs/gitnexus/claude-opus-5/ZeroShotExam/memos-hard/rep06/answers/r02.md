**Premise correction: there is no per-user API rate-limiting middleware in this repository.** Nothing is registered, so there are no request limits to report.

**What I checked**

A repo-wide search for `rate.?limit` / `ratelimit` / `throttl` across all file types (excluding `node_modules` and `.git`) returns exactly two files, both in `internal/email/`, and both are prose rather than code:

- `internal/email/doc.go:86` — a security-considerations bullet: "Rate limit email sending to prevent abuse."
- `internal/email/README.md:286-297` — a "5. Implement Rate Limiting" best-practices section with an *illustrative* snippet (`rate.NewLimiter(rate.Every(time.Second), 10)`, "10 emails per second"). This is example documentation for SMTP send throttling that a consumer *could* add; it is not wired into any handler, and it isn't per-user API limiting.

Those numbers are the only concrete limits anywhere, which makes them an easy thing to mistake for the answer — they aren't in effect.

**The actual middleware chain**

The Connect RPC interceptors are registered at `server/router/api/v1/v1.go:133-138`, and the chain is exactly four interceptors, all defined in `server/router/api/v1/connect_interceptors.go`:

| Interceptor | Source |
|---|---|
| `MetadataInterceptor` — HTTP headers → gRPC metadata | `connect_interceptors.go:22` |
| `LoggingInterceptor` | `connect_interceptors.go:98` |
| `RecoveryInterceptor` — panic recovery | `connect_interceptors.go:165` |
| `AuthInterceptor` — authn / anonymous-access policy | `connect_interceptors.go:208` |

No limiter is present. The only other `middleware.go` in the tree, `internal/scheduler/middleware.go`, is for background *jobs* (`Recovery`, `Logging`, `Timeout` at lines 27, 51, 74) — not HTTP requests, and it has no rate limiter either.

**Corroborating signals**

- `golang.org/x/time` (which provides `rate.Limiter`) appears in `go.mod:151` marked `// indirect` — pulled in transitively, not used directly by this codebase.
- No third-party limiter dependency (tollbooth, ulule/limiter, redis_rate, sethvargo) in `go.mod`/`go.sum`, and no JS limiter in `web/package.json`.

**What does exist** is a request *size* limit, not a request *rate* limit — `http.MaxBytesHandler(..., maxAPIRequestBytes)` applied at `v1.go:126`, `:141`, and `:144`, plus `connect.WithReadMaxBytes`. If you're looking for abuse protection, that byte cap is the only enforcement in the request path today.
