**Mechanism: explicit Go code inside the delete-user transaction — there is no database-level cascade for `reaction`.**

## What I checked

**1. The delete path.** `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:393`) calls `s.Store.DeleteUser` (`store/user.go:171`), which delegates to the per-driver `DeleteUser`.

**2. The driver transactions.** Each driver has a `user_delete.go` that runs the whole cleanup in one `tx`. In `store/db/sqlite/user_delete.go:92-127` (`deleteUserTargetsTx`), reactions are removed by two explicit statements, in this order:

- `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-388`) — `DELETE FROM reaction WHERE content_id IN (...)`, where the content IDs are `memos/<uid>` for the user's memos and their comment subtree (`memoContentIDsFromRefs`, `store/db/sqlite/user_delete.go:512`). This removes *other people's* reactions on the deleted user's memos.
- `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`) — `DELETE FROM reaction WHERE creator_id = ?`. This removes the deleted user's own reactions on *anyone's* memos.

The Postgres and MySQL drivers do the same: `store/db/postgres/user_delete.go:383` and `:401`, `store/db/mysql/user_delete.go:420` and `:438`.

**3. The schema — ruling out a DB rule.** The `reaction` table has no foreign key at all; `creator_id` and `content_id` are plain columns:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

Grepping each `LATEST.sql` for `REFERENCES|FOREIGN KEY|CASCADE` returns exactly one hit per dialect — `memo_share.memo_id → memo(id) ON DELETE CASCADE` (e.g. `store/migration/sqlite/LATEST.sql:109`). Nothing touches `reaction`. Note also that `content_id` is a text `memos/<uid>` reference, not an integer FK, so a cascade from `memo` would not be expressible here anyway.

**4. Tests confirming the behavior.**
- `server/router/api/v1/test/reaction_service_test.go:229-235` — deletes the reactor, then asserts `ListMemoReactions` on someone else's memo is empty (covers the by-creator delete).
- `server/router/api/v1/test/memo_service_test.go:405`, `:445`, `:485` — analogous coverage on the memo-service side.
- `server/router/api/v1/test/user_service_delete_test.go:366`, `:429-431` — the rollback test: with the `DeleteUserFailpointBeforeCommit` failpoint (`store/db/sqlite/user_delete.go:47`), the reaction is still present afterward, which demonstrates the removal is transactional application code rather than a schema rule.
