## How I determined it runs, rather than the other two

There are three implementations of `CreateMemo` satisfying the `store.Driver` interface (`store/driver.go:29`), so the name alone is ambiguous:

- `store/db/sqlite/memo.go:16` — backtick-quoted identifiers, `?` placeholders, `RETURNING`
- `store/db/mysql/memo.go:16` — backtick-quoted, `?` placeholders, no `RETURNING`; uses `ExecContext` + `LastInsertId()` then re-reads via `GetMemo`
- `store/db/postgres/memo.go:38` — unquoted identifiers, `$n` placeholders via `placeholders(len(args))`, `RETURNING`

I resolved which one executes by following the runtime dispatch chain backwards from the call site:

1. **Call site is interface-typed.** `store/memo.go:109-113` — `Store.CreateMemo` validates the UID against `base.UIDMatcher`, then delegates to `s.driver.CreateMemo(ctx, create)`. `s.driver` is field `driver store.Driver` (`store/store.go:15`), assigned once in `New` (`store/store.go:38-48`). There is no caching or decorator layer between the store and the driver, so whatever concrete type is injected there is what runs.
2. **Injection point is a switch on a string.** `store/db/db.go` — `NewDBDriver` switches on `profile.Driver`, mapping `"sqlite"`/`"mysql"`/`"postgres"` to the respective `NewDB`, and returning `errors.New("unknown db driver")` for anything else. So the concrete type is fully determined by that one config value.
3. **The default value of that string is `sqlite`.** `cmd/memos/main.go:122` sets `viper.SetDefault("driver", "sqlite")`, and `main.go:130` registers the persistent flag with the same `"sqlite"` default. `main.go:43` reads `Driver: viper.GetString("driver")` into the profile. With no flags, no env var, and no config file, both layers yield `sqlite` — corroborated by `internal/profile/profile.go:110`, whose `if p.Driver == "sqlite" && p.DSN == ""` branch auto-derives the DSN as `<data>/memos_prod.db`; that branch only makes sense as the unconfigured default path.
4. **`sqlite.NewDB` returns the type owning the method.** `store/db/sqlite/sqlite.go:24` returns a `store.Driver` backed by `*sqlite.DB`, which is the receiver of the `CreateMemo` at `store/db/sqlite/memo.go:16`.

One methodological caveat worth flagging: grepping for `INSERT INTO memo` surfaces **only** the Postgres implementation, because SQLite and MySQL backtick-quote the table name (`` INSERT INTO `memo` ``). Text search alone would have pointed at the wrong driver here — the identifier-quoting difference between drivers is exactly what defeats it. The interface-dispatch trace above is what actually settles it.
