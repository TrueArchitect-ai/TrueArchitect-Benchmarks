The avatar is not stored as a file — it's a base64 data URI in the `user.avatar_url` column, decoded at serve time. The chain:

```

FileServerService.RegisterRoutes (GET /file/users/:identifier/avatar) — server/router/fileserver/fileserver.go:124
```

Notes on the hops that matter:

- **Route wiring:** `fileserver.NewFileServerService(...)` + `RegisterRoutes(echoServer)` at `server/server.go:81-82`.
- **Authorization is instance-wide, not per-user.** `serveUserAvatar` only authenticates when `s.Profile.AllowAnonymous()` is false (`fileserver.go:173-181`). On a public instance, any browser can fetch any user's avatar by username; there is no check that the viewer may see that profile. That's deliberate — avatars are treated as public profile data — and is covered by `TestServeUserAvatar_PrivateInstanceRequiresAuth` (`server/router/fileserver/fileserver_test.go:508`).
- **The `:identifier` param is username-only** (`getUserByUsername` sets `store.FindUser{Username: &identifier}`), despite the generic param name — an ID or `users/x` resource name will 404.
- **Type gate after retrieval:** the decoded MIME type must be in `avatarAllowedTypes` (`fileserver.go:75-83`, checked at `:201`), otherwise 400.
- **The data layer is the `user` table itself** — no attachment/blob/S3 path is involved for avatars, unlike `serveAttachmentFile`.
