**Premise correction:** There is no Redis in this repository. There is no Redis client dependency in `go.mod`, no Redis config/env var, and no Redis reference anywhere in the source tree (a case-insensitive grep for "redis" across the repo returns zero hits). The cache layer is entirely **in-process, in-memory** — a hand-rolled `sync.Map`-based cache, not an external cache server. There is consequently no connection to configure: no host, port, DSN, or pool, and no persistence or sharing across processes/replicas.

**Actual mechanism**

*The cache implementation* — `store/cache/cache.go`. `Cache` (`store/cache/cache.go:67`) wraps a `sync.Map` plus an atomic item counter. Each entry (`item`, `store/cache/cache.go:35`) carries a value, an absolute `expiration` timestamp, and a rough size estimate. `New()` (`store/cache/cache.go:76`) starts a background `cleanupLoop` goroutine that ticks on `CleanupInterval` and evicts expired entries; `Get` (`store/cache/cache.go:123`) also lazily evicts on read when `time.Now()` is past `expiration`.

*Where it's "configured"* — `store/store.go:38-61`. `Store.New` builds one `cache.Config` literal and shares it across all three caches:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

That config is used for `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). These are the closest thing to "connection configuration," and they are hardcoded — not read from env vars, flags, or a config file. An identical set of defaults also exists in `cache.DefaultConfig()` (`store/cache/cache.go:57`), used by `cache.NewDefault()`, but `Store` does not call it; it duplicates the literal.

*TTL for user entries* — **10 minutes**, inherited from `DefaultTTL`. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` (`store/cache/cache.go:93`) delegates to `SetWithTTL` with `c.config.DefaultTTL`. Nothing in the user path calls `SetWithTTL` with a custom duration, so users get the same 10 minutes as instance settings and user settings.

Two details worth knowing:

- **The 10-minute TTL rarely expires a hot user.** Cache keys are just the user ID (`userCacheKey`, `store/user.go:88`), and `ListUsers` re-`Set`s every returned user (`store/user.go:142-144`), which resets the expiration each time. Invalidation is driven by writes and by explicit `Delete` on user deletion (`store/user_delete.go:40`) far more than by TTL.
- **Only lookups by ID hit the cache.** `GetUser` consults `userCache` solely when `find.ID != nil` (`store/user.go:149-156`); lookups by username or other fields always fall through to the driver.

Also note `MaxItems: 1000` means the user cache can evict under pressure before TTL, via `cleanupOldest` (`store/cache/cache.go:253`), which drops roughly 20% of max items. Since all three caches use separate `Cache` instances, the 1000-item limit applies per cache, so users get their own 1000-entry budget.
