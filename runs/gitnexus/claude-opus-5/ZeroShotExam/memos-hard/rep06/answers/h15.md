Memo visibility is enforced at nine distinct server-side sites (plus the shared store-level filter primitive they compile down to). MCP is *not* a separate site — `server/router/mcp/adapter.go:33` replays tool calls through the Echo HTTP stack, so it inherits the API v1 checks.

**Core enforcement sites**

Single-memo read gate (`checkMemoReadAccess`, used by GetMemo + ListMemoComments) — `server/router/api/v1/memo_service.go:39-66` (call sites `:356`, `:367`, and `server/router/api/v1/memo_service_comments.go:148`)
List-query visibility filter (ListMemos: anonymous → PUBLIC only; authed → CEL `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`) — `server/router/api/v1/memo_service.go:217-227`
User-stats list filter (same anonymous/other-user narrowing, independent copy of the ListMemos logic) — `server/router/api/v1/user_service_stats.go:84-92` and `:217-221`
Per-RPC inline checks on memo sub-resources (each re-implements the check rather than calling `checkMemoReadAccess`) — `server/router/api/v1/reaction_service.go:30-42` and `:83`; `server/router/api/v1/memo_attachment_service.go:214-225`; `server/router/api/v1/memo_service_comments.go:41`
Attachment access via the API (derives permission from the parent memo's visibility) — `checkAttachmentAccess`, `server/router/api/v1/attachment_service.go:419-454`
Raw file HTTP surface (separate Echo service, own auth + `AllowAnonymous` and `share_token` fallbacks) — `checkAttachmentPermission`, `server/router/fileserver/fileserver.go:650-703`
SSE broadcast fan-out filter (per-connected-client, decides which live events a subscriber may receive) — `SSEClient.canReceive`, `server/router/api/v1/sse_hub.go:133-145` (event visibility stamped in `server/router/api/v1/sse_event_helpers.go:29-37`)
Public feed / crawler surfaces (hard-pinned to `store.Public`) — `server/router/rss/rss.go:90` and `:141`; sitemap at `server/router/frontend/frontend.go:150`
Notification & inbox content gating (two independent `canViewerAccessMemo` implementations plus mention targeting) — `server/router/api/v1/user_service_notifications.go:302-316`; `server/notification/email.go:306-320`; `canUserAccessMentionContext` / `shouldSkipMentionInbox` in `server/router/api/v1/memo_mention_helpers.go:56-89`

**Deliberate bypass**

Share-token path — visibility is intentionally *not* consulted; possession of a non-expired token is the authority (only archived/missing memos are rejected) — `GetMemoByShare` at `server/router/api/v1/memo_share_service.go:151-192`, expiry check at `:194-208`; mirrored by the `share_token` query-param fallback in `server/router/fileserver/fileserver.go:681-689`.

**Shared primitive**

`FindMemo.VisibilityList` (`store/memo.go:69`) becomes the SQL `visibility IN (...)` predicate per driver — `store/db/sqlite/memo.go:96`, `store/db/mysql/memo.go:104`, `store/db/postgres/memo.go:89`. This is the mechanism the list-based sites rely on, not an independent policy decision.

The notable structural observation: the point-read sites split into one shared helper (`checkMemoReadAccess`) and four hand-rolled copies of nearly the same predicate, and the list sites duplicate the filter logic between `memo_service.go` and `user_service_stats.go` — so the same rule exists in several textual forms, with small differences (e.g. `checkMemoReadAccess` has no `isSuperUser` escape hatch, while the reaction/attachment/comment checks do).
