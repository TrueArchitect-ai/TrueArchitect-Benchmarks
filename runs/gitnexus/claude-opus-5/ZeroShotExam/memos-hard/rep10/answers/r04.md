**Premise correction:** Neither. This repo (memos) has no message broker at all — no NATS, no RabbitMQ, no AMQP, no Kafka. `go.mod` and `go.sum` contain zero broker client dependencies (verified by grep for `nats`, `rabbitmq`, `amqp`, `streadway`). There is no external queue to declare and no broker connection config anywhere.

**Actual mechanism:** webhook delivery uses an in-process Go channel with a fixed pool of goroutine workers, entirely inside a single server process.

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel holding 128 payloads.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are only logged via `slog.Warn`; there is no retry, no ack, no dead-letter path.
- **Producer:** `PostAsync` at `internal/webhook/webhook.go:184-196` does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning — the queue is lossy by design, and it's also purely in-memory, so anything pending is lost on restart.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, which fan out one payload per registered user webhook for memo created/updated/deleted and comment-created events.
- **Actual delivery:** `Post` at `internal/webhook/webhook.go:120-180` does a plain HTTP POST via a shared `safeClient` (30s timeout, SSRF-guarding `safeDialContext` at `:59`), optionally signing with Standard Webhooks HMAC-SHA256 headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`).

So "workers consuming from a broker queue" maps here to 4 goroutines reading a 128-slot channel in the same process that produced the events.
