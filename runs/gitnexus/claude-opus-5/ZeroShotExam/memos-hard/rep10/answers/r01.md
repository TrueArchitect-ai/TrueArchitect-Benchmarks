**Premise correction:** There is no Redis in this repository. `grep -ri redis` across all Go, TypeScript, YAML, TOML, JSON and Markdown files returns nothing — no client dependency in `go.mod`, no connection string, no config field. Memos' cache layer is a hand-rolled, in-process, in-memory cache. Nothing is shared between processes, so the cache is per-server-instance and lost on restart.

**Actual mechanism**

*Implementation* — `store/cache/cache.go`. A `Cache` struct backed by `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). Each entry is an `item{value, expiration, size}` (`store/cache/cache.go:34-39`). There is no connection to configure — `cache.New(config)` just starts a background `cleanupLoop` goroutine (`store/cache/cache.go:76-85`).

*Configuration* — `store/store.go:39-44`, inline in `store.New()`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

This is a hardcoded literal — not read from env vars, flags, or a config file. `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) holds the identical values but is not what the store uses. The same single `cacheConfig` is passed to all three caches (`store/store.go:50-53`): `instanceSettingCache`, `userCache`, `userSettingCache`.

*TTL for user entries* — **10 minutes**, inherited from `DefaultTTL`. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:92-95`). No user code path calls `SetWithTTL` with a custom duration — the only explicit TTL constant in the repo is `instanceStatsCacheTTL = 60 * time.Second` (`server/router/api/v1/instance_stats.go:21`), which belongs to a separate ad-hoc stats memo cache in the API layer, not to this cache package.

Two things affect the effective lifetime beyond the 10-minute clock:

- **Expiry is lazy plus swept.** `Get` checks `time.Now().After(itm.expiration)` and deletes on read (`store/cache/cache.go:135-144`); a background sweep runs every 5 minutes (`store/cache/cache.go:200-250`). So a stale entry can physically persist up to ~5 minutes past its TTL, but is never *served* past it.
- **Capacity eviction can cut it short.** At >1000 items, `cleanupOldest` drops ~20% (`store/cache/cache.go:117-119`, `:253-255`), so on an instance with many users an entry may be evicted well before 10 minutes.

Cache keys are the plain user ID as a string (`store/user.go:88-90`); user *settings* use a separate `userID-key` composite in a different cache (`store/cache.go`). Explicit invalidation happens on delete (`store/user_delete.go:40`); updates overwrite rather than invalidate, which resets the 10-minute window.
