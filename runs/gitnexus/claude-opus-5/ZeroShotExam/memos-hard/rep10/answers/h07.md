**Request path:** browser gets `avatarUrl = "/file/users/{username}/avatar"` from the User API (built in `convertUserFromStore`, `server/router/api/v1/user_service_converters.go:46-50`), then `<img src>` in `UserAvatar` (`web/src/components/UserAvatar.tsx:14`) issues the GET.

Hops from the HTTP route to stored data:

- `FileServerService.RegisterRoutes` — server/router/fileserver/fileserver.go:124 (`GET /file/users/:identifier/avatar`; wired up in server/server.go:81-82)
- `FileServerService.serveUserAvatar` — server/router/fileserver/fileserver.go:168 (serving handler)
- `FileServerService.getCurrentUser` → `auth.Authenticator.AuthenticateToUser` — server/router/fileserver/fileserver.go:708; server/auth (only when `!s.Profile.AllowAnonymous()`, i.e. private instances)
- `FileServerService.getUserByUsername` — server/router/fileserver/fileserver.go:715 (builds `store.FindUser{Username: &identifier}`)
- `Store.GetUser` — store/user.go:148 (userCache is consulted only for `find.ID`, so a username lookup always falls through)
- `Store.ListUsers` — store/user.go:136 (delegates to the driver, then populates userCache)
- `DB.ListUsers` — store/db/sqlite/user.go:88 (`SELECT ... avatar_url ... FROM user WHERE username = ?`; peers at store/db/postgres/user.go and store/db/mysql/user.go)
- SQLite/Postgres/MySQL `user.avatar_url` column — the stored data

Back in the handler, `FileServerService.parseDataURI` (server/router/fileserver/fileserver.go:737) decodes the base64 data URI held in `user.AvatarURL`, the MIME type is checked against `avatarAllowedTypes` (line 75), and the bytes go out via `c.Blob` (line 209). There is no filesystem/S3 hop for avatars — unlike attachments, the image bytes live inline in the `user` row.
