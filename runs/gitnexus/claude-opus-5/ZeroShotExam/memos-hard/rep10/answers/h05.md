**Mechanism: explicit Go code** — two `DELETE FROM reaction` statements inside the delete-user transaction, one per storage driver. There is no database-level cascade for reactions.

## What I checked

**1. The delete-user transaction (the mechanism)**

Each driver has a `deleteUserTargetsTx` that issues the reaction deletes before removing the user row:

- `store/db/sqlite/user_delete.go:96` and `:102`
- `store/db/postgres/user_delete.go:96` and `:102`
- `store/db/mysql/user_delete.go:96` and `:102`

The two statements cover the two distinct ways a user is tied to a reaction:

| Helper | Statement | Covers |
|---|---|---|
| `deleteReactionsByContentIDsTx` — sqlite/postgres `:380`, mysql `:417` | `DELETE FROM reaction WHERE content_id IN (...)` | Everyone's reactions **on** the user's memos |
| `deleteReactionsByCreatorTx` — sqlite/postgres `:400`, mysql `:437` | `DELETE FROM reaction WHERE creator_id = ?` | The user's own reactions, including those left on **other people's** memos |

The `content_id` list is built by `memoContentIDsFromRefs` (sqlite `:512`) as `"memos/" + uid`, over the memo set from `listDeleteUserMemoTree` (sqlite `:129`) — a recursive CTE (iterative BFS on MySQL, `:133`) that walks the `COMMENT` relation, so reactions on comments beneath the user's memos are removed too. Note this also means reactions are joined to memos by a *string* `content_id`, not a memo FK — a DB cascade could not express that side at all.

All of this runs in one transaction (`DeleteUser`, sqlite `:29-59`), wrapped by `store/user.go:171` and reached from `server/router/api/v1/user_service.go:414`.

**2. Ruled out a database-level rule**

The `reaction` table has no foreign keys in any dialect — only a `UNIQUE(creator_id, content_id, reaction_type)`:

- `store/migration/sqlite/LATEST.sql:92-99` (original `store/migration/sqlite/0.20/00__reaction.sql`)
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

Grepping `ON DELETE`/`REFERENCES` across `store/migration/` returns hits only for `memo_share`, `user_setting`, `memo`, `memo_resource` — never `reaction`. Separately, SQLite opens with FK enforcement off entirely (`_pragma=foreign_keys(0)`, `store/db/sqlite/sqlite.go:53`), so even an FK wouldn't cascade there.

**3. Test coverage confirming the behavior**

- `store/test/user_delete_test.go:97-112, 217-220` — seeds reactions, then asserts a peer's reaction on an unrelated memo survives.
- `server/router/api/v1/test/user_service_delete_test.go:188-209, 287-298` — asserts reactions on the user's own memo and on their comment are empty afterward, while another user's reaction on a foreign memo is kept.
- Same file `:366-431` — the rollback failpoint test asserts the reaction still exists if the transaction aborts, confirming the deletes are transactional rather than incidental.
