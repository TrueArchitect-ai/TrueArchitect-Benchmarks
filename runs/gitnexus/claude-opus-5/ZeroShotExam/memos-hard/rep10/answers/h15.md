h15.

Memo visibility is enforced independently in several places — there is no single chokepoint; each surface re-implements the PUBLIC / PROTECTED / PRIVATE rule.

**Core RPC read gate**
- `checkMemoReadAccess` — single-memo read gate (archived → creator only; non-public → must be authed; private → creator only); called by `GetMemo` and parent-memo lookup — `server/router/api/v1/memo_service.go:39` (callers at `:356`, `:367`)
- `ListMemoComments` visibility gate (reuses `checkMemoReadAccess`) — `server/router/api/v1/memo_service_comments.go:148`

**RPC list/query filtering (enforced by narrowing the store query, not by rejecting)**
- `ListMemos` — anonymous ⇒ `VisibilityList = [PUBLIC]`; authed ⇒ CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` — `server/router/api/v1/memo_service.go:218-227`
- `ListAllUserStats` / `GetUserStats` — `VisibilityList` narrowed to PUBLIC (anon) or PUBLIC+PROTECTED (other users) — `server/router/api/v1/user_service_stats.go:84`, `:90`, `:218`, `:220`
- Store-level predicate that actually applies `VisibilityList` — `store/memo.go:69`, `store/db/sqlite/memo.go:96`, `store/db/mysql/memo.go:104`, `store/db/postgres/memo.go:89`

**Sibling RPC services with their own inline private-memo check (do not call `checkMemoReadAccess`)**
- `ListMemoReactions` / `UpsertMemoReaction` — `server/router/api/v1/reaction_service.go:30-38`, `:83`
- `ListMemoAttachments` — `server/router/api/v1/memo_attachment_service.go:214-222`
- `checkAttachmentAccess` (attachment RPC, resolves attachment → owning memo) — `server/router/api/v1/attachment_service.go:422-451`
- `CreateMemoComment` — `server/router/api/v1/memo_service_comments.go:41`

**Non-RPC HTTP surfaces**
- `checkAttachmentPermission` — raw file/attachment serving, with an anonymous-instance rule and a `share_token` bypass — `server/router/fileserver/fileserver.go:650-703` (private check at `:699`, share-token fallback at `:684-688`)
- RSS feeds (explore + per-user) — hard-pinned to `VisibilityList = [PUBLIC]` — `server/router/rss/rss.go:90`, `:141`
- Sitemap SSR — hard-pinned to `[PUBLIC]` — `server/router/frontend/frontend.go:150`
- MCP router is *not* a distinct site: it replays requests through the Echo API server (`server/router/mcp/adapter.go:27-42`), so it inherits the RPC checks; `server/router/mcp/catalog.go:12,14` only whitelists the tools.

**SSE fan-out**
- `SSEClient.canReceive` — per-connected-client filter on broadcast events (private ⇒ creator or admin) — `server/router/api/v1/sse_hub.go:134-142`

**Notification / inbox / email rendering (whether memo content may be shown to the notified user)**
- `canViewerAccessMemo` (inbox payloads) — `server/router/api/v1/user_service_notifications.go:302` (used at `:337`, `:342`, `:370`, `:385`)
- `canViewerAccessMemo` (duplicate implementation for outbound email) — `server/notification/email.go:306` (used at `:155`, `:187`)
- `canUserAccessMentionContext` / `shouldSkipMentionInbox` — mention fan-out — `server/router/api/v1/memo_mention_helpers.go:56`, `:75`

**Share-token path (alternate authority that deliberately overrides visibility)**
- `GetMemoByShare` — resolves an unexpired share token and returns the memo *without* any visibility check; the token is the authority (only archived/missing is rejected). Unauthenticated by design — `server/router/api/v1/memo_share_service.go:151-192`, allowlisted in `server/router/api/v1/acl_config.go:40`, `:71`

Two things worth flagging: the private-memo rule is written out by hand in at least eight separate places with subtly different admin handling (`checkMemoReadAccess` at `memo_service.go:63` has **no** super-user escape, while `reaction_service.go:38`, `memo_attachment_service.go:222`, and `attachment_service.go:451` all include `!isSuperUser(user)`), and `canViewerAccessMemo` exists as two independent copies (`user_service_notifications.go:302` uses `isSuperUser`, `email.go:306` compares `Role == store.RoleAdmin` directly).
