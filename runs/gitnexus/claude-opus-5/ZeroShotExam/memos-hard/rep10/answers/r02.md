**Premise correction: there is no per-user API rate-limiting middleware in this repo.** No middleware, interceptor, or handler enforces a per-user (or per-IP) request quota anywhere, so there are no "request limits" to report.

**What I checked**

- `server/server.go:51-52` — the only global Echo middleware registered is `middleware.Recover()` and `newCORSMiddleware(profile)`.
- `server/router/api/v1/v1.go:133-137` — the full Connect interceptor chain is `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor`. Nothing rate-related.
- `server/router/api/v1/connect_interceptors.go` — those four interceptors are the complete set defined in the file.
- No rate-limiting dependency is in use: `go.mod:151` lists `golang.org/x/time v0.15.0` only as `// indirect` (nothing imports `golang.org/x/time/rate`), and there's no tollbooth/ulule-style limiter.
- A repo-wide grep for rate/throttle/quota/429 language turns up only aspirational docs about *email* sending — `internal/email/README.md:286` ("### 5. Implement Rate Limiting") and `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse") — both unimplemented suggestions, not code.

**What likely prompted the question** — there are two limiting mechanisms, but neither is per-user and neither is rate-based:

1. **Request body size cap**, not a rate limit: `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` to the gateway routes (`v1.go:126,130-131`) and to the Connect mux (`v1.go:141,144`).
2. **Global concurrency semaphores**, not per-user quotas — these cap simultaneous in-flight work process-wide, and callers block rather than being rejected by a counter:
   - `imageProcessingSemaphore: semaphore.NewWeighted(2)` (`v1.go:60`) — at most 2 concurrent EXIF-strip operations, acquired in `acquireImageProcessingSlot` (`server/router/api/v1/attachment_service_image.go:67-77`). This is the source of the `ResourceExhausted` / "too many image processing requests" error at `server/router/api/v1/attachment_service.go:158-160` — but it only fires when the request context is canceled while waiting, not on a per-user rate.
   - `thumbnailSemaphore: semaphore.NewWeighted(3)` (`v1.go:59`), and a separate `maxConcurrentThumbnails = 3` in the file server (`server/router/fileserver/fileserver.go:46,116`).

If you want genuine per-user rate limiting, the natural insertion point is a new interceptor added to the chain at `server/router/api/v1/v1.go:133-137`, placed after `NewAuthInterceptor` so the authenticated user is available on the context.
