Notes worth having:

- **Where the URL comes from.** The browser never requests a raw avatar path from markup it invents — `convertUserFromStore` rewrites a base64 avatar into `/file/users/{username}/avatar` (`server/router/api/v1/user_service_converters.go:31-40`), and `UserAvatar` just sets it as `<img src>` (`web/src/components/UserAvatar.tsx:13`). A non-base64 `avatarUrl` is passed through verbatim and never touches this handler.
- **The "another user" part.** There is no per-user authorization on this route. On a public instance (`Profile.AllowAnonymous()` true) any avatar is served to anyone; on a private instance the only gate is *some* valid session/PAT — any authenticated viewer can fetch any other user's avatar by username.
- **The data layer is the `user` table itself**, not attachment/blob storage: avatars live inline in `user.avatar_url` as a base64 data URI. None of the S3/local-file/thumbnail machinery in `fileserver.go` is on this path — that's the attachment route (`serveAttachmentFile`, :133).
