**Premise correction:** Neither. This repo (memos) has no message broker at all — no NATS, no RabbitMQ, no AMQP/Kafka/Redis-queue dependency anywhere in `go.mod`/`go.sum`. (A grep for "nats" only hits Catalan words like "eliminats" in `web/src/locales/ca.json`.) There is also no separate worker process or queue-declaration step to find.

**Actual mechanism — an in-process buffered Go channel with a fixed goroutine pool**, all in `internal/webhook/webhook.go`:

- **"Queue" declaration** — `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel holding 128 payloads. That single line is the entire queue.
- **"Workers"** — `internal/webhook/webhook.go:42-55`: a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`; failures are logged with `slog.Warn` and dropped (no retry, no dead-letter).
- **Enqueue** — `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **silently dropped** with a warning — there's no durability, so anything in flight is lost on process restart.
- **Delivery** — `Post` (`internal/webhook/webhook.go:120-180`) does a plain HTTP POST via a shared `safeClient` (30s timeout, SSRF-guarded dialer at `webhook.go:59`), optionally signed with Standard Webhooks HMAC-SHA256 headers (`webhook-id`/`webhook-timestamp`/`webhook-signature`).

Producers are the API layer, not a broker publisher: `server/router/api/v1/memo_service_webhooks.go:43` and `:71` call `webhook.PostAsync(payload)` after loading the user's registered hooks via `s.Store.GetUserWebhooks` (webhook URLs are stored as user settings — `store/user_setting.go`, `proto/store/user_setting.proto`).
