**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the store's delete-user transaction, in all three DB drivers. There is no FK/cascade on the `reaction` table.

## What I checked

**1. Schema — is there a DB-level rule?** No. The `reaction` table has no foreign key on `creator_id` (or `content_id`) in any dialect:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-97`
- Original creation had none either: `store/migration/sqlite/0.20/00__reaction.sql`, `store/migration/mysql/0.20/00__reaction.sql`

The only `ON DELETE CASCADE` in current schema is `memo_share.memo_id → memo(id)` (e.g. `store/migration/sqlite/LATEST.sql:109`). Additionally, SQLite is opened with FK enforcement off — `_pragma=foreign_keys(0)` at `store/db/sqlite/sqlite.go:53` — so even legacy FKs from older migrations wouldn't cascade.

**2. Go delete path.** `server/router/api/v1/user_service.go:414` calls `store.DeleteUser` → `store/user.go:171` → driver. Each driver runs one transaction (`store/db/sqlite/user_delete.go:29-59`) whose statement sequence is `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`), which issues **two** reaction deletes:

- `deleteReactionsByContentIDsTx` — reactions *on* the deleted user's memos and their comment subtree, matched by `content_id IN ('memos/<uid>', …)`; content IDs come from the recursive memo-tree walk (`store/db/sqlite/user_delete.go:380-388`, `memoContentIDsFromRefs` at `:512`, tree query at `:134-147`)
- `deleteReactionsByCreatorTx` — reactions *authored by* the user anywhere, `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go:400-403`)

Identical pair in the other drivers:
- `store/db/postgres/user_delete.go:96,102,380-386,400-402`
- `store/db/mysql/user_delete.go:96,102,417-423,437-439`

**3. Tests confirming the behavior.**
- `store/test/user_delete_test.go:97-114, 216-220` — user's reaction on a peer's memo and a peer's reaction on the user's memo are both gone; only the unrelated peer reaction survives.
- `server/router/api/v1/test/reaction_service_test.go:219-232` — after deleting the reactor, `ListMemoReactions` on the surviving owner's memo returns empty (no orphaned reactions).

**Answer:** explicit Go code (two `DELETE FROM reaction` statements per driver, inside the delete-user transaction); `store/db/{sqlite,postgres,mysql}/user_delete.go` (`deleteReactionsByContentIDsTx`, `deleteReactionsByCreatorTx`), no FK/cascade in `store/migration/*/LATEST.sql`.
