When `DeleteMemo` runs (via `server/router/api/v1/memo_service.go:518`), the following tables are affected:

1. **`memo`** — the memo row itself is deleted, plus any comment memos are recursively deleted first (lines 567–577)
2. **`memo_relation`** — comment memo relations are found and their associated memos deleted; the `memo_relation` rows for the deleted memo are implicitly orphaned (no FK cascade defined on this table)
3. **`memo_share`** — cascaded automatically via `ON DELETE CASCADE` foreign key on `memo_share.memo_id` (defined in `store/migration/postgres/LATEST.sql:108`)

The `reaction` and `attachment` records are loaded before deletion (lines 545–557) but only for webhook payload construction — they are not explicitly deleted in the DeleteMemo code path, nor do they have CASCADE constraints on `memo.id`.
