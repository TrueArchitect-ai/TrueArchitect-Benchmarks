The browser hits `GET /file/users/:identifier/avatar`. Here is each hop from HTTP handler to data layer:

1. `serveUserAvatar` — `server/router/fileserver/fileserver.go:167` (HTTP handler, registered at line 124)
2. `getUserByUsername` — `server/router/fileserver/fileserver.go:715` (resolves the `:identifier` param to a user)
3. `Store.GetUser` — `store/user.go:148` (store-level lookup; checks user cache, then delegates)
4. `Store.ListUsers` — `store/user.go:136` (called by `GetUser` at line 158; delegates to the driver)
5. `driver.ListUsers` — `store/driver.go:47` (driver interface); concrete implementation e.g. `DB.ListUsers` — `store/db/sqlite/user.go:88`

The returned `User.AvatarURL` (a `data:` URI) is then decoded inline by `parseDataURI` (`server/router/fileserver/fileserver.go:737`) and served as a blob — no further store hop is needed for the image data itself, since the avatar is stored as a base64 data URI directly on the user row.
