**Mechanism: explicit Go code** — reactions are removed by two dedicated functions within the user-deletion transaction, across all three database drivers.

**Evidence locations:**

In each driver's `deleteUserTargetsTx` function, two reaction-deletion steps execute inside the transaction:

1. **`deleteReactionsByContentIDsTx`** — deletes reactions on the user's memos (by `content_id`):
   - `store/db/sqlite/user_delete.go:96` (call) and `:380–388` (implementation: `DELETE FROM reaction WHERE content_id IN ...`)
   - `store/db/mysql/user_delete.go:96` (call) and `:417–425` (implementation)
   - `store/db/postgres/user_delete.go:96` (call) and `:380–388` (implementation)

2. **`deleteReactionsByCreatorTx`** — deletes reactions the user created on any content (by `creator_id`):
   - `store/db/sqlite/user_delete.go:102` (call) and `:400–403` (implementation: `DELETE FROM reaction WHERE creator_id = ?`)
   - `store/db/mysql/user_delete.go:102` (call) and `:437–440` (implementation)
   - `store/db/postgres/user_delete.go:102` (call) and `:400–403` (implementation)

There are no foreign-key cascade constraints handling this — the schema migrations do not define `ON DELETE CASCADE` from `user` to `reaction`. The cleanup is entirely in explicit Go code, executed within the same database transaction that deletes the user row.
