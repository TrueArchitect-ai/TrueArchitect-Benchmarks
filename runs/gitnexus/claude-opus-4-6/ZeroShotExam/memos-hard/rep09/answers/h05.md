**Explicit Go code**; reactions are removed by application-level DELETE statements inside a transaction, not by database CASCADE rules.

The `reaction` table has **no foreign key constraints** at all — no `ON DELETE CASCADE` on `creator_id` or `content_id`:

- `store/migration/sqlite/LATEST.sql:91-99` (and equivalent Postgres/MySQL migrations) — plain columns, no FK.

When a user is deleted, the driver-level `deleteUserTargetsTx` function performs two explicit cleanup steps within the deletion transaction:

1. **Delete all reactions on the user's memos** (by content ID):  
   `DELETE FROM reaction WHERE content_id IN (...)` — `store/db/sqlite/user_delete.go:96-98,380-388` (and identical code in `postgres/user_delete.go`, `mysql/user_delete.go`).

2. **Delete all reactions the user placed on others' content** (by creator ID):  
   `DELETE FROM reaction WHERE creator_id = ?` — `store/db/sqlite/user_delete.go:102-104,400-403` (and identical in the other drivers).

Both run inside the same transaction before the memo and user rows are deleted (`store/db/sqlite/user_delete.go:92-127`). Test coverage confirming this behavior is at `store/test/user_delete_test.go:97-114,216-220`.

**Mechanism: explicit Go code; evidence: `store/db/{sqlite,postgres,mysql}/user_delete.go` (application-level DELETEs in transaction), `store/migration/*/LATEST.sql` (no FK/CASCADE on reaction table).**
