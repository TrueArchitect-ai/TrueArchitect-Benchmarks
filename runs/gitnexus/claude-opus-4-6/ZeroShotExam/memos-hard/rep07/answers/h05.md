h05.

**Explicit Go code**; reactions are deleted in application-level Go code within a transaction — there are no database-level CASCADE rules.

**Evidence:**

The `reaction` table has no foreign key constraints at all — no `ON DELETE CASCADE` or any referential action:
- `store/migration/postgres/0.20/00__reaction.sql` — `creator_id INTEGER NOT NULL` with no FK
- `store/migration/sqlite/0.20/00__reaction.sql` — same
- `store/migration/mysql/0.20/00__reaction.sql` — same

Instead, `deleteUserTargetsTx` in each backend's `user_delete.go` explicitly issues two DELETE statements inside a transaction:

1. **`deleteReactionsByContentIDsTx`** — removes all reactions *on* the deleted user's memos (`DELETE FROM reaction WHERE content_id IN (...)`)
   - `store/db/postgres/user_delete.go:96,380-388`
   - `store/db/sqlite/user_delete.go:96,380-388`
   - `store/db/mysql/user_delete.go:96,417-425`

2. **`deleteReactionsByCreatorTx`** — removes all reactions *created by* the deleted user (`DELETE FROM reaction WHERE creator_id = ?`)
   - `store/db/postgres/user_delete.go:102,400-403`
   - `store/db/sqlite/user_delete.go:102,400-403`
   - `store/db/mysql/user_delete.go:102,437-440`

Both are called before the user row itself is deleted, within the same transaction orchestrated by `deleteUserTargetsTx`.
