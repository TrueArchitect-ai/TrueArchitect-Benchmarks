The premise is incorrect — there is no Redis connection in this project. The cache layer is entirely **in-memory**, implemented in pure Go using `sync.Map`, not Redis.

**Cache implementation:** `store/cache/cache.go` defines a `Cache` struct backed by `sync.Map` with TTL-based expiration and a background cleanup goroutine (lines 66–85).

**Configuration:** The cache is configured in `store/store.go:38–45` via a `cache.Config` struct with hardcoded defaults:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
}
```

**User entry TTL:** The `userCache` is created at `store/store.go:52` with the same shared `cacheConfig`, so user entries get the `DefaultTTL` of **10 minutes**. There is no per-cache TTL override — all three caches (`instanceSettingCache`, `userCache`, `userSettingCache`) share the identical config.

There is a separate, unrelated RSS feed cache in `server/router/rss/rss.go` using a plain `map[string]*cacheEntry` with a 1-hour TTL (`defaultCacheDuration`, line 25), but that caches rendered RSS XML, not user data, and is also not Redis-backed.
