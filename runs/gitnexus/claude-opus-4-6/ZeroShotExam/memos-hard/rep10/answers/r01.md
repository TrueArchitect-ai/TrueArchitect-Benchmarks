The premise is incorrect — there is no Redis connection in this project. The cache layer is entirely **in-memory**, implemented as a custom Go cache using `sync.Map` in `store/cache/cache.go`.

The cache is configured in `store/store.go:38-45`, where `New()` constructs a `cache.Config` with a **`DefaultTTL` of 10 minutes**, a cleanup interval of 5 minutes, and a max of 1000 items. The user cache is one of three `*cache.Cache` instances created with this same config (`store/store.go:52`):

```go
userCache: cache.New(cacheConfig),
```

So user entries share the default **10-minute TTL** — there is no per-cache override for users. The `cache.Cache` struct (`store/cache/cache.go:67-73`) stores items with an expiration timestamp and evicts them lazily on read (`Get`, line 135) and periodically via a background `cleanupLoop` (line 200).

On the frontend side, there is a separate editor draft cache (`web/src/components/MemoEditor/services/cacheService.ts`) that uses **browser `localStorage`** — also not Redis. It has no TTL; entries persist until explicitly cleared.
