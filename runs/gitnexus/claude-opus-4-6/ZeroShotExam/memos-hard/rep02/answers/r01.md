**Premise correction:** There is no Redis connection in this project. The cache layer does not use Redis at all.

**Actual mechanism:** The cache is a **custom in-memory implementation** built on Go's `sync.Map`, defined in `store/cache/cache.go`. It is configured and instantiated in `store/store.go:38-45`, where the `Store` constructor creates a `cache.Config` with:

- **DefaultTTL:** 10 minutes (`store/store.go:41`)
- **CleanupInterval:** 5 minutes (`store/store.go:42`)
- **MaxItems:** 1000 (`store/store.go:43`)

These same defaults apply uniformly to all three cache instances created in `store/store.go:51-53`: `instanceSettingCache`, `userCache`, and `userSettingCache`. There is no per-cache TTL override — **user entries get the same 10-minute default TTL** as all other cached entities.

The cache supports per-item TTL override via `SetWithTTL()` (`store/cache/cache.go:98`), but the standard `Set()` method (`store/cache/cache.go:93-95`) delegates to `SetWithTTL` with the configured `DefaultTTL`. Expired items are cleaned up both lazily on read (`store/cache/cache.go:135-136`) and proactively by a background goroutine running every `CleanupInterval` (`store/cache/cache.go:200-215`).

Separately, the frontend has its own `cacheService` (`web/src/components/MemoEditor/services/cacheService.ts`) for editor draft persistence, but that uses browser `localStorage` with no TTL — it is unrelated to the server-side cache layer.
