**Premise correction:** Neither. The webhook delivery workers don't consume from an external message broker at all — there's no NATS or RabbitMQ dependency anywhere in this codebase (`go.mod`/`go.sum` have no such entries, and no `.go` files reference `nats.` or `amqp`).

**Actual mechanism:** Webhook dispatch uses an in-process, in-memory Go channel as a bounded queue, defined in `internal/webhook/webhook.go:39`:

```go
asyncPostQueue = make(chan *WebhookRequestPayload, 128)
```

Four worker goroutines are spawned in `init()` (`internal/webhook/webhook.go:42-55`) that range over this channel and call `Post()` to deliver each webhook via HTTP. Producers enqueue work through `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send and drops (with a warning log) if the channel is full — there's no persistence or external broker, so queued webhooks are lost on process restart.
