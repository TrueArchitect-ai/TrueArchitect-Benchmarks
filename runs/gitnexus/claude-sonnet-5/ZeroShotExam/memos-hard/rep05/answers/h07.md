Back in `serveUserAvatar`, the returned `user.AvatarURL` (a data-URI stored in the `user` row) is parsed by `parseDataURI` and streamed back as the image blob — no additional data-layer access is needed since the avatar bytes are embedded in the user record itself, not a separate file/blob store.

Note: there is no per-viewer ownership check on the target avatar — `serveUserAvatar` only verifies the *viewer* is authenticated (on private instances), not that the viewer owns the requested `identifier`, which is expected for a public-facing avatar endpoint but worth confirming matches intended access-control design.
