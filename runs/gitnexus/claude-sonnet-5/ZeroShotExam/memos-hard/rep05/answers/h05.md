h05.
Mechanism: **explicit Go code**, not a database-level cascade rule.

Evidence:
- `store/db/postgres/user_delete.go:100-104`, `store/db/mysql/user_delete.go:100-104` (equivalent) — `DeleteUser` calls `deleteReactionsByCreatorTx(ctx, tx, userID)`, which runs `DELETE FROM reaction WHERE creator_id = ?`.
- `store/db/sqlite/user_delete.go:400-403` — identical `deleteReactionsByCreatorTx` doing the same `DELETE FROM reaction WHERE creator_id = ?`.
- Same files (all three dialects) also call `deleteReactionsByContentIDsTx` (e.g. `store/db/postgres/user_delete.go:96,380-388`) which deletes `reaction` rows whose `content_id` matches any of the deleted user's memos — so reactions *on* the deleted user's memos are removed too, again by explicit Go code, not a DB trigger.
- This all happens inside one transaction in `DeleteUser` (`store/db/postgres/user_delete.go:29-59`), ordered before `deleteUserRowTx` deletes the `"user"` row (line 123 / 461).
- Schema check: `store/migration/{postgres,mysql,sqlite}/LATEST.sql` (~lines 90-98) define `reaction.creator_id` as a plain `INTEGER`/`INT` column with **no foreign key constraint** to `user`, and no `ON DELETE CASCADE` anywhere in the reaction table definition — ruling out a database-level rule.
- `store/test/user_delete_test.go` and `store/test/reaction_test.go` exercise this path, corroborating it's intentional application logic.

So both reactions the user created and reactions on the user's own memos are cleaned up, entirely via application-level SQL statements in a transaction — the database schema imposes no cascading rule on its own.
