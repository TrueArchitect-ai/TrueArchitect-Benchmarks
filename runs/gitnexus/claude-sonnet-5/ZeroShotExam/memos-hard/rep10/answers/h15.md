Memo visibility (who may view/receive a memo) is checked independently in several places — there is no single central gate; each surface re-implements (or duplicates) the Private/Protected/Public rules:

- Memo read/get/list access (`checkMemoReadAccess`, used by `GetMemo` and `ListMemoComments`; plus inline visibility filter in `ListMemos`) — server/router/api/v1/memo_service.go
- Comment creation visibility check (`CreateMemoComment` inline check on the parent memo) — server/router/api/v1/memo_service_comments.go
- Reaction list/create visibility check (inline, duplicated per-handler) — server/router/api/v1/reaction_service.go
- Attachment access control (`checkAttachmentAccess`, follows linked memo's visibility) — server/router/api/v1/attachment_service.go
- Memo-scoped attachment listing visibility check (`ListMemoAttachments` inline check) — server/router/api/v1/memo_attachment_service.go
- SSE event delivery filtering (`SSEClient.canReceive`, gates real-time broadcasts by visibility/creator/admin) — server/router/api/v1/sse_hub.go
- In-app notification payload filtering (`canViewerAccessMemo`) — server/router/api/v1/user_service_notifications.go
- Email notification payload filtering (`canViewerAccessMemo`, a separate duplicate implementation in a different package) — server/notification/email.go

Note: `acl_config.go` (server/router/api/v1/acl_config.go) marks `GetMemo`/`ListMemos`/`ListMemoComments` as not requiring authentication but explicitly defers actual visibility enforcement to the service layer above, so it is not itself an enforcement site.
