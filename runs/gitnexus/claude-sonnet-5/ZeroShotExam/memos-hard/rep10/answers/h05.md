**Mechanism: explicit Go code** (application-level, inside the `DeleteUser` transaction) — **not** a database-level cascade/trigger rule.

**Evidence:**

1. **Schema has no FK/cascade on `reaction`** — `store/migration/sqlite/LATEST.sql:92-99` (and the equivalent postgres/mysql `LATEST.sql`) shows `reaction` as a bare table (`id, created_ts, creator_id, content_id, reaction_type`, unique constraint) with no foreign key or `ON DELETE CASCADE` clause referencing `user` or `memo`. So the database itself does nothing automatically.

2. **Go code explicitly deletes reactions during user deletion**, in all three DB drivers, inside `deleteUserTargetsTx`:
   - `store/db/sqlite/user_delete.go:96-104`
   - `store/db/postgres/user_delete.go:96-104`
   - `store/db/mysql/user_delete.go:96-104`
   
   Two explicit deletes cover both directions:
   - `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` for every memo (including comments) owned by the deleted user (removes reactions *others* left on the deleted user's content) — e.g. `store/db/sqlite/user_delete.go:380-388`.
   - `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` (removes reactions the deleted user *made* on others' content) — e.g. `store/db/sqlite/user_delete.go:400-403`.

3. **Confirmed by test**: `store/test/user_delete_test.go:97-114, 216-220` creates three reactions (one by the peer on the deleted user's memo, one by the deleted user on the peer's memo, one by the peer on their own memo) and asserts after deletion that only the unrelated peer-on-peer reaction survives — proving both deletion paths run and nothing is left orphaned.

Both target-side (content owner deleted) and actor-side (reaction creator deleted) reactions are cleaned up, purely via application logic in the transactional delete-user routine, before the `user` row itself is deleted.
