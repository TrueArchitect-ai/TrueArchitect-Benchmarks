**Premise correction:** There is no Redis anywhere in this codebase (memos) — a repo-wide search for "redis" turns up zero matches. The cache layer is a pure in-process, in-memory Go cache, not an external Redis connection.

**Actual mechanism:** It's implemented in `store/cache/cache.go` (a generic `Cache` type with `Set`/`SetWithTTL`/`Config`) and instantiated in `store/store.go:38-58`. `Store.New` builds a single `cache.Config{DefaultTTL: 10 * time.Minute, CleanupInterval: 5 * time.Minute, MaxItems: 1000}` and reuses it for three separate in-memory caches: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:24-29,40-53`).

For user entries specifically: `userCache` is one of these three caches, and since entries are written with the plain `Set` (which calls `SetWithTTL(ctx, key, value, c.config.DefaultTTL)` per `store/cache/cache.go:93-94`), user cache entries expire after the shared **10-minute default TTL**, with a background cleanup sweep every 5 minutes and a 1000-item cap (LRU/eviction behavior governed by `MaxItems`/`OnEviction` in the same config).

There's an unrelated second cache (`server/router/rss/rss.go`) for RSS feed responses with its own 1-hour TTL, but that's not the "user entries" cache — that's the `userCache` in `store/store.go`.
