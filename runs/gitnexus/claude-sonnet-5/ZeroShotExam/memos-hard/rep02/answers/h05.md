Mechanism: **explicit Go application code** (not a database-level rule). The `reaction` table has no foreign key at all on `creator_id`/`content_id` in any of the three supported SQL dialects, so cleanup is done manually inside the same transaction as user deletion.

Evidence locations:
- `store/user.go:171` — `Store.DeleteUser` dispatches to a dialect-specific driver.
- `store/db/sqlite/user_delete.go:92-127` (and the structurally identical `store/db/mysql/user_delete.go` / `store/db/postgres/user_delete.go`) — `deleteUserTargetsTx` explicitly calls, in order:
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — deletes reactions **on** the memos the user owned (`DELETE FROM reaction WHERE content_id IN (...)`), run before those memos are deleted.
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` — deletes reactions the user **made** (`DELETE FROM reaction WHERE creator_id = ?`).
  - Helper implementations at `store/db/sqlite/user_delete.go:380-403` (identical logic in `mysql/user_delete.go:417-440` and `postgres/user_delete.go:380-403`).
- Schema check — `store/migration/{sqlite,mysql,postgres}/LATEST.sql`, `reaction` table (~lines 91-99 in each): columns `creator_id INTEGER/INT NOT NULL` and `content_id TEXT/VARCHAR NOT NULL`, with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — **no `FOREIGN KEY` and no `ON DELETE CASCADE`** on either column, in any dialect. (Contrast with `memo_share` in the same files, which does declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`.) `content_id` is a string resource name (`memos/<uid>`), not even FK-able to `memo.id`.
- Corroborating tests: `store/test/user_delete_test.go` (`TestDeleteUserCleansRelatedData`) and `server/router/api/v1/test/user_service_delete_test.go`.
