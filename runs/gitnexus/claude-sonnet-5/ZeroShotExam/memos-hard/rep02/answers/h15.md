Memo-visibility enforcement is duplicated across at least six independent server-side sites rather than funneled through one shared authorization layer:

1. **Shared gRPC read-access helper** — `server/router/api/v1/memo_service.go` (`checkMemoReadAccess`, called from `GetMemo` and reused by comment listing in `server/router/api/v1/memo_service_comments.go`)
2. **Reaction endpoints (separate re-implementation)** — `server/router/api/v1/reaction_service.go` (`ListMemoReactions`, `UpsertMemoReaction` each inline-check `memo.Visibility` rather than calling `checkMemoReadAccess`)
3. **Attachment listing endpoint (separate re-implementation)** — `server/router/api/v1/memo_attachment_service.go` (`ListMemoAttachments` inline-checks visibility again)
4. **Raw file/attachment HTTP server** — `server/router/fileserver/fileserver.go` (`checkAttachmentPermission`, a third independent implementation that also handles the `share_token` bypass path)
5. **Real-time SSE event broadcast filter** — `server/router/api/v1/sse_hub.go` (`SSEClient.canReceive`, filters push events by `event.Visibility`/`CreatorID` independent of the request-based checks above)
6. **Query-level visibility restriction for listings/feeds** — instead of per-item checks, these restrict the query itself to allowed `VisibilityList` values: `server/router/api/v1/memo_service.go` (`ListMemos`), `server/router/api/v1/user_service_stats.go` (memo stats/heatmap), `server/router/rss/rss.go` (RSS feed, public-only), and `server/router/frontend/frontend.go` (SSR meta tags, public-only)
