**Premise correction:** Neither. This repository (usememos/memos) has no NATS or RabbitMQ dependency anywhere in the codebase — there is no external message broker involved in webhook delivery at all.

**Actual mechanism:** Webhook delivery is handled entirely in-process with an in-memory buffered Go channel, not a message broker:

- `asyncPostQueue` is declared as `make(chan *WebhookRequestPayload, 128)` in `internal/webhook/webhook.go:39` — a bounded, in-memory Go channel (capacity 128), not a broker-backed queue.
- A pool of 4 goroutines is spun up in an `init()` function (`internal/webhook/webhook.go:42-55`) that range over `asyncPostQueue` and call `Post()` for each payload, performing a direct `http.Client.Do()` POST to the webhook URL (`internal/webhook/webhook.go:120-180`).
- Producers call `webhook.PostAsync()` (`internal/webhook/webhook.go:184-194`), which does a non-blocking `select` send into `asyncPostQueue`, dropping (and logging a warning for) the payload if the channel is full — there's no persistence or durability.
- Dispatch is triggered from request handlers like `dispatchMemoRelatedWebhook` in `server/router/api/v1/memo_service_webhooks.go` and `dispatchMemoUpdatedSideEffects` in `server/router/api/v1/memo_update_helpers.go`.

So "the queue" is a fixed-size Go channel living inside the single server process, consumed by 4 worker goroutines — there's no separate broker process, no queue declaration/binding, and no cross-process consumption.
