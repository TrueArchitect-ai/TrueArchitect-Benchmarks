h05.
Mechanism: **explicit Go application code** inside the `DeleteUser` transaction — no database-level `ON DELETE CASCADE` rule is involved.

Evidence:
- Schema: `reaction` table has no foreign key at all on `creator_id` (or `content_id`) in any backend's `LATEST.sql` migration — `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/sqlite/LATEST.sql:92-99`. It's just a plain column with a `UNIQUE(creator_id, content_id, reaction_type)` constraint, so the DB has no way to cascade-delete reactions on its own.
- Go code: each backend's `deleteUserTargetsTx` explicitly deletes reactions in two passes before other cleanup steps, all inside the same SQL transaction as the user deletion:
  - `deleteReactionsByContentIDsTx` — removes reactions *on* memos owned by the deleted user (keyed by the user's memo tree's `content_id`s), e.g. `store/db/postgres/user_delete.go:96,380-388`, `store/db/mysql/user_delete.go:96,417-... `, `store/db/sqlite/user_delete.go:96,380-388`.
  - `deleteReactionsByCreatorTx` — removes reactions the deleted user *made* on any memo, via `DELETE FROM reaction WHERE creator_id = ?`, e.g. `store/db/postgres/user_delete.go:102,400-403`, `store/db/mysql/user_delete.go:102,437-...`, `store/db/sqlite/user_delete.go:102,400-403`.
- The orchestration lives in `deleteUserTargetsTx`, called from `DeleteUser` (`store/db/postgres/user_delete.go:29`, mirrored in the mysql/sqlite equivalents), and the store-level test `store/test/user_delete_test.go:TestDeleteUserCleansRelatedData` / `server/router/api/v1/test/user_service_delete_test.go` exercise this cleanup behavior.

So both a user's own reactions and reactions left on their memos are removed, but purely via explicit application-level `DELETE` statements run in the same transaction — not by a database foreign-key cascade.
