The browser hits `GET /file/users/:identifier/avatar`, routed to `serveUserAvatar`, which resolves the target user by username/identifier, reads the `AvatarURL` field off the `store.User` struct, and serves it directly (no separate blob store — avatar is a data-URI stored inline on the user row). The chain down to the data layer:

- `serveUserAvatar` — server/router/fileserver/fileserver.go:167 (route: `GET /file/users/:identifier/avatar`, registered in `RegisterRoutes`, fileserver.go:124)
- `getUserByUsername` — server/router/fileserver/fileserver.go:714
- `Store.GetUser` — store/user.go:148
- `Store.ListUsers` — store/user.go:136 (also populates `userCache`)
- `driver.ListUsers` (interface field `Store.driver`, `store.Driver`) — store implementation entry point
- `DB.ListUsers` — store/db/sqlite/user.go:88 (builds `SELECT ... FROM user WHERE ...`, default driver; parallel implementations in store/db/mysql/user.go and store/db/postgres/user.go)

The resulting `store.User.AvatarURL` (store/user.go:43) is the stored data — parsed as a data URI (`parseDataURI`, fileserver.go) and streamed back as the image blob. No authorization check restricts viewing *other* users' avatars beyond the private-instance/anonymous gate (`Profile.AllowAnonymous`) — any authenticated (or, on public instances, anonymous) caller can fetch any user's avatar by username via this route.
