**Mechanism: explicit Go code (application-level), inside the `DeleteUser` transaction — not a database-level cascade/trigger.**

Evidence:

- Schema check: `reaction` table has no foreign key on `creator_id` or `content_id` in any driver's schema (`store/migration/mysql/LATEST.sql`, `store/migration/sqlite/LATEST.sql`, `store/migration/postgres/LATEST.sql` — just a `UNIQUE(creator_id, content_id, reaction_type)` constraint). So there is no DB-level `ON DELETE CASCADE` rule that would remove reactions automatically.
- Application code deletes reactions explicitly, in two passes, for all three DB drivers:
  - `store/db/sqlite/user_delete.go:96` (and mirrored at `store/db/mysql/user_delete.go:96`, `store/db/postgres/user_delete.go:~96`) — `deleteReactionsByContentIDsTx` removes reactions attached to memos owned by the deleted user (`DELETE FROM reaction WHERE content_id IN (...)`, `store/db/sqlite/user_delete.go:380`, `store/db/mysql/user_delete.go:417`, `store/db/postgres/user_delete.go:383`).
  - `store/db/sqlite/user_delete.go:102` (and mirrored at `store/db/mysql/user_delete.go:102`, `store/db/postgres/user_delete.go:~102`) — `deleteReactionsByCreatorTx` removes reactions the deleted user made on any memo (`DELETE FROM reaction WHERE creator_id = ?`, `store/db/sqlite/user_delete.go:400`, `store/db/mysql/user_delete.go:438`, `store/db/postgres/user_delete.go:401`).
- These are invoked from `deleteUserTargetsTx`, called within `Store.DeleteUser` (`store/user.go:171`) via each driver's `DB.DeleteUser` (e.g. `store/db/mysql/user_delete.go:29`), all inside a single DB transaction so the cleanup is atomic with the rest of user deletion.
- Test coverage confirms this behavior: `server/router/api/v1/test/user_service_delete_test.go` (`TestDeleteUserSelfDeleteRemovesOwnedResourcesAndMemoSubtrees`, `TestDeleteUserRollbackPreservesAllResources`) and `store/test/reaction_test.go`.
