Detail on each hop:

1. **`serveUserAvatar`** (`server/router/fileserver/fileserver.go:167-209`) — the Echo handler bound to `GET /file/users/:identifier/avatar`. It reads `identifier` from the URL path param, and if the instance isn't `AllowAnonymous`, it only checks that *some* viewer is authenticated (`getCurrentUser`) — it does **not** verify the viewer matches `identifier`, so any authenticated (or anonymous, if allowed) user can request any other user's avatar by username.
2. **`getUserByUsername`** (`fileserver.go:714-716`) — thin wrapper: `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`.
3. **`Store.GetUser`** (`store/user.go:147-168`) — checks the in-memory `userCache` (by ID only, so a username lookup always misses), otherwise calls `Store.ListUsers`.
4. **`Store.ListUsers`** (`store/user.go:135-145`) — delegates to `s.driver.ListUsers(ctx, find)`, then populates the cache.
5. **`DB.ListUsers`** (driver implementation — e.g. `store/db/sqlite/user.go:88`, `store/db/mysql/user.go:84`, `store/db/postgres/user.go:87`) — builds and executes the SQL `SELECT` against the `user` table (filtered by `username`), returning the row including `avatar_url`, which is where the stored profile image data (`user.AvatarURL`, `store/user.go`) lives.

The image bytes themselves are decoded back in `serveUserAvatar` from the `AvatarURL` data URI (`parseDataURI`, `fileserver.go`) and streamed as the response blob — the "stored data" is the base64 image embedded in the `user.avatar_url` column, not a separate file/blob store.
