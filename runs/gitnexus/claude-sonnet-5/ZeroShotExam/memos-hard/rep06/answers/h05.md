Confirmed: the `reaction` table has no foreign key on `creator_id`, so no DB-level cascade covers reactions on user deletion — deletion is done entirely via explicit Go code.

h05. **Mechanism: explicit Go code (application-level transaction), not a database-level rule.**

The `reaction` table (`store/migration/{postgres,mysql,sqlite}/LATEST.sql`, e.g. `store/migration/postgres/LATEST.sql:91-98`) has no `FOREIGN KEY` on `creator_id` and no `ON DELETE CASCADE` — unlike e.g. `memo_share.memo_id`, which *does* declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`. So the database itself would leave orphaned reaction rows if a user row were simply deleted.

Instead, each of the three per-driver `DeleteUser` implementations — `store/db/postgres/user_delete.go`, `store/db/sqlite/user_delete.go`, `store/db/mysql/user_delete.go` — runs the deletion inside one explicit transaction (`deleteUserTargetsTx`) that removes reactions via two targeted queries before deleting the user row itself:

- `deleteReactionsByContentIDsTx` (e.g. `store/db/postgres/user_delete.go:380-388`): `DELETE FROM reaction WHERE content_id IN (...)` for every memo (and its comment-tree) owned by the deleted user — removes reactions *others* left on that user's memos.
- `deleteReactionsByCreatorTx` (e.g. `store/db/postgres/user_delete.go:400-403`): `DELETE FROM reaction WHERE creator_id = ?` — removes reactions *the deleted user* left on any memo.

Both calls happen early in `deleteUserTargetsTx` (`store/db/postgres/user_delete.go:92-127`, mirrored in the sqlite and mysql files at the same lines), before the user row (`deleteUserRowTx`) or memo rows are deleted, and everything commits/rolls back atomically in one `sql.Tx`.

Also checked: `store/reaction.go` (interface) and `store/test/user_delete_test.go` / `store/test/reaction_test.go` for corroborating test coverage of this behavior — consistent with the above.
