**Mechanism:** Explicit Go code deletes reactions inside the `DeleteUser` transaction — there is no DB-level foreign-key `ON DELETE CASCADE` on `reaction.creator_id` or `reaction.content_id`.

**Evidence locations:**
- Schema has no FK/cascade on the `reaction` table: `store/migration/postgres/LATEST.sql:91-98` (same pattern in `store/migration/mysql/LATEST.sql:91` and `store/migration/sqlite/LATEST.sql:92`) — `creator_id`/`content_id` are plain columns, no `REFERENCES`/`CASCADE`.
- Application-level deletion in the user-delete transaction (identical logic duplicated per driver):
  - `store/db/postgres/user_delete.go:96-104` — calls `deleteReactionsByContentIDsTx` (removes reactions on every memo/comment the deleted user authored, matched by `content_id`) and `deleteReactionsByCreatorTx` (removes reactions the deleted user themself made on any memo), both executed before the memo rows and the user row are deleted.
  - Same two functions/calls at `store/db/mysql/user_delete.go:96-104` and `store/db/sqlite/user_delete.go:96-104`.
  - The actual `DELETE FROM reaction ...` statements: `deleteReactionsByContentIDsTx` (`...:380-388`) and `deleteReactionsByCreatorTx` (`...:400-403`) in each of the three files.

So reactions are removed two ways in Go code: reactions *on* the deleted user's memos/comments (by `content_id`), and reactions *made by* the deleted user on others' memos (by `creator_id`) — both inside the same transaction as the user deletion, with no reliance on a database cascade rule.
