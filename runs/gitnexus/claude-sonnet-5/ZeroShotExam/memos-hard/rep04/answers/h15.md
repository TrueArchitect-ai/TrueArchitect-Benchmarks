Memo visibility ("who may view a memo") is checked independently in at least seven separate places in the Go server, each with its own copy of the Public/Protected/Private logic:

- API memo read-access gate (used by GetMemo and related memo endpoints, `checkMemoReadAccess`) — `server/router/api/v1/memo_service.go` (lines 39-68)
- API memo list-visibility filter (ListMemos scopes `VisibilityList`/filter by requester) — `server/router/api/v1/memo_service.go` (lines 195-227)
- API reactions endpoint (`ListMemoReactions`, inline duplicate of the visibility check) — `server/router/api/v1/reaction_service.go` (lines 15-41)
- API attachments endpoint (`ListMemoAttachments`, inline duplicate of the visibility check) — `server/router/api/v1/memo_attachment_service.go` (lines 200-224)
- File/attachment HTTP server (`checkAttachmentPermission`, includes share-token bypass for private/protected memos) — `server/router/fileserver/fileserver.go` (lines 649-704)
- SSE real-time event delivery filter (`canReceive`, gates which connected clients get a broadcast memo event) — `server/router/api/v1/sse_hub.go` (lines 134-144)
- Notification/email dispatch gate (`canViewerAccessMemo`, decides whether a comment/reaction notification may disclose memo content) — duplicated separately in `server/router/api/v1/user_service_notifications.go` (lines 302-320ish) and `server/notification/email.go` (lines 306-319)

Additionally, `server/router/rss/rss.go` and `server/router/frontend/frontend.go` (sitemap.xml) enforce visibility more coarsely by only querying the store for `store.Public` memos (`VisibilityList: []store.Visibility{store.Public}`), rather than per-memo checks.

Note: the reaction/attachment/notification copies are near-identical reimplementations of the same Public/Protected/Private branching logic rather than calls into a shared helper — worth flagging as duplication risk if visibility rules ever change.
