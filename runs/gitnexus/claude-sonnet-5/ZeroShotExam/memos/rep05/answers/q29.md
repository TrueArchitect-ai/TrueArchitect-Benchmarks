- **Interceptor path:** `web/src/connect.ts` (`authInterceptor`, lines 156-178) — a Connect-RPC `Interceptor` attached to the shared `transport` used by all frontend service clients. It attaches the bearer token via `setAuthorizationHeader`, proactively refreshes near-expiry tokens (`getRequestToken`), and reactively retries once on a `Code.Unauthenticated` response by calling `refreshAndGetAccessToken()` before redirecting to login on failure (`redirectOnAuthFailure`, in `web/src/utils/auth-redirect.ts`). Token state itself (get/set/expiry) is managed in `web/src/auth-state.ts`.

- **Token kinds:** Two — a short-lived **JWT access token** (attached as `Authorization: Bearer <token>` header, held in memory/broadcast via `TOKEN_CHANNEL_NAME`) and an HTTP-only **refresh token cookie** (sent via `credentials: "include"`, used by `refreshAccessToken()` → `AuthService.refreshToken` to mint new access tokens). On the backend, `Authenticator` also recognizes a third kind, the **Personal Access Token (PAT)**, for programmatic/non-browser API access.

- **Backend package that validates them:** `server/auth` (Go package `auth`, see `server/auth/authenticator.go`). The `Authenticator` struct validates JWT access tokens (`AuthenticateByAccessTokenV2` — stateless), refresh tokens (`AuthenticateByRefreshToken` — checked against the DB for revocation/expiry), and PATs (`AuthenticateByPAT` — hash lookup via the store), unifying them in `Authenticate`/`AuthenticateToUser` used by the gRPC/Connect interceptors and file server.
