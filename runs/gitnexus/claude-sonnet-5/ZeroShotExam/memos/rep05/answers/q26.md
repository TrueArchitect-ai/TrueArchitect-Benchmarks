No FK constraints/cascades at the schema level — no `ON DELETE CASCADE` anywhere (they were explicitly removed per `sqlite/0.7/00__remove_fk.sql`). So cascading is entirely handled in Go code. `memo_share` has no cleanup call in `DeleteMemo`, and `reaction` rows are only read (for the webhook payload), never deleted.

q26. Tables affected when `DeleteMemo` runs:

- **`memo`** — the target memo row is deleted directly (`store/db/{sqlite,mysql,postgres}/memo.go:DeleteMemo`); comment memos (rows in `memo_relation` of type `comment` pointing at this memo) are also deleted, recursively invoking the same cascade (`server/router/api/v1/memo_service.go:567-577`, `store/memo.go:140`).
- **`memo_relation`** — explicitly cleaned up in `store.Store.DeleteMemo` (`store/memo.go:142-147`), deleting rows where the memo is either `memo_id` or `related_memo_id`.
- **`attachment`** — explicitly cleaned up in `store.Store.DeleteMemo` via `ListAttachments`/`DeleteAttachment` (`store/memo.go:148-157`), which also deletes the underlying blob/file storage (`store/attachment.go:132-149`).

Not touched by explicit cascade code (despite being memo-linked): `reaction` (only listed via `ListReactions` for the deleted-webhook payload, never deleted — `server/router/api/v1/memo_service.go:545-550`) and `memo_share` (no reference in `DeleteMemo` at all).
