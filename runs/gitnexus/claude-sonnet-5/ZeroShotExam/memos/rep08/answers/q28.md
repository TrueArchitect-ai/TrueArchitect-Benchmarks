**Runners the server actually starts (and what drives each):**

- **S3 presign runner** — `time.NewTicker` on a **12-hour** interval. Started in `Server.startBackgroundRunners` (`server/server.go:153-171`), via `s3presign.NewRunner(s.Store)`, run once immediately then looped by `ticker := time.NewTicker(runnerInterval)` where `runnerInterval = 12h` (`server/runner/s3presign/runner.go:27-40`). This is the only runner registered in `Server.startBackgroundRunners`, called from `s.Start(ctx)` at `server/server.go:129`.
- **In-process cache cleanup (×3: instanceSetting/user/userSetting caches)** — `time.NewTicker` on a **5-minute** interval. Started earlier in boot, inside `store.New()` (`store/store.go:37-61`, `CleanupInterval = 5 * time.Minute` at `store/store.go:41`); each `cache.New()` spawns `go c.cleanupLoop()` (`store/cache/cache.go:76-84`) which ticks every 5 min (`store/cache/cache.go:201-213`).
- **Async email dispatch pool (2 goroutines)** — driven by blocking receive on a buffered channel (queue-consumer, not a timer). Spawned in Go's `init()` (`internal/email/email.go:15-35`), consuming `asyncEmailQueue` (buffer 128); runs unconditionally once the binary loads because `internal/email` is transitively imported.
- **Async webhook dispatch pool (4 goroutines)** — same pattern: `init()`-spawned consumers of `asyncPostQueue` (`internal/webhook/webhook.go:41-53`), triggered by items being pushed onto the channel, always active since `cmd/memos/main.go` imports `internal/webhook`.

**Unused scheduling infrastructure (present but NOT wired into the server):**
- `internal/scheduler/*` — a full hand-rolled cron scheduler (5/6-field cron, timezones, middleware) exposing `scheduler.New()`/`Register`/`Start`/`Stop`. No non-test file anywhere in the repo imports `internal/scheduler` (confirmed via grep) — it's exercised only by its own package tests and never instantiated by the server.
- `server/runner/memopayload.Runner` — defines a batch `RunOnce` job via `NewRunner(store, markdownService)`, but `memopayload.NewRunner` is never called anywhere in the codebase. Only the standalone `memopayload.RebuildMemoPayload(...)` helper (not the `Runner`/batch job) is used, and it's invoked synchronously inline during memo create/update requests (`server/router/api/v1/memo_service.go:108,447`), not as a background job.
