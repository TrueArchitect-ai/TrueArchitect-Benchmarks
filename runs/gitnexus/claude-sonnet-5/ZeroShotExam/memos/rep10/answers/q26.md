**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted (`store/db/{sqlite,postgres,mysql}/memo.go` `DB.DeleteMemo`, e.g. `store/db/sqlite/memo.go:237-248`), and any child comment memos are also deleted first via recursive `Store.DeleteMemo` calls (`server/router/api/v1/memo_service.go:567-577`).
- **`memo_relation`** — rows where the memo is either `memo_id` or `related_memo_id` are explicitly deleted (`store/memo.go:142,145`).
- **`attachment`** — attachments linked to the memo are explicitly deleted row-by-row via `Store.DeleteAttachment` (`store/memo.go:149-157`, `store/attachment.go:132-149`), which also removes the underlying file/S3 blob (not a DB table).
- **`memo_share`** — cascade-deleted at the database level only, via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/{sqlite,postgres,mysql}/LATEST.sql`, e.g. sqlite line 109). No explicit Go delete call exists for this table.

**Not affected (orphaned, notable gap):** `reaction` rows tied to the deleted memo/comments are only read via `ListReactions` (`server/router/api/v1/memo_service.go:545-549`) and are never deleted — `reaction.content_id` has no FK constraint, so these rows are left orphaned. `memo_organizer` no longer exists (dropped in migration 0.26), and `inbox`/`activity` have no relation to `memo.id` at all.
