**Tables affected when `DeleteMemo` runs** (server/router/api/v1/memo_service.go:518 → store/memo.go:140 `Store.DeleteMemo`):

- **`memo`** — the target row is deleted directly (`store/db/sqlite|mysql|postgres/memo.go`, e.g. sqlite `DeleteMemo` at store/db/sqlite/memo.go:237). Additionally, the API handler first recursively deletes any child "comment" memos via `store.DeleteMemo` (server/router/api/v1/memo_service.go:567-577), each of which repeats this whole cascade.
- **`memo_relation`** — explicit cascade: `store.DeleteMemo` calls `driver.DeleteMemoRelation` twice, once for `MemoID` and once for `RelatedMemoID` (store/memo.go:142-147), removing relation rows where the memo is either the source or the target.
- **`attachment`** — explicit cascade: `store.DeleteMemo` lists attachments for the memo and calls `Store.DeleteAttachment` on each (store/memo.go:148-157 → store/attachment.go:132), which also removes the underlying blob/local file/S3 object (not a DB table).
- **`memo_share`** — DB-level cascade only: the schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/{postgres,mysql,sqlite}/LATEST.sql:108-109). This fires automatically on Postgres/MySQL. Note: SQLite opens with `_pragma=foreign_keys(0)` (store/db/sqlite/sqlite.go:53), so on SQLite this FK is **not enforced** and `memo_share` rows are not actually cascade-deleted there — no Go code deletes them either.

**Not affected:** `reaction` rows referencing the memo are read (for the deleted-webhook payload) but never deleted — reactions key on a string `content_id`, not an integer FK, and there is no cascade code or DB constraint for them, so they become orphaned.
