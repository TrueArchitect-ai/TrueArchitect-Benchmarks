**Tables affected when `DeleteMemo` runs** (traced from `server/router/api/v1/memo_service.go:APIV1Service.DeleteMemo` → `store/memo.go:Store.DeleteMemo` → per-driver SQL):

- **`memo`** — the target memo row is deleted directly (`store/db/{sqlite,mysql,postgres}/memo.go: DeleteMemo`). Also, before deleting the target memo, the handler recursively calls `Store.DeleteMemo` for every comment memo (`memo_relation` rows of type `MemoRelationComment`), so each comment's `memo` row is deleted too (`server/router/api/v1/memo_service.go:560-575`).
- **`memo_relation`** — explicitly cleaned up in `store/memo.go:Store.DeleteMemo` (lines 139-158) via two calls to `driver.DeleteMemoRelation`, once where the memo is the source (`memo_id`) and once where it's the target (`related_memo_id`). This runs for the main memo and for each deleted comment memo.
- **`attachment`** — explicitly cleaned up: `Store.DeleteMemo` lists attachments via `ListAttachments(MemoID)` and deletes each through `Store.DeleteAttachment` (`store/attachment.go:131-148`), which also removes the underlying blob/file storage.
- **`memo_share`** — cascades via a DB-level foreign key (`FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, present in `store/migration/{postgres,mysql,sqlite}/LATEST.sql`). This cascade is enforced on **Postgres and MySQL**, but **not on SQLite**, since the SQLite driver explicitly opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), disabling FK enforcement — so on SQLite, `memo_share` rows for a deleted memo become orphaned.

Note: `reaction` rows tied to the memo are only **read** (`ListReactions`, for the webhook payload) — never deleted — so they're not affected/cascaded, and become orphaned after a memo delete.
