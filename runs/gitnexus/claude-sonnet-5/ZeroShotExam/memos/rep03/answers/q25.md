**Engine:** CEL (Common Expression Language, `github.com/google/cel-go/cel`), wrapped by a custom filter engine at `internal/filter/` (core files: `internal/filter/engine.go`, `internal/filter/parser.go`/`ir.go`, `internal/filter/schema.go`, `internal/filter/render.go`).

**How ListMemos uses it:** `ListMemos` (`server/router/api/v1/memo_service.go:211-213`) takes `request.Filter` as a CEL-style expression (e.g. `creator_id == 1 || visibility in ["PUBLIC","PROTECTED"]`) and passes it to `validateFilter` (`server/router/api/v1/shortcut_service.go:336`), which calls `filter.DefaultEngine()` and `engine.CompileToStatement(ctx, filterStr, filter.RenderOptions{Dialect: ...})`.

**Mechanism:** `Engine.Compile` (`internal/filter/engine.go`) uses a `cel.Env` built from the schema's `EnvOptions` to parse the filter string into a CEL AST, converts it via `buildCondition` into a dialect-agnostic `Condition` IR tree (`internal/filter/ir.go`), and then `Program.Render` (`internal/filter/render.go`) walks that IR tree and emits parameterized SQL fragments, branching per-node on a `DialectName` (`sqlite`/`mysql`/`postgres`, `internal/filter/schema.go`) to pick dialect-specific SQL syntax (e.g. string concat as `||` vs `CONCAT()`, timestamp handling via `UNIX_TIMESTAMP()` for MySQL vs raw column for Postgres/SQLite), producing a final `Statement` (SQL text + args) that the store layer (`store/db/{sqlite,postgres,mysql}/memo.go`) appends to its query.
