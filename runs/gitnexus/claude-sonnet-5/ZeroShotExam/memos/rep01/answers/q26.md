q26. **Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted directly (`DELETE FROM memo WHERE id = ...` in `store/db/{postgres,mysql,sqlite}/memo.go`). Comment-type child memos (found via `memo_relation` lookups in `server/router/api/v1/memo_service.go:567-577`) are also deleted first, recursively hitting this same table.
- **`memo_relation`** — explicitly cleaned up in `store/memo.go:140-147` (`Store.DeleteMemo`), which issues two deletes: one where the memo is the source (`MemoID`) and one where it's the target (`RelatedMemoID`).
- **`attachment`** — explicitly cleaned up in `store/memo.go:148-157`: attachments for the memo are listed via `ListAttachments` and deleted one-by-one via `Store.DeleteAttachment` (`store/attachment.go:132-149`), which also deletes the underlying blob/file storage.
- **`memo_share`** — not touched by any Go code, but cascades automatically at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (present identically in `store/migration/{postgres,mysql,sqlite}/LATEST.sql`).

**Not affected:** `reaction` — although `DeleteMemo` in `memo_service.go:545-550` lists reactions (for the webhook payload), it never deletes them, and the `reaction` table has no FK to `memo` (it references content by a `content_id TEXT` string, not an integer FK) — so reaction rows are orphaned rather than cascaded.

**Caveat:** on SQLite, foreign-key enforcement is explicitly disabled (`store/db/sqlite/sqlite.go:53`, `_pragma=foreign_keys(0)`), so the `memo_share` cascade only actually fires on Postgres/MySQL — on SQLite those rows would be silently orphaned too.
