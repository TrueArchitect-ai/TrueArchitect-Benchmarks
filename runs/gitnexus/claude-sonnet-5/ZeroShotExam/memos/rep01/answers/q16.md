The driver-level `DeleteMemo` only issues `DELETE FROM memo`. All related-record cleanup happens in `store.Store.DeleteMemo` (`store/memo.go:140-159`), which runs before calling `s.driver.DeleteMemo`.

q16.
- **Memo relations** — rows in `memo_relation` where the memo is the source (`MemoID`) *and* rows where it is the target (`RelatedMemoID`), deleted via two calls to `s.driver.DeleteMemoRelation` (`store/memo.go:142-147`)
- **Attachments** — all attachments linked to the memo, fetched via `ListAttachments` and deleted one-by-one via `DeleteAttachment` (`store/memo.go:149-157`), which itself cleans up the attachment's storage blob/reference

Additionally, one level up in the API handler (`server/router/api/v1/memo_service.go:567-577`), before calling `store.DeleteMemo` on the memo itself, the handler finds and deletes any **comment memos** (memos related via a `MemoRelationComment` relation pointing at this memo) by recursively calling `s.Store.DeleteMemo` on each comment — which in turn triggers the same relation/attachment cleanup for each comment memo.

Note: reactions (`ListReactions`) and webhook dispatch are read/used for the deletion notification payload in the handler, but reactions are not explicitly deleted in this code path (likely cascade-deleted at the DB schema level, not by the store layer).
