**Tables affected when `DeleteMemo` runs** (via `server/router/api/v1/memo_service.go:APIV1Service.DeleteMemo` → `store/memo.go:Store.DeleteMemo` → driver layer):

1. **`memo`** — the target memo row itself is deleted (`store/db/sqlite/memo.go:237` etc.), and this is also applied recursively to each child comment memo first (comments are found via `memo_relation` with type `comment` and deleted through the same `Store.DeleteMemo` path).
2. **`memo_relation`** — explicitly cascaded in `store/memo.go:141-147`: rows where the memo is either `memo_id` or `related_memo_id` are deleted before the memo row itself.
3. **`attachment`** — explicitly cascaded in `store/memo.go:148-157`: all attachments with `memo_id` = the memo are looked up and deleted one-by-one via `Store.DeleteAttachment` (which also removes the underlying blob/local file/S3 object).
4. **`memo_share`** — cascaded implicitly at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, defined identically in `store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, and `store/migration/postgres/LATEST.sql:108`.

Not deleted: `reaction` rows tied to the memo are only *read* (`ListReactions`, for the webhook payload) but never deleted — the `reaction.content_id` column has no FK to `memo`, so these become orphaned.
