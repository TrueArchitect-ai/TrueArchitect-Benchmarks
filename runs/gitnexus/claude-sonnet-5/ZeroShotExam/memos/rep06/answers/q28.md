This confirms the picture clearly. The server starts exactly one continuous background runner; `memopayload` is invoked synchronously on request, not scheduled; and `internal/scheduler` (a full cron-expression scheduler package) is entirely unused by the server.

q28.
- **s3presign runner** (`server/runner/s3presign/runner.go`) — self-driven `time.Ticker` on a 12-hour interval (`runnerInterval = time.Hour * 12`, `runner.go:27`); started as a goroutine from `Server.startBackgroundRunners` in `server/server.go:161-171`, which also runs it once synchronously via `RunOnce(ctx)` at startup (`server.go:163`) before the ticker loop begins (`server.go:167-170`).

That is the only continuous background runner the server actually launches — `Server.Start` (`server/server.go:124-130`) calls `s.startBackgroundRunners(ctx)` once, and that function only wires up `s3presign`.

Not a scheduled background worker, for contrast:
- **memopayload runner** (`server/runner/memopayload/runner.go`) — has a `RunOnce` method but is never started as a background loop; it's only invoked synchronously inline from request handlers in `server/router/api/v1/memo_service.go:108` and `:447` (memo create/rebuild paths), i.e. triggered by an API request, not by any timer.

Unused scheduling infrastructure:
- `internal/scheduler` — a full cron-expression scheduler package (`scheduler.go`, `parser.go`, `job.go`, with `ParseCronExpression`, `Scheduler.Start`, `Scheduler.runJobWithSchedule`) exists in the repo but `scheduler.New(...)` is called **only** from its own tests/examples (`integration_test.go`, `example_test.go`) and referenced in `doc.go`. There are no references to `internal/scheduler` anywhere in `server/` or `cmd/memos/main.go` — the server never instantiates or starts this scheduler.
