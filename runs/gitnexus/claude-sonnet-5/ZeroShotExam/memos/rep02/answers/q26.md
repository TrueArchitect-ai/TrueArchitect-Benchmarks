When `DeleteMemo` runs (`server/router/api/v1/memo_service.go:518` → `store/memo.go:140` → driver, e.g. `store/db/postgres/memo.go:244`), the following tables are affected:

- **`memo`** — the target memo row is deleted, and this repeats recursively for each comment memo first (`memo_service.go:567-577` lists comment relations via `ListMemoRelations` and calls `store.DeleteMemo` on each `relation.MemoID` before deleting the parent memo).
- **`memo_relation`** — explicitly cleaned in `store/memo.go:142-147`, deleting rows where the memo is either `memo_id` or `related_memo_id` (`store/db/postgres/memo_relation.go:153-168`).
- **`attachment`** — explicitly cleaned in `store/memo.go:148-157`, which lists attachments for the memo and calls `DeleteAttachment` on each (`store/attachment.go:132-149` → `DELETE FROM attachment WHERE id = $1`, `store/db/postgres/attachment.go:211-220`); this also deletes the associated file from storage (not a DB table).
- **`memo_share`** — not touched by application code, but cascaded at the schema level: `memo_share.memo_id` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:101-108`), so rows are removed automatically when the `memo` row is deleted.

Notably **not** cascaded: `reaction` rows are only read (`ListReactions`, `memo_service.go:545-550`, used for the deleted-webhook payload) but never deleted — `reaction.content_id` is a plain `TEXT` column with no FK to `memo`, so reactions on a deleted memo are orphaned rather than cascaded.
