Tables affected when `DeleteMemo` runs:

- **memo** — the target row (and, for each child comment memo found via `memo_relation` with type `COMMENT`, those rows too) is deleted directly (`store/memo.go:140-158`, e.g. `store/db/sqlite/memo.go:237`).
- **memo_relation** — explicitly deleted for the memo both as source and as target (`store/memo.go:142-147`, via `driver.DeleteMemoRelation`).
- **attachment** — explicitly deleted for every attachment linked to the memo (`store/memo.go:148-157`, via `s.DeleteAttachment`), which also triggers attachment-storage/file cleanup (`store/attachment.go:132-149`).
- **memo_share** — not touched by any Go code, but cascades automatically at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (present identically in `store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`).

Because `server/router/api/v1/memo_service.go:567-577` first deletes each `COMMENT`-type `memo_relation` target via `s.Store.DeleteMemo`, deleting a memo with comments recursively repeats this same cascade (memo/memo_relation/attachment/memo_share) for every comment memo.

Note: `reaction` rows referencing the memo (via `content_id`) are only *listed* (`server/router/api/v1/memo_service.go:545-550`) for the deletion webhook — they are never deleted, so the `reaction` table is not affected by `DeleteMemo`.
