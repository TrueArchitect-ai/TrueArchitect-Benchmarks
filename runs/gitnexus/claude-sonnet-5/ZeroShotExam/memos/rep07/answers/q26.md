Tables affected when `DeleteMemo` runs (handler `server/router/api/v1/memo_service.go:518` → `store.DeleteMemo` `store/memo.go:140` → driver `store/db/sqlite|mysql|postgres/memo.go`):

- **`memo`** — the target memo row itself, and recursively any comment memos (rows where `memo_relation.type = COMMENT` and `related_memo_id = memo.id`) are also deleted, since the handler loops and calls `store.DeleteMemo` for each comment (`memo_service.go:568-577`).
- **`memo_relation`** — explicitly cleaned up in `store.DeleteMemo` (`store/memo.go:142-147`), deleting rows where the memo is either `memo_id` or `related_memo_id`.
- **`attachment`** — explicitly cleaned up in `store.DeleteMemo` via `ListAttachments`/`DeleteAttachment` loop (`store/memo.go:148-157`), deleting rows where `memo_id` matches.
- **`memo_share`** — not touched by application code, but the schema defines `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, and equivalently in the mysql/postgres `LATEST.sql`), so rows are removed automatically by the database when the `memo` row is deleted.

Not affected: `reaction` — the handler calls `ListReactions` only to build the webhook payload before deletion; no delete is issued and `reaction.content_id` is a plain TEXT column with no FK/cascade to `memo`, so reaction rows for a deleted memo are orphaned rather than cleaned up.
