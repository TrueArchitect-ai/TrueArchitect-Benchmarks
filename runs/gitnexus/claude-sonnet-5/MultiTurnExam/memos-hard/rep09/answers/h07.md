**Route → handler**: The route (`GET /file/users/:identifier/avatar` or similar, registered in the fileserver router) dispatches to:

1. `serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (extracts `identifier` from the URL param, requires an authenticated viewer if the instance isn't public)
2. `getUserByUsername` — `server/router/fileserver/fileserver.go:715` (thin wrapper resolving the identifier to a user)
3. `Store.GetUser` — `store/user.go:148` (checks in-memory `userCache` first, falls through to `ListUsers` on a miss)
4. `Store.ListUsers` — `store/user.go:136` (populates the cache after fetching, delegates to the driver interface)
5. `driver.ListUsers` — `store/driver.go:47` (interface method on `store.Driver`)
6. `DB.ListUsers` (concrete SQLite implementation) — `store/db/sqlite/user.go:88` (builds and executes the `SELECT ... FROM user WHERE ...` query against the underlying `*sql.DB`; equivalent implementations exist in `store/db/postgres/user.go` and `store/db/mysql/user.go`)

After `GetUser` returns, `serveUserAvatar` reads `user.AvatarURL` (a data-URI stored directly on the user row) and decodes/serves it via `parseDataURI` — no separate attachment/blob storage hop for avatars.
