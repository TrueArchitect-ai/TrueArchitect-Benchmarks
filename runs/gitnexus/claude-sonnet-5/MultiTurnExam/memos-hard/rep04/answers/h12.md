**Concrete method:** `(*sqlite.DB).CreateMemo` — `store/db/sqlite/memo.go:16`, which builds and executes `INSERT INTO \`memo\` (...) VALUES (...) RETURNING ...` (`store/db/sqlite/memo.go:41-49`).

**Determination method:**
1. `store.Store` (the storage facade used everywhere in the server) has a `CreateMemo` method (`store/memo.go:109-114`) that does no SQL itself — it just delegates to `s.driver.CreateMemo(ctx, create)`, where `driver` is the `store.Driver` interface, implemented separately by the `sqlite`, `postgres`, and `mysql` packages (three concrete candidates for "the INSERT").
2. Which concrete implementation is wired into `s.driver` is decided at startup by `db.NewDBDriver` (`store/db/db.go:14-29`), which switches on `profile.Driver` and calls `sqlite.NewDB`, `postgres.NewDB`, or `mysql.NewDB` accordingly.
3. `profile.Driver` comes from the `--driver` CLI flag/`MEMOS_DRIVER` env var via viper, and its **default value is `"sqlite"`** — `viper.SetDefault("driver", "sqlite")` at `cmd/memos/main.go:122`, consumed into `profile.Profile{Driver: viper.GetString("driver"), ...}` at `cmd/memos/main.go:43`.
4. Therefore, with no database flags overriding this default, `db.NewDBDriver` selects `sqlite.NewDB`, so `s.driver` is a `*sqlite.DB`, and the code that actually executes on `Store.CreateMemo` is `(*sqlite.DB).CreateMemo` at `store/db/sqlite/memo.go:16`, not the postgres or mysql equivalents.
