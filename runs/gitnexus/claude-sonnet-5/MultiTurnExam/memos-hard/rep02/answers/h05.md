All three drivers (Postgres, MySQL, SQLite) explicitly delete reactions in their `DeleteUser` transaction, covering both directions: reactions the user created, and reactions on memos the user owned (which get deleted as a cascade of the memo tree deletion).

h05.

**Mechanism** — explicit Go code, not a database-level rule.

**Evidence locations:**
- `store/db/postgres/user_delete.go:96` and `:380-388` (`deleteReactionsByContentIDsTx`) — deletes reactions on every memo/comment in the user's memo tree (`DELETE FROM reaction WHERE content_id IN (...)`).
- `store/db/postgres/user_delete.go:102` and `:400-403` (`deleteReactionsByCreatorTx`) — deletes reactions the user themself authored on other people's content (`DELETE FROM reaction WHERE creator_id = ?`).
- Identical logic in `store/db/mysql/user_delete.go:96,102,417-425,437-440` and `store/db/sqlite/user_delete.go:96,102,380-388,400-403`.
- These calls happen inside `deleteUserTargetsTx`, run within the same `BeginTx`/`Commit` transaction as the rest of `DeleteUser` (e.g. `store/db/postgres/user_delete.go:29-59`), before the memo rows and the user row itself are deleted — so it's ordered application logic, not an ON DELETE CASCADE constraint.
- I checked the `reaction` table's schema/migrations for a `FOREIGN KEY ... ON DELETE CASCADE` on `creator_id`/`content_id` and found none referenced in this code path — the explicit `DELETE FROM reaction` statements are what actually remove the rows.
