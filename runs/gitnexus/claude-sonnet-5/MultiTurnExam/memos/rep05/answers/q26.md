q26. Tables affected when `DeleteMemo` runs:

- **`memo`** — the row itself is deleted (`store/db/postgres/memo.go:246`, `DELETE FROM memo WHERE id = ...`)
- **`memo_relation`** — explicitly cleaned up in `store.Store.DeleteMemo` (`store/memo.go:142-147`), removing rows where the memo is source or target
- **`attachment`** — explicitly cleaned up in `store.Store.DeleteMemo` via `ListAttachments`/`DeleteAttachment` (`store/memo.go:149-157`; storage blob also removed)
- **`memo_share`** — not touched by application code, but cascades automatically at the DB level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`)

Note: `reaction` rows referencing the memo (via `content_id`) are **not** deleted — there's no FK and no explicit cleanup call in `DeleteMemo` (the API handler only *lists* reactions, for the webhook payload, before deletion).
