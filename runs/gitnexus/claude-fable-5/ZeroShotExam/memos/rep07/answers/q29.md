**Answer:** `web/src/connect.ts`; a short-lived JWT access token (sent as `Authorization: Bearer`, refreshed proactively before expiry and reactively on 401) plus a refresh token carried in an HTTP-only cookie (`credentials: "include"`); validated by the `server/auth` package (`server/auth/authenticator.go`).

Details:

- **Interceptor location:** `web/src/connect.ts:156` defines `authInterceptor`, a Connect RPC `Interceptor` installed on the `createConnectTransport` used by all frontend service clients (`web/src/connect.ts:184-189`). It attaches the token via `setAuthorizationHeader` (`Authorization: Bearer <token>`, line 97-100), and on a `Code.Unauthenticated` error it refreshes the token and retries the request once (marked with an `X-Retry` header).
- **Tokens it manages:** the **access token** — a short-lived (15-minute) JWT kept via `web/src/auth-state.ts` helpers (`getAccessToken`/`setAccessToken`/`isTokenExpired`) — and the **refresh token**, which lives in an HTTP-only cookie and is sent because all fetches use `credentials: "include"`. `refreshAccessToken()` calls `AuthService.RefreshToken` over a separate interceptor-free transport to avoid recursion (`web/src/connect.ts:64-91`), with a dedup manager so concurrent refreshes (interceptor vs. the `useTokenRefreshOnFocus` hook) don't conflict with server-side token rotation.
- **Backend validation:** the `server/auth` package. `server/auth/authenticator.go` defines `Authenticator`, used by the gRPC/Connect interceptors and file server; `AuthenticateByAccessTokenV2` does stateless JWT validation of access tokens, `AuthenticateByRefreshToken` validates refresh tokens against the database (revocation check), and it also handles Personal Access Tokens. The refresh endpoint itself is `server/router/api/v1/auth_service_session.go` (`APIV1Service.RefreshToken`).
