The server starts exactly one dedicated background runner, plus incidental background goroutines owned by the store's caches. Notably, a full cron scheduler package exists but is never wired in.

- **s3presign runner** (`server/runner/s3presign/runner.go`) — the only runner launched by the server. In `startBackgroundRunners` (`server/server.go:153-174`, called from `Server.Start`), it runs once immediately at startup (`RunOnce`), then a goroutine runs it on a fixed 12-hour `time.Ticker` (`runnerInterval = time.Hour * 12`, `server/runner/s3presign/runner.go:27-41`) until its context is cancelled at shutdown.
- **Cache cleanup goroutines** (`store/cache/cache.go:199` `cleanupLoop`) — not a "runner" in the server's sense, but each cache created in `store/store.go:51-53` spawns a goroutine driven by a `time.Ticker` at the cache's `CleanupInterval`, stopped via `Cache.Close` when the store closes. (Per-connection SSE heartbeat tickers in `server/router/api/v1/sse_handler.go:64` are request-scoped, not background workers.)

Not started by the server:

- **memopayload runner** (`server/runner/memopayload/runner.go`) — despite living in `server/runner/`, it has only a `RunOnce` (no ticker loop) and is never instantiated or started anywhere. Only its standalone function `RebuildMemoPayload` is called synchronously from the API layer (`server/router/api/v1/memo_service.go:108,447`).

Unused scheduling infrastructure: **`internal/scheduler`** — a complete GitHub-Actions-style cron scheduler (cron expression parser, job definitions, middleware, docs and tests: `internal/scheduler/{scheduler,parser,job,middleware}.go`) — is imported by nothing outside its own package. The server's scheduling is done entirely with raw `time.Ticker`s; the cron package is dead infrastructure as far as the running server is concerned.
