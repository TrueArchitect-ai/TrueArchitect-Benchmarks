**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`.**

The cascade lives in `Store.DeleteMemo` at `store/memo.go:140-159`:

1. **`memo_relation`** — deleted explicitly, in both directions: rows where the memo is the source (`MemoID`) and rows where it's the target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL in e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — deleted explicitly: attachments linked to the memo are listed and each is removed via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also deletes the underlying file/blob from storage before issuing `DELETE FROM attachment` (`store/attachment.go:132-149`, `store/db/sqlite/attachment.go:212`).
3. **`memo`** — the memo row itself, via the driver's `DeleteMemo` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259` — each is just `DELETE FROM memo WHERE id = ?`).
4. **`memo_share`** — cleaned up not by Go code but by an explicit schema-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`; the migration comment in `store/migration/sqlite/0.27/04__memo_share.sql` states this is intentional cleanup on memo deletion).

Additionally, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) first deletes all comment memos (recursively invoking `Store.DeleteMemo`, hitting the same four tables for each comment) before deleting the memo itself.
