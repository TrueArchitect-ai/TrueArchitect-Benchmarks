**Tables: `memo`, `memo_relation`, `attachment`** (plus `memo_share` via a database-level foreign-key cascade, not code).

How each is hit:

- **`memo`** — the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) calls `Store.DeleteMemo` for each comment memo and then the memo itself; the driver's `DeleteMemo` runs `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, with equivalents in `store/db/mysql/memo.go:258` and `store/db/postgres/memo.go:243`).
- **`memo_relation`** — explicit cascade in `Store.DeleteMemo` (`store/memo.go:140-147`): it calls `driver.DeleteMemoRelation` twice, removing rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`) (delete statement at `store/db/sqlite/memo_relation.go:149`).
- **`attachment`** — explicit cascade in `Store.DeleteMemo` (`store/memo.go:148-157`): it lists attachments linked to the memo and deletes each via `Store.DeleteAttachment` (`store/attachment.go:132`), whose driver runs `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go:211`). This also deletes the attachment's blob from object/local storage, though that's not a DB table.
- **`memo_share`** — not touched by any Go code, but its schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, same in the mysql/postgres `LATEST.sql`), so share rows are removed by the database when the `memo` row is deleted.

Notably **not** affected: `reaction` — the API handler lists reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545`) and never deletes them, and `reaction` has no memo foreign key. `memo_organizer` is likewise not cleaned up in this path.
