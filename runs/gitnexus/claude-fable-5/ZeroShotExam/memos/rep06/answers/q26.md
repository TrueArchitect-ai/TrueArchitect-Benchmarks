**Tables affected: `memo`, `memo_relation`, `attachment`**

`Store.DeleteMemo` (`store/memo.go:140-159`) performs the explicit cascade:

1. **`memo_relation`** — deleted twice via `driver.DeleteMemoRelation`, once with the memo as source (`MemoID`) and once as target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL `DELETE FROM memo_relation` at `store/db/sqlite/memo_relation.go:149`, with equivalents in `store/db/mysql/memo_relation.go` and `store/db/postgres/memo_relation.go`).
2. **`attachment`** — attachments linked to the memo are listed and deleted one by one via `Store.DeleteAttachment` (`store/memo.go:149-157`), which runs `DELETE FROM attachment` (`store/db/sqlite/attachment.go:212`) and also removes the underlying blob from local disk or S3 (`store/attachment.go:132-149` — file/object storage, not a table).
3. **`memo`** — finally the memo row itself: `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`, plus mysql/postgres counterparts).

Note the API handler (`server/router/api/v1/memo_service.go:518-593`) additionally deletes comment memos first (each recursively running the same cascade), but that still only touches these three tables. It *lists* reactions for the deleted-memo webhook payload but does not delete them — no `reaction` table rows are removed by this path.
