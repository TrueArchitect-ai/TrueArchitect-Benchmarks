Frontend API requests are authenticated by a ConnectRPC client interceptor in `web/src/connect.ts` (the `authInterceptor`, `web/src/connect.ts:156`), which is installed on the transport used by all service clients.

What it does and the tokens involved:

- **Access token** — a short-lived JWT (15-minute lifetime, audience `user.access-token`). The interceptor fetches it from in-memory state (`web/src/auth-state.ts`, via `getAccessToken`/`setAccessToken`) and attaches it as an `Authorization: Bearer <token>` header on every request. It proactively refreshes when the token is expired or near expiry, and reactively retries once (with an `X-Retry` header) after an `Unauthenticated` error.
- **Refresh token** — held in an HTTP-only cookie, sent automatically because the transport uses `credentials: "include"`. The interceptor's refresh path calls `AuthService.refreshToken` over a separate interceptor-free transport to exchange it for a new access token; concurrent refreshes are deduplicated by a refresh manager (shared with `web/src/hooks/useTokenRefreshOnFocus.ts`). If refresh fails, the user is redirected to sign-in.

On the backend, the `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go` reads the `Authorization` header and delegates to the shared `Authorizer` (`server/router/api/v1/authz.go`), which validates tokens using the **`server/auth`** package (`server/auth/token.go`, `server/auth/authenticator.go`) — HS256 JWT validation for access tokens, plus handling for refresh tokens and `memos_pat_`-prefixed personal access tokens.

Answer format: `web/src/connect.ts`; JWT access tokens (Bearer header) + refresh tokens (HTTP-only cookie); `server/auth`
