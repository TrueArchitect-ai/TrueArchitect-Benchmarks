**Tables affected: `memo`, `memo_relation`, `attachment`**

The cascade lives in `store.DeleteMemo` (`store/memo.go:140-159`):

1. **`memo_relation`** — explicitly deleted twice, once for relations where the memo is the source (`MemoID`) and once where it's the target (`RelatedMemoID`), via `driver.DeleteMemoRelation` (`store/memo.go:142-147`; SQL in `store/db/sqlite/memo_relation.go:149` and the mysql/postgres equivalents).
2. **`attachment`** — explicitly cleaned up: the store lists attachments for the memo and calls `DeleteAttachment` on each (`store/memo.go:148-157`; `DELETE FROM attachment` in `store/db/sqlite/attachment.go:212`). This also removes the file from local/S3 storage (`store/attachment.go:132-148`), but that's filesystem/object storage, not a table.
3. **`memo`** — the final `driver.DeleteMemo` deletes only the memo row itself (`store/db/sqlite/memo.go:237-248`).

The API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) adds one more layer: it first deletes all comment memos (relations of type `COMMENT`) by calling `store.DeleteMemo` for each (`memo_service.go:567-577`), which touches the same three tables for each comment. It lists reactions and attachments before deleting, but only to build the webhook payload — no `reaction` rows are deleted by explicit code.

One caveat worth noting: **`memo_share`** rows are also removed, but by a schema-level `ON DELETE CASCADE` foreign key (`store/migration/sqlite/LATEST.sql:109`), not by explicit cascade code — so it's affected at the database level, though outside the "explicit code" scope. There is no `memo_organizer` table anymore (dropped in migration `store/migration/postgres/0.26/01__drop_memo_organizer.sql`; pin state now lives on the `memo` table).
