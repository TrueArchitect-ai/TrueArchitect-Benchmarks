Frontend requests are authenticated by a Connect RPC interceptor defined in `web/src/connect.ts` (`authInterceptor`, `web/src/connect.ts:156`), which is installed on the transport used by all service clients. Backend validation lives in the `server/auth` package, invoked via the server-side `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go`.

- **Interceptor path:** `web/src/connect.ts` — `authInterceptor` attaches `Authorization: Bearer <token>` to every request (token state helpers in `web/src/auth-state.ts`), proactively refreshes tokens that are expired or near expiry, and on a `401 Unauthenticated` response refreshes once and retries (marked with an `X-Retry` header), redirecting to login if refresh fails. Concurrent refreshes are deduplicated via a token-refresh manager shared with `web/src/hooks/useTokenRefreshOnFocus.ts`.
- **Token kinds:** a short-lived JWT **access token** (held in client state, sent as a Bearer header) and a **refresh token** carried in an HTTP-only cookie (requests use `credentials: "include"`; a separate interceptor-free transport calls the `refreshToken` RPC to mint new access tokens). The backend additionally accepts **personal access tokens** on the same Bearer header (`AuthenticateByPAT`).
- **Backend package:** `server/auth` — `authenticator.go` (`Authenticate`, `AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, `AuthenticateByPAT`) and `token.go` (JWT parsing/verification via `jwt.ParseWithClaims`), wired into request handling by `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:220`, which forwards the `Cookie` header so the `RefreshToken` RPC can read the refresh-token cookie.

Answer format summary: `web/src/connect.ts`; access token (Bearer JWT) + refresh token (HTTP-only cookie), with PATs also accepted; `server/auth`.
