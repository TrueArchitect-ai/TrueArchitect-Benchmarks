Frontend requests are authenticated by a Connect RPC interceptor: `authInterceptor` in `web/src/connect.ts` (line 156), which is installed on the shared `createConnectTransport` used by every service client in that file.

How it works: before each request, `getRequestToken()` fetches the current **access token** (a short-lived JWT kept in client state via `web/src/auth-state.ts`) and sets it as an `Authorization: Bearer <token>` header, proactively refreshing it if it's expired or missing. The refresh itself calls `AuthService.refreshToken` over a separate interceptor-free transport with `credentials: "include"`, so the **refresh token** — stored in an HTTP-only cookie — is sent automatically; the response yields a new access token (`doRefreshAccessToken`). On a 401 (`Code.Unauthenticated`), the interceptor refreshes once and retries (marked with an `X-Retry` header), redirecting to sign-in if that fails. `web/src/hooks/useTokenRefreshOnFocus.ts` also refreshes proactively on tab focus, deduplicated through the same refresh manager.

The backend validates these in the `server/auth` package: `server/auth/token.go` parses the JWTs (`ParseAccessTokenV2`, `ParseRefreshToken`) and `server/auth/authenticator.go` authenticates them (`AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, plus `AuthenticateByPAT` for personal access tokens, another accepted bearer credential); `server/auth/extract.go` pulls the bearer token from the Authorization header and the refresh token from the cookie.

Answer format summary: `web/src/connect.ts` (authInterceptor); JWT access token (Bearer header) + refresh token (HTTP-only cookie), with personal access tokens also accepted as bearer credentials; `server/auth`.
