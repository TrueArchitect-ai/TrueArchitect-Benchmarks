**Tables affected: `memo`, `memo_relation`, `attachment`**

When the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) runs, it deletes each comment memo and then the memo itself through `Store.DeleteMemo` (`store/memo.go:140`), which contains the explicit cascade code:

- **`memo_relation`** — `Store.DeleteMemo` calls `driver.DeleteMemoRelation` twice, removing rows where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL `DELETE FROM memo_relation` at `store/db/sqlite/memo_relation.go:149`).
- **`attachment`** — it lists attachments linked to the memo and deletes each via `Store.DeleteAttachment` (`store/memo.go:149-157`), which issues `DELETE FROM attachment` (`store/db/sqlite/attachment.go:211`). This also removes the stored file/blob from storage, but that's not a table.
- **`memo`** — finally the driver deletes the memo row itself: `DELETE FROM memo` (`store/db/sqlite/memo.go:237`, with equivalent implementations in `store/db/mysql/memo.go` and `store/db/postgres/memo.go`).

Notably, `reaction` rows are **not** deleted — the handler lists reactions only to build the webhook payload (`memo_service.go:545`), and there is no `DeleteReaction` call in the delete path nor any `ON DELETE CASCADE` foreign keys in the schema, so no other tables are touched.
