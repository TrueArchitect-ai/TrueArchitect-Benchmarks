**Tables affected by explicit cascade code: `memo`, `memo_relation`, `attachment`.**

`Store.DeleteMemo` (`store/memo.go:140-159`) explicitly performs three cleanups before/while deleting:

1. **`memo_relation`** — deleted in both directions via `DeleteMemoRelation` with `MemoID` and again with `RelatedMemoID` (`store/memo.go:142-147`; SQL in e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists attachments linked to the memo and calls `DeleteAttachment` for each (`store/memo.go:149-157`), which deletes the row (`store/db/sqlite/attachment.go:212`) and also removes the underlying file/blob storage via `DeleteAttachmentStorage` (`store/attachment.go:132-149` — storage, not a table).
3. **`memo`** — the row itself via the driver (`store/db/sqlite/memo.go:237-248`, likewise in the mysql and postgres drivers).

The API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally deletes all comment memos first by calling `Store.DeleteMemo` recursively per comment (`memo_service.go:567-577`) — same three tables, just more rows.

Two clarifying notes:

- **`memo_share`** is also emptied for that memo, but by a database-level `FOREIGN KEY ... ON DELETE CASCADE` constraint (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/0.27/04__memo_share.sql`), not by any Go cascade code. Include it if you count schema-level cascades; it's not "explicit cascade code."
- **`reaction`** is *not* cleaned up: the API handler lists reactions only to build the webhook payload (`memo_service.go:545-550`); no `DeleteReaction` is called anywhere in the delete path, and the `reaction` table has no FK cascade — those rows are orphaned.
