Frontend requests are authenticated by a Connect RPC interceptor that attaches `Authorization: Bearer <access token>` to every call, with automatic refresh on 401.

- **Interceptor path:** `web/src/connect.ts` — the `authInterceptor` (line 156) is wired into the Connect transport (line 184-189) used by all service clients. It gets the token via `getRequestToken()`, does a preflight refresh when the token is near expiry, and on an `Unauthenticated` error refreshes once and retries (marked with an `X-Retry` header), redirecting to sign-in if that fails. Token storage/expiry logic lives in `web/src/auth-state.ts` (localStorage + BroadcastChannel cross-tab sync).

- **Token kinds:** two tokens are managed by the frontend — a short-lived **JWT access token** (~15 min, sent as the `Bearer` header) and a **refresh token** carried in an HTTP-only cookie (requests use `credentials: "include"`; `refreshAccessToken()` calls `AuthService.RefreshToken` on a separate interceptor-free transport to avoid recursion). The backend additionally accepts long-lived **Personal Access Tokens (PATs)** for programmatic access via the same Bearer header.

- **Backend package:** `server/auth` — `server/auth/authenticator.go` defines `Authenticator` with `AuthenticateByAccessTokenV2` (stateless JWT validation), `AuthenticateByRefreshToken` (DB-checked), and PAT validation. It's invoked from the API-layer interceptors in `server/router/api/v1/` (e.g. `connect_interceptors.go`, `authz.go`), with public/bootstrap method allowlists in `server/router/api/v1/acl_config.go`.

Answer format summary: `web/src/connect.ts`; JWT access token (Bearer) + cookie-based refresh token (plus PATs accepted server-side); `server/auth`.
