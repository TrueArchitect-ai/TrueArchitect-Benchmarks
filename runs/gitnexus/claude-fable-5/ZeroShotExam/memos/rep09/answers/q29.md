Frontend API requests are authenticated by a Connect RPC interceptor defined in **`web/src/connect.ts`** (`authInterceptor`, `web/src/connect.ts:156`), which is installed on the shared Connect transport used by all service clients. On every request it obtains the current token via `getRequestToken()` and sets an `Authorization: Bearer <token>` header. Backend-side, the header is checked by `AuthInterceptor` in `server/router/api/v1/connect_interceptors.go:205`, which delegates to the `Authorizer` (`server/router/api/v1/authz.go`) and ultimately to the **`server/auth`** package (`server/auth/authenticator.go`, `server/auth/token.go`), where the JWTs are validated with `golang-jwt/jwt/v5` (HS256 claims, access-token audience).

The interceptor manages two token kinds:

- A short-lived **JWT access token**, kept in client state (`web/src/auth-state.ts`) and sent as the `Authorization: Bearer` header. It's proactively refreshed before expiry (`isTokenExpired` preflight in `getRequestToken`) and reactively refreshed once on a `Code.Unauthenticated` error, using an `X-Retry` header to prevent retry loops.
- A **refresh token**, held in an HTTP-only cookie (all fetches use `credentials: "include"`); the interceptor uses it indirectly by calling `AuthService.refreshToken` over a separate interceptor-free transport (`refreshTransport`) to mint a new access token, with concurrent refreshes deduplicated by `tokenRefreshManager`. The backend's `AuthenticateByRefreshToken` in `server/auth/authenticator.go` validates it (the Connect interceptor forwards the Cookie header for this).

Answer format: `web/src/connect.ts`; JWT access token (Bearer header) + refresh token (HTTP-only cookie); `server/auth` (wired through `server/router/api/v1/connect_interceptors.go` / `authz.go`).
