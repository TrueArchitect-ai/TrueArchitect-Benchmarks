Three tables are affected: **`memo`, `memo_relation`, and `attachment`**.

The cascade is coded explicitly in `Store.DeleteMemo` (`store/memo.go:140-159`):

1. **`memo_relation`** — deleted twice via `driver.DeleteMemoRelation`, once with the memo as source (`MemoID`) and once as target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL in e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — attachments linked to the memo are listed and deleted one by one via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying file/S3 object before running `DELETE FROM attachment` (`store/attachment.go:132-148`, `store/db/sqlite/attachment.go:212`).
3. **`memo`** — finally the memo row itself is deleted (`store/db/sqlite/memo.go:239`, likewise in the mysql and postgres drivers).

The API-level handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) adds recursion — it first deletes all comment memos (each of which repeats the same three-table cascade) — but touches no additional tables. Notably, it lists `reaction` rows only to build the deleted-memo webhook payload; there is no reaction deletion in this path, and no `memo_organizer` cleanup either, so those tables are not affected by explicit cascade code.
