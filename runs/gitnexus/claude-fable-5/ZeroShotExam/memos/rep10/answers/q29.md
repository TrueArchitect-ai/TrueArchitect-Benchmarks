Frontend requests are authenticated by a Connect RPC interceptor: `authInterceptor` in `web/src/connect.ts` (defined at `web/src/connect.ts:156`, installed on the transport at line 188). It manages two token kinds:

1. **Short-lived JWT access tokens** — held client-side via `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`), attached to every request as an `Authorization: Bearer <token>` header. The interceptor does a preflight refresh when the token is expired/near expiry (`getRequestToken`) and a reactive refresh-and-retry on a 401 `Unauthenticated` error.
2. **Refresh tokens** — sent as an HTTP cookie (`fetchWithCredentials` uses `credentials: "include"`); a separate interceptor-free transport calls `AuthService.RefreshToken` to mint a new access token (with dedup via `tokenRefreshManager` and cross-tab sharing via BroadcastChannel in `auth-state.ts`).

On the backend, tokens are validated by the **`server/auth`** package (`github.com/usememos/memos/server/auth`): `server/auth/authenticator.go` defines `Authenticator`, which statelessly validates JWT access tokens (`AuthenticateByAccessTokenV2` / `ParseAccessTokenV2` in `server/auth/token.go`), validates refresh tokens against the database, and also accepts long-lived Personal Access Tokens (PATs). It's used by the gRPC/Connect interceptors and the file server; the session refresh endpoint itself lives in `server/router/api/v1/auth_service_session.go`.

Answer format summary: `web/src/connect.ts` (authInterceptor); short-lived JWT access tokens (Bearer header) + cookie-based refresh tokens (plus PATs accepted server-side); `server/auth`.
