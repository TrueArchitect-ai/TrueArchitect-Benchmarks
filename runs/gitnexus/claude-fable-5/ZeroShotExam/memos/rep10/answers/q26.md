**Tables affected: `memo`, `memo_relation`, `attachment`**

The flow, starting from the API handler `DeleteMemo` in `server/router/api/v1/memo_service.go:518`:

1. The handler first deletes all comment memos (memos linked by a `Comment` relation), then the memo itself — both by calling `store.DeleteMemo` (`server/router/api/v1/memo_service.go:573-582`).
2. `store.DeleteMemo` in `store/memo.go:140` performs the explicit cascade:
   - **`memo_relation`** — deleted twice, for rows where the memo is the source (`MemoID`) and where it is the target (`RelatedMemoID`) (`store/memo.go:142-147`, executed via e.g. `store/db/sqlite/memo_relation.go:149`).
   - **`attachment`** — every attachment linked to the memo is deleted via `store.DeleteAttachment` (`store/memo.go:149-157`, DB delete in e.g. `store/db/sqlite/attachment.go:212`; this also removes the underlying local/S3 file, which is storage, not a table).
   - **`memo`** — finally the driver's `DeleteMemo` runs a plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/mysql/memo.go:259`, `store/db/postgres/memo.go:244`).

Notably **not** deleted by this path: `reaction` rows (the handler lists them only to build the deleted-memo webhook payload at `memo_service.go:545`) and `memo_share` rows — neither has cascade code in the `DeleteMemo` flow (their cleanup exists only in the separate user-deletion path, `store/db/sqlite/user_delete.go`). There is also no `memo_organizer` table anymore; it was removed by the 0.13 migration `store/migration/sqlite/0.13/01__remove_memo_organizer_id.sql`.
