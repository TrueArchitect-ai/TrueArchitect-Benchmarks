Frontend requests are authenticated by a Connect RPC interceptor: `authInterceptor` in `web/src/connect.ts` (registered on the transport at `web/src/connect.ts:184-189`). Before each request it obtains a short-lived **access token** (via `getRequestToken`, backed by `web/src/auth-state.ts`) and sets it as an `Authorization: Bearer <token>` header. When the token is missing/expired or the server returns `Unauthenticated`, it calls `refreshAccessToken()`, which hits the `RefreshToken` RPC on a separate interceptor-free transport using `credentials: "include"` — so the long-lived **refresh token** travels as an HTTP-only cookie rather than being stored in JS. A refresh-dedup manager prevents concurrent refreshes, and one retry is marked with an `X-Retry` header.

On the backend, the server-side auth interceptor (`server/router/api/v1/connect_interceptors.go:222`) delegates to the `server/auth` package, whose `Authenticator` validates the credentials: `AuthenticateByAccessTokenV2` parses/verifies access-token JWTs, `AuthenticateByRefreshToken` validates refresh tokens (rotating them against stored user settings), and `AuthenticateByPAT` handles personal access tokens; the JWT claims and parsing live in `server/auth/token.go` (`AccessTokenClaims`, `RefreshTokenClaims`).

Answer: `web/src/connect.ts` (authInterceptor); short-lived access tokens (Bearer JWT) + long-lived refresh tokens (HTTP-only cookie), plus personal access tokens server-side; `server/auth` (authenticator.go, token.go).
