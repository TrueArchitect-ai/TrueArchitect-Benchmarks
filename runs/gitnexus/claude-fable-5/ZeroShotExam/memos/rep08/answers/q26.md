**Tables affected: `memo`, `memo_relation`, `attachment`**

The cascade is coded explicitly in `Store.DeleteMemo` (`store/memo.go:140-159`):

- **`memo_relation`** — deleted first, twice: once for rows where the memo is the source (`DeleteMemoRelation{MemoID}`) and once where it's the target (`DeleteMemoRelation{RelatedMemoID}`); the driver DELETE is in e.g. `store/db/sqlite/memo_relation.go:149`.
- **`attachment`** — all attachments linked to the memo are listed and deleted via `Store.DeleteAttachment` (`store/attachment.go:132-149`), which issues `DELETE FROM attachment` (`store/db/sqlite/attachment.go:212`). This also removes the stored file blob (local disk or S3), but that's object storage, not a table.
- **`memo`** — finally the memo row itself via `driver.DeleteMemo`, a plain `DELETE FROM memo WHERE id = ?` in each driver (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

The API-level handler (`server/router/api/v1/memo_service.go:518-593`) additionally deletes each comment memo first (relations of type `COMMENT`), but each of those goes through the same `Store.DeleteMemo`, so it touches the same three tables. Notably, it *lists* reactions only to build the webhook payload — there is no explicit deletion of `reaction` rows, and no `memo_organizer` cleanup either, so those tables are not touched by the cascade code.
