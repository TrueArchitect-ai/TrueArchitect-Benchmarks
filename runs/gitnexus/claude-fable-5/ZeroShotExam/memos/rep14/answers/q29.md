Frontend requests are authenticated by a Connect RPC client interceptor:

- **Interceptor path:** `web/src/connect.ts` — the `authInterceptor` (line 156) is installed on the shared Connect transport used by all service clients. Before each request it calls `getRequestToken()` and sets an `Authorization: Bearer <token>` header; on an `Unauthenticated` error it refreshes the token once and retries (marked with an `X-Retry` header), redirecting to login if the refresh fails. Token storage/expiry helpers live in `web/src/auth-state.ts`, and proactive refresh on tab focus is in `web/src/hooks/useTokenRefreshOnFocus.ts`.

- **Token kinds:** two tokens. A short-lived **access token** (JWT) held in frontend state and sent as the Bearer header, and a **refresh token** carried in an HTTP-only cookie (the transport uses `credentials: "include"`; a separate interceptor-free `refreshTransport` calls `AuthService.RefreshToken` to rotate it and obtain a new access token). The backend additionally accepts **personal access tokens (PATs)** on the same Bearer header, though the interceptor itself only manages the access/refresh pair.

- **Backend package:** `server/auth` — `server/auth/authenticator.go` validates them (`AuthenticateByAccessTokenV2` for the JWT access token, `AuthenticateByRefreshToken` for the cookie-borne refresh token, `AuthenticateByPAT` for PATs), with JWT signing/claims in `server/auth/token.go`. It is wired into the API through the gRPC/Connect auth interceptors in `server/router/api/v1` (e.g. `server/router/api/v1/connect_interceptors.go`).

**Answer format:** `web/src/connect.ts`; access token (JWT Bearer) + refresh token (HTTP-only cookie, rotated; backend also accepts PATs); `server/auth`
