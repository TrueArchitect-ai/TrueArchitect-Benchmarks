**Tables affected by `Store.DeleteMemo` (`store/memo.go:139`): `memo_relation`, `attachment`, `memo`.**

The explicit cascade code in `Store.DeleteMemo` at `store/memo.go:139-159` does, in order:

1. `memo_relation` — deleted twice via `driver.DeleteMemoRelation`, once with `MemoID = delete.ID` and once with `RelatedMemoID = delete.ID`, so relations in both directions are removed.
2. `attachment` — attachments linked to the memo are listed and each is deleted via `Store.DeleteAttachment` (`store/attachment.go:132`), which removes the stored file (local disk/S3 — not a table) and then executes `DELETE FROM attachment` (e.g. `store/db/sqlite/attachment.go:211`).
3. `memo` — finally `driver.DeleteMemo` runs `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:236`, with equivalents in `store/db/mysql/memo.go:258` and `store/db/postgres/memo.go:243`).

Two clarifying notes:

- The API-layer wrapper `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:517`) additionally deletes all comment memos first — but it does so by calling `Store.DeleteMemo` per comment, so it touches the same three tables, just for more rows. It *lists* reactions only to build the webhook payload; the `reaction` table is not deleted by any code in this flow.
- `memo_share` rows are also removed, but by a database-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` constraint (`store/migration/sqlite/LATEST.sql:109`), not by explicit Go cascade code. Include it if DB-declared cascades count; the explicit-code answer is the three tables above.
