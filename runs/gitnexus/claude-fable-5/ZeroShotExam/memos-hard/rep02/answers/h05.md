**Mechanism: explicit Go code.** When a user is deleted, each database driver's `DeleteUser` implementation runs explicit `DELETE FROM reaction ...` statements inside the delete-user transaction. There is no database-level rule — the `reaction` table has no foreign keys at all, so no `ON DELETE CASCADE` could apply.

What I checked:

**1. The Go deletion path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver. In each driver's `user_delete.go`, `deleteUserTargetsTx` deletes reactions two ways before deleting the user row:
- `deleteReactionsByContentIDsTx` — removes reactions *on* the user's memos (`DELETE FROM reaction WHERE content_id IN (...)`, where content IDs are built as `"memos/"+uid` from the user's memo tree)
- `deleteReactionsByCreatorTx` — removes reactions the user *made* (`DELETE FROM reaction WHERE creator_id = ?`)

Evidence, per driver:
- SQLite: `store/db/sqlite/user_delete.go:96,102` (calls), `:380-388` and `:400-403` (the DELETE statements)
- Postgres: `store/db/postgres/user_delete.go:96,102`, `:380-383`, `:400-401`
- MySQL: `store/db/mysql/user_delete.go:96,102`, `:417-420`, `:437-438`

**2. The schema, to rule out a DB-level rule.** The `reaction` table DDL in `store/migration/sqlite/LATEST.sql:92`, `store/migration/postgres/LATEST.sql:91`, `store/migration/mysql/LATEST.sql:91` (and the original `0.20/00__reaction.sql` migrations) defines `creator_id` as a plain `INTEGER/INT NOT NULL` column with only a UNIQUE constraint — no `FOREIGN KEY`, no `REFERENCES`, no `CASCADE`. So the database cannot remove reactions on its own; the explicit Go statements are the only mechanism.
