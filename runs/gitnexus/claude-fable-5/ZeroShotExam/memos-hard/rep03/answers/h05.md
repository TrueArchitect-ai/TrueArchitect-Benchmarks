**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements inside each driver's `DeleteUser` transaction — not by any database-level rule, since the `reaction` table has no foreign keys at all (so no `ON DELETE CASCADE` is possible).

What I checked:

**Go code (all three drivers):** Each driver's `DeleteUser` (at line 29 of each file) runs a transaction that deletes reactions two ways — by the memos' content IDs and by the user as creator:
- `store/db/sqlite/user_delete.go` — `deleteReactionsByContentIDsTx` (line ~380–388, `DELETE FROM reaction WHERE content_id IN ...`) and `deleteReactionsByCreatorTx` (line ~400–403, `DELETE FROM reaction WHERE creator_id = ?`), called from `DeleteUser` at lines 96 and 102.
- `store/db/mysql/user_delete.go` — same pair at lines ~420 and ~438, called at lines 96 and 102.
- `store/db/postgres/user_delete.go` — same pair, called at lines 96 and 102.

**Schema (no DB-level rule):** The `reaction` table definitions have `creator_id`/`content_id` as plain columns with no `FOREIGN KEY` or `ON DELETE` clause — only a UNIQUE constraint:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

So without the explicit Go deletes, reactions would be orphaned; the application code is what guarantees cleanup.
