**Premise correction:** There is no Redis in this repository. A grep across the codebase finds zero Redis references — no client library, no connection config, no environment variable. The cache layer is a homegrown, thread-safe **in-memory** cache, so there is no connection to configure at all.

**Actual mechanism:**

- The cache implementation lives in `store/cache/cache.go` — a mutex-protected in-process map with per-entry expiration, a periodic cleanup goroutine, and a max-items cap (`Config` struct at `store/cache/cache.go:43` defines `DefaultTTL`, `CleanupInterval`, `MaxItems`, `OnEviction`).
- The store wires it up in `store/store.go` (`New`, around line 39): it builds a `cache.Config` with `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`, and creates three caches from it — `instanceSettingCache`, `userCache`, and `userSettingCache`.
- **TTL for user entries: 10 minutes.** User entries are written via `s.userCache.Set(...)` in `store/user.go` (e.g., lines 98, 122, 132, 167), and `Set` applies the default TTL (`store/cache/cache.go:92-94`) — no custom `SetWithTTL` is used for users, so the 10-minute default from `store/store.go:41` applies.

(Separately, `server/router/rss/rss.go` has its own small in-memory cache for RSS output, and the frontend has `web/src/components/MemoEditor/services/cacheService.ts` — neither involves Redis either.)
