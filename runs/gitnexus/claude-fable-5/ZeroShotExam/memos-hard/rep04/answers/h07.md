The browser hits `GET /file/users/:identifier/avatar`. The avatar is not a separate file — it is stored inline in the user row's `avatar_url` column as a base64 data URI, so "reaching stored data" means the user-row SQL SELECT, after which the handler decodes the data URI in-process and writes the bytes.

Hops from request to stored data:

RegisterRoutes (route `/file/users/:identifier/avatar` → handler) — server/router/fileserver/fileserver.go:124
serveUserAvatar (serving handler) — server/router/fileserver/fileserver.go:168
getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
driver.ListUsers (SQL SELECT on the user row incl. `avatar_url`) — store/db/sqlite/user.go:88 (also store/db/postgres/user.go:87, store/db/mysql/user.go:84)

Then, back in the handler, the stored data URI is turned into image bytes and sent:

parseDataURI (base64-decodes `user.AvatarURL` → imageType, imageData) — server/router/fileserver/fileserver.go:737
c.Blob (writes image bytes to the response) — server/router/fileserver/fileserver.go:209

Note: the authorization gate at the top of `serveUserAvatar` only requires *some* valid viewer on a private instance (`AllowAnonymous()` false → `getCurrentUser`); it does not restrict which user's avatar can be fetched, so any user's profile image is served by username.
