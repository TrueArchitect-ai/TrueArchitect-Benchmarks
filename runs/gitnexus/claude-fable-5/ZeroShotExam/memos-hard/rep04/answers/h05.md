**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the user-deletion transaction in each database driver — not by any database-level rule. The `reaction` table has no foreign key at all (no `ON DELETE CASCADE`), so nothing at the schema level would clean them up.

Evidence:

- **Go code that does the deletion** — each driver's user-delete transaction has two helpers: `deleteReactionsByCreatorTx`, which runs `DELETE FROM reaction WHERE creator_id = $1` (removes reactions the user made anywhere), and `deleteReactionsByContentIDsTx`, which runs `DELETE FROM reaction WHERE content_id IN (...)` (removes other users' reactions on the deleted user's memos).
  - `store/db/postgres/user_delete.go:380-402` (both helpers shown above)
  - `store/db/sqlite/user_delete.go:383` and `:401`
  - `store/db/mysql/user_delete.go:420` and `:438`
  - These run inside the transaction opened by `DeleteUser` (`store/db/postgres/user_delete.go:29`), with the shared result/failpoint plumbing in `store/user_delete.go`.

- **Schema confirms no DB-level rule** — `store/migration/postgres/LATEST.sql:91-98` defines `CREATE TABLE reaction` with plain `creator_id INTEGER NOT NULL` and no `FOREIGN KEY` clause (contrast with `memo_share` immediately below it at line 108, which does have `FOREIGN KEY ... ON DELETE CASCADE`). The original creation migrations (`store/migration/{postgres,sqlite,mysql}/0.20/00__reaction.sql`) likewise define no foreign key, and the 0.23 migrations only rewrite `reaction_type` values.

So reaction cleanup on user deletion depends entirely on the explicit Go statements; if those were skipped, the rows would be orphaned rather than cascaded away.
