**Mechanism: explicit Go code.** When a user is deleted, their reactions are removed by hand-written `DELETE` statements inside the user-deletion transaction in each database driver — not by any database-level rule, since the `reaction` table has no foreign keys at all.

What I checked:

1. **The user-deletion code path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver, and all three drivers do the same thing inside a transaction:
   - `store/db/sqlite/user_delete.go:96` and `:102` call `deleteReactionsByContentIDsTx` and `deleteReactionsByCreatorTx`, which run `DELETE FROM reaction WHERE content_id IN (...)` (`:383`) and `DELETE FROM reaction WHERE creator_id = ?` (`:401`).
   - The same pair exists in `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`.
   
   So the code removes both the reactions the user authored (`creator_id`) and the reactions other users left on the deleted user's memos (`content_id` of the user's memo tree).

2. **The schema, to rule out a database-level rule.** The `reaction` table DDL in `store/migration/sqlite/LATEST.sql:92` (and the postgres/mysql equivalents at `store/migration/postgres/LATEST.sql:91`) defines only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`, no `ON DELETE CASCADE`. A grep for `CASCADE`/`REFERENCES` across all three `LATEST.sql` files finds exactly one foreign key in the entire schema, and it's on a `memo_id` column of a different table (line 109), not on `reaction`.

So without the explicit Go deletes, reactions would be orphaned; the drivers' `user_delete.go` code is the only mechanism that cleans them up.
