The browser hits `GET /file/users/:identifier/avatar`. The handler resolves the target user by the `:identifier` (username) path param, reads that user's `AvatarURL` field (a base64 data URI stored in the `users` table), decodes it, and writes the bytes back. Here is each hop from route to the database:

```
RegisterRoutes (route GET /file/users/:identifier/avatar) — server/router/fileserver/fileserver.go:120
serveUserAvatar (serving handler)                          — server/router/fileserver/fileserver.go:167
getUserByUsername                                          — server/router/fileserver/fileserver.go:714
Store.GetUser                                              — store/user.go:147
Store.ListUsers                                            — store/user.go:135
Driver.ListUsers (interface boundary)                     — store/driver.go:46
DB.ListUsers (SQLite impl, executes SQL on users table)   — store/db/sqlite/user.go:88
```

Notes:
- The requested image data itself is not a separate file/blob: it lives on the returned `User.AvatarURL` field (`store/user.go`). `serveUserAvatar` decodes it via `parseDataURI` (`server/router/fileserver/fileserver.go`) and returns it with `c.Blob(...)`.
- The final data-layer hop has three interchangeable driver implementations selected at runtime; the SQLite one is shown above. The equivalents are `store/db/postgres/user.go:86` and `store/db/mysql/user.go:83`.
- "Another user's" is handled by `getUserByUsername` looking up by the `:identifier` param rather than the current viewer; access is gated earlier in the handler (on a private instance, `s.Profile.AllowAnonymous()` forces `getCurrentUser` auth before the lookup).
