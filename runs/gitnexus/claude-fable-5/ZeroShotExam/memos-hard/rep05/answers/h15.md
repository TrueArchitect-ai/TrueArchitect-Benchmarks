Memo visibility is checked independently in several server surfaces, not just the memo API:

- gRPC/Connect memo API read check — `server/router/api/v1/memo_service.go` (`checkMemoReadAccess`, lines 39–68: public memos pass, non-public require auth, private require creator; plus list-time filtering in `ListMemos`, lines 218–227, which constrains `VisibilityList`/filters by the current user)
- Memo attachment listing — `server/router/api/v1/memo_attachment_service.go` (`ListMemoAttachments`, lines 213–226: re-checks the parent memo's visibility before returning its attachments)
- Attachment API access via linked memo — `server/router/api/v1/attachment_service.go` (lines 436–454: an attachment linked to a memo inherits that memo's visibility rules, with superuser override)
- File server (raw attachment bytes over HTTP) — `server/router/fileserver/fileserver.go` (lines 666–704: public + anonymous-allowed passes, share-token fallback, otherwise authenticated user with private-memo creator/admin check)
- SSE real-time event delivery — `server/router/api/v1/sse_hub.go` (`canReceive`, lines 134–144: private-memo events are delivered only to the creator or an admin)
- RSS feed — `server/router/rss/rss.go` (lines 88–94 and ~141: memo queries hard-coded to `VisibilityList: [Public]`)
- Frontend sitemap/SEO rendering — `server/router/frontend/frontend.go` (line 149–151: only public memos are listed)

The first five are per-request enforcement of the visibility rule (public / protected-requires-login / private-requires-creator-or-admin); the RSS and frontend surfaces enforce it by restricting their queries to public memos only.
