### How it fits together

- **Route → handler:** `RegisterRoutes` binds `/file/users/:identifier/avatar` to `serveUserAvatar` (`server/router/fileserver/fileserver.go:124`). The handler does an auth gate on private instances via `getCurrentUser` (line 708), then resolves the target user.
- **Handler → store:** `getUserByUsername` calls `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})` — this is the hop to another user's record, keyed on the username from the URL.
- **Store → cache/driver:** `Store.GetUser` falls through to `Store.ListUsers`, which calls `s.driver.ListUsers` (`store/user.go:137`).
- **Driver → data layer:** `DB.ListUsers` builds a `SELECT ... avatar_url ... FROM user WHERE username = ?` and runs `d.db.QueryContext`, scanning the column into `user.AvatarURL` (`store/db/sqlite/user.go:159,173,189`). This is the actual read of stored data. (Parallel implementations exist for Postgres at `store/db/postgres/user.go:87` and MySQL at `store/db/mysql/user.go:84`.)
- **Stored form:** the image is **not** an attachment blob or file on disk — it lives inline in the `user.avatar_url` column as a `data:<type>;base64,...` URI. Back in `serveUserAvatar`, `parseDataURI` (line 737) base64-decodes it, validates the type against `avatarAllowedTypes`, and emits it with `c.Blob(...)` (line 209).

So the data layer for a profile image is the `avatar_url` column of the `user` table, reached through the standard `GetUser → ListUsers → driver.ListUsers` store path — not the attachment/S3/local-file storage path used by `serveAttachmentFile`.
