**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside each database driver's `DeleteUser` transaction, not by any database rule.

What I checked:

1. **The Go deletion path.** Each driver has a `DeleteUser` implementation that runs a single transaction deleting all of a user's dependent rows. In `store/db/sqlite/user_delete.go`, `deleteUserTargetsTx` (lines 92–127) calls two reaction cleanup steps:
   - `deleteReactionsByCreatorTx` (line 400): `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the deleted user made.
   - `deleteReactionsByContentIDsTx` (line 380): `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *other* users left on the deleted user's memos and comment tree (content IDs built as `"memos/"+uid` in `memoContentIDsFromRefs`, line 512).

   The MySQL and Postgres drivers do the same: `store/db/mysql/user_delete.go:417,437` and `store/db/postgres/user_delete.go:380,400`, both invoked from their `deleteUserTargetsTx` at lines 96 and 102.

2. **The schema, to rule out a database-level rule.** The `reaction` table definitions have no foreign keys at all — no `REFERENCES` clause and therefore no `ON DELETE CASCADE`. See `store/migration/sqlite/LATEST.sql:92-98`, `store/migration/postgres/LATEST.sql:91-97`, and the original migrations (`store/migration/sqlite/0.20/00__reaction.sql`, `store/migration/postgres/0.20/00__reaction.sql`). The only constraint is `UNIQUE(creator_id, content_id, reaction_type)`, so the database could not cascade the delete even if FK enforcement were on.

So: cleanup happens entirely in application code, transactionally alongside the user row delete (`deleteUserRowTx`, `store/db/sqlite/user_delete.go:461`), covering both reactions authored by the user and reactions on the user's content. There is also a test exercising this path at `server/router/api/v1/test/user_service_delete_test.go`.
