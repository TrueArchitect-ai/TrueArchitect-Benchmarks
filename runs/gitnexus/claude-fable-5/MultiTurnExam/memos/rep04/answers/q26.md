Tables affected when DeleteMemo runs:

- **memo** — the memo row itself, plus any comment memos: the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`) first deletes all comment memos (relations of type `COMMENT`) via `Store.DeleteMemo`, then the memo.
- **memo_relation** — explicit cascade code in `Store.DeleteMemo` (`store/memo.go:142-147`) deletes relation rows where the memo is either source (`memo_id`) or target (`related_memo_id`).
- **attachment** — `Store.DeleteMemo` (`store/memo.go:148-157`) deletes each linked attachment via `Store.DeleteAttachment` (`store/attachment.go:132`, which also removes the underlying blob/local file storage).
- **memo_share** — deleted by database-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`).

Notably, **reaction** rows are *not* deleted — the handler lists reactions only to build the webhook payload (`memo_service.go:545-550`), and the `reaction` table has no foreign key to `memo` (`store/migration/sqlite/LATEST.sql:92-99`).
