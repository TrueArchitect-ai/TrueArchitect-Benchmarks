Tables affected: **memo**, **memo_relation**, **attachment**

Per `Store.DeleteMemo` (`store/memo.go:140-159`):
- `memo_relation` — explicitly deleted for both directions (rows where the memo is `memo_id` and where it is `related_memo_id`)
- `attachment` — each attachment linked to the memo is deleted via `Store.DeleteAttachment` (`store/attachment.go:132`, which also removes the underlying file/object storage)
- `memo` — the memo row itself, via the driver's plain `DELETE FROM memo` (`store/db/sqlite/memo.go:237`)

Additionally, the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) deletes comment memos first, which hits the same three tables again for each comment. Notably, `reaction` and `memo_share` rows are **not** cleaned up by any explicit cascade code in the delete path, and the SQLite schema (`store/migration/sqlite/LATEST.sql`) defines no foreign-key cascades — so only the three tables above are affected.
