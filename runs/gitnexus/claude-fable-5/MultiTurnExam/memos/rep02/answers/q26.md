Tables affected when DeleteMemo runs (explicit cascade code in `Store.DeleteMemo`, `store/memo.go:140-159`):

- **memo_relation** — relation rows deleted where the memo is either source (`MemoID`) or target (`RelatedMemoID`)
- **attachment** — attachment rows linked to the memo are deleted via `Store.DeleteAttachment` (`store/attachment.go:132`; this also removes the underlying blob from local/S3 storage, which is filesystem/object storage, not a table)
- **memo** — the memo row itself via the driver's `DELETE FROM memo` (`store/db/sqlite/memo.go:237`); note the API handler (`server/router/api/v1/memo_service.go:518`) also deletes comment memos first by calling `Store.DeleteMemo` per comment, so additional `memo` rows (and their relations/attachments) go through the same cascade

Reactions are listed only to build the webhook payload in the handler — no reaction deletion happens in this path.
