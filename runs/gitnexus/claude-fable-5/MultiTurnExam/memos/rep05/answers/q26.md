When DeleteMemo runs, these tables are affected:

- **memo** — the memo row itself (and, in the API handler, comment memos are deleted first via recursive `Store.DeleteMemo` calls — `server/router/api/v1/memo_service.go:568-578`)
- **memo_relation** — explicit cascade code deletes rows where the memo is source or target (`store/memo.go:142-147`)
- **attachment** — explicit cascade code lists and deletes linked attachments (`store/memo.go:149-157`, via `Store.DeleteAttachment` in `store/attachment.go:132`; this also removes blob storage, which is filesystem/S3, not a table)
- **memo_share** — deleted by a database-level `ON DELETE CASCADE` foreign key on `memo_id` (`store/migration/sqlite/LATEST.sql:108-109`, same in the mysql/postgres schemas)

Notably, **reaction** rows are *not* cleaned up in this path — the handler lists reactions only to build the webhook payload, and there is no FK cascade on that table.
