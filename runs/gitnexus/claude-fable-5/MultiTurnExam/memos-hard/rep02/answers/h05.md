**Mechanism: explicit Go code — reactions are deleted by hand-written SQL inside each database driver's `DeleteUser` transaction, not by any database-level rule.**

Evidence locations:

- `store/db/sqlite/user_delete.go` — `deleteUserTargetsTx` runs two explicit reaction deletions inside the delete-user transaction: `deleteReactionsByContentIDsTx` at line 96 (`DELETE FROM reaction WHERE content_id IN (...)`, removing reactions *on* the user's memos and their comment tree, lines 380-388) and `deleteReactionsByCreatorTx` at line 102 (`DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user *made*, lines 400-403).
- The MySQL and Postgres drivers do the same: `store/db/mysql/user_delete.go:96,102` (helpers at lines 417, 437) and `store/db/postgres/user_delete.go:96,102` (helpers at lines 380, 400).
- No database-level rule exists for reactions: the `reaction` table DDL in `store/migration/sqlite/LATEST.sql:92-99` (and the MySQL/Postgres equivalents) has no foreign keys at all — just a UNIQUE constraint. The only `ON DELETE CASCADE` in any schema is on `memo_share.memo_id` (`store/migration/sqlite/LATEST.sql:109`, `mysql/LATEST.sql:108`, `postgres/LATEST.sql:108`), which is unrelated to reactions.

So without the explicit Go deletions, reactions would be orphaned — the schema would not clean them up.
