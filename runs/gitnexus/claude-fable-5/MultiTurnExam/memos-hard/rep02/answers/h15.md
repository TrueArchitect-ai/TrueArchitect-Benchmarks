Memo visibility is enforced independently on five server surfaces:

- **gRPC/Connect API single-memo access — `checkMemoReadAccess`** — `server/router/api/v1/memo_service.go:39` (Public open; non-public requires auth; Private requires creator; archived memos creator-only). Reused by `GetMemo` (`memo_service.go:356,367`) and comment listing (`server/router/api/v1/memo_service_comments.go:148`).
- **gRPC/Connect API list scoping — `ListMemos` query construction** — `server/router/api/v1/memo_service.go:219-225`: anonymous callers get `VisibilityList = [Public]`, authenticated callers viewing others get `[Public, Protected]`, so the visibility filter is pushed into the store query itself.
- **File server (attachment/blob downloads) — `checkAttachmentPermission`** — `server/router/fileserver/fileserver.go:650-699`: looks up the attachment's memo and enforces its visibility (Public allowed anonymously only if the instance permits, `fileserver.go:677`; Private blocked unless creator or admin, `fileserver.go:699`).
- **RSS feeds** — `server/router/rss/rss.go:90,141`: both feed endpoints hard-code `VisibilityList: []store.Visibility{store.Public}`, so only public memos are ever syndicated.
- **Frontend router (server-rendered pages/meta)** — `server/router/frontend/frontend.go:150`: memo pages are resolved with `VisibilityList: [Public]` only.
- **SSE realtime delivery — `SSEHub.canReceive`** — `server/router/api/v1/sse_hub.go:131-141` (visibility carried on events via `server/router/api/v1/sse_event_helpers.go:29-37`): per-subscriber filtering by event visibility before an update event is delivered, denying on unknown visibility.

That's the API (two distinct mechanisms: per-memo check and list scoping), the file server, RSS, the frontend page renderer, and the SSE hub — each re-implements the visibility rule for its own data path.
