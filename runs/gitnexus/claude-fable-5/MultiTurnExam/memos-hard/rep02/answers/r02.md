**Premise correction: there is no per-user API rate-limiting middleware in this codebase — none is registered anywhere, so there are no request limits to report.**

What I checked:

- The Echo server's global middleware stack is just `middleware.Recover()` and a CORS middleware (`server/server.go:51-52`); the frontend router adds only static-file/SPA-fallback middleware (`server/router/frontend/frontend.go:54-59`). Echo's built-in `RateLimiter` middleware is never used.
- The Connect/gRPC API's interceptor chain is metadata, logging, recovery, and auth only (`server/router/api/v1/v1.go:133-137`) — no throttling interceptor.
- A case-insensitive repo-wide grep for rate-limit vocabulary (`rate`, `ratelimit`, `throttle`, `limiter`) over backend Go code finds no rate-limiting implementation.

The "limits" that do exist are of a different kind: a request body size cap (`connect.WithReadMaxBytes(maxAPIRequestBytes)`, `server/router/api/v1/v1.go:141`), concurrency semaphores for thumbnail/image processing (`server/router/api/v1/v1.go` and `server/router/fileserver/fileserver.go:107,116`), a bounded webhook dispatch queue (`internal/webhook/webhook.go:39`), and memo content length limits — none of which is per-user request rate limiting.
