The browser hits `GET /file/users/{identifier}/avatar`, and the avatar bytes live in the `user` row itself (the `avatar_url` column holds a data URI, decoded at serve time). The chain, hop per line:

- `FileServerService.RegisterRoutes` (binds `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (handler; enforces auth on private instances, then looks up the target user) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks `userCache`, else falls through) — `store/user.go:148`
- `Store.ListUsers` (delegates to the DB driver) — `store/user.go:136`
- `(*DB).ListUsers` (driver SQL `SELECT ... avatar_url ... FROM user`) — `store/db/sqlite/user.go:88` (equivalents: `store/db/mysql/user.go:84`, `store/db/postgres/user.go:87`)
- `FileServerService.parseDataURI` (decodes the stored `user.AvatarURL` data URI into MIME type + raw image bytes) — `server/router/fileserver/fileserver.go:737`

Back in `serveUserAvatar`, the decoded type is checked against the `avatarAllowedTypes` allowlist (`fileserver.go:201`), security and cache headers are set, and the bytes are written with `c.Blob` (`fileserver.go:209`). Note there is no separate blob store for avatars — the "data layer" terminus is the user row fetched by the driver's `ListUsers` query.
