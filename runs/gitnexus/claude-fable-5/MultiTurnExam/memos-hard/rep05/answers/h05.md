**Mechanism: explicit Go code** — the reactions are deleted by hand-written SQL inside each database driver's user-deletion transaction, not by any database-level rule.

What I checked:

1. **The deletion code path.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver. Each of the three drivers has a `user_delete.go` that runs the whole cleanup in one transaction and explicitly deletes reactions two ways:
   - by creator: `DELETE FROM reaction WHERE creator_id = ?` — `store/db/sqlite/user_delete.go:400-401`, `store/db/mysql/user_delete.go:437-438`, `store/db/postgres/user_delete.go:400-401` (called from `deleteUserTargetsTx` at line 102 in each file);
   - by content: `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-383` and equivalents) removes reactions *on* the deleted user's memos, using the collected memo UIDs as `content_id`s (line 96 in each driver's `deleteUserTargetsTx`).

2. **The schema, to rule out a database-level rule.** The `reaction` table DDL in all three dialects — `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/mysql/LATEST.sql:91-98`, `store/migration/postgres/LATEST.sql:91-98` — declares `creator_id` as a plain integer column with no `FOREIGN KEY` and therefore no `ON DELETE CASCADE`. There is no trigger either; the schema files contain only tables and indexes.

So: when a user is deleted, both the reactions they authored and the reactions others left on their memos are removed by explicit Go code inside the same transaction that deletes the user row.
