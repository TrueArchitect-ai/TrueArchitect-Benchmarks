**Premise correction: there is no per-user API rate-limiting middleware in this codebase.** Nothing like it is registered anywhere, and no request-count limits exist.

What I checked: a repo-wide search of Go code for rate-limit/throttle/limiter terms turns up nothing except a documentation comment suggesting rate limiting as a *future* consideration for email sending (`internal/email/doc.go:86`). The only HTTP middleware registered on the Echo server is `middleware.Recover()` and a CORS middleware (`server/server.go:51-52`); the gRPC-Gateway/Connect layer adds only an authentication middleware (`server/router/api/v1/v1.go:69-97`), not rate limiting.

The closest things that exist are not per-user rate limits:

- Two **concurrency** semaphores in the API service — at most 3 concurrent thumbnail generations and 2 concurrent image-processing operations, globally, not per user (`server/router/api/v1/v1.go:59-60`).
- Batch-size caps in background runners (e.g. the S3 presign runner processes attachments 100 at a time, `server/runner/s3presign/runner.go`), which bound work, not client request rates.

So if per-user rate limiting is a requirement, it would have to be added — today a single user can issue unlimited API requests as far as the server code is concerned.
