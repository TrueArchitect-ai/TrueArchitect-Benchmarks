A profile image is fetched by the browser at `GET /file/users/{identifier}/avatar`. The avatar bytes aren't a file on disk — they're stored as a data URI in the `avatar_url` column of the user row, so the "data layer" hop ends at the user query in the SQL driver. The chain, hop by hop:

- Route registration `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (handler: optional auth check on private instances, then loads the user) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks the in-memory `userCache`, else falls through) — `store/user.go:148`
- `Store.ListUsers` (delegates to the DB driver, populates cache) — `store/user.go:136`
- Driver `DB.ListUsers` (SQL `SELECT` including the `avatar_url` column) — `store/db/sqlite/user.go:88` (equivalents: `store/db/mysql/user.go:84`, `store/db/postgres/user.go:87`)

Back in the handler, the stored value is decoded and returned to the browser: `parseDataURI` splits the `data:image/...;base64,` URI into MIME type and raw bytes (`server/router/fileserver/fileserver.go:196`), the type is checked against `avatarAllowedTypes` (`fileserver.go:75`), and the bytes are written with `c.Blob(...)` (`fileserver.go:209`).
