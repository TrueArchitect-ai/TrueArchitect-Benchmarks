**Mechanism: explicit Go code — each database driver's user-deletion transaction issues `DELETE FROM reaction ...` statements. There is no database-level rule (no foreign keys or `ON DELETE CASCADE` on the reaction table).**

What I checked:

1. **Explicit Go deletion code.** Each driver's `DeleteUser` implementation runs a transaction (`deleteUserTargetsTx`) that removes reactions two ways: by the deleted user's authorship (`deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`) and by content, wiping other users' reactions on the deleted user's memos (`deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`). These exist in all three drivers:
   - `store/db/sqlite/user_delete.go:380-403` (called from lines 96 and 102 of the same file)
   - `store/db/mysql/user_delete.go:420` and `:438`
   - `store/db/postgres/user_delete.go:383` and `:401`

2. **No database-level rule.** The `reaction` table definitions have no `FOREIGN KEY`, `REFERENCES`, or `CASCADE` clauses in any schema — just a unique constraint on `(creator_id, content_id, reaction_type)`:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/mysql/LATEST.sql:91-98`
   - `store/migration/postgres/LATEST.sql:91` (same shape)

So reactions can't be cleaned up by the database itself; the explicit statements in each driver's `user_delete.go` are what removes them, and they do run as part of `DeleteUser` (`store/db/{sqlite,mysql,postgres}/user_delete.go:29` via `store/user.go:171`).
