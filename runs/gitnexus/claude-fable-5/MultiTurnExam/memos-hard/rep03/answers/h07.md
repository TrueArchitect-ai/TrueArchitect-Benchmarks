A browser fetches `GET /file/users/{identifier}/avatar`. The avatar itself is stored as a data-URI string in the user row's `avatar_url` column, so "stored data" is reached through the user store. Hops:

- Route registration `FileServerService.RegisterRoutes` (`fileGroup.GET("/users/:identifier/avatar", ...)`) — `server/router/fileserver/fileserver.go:121-124`
- `FileServerService.serveUserAvatar` (handler: optional auth check on private instances, then looks up the target user, parses and validates the avatar, writes the image bytes) — `server/router/fileserver/fileserver.go:168-210`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715-717`
- `Store.GetUser` (checks the user cache, falls through to a list query) — `store/user.go:148-169`
- `Store.ListUsers` (delegates to the DB driver, populates cache) — `store/user.go:136`
- `Driver.ListUsers` interface dispatch (`store/driver.go`) to the concrete driver, e.g. `DB.ListUsers` — `store/db/sqlite/user.go:88` (equivalents in `store/db/mysql/user.go`, `store/db/postgres/user.go`) — which SELECTs the user row including `avatar_url`

Back in the handler, the stored `user.AvatarURL` data-URI is decoded by `FileServerService.parseDataURI` and served with `c.Blob(...)` after a MIME allowlist check (`avatarAllowedTypes`) — `server/router/fileserver/fileserver.go:196-209`. No attachment/blob table is involved for avatars; the image bytes live inline in the user record.
