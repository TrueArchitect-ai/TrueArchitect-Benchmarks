A browser hits `GET /file/users/{identifier}/avatar`; the avatar bytes live in the `user` row itself (the `avatar_url` column holds a `data:` URI), so the trace ends at the user query in the DB driver. Hops:

1. Route registration: `fileGroup.GET("/users/:identifier/avatar", s.serveUserAvatar)` — `server/router/fileserver/fileserver.go:124`
2. `serveUserAvatar` (handler: optional auth check via `AllowAnonymous`/`getCurrentUser`, then looks up the target user) — `server/router/fileserver/fileserver.go:168`
3. `getUserByUsername` (wraps the lookup as `store.FindUser{Username}`) — `server/router/fileserver/fileserver.go:715`
4. `(*Store).GetUser` (checks `userCache`, else falls through) — `store/user.go:148`
5. `(*Store).ListUsers` (delegates to the selected driver, populates cache) — `store/user.go:136`
6. `(*DB).ListUsers` (driver SQL `SELECT` on the `user` table, which includes `avatar_url`) — `store/db/sqlite/user.go:88` (equivalents in `store/db/mysql/user.go` and `store/db/postgres/user.go`)

Back in the handler, the stored value is turned into the response: `parseDataURI` decodes the `data:` URI from `user.AvatarURL`, the MIME type is checked against `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:75`), and the bytes are written with `c.Blob` (`fileserver.go:196-209`). Note the avatar is *not* an attachment — unlike memo attachments there's no local-file/S3/database branch; the image data comes entirely from the user record.
