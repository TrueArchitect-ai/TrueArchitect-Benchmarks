Memo visibility is enforced independently in these server surfaces:

1. **gRPC/Connect API — single-memo read guard**: `checkMemoReadAccess` — `server/router/api/v1/memo_service.go:39-66` (archived-memo creator check, then non-Public requires auth; Private requires creator/superuser). Reused by `GetMemo`, comment creation (`server/router/api/v1/memo_service_comments.go:33-41`), and related endpoints.

2. **gRPC/Connect API — list-query filtering**: list endpoints inject visibility predicates into the store query rather than post-filtering: `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:158-160`), `ListMemoRelations` (`server/router/api/v1/memo_relation_service.go:109-111`), user stats (`server/router/api/v1/user_service_stats.go:84-90`) — anonymous gets `visibility == "PUBLIC"`, signed-in gets `creator_id == me || visibility in ["PUBLIC","PROTECTED"]`.

3. **gRPC/Connect API — attachment access via linked memo**: attachments inherit the memo's visibility: `server/router/api/v1/attachment_service.go:436-451` and `server/router/api/v1/memo_attachment_service.go:213-222`.

4. **File server (raw HTTP file/thumbnail serving)**: `checkAttachmentPermission` — `server/router/fileserver/fileserver.go:650-699` (Public served anonymously only if the instance allows anonymous access; otherwise requires authenticated user, with Private restricted to creator/admin, plus a share-token path).

5. **RSS feeds**: only `store.Public` memos are ever queried — `server/router/rss/rss.go:90` and `:141` (`VisibilityList: []store.Visibility{store.Public}`).

6. **Notification/email surface (content redaction by visibility)**: emails and in-app notification payloads redact non-public memo content — `server/notification/email.go:313-316` and `server/router/api/v1/user_service_notifications.go:309-312`.

(The ACL layer explicitly delegates: `server/router/api/v1/acl_config.go:32` notes visibility filtering is done in the service layer; MCP has no separate check of its own.)
