The browser hits `GET /file/users/{identifier}/avatar`. The avatar itself is stored as a base64 data URI in the user row's `avatar_url` column, so the "stored data" is reached through the user lookup. Hops:

- `FileServerService.RegisterRoutes` (route `GET /file/users/:identifier/avatar`) — `server/router/fileserver/fileserver.go:124`
- `FileServerService.serveUserAvatar` (serving handler: optional auth check on private instances, then decodes and returns the image) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (checks `userCache`, else falls through) — `store/user.go:148`
- `Store.ListUsers` (delegates to the DB driver, populates cache) — `store/user.go:136`
- `driver.ListUsers` (SQL `SELECT ... avatar_url ... FROM user`; per-backend implementation) — `store/db/sqlite/user.go:88` (equivalents at `store/db/mysql/user.go:84`, `store/db/postgres/user.go:87`)

Back in the handler, `serveUserAvatar` takes the fetched `user.AvatarURL`, parses it with `FileServerService.parseDataURI` (`server/router/fileserver/fileserver.go`), validates the MIME type against `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:75`), and writes the decoded bytes with `c.Blob`. Unlike attachments, no blob storage or filesystem hop is involved — the image data lives entirely in the `user` table.
