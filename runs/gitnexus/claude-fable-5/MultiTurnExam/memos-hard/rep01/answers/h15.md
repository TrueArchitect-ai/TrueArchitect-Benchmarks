Distinct server surfaces that enforce memo visibility:

- **gRPC/Connect API — single-memo reads:** `APIV1Service.checkMemoReadAccess` — `server/router/api/v1/memo_service.go:44-68` (public passes; non-public requires authentication; private requires being the creator). Related per-RPC checks reuse the same rule, e.g. reactions on non-public memos (`server/router/api/v1/reaction_service.go:30`) and attachment listing (`server/router/api/v1/memo_attachment_service.go:214`).
- **gRPC/Connect API — list queries:** `ListMemos` scopes the store query by viewer: anonymous → `VisibilityList = [Public]`, authenticated viewing someone else → `[Public, Protected]`, otherwise a `creator_id == X || visibility in ["PUBLIC","PROTECTED"]` filter — `server/router/api/v1/memo_service.go:217-227` (same pattern in user stats: `server/router/api/v1/user_service_stats.go:84-90, 218-220`).
- **File server (attachment downloads):** `FileServerService.checkAttachmentPermission` — `server/router/fileserver/fileserver.go:650` — resolves the attachment's memo and enforces its visibility (public + anonymous-allowed passes; otherwise share-token or authenticated user; private restricted to creator/admin), called from `serveAttachmentFile` at `server/router/fileserver/fileserver.go:149`.
- **SSE event stream:** `SSEClient.canReceive` — `server/router/api/v1/sse_hub.go:134` — server-side delivery filtering so private-memo events reach only the creator or an admin (unknown visibility is denied).
- **RSS feeds:** feed builders query only `VisibilityList: [Public]` — `server/router/rss/rss.go:90` and `:141`.
- **Frontend sitemap:** public-only memo listing for sitemap generation — `server/router/frontend/frontend.go:149-151`.

One more adjacent site: comment/mention notification logic suppresses cross-user delivery for private memos (`server/router/api/v1/memo_mention_helpers.go:84`, `server/router/api/v1/memo_service_comments.go:100`), enforcing visibility in the notification surface.
