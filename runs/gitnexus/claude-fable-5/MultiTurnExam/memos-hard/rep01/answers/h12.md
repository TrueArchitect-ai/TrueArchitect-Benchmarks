Determination method — the call is dynamic (through the `store.Driver` interface), so I resolved which of the three candidate implementations (`store/db/sqlite/memo.go:16`, `store/db/mysql/memo.go:16`, `store/db/postgres/memo.go:16`) is bound at runtime by tracing the configuration rather than the call graph:

1. `Store.CreateMemo` delegates to `s.driver.CreateMemo(ctx, create)` at `store/memo.go:113` — an interface dispatch, ambiguous statically.
2. The concrete driver is chosen once at startup in the factory `NewDBDriver` (`store/db/db.go:14`), which switches on `profile.Driver`: `"sqlite"` → `sqlite.NewDB`, `"mysql"` → `mysql.NewDB`, `"postgres"` → `postgres.NewDB`.

With no database flags, the default value of that setting is `"sqlite"`: the entrypoint registers `viper.SetDefault("driver", "sqlite")` at `cmd/memos/main.go:122` and the `--driver` flag's default is also `"sqlite"` at `cmd/memos/main.go:130`; the profile is built from `viper.GetString("driver")` at `cmd/memos/main.go:43` (and `internal/profile/profile.go:110` further assumes sqlite when no DSN is given, defaulting the DSN to a local file).

So in a default installation the switch takes the `"sqlite"` branch, the bound driver is `*sqlite.DB`, and its `CreateMemo` executes the actual SQL INSERT.
