From the schema:
- `memo` table itself (deleted directly)
- `memo_share` table - has foreign key memo_id with ON DELETE CASCADE
- `memo_relation` table - has memo_id and related_memo_id (no constraint)
- `attachment` table - has memo_id (no constraint)
- `reaction` table - has content_id (TEXT, not a foreign key - contains memo resource name)

When DeleteMemo runs: the `memo` row is deleted directly. The `memo_share` table is automatically cleaned via ON DELETE CASCADE foreign key constraint. The `memo_relation` table entries referencing the deleted memo (both as memo_id and related_memo_id) are not automatically deleted by the database. The `attachment` table entries linked to the memo via memo_id are not automatically deleted. The `reaction` table entries referencing the memo via content_id are not automatically deleted. However, based on the API handler code (line 567-577 in `/bench/repo/server/router/api/v1/memo_service.go`), related memo comments are explicitly deleted first.
