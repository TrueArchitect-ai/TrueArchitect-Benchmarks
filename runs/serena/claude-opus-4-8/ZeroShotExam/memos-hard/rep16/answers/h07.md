I now have the full chain. The avatar is stored as a base64 data URI directly in the `user.avatar_url` column (there's no separate blob store for it).

A browser requests another user's avatar via `GET /file/users/:identifier/avatar`. The trip to stored data:

1. `serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (the serving handler; route registered at line 124). It authorizes, then resolves the target user and finally decodes the stored data URI into image bytes via `parseDataURI` (line 196 → 737).
2. `getUserByUsername` — `server/router/fileserver/fileserver.go:715` (looks the user up by the `:identifier` path param).
3. `(*Store).GetUser` — `store/user.go:148` (checks user cache, delegates to list).
4. `(*Store).ListUsers` — `store/user.go:136` (forwards to the DB driver).
5. `(*DB).ListUsers` — `store/db/sqlite/user.go` (function at ~line 130; `SELECT ... avatar_url ... FROM user` at lines 151–165, scanned into `user.AvatarURL` at line 189). The SQLite driver runs the query and reads the row.

The data itself lives in the `avatar_url` column of the `user` table as a `data:<mime>;base64,...` URI — it is not stored as a file/attachment blob. The handler decodes that base64 (`parseDataURI`, `server/router/fileserver/fileserver.go:737`) and writes the raw image bytes back with `c.Blob` (line 209).

(Equivalent driver files exist for the other databases: `store/db/postgres/user.go` and `store/db/mysql/user.go`; SQLite is shown as the representative path.)
