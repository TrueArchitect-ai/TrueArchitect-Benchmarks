**Premise correction:** Neither. The question presupposes an external message broker (NATS or RabbitMQ), but the webhook delivery workers consume from **no external broker at all**. This is the `memos` Go application, and there is no NATS, RabbitMQ, AMQP, Kafka, or Redis dependency anywhere in it.

**Actual mechanism:** Webhook delivery uses an **in-process, in-memory Go buffered channel** drained by a fixed pool of goroutine workers inside the same server process.

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`. The "queue" is a package-level Go channel with a buffer capacity of 128. There is no stream/subject/topic creation call; this channel declaration is the entire queue definition.
- **Worker consume point:** `internal/webhook/webhook.go:45` — 4 worker goroutines spawned in `init()` (lines 42–55), each running `for payload := range asyncPostQueue { ... Post(payload) }`, where `Post` performs the outbound HTTP POST.
- **Producer side:** `PostAsync` enqueues via a non-blocking send at `internal/webhook/webhook.go:190` (`case asyncPostQueue <- requestPayload:`), dropping with a warning if the buffer is full. It is triggered by the memo webhook dispatch methods at `server/router/api/v1/memo_service_webhooks.go:43,71`.

So the "broker" is simply a bounded Go channel with a 4-goroutine worker pool — entirely in-memory, no external queue infrastructure involved.
