**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by two explicit `DELETE FROM reaction` statements run inside the delete-user transaction — not by any database-level cascade, and not left behind.

**Evidence locations:**

1. **The deletion orchestration** — `store/db/sqlite/user_delete.go` and `store/db/postgres/user_delete.go`, function `deleteUserTargetsTx`. It explicitly calls, in order:
   - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` — removes reactions *on* the user's own memos (the memo tree, including comment children), keyed by `content_id` (`"memos/"+uid`).
   - `deleteReactionsByCreatorTx(ctx, tx, userID)` — removes reactions the user *made* on anyone's content.

2. **The actual SQL** (same files):
   - `deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)`
   - `deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = ?`

3. **Entry point**: `store/user.go:171` `Store.DeleteUser` → dispatches to `s.driver.DeleteUser` (the driver functions above), all wrapped in a single transaction that commits at the end.

4. **No DB-level rule** — the `reaction` table schema has `creator_id INTEGER NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and **no foreign key** to the user table, so there is no `ON DELETE CASCADE` to fall back on:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-97`
   
   (For contrast, the only cascading FKs in these schemas are `attachment.memo_id → memo(id) ON DELETE CASCADE` at line ~108 in each — nothing points reactions at users.)

So removing reactions on user deletion depends entirely on that explicit Go code; if it were absent, the reactions would be orphaned rather than cleaned up automatically.
