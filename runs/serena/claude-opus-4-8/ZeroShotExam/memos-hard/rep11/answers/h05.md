**Mechanism: Removed by explicit Go code** (raw `DELETE FROM reaction` statements run inside the user-delete transaction), **not** by a database-level rule. The `reaction` table has no foreign key on `creator_id`, so there is no `ON DELETE CASCADE` or trigger that would clean it up automatically.

**Evidence:**

1. **Explicit Go deletion** — the delete-user transaction calls two reaction-cleanup steps in `deleteUserTargetsTx`:
   - `store/db/sqlite/user_delete.go:96` → `deleteReactionsByContentIDsTx` (defined at `:380-388`): `DELETE FROM reaction WHERE content_id IN (...)` — removes reactions *on* the deleted user's memos.
   - `store/db/sqlite/user_delete.go:102` → `deleteReactionsByCreatorTx` (defined at `:400-403`): `DELETE FROM reaction WHERE creator_id = ?` — removes reactions the user *made*.
   - The same two functions exist for the other backends: `store/db/postgres/user_delete.go:96,102` (defs `:380`, `:400`) and `store/db/mysql/user_delete.go:96,102` (defs `:417`, `:437`).
   - Entry point is `(*DB).DeleteUser` at `store/db/sqlite/user_delete.go:29`, wrapped by `store/user.go:171` (`(*Store).DeleteUser`).

2. **No DB-level cascade** — the `reaction` table schema declares `creator_id INTEGER NOT NULL` with only a `UNIQUE` constraint and no `REFERENCES`/foreign key:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`

So without the explicit Go `DELETE` statements, a deleted user's reactions would be orphaned; the cleanup depends entirely on that code.

Note the two paths differ in scope: reactions *by* the user are deleted directly by `creator_id`, while reactions *by others on the user's memos* are deleted by `content_id`. Reactions the user placed are covered; a database constraint plays no role.
