In this codebase a user's profile image is **not** served by a dedicated image/binary endpoint. The avatar is stored as a data-URI string in the `user.avatar_url` column and returned inline in the `avatar_url` field of the gRPC/REST `GetUser` response. So a browser fetching another user's profile image issues `GET /api/v1/users/{username}` (the `AvatarUrl` field is then used directly as the `<img src>`), and that request flows down to storage as follows:

1. `GetUser` — server/router/api/v1/user_service.go:171 (serving handler; resolves the user, then converts)
2. `ResolveUserByName` — server/router/api/v1/user_resource_name.go:49 (parses username, calls the store)
3. `Store.GetUser` — store/user.go:148 (cache check, delegates to ListUsers)
4. `Store.ListUsers` — store/user.go:136 (calls the DB driver, caches results)
5. `DB.ListUsers` — store/db/sqlite/user.go:88 (builds `SELECT ... avatar_url ... FROM user`, scans into `user.AvatarURL`; MySQL/Postgres equivalents at store/db/mysql/user.go:84 and store/db/postgres/user.go:87)

The avatar bytes are then mapped back to the wire message by `convertUserFromStore` — server/router/api/v1/user_service_converters.go:16 (`AvatarUrl: user.AvatarURL`, line 25), which is what `GetUser` returns at user_service.go:180.

Data layer detail: the image data itself lives in the `avatar_url` column of the `user` table (SELECT/Scan of `avatar_url` ↔ `store.User.AvatarURL` in store/db/sqlite/user.go:158,183).
