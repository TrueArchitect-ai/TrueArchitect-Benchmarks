**Premise correction:** There is no Redis anywhere in this repository. Memos is a self-hosted Go application, and its cache layer is an **in-process, in-memory cache** — not a Redis-backed one. There is no Redis connection to configure (no `redis`/`ioredis` client, no connection string, no dependency in `go.mod`). The one grep hit for "redis" (`web/src/connect.ts`) is an unrelated false positive.

**Actual mechanism:**

- The cache is implemented as a thread-safe in-memory store in `store/cache/cache.go` — backed by a `sync.Map` with per-item expiration timestamps and a background cleanup goroutine (`cleanupLoop`). No external service; state lives in the process and is lost on restart.
- It is "configured" in `store/store.go:38-58`, where `Store.New` builds a single `cache.Config` and instantiates three separate caches: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). The config used (`store/store.go:40-45`) is:
  - `DefaultTTL: 10 * time.Minute`
  - `CleanupInterval: 5 * time.Minute`
  - `MaxItems: 1000`

  (This mirrors the package's `DefaultConfig()` at `store/cache/cache.go:57-64`.)

**TTL for user entries:** User records are written into `userCache` via `s.userCache.Set(...)` (e.g. `store/user.go:98, 122, 132, 143, 167`). `Set` delegates to `SetWithTTL` using the cache's `DefaultTTL` (`store/cache/cache.go:92-95`), so **user entries expire 10 minutes after they are written**. There is no user-specific TTL override — it inherits the single 10-minute `DefaultTTL` shared by all three caches. Expired entries are evicted lazily on `Get` (`store/cache/cache.go:135-144`) and swept periodically every 5 minutes by the cleanup goroutine.
