h05.

**Mechanism: explicit Go code.** When a user is deleted (memos uses a hard delete — there is no soft/purge distinction), their emoji reactions are removed by an explicit `DELETE FROM reaction WHERE creator_id = ?` inside the deletion transaction. There is **no** database-level foreign key, cascade, or trigger backing this up — the `reaction` table has no FK to `user`.

Evidence locations:

**1. Deletion entry point → store → per-driver driver**
- `server/router/api/v1/user_service.go:393` (`DeleteUser`) calls `s.Store.DeleteUser` (~line 414)
- `store/user.go:171` delegates to the DB driver
- Each driver's `DeleteUser` runs everything in one transaction via `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:29`, plus postgres/mysql equivalents)

**2. Explicit reaction deletion (the mechanism)** — `store/db/sqlite/user_delete.go`:
- Line 96 calls `deleteReactionsByContentIDsTx` — removes reactions *on* the deleted user's memos
- Line 102 calls `deleteReactionsByCreatorTx` — removes the user's *own* reactions:
  ```go
  // store/db/sqlite/user_delete.go:400
  func deleteReactionsByCreatorTx(ctx context.Context, tx *sql.Tx, userID int32) error {
      _, err := tx.ExecContext(ctx, `DELETE FROM reaction WHERE creator_id = `+deleteUserPlaceholder(1), userID)
      return err
  }
  ```
  Mirrored in `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`.

**3. No database rule** — `store/migration/sqlite/LATEST.sql:92-99`: the `reaction` table has only `creator_id INTEGER NOT NULL` and a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `REFERENCES user`, no `ON DELETE CASCADE`. The only cascade in the schema is `memo_share.memo_id → memo(id)` (line 109), unrelated to reactions. Same in the postgres/mysql `LATEST.sql` files (~line 91). So without the Go code, reactions would be orphaned.
