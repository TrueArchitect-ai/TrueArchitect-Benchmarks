A browser fetching another user's profile image hits `GET /file/users/:identifier/avatar`. The avatar is not a separate blob/file — it is stored inline as a base64 data URI in the user's `avatar_url` column, so the "data layer" hop is the user-row read from the database.

Hops from serving handler down to stored data:

- `RegisterRoutes` (registers `GET /file/users/:identifier/avatar` → `serveUserAvatar`) — server/router/fileserver/fileserver.go:124
- `serveUserAvatar` (handler; looks up user, then decodes `user.AvatarURL` and writes it) — server/router/fileserver/fileserver.go:168
- `getUserByUsername` (`s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`) — server/router/fileserver/fileserver.go:715
- `Store.GetUser` (cache check, then delegates to ListUsers) — store/user.go:148
- `Store.ListUsers` (`s.driver.ListUsers(...)`) — store/user.go:136
- `DB.ListUsers` (driver; runs `SELECT ... avatar_url ... FROM user WHERE username = ?` and scans the row — this is the read of stored data) — store/db/sqlite/user.go:88 (equivalents: store/db/postgres/user.go:87, store/db/mysql/user.go:84)

Back in the handler, the stored `avatar_url` data URI is turned into bytes by `parseDataURI` (server/router/fileserver/fileserver.go:737) and returned via `c.Blob` (fileserver.go:209).

Note: the stored value is the `avatar_url` column of the `user` table; it holds a `data:<mime>;base64,...` URI rather than a reference to attachment/file/S3 storage.
