**Premise correction:** There is no Redis anywhere in this repository. A search for `redis`/`ioredis`/connection strings across all source, config, and env files returns nothing. The premise that the cache layer is backed by Redis is incorrect.

**Actual mechanism:** The cache layer is a hand-rolled, in-process, thread-safe in-memory cache — no external cache server, no network connection to configure.

- The cache implementation lives in `store/cache/cache.go`. It's a `Cache` struct backed by a `sync.Map` with per-item expiration timestamps and a background `cleanupLoop` goroutine (`store/cache/cache.go:66-90`, `:199-250`). "Configuration" here means passing a `cache.Config` struct, not a connection — there is no host/port/DSN.
- The caches are instantiated in `store/store.go:47-53`, where `New()` builds three separate in-memory caches (`instanceSettingCache`, `userCache`, `userSettingCache`), each from the same `cacheConfig` defined at `store/store.go:40-45`.

**TTL for user entries:** User records are written to `userCache` via `s.userCache.Set(...)` in `store/user.go` (e.g. lines 98, 122, 132, 143, 167). `Set` (as opposed to `SetWithTTL`) always uses the cache's `DefaultTTL` — see `store/cache/cache.go:92-95`. That `DefaultTTL` is configured to **10 minutes** in `store/store.go:41` (`DefaultTTL: 10 * time.Minute`), with expired entries swept every 5 minutes by the cleanup interval (`store/store.go:42`) or lazily evicted on read (`store/cache/cache.go:135-144`). So user entries expire 10 minutes after they are cached.

(Note: `store/cache/cache.go:57-64` defines an identical `DefaultConfig()` of 10 min TTL / 5 min cleanup / 1000 max items, but the store does not use it — it constructs its own equivalent `cacheConfig` inline.)
