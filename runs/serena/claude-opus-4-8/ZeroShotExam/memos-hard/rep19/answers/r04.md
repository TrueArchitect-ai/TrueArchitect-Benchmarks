**Premise correction:** The question assumes the webhook delivery workers consume from an external message broker (NATS or RabbitMQ). Neither is used. This repository (the `usememos/memos` codebase) has **zero** references to NATS, RabbitMQ, JetStream, AMQP, or Kafka anywhere in `.go`, `go.mod`, or `go.sum`.

**Actual mechanism:** Webhook delivery is entirely **in-process**, using a buffered Go channel plus a fixed pool of goroutine workers, all in `internal/webhook/webhook.go`:

- **"Queue" declaration** — a buffered channel of capacity 128, at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- **Consumers** — 4 goroutines spawned in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over that channel and dispatching via HTTP (`Post`).
- **Producer** — `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking send onto the channel, dropping the payload if the buffer is full.

Producers of these payloads are the API handlers in `server/router/api/v1/memo_service_webhooks.go` and `server/router/api/v1/user_service_webhooks.go`.

So there is no NATS subject/stream or AMQP queue to point to — delivery is a self-contained goroutine worker pool with an in-memory channel as the "queue."
