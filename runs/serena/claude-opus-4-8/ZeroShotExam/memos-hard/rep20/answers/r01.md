**Premise correction:** There is no Redis anywhere in this repository. The cache layer is not backed by Redis (or any external cache store) — the premise of a "Redis connection" doesn't apply.

**Actual mechanism:** The cache is a custom, in-process, thread-safe in-memory cache implemented in Go at `store/cache/cache.go`. It stores entries in a `sync.Map` with per-item expiration timestamps and a background cleanup goroutine (`cleanupLoop`) — no network connection or external service is involved.

There is no single "user cache TTL" configured specially; user entries use the store's default cache config:

- The store creates a dedicated `userCache` (plus `userSettingCache` and `instanceSettingCache`), each via `cache.New(cacheConfig)` in `store/store.go:47-53`. The `userCache` field is declared at `store/store.go:28`.
- That shared `cacheConfig` is defined inline in `Store.New` at `store/store.go:40-45` with `DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`.
- User entries are written with `Set` (`store/user.go`, e.g. around line 151 for reads), which applies the default TTL via `SetWithTTL(..., c.config.DefaultTTL)` at `store/cache/cache.go:92-95`.

**So: user entries have a 10-minute TTL**, coming from the store's `DefaultTTL` (`store/store.go:41`), not from any Redis configuration. This 10-minute default is also mirrored in `cache.DefaultConfig()` at `store/cache/cache.go:57-64`, though the store supplies its own explicit config rather than calling that.
