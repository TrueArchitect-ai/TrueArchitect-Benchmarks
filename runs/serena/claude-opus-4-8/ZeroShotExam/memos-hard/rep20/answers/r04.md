**Premise correction:** The question's premise is false on both counts — the webhook delivery workers consume from *neither* NATS nor RabbitMQ. This repository (memos, a Go project) has **no external message broker at all**. A grep of `go.mod`/`go.sum` for `nats-io`, `rabbitmq`, `streadway`, `amqp091`, `kafka`, and `sarama` returns nothing.

**Actual mechanism:** Webhook delivery is entirely in-process. The "queue" is a bounded buffered Go channel and the "workers" are goroutines — all in `internal/webhook/webhook.go`:

- **Queue declaration** — `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (capacity-128 in-memory channel, not a broker subject/stream/queue).
- **Workers (consumers)** — `internal/webhook/webhook.go:42-55`: an `init()` spawns 4 goroutines, each ranging over `asyncPostQueue` and delivering the payload via `Post()`.
- **Producer (enqueue)** — `internal/webhook/webhook.go:184-196`: `PostAsync` does a non-blocking send onto the same channel, dropping if the buffer is full.
- **Delivery** — `Post()` at `internal/webhook/webhook.go:120-180` marshals to JSON and makes a direct outbound HTTP POST (SSRF-guarded, optional HMAC-SHA256 signing). No broker consume is involved.

So: 4 goroutines consuming from the in-process buffered channel `asyncPostQueue`, declared at `internal/webhook/webhook.go:39`.

(For completeness, the `SSEHub` in `server/router/api/v1/sse_hub.go` is an in-memory SSE fan-out — pub/sub-looking naming but unrelated to webhooks and still not a broker.)
