**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed programmatically inside the `DeleteUser` transaction — there is no database-level cascade rule.

**Evidence:**

1. **Deletion orchestration** — `store/db/sqlite/user_delete.go` `deleteUserTargetsTx` (mirrored in `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go`) explicitly calls two reaction-removal steps within the delete transaction:
   - `deleteReactionsByContentIDsTx(...)` — removes reactions on the deleted user's own memos (line ~96)
   - `deleteReactionsByCreatorTx(...)` — removes reactions the user made on any content (line ~102)

2. **The actual SQL** (`store/db/sqlite/user_delete.go:380-403`):
   - `DELETE FROM reaction WHERE content_id IN (...)` (reactions on the user's memos)
   - `DELETE FROM reaction WHERE creator_id = ?` (reactions authored by the user)

3. **No DB-level rule.** The `reaction` table schema has no foreign key or `ON DELETE CASCADE` on `creator_id` — `store/migration/sqlite/LATEST.sql:92`, `store/migration/postgres/LATEST.sql:91`, `store/migration/mysql/LATEST.sql:91` (and the original `0.20/00__reaction.sql` files). `creator_id` is just an `INTEGER NOT NULL` column with a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no FK, so nothing cascades automatically.

The top-level entry point is `store/user.go:171` `DeleteUser`, which delegates to the per-driver `DeleteUser` implementations above.
