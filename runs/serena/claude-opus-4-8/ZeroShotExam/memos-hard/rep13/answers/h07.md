The browser hits `GET /file/users/:identifier/avatar`. The avatar image is not a separate blob/file — it is stored inline in the `user` table's `avatar_url` column as a base64 `data:` URI, which the handler decodes and serves. Full trace from serving handler to stored data:

1. `serveUserAvatar` — server/router/fileserver/fileserver.go:168 *(route registered at fileserver.go:124: `fileGroup.GET("/users/:identifier/avatar", ...)`)*
2. `getUserByUsername` — server/router/fileserver/fileserver.go:715
3. `(*Store).GetUser` — store/user.go:148
4. `(*Store).ListUsers` — store/user.go:136
5. `(*DB).ListUsers` (driver, `SELECT ... avatar_url ... FROM user`) — store/db/sqlite/user.go:88 *(equivalents: store/db/postgres/user.go, store/db/mysql/user.go)*

Then back in the handler, the stored value is turned into image bytes:
- `parseDataURI(user.AvatarURL)` decodes the base64 `data:` URI — server/router/fileserver/fileserver.go:196 / 737
- `c.Blob(...)` writes the decoded bytes — server/router/fileserver/fileserver.go:209

So the "stored data" is the `avatar_url` column of the `user` row (a base64 data URI), not an attachment file on disk/S3.
