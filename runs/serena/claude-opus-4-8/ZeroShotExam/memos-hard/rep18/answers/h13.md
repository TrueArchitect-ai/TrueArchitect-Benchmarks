**impl** — The interface is `markdown.Service` (`internal/markdown/markdown.go:31`). The single concrete implementation that runs at runtime is the unexported struct `service` (`internal/markdown/markdown.go:57-60`), which wraps a `goldmark.Markdown` engine. Its `RenderMarkdown`/`RenameTag` methods internally delegate to a helper concrete type `renderer.MarkdownRenderer` (`internal/markdown/renderer/markdown_renderer.go:15`), but that helper sits *inside* the impl, not behind the `Service` interface. There is no separate production vs. mock implementation — tests use the same real `service`.

**construction** — Built via the factory `markdown.NewService(...)` (`internal/markdown/markdown.go:85`), which returns `&service{md: ...}`. It is constructed once in production inside `NewAPIV1Service` (`server/router/api/v1/v1.go:48-51`) with `WithTagExtension()` and `WithMentionExtension()`. That single instance is then shared to the other holders — passed to the RSS service in `server/server.go:85` and to `memopayload.RebuildMemoPayload` in `server/router/api/v1/memo_service.go:108,447`. (Tests separately construct one in `server/router/api/v1/test/test_helper.go:44`.) The internal `renderer.NewMarkdownRenderer()` is `new`-constructed on demand inside the impl's render methods (`internal/markdown/markdown.go:250,451`).

**holders** — Three components hold the `markdown.Service` interface:
- `APIV1Service.MarkdownService` field — `server/router/api/v1/v1.go:35`
- `memopayload.Runner.MarkdownService` field, plus the `NewRunner`/`RebuildMemoPayload` parameters — `server/runner/memopayload/runner.go:16,19,74`
- `rss.RSSService.MarkdownService` field, plus `NewRSSService` parameter — `server/router/rss/rss.go:45,58`
