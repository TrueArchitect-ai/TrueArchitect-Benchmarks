**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction ...` statements run inside each database driver's `DeleteUser` transaction. There is **no** database-level rule — the `reaction` table has no foreign key to `user`, no `ON DELETE CASCADE`, and no SQL trigger.

Reactions are cleaned up in two ways within that transaction: (1) reactions the user authored (`WHERE creator_id = ?`), and (2) reactions on the deleted user's memos (`WHERE content_id IN (...)`, where `content_id = "memos/"+memo.UID`).

**Evidence — deletion code path**
- `store/db/sqlite/user_delete.go:92-127` — `deleteUserTargetsTx` orchestrates deletes; line 96 calls `deleteReactionsByContentIDsTx` (reactions *on* the user's memos), line 102 calls `deleteReactionsByCreatorTx` (reactions *by* the user).
- `store/db/sqlite/user_delete.go:380-388` — `deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)`.
- `store/db/sqlite/user_delete.go:400-403` — `deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = ?`.
- Same logic in the other drivers: `store/db/postgres/user_delete.go:96,102` (deletes at `:380-388`, `:400-403`) and `store/db/mysql/user_delete.go:96,102` (deletes at `:417-425`, `:437-440`).
- Upstream delegation with no reaction logic of its own: `store/user.go:171-181` (`Store.DeleteUser`) and `server/router/api/v1/user_service.go:393` (RPC handler).

**Evidence — reaction store has no per-user delete**
- `store/reaction.go:39-41` — `DeleteReaction` deletes only a single reaction by ID; there is no `DeleteByCreator`/`PermanentDeleteByUser` method. Driver impls (`store/db/sqlite/reaction.go:133-135`, plus postgres/mysql equivalents) are `DELETE ... WHERE id = ?` only. So the per-user cleanup is inlined in `user_delete.go`, not in the reaction store.

**Evidence — schema/migrations confirm no DB-level rule**
- The `reaction` table has only a primary key and `UNIQUE(creator_id, content_id, reaction_type)` — no FK, so no cascade; `creator_id` is a plain `INTEGER`: `store/migration/sqlite/LATEST.sql:92-99` (and postgres/mysql `LATEST.sql:91-98`); original `store/migration/sqlite/0.20/00__reaction.sql:2-9`.
- `ON DELETE CASCADE` on `user(id)` exists for *other* tables (`user_setting`, `memo`, `shortcut`, `resource`) at `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql:59,98,125,167,204` — but not for `reaction`.
- Triggers exist only for `*_modification_time` updates (`store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql:32,73,139,181`; `0.6/00__recreate_triggers.sql`); a search for `TRIGGER` + `reaction` found nothing.
- Other reaction migrations are data backfills only (`store/migration/{sqlite,postgres,mysql}/0.23/00__reactions.sql`), not constraints.

Bottom line: if those explicit Go `DELETE` statements were removed, a deleted user's reactions would be left orphaned — the DB would not clean them up.
