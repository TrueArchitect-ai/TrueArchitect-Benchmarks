**Mechanism: explicit Go code.** When a user is permanently deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the delete-user transaction — not by any database-level cascade rule. There are actually **two** explicit deletions: reactions the user *created*, and reactions on content (memos) the user *owned*.

## Evidence

**Orchestration** — `deleteUserTargetsTx` in `store/db/sqlite/user_delete.go:92-127` explicitly calls both reaction deletions during the transaction:
- `deleteReactionsByContentIDsTx(...)` at line 96 — removes reactions on the deleted user's memos
- `deleteReactionsByCreatorTx(...)` at line 102 — removes reactions the user made on any content

**The actual DELETE statements** (`store/db/sqlite/user_delete.go`):
- `deleteReactionsByContentIDsTx`, lines 380-388: `DELETE FROM reaction WHERE content_id IN (...)`
- `deleteReactionsByCreatorTx`, lines 400-403: `DELETE FROM reaction WHERE creator_id = ?`

**Same logic in the other two DB drivers** (confirming it's driver-side Go, not a DB rule):
- `store/db/postgres/user_delete.go:96, 102, 380-403`
- `store/db/mysql/user_delete.go:96, 102, 417-438`

**Entry point:** `store/user.go:171` `DeleteUser` → `s.driver.DeleteUser` (interface at `store/driver.go:48`), dispatching to the driver implementations above.

**No DB-level cascade exists.** The `reaction` table schema declares only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and no foreign key / `ON DELETE CASCADE`:
- `store/migration/postgres/0.20/00__reaction.sql:1-9` (full table def — `creator_id INTEGER NOT NULL`, no FK)
- Same in `store/migration/sqlite/0.20/00__reaction.sql:8`, `store/migration/mysql/0.20/00__reaction.sql:8`, and the `LATEST.sql` files for all three engines.

So reaction cleanup depends entirely on the Go code above; if that code were removed, orphaned reactions would remain since the schema wouldn't cascade them.
