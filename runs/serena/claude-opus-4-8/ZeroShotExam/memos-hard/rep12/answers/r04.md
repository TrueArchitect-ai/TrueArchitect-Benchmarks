**Premise correction:** The question assumes a false binary — the webhook delivery workers consume from *neither* NATS *nor* RabbitMQ. Neither broker exists anywhere in the repository. A case-insensitive grep for `nats`, `rabbitmq`, `amqp`, `jetstream`, `kafka`, `redis` across Go source, `go.mod`, and `go.sum` returns zero matches (the only stray "nats" substring is inside an unrelated translation string in `web/src/locales/ca.json`).

**Actual mechanism:** Webhook delivery is entirely in-process, backed by a buffered Go channel drained by a fixed pool of goroutine workers — no external message broker at all.

- The "queue" is declared as a buffered channel (capacity 128) at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
- It's consumed by 4 worker goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over the channel and calling `Post()`.
- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), using a non-blocking `select`/`default` that **drops** the payload with a warning if the buffer is full.
- `Post()` (`internal/webhook/webhook.go:119-180`) does the real work: an outbound HTTP POST via a shared client with SSRF protection and optional HMAC-SHA256 "Standard Webhooks" signing.
- Enqueue call sites are in `server/router/api/v1/memo_service_webhooks.go` (e.g. lines 43, 71) on memo/comment events.

Consequence worth noting: because this is an in-memory channel rather than a durable broker, pending webhook payloads are lost on process restart or on buffer overflow.
