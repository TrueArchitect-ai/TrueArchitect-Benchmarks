**Mechanism: explicit Go code** (not a database-level cascade). When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the delete-user transaction — in two ways: reactions the user *created* (`creator_id = ?`) and reactions on the user's own content/memos (`content_id IN (...)`).

Evidence locations:

- **Orchestration** — `deleteUserTargetsTx` calls both `deleteReactionsByContentIDsTx` and `deleteReactionsByCreatorTx` within the transaction: `store/db/mysql/user_delete.go:96,102` (and identically `store/db/sqlite/user_delete.go:96,102`, `store/db/postgres/user_delete.go:96,102`).
- **The actual reaction deletes**:
  - By content ID (user's memos): `store/db/mysql/user_delete.go:417-420` → `DELETE FROM reaction WHERE content_id IN (...)` (mirrored at `store/db/sqlite/user_delete.go:380-383`, `store/db/postgres/user_delete.go:380-383`).
  - By creator (user's own reactions): `store/db/mysql/user_delete.go:437-438` → `DELETE FROM reaction WHERE creator_id = ?` (mirrored at `store/db/sqlite/user_delete.go:400-401`, `store/db/postgres/user_delete.go:400-401`).
- **No DB-level rule exists** — the `reaction` table has no foreign key or `ON DELETE CASCADE`; it just has plain `creator_id`/`content_id` columns and a uniqueness constraint: `store/migration/postgres/LATEST.sql:90-98` (same in `store/migration/sqlite/LATEST.sql:91-98` and `store/migration/mysql/LATEST.sql:90-97`). So removal depends entirely on the explicit Go code above.
