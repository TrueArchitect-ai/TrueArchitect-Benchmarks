**Premise correction: neither. The webhook delivery workers do not consume from NATS, RabbitMQ, or any external message broker.** There is no AMQP/NATS client in the codebase (no such imports in the Go sources), and no queue is "declared" on a broker. The "queue" is an in-process buffered Go channel.

**Actual mechanism** (all in `internal/webhook/webhook.go`):
- The queue is a plain buffered channel with capacity 128: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — declared at `internal/webhook/webhook.go:39`.
- The workers are 4 goroutines started in the package `init()` (`internal/webhook/webhook.go:42-55`); each ranges over `asyncPostQueue` and calls `Post` to perform the actual HTTP delivery (`webhook.go:46`, delivery in `Post` at `webhook.go:120`/`safeClient.Do` at `:152`).
- Producers enqueue via `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking send onto `asyncPostQueue`; if the channel buffer is full, the dispatch is **dropped** with a warning (`webhook.go:189-195`) rather than being persisted or retried by any broker.

So delivery is handled entirely in-memory within the server process — an ephemeral, bounded, at-most-once channel-based worker pool — with no external broker and no durable queue.
