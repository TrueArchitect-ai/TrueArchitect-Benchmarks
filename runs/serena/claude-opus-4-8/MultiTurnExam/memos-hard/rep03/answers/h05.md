**Mechanism: explicit Go code.** A user's emoji reactions are removed by explicit `DELETE FROM reaction` statements inside the `DeleteUser` transaction — there is no database-level cascade for reactions.

Evidence locations (what I checked):

1. **Schema — no DB-level rule.** The `reaction` table has `creator_id INTEGER NOT NULL` with **no foreign key / `ON DELETE CASCADE`** on it in any driver:
   - `store/migration/postgres/LATEST.sql:91` (reaction table, `creator_id` at `:94`, only a `UNIQUE` constraint)
   - `store/migration/sqlite/LATEST.sql` (reaction table, same shape)
   - `store/migration/mysql/LATEST.sql` (`` `reaction` `` table, same shape)
   So the database will not delete reactions on its own when a user row goes away.

2. **Explicit Go deletion in the DeleteUser transaction.** `Store.DeleteUser` (`store/user.go:171`) delegates to the driver's `DeleteUser`, and each driver's `user_delete.go` explicitly deletes reactions inside the transaction, calling two helpers:
   - `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ...` (removes reactions the deleted user *made*)
   - `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN ...` (removes reactions on the deleted user's content)

   Present identically in all three drivers:
   - `store/db/postgres/user_delete.go:96,102` (helpers at `:380`, `:400–401`)
   - `store/db/mysql/user_delete.go:96,102` (helpers at `:417`, `:437–438`)
   - `store/db/sqlite/user_delete.go:96,102` (helpers at `:380`, `:400–401`)
