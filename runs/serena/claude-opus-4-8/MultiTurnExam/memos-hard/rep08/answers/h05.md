**Mechanism: explicit Go code.** The `reaction` table has no foreign key or `ON DELETE CASCADE` on `creator_id`, so nothing at the DB level removes a deleted user's reactions — they are deleted explicitly inside the `DeleteUser` transaction.

Evidence locations:

- **Schema shows no DB-level rule.** In all three drivers' `LATEST.sql`, the `reaction` table declares only a `UNIQUE(creator_id, content_id, reaction_type)` constraint with no `FOREIGN KEY` / `ON DELETE CASCADE` on `creator_id`:
  - `store/migration/sqlite/LATEST.sql:92-99`
  - `store/migration/postgres/LATEST.sql:91-98`
  - `store/migration/mysql/LATEST.sql:91-98`
  (Contrast with e.g. `memo_share`, which does declare `FOREIGN KEY (memo_id) ... ON DELETE CASCADE` at `store/migration/sqlite/LATEST.sql:109`.)

- **Explicit Go deletion in the delete-user transaction.** In `store/db/sqlite/user_delete.go`, `deleteUserTargetsTx` runs two reaction deletes:
  - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/sqlite/user_delete.go`, called at the `deleteReactionsByCreatorTx(ctx, tx, userID)` step) removes reactions the deleted user made.
  - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` also removes reactions left on the user's own memos.
  - These are wired into `DeleteUser` via `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go`). The Postgres and MySQL drivers have equivalent `user_delete.go` files (`store/db/postgres/user_delete.go`, `store/db/mysql/user_delete.go`).

So a deleted user's emoji reactions are removed by explicit Go code (`DELETE FROM reaction WHERE creator_id = ?`), not by a database cascade.
