**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by explicit `DELETE FROM reaction` statements issued inside the delete-user transaction — not by a database FK/cascade rule.

Two distinct removals run per driver, both inside `deleteUserTargetsTx`:
- `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` — reactions the deleted user *made*.
- `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` — reactions *on the deleted user's memos* (content IDs of the form `memos/{uid}`, gathered via the recursive memo tree).

What I checked:
- **SQLite** driver: orchestration `store/db/sqlite/user_delete.go:96` and `:102`; implementations at `store/db/sqlite/user_delete.go:380-388` (by content ID) and `:400-403` (by creator).
- **Postgres** driver: `store/db/postgres/user_delete.go:96,102` and `:380,:400-401`.
- **MySQL** driver: `store/db/mysql/user_delete.go:96,102` and `:417,:437-438`.
- Store-level wrapper `store/user_delete.go` (defines `DeleteUser` result/cache handling; delegates the actual deletes to the driver) — no cascade logic there.

All three drivers issue the same explicit statements within a single transaction (`BeginTx` … `Commit`), so removal does not rely on a database-level cascade.
