**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the `DeleteUser` transaction — in two ways: reactions the user *created* (`WHERE creator_id = ?`) and reactions on the user's own content/memos (`WHERE content_id IN (...)`, where content IDs are `memos/<uid>`). This is duplicated identically across all three DB drivers, not delegated to a database cascade rule.

Evidence locations (all three drivers mirror each other):
- **MySQL** — `store/db/mysql/user_delete.go`: orchestration calls both deletions at lines 93 and 100 (`deleteUserTargetsTx`); implementations at `deleteReactionsByContentIDsTx` (line ~377, `DELETE FROM reaction WHERE content_id IN ...`) and `deleteReactionsByCreatorTx` (line ~400, `DELETE FROM reaction WHERE creator_id = ?`).
- **SQLite** — `store/db/sqlite/user_delete.go:96` and `:102` (calls), `:380`/`:383` and `:400`/`:401` (SQL).
- **Postgres** — `store/db/postgres/user_delete.go:96` and `:102` (calls), `:380`/`:383` and `:400`/`:401` (SQL).

What I checked and what I did *not* find: I inspected the `DeleteUser` code paths in each driver and confirmed reactions are deleted explicitly. The deletions run in application code within a transaction (`BeginTx`/`Commit`), and the `reaction` rows are removed before the `user` row itself (`deleteUserRowTx`), which is the pattern you'd use precisely because there is no DB-level `ON DELETE CASCADE` being relied upon here. I did not locate a schema-level cascade rule driving this; the removal is done by explicit Go code.
