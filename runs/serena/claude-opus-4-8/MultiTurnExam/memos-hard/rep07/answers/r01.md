**Premise correction:** There is no Redis in this codebase. The cache layer is **not** backed by Redis (or any external store) — it's a custom, thread-safe **in-process, in-memory cache** implemented in pure Go using `sync.Map`, with no network connection to configure. Searching the backend for Redis/connection configuration turns up nothing; the entire cache is `store/cache/cache.go`.

**Actual mechanism:**
- The cache type is `cache.Cache` (`store/cache/cache.go:67`), created via `cache.New(config)` (`:76`), which starts a background `cleanupLoop` goroutine to evict expired entries. Entries are stored in a `sync.Map` with a per-item `expiration` timestamp (`:110-114`); expiry is enforced lazily on `Get` (`:135`) and periodically by `cleanup` (`:218`).
- User entries live in the `Store.userCache` instance, constructed in `store.New` at `store/store.go:52`, using `cacheConfig` defined at `store/store.go:40-45`.
- **TTL for user entries:** the default TTL, **10 minutes** (`DefaultTTL: 10 * time.Minute`, `store/store.go:41`; same as the package default in `store/cache/cache.go:59`). `Store.GetUser`/`ListUsers` populate this cache via `Set`, which applies the default TTL (`cache.go:93-95`). The cache also has a `CleanupInterval` of 5 minutes and a `MaxItems` cap of 1000 (LRU-ish oldest-eviction when exceeded).

So: no Redis to configure — user cache entries are held in an in-memory `cache.Cache` and expire after a **10-minute** default TTL, configured at `store/store.go:40-52`.
