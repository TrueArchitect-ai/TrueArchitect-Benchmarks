h15. Memo visibility is enforced at these distinct server surfaces:

Single-memo read (gRPC/Connect `GetMemo`) — `server/router/api/v1/memo_service.go:55-63`
Memo list read (`ListMemos` visibility filter) — `server/router/api/v1/memo_service.go:219-225`
Memo relations read (`memoFilter` on related memos) — `server/router/api/v1/memo_relation_service.go:109-111`
User memo stats read — `server/router/api/v1/user_service_stats.go:84-90` and `:218-220`
Reactions (create/list gated by linked memo visibility) — `server/router/api/v1/reaction_service.go:30-38` and `:83`
Attachment access via API (linked-memo visibility rules) — `server/router/api/v1/attachment_service.go:445-451`
File server (attachment blob/stream serving) — `server/router/fileserver/fileserver.go:677` and `:699`
RSS feed (public-only) — `server/router/rss/rss.go:90` and `:141`
Frontend SSR/meta rendering (public-only) — `server/router/frontend/frontend.go:150`
SSE real-time delivery filtering (`canReceive`) — `server/router/api/v1/sse_hub.go:135-141`

Note: the API v1 read paths (`memo_service.go`, `memo_relation_service.go`, `user_service_stats.go`) ultimately push the visibility predicate down into the store query (`VisibilityList` / CEL `visibility in [...]` filter), while the fileserver, RSS, frontend, reaction, attachment, and SSE surfaces each enforce it with their own independent checks.
