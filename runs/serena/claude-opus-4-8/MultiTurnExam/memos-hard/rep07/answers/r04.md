**Premise correction:** Neither. The webhook delivery workers do not consume from any external message broker — there is no NATS, no RabbitMQ, and no AMQP/message-queue client anywhere in the codebase. A search of the backend for such brokers turns up nothing.

**Actual mechanism:** Webhook delivery uses a purely **in-process buffered Go channel** as the queue, all within `internal/webhook/webhook.go`:
- The "queue" is a package-level buffered channel with capacity 128: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`).
- The "workers" are 4 goroutines started in `init()`, each ranging over that channel and calling `Post` for every payload (`internal/webhook/webhook.go:42-55`).
- Producers enqueue via `PostAsync`, a non-blocking send with a `default` drop-if-full case (logs "async queue is full" and discards) (`internal/webhook/webhook.go:184-196`).
- The actual HTTP delivery happens in `Post`, which sends the request via the SSRF-guarded `safeClient` (`internal/webhook/webhook.go:120`, send at `:152`).

Because the queue lives entirely in memory within the single server process, it is not durable — pending webhooks are lost on restart, and overflow beyond 128 queued items is dropped. So the delivery pipeline is an in-memory channel + goroutine worker pool, not a NATS/RabbitMQ consumer.
