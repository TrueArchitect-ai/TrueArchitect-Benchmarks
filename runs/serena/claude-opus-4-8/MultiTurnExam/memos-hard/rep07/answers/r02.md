**Premise correction:** There is no per-user API rate-limiting middleware in this codebase — so there's no registration site or request-limit numbers to cite. A search of the server and internal packages for any rate-limiter, throttle, limiter, or `429`/"too many requests" handling turns up nothing implemented (the only hit is an aspirational comment about email sending in `internal/email/doc.go:86`).

What actually protects the API is a different, non-rate-based set of middleware/interceptors. The Connect/gRPC chain registered in `server/router/api/v1/v1.go:133-138` consists of:
- `NewMetadataInterceptor` (HTTP-header → gRPC-metadata)
- `NewLoggingInterceptor`
- `NewRecoveryInterceptor` (panic recovery)
- `NewAuthInterceptor` (authentication/authorization)

The only request-volume-related limit is a **request body size cap**, not a rate limit: `maxAPIRequestBytes` applied via `connect.WithReadMaxBytes` and `http.MaxBytesHandler` (`server/router/api/v1/v1.go:141` and `:144`). At the Echo layer the only global middleware are `Recover()` and CORS (`server/server.go:51-52`, `server/cors.go`). None of these enforce per-user (or per-IP) request-count/rate limits.
