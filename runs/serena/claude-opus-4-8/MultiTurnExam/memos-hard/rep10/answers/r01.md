**Premise correction:** There is no Redis anywhere in this project — no `redis` import in any `.go` file and no redis dependency in `go.mod`. The cache layer is an in-process, in-memory cache, not a Redis-backed one, so there is no "Redis connection" to configure.

**Actual mechanism:**
- The cache is a custom in-memory implementation in `store/cache/cache.go` (a `Cache` struct backed by a map + background cleanup goroutine; interface at `store/cache/cache.go:10`).
- It is instantiated in `store.New` (`store/store.go:38`), which builds a single `cache.Config` (`store/store.go:40-45`) and creates three caches with it — `instanceSettingCache`, **`userCache`**, and `userSettingCache` (`store/store.go:51-53`). There's no connection string/host config; it's purely local.
- **TTL for user entries:** user entries are written via `userCache.Set(...)` (e.g. `store/user.go:98,122,132,143,167`). `Set` applies the cache's default TTL, and the config's `DefaultTTL` is **10 minutes** (`store/store.go:41`, matching `cache.DefaultConfig()` at `store/cache/cache.go:~58`). The cache also runs a cleanup sweep every 5 minutes (`CleanupInterval`) and caps at 1000 items. No code path uses `SetWithTTL` for users, so the effective user-entry TTL is the default **10 minutes**.
