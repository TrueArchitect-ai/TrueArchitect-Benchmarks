Each hop from the browser's `GET /file/users/{identifier}/avatar` down to stored data:

- `GET /users/:identifier/avatar` route → `s.serveUserAvatar` — server/router/fileserver/fileserver.go:124
- `serveUserAvatar` (handler; auth-gates, then reads `user.AvatarURL`) — server/router/fileserver/fileserver.go:168
- `getUserByUsername` (wraps a `FindUser{Username}` lookup) — server/router/fileserver/fileserver.go:715
- `Store.GetUser` (cache check, then delegates) — store/user.go:148
- `Store.ListUsers` (delegates to driver) — store/user.go:136
- `(*DB).ListUsers` (driver: builds SQL against the `user` table, the data layer) — store/db/sqlite/user.go:88 (with parallel driver impls in store/db/postgres/user.go and store/db/mysql/user.go)

The image bytes themselves live in the returned `user.AvatarURL` as a base64 data URI, which the handler decodes via `s.parseDataURI(user.AvatarURL)` (server/router/fileserver/fileserver.go:196) before writing them with `c.Blob(...)` (fileserver.go:209).
