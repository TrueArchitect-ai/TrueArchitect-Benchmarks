**Mechanism: explicit Go code.** A user's emoji reactions are removed by hand-written `DELETE FROM reaction` statements inside the `DeleteUser` transaction — there is no database-level cascade (the `reaction` table has no foreign keys).

Evidence locations:
- `store/db/sqlite/user_delete.go:102` — `deleteUserTargetsTx` calls `deleteReactionsByCreatorTx(ctx, tx, userID)`, whose body (`user_delete.go:400-403`) runs `DELETE FROM reaction WHERE creator_id = ?`. This removes reactions the deleted user *authored*.
- `store/db/sqlite/user_delete.go:96` — the same function also calls `deleteReactionsByContentIDsTx(...)` (defined at `user_delete.go:380`), which deletes reactions *on the deleted user's own memos* (by content_id). So both the user's outgoing reactions and reactions others left on their content are explicitly removed.
- Parallel implementations exist for the other drivers: `store/db/postgres/user_delete.go` and `store/db/mysql/user_delete.go` (both with `deleteReactionsByCreatorTx` / `deleteReactionsByContentIDsTx` invoked from `deleteUserTargetsTx`).
- The schema confirms there is **no** DB-level rule doing this: `store/migration/sqlite/LATEST.sql` defines `CREATE TABLE reaction (...)` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint and no `FOREIGN KEY ... ON DELETE CASCADE` (same in the postgres/mysql `LATEST.sql`). Cleanup therefore depends entirely on the Go code above.

The behavior is also asserted by the test `TestDeleteUserCleansRelatedData` in `store/test/user_delete_test.go`.
