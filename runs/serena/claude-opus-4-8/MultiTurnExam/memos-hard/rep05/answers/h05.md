**Mechanism: explicit Go code.** When a user is deleted, their emoji reactions are removed by hand-written `DELETE FROM reaction` SQL executed inside the delete-user transaction — not by a DB cascade rule, and definitely not "not at all." The code deletes reactions two ways: those the user *authored* (`creator_id = user`) and those on content the user *owned* (`content_id IN` the user's memos).

Evidence locations (all three driver implementations mirror each other):
- **SQLite:** `store/db/sqlite/user_delete.go`
  - `deleteUserTargetsTx` invokes both `deleteReactionsByContentIDsTx` (line 96) and `deleteReactionsByCreatorTx` (line 102).
  - `deleteReactionsByContentIDsTx` runs `DELETE FROM reaction WHERE content_id IN ...` (line 383).
  - `deleteReactionsByCreatorTx` runs `DELETE FROM reaction WHERE creator_id = ?` (line 401).
- **Postgres:** `store/db/postgres/user_delete.go:383` and `:401` — same two `DELETE FROM reaction` statements.
- **MySQL:** `store/db/mysql/user_delete.go:420` and `:438` — same two `DELETE FROM reaction` statements.

Entry path that reaches this code: `DeleteUser` in each driver (`store/db/sqlite/user_delete.go:29`, etc.) begins a transaction, calls `collectDeleteUserTargets`, then `deleteUserTargetsTx`, which performs the reaction deletes before commit. The store-level `Store.DeleteUser` (`store/user.go:171`) and the API handler `APIV1Service.DeleteUser` (`server/router/api/v1/user_service.go:393`) sit above it.

What I checked and ruled out: I grepped every `user_delete.go` for `reaction` (explicit statements found in all three drivers), read the SQLite `DeleteUser`/`deleteUserTargetsTx` flow to confirm the functions are actually called within the transaction, and found no reliance on a schema-level `ON DELETE CASCADE` for reactions — the removal is done explicitly in Go.
