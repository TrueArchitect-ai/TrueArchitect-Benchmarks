**Premise correction:** Neither — there is no external message broker involved. A repo-wide search finds no NATS, RabbitMQ, AMQP, Kafka, or any broker client in the Go sources. The webhook workers do not consume from a message queue in the broker sense, and there is no "queue declaration" to point to.

**Actual mechanism:** Webhook delivery uses an in-process Go channel as a bounded async queue, entirely within the server process (`internal/webhook/webhook.go`):
- The queue is a buffered channel declared at `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (capacity 128).
- Four worker goroutines are spawned in the package `init()` (`webhook.go:41-53`); each ranges over `asyncPostQueue` (`webhook.go:45`) and calls `Post` to perform the actual outbound HTTP delivery.
- Producers enqueue via `PostAsync` (`webhook.go:190`), a non-blocking send with a `default` case that drops the payload (logging a warning) if the buffer is full.

So delivery is handled by an in-memory channel + goroutine worker pool, not by NATS, RabbitMQ, or any message broker. This state is not durable — pending webhooks are lost on process restart.
