**Premise correction:** There is no Redis anywhere in this repository — a full-repo grep for "redis" returns zero matches, and no Redis client/driver is imported anywhere.

**Actual mechanism:** The "cache layer" is a custom in-process, in-memory cache (`sync.Map`-backed), not Redis. It's implemented in `store/cache/cache.go` (the `Cache` type, `New`/`NewDefault`, `Set`/`SetWithTTL`/`Get`, with a background `cleanupLoop` goroutine for expiry/eviction).

It's wired up in `store/store.go:38-58` (`store.New`), where a `cache.Config` is built with:
```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
and used to construct three separate in-memory caches: `instanceSettingCache`, `userCache`, and `userSettingCache` (each `cache.New(cacheConfig)`).

For user entries specifically, `userCache` holds `*User` records keyed by `userCacheKey(user.ID)` (see `store/user.go:98,122,132,143,150,167` and eviction on delete in `store/user_delete.go:40`). Since no per-entry TTL override (`SetWithTTL`) is used for users, they inherit the cache's `DefaultTTL` of **10 minutes**, with a cleanup sweep every 5 minutes and a 1000-item cap.
