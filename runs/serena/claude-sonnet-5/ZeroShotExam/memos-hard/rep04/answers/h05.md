**Mechanism:** By explicit Go code — not a database-level `ON DELETE CASCADE`/trigger, and not left alone.

**Evidence locations:**
- `server/router/api/v1/user_service.go:393-454` — `APIV1Service.DeleteUser` calls `s.Store.DeleteUser(ctx, &store.DeleteUser{ID: user.ID})` inside a single logical delete operation.
- `store/db/postgres/user_delete.go:29-59` (`DB.DeleteUser`) runs the whole deletion inside one SQL transaction (`d.db.BeginTx` … `tx.Commit()`), calling `deleteUserTargetsTx`.
- `store/db/postgres/user_delete.go:92-116` (`deleteUserTargetsTx`) explicitly calls, in order:
  - `deleteReactionsByContentIDsTx(ctx, tx, contentIDs)` (line 96) — removes reactions left by *anyone* on memos owned by the deleted user, matched via `content_id`.
  - `deleteReactionsByCreatorTx(ctx, tx, userID)` (line 102) — removes reactions the deleted user made on *other* memos, matched via `creator_id`.
- `store/db/postgres/user_delete.go:380-403` — the actual SQL: `DELETE FROM reaction WHERE content_id IN (...)` and `DELETE FROM reaction WHERE creator_id = $1`.
- Identical logic exists per-driver in `store/db/sqlite/user_delete.go:96,102,380-403` and `store/db/mysql/user_delete.go:96,102,417-438` (same function names/structure, confirmed via grep).
- Schema check: `store/migration/postgres/LATEST.sql:91-98` defines the `reaction` table with `creator_id INTEGER NOT NULL` and **no foreign key / `ON DELETE CASCADE`** referencing the `user` table — ruling out a database-level rule as the mechanism.
- `store/user_delete.go:1-47` — the shared (driver-agnostic) `Store.DeleteUser`/`DeleteUserResult`/failpoint scaffolding that wraps the per-driver implementation, plus `deleteUserCache` for cache invalidation, but the actual reaction deletion happens in the driver-specific transactional code above.
