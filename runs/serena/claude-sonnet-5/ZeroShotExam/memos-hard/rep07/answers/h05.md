**Mechanism:** Explicit Go code (application-level), not a database-level cascade rule.

**Evidence:**
- `store/db/sqlite/user_delete.go` — `deleteUserTargetsTx` (lines ~96–121) calls `deleteReactionsByContentIDsTx` (deletes reactions on all memos owned by the user being deleted: `DELETE FROM reaction WHERE content_id IN (...)`, line ~330) and `deleteReactionsByCreatorTx` (deletes reactions the user themself made: `DELETE FROM reaction WHERE creator_id = ?`, line ~347). Both run inside the same DB transaction as the rest of `DeleteUser`, before the user row is finally removed (`deleteUserRowTx`).
- Identical logic is duplicated per-driver:
  - `store/db/postgres/user_delete.go:383` (`DELETE FROM reaction WHERE content_id IN ...`) and `:401` (`DELETE FROM reaction WHERE creator_id = ...`)
  - `store/db/mysql/user_delete.go:420` and `:438` (same two statements)

No FK/`ON DELETE CASCADE` constraint is relied upon here — the `reaction` table rows are removed via explicit `DELETE` statements executed by Go code as part of the `deleteUserTargetsTx` transaction, covering both reactions the deleted user placed on others' memos and reactions others placed on the deleted user's own memos.
