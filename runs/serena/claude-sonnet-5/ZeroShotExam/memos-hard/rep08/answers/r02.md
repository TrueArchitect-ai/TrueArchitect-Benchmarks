Premise correction: there is no per-user API rate-limiting middleware in this codebase, so no such registration point or request limits exist to report.

What actually exists is different in kind:

- Global HTTP middleware registered in `server/server.go:50-52` is only `middleware.Recover()` and a CORS middleware (`newCORSMiddleware`, defined in `server/cors.go`) — nothing throttling requests.
- The Connect-RPC interceptor chain (`server/router/api/v1/connect_interceptors.go:17-239`) consists of `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor` — again, no rate limiting.
- The closest things to "limits" are fixed-size, instance-wide (not per-user) concurrency semaphores for image work, not time-windowed rate limits:
  - `server/router/api/v1/v1.go:39-41,59-60` — `thumbnailSemaphore` capped at 3 concurrent operations, `imageProcessingSemaphore` capped at 2, enforced in `attachment_service.go:158-160` (returns `codes.ResourceExhausted` when exceeded).
  - `server/router/fileserver/fileserver.go:106-116,448-451` — a similar `thumbnailSemaphore`.
- `internal/email/README.md:286-297` and `internal/email/doc.go:86` mention rate limiting as a suggested future improvement for email sending, but it's documentation only — never implemented.
- No `go.mod`/`go.sum` dependency for rate limiting (e.g. `golang.org/x/time/rate`), no `express-rate-limit` in `web/package.json`, and no nginx/proxy config in the repo.

So there's no per-user, per-time-window API rate limit anywhere in this repo to cite numbers for.
