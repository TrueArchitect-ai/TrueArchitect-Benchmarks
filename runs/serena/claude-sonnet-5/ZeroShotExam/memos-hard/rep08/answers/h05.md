**Mechanism: explicit Go application code (not a DB-level constraint, and not a no-op).**

Evidence locations:

- **Schema — no FK/CASCADE on reactions**: `store/migration/sqlite/LATEST.sql:91-99` (and equivalents `store/migration/postgres/LATEST.sql:90-98`, `store/migration/mysql/LATEST.sql:90-98`). The `reaction` table's `creator_id INTEGER NOT NULL` column has no `FOREIGN KEY`/`REFERENCES` clause referencing `user` — unlike e.g. `memo_share`, which explicitly declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the same file. So there is no database-level rule (`ON DELETE CASCADE` or otherwise) tying reaction deletion to user deletion.

- **Reaction Go struct**: `store/reaction.go:7-14` — `CreatorID int32` maps to `User.ID` only in application logic.

- **User deletion code path**:
  - `server/router/api/v1/user_service.go:393` `DeleteUser` handler → calls `s.Store.DeleteUser`.
  - `store/user.go:171-181` → delegates to per-driver deletion, then invalidates caches (`store/user_delete.go:39-47`).
  - Driver implementations (identical across backends): `store/db/sqlite/user_delete.go:29-127`, `store/db/postgres/user_delete.go:29-127`, `store/db/mysql/user_delete.go:29-127` — run one transaction that explicitly deletes reactions before deleting the user row.

- **Explicit reaction cleanup code**:
  - `store/db/sqlite/user_delete.go:380-388` — `deleteReactionsByContentIDsTx`: `DELETE FROM reaction WHERE content_id IN (...)` for reactions on the deleted user's memos.
  - `store/db/sqlite/user_delete.go:400-403` — `deleteReactionsByCreatorTx`: `DELETE FROM reaction WHERE creator_id = ?` for reactions the deleted user made.
  - Both invoked from `deleteUserTargetsTx` (sqlite `user_delete.go:96,102`; postgres `user_delete.go:96,102`; mysql `user_delete.go:96,102`), executed before the final `DELETE FROM user` (`deleteUserRowTx`, sqlite `user_delete.go:461-464`).
  - Equivalent code: `store/db/postgres/user_delete.go:380-388,400-403`; `store/db/mysql/user_delete.go:417-425,437-440`.

- **No soft-delete involved**: `user` table has a `row_status` (NORMAL/ARCHIVED) column but `DeleteUser` does a real `DELETE FROM user`; no `deleted_at` column exists anywhere in the schema, and reactions are hard-deleted too.

- **Test confirming behavior**: `store/test/user_delete_test.go:97-112` seeds reactions by the deleted user and a peer's reaction on the deleted user's content; `:217-220` asserts the deleted user's reactions are gone while the unrelated peer reaction survives.

Conclusion: emoji reactions are removed via hand-written `DELETE FROM reaction ...` statements inside the `DeleteUser` transaction in each DB driver, not via a foreign-key `ON DELETE CASCADE` rule (none exists on `reaction.creator_id`).
