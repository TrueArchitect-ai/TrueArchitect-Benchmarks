**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted directly (`server/router/api/v1/memo_service.go:580` → `store/memo.go:158` → `store/db/{sqlite,postgres,mysql}/memo.go` `DeleteMemo`). Comment-type child memos (linked via `memo_relation`, type `COMMENT`) are also deleted the same way in a loop first (`memo_service.go:567-577`).
- **`memo_relation`** — explicitly cleaned up in `store.Store.DeleteMemo` (`store/memo.go:142-147`), which deletes rows where the memo is either `memo_id` or `related_memo_id`, before the memo row itself is removed.
- **`attachment`** — explicitly cleaned up in `store.Store.DeleteMemo` (`store/memo.go:148-157`): attachments linked via `memo_id` are looked up and deleted one-by-one via `DeleteAttachment`.
- **`memo_share`** — not touched by application code, but the schema defines `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:102-110`, same pattern in postgres/mysql `LATEST.sql`), so DB-level cascade deletes matching rows when the `memo` row is deleted.

Not affected: `reaction` rows are only `ListReactions`'d (for the deleted-webhook payload) but never deleted, and the `reaction.content_id` column has no FK/cascade tying it to `memo`, so reactions become orphaned rather than cascade-deleted.
