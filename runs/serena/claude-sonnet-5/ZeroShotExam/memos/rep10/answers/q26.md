**Tables affected when `DeleteMemo` runs:**

1. **`memo`** — the target memo row is deleted, and (recursively) any comment memos are deleted first. `server/router/api/v1/memo_service.go:567-582` lists comment relations and calls `s.Store.DeleteMemo` for each comment, then for the memo itself; the actual `DELETE FROM memo` happens in `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`.

2. **`memo_relation`** — explicitly cleaned up in `store/memo.go:140-147` (`Store.DeleteMemo`), which calls `driver.DeleteMemoRelation` twice: once where the memo is the source (`MemoID`) and once where it is the target (`RelatedMemoID`). This runs for the deleted memo and for every deleted comment memo (since comments are deleted via the same `Store.DeleteMemo` path).

3. **`attachment`** — explicitly cleaned up in `store/memo.go:148-157`, which lists attachments for the memo (`ListAttachments`) and calls `Store.DeleteAttachment` for each, which issues `DELETE FROM attachment` (`store/db/sqlite/attachment.go:211-221`, similarly in postgres/mysql drivers) and also deletes the underlying file/blob storage (`store/attachment.go:132-148`).

4. **`memo_share`** — not touched by any Go code, but cascades at the database level via a declared foreign key: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`). Note: the sqlite driver opens its connection with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite this cascade is effectively **not enforced**, even though it's declared in the schema; on Postgres/MySQL it is enforced by the engine.

**Not affected:** `reaction` rows are read (`ListReactions` in `server/router/api/v1/memo_service.go:545-550`, keyed by `content_id`, a string name rather than an FK) only to build the webhook payload — they are never deleted, so they become orphaned.
