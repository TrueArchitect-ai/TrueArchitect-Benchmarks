The background research agent I'd launched earlier finished and confirms my answer with a bit more nuance worth noting:

- Archive/restore/pin are **not** separate webhook events — they go through `UpdateMemo`'s generic update-mask path and fire `DispatchMemoUpdatedWebhook` same as any other edit (`server/router/api/v1/memo_service.go:401-516`).
- Attachment changes (`memo_attachment_service.go:41,48`) and relation changes (`memo_relation_service.go:41,48`) also touch `updated_ts` and re-fire `DispatchMemoUpdatedWebhook` via the same `dispatchMemoUpdatedSideEffects` helper.
- Creating a comment triggers both `"memos.memo.comment.created"` **and**, since `CreateMemoComment` internally calls `CreateMemo`, a `"memos.memo.created"` webhook for the comment's own memo object.
- Delivery confirmed as two-stage: `webhook.PostAsync` enqueues onto a bounded channel (`internal/webhook/webhook.go:184`), drained by 4 worker goroutines that call `webhook.Post` (`internal/webhook/webhook.go:120`) for the actual signed HTTP POST.

My original answer above stands — this just adds detail on the "updated" event's broader triggers and the two-stage nature of the delivery path.
