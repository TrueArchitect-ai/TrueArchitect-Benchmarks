When `store.DeleteMemo` runs (`/bench/repo/store/memo.go:140-159`), it deletes the following before removing the `memo` row itself:

1. **`memo_relation` records where the memo is the source** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{MemoID: &delete.ID})` (`store/memo.go:142`)
2. **`memo_relation` records where the memo is the target/related memo** — `s.driver.DeleteMemoRelation(ctx, &DeleteMemoRelation{RelatedMemoID: &delete.ID})` (`store/memo.go:145`)
3. **`attachment` records linked to the memo** (plus their underlying storage — local file or S3 object) — via `s.ListAttachments` then `s.DeleteAttachment` for each (`store/memo.go:149-157`, which internally calls `DeleteAttachmentStorage` and `driver.DeleteAttachment`, see `store/attachment.go:132-148`)

Only then does it call `s.driver.DeleteMemo(ctx, delete)` to delete the `memo` row (`store/memo.go:158`, implemented e.g. in `store/db/sqlite/memo.go:237-248`).

Notes:
- One level up, the API handler (`server/router/api/v1/memo_service.go:567-577`) also recursively deletes comment memos (memo rows related via `memo_relation` with type `Comment`) by calling `store.DeleteMemo` again for each before deleting the parent memo — but that's the same record type (memos), not a different kind of record.
- `reaction` rows are **not** deleted by the store layer (only listed, for the webhook payload) and have no FK cascade in the schema, so they're left orphaned.
- `memo_share` rows are removed via a DB-level `ON DELETE CASCADE` foreign key (`store/migration/sqlite/LATEST.sql:109`), not by explicit store-layer code.
