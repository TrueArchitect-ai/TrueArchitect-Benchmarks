**Tables affected when `DeleteMemo` runs:**

1. **`memo`** — the row itself is deleted.
   `server/router/api/v1/memo_service.go:580` → `store/memo.go:158` → driver DELETE at `store/db/sqlite/memo.go:237-248` (equivalents in `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

2. **`memo_relation`** — explicitly cleaned up as both source and target of the deleted memo.
   `store/memo.go:142` (`MemoID: &delete.ID`) and `store/memo.go:145` (`RelatedMemoID: &delete.ID`) → driver `DELETE FROM memo_relation WHERE ...` (`store/db/sqlite/memo_relation.go:137-158`, equivalents in postgres/mysql).

3. **`attachment`** — explicitly listed then deleted one-by-one for the memo.
   `store/memo.go:149-157` (`ListAttachments` + loop calling `DeleteAttachment`) → driver `DELETE FROM attachment WHERE id = ?` (`store/db/sqlite/attachment.go:211-221`, equivalents in postgres/mysql).

4. **`memo_share`** — not deleted by explicit app code, but affected via a real DB-level `ON DELETE CASCADE` foreign key on `memo_share.memo_id → memo(id)`, so rows are removed automatically when the `memo` row is deleted (`store/migration/sqlite/LATEST.sql:101-112`; same in `store/migration/postgres/LATEST.sql:108` and `store/migration/mysql/LATEST.sql:108`).

5. **Comment memos → recursively cascades tables 1-3 again**: before deleting the target memo, the handler finds `memo_relation` rows of type `Comment` pointing at it and calls `Store.DeleteMemo` on each comment's own memo ID (`server/router/api/v1/memo_service.go:567-577`), so each comment's own `memo`, `memo_relation`, and `attachment` rows are deleted too.

**Note:** `reaction` rows tied to the memo are only read (`ListReactions`, `memo_service.go:545-550`, for the webhook payload) — they are never deleted and have no FK/cascade tying them to `memo`, so they end up orphaned rather than cascaded.

**Summary table list:** `memo`, `memo_relation`, `attachment`, `memo_share` (DB-cascade only).
