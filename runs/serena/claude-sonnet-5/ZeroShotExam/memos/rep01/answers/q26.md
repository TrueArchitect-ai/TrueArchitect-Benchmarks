**Directly deleted tables (by explicit application code in `DeleteMemo`):**
- **`memo`** — the memo row itself, and any comment memos (`memo_relation` rows of type `COMMENT`) are recursively deleted too (`server/router/api/v1/memo_service.go:567-582`, `store/memo.go:140-159`).
- **`memo_relation`** — all rows where the memo is either `memo_id` or `related_memo_id` (`store/memo.go:142-147`, deleted via `store/db/sqlite/memo_relation.go:137-157` and mysql/postgres equivalents).
- **`attachment`** — all attachments linked to the memo via `memo_id`, deleted one-by-one through `Store.DeleteAttachment` (`store/memo.go:148-157`, `store/attachment.go:132-149`).

**Cascaded via explicit DB foreign-key constraint (not app code):**
- **`memo_share`** — declared `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in postgres/mysql/sqlite schemas (`store/migration/{postgres,mysql,sqlite}/LATEST.sql`, e.g. sqlite lines 101-110). Note: on SQLite this cascade is effectively inert because the driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite deployments `memo_share` rows are actually left orphaned; on Postgres/MySQL the cascade fires.

**Not affected (orphaned, no cascade):**
- **`reaction`** — reactions are only `ListReactions`'d (to build the webhook payload) but never deleted; `reaction.content_id` has no FK constraint to `memo`. So reaction rows survive memo deletion (`server/router/api/v1/memo_service.go:545-550`).
