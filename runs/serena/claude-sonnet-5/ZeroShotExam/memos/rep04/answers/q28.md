q28. What background workers/runners does the server actually START, and what drives each one's scheduling?

**S3 presign runner** — `time.Ticker` firing every **12 hours** (`server/runner/s3presign/runner.go:27-41`, constant `runnerInterval = time.Hour * 12`), plus one synchronous run-once at boot. Started from `Server.startBackgroundRunners` (`server/server.go:153-174`), which is invoked from `Server.Start` (`server/server.go:129`), called from `cmd/memos/main.go:87`. It scans S3-backed attachments and refreshes presigned URLs nearing their 5-day expiry.

**In-memory cache eviction loops (3 instances)** — `time.Ticker` firing every **5 minutes** (`store/cache/cache.go:83` spawns `cleanupLoop()`, ticker configured via `CleanupInterval: 5 * time.Minute` in `store/store.go:41`). These are `instanceSettingCache`, `userCache`, and `userSettingCache`, created in `store.New()` (called from `cmd/memos/main.go:59`), so they start transitively at server bootstrap rather than being explicitly listed in `startBackgroundRunners`.

**Webhook delivery workers** — not scheduled/periodic; 4 goroutines spawned in `init()` (`internal/webhook/webhook.go:39-55`) that drain a buffered channel (`asyncPostQueue`), triggered whenever application code enqueues a webhook payload.

**Email delivery workers** — same pattern, 2 goroutines spawned in `init()` (`internal/email/email.go:14-36`) draining `asyncEmailQueue`, triggered by event, not a timer.

**SSE heartbeat** — per-connection `time.Ticker` every 30s (`server/router/api/v1/sse_handler.go`), scoped to each individual client connection, not a server-wide scheduled job.

**Unused scheduling infrastructure:** `internal/scheduler/` (`scheduler.go`, `job.go`, `parser.go`, `middleware.go`) is a fully-built cron scheduler with cron-expression parsing, timezones, and middleware — but it is **never wired into the server**. `grep -rn "internal/scheduler"` shows the only importers are its own test files (`internal/scheduler/example_test.go:10`, `internal/scheduler/integration_test.go:13`); nothing in `cmd/`, `server/`, or `store/` calls `scheduler.New()`/`Register()`/`Start()`. Similarly, `memopayload.Runner`'s batch `RunOnce` (`server/runner/memopayload/runner.go`) is defined but never instantiated anywhere — only its unrelated single-memo helper `RebuildMemoPayload` is called synchronously inside request handlers (`server/router/api/v1/memo_service.go:108,447`).
