Confirmed — no `memo_organizer`/tags table exists (tags are stored in the memo's `payload` JSON). This is the complete set of `memo_id`-referencing tables.

q26. Tables affected when `DeleteMemo` runs (server/router/api/v1/memo_service.go:518, delegating to store/memo.go:140 `Store.DeleteMemo`):

- **memo** — the target memo row is deleted directly (store/db/{postgres,mysql,sqlite}/memo.go `DeleteMemo`); additionally, any child "comment" memos (found via `memo_relation` with type `COMMENT`) are deleted recursively first (server/router/api/v1/memo_service.go:567-577), so multiple `memo` rows can be removed per call.
- **memo_relation** — explicitly cleared for each deleted memo, both where it is `memo_id` and where it is `related_memo_id` (store/memo.go:142-147, store/memo_relation.go `DeleteMemoRelation`).
- **attachment** — explicitly cleaned up for each deleted memo by listing and deleting all attachments referencing `memo_id` (store/memo.go:148-157, store/attachment.go:132 `DeleteAttachment`).
- **memo_share** — not touched explicitly in Go code, but cascades automatically at the database level via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (store/migration/postgres/LATEST.sql:101-108, equivalently in the sqlite/mysql migration files).

Note: `reaction` rows tied to the memo are only *read* (`ListReactions`, for the webhook payload) at memo_service.go:545-550, not deleted — there's no FK/cascade for `reaction.content_id`, so reaction rows are left orphaned and are not "affected" in the write sense.
