**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted directly (`store/db/{sqlite,postgres,mysql}/memo.go: DeleteMemo`), and each comment-type child memo (found via `memo_relation` with type `COMMENT`) is also deleted directly, recursively triggering the same cascade for each comment (`server/router/api/v1/memo_service.go:567-577`).
- **`memo_relation`** — explicitly deleted for both directions (`memo_id` and `related_memo_id`) before the memo row is removed (`store/memo.go:142-147`, `Store.DeleteMemo`).
- **`attachment`** — explicitly deleted for every attachment linked to the memo (and to each deleted comment memo), via `Store.ListAttachments` + `Store.DeleteAttachment` (`store/memo.go:148-157`), which also removes the underlying blob/S3/local storage object.
- **`memo_share`** — not touched by Go code, but removed via the DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` constraint when the `memo` row is deleted (`store/migration/{sqlite,postgres,mysql}/LATEST.sql`, memo_share table def).

Note: `reaction` rows tied to the memo are read via `s.Store.ListReactions` for the deletion webhook payload (`server/router/api/v1/memo_service.go:545-550`) but are **not** deleted — there is no explicit cascade or FK cascade for the `reaction` table, so it is not affected by `DeleteMemo`.
