**Tables affected when `DeleteMemo` runs:**

- **`memo`** — the target memo row is deleted directly, plus (in the service layer) any comment memos found via `memo_relation` (type `COMMENT`) are recursively deleted the same way. (`server/router/api/v1/memo_service.go:567-582`, `store/db/sqlite/memo.go:237-248`)
- **`memo_relation`** — explicitly deleted in `store.DeleteMemo` for rows where the memo is either `memo_id` or `related_memo_id` (`store/memo.go:142-147`)
- **`attachment`** — explicitly deleted (and underlying blob/storage removed) for every attachment linked via `memo_id` (`store/memo.go:148-157`, `store/attachment.go:132-149`)
- **`memo_share`** — not touched by any Go code, but cascades automatically at the DB layer via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, same in postgres/mysql `LATEST.sql:108`)

Not affected: `reaction` (linked only loosely by a `content_id` string, no FK, and `DeleteMemo` never calls `DeleteReaction`) — reactions on a deleted memo appear to become orphaned rather than cascaded.
