q26. Tables affected when `Store.DeleteMemo` runs (`store/memo.go:140-159`):

- `memo` — the row itself is deleted (`DB.DeleteMemo`, e.g. `store/db/postgres/memo.go:244-255`)
- `memo_relation` — explicitly deleted for both directions (`memo_id` and `related_memo_id`) before the memo row
- `attachment` — explicitly deleted (linked attachments looked up via `ListAttachments` then removed via `DeleteAttachment`)
- `memo_share` — has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`), so it cascades automatically at the DB level when the memo row is deleted (Postgres/mysql; SQLite's FK enforcement depends on `PRAGMA foreign_keys`)

Note: `reaction` rows reference memos only loosely via `content_id` (a text field, not a FK to `memo.id`), so they are not covered by explicit code or a declared FK cascade in this migration.
