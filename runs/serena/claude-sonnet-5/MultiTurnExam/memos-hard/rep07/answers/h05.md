**Mechanism: explicit Go code** (not a database-level cascade).

**Evidence locations:**
- All three drivers execute explicit `DELETE FROM reaction` statements inside the `DeleteUser` transaction, before the user row is removed:
  - SQLite: `store/db/sqlite/user_delete.go:383` (`DELETE FROM reaction WHERE content_id IN ...`) and `:401` (`DELETE FROM reaction WHERE creator_id = ...`), invoked from `deleteUserTargetsTx`.
  - MySQL: `store/db/mysql/user_delete.go:420` and `:438` (same two statements).
  - PostgreSQL: `store/db/postgres/user_delete.go:383` and `:401` (same two statements).
  - This covers both reactions the user made (`creator_id`) and reactions left on the deleted user's own memos (`content_id`).
- Checked schema definitions for a DB-level rule: `store/migration/{sqlite,postgres,mysql}/LATEST.sql`, `reaction` table (~lines 91-99 in each) has **no** `FOREIGN KEY` clause at all — no `REFERENCES user(id)`, no `ON DELETE CASCADE`. By contrast, the adjacent `memo_share` table in the same files *does* declare `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, confirming cascades are used elsewhere but were not applied to `reaction`.

Conclusion: reactions are cleaned up entirely by explicit `DELETE` statements in application code, not by any database-enforced cascade.
