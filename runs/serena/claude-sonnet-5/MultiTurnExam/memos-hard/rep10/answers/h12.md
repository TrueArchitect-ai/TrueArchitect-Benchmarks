**Concrete method:** `(*DB).CreateMemo` in the **sqlite** driver — `store/db/sqlite/memo.go:16-52` — which builds and executes `INSERT INTO `memo` (...) VALUES (...) RETURNING ...` via `d.db.QueryRowContext(ctx, stmt, args...)` (`store/db/sqlite/memo.go:41-42`).

**Determination method:**
1. `Store.CreateMemo` (`store/memo.go:109-114`) doesn't run SQL itself — it validates the UID and dispatches to `s.driver.CreateMemo(ctx, create)`, where `s.driver` is the `store.Driver` interface, so the *concrete* type that actually executes depends on which driver was constructed.
2. That construction happens in the driver-selection factory `NewDBDriver` (`store/db/db.go:14-30`), which switches on `profile.Driver` and calls `sqlite.NewDB`, `mysql.NewDB`, or `postgres.NewDB` — one of three separate packages under `store/db/`, each with its own `CreateMemo` implementation and its own literal `INSERT INTO memo ...` statement (I confirmed all three exist: `store/db/sqlite/memo.go`, `store/db/mysql/memo.go`, `store/db/postgres/memo.go`).
3. To find which one runs by default (no `--driver`/`MEMOS_DRIVER` flag set), I checked how `profile.Driver` is populated: `cmd/memos/main.go:122` sets `viper.SetDefault("driver", "sqlite")`, and the CLI flag itself defaults to `"sqlite"` (`cmd/memos/main.go:130`, `rootCmd.PersistentFlags().String("driver", "sqlite", ...)`).
4. Since the default resolves to `"sqlite"`, the `switch` in `NewDBDriver` (`store/db/db.go`) takes the `case "sqlite": driver, err = sqlite.NewDB(profile)` branch, making `store/db/sqlite/memo.go`'s `CreateMemo` the concrete code that runs the INSERT on a default installation.
