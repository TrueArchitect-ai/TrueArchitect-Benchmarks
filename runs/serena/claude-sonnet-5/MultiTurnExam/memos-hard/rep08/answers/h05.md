**Mechanism:** By explicit Go code, not a database-level rule (no foreign key / cascade exists on `reaction`).

**Evidence locations:**
- Schema: `reaction` table has no foreign key at all in any driver's schema — `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql` (reaction block), `store/migration/mysql/LATEST.sql` (reaction block) all define `creator_id`/`content_id` as plain columns with no `FOREIGN KEY`/`ON DELETE CASCADE` clause (contrast with `memo_share`, which does have `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, e.g. `store/migration/sqlite/LATEST.sql:109`).
- Code: `store.Store.DeleteUser` drivers explicitly delete reactions in two passes inside the delete-user transaction:
  - `deleteReactionsByContentIDsTx` — removes reactions left *on* memos/comments owned by the deleted user (`store/db/sqlite/user_delete.go:96,380-388`; `store/db/postgres/user_delete.go:96,380`; `store/db/mysql/user_delete.go:96,417`).
  - `deleteReactionsByCreatorTx` — removes reactions the deleted user made *on* others' content (`store/db/sqlite/user_delete.go:102,400-403`; `store/db/postgres/user_delete.go:102,400`; `store/db/mysql/user_delete.go:102,437`).

All three drivers (sqlite, postgres, mysql) implement this identically in application code inside the same transaction that deletes the user row.
