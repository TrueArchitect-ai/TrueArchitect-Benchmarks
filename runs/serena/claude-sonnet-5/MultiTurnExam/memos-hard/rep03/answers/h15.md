Memo-visibility (`store.Visibility`: `Private`/`Protected`/`Public`) view-access checks are independently re-implemented at several distinct server surfaces (not a single shared gate):

- **Core API memo access** — `checkMemoReadAccess` in `server/router/api/v1/memo_service.go:39-63` (gates `GetMemo` at `memo_service.go:356` and comment parent lookup at `memo_service.go:367`, also reused by `server/router/api/v1/memo_service_comments.go:148` for `ListMemoComments`)

- **Attachment retrieval (API)** — `server/router/api/v1/attachment_service.go:436-453` (permission check inside `GetAttachment`, separately re-derives visibility rules for linked attachments)

- **Memo-attachment listing (API)** — `server/router/api/v1/memo_attachment_service.go:213-224` (`ListMemoAttachments` re-checks the parent memo's visibility)

- **Reaction access (API)** — `server/router/api/v1/reaction_service.go:29-40,82-85` (gates listing/creating reactions based on the target memo's visibility)

- **File-serving HTTP surface** — `checkAttachmentPermission` in `server/router/fileserver/fileserver.go:650-704` (gates `GET /file/attachments/:uid/:filename` based on the owning memo's visibility, independent of the API-layer checks)

- **RSS feed surface** — `server/router/rss/rss.go:90` and `:141` (enforces visibility at the query level by hard-restricting `FindMemo.VisibilityList` to `[]store.Visibility{store.Public}`, rather than per-item filtering)

- **Frontend SSR/meta surface** — `server/router/frontend/frontend.go:150` (same query-level restriction to `store.Public` only, for server-rendered link-preview/meta tags)
