**Mechanism: explicit Go code**, via two separate deletion steps within the `deleteUserTargetsTx` function.

**Evidence locations:**

1. **`deleteReactionsByContentIDsTx`** — deletes all reactions on the user's memos (by `content_id`), called at e.g. `store/db/sqlite/user_delete.go:96`, `store/db/mysql/user_delete.go:96`, `store/db/postgres/user_delete.go:96`. The SQL is `DELETE FROM reaction WHERE content_id IN (...)`.

2. **`deleteReactionsByCreatorTx`** — deletes all reactions *created by* the user (by `creator_id`), called at e.g. `store/db/sqlite/user_delete.go:102`, `store/db/mysql/user_delete.go:102`, `store/db/postgres/user_delete.go:102`. The SQL is `DELETE FROM reaction WHERE creator_id = ?`.

Both are called from `deleteUserTargetsTx` in each driver's `user_delete.go`. There are no database-level cascade rules handling this — the reaction table has no foreign-key `ON DELETE CASCADE` wired up; the cleanup is done entirely by explicit `DELETE` statements in Go code within the same transaction that removes the user.
