Trace of `GET /file/users/:identifier/avatar` from handler to stored data:

1. `FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go`
2. `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go`
3. `Store.GetUser` — `store/user.go`
4. `Store.ListUsers` — `store/user.go`
5. `Driver.ListUsers` (interface) — `store/driver.go`
6. `DB.ListUsers` (concrete, e.g. SQLite) — `store/db/sqlite/user.go`

The route is registered in `FileServerService.RegisterRoutes` (`server/router/fileserver/fileserver.go`). The handler extracts the username from the URL, calls `getUserByUsername` which delegates to `Store.GetUser`, which checks the in-memory user cache and falls back to `Store.ListUsers`, which calls the `Driver.ListUsers` interface method implemented by each DB backend (sqlite/postgres/mysql). The returned `User.AvatarURL` field is a data URI; back in the handler, `parseDataURI` (`server/router/fileserver/fileserver.go`) decodes the base64 payload and the raw image bytes are sent to the browser.
