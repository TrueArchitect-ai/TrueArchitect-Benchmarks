**Mechanism: explicit Go code**, not a database-level rule. The `reaction` table has no foreign key constraints in any backend.

**Evidence locations:**

- **No CASCADE in schema** — The `reaction` table is defined without foreign keys in all three drivers:
  - `store/migration/sqlite/LATEST.sql` (lines ~92–99)
  - `store/migration/postgres/LATEST.sql` (lines ~91–98)
  - `store/migration/mysql/LATEST.sql` (lines ~91–98)

- **Explicit deletion in Go** — The per-driver `deleteUserTargetsTx` function (runs inside a transaction) performs two reaction cleanup steps:
  1. `deleteReactionsByContentIDsTx` — deletes all reactions *on* the user's memos (by `content_id`), e.g. `store/db/sqlite/user_delete.go` (~line 380)
  2. `deleteReactionsByCreatorTx` — deletes all reactions *created by* the user (by `creator_id`), e.g. `store/db/sqlite/user_delete.go` (~line 400)

  The same logic exists in all three drivers: `store/db/sqlite/user_delete.go`, `store/db/postgres/user_delete.go`, `store/db/mysql/user_delete.go`.

- **Test verification** — `store/test/user_delete_test.go` (`TestDeleteUserCleansRelatedData`) explicitly asserts that both categories of reactions are removed and unrelated reactions survive.
