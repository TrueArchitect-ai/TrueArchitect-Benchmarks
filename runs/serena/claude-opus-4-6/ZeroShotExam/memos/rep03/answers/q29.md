**Interceptor path:** `web/src/connect.ts` — the `authInterceptor` (a ConnectRPC `Interceptor`) attaches an `Authorization: Bearer <token>` header to every outgoing RPC call, handles 401 retries with token refresh, and deduplicates concurrent refresh requests.

**Token kinds managed:**
1. **Access token** (short-lived JWT, 15-min expiry) — stored client-side in memory and `localStorage` (`web/src/auth-state.ts`), sent as `Bearer` in the `Authorization` header.
2. **Refresh token** (long-lived, 30-day expiry) — stored server-side only, delivered via an `HttpOnly` cookie (`memos_refresh`); the frontend never reads it directly but triggers refresh via `AuthService.RefreshToken` RPC (with `credentials: "include"`).
3. **Personal Access Token (PAT)** — prefixed `memos_pat_`, validated by SHA-256 hash lookup in the database (not JWT-based).

**Backend validation package:** `server/auth/` — specifically `server/auth/token.go` (JWT parsing/verification with `golang-jwt/jwt/v5`, HS256 signing, audience/issuer checks) and `server/auth/authenticator.go` (`Authenticate()` dispatches to access-token or PAT validation via `resolveBearer()`). The Connect RPC middleware that invokes it lives in `server/router/api/v1/connect_interceptors.go` (`AuthInterceptor`).
