The following database tables are affected when `DeleteMemo` runs:

1. **`memo`** — the memo row itself is deleted (`store/db/sqlite/memo.go:239`, `store/db/postgres/memo.go:246`, `store/db/mysql/memo.go:261`)
2. **`memo_relation`** — explicitly deleted in `store/memo.go:142-145` via two calls to `DeleteMemoRelation` (clearing rows where the memo is either `memo_id` or `related_memo_id`), which issues `DELETE FROM memo_relation` (`store/db/sqlite/memo_relation.go:148-150`)
3. **`attachment`** — explicitly deleted in `store/memo.go:149-156` by listing attachments for the memo and deleting each one via `DELETE FROM attachment` (`store/db/sqlite/attachment.go:212`)
4. **`memo_share`** — deleted via `ON DELETE CASCADE` foreign key on `memo_id REFERENCES memo(id)` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`)

Additionally, the service layer in `server/router/api/v1/memo_service.go:567-577` recursively calls `DeleteMemo` for comment memos (found via `memo_relation` with type `Comment`), so all four tables are affected again for each comment memo.
