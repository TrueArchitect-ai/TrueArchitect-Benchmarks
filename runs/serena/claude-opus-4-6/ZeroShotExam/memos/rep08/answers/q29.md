The frontend auth interceptor lives in **`web/src/connect.ts`** — it is a Connect RPC `Interceptor` that attaches a `Bearer` access token (via `Authorization` header) to every outgoing request, handles 401 (`Code.Unauthenticated`) by refreshing the token and retrying once, and redirects to the auth page on final failure.

**Token kinds managed:**

1. **Access tokens** (short-lived JWTs, 15 min) — stored in-memory and in `localStorage` under `memos_access_token`, with expiry tracking. Managed by `web/src/auth-state.ts`.
2. **Refresh tokens** (long-lived JWTs, 30 days) — handled as HTTP-only cookies (`memos_refresh`), never directly accessed by frontend JS. The interceptor uses a separate `refreshTransport` with `credentials: "include"` to send the cookie to `AuthService.refreshToken`.
3. **Personal access tokens (PATs)** — random strings prefixed `memos_pat_`, stored as SHA-256 hashes in the database. Accepted as Bearer tokens on the backend alongside JWTs.

**Backend validation package:** **`server/auth`** (`github.com/usememos/memos/server/auth`). Its `Authenticator` struct dispatches via `Authenticate()` → `resolveBearer()`, which routes to `AuthenticateByAccessTokenV2()` for JWTs or `AuthenticateByPAT()` for PAT-prefixed tokens. JWT validation uses `github.com/golang-jwt/jwt/v5` with HS256 signing. The auth package is consumed by the Connect RPC interceptor at `server/router/api/v1/connect_interceptors.go` (`AuthInterceptor`).

**Summary:** `web/src/connect.ts`; access tokens (JWT), refresh tokens (HTTP-only cookie JWT), personal access tokens (PAT); `server/auth`.
