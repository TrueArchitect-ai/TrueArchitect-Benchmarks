The premise of the question is incorrect — there is no Redis connection in this project. The cache layer is an **in-memory cache** (`sync.Map`-based), not Redis-backed.

The implementation lives in `store/cache/cache.go`, which defines a `Cache` struct backed by Go's `sync.Map` with TTL expiration and a background cleanup goroutine. It is instantiated in `store/store.go:38-45`, where three separate cache instances are created — including `userCache` — all sharing the same `cache.Config`:

- **Default TTL**: `10 * time.Minute` (`store/store.go:41`)
- **Cleanup interval**: `5 * time.Minute` (`store/store.go:42`)
- **Max items**: `1000` (`store/store.go:43`)

There is no per-cache-type TTL override for user entries specifically; the `userCache` (`store/store.go:52`) uses the same `cacheConfig` as `instanceSettingCache` and `userSettingCache`, so user entries get the same 10-minute TTL as everything else. Individual callers could use `SetWithTTL` (`store/cache/cache.go:98`) to override per-entry, but no Redis is involved anywhere in the project.
