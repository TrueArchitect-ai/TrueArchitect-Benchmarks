**Explicit Go code**; reactions are removed in application-level SQL within a transaction — not by any database-level CASCADE rule.

**Evidence:**

1. **No database CASCADE on the `reaction` table.** The `creator_id` column is a plain `INTEGER NOT NULL` with no `REFERENCES` or `ON DELETE CASCADE` clause. This is consistent across all three backends:
   - `store/migration/sqlite/LATEST.sql` (lines 91–99)
   - `store/migration/postgres/LATEST.sql` (lines 90–98)
   - `store/migration/mysql/LATEST.sql` (lines 90–98)

2. **Go code explicitly deletes reactions in two steps** inside the `deleteUserTargetsTx` transaction function, identically in all three drivers:
   - `store/db/sqlite/user_delete.go` (lines 92–104)
   - `store/db/postgres/user_delete.go` (lines 92–104)
   - `store/db/mysql/user_delete.go` (lines 92–104)

   **Step 1** — `deleteReactionsByContentIDsTx`: deletes all reactions *on* the user's memos (`DELETE FROM reaction WHERE content_id IN (...)`) — lines ~380–388 in sqlite/postgres, ~417–425 in mysql.

   **Step 2** — `deleteReactionsByCreatorTx`: deletes all reactions *by* the user on others' memos (`DELETE FROM reaction WHERE creator_id = ?`) — lines ~400–403 in sqlite/postgres, ~437–439 in mysql.

3. **Test confirms both paths**: `store/test/user_delete_test.go`, function `TestDeleteUserCleansRelatedData` (lines 97–114 create reactions; lines 216–220 assert only the unrelated peer-to-peer reaction survives after deletion).
