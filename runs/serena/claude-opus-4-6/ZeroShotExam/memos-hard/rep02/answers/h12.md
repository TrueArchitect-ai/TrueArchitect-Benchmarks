**Concrete method — `CreateMemo` in `store/db/sqlite/memo.go` (the SQLite driver's implementation); determination method: tracing the driver selection default in `cmd/memos/main.go`.**

There are three candidate `CreateMemo` implementations — one each for SQLite (`store/db/sqlite/memo.go`), PostgreSQL (`store/db/postgres/memo.go`), and MySQL (`store/db/mysql/memo.go`). All three implement the `Driver` interface defined in `store/driver.go`. The call chain is:

1. The API handler in `server/router/api/v1/memo_service.go` calls `s.Store.CreateMemo(ctx, create)`.
2. The `Store` facade in `store/memo.go` delegates to `s.driver.CreateMemo(ctx, create)`.
3. The factory in `store/db/db.go` switches on `profile.Driver` to pick which concrete driver to instantiate (sqlite, mysql, or postgres).

To determine which one actually runs by default, `cmd/memos/main.go` (line ~122) registers the default:

```go
viper.SetDefault("driver", "sqlite")
```

and the CLI flag (line ~130):

```go
rootCmd.PersistentFlags().String("driver", "sqlite", "database driver")
```

So with no `--driver` flag and no `MEMOS_DRIVER` env var, the SQLite driver is selected. The concrete SQL INSERT that executes lives in `store/db/sqlite/memo.go`, which builds and runs:

```sql
INSERT INTO `memo` (`uid`, `creator_id`, `content`, `visibility`, `payload`)
VALUES (?, ?, ?, ?, ?)
RETURNING `id`, `created_ts`, `updated_ts`, `row_status`
```

via `d.db.QueryRowContext`. The disambiguation between the three candidates was resolved by following the default value of the `driver` config key back through `viper.SetDefault` and the CLI flag definition in the application entrypoint.
