**Explicit Go code**; reactions are removed by application-level DELETE statements in a transaction, not by any database-level CASCADE rule.

**Evidence:**

1. **No database CASCADE on the `reaction` table.** The `reaction` table has no foreign key constraints at all — `creator_id` is just `INTEGER NOT NULL` with no `REFERENCES` clause:
   - `store/migration/sqlite/LATEST.sql` (lines 92–99)
   - `store/migration/postgres/LATEST.sql` (lines 91–98)
   - `store/migration/mysql/LATEST.sql` (lines 91–98)

2. **Two explicit Go deletion functions** handle cleanup, called within `deleteUserTargetsTx`:
   - **`deleteReactionsByContentIDsTx`** — deletes all reactions (by anyone) targeting the deleted user's memos (`DELETE FROM reaction WHERE content_id IN (...)`)
     - `store/db/sqlite/user_delete.go:380–388`, `store/db/postgres/user_delete.go:380–388`, `store/db/mysql/user_delete.go:417–425`
   - **`deleteReactionsByCreatorTx`** — deletes all reactions the deleted user created on any memo (`DELETE FROM reaction WHERE creator_id = ?`)
     - `store/db/sqlite/user_delete.go:400–402`, `store/db/postgres/user_delete.go:400–402`, `store/db/mysql/user_delete.go:437–439`

3. **Orchestration** in `deleteUserTargetsTx` (e.g. `store/db/sqlite/user_delete.go:92–127`) calls both reaction-deletion functions inside a single transaction before deleting the user's memos and finally the user row itself.

4. **Test coverage** confirms this behavior: `store/test/user_delete_test.go:TestDeleteUserCleansRelatedData` (lines 97–114, 216–220) creates reactions in both directions and asserts that only unrelated reactions survive after user deletion.
