**Mechanism: explicit Go code** — reactions are removed by application-level `DELETE` SQL statements, not by database-level cascade rules.

When a user is deleted, two explicit cleanup steps run inside a single transaction:

1. **Reactions on the user's memos** (by anyone) are deleted via `DELETE FROM reaction WHERE content_id IN (...)`, where content IDs are built from the user's memo tree.
   - `store/db/sqlite/user_delete.go:96-98` (call) and `:380-388` (implementation)
   - Postgres and MySQL equivalents at the same locations in their respective `user_delete.go` files.

2. **Reactions by the user** (on anyone else's content) are deleted via `DELETE FROM reaction WHERE creator_id = ?`.
   - `store/db/sqlite/user_delete.go:102-103` (call) and `:400-403` (implementation)
   - Postgres/MySQL equivalents in their `user_delete.go` files (MySQL at `:437-440`).

**No database-level CASCADE exists.** The `reaction` table in all three backends (`store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`) defines `creator_id INTEGER NOT NULL` with no foreign key constraint referencing the `user` table. Migration `0.5/00__regenerate_foreign_keys.sql` added cascades to other tables but not `reaction`; migration `0.7/00__remove_fk.sql` later stripped those cascades entirely.

**Evidence:** explicit Go code; `store/db/*/user_delete.go` (deletion logic), `store/migration/*/LATEST.sql` (no FK on reaction table).
