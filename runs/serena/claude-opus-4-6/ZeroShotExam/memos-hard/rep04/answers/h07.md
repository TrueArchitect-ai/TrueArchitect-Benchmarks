Here is the request path from the browser to stored data, hop by hop:

```
serveUserAvatar         — server/router/fileserver/fileserver.go
getUserByUsername        — server/router/fileserver/fileserver.go
Store.GetUser           — store/user.go
Store.ListUsers         — store/user.go
Driver.ListUsers        — store/driver.go  (interface)
DB.ListUsers            — store/db/sqlite/user.go  (or postgres/mysql equivalents)
```

**Detail:**

1. **`serveUserAvatar`** — `server/router/fileserver/fileserver.go:168` — The HTTP handler registered at `GET /file/users/:identifier/avatar`. Extracts the `:identifier` param, optionally checks auth, then delegates to find the user.
2. **`getUserByUsername`** — `server/router/fileserver/fileserver.go:715` — A thin wrapper that calls `s.Store.GetUser` with a `FindUser{Username: &identifier}`.
3. **`Store.GetUser`** — `store/user.go:148` — Checks the in-memory `userCache`; on miss, calls `Store.ListUsers`.
4. **`Store.ListUsers`** — `store/user.go:136` — Delegates to `s.driver.ListUsers`, the database driver.
5. **`Driver.ListUsers`** (interface) — `store/driver.go:47` — The `Driver` interface method.
6. **`DB.ListUsers`** (concrete) — e.g. `store/db/sqlite/user.go:88` — Builds a SQL query filtering by `username = ?`, scans the row (including `AvatarURL`), and returns the `*store.User`.

Back in `serveUserAvatar`, the handler reads `user.AvatarURL` (a base64 data-URI), parses it with `parseDataURI`, validates the MIME type against `avatarAllowedTypes`, and writes the raw bytes to the response.
