**Mechanism: explicit Go code; not database-level CASCADE.**

The `reaction` table has **no foreign key constraints** — `creator_id` is a plain `INTEGER NOT NULL` with no `REFERENCES` or `ON DELETE CASCADE` clause. Instead, reactions are cleaned up by direct SQL `DELETE` statements inside the user-deletion transaction.

**Evidence locations:**

1. **No FK in schema** — `store/migration/postgres/0.20/00__reaction.sql`, `store/migration/mysql/0.20/00__reaction.sql`, `store/migration/sqlite/0.20/00__reaction.sql` all define `creator_id INTEGER NOT NULL` with no foreign key.

2. **Explicit Go deletion** — In `store/db/sqlite/user_delete.go` (and the equivalent postgres/mysql files), the function `deleteUserTargetsTx` performs two reaction deletions:
   - **~line 96**: calls `deleteReactionsByContentIDsTx` → `DELETE FROM reaction WHERE content_id IN (...)` — removes all reactions on the deleted user's memos.
   - **~line 102**: calls `deleteReactionsByCreatorTx` → `DELETE FROM reaction WHERE creator_id = ?` — removes all reactions the deleted user placed on others' memos.

3. **Test confirmation** — `store/test/user_delete_test.go` (lines ~97–220) explicitly verifies both categories of reactions are removed and that unrelated reactions survive.
