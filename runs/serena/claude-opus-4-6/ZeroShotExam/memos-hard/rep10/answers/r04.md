The premise is incorrect — webhook delivery workers use **neither NATS nor RabbitMQ**. There is no external message broker involved at all. The codebase has zero dependencies on NATS, RabbitMQ, AMQP, Kafka, or any pub/sub library (confirmed by the absence of any such imports in `go.mod`).

The actual mechanism is an **in-memory buffered Go channel** with a pool of goroutine workers:

- **Queue declaration:** `server/internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel with capacity 128.
- **Worker pool:** `server/internal/webhook/webhook.go:42–53` — an `init()` function spawns 4 goroutines that each loop over `asyncPostQueue`, calling `Post()` to perform the HTTP delivery.
- **Enqueue:** `server/internal/webhook/webhook.go:182–193` — `PostAsync()` uses a non-blocking `select` to send into the channel; if the buffer is full, the webhook is silently dropped with a warning log.

There is no persistence of pending deliveries, no retry mechanism, and no dead-letter queue — it is a purely in-process, lossy, fire-and-forget dispatch system.
