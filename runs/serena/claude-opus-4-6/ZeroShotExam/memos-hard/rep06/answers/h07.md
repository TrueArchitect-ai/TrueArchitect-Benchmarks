Here is the hop-by-hop trace for a browser request for another user's profile image (`GET /file/users/:identifier/avatar`):

1. `FileServerService.RegisterRoutes` — `server/router/fileserver/fileserver.go` (route registration, binds `GET /file/users/:identifier/avatar`)
2. `(*FileServerService).serveUserAvatar` — `server/router/fileserver/fileserver.go` (HTTP handler; extracts `:identifier`, calls auth if private instance)
3. `(*FileServerService).getUserByUsername` — `server/router/fileserver/fileserver.go` (helper that wraps the store call with `FindUser{Username: &identifier}`)
4. `(*Store).GetUser` — `store/user.go` (checks in-memory `userCache`, falls through on miss)
5. `(*Store).ListUsers` — `store/user.go` (delegates to the database driver)
6. `Driver.ListUsers` — `store/driver.go` (interface method)
7. `(*DB).ListUsers` — `store/db/sqlite/user.go` (or `postgres/user.go`, `mysql/user.go`) (executes `SELECT … avatar_url … FROM user WHERE …`, scans `avatar_url` into `User.AvatarURL`)

Back in the handler, the stored `AvatarURL` (a `data:image/…;base64,…` string) is decoded:

8. `(*FileServerService).parseDataURI` — `server/router/fileserver/fileserver.go` (regex-parses the data URI, base64-decodes the image bytes)

The handler then validates the MIME type against `avatarAllowedTypes`, sets security headers, and returns the raw image bytes via `c.Blob()`.

**Note:** The frontend never requests the raw data URI directly. The gRPC API converter `convertUserFromStore` in `server/router/api/v1/user_service_converters.go` rewrites any base64 `AvatarURL` into the path `/file/users/<username>/avatar`, so the browser is always directed to the file-server route above.
