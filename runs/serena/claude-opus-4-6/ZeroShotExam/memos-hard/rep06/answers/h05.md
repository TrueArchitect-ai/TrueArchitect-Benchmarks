**Mechanism: explicit Go code** — reactions are removed by application-level SQL in the `DeleteUser` transaction, not by any database-level CASCADE rule.

**Evidence:**

1. **No database CASCADE on reactions.** The `reaction` table has no foreign key referencing the `user` table in any backend:
   - `store/migration/sqlite/LATEST.sql:91-99`
   - `store/migration/postgres/LATEST.sql:90-98`
   - `store/migration/mysql/LATEST.sql:90-98`

2. **Explicit deletion in Go code within `DeleteUser`.** Each database driver's `deleteUserTargetsTx` function performs two reaction-deletion passes inside a transaction:
   - **Pass 1** — `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380`, postgres and mysql equivalents): executes `DELETE FROM reaction WHERE content_id IN (...)` to remove all reactions (by any user) on the deleted user's memos.
   - **Pass 2** — `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400`, postgres and mysql equivalents): executes `DELETE FROM reaction WHERE creator_id = ?` to remove reactions the deleted user placed on other people's memos.

3. **Test coverage confirms both paths.** `store/test/user_delete_test.go:97-114` creates reactions in three scenarios (peer→owner's memo, owner→peer's memo, peer→peer's memo) and lines 216-220 verify that only the uninvolved reaction survives deletion.
