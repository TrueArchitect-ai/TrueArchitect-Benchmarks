Neither — the premise is false. The webhook delivery workers in this repository don't consume from NATS or RabbitMQ (neither broker appears anywhere in the Go code; the only grep hit for those terms is an unrelated Catalan locale string).

The actual mechanism is entirely in-process, in `internal/webhook/webhook.go`:

- The "queue" is a plain buffered Go channel declared at `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`.
- The "workers" are 4 goroutines started in the package's `init()` function (`internal/webhook/webhook.go:42-55`), each ranging over `asyncPostQueue` and calling `Post()` to deliver the webhook via HTTP.
- Producers enqueue with `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking send and drops the payload with a warning if the 128-slot channel buffer is full.

So there is no external message broker at all — delivery is best-effort, bounded, in-memory fan-out within the server process, and pending webhooks are lost on restart.
