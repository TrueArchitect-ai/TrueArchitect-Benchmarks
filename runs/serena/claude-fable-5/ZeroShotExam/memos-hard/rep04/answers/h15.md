Memo visibility is checked independently in (at least) eight places across the server. The distinct enforcement sites:

- gRPC memo read access (`checkMemoReadAccess`, used by GetMemo etc., plus the `VisibilityList` narrowing in ListMemos) — `server/router/api/v1/memo_service.go` (lines ~39–68 and ~219–225)
- Memo attachment listing (`ListMemoAttachments` re-checks the memo's visibility before returning attachments) — `server/router/api/v1/memo_attachment_service.go` (lines ~213–226)
- Attachment access for linked attachments (attachment access check falls through to the owning memo's visibility) — `server/router/api/v1/attachment_service.go` (lines ~436–454)
- Reaction endpoints (listing/upserting reactions re-checks the target memo's visibility) — `server/router/api/v1/reaction_service.go` (lines ~29–41 and ~83)
- HTTP file server for attachment binaries (public-only anonymous serving, share-token fallback, private → creator/admin only) — `server/router/fileserver/fileserver.go` (lines ~666–702)
- SSE event delivery filtering (`SSEClient.canReceive` drops events for private memos unless the client is the creator or an admin) — `server/router/api/v1/sse_hub.go` (lines ~134–144)
- RSS feeds (queries are hard-limited to `store.Public` memos) — `server/router/rss/rss.go` (lines ~90 and ~141)
- Frontend router (sitemap generation lists only public memos) — `server/router/frontend/frontend.go` (line ~150)

The first four live in the gRPC API surface but each duplicates the check rather than sharing one gate; the fileserver, SSE hub, RSS, and frontend routers are separate server surfaces with their own enforcement.
