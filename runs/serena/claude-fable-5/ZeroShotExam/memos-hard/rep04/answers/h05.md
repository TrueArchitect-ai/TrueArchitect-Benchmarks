**Mechanism: explicit Go code.** Each database driver's `DeleteUser` implementation runs explicit `DELETE FROM reaction ...` statements inside the user-deletion transaction — there is no database-level rule (the `reaction` table has no foreign keys or `ON DELETE CASCADE` at all).

**Evidence:**

1. **Explicit Go deletes** — the transactional delete sequence in `deleteUserTargetsTx` (`store/db/sqlite/user_delete.go:92-127`) calls two reaction-cleanup helpers:
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (removes the user's own reactions): `store/db/sqlite/user_delete.go:400-403`
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (removes reactions on the user's memos, keyed by `"memos/"+uid` content IDs built in `memoContentIDsFromRefs`, `store/db/sqlite/user_delete.go:380-388, 512-518`)

   The same statements exist in the other drivers: `store/db/mysql/user_delete.go:420, 438` and `store/db/postgres/user_delete.go:383, 401`. The entry point is `Store.DeleteUser` at `store/user.go:171`, which dispatches to these drivers.

2. **No database-level rule** — the `reaction` table definitions contain no foreign key constraints or cascades in any dialect, so the DB could not do this automatically:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`

   A grep across `store/migration/` for `FOREIGN`/`CASCADE`/`REFERENCES` near `reaction` returned nothing.
