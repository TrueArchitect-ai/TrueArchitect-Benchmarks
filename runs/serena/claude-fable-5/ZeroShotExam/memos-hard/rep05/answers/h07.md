A browser requesting another user's profile image hits `GET /file/users/:identifier/avatar`. The avatar isn't a separate blob file — it's stored inline as a base64 data URI in the `user` table's `avatar_url` column, so the trace ends at a plain `SELECT` against that table.

Hops (serving handler → data layer):

- `RegisterRoutes` (registers `GET /file/users/:identifier/avatar`) — server/router/fileserver/fileserver.go:124
- `serveUserAvatar` (serving handler; looks up user, parses `user.AvatarURL` data URI, writes the bytes with `c.Blob`) — server/router/fileserver/fileserver.go:168
- `getUserByUsername` — server/router/fileserver/fileserver.go:715
- `Store.GetUser` (cache check, then delegates to ListUsers) — store/user.go:148
- `Store.ListUsers` (delegates to the DB driver) — store/user.go:136
- `DB.ListUsers` (SQLite driver; `SELECT ... avatar_url ... FROM user` and scans into `user.AvatarURL`) — store/db/sqlite/user.go:88 (Postgres and MySQL equivalents: store/db/postgres/user.go:87, store/db/mysql/user.go:84)

Stored data: the image bytes live in the `avatar_url` column of the `user` table as a `data:<mime>;base64,...` URI, which `serveUserAvatar` decodes via `parseDataURI` (server/router/fileserver/fileserver.go:737) before serving. No filesystem or S3 hop is involved for avatars.
