**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction ...` statements inside the user-deletion transaction in each database driver. There is no database-level rule (the `reaction` table has no foreign key, so no `ON DELETE CASCADE` is possible).

What I checked:

**1. The explicit Go deletion code.** Each store driver has a `DeleteUser` that runs a transaction calling `deleteUserTargetsTx`, which removes reactions in two ways:

- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (reactions the deleted user made): `store/db/sqlite/user_delete.go:400-403`, called at `store/db/sqlite/user_delete.go:102`.
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (reactions from anyone on the deleted user's memos): `store/db/sqlite/user_delete.go:380-388`, called at `store/db/sqlite/user_delete.go:96`.

The same pair exists for the other backends: `store/db/postgres/user_delete.go:383` and `:401`, and `store/db/mysql/user_delete.go:420` and `:438`. The store-layer entry point is `Store.DeleteUser` at `store/user.go:171`, which delegates to the driver.

**2. Ruled out a database-level rule.** The `reaction` table schema defines `creator_id INTEGER NOT NULL` with no `FOREIGN KEY`/`REFERENCES` clause at all, so there is no `ON DELETE CASCADE`:

- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- and the original migrations, e.g. `store/migration/sqlite/0.20/00__reaction.sql`, `store/migration/mysql/0.20/00__reaction.sql`

There's also a test exercising this path at `server/router/api/v1/test/user_service_delete_test.go`.
