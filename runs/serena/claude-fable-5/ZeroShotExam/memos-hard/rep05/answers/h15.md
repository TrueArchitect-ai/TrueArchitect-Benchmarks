Memo visibility is enforced independently on five distinct server surfaces:

1. **gRPC/HTTP API v1 (memo read access check)** — `server/router/api/v1/memo_service.go`. The access-validation helper rejects non-public memos for anonymous users and private memos for non-creators (`memo_service.go:55-66`), and `ListMemos` constrains the store query to `Public` (anonymous) or `Public, Protected` (signed-in non-owner) visibility lists (`memo_service.go:219-225`). The same check pattern is replicated for memo-adjacent API resources in `server/router/api/v1/reaction_service.go` (lines 30-38, 83), `server/router/api/v1/memo_attachment_service.go` (lines 214-222), `server/router/api/v1/attachment_service.go` (lines 445-451), and `server/router/api/v1/memo_service_comments.go` (line 41).

2. **Raw attachment file server** — `server/router/fileserver/fileserver.go`. When serving an attachment binary, it loads the owning memo and enforces visibility: public memos served anonymously only if the instance allows it, otherwise it requires an authenticated user (or a valid share token) and forbids private memos to anyone but the creator or an admin (`fileserver.go:677-702`).

3. **RSS feeds** — `server/router/rss/rss.go`. Both the explore feed and per-user feed hard-code `VisibilityList: []store.Visibility{store.Public}` in their store queries, so only public memos are ever syndicated (`rss.go:90`, `rss.go:141`).

4. **Frontend sitemap** — `server/router/frontend/frontend.go`. `getSitemapXML` lists only `store.Public` memos when generating sitemap URLs, so non-public memo UIDs are never exposed (`frontend.go:150`).

5. **SSE real-time event delivery** — `server/router/api/v1/sse_hub.go`. `SSEClient.canReceive` filters broadcast events server-side: private-memo events are delivered only to the creator or an admin, and unknown visibility values are denied (`sse_hub.go:134-144`).
