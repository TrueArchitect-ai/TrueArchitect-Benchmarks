**Mechanism: explicit Go code** — user deletion runs a transaction that issues `DELETE FROM reaction ...` statements directly; there is no database-level rule (no foreign key or `ON DELETE CASCADE`) on the `reaction` table.

Evidence:

- **Explicit Go deletes (all three DB drivers):** In `store/db/sqlite/user_delete.go`, `deleteUserTargetsTx` (lines 92–127) calls both `deleteReactionsByContentIDsTx` (line 96, removes reactions on the user's memos: `DELETE FROM reaction WHERE content_id IN (...)`, lines 380–388) and `deleteReactionsByCreatorTx` (line 102, removes reactions the user made: `DELETE FROM reaction WHERE creator_id = ?`, lines 400–403), all before deleting the `user` row itself (line 461–464), inside a single transaction begun in `DeleteUser` (line 29). The Postgres and MySQL drivers have the same functions: `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`.
- **No DB-level rule:** The `reaction` table has no foreign keys at all — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — in all three schemas: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. I grepped all `LATEST.sql` files for `FOREIGN KEY`/`CASCADE`; the only cascade in the schema is on `memo_share.memo_id → memo(id)` (e.g. `store/migration/sqlite/LATEST.sql:109`), not on `reaction`.

So both the reactions the deleted user authored and the reactions others left on that user's memos are removed by hand-written SQL in the Go store layer, not by the database.
