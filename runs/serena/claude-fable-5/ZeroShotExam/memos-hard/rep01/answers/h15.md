Memo visibility is enforced independently in five places across four server surfaces (this is the usememos-style server under `server/`):

1. gRPC/Connect API v1 — read-access check on individual memos: `checkMemoReadAccess` in `server/router/api/v1/memo_service.go:38` (public → anyone; non-public → must be authenticated; private → creator only). The same surface also enforces it on listing (`ListMemos` builds a `VisibilityList`/creator filter for anonymous vs. authenticated users, `server/router/api/v1/memo_service.go:219-225`) and repeats the check for memo-adjacent resources (`server/router/api/v1/reaction_service.go:30-38`, `server/router/api/v1/memo_attachment_service.go:213-222`, `server/router/api/v1/attachment_service.go:436-451`).

2. File server (raw attachment bytes over HTTP) — `checkAttachmentPermission` in `server/router/fileserver/fileserver.go:650` (lines 674–702): serves an attachment only if the linked memo is public on an anonymous-allowed instance, a valid non-expired share token for that memo is presented, or the requester is authenticated and (for private memos) is the creator or an admin.

3. RSS feeds — `server/router/rss/rss.go:90` and `server/router/rss/rss.go:141`: the store query is hard-limited to `VisibilityList: []store.Visibility{store.Public}`, so only public memos ever appear in feeds.

4. Frontend/SEO router — `server/router/frontend/frontend.go:150`: the sitemap generator likewise queries only `store.Public` memos, so non-public memo URLs are never exposed.

5. Email notifications — `canViewerAccessMemo` in `server/notification/email.go:306`, applied at `server/notification/email.go:155` and `server/notification/email.go:187`: memo content is only included in a notification email if the receiving user could view the memo (admin → yes; private → creator only; protected → any signed-in user).

The MCP router (`server/router/mcp/`) contains no visibility checks of its own — it adapts onto the API v1 services, which carry the enforcement.
