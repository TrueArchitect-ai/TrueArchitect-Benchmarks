**Yes — but only in one place, a unit test inside the MySQL package itself.**

Evidence:

- The driver-selection factory is `NewDBDriver` in `store/db/db.go:14`, which calls `mysql.NewDB(profile)` at `store/db/db.go:22` when the profile's driver is MySQL. That file is the **only** place outside the `store/db/mysql` package that imports the package at all (verified by grepping all Go files for the `store/db/mysql` import path).
- However, inside the package, `store/db/mysql/auth_config_test.go:12` constructs the driver struct directly with `db := &DB{}` (no `NewDB`, no profile, no connection) in `TestIsRetryableAuthenticationMutationError`, purely to exercise the `IsRetryableAuthenticationMutationError` method against `go-sql-driver/mysql` error codes.
- The only other struct-literal construction is `driver := DB{profile: profile}` at `store/db/mysql/mysql.go:29`, which is inside the `NewDB` constructor itself and thus part of the normal factory path.
- All other test infrastructure goes through the factory: `store/test/store.go:28` and `store/test/store.go:50` call `db.NewDBDriver(profile)`, and `store/test/containers.go` only uses the testcontainers MySQL module and the raw `go-sql-driver/mysql` package (for DSN parsing/waiting), not the repo's MySQL driver type.

So in production code the MySQL driver is constructed exclusively via the factory; the single direct construction is the zero-value `&DB{}` in the package's own test file.
