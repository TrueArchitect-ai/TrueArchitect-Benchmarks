Neither — the premise is wrong. This repository (memos) uses no message broker at all; there is no NATS or RabbitMQ dependency anywhere in the codebase (the only grep hit for "nats" is a coincidental substring in a Catalan translation word in `web/src/locales/ca.json`).

The actual mechanism is an in-process Go channel with worker goroutines, defined entirely in `internal/webhook/webhook.go`:

- The "queue" is a buffered channel declared at `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`.
- The "workers" are four goroutines started in `init()` (`internal/webhook/webhook.go:42-55`) that range over the channel and call `Post()` to deliver each webhook over HTTP.
- Producers enqueue via `PostAsync()` (`internal/webhook/webhook.go:184-196`), which does a non-blocking send and drops (with a warning log) if the queue is full. It's called from the API layer, e.g. `server/router/api/v1/memo_service_webhooks.go`.

So delivery is bounded async dispatch within the server process itself — nothing is consumed from an external broker, and there's no durable queue; undelivered payloads are lost on overflow or restart.
