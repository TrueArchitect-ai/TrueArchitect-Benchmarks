Memo visibility is enforced independently in six server surfaces:

- gRPC/API v1 memo read access (`checkMemoReadAccess` gating GetMemo, plus `VisibilityList` narrowing in ListMemos) — server/router/api/v1/memo_service.go (lines 39–67, 219–225); the same API surface re-checks visibility for comments (server/router/api/v1/memo_service_comments.go:33–41), reactions (server/router/api/v1/reaction_service.go:29–38, 82–83), attachment listing/binding (server/router/api/v1/attachment_service.go:436–451, server/router/api/v1/memo_attachment_service.go:213–222), and mention notifications (server/router/api/v1/memo_mention_helpers.go:62–84)
- Attachment/file HTTP server (checks the linked memo's visibility before serving blobs, with anonymous-access and share-token rules) — server/router/fileserver/fileserver.go (lines ~666–702)
- RSS feeds (queries are hard-restricted to `store.Public` memos only) — server/router/rss/rss.go (lines 90, 141)
- Frontend router sitemap generation (sitemap.xml lists only `store.Public` memos) — server/router/frontend/frontend.go (lines 149–150)
- SSE real-time event delivery (`canReceive` filters events per client by memo visibility/creator/role before fan-out) — server/router/api/v1/sse_hub.go (lines 134–144)
- Email notification pipeline (`canViewerAccessMemo` verifies the recipient may view the memo before emailing about it) — server/notification/email.go (lines 306–320)

The three clearest distinct surfaces are the API v1 service, the file server, and the RSS router; the frontend sitemap, SSE hub, and email notifier are additional independent enforcement points.
