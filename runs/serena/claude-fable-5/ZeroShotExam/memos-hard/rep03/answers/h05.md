**Mechanism: explicit Go code.** When a user is deleted, their reactions are removed by hand-written `DELETE FROM reaction` statements inside the user-deletion transaction in each database driver — not by any database-level rule, since the `reaction` table has no foreign key at all on `creator_id`.

What I checked:

**Go deletion code** — each driver's `DeleteUser` runs a transaction (`deleteUserTargetsTx`) that issues two explicit reaction deletes:
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (removes the deleted user's own reactions): `store/db/sqlite/user_delete.go:400-403`, `store/db/mysql/user_delete.go:438`, `store/db/postgres/user_delete.go:401`
- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` (removes anyone's reactions on the user's memos, keyed by `"memos/"+uid` content IDs): `store/db/sqlite/user_delete.go:380-388`, `store/db/mysql/user_delete.go:420`, `store/db/postgres/user_delete.go:383`

The call ordering is visible in `deleteUserTargetsTx` at `store/db/sqlite/user_delete.go:92-127`, invoked from `DeleteUser` at line 29 (the store-level wrapper is `store/user.go:171`).

**Database schema** — the `reaction` table definition has no `FOREIGN KEY` / `ON DELETE CASCADE` clause in any dialect; its only constraint is `UNIQUE(creator_id, content_id, reaction_type)`:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

(For contrast, `memo_share` in the same files *does* use `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE`, e.g. `store/migration/sqlite/LATEST.sql:109` — so the schema uses cascades elsewhere but deliberately not for reactions.) A grep for `REFERENCES` across all `LATEST.sql` files confirmed no FK references the `user` or `reaction` tables.
