**Yes** — in one place, a unit test inside the mysql package itself.

Evidence:

- The driver-selection factory is `NewDBDriver` in `store/db/db.go:14`, which calls `mysql.NewDB(profile)` at `store/db/db.go:22`. That is the only call to the driver's constructor outside its own package: `grep -rn "mysql.NewDB"` across the repo hits only `store/db/db.go:22` and the definition at `store/db/mysql/mysql.go:20`.
- However, the driver struct (`type DB struct` in `store/db/mysql/mysql.go:14`) is constructed directly — bypassing both the factory and `NewDB` — in `store/db/mysql/auth_config_test.go:12`: `db := &DB{}`, used by `TestIsRetryableAuthenticationMutationError` to call `db.IsRetryableAuthenticationMutationError(...)` on a zero-value driver.
- All other consumers go through the factory: the integration test harness uses `db.NewDBDriver(profile)` (`store/test/store.go:28` and `:50`), and no other file imports `store/db/mysql` besides `store/db/db.go:8`.

So in production code the MySQL driver is only ever built via the factory, but it is directly instantiated (as a bare `&DB{}` struct literal) in the package's own test file.
