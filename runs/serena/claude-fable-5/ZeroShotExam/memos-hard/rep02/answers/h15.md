The memos server enforces memo visibility (public / protected / private) at several independent surfaces, each with its own check:

- gRPC/Connect API read access (`checkMemoReadAccess`: private → creator only, non-public → must be authenticated; used by GetMemo, GetMemoComments, parent lookups) — `server/router/api/v1/memo_service.go:39` (list-side filtering to Public/Protected for ListMemos at `server/router/api/v1/memo_service.go:219-225`)
- API v1 sibling services re-checking visibility on memo-scoped reads (reactions, memo attachments, attachment listing) — `server/router/api/v1/reaction_service.go:30`, `server/router/api/v1/memo_attachment_service.go:214`, `server/router/api/v1/attachment_service.go:445`
- File/attachment HTTP serving (checks the owning memo's visibility, allows anonymous only for public memos on instances that allow it, supports a share-token fallback, forbids private memos' files to non-creator/non-admin) — `server/router/fileserver/fileserver.go` (roughly lines 666–705)
- RSS feeds (explore and per-user feeds hard-restrict queries to `VisibilityList: []store.Visibility{store.Public}`) — `server/router/rss/rss.go:90` and `server/router/rss/rss.go:141`
- Frontend sitemap generation (only public memos are listed in sitemap.xml) — `server/router/frontend/frontend.go:150`
- SSE realtime event delivery (`canReceive` filters memo events per subscriber: private events only to the creator or an admin) — `server/router/api/v1/sse_hub.go:134-144`
- Inbox/notification API (`canViewerAccessMemo` gates whether notification payloads expose memo content to the viewer) — `server/router/api/v1/user_service_notifications.go:302`
- Email notifications (a separate `canViewerAccessMemo` copy suppresses memo content in emails the receiver isn't allowed to see) — `server/notification/email.go:306`

So beyond the primary API check, the same policy is independently enforced in the fileserver, RSS, frontend sitemap, SSE hub, and notification (inbox + email) paths.
