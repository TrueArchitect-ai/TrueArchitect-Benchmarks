**Tables affected: `memo`, `memo_relation`, `attachment`**

`Store.DeleteMemo` (`store/memo.go:140-159`) performs the explicit cascade:

1. **`memo_relation`** — two `driver.DeleteMemoRelation` calls remove rows where the memo is the source (`MemoID`) or the target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL in e.g. `store/db/sqlite/memo_relation.go:149`).
2. **`attachment`** — it lists attachments for the memo and deletes each via `Store.DeleteAttachment` (`store/memo.go:148-157`), which removes the storage blob and then the row (`store/attachment.go:132-149`, `store/db/sqlite/attachment.go:212`).
3. **`memo`** — finally `driver.DeleteMemo` runs `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`).

The API-level `DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) additionally deletes all comment memos first by calling `Store.DeleteMemo` for each comment relation, but that only touches the same three tables again.

Two adjacent notes: **`memo_share`** rows are removed too, but only via a database-level `FOREIGN KEY ... ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`), not by explicit cascade code; and **`reaction`** rows are only *listed* for the deletion webhook (`memo_service.go:545`) — no code in this path deletes them.
