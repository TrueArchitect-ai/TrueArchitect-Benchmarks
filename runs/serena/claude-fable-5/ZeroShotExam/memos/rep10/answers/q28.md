**Runners the server actually starts** (`Server.startBackgroundRunners`, `server/server.go:153-174` — called from `Server.Start` at `server/server.go:129`):

- **s3presign runner** (`server/runner/s3presign/runner.go`) — this is the *only* background runner the server starts. Trigger: it is run once immediately at startup (`RunOnce(ctx)`, `server/server.go:163`), then a goroutine runs `Run(ctx)`, which is driven by a `time.NewTicker` firing every 12 hours (`const runnerInterval = time.Hour * 12`, `server/runner/s3presign/runner.go:26-40`), until its per-runner cancel context is cancelled at shutdown.

For completeness, two other background loops exist but are not server-level "runners": each `cache.New` in the store layer spawns a `cleanupLoop` goroutine on a 5-minute ticker (`store/cache/cache.go:83,199`, interval set in `store/store.go:42`), and each SSE connection runs a per-connection heartbeat ticker (`server/router/api/v1/sse_handler.go:64`).

**Unused scheduling infrastructure:**

- **`memopayload` runner** (`server/runner/memopayload/runner.go`) is runner-shaped infrastructure (`NewRunner` + `RunOnce`, which batch-rebuilds the payload of all memos) that the server **never starts** — `memopayload.NewRunner` has zero callers in the codebase. Only the package's plain helper function `RebuildMemoPayload` is used, called synchronously from the memo API service on memo create/update (`server/router/api/v1/memo_service.go:108,447`). It also has no periodic `Run` loop of its own — even if wired up it would be one-shot.

No cron library or other scheduler dependency exists in `go.mod`; all scheduling is plain `time.Ticker`.
