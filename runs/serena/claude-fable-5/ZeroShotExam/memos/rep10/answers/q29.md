Frontend requests are authenticated by a Connect RPC interceptor:

- **Interceptor path:** `web/src/connect.ts` — the `authInterceptor` (line 156) is installed on the Connect transport for all service clients. It calls `getRequestToken()` and sets an `Authorization: Bearer <token>` header, does a preflight refresh if the token is near expiry, and on a 401 (`Code.Unauthenticated`) refreshes once and retries (marked with an `X-Retry` header) before redirecting to login.
- **Token kinds:** two tokens are managed — a short-lived **JWT access token** (kept in client auth state via `web/src/auth-state.ts` and sent as a Bearer header) and a **refresh token** (sent as a cookie via `credentials: "include"`, used by `refreshAccessToken()` through a separate interceptor-free transport calling `AuthService.RefreshToken`). The backend additionally accepts long-lived Personal Access Tokens over the same Bearer header, though the web interceptor itself only handles access/refresh tokens.
- **Backend validation package:** `server/auth` (`github.com/usememos/memos/server/auth`) — the `Authenticator` in `server/auth/authenticator.go` validates JWT access tokens statelessly (`AuthenticateByAccessTokenV2`, token parsing in `server/auth/token.go`), plus refresh tokens and PATs against the store; it's shared by the gRPC/Connect interceptors and the file server.
