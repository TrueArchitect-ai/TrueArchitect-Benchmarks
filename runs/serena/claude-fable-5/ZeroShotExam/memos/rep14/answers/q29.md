Frontend API requests are authenticated by a Connect RPC interceptor:

- **Interceptor:** `web/src/connect.ts` — the `authInterceptor` (defined at `web/src/connect.ts:156`) is registered on the Connect transport (`web/src/connect.ts:184-189`) that all service clients use. It attaches an `Authorization: Bearer <token>` header via `setAuthorizationHeader`, and on a `Code.Unauthenticated` error it refreshes the token once (marked with an `X-Retry` header to prevent loops) and retries, redirecting to login if refresh fails.

- **Tokens managed:** two kinds of JWTs.
  - A **short-lived access token** (15-minute lifetime) held in memory/storage via `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`, with expiry preflight checks and cross-tab sharing over a BroadcastChannel).
  - A **long-lived refresh token** (30 days) stored in an HTTP-only cookie (`memos_refresh`), sent automatically because the transport uses `fetch` with `credentials: "include"`; the interceptor calls `AuthService.refreshToken` through a separate no-interceptor transport (`refreshTransport`) to obtain new access tokens.

- **Backend validation:** the Go package `server/auth` (notably `server/auth/authenticator.go` and `server/auth/token.go`). Its `Authenticator` validates the JWT access tokens statelessly (`AuthenticateByAccessTokenV2`/`ParseAccessTokenV2`), validates refresh tokens against the database, and also supports Personal Access Tokens (`memos_pat_` prefix). It's shared by the gRPC/Connect interceptors in `server/router/api/v1` and the file server (`server/router/fileserver`).

**Answer:** `web/src/connect.ts` (authInterceptor); short-lived JWT access tokens (15 min, Bearer header) + long-lived refresh tokens (30 days, `memos_refresh` cookie) — the backend additionally accepts PATs; `server/auth`.
