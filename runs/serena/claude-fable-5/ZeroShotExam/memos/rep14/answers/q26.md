**Tables affected: `memo`, `memo_relation`, `attachment`** (plus `memo_share` via a database-level `ON DELETE CASCADE`, not application code).

Details of the delete path in `store.DeleteMemo` (`store/memo.go:140-159`):

- **`memo_relation`** — explicit cascade code: `store/memo.go:142-147` calls `driver.DeleteMemoRelation` twice (once for `MemoID`, once for `RelatedMemoID`), executing `DELETE FROM memo_relation` (`store/db/sqlite/memo_relation.go:149`, with mysql/postgres equivalents).
- **`attachment`** — explicit cascade code: `store/memo.go:149-157` lists the memo's attachments and deletes each via `store.DeleteAttachment` (`store/attachment.go:132-149`), which runs `DELETE FROM attachment` (`store/db/sqlite/attachment.go:211-221`). This also removes the attachment's blob from local/S3 storage, but that's filesystem/object storage, not a table.
- **`memo`** — the direct delete: `driver.DeleteMemo` runs `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`, `store/db/postgres/memo.go:246`, `store/db/mysql/memo.go:261`).
- **`memo_share`** — affected too, but by the database schema rather than Go code: `memo_share.memo_id` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`).

Two notes: the API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally deletes each comment memo by calling `store.DeleteMemo` recursively (`memo_service.go:573-577`), which touches the same tables. The `reaction` table is **not** cleaned up — reactions are only listed to build the webhook payload (`memo_service.go:545-550`), and no cascade exists for them.
