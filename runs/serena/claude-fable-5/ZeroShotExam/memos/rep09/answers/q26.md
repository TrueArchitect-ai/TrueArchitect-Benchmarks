**Tables: `memo`, `memo_relation`, `attachment`** (plus `memo_share` via a schema-level FK cascade, if that counts).

Details:

- `store.Store.DeleteMemo` (`store/memo.go:140`) contains the explicit cascade code. Before deleting the memo row it:
  - deletes `memo_relation` rows where the memo is either side of the relation (two `driver.DeleteMemoRelation` calls — see `store/db/sqlite/memo_relation.go:149`),
  - lists and deletes each linked `attachment` row via `Store.DeleteAttachment` (`store/attachment.go`, `store/db/sqlite/attachment.go:212`), which also removes the stored file blob,
  - finally issues `DELETE FROM memo` (`store/db/sqlite/memo.go:237`, with equivalents in `store/db/postgres/memo.go` and `store/db/mysql/memo.go`).
- The API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally finds comment memos (`memo_relation` type `COMMENT`) and calls `store.DeleteMemo` on each, so comment memos hit the same three tables recursively.
- `memo_share` is not touched by any Go code in this path, but its schema declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, same in the postgres and mysql `LATEST.sql`), so share rows are removed by the database when the memo row is deleted.
- `reaction` rows are only *read* (for the deletion webhook payload) — they are not deleted, and the reaction table has no FK cascade.
