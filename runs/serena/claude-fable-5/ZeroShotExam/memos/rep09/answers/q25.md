**Engine:** CEL (Common Expression Language) via `github.com/google/cel-go` — the parsing/rendering engine lives in the in-repo package `internal/filter/` (`engine.go`, `parser.go`, `ir.go`, `render.go`, `schema.go`).

**Mechanism:** `ListMemos` (`server/router/api/v1/memo_service.go:211-215`) validates the filter string and appends it to `MemoFind.Filters`; each store driver (`store/db/sqlite/memo.go:57-61`, `store/db/mysql/memo.go:65-69`, `store/db/postgres/memo.go:54-58`) calls `filter.AppendConditions` (`internal/filter/helpers.go`) with its own `DialectName` (`sqlite`/`mysql`/`postgres`, defined in `internal/filter/schema.go`). Under the hood, `Engine.Compile` (`internal/filter/engine.go`) compiles the CEL expression against a schema-defined CEL environment and converts the parsed AST into a dialect-agnostic condition tree (IR in `internal/filter/ir.go`, built by `parser.go`); then a `renderer` (`internal/filter/render.go`) walks that tree and emits dialect-specific parameterized SQL (`Statement{SQL, Args}`), switching on the dialect for things like JSON extraction, timestamp accessors, and string/array functions, with per-dialect column expressions declared in `schema.go`. The resulting fragments are appended as `WHERE` clauses with placeholder args.

**One-sentence summary:** The filter is a CEL expression parsed by google/cel-go inside the in-repo `internal/filter` package, which lowers the CEL AST to a neutral condition-tree IR and then renders it into parameterized SQL per dialect (SQLite/MySQL/Postgres) via `filter.AppendConditions` called from each store driver.
