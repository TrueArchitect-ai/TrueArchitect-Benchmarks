**Tables: `memo`, `memo_relation`, `attachment` (plus `memo_share` via a schema-level `ON DELETE CASCADE`).**

Details:

- `store.DeleteMemo` (`store/memo.go:140-159`) contains the explicit cascade code: it first deletes `memo_relation` rows where the memo is either the source (`MemoID`) or target (`RelatedMemoID`), then lists and deletes each linked `attachment` (via `Store.DeleteAttachment`, which removes the row from the `attachment` table — `store/db/sqlite/attachment.go:211` — and also the file/blob storage), and finally calls the driver's `DeleteMemo`, which runs only `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, same in `store/db/mysql/memo.go:259` and `store/db/postgres/memo.go:244`).
- The API-layer `DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally loops over comment memos and calls `store.DeleteMemo` for each, so the same three tables are hit for every comment too — but no new tables.
- `memo_share` is not touched by any Go code; it is cleaned up by the database itself through the only foreign key in the current schema: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`).
- Notably, `reaction` rows are *not* deleted — the API handler only lists reactions to build the webhook payload (`memo_service.go:545`), so that table is unaffected.
