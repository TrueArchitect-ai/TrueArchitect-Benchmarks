**Tables affected: `memo`, `memo_relation`, `attachment`**

`Store.DeleteMemo` (`store/memo.go:140-159`) performs explicit cascade cleanup before deleting the memo row itself:

1. **`memo_relation`** — deleted twice via `driver.DeleteMemoRelation`, once for rows where the memo is the source (`MemoID`) and once where it is the target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL in e.g. `store/db/sqlite/memo_relation.go:137`).
2. **`attachment`** — all attachments linked to the memo are listed and deleted via `Store.DeleteAttachment` (`store/memo.go:149-157`), which deletes the `attachment` row (`store/db/sqlite/attachment.go:211-221`) and also removes the underlying file from local/S3 storage (`store/attachment.go:132-148` — a filesystem/object-store side effect, not a table).
3. **`memo`** — finally the memo row itself (`store/db/sqlite/memo.go:237-248`).

Note that the API-level handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) additionally deletes comment memos by calling `Store.DeleteMemo` for each comment relation, but that just re-runs the same cascade over the same three tables. It *lists* reactions (`reaction` table) only to build the webhook payload — it does not delete them, so `reaction` (and `memo_organizer`) rows are not touched by this code path.
