**Tables affected: `memo`, `memo_relation`, `attachment`** (plus `memo_share` via a schema-level FK cascade, if that counts — see below).

The call chain:

- **API layer** — `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first deletes all comment memos (it lists `memo_relation` rows of type comment and calls `store.DeleteMemo` for each, lines 567–577), then deletes the memo itself (line 580). Both go through the same store method, so the same tables are hit.
- **Store layer** — `Store.DeleteMemo` (`store/memo.go:140`) contains the explicit cascade code:
  - `driver.DeleteMemoRelation` twice (by `MemoID` and by `RelatedMemoID`) → deletes from **`memo_relation`** (`store/db/sqlite/memo_relation.go:149`)
  - lists attachments and calls `Store.DeleteAttachment` for each → deletes rows from **`attachment`** (`store/db/sqlite/attachment.go:212`; also removes the local/S3 file blob, which is storage, not a table — `store/attachment.go:132–148`)
  - finally `driver.DeleteMemo` → `DELETE FROM memo` — the **`memo`** table (`store/db/sqlite/memo.go:237`, same in `store/db/mysql/memo.go:259` and `store/db/postgres/memo.go:244`)

Two clarifications:

- **`memo_share`** is also emptied for that memo, but by a database-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in the schema (`store/migration/sqlite/LATEST.sql:109`), not by explicit Go code. Include it if schema cascades count.
