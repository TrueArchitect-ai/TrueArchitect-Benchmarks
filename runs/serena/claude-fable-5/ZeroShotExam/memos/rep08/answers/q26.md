**Tables affected: `memo`, `memo_relation`, `attachment`**

Tracing the call chain:

1. **API layer** — `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) first deletes any comment memos (each via `store.DeleteMemo`, `memo_service.go:573-577`), then deletes the memo itself (`memo_service.go:580`). Reactions and shares are only *listed* here (for the webhook payload), not deleted.

2. **Store layer** — `Store.DeleteMemo` (`store/memo.go:140`) contains the explicit cascade code:
   - Deletes `memo_relation` rows where the memo is source or target (`store/memo.go:142-147`, executed in the driver at e.g. `store/db/sqlite/memo_relation.go:149`).
   - Deletes each linked attachment via `Store.DeleteAttachment` (`store/memo.go:149-157`), which removes rows from the `attachment` table (`store/db/sqlite/attachment.go:212`; the storage-blob cleanup in `store/attachment.go:141` is filesystem/S3, not a table).
   - Finally deletes the row from `memo` (`store/db/sqlite/memo.go:239`, same pattern in the mysql/postgres drivers).

Other memo-adjacent tables (`reaction`, `memo_share`, `inbox`) are **not** touched by the DeleteMemo path — they are only cleaned up in the separate user-deletion code (`store/db/sqlite/user_delete.go`).
