**Runners the server actually starts** (all in `Server.startBackgroundRunners`, `server/server.go:153-174`, called from `Server.Start`):

- `s3presign.Runner` (`server/runner/s3presign/runner.go`) — the only background runner the server starts. It is run once immediately at startup (`RunOnce(ctx)` at `server/server.go:163`), then continuously in a goroutine whose scheduling is a `time.NewTicker` with `runnerInterval = 12 * time.Hour` (`server/runner/s3presign/runner.go:26-40`), stopped via a per-runner `context.CancelFunc` on shutdown.

**Unused scheduling infrastructure:**

- `memopayload.Runner` (`server/runner/memopayload/runner.go`) — a second runner package with the same `NewRunner`/`RunOnce` shape exists, but the server never constructs or starts it: there are no calls to `memopayload.NewRunner` or `Runner.RunOnce` anywhere in the codebase. Only its standalone helper function `RebuildMemoPayload` is used, and that is invoked synchronously from API request handlers (`server/router/api/v1/memo_service.go:108` and `:447`), not as a background job. Unlike s3presign, it also has no ticker/`Run` loop at all — it's one-shot-only infrastructure that nothing invokes.

Incidental note (not part of `startBackgroundRunners`): each in-memory cache created by the store spawns its own cleanup goroutine on a 5-minute ticker (`store/cache/cache.go:83, 199-207`, constructed in `store/store.go:51-53`), but that's internal to the cache, not a server-managed runner. Per-SSE-connection heartbeat tickers (`server/router/api/v1/sse_handler.go:64`) are likewise request-scoped, not background workers.
