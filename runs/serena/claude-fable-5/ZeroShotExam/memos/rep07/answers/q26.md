**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`.**

When `DeleteMemo` runs (API handler `server/router/api/v1/memo_service.go:518` → store method `store/memo.go:140`):

- **`memo`** — the target row is deleted directly by the driver (`store/db/sqlite/memo.go:237`). The API handler also deletes all comment memos of the target first, each through the same `store.DeleteMemo` path (`server/router/api/v1/memo_service.go:567-577`), so multiple `memo` rows can go.
- **`memo_relation`** — explicit cascade code in `Store.DeleteMemo` deletes relations where the memo is either the source (`MemoID`) or the target (`RelatedMemoID`) (`store/memo.go:142-147`).
- **`attachment`** — explicit cascade code lists the memo's attachments and deletes each one (rows plus their backing storage) via `Store.DeleteAttachment` (`store/memo.go:149-157`, `store/attachment.go:132`).
- **`memo_share`** — cleaned up not by Go code but by an explicit schema-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:102-109`, same in the postgres/mysql schemas; the migration `store/migration/sqlite/0.27/04__memo_share.sql` even comments that this is the intended cleanup mechanism).

Notably **not** deleted: `reaction` rows — the handler only *lists* reactions to build the deleted-memo webhook payload (`memo_service.go:545-550`); nothing removes them, and the `reaction` table has no FK cascade.
