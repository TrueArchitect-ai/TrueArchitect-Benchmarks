**Tables affected: `memo_relation`, `attachment`, `memo`**

`Store.DeleteMemo` (`store/memo.go:140-159`) runs explicit cascade code before deleting the memo row:

1. **memo_relation** — deleted for both directions (where the memo is `memo_id` and where it is `related_memo_id`), lines 142–147.
2. **attachment** — all attachments linked to the memo are listed and deleted via `Store.DeleteAttachment` (`store/attachment.go:132`), which also removes the underlying file from local/S3 storage (not a table).
3. **memo** — finally the memo row itself is deleted via the driver (e.g. `store/db/sqlite/memo.go:237`, a plain `DELETE FROM memo WHERE id = ?` with no SQL-level cascades).

Additionally, the API-layer handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:568-582`) first finds comment memos (rows in `memo_relation` of type comment) and calls `Store.DeleteMemo` for each — so comment rows in the same three tables are cascaded too. No other tables (e.g. `reaction`, `memo_share`) are deleted by this path — reactions are only read to build the webhook payload.
