The browser hits `GET /file/users/{username}/avatar` (route registered at `server/router/fileserver/fileserver.go:124`). The avatar itself is stored as a data URI in the user row's `avatar_url` column, so the "stored data" is reached through the user store. Hops:

- `FileServerService.serveUserAvatar` (serving handler; auth check for private instances, then decodes the data URI and writes the image bytes) — `server/router/fileserver/fileserver.go:168`
- `FileServerService.getUserByUsername` (wraps the lookup in a `FindUser{Username}`) — `server/router/fileserver/fileserver.go:715`
- `Store.GetUser` (cache-aware lookup; delegates to `ListUsers`) — `store/user.go:148`
- `Store.ListUsers` (calls the DB driver, populates the user cache) — `store/user.go:136`
- `DB.ListUsers` (driver-level SQL that reads the user row, including `avatar_url`, from the database) — `store/db/sqlite/user.go:88` (equivalently `store/db/mysql/user.go:84` / `store/db/postgres/user.go:87` depending on the configured driver)

Back in the handler, `parseDataURI` (`server/router/fileserver/fileserver.go:196`) decodes `user.AvatarURL` and the bytes are returned via `c.Blob` after a MIME allowlist check (`avatarAllowedTypes`, `server/router/fileserver/fileserver.go:75`).
