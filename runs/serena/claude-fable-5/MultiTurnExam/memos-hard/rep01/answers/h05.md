h05.

**Mechanism: explicit Go code** — reactions are deleted by application-level SQL inside the user-deletion transaction, not by any database rule.

Evidence:

1. **Explicit deletion code in all three DB drivers.** Each driver's user-deletion flow removes reactions two ways inside the same transaction: reactions the user *made* (`DELETE FROM reaction WHERE creator_id = ?` in `deleteReactionsByCreatorTx`) and reactions *on the user's content* (`DELETE FROM reaction WHERE content_id IN (...)` in `deleteReactionsByContentIDsTx`). See:
   - `store/db/sqlite/user_delete.go:96`, `:102` (call sites) and `:380`, `:400` (implementations)
   - `store/db/mysql/user_delete.go:96`, `:102`, `:417`, `:437`
   - `store/db/postgres/user_delete.go:96`, `:102`, `:380`, `:400`

2. **No database-level rule exists for the reaction table.** The `reaction` table has no foreign keys at all — just a UNIQUE constraint (`store/migration/sqlite/LATEST.sql:92-99`, and the same in `store/migration/mysql/LATEST.sql` and `store/migration/postgres/LATEST.sql`; original migration `store/migration/sqlite/0.20/00__reaction.sql`). The only `ON DELETE CASCADE` anywhere in the schemas belongs to `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109`, `mysql/LATEST.sql:108`, `postgres/LATEST.sql:108`), which cascades on memo deletion, not user deletion.
