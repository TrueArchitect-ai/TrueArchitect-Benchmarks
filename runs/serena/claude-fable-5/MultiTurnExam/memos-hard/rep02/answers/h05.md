**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside the user-deletion transaction in each database driver, not by any database-level rule (the `reaction` table has no foreign keys at all).

Evidence locations:

1. **Explicit Go deletion code** — each driver's `user_delete.go` deletes reactions in two passes inside `deleteUserTargetsTx`: reactions *on* the user's memos (`deleteReactionsByContentIDsTx`, `DELETE FROM reaction WHERE content_id IN ...`) and reactions *created by* the user (`deleteReactionsByCreatorTx`, `DELETE FROM reaction WHERE creator_id = ?`):
   - `store/db/sqlite/user_delete.go:96,102` (call sites) and `:380,:400` (helpers)
   - `store/db/postgres/user_delete.go:383,401`
   - `store/db/mysql/user_delete.go:420,438`

2. **No database-level rule exists for this table** — the `reaction` table definitions have no `FOREIGN KEY` clauses (so no `ON DELETE CASCADE` could apply):
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`

   This contrasts with other tables in the same schemas (e.g. `memo`, `user_setting`) that do use `FOREIGN KEY ... REFERENCES user(id) ON DELETE CASCADE` — reactions deliberately rely on application code instead, which also makes sense since `content_id` is a text UID that couldn't carry an FK to the user anyway.
