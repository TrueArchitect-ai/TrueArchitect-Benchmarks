The browser hits `GET /file/users/:identifier/avatar` (route registered at `server/router/fileserver/fileserver.go:124`). The avatar bytes live as a base64 data-URI in the user row's `avatar_url` column, so the data layer is the user table. Hops:

1. `FileServerService.serveUserAvatar` — `server/router/fileserver/fileserver.go:168` (Echo handler: optional auth check on private instances, then looks up the target user and decodes the avatar)
2. `FileServerService.getUserByUsername` — `server/router/fileserver/fileserver.go:715` (wraps the path's `:identifier` into a `store.FindUser{Username: ...}`)
3. `Store.GetUser` — `store/user.go:148` (checks `userCache`, else delegates to `ListUsers` and populates the cache)
4. `Store.ListUsers` — `store/user.go:136` (calls the database driver through the `store.Driver` interface, declared in `store/driver.go:47`)
5. `DB.ListUsers` — `store/db/sqlite/user.go:88` (or the equivalent `store/db/mysql/user.go` / `store/db/postgres/user.go` per configured driver; runs `SELECT ... FROM user WHERE username = ?`, returning the row including `avatar_url`)

Back in the handler, `parseDataURI` (`server/router/fileserver/fileserver.go:196`) decodes `user.AvatarURL` into MIME type + raw bytes, the type is checked against `avatarAllowedTypes` (`fileserver.go:75`), and the image is written with `c.Blob(...)` — no separate blob/attachment storage is involved for profile images.
