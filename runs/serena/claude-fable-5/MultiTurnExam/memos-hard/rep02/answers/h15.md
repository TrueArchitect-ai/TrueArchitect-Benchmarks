Memo visibility is enforced independently at these distinct server surfaces:

1. **gRPC/API memo service (read path)** — `GetMemo`'s access check denies non-public memos to anonymous users and private memos to non-creators (`server/router/api/v1/memo_service.go:55-66`); list endpoints constrain the query itself via `VisibilityList` / CEL filters (`memo_service.go:219-225`, `memo_service_converter.go:184-186`).
2. **Reaction service** — viewing/creating reactions re-checks the target memo's visibility (`server/router/api/v1/reaction_service.go:30,38,83`).
3. **Attachment API service** — access to an attachment is gated by the linked memo's visibility (`server/router/api/v1/attachment_service.go:436-451`, also 255).
4. **Memo relation service** — related-memo listings are filtered to `PUBLIC`/`PROTECTED` or own memos (`server/router/api/v1/memo_relation_service.go:109-111`).
5. **File server (raw blob serving over HTTP)** — serving attachment bytes checks the owning memo: public + anonymous-allowed passes, share-token fallback, otherwise authenticated and private-only-for-creator/admin (`server/router/fileserver/fileserver.go:674-699`).
6. **SSE event hub** — server-side delivery filtering: `SSEClient.canReceive` drops `Private` memo events for anyone but the creator or an admin (`server/router/api/v1/sse_hub.go:134-143`).
7. **RSS feeds** — feed queries hard-restrict to `store.Public` (`server/router/rss/rss.go:90,141`).
8. **Frontend router (sitemap/meta)** — sitemap generation lists only public memos (`server/router/frontend/frontend.go:150`).
9. **Notification/email path** — mention notifications respect visibility before notifying (`server/notification/email.go:313-316`, `server/router/api/v1/user_service_notifications.go:309-312`).

So the same rule (Public > Protected [any authenticated user] > Private [creator/admin only]) is re-implemented at the API layer, the raw file server, the realtime SSE fan-out, and the public-content surfaces (RSS/sitemap), plus reaction/attachment/relation sub-services.
