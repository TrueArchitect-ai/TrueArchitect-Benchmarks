**Mechanism: explicit Go code — each database driver's `DeleteUser` transaction issues `DELETE FROM reaction ...` statements itself; there is no database-level cascade.**

Evidence checked:

- **Explicit deletion code:** each driver's `DeleteUser` (e.g. `store/db/sqlite/user_delete.go:29`) runs a transaction that calls two reaction cleanup helpers: `deleteReactionsByContentIDsTx` (`DELETE FROM reaction WHERE content_id IN ...`, removing reactions on the user's memos) and `deleteReactionsByCreatorTx` (`DELETE FROM reaction WHERE creator_id = ?`, removing reactions the user made). Locations:
  - SQLite: `store/db/sqlite/user_delete.go:96,102,380-401`
  - MySQL: `store/db/mysql/user_delete.go:96,102,417-438`
  - Postgres: `store/db/postgres/user_delete.go:96,102,380` (same pair of helpers)
- **No database-level rule:** the `reaction` table schema has no foreign keys at all — just plain `creator_id INTEGER NOT NULL` / `content_id TEXT NOT NULL` columns with a UNIQUE constraint and no `FOREIGN KEY ... ON DELETE CASCADE`. Checked `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:91-98`, and the MySQL equivalent in `store/migration/mysql/LATEST.sql` (plus the original `0.20/00__reaction.sql` and `0.23/00__reactions.sql` migrations). So the database could not cascade these deletes even in principle; the Go code has to do it, and does.
