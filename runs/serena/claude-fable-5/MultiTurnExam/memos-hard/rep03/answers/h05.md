**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside each driver's `DeleteUser` transaction, not by any database-level rule.

Evidence I checked:

1. **Explicit deletion code.** Each of the three drivers has a `user_delete.go` with two reaction-cleanup helpers, both invoked from the `DeleteUser` transaction (e.g., `store/db/sqlite/user_delete.go:96` and `:102`):
   - `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` removes the user's own reactions (`store/db/sqlite/user_delete.go:400-403`, `store/db/mysql/user_delete.go:438`, `store/db/postgres/user_delete.go:401`).
   - `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)` removes other users' reactions left on the deleted user's memos, in batches (`store/db/sqlite/user_delete.go:380-388`, `store/db/mysql/user_delete.go:420`, `store/db/postgres/user_delete.go:383`).

2. **No database-level rule exists.** The `reaction` table schema has no foreign keys at all — hence no `ON DELETE CASCADE` — in any dialect: `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, and the original migrations (`store/migration/sqlite/0.20/00__reaction.sql`, `store/migration/postgres/0.20/00__reaction.sql`). The table declares only a primary key and a `UNIQUE(creator_id, content_id, reaction_type)` constraint, so the Go code is the only cleanup mechanism.

The entry point is `Store.DeleteUser` (`store/user.go:171`) dispatching to the driver interface's `DeleteUser` (`store/driver.go:48`).
