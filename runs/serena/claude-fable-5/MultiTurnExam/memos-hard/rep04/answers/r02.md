**Premise correction:** there is no per-user API rate-limiting middleware in this codebase — nothing to register and no request limits to report. Searching the backend for rate-limiter/throttle code finds no such middleware; the only Echo middleware installed globally are things like `middleware.Recover()` (`server/server.go:51`), plus CORS/logging setup — no `middleware.RateLimiter` or custom equivalent anywhere.

What does exist are narrower concurrency/abuse controls that are not per-user request rate limits:

- **Concurrency semaphores**, not rate limits: thumbnail generation is capped by `thumbnailSemaphore` (`server/router/fileserver/fileserver.go:107,116,447-449`), and the API service holds `thumbnailSemaphore` (3) and `imageProcessingSemaphore` (2) (`server/router/api/v1/v1.go:40-41,59-60`). These bound simultaneous expensive operations instance-wide, not requests per user.
- **Bounded webhook dispatch queue** (128-item channel, 4 workers) in `internal/webhook/webhook.go:39-55` — backpressure on outbound deliveries, again not inbound API limiting.
- **SSE slow-client drop** (`server/router/api/v1/sse_hub.go`) discards events for slow consumers.

So if per-user API rate limiting is required for a deployment, it would have to be added (or provided by a reverse proxy in front of the server); the repo itself ships none.
