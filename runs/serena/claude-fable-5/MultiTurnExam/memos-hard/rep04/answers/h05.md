**Mechanism: explicit Go code** — reactions are deleted by hand-written SQL inside each database driver's user-deletion transaction, not by any database-level rule.

Evidence checked:

1. **Explicit deletion code (all three drivers).** Each driver's `user_delete.go` deletes reactions in two passes inside the delete-user transaction: `deleteReactionsByContentIDsTx` (removes reactions on the user's own memos, `DELETE FROM reaction WHERE content_id IN ...`) and `deleteReactionsByCreatorTx` (removes reactions the user made elsewhere, `DELETE FROM reaction WHERE creator_id = ?`). See `store/db/sqlite/user_delete.go:380-403` (called at lines 96 and 102), `store/db/postgres/user_delete.go:383,401`, and `store/db/mysql/user_delete.go:420,438`.

2. **No database-level rule for reactions.** The `reaction` table schema has no foreign keys at all — just a UNIQUE constraint on `(creator_id, content_id, reaction_type)` — so nothing cascades from `user` (or `memo`) deletion. See `CREATE TABLE reaction` in `store/migration/sqlite/LATEST.sql` (and the matching postgres/mysql `LATEST.sql`). The only `ON DELETE CASCADE` in each schema is on `memo_id REFERENCES memo(id)` for a different table (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`), not on `reaction`.
