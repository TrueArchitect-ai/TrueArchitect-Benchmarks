**Engine: Google CEL (`github.com/google/cel-go`), wrapped by the `internal/filter` package — `internal/filter/engine.go`**

**Mechanism:** the filter string is parsed by a CEL environment whose variables (`content`, `creator`, `creator_id`, `visibility`, `tag`, timestamps, …) are declared in `internal/filter/schema.go`, converted into a dialect-agnostic condition tree (the IR in `internal/filter/ir.go`, built by `internal/filter/parser.go`), and then rendered to parameterized SQL per backend by `internal/filter/render.go`, which switches on `DialectSQLite` / `DialectPostgres` / `DialectMySQL` to emit the right functions and placeholder style.

Wiring details:
- `Engine.CompileToStatement` (`internal/filter/engine.go:74`) returns a `Statement{SQL, Args}` for a given `RenderOptions{Dialect, PlaceholderOffset}`.
- Each driver calls the shared helper `filter.AppendConditions` (`internal/filter/helpers.go:9`), which appends each compiled filter as a parenthesized `WHERE` clause plus its bound args — e.g. `store/db/sqlite/memo.go:57-61` passes `filter.DialectSQLite`; the postgres and mysql `ListMemos` do the same with their dialects (`store/db/postgres/memo.go`, `store/db/mysql/memo.go`).
- Because args are bound rather than interpolated, user filter expressions can't inject SQL. Dialect divergences (date extraction, string length, JSON access) are handled in the render switch — see `internal/filter/render.go:231-238` for the timestamp case and `internal/filter/MAINTENANCE.md` for the guide on adding fields.
