**memo, memo_relation, attachment** — plus **memo_share** on Postgres/MySQL via DB-level `ON DELETE CASCADE`.

Breakdown for `Store.DeleteMemo` (`store/memo.go:140-159`) as invoked by the API handler (`server/router/api/v1/memo_service.go:518`):

- **memo_relation** — two explicit deletes, one for rows where the memo is the source (`store/memo.go:142`) and one where it's the target (`:145`).
- **attachment** — rows listed by `MemoID` and deleted individually (`store/memo.go:149-157`); `Store.DeleteAttachment` also removes the underlying local file or S3 object (`store/attachment.go:141`), which is outside the DB.
- **memo** — the row itself, via the driver's `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`). Additional `memo` rows go too: the API handler first deletes every comment memo by recursing through `Store.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`), so each child's relations and attachments are removed as well.
- **memo_share** — no explicit delete code on this path; it relies on `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`, `store/migration/sqlite/LATEST.sql:109`).

Worth flagging: on SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so that cascade does **not** fire there — `memo_share` rows for a deleted memo are left orphaned on SQLite, and are only cleaned up explicitly on the user-deletion path (`store/db/sqlite/user_delete.go:411`).

**reaction** is not touched — reactions are read for the webhook payload (`memo_service.go:545`) but never deleted, and `reaction.content_id` is a plain text column with no FK (`store/migration/sqlite/LATEST.sql:92-99`).
