**web/src/connect.ts; short-lived JWT access tokens + an HTTP-only refresh-token cookie (plus personal access tokens for API clients); server/auth**

How it works:

- **Interceptor:** `authInterceptor` in `/bench/repo/web/src/connect.ts:156` sets `Authorization: Bearer <token>` on every Connect request, and on a `Code.Unauthenticated` response refreshes once and retries with an `X-Retry` marker, redirecting to login if the refresh fails (lines 164-177). The transport also sends `credentials: "include"` (line 57) so the refresh cookie rides along.
- **Tokens:** the access token is a JWT held in `localStorage` with its expiry, managed by `/bench/repo/web/src/auth-state.ts` (`getAccessToken`, `setAccessToken`, `isTokenExpired`). `getRequestToken` (`connect.ts:124`) proactively refreshes when the token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30 s) of expiring. The refresh token itself is never visible to JS — it's an HTTP-only cookie, exchanged via `AuthService.RefreshToken` through a separate interceptor-free transport (`refreshAuthClient`, lines 65-72) to avoid recursion, with concurrent refreshes deduplicated by `tokenRefreshManager` (line 30).
- **Backend validation:** the **`/bench/repo/server/auth`** package. `Authenticator.Authenticate` (`authenticator.go:213`) is the request-path entry; `AuthenticateByAccessTokenV2` (line 41) verifies the JWT, `AuthenticateByRefreshToken` (line 61) parses the cookie token and checks it against the DB for revocation/expiry, and `AuthenticateByPAT` (line 102) handles personal access tokens (recording last-used at line 179). Header/cookie parsing lives in `extract.go`, JWT claims and signing in `token.go`, context propagation in `context.go`. It is invoked from the Connect interceptors (`/bench/repo/server/router/api/v1/connect_interceptors.go`) and the gateway middleware in `/bench/repo/server/router/api/v1/v1.go:96`, with per-RPC access rules in `acl_config.go` / `authz.go`.
