**memo, memo_relation, attachment** (plus **memo_share** via a schema-level FK cascade, not application code)

Breakdown, following `Store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) and the API handler `APIV1Service.DeleteMemo` (`/bench/repo/server/router/api/v1/memo_service.go:518`):

- **`memo_relation`** — two explicit deletes, once as source (`MemoID`) and once as target (`RelatedMemoID`), at `store/memo.go:142` and `:145`.
- **`attachment`** — rows linked to the memo are listed and deleted individually via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the backing file/object first (`/bench/repo/store/attachment.go:132-148`; local-file removal in `deleteAttachmentStorageImpl`, line 202).
- **`memo`** — the row itself, and additionally one row per comment memo: the handler deletes each comment through the same `Store.DeleteMemo` path first (`memo_service.go:567-577`), so their relations and attachments are cleaned up too. The final `DELETE FROM memo` is in the driver, e.g. `/bench/repo/store/db/sqlite/memo.go:237`.
- **`memo_share`** — no application code deletes these; the table declares `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`/bench/repo/store/migration/sqlite/LATEST.sql:109`). Worth flagging: the SQLite driver opens the connection with `_pragma=foreign_keys(0)` (`/bench/repo/store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not actually fire and `memo_share` rows are orphaned.

Not touched: **`reaction`**. Reactions are read at `memo_service.go:545` only to build the webhook payload, and nothing deletes rows whose `content_id` points at the removed memo.
