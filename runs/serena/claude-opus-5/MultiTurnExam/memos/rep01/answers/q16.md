Inside `Store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`), before the memo row is removed:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (line 142)
2. **`memo_relation` rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (line 145)
3. **Attachments linked to the memo** — listed via `ListAttachments{MemoID: ...}` and deleted one by one through `Store.DeleteAttachment` (lines 149-157), which also removes the backing blob/file for local storage

Only then does it call `s.driver.DeleteMemo` for the `memo` row itself (line 158).

The API handler `APIV1Service.DeleteMemo` (`/bench/repo/server/router/api/v1/memo_service.go:518`) adds a step above that: it first finds all comment memos (`memo_relation` rows of type `MemoRelationComment` pointing at this memo) and calls `Store.DeleteMemo` on each (lines 567-577), so each comment goes through the same relation/attachment cleanup. It also dispatches the memo-deleted webhook beforehand and broadcasts an SSE event afterward.

One thing to note: reactions are *read* at line 545 only to build the webhook payload — neither the handler nor the store deletes `reaction` rows, so reactions whose `content_id` refers to the deleted memo are left behind.
