Before the `memo` row itself, `Store.DeleteMemo` (`store/memo.go:140-159`) deletes, in order:

1. **`memo_relation` rows where the memo is the source** (`memo_id = ID`) — `store/memo.go:142`
2. **`memo_relation` rows where the memo is the target** (`related_memo_id = ID`) — `store/memo.go:145`
3. **Attachments linked to the memo** — listed by `MemoID` and deleted one by one (`store/memo.go:149-157`); each `Store.DeleteAttachment` (`store/attachment.go:132`) first removes the underlying stored blob (local file or S3 object, via `DeleteAttachmentStorage`) and then the `attachment` row.

Only then does it call `s.driver.DeleteMemo`, which is a plain `DELETE FROM memo WHERE id = ?` (e.g. `store/db/sqlite/memo.go:237`).

Additionally, at the API layer, `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) deletes **comment memos** first — it lists `memo_relation` rows of type `comment` pointing at this memo and calls `Store.DeleteMemo` on each child (`memo_service.go:567-577`), so each comment goes through the same relation/attachment cleanup.

Two things that are *not* explicitly deleted by the store: **reactions** (they're only listed to build the webhook payload at `memo_service.go:545`; the `reaction` table has no FK cascade in the schema) and **`memo_share` rows**, which are removed by the database instead via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`).
