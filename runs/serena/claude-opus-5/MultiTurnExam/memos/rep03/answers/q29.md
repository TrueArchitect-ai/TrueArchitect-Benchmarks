**web/src/connect.ts (state in web/src/auth-state.ts); short-lived JWT access token (Bearer) + HTTP-only refresh-token cookie, plus Personal Access Tokens; server/auth**

**Interceptor** — `authInterceptor` at `web/src/connect.ts:156`, installed on the shared Connect transport (`:184-189`). Per request it fetches a token via `getRequestToken` (`:124`) and sets `Authorization: Bearer <token>` (`:97-100`). Transports use `credentials: "include"` (`:57-62`) so the refresh cookie rides along.

**Tokens it manages:**
- **Access token** — a short-lived JWT held in memory/`web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`/`isTokenExpired`). Refreshed *proactively* when within the expiry buffer (`connect.ts:140`) and *reactively* on a `Code.Unauthenticated` response, retried once using the `X-Retry` header guard (`:164-172`); failure triggers `redirectOnAuthFailure()`.
- **Refresh token** — an HTTP-only cookie the browser never reads; exchanged via `AuthService.RefreshToken` on a separate interceptor-free transport to avoid recursion (`:65-83`). Concurrent refreshes are deduplicated by `tokenRefreshManager` (`:30-51`).
- **Personal Access Tokens (PATs)** — accepted by the backend in the same `Bearer` slot for API clients (not issued by this interceptor).

**Backend validation** — the `server/auth` package: `Authenticator.AuthenticateByAccessTokenV2` (`server/auth/authenticator.go:41`), `AuthenticateByRefreshToken` (`:61`, checks DB revocation and expiry), `AuthenticateByPAT` (`:102`), unified in `resolveBearer` (`:149`) and `AuthenticateToUser` (`:190`), which falls back to the refresh cookie via `ExtractRefreshTokenFromCookie`. JWT signing/parsing lives in `server/auth/token.go`, header/cookie extraction in `server/auth/extract.go`. It's wired into request handling as the gateway auth middleware referenced in `server/router/api/v1/v1.go:96-97` and the Connect interceptors.
