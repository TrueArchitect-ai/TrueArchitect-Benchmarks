**web/src/connect.ts; short-lived JWT access token (in-memory `Authorization: Bearer`) + long-lived refresh token (httpOnly cookie); server/auth**

Frontend — `authInterceptor` at `web/src/connect.ts:156` is attached to the shared Connect transport (`:184-189`) so every RPC carries auth. Per request it calls `getRequestToken()` (:124) which reads the in-memory access token, proactively refreshes it if within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry, and sets the `Authorization: Bearer` header. On a `Code.Unauthenticated` response it refreshes once, marks the retry with an `X-Retry` header to prevent loops, and redirects to login if that fails (:161-177). Refresh itself goes through `refreshAccessToken` (:89), deduplicated by `tokenRefreshManager` (:30) and sent on a *separate* transport with no auth interceptor (:65-72) to avoid recursion; the refresh token rides along as a cookie because all fetches use `credentials: "include"` (:57-62). Token storage/expiry lives in `web/src/auth-state.ts`.

Backend — the **`server/auth`** package validates them: `Authenticator.AuthenticateByAccessTokenV2` (`server/auth/authenticator.go:41`) parses the JWT access token, `AuthenticateByRefreshToken` (:61) verifies the cookie token against the DB, and `AuthenticateToUser`/`Authenticate` (:190, :210) try the `Authorization` header first then fall back to the refresh cookie. Token minting/parsing is in `server/auth/token.go`, header/cookie extraction in `server/auth/extract.go`, and context propagation in `server/auth/context.go`. It's invoked from the Connect interceptors (`server/router/api/v1/connect_interceptors.go`) and the gateway middleware (`server/router/api/v1/v1.go`).

A third token kind also flows through the same header for programmatic clients: **Personal Access Tokens** (`memos_pat_`-prefixed), validated by `AuthenticateByPAT` (:102) via a hash lookup — the frontend interceptor doesn't issue these, but `resolveBearer` (:149) accepts either kind on the Bearer header.
