| Table | How |
|---|---|

| `attachment` | Explicit cascade code — listed by `MemoID` and deleted one by one via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying local/S3 blob (`store/attachment.go:132-149`) |
| `memo` | The row itself (`store/memo.go:158`), plus **comment memo rows** deleted recursively first by the handler walking `MemoRelationComment` relations (`server/router/api/v1/memo_service.go:567-577`) — each of those re-enters the same cascade |
| `memo_share` | DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, `store/migration/postgres/LATEST.sql:108`) — no Go code deletes it |

Two caveats worth flagging:

- **`reaction` is not touched.** The handler lists reactions at `server/router/api/v1/memo_service.go:545` only to build the webhook payload; the sole `Store.DeleteReaction` caller is the `DeleteMemoReaction` RPC (`server/router/api/v1/reaction_service.go:141`). Because `reaction.content_id` holds a resource name rather than a memo FK, reaction rows for a deleted memo are orphaned. (This corrects what I said in q16 — I stated the handler cleans up reactions; it doesn't.)
- **The `memo_share` cascade doesn't fire on SQLite.** The connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so FK enforcement is off there; those rows are orphaned on SQLite but cascade on MySQL/Postgres.
