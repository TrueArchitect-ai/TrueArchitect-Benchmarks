Inside `Store.DeleteMemo` (`store/memo.go:140-158`), before the `memo` row is deleted:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachments linked to the memo** — listed via `FindAttachment{MemoID}` and deleted one by one (`store/memo.go:149-157`); `Store.DeleteAttachment` also removes the backing file for local/external storage

Then `s.driver.DeleteMemo` issues the plain `DELETE FROM memo` (e.g. `store/db/sqlite/memo.go:237`).

Two things happen around that, not in it:
- The API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:567-577`) first deletes each **comment memo** (relations of type `MemoRelationComment`), recursing through `Store.DeleteMemo` for each so their own relations/attachments are cleaned up.
- **memo_share** rows are not deleted in Go — they go via the DB's `ON DELETE CASCADE` foreign key (`store/migration/sqlite/LATEST.sql:109`). Reactions are listed for the webhook payload but are not deleted by this path.
