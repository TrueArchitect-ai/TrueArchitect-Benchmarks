**web/src/connect.ts; short-lived JWT access token (in-memory, `Authorization: Bearer`) + rotating refresh token (HttpOnly cookie) — plus Personal Access Tokens for programmatic clients; server/auth**

- **Interceptor** — `authInterceptor` at `web/src/connect.ts:156`, installed on the shared Connect transport (`:184-189`). It attaches the access token to each request, and on a `Code.Unauthenticated` response refreshes once and retries with an `X-Retry` marker, redirecting to login if the refresh fails. All transports use `credentials: "include"` (`:57-62`) so the refresh cookie rides along.
- **Tokens it manages** — the access token is held in memory by `web/src/auth-state.ts` (`getAccessToken`/`setAccessToken`/`isTokenExpired`); `getRequestToken` (`connect.ts:124`) refreshes preemptively when the token is within the expiry buffer, which matters for public endpoints like ListMemos that would otherwise silently return guest-scoped data. Refresh calls go through `refreshAuthClient` on a separate interceptor-free transport (`:65-72`) to avoid recursion, and `tokenRefreshManager` (`:30-51`) de-duplicates concurrent refreshes so tab-focus refresh and 401-triggered refresh don't race server-side token rotation.
- **Backend validation** — `server/auth`: `Authenticator.AuthenticateByAccessTokenV2` (`authenticator.go:41`, via `ParseAccessTokenV2` in `token.go`), `AuthenticateByRefreshToken` (`:61`, JWT parse + DB lookup of the stored token ID), and `AuthenticateByPAT` (`:102`, prefix check + hash lookup, expiry check, async last-used update). Header/cookie extraction lives in `server/auth/extract.go`, request-context plumbing in `server/auth/context.go`. It's invoked from the Connect interceptor and the grpc-gateway middleware in `server/router/api/v1/` (see the gateway auth middleware in `v1.go`).
