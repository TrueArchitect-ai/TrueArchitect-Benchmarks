**memo, memo_relation, attachment, memo_share**

Breakdown, following `Store.DeleteMemo` (`store/memo.go:140-158`) and its caller `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):

- **memo_relation** — two explicit deletes, once as `memo_id` and once as `related_memo_id` (`store/memo.go:142`, `:145`).
- **attachment** — rows found via `FindAttachment{MemoID}` are deleted individually through `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the backing blob/file (`store/attachment.go:132-148`).
- **memo** — the row itself (`store/db/sqlite/memo.go:237`), plus one additional `memo` row per comment: the handler deletes each `MemoRelationComment` child memo first (`server/router/api/v1/memo_service.go:567-577`), recursing through the same cleanup.
- **memo_share** — only via the `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` declared in the schema (`store/migration/sqlite/LATEST.sql:109`), not by Go code.

Two caveats worth flagging: that cascade does **not** fire on SQLite, because the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`) — so `memo_share` rows are left orphaned on SQLite deployments. And **reaction** rows are never deleted on this path: they're only read to build the webhook payload (`memo_service.go:545`), and `reaction.content_id` is a resource-name string with no foreign key (`LATEST.sql:92`). Both tables *are* cleaned up on the user-deletion path (`store/db/*/user_delete.go`).
