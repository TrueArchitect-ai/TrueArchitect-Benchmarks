Tables touched by a `DeleteMemo` (API path, `server/router/api/v1/memo_service.go:518` → `Store.DeleteMemo`, `store/memo.go`):

```
memo_relation
attachment
memo
memo_share   (only via the ON DELETE CASCADE foreign key, not explicit code)
```

- **`memo_relation`** — deleted explicitly, twice: rows where the memo is the source (`MemoID`) and rows where it's the target (`RelatedMemoID`) (`store/memo.go`, `store/db/*/memo_relation.go`).
- **`attachment`** — rows linked to the memo are listed and deleted one by one via `Store.DeleteAttachment`, which also removes the backing file/blob from storage (`store/attachment.go`).
- **`memo`** — the row itself, plus the rows of any comment memos, which the handler deletes first by walking `memo_relation` entries of type `MemoRelationComment` (each recursing through the same cleanup).
- **`memo_share`** — declared `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, and the mysql equivalent). There is no explicit delete in the `DeleteMemo` path. Worth flagging: the SQLite connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade is not enforced and share rows for a deleted memo are left behind — they are only cleaned up explicitly in the user-deletion path (`store/db/sqlite/user_delete.go:406,411`).

`reaction` rows are read to build the webhook payload but never deleted here.
