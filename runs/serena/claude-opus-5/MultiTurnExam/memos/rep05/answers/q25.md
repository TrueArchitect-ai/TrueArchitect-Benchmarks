**Engine: CEL (Google's Common Expression Language, `github.com/google/cel-go`) — `internal/filter/` (`engine.go`, `parser.go`, `ir.go`, `render.go`, `schema.go`, `helpers.go`)**

**Mechanism:** `Engine.Compile` compiles the filter string against a CEL environment defined by a `Schema` and lowers the AST into a dialect-agnostic `Condition` tree (`internal/filter/engine.go:47`, `parser.go`, `ir.go`), then `CompileToStatement`/`Render` emits dialect-specific SQL plus bound args by switching on `DialectSQLite` / `DialectMySQL` / `DialectPostgres` (`internal/filter/render.go`) — each driver calls `filter.AppendConditions(ctx, engine, find.Filters, filter.Dialect*, &where, &args)` (`internal/filter/helpers.go:9`) to append the rendered predicates to its WHERE clause, e.g. `store/db/sqlite/memo.go:57-61` and the postgres/mysql equivalents.

Supporting detail: the CEL variable/function surface for memos is declared in `internal/filter/schema.go` (with the API-facing filter validation in `server/router/api/v1/memo_service_filter.go` and `user_service_filter.go`), and `render.go` handles per-dialect differences such as `LENGTH` vs `CHAR_LENGTH` (line 297), regex operators (line 565), LIKE escaping (line 580), and timestamp extraction (lines 231–237). Placeholder numbering is offset per filter so Postgres `$n` args stay consistent (`helpers.go:13`). Notes on maintaining this live in `internal/filter/README.md` and `MAINTENANCE.md`.
