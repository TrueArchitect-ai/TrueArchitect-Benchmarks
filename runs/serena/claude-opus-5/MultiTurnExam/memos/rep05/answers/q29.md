**web/src/connect.ts (`authInterceptor`, with token state in web/src/auth-state.ts); JWT access token (in-memory, sent as `Authorization: Bearer`) + refresh token (HTTP-only cookie, sent via `credentials: "include"`); server/auth**

How it works:
- `authInterceptor` (`/bench/repo/web/src/connect.ts:156`) is installed on the shared Connect transport (line 188). On each request it resolves a token via `getRequestToken()` (line 124) and sets `Authorization: Bearer <token>` (line 97). It refreshes preemptively when the token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry (line 140), and reactively on a `Code.Unauthenticated` response — retrying once with an `X-Retry` marker, then calling `redirectOnAuthFailure()` if the refresh fails (lines 163–177).
- Refreshes go through `AuthService.RefreshToken` on a **separate transport with no interceptors** to avoid recursion (`refreshTransport`/`refreshAuthClient`, lines 65–72), and are de-duplicated by `tokenRefreshManager` (lines 30–51). The refresh token itself is never read by JS — it rides along as a cookie because both transports use `fetchWithCredentials` (line 57). Access-token storage/expiry lives in `/bench/repo/web/src/auth-state.ts` (`getAccessToken`, `setAccessToken`, `isTokenExpired`, `clearAccessToken`).
- Validation happens in **`/bench/repo/server/auth/`**: `Authenticator.AuthenticateToUser`/`Authenticate` (`authenticator.go:190,213`) check the `Authorization` header first, then fall back to the refresh cookie; `AuthenticateByAccessTokenV2` (line 41), `AuthenticateByRefreshToken` (line 61), and `AuthenticateByPAT` (line 102) handle the three credential kinds — so personal access tokens are a third accepted bearer credential, used by API clients rather than the web app. JWT signing/parsing is in `server/auth/token.go`, header/cookie extraction in `extract.go`, and context propagation in `context.go`. It's wired into the request path by the gateway/Connect auth middleware in `server/router/api/v1/`.
