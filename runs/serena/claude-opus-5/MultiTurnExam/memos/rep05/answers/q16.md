In `Store.DeleteMemo` (`/bench/repo/store/memo.go`), before the `memo` row is deleted:

- **`memo_relation` rows where the memo is the source** (`DeleteMemoRelation{MemoID: &delete.ID}`)
- **`memo_relation` rows where the memo is the target** (`DeleteMemoRelation{RelatedMemoID: &delete.ID}`)
- **`attachment` rows linked to the memo** — listed via `FindAttachment{MemoID}` and removed one by one with `Store.DeleteAttachment`, which also deletes the underlying stored file/blob (`/bench/repo/store/attachment.go`, `DeleteAttachmentStorage`)

Only then does it call `s.driver.DeleteMemo`, which is a plain `DELETE FROM memo WHERE id = ?` (`/bench/repo/store/db/sqlite/memo.go`, and the mysql/postgres equivalents).

Additionally, the API handler `APIV1Service.DeleteMemo` (`/bench/repo/server/router/api/v1/memo_service.go:518`) first deletes **comment memos** — it lists `memo_relation` rows of type `MemoRelationComment` pointing at this memo and calls `Store.DeleteMemo` on each (which in turn cleans up their own relations and attachments) — before deleting the target memo. Note that `reaction` rows are only *read* there (to build the webhook payload); they are not deleted in this path.
