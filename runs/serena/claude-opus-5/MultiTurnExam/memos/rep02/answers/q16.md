`Store.DeleteMemo` (`store/memo.go:140-158`) deletes, in order, before issuing the memo-row delete:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachments linked to the memo** — listed via `FindAttachment{MemoID}` then deleted one by one (`store/memo.go:149-157`)

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`).

Two adjacent details: the API handler `APIV1Service.DeleteMemo` first deletes each **comment memo** (memos related to this one with type `MemoRelationComment`) by recursively calling `Store.DeleteMemo` (`server/router/api/v1/memo_service.go:566-576`), and **memo_share** rows are removed by the database rather than the store layer, via `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`). Reactions are read for the webhook payload but are not deleted in this path — the `reaction` table has no FK to `memo` (`store/migration/sqlite/LATEST.sql:92-99`).
