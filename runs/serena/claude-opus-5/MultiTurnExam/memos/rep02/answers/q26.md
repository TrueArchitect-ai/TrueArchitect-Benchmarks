**memo, memo_relation, attachment, memo_share**

- **memo_relation** — deleted explicitly in both directions (`MemoID` and `RelatedMemoID`) at `store/memo.go:142,145`.
- **attachment** — attachments with `MemoID = memo.ID` are listed and deleted one by one at `store/memo.go:149-157`, via `Store.DeleteAttachment` (`store/attachment.go:132`), which also removes the underlying local/S3 object.
- **memo** — the row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-240`, with postgres/mysql equivalents).
- **memo_share** — removed by the database, not by store code: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three dialects (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`, `store/migration/mysql/LATEST.sql:108`).

The same four tables are hit again for each comment memo, since `APIV1Service.DeleteMemo` recursively calls `Store.DeleteMemo` for comment-type relations (`server/router/api/v1/memo_service.go:566-576`). `reaction` rows are **not** touched — they're only read to build the webhook payload, and the table has no FK to `memo` (`store/migration/sqlite/LATEST.sql:92-99`), so reactions on a deleted memo are left orphaned.
