**web/src/connect.ts; short-lived JWT access tokens (Bearer, held in memory) + an HTTP-only refresh-token cookie — with Personal Access Tokens as an alternative Bearer credential for non-browser clients; server/auth**

Frontend: the Connect `authInterceptor` at `web/src/connect.ts:156-178` is attached to the transport at `web/src/connect.ts:188`. Per request it calls `getRequestToken()` (:124) and sets `Authorization: Bearer <token>`; the token itself is stored by `web/src/auth-state.ts`. It handles refresh two ways — proactively when `isTokenExpired(REQUEST_TOKEN_EXPIRY_BUFFER_MS)` (:140), and reactively on a `Code.Unauthenticated` response, retrying once with an `X-Retry` marker and redirecting to login if refresh fails (:164-176). Refresh calls `AuthService.refreshToken` through a *separate* interceptor-free transport (`web/src/connect.ts:65-72`) to avoid recursion, and all callers funnel through `tokenRefreshManager` (:30-51, :89) so concurrent refreshes are deduplicated. The refresh token rides along as a cookie because every request uses `credentials: "include"` (:57-62).

Backend: `server/auth` — `Authenticator` in `server/auth/authenticator.go` validates each kind: `AuthenticateByAccessTokenV2` (:41, JWT parsed by `server/auth/token.go`), `AuthenticateByRefreshToken` (:61, JWT plus a DB lookup via `GetUserRefreshTokenByID`), and `AuthenticateByPAT` (:102, prefix check + hash lookup, expiry check, last-used recording). `resolveBearer` (:149) picks JWT vs PAT by prefix; `AuthenticateToUser` (:190) falls back to the refresh cookie via `server/auth/extract.go`.

That authenticator is wired into both protocols through one shared `Authorizer` created in `server/router/api/v1/v1.go:68` — the Connect side via `NewAuthInterceptor` (`server/router/api/v1/connect_interceptors.go`) and the REST side via the gateway middleware in `v1.go:69-92`, with per-method access policy in `server/router/api/v1/authz.go` and `acl_config.go`.
