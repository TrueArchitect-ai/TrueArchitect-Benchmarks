`Store.DeleteMemo` (`store/memo.go:140-158`) removes, in order, before issuing the memo-row delete:

1. **memo_relation rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **memo_relation rows where the memo is the target** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **attachments linked to the memo** — listed then deleted one by one (`store/memo.go:148-157`); each `Store.DeleteAttachment` also deletes the **backing stored file/blob** via `DeleteAttachmentStorage` before the `attachment` row (`store/attachment.go:132-148`)

Then `s.driver.DeleteMemo` deletes the memo row itself (`store/memo.go:158`).

Two things sit outside that store method:
- **Comment memos** are deleted first by the API handler, which lists `MemoRelationComment` relations pointing at the memo and calls `Store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:567-577`) — so each comment goes through the same relation/attachment cleanup.
- **memo_share rows** are not deleted explicitly; they go away via `ON DELETE CASCADE` on the FK to `memo(id)` (`store/migration/sqlite/LATEST.sql:109`). Reaction rows are only read for the webhook payload (`server/router/api/v1/memo_service.go:545`) — the `reaction` table keys on a `content_id` string with no FK (`store/migration/sqlite/LATEST.sql:92-99`), so reactions are not deleted on this path.
