**web/src/connect.ts; short-lived access token (JWT "Access Token V2", Bearer header) + refresh token (httpOnly cookie) — with Personal Access Tokens as an alternative Bearer credential for non-browser clients; server/auth**

- **Interceptor:** `authInterceptor` at `web/src/connect.ts:156-178`, installed on the shared Connect transport (`:184-189`). Per request it fetches a token via `getRequestToken` (`:124`), sets `Authorization: Bearer <token>`, and on a `Code.Unauthenticated` response refreshes once and retries with an `X-Retry` marker, redirecting to login if the refresh fails.
- **Tokens it manages:**
  - *Access token* — stored in `localStorage` with its expiry, read/written by `web/src/auth-state.ts` (`getAccessToken:52`, `setAccessToken:78`, `isTokenExpired:99`). The interceptor refreshes it both proactively (expiry within `REQUEST_TOKEN_EXPIRY_BUFFER_MS`, `web/src/connect.ts:140`) and reactively on 401.
  - *Refresh token* — never touched by JS; it rides an httpOnly cookie, which is why every fetch uses `credentials: "include"` (`web/src/connect.ts:57-62`). Refresh calls go through a separate interceptor-free transport/client (`:65-72`) to avoid recursion, and concurrent refreshes are de-duplicated by `tokenRefreshManager` (`:30-51`, `:89`).
- **Backend validation:** the `server/auth` package. `Authenticator` (`server/auth/authenticator.go:32`) validates access tokens via `ParseAccessTokenV2` (`:41`, JWT signed with the server secret — `server/auth/token.go`), refresh tokens against the DB with revocation/expiry checks (`:61-83`), and PATs by hash lookup (`:102-123`). `AuthenticateToUser` (`:190`) tries the Bearer header first, then falls back to the refresh cookie (`ExtractBearerToken` / `ExtractRefreshTokenFromCookie` in `server/auth/extract.go`). It's wired into the API as gateway middleware (`server/router/api/v1/v1.go:94-97`) and used by the SSE endpoint (`server/router/api/v1/sse_handler.go:26`).
