Detail:
- **s3presign** — `startBackgroundRunners` creates the runner, calls `RunOnce(ctx)`, then launches `Run(s3Context)` in a goroutine tracked by a WaitGroup with its own cancel func (`server/server.go:153-174`). `Run` ticks on `runnerInterval = 12h` (`server/runner/s3presign/runner.go:27-41`); each pass re-presigns S3 attachment URLs older than 4 days (`:88`). It's the *only* runner `startBackgroundRunners` starts.
- **webhook workers** — `internal/webhook/webhook.go:42-54` spawns 4 consumer goroutines on a 128-slot `asyncPostQueue`, fed by `PostAsync` (`:184`); these start implicitly on package import, not from `Server.Start`.
- **SSE heartbeat** — `server/router/api/v1/sse_handler.go:64` runs a `sseHeartbeatInterval` ticker for the lifetime of each client connection.

**Unused infrastructure:** `server/runner/memopayload` ships a full runner type — `NewRunner(store, markdownService)` and `RunOnce(ctx)` (`server/runner/memopayload/runner.go:19`, `:27`), which walks all memos and rebuilds their payloads — but **nothing starts it**. `startBackgroundRunners` never references it, and the only production uses of that package are direct calls to the standalone helper `memopayload.RebuildMemoPayload` from the memo handlers (`server/router/api/v1/memo_service.go:108` on create, `:447` on update). So the batch/backfill runner is dead scheduling infrastructure in the current server.
