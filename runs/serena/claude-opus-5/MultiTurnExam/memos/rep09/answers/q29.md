**`web/src/connect.ts` (the `authInterceptor`, line 156); short-lived JWT access tokens + an HttpOnly refresh-token cookie (plus PATs for programmatic clients); `server/auth`**

How it works:

- **Interceptor** — `authInterceptor` at `web/src/connect.ts:156-178` is installed on the Connect transport (line 188). On each request it fetches a token via `getRequestToken()` and sets `Authorization: Bearer <token>` (lines 97-100, 158-159). It also proactively refreshes when the token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` of expiry (lines 140-147), and reactively retries once on a `Code.Unauthenticated` response — refreshing, re-signing, and marking the retry with an `X-Retry` header (lines 164-172); if the refresh fails it calls `redirectOnAuthFailure()`.
- **Tokens managed** — the **access token** (JWT, stored in `localStorage` with its expiry, `web/src/auth-state.ts:52-96`) and the **refresh token**, which the browser never touches directly: it's the `memos_refresh` HttpOnly cookie sent because the transport uses `credentials: "include"` (`web/src/connect.ts:57-62`). Refresh goes through a separate interceptor-free transport and `refreshAuthClient` to avoid recursion (lines 65-83), deduplicated by `tokenRefreshManager` (lines 30-51, 89-91).
- **Backend validation** — `server/auth` (`server/auth/authenticator.go`): `AuthenticateByAccessTokenV2` (line 41), `AuthenticateByRefreshToken` (line 61), and `AuthenticateByPAT` (line 102), with `resolveBearer` (line 149) trying access-token-then-PAT and `AuthenticateToUser` (line 190) falling back to the refresh cookie. Token minting/claims and the constants (`AccessTokenDuration` 15 min, `RefreshTokenCookieName = "memos_refresh"`, `PersonalAccessTokenPrefix = "memos_pat_"`) are in `server/auth/token.go:35-52`, using `golang-jwt/jwt/v5`; header/cookie extraction in `server/auth/extract.go`. It's wired into both protocols — the gateway middleware in `server/router/api/v1/v1.go:60-93` and the Connect interceptor path.
