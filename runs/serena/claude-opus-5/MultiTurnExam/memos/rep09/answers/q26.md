**memo, memo_relation, attachment, memo_share**

Breakdown of how each is hit when `Store.DeleteMemo` (`store/memo.go:140-159`) runs:

- **memo_relation** — explicit deletes in both directions: `DeleteMemoRelation{MemoID}` and `{RelatedMemoID}` (`store/memo.go:142,145`).
- **attachment** — explicit: attachments with `MemoID` are listed and deleted one at a time (`store/memo.go:148-157`); each `Store.DeleteAttachment` (`store/attachment.go:132-149`) also removes the backing file/object from storage before the row.
- **memo** — the row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`, `store/db/postgres/memo.go:244-255`, plus the MySQL equivalent). Comment memos are additional `memo` rows deleted by the API handler, which recurses into `Store.DeleteMemo` for each comment relation (`server/router/api/v1/memo_service.go:567-577`).
- **memo_share** — no Go code deletes it; rows go away via the DB-level `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `store/migration/postgres/LATEST.sql:108`).

Not affected: `reaction` rows are only *read* for the webhook payload (`server/router/api/v1/memo_service.go:545-550`) and are left in place — the `reaction` table has no `memo_id` FK, it keys off a string `content_id` (`store/reaction.go:12`).
