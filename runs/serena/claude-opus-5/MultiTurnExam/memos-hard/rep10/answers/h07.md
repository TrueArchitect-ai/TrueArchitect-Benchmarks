What happens at each hop:

- **`serveUserAvatar`** (`fileserver.go:168-207`): if the instance isn't anonymous-readable (`s.Profile.AllowAnonymous()`), it first resolves the viewer via `getCurrentUser` and 401s if there is none (`:173-180`). Then it takes the `:identifier` path param, loads the target user, and 404s if the user is missing or `AvatarURL` is empty (`:188-194`).
- **`getUserByUsername`** (`fileserver.go:715-717`): a one-line wrapper — `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})`. Note the lookup is by **username**, not ID.
- **`Store.GetUser`** (`store/user.go:148-169`): consults `userCache` only when `find.ID` is set — a username lookup like this one always misses the cache and falls through to `ListUsers`; the result is then cached by ID (`:167`).
- **`Store.ListUsers`** (`store/user.go:136-146`): delegates to `s.driver.ListUsers` and warms the per-ID cache for each row.
- **Driver** (`store/db/sqlite/user.go:88`): builds the `WHERE` clause and selects the user columns including `avatar_url` (see the field list at `store/db/sqlite/user.go:14`).

Back in the handler, the stored `AvatarURL` is a data URI, so the bytes never leave the DB row: `parseDataURI` (`fileserver.go:737`) splits MIME type and base64 payload, the type is checked against `avatarAllowedTypes` (`fileserver.go:75`, enforced at `:201`), `setSecurityHeaders` plus `Cache-Control` are applied (`:205-207`), and the decoded bytes go out via `c.Blob` (`:209`).
