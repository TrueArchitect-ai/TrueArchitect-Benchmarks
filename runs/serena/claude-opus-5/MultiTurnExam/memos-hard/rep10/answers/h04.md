**No — outside `store/db/db.go`, nothing in the repo constructs the MySQL driver.**

Evidence:

1. **Only one importer.** `grep -rn "store/db/mysql" --include=*.go` over the whole repo returns exactly one hit: `store/db/db.go:8`. Since Go requires an import to reference a package's identifiers, no other file — production or test — can call `mysql.NewDB` or build a `mysql.DB` literal.
2. **Only one call site.** `mysql.NewDB` is defined at `store/db/mysql/mysql.go:20` and called once, at `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver` (`store/db/db.go:14-31`). By comparison, `sqlite.NewDB` *is* called directly outside the factory, in `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416` — so the pattern exists in the codebase; MySQL just doesn't participate in it.
3. **Tests go through the factory too.** The test harnesses build drivers via `db.NewDBDriver` — `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70` — so MySQL-backed tests still reach `mysql.NewDB` only through the switch.
4. **Two near-misses that aren't this.** `store/test/containers.go:42,101-105` references `mysql.MySQLContainer` / `mysql.Run` / `mysql.WithDatabase`, but that's the **testcontainers** MySQL module spinning up a server, not the store driver. Likewise `store/db/mysql/mysql.go:6` imports `github.com/go-sql-driver/mysql` for `ParseDSN`/`Config` — a different `mysql` package, used inside the driver itself.
5. **The struct is unexported in practice.** `DB` (`store/db/mysql/mysql.go:14`) has only unexported fields (`db`, `profile`, `config`), so even an importing package outside `store/db/mysql` couldn't usefully construct a working `&mysql.DB{...}` by literal — `NewDB` is the only viable path. The in-package tests (`store/db/mysql/auth_config_test.go`, `user_delete_test.go`) are inside the driver package, not "outside" it.
