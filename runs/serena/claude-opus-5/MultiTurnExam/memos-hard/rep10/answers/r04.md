**Premise correction: neither. There is no message broker anywhere in this repository** — grepping `go.mod`, `go.sum`, and all Go sources for `nats`, `rabbit`, `amqp`, `kafka`, and `streadway` returns zero hits. No queue is declared because none exists.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool**, all in `internal/webhook/webhook.go`:

- **The "queue"** is a package-level channel with 128 slots: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`.
- **The workers** are 4 goroutines started in `init()` — `internal/webhook/webhook.go:42-55`. Each ranges over the channel and calls `Post(payload)`, logging a warning on failure (`:46-51`).
- **Producers** call `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send. On a full queue it takes the `default` branch and **drops the event** with a warning (`:191-195`) — there is no persistence, retry, dead-letter, or redelivery.
- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`), which marshals the payload, optionally adds Standard Webhooks HMAC headers, and executes `safeClient.Do(req)` at `:152`.

Enqueue sites are the memo webhook dispatchers — `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.

Practical consequences of it being a channel rather than a broker: the queue lives in the server's memory, so pending webhooks are **lost on restart or crash**; it doesn't span multiple server instances (each process has its own 128-slot buffer and 4 workers); and a burst beyond 128 undelivered payloads silently sheds load. The workers are started by `init()` rather than by server startup, so they exist in any process that imports the package, including tests.
