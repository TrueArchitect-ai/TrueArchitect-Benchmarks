Visibility is enforced in three architectural surfaces — the gRPC/Connect API, the plain-HTTP file server, and the push/feed surfaces — with several distinct sites inside each:

Two structural notes. First, enforcement splits into two *kinds*: post-fetch gates that reject a single already-loaded memo (`checkMemoReadAccess`, the reaction/attachment checks, the file server), and pre-query scoping that constrains what the store returns (`VisibilityList` / the `creator_id == N || visibility in [...]` CEL filter). The scoping idiom is duplicated verbatim in at least four places rather than centralized, so a policy change would need edits in all of them.

Second, the file server and the SSE hub are genuinely independent of the API layer — the file server re-derives permission from the linked memo in its own Echo handler (`server/router/fileserver/fileserver.go:666`) and is the only site honoring `share_token`, while `canReceive` (`server/router/api/v1/sse_hub.go:134`) is the only site where PROTECTED is treated as broadcast-safe to every connected client.
