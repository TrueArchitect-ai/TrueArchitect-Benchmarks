**Premise correction: there is no Redis anywhere in this repository.** A case-insensitive search for `redis` across all Go sources, `go.mod`, `go.sum`, and YAML/JSON config returns zero matches. There is no external cache server, no connection string, and no client dependency to configure.

**Actual mechanism:** the cache layer is a hand-rolled, in-process, in-memory cache — `store/cache/cache.go`. `Cache` is a struct over `sync.Map` plus an atomic item counter (`store/cache/cache.go:67-73`), created by `cache.New(config)` (`:75`), which spawns a background `cleanupLoop` goroutine (`:200-215`) that sweeps expired entries on a ticker. It is process-local: nothing is shared across replicas, and everything is lost on restart.

**Configuration site:** not a connection — a `cache.Config` literal built inline in `store.New`, at `store/store.go:39-44`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

Three caches are then constructed from that same config — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:50-52`, fields at `:27-29`). Note this literal duplicates `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), which has identical values but is not what the store calls.

**TTL for user entries: 10 minutes.** Every write to `userCache` goes through `Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`), stamping `expiration = time.Now().Add(ttl)` (`:112`). Nothing in the codebase calls `SetWithTTL` directly, so there is no per-entry override — the 10-minute value is uniform, and it is a hardcoded constant with no flag or env var behind it.

Two caveats worth knowing: entries can also disappear before the TTL, because exceeding `MaxItems` (1000) triggers `cleanupOldest`, which drops 20% of capacity at once (`store/cache/cache.go:253-257`); and user entries are explicitly invalidated on delete (`store/user_delete.go:40`). Also, reads only hit this cache when looking up by ID — `Store.GetUser` consults `userCache` solely when `find.ID != nil` (`store/user.go:149-156`), so username- or email-keyed lookups always fall through to the database regardless of TTL.
