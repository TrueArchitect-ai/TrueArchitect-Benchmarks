Route is `GET /file/users/:identifier/avatar`; the browser gets that URL because the API rewrites base64 avatars into it. Hops, in order:

```
RegisterRoutes (route registration)   — server/router/fileserver/fileserver.go:124
serveUserAvatar (HTTP handler)        — server/router/fileserver/fileserver.go:168
getUserByUsername                     — server/router/fileserver/fileserver.go:715
Store.GetUser                         — store/user.go:148
Store.ListUsers                       — store/user.go:136
Driver.ListUsers (interface)          — store/driver.go:10
DB.ListUsers (sqlite impl; SELECT ... avatar_url ... FROM user WHERE username = ?)
                                      — store/db/sqlite/user.go:88
```

Supporting detail per hop:

- **How the browser learns the URL**: `convertUserToProto` checks whether the stored `AvatarURL` is a base64 data URI and, if so, replaces it in the API response with `/file/{user.Name}/avatar` — `server/router/api/v1/user_service_converters.go:32-38`. Since `Name` is `users/{username}`, the emitted path matches the registered route. If the stored value isn't a data URI it's passed through verbatim (`:38`) and no server hop happens at all.

- **Wiring**: the service is constructed and its routes registered during startup at `server/server.go:81-82`; constructor at `server/router/fileserver/fileserver.go:111`.

- **Auth gate (conditional hop)**: on a private instance, `serveUserAvatar` first calls `getCurrentUser` (`fileserver.go:708`) → `authenticator.AuthenticateToUser` (`fileserver.go:711`) and 401s anonymous viewers — `fileserver.go:171-179`. When `Profile.AllowAnonymous()` is true this is skipped entirely.

- **Store layer**: `getUserByUsername` builds `&store.FindUser{Username: &identifier}` — note it looks up by *username*, so the `:identifier` segment must be a username, not a numeric ID. `Store.GetUser` (`store/user.go:148`) consults `userCache` only when `find.ID` is set (`:149-156`), so this username-keyed path always misses the read cache and delegates to `Store.ListUsers` (`:158`), which calls the driver and back-fills the cache by ID (`store/user.go:137-144`).

- **Data layer**: `DB.ListUsers` appends `username = ?` to the WHERE clause (`store/db/sqlite/user.go:128-130`) and issues the `SELECT` that includes `avatar_url` from the `user` table (`store/db/sqlite/user.go:151-165`), scanning it into `store.User.AvatarURL` (`store/db/sqlite/user.go:189`; field declared at `store/user.go:43`). Postgres and MySQL have parallel implementations in `store/db/postgres/user.go` and `store/db/mysql/user.go`.

- **Back in the handler**: the stored data URI is decoded by `parseDataURI` via `dataURIRegex` (`fileserver.go:737`, regex at `:98`), the MIME type is checked against `avatarAllowedTypes` (`:75-80`, enforced at `:201`), security headers and a 1-hour `Cache-Control` are set, and the bytes are written with `c.Blob` (`fileserver.go:205-209`). So the image bytes live in the `user.avatar_url` column itself — there is no attachment or filesystem hop on this path.
