**No — outside the factory, the MySQL driver is never constructed directly.**

Evidence:

1. **Only one importer of the package.** `grep -rn "store/db/mysql" --include=*.go .` returns exactly one hit: `store/db/db.go:8`. No other file in the repo — production or test — imports `github.com/usememos/memos/store/db/mysql`, so no other file can call its exported constructor.

2. **Only one call site of the constructor.** `mysql.NewDB` is defined at `store/db/mysql/mysql.go:20` and is called exactly once, at `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver`. (For contrast, `sqlite.NewDB` *is* called directly outside the factory, at `store/deployment_config_test.go:416` and `store/demo_seed_test.go:24` — so the pattern is not uniform across drivers, which makes the MySQL result a real finding rather than an artifact of nothing importing drivers at all.)

3. **Everything else routes through the factory.** The only entry points that obtain a driver are `db.NewDBDriver` calls at `store/test/store.go:28`, `store/test/store.go:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70`. MySQL-backed tests get their driver this way — `store/test/containers.go:101-105` only spins up a testcontainer and builds a DSN; it does not construct the driver itself.

One qualification: within the package there is a bare struct literal `db := &DB{}` at `store/db/mysql/auth_config_test.go:12`. That is an in-package test constructing the struct without `NewDB` (no connection, just exercising query-building), so it is inside the driver package rather than "outside the factory," and it bypasses the constructor rather than calling it.
