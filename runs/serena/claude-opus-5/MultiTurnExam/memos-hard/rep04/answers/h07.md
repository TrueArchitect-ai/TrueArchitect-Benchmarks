The browser gets the URL from the API (`GET /api/v1/users/*` responses rewrite base64 avatars to `/file/users/{username}/avatar` — `server/router/api/v1/user_service_converters.go:31-39`), then requests that path. Hops:

Notes on the path:

- **Wiring** — the file server is constructed and its routes registered at server startup: `server/server.go:81-82`.
- **Auth gate** — before any lookup, `serveUserAvatar` checks `s.Profile.AllowAnonymous()`; on a private instance it requires a session/access token/PAT via `s.getCurrentUser` and returns 401 otherwise (`server/router/fileserver/fileserver.go:173-181`). Note this authenticates the *viewer* only — there's no per-target-user authorization, so any permitted viewer can fetch any user's avatar.
- **Lookup key** — the `:identifier` path param is treated as a username: `store.FindUser{Username: &identifier}` (`fileserver.go:716`).
- **Cache layer** — `Store.GetUser` consults `userCache` only when finding by ID (`store/user.go:149-156`); a username lookup always falls through to `ListUsers` → driver → SQL, though results are written back into the cache (`store/user.go:142-144`, `:167`).
- **Storage form** — the avatar isn't a file on disk or in S3; it's a base64 data URI stored in the `user.avatar_url` column (selected at `store/db/sqlite/user.go:157`). The handler decodes it with `s.parseDataURI` (using `dataURIRegex`, `fileserver.go:98`), validates the MIME type against `avatarAllowedTypes` (`fileserver.go:75`, `:201`), sets security + cache headers, and writes the bytes with `c.Blob` (`fileserver.go:205-209`).
