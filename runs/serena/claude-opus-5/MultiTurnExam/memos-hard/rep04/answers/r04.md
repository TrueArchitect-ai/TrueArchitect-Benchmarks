**Premise correction: neither. There is no message broker in this repository — no NATS, RabbitMQ, AMQP, Kafka, or NSQ client appears in `go.mod` or any Go source (the only grep hits are base64 fragments inside `web/pnpm-lock.yaml` and unrelated `SQL` substrings in a test file). Consequently there is no queue declaration, no exchange/subject binding, and no external broker connection to configure.**

**Actual mechanism — an in-process buffered Go channel, all in `internal/webhook/webhook.go`:**

- **The "queue"** is a package-level buffered channel with 128 slots: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` (`internal/webhook/webhook.go:39`). That's the entire declaration — it lives in the same `var` block as the shared HTTP client.
- **The "workers"** are 4 goroutines started in the package `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post(payload)` (`:46`), logging a warning on failure. They're unsupervised — not tracked by any WaitGroup and not tied to a context.
- **Producers** call `PostAsync` (`internal/webhook/webhook.go:184`), which does a non-blocking `select` send: if the buffer is full, the payload is **dropped** with a warning rather than blocking the RPC handler (`:189-195`). Callers are the memo webhook dispatchers at `server/router/api/v1/memo_service_webhooks.go:43,71`.
- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`) — JSON marshal, optional Standard Webhooks HMAC headers, then `safeClient.Do` at `:152` with a 30-second timeout (`:27`).

Practical consequences of it being a channel rather than a broker: no persistence (queued webhooks are lost on restart), no retries or dead-letter handling (a failed `Post` is logged and discarded), no cross-instance distribution, and silent drops under burst load beyond 128 pending items.
