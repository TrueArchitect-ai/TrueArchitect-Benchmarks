**No** — `mysql.NewDB` is called from exactly one place, the factory.

Evidence:

1. **Only one import of the package.** Grepping the whole repo for the import path `github.com/usememos/memos/store/db/mysql` returns a single hit: `store/db/db.go:8`. No other Go file in the codebase — including `cmd/`, `server/`, `store/`, and all tests — imports the MySQL driver package, so `mysql.NewDB` is unreachable from anywhere else by qualified call.

2. **That single import is the factory itself.** `NewDBDriver` in `store/db/db.go:14-32` is a `switch profile.Driver` that calls `mysql.NewDB(profile)` at `store/db/db.go:22`, alongside `sqlite.NewDB` (`:20`) and `postgres.NewDB` (`:24`). That is the only `mysql.NewDB` call site repo-wide.

3. **Constructor is only used internally once.** Inside the package, `NewDB` builds `DB{profile: profile}` at `store/db/mysql/mysql.go:29` and returns `&driver` as a `store.Driver` (`store/db/mysql/mysql.go:20-40`).

Two things worth noting so the "no" isn't overstated:

- The SQLite driver *is* constructed directly outside the factory — `sqlite.NewDB(p)` appears in `store/demo_seed_test.go:24` and `store/deployment_config_test.go:416`. MySQL has no such bypass; that asymmetry is what makes the MySQL answer clean.
- Within the MySQL package's own tests, the `DB` struct is instantiated as a zero value at `store/db/mysql/auth_config_test.go:12` (`db := &DB{}`) to exercise query-building methods without a live connection. That's a bare struct literal in the same package, not a call to the `NewDB` constructor, and it's inside the driver package rather than "elsewhere in the codebase."
