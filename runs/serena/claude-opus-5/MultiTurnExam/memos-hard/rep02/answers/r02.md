**Premise correction: there is no per-user API rate-limiting middleware in this repository. Nothing is registered, so there are no request limits to report.**

Evidence:

- A case-insensitive grep across all Go sources for `ratelimit`, `rate_limit`, "rate limit", `throttl`, `TooManyRequests`, and `429` returns exactly one hit, and it is an aspirational comment in package documentation — `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse"), listed among future considerations, not implemented.
- `golang.org/x/time` is present in `go.mod:151` but marked `// indirect` — no file in the repo imports `golang.org/x/time/rate`. It's a transitive dependency, not a limiter this code uses.
- The Echo middleware chain is two entries long: `middleware.Recover()` and `newCORSMiddleware(profile)` — `server/server.go:51-52`. Echo's `middleware.RateLimiter` is never referenced; the only `middleware` imports are in `server/cors.go:8`, `server/server.go:15`, and `server/router/frontend/frontend.go:13`, none for limiting.
- The Connect interceptor chain (`server/router/api/v1/connect_interceptors.go`) contains only `MetadataInterceptor` (`:22`), `LoggingInterceptor` (`:98`), and `RecoveryInterceptor` (`:164`). No limiter interceptor exists, and the gRPC-Gateway path (`server/router/api/v1/v1.go:95`) wraps handlers only with the auth middleware.

**What does exist** are unrelated concurrency and size caps, which are sometimes mistaken for rate limiting but are neither per-user nor request-rate based:

- Thumbnail generation is capped at 3 concurrent operations via a semaphore — `server/router/fileserver/fileserver.go:46` (`maxConcurrentThumbnails`), also `server/router/api/v1/v1.go:60-61` (thumbnail 3, image processing 2).
- Outbound webhook delivery uses a bounded 128-slot queue drained by 4 workers, dropping on overflow — `internal/webhook/webhook.go:39-55`, `:189-195`.
- Memo content length is bounded by an instance setting — `server/router/api/v1/memo_service.go:101-107`.

If per-user API rate limiting is needed, it would have to be added — most naturally as a Connect interceptor alongside the three in `server/router/api/v1/connect_interceptors.go`, since that's the chokepoint where the authenticated user is already resolved.
