**Explicit Go code — two separate `DELETE FROM reaction` statements inside the delete-user transaction, in each of the three drivers. No database-level rule backs it up.**

What I checked:

**1. The delete path.** `Store.DeleteUser` (`store/user.go:171-172`) just forwards to `s.driver.DeleteUser`. Each driver's implementation opens a transaction and calls `deleteUserTargetsTx`, which removes reactions in two passes:

- `deleteReactionsByContentIDsTx` — reactions *on* the user's memos, keyed by `content_id` (`"memos/" + memo.UID`, built by `memoContentIDsFromRefs`). This catches other people's reactions to content that's going away.
- `deleteReactionsByCreatorTx` — reactions *authored by* the user, `DELETE FROM reaction WHERE creator_id = ?`. This catches their reactions on memos that survive.

Call sites and definitions, all three drivers:

| driver | calls | definitions |
|---|---|---|
| sqlite | `store/db/sqlite/user_delete.go` (in `deleteUserTargetsTx`) | `deleteReactionsByContentIDsTx`, `deleteReactionsByCreatorTx` |
| mysql | `store/db/mysql/user_delete.go:96`, `:102` | `:417`, `:437` |
| postgres | `store/db/postgres/user_delete.go:96`, `:102` | `:380`, `:400` |

The content-ID deletion is batched at 500 IDs per statement (`deleteUserBatchSize`), and the memo set it works from comes from a recursive CTE that also pulls in comment memos.

**2. The schema — no cascade.** The `reaction` table declares `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` as plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint. No `FOREIGN KEY`, no `ON DELETE CASCADE`, in any of:
- `store/migration/sqlite/LATEST.sql:91-99`
- `store/migration/postgres/LATEST.sql:90-98`
- `store/migration/mysql/LATEST.sql:90-98`
- and the original creation, `store/migration/sqlite/0.20/00__reaction.sql:2-9`

Cascades do exist elsewhere in the schema (e.g. `memo_share.memo_id` at `store/migration/sqlite/LATEST.sql:109`, and various `REFERENCES user(id) ON DELETE CASCADE` in the older `0.3`–`0.5` migrations), so their absence on `reaction` is a real gap, not an artifact of a schema that never uses FKs. `content_id` is a string reference anyway and couldn't be a foreign key.

**3. Test confirmation.** `store/test/user_delete_test.go` seeds three reactions — a peer's reaction on the deleted user's memo (`:97`), the deleted user's reaction on a peer memo (`:103`), and a peer's reaction on a peer memo that should survive (`:109`). After deletion it asserts exactly one reaction remains on the peer memo, the `peerReactionToKeep` (`:217-220`), which verifies both deletion passes and that unrelated reactions are untouched.
