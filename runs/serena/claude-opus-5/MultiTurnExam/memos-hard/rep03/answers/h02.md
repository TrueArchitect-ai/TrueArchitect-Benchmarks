**`webhook.Post` — `internal/webhook/webhook.go:120` (dispatched off `PostAsync`'s bounded queue at `internal/webhook/webhook.go:184`, drained by 4 worker goroutines started in `init()`, `webhook.go:42-55`); SSRF guard via `safeDialContext` → `isReservedIP` — `internal/webhook/webhook.go:59` and `internal/webhook/validate.go:44`**

How it fits together:

- **Delivery**: `Post` marshals the payload, builds the POST, optionally adds Standard Webhooks HMAC-SHA256 headers (`webhook-id` / `webhook-timestamp` / `webhook-signature`, `webhook.go:133-150`), and executes the request with `safeClient.Do(req)` at `internal/webhook/webhook.go:152`. Response body reads are capped at 1 MiB (`webhook.go:158`) and the client has a 30 s timeout (`webhook.go:27,32-37`).
- **Trigger points**: memo create/update/delete flows call `webhook.PostAsync` at `server/router/api/v1/memo_service_webhooks.go:43` and `:71`.
- **Protection**: all dispatches go through the shared `safeClient` whose `Transport.DialContext` is `safeDialContext` (`webhook.go:32-37`). That function resolves the hostname itself and rejects the connection if *any* resolved address is reserved (`webhook.go:59-77`). Because the check happens at dial time on the addresses actually being connected to, it also defeats DNS rebinding — a TOCTOU bypass that URL-validation-only checks would miss.
- **Blocked ranges**: `reservedCIDRs` in `internal/webhook/validate.go:14-23` — IPv4/IPv6 loopback, RFC-1918, IPv6 ULA, and link-local `169.254.0.0/16` (explicitly covering cloud IMDS at 169.254.169.254), parsed once at startup (`validate.go:28-36`).
- **Second layer + escape hatch**: `webhook.ValidateURL` (`validate.go:62`) rejects bad schemes and reserved-IP targets at configuration time, called from `server/router/api/v1/user_service_webhooks.go:74`, `:161`, `:182`. The package-level `AllowPrivateIPs` flag (`validate.go:41`, checked first in `isReservedIP` at `validate.go:45-47`) disables both layers for self-hosted setups targeting LAN services — note that nothing in the non-test tree currently assigns it, so it defaults to `false` and the protection is on.
