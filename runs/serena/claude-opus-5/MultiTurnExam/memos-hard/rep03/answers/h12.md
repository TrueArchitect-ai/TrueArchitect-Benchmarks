**How I determined which of the three candidates runs.** `Store.CreateMemo` (`store/memo.go:109`) validates the UID and then calls `s.driver.CreateMemo` (`store/memo.go:113`) — an interface dispatch through `store.Driver` (`store/driver.go`), so the call site alone doesn't identify the code. There are three implementations: `store/db/sqlite/memo.go:16`, `store/db/mysql/memo.go`, `store/db/postgres/memo.go`. I resolved the dispatch by following the value that selects it:

1. **Default flag value** — `driver` defaults to `"sqlite"` in two places that agree: `viper.SetDefault("driver", "sqlite")` (`cmd/memos/main.go:122`) and the persistent flag default (`cmd/memos/main.go:130`). With no flags and no `MEMOS_DRIVER` env var (env binding at `cmd/memos/main.go:167-169`), this is what's read.
2. **Into the profile** — `Driver: viper.GetString("driver")` (`cmd/memos/main.go:43`). Corroborating evidence that `"sqlite"` is the intended default: `profile.Validate` special-cases it to auto-derive a DSN of `<data>/memos_prod.db` when `DSN` is empty (`internal/profile/profile.go:110-116`), so a flagless install is fully functional only on this branch.
3. **Factory switch** — `NewDBDriver` maps `case "sqlite"` to `sqlite.NewDB(profile)` (`store/db/db.go:19-20`); the other two cases require an explicit `--driver mysql`/`--driver postgres`.
4. **Injection** — `cmd/memos/main.go:57` builds that driver and `cmd/memos/main.go:64` passes it to `store.New(dbDriver, instanceProfile)`, so `s.driver` in step one is the `*sqlite.DB`.

The reaching call from the API is `s.Store.CreateMemo(ctx, create)` in the `CreateMemo` RPC handler (`server/router/api/v1/memo_service.go:115`).

Minor note that could otherwise mislead a reader: the SQLite implementation quotes identifiers with backticks, which looks like MySQL code — it isn't; SQLite accepts backticks for MySQL compatibility, and the `RETURNING` clause it uses requires SQLite 3.35+.
