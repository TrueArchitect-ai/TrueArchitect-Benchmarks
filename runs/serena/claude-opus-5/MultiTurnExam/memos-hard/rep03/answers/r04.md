**Premise correction: neither. There is no message broker in this repository — no NATS, no RabbitMQ, and therefore no queue declaration to point to.** A case-insensitive grep across all Go files and `go.mod` for `nats`, `rabbitmq`, `amqp`, `kafka`, `streadway`, and `pubsub` returns zero hits.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool, entirely inside `internal/webhook/webhook.go`.**

- **The "queue"** is a package-level buffered channel holding 128 payloads:
  `asyncPostQueue = make(chan *WebhookRequestPayload, 128)` — `internal/webhook/webhook.go:39`.
- **The workers** are 4 goroutines started in the package's `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post(payload)`, logging a warning on failure.
- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send. On a full buffer it takes the `default` branch and **drops the event** with a warning (`webhook.go:191-194`) — no retry, no persistence, no dead-letter.
- **Enqueue call sites**: `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, reached from the memo create/update/delete/comment RPC handlers.
- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`), which signs the payload and executes the HTTP request via the SSRF-guarded `safeClient` at `webhook.go:152`.

Three consequences worth being explicit about, since they're what a broker would otherwise provide: queued webhooks live only in the process's memory, so a restart loses anything in flight; delivery is at-most-once with no retry on failure; and the queue is per-instance, so it doesn't coordinate across multiple server replicas.
