Notes on what happens at each hop:

- **`serveUserAvatar`** (`fileserver.go:168`) — if the instance isn't anonymous-readable (`!s.Profile.AllowAnonymous()`), it first requires a viewer via `s.getCurrentUser` and 401s otherwise (`fileserver.go:173-181`). It then reads the `:identifier` path param (`:183`).
- **`getUserByUsername`** (`fileserver.go:715`) — a one-line adapter building `&store.FindUser{Username: &identifier}`. Note the lookup is by **username only**, so a numeric ID or `users/{id}` in the path won't resolve here.
- **`Store.GetUser`** (`store/user.go:148`) — the user cache is consulted **only when `find.ID` is set** (`store/user.go:149-156`); since this path filters by username, the cache is bypassed on read and every avatar request falls through to the driver. The result is written back into the cache keyed by ID (`:167`).
- **`Store.ListUsers`** (`store/user.go:136`) — delegates to `s.driver.ListUsers` and populates the cache for each row (`:137-145`).
- **Driver** — concrete SQL against the `user` table; the driver instance is chosen by `NewDBDriver` (`store/db/db.go:14-32`).

The image bytes never leave the database row: `user.AvatarURL` holds a data URI, which `s.parseDataURI` decodes into `imageType`/`imageData` (`fileserver.go:196`). The type is checked against `avatarAllowedTypes` (`fileserver.go:75`, enforced at `:201`), security headers and `Cache-Control` are set (`:205-207`), and the decoded bytes are written with `c.Blob` (`:209`).
