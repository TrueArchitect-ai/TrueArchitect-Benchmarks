**Explicit Go code — no database-level rule exists for reactions; evidence: `store/db/{sqlite,mysql,postgres}/user_delete.go` vs. the FK-free `reaction` table in `store/migration/*/LATEST.sql`**

What I checked:

**1. The Go delete path.** Each driver's `DeleteUser` runs one transaction (`store/db/sqlite/user_delete.go:28`) that collects targets and then issues explicit `DELETE`s in `deleteUserTargetsTx` (`sqlite/user_delete.go:88-122`). Reactions are removed twice over, by two different criteria:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`sqlite/user_delete.go:380-388`). The content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + memo.UID` (`sqlite/user_delete.go:...`), covering reactions *other* users left on the deleted user's memos — including comment memos found via the recursive `memo_tree` CTE (`sqlite/user_delete.go:129-152`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`sqlite/user_delete.go:400-403`), covering the deleted user's own reactions on anyone's content.

Both are called in order at `sqlite/user_delete.go:94` and `:102`, before the memo rows and the user row are deleted (`:114`, `:117`).

**2. All three drivers.** The same pair exists in each: `store/db/sqlite/user_delete.go:102,383,400`, `store/db/postgres/user_delete.go:102,383,400`, `store/db/mysql/user_delete.go:102,420,437`. The MySQL factory is reachable only through `store/db/db.go:22`.

**3. The schema, to rule out a DB-level rule.** The `reaction` table in `store/migration/sqlite/LATEST.sql`, `store/migration/mysql/LATEST.sql`, and `store/migration/postgres/LATEST.sql` declares `creator_id` as a plain `INTEGER`/`INT NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`, no `ON DELETE CASCADE`. A repo-wide grep for `REFERENCES`/`CASCADE` in the three `LATEST.sql` files returns exactly one FK per driver, and it's on `memo_relation.memo_id → memo(id)` (`store/migration/mysql/LATEST.sql:108`, `postgres/LATEST.sql:108`, `sqlite/LATEST.sql:109`) — nothing touching `reaction`.

So the cleanup is entirely application-level: if a reaction row were inserted outside this path, no database constraint would collect it.
