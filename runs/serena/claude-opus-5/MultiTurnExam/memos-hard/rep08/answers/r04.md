**Premise correction: neither. There is no message broker in this repository — no NATS, no RabbitMQ/AMQP, no Kafka, no SQS — and therefore no queue declaration.** Grepping for `nats`/`rabbit`/`amqp`/`kafka`/`pubsub`/`sqs` across all Go sources, `go.mod`, and `go.sum` yields nothing but an incidental substring match inside a `go.sum` hash line. The direct dependency list (`go.mod:5-44`) contains no broker client.

**Actual mechanism: an in-process buffered Go channel with a fixed worker pool, all inside `internal/webhook/webhook.go`.**

- **The "queue"** is a package-level channel declared at `internal/webhook/webhook.go:39`: `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`. That's the only declaration — no broker topic, exchange, or subject.
- **The "workers"** are four goroutines started in `init()` (`internal/webhook/webhook.go:42-55`). Each ranges over the channel and calls `Post(payload)`, logging a warning on failure. They start when the package is first loaded, not from any server wiring.
- **Enqueue** happens in `PostAsync` (`internal/webhook/webhook.go:184-196`), called from the memo webhook dispatchers at `server/router/api/v1/memo_service_webhooks.go:43,71`. It uses a non-blocking `select` with a `default` branch, so **when the buffer is full the payload is dropped** with a warning — there is no retry, no dead-letter path, and no persistence.
- **Delivery** is `Post` (`internal/webhook/webhook.go:120`), which marshals the JSON body, optionally attaches Standard Webhooks HMAC headers, and issues the POST via `safeClient.Do` (`:152`).

Practical consequences of it being a channel rather than a broker: the queue is per-process and in-memory, so pending webhooks are lost on restart; nothing is shared across replicas if the instance is scaled out; and delivery is at-most-once with a hard drop under backpressure past 128 queued payloads.
