**Explicit Go code — two deliberate `DELETE FROM reaction` statements inside the transactional `DeleteUser` driver method, on all three backends. There is no database-level rule doing this.**

What I checked:

**1. The Go delete path.** `Store.DeleteUser` (`store/user.go:171-172`) delegates to the driver's `DeleteUser`, which opens a transaction and calls `deleteUserTargetsTx`. That function removes reactions twice, and the two passes cover different things (`store/db/mysql/user_delete.go:96,102`, mirrored at `store/db/sqlite/user_delete.go:96,102` and `store/db/postgres/user_delete.go:96,102`):

- `deleteReactionsByContentIDsTx` — deletes reactions *on* the deleted user's memos, including everyone else's reactions. The content IDs come from `memoContentIDsFromRefs`, which builds `"memos/" + uid` strings (`store/db/mysql/user_delete.go:~535`) over the full memo tree walked by `listDeleteUserMemoTreeIterative` (roots plus `COMMENT`-related descendants).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?` (`store/db/mysql/user_delete.go:~400`), removing the user's own reactions left on *other* people's memos.

**2. The schema — no cascade exists to rely on.** The `reaction` table has no foreign keys at all in any backend: `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:90-98`, `store/migration/mysql/LATEST.sql:90-98`. `creator_id` and `content_id` are plain `INTEGER`/`TEXT` columns; `content_id` is a string like `memos/<uid>`, so it couldn't be an FK to `memo.id` anyway. Grepping `ON DELETE` across `store/migration/` shows the only current cascade is `memo_share.memo_id → memo(id)`; the old `user(id)` cascades appear solely in historical 0.3–0.5 migrations, not in the reaction table.

**3. Test confirmation.** `store/test/user_delete_test.go:97-112` seeds three reactions and `:217-220` asserts that after deletion exactly one survives — a bystander's reaction on a peer's memo — confirming both passes fire and that unrelated reactions are preserved.
