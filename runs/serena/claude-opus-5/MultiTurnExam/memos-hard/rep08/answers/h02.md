**Delivery: `webhook.Post` — `internal/webhook/webhook.go:120`; protection: dial-time reserved-IP blocking via `safeDialContext`/`isReservedIP` on the shared `safeClient` transport — `internal/webhook/webhook.go:59` and `internal/webhook/validate.go:44`.**

How it fits together:

- **Where delivery executes**: API handlers call `webhook.PostAsync` (`server/router/api/v1/memo_service_webhooks.go:43,71`), which just enqueues onto a bounded 128-slot channel and drops on overflow (`internal/webhook/webhook.go:184-196`). Four worker goroutines started in `init()` (`webhook.go:42-55`) drain that queue and call `Post`, which marshals the payload, optionally adds Standard Webhooks HMAC-SHA256 headers, and issues the actual `POST` via `safeClient.Do(req)` (`webhook.go:152`).
- **The primary protection** is at dial time, not URL-parse time: `safeClient`'s `http.Transport` uses `safeDialContext` (`webhook.go:32-37`), which splits the address, resolves the host, and refuses to dial if *any* resolved IP is reserved (`webhook.go:59-77`). Because the check happens on each connection's own resolution, it also defeats DNS rebinding — a hostname that passed validation at save time but later resolves to `169.254.169.254` still fails to connect.
- **Blocked ranges** are the parsed `reservedCIDRs` list: IPv4 loopback, all three RFC-1918 blocks, link-local/cloud IMDS, plus IPv6 loopback, unique-local and link-local (`internal/webhook/validate.go:14-36`).
- **Secondary, at configuration time**: `webhook.ValidateURL` (`internal/webhook/validate.go:62`) rejects non-http(s) schemes and hostnames resolving to reserved IPs when a user creates or updates a webhook (`server/router/api/v1/user_service_webhooks.go:74,161,182`). This is a usability guard; the dial-time check is what actually enforces it.
- **Escape hatch**: `webhook.AllowPrivateIPs` (`internal/webhook/validate.go:41`) disables both checks for self-hosted setups targeting LAN services. Note that nothing in the non-test code sets it — it's only flipped in `internal/webhook/webhook_test.go:91,142`, so there's currently no flag or env var wiring it up for real deployments despite the doc comment describing that use case.
