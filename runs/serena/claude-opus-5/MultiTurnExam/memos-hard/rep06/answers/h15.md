Two observations worth flagging:

- The logic is duplicated rather than centralized. `checkMemoReadAccess`, `checkAttachmentAccess`, `ListMemoAttachments`, and `ListMemoReactions` each re-implement the same "public → allow; else require auth; private → creator (or superuser)" ladder inline, and `canViewerAccessMemo` exists twice with slightly different admin tests — `viewer.Role == store.RoleAdmin` (`server/notification/email.go:310`) vs `isSuperUser(viewer)` (`server/router/api/v1/user_service_notifications.go:307`). `checkMemoReadAccess` notably does *not* grant admins access to private memos, while the attachment/reaction checks do.
- **Share tokens are a deliberate bypass:** `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:151`, "No authentication required") resolves a token to a memo without a visibility check, and the file server honors a `share_token` query param before its visibility branch (`server/router/fileserver/fileserver.go:681-688`), gated only on the token existing, matching that memo, and not being expired.
