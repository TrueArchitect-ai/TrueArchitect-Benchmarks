**Premise correction: there is no Redis anywhere in this repository — the cache layer is a process-local, in-memory map. No `redis` import, module in `go.mod`/`go.sum`, config key, or even a mention in docs; a case-insensitive grep for "redis" across the whole repo returns nothing.**

**Actual mechanism.**

The cache is `store/cache/cache.go` — a `Cache` struct backed by a `sync.Map` with an atomic item counter and a background cleanup goroutine (`store/cache/cache.go:66-85`). Entries carry an absolute `expiration` stamped at write time (`item`, `:35-39`). It is per-process state, so in a multi-replica deployment each instance has its own independent copy.

There's no connection configuration at all — just a `cache.Config` struct (`store/cache/cache.go:42-54`) constructed in Go. The values used by the server are hardcoded in `store.New`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
— `store/store.go:38-44`. Three caches are built from that one config: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:50-52`). `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) holds the same numbers but isn't what the store uses.

**TTL for user entries: 10 minutes.** Every user write goes through `Cache.Set`, which forwards to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — the store never calls `SetWithTTL` directly, so there's no user-specific override. Call sites: `store/user.go:98`, `:122`, `:132`, `:143`, `:167`, all keyed by `userCacheKey(user.ID)` (`store/user.go:88`).

Three details that matter more than the nominal TTL:

- **Expiry is lazy plus swept.** `Get` checks `time.Now().After(itm.expiration)` and deletes on read (`store/cache/cache.go:135-144`); a ticker at `CleanupInterval` (5 min) sweeps the rest (`:200-250`). So an entry can outlive 10 minutes in memory until it's read or swept.
- **Capacity eviction can drop entries early.** Once the shared 1000-item ceiling is crossed, `cleanupOldest` evicts ~20% (`store/cache/cache.go:117-119`, `:253`), so a user entry may vanish well before its TTL.
- **Explicit invalidation on delete:** `store/user_delete.go:40` removes the entry directly. Note also that `Store.GetUser` only consults the cache when looking up by ID — a username lookup always hits the database (`store/user.go:148-156`).
