**Premise correction: neither. There is no message broker in this repository — no NATS, RabbitMQ/AMQP, or Kafka client appears in any Go file, and none is present in `go.mod`/`go.sum`. There is no queue *declaration* in the broker sense, and nothing is consumed over a network.**

**Actual mechanism: an in-process buffered Go channel drained by four goroutines, all inside `internal/webhook/webhook.go`.**

- **The "queue"** is a package-level channel with a fixed capacity of 128:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  — `internal/webhook/webhook.go:39`, declared in the same `var` block as the shared HTTP client.

- **The workers** are started by the package's `init()` — a fixed pool of four goroutines, each ranging over the channel and calling `Post`, logging a warning on failure (`internal/webhook/webhook.go:42-55`). They start when the package is first loaded, not from any explicit server wiring, and there's no shutdown path that drains or closes the channel.

- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184-196`), called from the memo webhook dispatchers (`server/router/api/v1/memo_service_webhooks.go:43`, `:71`). It's a non-blocking `select` with a `default` branch: **if the buffer is full the payload is dropped** with a `slog.Warn`, rather than blocking or retrying.

- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`), which marshals the payload, optionally adds Standard Webhooks HMAC headers, and issues the request via `safeClient.Do` at `:152`.

Consequences worth being explicit about, since they're exactly what a broker would change: the queue is per-process and in-memory, so nothing is persisted, nothing survives a restart or crash, there is no acknowledgement, no retry or dead-letter path, and no cross-replica sharing — each server instance dispatches only the events it produced. The only backpressure is the 128-slot buffer and the drop-on-full behavior.
