**1st: `store.User` (~7 packages, 5 of them non-test); 2nd: `store.Memo` (~6 packages, 4 non-test)**

Method: I enumerated the entity structs declared in the `store` package root (`store/user.go:29`, `store/memo.go:35`, `store/attachment.go`, `store/inbox.go`, `store/reaction.go`, `store/memo_relation.go`, `store/memo_share.go`, `store/user_identity.go`, …), then counted distinct packages under `server/`, `cmd/`, and `internal/` — i.e. outside the `store` tree, excluding the three driver packages and `store/test`, which reference nearly everything by construction — that name each type.

**`store.User`** — 7 packages:
- `server/router/api/v1` (heaviest user; e.g. `user_service.go`, `memo_service_converter.go`)
- `server/auth` (`server/auth/authenticator.go`)
- `server/notification` (`server/notification/email.go`)
- `server/router/fileserver` (`fileserver.go:715`)
- `server/router/frontend`
- `server/router/rss`
- `server/router/api/v1/test` (test package)

**`store.Memo`** — 6 packages:
- `server/router/api/v1`
- `server/notification` (`server/notification/email.go`, the densest single file at ~10 references)
- `server/router/frontend`
- `server/router/rss`
- `server/runner/memopayload` (`RebuildMemoPayload` takes a `*store.Memo`)
- `server/router/api/v1/test` (test package)

Third is `store.Attachment` at 4 packages (`api/v1`, `fileserver`, `rss`, plus the v1 test package), so the top two are clearly separated from the rest.

Two notes on the counting: `store.User` leads partly because auth and the file server both need the user record directly, whereas `store.Memo` never surfaces in `server/auth` or `server/router/fileserver`. And several entity types score zero outside the data layer — `store.UserSetting`, `store.InstanceSetting`, and `store.IdentityProvider` — because the API layer works with the protobuf forms (`storepb.UserSetting`, etc.) rather than the store structs. Counts are grep-based on the qualified identifier (`store.User\b`), so they're approximate rather than type-resolved.
