Notes on the hops:

- **How the browser gets the URL.** The avatar is stored as a base64 data URI in the user row, so the API never ships the blob in JSON. `convertUserToProto` rewrites the field to `/file/{users/username}/avatar` when the stored value parses as a data URI (`server/router/api/v1/user_service_converters.go:36`), which is what produces the `/file/users/:identifier/avatar` request.

- **Access check before the lookup.** `serveUserAvatar` gates anonymous access on instance visibility: if `s.Profile.AllowAnonymous()` is false, it resolves the caller via `getCurrentUser` and 401s when there's no session/access token/PAT (`server/router/fileserver/fileserver.go:173-181`). On an open instance the fetch proceeds unauthenticated.

- **Data layer.** `getUserByUsername` builds `&store.FindUser{Username: &identifier}` and calls `Store.GetUser`. `GetUser` consults `s.userCache` only when looking up by ID (`store/user.go:149-156`) — this path filters by username, so it always falls through to `ListUsers`, which delegates to `s.driver.ListUsers` and warms the cache (`store/user.go:136-146`). The driver builds the `username = ?` predicate and selects `avatar_url` among the columns (`store/db/sqlite/user.go:88,128`; column list at `store/db/sqlite/user.go:14`).

- **Back out.** The handler reads `user.AvatarURL`, decodes it with `parseDataURI`, rejects anything outside `avatarAllowedTypes` (`server/router/fileserver/fileserver.go:75, 196-203`), sets security and cache headers, and writes the bytes with `c.Blob` (`:205-209`).
