**Premise correction: there is no nightly database-cleanup job, and the cron scheduler is never used by the running server — so there is no scheduled time to report.**

Two separate corrections:

**1. No database-cleanup job exists.** Grepping for `cleanup`/`vacuum`/`purge`/`prune` across `server/`, `store/`, and `cmd/` turns up no scheduled maintenance task. The hits are unrelated: in-request attachment-storage cleanup during user deletion (`server/router/api/v1/user_service.go:421-450`), a comment about relation/attachment cleanup inside `DeleteMemo` (`server/router/api/v1/memo_service.go:579`), and the in-memory cache's `CleanupInterval` of 5 minutes (`store/store.go:42`, `store/cache/cache.go:47,60`) — that last one expires cache entries in a goroutine (`store/cache/cache.go:83`), not database rows.

**2. The cron scheduler isn't wired into the server at all.** `internal/scheduler` is a complete, working package — cron parsing (`internal/scheduler/parser.go`), job registration (`internal/scheduler/scheduler.go`), and Recovery/Logging/Timeout middleware (`internal/scheduler/middleware.go`) — but every reference to `scheduler.New` and `.Register(` lives in that package's own tests (`internal/scheduler/integration_test.go`, `scheduler_test.go`, `example_test.go`). No production file imports it. The `"0 9 * * *"` expression you might find in a search is test data at `internal/scheduler/integration_test.go:183`, not a configured job.

**What actually runs on a schedule:** exactly one background job, and it's not cron-driven or nightly. `s3presign.Runner` re-signs S3 attachment URLs on a `time.Ticker` with `runnerInterval = 12 * time.Hour` (`server/runner/s3presign/runner.go:27,29-41`), started from `Server.startBackgroundRunners` at `server/server.go:162-171` with one immediate pass at boot (`:163`). Being interval-based from process start, it has no fixed wall-clock time — it fires 12 and 24 hours after whenever the server last started.
