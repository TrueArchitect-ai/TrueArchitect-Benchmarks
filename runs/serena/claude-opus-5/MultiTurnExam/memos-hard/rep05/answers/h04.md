Evidence:

1. **Exactly one import of the package in the entire tree.** `grep -rn "usememos/memos/store/db/mysql" --include=*.go` returns a single hit: `store/db/db.go:8`. Since Go requires an import to reference a package's exported identifiers, no other file can construct the MySQL driver.

2. **That import is the factory itself.** `store/db/db.go:14` defines `NewDBDriver`, and the only call to `mysql.NewDB` is inside its `switch profile.Driver` at `store/db/db.go:22`, alongside the sqlite and postgres branches (`:20`, `:24`).

3. **Callers go through the factory.** Every other driver construction site uses `db.NewDBDriver` — `store/test/store.go:28` and `:50`, and `server/router/api/v1/test/memo_service_benchmark_test.go:70`.

Two things that look like counterexamples but aren't:

- `store/db/mysql/mysql.go:17,30,73` reference `mysql.Config` / `mysql.ParseDSN` — that's the third-party `github.com/go-sql-driver/mysql` package being used *inside* the driver implementation for DSN parsing, not the repo's own driver being constructed.
- `store/test/containers.go:42,101-105` uses `mysql.Run` / `mysql.WithDatabase` — that's the testcontainers MySQL module spinning up a database server for integration tests; the resulting DSN is then fed through `profile` into `db.NewDBDriver`.

The only direct constructions of a sibling driver outside the factory are sqlite ones in tests (`store/demo_seed_test.go:24`, `store/deployment_config_test.go:416`); MySQL has no such bypass.
