**1st: `store.User` (~7 packages outside the store layer, 30 files); 2nd: `store.Memo` (~6 packages, 21 files)**

Counting packages (directories) outside `store/**` that reference each entity type by name:

**`store.User` — 7 packages** (6 non-test):
- `server/auth` (`server/auth/*.go`)
- `server/notification`
- `server/router/api/v1`
- `server/router/fileserver` (e.g. `getUserByUsername` at `server/router/fileserver/fileserver.go:715`)
- `server/router/frontend`
- `server/router/rss`
- `server/router/api/v1/test` (test-only)

**`store.Memo` — 6 packages** (4 non-test):
- `server/notification`
- `server/router/api/v1`
- `server/router/rss`
- `server/runner/memopayload` (`RebuildMemoPayload`, `server/runner/memopayload/runner.go`)
- `server/router/frontend` and `server/router/api/v1/test` (test files only)

Rest of the field, for context: `store.Attachment` 4 packages (`api/v1`, `api/v1/test`, `fileserver`, `rss`); `store.Inbox`, `store.MemoShare`, `store.MemoRelation` 3 each; `store.Reaction` and `store.UserIdentity` 2 each; `store.IdentityProvider`, `store.UserSetting`, `store.InstanceSetting` are essentially confined to `server/router/api/v1`.

`User` leads mainly because authentication touches it everywhere — `server/auth` resolves users for tokens/sessions, and both `fileserver` and `frontend` need a user for avatar serving and page rendering, whereas `Memo` is concentrated in the API service plus RSS.

Method note: this is a grep over `store.<Type>\b` in non-generated `.go` files (`proto/gen` excluded), with the `store/` tree itself — including `store/db/{sqlite,mysql,postgres}` and `store/test` — excluded as "the data layer." The `\b` anchor keeps `store.User` from matching `store.UserSetting`/`store.UserIdentity` and `store.Memo` from matching `store.MemoRelation`/`store.MemoShare`. Companion query structs (`FindUser`, `UpdateMemo`, …) aren't counted as the entity type; including them would widen `User`'s lead, since `FindUser` appears in `server/auth` and both router packages as well.
