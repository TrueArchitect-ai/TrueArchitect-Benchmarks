Two related notes:

- **Deliberate bypass:** `GetMemoByShare` (`server/router/api/v1/memo_share_service.go:151-192`) serves a memo with no authentication — the share token *is* the grant, validated for existence and expiry via `getActiveMemoShare` (`:199`) / `isMemoShareExpired` (`:195`). The file server honors the same token (`fileserver.go:683-690`).
- **Not a separate site:** the MCP router exposes `MemoService_ListMemos` / `MemoService_GetMemo` (`server/router/mcp/catalog.go:12,14`) but delegates to the same `APIV1Service` handlers, so it inherits enforcement rather than reimplementing it.

The duplication is worth flagging: `canViewerAccessMemo` exists twice with identical logic (`user_service_notifications.go:309` and `notification/email.go:313`), and the `Visibility != Public → require user → Private requires owner/superuser` pattern is hand-inlined in at least four API handlers instead of routing through `checkMemoReadAccess`. One difference is substantive: `checkMemoReadAccess` does *not* grant admins access to private memos (`memo_service.go:63`), while the inlined copies and the file server do (`isSuperUser` / `RoleAdmin`).
