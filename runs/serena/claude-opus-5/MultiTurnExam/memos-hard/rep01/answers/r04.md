**Premise correction: neither. There is no message broker in this repository at all — no NATS, no RabbitMQ, no AMQP, no Kafka. Greps over `go.mod`/`go.sum` and all Go sources for `nats`, `rabbit`, `amqp`, and `kafka` return zero hits, so there is no queue declaration to point to.**

**Actual mechanism — an in-process buffered Go channel with a fixed worker pool, entirely in `internal/webhook/webhook.go`:**

- **The "queue"** is a package-level channel declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  Capacity 128, in memory, per process.
- **The "workers"** are 4 goroutines started in `init()` (`internal/webhook/webhook.go:42-55`), each ranging over the channel and calling `Post` for every payload, logging a warning on failure. There is no consumer group, no ack, no broker connection.
- **The producer** is `PostAsync` (`internal/webhook/webhook.go:184-196`), which does a non-blocking `select` send: if the buffer is full, the payload is **dropped** with a `slog.Warn` rather than blocking or retrying (`:191-195`). A nil payload is likewise dropped (`:185-188`).
- **Delivery** happens in `Post` (`internal/webhook/webhook.go:120`) — signs the body when a secret is configured, then POSTs via the SSRF-guarded `safeClient` (30 s timeout).

Operational consequences of this design, since a broker would have provided otherwise: no persistence (a restart loses queued events), no retry or dead-letter path (a failed POST is logged and discarded at `:46-51`), no cross-instance distribution (each process has its own queue and workers), and silent shedding under burst load beyond 128 pending events.

The upstream producers are the memo RPC handlers described in h06, which all funnel through `PostAsync`.
