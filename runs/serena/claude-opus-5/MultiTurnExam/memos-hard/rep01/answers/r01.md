**Premise correction: there is no Redis anywhere in this repository.** No `redis` import, no dependency in `go.mod`/`go.sum`, no config key or connection setup — a case-insensitive grep across Go sources, mod files, and YAML returns nothing. The cache layer is entirely in-process.

**Actual mechanism:**

- **Implementation** — a hand-rolled, thread-safe in-memory cache in `store/cache/cache.go`: `sync.Map` for storage, an atomic item counter, per-item expiration timestamps, and a background cleanup goroutine (`Cache` struct at `store/cache/cache.go:66-72`, `New` at `:74`). The `Interface` it satisfies is declared at `store/cache/cache.go:11-32`.
- **Where it's "configured"** — `store.New` builds one `cache.Config` and hands it to three caches (`store/store.go:38-53`):
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  used for `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29, 50-52`). The identical defaults also exist as `cache.DefaultConfig()` (`store/cache/cache.go:57-64`), which `store.New` doesn't call — it inlines the same values.

**TTL for user entries: 10 minutes**, and it is not separately tunable. Every user write goes through `s.userCache.Set(...)` (`store/user.go:98,122,132,143,167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:92-95`) — nothing in the repo ever calls `SetWithTTL` with a custom TTL. There's no env var or flag for it; changing it means editing `store/store.go:40`.

Two behaviors worth knowing alongside the TTL:

- **Capacity eviction can drop entries early** — exceeding `MaxItems: 1000` triggers `cleanupOldest()` on the next `Set` (`store/cache/cache.go:115-118`), so on an instance with >1000 active users, entries may be evicted well before 10 minutes.
- **Reads are lazily expiring, and only ID lookups hit the cache** — `Get` checks expiration and deletes on access (`store/cache/cache.go:135-146`); `Store.GetUser` consults the cache only when finding by ID (`store/user.go:149-156`), so username/email lookups always reach the database. Explicit invalidation happens on user deletion (`store/user_delete.go:40`), and all three caches' cleanup goroutines stop in `Store.Close` (`store/store.go:74-76`).
