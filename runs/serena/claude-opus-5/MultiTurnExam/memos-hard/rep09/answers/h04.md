**No — `mysql.NewDB` is constructed in exactly one place, the factory itself.**

Evidence:

1. A repo-wide grep for the package's import path, `github.com/usememos/memos/store/db/mysql`, returns exactly one hit: `store/db/db.go:8`. Since Go requires an import to reference an exported identifier, no other file in the module — production or test — can construct the driver. That single grep is dispositive.

2. The only constructor the package exports is `func NewDB(profile *profile.Profile) (store.Driver, error)` at `store/db/mysql/mysql.go:20`, and its sole call site is `store/db/db.go:22`, inside the `switch profile.Driver` in `NewDBDriver`. Note it returns the `store.Driver` interface, not a concrete `*DB`, so callers can't get at package internals even indirectly.

3. Everything else funnels through the factory. The files that mention "mysql" outside the package do so as a driver-name string or dialect branch, not a construction — e.g. `internal/profile/profile.go` (validating the `--driver` value), `internal/filter/*` (SQL dialect branching), `store/test/containers.go` (spinning up a MySQL test container and building a DSN). The test helpers then call `db.NewDBDriver` (`store/test/store.go:28`, `:50`), as does `server/router/api/v1/test/memo_service_benchmark_test.go:70`.

The same holds for the sibling drivers: `sqlite` and `postgres` are likewise only reachable via `store/db/db.go:20` and `:24`.
