**Explicit Go code — no database-level rule exists for reactions; each driver deletes them by hand inside the delete-user transaction.**

Evidence, and what I checked:

**1. The Go deletion path.** Each driver's `DeleteUser` opens a transaction and calls `deleteUserTargetsTx`, which removes reactions in two separate sweeps before the memos and user row go away:

- `deleteReactionsByContentIDsTx` — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500, covering reactions *other people* left on the deleted user's memos. Content IDs are built as `"memos/" + memo.UID` by `memoContentIDsFromRefs` (`store/db/mysql/user_delete.go:417`, `:549`).
- `deleteReactionsByCreatorTx` — `DELETE FROM reaction WHERE creator_id = ?`, covering reactions the deleted user left on *anyone's* memos (`store/db/mysql/user_delete.go:437`).

Both are invoked from `deleteUserTargetsTx` at `store/db/mysql/user_delete.go:96` and `:102`. All three drivers carry the same code at the same lines: `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/sqlite/user_delete.go:96,102,380,400`.

**2. The schema has no constraint to do it.** The `reaction` table in all three `LATEST.sql` files declares `creator_id` as a bare `INTEGER/INT NOT NULL` with only a `UNIQUE(creator_id, content_id, reaction_type)` — no `FOREIGN KEY`, hence no `ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql`, `store/migration/postgres/LATEST.sql`, `store/migration/mysql/LATEST.sql`). Grepping every migration for `FOREIGN KEY|ON DELETE|CASCADE` shows the only cascades in the current schema are on `memo_share.memo_id → memo(id)` (`store/migration/*/LATEST.sql:108-109`). The older per-version SQLite migrations did have `creator_id → user(id) ON DELETE CASCADE` on some tables (e.g. `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql`), but those don't cover `reaction` and aren't in the current schema.

Also worth noting: `content_id` is a text reference like `memos/{uid}`, not a numeric FK, so a cascade on that side isn't expressible anyway — which is why the Go code resolves the memo tree (including comment descendants) first and deletes by content ID.
