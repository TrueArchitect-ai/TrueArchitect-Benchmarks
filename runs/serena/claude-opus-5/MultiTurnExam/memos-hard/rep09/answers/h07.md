Notes on the hops:

- **Wiring**: the service is constructed and its routes registered at `server/server.go:81-82`; the group `/file` is created in `RegisterRoutes` (`fileserver.go:122`).
- **Handler** (`fileserver.go:168`): on a private instance (`!s.Profile.AllowAnonymous()`) it first requires a viewer via `getCurrentUser` → `auth.Authenticator.AuthenticateToUser` (`fileserver.go:708-712`). Then it reads `:identifier` and looks the user up.
- **Lookup** (`fileserver.go:715`): `getUserByUsername` calls `s.Store.GetUser(ctx, &store.FindUser{Username: &identifier})` — username only, never ID.
- **Store layer** (`store/user.go:148`): `GetUser` only consults `userCache` when `find.ID != nil`, so this avatar path always falls through to `ListUsers` (`store/user.go:136`), which delegates to `s.driver.ListUsers` and populates the cache by ID.
- **Data layer**: the driver builds the `WHERE username = ?` query and scans the row, including `avatar_url` (`store/db/sqlite/user.go:88`, with parallel implementations in `store/db/postgres/user.go` and `store/db/mysql/user.go`).

The image bytes themselves never leave the database row: `user.AvatarURL` holds a `data:<mime>;base64,...` URI, which `parseDataURI` (`fileserver.go:737`) decodes; the MIME type is checked against `avatarAllowedTypes` (`fileserver.go:75`, `:201`) before the blob is written out with security and cache headers (`fileserver.go:205-209`).
