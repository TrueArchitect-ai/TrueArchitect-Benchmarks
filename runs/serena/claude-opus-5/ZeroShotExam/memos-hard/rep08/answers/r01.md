**Premise correction:** There is no Redis anywhere in this repository. A case-insensitive search for `redis` (and `memcach`) across the whole tree — Go source, configs, Docker/compose files, docs, and the `web/` frontend — returns zero hits, and `go.mod` has no Redis client dependency. There is no external cache server, no connection string, and no cache-related env var to configure. The cache layer is a **process-local, in-memory Go cache**, so it is not shared between instances and is empty on every restart.

**Actual mechanism**

*Implementation* — `store/cache/cache.go` defines a thread-safe in-memory cache built on `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-90`). Each entry (`item`) stores the value, an absolute `expiration` timestamp, and a rough size estimate (`store/cache/cache.go:34-39`).

*Wiring* — `store.New()` in `store/store.go:38-61` builds one `cache.Config` and uses it for three separate caches held on the `Store` struct (`store/store.go:26-29`):
- `instanceSettingCache`
- `userCache`
- `userSettingCache`

*TTL for user entries* — **10 minutes**, from the shared `cacheConfig.DefaultTTL` at `store/store.go:40-45`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
}
```

Every user write path calls plain `Set` (`store/user.go:98, 122, 132, 143, 167`), which delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`) — nothing in the codebase calls `SetWithTTL` directly, so users get the default 10 minutes with no per-entry override. `cache.DefaultConfig()` (`store/cache/cache.go:57-64`) declares the same values independently, but the store does not use it.

Two details worth noting about that TTL:
- Expiry is **absolute from write, not sliding** — `expiration: time.Now().Add(ttl)` is set on write and reads don't extend it (`store/cache/cache.go:110-114`), and a re-`Set` from any of the write paths resets the 10-minute clock.
- The TTL is not the only eviction path. `MaxItems: 1000` triggers `cleanupOldest()` (`store/cache/cache.go:117-119`), which drops ~20% of entries, so a user entry can disappear well before 10 minutes on a busy instance. A background `cleanupLoop` also sweeps expired entries every 5 minutes (`store/cache/cache.go:200-215`); reads are lazily validated against expiry regardless (`store/cache/cache.go:135-144`).

Cache keys: users are keyed by the plain user ID (`userCacheKey`, `store/user.go:88-90`); user settings use `"<userID>-<key>"` (`getUserSettingCacheKey`, `store/cache.go:7-9`).
