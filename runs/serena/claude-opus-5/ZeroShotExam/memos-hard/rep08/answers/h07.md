Two things worth noting about this path:

- The avatar bytes live **in the `user` row itself** as a base64 `data:` URI in `avatar_url` — not in the attachment/blob storage layer. So there is no local-file/S3 branch here, unlike `serveAttachmentFile`; the data layer is a single column read.
- There is **no per-user authorization check** on another user's avatar. The only gate is instance-level: if `Profile.AllowAnonymous()` is false, *some* valid session/PAT is required (`fileserver.go:173-181`), but any authenticated viewer may fetch any user's avatar by username. That's deliberate — avatars are treated as public profile data — and contrasts with `checkAttachmentPermission` (`fileserver.go:650`), which does enforce creator/visibility rules.
