**Premise correction: there is no per-user API rate-limiting middleware in this repository.** Memos has no rate limiter registered anywhere in its HTTP or RPC stack, so there are no per-user request limits to report.

**What I checked**

- **Echo HTTP middleware chain** — `server/server.go:51-52` registers exactly two: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`). Nothing else.
- **Connect/gRPC interceptor chain** — `server/router/api/v1/v1.go:133-137` registers four interceptors: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). No rate-limit interceptor.
- **Dependency check** — `golang.org/x/time` is present in `go.mod:151` but marked `// indirect`; `rate.Limiter` is never imported or used in any `.go` file. No tollbooth, ulule/limiter, or similar.
- **Repo-wide grep** for `rate limit` / `429` / `ResourceExhausted` / `throttle` / `limiter` turns up no request-rate logic.
- The only file matching "rate limit" as a concept is `internal/email/README.md:286` ("### 5. Implement Rate Limiting") and `internal/email/doc.go:86` — both are *security recommendations for consumers of the email package*, with an illustrative `rate.NewLimiter(rate.Every(time.Second), 10)` snippet. That code is documentation only; it isn't wired into anything.

**Three things that are adjacent but are not per-user rate limiting**

| Mechanism | Location | What it actually is |
|---|---|---|
| `maxAPIRequestBytes = 256 << 20` | `server/router/api/v1/v1.go:20`, applied at `:126`, `:141`, `:144` | A 256 MiB **per-request body size** cap (`http.MaxBytesHandler` + `connect.WithReadMaxBytes`) — a payload limit, not a rate. |
| `imageProcessingSemaphore` | declared `server/router/api/v1/v1.go:41`, initialized `semaphore.NewWeighted(2)` at `:60`, acquired in `acquireImageProcessingSlot` (`server/router/api/v1/attachment_service_image.go:67-77`) | A **global concurrency cap of 2** simultaneous EXIF-stripping operations, shared across all users. Callers that can't acquire a slot get `codes.ResourceExhausted` ("too many image processing requests", `server/router/api/v1/attachment_service.go:160`). It bounds parallelism, not requests over time, and has no per-user dimension. |
| `internal/scheduler/middleware.go` | `Recovery`, `Logging`, `Timeout` | Middleware for **background scheduled jobs**, not API requests. |

If you need per-user API rate limiting for a Memos deployment, it currently has to come from a reverse proxy in front of it — the application itself provides no hook for it.
