**Premise correction:** There is no Redis in this repository. A case-insensitive search across the entire tree (excluding `.git`/`node_modules`) for `redis` or `memcache` returns zero hits — no client dependency in `go.mod`, no connection string, no config flag, no Docker service. Memos is a single Go binary backed by SQLite/MySQL/Postgres, and its cache layer is purely **in-process and in-memory**.

**Actual mechanism**

*Cache implementation* — `store/cache/cache.go` defines a thread-safe in-memory cache built on `sync.Map` plus an `atomic.Int64` item counter. Each entry (`item`, line 35) stores the value, an absolute `expiration` time, and a rough size estimate. Expiry is lazy-on-read (`Get`, line 123, deletes and reports a miss if `time.Now().After(itm.expiration)`) plus a background `cleanupLoop` goroutine (line 199). There is also a `MaxItems` overflow eviction path, `cleanupOldest` (line 254).

*Where it's "configured"* — `store/store.go:40-56`, in `store.New()`. Instead of a connection, the store builds one `cache.Config` literal and instantiates three separate caches with it:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

held as `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:27-29`), each with its own goroutine, all shut down in `Store.Close()` (lines 74-76). Note these caches are per-`Store` — i.e. per process — so they are not shared across replicas.

*TTL for user entries* — **10 minutes**, inherited from `DefaultTTL`. Every write goes through `Cache.Set` (`store/cache/cache.go:93`), which delegates to `SetWithTTL(..., c.config.DefaultTTL)`. Nothing in the user path calls `SetWithTTL` with a custom duration, so the 10-minute default applies uniformly. The same 10 minutes applies to user settings and instance settings.

*User cache lifecycle* — `store/user.go`: key is just the stringified user ID (`userCacheKey`, line 88). Entries are populated/refreshed on `CreateUser` (98), `CreateUserIfNoUsers` (122), `UpdateUser` (132), `ListUsers` (143, caches every user in the result), and `GetUser` (167). Reads only hit the cache when the lookup is by ID (`GetUser`, line 150) — lookups by username or other fields always fall through to the driver. Invalidation on delete is explicit via `deleteUserCache` (`store/user_delete.go:39-45`), which drops the user key and the associated user-setting keys.

One consequence worth flagging: because the TTL is absolute from the moment of `Set` and every write path re-`Set`s the entry, a frequently-read user is *not* kept alive indefinitely by reads — but `GetUser` on a miss re-caches via `ListUsers`, so the effective refresh is at most every 10 minutes per user.
