**Premise correction: this repository has no per-user API rate-limiting middleware.** There is no middleware, interceptor, or config that limits requests per user (or per IP) anywhere in the Memos server, so there are no request limits to report.

What I verified:

- **The full Echo HTTP middleware stack** is just two entries — `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`). Nothing else is registered via `.Use(...)`.
- **The full Connect RPC interceptor chain** is four entries — `server/router/api/v1/v1.go:133-138`: `MetadataInterceptor` (header→gRPC metadata), `LoggingInterceptor`, `RecoveryInterceptor`, and `AuthInterceptor`. All four are defined in `server/router/api/v1/connect_interceptors.go`; none counts or throttles requests.
- A repo-wide search for `rate limit` / `ratelimit` / `throttle` / `429` / `TooManyRequests` / `x/time/rate` across all Go, TS/TSX, and proto sources returns only two hits, both aspirational docs about a feature that doesn't exist: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse", listed under future considerations) and `internal/email/README.md:286` (a "### 5. Implement Rate Limiting" example snippet).
- `golang.org/x/time` is present in `go.mod:151` but marked `// indirect` — pulled in transitively, not used for a limiter.

**The only per-request limit that does exist is a body-size cap, not a rate cap:** `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied three ways — `http.MaxBytesHandler` on the gRPC-gateway routes (`/api/v1/*`, `/file/*`) at line 126, `connect.WithReadMaxBytes` at line 141, and `http.MaxBytesHandler` on the Connect routes at line 144.

If you're looking for the per-user *authorization* layer instead, that's `AuthInterceptor` (`connect_interceptors.go:205-213`) backed by `Authorizer` in `server/router/api/v1/authz.go` — it gates access by identity and role, but applies no frequency limits.
