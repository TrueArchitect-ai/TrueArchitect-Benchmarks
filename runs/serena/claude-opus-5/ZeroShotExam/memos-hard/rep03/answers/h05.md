**h05.**

**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the delete-user transaction. There is no FK/cascade on the `reaction` table.

**What I checked**

1. **Schema — no database-level rule.** The `reaction` table has `creator_id INTEGER NOT NULL` and `content_id TEXT NOT NULL` as plain columns with only a `UNIQUE(creator_id, content_id, reaction_type)` constraint — no `FOREIGN KEY`, no `ON DELETE CASCADE`:
   - `store/migration/sqlite/LATEST.sql:92-99`
   - `store/migration/postgres/LATEST.sql:91-98`
   - `store/migration/mysql/LATEST.sql:91-98`

   Grepping `FOREIGN KEY|REFERENCES|ON DELETE` across all three `LATEST.sql` files returns exactly one hit per dialect, and it's `memo_share.memo_id → memo(id) ON DELETE CASCADE` (e.g. `store/migration/sqlite/LATEST.sql:109`) — nothing touching `reaction`. The `0.20`/`0.23` reaction migrations only create the table and rewrite `reaction_type` values.

2. **Go code — two explicit deletes, per driver.** `deleteUserTargetsTx` runs both before the memo/user rows are removed:
   - `deleteReactionsByContentIDsTx` — removes reactions *on* the deleted user's memos (and their comment subtree), keyed by `content_id` built as `"memos/" + memo.UID` (`memoContentIDsFromRefs`).
   - `deleteReactionsByCreatorTx` — removes reactions the user *made* anywhere, `DELETE FROM reaction WHERE creator_id = ?`.

   Locations:
   - sqlite: `store/db/sqlite/user_delete.go:94-103` (call sites), `:380-386` and `:399-402` (implementations)
   - postgres: `store/db/postgres/user_delete.go:96,102`, `:380-386`, `:400-402`
   - mysql: `store/db/mysql/user_delete.go:96,102`, `:417-423`, `:437-439`

   All of this runs in one transaction opened in `DeleteUser` (`store/db/sqlite/user_delete.go:29-57`), reached from `store.DeleteUser` → `s.driver.DeleteUser` (`store/user.go:171-172`).

3. **Test coverage confirming behavior.** `store/test/user_delete_test.go` creates three reactions (two by the deleted user, one by a peer on a peer-owned memo) and asserts after deletion that only the peer's reaction on the surviving memo remains (`store/test/user_delete_test.go:97-113`, `:216-220`).

Note the content-ID delete is keyed by memo UID string, not by an FK — so reaction cleanup depends on the memo tree being collected correctly by `listDeleteUserMemoTreeRecursive` (`store/db/sqlite/user_delete.go:128-160`); any reaction whose `content_id` refers to a non-memo resource would not be covered by that path, only by the `creator_id` delete.
