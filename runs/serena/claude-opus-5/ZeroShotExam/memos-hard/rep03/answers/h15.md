Memo visibility is enforced independently on several server surfaces. Distinct enforcement sites:

**Core Connect/gRPC memo API**
- Single-memo read gate (`checkMemoReadAccess`: archived → creator only, non-public → auth required, private → creator only) — `server/router/api/v1/memo_service.go:39-77` (called from `GetMemo` at :356, parent memo at :367, and `ListMemoComments` at `server/router/api/v1/memo_service_comments.go:148`)
- List query shaping (anonymous → `VisibilityList = [PUBLIC]`; authed → CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]`) — `server/router/api/v1/memo_service.go:217-227`
- Comment listing filter (separate `memoFilter` string on the relation query) — `server/router/api/v1/memo_service_comments.go:155-161`
- Memo-relation visibility filter when converting relations — `server/router/api/v1/memo_service_converter.go:183-188` (`batchConvertMemoRelations`) and `server/router/api/v1/memo_relation_service.go:108-112`
- User stats aggregation — `server/router/api/v1/user_service_stats.go:77-92` and `:216-221`

**Memo sub-resources (each re-checks visibility inline, not via `checkMemoReadAccess`)**
- Reactions (list/upsert/delete) — `server/router/api/v1/reaction_service.go:38-40`, `:83-85`
- Comment creation — `server/router/api/v1/memo_service_comments.go:41-43`
- Memo attachments listing — `server/router/api/v1/memo_attachment_service.go:213-225`
- Attachment access via API (`checkAttachmentAccess`, follows the linked memo's visibility) — `server/router/api/v1/attachment_service.go:122-155` (visibility branch at :445-452)

**Non-gRPC HTTP surfaces**
- Raw file/blob serving (`checkAttachmentPermission`; public+anonymous allowed, share-token fallback, private → creator/admin) — `server/router/fileserver/fileserver.go:650-703` (invoked at :149)
- RSS feeds (explore + per-user, hard-limited to `[]store.Visibility{store.Public}`) — `server/router/rss/rss.go:90` and `:141`
- Sitemap XML (public-only listing) — `server/router/frontend/frontend.go:150`
- Share-link resolution — visibility is deliberately bypassed in favor of an opaque token, with archived/missing treated as not-found — `server/router/api/v1/memo_share_service.go` (`GetMemoByShare`, ~:148-175); token issuance/revocation restricted to creator/admin at :44, :93, :134

**Push / notification surfaces**
- SSE broadcast filtering (`SSEClient.canReceive`: private events only to creator or admin) — `server/router/api/v1/sse_hub.go:134-143`, with event visibility populated in `server/router/api/v1/sse_event_helpers.go:29-37`
- Email notifications (`canViewerAccessMemo`) — `server/notification/email.go:306-320`
- Mention/inbox targeting (`canUserAccessMentionContext`) — `server/router/api/v1/memo_mention_helpers.go:56-72`

**Backing store layer** (executes the filters the API surfaces build, not an independent policy): `store/memo.go:69` (`FindMemo.VisibilityList`) and `store/memo_relation.go:26` (`FindMemoRelation.MemoFilter`).

Note the MCP router (`server/router/mcp/`) adds no visibility logic of its own — it proxies to the v1 handlers above.
