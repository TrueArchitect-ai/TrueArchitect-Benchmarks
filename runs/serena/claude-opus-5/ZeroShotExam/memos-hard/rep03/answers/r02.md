**Premise correction: this repository (Memos) has no per-user API rate-limiting middleware.** There is no request-per-interval limiter registered anywhere — not per user, not per IP, not global.

**What actually is registered**

Echo middleware chain, `server/server.go:51-52`:
- `middleware.Recover()`
- `newCORSMiddleware(profile)` (`server/cors.go:13`)

Connect RPC interceptors, `server/router/api/v1/v1.go:133-137`:
- `NewMetadataInterceptor()`, `NewLoggingInterceptor()`, `NewRecoveryInterceptor()`, `NewAuthInterceptor(authorizer)` — all defined in `server/router/api/v1/connect_interceptors.go`

The gRPC-Gateway path gets only an auth middleware (`server/router/api/v1/v1.go:69`, `:97`). No limiter is in either chain, and no rate-limiting library is a direct dependency — `golang.org/x/time` appears in `go.mod:151` marked `// indirect`.

**The limits that do exist** (none are rate limits — they cap size or concurrency, and none are keyed by user)

| Limit | Value | Location |
|---|---|---|
| Max API request body | 256 MiB (`256 << 20`) | `server/router/api/v1/v1.go:20`, applied at `:126`, `:141`, `:144` |
| Concurrent image EXIF-strip ops | 2 (process-wide semaphore) | `server/router/api/v1/v1.go:60`; acquired in `attachment_service_image.go:67-77`, used at `attachment_service.go:158-160` |
| Concurrent thumbnail generations | 3 | `server/router/api/v1/v1.go:59` and `server/router/fileserver/fileserver.go:46` |

The image semaphore is the only thing that returns a "too many requests"-flavored error (`codes.ResourceExhausted`, `server/router/api/v1/attachment_service.go:160`), but it's a global concurrency gate — a caller blocks until a slot frees rather than being throttled by identity, and it only errors if the request context is cancelled.

The one explicit acknowledgment that rate limiting is absent is a note in the email package's future-work list: `internal/email/doc.go:86` — "Rate limit email sending to prevent abuse."
