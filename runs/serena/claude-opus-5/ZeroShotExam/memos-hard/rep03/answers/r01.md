**Premise correction:** There is no Redis in this repository. A case-insensitive grep for `redis` across the whole tree (excluding `node_modules`) returns zero hits — no client dependency in `go.mod`, no connection string, no config key, no Docker service. This is Memos, a single-binary Go app whose "no external dependencies beyond the database" design is stated in `README.md`. There is also no per-entity TTL for user entries — users share the same global cache TTL as everything else.

**Actual mechanism:**

**1. The cache is a hand-rolled, in-process, in-memory cache** — `store/cache/cache.go`. It's a `sync.Map` plus an `atomic.Int64` item counter, with per-item `expiration time.Time` (`store/cache/cache.go:35-39`) and a background goroutine (`cleanupLoop`, `store/cache/cache.go:190`) that sweeps expired entries on a ticker. It's process-local: nothing is shared across replicas, and everything is lost on restart.

**2. "Configuration" is a Go struct literal, not connection settings** — `store/store.go:38-44`, in `store.New()`:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

These values are hardcoded — there is no env var, flag, or settings-file override. The same config is handed to three separate `cache.New` instances (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, and `userSettingCache`. An identical set of defaults is duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:56-63`), though `store.New` doesn't call it.

**3. TTL for user entries: 10 minutes**, inherited from `DefaultTTL`. Every user write goes through `Set` (not `SetWithTTL`), which applies `c.config.DefaultTTL` (`store/cache/cache.go:88-90`) — see `store/user.go:98` (`CreateUser`), `:122` (`CreateUserIfNoUsers`), `:132` (`UpdateUser`), `:143` (`ListUsers`, caching each row), and `:167` (`GetUser`). `SetWithTTL` exists but no caller in the user path uses it, so 10 minutes is the only TTL users ever get.

Two details worth noting about how that TTL actually behaves:

- **TTL is absolute, not sliding.** `SetWithTTL` sets `expiration: time.Now().Add(ttl)` and `Get` never extends it (`store/cache/cache.go:105-110`), so a hot user entry still expires 10 minutes after its last *write*.
- **Staleness is bounded well below 10 minutes in practice**, because `ListUsers` re-`Set`s every returned user, and `GetUser` only reads cache when looked up by ID (`store/user.go:149-150`) — lookups by username or email always fall through to the driver.

**4. Invalidation is explicit, keyed by user ID.** `userCacheKey` is just the stringified ID (`store/user.go:88-90`), and `DeleteUser` evicts via `s.userCache.Delete(ctx, userCacheKey(userID))` (`store/user_delete.go:40`). On shutdown, `Store.Close()` stops all three cleanup goroutines before closing the driver (`store/store.go:73-76`).

One thing to flag if you're relying on this cache's bounds: the `MaxItems: 1000` eviction path, `cleanupOldest` (`store/cache/cache.go:246`), does not actually evict the oldest entries. Its `Range` callback fills `candidates` with the first `threshold` items encountered and `return`s early for each (`store/cache/cache.go:270-273`); the oldest-replacement logic below that line is only reached once `candidates` is full, so the result is closer to "evict ~200 arbitrary entries" than LRU-by-expiration. That affects correctness of the size bound, not of the TTL.
