**Premise correction:** Neither. This repo (Memos, a single Go binary) has no message broker at all — no NATS, no RabbitMQ/AMQP, no Kafka or Redis queue. `go.mod` contains no broker client library, and a repo-wide grep for `nats`/`amqp`/`rabbitmq` in Go sources returns nothing. There are no separate "delivery worker" processes either; everything runs in the one server process.

**Actual mechanism — an in-process buffered Go channel:**

- **The "queue"** is declared at `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  a package-level buffered channel holding 128 payloads.

- **The "workers"** are 4 goroutines started in `init()` at `internal/webhook/webhook.go:42-55`, each ranging over `asyncPostQueue` and calling `Post()` for every payload; failures are only logged via `slog.Warn` (no retry, no dead-letter).

- **Producing side:** `PostAsync()` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. When the buffer is full the payload is **dropped** with a warning — delivery is best-effort, not durable.

- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` fan out one `PostAsync` per registered user webhook for `memos.memo.created/updated/deleted` and `memos.memo.comment.created`.

- **Delivery itself** is a plain HTTP POST via a shared `http.Client` with a 30s timeout and an SSRF-guarding `DialContext` that rejects reserved/private IPs (`internal/webhook/webhook.go:32-37`, `59-77`), optionally signed with Standard Webhooks HMAC-SHA256 headers (`:133-150`).

Practical consequence: since the queue lives in process memory, anything still buffered is lost on restart, and the 128-slot cap means bursts silently shed load.
