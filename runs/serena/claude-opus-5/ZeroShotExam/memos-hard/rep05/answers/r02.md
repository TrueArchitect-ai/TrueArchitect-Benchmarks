**Premise correction: there is no per-user API rate-limiting middleware in this repository.** No middleware, interceptor, or handler enforces a request-count-per-time-window limit — per user or otherwise — so there are no "request limits" to report.

**Evidence**

The full Echo middleware stack is two entries, neither of which rate-limits (`server/server.go:51-52`):

```go
echoServer.Use(middleware.Recover())
echoServer.Use(newCORSMiddleware(profile))
```

The Connect RPC interceptor chain is four entries, all defined in `server/router/api/v1/connect_interceptors.go` (`server/router/api/v1/v1.go:133-138`):

- `NewMetadataInterceptor()` — HTTP headers → gRPC metadata
- `NewLoggingInterceptor(logStacktraces)`
- `NewRecoveryInterceptor(logStacktraces)`
- `NewAuthInterceptor(authorizer)` — authn/authz only

No rate-limiting library is a direct dependency (`go.mod` — `golang.org/x/time` appears only as `// indirect` at `go.mod:151`), and no code path returns HTTP 429 / `TooManyRequests`.

**What does exist (adjacent but different limits)**

These are the only request-constraining mechanisms, and all are global/per-request, not per-user:

1. **Request body size cap** — `maxAPIRequestBytes = 256 << 20` (256 MiB), declared at `server/router/api/v1/v1.go:20` and applied in three places: the REST gateway (`v1.go:126`), Connect read-max-bytes (`v1.go:141`), and the Connect mux (`v1.go:144`).
2. **Global concurrency semaphores** — process-wide, shared by all users, constructed in `NewAPIV1Service` (`server/router/api/v1/v1.go:59-60`): `thumbnailSemaphore` = 3 concurrent thumbnail generations, `imageProcessingSemaphore` = 2 concurrent EXIF-stripping operations. The image one is acquired at `server/router/api/v1/attachment_service_image.go:67-77`; when the context is cancelled while waiting, the caller returns `codes.ResourceExhausted, "too many image processing requests"` (`server/router/api/v1/attachment_service.go:158-160`). That message reads like rate limiting but is a concurrency gate — it caps simultaneous work, not request frequency, and never rejects based on who is calling.

Rate limiting appears in the repo only as unimplemented advisory documentation: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse") and `internal/email/README.md:286-295`, a "### 5. Implement Rate Limiting" section showing sample code a custom `EmailSender` implementer could write.
