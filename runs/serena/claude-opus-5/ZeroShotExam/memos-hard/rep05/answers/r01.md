**Premise correction:** There is no Redis anywhere in this repository — no client dependency in `go.mod`, no connection string, no config knob, no Docker service. A `grep -ri redis` across the tree returns zero hits. Memos is deliberately a single Go binary (`README.md`: "Single Go binary, ~20MB Docker image"), and its only external datastore is the SQL database (SQLite/MySQL/PostgreSQL). So there is no Redis connection to configure, and nothing to point at an external cache server.

**Actual mechanism:** The cache layer is an in-process, in-memory cache built on `sync.Map`, implemented in `store/cache/cache.go`. `Cache` (`store/cache/cache.go:67`) stores `item` values carrying an absolute `expiration time.Time` (`store/cache/cache.go:35-39`), with a background goroutine (`cleanupLoop`, `store/cache/cache.go:200`) sweeping expired entries and `cleanupOldest` (`store/cache/cache.go:253`) shedding load when the item cap is exceeded. Expiry is also checked lazily on read — `Get` deletes and reports a miss if `time.Now().After(itm.expiration)` (`store/cache/cache.go:135-144`).

**Where it's "configured":** hardcoded in Go, not in any config file or env var. `store.New` builds one `cache.Config` literal at `store/store.go:40-45` and hands the same values to all three caches — `instanceSettingCache`, `userCache`, `userSettingCache` (`store/store.go:51-53`):

- `DefaultTTL: 10 * time.Minute`
- `CleanupInterval: 5 * time.Minute`
- `MaxItems: 1000`

The same values are duplicated in `cache.DefaultConfig()` (`store/cache/cache.go:57-64`). Caches are torn down via `Store.Close` (`store/store.go:72-79`).

**TTL for user entries:** **10 minutes**, inherited from `DefaultTTL`. Every user write path calls the plain `Set` — `CreateUser` (`store/user.go:98`), `CreateUserIfNoUsers` (`store/user.go:122`), `UpdateUser` (`store/user.go:132`), `ListUsers` (`store/user.go:143`), and `GetUser` (`store/user.go:167`) — and `Set` simply delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). `SetWithTTL` has no non-test callers anywhere in the repo, so no entry type gets a custom TTL; users, user settings, and instance settings all expire at 10 minutes.

Two details worth noting since they affect cache behavior more than the TTL does:

- **Only lookups by ID hit the cache.** `GetUser` consults `userCache` solely when `find.ID != nil` (`store/user.go:149-156`); lookups by username, email, etc. fall through to the database every time (though they repopulate the cache on the way back).
- **Invalidation is explicit on delete, so the TTL is rarely the thing that matters.** `deleteUserCache` (`store/user_delete.go:39-46`) evicts the user entry and its settings immediately. Combined with every mutation re-`Set`ting the entry, the 10-minute window mainly bounds staleness from writes that bypass the store (e.g. direct DB edits), not normal application updates.
