h15.

Memo visibility (PUBLIC / PROTECTED / PRIVATE) is enforced independently in several places — there is no single chokepoint. Distinct enforcement sites:

**Core gRPC/Connect API (memo reads)**
- Single-memo read gate `checkMemoReadAccess` (non-public ⇒ auth required; PRIVATE ⇒ creator only; also archived-only-to-creator) — `server/router/api/v1/memo_service.go:39-68`, called from `GetMemo` (`:356`, and again for the parent memo `:367`) and `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`)
- List-query scoping in `ListMemos` — anonymous ⇒ `VisibilityList=[PUBLIC]`, authenticated ⇒ CEL filter `creator_id == N || visibility in ["PUBLIC","PROTECTED"]` — `server/router/api/v1/memo_service.go:218-227`
- Comment-list scoping (same anonymous/authenticated filter, applied to related memos) — `server/router/api/v1/memo_service_comments.go:151-156`
- Comment creation gate (PRIVATE parent ⇒ creator/superuser only; comment inherits parent visibility) — `server/router/api/v1/memo_service_comments.go:41,52`

**Stats**
- `ListAllUserStats` / `GetUserStats` visibility scoping of the memo query — `server/router/api/v1/user_service_stats.go:83-91` and `:217-221`

**Reactions**
- `ListMemoReactions` (`:29-40`) and `UpsertMemoReaction` (`:82-85`) — `server/router/api/v1/reaction_service.go`

**Attachments (two separate surfaces)**
- gRPC attachment access via the owning memo — `checkAttachmentAccess`, `server/router/api/v1/attachment_service.go:422-454`
- `ListMemoAttachments` — `server/router/api/v1/memo_attachment_service.go:213-225`
- Raw HTTP file server (independent implementation, adds anonymous-instance and `share_token` fallbacks) — `checkAttachmentPermission`, `server/router/fileserver/fileserver.go:650-704`

**SSE / realtime delivery**
- Per-client broadcast filtering `SSEClient.canReceive` (PRIVATE ⇒ creator or admin; unknown visibility ⇒ deny) — `server/router/api/v1/sse_hub.go:133-143`, with visibility stamped on events in `server/router/api/v1/sse_event_helpers.go:29-37`

**Share tokens (deliberate visibility bypass, gated on token validity)**
- `GetMemoByShare` — unauthenticated resolution of a token to a memo regardless of visibility, rejecting only expired/invalid tokens and archived memos — `server/router/api/v1/memo_share_service.go:153-192`; share CRUD is creator/superuser-gated at `:43`, `:92`, `:133`; the matching token fallback for attachments is `server/router/fileserver/fileserver.go:684-690`

**Anonymous/public feeds**
- RSS (explore and per-user) restricted to `[PUBLIC]` — `server/router/rss/rss.go:90` and `:141`
- Sitemap restricted to `[PUBLIC]` — `server/router/frontend/frontend.go:149-151`

**Notifications (visibility re-checked before content leaves the server)**
- In-app notification conversion `canViewerAccessMemo` — `server/router/api/v1/user_service_notifications.go:302-316` (used at `:337`, `:342`, `:370`, `:385`)
- Email notifications, a separate copy of the same predicate — `server/notification/email.go:306-320` (used at `:155`, `:187`)
- Mention targeting `canUserAccessMentionContext` / `shouldSkipMentionInbox` — `server/router/api/v1/memo_mention_helpers.go:56-89`

Note the two `canViewerAccessMemo` implementations are duplicated logic that differ slightly: the API version uses `isSuperUser(user)`, the email version checks `user.Role == store.RoleAdmin` directly.
