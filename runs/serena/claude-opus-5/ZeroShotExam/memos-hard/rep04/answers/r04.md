**Premise correction:** Neither. This repository (memos) has no external message broker at all — there is no NATS, RabbitMQ, AMQP, Kafka, or Redis dependency anywhere in `go.mod`/`go.sum`, and no broker client code. So there is no "queue declaration" in the broker sense to point at.

**Actual mechanism — an in-process Go channel with a fixed worker pool:**

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel holding 128 pending payloads.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are only logged (`slog.Warn`), never retried.
- **Producer:** `PostAsync` at `internal/webhook/webhook.go:184-196` does a non-blocking `select` send; if the buffer is full the payload is **dropped** with a warning ("Dropped webhook dispatch because the async queue is full"). Nil payloads are dropped too.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` — memo created/updated/deleted and comment-created events fetch the user's webhooks from the store and call `webhook.PostAsync` per hook.
- **Delivery itself:** `Post` at `internal/webhook/webhook.go:120` does a plain HTTP POST via a shared `http.Client` with a 30s timeout and an SSRF-guarding `DialContext` (`webhook.go:32-37`, `:59-77`), plus optional Standard Webhooks HMAC-SHA256 signing headers.

Practical consequences of this design: the queue is per-process and in-memory, so pending deliveries are lost on restart, there is no durability, no retry/backoff, no dead-letter path, and no cross-instance coordination if memos is run with more than one replica.
