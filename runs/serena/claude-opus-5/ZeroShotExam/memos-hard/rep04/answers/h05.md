**Mechanism: explicit Go code** — two deliberate `DELETE FROM reaction` statements inside the driver-level user-deletion transaction. There is no database-level rule; the `reaction` table has no foreign keys at all.

## The explicit deletion

The store driver implements `DeleteUser` as a single transaction whose deletion order is spelled out in `deleteUserTargetsTx`, duplicated per dialect:

- `store/db/sqlite/user_delete.go:92-127`
- `store/db/postgres/user_delete.go:92-127`
- `store/db/mysql/user_delete.go:92-127`

Two separate reaction sweeps run there, covering the two directions a reaction can relate to the user:

1. **Reactions *on* the user's content** (by anyone) — `deleteReactionsByContentIDsTx`, called at line 96, batched over `content_id IN (...)`:
   - sqlite `store/db/sqlite/user_delete.go:380-388`, postgres `:380-388`, mysql `store/db/mysql/user_delete.go:417-425`

   The content IDs come from `memoContentIDsFromRefs` (sqlite/postgres `:512-518`, mysql `:549-555`), which maps each memo to the `"memos/"+uid` form used as the reaction's `content_id`. The memo set is not just the user's own memos — `listDeleteUserMemoTree` walks the `COMMENT` relation transitively, so comments under the user's memos are included (recursive CTE in sqlite/postgres `:133-166`, iterative BFS in mysql `:133-181`).

2. **Reactions *by* the user** on anyone else's content — `deleteReactionsByCreatorTx`, called at line 102, a plain `DELETE FROM reaction WHERE creator_id = ?`:
   - sqlite/postgres `:400-403`, mysql `:437-440`

Both run before `deleteMemosTx` and `deleteUserRowTx` in the same transaction, and the whole thing commits atomically (`DeleteUser`, line 29-59 in each file). Callers just delegate: `store/user.go:171-181` → `server/router/api/v1/user_service.go:414-416`.

## Why it can't be a database rule

The `reaction` table is declared with no `FOREIGN KEY` clause in any of the three dialects — only a `UNIQUE(creator_id, content_id, reaction_type)` constraint:

- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`

`creator_id` and `content_id` are bare `INTEGER`/`TEXT` columns. Grepping for `FOREIGN KEY`/`ON DELETE` across `store/migration` turns up cascades only on `memo_share.memo_id → memo(id)` (e.g. `store/migration/sqlite/LATEST.sql:109`), never on `reaction`. Historically FKs were stripped from the schema in `store/migration/sqlite/0.7/00__remove_fk.sql`, and sqlite is opened with them off regardless: `store/db/sqlite/sqlite.go:53` sets `_pragma=foreign_keys(0)`. So even if a constraint existed it wouldn't fire on sqlite.

## Tests confirming the behavior

- `server/router/api/v1/test/user_service_delete_test.go:188-209` seeds four reactions, then asserts at `:287-298` that reactions on the user's own memo and on the user's comment under a foreign memo are gone, while a third party's reaction on a foreign memo survives (`require.Len(..., 1)`).
- Same shape at the store layer: `store/test/user_delete_test.go:97-112` and `:217-220`.
- `server/router/api/v1/test/user_service_delete_test.go:366-431` uses the `DeleteUserFailpointBeforeCommit` hook (`store/db/*/user_delete.go:47-49`) to verify the reaction is still present after a rollback — i.e. reaction removal is inside the transaction, not a side effect.
