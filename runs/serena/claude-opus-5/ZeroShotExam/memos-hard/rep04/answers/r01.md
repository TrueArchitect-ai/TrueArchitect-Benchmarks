**Premise correction:** There is no Redis in this repository. `grep -ri redis` across the entire tree returns zero hits, and `go.mod` has no Redis client dependency. This is Memos, a single-binary self-hosted Go app whose stated design goal is "Single Go binary, ~20MB Docker image" with SQLite/MySQL/PostgreSQL as the only external datastore (`README.md`). There is no external cache service to point a connection string at, and no config option, env var, or flag for one.

**Actual mechanism:**

The cache layer is a hand-rolled, in-process, in-memory cache — not a network client.

- **Implementation:** `store/cache/cache.go` — a `Cache` struct backed by `sync.Map` plus an `atomic.Int64` item counter, with per-entry expiration timestamps and a background `cleanupLoop` goroutine (`store/cache/cache.go:66-90`, `:200-250`). It implements a local `Interface` (`store/cache/cache.go:11-32`) with `Set`/`SetWithTTL`/`Get`/`Delete`/`Clear`/`Size`/`Close`.

- **"Connection" configuration** — the closest analogue is the `cache.Config` literal built in `store.New`, `store/store.go:40-45`:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  These values are hardcoded — not read from a profile, flag, or env var. The same config instance is handed to three separate caches: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). All three are torn down in `Store.Close` (`store/store.go:74-76`).

**TTL for user entries: 10 minutes**, inherited from `DefaultTTL`.

Every user write goes through `userCache.Set` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). No call site ever passes a user-specific TTL — `SetWithTTL` is not called anywhere outside the cache package and its tests. Cache keys are the bare user ID as a string (`userCacheKey`, `store/user.go:88-90`).

Two caveats worth knowing:

- **Expiry is lazy plus swept.** `Get` checks expiration on read and evicts on the spot (`store/cache/cache.go:135-144`); the 5-minute `cleanupLoop` sweeps the rest. So an entry can live slightly past 10 minutes before anything notices.
- **Capacity eviction can cut the TTL short.** With `MaxItems: 1000`, exceeding the cap triggers `cleanupOldest`, which drops ~20% of entries (`store/cache/cache.go:117-119`, `:253-313`). On an instance with over 1000 users, a user entry can be evicted well before its 10 minutes elapse.

Only explicit invalidation is `DeleteUser`, which calls `s.userCache.Delete` (`store/user_delete.go:40`).

Separately, there's an unrelated second cache in the API layer: `instanceStatsCache`, a single-value mutex-guarded memo with a 60-second TTL (`server/router/api/v1/instance_stats.go:21`) — also purely in-process.

One loose end: the `cacheConfig` field is stored on `Store` (`store/store.go:24`, `:50`) but never read after construction.
