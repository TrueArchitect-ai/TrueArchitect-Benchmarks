**Premise correction: there is no per-user API rate-limiting middleware in this repository.** No middleware, interceptor, or handler enforces requests-per-user or requests-per-time-window anywhere in the Go server, so there are no "request limits" to report.

What is actually registered:

**Echo-level middleware** (`server/server.go:51-52`, `server/router/frontend/frontend.go:54`):
- `middleware.Recover()`
- `newCORSMiddleware(profile)` (`server/cors.go:13`)
- static-file / SPA-fallback middleware for the frontend

**Connect RPC interceptors** (`server/router/api/v1/v1.go:133-138`) — the closest thing to an API middleware chain:
- `MetadataInterceptor` — copies HTTP headers into gRPC metadata (`server/router/api/v1/connect_interceptors.go:22`)
- `LoggingInterceptor`
- `RecoveryInterceptor`
- `AuthInterceptor` — authentication/authorization only

None of these count requests or track per-user usage. No storage of request counters, no `429`/`Retry-After` handling, and no rate-limiter dependency in `go.mod`.

Things nearby that are sometimes mistaken for rate limits, and what they really are:

| Mechanism | Location | Actual limit | Scope |
|---|---|---|---|
| Request body size cap | `server/router/api/v1/v1.go:20,126,141-143` | `maxAPIRequestBytes = 256 << 20` (256 MiB) via `http.MaxBytesHandler` + `connect.WithReadMaxBytes` | per request, not per user |
| Thumbnail generation semaphore | `server/router/api/v1/v1.go:59` | 3 concurrent operations | process-wide |
| Image/EXIF processing semaphore | `server/router/api/v1/v1.go:60`, acquired at `attachment_service_image.go:67` | 2 concurrent operations; overflow returns `codes.ResourceExhausted` "too many image processing requests" (`attachment_service.go:160`) | process-wide, concurrency gate — a caller blocks rather than being throttled by rate |
| Upload size limit | `server/router/api/v1/attachment_service.go:118-125` | instance setting `UploadSizeLimitMb`, defaulting to `MaxUploadBufferSizeBytes = 32 MiB` | per upload |
| Audio transcription cap | `server/router/api/v1/ai_service.go:24` | `25 * MebiByte` | per request |

The only mentions of the phrase "rate limit" in the codebase are aspirational documentation for the email package — `internal/email/doc.go:86` lists it as a security consideration, and `internal/email/README.md:286` shows a sample `limiter.Allow()` snippet as a suggestion for callers. Neither is implemented.
