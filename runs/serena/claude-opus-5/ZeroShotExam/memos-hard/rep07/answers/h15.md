Memo visibility is enforced in many separate places — there is no single chokepoint. The distinct enforcement sites:

**Core API read gate (single memo)**
- `checkMemoReadAccess` (archived → creator only; non-public → auth required; private → creator only) — `server/router/api/v1/memo_service.go:39-68`, called by `GetMemo` and its parent-memo check (`server/router/api/v1/memo_service.go:356,367`) and by `ListMemoComments` (`server/router/api/v1/memo_service_comments.go:148`)

**Core API list filter (query-level)**
- `ListMemos` visibility scoping (`VisibilityList = [PUBLIC]` for anonymous; `creator_id == N || visibility in [PUBLIC, PROTECTED]` otherwise) — `server/router/api/v1/memo_service.go:218-227`
- Comment listing filter passed to the relation query — `server/router/api/v1/memo_service_comments.go:151-160`
- Relation expansion filters (so private related memos aren't leaked as relations/snippets) — `server/router/api/v1/memo_service_converter.go:177-187` (`batchConvertMemoRelations`) and `server/router/api/v1/memo_relation_service.go:103-112` (`ListMemoRelations`)
- User stats aggregation — `server/router/api/v1/user_service_stats.go:78-92` (`ListAllUserStats`) and `:216-222` (`GetUserStats`)

**HTTP file server (attachment blobs, separate from gRPC)**
- `checkAttachmentPermission` — public + anonymous-allowed → open; share-token fallback; else auth required and private → creator/admin — `server/router/fileserver/fileserver.go:650-704`

**Attachment APIs (gRPC/Connect)**
- `checkAttachmentAccess` for attachments linked to a memo — `server/router/api/v1/attachment_service.go:419-455` (used by `GetAttachmentBinary` path at `:256`)
- `ListMemoAttachments` inline visibility check — `server/router/api/v1/memo_attachment_service.go:213-226`

**Reactions**
- `ListMemoReactions` — `server/router/api/v1/reaction_service.go:29-41`; `UpsertMemoReaction` — `server/router/api/v1/reaction_service.go:82-85`

**Comment creation**
- `CreateMemoComment` private-parent check (and forcing the comment to inherit parent visibility) — `server/router/api/v1/memo_service_comments.go:33-52`

**SSE live event fan-out**
- `SSEClient.canReceive` — private events only to creator or admin — `server/router/api/v1/sse_hub.go:134-143`, with event visibility populated in `server/router/api/v1/sse_event_helpers.go:29-37`

**Notification fan-out (two separate copies of `canViewerAccessMemo`)**
- Email notifications — `server/notification/email.go:306-320`
- In-app/user notifications — `server/router/api/v1/user_service_notifications.go:300-316`
- Mention-notification eligibility — `server/router/api/v1/memo_mention_helpers.go:62-84`

**Unauthenticated public surfaces (public-only queries)**
- RSS feeds (explore + per-user) — `server/router/rss/rss.go:90,141`
- Sitemap — `server/router/frontend/frontend.go:150`

**Share-token surface (visibility deliberately bypassed; the token is the authorization)**
- `GetMemoByShare` — no visibility check, only token validity/expiry and archived-state — `server/router/api/v1/memo_share_service.go:152-190`; matching share-token fallback for attachments at `server/router/fileserver/fileserver.go:684-690`

Note: the MCP surface (`server/router/mcp/`) is a proxy over the same Connect handlers (`server/router/mcp/catalog.go:12-24`) and adds no visibility logic of its own, so it inherits the core API gates above.
