**Premise correction: this repository (Memos) has no per-user API rate-limiting middleware.** There is no rate limiter to register, and therefore no request limits to report.

What I verified:

- **The full middleware/interceptor chains contain no rate limiter.** Echo-level middleware is only `middleware.Recover()` and the CORS middleware (`server/server.go:51-52`, `server/cors.go:13`). The Connect interceptor chain is `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (`server/router/api/v1/v1.go:133-138`), and the gRPC-Gateway path uses only `gatewayAuthMiddleware` (`server/router/api/v1/v1.go:69, 97`).
- **No rate-limiting code or dependency exists.** A repo-wide grep for `rate limit`/`ratelimit`/`rate_limit` matches only a *wishlist* comment — `internal/email/doc.go:86`: "Rate limit email sending to prevent abuse" (an unimplemented future consideration). `golang.org/x/time` is present in `go.mod:151` but only as an **indirect** dependency; `golang.org/x/time/rate` is not imported anywhere.

The limits that do exist are different in kind — none are per-user or time-windowed:

| Limit | Value | Location |
|---|---|---|
| Max API request body size | 256 MiB | `server/router/api/v1/v1.go:20, 126, 141, 144` |
| Max upload buffer size | 32 MiB | `server/router/api/v1/attachment_service.go:27` |
| Max page size (list RPCs) | 1000 | `server/router/api/v1/common.go:17` |
| Concurrent EXIF/image-processing slots | 2 (process-wide semaphore) | `server/router/api/v1/v1.go:41, 60`; acquired at `attachment_service.go:158` |

The image-processing semaphore is the closest thing to throttling and is the only source of a `ResourceExhausted` ("too many image processing requests", `attachment_service.go:160`), but it's a global concurrency gate of 2 shared by all users, not a per-user request-rate limit — it blocks and waits rather than counting requests per interval.
