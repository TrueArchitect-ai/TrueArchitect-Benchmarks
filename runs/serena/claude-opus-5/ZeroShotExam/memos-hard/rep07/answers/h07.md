The `<img>` src comes from the API as `/file/{user.Name}/avatar` (i.e. `/file/users/{username}/avatar`), and that URL is served by the file server, not gRPC. Chain:

```
convertUserFromStore (URL origin: rewrites base64 avatar to "/file/%s/avatar") — server/router/api/v1/user_service_converters.go:36
UserAvatar (<img src={avatarUrl}>) — web/src/components/UserAvatar.tsx:14
FileServerService.RegisterRoutes (GET /file/users/:identifier/avatar) — server/router/fileserver/fileserver.go:124
FileServerService.serveUserAvatar — server/router/fileserver/fileserver.go:168
FileServerService.getUserByUsername — server/router/fileserver/fileserver.go:715
Store.GetUser — store/user.go:148
Store.ListUsers — store/user.go:136
Driver.ListUsers (interface) — store/driver.go:47
DB.ListUsers (SELECT ... avatar_url ... FROM user WHERE username = ?) — store/db/sqlite/user.go:88 (also store/db/mysql/user.go:84, store/db/postgres/user.go:87)
```

Notes on the hops:

- Route wiring: `fileserver.NewFileServerService(...).RegisterRoutes(echoServer)` at server/server.go:81-82, registered before the gRPC gateway.
- Driver selection: `NewDBDriver` picks sqlite/mysql/postgres from the profile — store/db/db.go:14; the `Store` holds it as `s.driver` — store/store.go:48.
- Cache: `Store.GetUser` only consults `userCache` when looked up by ID (store/user.go:149-156). This path looks up by username, so it always falls through to `ListUsers` → SQL; results are then written back into the cache (store/user.go:142-144, 167).
- After the data layer returns, the handler decodes the stored value in place: `user.AvatarURL` is a `data:<type>;base64,...` URI parsed by `parseDataURI` (server/router/fileserver/fileserver.go:737) and written with `c.Blob`. The bytes live in the `user.avatar_url` column — there is no filesystem/S3 hop for avatars, unlike attachments.
- Access control before the store hop: on a private instance (`!s.Profile.AllowAnonymous()`), `getCurrentUser` (server/router/fileserver/fileserver.go:708) → `auth.Authenticator.AuthenticateToUser` must resolve a session/PAT first; otherwise any user's avatar is served anonymously. There is no per-user authorization check beyond that.
