**Premise correction:** Neither. This repo (Memos) has no message broker at all — no NATS, no RabbitMQ, no AMQP client. There is no dependency on either in `go.mod`, and grepping the tree for `nats`/`rabbitmq`/`amqp` returns only one false positive: the Catalan word "predeterminats" in `web/src/locales/ca.json`. The webhook "workers" are goroutines inside the single Memos server process, not broker consumers.

**Actual mechanism** — an in-process buffered Go channel, all in `internal/webhook/webhook.go`:

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel with capacity 128. That's the entire "queue."
- **Workers:** `internal/webhook/webhook.go:42-55` — an `init()` function spawns exactly 4 goroutines (`for range 4`), each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are logged via `slog.Warn` and dropped; there is no retry, no dead-letter, no ack.
- **Producer:** `PostAsync` at `internal/webhook/webhook.go:184-196` does a non-blocking `select` send. If the buffer is full, the `default` branch **drops the webhook** with a warning — backpressure is data loss, not blocking.
- **Delivery:** `Post` (`internal/webhook/webhook.go:120`) does the actual HTTP POST via a shared `safeClient` with a 30s timeout and an SSRF-guarding dialer (`safeDialContext`, line 59) that rejects reserved/private IPs. Optional HMAC-SHA256 signing follows the Standard Webhooks spec (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers, lines 133-150).
- **Call sites:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` enqueue on memo create/update events.

Two consequences worth noting since the question implies durability expectations: because the queue is an in-memory channel, **pending webhooks are lost on process restart**, and delivery is single-instance only — a horizontally scaled deployment gets no shared queue.
