**Premise correction:** There is no Redis anywhere in this repository. A case-insensitive search for "redis" across the whole tree (excluding `.git`/`node_modules`) returns zero hits — no client dependency in `go.mod`, no connection string, no config flag, no Docker/compose service. Memos is a single Go binary backed by SQLite/MySQL/Postgres, and its cache layer is purely **in-process, in-memory**.

**Actual mechanism**

- **Implementation:** `store/cache/cache.go` — a thread-safe in-memory cache built on `sync.Map` plus an `atomic.Int64` item counter. Entries (`item`) hold the value, an absolute `expiration` time, and a rough size estimate. A background `cleanupLoop` goroutine (`store/cache/cache.go:203`) ticks on `CleanupInterval` to evict expired entries; `Get` also lazily evicts on read if `time.Now().After(itm.expiration)` (`store/cache/cache.go:135`). When `MaxItems` is exceeded, `cleanupOldest` drops ~20% of `MaxItems` (`store/cache/cache.go:250`).

- **Where it's "configured":** not a connection URL but a `cache.Config` literal in `store.New` at `store/store.go:40-44`:
  ```go
  cacheConfig := cache.Config{
      DefaultTTL:      10 * time.Minute,
      CleanupInterval: 5 * time.Minute,
      MaxItems:        1000,
      OnEviction:      nil,
  }
  ```
  Three separate cache instances share that same config (`store/store.go:51-53`): `instanceSettingCache`, `userCache`, `userSettingCache`. `cache.DefaultConfig()` (`store/cache/cache.go:57`) carries identical values. None of these are configurable via env vars or flags — they're hardcoded.

- **TTL for user entries:** **10 minutes**, inherited from `DefaultTTL`. Every user write path calls `s.userCache.Set(...)` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` with `c.config.DefaultTTL` (`store/cache/cache.go:90`). No caller passes a custom TTL for users. Entries are keyed by the stringified user ID (`userCacheKey`, `store/user.go:88`), and reads only hit the cache when looking up by ID (`store/user.go:149-155`).

- **Invalidation:** explicit deletion on user delete (`store/user_delete.go:40`); otherwise updates overwrite the entry and reset its 10-minute window. Because the cache is per-process, a multi-instance deployment would have independent, non-coordinated caches — which is likely the real concern behind the question.
