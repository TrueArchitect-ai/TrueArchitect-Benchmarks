**Premise correction:** Neither. This repo (Memos) has no message broker at all — there is no NATS, RabbitMQ/AMQP, Kafka, or Redis client anywhere in the Go source or in `go.mod`. There are also no separate "delivery worker" processes; Memos ships as a single Go binary.

**Actual mechanism:** webhook delivery is done in-process by a fixed pool of goroutines reading from a buffered Go channel.

- **Queue declaration** — `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A package-level buffered channel of capacity 128, declared in the same `var` block as the shared SSRF-guarded HTTP client.

- **Workers** — `internal/webhook/webhook.go:42-55`: a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`; failures are only logged via `slog.Warn`.

- **Producer** — `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning log — there is no retry, no persistence, and no dead-letter path.

- **Callers** — `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, which fan out one `PostAsync` per registered user webhook for `memos.memo.created/updated/deleted` and `memos.memo.comment.created`.

Delivery itself is a plain HTTP POST in `Post` (`internal/webhook/webhook.go:120`), signed with Standard Webhooks HMAC-SHA256 headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`) when a signing secret is set. Webhook *definitions* (URL + signing secret) are persisted in the database and read via `s.Store.GetUserWebhooks` — that's the only durable storage involved; the delivery queue is purely in-memory and does not survive a restart.
