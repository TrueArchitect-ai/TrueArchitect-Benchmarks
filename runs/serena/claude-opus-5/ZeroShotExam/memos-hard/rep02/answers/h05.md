**Mechanism: explicit Go code** — reactions are removed by hand-written `DELETE FROM reaction` statements inside the driver-level `DeleteUser` transaction. There is no database-level cascade for them.

## What the Go code does

`DeleteUser` runs as a single transaction per driver, and `deleteUserTargetsTx` issues **two** distinct reaction deletes (`store/db/sqlite/user_delete.go:92-127`):

1. `deleteReactionsByContentIDsTx` (`store/db/sqlite/user_delete.go:380-388`) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500. The content IDs come from `memoContentIDsFromRefs` (`:512-518`), which maps the recursive memo tree (the user's memos **plus** descendant `COMMENT`-related memos, `listDeleteUserMemoTreeRecursive` `:133-166`) to `"memos/"+uid`. This removes *other people's* reactions on the deleted user's content.
2. `deleteReactionsByCreatorTx` (`store/db/sqlite/user_delete.go:400-403`) — `DELETE FROM reaction WHERE creator_id = ?`. This removes the deleted user's *own* reactions on content they don't own.

Same code in the other two drivers:
- `store/db/postgres/user_delete.go:383` and `:401`
- `store/db/mysql/user_delete.go:420` and `:438`

Entry points: `store/user.go:171` → `store/driver.go:48` → the per-driver implementations.

## Why it is not a DB rule

The `reaction` table is declared with **no foreign keys at all** — no `REFERENCES user(id)`, no `ON DELETE CASCADE`:
- `store/migration/sqlite/LATEST.sql:92-99`
- `store/migration/postgres/LATEST.sql:91-98`
- `store/migration/mysql/LATEST.sql:91-98`
- original creation: `store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql`

Grepping `FOREIGN KEY|REFERENCES|ON DELETE CASCADE` across `store/migration/` returns cascades only for `memo_share`, `memo_resource`, `user_setting`, etc. — never `reaction`. Additionally, SQLite opens with FK enforcement **off** (`_pragma=foreign_keys(0)`, `store/db/sqlite/sqlite.go:53`), so even legacy cascades wouldn't fire.

## Tests confirming it

- `server/router/api/v1/test/user_service_delete_test.go:287-298` — reactions on the user's own memo and on their comment are empty afterward, while a peer's reaction on a *foreign* memo survives.
- `store/test/user_delete_test.go:217-220` — same kept/removed split at the store layer.
- `server/router/api/v1/test/user_service_delete_test.go:429-431` — with the `before_commit` failpoint (`store/user_delete.go:14`), the reaction still exists, proving deletion is transactional Go work rather than an independent DB rule.

**Answer:** explicit Go code (two `DELETE FROM reaction` statements — by `creator_id` and by memo-tree `content_id` — inside the `DeleteUser` transaction); evidence: `store/db/sqlite/user_delete.go:96,102,380-403`, `store/db/postgres/user_delete.go:383,401`, `store/db/mysql/user_delete.go:420,438`, no FK/cascade in `store/migration/*/LATEST.sql` reaction DDL, `store/db/sqlite/sqlite.go:53`.
