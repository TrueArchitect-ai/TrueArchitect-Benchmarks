**Trace: `GET /file/users/{username}/avatar` → `user.avatar_url` column**

The image is not a separate blob/file — it is stored as a base64 data URI in the `user` table's `avatar_url` column, and the handler decodes it on the way out.

**How the browser gets that URL:** the API converter rewrites the raw base64 into a URL so responses stay small — `convertUserToProto` sets `AvatarUrl = "/file/%s/avatar"` (with `userpb.Name` = `users/{username}`) at `server/router/api/v1/user_service_converters.go:36`; `UserAvatar` then renders it as an `<img src>` (`web/src/components/UserAvatar.tsx`).

Details worth noting along the path:

- **Auth gate (fileserver.go:173-181):** if `Profile.AllowAnonymous()` is false, `getCurrentUser` → `authenticator.AuthenticateToUser` (fileserver.go:708) must resolve a session/access token/PAT first. On a public instance, any user's avatar is served anonymously — there is no per-viewer permission check beyond that, unlike `checkAttachmentPermission` for attachments.
- **Cache bypass (store/user.go:149-156):** `GetUser` only consults `userCache` when `find.ID` is set. This lookup passes `Username`, so it always falls through to `ListUsers` and hits the DB; the row is then written into the cache keyed by ID (store/user.go:143).
- **MIME allowlist (fileserver.go:201):** the decoded type must be in `avatarAllowedTypes` (fileserver.go:75), and `setSecurityHeaders` sets `nosniff` + a locked-down CSP before the blob is written.
