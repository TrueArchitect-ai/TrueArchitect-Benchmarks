**Premise correction: there is no per-user API rate-limiting middleware in this repository.** Nothing registers a rate limiter, per-user or otherwise, so there are no request limits to report.

What I verified:

- A repo-wide search for `rate limit` / `ratelimit` / `throttle` matches only two files, both documentation: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse", listed as a future consideration) and `internal/email/README.md:286` ("### 5. Implement Rate Limiting"), which shows an illustrative `golang.org/x/time/rate` snippet as a security *recommendation*, not wired-up code.
- `golang.org/x/time` appears in `go.mod:151` marked `// indirect`, and `x/time/rate` is imported nowhere in the codebase.
- The global HTTP middleware chain is just two entries — `server/server.go:51-52`: `middleware.Recover()` and `newCORSMiddleware(profile)` (`server/cors.go`).
- The Connect RPC interceptor chain is registered at `server/router/api/v1/v1.go:133-138` and contains exactly four interceptors, all defined in `server/router/api/v1/connect_interceptors.go`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor`. None does rate limiting.
- `server/auth/` contains no login-attempt throttling or lockout logic.

The nearest things to a "limit", which are easy to mistake for rate limiting but are neither per-user nor time-based:

| Mechanism | Location | What it actually limits |
|---|---|---|
| `maxAPIRequestBytes = 256 << 20` (256 MiB) | `server/router/api/v1/v1.go:20`, applied at `:126`, `:141`, `:144` | Request **body size** per request, via `http.MaxBytesHandler` and `connect.WithReadMaxBytes` |
| `imageProcessingSemaphore` = weight 2 | `server/router/api/v1/v1.go:41,60`; acquired at `server/router/api/v1/attachment_service.go:158` | **Server-wide concurrent** EXIF-stripping operations; excess returns `ResourceExhausted` "too many image processing requests" (`attachment_service.go:160`) |
| `thumbnailSemaphore` = weight 3 | `server/router/api/v1/v1.go:40,59` | Server-wide concurrent thumbnail generations |

Both semaphores are process-global concurrency gates shared by all callers — they cap simultaneous in-flight work, not requests per user per unit time, and they carry no window or quota. `connect_interceptors.go:153` merely maps `CodeResourceExhausted` to a log level.
