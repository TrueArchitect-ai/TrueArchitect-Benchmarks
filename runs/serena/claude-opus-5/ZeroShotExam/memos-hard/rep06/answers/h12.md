### How I determined which candidate runs

There are three `CreateMemo` implementations, all satisfying the same interface, so the SQL grep alone is ambiguous:

The disambiguation is the config default, not the code shape:

1. **Default value.** `cmd/memos/main.go:122` sets `viper.SetDefault("driver", "sqlite")`, and the flag itself defaults to `"sqlite"` (`main.go:130`). With no flags and no `MEMOS_DRIVER` env var, `Driver == "sqlite"`.

That opens the pure-Go `modernc.org/sqlite` driver against `profile.DSN` (`store/db/sqlite/sqlite.go:53`), which `profile.Validate()` defaults to `<data>/memos_prod.db` (`internal/profile/profile.go:110-118`).
3. **Dispatch is a plain interface call, not a wrapper.** `store.New(dbDriver, ...)` (`main.go:64`) stores it in `Store.driver` (`store/store.go:14-16`). `(*Store).CreateMemo` (`store/memo.go:104`) only validates the UID and then delegates: `return s.driver.CreateMemo(ctx, create)`. The caches in `Store` cover instance settings, users, and user settings — there is no memo cache or decorator layer intercepting the write.
4. **Request path confirms the same entry point.** The RPC handler `ConnectServiceHandler.CreateMemo` (`server/router/api/v1/connect_services.go:306`) → `APIV1Service.CreateMemo` (`server/router/api/v1/memo_service.go:70`) → `s.Store.CreateMemo` (`memo_service.go:115`).

So the postgres and mysql variants are compiled in but unreachable on a default install; only the sqlite one executes.
