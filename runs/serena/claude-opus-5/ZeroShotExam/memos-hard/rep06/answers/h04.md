**Yes — but only once, in a unit test, via a bare struct literal (never via the constructor).**

Evidence:

- **The factory** is `NewDBDriver` in `store/db/db.go:14-32`; its only MySQL branch is `mysql.NewDB(profile)` at `store/db/db.go:22`.
- **The exported constructor `mysql.NewDB`** (`store/db/mysql/mysql.go:20`) is called from exactly one place in the repo. `grep -rn "mysql\.NewDB\|store/db/mysql" --include=*.go .` outside the package itself returns only `store/db/db.go:8` (the import) and `store/db/db.go:22` (the call). Notably the integration-test harness (`store/test/store.go`, `store/test/main_test.go:25`) also goes through the factory rather than importing the mysql package directly.
- **One direct construction exists**: `store/db/mysql/auth_config_test.go:12` does `db := &DB{}` — an in-package test for `IsRetryableAuthenticationMutationError` that needs only a method receiver, so it builds a zero-valued `DB` (nil `db`, `profile`, `config`) instead of opening a connection. That is the sole `&DB{}` / `DB{` literal outside `mysql.go` itself; `grep -rn "DB{\|NewDB(" store/db/mysql/*_test.go` returns only that line.

For contrast, the Postgres driver is constructed directly in three of its own tests (`store/db/postgres/user_setting_test.go:36,194,257` use `&DB{db: db}`) plus `store/db/postgres/auth_config_test.go:12`, so the MySQL package is the more disciplined of the two.

So: no production code path constructs the MySQL driver outside `NewDBDriver`; the only direct construction is a test-local zero-value struct literal inside the `mysql` package.
