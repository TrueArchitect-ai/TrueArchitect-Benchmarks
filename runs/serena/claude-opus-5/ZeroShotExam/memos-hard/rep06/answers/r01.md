**Premise correction:** There is no Redis in this repository. A case-insensitive search for `redis` (also `memcached`/`valkey`) across the entire tree — including `go.mod`/`go.sum`, `web/`, `docs/`, and Docker/deploy files — returns zero hits. Memos ships as a single Go binary and its cache layer is a hand-rolled, in-process, in-memory cache. There is no connection string, host/port, or external cache service to configure at all.

**Actual mechanism:**

*The cache implementation* — `store/cache/cache.go` defines a `Cache` backed by a `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). Each entry is an `item{value, expiration, size}` (`store/cache/cache.go:35-39`). A background goroutine started in `New` (`store/cache/cache.go:83`) runs `cleanupLoop` on a ticker to evict expired entries, and `SetWithTTL` triggers `cleanupOldest` when the item count exceeds `MaxItems` (`store/cache/cache.go:117-119`).

*Where it's "configured"* — in code, not config: `store.New` in `store/store.go:38-61` builds a literal `cache.Config` and creates three separate cache instances from it:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```
— `store/store.go:40-45`, used for `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:51-53`). These values are hardcoded; no env var, flag, or config file overrides them. (`store/cache/cache.go:57-64` has an identical `DefaultConfig()`, but `store.New` doesn't call it — it duplicates the literal.)

**TTL for user entries: 10 minutes**, inherited from `DefaultTTL`. Every user write path calls plain `Set`, never `SetWithTTL`, so no per-entry override exists — `Set` just forwards `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). Call sites: `CreateUser` (`store/user.go:98`), `CreateUserIfNoUsers` (`store/user.go:122`), `UpdateUser` (`store/user.go:132`), `ListUsers` (`store/user.go:143`), `GetUser` (`store/user.go:167`). Keys are the plain user ID as a string (`userCacheKey`, `store/user.go:88-90`).

Two behavioral notes worth having: the cache is only read on `GetUser` when `find.ID` is set (`store/user.go:148-156`) — lookups by username or email always hit the driver. And staleness is bounded well below 10 minutes in practice because mutations write through rather than invalidate: updates re-`Set` the fresh value, and `DeleteUser` explicitly evicts the key (`store/user_delete.go:40`). Since the cache lives in process memory, each replica in a multi-instance deployment keeps its own independent copy with no cross-node invalidation.
