**Premise correction:** Neither. This repo (Memos, a single-binary Go app) has no message broker at all — no NATS, no RabbitMQ, no AMQP. `grep` over `go.mod`/`go.sum` and all Go/YAML sources returns zero hits for `nats`, `rabbitmq`, `amqp`, or any broker client library. There are also no separate "delivery worker" processes; everything runs inside the one `memos` binary.

**Actual mechanism — an in-process buffered Go channel:**

- **Queue declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel with capacity 128.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`; failures are logged with `slog.Warn` and dropped (no retry, no dead-letter).
- **Producer:** `PostAsync` at `internal/webhook/webhook.go:184-196` does a non-blocking `select` send; if the buffer is full the payload is **dropped** with a warning rather than blocking the caller.
- **Callers:** `server/router/api/v1/memo_service_webhooks.go:43` and `:71` fan out one `PostAsync` per registered user webhook for memo created/updated/deleted and comment-created events.
- **Delivery itself:** `Post` (`internal/webhook/webhook.go:120`) does a plain `POST` via a shared `http.Client` with a 30s timeout and an SSRF-guarding `DialContext` (`internal/webhook/webhook.go:59`), optionally adding Standard Webhooks HMAC headers (`webhook-id`, `webhook-timestamp`, `webhook-signature`).

Practical consequence: the queue is per-process and purely in-memory, so pending webhooks are lost on restart and are not shared across replicas.
