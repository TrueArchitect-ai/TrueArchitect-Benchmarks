**Premise correction:** Neither. This repo (memos, a Go monolith) has no external message broker at all — no NATS, no RabbitMQ, no Kafka/Redis queue. `go.mod`/`go.sum` contain no AMQP, NATS, or similar client dependency (the only `rabbit`/`nats` string in the tree is an unrelated Catalan locale entry in `web/src/locales/ca.json`).

**Actual mechanism:** webhook delivery runs on an in-process Go buffered channel with a fixed goroutine worker pool, all inside `internal/webhook/webhook.go`.

- **Queue declaration** — `internal/webhook/webhook.go:39`:
  ```go
  asyncPostQueue = make(chan *WebhookRequestPayload, 128)
  ```
  A package-level buffered channel holding 128 pending payloads.

- **Workers** — `internal/webhook/webhook.go:42-55`: a package `init()` spawns 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`; failures are only logged at warn level (`slog.Warn("Failed to dispatch webhook asynchronously", ...)`) — there is no retry and no dead-letter path.

- **Producer side** — `PostAsync` (`internal/webhook/webhook.go:184-196`) does a non-blocking `select` send; if the buffer is full the payload is **dropped** with a warning, not backpressured. Callers are `server/router/api/v1/memo_service_webhooks.go` (memo created/updated/deleted, comment created), which fan out one `PostAsync` per registered user webhook from `s.Store.GetUserWebhooks`.

- **Delivery itself** — `Post` (`internal/webhook/webhook.go:120`) does a plain `http.Client` POST via `safeClient`, with a 30s timeout, SSRF-guarded dialer (`safeDialContext`, line 59), and optional Standard Webhooks HMAC-SHA256 signing (`webhook-id` / `webhook-timestamp` / `webhook-signature` headers).

Practical consequence: the "queue" is process-local and non-durable — a restart or a burst past 128 queued items loses webhook deliveries silently.
