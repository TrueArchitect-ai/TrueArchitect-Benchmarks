**Short answer:** `*markdown.service` (goldmark-backed, the only impl) — constructed once in `NewAPIV1Service` — held by `APIV1Service`, `RSSService`, and `memopayload.Runner`.

## The interface

`markdown.Service` — `internal/markdown/markdown.go:31-58`. Nine methods: `ExtractAll`, `ExtractTags`, `ExtractProperties`, `RenderMarkdown`, `RenderHTML`, `GenerateSnippet`, `ValidateContent`, `RenameTag`.

## Concrete implementation

Exactly one: the unexported `service` struct (`internal/markdown/markdown.go:61-63`), wrapping a `goldmark.Markdown`. It's returned as `Service` by `NewService(opts ...Option)` (`markdown.go:85-114`). There are no mocks, fakes, or alternate implementations anywhere in the repo — every method receiver `(s *service)` lives in that one file.

Internally it delegates markdown-to-markdown rendering to `renderer.NewMarkdownRenderer()` (`internal/markdown/renderer/markdown_renderer.go`), a concrete type not behind any interface, and parses custom syntax via the `tag` / `mention` goldmark extensions in `internal/markdown/extensions/`.

## Construction

One runtime construction site — `NewAPIV1Service`, `server/router/api/v1/v1.go:47-51`:

```go
markdownService := markdown.NewService(
    markdown.WithTagExtension(),
    markdown.WithMentionExtension(),
)
```

So the production instance always has both `#tag` and `@mention` extensions enabled, plus GFM and auto heading IDs. That single instance is then shared: `server/server.go:85` passes `apiV1Service.MarkdownService` into `rss.NewRSSService`, rather than building a second one.

Test-only constructions (different option sets, hence worth noting they're *not* representative of runtime): `server/router/api/v1/test/test_helper.go:44` (tags + mentions), `server/router/fileserver/fileserver_test.go:427` (tags only), `server/router/rss/rss_test.go:54` (no extensions).

## Holders of the interface

| Holder | Field | Usage |
|---|---|---|
| `APIV1Service` | `server/router/api/v1/v1.go:35` | `ExtractAll` for mentions (`memo_mention_helpers.go:32`), `GenerateSnippet` for webhook payloads (`memo_service_webhooks.go:85`), and passed to `memopayload.RebuildMemoPayload` at `memo_service.go:108` and `:447` |
| `RSSService` | `server/router/rss/rss.go:45` | `RenderHTML` for feed item content (`rss.go:339`) — the server-side HTML path the interface doc comment calls out |
| `memopayload.Runner` | `server/runner/memopayload/runner.go:16` | `RebuildMemoPayload` → `ExtractAll` (`runner.go:52`, `:80`) |

One caveat on that third holder: `memopayload.NewRunner` has no callers outside its own file — grep finds no construction of `Runner` in `server.go` or anywhere else. So at runtime the *struct field* is never populated; the package is reached only through the free function `RebuildMemoPayload(ctx, memo, markdownService)`, which `APIV1Service` calls with its own instance. The `Runner` type is effectively dormant backfill machinery.

Note also that the interface's doc comment (`markdown.go:27-30`) states HTML rendering is primarily done in the frontend with markdown-it (`web/src/components/MemoContent/`); the Go `RenderHTML` exists for RSS and other server-side rendering.
