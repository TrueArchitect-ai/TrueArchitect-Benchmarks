**Mechanism: explicit Go code** — reactions are deleted by hand-written `DELETE FROM reaction` statements inside the driver-level delete-user transaction. There is no database-level cascade for them.

## What happens

`store/db/sqlite/user_delete.go:92` (`deleteUserTargetsTx`) runs two separate reaction deletes, before the memos and the user row are removed:

1. **`deleteReactionsByContentIDsTx`** (`store/db/sqlite/user_delete.go:96`, impl at `:380`) — `DELETE FROM reaction WHERE content_id IN (...)`, batched at 500 (`deleteUserBatchSize`, `:14`). The content IDs are `"memos/"+uid` for every memo in the user's memo tree, including comments (`memoContentIDsFromRefs`, `:512`). This removes *everyone's* reactions on the deleted user's memos.
2. **`deleteReactionsByCreatorTx`** (`store/db/sqlite/user_delete.go:102`, impl at `:400`) — `DELETE FROM reaction WHERE creator_id = ?`. This removes the deleted user's own reactions on *other* people's memos.

Both statements run inside the same transaction opened in `DeleteUser` (`store/db/sqlite/user_delete.go:29-53`), so reaction cleanup is atomic with the user row deletion. The same logic is duplicated per driver: `store/db/postgres/user_delete.go:96,102,380,400` and `store/db/mysql/user_delete.go:96,102,417,437`. Entry point is `store/user.go:171` → `store/driver.go:48`, called from `server/router/api/v1/user_service.go:414` and `server/router/api/v1/auth_service_sso.go:77`.

## Why it is not a DB rule

The `reaction` table has **no foreign key at all** — not on `creator_id`, not on `content_id`:

- `store/migration/sqlite/LATEST.sql:92-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98` — only `UNIQUE(creator_id, content_id, reaction_type)`.
- Original creation in `store/migration/{sqlite,postgres,mysql}/0.20/00__reaction.sql` — same, no FK.

A cascade would not be possible for `content_id` anyway: it stores the resource name string `"memos/<uid>"` (`store/db/sqlite/user_delete.go:515`), not an integer memo ID. Grepping `FOREIGN KEY|ON DELETE|REFERENCES` across `store/migration/` shows cascades exist for other tables (e.g. `memo_share` → `memo` in `store/migration/sqlite/0.27/04__memo_share.sql:11`, and the old `store/migration/sqlite/0.5/00__regenerate_foreign_keys.sql` user cascades) but never for `reaction`.

## Test coverage confirming it

- `server/router/api/v1/test/user_service_delete_test.go:287-298` — after deleting the user, reactions on their own memo and on their comment are empty, while a peer's reaction on a foreign memo survives.
- `store/test/user_delete_test.go:217-220` — same expectation at store level.
- `server/router/api/v1/test/user_service_delete_test.go:429-431` — with the `before_commit` failpoint (`store/user_delete.go:14`), the reaction is still present, confirming the deletes are transactional rather than driven by an independent DB rule.
