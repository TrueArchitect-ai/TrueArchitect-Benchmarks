**Premise correction:** There is no Redis in this repository, and no external cache service of any kind. A case-insensitive search for "redis" across the entire tree (Go, JS/TS, JSON, YAML, Markdown, Docker files) returns zero hits, and `go.mod` contains no Redis client dependency. This is Memos — a single-binary, self-hosted app whose design goal is "Single Go binary, ~20MB Docker image" (`README.md`) — so there is no connection string, host/port, or pool config to point at.

**Actual mechanism:** The cache layer is a **process-local, in-memory cache** implemented from scratch in `store/cache/cache.go`, backed by a `sync.Map` plus an `atomic.Int64` item counter (`store/cache/cache.go:66-73`). It is not shared across processes — each Memos instance has its own copy.

Configuration lives in `store/store.go:38-61`, in `store.New()`. Rather than a connection, what's "configured" is a `cache.Config` literal applied identically to three separate cache instances:

```go
cacheConfig := cache.Config{
    DefaultTTL:      10 * time.Minute,
    CleanupInterval: 5 * time.Minute,
    MaxItems:        1000,
    OnEviction:      nil,
}
```

The three caches are fields on `Store` (`store/store.go:26-29`): `instanceSettingCache`, `userCache`, and `userSettingCache`. The same values are duplicated in `cache.DefaultConfig()` at `store/cache/cache.go:57-64`.

**TTL for user entries: 10 minutes.** Every write to `userCache` goes through `Set()` (`store/user.go:98`, `:122`, `:132`, `:143`, `:167`), and `Set` delegates to `SetWithTTL` using `c.config.DefaultTTL` (`store/cache/cache.go:93-95`). There are no `SetWithTTL` callers anywhere outside the cache package itself, so users get no custom TTL — they inherit the 10-minute default, with the expiration stamped at write time as `time.Now().Add(ttl)` (`store/cache/cache.go:112`).

Two details worth knowing about how that TTL actually behaves:

- **Expiry is lazy plus swept.** `Get` checks `time.Now().After(itm.expiration)` and evicts on read (`store/cache/cache.go:135-144`); a background `cleanupLoop` goroutine sweeps expired entries every 5 minutes (`store/cache/cache.go:200-250`). So an entry can outlive its TTL in memory but is never *served* past it.
- **TTL is not the only eviction path.** At 1000 items the cache drops ~20% of `MaxItems` via `cleanupOldest()` (`store/cache/cache.go:253-313`), so user entries can be evicted well before 10 minutes on a busy instance. Explicit invalidation on delete happens in `deleteUserCache` (`store/user_delete.go:39-47`).

Also note the read path is narrower than the write path: `GetUser` only consults the cache when looking up by ID (`store/user.go:149-156`) — lookups by username or other fields always hit the database. Cache keys are just the stringified user ID (`store/user.go:88-90`); user *settings* are cached separately under `"<userID>-<key>"` (`store/cache.go:7-9`), also at the same 10-minute default.
