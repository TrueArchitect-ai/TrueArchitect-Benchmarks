**Premise correction: there is no per-user API rate-limiting middleware in this repository.** No middleware, interceptor, or handler enforces a per-user (or per-IP) request-rate limit, so there are no request limits to report.

**What's actually registered**

- Echo-level middleware — `server/server.go:51-52`: only `middleware.Recover()` and `newCORSMiddleware(profile)`.
- Connect RPC interceptors — `server/router/api/v1/v1.go:133-138`: `MetadataInterceptor`, `LoggingInterceptor`, `RecoveryInterceptor`, `AuthInterceptor` (all defined in `server/router/api/v1/connect_interceptors.go`). None does rate limiting.
- No rate-limiter dependency is used. `golang.org/x/time` appears in `go.mod:151` only as an indirect dependency, and there are no references to `x/time/rate`, tollbooth, or any limiter package in the Go source.

**Nearby limits that are sometimes mistaken for rate limiting** (none are per-user, and none are time-based):

- Request **size** cap, not rate: `maxAPIRequestBytes = 256 << 20` (256 MiB) at `server/router/api/v1/v1.go:20`, applied via `http.MaxBytesHandler` to the gRPC-gateway routes and Connect routes (`server/router/api/v1/v1.go:126,144`) and as `connect.WithReadMaxBytes` (`v1.go:141`).
- Global **concurrency** semaphores, process-wide and shared by all users: `thumbnailSemaphore = semaphore.NewWeighted(3)` and `imageProcessingSemaphore = semaphore.NewWeighted(2)` (`server/router/api/v1/v1.go:59-60`). The image one is acquired in `attachment_service_image.go:68-75` and returns `ResourceExhausted "too many image processing requests"` on failure (`server/router/api/v1/attachment_service.go:160`) — that 429-ish error is a concurrency rejection, not a rate limit.

The only mentions of rate limiting in the repo are aspirational docs, not code: `internal/email/doc.go:86` ("Rate limit email sending to prevent abuse", in a future-work list) and `internal/email/README.md:286-295` (an "Implement Rate Limiting" example sketch).
