**Where the URL comes from:** the API's user converter rewrites a base64 avatar into a URL — `convertUserFromStore` → `fmt.Sprintf("/file/%s/avatar", userpb.Name)` where `Name` is `users/{username}` (`server/router/api/v1/user_service_converters.go:31-39`, `BuildUserName` at `server/router/api/v1/user_resource_name.go:13`). The browser renders it as an `<img src>` in `web/src/components/UserAvatar.tsx:14`.

Notes worth flagging:

- **The stored data is the DB row, not a file.** Avatars live inline in the `user.avatar_url` column as a base64 data URI — there's no attachment/S3/local-disk hop, unlike `serveAttachmentFile`. `parseDataURI` decodes it in-process and the MIME type is checked against `avatarAllowedTypes` (`fileserver.go:73-81`) before serving.
- **A cache sits in front of the driver.** `Store.GetUser` only short-circuits on the ID cache (`store/user.go:149-156`); a username lookup like this one always falls through to `ListUsers` → driver → SQL, then populates `userCache` (`store/store.go:28`).
- **Authorization for "another user's" avatar is instance-wide, not per-user.** The handler only checks that *someone* is authenticated when `AllowAnonymous()` is false (`fileserver.go:171-179`); any logged-in user may fetch any other user's avatar by username. There's no per-user access check, in contrast to `checkAttachmentPermission`. That appears intentional (avatars are public profile data), but it's the one place the trace differs from what "another user's" might imply.

The route is mounted directly on the Echo server at `server/server.go:81-82`.
