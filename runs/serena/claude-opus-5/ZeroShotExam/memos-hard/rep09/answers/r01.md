**Premise correction:** There is no Redis anywhere in this repository — no `redis` dependency in `go.mod`/`go.sum`, no connection string, no config option, no mention in `docs/` or the web app. The cache layer is a hand-rolled, in-process, in-memory cache. Nothing is shared between server instances, and nothing survives a restart.

**Actual mechanism:**

- **Implementation:** `store/cache/cache.go` — a `Cache` struct backed by a `sync.Map` plus an `atomic.Int64` item counter, with a background `cleanupLoop()` goroutine on a ticker and size-based eviction (`cleanupOldest`, drops ~20% of `MaxItems` when over the limit). It satisfies a local `Interface` (`Set`, `SetWithTTL`, `Get`, `Delete`, `Clear`, `Size`, `Close`).

- **"Connection" configuration:** there isn't one — the caches are constructed in `store.New()` at `store/store.go:37-60`. Three separate instances are created from one shared `cache.Config`: `instanceSettingCache`, `userCache`, and `userSettingCache` (`store/store.go:26-29`, `51-53`). They're torn down in `Store.Close()` (`store/store.go:71-77`).

- **TTL for user entries:** **10 minutes**, from the `DefaultTTL` in the config literal at `store/store.go:40-45` (`DefaultTTL: 10 * time.Minute`, `CleanupInterval: 5 * time.Minute`, `MaxItems: 1000`). `store/cache/cache.go`'s `DefaultConfig()` uses the same values, but the store doesn't call it — it builds its own identical config inline. There is no user-specific TTL override: every user write path uses `Set` (`store/user.go:98, 122, 132, 143, 167`), which delegates to `SetWithTTL` with the default; `SetWithTTL` is never called explicitly outside the cache package and its tests.

- **Key and invalidation:** the key is just the decimal user ID (`userCacheKey` at `store/user.go:88-90`). `GetUser` only hits the cache when `find.ID` is set (`store/user.go:148-156`); lookups by username/email always go to the driver. Explicit invalidation happens on delete (`store/user_delete.go:40`). Note the TTL is absolute, not sliding — `Get` does not refresh `expiration`, so an entry expires 10 minutes after its last write regardless of read traffic. Related user-setting keys use a separate `userID-key` format (`store/cache.go`) in the distinct `userSettingCache`.
