**Mechanism: explicit Go code, inside the per-driver `DeleteUser` transaction. There is no DB-level cascade — the `reaction` table has no foreign keys at all.**

## What the Go code does

`store.DeleteUser` (`store/user.go:171`) delegates to the driver, and each driver's `deleteUserTargetsTx` runs *two* reaction deletes before removing the user row:

- `store/db/sqlite/user_delete.go:94` and `:102` → `deleteReactionsByContentIDsTx` (`:381`, `DELETE FROM reaction WHERE content_id IN (...)`) and `deleteReactionsByCreatorTx` (`:400`, `DELETE FROM reaction WHERE creator_id = ?`)
- `store/db/postgres/user_delete.go:96`, `:102`, with the implementations at `:380` and `:400`
- `store/db/mysql/user_delete.go:96`, `:102`, with the implementations at `:417` and `:437`

The two passes cover both directions:
- **by creator** — reactions the deleted user left on anyone's content.
- **by content_id** — reactions *anyone* left on the deleted user's memos. The content IDs come from `memoContentIDsFromRefs` (`store/db/sqlite/user_delete.go`, near the bottom), which builds `"memos/" + memo.UID` over the recursive memo tree from `listDeleteUserMemoTreeRecursive` — so comments descending from the user's memos are included too.

All of this happens inside one `BeginTx`/`Commit` (`store/db/sqlite/user_delete.go:29-56`), so a failure rolls the reactions back with everything else.

## What the schema does *not* do

`reaction` is declared with no `FOREIGN KEY` clause in any dialect — `store/migration/sqlite/LATEST.sql:91-99`, `store/migration/postgres/LATEST.sql:91-98`, `store/migration/mysql/LATEST.sql:91-98`. The only `ON DELETE CASCADE` in the whole schema set is `memo_share.memo_id → memo(id)` (`store/migration/sqlite/LATEST.sql:109`, and the pg/mysql equivalents at `:108`). The `0.20`/`0.23` reaction migrations only create the table and rewrite `reaction_type` values; none add constraints.

Separately, SQLite opens with FK enforcement off entirely — `_pragma=foreign_keys(0)` at `store/db/sqlite/sqlite.go:53` — so even a declared FK wouldn't cascade there.

## Tests that pin this behavior

- `store/test/user_delete_test.go:97-112, 217-220` — reactions by the deleted user are gone; a peer's reaction on a *peer's* memo survives.
- `server/router/api/v1/test/user_service_delete_test.go:287-298` — reactions on the user's own memo and on their comment are empty afterward, while a peer's reaction on a foreign memo remains.
- `server/router/api/v1/test/user_service_delete_test.go:366-431` — with the `DeleteUserFailpointBeforeCommit` failpoint, the reaction is still present after rollback, confirming the deletes are transactional Go statements rather than an independent DB rule.
