Memo visibility is **not** enforced in one central place — there are several independent, duplicated enforcement points across the Connect/gRPC API, the plain-HTTP surfaces, the SSE fan-out, and the notification paths. The store layer only applies whatever filter the caller passes (`FindMemo.VisibilityList` / `FindMemoRelation.MemoFilter` — `store/memo.go:69`, `store/db/sqlite/memo.go:96`), so every caller must enforce for itself.

Single-memo read gate (API v1) — `server/router/api/v1/memo_service.go:39` (`checkMemoReadAccess`, called from `GetMemo` at :356 and for the parent memo at :367)
List-memos visibility scoping (API v1) — `server/router/api/v1/memo_service.go:218-227`
Comments: parent-memo gate + per-comment filter — `server/router/api/v1/memo_service_comments.go:41` (`CreateMemoComment`), `:148` and `:155-161` (`ListMemoComments`)
Memo relations filter — `server/router/api/v1/memo_relation_service.go:107-112` and `server/router/api/v1/memo_service_converter.go:181-186` (`batchConvertMemoRelations`)
Memo attachments listing — `server/router/api/v1/memo_attachment_service.go:213-225`
Attachment metadata/get (API v1) — `server/router/api/v1/attachment_service.go:422-453` (`checkAttachmentAccess`, inherits the linked memo's visibility)
Reactions (list + upsert) — `server/router/api/v1/reaction_service.go:29-41` and `:82-85`
User stats aggregation — `server/router/api/v1/user_service_stats.go:83-92` (`ListAllUserStats`) and `:217-221` (`GetUserStats`)
Share-token bypass path — `server/router/api/v1/memo_share_service.go` (`GetMemoByShare` deliberately skips `checkMemoReadAccess`; the token + expiry is the gate, and creator/admin-only checks guard create/list/delete)
SSE event fan-out filter — `server/router/api/v1/sse_hub.go:134-143` (`SSEClient.canReceive`), fed by `server/router/api/v1/sse_event_helpers.go:29-37`
Attachment blob file server (raw `/file/...` HTTP, own auth stack) — `server/router/fileserver/fileserver.go:650-703` (`checkAttachmentPermission`, incl. `share_token` fallback at :683-690)
RSS feeds — `server/router/rss/rss.go:90` and `:141` (public-only)
Sitemap — `server/router/frontend/frontend.go:150` (public-only)
In-app notification rendering — `server/router/api/v1/user_service_notifications.go:302` (`canViewerAccessMemo`, applied at :337, :342, :370, :385)
Mention notification dispatch — `server/router/api/v1/memo_mention_helpers.go:56-72` (`canUserAccessMentionContext`)
Email notification dispatch — `server/notification/email.go:306` (a second, separate copy of `canViewerAccessMemo`, applied at :155 and :187)

The MCP surface (`server/router/mcp/`) is not a distinct site — it proxies the OpenAPI/HTTP API and inherits the API v1 checks.

Two things worth flagging: `canViewerAccessMemo` exists twice with slightly different admin checks (`isSuperUser` in `user_service_notifications.go:305` vs. a direct `RoleAdmin` comparison in `email.go:309`), and the inline `Public → user != nil → Private && !creator && !superuser` pattern is copy-pasted verbatim in at least four API files rather than routed through `checkMemoReadAccess`.
