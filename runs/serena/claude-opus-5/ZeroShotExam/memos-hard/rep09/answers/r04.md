**Premise correction:** Neither. The repo has no message broker at all — there is no NATS, RabbitMQ/AMQP, Kafka, or Redis dependency anywhere in `go.mod`/`go.sum` (a grep for `nats|amqp|rabbit|kafka|asynq|redis` across the module files returns nothing), and no broker service in the deployment docs. Memos ships as a single Go binary, so webhook delivery is entirely in-process.

**Actual mechanism** — a buffered Go channel with a fixed worker pool, all in `internal/webhook/webhook.go`:

- **"Queue" declaration:** `internal/webhook/webhook.go:39` — `asyncPostQueue = make(chan *WebhookRequestPayload, 128)`, a package-level buffered channel holding 128 pending payloads.
- **Workers:** `internal/webhook/webhook.go:42-55` — a package `init()` spawns exactly 4 goroutines, each ranging over `asyncPostQueue` and calling `Post(payload)`. Failures are logged with `slog.Warn` only; there is no retry or dead-letter path.
- **Producer:** `PostAsync` at `internal/webhook/webhook.go:184-196` does a non-blocking `select` send. If the buffer is full, the payload is **dropped** with a warning ("Dropped webhook dispatch because the async queue is full") — no backpressure, no persistence, so anything in flight is lost on process restart.
- **Delivery itself:** `Post` at `internal/webhook/webhook.go:120` does a plain HTTP POST via `safeClient`, a shared `http.Client` with a 30s timeout and an SSRF-guarding `DialContext` (`safeDialContext`, line 59) that rejects reserved/private IPs. Optional Standard Webhooks HMAC-SHA256 signing adds `webhook-id`/`webhook-timestamp`/`webhook-signature` headers (lines 133-150).

Callers are the API layer, e.g. `server/router/api/v1/memo_service_webhooks.go:43` and `:71`, which fetch the user's webhooks from the store and call `webhook.PostAsync` per hook.
