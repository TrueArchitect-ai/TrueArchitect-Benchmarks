**Tables affected: `memo`, `memo_relation`, `attachment` — plus `memo_share` on Postgres/MySQL only (FK cascade).**

**Direct path** — `store.DeleteMemo` (`store/memo.go:140-159`) does explicit cascade code before touching the memo row:

1. `memo_relation` — two deletes, one where the memo is the source (`MemoID`) and one where it's the target (`RelatedMemoID`) (`store/memo.go:142-147`; SQL at `store/db/sqlite/memo_relation.go:149`).
2. `attachment` — lists attachments with `MemoID` and deletes each via `store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying blob/local file (`store/attachment.go:132-148`) before the row delete (`store/db/sqlite/attachment.go:212`).
3. `memo` — the row itself: `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237-248`).

**API layer** — `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-593`) additionally deletes comment memos first: it lists `memo_relation` rows of type `comment` pointing at this memo and calls `store.DeleteMemo` on each (lines 567-577), so the three tables above are hit again per comment.

**Cascade by FK** — `memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). This fires on Postgres/MySQL, but **not on SQLite**, where the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`) — so share rows are orphaned there.

**Not affected:** `reaction`. `DeleteMemo` reads reactions only to build the webhook payload (`server/router/api/v1/memo_service.go:545-550`); nothing deletes them, and `reaction.content_id` is a plain TEXT column with no FK (`store/migration/sqlite/LATEST.sql:92-99`), so reactions on a deleted memo are left orphaned on all three backends.
