**Tables affected: `memo`, `memo_relation`, `attachment`, plus `memo_share` (DB-level FK cascade — Postgres/MySQL only).**

**Path 1 — API handler** (`server/router/api/v1/memo_service.go:518-593`):
- Lists comment memos via `memo_relation` (`RelatedMemoID` + type `COMMENT`) and calls `store.DeleteMemo` on each (`memo_service.go:567-577`), then on the memo itself (`memo_service.go:580`).
- Reactions and attachments are read at `memo_service.go:545-557`, but only to build the webhook payload — nothing deletes them there.

**Path 2 — `store.DeleteMemo`** (`store/memo.go:140-159`), for each memo (comments and parent):
1. `memo_relation` — two deletes, one by `memo_id` and one by `related_memo_id` (`store/memo.go:142-147`).
2. `attachment` — lists attachments with that `memo_id` and calls `store.DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the underlying file/object from storage before the row delete (`store/attachment.go:132-149`).
3. `memo` — the driver's plain `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`).

**`memo_share`** is affected only by the schema-level constraint `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`) — there is no explicit Go cleanup. Note that on SQLite this cascade does **not** fire: the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so share rows are left orphaned on that driver.

**Not touched:** `reaction`. The `reaction` table has no FK to `memo` (`store/migration/sqlite/LATEST.sql:92-99` — it links by a text `content_id`), and no code in the delete path removes those rows, so reactions on a deleted memo are orphaned on every driver.
