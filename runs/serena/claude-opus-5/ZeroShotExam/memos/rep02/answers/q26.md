**Tables affected: `memo`, `memo_relation`, `attachment`, `memo_share`** (the last only on Postgres/MySQL — see caveat).

**Call chain**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):
1. Lists comment memos via `memo_relation` (type `COMMENT`) and calls `Store.DeleteMemo` for each (`memo_service.go:567-577`) — so every table below is hit for each comment memo too.
2. Calls `Store.DeleteMemo` for the memo itself (`memo_service.go:580`).

`Store.DeleteMemo` (`store/memo.go:140-159`) — the explicit cascade code:
- **`memo_relation`** — two `DeleteMemoRelation` calls, one on `memo_id`, one on `related_memo_id` (`store/memo.go:142-147`; drivers e.g. `store/db/sqlite/memo_relation.go`).
- **`attachment`** — lists attachments with `MemoID` and calls `DeleteAttachment` per row (`store/memo.go:149-157` → `store/attachment.go:132-148`, which also deletes the local/S3 blob).
- **`memo`** — final `driver.DeleteMemo` → `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, and the postgres/mysql equivalents).

**`memo_share`** — no Go code deletes it; it relies on the schema FK `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). Note that the SQLite driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does **not** fire and share rows are left orphaned.

**Not affected:** `reaction`. It is only read to build the webhook payload (`memo_service.go:545-550`); its `content_id` is a string name with no FK and no cleanup call, so reaction rows survive the delete.
