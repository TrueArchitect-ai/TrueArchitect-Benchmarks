**Background workers the server actually starts**

- **s3presign runner (`server/runner/s3presign/runner.go`)** — the only registered background runner. Started in `Server.startBackgroundRunners` (`server/server.go:154-176`): one synchronous `RunOnce(ctx)` at boot, then a goroutine running `Run(s3Context)` driven by a `time.NewTicker(12h)` (`runnerInterval`, `server/runner/s3presign/runner.go:28-42`). Each tick re-presigns S3 attachment URLs whose `LastPresignedTime` is older than 4 days. Lifecycle: its own cancelable context stored in `backgroundRunnerCancels`, tracked by `backgroundRunnerWG`, cancelled in `Shutdown` (`server/server.go:141-147`, `178-207`).
- **HTTP serve goroutine (`server/server.go:122-128`)** — event-driven, not scheduled; `http.Server.Serve(listener)`, stopped by `shutdownHTTPServer`.
- **3× store cache janitors (`store/store.go:40-53` → `store/cache/cache.go:75-85, 199-214`)** — started implicitly by `cache.New` for `instanceSettingCache`, `userCache`, `userSettingCache`; each runs `cleanupLoop` on a `time.NewTicker(CleanupInterval = 5m)`. Stopped by `Store.Close()` (`store/store.go:72-79`), which `Shutdown` calls. These aren't part of the runner framework — they're a side effect of constructing the store in `cmd/memos/main.go:64`.
- **Signal-watch goroutine (`cmd/memos/main.go:99-103`)** — trigger is SIGINT/SIGTERM, not a timer; calls `s.Shutdown`.

Per-request/per-connection goroutines, not runners: SSE heartbeat `time.NewTicker(sseHeartbeatInterval)` per connection (`server/router/api/v1/sse_handler.go:64`), async webhook dispatch (`internal/webhook/webhook.go:44`), async email send (`internal/email/email.go:18`), async PAT last-used write (`server/auth/authenticator.go:178-184`).

**Unused scheduling infrastructure**

- **`internal/scheduler/` is dead code as far as the server is concerned.** It's a full cron scheduler (5/6-field cron parser, timezone support, middleware chain, graceful shutdown — `internal/scheduler/scheduler.go`, `parser.go`, `job.go`, `middleware.go`, `README.md`), but grepping for `usememos/memos/internal/scheduler` yields imports only from its own tests (`internal/scheduler/example_test.go`, `integration_test.go`). No production code registers a job or calls `scheduler.New`. The one runner that exists uses a raw `time.Ticker` instead.
- **`server/runner/memopayload/runner.go` is registered nowhere.** Its `Runner`/`RunOnce` (a batched rebuild of all memo payloads) is never constructed by the server; only the package-level helper `memopayload.RebuildMemoPayload` is used, inline on memo create/update (`server/router/api/v1/memo_service.go:108`, `:447`). So `server/runner/` contains two runners but only `s3presign` is wired up.
