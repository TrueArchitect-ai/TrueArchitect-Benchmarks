`store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) deletes these records before the memo row:

1. **Memo relations where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **Memo relations where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachments linked to the memo** — listed via `ListAttachments(FindAttachment{MemoID: &delete.ID})` and removed one by one with `DeleteAttachment` (`store/memo.go:148-157`), which also deletes the underlying stored file/blob via `DeleteAttachmentStorage` (`store/attachment.go:132-149`)

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`).

Two things the store layer does *not* handle, done by the API handler in `server/router/api/v1/memo_service.go:518-593` instead:
- **Comment memos** — child memos found via `MemoRelationComment` relations are deleted first by recursively calling `store.DeleteMemo` (lines 567-577).
- **Reactions** — these are listed at line 545 for the webhook payload; the store's `DeleteMemo` does not remove reaction rows.
