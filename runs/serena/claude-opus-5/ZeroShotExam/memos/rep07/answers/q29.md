**`web/src/connect.ts`; JWT access token (in-memory + localStorage, `Authorization: Bearer`) + JWT refresh token (httpOnly `memos_refresh` cookie), plus Personal Access Tokens for programmatic clients; `server/auth`**

How it fits together:

**Interceptor — `web/src/connect.ts:148` (`authInterceptor`)**
- Attached to the Connect-Web transport (`web/src/connect.ts:172`) that backs every service client (`memoServiceClient`, `userServiceClient`, etc.), so all frontend RPCs go through it.
- On each request it calls `getRequestToken()` and sets `Authorization: Bearer <token>`.
- Preflight: if the token is expired/near expiry (30 s buffer, `REQUEST_TOKEN_EXPIRY_BUFFER_MS`) it refreshes first — important for public endpoints like `ListMemos` that would otherwise silently return guest-scoped data.
- Reactive: on a `Code.Unauthenticated` response it refreshes once, retries with an `X-Retry: true` header guard against loops, and calls `redirectOnAuthFailure()` if the refresh fails.
- Refresh calls go through a *separate* transport with no interceptors (`web/src/connect.ts:64`) to avoid recursion, and are deduplicated by `tokenRefreshManager` so concurrent callers share one in-flight refresh.

**Token storage — `web/src/auth-state.ts`**
- Access token kept in memory and mirrored to `localStorage` (`memos_access_token` / `memos_token_expires_at`); a `BroadcastChannel` (`memos_token_sync`) shares freshly refreshed tokens across tabs.
- Refresh token is never touched by JS — it's an httpOnly cookie, which is why the transports use `credentials: "include"` (`web/src/connect.ts:57`).
- `web/src/hooks/useTokenRefreshOnFocus.ts` proactively refreshes on tab visibility with a longer 2-minute buffer.

**Backend validation — `server/auth`**
- `server/auth/token.go` defines the scheme: access tokens ~15 min (`AccessTokenAudienceName`), refresh tokens 30 days (`RefreshTokenCookieName = "memos_refresh"`), PATs prefixed `memos_pat_`, HMAC-signed with `KeyID = "v1"`.
- `server/auth/authenticator.go` — `Authenticator.AuthenticateByAccessTokenV2` validates access tokens statelessly by signature; refresh tokens are additionally checked against the DB for revocation.
- `server/auth/extract.go` pulls the bearer token from the header and the refresh token from the cookie.
- Wired in at `server/router/api/v1/connect_interceptors.go:222` and `server/router/api/v1/v1.go:78` via the `Authorizer` (`server/router/api/v1/authz.go:36`), and reused by `server/router/fileserver/fileserver.go:115` and `server/router/api/v1/sse_handler.go:26`.
