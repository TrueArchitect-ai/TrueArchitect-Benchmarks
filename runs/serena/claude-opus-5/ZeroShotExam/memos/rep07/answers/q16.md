`store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) deletes the following before issuing the `DELETE FROM memo` statement:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **`attachment` rows linked to the memo** — listed via `ListAttachments(FindAttachment{MemoID: &delete.ID})` and removed one by one with `Store.DeleteAttachment` (`store/memo.go:148-157`), which also deletes the underlying stored blob/local file first (`store/attachment.go:132-148`, `deleteAttachmentStorageImpl` at `store/attachment.go:202`).

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`; e.g. the SQLite driver at `store/db/sqlite/memo.go:237`).

Note on the surrounding API layer: `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518-582`) additionally deletes the memo's comment memos beforehand — for each comment relation it calls `Store.DeleteMemo` recursively (`memo_service.go:567-577`) — but that comment cleanup lives in the service layer, not in `store.DeleteMemo`. Reactions are only listed there for the webhook payload, not deleted.
