**Tables written to when `DeleteMemo` runs: `memo`, `memo_relation`, `attachment`, `memo_share`** (the last only via DB-level FK cascade, with a caveat below).

**Call chain**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):
- Reads memo/reactions/attachments/relations for the webhook payload (read-only).
- Lists comment relations (`memo_relation`, type `COMMENT`) and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`), then for the memo itself (`memo_service.go:580`) — so all of the below happen once per comment memo plus once for the parent.

`Store.DeleteMemo` (`store/memo.go:140-159`) — explicit cascade code:
1. `memo_relation`: two deletes, one by `memo_id`, one by `related_memo_id` (`store/memo.go:142-147`).
2. `attachment`: lists attachments with `MemoID` and calls `Store.DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the underlying file/object storage before the row delete (`store/attachment.go:132-148`).
3. `memo`: driver `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, and the postgres/mysql equivalents).

**Cascade by schema, not code**

`memo_share` has `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). Worth flagging: the SQLite driver opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and `memo_share` rows are left orphaned — there is no explicit `DeleteMemoShare` call in the delete path.

**Not touched:** `reaction`. Reactions are listed for the webhook payload but never deleted; `reaction.content_id` is a plain text column with no FK (`store/migration/sqlite/LATEST.sql:92-100`), so they orphan too.
