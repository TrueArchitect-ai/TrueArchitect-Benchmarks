**`web/src/connect.ts`; short-lived JWT access token (localStorage, `Authorization: Bearer`) + long-lived refresh token (HttpOnly cookie `memos_refresh`), plus PATs supported on the same header; `server/auth`**

**Frontend interceptor — `web/src/connect.ts:150`**
- `authInterceptor` is attached to the ConnectRPC transport (`createConnectTransport`, `web/src/connect.ts:174`) that backs every service client (memo, user, auth, attachment, etc.). All RPCs go through it.
- On each request it calls `getRequestToken()` (`web/src/connect.ts:120`) and sets `Authorization: Bearer <token>`. If the token is within `REQUEST_TOKEN_EXPIRY_BUFFER_MS` (30 s) of expiry it refreshes preemptively.
- On a `Code.Unauthenticated` response it refreshes once, marks the retry with an `X-Retry: true` header to prevent loops, and replays; if refresh fails it calls `redirectOnAuthFailure()` (`web/src/utils/auth-redirect.ts`).
- Refresh uses a *separate* transport with no interceptors (`web/src/connect.ts:65`) to avoid recursion, and `fetch` with `credentials: "include"` so the refresh cookie is sent. Concurrent refreshes are deduped by `tokenRefreshManager` (`web/src/connect.ts:30`).

**Tokens managed — `web/src/auth-state.ts`**
- *Access token*: JWT, 15 min lifetime, kept in memory + `localStorage` (`memos_access_token` / `memos_token_expires_at`), broadcast to other tabs via a `BroadcastChannel` (`memos_token_sync`).
- *Refresh token*: never touched by JS — server-set HttpOnly cookie `memos_refresh`, 30 days, exchanged via `AuthService.refreshToken` (`web/src/connect.ts:73`). Proactive refresh on tab focus lives in `web/src/hooks/useTokenRefreshOnFocus.ts`.
- *Personal Access Tokens*: same `Authorization: Bearer` path for programmatic clients (prefix `memos_pat_`).

**Backend validation — `server/auth/`**
- `server/auth/token.go` defines the token constants/claims (`AccessTokenDuration` 15 min, `RefreshTokenDuration` 30 days, audiences `user.access-token` / `user.refresh-token`, cookie `memos_refresh`, PAT prefix + SHA-256 hashing).
- `server/auth/authenticator.go` (`Authenticator.AuthenticateByAccessTokenV2`, `AuthenticateByRefreshToken`, PAT lookup) does the actual verification; `server/auth/extract.go` pulls the bearer token from the header and the refresh token from the cookie.
- It's wired into the request path via `Authorizer` in `server/router/api/v1/authz.go`, used by the Connect interceptor (`server/router/api/v1/connect_interceptors.go`) and also by `server/router/fileserver/fileserver.go` and `server/router/api/v1/sse_handler.go`.
