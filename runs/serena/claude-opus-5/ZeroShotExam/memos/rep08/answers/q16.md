`Store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) removes, in order, before issuing the `DELETE FROM memo`:

1. **Memo relation records where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`).
2. **Memo relation records where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`).
3. **Attachments linked to the memo** — listed via `ListAttachments{MemoID: &delete.ID}` and deleted one by one with `DeleteAttachment` (`store/memo.go:149-157`), which also deletes the underlying stored blob/local file before the attachment row (`store/attachment.go:132-148`).

Only then does it call `s.driver.DeleteMemo` to delete the memo row itself (`store/memo.go:158`; e.g. the SQLite driver at `store/db/sqlite/memo.go:237`).

Two related points on the API path, which are outside `Store.DeleteMemo` itself:

- The API handler `APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518+`) first deletes each **comment memo** (relations of type `MemoRelationComment` pointing at this memo) by recursively calling `Store.DeleteMemo` on them, so those comments' own relations and attachments get cleaned up too.
- **Reactions and memo shares** are not deleted by the store layer explicitly; `memo_share` rows go away via the `ON DELETE CASCADE` foreign key on `memo_id` (`store/migration/sqlite/LATEST.sql:109`), and reactions are keyed by content name rather than a memo FK.
