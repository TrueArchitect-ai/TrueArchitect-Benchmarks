**Deletion path**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):
- Lists comment relations (`FindMemoRelation{RelatedMemoID, Type: comment}`) and calls `store.DeleteMemo` for each comment memo (`memo_service.go:567-577`), then for the memo itself (`:580`). So the whole set below is repeated per comment memo.
- Reactions and attachments read at `:545-557` are only used to build the webhook payload — no delete.

`Store.DeleteMemo` (`store/memo.go:140-159`) is where the explicit cascade lives:
1. `memo_relation` — two `DeleteMemoRelation` calls, by `MemoID` and by `RelatedMemoID` (`store/memo.go:142-147`; SQL in `store/db/sqlite/memo_relation.go`, `postgres/`, `mysql/`).
2. `attachment` — lists attachments for the memo and calls `DeleteAttachment` per row (`store/memo.go:149-157`); `Store.DeleteAttachment` (`store/attachment.go:132-149`) removes the blob/file from storage, then `DELETE FROM attachment` (`store/db/sqlite/attachment.go:211`).
3. `memo` — the driver's `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `postgres/memo.go:244`, `mysql/memo.go:259`).

**`memo_share`** is deleted only by the schema FK `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`) — there is no Go code deleting it. Note the SQLite driver opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and `memo_share` rows are left orphaned.

**Not affected:** `reaction` — it keys memos by a string `content_id` with no FK (`store/migration/sqlite/LATEST.sql:92-99`) and nothing in the delete path removes reaction rows, so they are orphaned on every backend.
