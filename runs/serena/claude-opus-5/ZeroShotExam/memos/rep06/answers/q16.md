`store.DeleteMemo` (`/bench/repo/store/memo.go:140-159`) deletes these before issuing the memo row delete:

1. **`memo_relation` rows where the memo is the source** — `DeleteMemoRelation{MemoID: &delete.ID}` (`store/memo.go:142`)
2. **`memo_relation` rows where the memo is the target/related memo** — `DeleteMemoRelation{RelatedMemoID: &delete.ID}` (`store/memo.go:145`)
3. **Attachment records linked to the memo** — listed via `ListAttachments{MemoID: &delete.ID}` and removed one-by-one with `s.DeleteAttachment` (`store/memo.go:149-157`). Each of those also deletes the attachment's underlying stored blob (local file or S3 object) before the DB row — `store/attachment.go:132-149`, `deleteAttachmentStorageImpl` at `store/attachment.go:202`.

Only then does it call `s.driver.DeleteMemo` for the memo row itself (`store/memo.go:158`).

Two related notes: comment memos are *not* handled by the store layer — the API service deletes them first by looking up `MemoRelationComment` relations and calling `store.DeleteMemo` on each (`server/router/api/v1/memo_service.go:566-576`). Reactions are read for the webhook payload (`memo_service.go:545`) but are not explicitly deleted in either layer.
