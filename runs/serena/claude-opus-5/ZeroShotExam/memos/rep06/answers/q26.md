**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`** (the last only via a DB-level FK cascade, not code).

**Call path**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):
1. Lists comment relations and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`) — recursive, same table set per comment.
2. Calls `Store.DeleteMemo` for the memo itself (`memo_service.go:579`).

`Store.DeleteMemo` (`store/memo.go:140-159`) does the explicit cascade:
- `memo_relation` — two `DeleteMemoRelation` calls, by `memo_id` and by `related_memo_id` (`store/memo.go:142-147`).
- `attachment` — lists attachments by `MemoID` and deletes each via `Store.DeleteAttachment` (`store/memo.go:149-157`, `store/attachment.go:132`), which also removes the underlying blob/local file (`DeleteAttachmentStorage`).
- `memo` — the row itself, via the driver `DeleteMemo` (e.g. `store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go`, `store/db/mysql/memo.go`).

**`memo_share`** is not touched by any Go code; it's declared with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:108`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). Note that SQLite opens the DB with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so on SQLite that cascade does not fire and share rows are left orphaned; Postgres/MySQL enforce it.

**Not affected:** `reaction`. `DeleteMemo` only *reads* reactions to build the webhook payload (`memo_service.go:545-550`); reaction rows key off `content_id` (the memo resource name string) with no FK, so they survive the delete.
