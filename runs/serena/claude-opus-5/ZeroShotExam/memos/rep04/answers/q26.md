**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`** (the last only on MySQL/Postgres — see caveat).

**Path of execution**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`) does no table writes itself; it reads the memo, reactions, attachments and relations for the webhook payload, then deletes comment memos and the memo itself through `store.DeleteMemo` (`server/router/api/v1/memo_service.go:569-582`).

`Store.DeleteMemo` (`store/memo.go:140-159`) is where the explicit cascade code lives:

1. **`memo_relation`** — two deletes, one for `memo_id = ID` and one for `related_memo_id = ID` (`store/memo.go:142-147`; SQL at `store/db/sqlite/memo_relation.go:149` and the mysql/postgres equivalents).
2. **`attachment`** — lists attachments with `MemoID` and deletes each via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying blob/local file before the row delete (`store/attachment.go:132-148`, SQL at `store/db/sqlite/attachment.go:212`).
3. **`memo`** — the row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`). This runs once per comment memo plus once for the target memo.

**`memo_share`** is affected only by a DB-level foreign key, not by Go code: `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in `store/migration/postgres/LATEST.sql:109`, `store/migration/mysql/LATEST.sql:108`, and `store/migration/sqlite/LATEST.sql:109`. On SQLite the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), so the cascade does **not** fire there and `memo_share` rows are left orphaned.

**Not touched: `reaction`.** `DeleteMemo` reads reactions for the webhook payload (`server/router/api/v1/memo_service.go:545-550`) but never deletes them, and `reaction.content_id` is a plain TEXT column with no FK (`store/migration/sqlite/LATEST.sql:92-99`), so reaction rows for a deleted memo persist.
