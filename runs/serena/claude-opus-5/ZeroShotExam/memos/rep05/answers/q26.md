**Tables affected: `memo`, `memo_relation`, `attachment`, and `memo_share`** (the last only via DB-level FK cascade — see caveat).

**Call path**

`APIV1Service.DeleteMemo` — `server/router/api/v1/memo_service.go:518`:
- Lists comment relations (`store.MemoRelationComment`) and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:569-577`), then for the memo itself (`memo_service.go:580`).

`Store.DeleteMemo` — `store/memo.go:140-159`, the explicit cascade code:
1. `memo_relation` — two deletes, matching the memo as source (`MemoID`) and as target (`RelatedMemoID`) — `store/memo.go:142-147`.
2. `attachment` — lists attachments with `MemoID` and calls `Store.DeleteAttachment` per row (`store/memo.go:149-157`), which also removes the underlying blob/local/S3 object before the row delete (`store/attachment.go:132-149`, `store/db/sqlite/attachment.go:211`).
3. `memo` — the row itself, `DELETE FROM memo WHERE id = ?` (`store/db/sqlite/memo.go:237`, plus the postgres/mysql equivalents).

**`memo_share`**: declared with `FOREIGN KEY (memo_id) REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:99-107`, `store/migration/postgres/LATEST.sql:101-108`, `store/migration/mysql/LATEST.sql:101-109`). So on Postgres/MySQL its rows go away automatically. On SQLite they do **not**: the connection is opened with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), and there is no explicit `memo_share` cleanup in `Store.DeleteMemo` — the only explicit share deletes are the single-share API path (`store/memo_share.go:45`) and user deletion (`store/db/sqlite/user_delete.go:405-411`).

**Not touched**: `reaction`. `DeleteMemo` reads reactions only to build the webhook payload (`memo_service.go:545-550`); reaction rows key off the memo *name* string (`content_id`) with no FK, so they are left orphaned.
