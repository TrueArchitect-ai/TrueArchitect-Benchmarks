**Tables affected: `memo`, `memo_relation`, `attachment` — plus `memo_share` only via a DB-level FK cascade (MySQL/Postgres; not SQLite).**

**Call chain**

`APIV1Service.DeleteMemo` (`server/router/api/v1/memo_service.go:518`):
- Lists comment relations and calls `Store.DeleteMemo` for each comment memo (`memo_service.go:567-577`), then for the memo itself (`memo_service.go:580`). So `memo` rows are deleted for the target memo *and* all of its comment memos.

`Store.DeleteMemo` (`store/memo.go:140-159`) is where the explicit cascade code lives:
- `memo_relation` — deleted twice, once by `MemoID` and once by `RelatedMemoID` (`store/memo.go:142-147`).
- `attachment` — every attachment with `MemoID` is fetched and deleted via `Store.DeleteAttachment` (`store/memo.go:149-157`), which also removes the underlying blob/local file (`store/attachment.go:132-148`) — file storage, not a table.
- `memo` — final `DELETE FROM memo WHERE id = ?` in the driver (`store/db/sqlite/memo.go:237`, `store/db/postgres/memo.go:244`, `store/db/mysql/memo.go:259`). The SQL is a plain single-table delete; no driver-level cascade.

**Cascade caveat — `memo_share`**

`memo_share.memo_id` has `FOREIGN KEY ... REFERENCES memo(id) ON DELETE CASCADE` in all three schemas (`store/migration/sqlite/LATEST.sql:109`, `postgres/LATEST.sql:108`, `mysql/LATEST.sql:108`). There is no Go code deleting shares on memo deletion — `store.DeleteMemoShare` only accepts `ID`/`UID` (`store/memo_share.go:23-26`). On MySQL/Postgres the DB enforces the cascade; on SQLite it does **not**, because the connection opens with `_pragma=foreign_keys(0)` (`store/db/sqlite/sqlite.go:53`), leaving orphaned `memo_share` rows.

**Not affected (orphans left behind)**

- `reaction` — `DeleteMemo` lists reactions only to build the webhook payload (`memo_service.go:545-550`); nothing deletes them, and `reaction.content_id` is a plain text memo name with no FK (`store/migration/sqlite/LATEST.sql:92-99`).
- `inbox` — no cleanup of notifications referencing the deleted memo.
